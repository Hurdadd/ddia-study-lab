ایدهٔ کلیدی فصلChapter thesis

مدل‌های داده شاید مهم‌ترین تیکهٔ نرم‌افزار باشن، چون فقط شکل کد زدن رو تعیین نمی‌کنن؛ شکل فکر کردنمون دربارهٔ مسئله رو هم تعیین می‌کنن. هر برنامه‌ای از چند تا لایهٔ مدل داده ساخته شده:

  1. لایهٔ برنامه: دنیای واقعی (آدم‌ها، شرکت‌ها، پول، سنسورها) رو با شیءها و APIهای خودت مدل می‌کنی.
  2. لایهٔ ذخیره‌سازی: همون ساختارها رو با یه مدل عمومی می‌گی: JSON/XML، جدول رابطه‌ای، یا گره و یال گراف. موضوع این فصل همینه.
  3. لایهٔ موتور ذخیره‌سازی: اون مدل چطور می‌شه بایت رو دیسک/حافظه/شبکه (فصل ۴).
  4. لایهٔ سخت‌افزار: بایت‌ها چطور با جریان برق و نور و مغناطیس نشون داده می‌شن.

هر لایه پیچیدگی لایهٔ زیری رو پشت یه مدل تمیز قایم می‌کنه و همین باعث می‌شه تیم‌های مختلف بتونن با هم کار کنن.

A resume looks like one object in application code. On disk, it might occupy several tables and many pages. Each layer has its own model, so changing what you see on the screen doesn't necessarily change how bytes are stored.

Data models shape how you think about the problem, as well as how you write the code. An application uses several layers:

  1. App layer: represent people, organizations, money and sensors through objects and APIs.
  2. Storage layer: express those structures as JSON/XML, relational tables, or graph nodes and edges. This is the subject of this chapter.
  3. Storage engine layer: turn that model into bytes on disk, in memory and on the network. Chapter 4 covers this layer.
  4. Hardware layer: represent the bytes through electric current, light and magnetism.

Each layer hides some details of the one below. Teams can work with a clear interface without handling every detail of the whole stack.

The examples here are teaching scenarios based on everyday engineering work. They don't describe a particular company's architecture. Their numbers are chosen to make the ideas easier to follow.

زبان کوئری اعلانی (Declarative) در برابر دستوری (Imperative)Declarative vs imperative query languages

زبون اعلانی می‌گه چی می‌خوای؛ زبون دستوری قدم‌به‌قدم رسیدن رو مشخص می‌کنه. تو SQL معمولاً انتخاب روش اجرا رو می‌سپری به موتور دیتابیس — بسپر بهش، بلده.

مثال فنی: SQL نتیجه را می‌خواهد، نه حلقه را

وضعیت اولیه: فرض کن هدف مشتری‌هایین که بیش از سه تا سفارش دارن.

اجرای مرحله‌به‌مرحله: حالا GROUP BY customer_id HAVING COUNT(*) > 3 شرط نتیجه رو می‌گه؛ optimizer می‌تونه نوع اسکن و تجمیع رو انتخاب کنه.

نتیجه و دلیل: پس توی حلقهٔ دستوری ترتیب اجرا رو خودت تعیین می‌کنی؛ اعلانی بودن آزادی انتخاب طرح اجرا رو می‌ده به موتور — بگو چی می‌خوای، نه چطور.

  • اعلانی (مثل SQL و Cypher و SPARQL و Datalog): می‌گی چی می‌خوای — چه الگویی، چه شرطی، چه مرتب‌سازی و جمعی — ولی نمی‌گی «چطور».
  • دستوری (مثل Python و Java): باید الگوریتم و ترتیب کار رو خودت بنویسی — همه‌ش با توئه.
  • سود بزرگ اعلانی: جزئیات موتور کوئری قایم می‌مونه، پس بهینه‌ساز دیتابیس می‌تونه ایندکس و الگوریتم join رو عوض کنه — حتی کوئری رو موازی کنه — بدون اینکه یه خط از کد تو عوض بشه. مفته!
  • Declarative languages, including SQL, Cypher, SPARQL and Datalog, describe what result you want: a pattern, filter, sort order or calculation. You leave the execution steps to the engine.
  • Imperative code, such as Python or Java, spells out the algorithm and the order of the steps.
  • That separation gives the query optimizer room to choose indexes, change join algorithms or run work in parallel without rewriting the query. You describe the result; the engine chooses a plan.

Example: SQL describes the result

Setup: You need customers who have more than three orders.

Walk through it: The condition GROUP BY customer_id HAVING COUNT(*) > 3 states which groups qualify. The optimizer can choose how to scan the data and compute the counts.

What this tells you: An imperative loop specifies the steps. A declarative query leaves the execution plan to the engine. Describe the result clearly.

۱1 مدل رابطه‌ای در برابر مدل سندیRelational vs document model

تو مدل رابطه‌ای داده تو جدول‌ها و رابطهٔ بینشون نگه داشته می‌شه. تو مدل سندی اطلاعات مرتبط می‌تونه بره تو یه سند تودرتو — یه جا، یه تیکه.

مثال فنی: دو نمایش یک سابقهٔ شغلی

وضعیت اولیه: فرض کن مریم با person_id=17 توی شرکت 7 کار کرده.

اجرای مرحله‌به‌مرحله: حالا رابطه‌ای: یه ردیف توی people و یه ردیف توی jobs با کلید خارجی؛ سندی: آرایهٔ jobs داخل سند مریم.

نتیجه و دلیل: پس سند خوندن یه‌جای رزومه رو ساده می‌کنه؛ گزارش همهٔ کارمندهای شرکت ممکنه ایندکس و پردازش متفاوتی بخواد — هر مدل یه جا می‌درخشه.

In 1970, Codd proposed organizing data into relations, represented as tables in SQL, with no inherent row order. Relational databases became widely used by the mid-1980s, including in business applications and analytics.

Network, hierarchical, object and XML databases offered other models. Relational systems also incorporated features for XML, JSON and graphs. In the 2010s, NoSQL drew attention to documents, flexible schemas and scaling out, while NewSQL pursued scale alongside relational guarantees. These approaches give you different options for representing related data.

Example: One job, two representations

Setup: Maryam, with person_id=17, has worked at company 7.

Walk through it: In the relational model, store a row in people and a row in jobs linked by a foreign key. In a document, embed the jobs array inside Maryam's record.

What this tells you: The document makes reading the whole resume straightforward. Reporting on every employee of a company may need a different index or query. Compare both access patterns.

ناهماهنگی شیء-رابطه‌ای (Impedance Mismatch) و ORMObject-relational impedance mismatch and ORMs

ORM یه واسطه‌ست که شیءهای برنامه رو تبدیل می‌کنه به جدول و ردیف. کد زدن رو آسون‌تر می‌کنه، ولی فرق شکل شیء و جدول رو پاک نمی‌کنه — اختلاف سر جاشه.

مثال فنی: N+1 در صفحهٔ رزومه‌ها

وضعیت اولیه: فرض کن ORM اول ۱۰۰ تا متقاضی رو با یه SQL می‌خونه.

اجرای مرحله‌به‌مرحله: حالا دسترسی lazy به person.jobs برای هر متقاضی یه SQL جدا می‌زنه: مجموعاً ۱۰۱ تا کوئری! preload می‌تونه رابطه‌ها رو دسته‌ای بخونه.

نتیجه و دلیل: پس کد کوتاه لزوماً مسیر کم‌هزینه نیست. تعداد query و دادهٔ برگردونده‌شده رو باید دید — ORM راحته، ولی مجانی نیست.

Application code often works with nested objects. A relational database stores rows linked across tables. Translating between those shapes is the object-relational impedance mismatch, a term borrowed from electronics.

An ORM, such as Hibernate or ActiveRecord, handles much of that translation. It saves boilerplate, but the difference between the models still matters:

  • پیچیده‌ان و نمی‌تونن فرق دو تا مدل رو کامل قایم کنن.
  • فقط به درد OLTP می‌خورن؛ مهندس داده هنوز با نمایش رابطه‌ای زیری کار داره، پس طراحی اسکیما مهم می‌مونه.
  • تو سیستم‌های جورواجور (موتور جست‌وجو، گراف، NoSQL) معمولاً پشتیبانی ندارن.
  • اسکیمایی که تولید می‌کنن هم ممکنه حال کاربر مستقیم داده رو بگیره هم کند باشه — دو سر باخت.
  • راحت کوئری کند می‌سازن؛ مثال معروف: درد N+1 — یه کوئری برای N تا نظر، بعد N تا کوئری جدا برای نویسندهٔ هر نظر، در حالی که یه JOIN همون کار رو یه‌جا می‌کرد. کلاسیک!
  • ORMs add complexity and can't hide every difference between objects and tables.
  • Their focus is OLTP application code. Data engineers and analysts still use the underlying relational representation, so schema design matters.
  • Support doesn't necessarily extend to search engines, graph databases and other NoSQL systems.
  • An automatically generated schema can be awkward for people querying the data directly, and its queries can be slow.
  • Watch for the N+1 problem: one query loads N comments, then N more fetch their authors. A JOIN or eager loading can fetch the related data together. Count database round trips, even when the application code looks short.

Setup: An ORM loads 100 applicants with one SQL query.

Walk through it: Lazy access to each applicant's person.jobs runs another query: 101 queries in total. Preloading can fetch the related records in batches.

What this tells you: Short application code doesn't guarantee a cheap database path. Count queries and the data they return.

مدل سندی: رزومه به‌صورت یک درختThe document model: a resume as a tree

یه سند به درد داده‌ای می‌خوره که یه‌جا و تودرتو خونده می‌شه. این سادگی وقتی کم می‌شه که تیکه‌های سند بین خیلی‌ها مشترک باشه — اشتراک، دشمن سادگیه.

مثال فنی: Embedding تا کجا مناسب است؟

وضعیت اولیه: فرض کن رزومه دو تا سابقهٔ شغلی داره و هر دو توی آرایهٔ jobs ذخیره‌ان.

اجرای مرحله‌به‌مرحله: حالا خوندن سند همهٔ رزومه رو میاره؛ اگه نام شرکت توی ۱۰ هزار رزومه کپی شده باشه، تغییر نام یعنی اصلاح همون ۱۰ هزار نسخه.

نتیجه و دلیل: پس بخش‌های مال یه رزومه برای embedding خوبن؛ هویت مشترک شرکت معمولاً مرجع مستقل می‌خواد — کپی ارزونه، اصلاحش گرونه.

Take a resume: one name, several jobs, several education entries and several contact details. That's a nested structure you often read as a whole. You can split it across related tables or keep it together in a document.

  • Shredding (تکه‌تکه کردن): هر تیکه تو یه جدول جدا با کلید خارجی به جدول users — پخش و پلا.
  • Embedding (توکار کردن): همه تو یه سند JSON — یه درخت یک‌به‌چند که دقیقاً همون شکل شیء تو کده.
  • Shredding: put each part in its own table, with foreign keys pointing to users.
  • Embedding: put the parts inside one JSON document. The nested one-to-many tree stays close to the application's object structure.

برگ برندهٔ سند: locality — هرچی برای نشون دادن یه پروفایل لازمه یه‌جاست و یه خوندن کافیه؛ تو مدل رابطه‌ای یا باید چند تا کوئری بزنی یا یه join چندطرفهٔ درهم‌وبرهم — هر دو حال‌گیری. ولی اگه آیتم‌های مرتبط واقعاً «زیاد» باشن (مثلاً هزاران نظر زیر یه پست)، توکار کردن تو سند حال‌به‌هم‌زن می‌شه.

A document offers locality: the fields needed for a profile page sit together, so you can fetch them in one read. With separate relational tables, you'll assemble that tree through several queries or a multi-way join.

Check how large the nested collections can get. A few jobs fit naturally inside a resume. Thousands of comments under a post make embedding much less convenient. Reading one bounded tree and managing an ever-growing collection are different jobs.

نرمال‌سازی در برابر نرمال‌زداییNormalization vs denormalization

ایدهٔ کلیدیKey idea

نرمال‌سازی یعنی اطلاعات مشترک رو یه‌جا نگه داری و با شناسه بهش ارجاع بدی. نرمال‌زدایی یعنی برای آسون‌تر شدن خوندن، بخشی از داده رو تکرار کنی — کپی عمدی.

مثال فنی: نشانیِ فعلی و نشانیِ تاریخی

وضعیت اولیه: فرض کن نشانی فعلی مشتری توی جدول customers ـه؛ سفارش ۴۲ به نشانی زمان خرید نیاز داره.

اجرای مرحله‌به‌مرحله: حالا سفارش یه snapshot از نشانی ارسال نگه می‌داره؛ تغییر نشانی فعلی، سفارش تحویل‌شدهٔ قدیمی رو بازنویسی نمی‌کنه.

نتیجه و دلیل: پس این تکرار داده عمدیه. هر کپی معنای زمانی جدا داره و نباید بی‌فکر با مرجع فعلی همگام بشه — تاریخ رو دستکاری نکن.

Store region_id instead of repeating “Washington, DC” in every user record. That's normalization: keep the region's name in one authoritative place and refer to it by ID. The identifier can stay stable when the readable name changes.

Denormalization copies that readable information into other records to simplify reads. If those copies are meant to show the current name, a rename has to reach every copy. Decide what each copy means before deciding how to update it.

Example: Current address or historical address?

Setup: The customer's current address lives in customers. Order 42 needs the shipping address used when it was placed.

Walk through it: The order stores a snapshot of that address. Changing the customer's current address doesn't rewrite the address on an old, delivered order.

What this tells you: This copy is intentional historical data. It has a different meaning from the current address, so keeping it synchronized would change the history.

  • درس شبکهٔ اجتماعی (فصل ۲): تایم‌لاین آمادهٔ X فقط ID پست و فرستنده رو نگه می‌داره، نه متن و تعداد لایک رو — چون اونا تند عوض می‌شن. موقع خوندن این IDها رو «آبرسانی» می‌کنن (hydrating IDs) که عملاً یه join تو کد برنامه‌ست.
  • نتیجهٔ مهم: «join موقع خوندن» ذاتاً ترمز مقیاس نیست؛ آبرسانی IDها قشنگ موازی می‌شه — نترس.
  • تصمیم نرمال‌زدایی همیشه بدیهی نیست: بعضی‌ها رو دنرمال کن، بعضی‌ها رو نرمال نگه دار؛ بستگی داره چی هر چند وقت عوض می‌شه و خوندن/نوشتن چقدر می‌ارزه.
  • Treat denormalized copies as derived data, as in Chapter 1. If a copy represents current source data, give it a process that keeps it up to date.
  • In the Chapter 2 social-network example, the prepared X timeline holds post and sender IDs. Text and like counts change, so they're fetched separately at read time. Resolving those references, or hydrating IDs, is a join performed in application code.
  • A read-time join doesn't automatically prevent scaling. Independent ID lookups can run in parallel, though they still have a cost.
  • You can copy some fields and keep others normalized. Compare how often each field changes with the cost of reading it and updating its copies.

یک‌به‌چند، چند‌به‌یک و چند‌به‌چندOne-to-many, many-to-one and many-to-many

نوع رابطه مشخص می‌کنه چند تا رکورد به چند تا رکورد دیگه وصل می‌شن. بهتره با نیاز واقعی بشناسیش، نه فقط با شکل نمودار — نمودار نقشه‌ست، نه خاک.

مثال فنی: کلید خارجی و جدول واسط

وضعیت اولیه: فرض کن مشتری 17 دو تا سفارش 42 و 43 داره؛ هر سفارش چند تا کالا داره.

اجرای مرحله‌به‌مرحله: حالا orders.customer_id رابطهٔ چندبه‌یک رو می‌سازه؛ order_items(order_id, product_id, qty) سفارش و کالا رو چندبه‌چند می‌کنه.

نتیجه و دلیل: پس هر قلم می‌تونه qty مخصوص همون رابطه داشته باشه؛ گذاشتنش فقط روی مشتری یا کالا معنای درستی نداره — qty مال رابطه‌ست، نه طرفین.

  • یک‌به‌چند (one-to-few): رزومه چند تا شغل داره — درخت مناسب مدل سندی، جفتشون مثل هم.
  • چند‌به‌یک: خیلی‌ها تو یه منطقه زندگی می‌کنن → منطقه رو با ID ارجاع بده.
  • چند‌به‌چند: یک نفر در چند سازمان کار کرده و هر سازمان چند نفر دارد → در رابطه‌ای با جدول انجمنی (join table)؛ در مدل سندی یا ارجاع به سند دیگر یا نگه‌داشتن ID در هر دو طرف (که خودش دنرمال‌شده و ناسازگاری‌ساز است).
  • راه‌حل تمیز: رابطه رو یه‌جا نگه دار و با ایندکس ثانویه رو هر دو ستون، جست‌وجو هر دو طرف رو تند کن.
  • محدودیت سند: نمی‌تونی به یه آیتم توکار مستقیم ارجاع بدی (باید بگی «آیتم دوم لیست positions کاربر ۲۵۱»)؛ و برای لیست‌هایی که کاربر جابه‌جاشون می‌کنه (مثل to-do)، آرایهٔ JSON خیلی طبیعی‌تر از شعبده‌های رابطه‌ایه.

Relationship types describe how many records connect to how many others. Start with the actual entities:

  • One-to-few: a resume has a handful of jobs. A document can keep that tree together.
  • Many-to-one: many people share one region. Refer to the region by ID.
  • Many-to-many: a person has worked for several organizations, and each organization has employed many people. In a relational model, an association table, or join table, stores those links. Documents can reference other documents; storing ID lists on both sides creates copies that need coordination.
  • Store each relationship once and add a secondary index on each reference column to support lookups in both directions.
  • An embedded item needs an identity strategy if something outside the document must reference it. “The second item in user 251's positions list” won't stay reliable when the list is reordered. A JSON array does naturally represent order, which is useful for a to-do list the user rearranges.

Example: A foreign key and a join table

Setup: Customer 17 has orders 42 and 43. Each order contains several products.

Walk through it: The field orders.customer_id represents many orders belonging to one customer. The table order_items(order_id, product_id, qty) links orders and products in a many-to-many relationship.

What this tells you: Each order item has its own qty. That quantity belongs to the particular order-product relationship, rather than to the customer or product alone.

اسکیمای تحلیلی: Star، Snowflake و OBTAnalytic schemas: star, snowflake and OBT

تو مدل تحلیلی، جدول واقعیت رویدادها و مقدارها رو نگه می‌داره و جدول‌های بُعد ویژگی‌های توصیفی رو. اینکه این اطلاعات رو چقدر جدا کنی یا بچسبونی، شکل اسکیما رو تعیین می‌کنه — سلیقه‌ست، ولی سلیقهٔ مهم.

مثال فنی: Fact و dimension روی یک فروش

وضعیت اولیه: فرض کن قلم فروش شامل product_id=7, store_id=3, amount=200 ـه.

اجرای مرحله‌به‌مرحله: حالا جدول fact مبلغ و کلیدها رو داره؛ dimension محصول نام و دسته‌بندی رو می‌ده؛ join برای جمع فروش به تفکیک دسته اجرا می‌شه.

نتیجه و دلیل: پس توی OBT نام دسته توی ردیف‌های فروش تکرار می‌شه؛ خوندن ساده‌تر می‌شه ولی تغییر و معنای تاریخچه باید مدیریت بشه — راحتی حالا، بدهی بعداً.

For a sales report, start with the event you want to count. In a star schema, a central fact table, such as fact_sales, stores one purchase event per row. Columns hold measures such as price and cost, plus references to dimension tables.

The dimensions describe the who, what, where and when: dim_product holds SKU, brand and category; dim_store describes the store; dim_date can identify dates and holidays. To report holiday sales by product category, join the facts to those dimensions. The tables around the fact table give the layout its star shape.

Setup: A sale item contains product_id=7, store_id=3, amount=200.

Walk through it: The fact table holds the amount and reference keys. A product dimension supplies its name and category. Join them to total sales by category.

What this tells you: An OBT repeats the category in sales rows. That can simplify reading, but you still need to decide how updates and historical meanings work.

  • Snowflake: بعدها می‌شکنن به زیربعد (برند و دسته جدول جدا) — نرمال‌تر، ولی تحلیلگر با star راحت‌تره.
  • OBT (One Big Table): جدول‌های بعد کلاً حذف و اطلاعاتشون تا می‌شه تو ستون‌های دنرمال — جای بیشتر، گاهی کوئری تندتر.
  • دنرمال کردن تو تحلیل بی‌دردسره: داده تاریخچهٔ تغییرناپذیره و دغدغهٔ سازگاری نوشتن OLTP رو نداره — راحت باش.
  • جدول واقعیت می‌تونه پتابایتی بشه؛ چون هر رویداد رو جدا نگه می‌دارن، بعداً دستت برای تحلیل بازتره.
  • Snowflake: split dimensions into related sub-dimensions, such as separate brand and category tables. This is more normalized; a star keeps the analyst's joins simpler.
  • OBT (One Big Table): fold dimension information into denormalized columns on one table. It uses more space and can simplify or speed up some queries.
  • Historical event data often avoids the repeated current-state updates of OLTP. Still, decide whether a field means “value at the time” or “current value”. The sales example shows why those copies need different treatment.
  • A fact table can grow to petabytes. Keeping individual events leaves more options for future analysis than retaining only an aggregate.

Schema-on-Read در برابر Schema-on-Write + نمودار ۱Schema-on-read vs schema-on-write + Diagram 1

تو schema-on-write، داده قبل ذخیره با ساختار موردانتظار چک می‌شه. تو schema-on-read، بخش بیشتری از تفسیر و بررسی ساختار موقع خوندن انجام می‌شه؛ دادهٔ سندی هم الزاماً بی‌ساختار نیست — بی‌قانون نیست، دیرقانونه.

مثال فنی: اعتبارسنجی در نوشتن یا خواندن

وضعیت اولیه: فرض کن منبعی age="unknown" می‌فرسته، ولی گزارش میانگین سن عدد می‌خواد.

اجرای مرحله‌به‌مرحله: حالا schema-on-write می‌تونه رکورد نامعتبر رو همون ورود رد کنه؛ schema-on-read فایل خام رو می‌پذیره و موقع تحلیل خطا یا مقدار نامعلوم رو مدیریت می‌کنه.

نتیجه و دلیل: پس نبود schema موقع ذخیره، نیاز به تفسیر و اعتبارسنجی رو حذف نمی‌کنه؛ فقط جاش عوض می‌شه — صورت‌حساب همیشه میاد، فقط دیرتر.

  • schema-on-write (رابطه‌ای سنتی): اسکیما صریحه و دیتابیس موقع نوشتن تضمین می‌کنه داده مطابق اون باشه — مثل type checking ایستا، سخت‌گیر.
  • schema-on-read (سند): هیچ اسکیمایی اجرا نمی‌شه و ساختار فقط موقع خوندن تفسیر می‌شه — مثل type checking پویا، راحت. واژهٔ «schemaless» گول‌زننده‌ست چون کد خواننده همیشه یه ساختاری رو فرض می‌کنه.
  • موقع تغییر قالب (مثلاً نصف کردن نام کامل به نام و نام خانوادگی): تو سند، کد برنامه باید با سندهای قدیمی بسازه؛ تو رابطه‌ای، مهاجرت (ALTER TABLE + UPDATE) که رو جدول بزرگ کنده — قهوه‌ت رو بخور.
  • schema-on-read وقتی به درد می‌خوره که ساختار داده ناهمگون باشه یا سیستم‌های بیرونی تعیینش کنن.
  • Schema-on-write: the traditional relational approach states the schema explicitly and checks data when it's written. Think of the comparison with static type checking.
  • Schema-on-read: readers interpret the stored structure when they use it, similar to dynamic type checking. Document data may be handled this way. “Schemaless” is misleading: the reader still expects a shape.
  • Suppose a full name becomes first and last names. Document readers may need to handle both old and new formats. A relational migration can use ALTER TABLE and UPDATE; changing a large table can take substantial work.
  • Schema-on-read is useful when inputs have mixed structures or outside systems determine their format. It moves interpretation and validation work to the reader; that work still needs doing.

Property Graph در برابر Triple StoreProperty graphs vs triple stores

تو property graph گره و یال می‌تونن ویژگی داشته باشن. تو triple store اطلاعات با سه‌تایی موضوع و رابطه و مقدار گفته می‌شه — جملهٔ سه‌کلمه‌ای.

مثال فنی: ویژگی روی گره یا یال

وضعیت اولیه: فرض کن گره‌های Person:17 و Company:7 رو داری و شروع همکاری سال 2020 ـه.

اجرای مرحله‌به‌مرحله: حالا توی property graph، یال WORKS_AT ویژگی since=2020 داره؛ توی triple store رابطه‌ها به subject و predicate و object بیان می‌شن و مشخصات رابطه مدل‌سازی اضافه می‌خواد.

نتیجه و دلیل: پس زمان شروع مال رابطه‌ست، نه مال همهٔ شغل‌های شخص یا همهٔ کارمندهای شرکت — صفت رو به صاحبش بچسبون.

  • Property graph (Neo4j و Memgraph و KùzuDB): هر گره = شناسهٔ یکتا + برچسب (نوع شیء) + یه مشت ویژگی + یال‌های ورودی/خروجی. هر یال = شناسه + گره شروع + گره پایان + برچسب رابطه + ویژگی‌ها. عملاً همون دو تا جدول رابطه‌ای (vertices و edges) با ایندکس هر دو طرف — آشنا اومد؟
  • هیچ اسکیمایی جلو وصل شدن گره‌ها رو نمی‌گیره؛ با برچسب‌های مختلف می‌تونی چند جور اطلاعات رو تو یه گراف نگه داری (مثل گراف فیسبوک یا knowledge graph موتورهای جست‌وجو) — مهمونی مختلط.
  • Triple store (Datomic و AllegroGraph و Blazegraph): همه‌چی سه‌تایی (subject, predicate, object) — مثلاً (lucy, bornIn, idaho) یا (lucy, birthYear, 1989). مدل RDF و فرمت‌هایی مثل Turtle از همین‌جا اومدن.
  • محدودیت: یه یال فقط دو تا گره رو به هم وصل می‌کنه؛ رابطهٔ سه‌نفره رو باید با یه گره اضافه یا hypergraph مدل کنی — یال دستش کوتاهه.
  • Property graph (Neo4j, Memgraph, KùzuDB): a vertex has a unique ID, label, properties, and incoming and outgoing edges. An edge has an ID, tail, head, label and properties. You can represent this model with vertices and edges tables, indexed at both ends.
  • Labels let one graph hold several kinds of entities and relationships, as in a social network or a search engine's knowledge graph. The model can connect unlike entities without giving every node the same fields.
  • Triple store (Datomic, AllegroGraph, Blazegraph): represent facts as (subject, predicate, object) triples, such as (lucy, bornIn, idaho) and (lucy, birthYear, 1989). RDF uses this model, with formats such as Turtle.
  • A regular edge connects two vertices. For a relationship involving three or more participants, introduce another vertex or consider a hypergraph model.

این نمودار برخلاف قبلی‌ها «جریان» نشون نمی‌ده؛ ساختار نشون می‌ده — دقیقاً مثل نمودار کلاس تو UML. سمت چپ دو تا «کلاس» داری: «Vertex» با فیلدهای «id, label, properties» و برچسب «entity»، و پایین‌تر «Edge» با فیلدهای «id, tail, head, label, props» و برچسب «relationship» — شناسنامهٔ هر کدوم. فلش چین‌چین «tail + head» از Edge به Vertex می‌گه هر یال به دو تا رأس اشاره می‌کنه — هر یال دو سر داره.

حالا سمت راست ببین همین دو «کلاس» چطور تو یه دیتابیس رابطه‌ای پیاده می‌شن: فلش پررنگ «maps to» از Vertex می‌ره به «vertices table» («PK vertex_id, label, jsonb») و از Edge به «edges table» («PK edge_id, FK tail, FK head»). فلش چین‌چین «FK references» بین دو جدول همون کلیدهای خارجیه — آشنا اومد؟

و آخرین جعبه، «Indexes» با برچسب «both directions»: ایندکس رو tail_vertex برای یال‌های خروجی و رو head_vertex برای یال‌های ورودی. بدون این دو تا ایندکس، هر قدم زدن تو گراف باید کل جدول edges رو بگرده؛ باهاشون قدم زدن تو گراف تند می‌مونه — ایندکس، کفش دوئه.

زبون کوئری گراف الگوی رابطه‌ای که دنبالشیم رو توصیف می‌کنه. بعضی زبون‌ها الگو رو اعلام می‌کنن و بعضی مسیر رفتن رو قدم‌به‌قدم می‌سازن — دو تا سبک.

مثال فنی: همان مسیر با زبان گراف

وضعیت اولیه: فرض کن گراف شامل مریم، دوست‌هاش و شرکت‌هاشونه.

اجرای مرحله‌به‌مرحله: حالا Cypher می‌تونه الگویی مثل (p)-[:KNOWS]->(f)-[:WORKS_AT]->(c) رو match کنه و نام شرکت رو برگردونه.

نتیجه و دلیل: پس موتور نحوهٔ پیمایش رو انتخاب می‌کنه؛ SPARQL روی الگوی triple و Datalog با قواعد رابطه‌ای همون نوع مسئله رو صورت‌بندی می‌کنن — بگو چی می‌خوای، موتور راهش رو پیدا می‌کنه.

// Cypher (Neo4j / openCypher): the pattern from Diagram 2
MATCH (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (:Location {name:'United States'}),
      (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'Europe'})
RETURN person.name
  • Cypher: تطبیق الگو با فلش‌ها؛ از Neo4j اومد و حالا استاندارد بازه (openCypher). اسمش از یارو تو فیلم ماتریکسه، نه رمزنگاری — اشتباه نگیر!
  • SPARQL: مال triple storeهای RDF؛ الگوش تقریباً همون Cypher ـه (?person :bornIn / :within* / :name "United States") و چون RDF بین صفت و یال فرق نمی‌ذاره، همون سینتکس برای صفت‌ها هم جواب می‌ده.
  • Datalog: قدیمی‌تر و ریشه‌دار تو پژوهش‌های دههٔ ۸۰؛ به‌جای SELECT قاعده تعریف می‌کنی و جدول مجازی می‌سازی (مثل view)، و قاعده‌ها می‌تونن بازگشتی باشن → پیمایش گراف. پدربزرگ خردمند.
  • GraphQL: با بقیه فرق داره — مال OLTP و رابط کاربریه؛ کلاینت شکل دقیق JSON جواب رو تعیین می‌کنه. عمداً محدوده: نه کوئری بازگشتی، نه شرط دلبخواهی (چون از منبع نامطمئن میاد و می‌تونه DoS درست کنه). رو هر دیتابیسی پیاده می‌شه.
  • GQL: استاندارد ISO سال ۲۰۲۴ رو دوش Cypher — امید به یه‌دست شدن بیشتر. ببینیم چی می‌شه.
  • Cypher: describe graph patterns using arrows. It originated with Neo4j and led to openCypher. The name refers to the Matrix character, rather than cryptography.
  • SPARQL: query RDF triples. A path can look like ?person :bornIn / :within* / :name "United States". Attributes and relationships use the same triple-based representation.
  • Datalog: rooted in work from the 1980s, it defines results through logical rules. The rules build virtual relations, similar to views, and can recurse to express graph walks.
  • GraphQL: an API query language, often used for OLTP-backed UIs. The client selects the JSON response fields through a declared schema. Queries follow the API's fields and resolvers; they don't provide arbitrary database recursion or conditions. Those limits alone don't prevent expensive requests, and the backing database can use any model.
  • GQL: the 2024 ISO graph query language standard builds on ideas from Cypher. Its aim is a common language for graph queries.

Walk through it: Cypher can match a pattern such as (p)-[:KNOWS]->(f)-[:WORKS_AT]->(c) and return the company names.

۳3 Event Sourcing و CQRSEvent sourcing and CQRS

ایدهٔ کلیدیKey idea

تو Event Sourcing تغییرها رو به شکل رویداد نگه می‌داریم و وضعیت فعلی رو از روشون می‌سازیم. CQRS یعنی مدل ثبت تغییر و مدل جواب به خوندن می‌تونن جدا باشن؛ این دو تا مفهوم یکی نیستن — پسرعموئن، نه دوقلو.

مثال فنی: رویداد و نمای خواندن

وضعیت اولیه: فرض کن برای سفارش ۴۲ رویدادهای OrderPlaced و بعد OrderCancelled با شمارهٔ ترتیب ثبت می‌شن.

اجرای مرحله‌به‌مرحله: حالا projector اون‌ها رو به‌ترتیب اعمال می‌کنه و ردیف خوندنی status=cancelled می‌سازه؛ command مسیر اعتبارسنجی و ثبت رویداد رو داره.

نتیجه و دلیل: پس Event Sourcing تاریخچه رو مرجع می‌گیره؛ CQRS مسیر ثبت فرمان و نمایش نتیجه رو جدا می‌کنه و الزاماً نیازمند هم نیستن — دو تا ایدهٔ جدا که خوب با هم می‌شینن.

A booking history and a support dashboard ask for different shapes of the same data. You can store changes in a form suited to writing, then derive views suited to those reads.

An append-only event log records what happened. Event sourcing uses that history as the source from which state is built. CQRS separates the models used for commands and queries. They're separate ideas that can work together.

  • Event Sourcing: هر تغییر وضعیت اول به شکل رویداد می‌ره تو لاگ؛ رویدادها تغییرناپذیرن و فقط اضافه می‌شن. رویدادها رو به زمان گذشته اسم بذار (seats were booked) چون گزارش چیزی‌ان که افتاده — گذشته‌ست، نه آرزو.
  • CQRS: جدا کردن کار فرمان از کار کوئری — نماهای فقط‌خوندنی (projection / read model / materialized view) از رو لاگ ساخته و به‌روز می‌شن.
  • Command → اعتبارسنجی → fact: درخواست کاربر اول باید معتبر بشه (مثلاً صندلی خالی باشه)؛ بعد رویدادش می‌شینه تو لاگ. پس لاگ فقط رویداد معتبر داره و مصرف‌کنندهٔ نما حق رد کردن رویداد رو نداره — لاگ دروغ نمی‌گه.
  • Event sourcing: record each accepted state change as an immutable event in the append-only log. Use past-tense names, such as seats were booked, because an event describes something that happened.
  • CQRS: separate the command and query models. In this design, consumers build and update read views from the log: projections, read models or materialized views. CQRS doesn't require event sourcing in every implementation.
  • Command → validation → fact: check the request first, including whether a seat is available. An accepted request produces an event. View consumers apply that recorded fact; they don't decide afterward whether the original command should have been accepted.

مزیت‌هاAdvantages

رویدادها امکان دنبال کردن تغییر و ساختن نماهای تازه رو می‌دن، اگه تاریخچه و قواعد بازپخش کافی و معتبر باشن.

مثال فنی: بازسازی یک گزارش تازه

وضعیت اولیه: فرض کن تاریخچهٔ سفارش شامل زمان ثبت، پرداخت و ارساله.

اجرای مرحله‌به‌مرحله: حالا projector جدید فاصلهٔ پرداخت تا ارسال رو حساب می‌کنه؛ رویدادهای قدیمی بدون تغییر منبع دوباره پردازش می‌شن.

نتیجه و دلیل: پس می‌تونی نمای تازه بسازی، به‌شرط حفظ داده و معنای رویدادها؛ snapshot وضعیت نهایی به‌تنهایی این فاصله‌ها رو نمی‌ده — تاریخچه گنجه.

  • رویداد نیت رو می‌گه: «رزرو لغو شد» بهتره از «ستون active ردیف ۴۰۰۱ false شد» — آدم‌فهم در برابر ماشین‌فهم.
  • نماها قابل بازتولیدن: پاک کن و همون رویدادها رو با همون ترتیب و کد دوباره پخش کن — مثل روز اول.
  • هر تعداد نمای بهینه که دلت خواست، حتی فقط تو حافظه؛ نمای جدید از رو لاگ قدیمی هم ساخته می‌شه — لاگ گنجه.
  • کارهای بی‌برگشت کمتر می‌شه؛ لاگ همزمان حسابرسی (audit) هم هست — دو تا پرنده با یه سنگ.
  • نوشتن ترتیبی throughput بالا می‌ده و جهش رویداد رو جذب می‌کنه — صف خودش جمعش می‌کنه.
  • Events express domain meaning: “booking canceled” tells you more about intent than “row 4001's active column set to false”.
  • Rebuild a view by replaying the same events in the required order with the same deterministic processing logic.
  • Build several views for different queries, including memory-only views. A new projection can use old events if the history contains the information it needs.
  • The retained history provides an audit trail and leaves more options for future processing.
  • Sequential appends can support high write rates, while a queue lets projections catch up after a burst. Check consumer capacity too; a backlog still takes time to process.

هشدارهاCautions

رویداد قدیمی با عوض شدن کد غیب نمی‌شه. باید نسخهٔ رویداد و بازپخش و اثرهای جانبی رو با چشم باز مدیریت کنی — حوـه باشه.

مثال فنی: Replay نباید پیامک تاریخی بفرستد

وضعیت اولیه: فرض کن projector گزارش، رویداد OrderPlaced سال گذشته رو دوباره می‌خونه.

اجرای مرحله‌به‌مرحله: حالا مسیر بازسازی فقط جدول گزارش رو می‌نویسه؛ ارسال پیامک مسیر اثر جانبی جدا با شناسهٔ یکتا و سیاست جلوگیری از تکرار داره.

نتیجه و دلیل: پس بازپخش محاسبه با تکرار اثر بیرونی فرق داره؛ کپی کردن همهٔ handlerهای زنده توی replay خطرناکه — پیامک دوباره نفرست، مشتری شاکی می‌شه!

  • پردازش باید قطعی (deterministic) باشه: نرخ ارز رو بذار تو خود رویداد، نه اینکه از بیرون بگیری — بیرون عوض می‌شه، رویداد نه.
  • تغییرناپذیری با «حق حذف» قانون حریم خصوصی دعوا داره: راه‌حل‌هایی مثل crypto-shredding — کلید رو بنداز دور، داده بمیره.
  • بازپخش نباید اثر جانبی رو تکرار کنه (مثلاً دوباره ایمیل تأیید نره — مشتری شاکی می‌شه).
  • قانون فنی: همهٔ نماها باید رویدادها رو دقیقاً با همون ترتیب لاگ ببینن — ترتیب مقدسه.

Old events remain after the code changes. Plan how their versions, processing rules and external effects will work during a replay:

  • Deterministic processing: record an exchange rate in the event if rebuilding the result depends on that rate. Fetching today's rate won't reproduce yesterday's calculation.
  • Deletion requirements: immutable history can conflict with a need to erase personal data. Crypto-shredding, which destroys the relevant encryption key, is one approach to consider; deletion still needs an explicit design.
  • Side effects: rebuilding a report mustn't resend the original confirmation email or message. Separate replayed calculations from external actions.
  • Order: each view must apply order-dependent events in the required log order. A cancellation followed by an older booking event shouldn't accidentally restore the booking.

اجرای مرحله‌به‌مرحله: حالا روی DataFrame، فیلتر روز و جمع مبلغ اجرا می‌شه؛ روی تصویر، محاسبه با اندیس محورهای ارتفاع و عرض و رنگ انجام می‌شه.

A DataFrame looks like a table you can filter, join and transform during analysis. Matrices and arrays fit numerical operations and multidimensional data. These models are common in analytics and data science; their operations differ from the usual OLTP record lookup.

  • DataFrame (R و Pandas و Spark و Dask): اولش شبیه جدوله و عملگر رابطه‌ای هم داره (فیلتر، گروه‌بندی، ادغام که همون join ـه)، ولی به‌جای زبون اعلانی با یه رشته دستور ور می‌ری — دقیقاً به قوارهٔ کار تدریجی دانشمند داده رو نسخهٔ شخصی داده.
  • کاربرد مهم: تبدیل دادهٔ رابطه‌ای به ماتریس تنک (sparse) برای الگوریتم‌های ML — مثلاً ماتریس امتیاز کاربرها به فیلم‌ها. ستون‌ها می‌تونن هزاران عدد باشن که تو دیتابیس رابطه‌ای جا نمی‌شن.
  • داده‌های غیرعددی باید عددی بشن: تاریخ‌ها رو مقیاس کن، دسته‌ها رو با one-hot encoding — همه باید عدد بشن، قانون بازیه.
  • دیتابیس آرایه‌ای (مثل TileDB) برای آرایه‌های چندبُعدی گنده: دادهٔ ژئومکانیکی، عکس پزشکی، رصدخونه‌ها؛ و تو مالی برای سری زمانی قیمت‌ها.
  • DataFrame (R, Pandas, Spark, Dask): a table-like representation with relational operations such as filtering, group-by and merging as a join. You often build a chain of operations while exploring a working copy of the data.
  • One use is turning relational data into a sparse matrix for ML, such as users' ratings of movies. Thousands of numerical feature columns fit that style of computation more naturally than an ordinary relational schema.
  • Numerical algorithms need numerical inputs. Dates may need scaling; categorical values can use one-hot encoding. Choose a representation that matches the algorithm.
  • Array databases, such as TileDB, handle large multidimensional arrays used in geospatial data, medical images, astronomy and financial price histories.

اجرای مرحله‌به‌مرحله: حالا GROUP BY customer_id HAVING COUNT(*) > 3 شرط نتیجه رو می‌گه؛ optimizer می‌تونه نوع اسکن و تجمیع رو انتخاب کنه.

نتیجه و دلیل: پس توی حلقهٔ دستوری ترتیب اجرا رو خودت تعیین می‌کنی؛ اعلانی بودن آزادی انتخاب طرح اجرا رو می‌ده به موتور — بگو چی می‌خوای، نه چطور.

A declarative query describes the result and lets the engine plan the steps. The optimizer can choose indexes, join algorithms or parallel execution as the data and resources change, while the query keeps its meaning.

Example: SQL describes the result

Setup: You need customers who have more than three orders.

Walk through it: The condition GROUP BY customer_id HAVING COUNT(*) > 3 states which groups qualify. The optimizer can choose how to scan the data and compute the counts.

What this tells you: An imperative loop specifies the steps. A declarative query leaves the execution plan to the engine. Describe the result clearly.

۳. ORM چه کمکی می‌کند و مسئلهٔ N+1 چیست؟3. How do ORMs help, and what is the N+1 problem?

ORM ترجمهٔ شیء و جدول رو آسون می‌کنه، ولی خرج کوئری رو حذف نمی‌کنه. تو N+1، یه کوئری اول و بعد یه کوئری جدا برای هر نتیجه اجرا می‌شه — ۱+N تا رفت‌وبرگشت!

مثال فنی: N+1 در صفحهٔ رزومه‌ها

وضعیت اولیه: فرض کن ORM اول ۱۰۰ تا متقاضی رو با یه SQL می‌خونه.

اجرای مرحله‌به‌مرحله: حالا دسترسی lazy به person.jobs برای هر متقاضی یه SQL جدا می‌زنه: مجموعاً ۱۰۱ تا کوئری! preload می‌تونه رابطه‌ها رو دسته‌ای بخونه.

نتیجه و دلیل: پس کد کوتاه لزوماً مسیر کم‌هزینه نیست. تعداد query و دادهٔ برگردونده‌شده رو باید دید — ORM راحته، ولی مجانی نیست.

An ORM reduces object-to-table translation code. It doesn't remove the cost of the generated queries. N+1 means one initial query followed by one more for each of N results. A JOIN or eager loading can fetch related records together. Check the query count and returned data, rather than judging by the length of the application code.

Example: N+1 on a resume listing

Setup: An ORM loads 100 applicants with one SQL query.

Walk through it: Lazy access to each applicant's person.jobs runs another query: 101 queries in total. Preloading can fetch the related records in batches.

What this tells you: Short application code doesn't guarantee a cheap database path. Count queries and the data they return.

۴. تفاوت shredding و embedding؟4. Shredding vs embedding?

Shredding یعنی دادهٔ تودرتو رو بشکنی به رکوردهای مرتبط؛ embedding یعنی تیکه‌های مرتبط رو نگه داری تو یه سند. خوندن یه مجموعه و عوض کردن رابطهٔ بین مجموعه‌ها دو تا نیاز جدا‌ان.

مثال فنی: Embedding تا کجا مناسب است؟

وضعیت اولیه: فرض کن رزومه دو تا سابقهٔ شغلی داره و هر دو توی آرایهٔ jobs ذخیره‌ان.

اجرای مرحله‌به‌مرحله: حالا خوندن سند همهٔ رزومه رو میاره؛ اگه نام شرکت توی ۱۰ هزار رزومه کپی شده باشه، تغییر نام یعنی اصلاح همون ۱۰ هزار نسخه.

نتیجه و دلیل: پس بخش‌های مال یه رزومه برای embedding خوبن؛ هویت مشترک شرکت معمولاً مرجع مستقل می‌خواد — کپی ارزونه، اصلاحش گرونه.

Shredding splits a nested structure into related records. Embedding keeps its parts inside one document. A small tree read together suits embedding; shared entities and references to individual items need more thought. Retrieving a whole resume and updating a company shared by many resumes are different requirements.

Example: Where embedding stops helping

Setup: A resume has two jobs, both stored in its jobs array.

Walk through it: Reading the document retrieves the whole resume. But if a company name is copied into 10,000 resumes, renaming that company means updating 10,000 copies.

What this tells you: Parts owned by one resume suit embedding. A shared company identity often deserves a separate reference. Include the update cost in the choice.

۵. کی نرمال‌سازی و کی نرمال‌زدایی؟5. When to normalize, when to denormalize?

نرمال‌سازی تکرار رو کم و عوض کردن اطلاعات مشترک رو آسون می‌کنه؛ نرمال‌زدایی بعضی خوندن‌ها رو ساده‌تر می‌کنه، ولی هماهنگ نگه‌داشتن نسخه‌های تکراری خرج داره — هیچی مفت نیست.

مثال فنی: نشانیِ فعلی و نشانیِ تاریخی

وضعیت اولیه: فرض کن نشانی فعلی مشتری توی جدول customers ـه؛ سفارش ۴۲ به نشانی زمان خرید نیاز داره.

اجرای مرحله‌به‌مرحله: حالا سفارش یه snapshot از نشانی ارسال نگه می‌داره؛ تغییر نشانی فعلی، سفارش تحویل‌شدهٔ قدیمی رو بازنویسی نمی‌کنه.

نتیجه و دلیل: پس این تکرار داده عمدیه. هر کپی معنای زمانی جدا داره و نباید بی‌فکر با مرجع فعلی همگام بشه — تاریخ رو دستکاری نکن.

Normalization reduces duplication and makes shared information easier to update in one place. Denormalization copies information to simplify selected reads, then needs a process to maintain those copies. Compare writes, reads and consistency for the actual workload. OLTP often benefits from normalized records; analytics often uses prepared denormalized views.

Example: Current address or historical address?

Setup: The customer's current address lives in customers. Order 42 needs the shipping address used when it was placed.

Walk through it: The order stores a snapshot of that address. Changing the customer's current address doesn't rewrite the address on an old, delivered order.

What this tells you: This copy is intentional historical data. It has a different meaning from the current address, so keeping it synchronized would change the history.

۶. در مثالِ تایم‌لاینِ فصل، چرا شناسهٔ پست ذخیره می‌شود؟6. Why does X’s timeline store only IDs?

تو سناریوی تایم‌لاین فصل، شناسهٔ پست می‌ره تو فهرست و محتوای قابل‌تغییر جدا خونده می‌شه. این کار حجم کپی و خرج اصلاح داده رو کم می‌کنه — فقط شناسه رو کپی کن، نه کل پست رو.

مثال فنی: چرا timeline شناسه نگه می‌دارد؟

وضعیت اولیه: فرض کن پست p9 به timeline هزار تا دنبال‌کننده وارد شده.

اجرای مرحله‌به‌مرحله: حالا فهرست‌ها فقط post_id دارن؛ متن از مخزن پست خونده می‌شه، پس ویرایش متن نیاز به تغییر هزار تا کپی متن نداره.

نتیجه و دلیل: پس هنوز باید حذف پست و کش مدیریت بشه؛ کم کردن تکرار متن همهٔ هزینهٔ نگهداری timeline رو حذف نمی‌کنه — یه درد کم شد، درد دیگه مونده.

In the timeline example, lists hold post IDs while mutable text, likes and avatars are fetched separately at read time. That's ID hydration, a join in application code. It reduces copied data and the work of updating that data across timelines. Independent lookups can run in parallel, but deletion and caching still need handling.

Example: Why a timeline holds IDs

Setup: Post p9 has entered the timelines of a thousand followers.

Walk through it: The lists contain only post_id; text comes from the post store. Editing that text doesn't require changing a thousand copied versions.

What this tells you: Deletion and caching still need handling. Reducing duplicated text removes one maintenance cost without removing every timeline concern.

۷. star schema چیست و fact/dimension یعنی چه؟7. What is a star schema? What are facts and dimensions?

تو طرح ستاره‌ای، جدول واقعیت رویداد و مقدارهای قابل‌حساب رو نگه می‌داره؛ جدول‌های بُعد اطلاعات توصیفی اونا رو دارن — وسط، دورش ستاره.

مثال فنی: Fact و dimension روی یک فروش

وضعیت اولیه: فرض کن قلم فروش شامل product_id=7, store_id=3, amount=200 ـه.

اجرای مرحله‌به‌مرحله: حالا جدول fact مبلغ و کلیدها رو داره؛ dimension محصول نام و دسته‌بندی رو می‌ده؛ join برای جمع فروش به تفکیک دسته اجرا می‌شه.

نتیجه و دلیل: پس توی OBT نام دسته توی ردیف‌های فروش تکرار می‌شه؛ خوندن ساده‌تر می‌شه ولی تغییر و معنای تاریخچه باید مدیریت بشه — راحتی حالا، بدهی بعداً.

A star schema puts a fact table in the center, with events and measurable values. Dimension tables describe those events: the product, store or date. Snowflake splits dimensions into further tables. OBT folds their descriptive fields into one denormalized table. The layout changes how much data is repeated and which joins a query needs.

Example: Facts and dimensions for one sale

Setup: A sale item contains product_id=7, store_id=3, amount=200.

Walk through it: The fact table holds the amount and reference keys. A product dimension supplies its name and category. Join them to total sales by category.

What this tells you: An OBT repeats the category in sales rows. That can simplify reading, but you still need to decide how updates and historical meanings work.

۸. schema-on-read در برابر schema-on-write؟8. Schema-on-read vs schema-on-write?

تو schema-on-write ساختار قبل ثبت چک می‌شه؛ تو schema-on-read خواننده موقع استفاده تفسیرش می‌کنه. روش دوم هم قرارداد داده می‌خواد — بی‌قانون نیست، دیرقانونه.

مثال فنی: اعتبارسنجی در نوشتن یا خواندن

وضعیت اولیه: فرض کن منبعی age="unknown" می‌فرسته، ولی گزارش میانگین سن عدد می‌خواد.

اجرای مرحله‌به‌مرحله: حالا schema-on-write می‌تونه رکورد نامعتبر رو همون ورود رد کنه؛ schema-on-read فایل خام رو می‌پذیره و موقع تحلیل خطا یا مقدار نامعلوم رو مدیریت می‌کنه.

نتیجه و دلیل: پس نبود schema موقع ذخیره، نیاز به تفسیر و اعتبارسنجی رو حذف نمی‌کنه؛ فقط جاش عوض می‌شه — صورت‌حساب همیشه میاد، فقط دیرتر.

Schema-on-write checks the expected structure before storing data. Schema-on-read leaves more interpretation to the reader, which still needs a data contract. The static-versus-dynamic typing comparison helps explain the difference. When a format changes, plan for old documents or a migration of existing rows.

Example: Validate at write time or read time

Setup: A source sends age="unknown", but an average-age report needs a number.

Walk through it: Schema-on-write can reject the invalid record as it arrives. Schema-on-read can retain the raw input and handle the error or unknown value during analysis.

What this tells you: Skipping a storage-time schema check doesn't remove interpretation or validation. The reader takes on that work.

۹. کی سراغ مدل گراف برویم؟9. When should we reach for the graph model?

وقتی رابطه‌های جورواجور و چندقدمه موضوع اصلی سؤالن، گراف نمایش طبیعی‌تری می‌شه. صرف وجود یه رابطه دلیل رفتن سراغ گراف نیست — توپ رو با تانک نزن.

مثال فنی: پیمایشِ دو رابطه

وضعیت اولیه: فرض کن مریم به علی با رابطهٔ KNOWS وصله و علی توی شرکت C7 کار می‌کنه.

اجرای مرحله‌به‌مرحله: حالا پرسش «دوست‌های مریم توی کدوم شرکتن؟» اول یال دوستی و بعد یال اشتغال رو طی می‌کنه.

نتیجه و دلیل: پس وقتی عمق و نوع رابطه‌ها متغیره، مدل گراف این مسیر رو مستقیم بیان می‌کنه؛ برای یه lookup ساده لزوماً لازم نیست — توپ رو با تانک نزن.

A graph is useful when varied relationships and multi-step paths are central to the questions. Its nodes can represent different kinds of entity. Having one relationship doesn't automatically justify a graph database; consider how much traversal the application actually needs.

Example: Following two relationships

Setup: Maryam connects to Ali through KNOWS, and Ali works at company C7.

Walk through it: To ask “Which companies do Maryam's friends work for?”, follow a friendship edge, then an employment edge.

What this tells you: A graph directly expresses paths whose depth and relationship types vary. A single simple lookup doesn't necessarily need a graph database.

۱۰. property graph از چه ساخته شده؟10. What is a property graph made of?

Property graph گره‌های شناسه‌دار و برچسب‌دار و ویژگی‌دار و یال‌های مقصددار و نوع‌دار و ویژگی‌دار داره. جهت یال و مشخصات مدل تو معنای رابطه اثر دارن — جزئیات مهمن.

مثال فنی: ویژگی روی گره یا یال

وضعیت اولیه: فرض کن گره‌های Person:17 و Company:7 رو داری و شروع همکاری سال 2020 ـه.

اجرای مرحله‌به‌مرحله: حالا توی property graph، یال WORKS_AT ویژگی since=2020 داره؛ توی triple store رابطه‌ها به subject و predicate و object بیان می‌شن و مشخصات رابطه مدل‌سازی اضافه می‌خواد.

نتیجه و دلیل: پس زمان شروع مال رابطه‌ست، نه مال همهٔ شغل‌های شخص یا همهٔ کارمندهای شرکت — صفت رو به صاحبش بچسبون.

A property-graph vertex has an ID, label, properties and incoming or outgoing edges. An edge has an ID, tail, head, label and properties of its own. You can represent this with vertices and edges tables and indexes on both endpoints. The relationship's direction and properties are part of its meaning.

Example: A property belongs to the relationship

Setup: The nodes are Person:17 and Company:7, and employment began in 2020.

Walk through it: In a property graph, the WORKS_AT edge carries since=2020. A triple store expresses facts through subject, predicate and object; describing the relationship itself needs additional modeling.

What this tells you: The start date belongs to this employment relationship. It isn't a property shared by all the person's jobs or all the company's employees.

۱۱. چرا همان گراف را در SQL نگه نداریم؟11. Why not keep the same graph in SQL?

گراف رو می‌شه تو جدول هم نگه داشت. مسئله راحتی گفتن و اجرای پیمایش چندقدمه و متغیره؛ SQL بازگشتی هم یه راهشه — می‌شه، ولی دست‌وپا شکسته.

مثال فنی: گراف در جدول هم ممکن است

وضعیت اولیه: فرض کن جدول edges(from_id,to_id,type) یال‌های دوستی رو نگه داشته.

اجرای مرحله‌به‌مرحله: حالا برای دو گام می‌تونی جدول رو به خودش join کنی؛ برای عمق متغیر از query بازگشتی یا موتور گراف استفاده می‌شه و هزینه با دادهٔ واقعی سنجیده می‌شه.

نتیجه و دلیل: پس رابطه‌ای بودن مانع ذخیرهٔ گراف نیست؛ فرق سر راحتی بیان مسیر، ایندکس و طرح اجرای پیمایشه — مدل گراف فقط یه جدول نیست، یه طرز فکره.

Yes. Tables can store vertices and edges, and joins can follow the links. Variable-depth paths may use recursive SQL. In this chapter's example, a four-line Cypher pattern corresponds to about 31 lines of WITH RECURSIVE SQL. That illustrates a difference in expression; measure execution cost on real data.

Example: A graph stored in tables

Setup: The table edges(from_id,to_id,type) holds friendship edges.

Walk through it: For a two-step path, join the table to itself. For variable depth, use a recursive query or graph engine, then measure the cost with actual data.

What this tells you: Relational storage can represent a graph. The differences include how easily you express paths, which indexes you have and how traversal executes.

۱۲. SPARQL و Datalog چه فرقی با Cypher دارند؟12. How do SPARQL and Datalog differ from Cypher?

Cypher الگوی گراف ویژگی‌دار رو می‌گه؛ SPARQL الگوی سه‌تایی‌های RDF رو؛ Datalog نتیجه رو با قاعده‌های منطقی، از جمله بازگشتی، تعریف می‌کنه — هرکی یه لهجه.

مثال فنی: همان مسیر با زبان گراف

وضعیت اولیه: فرض کن گراف شامل مریم، دوست‌هاش و شرکت‌هاشونه.

اجرای مرحله‌به‌مرحله: حالا Cypher می‌تونه الگویی مثل (p)-[:KNOWS]->(f)-[:WORKS_AT]->(c) رو match کنه و نام شرکت رو برگردونه.

نتیجه و دلیل: پس موتور نحوهٔ پیمایش رو انتخاب می‌کنه؛ SPARQL روی الگوی triple و Datalog با قواعد رابطه‌ای همون نوع مسئله رو صورت‌بندی می‌کنن — بگو چی می‌خوای، موتور راهش رو پیدا می‌کنه.

Cypher describes property-graph patterns. SPARQL matches RDF triples, using the same representation for attributes and relationships. Datalog defines derived relations through logical rules, including recursive rules. All three let you describe a result while the engine handles execution.

Example: Describe the path as a pattern

Setup: A graph holds Maryam, her friends and the companies they work for.

Walk through it: Cypher can match a pattern such as (p)-[:KNOWS]->(f)-[:WORKS_AT]->(c) and return the company names.

What this tells you: The engine chooses how to execute the traversal. SPARQL uses triple patterns and Datalog uses relational rules to express this kind of question.

۱۳. GraphQL دقیقاً چه می‌کند و چرا محدود است؟13. What exactly does GraphQL do, and why is it limited?

GraphQL قرارداد API ـه که کلاینت باهاش فیلدهای لازم جواب رو انتخاب می‌کنه. اسمش یعنی موتور دیتابیس گراف؟ نه! قابلیت پرسش به اسکیمای API و resolverها محدوده — اسم گولت نزنه.

مثال فنی: GraphQL و N+1 پشت API

وضعیت اولیه: فرض کن کلاینت people { name jobs { title } } می‌خواد.

اجرای مرحله‌به‌مرحله: حالا GraphQL شکل پاسخ API رو مشخص می‌کنه؛ resolver بد ممکنه برای هر فرد یه query بزنه و resolver دسته‌ای این تعداد رو کم کنه.

نتیجه و دلیل: پس GraphQL نوع دیتابیس یا بهینه بودن join رو تعیین نمی‌کنه؛ رفتار واقعی به اجرای resolver بستگی داره — اسم قشنگ یعنی کار درست؟ نه!

GraphQL is an API query language: the client selects the fields it needs in a JSON response. Queries follow the API schema and its resolvers, rather than exposing arbitrary database conditions or recursion. The backend can use any database model. Those restrictions don't guarantee cheap queries or prevent DoS; resolver behavior and request limits still matter.

Example: GraphQL can still hide N+1

Setup: A client requests people { name jobs { title } }.

Walk through it: GraphQL defines the response shape. A poorly implemented resolver might run a query for every person; a batched resolver can reduce that count.

What this tells you: GraphQL doesn't choose the database model or guarantee efficient joins. Resolver implementation determines the actual work.

۱۴. event sourcing یعنی چه و چرا رویدادها را به زمان گذشته نام‌گذاری می‌کنیم؟14. What is event sourcing, and why past-tense event names?

تو Event Sourcing تغییر قبول‌شده به شکل رویداد ذخیره می‌شه و وضعیت از روش ساخته می‌شه. اسم گذشته نشون می‌ده اتفاق افتاده، نه اینکه درخواستش فرستاده شده — گذشته، نه آرزو.

مثال فنی: رویداد و نمای خواندن

وضعیت اولیه: فرض کن برای سفارش ۴۲ رویدادهای OrderPlaced و بعد OrderCancelled با شمارهٔ ترتیب ثبت می‌شن.

اجرای مرحله‌به‌مرحله: حالا projector اون‌ها رو به‌ترتیب اعمال می‌کنه و ردیف خوندنی status=cancelled می‌سازه؛ command مسیر اعتبارسنجی و ثبت رویداد رو داره.

نتیجه و دلیل: پس Event Sourcing تاریخچه رو مرجع می‌گیره؛ CQRS مسیر ثبت فرمان و نمایش نتیجه رو جدا می‌کنه و الزاماً نیازمند هم نیستن — دو تا ایدهٔ جدا که خوب با هم می‌شینن.

Event sourcing stores accepted changes as immutable events and derives state from that history. Past-tense names describe what happened. Canceling a booking appends another event instead of removing the original booking. A correction also becomes a new part of the history.

Example: An event and its read view

Setup: Order 42 records OrderPlaced, then OrderCancelled, with sequence numbers.

Walk through it: A projector applies the events in order and builds a readable row with status=cancelled. Commands take a separate path through validation and event recording.

What this tells you: Event sourcing makes history authoritative. CQRS separates the command and query models. They work together here, but neither idea requires the other.

۱۵. CQRS چه چیزی را جدا می‌کند؟15. What does CQRS separate?

CQRS مدل ثبت تغییر و مدل خوندن رو جدا می‌کنه. مدل خوندن می‌تونه برای کوئری آماده بشه؛ استفاده از لاگ رویداد شرط واجب همهٔ پیاده‌سازی‌های CQRS نیست — پسرعموئن، نه دوقلو.

مثال فنی: رویداد و نمای خواندن

وضعیت اولیه: فرض کن برای سفارش ۴۲ رویدادهای OrderPlaced و بعد OrderCancelled با شمارهٔ ترتیب ثبت می‌شن.

اجرای مرحله‌به‌مرحله: حالا projector اون‌ها رو به‌ترتیب اعمال می‌کنه و ردیف خوندنی status=cancelled می‌سازه؛ command مسیر اعتبارسنجی و ثبت رویداد رو داره.

نتیجه و دلیل: پس Event Sourcing تاریخچه رو مرجع می‌گیره؛ CQRS مسیر ثبت فرمان و نمایش نتیجه رو جدا می‌کنه و الزاماً نیازمند هم نیستن — دو تا ایدهٔ جدا که خوب با هم می‌شینن.

CQRS separates the model that accepts changes from the model that answers queries. In this chapter's design, the write path appends events and projections build materialized read views. Those views can be rebuilt by replaying the retained events with appropriate logic. CQRS can also be implemented without event sourcing.

Example: An event and its read view

Setup: Order 42 records OrderPlaced, then OrderCancelled, with sequence numbers.

Walk through it: A projector applies the events in order and builds a readable row with status=cancelled. Commands take a separate path through validation and event recording.

What this tells you: Event sourcing makes history authoritative. CQRS separates the command and query models. They work together here, but neither idea requires the other.

۱۶. بزرگ‌ترین چالش‌های event sourcing؟16. The biggest event-sourcing challenges?

بازتولید نتیجه به نسخهٔ رویداد و منطق پردازش وصله. ورودی بیرونی و حذف داده و اثرهای جانبی تکراری هم باید جدا مدیریت بشن — هرکدوم یه درد.

مثال فنی: Replay نباید پیامک تاریخی بفرستد

وضعیت اولیه: فرض کن projector گزارش، رویداد OrderPlaced سال گذشته رو دوباره می‌خونه.

اجرای مرحله‌به‌مرحله: حالا مسیر بازسازی فقط جدول گزارش رو می‌نویسه؛ ارسال پیامک مسیر اثر جانبی جدا با شناسهٔ یکتا و سیاست جلوگیری از تکرار داره.

نتیجه و دلیل: پس بازپخش محاسبه با تکرار اثر بیرونی فرق داره؛ کپی کردن همهٔ handlerهای زنده توی replay خطرناکه — پیامک دوباره نفرست، مشتری شاکی می‌شه!

Rebuilding a view depends on the event versions and processing logic. Keep processing deterministic, including the historical exchange rate if the calculation needs it. Plan how deletion requirements interact with immutable history; crypto-shredding is one approach. Separate external actions from replay so rebuilding a report doesn't resend old emails or messages. Preserve the order that dependent events require.

Example: Replay without sending old messages

Setup: A reporting projector rereads last year's OrderPlaced event.

Walk through it: The rebuild path only writes the report table. Sending a text message uses a separate side-effect path, with a unique identifier and a policy to prevent repeats.

What this tells you: Recomputing a view differs from repeating an external action. Reusing every live handler during replay could send a customer the same old message again.

۱۷. DataFrame چه جایگاهی دارد؟17. Where do DataFrames fit?

DataFrame نمایش جدولی برای تبدیل و تحلیله و با مدل‌های عددی یادگیری ماشین هم قاطی می‌شه. عملیات مشابه تو اجرای محلی و پخش‌شده خرج و رفتار یکسانی ندارن — مواظب باش.

مثال فنی: جدول در برابر آرایه

وضعیت اولیه: فرض کن فروش روزانه ستون‌های day, amount داره؛ تصویر رنگی اندازهٔ 256×256×3 داره.

اجرای مرحله‌به‌مرحله: حالا روی DataFrame، فیلتر روز و جمع مبلغ اجرا می‌شه؛ روی تصویر، محاسبه با اندیس محورهای ارتفاع و عرض و رنگ انجام می‌شه.

نتیجه و دلیل: پس هر دو دادهٔ ساخت‌یافته‌ان، ولی عملیات و معنای محورهاشون فرق داره؛ تبدیل کورکورانه مدل رو نامفهوم می‌کنه — اسم مشترک یعنی معنای مشترک؟ نه!

A DataFrame provides a table-like form for filtering, joining, grouping and transforming data during analysis. It can feed numerical ML representations, including sparse matrices and one-hot encoded categories. Arrays represent values across numerical axes. Similar-looking operations can have different costs in local and distributed execution.

Example: A table and an array

Setup: Daily sales have columns day, amount. A color image has dimensions 256×256×3.

Walk through it: A DataFrame filters sales by day and sums amounts. Image calculations use indices along height, width and color axes.

What this tells you: Both are structured data, but their operations and axes mean different things. Choose the representation around the calculation.

۶.۳ اشتباهات رایج در جواب‌های مصاحبه6.3 Common interview mistakes

  • گفتن «SQL قدیمی شده» یا «NoSQL بهتره» بدون حرف زدن از شکل رابطه‌ها و الگوی دسترسی — شعار نده.
  • یادت بره که دنرمال‌سازی = دادهٔ مشتق‌شده و کپی‌ها به‌روزرسانی می‌خوان — بی‌لوله قبول نیست.
  • ادعای «join ذاتاً کنده» — مثال تایم‌لاین خلافش رو نشون می‌ده. Hydration رو یادته؟
  • نفهمیدن فرق schema-on-read و schema-on-write تو تکامل اسکیما — دو تا دنیای جدا.
  • GraphQL رو با گراف یکی دونستن، یا محدودیت‌های عمدیش رو ندونستن — اسم گولت نزنه.
  • event sourcing رو تعریف کردن بدون determinism و بازتولیدپذیری نماها — نصف جواب.
  • Choosing SQL or NoSQL by slogan without discussing relationship shape and access patterns.
  • Copying current data without explaining how derived copies stay up to date.
  • Claiming that joins are inherently slow. Use timeline ID hydration to discuss a concrete read-time join.
  • Confusing schema-on-read with schema-on-write, especially when existing data must evolve.
  • Treating GraphQL as a graph database, or assuming its query restrictions make every resolver inexpensive.
  • Explaining event sourcing without deterministic replay, event versions and reproducible views.

۶.۴ چک‌لیست مرور ۵ دقیقه‌ای قبل از مصاحبه6.4 Five-minute pre-interview checklist

  1. سه تا فرق کلیدی مدل سندی و رابطه‌ای + کی کدوم رو انتخاب کنی — چشم‌بسته.
  2. جدول نرمال در برابر دنرمال (نوشتن/خوندن/سازگاری) — جدولش رو بکش.
  3. تعریف star schema: fact و dimension — وسط و دورش.
  4. ساختار property graph + یه جمله دربارهٔ Cypher در برابر SQL بازگشتی (۴ خط در برابر ۳۱ خط!).
  5. سه جمله دربارهٔ event sourcing و CQRS و بازتولیدپذیری — کوتاه و دقیق.
  6. قاعدهٔ انتخاب مدل: اول شکل رابطه‌ها، بعد الگوی دسترسی — ترتیب مهمه.
  1. Explain three differences between document and relational models, and when you'd choose each.
  2. Compare normalization and denormalization across writes, reads and consistency.
  3. Draw a star schema with a central fact table and surrounding dimensions.
  4. Describe a property graph and the chapter's Cypher versus recursive SQL example: 4 lines versus 31.
  5. Explain event sourcing, CQRS and reproducibility in three clear sentences.
  6. Choose a model by relationship shape and access pattern, then check its maintenance cost.
