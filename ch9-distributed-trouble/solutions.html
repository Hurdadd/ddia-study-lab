سؤال مصاحبهInterview question
فرض کن یه شمارنده یا پرداخت داری که درخواست، commit یا پاسخش ممکنه گم بشه. history هر حالت رو نشون بده. پروتکل رو با request ID، result lookup، payload binding و retention طراحی کن؛ deadline، backoff+jitter و retry budget رو هم اضافه کن.
Picture this — you've got a counter or payment where the request, commit or reply can vanish. Trace each history. Design request ID, result lookup, payload binding and retention, then add deadlines, backoff with jitter and your retry budget.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

بعد از timeout نتیجه UNKNOWN می‌ماند — درخواست گم‌شده، سرور مرده و پاسخ گم‌شده یکسان دیده می‌شوند. پس هر درخواست تغییردهنده یک شناسهٔ انتخاب caller دارد که به payload گره خورده؛ سرور اول شناسه را lookup می‌کند، روی تکرار نتیجهٔ ذخیره‌شده را برمی‌گرداند و همان شناسه با payload تازه را رد می‌کند. بازتلاش‌ها سرتاسری کران‌دارند: deadline برای هر تلاش، backoff با jitter و بودجهٔ retry — سه لایهٔ سه‌تلاشی در اوج به ۲۷ تلاش downstream می‌رسند، هرگز بیشتر.
A timeout leaves the outcome UNKNOWN — lost request, dead server, or lost reply look identical. So every mutating request carries one caller-chosen ID bound to its payload; the server looks the ID up, returns the stored result on repeats, and rejects the ID with a new payload. Retries are bounded end to end: per-attempt deadlines, backoff with jitter, and a retry budget — three layers of three attempts peak at 27 downstream tries, never more.

صورت مسئله و فرض‌هاProblem and assumptions

  • یک سرویس شمارنده، یک کلاینت و در دمو حداکثر دو تلاش برای هر درخواست (اعداد آموزشی).
  • حساب retry لایه‌ای با ۳ لایه و ۳ تلاش برای هرکدام است (اعداد آموزشی) — شکل مهم است نه ثابت‌ها.
  • لاگ نتیجه سه‌تایی (شناسه درخواست، hashpayload و نتیجه) را بیشتر از پنجرهٔ حداکثر retry نگه می‌دارد (نگهداری آموزشی) — retry بعد از پنجره شکست صریح است نه حدس.
  • One counter service, one client, at-most-two attempts per request in the demo (teaching numbers).
  • Layered-retry math uses 3 layers x 3 attempts each (teaching numbers) — the shape matters, not the constants.
  • The result log keeps (request ID, payload hash, result) past the maximum retry window (teaching retention) — retry after the window is fail-loud, not guesswork.

چرا این روش و این عددها؟Why this method and these numbers?

timeout فقط نبود پاسخ را نشان می‌دهد، نه اجرا نشدن درخواست؛ به همین دلیل retry همان intent باید ID قبلی را حمل کند. سه لایه با سه attempt می‌توانند ۳×۳×۳=۲۷ فراخوان پایین‌دست بسازند، چون هر تلاش لایهٔ بالا تمام تلاش‌های پایین را دوباره فعال می‌کند. deadline مشترک، retry budget و jitter بار را محدود می‌کنند. دو attempt در دمو برای دیدن duplicate کافی است؛ عدد production باید از نرخ خطای گذرا و ظرفیت باقی‌مانده بیاید.

Timeout proves no response arrived, not that execution did not happen; retry the same intent with the same ID. Three layers with three attempts can cause 3×3×3=27 downstream calls because each upper attempt repeats lower attempts. Shared deadlines, retry budgets and jitter bound load. Two demo attempts expose duplication; production counts depend on transient errors and spare capacity.

مدل ذهنیMental model

شبکه بعد از ارسال هیچ بدهی به تو ندارد: سکوت واقعیتی دربارهٔ پاسخ است، هرگز واقعیتی دربارهٔ درخواست نیست. پس دست از «شکست خورد؟» بردار — سؤالی که سیم نمی‌تواند جوابش دهد — و بپرس «لاگ نتیجه دربارهٔ این شناسه چه می‌گوید؟». آن‌وقت retryها فقط دوباره‌پرسیدن مؤدبانهٔ سؤالی‌اند که جواب ذخیره‌شده دارد.
The network owes you nothing after you send: silence is a fact about the reply, never a fact about the request. So stop asking 'did it fail?' — a question the wire cannot answer — and ask 'what does the result log say about this ID?' instead. Retries are then just polite re-askings of a question with a stored answer.

حل گام‌به‌گامStep by step

  1. timeout یعنی «اجرا نشد» نیست اول ناشناخته را نام ببر: timeout با سه history می‌خواند — درخواست گم (هیچی اعمال نشده)، سرور مرده (شاید اعمال شده) و پاسخ گم (اعمال‌شدهٔ تأییدنشده). هیچ مدرک سمت کلاینت آن‌ها را جدا نمی‌کند، پس طراحی باید زیر هر سه کار کند.
  2. شناسهٔ ثابت، نتیجهٔ ذخیره‌شده به قصد یک شناسه بده و به سرور یک حافظه: کلاینت برای هر قصد یک UUID می‌سازد و در retryها نگهش می‌دارد؛ سرور (شناسه، hashpayload و نتیجه) را اتمیک درج-یا-lookup می‌کند و روی تکرار نتیجهٔ ذخیره‌شده را برمی‌گرداند.
  3. گره payload، نگهداری نتایج شناسه را به payload گره بزن و بیشتر از پنجرهٔ retry نگهش دار: همان شناسه با payload متفاوت رد می‌شود (باگ کلاینت که بلند گرفته می‌شود) و lookupهای بعد از انقضای نگهداری شکست صریح می‌خورند به‌جای اعمال کور.
  4. بودجه برای لایه‌ها طوفان را کران کن نه فقط تلاش را: deadline هر تلاش دم را می‌برد، backoff به‌علاوهٔ jitter گله را پخش می‌کند و بودجهٔ مشترک retry بار را shed می‌کند — در حساب آموزشی ۳ لایه × ۳ تلاش در اوج ۲۷ تلاش downstream می‌شوند.
  1. Timeout is not 'not executed' Name the unknown first: a timeout fits three histories — request lost (nothing applied), server dead (maybe applied), reply lost (applied, unconfirmed). No client-side evidence separates them, so the design must work under all three.
  2. Same ID, stored result Give the intent one ID and the server one memory: the client mints a UUID per intent and keeps it across retries; the server inserts-or-looks-up (ID, payload hash, result) atomically, returning the stored result on repeats.
  3. Bind payload, retain results Bind the ID to the payload and keep it past the retry window: the same ID with a different payload is rejected (client bug, caught loud), and lookups after retention expiry fail loud instead of applying blind.
  4. Budget the layers Bound the storm, not just the attempt: per-attempt deadlines cut tails, backoff plus jitter spreads the herd, and a shared retry budget sheds load — 3 layers x 3 attempts peak at 27 downstream tries in the teaching math.

طراحی مشخصConcrete design

شناسهٔ درخواست: یک UUID برای هر قصد caller که کلاینت قبل از اولین ارسال می‌سازد و در retryها نگه می‌دارد. جدول سرور (request_id UNIQUE, payload_hash, result, kept_until): هنگام رسیدن، درج-یا-lookup در یک گام اتمیک — شناسهٔ حاضر نتیجهٔ ذخیره‌شده را برمی‌گرداند (یا روی ناسازگاری payload رد می‌کند) و شناسهٔ غایب یک‌بار اعمال و ذخیره می‌شود. نگهداری طولانی‌ترین پنجرهٔ retry به‌علاوهٔ slack ساعت را پوشش می‌دهد؛ خواندن بعد از انقضا شکست صریح است. هر retry همان شناسه را دارد با deadline هر تلاش، backoff و jitter، و از بودجهٔ مشترک retry خرج می‌کند که هنگام کندی downstream بار را shed می‌کند.

Request ID: one UUID per caller intent, minted by the client before the first send and kept across retries. Server table (request_id UNIQUE, payload_hash, result, kept_until): on arrival, insert-or-lookup in one atomic step — a present ID returns its stored result (or rejects on payload mismatch), an absent ID applies once and stores. Retention covers the longest retry window plus clock slack; reads after expiry fail loud. Every retry carries the same ID, a per-attempt deadline, backoff with jitter, and charges a shared retry budget that sheds load when the downstream is slow.

مثال محاسبه‌شدهWorked example

حساب آموزشی: ۳ لایه و هرکدام تا ۳ تلاش، پس بدترین fan-out به downstream برای یک تلاش caller برابر ۳×۳×۳ = ۲۷ تلاش است. بودجهٔ مشترک retry به اندازهٔ آموزشی ۱۰٪ ترافیک یعنی ۲۸مین retry هم‌زمان به‌جای پیوستن به رمّه صبر می‌کند یا بلند شکست می‌خورد. backoff با jitter بازمانده‌ها را پخش می‌کند: بدون آن هر ۲۷تایی هم‌قدم می‌رسند؛ با آن در پنجرهٔ backoff پخش می‌شوند و downstream میان موج‌ها نفس می‌کشد.

Teaching math: 3 layers, up to 3 attempts each, so the worst downstream fan-out is 3 x 3 x 3 = 27 attempts for one caller try. A shared retry budget of a teaching 10% of traffic means the 28th concurrent retry waits or fails loud instead of joining the stampede. Backoff with jitter spreads the survivors: without it all 27 arrive in lockstep; with it they spread across the backoff window and the downstream recovers between waves.

  2. The reply is lost on the wire, so the client times out with outcome UNKNOWN — applied or not, the wire looks the same.

نقطهٔ تصمیم: نقطهٔ تصمیم پیکان lookup-قبل-از-اعمال است: هر رسیدن، چه اول چه retry، قبل از هر اثر از lookup شناسه می‌گذرد. بدون lookup، امنیتی نیست.

تضمین نشان‌داده‌شده: شکل نشان می‌دهد retry با lookup نتیجه در یک اثر جمع می‌شود و ناسازگاری payload رد می‌شود. طوفان retry میان لایه‌ها را کران نمی‌کند — آن کار نمودار اسمبل است.

تضمین نشان‌نداده‌شده: دربارهٔ مدت نگهداری نتایج، سرنوشت بعد از انقضا و ضرب تلاش‌ها میان لایه‌ها چیزی نمی‌گوید — همه بیرون این شکل‌اند.

خودآزماییSelf-check

پاسخ گم شده ولی اثر اعمال شده. چرا retry با شناسهٔ ثابت دو بار شارژ نمی‌کند؟

پاسخ: چون سرور قبل از اعمال شناسه را lookup می‌کند: req-7 تکراری به counter=1 ذخیره‌شده می‌خورد و همان را برمی‌گرداند. شناسهٔ تازه نو به‌نظر می‌رسد، پس بار دوم اعمال می‌شود.

The reply was lost but the effect applied. Why does the same-ID retry not double-charge?

Answer: Because the server looks the ID up before applying: the retried req-7 hits the stored counter=1 and returns it. A fresh ID looks new, so it applies a second time.

گزینه‌های جایگزینAlternatives

  • اول خواندن وضعیت وقتی نتیجه قابل استعلام است («req-7 را اعمال کردی؟»): یک lookup می‌تواند ناشناخته را بدون هیچ سیاست retry حل کند. وقتی خواندن ارزان و لاگ نتیجه با شناسه درخواست ایندکس شده، ارزان‌تر از idempotency کامل است — ولی وقتی عملیات حالت خواندنی ندارد بی‌فایده است.
  • شکست صریح وقتی عملیات نه idempotent است نه قابل استعلام: خطای صریح برگردان و بگذار انسان یا لایه بالاتر مغایرت را حل کند. قیمتش یک شکست visible است و سودش صفر corruption — وقتی شارژ دوباره بدتر از درخواست ردشده است، تریدآف درست همین است.
  • Read-back-first when the outcome is queryable ('did you apply req-7?'): one lookup can settle the unknown without any retry policy. Cheaper than full idempotency when reads are cheap and the result log is indexed by request ID — but useless when the operation has no readable state.
  • Fail-loud when the operation is neither idempotent nor queryable: return an explicit error and let a human or a higher layer reconcile. Costs a visible failure, buys zero corruption — the right trade when a double charge is worse than a rejected request.

سناریوهای خرابیFailure scenarios

  • طوفان retry روی downstream کند: بدون بودجه هر کلاینت هم‌زمان می‌کوبد و retryهای لایه‌ای چندبرابر می‌شوند (تا ۲۷ برابر). نگهبان: بودجهٔ مشترک retry، backoff به‌علاوهٔ jitter، deadline هر تلاش و shed کردن بار وقتی بودجه خالی شد.
  • گم شدن ورودی لاگ نتیجه قبل از پایان نگهداری (خرابی دیسک یا انقضای زود): retry بعد نو به‌نظر می‌رسد و دو بار اعمال می‌شود. نگهبان: ذخیرهٔ بادوام و تکثیرشدهٔ نتیجه و شکست صریح بعد از پنجرهٔ نگهداری به‌جای حدس.
  • قاطی payload: دو قصد متفاوت caller یک شناسه را شریک می‌شوند (باگ کلاینت). بررسی binding دومین payload را رد می‌کند — بلند و امن و قابل debug — به‌جای اعمال بی‌صدای قصد اشتباه.
  • Retry storm on a slow downstream: without a budget every client hammers at once and layered retries multiply (up to 27x). Guard with a shared retry budget, backoff plus jitter, per-attempt deadlines, and load shedding when the budget drains.
  • Result-log entry lost before retention ends (disk loss, early expiry): a retry then looks new and double-applies. Guard with durable, replicated result storage and fail-loud after the retention window instead of guessing.
  • Payload confusion: two different caller intents share one ID (client bug). The binding check rejects the second payload — loud, safe, and debuggable — instead of silently applying the wrong intent.

import java.util.*;
// Teaching demo: after a timeout the client knows NOTHING - the request may
// be lost, the server may have crashed, or the reply may be lost. Retry with
// the SAME request ID collapses repeats into one effect; a fresh ID doubles it.
public class TimeoutDemo {
    // What really happened on the server for one client request.
    enum Truth { LOST_REQUEST, CRASHED_BEFORE_APPLY, APPLIED_REPLY_LOST }
    static class Server {
        int effects = 0;                       // real-world effects applied
        Map<String, String> results = new HashMap<>(); // request ID -> stored result
        Map<String, String> payloadOf = new HashMap<>(); // request ID -> bound payload
        // Returns the result string; null means "client never sees it".
        String apply(String reqId, String payload, boolean replyLost) {
            if (results.containsKey(reqId)) {
                if (!payloadOf.get(reqId).equals(payload)) return "REJECTED: id reused with new payload";
                return results.get(reqId) + " (duplicate suppressed)";
            }
            payloadOf.put(reqId, payload);
            effects++;
            String r = "ok counter=" + effects;
            results.put(reqId, r);
            return replyLost ? null : r;
        }
    }
    // One client request with ONE retry. naive=false reuses the request ID.
    static String run(Truth truth, boolean naive) {
        Server s = new Server();
        String id = "req-7";
        String first = null;
        switch (truth) {
            case LOST_REQUEST -> first = null;                       // never arrived
            case CRASHED_BEFORE_APPLY -> first = null;               // died doing nothing
            case APPLIED_REPLY_LOST -> first = s.apply(id, "pay-100", true);
        }
        boolean timeout = (first == null);                            // client only sees silence
        String retryId = naive ? "req-7-again" : id;                  // naive = fresh ID
        String second = s.apply(retryId, "pay-100", false);
        return "timeout=" + timeout + " outcome=UNKNOWN retry=" + second + " effects=" + s.effects;
    }
    public static void main(String[] a) {
        for (Truth t : Truth.values()) {
            System.out.println(t + " naive-retry  -> " + run(t, true));
            System.out.println(t + " same-id-retry -> " + run(t, false));
        }
        int layers = 3, attempts = 3;                                 // teaching numbers
        int worst = (int) Math.pow(attempts, layers);                 // 3^3
        System.out.println("layered worst case = " + attempts + "^" + layers + " = " + worst + " downstream attempts");
        Server s = new Server();
        s.apply("req-7", "pay-100", false);
        System.out.println("payload binding -> " + s.apply("req-7", "pay-999", false));
        System.out.println("OK: unknown stays unknown; same ID keeps one effect");
    }
}

ناورداها: شناسه‌های متمایز هرکدام یک‌بار اعمال می‌شوند (شمارش اثر برابر شمارش شناسهٔ متمایز)؛ همان شناسه با همان payload بعد از N تکرار هنوز یک اثر دارد؛ همان شناسه با payload تازه رد می‌شود، هرگز اعمال نه. معیارها: نرخ retry هر وابستگی، رویدادهای خالی شدن بودجه، سن قدیمی‌ترین نتیجهٔ منقضی‌نشده و دم تأخیر تلاش‌ها — وقتی بودجه سریع‌تر از نرخ آموزشی خالی شد هشدار بده.
Invariants: distinct IDs applied once each (effect count equals distinct-ID count); same ID plus same payload retried N times still yields one effect; same ID plus new payload is rejected, never applied. پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (سینیور): حالا سه لایه داری که هر کدوم تا سه بار retry می‌کنن. حداکثر چند تلاش به downstream می‌رسه؟ حساب کن.Follow-up (Senior): You've got three layers each making up to three attempts. What's your maximum downstream attempts?

۲۷. هر لایه یک تلاش ورودی را تا سه تلاش downstream می‌کند و لایه‌ها ضربی روی هم می‌نشینند: ۳×۳×۳. این بدترین حالت بدون بودجه و بدون deadline است که دم را ببرد — عدد آموزشی فرض می‌کند هر لایه تلاش‌هایش را تمام می‌کند. در پروداکشن با بودجهٔ مشترک retry (کسری از ترافیک)، deadline هر تلاش و backoff jitterدار سقفش می‌زنی تا ۲۷تایی هرگز هم‌قدم نرسند.

27. Each layer turns one incoming attempt into up to three downstream attempts, and the layers stack multiplicatively: 3 x 3 x 3. That is the worst case with no budget and no deadline cutting tails — the teaching number assumes every layer exhausts its attempts. In production you cap it with a shared retry budget (a fraction of traffic), per-attempt deadlines, and jittered backoff so the 27 never arrive in lockstep.

پیگیری (استف): downstream کند است و هر کلاینت retry می‌کند. اول چه چیزی می‌شکند و کدام دستگیره را می‌چرخانی؟Follow-up (Staff): The downstream is slow and every client retries. What breaks first, and which knob do you turn?

اول بودجه و بعد deadline — به‌علاوهٔ jitter. اول بودجهٔ مشترک retry وقتی downstream از قبل مریض است تلاش تازه را متوقف می‌کند (این تنها دستگیره‌ای است که بار سرتاسری را می‌بیند). بعد deadline هر تلاش، تلاش آویزان را می‌برد تا یک وابستگی کند نتواند همهٔ workerها را نگه دارد. jitter بازمانده‌ها را پخش می‌کند تا هم‌قدم نرسند و shed کردن بار اضافه را با خطای صریح می‌اندازد به‌جای صف کردنش. بدون بودجه، backoff به‌تنهایی فقط همان رمّهٔ ۲۷برابری را عقب می‌اندازد.

The budget and the deadline, in that order — plus jitter. First the shared retry budget stops new attempts when the downstream is already sick (this is the only knob that sees global load). Then per-attempt deadlines cut each hanging try so one slow dependency cannot hold every worker. Jitter spreads the survivors so they do not arrive in lockstep, and load shedding drops the excess with an explicit error instead of queueing it. Without the budget, backoff alone just delays the same 27x stampede.

پیگیری (استف): در overload چرا retry و rate limit را با هم طراحی می‌کنی؟Follow-up (Staff): Why design retries and rate limiting together?

retry ورودی تازه تولید می‌کند ولی ظرفیت سرویس را بیشتر نمی‌کند. در token bucket، refill r درخواست/ثانیه از ظرفیت پایدارِ اندازه‌گیری‌شده با حاشیه می‌آید و burst b از کار اضافی قابل‌تحمل در deadline صف: اگر ظرفیت آزاد c و انتظار مجاز T باشد، b≤c×T یک کران آموزشی است. صف را کران‌دار نگه دار، 429/503 و Retry-After بده، retry را در یک لایه با deadline و jitter محدود کن. ظرفیت و fairness هر tenant را جدا بسنج.

Retries add arrivals, not capacity. Choose token-bucket refill r from measured sustainable capacity with margin and burst b from spare capacity c times the tolerated queue wait T: b≤c×T is a teaching bound. Bound queues, return 429/503 with Retry-After and limit retries to one layer with deadlines and jitter. Measure capacity and per-tenant fairness.

اشتباهات رایجCommon mistakes

  • خواندن timeout به‌معنای «اجرا نشد» و ارسال کورکورانهٔ دوباره: در حالت پاسخ‌گمشده اثر از قبل هست، پس ارسال دوباره دوتایش می‌کند. timeout یعنی ناشناخته — همیشه.
  • ساختن شناسهٔ تازه برای هر تلاش: سرور نمی‌تواند retry را به اصلی وصل کند، پس dedup هرگز عمل نمی‌کند و هر retry یک شارژ تازه است. شناسه مال قصد caller است نه مال تلاش.
  • retry بی‌کران در هر لایه: سه سیاست معصوم «۳ بار retry» روی هم می‌نشینند و ۲۷ تلاش downstream می‌شوند و بدون jitter هم‌قدم می‌رسند. تلاش‌ها را سرتاسری با بودجه کران کن، نه فقط محلی با شمارش.
  • Reading a timeout as 'it did not execute' and blindly resending: in the lost-reply case the effect already exists, so the resend doubles it. Timeout means unknown — always.
  • Minting a fresh request ID per attempt: the server cannot link the retry to the original, so dedup never fires and every retry is a new charge. The ID belongs to the caller intent, not to the attempt.
  • Unbounded retries at every layer: three innocent-looking 'retry 3 times' policies stack into 27 downstream attempts, and without jitter they arrive in lockstep. Bound attempts globally with a budget, not just locally with a count.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

زمان دیواری stamp می‌زند و monotonic اندازه می‌گیرد — فقط در یک ماشین و هرگز جابه‌جا. duration و timeout و انتظار TTL را با CLOCK_MONOTONIC بسنج؛ زمان دیواری فقط برای stamp لاگ برای انسان. skew واقعی دو host/VM مستقل می‌خواهد به‌علاوهٔ عدم‌قطعیت نمونه‌برداری (نصف RTT)؛ دو کانتینر روی یک host ساعت مشترک دارند و هیچ‌چیز را ثابت نمی‌کنند. جابه‌جایی‌های mock با برچسب MOCK می‌آیند و stamp دیواری هرگز last-writer-wins را تعیین نمی‌کند — ساعت ۲۵۰ms جلوتر، نوشتهٔ واقعاً دیرتر را دفن می‌کند.
Wall time stamps, monotonic measures — on one host only, and never the twain. Measure durations, timeouts and TTL waits with CLOCK_MONOTONIC; use wall time only to stamp logs for humans. Real skew needs two independent hosts or VMs plus the sampling uncertainty (half the RTT); two containers on one host share a clock and prove nothing. Mocked shifts are labelled MOCK, and wall timestamps never decide last-writer-wins — a 250ms-ahead clock buries a genuinely later write.

صورت مسئله و فرض‌هاProblem and assumptions

  • اعداد دمو MOCK آموزشی‌اند: skew جلو بودن B به‌اندازهٔ ۲۵۰ms، RTT نمونه ۴۰ms، گام NTP به‌اندازهٔ ۵۰۰ms- و ۱۲۰ms کار واقعی.
  • دو ماشین یعنی دو ساعت مستقل (VM/host جدا)؛ یک host با دو کانتینر یعنی یک ساعت.
  • رجیستر LWW مقداری را نگه می‌دارد که بزرگ‌ترین timestamp دیواری را دارد و مساوی‌ها دلبخواهی شکسته می‌شوند.
  • Demo numbers are teaching MOCKS: +250ms B-ahead skew, 40ms sample RTT, -500ms NTP step, 120ms of real work.
  • Two hosts means two independent clocks (separate VMs/hosts); one host with two containers means one clock.
  • LWW register keeps the value with the greatest wall timestamp, ties broken arbitrarily.

چرا این روش و این عددها؟Why this method and these numbers?

RTT/2 برآورد تأخیر یک‌طرفه تحت فرض تقارن است، نه اندازه‌گیری دقیق آن. اختلاف مسیر رفت و برگشت offset برآوردشده را جابه‌جا می‌کند؛ timestamp exchange یک بازهٔ ممکن برای offset می‌دهد و باید پردازش و drift طی نمونه‌گیری حساب شوند. ۲۵۰ms جابه‌جایی و ۵۰۰ms step برای واضح‌شدن اثر انتخاب شده‌اند؛ هر skew بزرگ‌تر از فاصلهٔ واقعی دو write می‌تواند ترتیب LWW را برعکس کند. monotonic برای مدت است چون با اصلاح ساعت دیواری عقب نمی‌پرد.

RTT/2 estimates one-way delay under symmetry; it is not a measured one-way delay. Asymmetry shifts offset estimates, so timestamp exchange should report a possible interval with processing and drift accounted for. The 250ms skew and 500ms step make the effect visible; skew exceeding the true write separation can reverse LWW order. Monotonic clocks measure local duration without wall-clock steps.

مدل ذهنیMental model

هر ساعت یک سؤال را خوب جواب می‌دهد و بقیه را بد: monotonic می‌داند «چقدر طول کشید» در همین ماشین، دیواری می‌داند «ساعت چند است» تقریباً همه‌جا و هیچ‌کدام نمی‌دانند «کدام نوشته آخر آمد» میان ماشین‌ها. skew یک عدد نیست — یک عدد است به‌علاوهٔ عدم‌قطعیت به‌علاوهٔ برچسب روش (REAL یا MOCK). هر کدام از سه‌تا را فراموش کنی، اندازه‌گیری شایعه است.
Every clock answers one question well and the others badly: monotonic knows 'how long' on this host, wall knows 'what time is it' roughly everywhere, and neither knows 'which write came last' across hosts. Skew is not a number — it is a number plus an uncertainty plus a method tag (REAL or MOCK). Forget any of the three and the measurement is a rumor.

حل گام‌به‌گامStep by step

  1. هر ساعت یک کار ساعت‌ها را با کار جدا کن: monotonic برای چقدر طول کشید در یک ماشین — duration و timeout و انتظار TTL؛ دیواری برای ساعت چند است برای انسان و لاگ. گام NTP در دمو ۱۲۰ms کار را به duration دیواری ۳۸۰ms- تبدیل می‌کند ولی monotonic دقیق می‌ماند.
  2. دو ماشین به‌علاوهٔ عدم‌قطعیت skew واقعی را روی دو host/VM مستقل بسنج: timestamp ردوبدل کن، RTT را نصف کن برای عدم‌قطعیت (RTT برابر ۴۰ms می‌دهد ۲۰ms+-) و اختلاف خام به‌علاوهٔ عدم‌قطعیت به‌علاوهٔ روش را گزارش بده. کانتینرهای یک host ساعت مشترک دارند — آن آزمایش از روی ساختار ~۰ اندازه می‌گیرد.
  3. آشکارا mock کن یا اصلاً نکن وقتی دو ماشین نداری، آشکارا mock کن: جابه‌جایی اعلام‌شده تزریق کن (۲۵۰+ روی B)، به هر عدد جابه‌جاشده برچسب MOCK بزن و حساب عدم‌قطعیت را یکسان نگه دار. mock سازوکار را یاد می‌دهد؛ فقط برچسب است که نمی‌گذارد اندازه‌گیری دروغین شود.
  4. stamp دیواری هرگز داوری نمی‌کند هرگز روی دیواری مرتب نکن: با ۲۵۰ms جلو بودن B، نوشتهٔ حقیقت-t برای B (با stamp برابر t+250) بر نوشتهٔ حقیقت-t+100 برای A (با stamp برابر t-400) می‌چربد — LWW نوشتهٔ زودتر را نگه می‌دارد و دیرتر را بی‌صدا می‌اندازد. last-write میان‌ماشینی علیت یا انتظار عدم‌قطعیت می‌خواهد، هرگز مقایسهٔ stamp.
  1. One job per clock Split the clocks by job: monotonic (CLOCK_MONOTONIC) for how-long on one host — durations, timeouts, TTL waits; wall (CLOCK_REALTIME) for what-time for humans and logs. The demo's NTP step turns 120ms of work into a -380ms wall duration while monotonic stays exact.
  2. Two hosts plus uncertainty Measure real skew on two independent hosts or VMs: exchange timestamps, halve the RTT for the uncertainty (40ms RTT gives +-20ms), and report raw diff plus uncertainty plus method. Containers on one host share the clock — that experiment measures ~0 by construction.
  3. Mock openly or not at all When you cannot use two hosts, mock openly: inject a stated shift (+250ms on B), label every shifted number MOCK, and keep the uncertainty math identical. A mock teaches the mechanism; only the label keeps it from becoming a false measurement.
  4. Wall stamps never arbitrate Never order on wall: with B 250ms ahead, B's truth-t write (stamp t+250) beats A's truth-t+100 write (stamp t-400) — LWW keeps the earlier write and drops the later one silently. Cross-host last-write needs causality or an uncertainty wait, never a stamp compare.

گزینه‌های جایگزینAlternatives

  • انتظار عدم‌قطعیت به‌سبک TrueTime: وقتی کران عدم‌قطعیت ساعت epsilon را داری، نویسنده epsilon بعد از timestamp صبر می‌کند بعد commit می‌کند و زمان دیواری را به ترتیب امن تبدیل می‌کند به قیمت latency. درست وقتی ترتیب میان‌ماشینی روی stamp دیواری اجتناب‌ناپذیر است — برای timeout و duration که monotonic رایگان است زیاده‌روی است.
  • ساعت منطقی برای ترتیب: timestamp لمپورت یا بردار نسخه «کی آخر نوشت» را از علیت می‌فهمد نه از خوانش دیواری. درست هر وقتی که نویسنده‌ها روی ماشین‌هایی‌اند که به ساعتشان اعتماد نداری — که میان ماشین‌ها همیشه همین است.
  • TrueTime-style uncertainty waits: when you have a bounded clock uncertainty epsilon, a writer waits epsilon past its timestamp before committing, turning wall time into safe order at the cost of latency. Right when cross-host order on wall stamps is unavoidable — overkill for timeouts and durations, where monotonic is free.
  • Logical clocks for order: Lamport timestamps or version vectors decide 'who wrote last' from causality, not from wall readings. Right whenever writers live on machines whose clocks you do not trust — which, across hosts, is always.

سناریوهای خرابیFailure scenarios

  • NTP ساعت دیواری را عقب می‌برد: هر duration و timeout و TTL دیواری‌سنج همان لحظه دروغ می‌گوید (دمو برای ۱۲۰ms کار، ۳۸۰ms- نشان می‌دهد). نگهبان: همهٔ spanها را با ساعت monotonic بسنج؛ دیواری فقط برای stamp است.
  • مقایسهٔ monotonic میان ماشین‌ها: monoA=999 در برابر monoB=5 قاطع به‌نظر می‌رسد و هیچ معنایی ندارد — صفرهای متفاوت و نرخ‌های متفاوت. نگهبان: هرگز مقایسه‌شان نکن؛ ترتیب میان ماشین‌ها ساعت منطقی یا بازهٔ عدم‌قطعیت می‌خواهد.
  • «آزمایش skew» تک‌ماشینی: دو کانتینر روی یک host ساعت زیرین مشترک دارند (مگر namespace زمانی جداشان کند)، پس اختلاف اندازه‌گیری‌شده ~۰ است و دربارهٔ skew واقعی هیچ‌چیز را ثابت نمی‌کند. نگهبان: دو host/VM مستقل یا برچسب MOCK برای جابه‌جایی و گزارش عدم‌قطعیت مبتنی بر RTT.
  • LWW با stamp دیواری میان نویسنده‌ها: نوشتهٔ زودتر ساعت جلوتر بر نوشتهٔ واقعاً دیرتر می‌برد، بی‌صدا. نگهبان: هرگز روی stamp دیواری مرتب نکن — علیت per-key یا ساعت منطقی یا انتظار عدم‌قطعیت.
  • NTP steps the wall clock backwards: every wall-measured duration, timeout and TTL in flight lies at that moment (the demo shows -380ms for 120ms of work). Guard by measuring all spans on the monotonic clock; wall is for stamps only.
  • Cross-host monotonic compare: monoA=999 against monoB=5 looks decisive and means nothing — different zeroes, different rates. Guard by never comparing them; order across hosts needs logical clocks or uncertainty intervals.
  • Single-host 'skew experiment': two containers on one host share the underlying clock (unless time namespaces split them), so the measured diff is ~0 and proves nothing about real skew. Guard with two independent hosts/VMs, or label the shift MOCK and report the RTT-based uncertainty.
  • Wall-stamped LWW across writers: the ahead clock's earlier write wins over the later real write, silently. Guard by never ordering on wall stamps — use per-key causality, logical clocks, or an uncertainty wait.

import java.util.*;
// Teaching demo with EXPLICITLY MOCKED clocks (labelled MOCK - not a real
// two-host measurement). Host B's wall clock runs 250ms ahead. Shows:
// wall breaks durations when NTP steps it; monotonic is safe for durations
// but meaningless across hosts; LWW lets the wall-ahead write bury a later one.
public class SkewDemo {
    static class MockWall { long offset; long now(long truth) { return truth + offset; } }
    static class Mono { long t; long now() { return t; } void advance(long d) { t += d; } }
    public static void main(String[] a) {
        MockWall wallA = new MockWall(), wallB = new MockWall();
        wallB.offset = 250;                                            // MOCK skew: B ahead 250ms
        long truth = 1_000_000;
        long sampleA = wallA.now(truth), sampleB = wallB.now(truth);
        long rtt = 40;                                                 // MOCK round-trip of the sample
        System.out.println("MOCK wallA=" + sampleA + " wallB=" + sampleB
            + " rawDiff=" + (sampleB - sampleA) + "ms rtt=" + rtt + "ms uncertainty=+-" + (rtt / 2) + "ms");
        Mono mono = new Mono();
        mono.advance(120);                                             // real work takes 120ms
        long wallStart = wallA.now(truth);
        wallA.offset -= 500;                                           // MOCK NTP step: wall jumps back
        long wallDur = wallA.now(truth + 120) - wallStart;             // wall-measured duration
        System.out.println("MOCK NTP step -500ms: wall duration=" + wallDur + "ms (lies) mono duration="
            + mono.now() + "ms (true) -> timeouts/TTL must use monotonic");
        Map<String, String> reg = new HashMap<>();                     // LWW register
        Map<String, Long> ts = new HashMap<>();
        // B writes at its wall time (truth t, wall t+250); A writes LATER (truth t+100) at wall t+100.
        reg.put("k", "from-B"); ts.put("k", wallB.now(truth));
        long tsA = wallA.now(truth + 100);                             // wallA offset is now -500
        if (tsA > ts.get("k")) { reg.put("k", "from-A"); ts.put("k", tsA); }
        System.out.println("LWW keeps=" + reg.get("k") + " (B's earlier write buries A's later write)");
        Mono mA = new Mono(), mB = new Mono();
        mA.advance(999); mB.advance(5);
        System.out.println("monoA=" + mA.now() + " monoB=" + mB.now()
            + " -> cross-host compare is meaningless (different zeroes)");
        System.out.println("OK: real skew needs two independent hosts; mock is labelled mock");
    }
}

Monotonic — CLOCK_MONOTONIC — for both. اشتباهات رایجCommon mistakes

  • اندازه‌گیری «skew» با دو کانتینر روی یک host: ساعت زیرین مشترک و اختلاف ~۰ و صفر اطلاعات دربارهٔ واگرایی واقعی. استقلال یعنی ساعت‌های کرنل جدا، نه namespace جدا.
  • مقایسهٔ خوانش‌های monotonic میان ماشین‌ها (monoA با monoB): هرکدام از بوت خودش شروع و با نرخ خودش می‌زند — مقایسه عددبازی است. monotonic اکیداً تک‌ماشینی است.
  • مرتب کردن نوشته‌ها با timestamp دیواری (LWW روی دیواری): سریع‌ترین دروغگو می‌برد — نوشتهٔ کهنهٔ ساعت جلوتر بدون خطا بر نوشتهٔ دیرتر صادق می‌چربد. stampهای دیواری ثبت می‌کنند، داوری نمی‌کنند.
  • Measuring 'skew' with two containers on one host: same underlying clock, ~0 diff, zero information about real divergence. Independence means separate kernels Clocks, not separate namespaces.
  • Comparing monotonic readings across hosts (monoA vs monoB): each starts at its own boot and ticks its own rate — the comparison is numerology. Monotonic is strictly single-host.
  • Ordering writes by wall timestamps (LWW on wall): the fastest liar wins — an ahead clock's stale write beats a later honest one with no error. Wall stamps record, they do not arbitrate.

سؤال مصاحبهInterview question
قضیه اینه که کارگر A با lease و token=7 pause می‌شه و B با token=8 می‌نویسه؛ بعد A بیدار می‌شه. storage باید stale epoch رو اتمیک رد کنه. چند write معتبر تو یه epoch رو از duplicate operation جدا کن و برای token allocation و دوام highest-seen شرط تعریف کن.
Think of it — owner A pauses at token 7, B grabs token 8 and writes, then A wakes up. Enforce atomic stale-epoch rejection in storage. Distinguish multiple legitimate same-epoch writes from duplicate operations and pin down token allocation plus highest-token durability.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

توکن fencing نام epoch در lease است — ۷ و بعد ۸ — نه هر نوشته. وقتی B در epoch هشت تحویل می‌گیرد و می‌نویسد، storage مقدار highest=8 را ثبت می‌کند؛ وقتی Aی pauseشده با epoch هفت بیدار می‌شود، storage کنار داده epoch کهنه را اتمیک رد می‌کند. نوشته‌های مجاز هم‌epoch (مثل op-b1 و op-b2 برای B) با شناسهٔ عملیات از هم جدا می‌شوند و op تکراری بدون اثر دوم dedup می‌شود. بزرگ‌ترین epoch دیده‌شده باید بادوام باشد: restartای که فراموشش کند دوباره epochهای کهنه را می‌پذیرد.
A fencing token names the lease epoch — 7, then 8 — not each write. When B takes over at epoch 8 and writes, storage records highest=8; when paused A wakes with epoch 7, storage atomically rejects the stale epoch beside the data. Legitimate same-epoch writes (B's op-b1 and op-b2) are told apart by operation ID, and a repeated op is deduped without a second effect. The highest-seen epoch must be durable: a restart that forgets it accepts stale epochs again.

صورت مسئله و فرض‌هاProblem and assumptions

  • epochهای ۷ و بعد ۸ با یک نگهدارندهٔ pauseشدهٔ A و یک جانشین B (سناریوی آموزشی از brief).
  • lock serviceepochهای بادوام و صعودی صادر می‌کند؛ storage اتمیک مقایسه و نوشتن می‌کند (در دمو یک گام synchronized).
  • op_id برای هر عملیات منطقی یکتاست و در تمام retryهای همان عملیات ثابت می‌ماند؛ dedup تا وقتی بازتحویل معتبر ممکن است حفظ می‌شود.
  • Epochs 7 then 8, one paused holder A and one successor B (teaching scenario from the brief).
  • The lock service issues durable, monotonic epochs; storage compares and writes atomically (single synchronized step in the demo).
  • An op_id uniquely identifies a logical operation and remains unchanged across its retries; retain dedup while valid redelivery remains possible.

چرا این روش و این عددها؟Why this method and these numbers?

عدد epoch فقط ترتیب مالکیت است؛ ۷ و ۸ را می‌توان با هر دو عدد افزایشی جایگزین کرد. شرط token<highest رد می‌کند تا مالک تازه بتواند چند write هم‌epoch انجام دهد؛ شرط سخت token>highest برای هر write، عملیات دوم همان مالک را اشتباه رد می‌کند. op_id برای هویت همان عملیات و retry آن است و باید در retry ثابت بماند. ذخیرهٔ highest و dedup کنار داده ضروری است چون restart حافظهٔ فرایند را پاک می‌کند.

Epoch numbers order ownership; any increasing pair can replace 7 and 8. Reject token<highest so the current owner can perform multiple same-epoch writes; requiring token>highest for every write wrongly rejects its second operation. Keep op_id stable across retries of one operation. Persist highest and dedup with data because restart erases process memory.

مدل ذهنیMental model

lease قولی دربارهٔ آینده است («تا زمان T هیچ‌کس دیگر نمی‌نویسد») و pause قول‌ها را می‌شکند — نگهدارنده نمی‌تواند بشنود که وقتش تمام شده. fencing دست از اعتماد به ساعت نگهدارنده می‌کشد و به حساب اعتماد می‌کند: هر نوشته شمارهٔ epoch خودش را دارد و storage که وسط مقایسه pause نمی‌شود، کوچک‌تر را رد می‌کند. توکن رمز نیست (A همان ۷ خودش را می‌داند) — شمارندهٔ نسل است و نسل‌های قدیم فقط نمی‌نویسند.
A lease is a promise about the future ('nobody else writes until T'), and a pause breaks promises — the holder cannot hear that its time is over. Fencing stops trusting the holder's clock and trusts arithmetic instead: every write carries its epoch number, and storage, which never pauses mid-compare, rejects the smaller one. The token is not a password (A knows its own 7) — it is a generation counter, and old generations simply do not write.

حل گام‌به‌گامStep by step

  1. انقضا خواب‌آلود را متوقف نمی‌کند ببین چرا انقضا امنیت نیست: lease هفت تمام می‌شود و Bepoch هشت را می‌گیرد ولی Aی pauseشده هرگز نمی‌فهمد — نوشتهٔ epoch-7 او بعداً با اعتماد کامل می‌رسد. هر نگهبانی که در ذهن A زندگی کند (تایمرها و ساعت‌های lease) نگهبانی خواب‌آلود است.
  2. رد epoch کهنه در storage رأی را به storage منتقل کن: هر نوشته (توکن و شناسهٔ op) را دارد؛ storage اتمیک توکن کمتر از بزرگ‌ترین دیده‌شده را رد می‌کند و بالاترین تازه را ثبت می‌کند و فقط بعد اعمال می‌کند. نویسندهٔ pauseشده کنار داده خلع‌سلاح می‌شود نه کنار ساعت خودش.
  3. epoch برای نوبت و op برای تلاش دو هویت را جدا کن: epoch می‌گوید نوبت کیست (یک epoch زنده برای هر منبع) و شناسهٔ عملیات می‌گوید این کدام تلاش است. هم‌epoch با op تازه دومین نوشتهٔ مجاز است؛ هم‌epoch با op دیده‌شده تکرار برای جذب است.
  4. دوام همان نرده است رأی را persist کن: بزرگ‌ترین دیده‌شده و مجموعهٔ op اعمال‌شده روی ذخیرهٔ بادوام با داده زندگی می‌کنند و قبل از تأیید نوشته می‌شوند. restartای که فراموششان کند epochهای کهنه را می‌پذیرد — همان خط HAZARD در دمو — پس فقط حافظه باگ fencing است.
  1. Expiry cannot stop a sleeper See why expiry is not safety: A's lease ends, B is granted epoch 8, but paused A never learns this — its epoch-7 write arrives later in full confidence. Any guard that lives in A's head (timers, lease clocks) cannot guard a sleeper.
  2. Reject stale epochs in storage Move the verdict into storage: every write carries (token, opId); storage atomically rejects token below highest-seen, records the new highest, and only then applies. The paused writer is disarmed at the data, not at its own clock.
  3. Epoch for turn, op for attempt Split the two identities: the epoch says whose turn it is (one live epoch per resource), the operation ID says which attempt this is. Same epoch plus new op is a second legitimate write; same epoch plus seen op is a retry to absorb.
  4. Durability is the fence Persist the verdict: highest-seen and the applied-op set live on durable storage with the data, written before the ack. A restart that forgets them accepts stale epochs — the demo's HAZARD line — so memory alone is a fencing bug.

طراحی مشخصConcrete design

lock service: تابع issue() برای هر اعطای lease یک epoch بادوام و اکیداً صعودی برمی‌گرداند (یکی برای هر epoch نه هر نوشته) و شمارنده را قبل از جواب persist می‌کند. مسیر نوشتن storage در یک گام اتمیک: اگر token از highest کمتر بود: رد کن؛ highest را برابر token کن؛ اگر opId دیده شده: dedup؛ وگرنه اعمال کن. بزرگ‌ترین epoch دیده‌شده و مجموعهٔ opهای اعمال‌شده هر دو روی ذخیرهٔ بادوام و تکثیرشده با داده زندگی می‌کنند — فقط حافظه با restart شکاف مغزی را دوباره باز می‌کند. قاعدهٔ تخصیص token: دقیقاً یک epoch زنده برای هر منبع؛ اعطای تازه همیشه از همهٔ قبلی‌ها بزرگ‌تر است، حتی بعد از failover خود lock service.

Lock service: issue() returns a durable, strictly monotonic epoch per lease grant (one per epoch, not per write) and persists the counter before answering. Storage write path, one atomic step: if token < highest: reject; highest = token; if opId seen: dedup; else apply. The highest-seen epoch and the applied-op set both live on durable storage, replicated with the data — memory alone reopens the split brain on restart. Token allocation rule: exactly one live epoch per resource; a new grant always exceeds every earlier one, even across lock-service failover.

پاسخ: بزرگ‌ترین دیده‌شده باید روی ذخیرهٔ بادوام و تکثیرشده با داده زندگی کند — فقط حافظه با restart فراموش می‌کند و فراموشی بدون هیچ خطای دیگر شکاف مغزی را دوباره باز می‌کند.

Where must the highest-seen epoch live, and what single fault breaks it?

Answer: Highest-seen must live on durable storage, replicated with the data — memory alone forgets on restart, and forgetting reopens the split brain with no other fault needed.

گزینه‌های جایگزینAlternatives

  • انقضای lease به‌تنهایی («lease هفت تمام شد پس A نمی‌تواند بنویسد»): فقط وقتی کار می‌کند که هر شرکت‌کننده به ساعت lease احترام بگذارد — فرایند pauseشده اصلاً پیام را نگرفته. ارزان‌تر است (لوله‌کشی token ندارد) ولی به همان نودی اعتماد می‌کند که بنابر فرض unreachable است. فقط جایی که pauseها کران‌دار و اندازه‌گیری‌شده‌اند، هرگز برای pauseهای GC یا VM.
  • fencing تک‌نویسنده با consensus (term در Raft/ZAB به‌عنوان epoch): همان شکل با صادرکنندهٔ قوی‌تر — epoch از term لیدر منتخب می‌آید نه شمارندهٔ lock service. درست وقتی خود lock service باید خرابی را تحمل کند؛ سنگین‌تر از شمارنده و همچنان با بررسی storage اجرا می‌شود.
  • Lease expiry alone ('A's lease ended, so A cannot write'): works only if every participant obeys the lease clock — a paused process never got the memo. Cheaper (no token plumbing), but it trusts the very node that is, by hypothesis, unreachable. Use only where pauses are bounded and measured, never across GC or VM pauses.
  • Single-writer fencing via consensus (Raft/ZAB term as the epoch): same shape, stronger issuer — the epoch comes from an elected leader term instead of a lock service counter. Right when the lock service itself must survive failures; heavier than a counter, and still enforced at the storage check.

سناریوهای خرابیFailure scenarios

  • fencing فقط با انقضای lease (خط no-fence): نوشتهٔ کهنهٔ A مقدار leader=B را با leader=A بازنویسی می‌کند — بدون خطا و با دو حقیقت. نگهبان: بررسی توکن سمت storage؛ انقضا مالکیت را جابه‌جا می‌کند و فقط بررسی اجرایش می‌کند.
  • فراموشی restart: مقدار highest-seen داخل حافظه با crash فراموش می‌شود و نوشتهٔ کهنهٔ بعدی اعمال می‌شود — همان خط HAZARD در دمو. نگهبان: persist کردن highest-seen (و مجموعهٔ op) با هر پذیرش، قبل از تأیید.
  • تکراری هم‌epoch بدون dedup در op: op-b2 تکرارشدهٔ B دو بار اعمال می‌شد (اینجا نوشتن دوبارهٔ x=1 بی‌ضرر است و جای دیگر شارژ دوباره). نگهبان: مجموعهٔ op اعمال‌شده به‌عنوان دغدغه‌ای جدا از مقایسهٔ epoch.
  • صادرکنندهٔ دوشاخهٔ توکن: دو lock service (یا failoverای که شمارنده را صفر می‌کند) یک epoch را دو بار می‌دهند و fencing مساوی را با مساوی مقایسه می‌کند. نگهبان: یک صادرکنندهٔ واحد برای هر منبع — term در consensus یا شمارندهٔ فنس‌دار — تا epochها هرگز دوشاخه نشوند.
  • Lease-expiry-only fencing (the no-fence line): A's stale write overwrites leader=B with leader=A — no error, two truths. Guard with the storage-side token check; expiry moves ownership, only the check enforces it.
  • Restart amnesia: highest-seen kept in memory is forgotten on crash, and the next stale write applies — the HAZARD line in the demo. Guard by persisting highest-seen (and the op set) on every accept, before acknowledging.
  • Same-epoch duplicate without op dedup: B's retried op-b2 would apply twice (x=1 written twice — harmless here, a double charge elsewhere). Guard with the applied-op set as a separate concern from the epoch compare.
  • Forked token issuer: two lock services (or a failover that resets the counter) hand out the same epoch twice, and fencing compares equal against equal. Guard with a single issuer per resource — consensus term or fenced counter — so epochs never fork.

import java.util.*;
// Teaching demo: fencing tokens are ownership EPOCHS, not per-write IDs.
// Storage atomically rejects stale epochs; legitimate same-epoch writes are
// told apart by operation ID (dedup), not by the epoch. Forgetting the
// highest token across a restart reopens the split brain.
public class FencingDemo {
    static class LockService {
        int epoch = 6;                                                 // teaching: A gets 7, B gets 8
        int issue() { return ++epoch; }                                // durable, monotonic
    }
    static class Storage {
        int highest = 0;                                               // durable highest-seen epoch
        Map<String, String> data = new HashMap<>();
        Set<String> appliedOps = new HashSet<>();                      // operation dedup, separate concern
        synchronized String write(int token, String opId, String k, String v) {
            if (token < highest) return "REJECT stale-epoch token=" + token + " highest=" + highest;
            highest = token;
            if (!appliedOps.add(opId)) return "DEDUP op=" + opId + " (same-epoch repeat, no second effect)";
            data.put(k, v);
            return "ACCEPT token=" + token + " op=" + opId + " " + k + "=" + v;
        }
    }
    public static void main(String[] a) {
        LockService lock = new LockService();
        Storage store = new Storage();
        int tokenA = lock.issue();                                     // A holds epoch 7
        System.out.println("A lease epoch=" + tokenA + " then A pauses (GC pause, teaching)");
        int tokenB = lock.issue();                                     // B holds epoch 8
        System.out.println("B lease epoch=" + tokenB);
        System.out.println("B write -> " + store.write(tokenB, "op-b1", "leader", "B"));
        System.out.println("A wakes, stale write -> " + store.write(tokenA, "op-a1", "leader", "A"));
        System.out.println("B second write same epoch -> " + store.write(tokenB, "op-b2", "x", "1"));
        System.out.println("B retry of op-b2 -> " + store.write(tokenB, "op-b2", "x", "1"));
        System.out.println("final leader=" + store.data.get("leader") + " x=" + store.data.get("x"));
        Storage noFence = new Storage() {
            @Override synchronized String write(int token, String opId, String k, String v) {
                data.put(k, v);                                        // lease-expiry only: NO token check
                return "APPLIED without check " + k + "=" + v;
            }
        };
        noFence.write(2, "op-b1", "leader", "B");
        System.out.println("no-fence A overwrite -> " + noFence.write(1, "op-a1", "leader", "A"));
        Storage restarted = new Storage();                             // amnesia: highest forgotten
        restarted.write(tokenB, "op-b1", "leader", "B");
        restarted.highest = 0;                                         // crash lost durable state
        System.out.println("restart-amnesia A write -> " + restarted.write(tokenA, "op-a9", "leader", "A")
            + " HAZARD: stale epoch accepted");
        System.out.println("OK: epoch rejects, op-id dedups, durability required");
    }
}

آزمون صحت و معیار عملیاتیCorrectness checks and operational criteria

ناورداها: هر نوشته با توکن کمتر از بزرگ‌ترین دیده‌شده رد می‌شود و هیچ‌چیز را عوض نمی‌کند؛ N نوشتهٔ مجاز هم‌epoch با opهای متمایز N اثر می‌دهند؛ هر op بعد از M تکرار هنوز یک اثر دارد؛ بعد از restart در storage، epoch کهنه هنوز رد می‌شود. بسنج با: تست تزریق pause (نگهدارنده را بعد از انقضا بخوابان و بیدار کن و reject را assert کن)، تست restart (بعد از پذیرش‌ها storage را بکش و کهنه را بازپخش کن و reject را assert کن) و شمارش rejectهای هر epoch به‌عنوان معیار سلامت fencing.
Invariants: any write with token below highest-seen is rejected and changes nothing; N legitimate same-epoch writes with distinct ops yield N effects; any op retried M times still yields one effect; after a storage restart, a stale epoch is still rejected. Measure with: a pause-injection test (sleep holder past expiry, wake, assert reject), a restart test (kill storage after accepts, replay stale, assert reject), and a counter of rejects per epoch as the fencing-health metric.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): حالا storage restart می‌شه و highest token رو فراموش می‌کنه. چه خطایی ممکنه پیش بیاد؟Follow-up (Staff): Your storage restarts and forgets the highest fencing token. What failure becomes possible?

نوشتهٔ epochکهنه دوباره می‌تواند اعمال شود — شکاف مغزی بدون هیچ خطای دیگر دوباره باز می‌شود. مشخصاً: storage با highest=0 ری‌استارت می‌شود ولی مقدار epoch-8 برای B داخل داده نشسته؛ Aی pauseشده با epoch هفت بیدار می‌شود و ۷ دیگر زیر هیچ highest به‌یادمانده‌ای نیست، پس روی B بازنویسی می‌کند. خط HAZARD در دمو دقیقاً همین است: ۷ کهنه پذیرفته می‌شود و leader به A برمی‌گردد. نگهبان دوام است: highest-seen (و مجموعهٔ op) را روی دیسک و تکثیرشده با داده persist کن، قبل از تأیید هر نوشته — فقط حافظه باگ fencing است.

A stale-epoch write can apply again — the split brain reopens with no other fault. Concretely: storage restarts with highest=0 while B's epoch-8 value sits in the data; paused A wakes with epoch 7, and 7 is no longer below any remembered highest, so it overwrites B. The demo's HAZARD line is exactly this: stale 7 accepted, leader flips to A. The guard is durability: persist highest-seen (and the op set) on disk, replicated with the data, before acknowledging any write — memory alone is a fencing bug.

پیگیری (سینیور): دو نوشتهٔ مجاز epoch هشت را شریک‌اند و بعد یکی retry می‌شود. چطور دو اثر را قبول می‌کنی ولی سه‌تا نه؟Follow-up (Senior): Two legitimate writes share epoch 8, then one is retried. How do you accept two but not three effects?

با شناسهٔ عملیات، هویت جدا. هر دو epoch هشت را دارند، پس بررسی epoch هر دو را قبول می‌کند — درست، چون هر دو زیر epoch زنده می‌رسند. بعد مجموعهٔ op تصمیم می‌گیرد: op-b2 تازه است، پس اعمال می‌شود (دومین نوشتهٔ مجاز epoch)؛ تکرار دوباره op-b2 را دارد و مجموعه از قبل داردش، پس بدون اثر دوم جذب می‌شود. epoch جواب می‌دهد «نوبت کیست» و شناسهٔ op جواب می‌دهد «کدام تلاش» — قاطی کردنشان یا نوشته‌های مجاز را رد می‌کند یا retryها را دو بار اعمال می‌کند.

By operation ID, the separate identity. Both carry epoch 8, so the epoch check passes both — correctly, because both arrive under the live epoch. Then the op set decides: op-b2 is new, so it applies (second legitimate write of the epoch); the retry carries op-b2 again, the set already holds it, so it absorbs with no second effect. Epoch answers 'whose turn', op ID answers 'which attempt' — conflating them either rejects legitimate writes or double-applies retries.

اشتباهات رایجCommon mistakes

  • اعتماد به انقضای lease برای متوقف کردن نویسندهٔ pauseشده: انقضا خوانش ساعت است و فرایند pauseشده نمی‌تواند ساعت بخواند. نوشتهٔ کهنه بعد از انقضا با اعتماد کامل می‌رسد — فقط بررسی storage جلویش را می‌گیرد.
  • ساختن یک توکن برای هر نوشته به‌جای هر epoch: آن‌وقت «کهنه» معنایی ندارد — هر توکن تازه است و مقایسه همه‌چیز را قبول می‌کند و نویسندهٔ pauseشده رد می‌شود. توکن باید نام نسل مالکیت باشد که همهٔ نوشته‌هایش شریک‌اند.
  • نگه داشتن highest-seen فقط در حافظه: تا اولین restart کار می‌کند و بعد هر epoch قدیمی دوباره جوان است. دوام اینجا بهینه‌سازی نیست — خود نرده است.
  • Trusting lease expiry to stop a paused writer: expiry is a clock reading, and the paused process cannot read clocks. The stale write arrives after expiry with full confidence — only the storage check stops it.
  • Minting one token per write instead of per epoch: then 'stale' has no meaning — every token is fresh, the compare passes everything, and the paused writer sails through. The token must name the ownership generation, shared by all its writes.
  • Keeping highest-seen in memory only: it works until the first restart, then every old epoch is young again. Durability is not an optimization here — it is the fence.

سؤال مصاحبهInterview question
داستان از این قراره که یه صف داری. safety رو این‌طور تعریف کن: «اثر پیام بیش از یه بار اعمال نشه» و liveness رو این‌طور: «پیام معتبر تحت بازیابی شبکه بالاخره اثر کنه». partition دائمی، redelivery و گم‌شدن dedup رو تحلیل کن. برای هر ادعا یه counterexample و فرض زمانی روشن بده.
Honestly, you've got a queue to reason about. Define no duplicate application effects as safety and eventual valid-message effects under recovery as liveness. Cover permanent partitions, redelivery and missing dedup state. Give a counterexample and an explicit timing assumption for each claim.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

Safety: هیچ پیامی دو بار اثر نمی‌کند — خاصیت اثرهای اپلیکیشن که با حالت dedup اجرا می‌شود و باید از restartای که redelivery را می‌سازد جان سالم به‌در ببرد. Liveness: هر پیام معتبر بالاخره اثر می‌کند ولی فقط زیر فرض‌های بازیابی اعلام‌شده (پارتیشن خوب می‌شود، ظرفیت هست و deadline انتظار را کران می‌کند). این دو مستقل می‌شکنند: پارتیشن دائمی فقط liveness را می‌شکند، مجموعهٔ dedup گمشده فقط safety را و سرویس reject-all در حالی‌که هیچ‌چیز پیش نمی‌رود safety را به‌صورت vacuous سبز نگه می‌دارد.
Safety: no message takes effect twice — a property of application effects, enforced by dedup state that must survive the restart that causes the redelivery. Liveness: every valid message eventually takes effect, but only under stated recovery assumptions (the partition heals, capacity exists, a deadline bounds the wait). The two fail independently: a permanent partition breaks liveness alone, a lost dedup set breaks safety alone, and a reject-all service keeps safety vacuously green while nothing progresses.

صورت مسئله و فرض‌هاProblem and assumptions

  • یک مصرف‌کنندهٔ صف و شناسه‌های رشته‌ای پیام و امکان redelivery بعد از هر crash یا پارتیشن (transport از نوع at-least-once).
  • اثرها در دمو شمارندهٔ هر پیام‌اند (جانشین آموزشی اثرهای واقعی اپلیکیشن).
  • deadlineهای liveness کران‌های آموزشی‌اند («بالاخره» همیشه با فرض اعلام‌شدهٔ زمان و شبکه و ظرفیت می‌آید).
  • One queue consumer, string message IDs, redelivery possible after any crash or partition (at-least-once transport).
  • Effects are per-message counters in the demo (teaching stand-ins for real application effects).
  • Liveness deadlines are teaching bounds ('eventually' always ships with a stated time, network and capacity assumption).

چرا این روش و این عددها؟Why this method and these numbers?

safety یعنی هیچ اجرای مجاز به حالت ممنوع نرسد؛ یک counterexample آن را رد می‌کند. liveness یعنی با فرض پیشرفت شبکه، پردازنده و ظرفیت، کار بالاخره تمام شود؛ timeout یک آزمایش محدود نمی‌تواند آن را برای همهٔ اجراها ثابت کند. deadline عملیاتی هدف محصول است و با eventually در مدل نظری یکسان نیست. at-most-once می‌تواند duplicate را منع کند ولی با دورریختن پیام، پیشرفت کسب‌وکاری را از بین ببرد.

Safety excludes forbidden states in every permitted execution; one counterexample refutes it. Liveness requires eventual completion under network, processor and capacity progress assumptions; a finite timeout test cannot prove it universally. An operational deadline differs from theoretical eventually. At-most-once can prevent duplicates while discarded messages destroy business progress.

مدل ذهنیMental model

safety نرده است («هیچ بدی هرگز رخ نمی‌دهد») و liveness جاده است («خوبی بالاخره رخ می‌دهد») — و نرده‌ای که در بیابان ایستاده جاده نیست. تحویل کامیون‌های جاده را می‌شمارد؛ اثر بار تخلیه‌شده در انبار را. سیستم می‌تواند هر کامیون را گم کند (جاده مرده و نرده سالم) یا یک کامیون را دو بار تخلیه کند (نرده شکسته و جاده شلوغ) یا هر کامیون را دم در برگرداند (نرده ظاهراً سالم و جاده خالی). نرده و جاده را همیشه جدا قضاوت کن.
Safety is a fence ('nothing bad ever happens') and liveness is a road ('something good eventually happens') — and a fence standing in a desert is not a road. Delivery counts trucks on the road; effects count cargo unloaded at the warehouse. A system can lose every truck (liveness dead, fence intact), unload one truck twice (fence broken, road busy), or wave every truck away at the gate (fence trivially intact, road empty). Judge the fence and the road separately, always.

حل گام‌به‌گامStep by step

  1. اثرها نه تحویل‌ها اثرها را بشمار نه تحویل‌ها را: سیم ممکن است تکراری و گم و جابه‌جا کند — اثر اپلیکیشن برای هر شناسهٔ پیام تنها چیزی است که کسب‌وکار حس می‌کند. «یک‌بار اعمال برای هر شناسه» همان جملهٔ safety است؛ بقیه transport است.
  2. dedup که زنده می‌ماند safety را با dedup زنده‌مانده اجرا کن: بررسی-بعد-اعمال در یک گام اتمیک و persist قبل از تأیید، تا restartای که redelivery را می‌سازد نتواند خاطرهٔ اثر اول را پاک کند. dedup همان نرده است و مجموعه میخ‌هایش.
  3. liveness با فرض‌ها liveness را با سه فرض نام‌دار کران کن: پارتیشن ظرف H خوب می‌شود و ظرفیت مصرف‌کننده بالای رسیدن‌ها می‌ماند و هر پیام معتبر ظرف T اثر می‌کند. آن‌وقت پارتیشن دائمی دقیقاً همان فرضی را می‌شکند که نام می‌برد — liveness شکسته و safety دست‌نخورده.
  4. چهار خانه و مستقل استقلال را با ماتریس چهارخانه اثبات کن: تحویل دوباره هر دو را نگه می‌دارد و پارتیشن فقط liveness را می‌شکند و گم‌شدن dedup فقط safety را و reject-all با liveness مرده safety را به‌صورت vacuous نگه می‌دارد. هر خاصیتی که نتواند تنها بشکند دو خاصیت است با یک نام.
  1. Effects, not deliveries Count effects, not deliveries: the wire may duplicate, lose, or reorder — the application effect per message ID is the only thing the business feels. 'Applied once per ID' is the safety sentence; everything else is transport.
  2. Dedup that survives Enforce safety with surviving dedup: check-then-apply under one atomic step, persisted before the ack, so the restart that triggers redelivery cannot wipe the memory of the first effect. Dedup is the fence; the set is its posts.
  3. Liveness with assumptions Bound liveness with three named assumptions: the partition heals within H, consumer capacity stays above arrivals, and every valid message effects within T. A permanent partition then breaks exactly the assumption it names — liveness violated, safety untouched.
  4. Four cells, independent Prove independence with the four-cell matrix: redelivery holds both, partition breaks liveness only, dedup-loss breaks safety only, reject-all holds safety vacuously with liveness dead. Any property that cannot break alone is two properties wearing one name.

طراحی مشخصConcrete design

حالت مصرف‌کننده با دو ساختار: dedup: Set[messageID] (دیده‌شده یعنی اثرکرده) و effects: Map[messageID, count] که در یک گام اتمیک به‌روز می‌شوند — بررسی-بعد-اعمال زیر همان قفل و persist قبل از تأیید. قرارداد تحویل: transport از نوع at-least-once با redelivery بی‌کران؛ مصرف‌کننده همه را جذب می‌کند. قرارداد liveness که برای هر صف اعلام می‌شود: پیام‌های معتبر ظرف T اثر می‌کنند به‌شرط این‌که پارتیشن ظرف H خوب شود و ظرفیت مصرف‌کننده بالای نرخ رسیدن بماند — کرانی با سه فرض نام‌دار، نه یک «بالاخره» لخت.

Consumer state, two structures: dedup: Set[messageID] (seen means effected) and effects: Map[messageID, count], updated in one atomic step — check-then-apply under the same lock, persisted before the ack. Delivery contract: at-least-once transport with unbounded redelivery; the consumer absorbs all of it. Liveness contract, stated per queue: valid messages take effect within T provided the partition heals within H and consumer capacity stays above arrival rate — a bound with three named assumptions, not a bare 'eventually'.

گزینه‌های جایگزینAlternatives

  • تحویل at-most-once به‌عنوان گزارهٔ safety («هر پیام حداکثر یک‌بار تحویل می‌شود»): روی سیم ساده‌تر دیده می‌شود ولی پیام گمشده بعد گم‌شدن داده با چراغ سبز safety است — شکست‌های progress را داخل چراغ سبز پنهان می‌کند. مگر وقتی transport واقعاً نمی‌تواند redeliver کند، گزارهٔ مبتنی بر اثر را ترجیح بده.
  • تأیید سرتاسری به‌علاوهٔ بازپخش اپراتوری برای liveness: به‌جای قول progress خودکار، قول تشخیص بده (هر پیام تأییدنشده visible است) به‌علاوهٔ مسیر بازپخش runbookشده. درست وقتی redelivery خودکار ناامن است (اثرهای non-idempotent) — آن‌وقت liveness به کران human-in-the-loop صادقانه‌اعلام‌شده تبدیل می‌شود.
  • At-most-once delivery as the safety statement ('each message delivered at most once'): simpler to observe on the wire, but a lost message is then a safety-preserving data loss — it hides progress failures inside a green light. Prefer the effect-based statement unless the transport truly cannot redeliver.
  • End-to-end acknowledgments plus operator replay for liveness: instead of promising automatic progress, promise detection (every un-acked message is visible) plus a runbooked replay path. Right when automatic redelivery is unsafe (non-idempotent effects) — liveness becomes a human-in-the-loop bound, stated honestly.

سناریوهای خرابیFailure scenarios

  • پارتیشن دائمی: پیام معتبر هرگز نمی‌رسد — liveness شکسته و safety دست‌نخورده. نگهبان: فرض اعلام‌شدهٔ خوب شدن به‌علاوهٔ بافر و بازپخش هنگام خوب شدن؛ بدون فرض، ادعای liveness آرزوست.
  • گم شدن حالت dedup در restart: تحویل دوباره‌ای که خوب شدن می‌آورد دو بار اعمال می‌کند — safety شکسته ولی liveness می‌ماند. نگهبان: persist کردن مجموعهٔ dedup قبل از تأیید، تکثیرشده با اثرها.
  • outage از نوع reject-all (پیکربندی مسموم یا گیت بسته): هر پیام رد می‌شود — safety به‌صورت vacuous سبز و liveness مرده و داشبورد با حذف دروغ می‌گوید. نگهبان: معیار progress (اثرکرده در دقیقه) کنار هر چراغ safety و پیج وقتی progress صفر شد.
  • تحویل at-most-once که به‌عنوان «بدون تکراری و بدون گم‌شدن» فروخته شود: پیام انداخته‌شده در معیار safety موفق شمرده می‌شود ولی اثر کسب‌وکاری هرگز رخ نمی‌دهد. نگهبان: اثرها را اعلام کن نه تحویل‌ها را — پیام‌های اثرکرده را بشمار و بقیه را redeliver کن و بگذار liveness مالک شکاف باشد.
  • Permanent partition: the valid message never arrives — liveness violated, safety untouched. Guard with the stated healing assumption plus buffering and replay on heal; without the assumption the liveness claim is a wish.
  • Dedup state lost across restart: the redelivery that healing brings double-applies — safety violated while liveness holds. Guard by persisting the dedup set before acking, replicated with the effects.
  • Reject-all outage (poison config, closed gate): every message refused — safety vacuously green, liveness dead, and the dashboard lies by omission. Guard with a progress metric (effected-per-minute) beside every safety light, paging when progress hits zero.
  • At-most-once delivery sold as 'no duplicates, no loss': a dropped message is counted as success by the safety metric while the business effect never happens. Guard by stating effects, not deliveries — count effected messages, redeliver the rest, and let liveness own the gap.

import java.util.*;
// Teaching demo: safety = "no message takes effect twice" (nothing bad);
// liveness = "every valid message eventually takes effect under recovery"
// (something good, needs stated time/network assumptions). Each can break
// without the other.
public class SafetyLivenessDemo {
    static class Consumer {
        Set<String> dedup = new HashSet<>();                           // dedup state (must survive restart)
        Map<String, Integer> effects = new HashMap<>();                // application effects per message
        void deliver(String id) {
            if (!dedup.add(id)) return;                                // redelivery: no second effect
            effects.merge(id, 1, Integer::sum);
        }
        boolean safetyHolds() { return effects.values().stream().allMatch(c -> c <= 1); }
    }
    public static void main(String[] a) {
        // 1. redelivery with dedup: both hold
        Consumer c1 = new Consumer();
        c1.deliver("m1"); c1.deliver("m1"); c1.deliver("m2");           // m1 redelivered
        System.out.println("redelivery+dedup: effects=" + c1.effects
            + " SAFETY=" + (c1.safetyHolds() ? "HOLDS" : "VIOLATED") + " LIVENESS=HOLDS");
        // 2. permanent partition: m3 never arrives
        Consumer c2 = new Consumer();
        c2.deliver("m1");
        boolean m3arrived = false;                                     // partition never heals
        System.out.println("permanent-partition: m3 arrived=" + m3arrived
            + " SAFETY=HOLDS (nothing applied twice) LIVENESS=VIOLATED (m3 never effected)");
        // 3. dedup state lost across restart: redelivery double-applies
        Consumer c3 = new Consumer();
        c3.deliver("m1");
        c3.dedup.clear();                                              // crash lost dedup state
        c3.deliver("m1");                                              // redelivery after restart
        System.out.println("dedup-lost: effects=" + c3.effects
            + " SAFETY=" + (c3.safetyHolds() ? "HOLDS" : "VIOLATED") + " LIVENESS=HOLDS (m1 did take effect)");
        // 4. reject-all service: drops every message
        Consumer c4 = new Consumer();
        System.out.println("reject-all: effects=" + c4.effects
            + " SAFETY=HOLDS vacuously (zero effects) LIVENESS=VIOLATED (nothing progresses)");
        System.out.println("OK: safety and liveness fail independently; liveness needs recovery assumptions");
    }
}

Safety — و دقیقاً به همین دلیل جواب جالب است. با صفر اثر، صفر تکراری هست، پس «هیچ پیامی دو بار اثر نمی‌کند» به‌صورت vacuous می‌ماند؛ چراغ داشبورد سبز می‌ماند. liveness («هر پیام معتبر بالاخره اثر می‌کند») مرده: هیچ‌چیز پیش نمی‌رود. درس: چراغ safety بدون معیار progress دروغ با حذف است — همیشه جفتشان کن و روی صفر شدن اثرکرده-در-دقیقه پیج بده، نه فقط روی safety.

Safety — and that is exactly why the answer is interesting. With zero effects there are zero duplications, so 'no message takes effect twice' holds vacuously; the dashboard light stays green. Liveness ('every valid message eventually takes effect') is dead: nothing progresses. The lesson: a safety light without a progress metric is a lie by omission — always pair them, and page on effected-per-minute hitting zero, not on safety alone.

پیگیری (استف): نشان دادی liveness تنها می‌شکند. آیا safety می‌تواند بشکند ولی progress ادامه داشته باشد؟Follow-up (Staff): You showed liveness breaking alone. Can safety break while progress continues?

بله — سناریوی dedup گمشده دقیقاً برعکس است: m1 تحویل می‌شود و crash مجموعهٔ dedup را پاک می‌کند و تحویل دوباره m1 را بار دوم اعمال می‌کند (effects={m1=2}). safety شکسته — یک پیام و دو اثر — ولی liveness می‌ماند چون m1 اثر کرد (دو بار). پس استقلال هر دو طرف می‌رود: progress بدون safety (اعمال دوباره) و safety بدون progress (پارتیشن و reject-all). هر بازبینی طراحی باید هر دو ضدمثال را بخواهد، نه فقط مد روز را.

Yes — the dedup-lost scenario is exactly the reverse: m1 is delivered, the crash wipes the dedup set, the redelivery applies m1 a second time (effects={m1=2}). Safety is violated — one message, two effects — while liveness holds, because m1 did take effect (twice). So the independence runs both ways: progress without safety (double-apply) and safety without progress (partition, reject-all). Any design review must ask for both counterexamples, not just the fashionable one.

اشتباهات رایجCommon mistakes

  • اعلام safety روی تحویل‌ها («حداکثر یک‌بار») و تمام دانستنش: پیام گمشده تحویل at-most-once را نگه می‌دارد ولی اثر کسب‌وکاری ناپدید می‌شود. safety باید روی اثرها اعلام شود وگرنه گم‌شدن داخل تضمین پنهان می‌شود.
  • قول liveness بدون فرض‌های بازیابی («هر پیام بالاخره تحویل می‌شود»): بالاخره زمان نیست و پارتیشن تأخیر نیست و دیسک پر شبکه نیست. liveness بی‌قید آرزوست — خوب شدن و ظرفیت و deadline را نام ببر یا ادعا را پس بگیر.
  • خواندن سبز safety به‌معنای سلامت در outage از نوع reject-all: صفر اثر یعنی صفر تکراری، پس چراغ سبز می‌ماند ولی کسب‌وکار ایستاده. هر داشبورد safety دوقلوی progress خودش را می‌خواهد.
  • Stating safety on deliveries ('at most once') and calling it done: a lost message preserves at-most-once delivery while the business effect vanishes. Safety must be stated on effects, or loss hides inside the guarantee.
  • Promising liveness without recovery assumptions ('every message is eventually delivered'): eventually is not a time, a partition is not a delay, and a full disk is not a network. Unconditional liveness is a wish — name heal, capacity, and deadline or withdraw the claim.
  • Reading safety-green as healthy during a reject-all outage: zero effects means zero duplications, so the light stays green while the business stands still. Every safety dashboard needs its progress twin.
