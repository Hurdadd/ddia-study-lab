ایدهٔ کلیدی فصلChapter thesis

فرض کن یه ماشین دیگه از پس دیتا و بار برنمیاد. پس دیتا رو تیکه می‌کنی و هر تیکه (shard) رو می‌ذاری یه جا. ولی یادت باشه بازی اصلی اینه: کلید تقسیم چی باشه، shardها چطور جابه‌جا بشن، و query از کجا بفهمه کجا بره. همین سه‌تا معلوم می‌کنن تقسیمت به درد می‌خوره یا فقط دردسر می‌خری.

مثال فنی: تقسیم داده با تکثیر فرق دارد

وضعیت اولیه: تصور کن کلیدهای 1…1000 رو نصف کردی: نصفش دست shard A، نصفش دست shard B.

اجرای مرحله‌به‌مرحله: حالا برای هر shard سه‌تا replica بذار؛ روی هم شش‌تا کپی فیزیکی داری. ولی قاطی نکن: A و B دو تیکهٔ فرق‌دار از دیتان، نه دو کپی از یه چیز.

نتیجه و دلیل: می‌بینی؟ sharding ظرفیت رو زیاد می‌کنه، replication جونت رو موقع خرابی نجات می‌ده. دوتا کار جدا ولی رفیق‌ان که کنار هم میان. اینو یادت نره.

این مثال‌ها رو مثل تمرین روزمره ببین، نه سند معماری یه شرکت واقعی. عددها فقط برای اینن که مطلب قشنگ جا بیفته. گیر نکن، برو سر اصل ماجرا.

Sharding means breaking data into smaller subsets and placing each subset on a different node; so each record sits in exactly one shard (and usually that same shard has several copies too — sharding combines with replication). The goal is spreading data and query load evenly across machines and avoiding hot spots.

For that you must pick a partition key and own an algorithm telling each record where it lives. Two main families: key-range sharding (keys are ordered and each shard holds one contiguous range; range queries are fast but hotspot risk) and hash sharding (hashing the key spreads it; order is lost but load is more even). And when nodes join or leave, rebalancing must move the least data.

کل فصل دور همین پنج‌تا ایده می‌چرخه — نقشهٔ گنج:

Five ideas this chapter revolves around:

  • الگوریتمِ نگاشت: فرض کن با partition key باید بفهمی کدوم shard، بعد بفهمی کدوم node. یادت باشه hash % N همون لحظه‌ای که N عوض بشه می‌ترکه.
  • Rebalancing: shard رو دربست جابه‌جا کنی، بازه رو نصف کنی، یا بری سراغ consistent hashing — هیچ‌کدوم مفت نیست، هرکدوم یه قیمتی داره.
  • Skew و hotspot: قاطی نکن: بهترین hash دنیا هم نمی‌تونه بار واقعی یه کلید داغ رو بین همه پخش کنه.
  • Request routing: کلاینت از کجا بفهمه کدوم کلید دست کدوم nodeـه؟ وسط جابه‌جایی shard چی می‌شه؟ این‌جاست که داستان قاطی می‌شه.
  • Secondary indexes: ایندکس ثانویه رو هم باید تیکه‌تیکه کنی: local (document-partitioned) یا global (term-partitioned). تهش باید یکی رو انتخاب کنی.
  • The mapping algorithm: from partition key to shard and from shard to node — and why hash % N is a disaster when N changes.
  • Rebalancing: moving whole shards, splitting ranges, or consistent hashing — each with its own price.
  • Skew and hotspots: even the best hash doesn't spread one hot key's real load.
  • Request routing: how a client learns which node owns which key — and what happens during shard moves.
  • Secondary indexes: a secondary index must be sharded too; local (document-partitioned) or global (term-partitioned).
دامِ اصطلاح: partition ≠ network partitionTerm trap: partition ≠ network partition

قاطی نکن: «Partition» این‌جا یعنی یه تیکه از دیتا؛ ولی network partition (netsplit) یعنی سیم بین nodeها قطع شده — یه مدل خرابیه که می‌ذاریمش برای فصل ۹. فقط اسمشون شبیه همه، وگرنه هیچ ربطی به هم ندارن.

“Partition” in this chapter means a piece of data; but a network partition (netsplit) means severed communication between nodes — a failure type covered in Chapter 9. The two only share a name and have nothing to do with each other.

نکتهٔ مصاحبهInterview tip

این جمله رو قاب کن: «sharding یه راه‌حل سنگینه برای مقیاس بزرگ». اگه یه ماشین هنوز از پس دیتا و نوشتن برمیاد — و یادت باشه امروز یه ماشین خیلی کار می‌کنه! — سمت sharding نرو. چون انتخاب partition key سخته، عوضش گرونه، و join یا نوشتن چند تیکهٔ مرتبط می‌افته گردن distributed transaction. تهش فقط دردسر می‌خری.

This chapter's golden line: “sharding is a heavy solution for large scale”. If one machine handles the data and writes — and today one machine does a lot! — don't shard; because picking the partition key is hard, changing it is expensive, and joining or writing related objects across shards needs a distributed transaction.

۱1 sharding چرا و چیست؟Why and what is sharding?

فرض کن دیتاست رو تیکه می‌کنی و هر تیکه (shard) یه مشت از رکوردها رو برمی‌داره. تکثیر فرق داره: از همون تیکه چندتا کپی می‌سازه. قاطیشون نکن؛ دوتا کار جدان ولی رفیق‌ان و معمولاً با هم میان.

مثال فنی: نقطهٔ شروعِ تقسیم

وضعیت اولیه: تصور کن 4 TB دیتا داری و هر ماشین فقط 1 TB جا داره.

اجرای مرحله‌به‌مرحله: کلیدها رو با یه نقشهٔ مشخص بین چند shard پخش می‌کنی؛ حالا هر query اول باید بفهمه بره کدوم shard، و کارهای چندتیکه‌ای هم قصهٔ جدا دارن.

نتیجه و دلیل: می‌بینی؟ مشکل جا حل شد، ولی مسیریابی و تعادل بار و هماهنگی اومد روی میز. هیچ‌چیز مفت نیست.

A distributed database usually spreads data across nodes in two ways:

  • Replication (فصل ۶): از همون دیتا چندتا کپی می‌ذاری رو چند node — که سرویس نخوابه و خواندن بیشتر جواب بده.
  • Sharding: فرض کن دیتا یا نوشتن از زور یه node بیشتره؛ دیتا رو می‌شکنی به shardهای کوچیک‌تر و هر shard رو می‌فرستی رو یه node جدا.
  • Replication (Chapter 6): a copy of the same data on several nodes — for failure tolerance and more reads.
  • Sharding: when data or writes exceed one node's capacity, data is broken into smaller shards and each shard goes to a different node.

یادت باشه هر رکورد دقیقاً مال یه shardـه. عملاً هر shard یه دیتابیس کوچیک و مستقله. حالا این دوتا رو قاطی کن: هر shard چندتا نسخه داره؛ leader هر shard رو یه nodeـه و followerهاش رو nodeهای دیگه — و هر node هم‌زمان می‌تونه leader چند shard و follower چندتای دیگه باشه. تهش همه هم صاحب‌ان هم پیرو.

Each record belongs to exactly one shard; in practice each shard is a small independent database (though some systems have multi-object operations). Sharding usually combines with replication: each shard has several copies, each shard's leader sits on one node and its followers on others — and each node can simultaneously lead some shards and follow others.

۱.۲ مزایا، هزینه‌ها و چندمستاجری1.2 Pros, costs and multitenancy

چرا sharding کنیم؟Why shard?

  • مقیاس‌پذیری: فرض کن حجم دیتا یا نوشتن از زور یه node بیشتره.
  • Scale-out: به‌جای یه ماشین گنده‌تر، چندتا ماشین بیشتر — اگه بار قشنگ پخش بشه، ۱۰ تا node ده‌برابر ظرفیت می‌دن. ولی شرطش پخش یکنواخته.
  • اگه فقط خواندن زیاده، سمت sharding نرو؛ read scaling با replication حل می‌شه (فصل ۶). تهش الکی دردسر نخر.
  • Scalability: data volume or writes exceed one node's capacity.
  • Scale-out: more machines instead of a bigger machine — if load splits evenly, 10 nodes give ten times the capacity.
  • If only reads are heavy, you don't need sharding; read scaling is solved by replication (Chapter 6).

چرا sharding نکنیم؟Why not shard?

  • انتخاب partition key سرنوشت کل سیستم رو معلوم می‌کنه، و عوض‌کردن طرح sharding خیلی گرونه. از اول درست انتخاب کن.
  • بدونی رکورد کجاست سریع می‌ری سراغش؛ ندونی باید بین همهٔ shardها بگردی و همه رو به زحمت بندازی.
  • دیتای رابطه‌ای سخت‌تره: جست‌وجو با ایندکس ثانویه و join ممکنه بین shardها پخش بشه و قاطی کنه.
  • نوشتن چند رکورد مرتبط تو چند shard می‌افته گردن distributed transaction — کندتره و گاهی گلوگاه کل سیستم می‌شه. اینو یادت نره.
  • Picking the partition key determines everything, and changing the sharding scheme is very expensive.
  • Knowing where a record lives is fast; not knowing means searching across all shards.
  • Relational data is harder: secondary-index searches and joins may scatter across shards.
  • Writing several related records across shards needs a distributed transaction — slower and sometimes the whole system's bottleneck.
نکتهٔ عمیق: sharding حتی روی یک ماشینDeep note: sharding even on one machine

تیکه‌کردن دیتا ظرفیت رو می‌بره بالا، ولی query روی چند تیکه و جابه‌جایی دیتا رو سخت‌تر می‌کنه. اگه یه ماشین هنوز جواب می‌ده، شاید این هزینه‌ها فعلاً لازم نباشن. عجله نکن.

مثال فنی: هزینهٔ تقسیمِ زودهنگام

وضعیت اولیه: تصور کن کل دیتاست فقط 20 GBـه و یه سرور به‌راحتی بار رو جواب می‌ده.

اجرای مرحله‌به‌مرحله: حالا تیکه‌اش کن به چهار shard؛ گزارش همهٔ سفارش‌ها باید چهارتا جواب رو جمع کنه و مهاجرت دیتا هم قاطی‌پاتی می‌شه.

نتیجه و دلیل: تا وقتی محدودیت واقعی ندیدی، sharding فقط مسیر ساده رو گرون می‌کنه؛ replica هم قصهٔ جداست و برای تحمل خرابیه. قاطیشون نکن.

Some systems shard on a single machine too: one single-threaded process per CPU core, to exploit CPU parallelism or NUMA architecture (memory nearer to some CPUs). Redis, VoltDB and FoundationDB use exactly this pattern. So a shard doesn't necessarily mean several machines; it means “an independent unit of load”.

sharding برای چندمستاجری (Multitenancy)Sharding for multitenancy

فرض کن تو یه محصول چندمستاجری دیتای چندتا سازمان رو تو یه سامانه نگه داشتی. تقسیم بر اساس سازمان جداسازی و جابه‌جایی رو راحت می‌کنه، ولی یادت باشه مشتری‌ها هم‌قد نیستن. تهش تعادل به‌هم می‌ریزه.

مثال فنی: یک tenant، یک محل

وضعیت اولیه: تصور کن مشتری سازمانی tenant_id=17 افتاده رو shard A.

اجرای مرحله‌به‌مرحله: بیشتر queryهای همین tenant محلی‌ان و سر جاشون جواب می‌گیرن؛ ولی اگه یه tenant به‌تنهایی ۶۰٪ بار بسازه، باید جابه‌جاش کنی یا دیتاش رو بشکنی.

نتیجه و دلیل: می‌بینی؟ tenant کلید طبیعی جداسازیه، ولی اندازه و بار tenantها مساوی نیست؛ «یه tenant یه shard» همیشه متعادل نمی‌مونه. اینو یادت نره.

In SaaS products, each customer (tenant) has separate, self-contained data. Sometimes sharding serves exactly that: one shard per tenant, or several small tenants in one shard. Advantages:

  • جداسازیِ منابع: عملیات سنگین یه tenant، performance بقیه رو خراب نمی‌کنه. هرکی سر جای خودشه.
  • جداسازیِ دسترسی: باگ تو کنترل دسترسی، دیتای tenant دیگه رو لو نمی‌ده (چون دیتاها فیزیکی جدان). یه لایه امنیت اضافه می‌خری.
  • Cell-based architecture: سرویس‌ها و storage یه دسته tenant رو می‌ریزی تو یه «cell» خودبسنده؛ خرابی هر cell همون‌جا می‌مونه و بقیه رو نمی‌ترکونه.
  • بکاپ و بازیابیِ جداگانه: یه tenant رو برمی‌گردونی بدون این‌که بقیه بفهمن — مثلاً بعد از یه delete اشتباهی. نگران نشو.
  • سازگاریِ قانونی: قوانین GDPR و CCPA حق «دسترسی و حذف دیتای شخصی» می‌دن؛ وقتی دیتای هر شخص تو shard خودشه، export و delete راحت می‌شه.
  • Data residence: اگه دیتای tenant باید تو یه حوزهٔ قضایی خاص بمونه، shard اون رو می‌چسبونی به همون region. تمیز و ساده.
  • عرضهٔ تدریجیِ schema: migrationها رو یه‌باره برای همه اجرا نمی‌کنی؛ tenantبه‌tenant جلو می‌ری و سوتی رو زودتر می‌گیری. تهش ریسکت کم می‌شه.
  • Resource isolation: one tenant's heavy operations don't ruin the rest's performance.
  • Access isolation: an access-control bug doesn't leak another tenant's data (physically separate data).
  • Cell-based architecture: one tenant group's services and storage gather in a self-contained “cell”; each cell's failure stays inside itself.
  • Separate backup and recovery: restoring one tenant without touching the rest — e.g. after a mistaken data deletion.
  • Legal compatibility: GDPR and CCPA grant “access and erase personal data” rights; when each person's data sits in its own shard, export and delete get simple.
  • Data residence: if a tenant's data must stay in a given jurisdiction, pin its shard to that region.
  • Gradual schema rollout: migrations don't run for everyone at once; you advance tenant by tenant and spot problems earlier.

چالش‌ها رو هم ببین: فرض اینه «هر tenant تو یه ماشین جا می‌شه» (ولی tenant غول‌پیکر رو داخل خودش هم shard کنی)، و خیل tenantهای فسقلی (overhead shard جدا و جابه‌جاکردنشون موقع رشد)، و سخت‌شدن قابلیت‌هایی که دیتای چند tenant رو به هم ربط می‌دن. تهش اینه: جداسازی خوبه، ولی مجانی نیست.

Challenges: the “each tenant fits on one machine” assumption (a giant tenant must be sharded inside itself too), many small tenants (per-shard overhead and moving them as they grow), and harder features spanning several tenants' data.

۲2 طرح‌های sharding برای دادهٔ key-valueSharding schemes for key-value data

فرض کن هر رکورد یه بلیته که روش نوشته کدوم shard سوارش کنه — همون partition key. یادت باشه فقط شمردن رکوردها کافی نیست. نکته ماندگار: shard پر ولی خلوت با shard کم‌داده ولی شلوغ فرق دارد.

مثال فنی: کلید تعیین‌کنندهٔ مسیر

وضعیت اولیه: تصور کن یه درخواست GET customer:17 داری، کنارش یه کوئری که همه مشتری‌های یه شهر رو می‌خواد.

اجرای مرحله‌به‌مرحله: اگه با customer_id shard کنی، اولی مستقیم میره سراغ یه shard. ولی کوئری شهر ایندکس درست نداشته باشه، مجبوره همه shardها رو بگرده.

نتیجه و دلیل: یادت باشه انتخاب کلید فقط پخش write نیست. نکته ماندگار: مشخص می‌کنه کوئری‌های مهمت به چندتا shard سر می‌زنن.

The core question: with all this data, where do we put which record? The goal is spreading data and query load evenly across nodes. Unfair splitting is called skew: some shards hold more data or queries and sharding goes ineffective — extremely, all load lands on one shard while 9 of 10 nodes idle. Such a shard is a hot shard and an overloaded key a hot key (e.g. a celebrity's account on a social network).

فرض کن الگوریتم نگاشت یه فرمول ساده‌ست: ورودی‌اش partition key، خروجی‌اش shard. تو key-value store معمولاً خود کلید (یا تیکه اولش) تو مدل رابطه‌ای هم یه ستون جدول (نه حتماً کلید اصلی). یادت باشه برای rebalancing و فرار از hotspot باید منعطف باشه؛ وگرنه قفل می‌شی.

The mapping algorithm's input must be the partition key and its output the shard; in a key-value store usually the key (or the key's first part), in the relational model one table column (not necessarily the primary key). The algorithm must also stay flexible for rebalancing — for escaping hotspots.

تصور کن تو range sharding هر shard یه تیکه پشت سر هم از کلیدهای مرتب رو نگه می‌داره. خوندن یه بازه راحته. ولی یادت باشه داده جدید معمولاً می‌ریزه رو آخرین بازه.

مثال فنی: بازهٔ زمانی و shard داغ

وضعیت اولیه: فرض کن ایونت‌های ساعت ۱۰ تا ۱۱ رفتن رو shard آخر، و همه ایونت‌های تازه هم مال همین الانه.

اجرای مرحله‌به‌مرحله: بازه‌های قدیمی خلوتن، ولی shard بازه جاری همه writeها رو می‌خوره. اگه بازه جاری رو ریزتر کنی یا کلید رو با bucket قاطی کنی، فشار پخش می‌شه.

نتیجه و دلیل: یادت باشه range sharding اسکن زمانی رو راحت می‌کنه، ولی کلید پشت سر هم همه writeها رو یه‌جا جمع می‌کنه.

Here each shard holds a contiguous range of sorted keys — like volumes of a printed encyclopedia: volume 1 words A and B, volume 12 words T to Z. Boundaries needn't be evenly spaced, because data isn't uniform; boundaries must adapt to the data.

  • مزیت: فرض کن داخل هر shard کلیدها مرتن (B-tree یا SSTable). نکته ماندگار: range scan اینجا سریعه؛ کلید ترکیبی هم مثل ایندکس چندستونی جواب میده.
  • مثال: تصور کن داده سنسورها با کلید timestamp داری؛ خوندن یه ماه کامل فقط یه range scan ساده‌ست.
  • خطر: یادت باشه کلیدهای پشت سر هم یه shard رو داغ می‌کنن. اگه کلید فقط timestamp باشه، همه writeهای «این ماه» می‌ریزن رو shard همین ماه و بقیه بیکار می‌مونن.
  • راه‌حلِ رایج: فرض کن اول کلید sensor-id (یا tenant) بذاری تا بار بین shardها پخش شه. بهاش رو یادت باشه: برای یه بازه از چند سنسور باید چندتا کوئری جدا بزنی.
  • مرزها: یا دستی می‌چینی (مثل Vitess) یا خودکار (مثل Bigtable، HBase، حالتِ range در MongoDB، CockroachDB، FoundationDB). تصور کن مرزها باید با داده‌ات تکون بخورن.
  • Rebalancing: اولش pre-splitting داری (اگه توزیع کلیدها رو ندونی خطرناکه)، بعد split/merge مثل بالای B-tree. یادت باشه آستانه معروف split تو HBase حدود ۱۰GB یا رد شدن مداوم write از آستانه‌ست.
  • گرانیِ split: فرض کن همه داده باید تو فایل جدید بازنویسی شه (مثل compaction). نکته تلخش اینه: دقیقاً shard داغِ زیر فشار split می‌شه و فشارش بیشتر می‌شه.
  • Advantage: inside each shard keys are ordered (B-tree or SSTable — Chapter 4), so range scans are fast and a composite key works like a multi-column index.
  • Example: sensor-network data keyed by timestamp — fetching a month of readings costs no effort.
  • Risk: concentrated writes on nearby keys heat one shard. If the key is only a timestamp, all of “this month's” writes go to this month's shard while the rest idle.
  • Common fix: prefixing the key with the sensor (or tenant) ID to spread load across shards — price: a multi-sensor time range needs several separate queries.
  • Boundaries: manual (like Vitess) or automatic (Bigtable, HBase, range mode in MongoDB, CockroachDB, FoundationDB).
  • Rebalancing: pre-splitting at the start (dangerous without knowing the key distribution), then split/merge like the top of a B-tree; HBase's common split threshold is ~10GB or writes persistently crossing a threshold.
  • Split cost: all data must be rewritten into new files (like compaction) — and exactly the hot shard under pressure splits, raising its pressure further.

۲.۲ تقسیم بر اساس hash و تلهٔ mod N + نمودار ۳2.2 Hash sharding and the mod-N trap + diagram 3

فرض کن تو hash sharding خروجی تابع hash میگه رکورد کجا بره. یادت باشه اگه مستقیم از باقیمونده تقسیم بر تعداد سرورها استفاده کنی، با عوض شدن تعداد سرورها کلی داده جابه‌جا می‌شه.

مثال فنی: تلهٔ تغییرِ مقسوم‌علیه

وضعیت اولیه: تصور کن hash یه کلید 10 شده؛ با سه سرور مقصد می‌شه 10 % 3 = 1.

اجرای مرحله‌به‌مرحله: حالا سرور چهارم رو اضافه کن، می‌شه 10 % 4 = 2. خیلی از کلیدهای دیگه هم باهاش جابه‌جا می‌شن.

نتیجه و دلیل: نکته ماندگار: shard منطقی رو از سرور فیزیکی جدا کن، تا اضافه شدن ماشین مجبورت نکنه همه کلیدها رو دوباره پخش کنی.

If key closeness doesn't matter to you (e.g. keys are tenant IDs), the most common move is first hashing the partition key. A good hash evens out skewed data: output looks random but identical input always gives identical output.

  • یادت باشه hash لازم نیست رمزنگارانه باشه: MongoDB از MD5 استفاده می‌کنه و Cassandra/ScyllaDB از Murmur3.
  • تصور کن hash خود زبون برنامه‌نویسی بین پروسه‌ها عوض شه (Object.hashCode() تو Java، Object#hash تو Ruby). اینا برای sharding به درد نمی‌خورن.
  • تلهٔ hash(key) % N: ظاهرش ساده‌ست، ولی با عوض شدن N تقریباً همه کلیدها جابه‌جا می‌شن (از ۳ node بری به ۴، بیشتر کلیدها node عوض می‌کنن). یادت باشه rebalancing باید کمترین جابه‌جایی رو بکنه، پس mod N مردوده.
  • تعدادِ ثابتِ shard: فرض کن از اول ۱۰۰۰ تا shard داری، رو ۱۰ تا node هرکدوم ۱۰۰ تا. کلید میره به shard hash(key) % 1000 و فقط «نگاشت shard به node» عوض می‌شه. با اومدن node جدید فقط چندتا shard کامل جابه‌جا می‌شن — خیلی ارزون‌تر از split. یادت باشه عددی انتخاب کن که مقسوم‌علیه زیاد داشته باشه، و به node قوی‌تر shard بیشتر بده (Citus، Riak، Elasticsearch، Couchbase).
  • بهای تعدادِ ثابت: اگه تعداد shard کم بذاری و بعد node بیشتر بخوای، resharding گرون رو دستته (شکافتن هر shard و بازنویسی فایل‌ها؛ بعضی سیستم‌ها موقع write اصلاً اجازه نمیدن).
  • بازه‌های hash: تصور کن key-range رو با hash قاطی کردی — هر shard یک بازه از مقادیرِ hash را دارد (مثلاً ۰ تا ۱۶۳۸۳ برای shard صفرم). کلیدهای نزدیک (مثل timestampهای پشت سر هم) پخش می‌شن و shard بزرگ مثل key-range split می‌شه. فقط range query رو خود partition key گرون می‌شه. نکته ماندگار: با کلید ترکیبی (partition key ستون اول، ترتیب با بقیه ستون‌ها) بازه‌خونی داخل shard رو نگه می‌داری. این طرح تو YugabyteDB و DynamoDB هست و در MongoDB یه گزینه‌ست.
  • The hash needn't be cryptographic: MongoDB uses MD5 and Cassandra/ScyllaDB use Murmur3.
  • Programming-language hash functions may differ between processes (Object.hashCode() in Java, Object#hash in Ruby) and don't fit sharding.
  • The hash(key) % N trap: seemingly simple, but when N changes nearly all keys move (going from 3 to 4 nodes, most keys switch nodes). Good rebalancing moves the least data, so mod N is rejected.
  • Fixed shard count: e.g. 1000 shards from the start, 100 on each of 10 nodes; a key goes to shard hash(key) % 1000 and only the “shard-to-node map” changes. When a node joins, a few whole shards move — cheaper than splitting. Pick the shard count with many divisors and give stronger nodes more shards (Citus, Riak, Elasticsearch, Couchbase).
  • Fixed-count price: if the shard count comes out small and more nodes are needed, expensive resharding is required (splitting each shard and rewriting files; some systems forbid it during writes).
  • Hash ranges: key-range combined with hashing — each shard holds a range of hash values (e.g. 0–16383 for shard zero). Nearby keys (consecutive timestamps) scatter and big shards split like key-range; only range queries on the partition key itself get expensive. The composite-key trick (partition key in the first column, order from the rest) still preserves in-shard range reads. This scheme lives in YugabyteDB and DynamoDB and is one MongoDB option.

تو مرحله اول خط بالا، گره «Partition Key» (زیرنویس: «key or key prefix»، برچسبِ «skewed input ok») نشسته است. فلشِ پررنگِ «hash the partition key» به گرهِ «Hash Function» می‌رود (زیرنویس: «Murmur3 or MD5»، برچسبِ «not cryptographic»). بعد فلشِ «map hash to a shard» به «Fixed Shards» (زیرنویسِ «hash(key) % 1000»، برچسبِ «count fixed up front») و سپس فلشِ «node joins: move shards» به «Move Whole Shards» (زیرنویس: «shard to node map»، برچسبِ «cheap rebalancing»).

خطِ پایین همان مسیر را برای داده‌ای که کلیدهایش در زمان خوشه می‌کنند باز می‌کند: گرهِ «Clustered Keys» (زیرنویس: «nearby keys cluster»، برچسبِ هشدارِ «hot shard risk») با فلشِ «nearby keys scatter apart» به «Uniform Spread» (زیرنویس: «ordering is lost»، برچسبِ «no key range scans») می‌رود؛ بعد «assign ranges of hashes» به «Hash Ranges» (زیرنویس: «ranges of hash values»، برچسبِ «count adapts to data») و سرانجام «shard too big: split it» به «Split and Merge» (زیرنویس: «rewrite to new files»، برچسبِ «expensive operation»).

درس شکل رو یادت باشه: دو تفاوت اصلی تو یه نگاه — «تعداد ثابت، جابه‌جایی کل shardها» در برابر «تعداد متغیر، شکافتن و بازنویسی». و هشدار دو خط پایین: hash بار رو یکنواخت می‌کنه ولی ترتیب رو می‌سوزونه و hotspot کلید داغ رو هم درمون نمی‌کنه — هر گلی یه بویی داره.

کد: تلهٔ mod N در برابر تعدادِ ثابتِ shardCode: the mod-N trap vs fixed shard count
# — نکن: با تغییرِ N بیشترِ کلیدها جابه‌جا می‌شوند
shard = hash(key) % N_nodes

# — بکن: نگاشت کلید به shard ثابته؛ فقط shard→node عوض می‌شه
N_SHARDS = 1000
shard_id = hash(key) % N_SHARDS          # هرگز عوض نمی‌شه
node_of  = assign_shards_to_nodes(N_SHARDS, nodes)   # با اضافه شدن node، چند تا shard کامل منتقل می‌شن

فرقش تو یه جمله: تو حالت دوم موقع رشد خوشه فقط «مالکیت shard» عوض می‌شه، نه «جای کلیدها». یادت باشه همین یه جمله نجاتت میده. 

# — don't: when N changes, most keys move
shard = hash(key) % N_nodes

# — do: key-to-shard mapping is fixed; only shard→node changes
N_SHARDS = 1000
shard_id = hash(key) % N_SHARDS          # never changes
node_of  = assign_shards_to_nodes(N_SHARDS, nodes)   # a few whole shards move when a node joins

The difference in one sentence: in the second case, cluster growth only changes “shard ownership”, not “where keys live”.

۲.۳ consistent hashing و انباره‌های داده2.3 Consistent hashing and data warehouses

تصور کن تو consistent hashing فضای hash رو تیکه‌تیکه میدی به nodeها. با اومدن node جدید معمولاً فقط چندتا بازه تکون می‌خورن. یادت باشه توازن هنوز به اندازه و تعداد بازه‌ها بستگی داره.

مثال فنی: دایرهٔ hash و مالک جدید

وضعیت اولیه: فرض کن توکن‌های A و B رو حلقه‌ان و هر کلید میره سراغ مالک بعدی.

اجرای مرحله‌به‌مرحله: با اضافه شدن C فقط بازه‌هایی که C مالکشون می‌شه جابه‌جا می‌شن؛ virtual nodeها هم می‌تونن تقسیم ظرفیت رو ریزتر کنن.

نتیجه و دلیل: یادت باشه consistent اینجا یعنی نگاشت سر جاش می‌مونه موقع تغییر اعضا؛ ربطی به consistency خوندن و نوشتن نداره.

Cassandra and ScyllaDB split the hash-value range (e.g. 0–1024) into contiguous ranges with random boundaries and give each node several ranges (default: 16 ranges per node in Cassandra, 256 in ScyllaDB). Some ranges are bigger but several ranges per node compensate the inequalities. When a node joins, boundaries shift and parts of ranges move — with no more transfer than needed.

Consistent hashing یک الگوریتمِ نگاشت با دو ویژگی است: (۱) تعدادِ کلیدهای هر shard تقریباً برابر باشد، (۲) با تغییرِ تعدادِ shard، کمترین تعدادِ کلید جابه‌جا شود. دقت کن «consistent» اینجا ربطی به consistencyِ replica (فصل ۶) یا ACID (فصل ۸) ندارد؛ یعنی «تمایلِ کلید به ماندن در جای خودش». خانواده‌های دیگر: rendezvous (highest random weight) و jump consistent hashing که به‌جای شکافتنِ بازه‌ها، کلیدهای پراکنده را به node تازه می‌دهند.

Consistent hashing is a mapping algorithm with two properties: (1) each shard holds roughly as many keys, (2) when the shard count changes, the fewest keys move. Note “consistent” here has nothing to do with replica consistency (Chapter 6) or ACID (Chapter 8); it means “a key's tendency to stay in its place”. Other families: rendezvous (highest random weight) and jump consistent hashing, which hand scattered keys to the fresh node instead of splitting ranges.

انباره‌های داده (Data Warehouses) هم همین مسئله را دارندData warehouses have the same problem

تصور کن تو BigQuery، partition key میگه رکورد تو کدوم partition بره و cluster columns ترتیب داخل partition رو می‌سازه. Snowflake رکوردها رو می‌ذاره تو micro-partitionهای خودکار و cluster key میده دستت؛ Delta Lake هر دو رو داره. یادت باشه خوشه‌بندی فقط range scan رو بهتر نمی‌کنه؛ فشرده‌سازی و filter رو هم راه می‌ندازه.

In BigQuery, the partition key decides which partition a record lands in and cluster columns order inside the partition. Snowflake places records in automatic micro-partitions and gives users a cluster key; Delta Lake supports both. Clustering doesn't just speed range scans; it improves compression and filtering too.

فرض کن تعداد رکوردها قشنگ نصف شده؛ فکر می‌کنی کارت تمومه؟ نه! ترافیک واقعی یه چیز دیگه‌ست. یادت باشه حجم، نرخ درخواست و هزینه پردازش هر shard رو جدا جدا چک کنی.

مثال فنی: کلید داغ با حجم کم

وضعیت اولیه: تصور کن کلید پست p9 خودش فقط چند کیلوبایتِ ناقابله، ولی نصف درخواست‌ها زوم کردن روش و دارن شمارنده‌ش رو تکون می‌دن.

اجرای مرحله‌به‌مرحله: فرض کن hash کردی و پخش کردی؛ قاطی نکن! همه عملیات همین یه کلید باز می‌ره می‌شینه رو همون یه shard.

نتیجه و دلیل: یادت باشه توازن بایت و کلید یعنی هیچی؛ بار واقعی یه چیز دیگه‌ست. یه hot key یه درمان مخصوص خودش می‌خواد.

۳.۱ خنثی‌سازیِ hotspotها3.1 Neutralizing hotspots

فرض کن یه hot key داری؛ یعنی یه کلید تنهایی نصف بار رو بلعیده. hash هم دلت رو خوش نکن، باز همون کلید رو می‌فرسته سراغ همون یه مقصد. برای پخش بارش باید نقشه داده یا مدل خواندن رو عوض کنی.

مثال فنی: شکستن شمارندهٔ داغ

وضعیت اولیه: تصور کن شمارنده بازدید p9 گیر کرده رو یه کلید و همون شده گلوگاه؛ همه صف کشیدن پشتش!

اجرای مرحله‌به‌مرحله: فرض کن نوشتن‌ها رو می‌پاشی رو ۱۶ تا کلید p9:0…15؛ موقع خواندن باید هر ۱۶ تا رو جمع بزنی و جواب بدی.

نتیجه و دلیل: بار نوشتن پخش می‌شه، ولی خواندن گرون می‌شه و گرفتن یه snapshot مشترک سخت می‌شه. برای موجودی جدی، بی‌گدار به آب نزن و همین‌جوری از این الگو استفاده نکن.

Consistent hashing spreads keys evenly, but that doesn't guarantee real load is even. If query load concentrates on some keys (a celebrity's post with millions of followers causing an activity storm), nodes still break under load while the rest idle.

  • جداسازیِ کلیدِ داغ: فرض کن تو طرح rangeای (کلید یا hash) کلید داغ رو تنها بنداز تو یه shard، حتی یه ماشین دربست بده بهش. ساده‌ست، ولی نکته‌ش اینه: اول باید پیداش کنی!
  • پیشوندِ تصادفی: افزودنِ دو رقمِ تصادفی به ابتدا یا انتهای کلید، نوشتنِ یک کلید را بین ۱۰۰ کلید پخش می‌کند. بها: خواندن‌ها باید ۱۰۰ کلید را بخوانند و ادغام کنند؛ فقط نوشتن پخش می‌شود، نه خواندن. ضمناً باید بدانی کدام کلیدها «داغ» شده‌اند و فرایندی برای تبدیلِ کلیدِ عادی به کلیدِ مدیریت‌شده داشته باشی.
  • تغییر در طولِ زمان: فرض کن پست وایرال چند روز می‌ترکه بعد می‌خوابه؛ بعضی کلیدها نوشتن‌داغن، بعضی خواندن‌داغ — نسخه هر کدوم فرق می‌کنه.
  • سیستم‌های ابری: فرض کن «heat management» یا «adaptive capacity» (مثل DynamoDB) خودش بار رو جابه‌جا می‌کنه؛ بی‌زحمت ولی پشت پرده‌ش از کتاب خارجه.
  • Isolating the hot key: in range-based schemes (key or hash), the hot key can sit alone in one shard and even get a dedicated machine.
  • Random prefix: adding two random digits to the key's start or end spreads one key's writes across 100 keys. Price: reads must fetch all 100 keys and merge; only writes spread, not reads. You must also know which keys turned “hot” and own a process for converting a plain key into a managed one.
  • Changing over time: a viral post is hot for days then calms; some keys are write-hot and some read-hot — each needs a different strategy.
  • Cloud systems: automatic “heat management” or “adaptive capacity” fixes (like DynamoDB) move load around; their details are outside the book.

Three columns answer “where do we put one hot key's load?” First column: place the hot key alone in one shard (even a dedicated machine) — simple, but you must find hot keys, and heat moves over time. Middle column: with a random suffix, spread one key's writes across 100 keys — but only writes spread, and reads must fetch and merge all 100.

Third column: adaptive cloud management (like DynamoDB) moves load itself — effortless but opaque. The diagram's lesson is in the footer: hashing spreads keys, not load; and “write-hot” vs “read-hot” need different cures.

۳.۲ rebalancing خودکار یا دستی؟3.2 Automatic or manual rebalancing?

تصور کن rebalancing یعنی اسباب‌کشیِ بخشی از داده و مسئولیت بین گره‌ها. حالت خودکار واکنش رو تندتر می‌کنه، ولی وسط فشار اگه زیاد جابه‌جا کنی، خودت بنزین می‌ریزی رو آتیش. نکته‌ش اینه: جابه‌جایی همیشه نجات نیست.

مثال فنی: مهاجرت در وقت نامناسب

وضعیت اولیه: فرض کن یه node کند شده و کنترل‌گر هوس کرده همون موقع 200 GB داده‌ش رو جابه‌جا کنه.

اجرای مرحله‌به‌مرحله: این انتقال شبکه و دیسک رو می‌بلعه و کندی رو بدتر می‌کنه؛ اول علت کندی رو پیدا کن، بعد با محدودیت نرخ حرکت کن.

نتیجه و دلیل: یادت باشه کندی موقتی همیشه rebalance نمی‌خواد؛ حلقه خودکارِ بدون مهار فقط ازدحام رو بیشتر می‌ترکونه.

Whenever a node joins or leaves, or data grows unbalanced, data must be respread (rebalancing). Three approaches exist:

فرض کن یه node فقط کند شده، نمرده! ولی بقیه فکر می‌کنن مرده و خودکار بارش رو خالی می‌کنن رو بقیه — یعنی رو سیستمِ زیر فشار، فشار بیشتر سوار می‌کنی. تهش چی؟ خرابی آبشاری: nodeهای بعدی هم می‌خوابن و الکی مرده اعلام می‌شن. برای همین تو rebalancing، «انسان در حلقه» معمولاً امن‌تره.

If a node is merely slow and the rest deem it dead, the cluster automatically takes its load and gives it to the rest — imposing more pressure on exactly the system under pressure. The result can be a cascading failure: the next nodes fall under load too and are wrongly declared dead. That is why a “human in the loop” is often safer for rebalancing.

Now shards have found their places. Next question: to read or write a given key, which node — which IP and port — do you connect to? That job is request routing, very like service discovery (the “load balancers and service meshes” section in Chapter 5). The big difference: application services are usually stateless and any instance can answer any request; but a key's request must only go to a node holding a replica of that key's owning shard.

۴.۲ سرویسِ هماهنگی و خطرِ split brain4.2 Coordination services and split-brain risk

  • کی تصمیم می‌گیره؟ فرض کن یه coordinator گذاشتی؛ اگه خودش بیفته چی؟ اگه failover بشه چطور جلوی split brain رو می‌گیری که دو تا coordinator حرف متضاد نزنن؟
  • کی باخبر می‌شه؟ تصور کن مالک shard عوض شده ولی routing tier یا کلاینت هنوز نفهمیدن — نقشه‌شون باد کرده.
  • درخواست‌های تو پرواز موقع cutover چی می‌شن؟ مالک تازه تحویل گرفته، ولی هنوز درخواست می‌رسه به مالک قدیمی. اینا رو نه می‌شه ول کرد نه قاطی کرد.
  • Who decides? The simplest case is one coordinator; but what if that node fails? And if the role fails over, how is split brain (two coordinators with conflicting decisions) prevented?
  • Who learns of changes? The routing tier or client must be told of shard-ownership changes.
  • In-flight requests at cutover: the fresh owner has taken over, but requests still reach the old owner.

تصور کن سرویس هماهنگی مثل تابلوی مشترک نقشه و مالکیته. اگه دو تا node هم‌زمان خودشون رو مالک یه shard بدونن، هر دو write ناسازگار قبول می‌کنن و کار می‌ترکه.

Moving one shard from node A to node B is no “single-step command”; it is a state machine. Data must be copied, writes arriving mid-copy must be followed, and ownership flips at only one defined instant. If we name each moment of that path a “state” and make transitions explicit, we understand what failure at each stage means and what the system must decide then — instead of picturing the move as one vague, irreversible process.

حساس‌ترین لحظه همون پنجرهٔ cutover ـه: همون چند لحظه که نقشهٔ shard سوییچ می‌شه ولی هنوز درخواست داره می‌ره سمت مالک قدیمی. فرض کن دو مدل مشتری داری: اونایی که درخواست‌شون هنوز می‌خوره به node قدیمی (و باید forward بشن یا رد بشن) و اونایی که نقشهٔ قدیمی رو کش کردن و اصلاً خبر ندارن مالک عوض شده — و writeهاشون می‌تونه بشینه یه جای اشتباه. این‌جا اگه شل بگیری کارت ساخته‌ست.

The most sensitive moment is the cutover window: that short span when the shard map switches while requests still fly to the old owner. In that window there are two customer kinds: those whose requests still reach the old node (and must be forwarded or rejected) and those who cached the old map and never heard the owner changed — whose writes may land in the wrong place.

قدم 01، stateیِ «Serving on A»: همون nodeای که فعلاً داره shard رو سرو می‌کنه. زیرنویسش «node A owns the shard» ـه و برچسب گوشه‌ش «stable assignment» — یعنی نقشهٔ shard آروم و معتبره. فلش خروجی «node joins» نام داره: همون لحظه‌ای که یه node تازه میاد تو خوشه و rebalancing می‌گه shard رو تکون بده. می‌رسی به قدم 02، «Copying Data» با زیرنویسِ «stream the shard to B» و برچسبِ «takes time» — حرفش اینه: کپی کُنده و دنیا واینمی‌سته. گذار بعدی «bulk copy done» ـه و می‌رسی به قدم 03، «Catch-Up» با زیرنویسِ «forward or buffer writes» و برچسبِ «lag must approach zero»: writeهایی که وسط کپی رسیدن باید دنبال بشن تا عقب‌افتادگی تقریباً صفر بشه.

وقتی عقب‌افتادگی کم شد، فلشِ «lag near zero» می‌بردت به قدم 04: «Cutover» با زیرنویسِ «shard map updated» و برچسبِ «ownership switches». شکل این state فرق داره (یه state تصمیمه) چون تنها لحظه‌ایه که دنیای بیرون باید عوض بشه: نقشهٔ shard دقیقاً همین‌جا atomic سوییچ می‌شه. فلش پررنگ خروجی «map: shard to B» می‌رسه به قدم 05: «Serving on B» با زیرنویسِ «node B owns the shard» و برچسبِ «new assignment» — مقایسه‌ش کن با برچسبِ قدم اولِ «stable assignment»: چرخه بسته شد، فقط مالک عوض شده.

حالا پنجرهٔ cutover. از stateیِ «Cutover» یه فلش چین‌چین میاد پایین: «requests still in flight» به stateیِ «Old Requests» تو laneِ «In-flight requests» — با زیرنویسِ «still heading for A» و برچسبِ «in the cutover window». این state دو تا خروجی داره که سرنوشت‌شون زمین تا آسمون فرق داره. راه اول فلشِ «forward or reject» ـه که برمی‌گرده به «Serving on B» — یعنی مالک قدیمی درخواست دیررسیده رو به مالک تازه forward می‌کنه یا مؤدبانه رد می‌کنه تا کلاینت retry بزنه. راه دوم فلش قرمزِ «client cached old map» ـه که مستقیم می‌ریزه تو lane پایانی: state شکستِ «Stranded Writes» با زیرنویسِ «stale routing table» و برچسبِ «writes to the wrong node». یعنی کلاینت با نقشهٔ قدیمی هنوز داره به node قدیمی می‌نویسه و writeش می‌شینه جایی که دیگه مالک نیست — دقیقاً همون فاجعه‌ای که cutover باید جلوش رو بگیره.

و مسیر سوم، مسیر سقوط. از stateیِ «Copying Data» یه فلش قرمز میاد پایین: «network or disk fails» به stateیِ «Move Aborted» تو laneِ «Abort path» — با زیرنویسِ «map still says A» و برچسبِ «no data lost». و نکتهٔ کلیدی همون فلش برگشتی پررنگه: «A still owns it» که برت می‌گردونه به «Serving on A». چرا چیزی گم نشده؟ چون نقشهٔ shard هیچ‌وقت به‌روز نشده بود؛ پس A هنوز مالک معتبره، کپی نصفهٔ رو B فقط دادهٔ دورریختنیه، و سیستم برمی‌گرده به همون حالت پایدار اول.

درس این شکل تو یه جمله: نقشهٔ shard تنها مرجع مالکیته. تا وقتی نقشه نگفته مالک عوض شده، مالک قدیمی هنوز صاحب تصمیمه و هر جابه‌جایی نصفه‌تمام قابلِ لغوه — همین «Move Aborted» رو امن می‌کنه نه فاجعه. از اون طرف، کل خطر «Stranded Writes» از یه جا میاد: یکی به نقشهٔ قدیمی تکیه کرده؛ پس یا باید تو پنجرهٔ cutover درخواست‌ها رو forward یا رد کنی، یا کش نقشهٔ کلاینت‌ها رو کوتاه و باطل‌کردنی نگه داری.

و قانون عملی آخر: تا مالک تازه تأیید نکرده، از مبدأ چیزی رو پاک نکن. دادهٔ رو A رو فقط وقتی می‌تونی حذف کنی که نقشهٔ جدید ثبت شده باشه، B سرویس‌دهی‌ش رو تأیید کرده باشه، و هیچ درخواست تو پروازی نمونده باشه. حذف زودهنگام دقیقاً همون کاریه که یه abort بی‌ضرر رو تبدیل می‌کنه به «Stranded Writes» دائمی.

Unlike diagram 4, a sequence, this diagram is a lifecycle: four horizontal lanes each holding a different path of the same story — “Ownership” on top (the main ownership path), “In-flight requests” (in-flight requests), “Abort path” (the failure path) and “Terminal” (terminal states). Main-path states carry step numbers, 01 to 05; so we start the story at step one.

Step 01, the “Serving on A” state: the node currently serving the shard. Its caption is “node A owns the shard” and its corner label “stable assignment” — in this state the shard map is calm and authoritative. The outgoing transition arrow is named “node joins”: the moment a fresh node joins the cluster and rebalancing decides to move the shard. We reach step 02, “Copying Data” captioned “stream the shard to B” and labelled “takes time” — the emphasis is just that: copying is slow and the world doesn't wait. The next transition “bulk copy done” brings step 03, “Catch-Up” captioned “forward or buffer writes” and labelled “lag must approach zero”: writes that arrived mid-copy must be followed until the lag is near zero.

When the lag shrinks, the “lag near zero” arrow carries us to step 04: “Cutover” captioned “shard map updated” and labelled “ownership switches”. This state's shape differs (a decision state) because it is the only instant the outside world must change: the shard map flips atomically right here. The bold outgoing “map: shard to B” arrow (the emphasized arrow) reaches step 05: “Serving on B” captioned “node B owns the shard” and labelled “new assignment” — compare with step one's “stable assignment” label: the cycle closed, only the owner changed.

Now the cutover window. A dashed arrow drops from the “Cutover” state: “requests still in flight” to the “Old Requests” state in the “In-flight requests” lane — captioned “still heading for A”, labelled “in the cutover window”. That state has two exits with utterly different fates. The first is the “forward or reject” arrow back to “Serving on B” — the old owner forwards the late request to the fresh owner or politely rejects it for the client to retry. The second is the red “client cached old map” arrow pouring straight into the terminal lane: the failed “Stranded Writes” state captioned “stale routing table” and labelled “writes to the wrong node”. An old-mapped client still writes to the old node, and its write lands where nobody owns — exactly the disaster cutover must prevent.

And the third path, the fall path. A red arrow drops from the “Copying Data” state: “network or disk fails” to the “Move Aborted” state in the “Abort path” lane — captioned “map still says A”, labelled “no data lost”. And the key point is that bold return arrow: “A still owns it” carries us back to “Serving on A”. Why was nothing lost? Because the shard map never updated; so A is still the authoritative owner, the incomplete copy on B is just deletable data, and the system returns to that same stable first state.

This figure's lesson in one sentence: the shard map is the only ownership authority. Until the map says the owner changed, the old owner still owns decisions, and any unfinished move is cancellable — which turns “Move Aborted” into a safe state, not a disaster. Conversely, all of “Stranded Writes”' danger comes from one place: someone relied on an old map; so either requests must be forwarded or rejected in the cutover window, or clients' map caches kept short and invalidatable. And the final practical rule: delete nothing from the source until the fresh owner confirms. Data on A may be removed only after the new map is registered, B confirmed serving, and no in-flight request remains. Early deletion is exactly what turns a harmless abort into permanent “Stranded Writes”.

Read this diagram as four horizontal lanes: “Shard rollout” on top (the main path), “Validation” for the checks, “Rollback controller” for the way back, and “Terminal exits” for the end states. Here's the thing: the reshard runs in two phases — logical first, physical second — and every step has a defined way back if something breaks.

Start at the start state “Single Primary” (“one host serves all”, tagged “baseline” — one host still serves everything). The “sample plans” arrow leads to “Shadow Validated” (“plans sampled live”, tagged “preview”): sharding plans are rehearsed in shadow first, not on live traffic. Then “views enabled” reaches step 02, “Logically Sharded” (“views route by hash”, tagged “serving”): the table hasn't physically moved yet; views just route traffic by hash. The point worth keeping: rollback at this stage is still cheap.

Now comes measurement: “measure overhead” reaches “Views Verified” (“overhead within budget”, tagged “measured”) — the views' overhead must stay inside budget. If the budget holds, “budget holds” carries you to step 03, “Physically Split” (“full copy to N hosts”, tagged “migrating”): now the data is really copied. When the copy finishes, “copy complete” reaches step 04, “Cutover Gate” (“health plus latency”, tagged “gate” — drawn as a decision, because it is a gate). If the gates go green, “gates pass” lands on “Steady Scaled” (“split again any time”, tagged “terminal”): the successful end state — and you can split again whenever you need.

And now the two ways back. The first is “Config Rollback” (“seconds, reroute flag”, tagged “automatic”): if a defect shows up in the logical phase (“defect found” from “Logically Sharded”) or overhead blows the budget (“over budget” from “Views Verified”), you return with just a reroute flag — “route restored” reaches “Rolled Back” (“unsharded serving restored”, tagged “terminal”). The second is “Coordinated Rollback” (“reconcile split writes”, tagged “automatic”): if the physical copy turns unhealthy (“split unhealthy” from “Physically Split”) or the gates go red (“gates fail” from “Cutover Gate”), writes on both sides must be reconciled — “writes reconciled” reaches that same “Rolled Back”. The punchline: the later it breaks, the pricier the return — so put a gate before every point of no return.

نتیجه و دلیل: پس جهانی خوندن رو متمرکزتر می‌کنه، ولی تغییر رنگ یا حذف کالا باید ایندکس احتمالاً دوردست رو هم اصلاح کنه — راحتی حالا، خرج بعداً.

Local secondary index (in information retrieval: document-partitioned): each shard indexes only its own records. Writing (add, delete, update) engages only that record's shard. The used-car-sale example with the ad's unique ID as partition key: adding one red car, its own shard appends the ID to the color:red postings list.

  • اگر partition key را بدانی، جست‌وجو فقط در همان shard انجام می‌شود؛ اگر فقط «چند نتیجه» می‌خواهی، هر shardی کافی است.
  • اگر همهٔ نتایج را بخواهی و partition key را ندانی، باید کوئری به همهٔ shardها برود و جواب‌ها ادغام شوند (ماشین‌های قرمز ممکن است در shard صفرم و یکم هر دو باشند).
  • پراکنده‌خوانی، tail latency را تقویت می‌کند و مقیاس‌پذیری را محدود: shard بیشتر یعنی فضای بیشتر، نه throughputِ کوئریِ بیشتر.
  • با این حال بسیار رایج است: MongoDB، Riak، Cassandra، Elasticsearch، SolrCloud و VoltDB.
  • خطر: اگر در کدِ برنامه خودت ایندکسِ value→ID بسازی، race condition و نوشتنِ ناقص، ایندکس را از داده جدا می‌کند؛ برای همین به multi-object transaction نیاز داری (فصل ۸).
  • If you know the partition key, the search runs in that same shard; if you want only “a few results”, any shard suffices.
  • If you want all results without knowing the partition key, the query must go to all shards and answers merge (red cars may sit in both shard zero and one).
  • Scatter reads amplify tail latency and bound scalability: more shards mean more space, not more query throughput.
  • Still very common: MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud and VoltDB.
  • Risk: if you build a value→ID index yourself in application code, race conditions and partial writes detach the index from the data; hence the need for multi-object transactions (Chapter 8).

Global secondary index (یا term-partitioned): ایندکس رو همهٔ shardهاست و خودش جدا shard می‌شه — مثلاً رنگ‌های a تا r در یک shard و s تا z در shard دیگر. چون «term» (هر مقدارِ قابلِ جست‌وجو) کلیدِ partition است، می‌دانی کدام shard را بخوانی.

Global secondary index (or term-partitioned): the index spans all shards and is sharded separately itself — e.g. colors a–r in one shard and s–z in another. Because a “term” (each searchable value) is the partition key, you know which shard to read.

  • کوئریِ تک‌شرط (color = red) postings list را از یک shard می‌خواند؛ اما گرفتنِ خودِ رکوردها هنوز از چند shard است.
  • شرط‌های چندگانه (رنگ + برند) احتمالاً به shardهای مختلف می‌افتند؛ AND یعنی اشتراکِ دو postings list — برای لیست‌های بلند کُند است.
  • نوشتن پیچیده‌تر است: یک رکورد ممکن است چند shard ایندکس را به‌روز کند (هر term ممکن است shard خودش را داشته باشد) و این به distributed transaction نیاز دارد.
  • CockroachDB و TiDB و YugabyteDB ایندکس global دارن؛ DynamoDB به‌روزرسانیش رو ناهمزمان انجام می‌ده، پس خوندنش ممکنه کهنه باشه — هرکی یه سازی می‌زنه.
  • A single-condition query (color = red) reads the postings list from one shard; but fetching the records themselves still spans shards.
  • Multi-condition queries (color + brand) likely land on different shards; AND means intersecting two postings lists — slow for long lists.
  • Writing is more complex: one record may update several index shards (each term may own its shard), needing distributed transactions.
  • CockroachDB, TiDB and YugabyteDB have global indexes; DynamoDB updates its own asynchronously, so reading it may be stale.

آخرین نکتهٔ فصل: استقلالِ shardها و نوشتنِ چندشیئیThe chapter's last note: shard independence and multi-object writes

یادت باشه whole point ـش اینه: هر shard تقریباً تنهایی کار می‌کنه — همین باعث می‌شه scale بشه. ولی امان از write چند shardی! تصور کن یکیش بگیره یکیش نه — این قاطی رو فصل‌های بعد با distributed transaction جمع می‌کنیم.

Sharding is designed so each shard works nearly independently — that is what makes scalability possible. But operations that must write several shards are problematic: if one shard's write succeeds and another's fails, what then? The coming chapters (distributed transactions) answer that question.

۱. sharding با replication چه تفاوتی دارد و چگونه با هم ترکیب می‌شوند؟1. How do sharding and replication differ, and how do they combine?

تصور کن replication یعنی فتوکپی از همون داده — node ترکید، کپی هست. sharding یعنی داده رو تیکه کن، هر تیکه یه shard متفاوت. یادت باشه ترکیبشون معموله: هر shard چند تا replica داره — هم ظرفیت می‌ترکه بالا، هم خرابی رو تحمل می‌کنی.

مثال فنی: تقسیم داده با تکثیر فرق دارد

وضعیت اولیه: تصور کن کلیدهای 1…1000 رو نصف کردی: نصفش دست shard A، نصفش دست shard B.

اجرای مرحله‌به‌مرحله: حالا برای هر shard سه‌تا replica بذار؛ روی هم شش‌تا کپی فیزیکی داری. ولی قاطی نکن: A و B دو تیکهٔ فرق‌دار از دیتان، نه دو کپی از یه چیز.

نتیجه و دلیل: می‌بینی؟ sharding ظرفیت رو زیاد می‌کنه، replication جونت رو موقع خرابی نجات می‌ده. دوتا کار جدا ولی رفیق‌ان که کنار هم میان. اینو یادت نره.

Replication means a copy of the same data on several nodes (failure tolerance and read scaling); sharding means splitting data into different pieces with each piece on a different node (more writes and volume). Combined, each shard has several copies; each shard's leader sits on one node and followers on others, and each node can lead some shards and follow others.

۲. چه زمانی نباید sharding کرد؟2. When should you not shard?

فرض کن یه ماشین هنوز جواب میده — امروز یه ماشین خیلی کار می‌کنه! sharding نکن؛ فقط routing و query چند shardی و operation رو قاطی می‌کنی. نکته ماندگار: اول اندازه بگیر، بعد تیکه کن.

مثال فنی: هزینهٔ تقسیمِ زودهنگام

وضعیت اولیه: تصور کن کل دیتاست فقط 20 GBـه و یه سرور به‌راحتی بار رو جواب می‌ده.

اجرای مرحله‌به‌مرحله: حالا تیکه‌اش کن به چهار shard؛ گزارش همهٔ سفارش‌ها باید چهارتا جواب رو جمع کنه و مهاجرت دیتا هم قاطی‌پاتی می‌شه.

نتیجه و دلیل: تا وقتی محدودیت واقعی ندیدی، sharding فقط مسیر ساده رو گرون می‌کنه؛ replica هم قصهٔ جداست و برای تحمل خرابیه. قاطیشون نکن.

When one machine handles the data and writes — and one machine today does a lot. Sharding brings complexity: picking the partition key, hard scheme changes, costlier joins and multi-object writes (distributed transactions). If only reads are heavy, replication suffices.

۳. key-range sharding چه مزیت و چه خطری دارد؟ چطور hotspot زمانی را درمان می‌کنند؟3. Key-range sharding's advantage and risk? How are temporal hotspots cured?

یادت باشه key-range برای range scan عالیه ولی تله داره: کلیدهای پشت سر هم مثل timestamp همه می‌ریزن رو shard «این ماه» و می‌ترکه. فرض کن sensor_id رو بچسبونی اول کلید — بار پخش می‌شه ولی query چند سنسور گرون می‌شه.

مثال فنی: بازهٔ زمانی و shard داغ

وضعیت اولیه: فرض کن ایونت‌های ساعت ۱۰ تا ۱۱ رفتن رو shard آخر، و همه ایونت‌های تازه هم مال همین الانه.

اجرای مرحله‌به‌مرحله: بازه‌های قدیمی خلوتن، ولی shard بازه جاری همه writeها رو می‌خوره. اگه بازه جاری رو ریزتر کنی یا کلید رو با bucket قاطی کنی، فشار پخش می‌شه.

نتیجه و دلیل: یادت باشه range sharding اسکن زمانی رو راحت می‌کنه، ولی کلید پشت سر هم همه writeها رو یه‌جا جمع می‌کنه.

Advantage: ordered keys per shard, so fast range scans and composite indexes. Risk: nearby-key writes (like timestamps) heat one shard. Cure: prefixing keys with a sensor or tenant ID to spread writes — price: a multi-sensor range needs several separate queries.

۴. چرا hash(key) % N برای sharding بد است؟4. Why is hash(key) % N bad for sharding?

تصور کن hash(key) % N گذاشتی و N از ۳ شد ۴ — تقریباً همه کلیدها جابه‌جا می‌شن، فاجعه! یادت باشه shard منطقی رو از سرور فیزیکی جدا کن تا اضافه شدن ماشین فقط مالکیت رو عوض کنه، نه جای کلیدها.

مثال فنی: تلهٔ تغییرِ مقسوم‌علیه

وضعیت اولیه: تصور کن hash یه کلید 10 شده؛ با سه سرور مقصد می‌شه 10 % 3 = 1.

اجرای مرحله‌به‌مرحله: حالا سرور چهارم رو اضافه کن، می‌شه 10 % 4 = 2. خیلی از کلیدهای دیگه هم باهاش جابه‌جا می‌شن.

نتیجه و دلیل: نکته ماندگار: shard منطقی رو از سرور فیزیکی جدا کن، تا اضافه شدن ماشین مجبورت نکنه همه کلیدها رو دوباره پخش کنی.

Because N is the node count, and adding or removing one node changes every key's division — nearly all records must move. Good rebalancing means minimal moves; so key-to-shard mapping must be independent of node count (fixed shard count, hash ranges, or consistent hashing).

۵. طرحِ «تعدادِ ثابتِ shard» چطور کار می‌کند و بهایش چیست؟5. How does the “fixed shard count” scheme work, and its price?

فرض کن از اول ۱۰۰۰ تا shard ثابت داری، هر node مثلاً ۱۰۰ تاشو می‌گیره. node جدید اومد؟ فقط چندتا whole shard جابه‌جا می‌شن. یادت باشه بهاش: اگه تعداد shard کم حدس بزنی، بعداً resharding می‌ترکه تو صورتت.

مثال فنی: شارد منطقی ثابت

وضعیت اولیه: فرض کن ۱۰۲۴ تا bucket منطقی داری که بین چهار تا ماشین پخش شدن.

اجرای مرحله‌به‌مرحله: حالا با اضافه شدن ماشین پنجم، بخشی از bucketها منتقل می‌شن ولی تابع تعیین bucket عوض نمی‌شه — تابع سر جاشه، فقط خونه‌ها عوض می‌شن.

نتیجه و دلیل: پس جابه‌جایی محدودتر می‌شه؛ ولی تعداد و اندازهٔ bucketها و نقشهٔ مالکیت و hot key هنوز باید مدیریت بشن — کار تموم نشده.

E.g. 1000 shards are created up front and several reach each node; a key goes to shard hash(key) % 1000 and the shard→node map is kept separately. Cluster changes move only a few whole shards. Price: if the shard count comes out small (more nodes than shards), expensive resharding is required; and picking the “right” shard count is hard when data volume varies wildly.

۶. hash-range sharding چه تفاوتی با key-range دارد؟6. How does hash-range sharding differ from key-range?

یادت باشه فرقش ساده‌ست: key-range یعنی Ali و Sara اگه پشت سر هم باشن کنار همان. hash-range یعنی اول hashشون کن بعد بازه hash رو تیکه کن — بار پخش می‌شه ولی ترتیب اصلی می‌پره. نکته ماندگار: نظم رو می‌دی، پخشی رو می‌گیری.

مثال فنی: range روی hash، نه روی نام

وضعیت اولیه: فرض کن اسم‌های Ali و Sara اول hash می‌شن و بازه‌های hash می‌رسن به shardها.

اجرای مرحله‌به‌مرحله: حالا lookup هر اسم می‌ره به یه مقصد؛ ولی اسم‌های شروع‌شونده با Sa تو hash بغل هم نیستن — پخش و پلان.

نتیجه و دلیل: پس hash-range برای پخش بار مناسب‌تره، ولی نظم کلید اصلی و اسکن prefix رو نگه نمی‌داره — یه چیزی می‌دی، یه چیزی می‌گیری.

Instead of a key range, each shard gets a range of hash values; so nearby keys (consecutive timestamps) scatter and temporal hotspots vanish. Growth splits/merges like key-range. Price: range queries on the partition key itself go inefficient; the composite-key trick (partition in the first column) rescues in-shard range reads.

۷. consistent hashing چه دو ویژگی‌ای دارد و «consistent» به چه معناست؟7. Consistent hashing's two properties, and what does “consistent” mean?

تصور کن node جدید اومد و فقط همسایه‌هاش تکون خوردن — اینه consistent hashing. یادت باشه consistent اینجا ربطی به replica یا ACID نداره؛ یعنی «کلید سر جاش می‌مونه». توازن دقیق هم مجانی نیست، virtual node می‌خواد.

مثال فنی: دایرهٔ hash و مالک جدید

وضعیت اولیه: فرض کن توکن‌های A و B رو حلقه‌ان و هر کلید میره سراغ مالک بعدی.

اجرای مرحله‌به‌مرحله: با اضافه شدن C فقط بازه‌هایی که C مالکشون می‌شه جابه‌جا می‌شن؛ virtual nodeها هم می‌تونن تقسیم ظرفیت رو ریزتر کنن.

نتیجه و دلیل: یادت باشه consistent اینجا یعنی نگاشت سر جاش می‌مونه موقع تغییر اعضا؛ ربطی به consistency خوندن و نوشتن نداره.

1) Each shard holds roughly as many keys; 2) when the shard count changes, the fewest keys move. “Consistent” means a key's tendency to stay in its own shard — not replica consistency, not ACID. Its family members: rendezvous hashing and jump consistent hashing. Cassandra and ScyllaDB hold randomly bounded ranges with several ranges per node (16 and 256).

۸. rebalancing چیست و چهار روشِ رایجِ انجامش کدامند؟8. What is rebalancing, and four common ways to do it?

فرض کن cluster تکون خورد — باید rebalancing کنی. چهار مدل داری: whole shard رو جابه‌جا کن، بازه رو split/merge کن، با consistent hashing چند کلید پراکنده بده به تازه‌وارد، یا کلاً resharding کن. یادت باشه آخری خیلی گرونه!

مثال فنی: چهار راه rebalance

وضعیت اولیه: فرض کن کلیدها و سرورهای مقصد باید بین اعضا دوباره تقسیم بشن. اسباب‌کشی!

اجرای مرحله‌به‌مرحله: حالا می‌تونی shardهای ثابت رو منتقل کنی، بازه‌های بزرگ رو بشکنی، تعداد بخش‌ها رو متناسب با نودها نگه داری یا توکن‌های حلقه رو جابه‌جا کنی — چهار تا راه داری.

نتیجه و دلیل: پس هر طرح اندازهٔ واحد انتقال و میزان عوض شدن نقشهٔ کلاینت رو عوض می‌کنه؛ «خودکار» اسم الگوریتم تقسیم نیست — گول اسم رو نخور.

Respreading data when the cluster changes. Ways: moving whole shards between nodes (fixed shard count), splitting/merging ranges (key-range or hash-range), reassigning scattered keys to the fresh node (consistent hashing), and full resharding (changing the shard count — very expensive, sometimes needing write pauses).

۹. چرا rebalancing کاملاً خودکار می‌تواند خطرناک باشد؟9. Why can fully automatic rebalancing be dangerous?

یادت باشه move داده مجانی نیست — شبکه و دیسک می‌خوره. تصور کن یه node فقط کند شده، تو به‌غلط مرده حسابش کنی و 200GB روش خالی کنی — فشار رو فشار می‌ذاری و cascading failure می‌سازی. نکته ماندگار: کندی موقت همیشه rebalance نمی‌خواد!

مثال فنی: مهاجرت در وقت نامناسب

وضعیت اولیه: فرض کن یه node کند شده و کنترل‌گر هوس کرده همون موقع 200 GB داده‌ش رو جابه‌جا کنه.

اجرای مرحله‌به‌مرحله: این انتقال شبکه و دیسک رو می‌بلعه و کندی رو بدتر می‌کنه؛ اول علت کندی رو پیدا کن، بعد با محدودیت نرخ حرکت کن.

نتیجه و دلیل: یادت باشه کندی موقتی همیشه rebalance نمی‌خواد؛ حلقه خودکارِ بدون مهار فقط ازدحام رو بیشتر می‌ترکونه.

Rebalancing is expensive (rerouting requests and moving lots of data) and may swamp the network or nodes. The worst mix is automatic failure detection: a slow node is declared “dead”, the cluster moves load, and the extra pressure builds a cascading failure. Hence often “human in the loop” or preventive rebalancing (before heavy events) is advised.

۱۰. یک hotspot (کلیدِ داغ) را با چه راه‌هایی می‌توان خنثی کرد؟10. How can one neutralize a hotspot (hot key)?

تصور کن یه کلید celebrity ترکیده — hash هم نجاتش نمی‌ده چون باز همون یه shard می‌ره! سه راه داری: بندازش تو shard اختصاصی، با suffix تصادفی write رو بین ۱۰۰ کلید پخش کن، یا بده adaptive capacity ابری جمعش کنه. یادت باشه راه دوم فقط write رو پخش می‌کنه، read باید هر ۱۰۰ تا رو merge کنه.

مثال فنی: شکستن شمارندهٔ داغ

وضعیت اولیه: تصور کن شمارنده بازدید p9 گیر کرده رو یه کلید و همون شده گلوگاه؛ همه صف کشیدن پشتش!

اجرای مرحله‌به‌مرحله: فرض کن نوشتن‌ها رو می‌پاشی رو ۱۶ تا کلید p9:0…15؛ موقع خواندن باید هر ۱۶ تا رو جمع بزنی و جواب بدی.

نتیجه و دلیل: بار نوشتن پخش می‌شه، ولی خواندن گرون می‌شه و گرفتن یه snapshot مشترک سخت می‌شه. برای موجودی جدی، بی‌گدار به آب نزن و همین‌جوری از این الگو استفاده نکن.

In range-based schemes, put the hot key in a dedicated shard or even a dedicated machine. At application level, adding a random prefix/suffix (two digits → 100 keys) spreads writes but reads must merge them all — and only writes spread. You must also know which keys are hot and manage their lifecycle. Hot keys change over time, and “write-hot” differs from “read-hot”.

۱۱. request routing چیست و چه تفاوتی با service discovery دارد؟11. What is request routing, and how does it differ from service discovery?

فرض کن service discovery فقط می‌گه کدوم instance زنده‌ست — چون stateless هستن هرکدوم جواب میده. ولی request routing باید بگه مالک کلید 17 دقیقاً کدوم shardه! یادت باشه shard اشتباه یعنی داده اشتباه — نقشه key→shard→node رو باید داشته باشی.

مثال فنی: سه راه پیدا کردن shard

وضعیت اولیه: تصور کن نقشه می‌گه کلید 17 الان رو B نشسته.

اجرای مرحله‌به‌مرحله: کلاینتِ shard-aware یه‌راست می‌ره سراغ B؛ proxy مسیرش می‌ده؛ یا نودی که درخواست بهش خورده forwardش می‌کنه.

نتیجه و دلیل: هر راه یه جور تاوان می‌ده و نقشه یه جا نگه داشته می‌شه. یادت باشه service discovery فقط می‌گه کدوم instance زنده‌ست، نمی‌گه صاحب کلید کیه.

Finding a key's owning node. In service discovery, service instances are stateless and any answers; in sharding, only the owning shard's replica nodes can. So routing must know and track the key→shard and shard→node maps.

۱۲. سه روشِ مسیریابیِ درخواست را مقایسه کن.12. Compare three request-routing styles.

تصور کن سه مدل داری: هر node خودش forward کنه — ساده ولی یه hop اضافه. routing tier بذاری — مثل mongos، کار تمیز ولی یه قطعه اضافه. کلاینت shard-aware باشه — سریع‌ترین ولی کلاینت باید نقشه رو کش کنه و تازه نگه داره. نکته ماندگار: هر سه با map قدیمی می‌لنگن!

مثال فنی: سه راه پیدا کردن shard

وضعیت اولیه: تصور کن نقشه می‌گه کلید 17 الان رو B نشسته.

اجرای مرحله‌به‌مرحله: کلاینتِ shard-aware یه‌راست می‌ره سراغ B؛ proxy مسیرش می‌ده؛ یا نودی که درخواست بهش خورده forwardش می‌کنه.

نتیجه و دلیل: هر راه یه جور تاوان می‌ده و نقشه یه جا نگه داشته می‌شه. یادت باشه service discovery فقط می‌گه کدوم instance زنده‌ست، نمی‌گه صاحب کلید کیه.

1) Any node: a request reaches any node and, if not the owner, is forwarded with the answer returned — simple, no extra component. 2) Routing tier: a component that only routes (a shard-aware load balancer) — separated duties, but more components. 3) Shard-aware client: straight to the right node — fastest, but every client must know and refresh the map.

۱۳. نقشِ ZooKeeper/etcd در مسیریابی چیست و جایگزینِ Riak چه فرقی دارد؟13. What is ZooKeeper/etcd's routing role, and how does Riak's alternative differ?

یادت باشه ZooKeeper/etcd نقشه معتبر shard→node رو نگه می‌دارن و با consensus جلوی split brain رو می‌گیرن. ولی gossip مثل Riak؟ گره‌ها همین‌جوری بین خودشون پچ‌پچ می‌کنن — مدتی دیدشون قاطی می‌شه و split brain ممکنه. نکته ماندگار: ارزونی gossip به قیمت شلی consistency تموم می‌شه.

مثال فنی: مالکیت با epoch

وضعیت اولیه: فرض کن نقشهٔ قدیمی shard S رو با epoch ۷ رو A نشون می‌ده و نقشهٔ تازه با epoch ۸ رو B.

اجرای مرحله‌به‌مرحله: مقصد باید write مالکیت منقضی رو رد کنه یا forward کنه؛ نباید دو تا نقشه دو تا نویسندهٔ معتبر بسازن.

نتیجه و دلیل: سرویس هماهنگی نقشه رو هماهنگ می‌کنه، ولی یادت باشه fencing تو مسیر داده هم لازمه.

These services keep the authoritative shard→node map, nodes register themselves, and every ownership change notifies subscribers; their consensus shields against split brain. Riak instead gossips between nodes: weaker consistency and possible split brain — acceptable for a leaderless database since it promises weaker guarantees anyway.

۱۴. هنگامِ جابه‌جاییِ shard، «پنجرهٔ cutover» چه مشکلی دارد؟14. When moving a shard, what's wrong with the “cutover window”?

تصور کن shard از A داره می‌ره B — وسط راه snapshot تا 500 رفته ولی writeها تا 560 اومدن! یادت باشه Cutover همون لحظه سوییچه: B باید catch-up کرده باشه، request در پرواز باید forward یا reject بشه، وگرنه write گم می‌شه یا دو طرف می‌نویسن و قاطی می‌شه.

مثال فنی: Cutover بدون گم‌شدنِ نوشتن

وضعیت اولیه: تصور کن shard داره از A می‌ره به B؛ snapshot تا موقعیت 500 کپی شده.

اجرای مرحله‌به‌مرحله: تغییرهای بعدی تا 560 می‌رسن؛ با سازوکار پروتکل، نوشتن نهایی همگام می‌شه و مالکیت می‌ره به epoch تازه.

نتیجه و دلیل: اگه نقشه زودتر از رسیدن تغییرها عوض بشه، B دادهٔ قدیمی نشون می‌ده؛ اگه دو طرف بنویسن، تعارض می‌ترکه.

Data transfer takes time, and during transfer the old map must serve. When the fresh owner takes over, requests still fly to the old owner; they must be forwarded or rejected so clients get a definite answer. Mismanaging that window builds cryptic “lost write” errors.

۱۵. چرا ایندکسِ ثانویه در دادهٔ شاردشده به طراحیِ جدا نیاز دارد؟15. Why is a secondary index incompatible with sharding?

فرض کن با product_id shard کردی ولی کاربر color=red می‌خواد — این شرط هیچ shard رو لو نمی‌ده! یادت باشه secondary index مشکلش همینه: جوابش ممکنه تو همه shardها پخش باشه، پس باید local یا global رو از اول طراحی کنی.

مثال فنی: query با کلیدِ متفاوت

وضعیت اولیه: فرض کن کالاها بر product_id تقسیم شدن، ولی کاربر color=red می‌خواد. کلیدها با هم نمی‌خونن!

اجرای مرحله‌به‌مرحله: حالا این شرط shard کالا رو معلوم نمی‌کنه؛ یا هر shard ایندکس محلی خودش رو می‌خونه یا ایندکس جهانی مقصدها رو معرفی می‌کنه — دو راه داری.

نتیجه و دلیل: پس ایندکس ثانویه طرح جدا می‌خواد، چون کلید جست‌وجو با کلید تقسیم یکی نیست — یادت باشه.

Because it doesn't identify via the partition key, and matching records may scatter across all shards. The “value→shard” map isn't as simple as the primary key; hence two fix families: local (document-partitioned) and global (term-partitioned).

۱۶. local secondary index چگونه کار می‌کند و چه بهایی دارد؟16. How does a local secondary index work, and its price?

تصور کن local index یعنی هر shard ایندکس خودشو داره؛ write فقط یه shard رو لمس می‌کنه، ارزون! ولی query قرمز؟ باید به A و B هر دو سر بزنی و merge کنی — scatter-gather می‌ترکه و tail latency بالا می‌ره. نکته ماندگار: نوشتن ارزون، خواندن گرون.

مثال فنی: محلی یا جهانی برای رنگ

وضعیت اولیه: فرض کن کالای P7 رو A قرمزه و کالای P9 رو B قرمزه.

اجرای مرحله‌به‌مرحله: حالا ایندکس محلی برای query قرمز نیاز به خوندن A و B داره؛ ایندکس جهانی قرمز هر دو شناسه رو بغل هم نگه می‌داره.

نتیجه و دلیل: پس جهانی خوندن رو متمرکزتر می‌کنه، ولی تغییر رنگ یا حذف کالا باید ایندکس احتمالاً دوردست رو هم اصلاح کنه — راحتی حالا، خرج بعداً.

Each shard indexes only its own records; writes engage just one shard. Keyless reads must go to all shards with merging answers (scatter-gather), amplifying tail latency; with more shards, query throughput doesn't grow. MongoDB, Cassandra, Elasticsearch and VoltDB all use this.

۱۷. global secondary index چگونه کار می‌کند و چه بهایی دارد؟17. How does a global secondary index work, and its price?

فرض کن global index خودش بر اساس term shard شده — قرمزها همه کنار همان. postings list رو از یه shard می‌خونی، تمیز! ولی یه write ممکنه چند index shard رو درگیر کنه و distributed transaction بخواد. یادت باشه DynamoDB حتی async آپدیت می‌کنه — ممکنه کهنه بخونی.

مثال فنی: محلی یا جهانی برای رنگ

وضعیت اولیه: فرض کن کالای P7 رو A قرمزه و کالای P9 رو B قرمزه.

اجرای مرحله‌به‌مرحله: حالا ایندکس محلی برای query قرمز نیاز به خوندن A و B داره؛ ایندکس جهانی قرمز هر دو شناسه رو بغل هم نگه می‌داره.

نتیجه و دلیل: پس جهانی خوندن رو متمرکزتر می‌کنه، ولی تغییر رنگ یا حذف کالا باید ایندکس احتمالاً دوردست رو هم اصلاح کنه — راحتی حالا، خرج بعداً.

The index is global and sharded separately by term; reading one condition's postings list wants just one shard. Price: fetching records still spans shards; a multi-term AND means intersecting long lists over the network; and writing one record may update several index shards (needing multi-object transactions). DynamoDB updates that index asynchronously, so reading it may be stale.

۱۸. چرا پیاده‌سازیِ دستیِ ایندکسِ ثانویه در کدِ برنامه خطرناک است؟18. Why is hand-rolling a secondary index in application code dangerous?

تصور کن رنگ P7 رو آبی کردی ولی قبل از آپدیت ایندکس crash کردی — سرچ هنوز قرمز نشونت میده، قاطی شد! یادت باشه دو تا write مستقل atomic نیستن؛ بدون multi-object transaction ایندکس دستی تو کد زود می‌ترکه.

مثال فنی: یک تغییر، ایندکس جا‌مانده

وضعیت اولیه: فرض کن برنامه رنگ P7 رو تو مرجع از قرمز به آبی تغییر می‌ده و قبل نوشتن ایندکس crash می‌کنه. بدشانسی!

اجرای مرحله‌به‌مرحله: حالا جست‌وجو هنوز P7 رو قرمز می‌دونه؛ log تغییر یا تراکنش مناسب باید راه همگام‌سازی و ترمیم رو بده.

نتیجه و دلیل: پس دو تا نوشتن مستقل تو کد برنامه atomicity یا ترتیب یکسان ایندکس و مرجع رو تضمین نمی‌کنن — دو تا قول جدا، هیچ تضمینی.

Because the index (the value-to-ID map) must always stay consistent with the primary data; race conditions and partial writes (part stored, part not) easily corrupt it. Without multi-object transactions (Chapter 8) consistency can't be guaranteed.

۱۹. چرا «هر tenant یک shard» در چندمستاجری جذاب است و چه محدودیتی دارد؟19. Why is “one shard per tenant” attractive in multitenancy, and its limits?

فرض کن هر tenant یه shard خودشو داره — بکاپ و restore و GDPR و data residence تمیز می‌شه، tenant غول هم بقیه رو اذیت نمی‌کنه. ولی یادت باشه tenantها هم‌قد نیستن! یه غول ۶۰٪ بار بسازه کل معادله می‌ترکه و باید خودشو هم shard کنی.

مثال فنی: یک tenant، یک محل

وضعیت اولیه: تصور کن مشتری سازمانی tenant_id=17 افتاده رو shard A.

اجرای مرحله‌به‌مرحله: بیشتر queryهای همین tenant محلی‌ان و سر جاشون جواب می‌گیرن؛ ولی اگه یه tenant به‌تنهایی ۶۰٪ بار بسازه، باید جابه‌جاش کنی یا دیتاش رو بشکنی.

نتیجه و دلیل: می‌بینی؟ tenant کلید طبیعی جداسازیه، ولی اندازه و بار tenantها مساوی نیست؛ «یه tenant یه shard» همیشه متعادل نمی‌مونه. اینو یادت نره.

Separate resources and access, cell-based fault isolation, separate backup/recovery, GDPR/CCPA compatibility (simple export and delete), data residence, and gradual schema rollout. Limits: each tenant must fit on one machine (a giant tenant must shard inside itself), many small tenants carry overhead, and cross-tenant features get hard.

وضعیت اولیه: فرض کن فایل‌های فروش بر روز partition شدن و تو هر روز بر customer_id مرتب یا خوشه‌بندی شدن.

اجرای مرحله‌به‌مرحله: حالا فیلتر روز فقط partition مربوط رو می‌خونه؛ فیلتر مشتری تو همون روز می‌تونه بلوک‌های بیشتری رو رد کنه.

نتیجه و دلیل: پس partition حجم درشت خوندن و clustering حذف بلوک‌های داخلش رو هدف می‌گیرن؛ اثر دقیقش بستگی به موتور داره — موتور رو بشناس.

The partition key (like BigQuery's) decides which partition a record lands in, and cluster columns order inside the partition; Snowflake uses automatic micro-partitions with a cluster key, Delta Lake has both. Result: faster range scans, and sometimes better compression and filtering.

۶.۳6.3 اشتباهات رایج در جواب‌های مصاحبهCommon interview mistakes

  • فرض کن sharding رو با network partition قاطی کردی — فقط اسمشون شبیه! یکیش تیکه داده‌ست، اون‌یکی قطعی شبکه‌ست که تو فصل ۹ می‌ترکه.
  • یادت باشه بگی «تیکه کردیم» کافی نیست! نکته ماندگار: هدف پخش داده و بارـه، نه فقط تیکه کردن — وگرنه hotspot همه رو می‌خوابونه.
  • تصور کن 20GB داده داری و هی sharding می‌کنی — فقط routing و join رو قاطی کردی! اگه یه ماشین جواب میده، نکن.
  • یادت باشه hash(key) % N تله‌ست! N از ۳ شد ۴، بیشتر کلیدها می‌پرن — تو مصاحبه اینو بگی می‌ترکی.
  • فرض کن کلیدت فقط timestampه — همه writeهای «این ماه» می‌ریزن رو یه shard و می‌ترکه. پیشوند sensor_id یادت نره!
  • تصور کن سلبریتی پست گذاشته — hash هم باشه باز همه requestها می‌رن همون یه shard! hash کلید پخش می‌کنه، نه بار داغ رو.
  • یادت باشه suffix تصادفی فقط write رو بین ۱۰۰ کلید پخش می‌کنه! read باید هر ۱۰۰ تا رو بخونه و merge کنه — این بهاشو بگو وگرنه نصفه گفتی.
  • فرض کن consistent hashing رو با consistency قاطی کنی — رفتی! اینجا consistent یعنی «کلید سر جاش می‌مونه»، نه ACID و نه replica.
  • یادت باشه split مجانی نیست — کل داده باید بازنویسی بشه، دقیقاً همون shard داغی که زیر فشاره بیشتر له می‌شه!
  • تصور کن node کند رو مرده حساب کنی و auto-rebalance راه بیفته — فشار رو فشار می‌ذاری و cascading failure می‌سازی. نکته ماندگار: انسان تو حلقه امن‌تره!
  • اگه فقط بگی «load balancer می‌ذاریم» باختی! یادت باشه سه سؤال سخت: کی تصمیم می‌گیره؟ کی باخبر می‌شه؟ request در پرواز تو cutover چی می‌شه؟
  • یادت باشه secondary index خودش هم shard می‌خواد! local یعنی scatter به همه shardها و tail latency می‌ترکه بالا.
  • تصور کن فکر کنی global index همه‌چی مجانیه — نه! postings از یه shard میاد ولی fetch رکوردها و AND چند term هنوز گرونه و distributed transaction می‌خواد.
  • ایندکس دستی تو کد بدون multi-object transaction؟ crash وسط دو write قاطی می‌کنه — ایندکس از داده جدا می‌افته!
  • یادت باشه shard یعنی ماشین نیست! یه واحد منطقیه — می‌تونه چند تاش رو یه ماشین باشه، حتی چند پروسه رو یه CPU مثل Redis.
  • Conflating sharding with network partitions — only their names match.
  • Saying “sharding means splitting data” and forgetting the real goal: evenly spreading data and load and avoiding hotspots.
  • Recommending sharding for any system; if one machine suffices, sharding is just extra complexity.
  • Recommending hash(key) % N as the fix — blind to most keys moving when N changes.
  • Forgetting that in key-range sharding, a bare timestamp key heats “this month's” shard.
  • Saying “hashing evens everything” while missing that one hot (celebrity) key's load still stays on one shard.
  • Saying “a random prefix fixes hotspots” without explaining that only writes spread while reads must merge 100 keys.
  • Conflating “consistent hashing” with consistency; here consistent means “a key stays in its place”.
  • Forgetting split cost: rewriting all data, exactly on the shard under pressure.
  • In rebalancing, missing the dangerous “automatic + automatic failure detection” mix and cascading-failure risk.
  • In routing, only saying “we use a load balancer” and missing the three hard questions: who decides, who learns of changes, and cutover in-flight requests.
  • Forgetting that a secondary index must itself be sharded, and that scatter-gather amplifies tail latency.
  • Saying “a global index makes reads free”; the postings list is one shard but fetching records and multi-term intersection stay expensive.
  • Recommending hand-rolled indexes in application code with no multi-object transaction (index-data inconsistency risk).
  • Saying “a shard is one machine”; a shard is a logical data unit and several shards can sit on one machine (even several processes on one CPU).

۶.۴ چک‌لیست مرور ۵ دقیقه‌ای قبل از مصاحبه6.4 Five-minute checklist before the interview

  1. فرض کن ۳۰ ثانیه وقت داری: shard چیه و با replication و network partition چه فرقی داره؟ یه جمله بگو و گیر نکن!
  2. یادت باشه دو خانواده رو با یه مزیت و یه بهاشون بگو: key-range — scan خوب ولی hotspot زمانی؛ hash — پخش خوب ولی ترتیب می‌پره.
  3. تصور کن N از ۳ شد ۴ — چرا hash % N می‌ترکه؟ با عدد بگو و سه جایگزینش رو نام ببر: fixed shards و hash-range و consistent hashing.
  4. چهار مدل rebalancing رو بشمر و بگو چرا auto + auto failure detection مساوی cascading failure ـه!
  5. hotspot چیه؟ سه درمانش رو با بهاش بگو: shard اختصاصی، suffix تصادفی — فقط write پخش می‌شه! — و heat management ابری.
  6. سه مدل routing — forward، routing tier، کلاینت shard-aware — رو مقایسه کن و سه سؤال سختش رو جواب بده: کی تصمیم می‌گیره؟ کی باخبر می‌شه؟ in-flight چی می‌شه؟
  7. یادت باشه local در برابر global: write و read هرکدوم از کجا می‌ره و کجاش گرونه؟ postings list از یه shard یا scatter به همه؟
  8. یه جمله بگو چرا shard per tenant وسوسه‌ست — ایزولیشن و بکاپ تمیز — ولی tenant غول معادله رو به‌هم می‌زنه!
  1. Define shard and its difference from replication and network partitions — in one sentence.
  2. Two main families (key-range vs hash) + one advantage and one price each.
  3. Define the mod-N trap with a numeric example (3 → 4 nodes) and name its three alternatives.
  4. Four rebalancing styles and the danger of mixing automatic rebalancing with automatic failure detection.
  5. Define hotspot and its three fixes (dedicated shard, random prefix, heat management) + each one's price.
  6. Three request-routing styles and the three hard questions (coordinator, change notification, cutover).
  7. Local vs global secondary index: each one's write and read paths + each one's price.
  8. One sentence on multitenancy and why “one shard per tenant” is both attractive and limited.

صورت تمرین (حل‌نشده — اول خودت تلاش کن)Problem brief (unsolved — try it first)

تصور کن سال ۲۰۲۳ است: یک primary تنها زیر حدود ۱۰۰ برابر رشد دیتابیس از ۲۰۲۰ دارد له می‌شود و downtime هم ممنوع است. گزارش تیم Figma نقشهٔ راه را داده: اول sharding منطقی پشت viewهای Postgres (مسیریابی hash با DBProxy)، بعد — وقتی viewها تأیید شدند — کپی کامل فیزیکی روی چند هاست، بعد gate و cutover. تو طراح این مهاجرت زنده‌ای: ترتیب فازها را بچین، شرط عبور هر gate را مشخص کن، و برای هر فاز یک مسیر برگشت (rollback) نام ببر که در چند ثانیه جواب بدهد.Picture 2023: a single lonely primary is groaning under roughly 100x database growth since 2020, and downtime is off the table.
