Avro: قواعد schema resolution

ایدهٔ کلیدی فصلChapter thesis

تصور کن داده می‌خواد از حافظهٔ برنامه بزنه بیرون — بره روی دیسک یا توی شبکه. باید بشه بایت. نگران نشو، دعوای این فصل سر «چطور بایت کنیم» نیست؛ سر اینه: وقتی قالب عوض شد، نسخهٔ قدیمی و جدید چطور هنوز همدیگه رو بفهمن؟ یادت باشه قالب عوض می‌شه، داده می‌مونه.

مثال فنی: رکورد قدیمی زیر کد جدید

وضعیت اولیه: فرض کن نسخهٔ ۱ فقط رکورد {name: "Sara"} رو نوشته، بعد نسخهٔ ۲ اومده یه فیلد email هم اضافه کرده.

اجرای مرحله‌به‌مرحله: حالا خوانندهٔ جدید باید بلد باشه رکورد قدیمیِ بدون email رو بخوره؛ خوانندهٔ قدیمی هم نباید با دیدن فیلد جدید قاطی کنه، فقط تحملش کنه.

نتیجه و دلیل: یادت باشه تست واقعی هر دو جهت رو می‌خواد؛ اینکه کد جدید با خودش حرف بزنه که هنر نیست.

یادت باشه مثال‌های این فصل همشون تمرینی‌ان، از دل کار روزمره. عددها رو جدی نگیر، فقط برای فهم‌اند؛ مال هیچ شرکت خاصی نیستن. نکتهٔ ماندگار: مثال را بخوان، قرارداد را یاد بگیر.

An object in memory needs a byte representation before another process can read it from a file or receive it over the network. A new version of the same program may need to read those bytes years later.

This chapter asks what happens when that representation changes. Who writes it? Who reads it? Which older records and newer fields must they understand?

The examples are teaching scenarios drawn from everyday engineering work. Their numbers illustrate the ideas; they don't describe a particular company's architecture.

Example: Old records under new code

Setup: Version 1 wrote only {name: "Sara"}. Version 2 adds email.

Walk through it: The new reader handles an old record without email. The old reader must also handle a new record with the added field according to the contract.

What this tells you: Test both mixed-version directions. A new version successfully reading its own output doesn't test compatibility.

یادت باشه deploy تو سیستم بزرگ یهویی نیست؛ تدریجی است (rolling upgrade)، تیکه‌تیکه میاد بالا. کلاینت‌ها رو هم نمی‌تونی مجبور کنی آپدیت کنن. پس تصور کن نسخهٔ قدیمی و جدیدِ کد هم‌زمان دارن کار می‌کنن، دادهٔ قدیمی و جدید هم قاطیِ همن. پس هر قالب باید هم backward باشه (کد جدید، دادهٔ قدیمی رو ببلعه) و هم forward (کد قدیمی با دیدن دادهٔ جدید نترکه). نکتهٔ ماندگار: وسط آپدیت همه‌چیز قاطیه، قالب باید هر دو طرف را نگه دارد.

A rolling upgrade changes servers gradually. Clients may take much longer to update. For a while, old and new code run together, reading both old and new data.

Backward compatibility lets new code read old data. Forward compatibility lets old code read new data according to the contract. If that old code rewrites the record, it must also avoid losing information it doesn't understand.

یادت باشه این فصل دو تیکهٔ مشخص داره:

We'll connect two parts of the problem:

  • نیمهٔ اول — قالب‌های کدگذاری: تصور کن از قالب مخصوص خود زبون شروع می‌کنی (مثل java.io.Serializable)، می‌رسی به JSON/XML/CSV، بعد می‌رسی به باینری‌های schemaدار مثل Protocol Buffers و Avro. یادت باشه هر کدوم قلق تکامل (schema evolution) خودشون رو دارن. نکتهٔ ماندگار: اسم قالب عوض بشه، قواعد بازی هم عوض می‌شه.
  • نیمهٔ دوم — حالت‌های جریان داده (modes of dataflow): داده بین processها چطور می‌چرخه؟ با پایگاه داده (نوشتن یعنی پیام دادن به خود آینده‌ات)، با سرویس‌ها (REST/RPC)، با workflow engine‌ها (اجرای پایدار)، یا با message broker و actorها (معماری event-driven). نگران نشو، هر مسیر ترکیب خودش از backward/forward رو می‌خواد. نکتهٔ ماندگار: مسیر عوض بشه، مدل سازگاری هم عوض می‌شه.
  • Encoding formats: compare language-native formats such as java.io.Serializable, textual JSON/XML/CSV, and schema-driven binary formats such as Protocol Buffers and Avro. Each gives you different rules for schema evolution.
  • Dataflow modes: follow data through a database, services using REST/RPC, workflow engines with durable execution, and message brokers or actors. The writers, readers and timing determine which compatibility directions matter.
نکتهٔ مصاحبهInterview tip
یادت باشه جملهٔ طلایی این فصل اینه: «data outlives code» — کد تو چند دقیقه deploy می‌شه و میره، ولی دادهٔ پنج‌ساله هنوز با همون فرمت روز اول رو دیسکه. پس هر انتخاب قالب یه تعهد بلندمدته، خیلی بلندتر از عمر هر نسخهٔ کد. نکتهٔ ماندگار: کد میره، داده می‌مونه.

Data outlives code. A deployment can take minutes while a five-year-old record remains in its original format. Choosing a format means making a contract with readers that may not exist yet.

۱1encode و decodeEncoding and decoding

تصور کن encoding یعنی دادهٔ توی برنامه رو بکنی بایت که بشه ذخیره یا ارسالش کرد. decode هم همون بایت‌ها رو برمی‌گردونه به دادهٔ به‌دردبخور. یادت باشه این ربطی به رمزنگاری امنیتی نداره؛ قاطیشون نکن. نکتهٔ ماندگار: encode می‌بره، decode برمی‌گردونه.

مثال فنی: شیء با بایت فرق دارد

وضعیت اولیه: تصور کن برنامه‌ات یه شیء تو حافظه داره با user_id=17 و name=Sara.

اجرای مرحله‌به‌مرحله: حالا encoder می‌بردش سمت بایت‌ها، decoder هم با همون قواعد قالب برش می‌گردونه سر جاش.

نتیجه و دلیل: نگران نشو، pointer و کلاسِ زبون خودش قرارداد نیست؛ یادت باشه قالب باید بگه هر فیلد یعنی چی.

Encoding turns application data into bytes for storage or transfer. Decoding interprets those bytes as useful data again. This isn't encryption; changing the representation doesn't make the contents secret. Compare the two representations:

Example: An object and its bytes

Setup: An in-memory object has user_id=17 and name=Sara.

Walk through it: The encoder writes a byte representation. A decoder uses the format's rules to reconstruct the values.

What this tells you: A pointer or language class isn't a shared exchange contract. The format must establish how the reader identifies and interprets fields.

  • درون حافظه: تصور کن object، struct، لیست، آرایه، hash table، درخت — چیزایی که برای سرعت CPU (معمولاً با pointer) ردیفن.
  • روی دیسک / شبکه: باید دنباله‌ای خوداتکا از بایت‌ها باشه (مثل یه سند JSON)؛ چون pointer برای process دیگه هیچ معنایی نداره. نکتهٔ ماندگار: pointer از درِ process بیرون نمی‌ره.
  • In memory: objects, structs, lists, arrays, hash tables and trees are arranged for CPU access, often through pointers.
  • On disk or the network: use a self-contained sequence of bytes, such as a JSON document. Another process can't use a pointer into the sender's memory.
تصور کن از حافظه به بایت رفتن می‌شه encoding (اسم‌های دیگه‌ش: serialization یا marshaling). برگشتنش می‌شه decoding (parsing، deserialization یا unmarshaling). یادت باشه فقط اسم‌ها قلمبه‌ان، کار یکیه. نکتهٔ ماندگار: رفت می‌شه encode، برگشت می‌شه decode.

Turning memory structures into bytes is encoding, also called serialization or marshaling. The reverse is decoding, also called parsing, deserialization or unmarshaling. The names differ; the direction tells you the job.

دامِ اصطلاحTerminology trap
یادت باشه واژهٔ serialization تو بحث تراکنش‌ها (فصل ۸) یه معنای کاملاً متفاوت داره (ترتیب‌پذیری اجرا). کتاب برای اینکه قاطی نکنی، همه‌جا می‌گه encoding. نکتهٔ ماندگار: یه کلمه، دو دنیا؛ تو این فصل فقط encoding بگو.

In transaction discussions, serialization has a different meaning: whether execution can be understood as a serial order, covered in Chapter 8. The book uses encoding here to keep the two subjects separate.

  • تصور کن گاهی encode/decode اصلاً لازم نیست: مثلاً موتوری که مستقیم روی دادهٔ فشردهٔ خونده‌شده از دیسک کار می‌کنه (بخش Query Execution در فصل ۴)، یا قالب‌های zero-copy مثل Cap'n Proto و FlatBuffers که همون بایت‌ها هم نمای اجراان هم نمای ذخیره، دیگه تبدیلی تو کار نیست.
  • ولی نگران نشو، اکثر سیستم‌ها این تبدیل بین آبجکت توی حافظه و رشتهٔ بایت رو می‌خوان — و انتخاب قالب فقط بحث اندازه و سرعت نیست؛ بحثِ تکامل‌پذیری است. نکتهٔ ماندگار: قالب خوب قالبیه که با تغییر نمی‌ترکه.
  • Some systems work directly on their stored representation. Chapter 4 showed operators using compressed data. Zero-copy formats such as Cap’n Proto and FlatBuffers let programs access the encoded layout without rebuilding a separate object representation.
  • Most systems still convert between objects and bytes. Compare evolvability as well as size and speed: can the next version still read what this one writes?

۲2سازگاری و ارتقای تدریجیCompatibility and gradual upgrades

تصور کن وسط rolling upgrade هستی: کد قدیم و جدید هم‌زمان دارن کار می‌کنن. یادت باشه backward یعنی کد جدید بتونه دادهٔ قدیم رو بخونه. forward یعنی کد قدیم بتونه با دادهٔ جدید طبق قرارداد کنار بیاد.

مثال فنی: چهار ترکیب در rolling upgrade

وضعیت اولیه: تصور کن نصف سرورها هنوز نسخهٔ ۱‌ان، نصف دیگه رفتن روی نسخهٔ ۲.

اجرای مرحله‌به‌مرحله: اول نسخهٔ ۲ رکورد قدیمی رو می‌خونه و حالشو می‌بره؛ بعد نوبت نسخهٔ ۱ـه که یه رکورد دست‌نویس نسخهٔ ۲ دستش می‌رسه.

نتیجه و دلیل: تهش اینه: backward یعنی جدید قدیمی رو بخونه، forward یعنی قدیمی جدید رو نگه داره. rolling upgrade هر دو رو هم‌زمان می‌خواد، قاطی نکن.

Adding a feature can add a field, introduce a record type or change an existing representation. You can't assume that every running process changes at the same instant:

Example: Four combinations during a rolling upgrade

Setup: Half the servers run version 1 and half run version 2.

Walk through it: Version 2 reads a record from version 1. Version 1 then receives a record produced by version 2. Include both same-version paths in the test matrix too.

What this tells you: Backward means the new reader handles old data. Forward means the old reader handles new data, retaining required information if it rewrites it. Mixed versions need both checks.

  • در سمت سرور: با rolling upgrade (یا staged rollout) میری جلو. نسخهٔ جدید رو nodeبه‌node deploy می‌کنی، پایش می‌کنی، بعد میری سراغ بعدی. downtime نداری؛ با ریلیزهای کوچیک و پشت‌سرهم.
  • در سمت کلاینت: کاربر حال نداره اپ رو آپدیت کنه؛ ماه‌ها با نسخهٔ قدیمی می‌مونه. این تیکه دیگه دست تو نیست.
  • Servers: rolling upgrades, or staged rollouts, deploy to nodes in steps. Monitor each stage before proceeding. Compatible versions can keep serving requests during that transition.
  • Clients: users may keep an old app for months. The server team doesn't control every client's update time.
پس چاره‌ای نیست: کد قدیم و جدید و دادهٔ قدیم و جدید باید یه مدت کنار هم زندگی کنن:

تصور کن کلاینت قدیمی داره سرویس جدید رو صدا می‌زنه: روی request سازگاری backward می‌خوای، روی response سازگاری forward. اگه کلاینت جدید با سرویس قدیمی حرف بزنه، برعکس. یادت باشه backward معمولاً راحته چون فرمت قدیم رو می‌شناسی؛ forward سخت‌تره چون کد قدیم باید چیز ناشناخته رو بی‌صدا رد کنه ولی نگهش داره.

An old client calling a new service writes an old request that new code reads: backward compatibility. The service writes a new response that old code reads: forward compatibility.

Reverse the versions and you reverse the directions. Ask who wrote the bytes and who's reading them. For a read-modify-write path, also test whether unknown fields survive the rewrite.

۲.۱ نمودار ۱ + روایت مدرس2.1 Diagram 1 — rolling upgrades and unknown-field loss

۳.۲ قالب‌های ویژهٔ زبان3.2 Language-native formats

قالب‌های مخصوص زبان کارت رو راحت می‌کنن: شیء همون زبان رو تند ذخیره می‌کنی. ولی وقتی پای زبون دیگه یا نسخهٔ جدید وسط باشه، قاطی می‌کنی. تازه بعضی‌هاشون برای ورودی مشکوک خطرناکن.

مثال فنی: نام کلاس، قرارداد پایدار نیست

وضعیت اولیه: فرض کن فایل ذخیره‌شده‌ات به کلاس OldUser نسخهٔ قبلی چسبیده.

اجرای مرحله‌به‌مرحله: حالا نسخهٔ جدید اون کلاس رو پاک کرده یا زبون عوض شده؛ decoder مخصوص اون زبون ممکنه اصلاً نتونه شیء رو بسازه و بترکه.

نتیجه و دلیل: یادت باشه داده از کد بیشتر عمر می‌کنه؛ برای تبادل schema مستقل می‌خوای و ورودی مطمئن.

  • تقریباً همهٔ زبان‌ها کدگذاری داخلی دارن: java.io.Serializable تو Java، pickle تو Python، Marshal تو Ruby و چیزایی مثل Kryo. خوبیشون؟ با دو خط کد object رو ذخیره و برمی‌گردونی.
  • ولی چهار تا مشکل اساسی دارن:
  • قفل زبانی: به یه زبان چسبیدی؛ خوندن داده با زبون دیگه سخته و وصل شدن به سازمان دیگه عملاً نمی‌شه.
  • امنیت: decoder برای ساختن object باید هر classای رو instantiate کنه — مهاجم بایت دلخواه بفرسته، کارت ساخته‌ست: می‌رسه به اجرای کد دلخواه (RCE).
  • نسخه‌بندی فرعی: اینا برای «سریع و راحت» ساخته شدن؛ سازگاری forward/backward براشون مهم نیست.
  • کارایی فرعی: serialization داخلی Java معروفه به کندی و بادکردگی.
  • حرف آخر: جز برای کار خیلی موقتی، سراغ کدگذاری داخلی زبان نرو.
  • Language-native tools include Java's java.io.Serializable, Python's pickle, Ruby's Marshal and libraries such as Kryo. They make storing and rebuilding language objects convenient.
  • Before using that convenience as a lasting data contract, check four costs:
  • Language lock-in: readers depend on the language and often its classes. Cross-language or cross-organization exchange becomes difficult.
  • Security: rebuilding objects from untrusted bytes can instantiate unexpected classes and enable remote code execution (RCE).
  • Versioning: convenience doesn't establish backward or forward compatibility when classes change.
  • Performance: Java's built-in serialization is the chapter's example of a verbose, slow representation.
  • Keep language-internal formats for tightly controlled, transient uses. They aren't the chapter's choice for long-lived exchange or untrusted input.

۳.۳ JSON، XML، CSV و JSON Schema3.3 JSON, XML, CSV and JSON Schema

JSON و XML اسم فیلد رو با خودشون دارن؛ CSV فقط به درد جدول ساده می‌خوره و ریزه‌کاری‌هاش رو باید با هم توافق کنی. JSON Schema هم می‌تونه بگه type فیلد چیه و اجباریه یا نه.

مثال فنی: شناسهٔ بزرگ در JSON

وضعیت اولیه: فرض کن شناسهٔ 9007199254740993 به‌صورت JSON number می‌رسه دست JavaScript.

اجرای مرحله‌به‌مرحله: نگران نشو اگه دیدی تبدیلش به Number گرد شد به 9007199254740992؛ اگه شناسه رو رشته‌ای قرارداد کنی رقم‌هاش سر جاش می‌مونه.

نتیجه و دلیل: یادت باشه JSON قول دقت به همه نمی‌ده؛ نوع فیلد رو دو طرف شفاف قرارداد کن.

JSON, XML and CSV work across languages and are readable as text. CSV represents tables rather than nested objects. These formats still need agreement about types, escaping and how readers handle change:

  • XML معمولاً حرفش اینه: طولانی و زیادی پیچیده‌ست.
  • ابهام عددها: تو XML و CSV اصلاً نمی‌فهمی این «123» عدده یا رشته (مگر با schema بیرونی). JSON رشته و عدد رو جدا می‌کنه ولی integer و floating-point رو نه، دقت هم معلوم نیست. عدد بزرگ‌تر از 2^53 تو IEEE 754 دقیق نمی‌مونه؛ مثلاً X شناسهٔ ۶۴بیتی هر post رو هم عدد JSON میده هم رشتهٔ متنی، که JavaScript قاطی نکنه.
  • رشتهٔ باینری ندارن: JSON/XML فقط Unicode (متن انسان‌خوان) می‌فهمن، نه بایت خام. راه رایج Base64 ـه که کار رو راه می‌ندازه ولی حجم رو حدود یک‌سوم باد می‌کنه.
  • XML Schema و JSON Schema قوی‌ان و برای همین پیچیده‌ان؛ اگه ازشون استفاده نکنی باید منطق encode/decode رو hardcode کنی.
  • CSV اصلاً schema نداره؛ معنی هر سطر و ستون با خودته و escape کردن ویرگول و خط جدید هم گنگه.
  • با همهٔ این‌ها، برای تبادل بین سازمان‌ها همینا «به‌اندازهٔ کافی خوب»‌ن: تا وقتی دو طرف روی قالب توافق دارن، خوشگلی و سرعت حرف دومه.
  • XML can be verbose and complex.
  • Numbers: XML and CSV text needs an external contract to distinguish a number from a numeric string. JSON distinguishes strings and numbers but doesn't settle every reader's numeric representation. IEEE 754 doubles can't represent every integer beyond 2^53. The book's X example carries each 64-bit post ID both as a JSON number and a string so JavaScript readers can use the exact digits.
  • Binary data: JSON/XML text doesn't directly carry arbitrary bytes. Base64 represents them as text, adding about one-third to the payload size.
  • XML Schema and JSON Schema express detailed validation rules, which adds complexity. Without them, application code still has to define and check its expectations.
  • CSV doesn't embed a schema. Agree on column meanings and the rules for commas, quotes and newlines.
  • For cross-organization exchange, a clearly agreed format can matter more than compactness. Readable text remains useful when both sides follow the contract.

JSON Schema also supports conditions such as if/else, named definitions and references to remote schemas. More expressive validation gives you more rules to check during evolution. XML Schema needs the same care: a field added by a writer can still violate an old reader's constraints.

چیزایی مثل MessagePack، CBOR و BSON همون مدل JSON رو باینری می‌کنن (گاهی با چند type اضافه مثل رشتهٔ باینری). ولی چون schema ندارن، هنوز اسم همهٔ فیلدها تو بایت‌هاست. مثال کتاب: رکورد سه‌فیلدی {"userName": "Martin", "favoriteNumber": 1337, "interests": [...]} با MessagePack میشه ۶۶ بایت در برابر ۸۱ بایت JSON متنی بدون فاصله — یه ذره صرفه‌جویی به قیمت از دست دادن انسان‌خوانی. همین رکورد رو جلوتر با Protocol Buffers (۳۳ بایت) و Avro (۳۲ بایت) می‌بینی.

MessagePack, CBOR and BSON provide binary representations close to the JSON model, sometimes with extra types such as byte strings. In an ordinary map representation, field names still travel with each record.

The chapter's example, {"userName": "Martin", "favoriteNumber": 1337, "interests": [...]}, takes 66 bytes in MessagePack versus 81 bytes in compact textual JSON. That's one record, rather than a universal saving. The same example uses 33 bytes in Protocol Buffers and 32 in Avro. The schema changes what metadata each record needs to carry.

تو Protocol Buffers هر فیلد یه شماره داره و همین شماره بخشی از هویتشه رو سیم. اسم عوض کردن کجا، شمارهٔ یه فیلد حذف‌شده رو دوباره دادن کجا — قاطیشون نکن.

مثال فنی: Tag هویت فیلد است

وضعیت اولیه: فرض کن تو schema پیامت داری string name = 1، بعد اومدی string email = 2 رو اضافه کردی.

اجرای مرحله‌به‌مرحله: یادت باشه شمارهٔ ۱ همیشه مال name می‌مونه؛ اگه email رو حذف کردی، شمارهٔ ۲ رو نده به یه معنای دیگه.

نتیجه و دلیل: اسم عوض کردن با هویت wire فرق داره؛ reuse شماره یعنی دادهٔ قدیمی رو با معنای اشتباه می‌خونی — تهش می‌ترکه.

Protocol Buffers, or protobuf, is Google's binary encoding system. Apache Thrift, originally from Facebook, uses a similar approach. Define the fields and their numbers in an interface definition language (IDL) before encoding the message:

message Person {

  • نوع فیلد و تگ تو یه بایت جا میشن؛ عددها طول‌متغیر (varint) ـن: ۱۳۷۱ تو دو بایت (بیت بالایی هر بایت یعنی «باز ادامه داره»). عددهای −64..63 تو یه بایت و −8192..8191 تو دو بایت جا میشن.

  • A code generator turns the schema into classes for different languages. The schema describes fields and types; separate application validation handles more detailed rules.
  • The example record takes 33 bytes. It carries tag numbers 1, 2 and 3 instead of field names. The schema maps those numbers back to meanings.
  • Small field tags and wire types fit in one byte. Varints use more bytes for larger values; 1337 takes two. A byte's top bit indicates whether another byte follows.   • اسم فیلد رو راحت عوض کن (اسم تو داده نیست)؛ ولی تگ رو دست نزن — همهٔ داده‌های موجود می‌ترکه.
  • فیلد جدید با تگ تازه = forward compatible: کد قدیمی تگ ناشناس رو نادیده می‌گیره و (اگه درست پیاده شده باشه) بایت‌هاش رو نگه می‌داره. backward هم اوکیه چون دادهٔ قدیمی برای فیلد تازه مقدار پیش‌فرض می‌گیره.
  • حذف فیلد آینهٔ اضافه کردنه: تگ قدیمی رو هیچ‌وقت دوباره استفاده نکن (هنوز داده با اون تگ نوشته شده)؛ می‌تونی تگ‌های بازنشسته رو تو schema reserve کنی.
  • عوض کردن type فیلد برای بعضی typeها میشه ولی خطر truncation داره: ۳۲بیتی ← ۶۴بیتی برای کد جدید راحته، ولی کد قدیمی مقدار ۶۴بیتی رو می‌ریزه تو متغیر ۳۲بیتی و می‌بُره.
  • A record combines encoded fields. An unset field can be absent from the bytes. The tag identifies the field on the binary wire.
  • Keep existing tag numbers stable. Renaming a source-level field doesn't change that binary identity; other representations or application users of the name still need checking.
  • Add a new field with a fresh tag. Old binary readers can skip it; check that the round-trip path retains it when needed. New readers must handle its absence in old messages through the applicable default or presence rules.
  • Remove without reusing. Old messages can still contain the retired tag. Mark retired numbers, and names where appropriate, as reserved.
  • Check type changes. Some are wire-compatible but can lose values. A 32-bit to 64-bit change lets new code read the old range; old code reading a larger new value may truncate it. Parsing successfully doesn't establish the same meaning.

  • پس موقع خوندن با دو تا schema کار داری: writer's schema (همونی که موقع نوشتن بوده) و reader's schema (همونی که کد فعلی می‌خواد). Avro با مقایسهٔ این دو تا، داده رو از دید writer به دید reader ترجمه می‌کنه.
  • The example uses 32 bytes. Fields aren't identified by tag numbers or names in the record; values follow the writer's schema order. A string, for example, carries a length and UTF-8 bytes. You need the writer's schema to interpret that sequence correctly.
  • The reader also has its own reader's schema, describing what the current code expects. Avro resolves between the two. Decoding the stored bytes and presenting the reader's expected fields are connected but distinct jobs.

قواعد resolution (فرمولِ شکل ۵-۶ کتاب)Resolution rules (the book’s Figure 5-6 formula)

خواننده باید داده‌ای که با schema قبلی نوشته شده رو با قواعد سازگاری به schema خودش نگاشت کنه؛ مقدار پیش‌فرض برای فیلد غایب به کار میاد.

مثال فنی: فیلد اضافی و فیلد غایب

وضعیت اولیه: فرض کن writer فیلدهای name, age رو داره ولی reader فقط name, country می‌خواد.

اجرای مرحله‌به‌مرحله: تصور کن age به کار reader نمیاد پس می‌ره کنار؛ ولی country باید default معتبر داشته باشه وگرنه resolution می‌ترکه.

نتیجه و دلیل: «نسخه‌ها فرق دارن» همیشه حل‌شدنی نیست؛ این قواعد schemaست که می‌گه خوندن آزاده یا نه.

  • فیلدها با اسم جفت میشن؛ ترتیبشون مهم نیست.
  • فیلد تو writer هست ولی تو reader نه ← می‌ره کنار.
  • فیلدی که reader می‌خواد ولی writer ننوشته ← با مقدار پیش‌فرض reader پر میشه.
  • برای سازگاری فقط فیلد defaultدار رو می‌تونی اضافه یا حذف کنی. اضافه کردن فیلد بدون default ← backward می‌ترکه؛ حذف فیلد بدون default ← forward.
  • تو Avro، null پیش‌فرض همه‌چیز نیست: برای nullable باید union { null, ... } بنویسی و فقط وقتی می‌تونی default رو null بذاری که null شاخهٔ اول union باشه.
  • عوض کردن اسم فیلد با alias تو reader's schema میشه → backward هست ولی forward نیست. اضافه کردن شاخه به union هم فقط backward ـه.
  • Match record fields by name, rather than requiring the reader to declare the same field order.
  • If the writer has a field the reader doesn't want, resolution ignores it.
  • If the reader expects a field the writer didn't write, use the reader's default. Without a matching field or valid default, resolution fails.
  • Adding a reader field needs a default for reading older records. Removing a writer field needs a default in any old reader that still expects it. Check each direction.
  • null isn't an automatic default or an allowed value for every field. Declare nullability with a union such as union { null, ... }. Its default must match an allowed union branch. The examples here put null first and use a null default.
  • A reader-side alias can map an old writer name to a new reader name, helping backward compatibility. It doesn't teach an old reader the new name. Likewise, a new union branch accepted by a new reader may not be accepted by an old one.

۳.۶ مزایای schema و اسکیماهای پویا3.6 Schema benefits and dynamic schemas

schema میگه شکل و معنی داده چیه. فقط داشتن فایل schema کافی نیست؛ باید نسخه‌ها، قواعد تغییر و اینکه خواننده به ساختار درست برسه رو هم مدیریت کنی.

مثال فنی: قرارداد پیش از ورود داده

وضعیت اولیه: فرض کن پیام ورودی فیلد age رو با متن old فرستاده، ولی قراردادت عدد می‌خواد.

اجرای مرحله‌به‌مرحله: تصور کن validation همون‌جا پیام رو رد یا قرنطینه می‌کنه و خطا رو ثبت می‌کنه؛ فقط کلاس ساختن از schema کافی نیست.

نتیجه و دلیل: schema اختلاف نوع رو زود لو می‌ده؛ ولی سن منفی و این حرف‌ها کنترل جدا می‌خواد — قاطیشون نکن.

  • schema پویا با Avro راحت‌تره: چون tag تو schema نیست، می‌تونی مستقیم از schema رابطه‌ای Avro schema بسازی (هر جدول ← یه record، هر ستون ← یه فیلد) و dump کامل دیتابیس رو بنویسی. اگه schema دیتابیس عوض شد، همون مبدل رو دوباره اجرا می‌کنی؛ چون فیلدها با اسم شناخته میشن، reader's schema قدیمی هنوز جفت میشه. تو protobuf باید tagها رو دستی بدی و حواست باشه tag تکراری نره.
  • قالب‌های باینری schemaدار چند تا برد بزرگ دارن: از «JSONهای باینری» جمع‌وجورترن (اسم فیلدها حذف میشه)؛ خود schema سند زنده‌ست (برخلاف داک دستی، همیشه به‌روزه چون برای decode لازمه)؛ با نگه داشتن registry می‌تونی سازگاری تغییر رو قبل از deploy چک کنی؛ و برای زبان‌های statically typed کد می‌سازه (چک type تو compile-time).
  • این ایده‌ها جدید نیستن: ASN.1 از ۱۹۸۴ با tag تکامل schema داشت (هنوز تو گواهی‌های SSL/X.509 با کدگذاری DER استفاده میشه) ولی پیچیده و بدمستنده. بیشتر دیتابیس‌های رابطه‌ای هم پروتکل باینری خودشون رو دارن که driver (JDBC/ODBC) بازش می‌کنه.
  • قانون عملی: تعداد قالب‌های هم‌زمان تو سیستم رو کم نگه دار؛ هر قالب اضافه یعنی دردسر بیشتر برای نگه داشتن سازگاری.
  • Dynamic schemas: Avro doesn't require assigning field tags. A converter can map each relational table to a record and each column to a field for a database dump. Regenerate the writer schema when the table changes, then check resolution against the readers that still need it. Protobuf needs stable tag allocation across those changes.
  • Schema-driven binary formats: removing repeated field names can save space. Schemas document structure, registries can check compatibility before deployment, and generated code can catch type mismatches in statically typed languages. Type checks don't replace business validation.
  • The idea has history: ASN.1 has supported tagged schema evolution since 1984, including DER encoding for SSL/X.509 certificates. It brings substantial complexity. Relational database drivers such as JDBC/ODBC also decode their systems' binary protocols.
  • Keep the number of simultaneous formats small. Each additional format adds readers, tools and compatibility rules to maintain.

فیلد رو یهویی عوض نکن، مرحله‌ای برو: اول خواننده‌ها رو آماده کن، بعد نوشتن شکل تازه رو شروع کن و وقتی وابستگی قدیمی رفت، شکل قبلی رو حذف کن.

مثال فنی: چرخهٔ حذف یک فیلد

وضعیت اولیه: فرض کن می‌خوای از full_name بری به given_name, family_name.

اجرای مرحله‌به‌مرحله: اول خواننده‌ها رو کاری کن هر دو شکل رو بخورن؛ بعد writerها رو یکی‌یکی عوض کن؛ حذف نهایی فقط وقتیه که مصرف‌کننده و دادهٔ قدیمی پوشش داده شدن.

نتیجه و دلیل: یادت باشه حذف فیلد فقط دست بردن تو یه فایل schema نیست؛ عمر داده و همه readerها جزئی از مهاجرتن.

Resolution connects the writer’s and reader’s schemas: ignore extra writer fields and use valid reader defaults for missing ones. Deployment order still matters. During a rolling upgrade, old and new versions may coexist for hours or days.

Treat a field change as a staged migration. Prepare readers, introduce new writes, then retire the old representation only after its dependencies are covered.

What this tells you: Removing a field is a migration across readers and data lifetimes. Editing one schema file doesn't finish that migration.

قانون طلایی این چرخه readers first ـه: اول کدی رو deploy کن که فیلد تازه رو می‌خونه و اگه نبود تحملش می‌کنه، بعد کدی که می‌نویستش. مفت‌ترین تغییر، اضافه کردن فیلد اختیاری با مقدار پیش‌فرض ـه — تو Avro یعنی union { null, ... } با default مناسب — چون خوانندهٔ قدیمی نادیده‌ش می‌گیره و خوانندهٔ جدید با پیش‌فرض خودش پرش می‌کنه. ولی عوض کردن اسم یا type یه فیلد یعنی «حذف + اضافه»: اگه یه‌ضرب انجامش بدی، یکی از دو سازگاری backward/forward می‌ترکه.

Use readers first for this migration: deploy readers that understand the new field and handle its absence, then enable writers to populate it. An optional field with a valid default makes that transition easier. In the Avro example, union { null, ... } explicitly allows null, and the reader's default handles older writer schemas.

Renaming or retyping can require a “remove + add” migration. Check backward/forward compatibility rather than changing the schema in one step and hoping every reader agrees.

چرا حذف همیشه آخره؟ چون داده از کد بیشتر عمر می‌کنه: پیام‌های قدیمی مونده تو صف‌ها، backupها و فایل‌های آرشیوی برای همیشه با همون schema قدیمی می‌مونن. پس اول نوشتن فیلد رو متوقف می‌کنی (deprecated) ولی خواننده‌ها هنوز باید رکوردهای دارای اون رو بخونن، و فقط وقتی هیچ خواننده‌ای بهش نیاز نداشت از schema حذفش می‌کنی. نمودار ۶ همین چرخه رو مثل یه state machine کشیده: پنج حالت اصلی فیلد، دو «دروازهٔ سازگاری» برای تصمیم‌های سخت، و یه بن‌بست برای وقتی که ترتیب رو اشتباه رفتی.

Leave removal until last. Queued messages, backups and archives can retain a field long after the deployment finishes. Mark it deprecated, stop producing new values when the format permits, and keep readers able to handle the retained data.

Remove it only when the remaining readers and historical-data paths are covered. Diagram 6 gives the migration five field states, two compatibility gates and a failure path for an unsafe transition.

Setup: The application is moving from full_name to given_name, family_name.

Read the lanes from top to bottom: Field states, Compatibility gates and Terminal. The top states, numbered 01 through 05, show the normal lifecycle. Two diamonds ask whether a stronger assumption or final removal is safe. The red state marks a breaking change.

از چپ نوار بالا شروع کن: «Proposed» (قدم «01») با زیرنویس «schema change drafted» و برچسب «not deployed» — یعنی تغییر هنوز فقط رو کاغذه و به هیچ سروری نرسیده. فلش پررنگ «deploy readers first» می‌بردت به «Added Optional» (قدم «02») — زیرنویس «new field, default or null» و برچسب «writers may omit it»: فیلد تو schema هست و خواننده‌ها تحملش می‌کنن، ولی هنوز هیچ writerای پرش نمی‌کنه. فلش بعدی، «writers fill it»، می‌رسه به «In Use» (قدم «03») — زیرنویس «new writers fill it» و برچسب «old readers ignore it» — تنها حالت از این پنج‌تا که فیلد واقعاً داده حمل می‌کنه.

Begin at Proposed, step 01, labelled schema change drafted and not deployed. The change is drafted but hasn't reached the running system.

Follow deploy readers first to Added Optional, step 02, with new field, default or null and writers may omit it. Readers now handle both the old absence and the new representation. For Avro, that absence can come from an older writer schema; a default doesn't let a writer omit a field required by its own schema.

Then writers fill it reaches In Use, step 03, with new writers fill it and old readers ignore it. Compatible new writers begin supplying the value while old readers continue under their established rules.

از اینجا داستان جمع کردنه. فلش «stop writing it» میره به «Deprecated» (قدم «04») — زیرنویس «no new writes» و برچسب «readers still tolerate it»: نوشتن تازه وایساده، ولی رکوردهای قدیمی هنوز فیلد رو دارن و خواننده‌ها باید همونا رو بخونن. آخرش فلش «drop the field» می‌رسه به «Removed» (قدم «05») — زیرنویس «gone from the schema» و برچسب خیال‌راحت‌کن «safe to drop». حواست باشه این پنج قدم فقط به همین ترتیب امن‌ان؛ اگه ترتیب رو جابه‌جا کنی، یکی از دو دروازهٔ نوار میانی باید «بله» بده.

The stop writing it route reaches Deprecated, step 04. Its labels no new writes and readers still tolerate it distinguish stopping new production from forgetting old records. Retained data can still carry the field.

Finally, drop the field reaches Removed, step 05, labelled gone from the schema and safe to drop. That last label is a condition to prove: no remaining reader or replay path should require the removed representation.

حالا دروازه‌ها. از «Added Optional» فلش چین‌چین «need it now?» میاد پایین به نوار «Compatibility gates»: لوزی «All Writers Upgraded?» با زیرنویس «old code still running» و برچسب «gate». اگه همهٔ writerها بالا رفته باشن، فلش «yes, all upgraded» مستقیم برمی‌گرده به «In Use» — یعنی نوشتن فیلد فقط بعد از رد شدن از این دروازه شروع میشه. ولی اگه نسخهٔ قدیمی هنوز داره کار می‌کنه، فلش قرمز «no, mixed fleet» میره به نوار «Terminal»: «Breaking Change» با زیرنویس «old code crashes or drops data» و برچسب «roll back» — یعنی یا کد قدیمی می‌ترکه یا داده رو قورت میده، و تنها راه برگردوندن deploy ـه.

From Added Optional, follow need it now? down into Compatibility gates. The diamond All Writers Upgraded?, with old code still running and gate, asks whether it's safe to rely on all writers supplying the new representation.

The yes, all upgraded route reaches In Use. The no, mixed fleet route reaches Terminal and Breaking Change, with old code crashes or drops data and roll back. Requiring a field while old writers still omit it can break the rollout.

Keep that distinction clear: a compatible writer can populate an optional field before every writer upgrades. Depending on its presence everywhere is the stronger assumption this gate checks.

دروازهٔ دوم سمت راست همون نواره: از «Deprecated» فلش چین‌چین «can we drop it?» میاد پایین به «All Readers Upgraded?» با زیرنویس «ignore unknown fields» و برچسب «gate». جواب مثبت — فلش «yes, all upgraded» — فیلد رو می‌رسونه به «Removed»؛ ولی جواب منفی — فلش «not yet» — برمی‌گرده به خود «Deprecated»: حلقه‌ای که ممکنه هفته‌ها و ماه‌ها بچرخه تا آخرین خواننده‌ای که هنوز به فیلد نیاز داره بازنشسته بشه. حذف فیلد فقط وقتی «safe to drop» ـه که این دروازه برای همیشه بسته شده باشه.

From Deprecated, follow can we drop it? to All Readers Upgraded?, labelled ignore unknown fields and gate. The yes, all upgraded route reaches Removed. The not yet route loops to Deprecated, so retirement can wait while old dependencies remain.

Confirm safe to drop against active readers and retained records. A migration isn't complete just because the latest server code no longer mentions the field.

درس اول شکل رو تو یه ترتیب جمع کن: readers first، writers second، drop last. اول کد خواننده رو ببر بالا که فیلد ناشناس رو تحمل کنه، بعد کد نویسنده رو که فیلد رو پر کنه، و حذف رو فقط آخر کار و بعد از هر دو دروازه انجام بده. تو یه rolling upgrade واقعی یعنی deployها رو باید با همین ترتیب بچینی: نسخه‌ای که فقط «می‌خونه» همیشه امنه، نسخه‌ای که «می‌نویسه» فقط بعد از اون.

Use the order readers first, writers second, removal last for this migration. Prepare readers to handle both representations before enabling new writes. Remove the old representation only after its dependents are covered.

During a rolling upgrade, test each mixed-version path. Following a sequence helps; it doesn't replace checking the actual reader and writer contracts.

و درس دوم: داده از کد بیشتر عمر می‌کنه، و هر تغییر «به‌ظاهر کوچیک» ممکنه لباس «حذف + اضافه» تنش باشه — عوض کردن اسم فیلد، عوض کردن type، یا حتی عوض کردن مقدار پیش‌فرض. قیمت به‌هم ریختن ترتیب همون یه فلش قرمز «no, mixed fleet» ـه: «Breaking Change» و بعد «roll back». اگه هر تغییر schema رو با همین پنج قدم و دو دروازه بسنجی، deploy بدون downtime دیگه شانس نیست؛ نتیجهٔ منطقی ترتیب درسته.

Data outlives code, so check name, type and default changes against historical records too. Each can change what a reader sees.

The red path no, mixed fleet leads to Breaking Change and roll back. The five states and two gates are prompts to find that incompatibility before rollout. Plan the transition around readers and data lifetimes, including a rollback path.

  • Workflow Engine has steps logged and replayed and durable execution, reached by step results to durable log. Future executions must still understand the stored history.
  • Broker / Actors has sender encodes, subscribers decode and async messages, reached by publish events and messages. Subscribers can upgrade or process the message at different times.
یادت باشه کار تو هر چهار حالت یکیه: object به بایت، بایت به object. ولی کی encode می‌کنه، کی decode، و کِی فرق می‌کنه. نکته ماندگار: همین «کی و کِی» تعیین می‌کنه چه سازگاری لازمه. جلو تک‌تک همین چهار شاخه رو باز می‌کنیم.

All four paths cross a representation boundary. What changes is who encodes, who decodes and when. That timing sets the compatibility window. A finished deployment doesn't make old database records, queued messages or workflow histories disappear.

۴.۲ جریان داده از طریق پایگاه داده4.2 Dataflow via databases

فرض کن نوشتن تو دیتابیس یعنی نامه فرستادن به خودِ آینده‌ت. ممکنه نسخه بعدی برنامه رکوردی رو بخونه که سال‌ها پیش ساخته شده. نکته ماندگار: ذخیره کردن یعنی پیام به آینده.

مثال فنی: ویرایش نام، حذف email

وضعیت اولیه: فرض کن نسخه ۲ رکورد {name:Sara,email:a@b} رو نوشته. ولی نسخه ۱ فقط name رو می‌شناسه.

اجرای مرحله‌به‌مرحله: تصور کن نسخه ۱ کل شیء رو می‌خونه. name رو عوض می‌کنه. بعد بدون email پس می‌نویسه. مگه اینکه update رو فقط به name محدود کنی یا فیلد ناشناخته رو نگه داری.

نتیجه و دلیل: یادت باشه یه read-modify-write قدیمی می‌تونه داده جدید رو بی‌صدا ببلعه. حتی وقتی decode هیچ خطایی نداده. نکته ماندگار: decode موفق یعنی داده سالم؟ نه!

  • فرض کن تو دیتابیس نویسنده encode می‌کنه، خواننده decode. اگه فقط یه process داری، خواننده همون خودتی در آینده. ذخیره کردن یعنی پیام به خودِ آینده‌ت. پس backward compatibility حتماً لازمه.
  • ولی معمولاً چند process هم‌زمان به دیتابیس وصل‌ان. وسط rolling upgrade بعضی جدیدن، بعضی قدیمی. پس forward compatibility هم لازمه. یادت باشه نسخه‌ها کنار هم زندگی می‌کنن.
  • data outlives code: تصور کن یه مقدار ۵ میلی‌ثانیه پیش نوشته شده، یکیش ۵ سال پیش. کد تو چند دقیقه عوض میشه. ولی داده تا بازنویسی صریح با همون فرمت قدیمی می‌مونه.
  • فرض کن می‌خوای همه داده رو به schema جدید migrate کنی. روی داده بزرگ گرونه. پس موتورها deferred و best-effort انجامش میدن. موتور LSM موقع compaction با فرمت جدید بازنویسی می‌کنه. دیتابیس رابطه‌ای ستون nullable اضافه می‌کنه بدون rewrite (ردیف قدیمی رو با null می‌خونه). نتیجه: دیتابیس «انگار» یه schema داره، ولی زیرش مخلوطی از نسخه‌هاست.
  • تغییر سخت‌تر (تک‌مقداری ← چندمقداری، جابه‌جایی به جدول جدا) هنوز بازنویسی سطح برنامه می‌خواد. نگه داشتن سازگاری تو این migrationها هنوز کار پژوهشیه.
  • بایگانی (archival): تصور کن snapshot یا dump معمولاً با جدیدترین schema و یکدست نوشته میشه. چون dump یه‌جا نوشته و فریز میشه، Avro object container files عالی‌ان. تازه فرصت خوبیه برای کدگذاری ستونی مثل Parquet (فصل ۱۱). نکته ماندگار: dump جای تسویه‌حساب با نسخه‌های قدیمیه.
  • A database writer encodes a value; a reader later decodes it. Even one application version eventually has a future reader, so backward compatibility matters.
  • Shared databases can serve several services or application versions. During rollout, forward compatibility matters too.
  • Data outlives code: one value may be 5 milliseconds old and another 5 years old. Deploying code doesn't rewrite either value automatically.
  • Full migrations can be expensive. Some engines defer conversion: an LSM may rewrite records during compaction, while a relational engine may represent a newly added nullable column without rewriting old rows. Readers see a consistent logical schema over mixed physical versions. The details depend on the engine and change.
  • Moving a single value to a collection or another table can still require application-level migration. Preserving compatibility across these changes needs an explicit plan.
  • Archives: a dump can translate records into one chosen, newer schema. Avro object container files retain the writer schema with the records. A dump can also be a useful point to adopt a columnar representation such as Parquet, covered in Chapter 11.

Example: Changing a name and losing an email

Setup: Version 2 writes {name:Sara,email:a@b}. Version 1 knows only name.

Walk through it: Version 1 reads the whole object, changes name and writes it back without email. It can avoid that loss by preserving unknown fields or updating only name.

What this tells you: An old read-modify-write path can silently delete new information. Successful decoding alone doesn't prove a safe update.

۴.۳ سرویس‌ها: REST و RPC4.3 Services: REST and RPC

  • فرض کن الگوی رایج همون کلاینت و سرورئه. سرور API رو می‌ذاره رو شبکه. کلاینت درخواست می‌فرسته. وب هم همینه (GET برای HTML/CSS/JS، POST برای فرستادن داده) با پروتکل‌های استاندارد (HTTP، URL، TLS، HTML).
  • یادت باشه کلاینت فقط مرورگر نیست. اپ موبایل و دسکتاپ و اپ JavaScript مرورگر هم با HTTP وصل میشن. معمولاً JSON می‌گیرن.
  • تصور کن سرویس‌ها شبیه دیتابیس‌ان (داده می‌گیرن و میدن). ولی به‌جای query language عمومی، API ویژه برنامه دارن با ورودی/خروجی ازپیش‌تعیین‌شده. همین میشه کپسوله‌سازی.
  • هدف microservices اینه هر سرویس مستقل deploy و تکامل پیدا کنه (معمولاً یه تیم، یه سرویس، release مکرر). پس نسخه قدیم و جدید سرور و کلاینت هم‌زمان‌ان. تا وقتی API سازگاره، تیم آزاده زیرش رو عوض کنه.
  • web service یعنی سرویس روی HTTP. سه‌جا به کار میره: کلاینت روی دستگاه کاربر (اینترنت عمومی)، سرویس‌به‌سرویس تو یه سازمان (شبکه خصوصی)، و سازمان‌به‌سازمان (API عمومی مثل پرداخت یا OAuth).
  • REST محبوب‌ترین فلسفه طراحیه: فرمت ساده، URL برای شناسایی منابع، امکانات HTTP برای cache و احراز هویت و content negotiation. ولی کلاینت هنوز باید بدونه کدوم endpoint و چه فرمتی. برای همین IDL می‌نویسن: OpenAPI (Swagger) برای JSON و Protocol Buffers برای gRPC. ابزار IDL داک می‌سازه، سازگاری schema رو چک می‌کنه، GUI تست میده. نکته ماندگار: قرارداد نانوشته، قرارداد نیست.
  • A client sends requests to a server's network API. On the web, GET retrieves resources such as HTML/CSS/JS and POST submits data, using HTTP, URLs and TLS.
  • Clients include browsers, mobile and desktop apps, and browser JavaScript. Many HTTP APIs exchange JSON.
  • A service exposes application-specific operations with defined inputs and outputs, rather than a general database query language. That provides encapsulation.
  • Microservices aim for independent deployment and evolution. Teams can change internals while preserving the APIs other versions still use.
  • A web service runs over HTTP. It may serve user devices across the internet, other services inside an organization, or external organizations through APIs such as payment processing and OAuth.
  • REST uses resource identity and HTTP facilities such as caching, authentication and content negotiation. Clients still need the endpoint and payload contract. IDLs, including OpenAPI (Swagger) for JSON services and Protocol Buffers for gRPC, can generate documentation, compatibility checks and testing tools.
چرا «فراخوانی از راه دور» مثل فراخوانیِ محلی نیست؟Why isn’t a “remote call” like a local call?

فرض کن تو REST یا RPC از یه سرویس دیگه کار می‌خوای. این صدا روی شبکه‌ست. ممکنه دیر برسه. جوابش گم بشه. یا نتیجه‌اش نامشخص بمونه. نکته ماندگار: شبکه مثل تابع محلی قول نمی‌ده.

مثال فنی: RPC ناموفق یا پاسخ نامعلوم؟

وضعیت اولیه: فرض کن کلاینت CreateOrder(request_id=r7) رو فرستاده. سرور سفارش رو ثبت کرده ولی جواب وسط راه گم شده.

اجرای مرحله‌به‌مرحله: تصور کن با همون شناسه retry می‌کنی، می‌رسی به همون نتیجه. ولی با شناسه تازه retry کنی ممکنه یه سفارش دوم بسازی.

نتیجه و دلیل: یادت باشه timeout یعنی «نمی‌دونم شد یا نه». نکته ماندگار: برخلاف تابع محلی، API باید خودش این ابهام رو مدیریت کنه.

RPC presents a remote request much like a function call, an idea called location transparency. The similar syntax doesn't remove the network boundary. Compare the outcomes before deciding how to retry:

Example: A timeout with an unknown outcome

Setup: A client sends CreateOrder(request_id=r7). The server creates the order, but its response is lost.

Walk through it: With a matching idempotence contract, retrying the same identifier returns the same operation's result. Retrying with a new identifier can create a second order.

What this tells you: A timeout means the client doesn't know whether the action happened. The API must define how to resolve that uncertainty.

  • فرض کن صدای محلی قابل‌پیش‌بینیه. ولی درخواست شبکه‌ای غیرقابل‌پیش‌بینیئه (گم شدن، کندی ماشین دور).
  • تابع محلی یا مقدار میده یا exception. ولی درخواست شبکه‌ای پایان سوم هم داره: timeout بدون نتیجه. نمی‌دونی اصلاً اجرا شد یا نه.
  • یادت باشه retry ممکنه عمل رو دوبار اجرا کنه (اگه فقط جواب گم شده باشه). مگه قرارداد idempotence و شناسه یکتا داشته باشی (فصل ۱۲).
  • latency شبکه متغیره: از کمتر از یه میلی‌ثانیه تا چند ثانیه. تابع محلی این‌طوری نیست.
  • نمی‌تونی pointer بدی. همه‌چیز باید encode بشه. برای داده بزرگ و object mutable دردسر میشه.
  • کلاینت و سرور ممکنه زبون متفاوت داشته باشن. ترجمه نوع‌ها زشت میشه (مثل اعداد بزرگ‌تر از 2^53 در JavaScript). نکته ماندگار: مرز زبان یعنی مرز سوءتفاهم.
  • A network request can be lost or delayed by a remote machine. Local-call syntax doesn't make that behavior predictable.
  • A timeout gives a third outcome beyond a returned value or known error: you don't know whether the operation happened.
  • A retry may execute the action twice if only the response was lost. Use an idempotence contract and stable request IDs where required; Chapter 12 returns to this.
  • Network latency can vary from less than a millisecond to seconds.
  • Pointers can't cross the boundary. Encode the values, accounting for large data and mutable objects.
  • Client and server languages may represent types differently, including JavaScript's integer precision beyond 2^53.
تصور کن جذابیت REST اینه انتقال state روی شبکه رو فراتر از صدا زدن تابع می‌فهمه. یادت باشه تاریخچه پر از شکست پرطمطراقه: EJB و RMI فقط Java، DCOM فقط مایکروسافت، CORBA پیچیده و ناسازگار، SOAP/WS-* پیچیده. نکته ماندگار: شفافیت لوکیشنِ دروغین گرون تموم میشه.

REST makes the transfer of resource state over the network explicit. An RPC interface can also work well when it exposes the network's failure semantics clearly.

The chapter's historical examples include Java-specific EJB and RMI, Microsoft-specific DCOM, and the complexity of CORBA and SOAP/WS-*. Hiding a remote call behind local-looking syntax doesn't settle interoperability, latency or uncertain outcomes.

سازگاریِ RPC دقیقاً چه می‌خواهد؟What exactly does RPC compatibility need?
فرض کن قراره اول همه سرورها، بعد کلاینت‌ها به‌روز بشن. پس روی request فقط backward لازمه. روی response فقط forward. gRPC و Avro RPC قواعد همون قالب کدگذاری‌شون رو ارث می‌برن. تو REST/JSON معمولاً «افزودن پارامتر اختیاری request» و «افزودن فیلد response» سازگار حساب میشه. ولی یادت باشه RPC اغلب از مرز سازمان رد میشه. کنترلی روی کلاینت‌ها نیست. پس سازگاری شاید باید تا ابد بمونه (یا چند نسخه API کنار هم). نسخه‌بندی هم توافق جهانی نداره: شماره تو URL، هدر Accept، یا نسخه هر کلاینت تو سرور. نکته ماندگار: API عمومی قول بلندمدت می‌خواد.

If every server upgrades before clients do, requests need backward compatibility and responses need forward compatibility for that transition. If a new client can reach an old server, test the reverse pair too.

gRPC and Avro RPC inherit their formats' rules. Optional request parameters and extra JSON response fields may be compatible, provided readers accept them. Across organizations, old clients can remain for years, so maintain the contract or provide API versions side by side. Versions may appear in a URL, an Accept header or a server's client-specific handling; agree on the policy.

۴.۴ workflow و اجرای پایدار (Durable Execution) + نمودار ۵4.4 Workflows and durable execution + Diagram 5

فرض کن گردش‌کار پایدار وضعیت قدم‌ها رو نگه می‌داره. تا بعد از توقف برنامه بشه ادامه داد. ولی اثر بیرونی هر قدم هنوز باید ضد اجرای دوباره باشه. نکته ماندگار: ادامه از تاریخچه، نه اجرای تکراری بی‌حساب.

مثال فنی: ادامهٔ workflow بعد از crash

وضعیت اولیه: فرض کن workflow اول رزرو داره بعد صدور رسید. رزرو با شناسه r7 موفق شده.

اجرای مرحله‌به‌مرحله: تصور کن engine پیشرفت رو پایدار کرده. بعد از crash از روی تاریخچه ادامه میده. ولی فعالیتی که نتیجه‌ش ثبت نشده ممکنه دوباره صدا زده بشه.

نتیجه و دلیل: یادت باشه اثر بیرونی رزرو باید با r7 امن تکرار بشه. نکته ماندگار: دوام workflow یعنی «ادامه از تاریخچه»، نه «فقط یه‌بار اجرا».

Consider a payment that checks fraud, charges a card and deposits funds through separate services. The sequence is a workflow; each step is a task. Temporal calls these activities, while some systems use durable functions.

A workflow can be a graph of tasks, described in a programming language, DSL or BPEL. Its history must remain readable if execution resumes after an upgrade or crash.

Example: Resuming a workflow after a crash

Setup: A workflow makes a reservation, then issues a receipt. The reservation with identifier r7 succeeds.

Walk through it: The engine retains progress and resumes from history after a crash. An activity whose outcome wasn't recorded may be called again.

What this tells you: The external reservation must be safe to retry with r7. Durable execution resumes from history; it doesn't guarantee each activity executes once.

  • فرض کن workflow engine تصمیم می‌گیره هر task کِی و رو کدوم ماشین بدوه. با خرابی چی کار کنه. چقدر موازی کنه. از یه orchestrator (زمان‌بندی) و یه یا چند executor (اجرا) ساخته شده. شروع با triggerئه: زمان‌بندی، وب‌سرویس، یا انسان.
  • خانواده‌ها رو تصور کن: ابزار داده‌ای مثل Airflow / Dagster / Prefect (هماهنگی ETL)، ابزار گرافیکی مثل Camunda / Orkes با BPMN برای غیرمهندس‌ها، و چارچوب durable execution مثل Temporal / Restate. نکته ماندگار: اسم‌ها عوض میشن، نقش orchestrator و executor همون‌ان.
  • A workflow engine schedules tasks, chooses executors, handles failures and controls parallel work. It combines an orchestrator with one or more executors. A schedule, web service or person can trigger a run.
  • Examples include ETL tools Airflow / Dagster / Prefect, graphical BPMN tools Camunda / Orkes, and durable execution frameworks Temporal / Restate. Compare their task and history contracts as well as their scheduling features.
durable execution چه دردی رو دوا می‌کنه؟What problem does durable execution solve?
فرض کن تو معماری سرویسی نمی‌تونی دو صدای کارت و بانک رو تو یه تراکنش دیتابیسی بپیچی. تازه با درگاه third-party هم طرفی. ولی می‌خوای هر پرداخت دقیقاً یه‌بار پردازش بشه. راه‌حل: چارچوب همه صداها و تغییرهای state رو تو ذخیره‌سازی پایدار (مثل write-ahead log) ثبت می‌کنه. اگه task بشکنه دوباره اجرا میشه. ولی قدم‌های موفق قبلی رد میشن و نتیجه قبلی‌شون برمی‌گرده. انگار صدا تکرار نشده. نکته ماندگار: exactly-once با لاگ و replayئه، نه با تراکنش کلاسیک.

A local database transaction doesn't automatically cover independent card and bank APIs. Durable execution records progress in persistent storage, such as a write-ahead log. On replay, it can reuse recorded successful results rather than calling those steps again.

A step whose result wasn't recorded may run again, even if its external effect happened. An exactly-once effect therefore also needs the destination's idempotence or deduplication contract. The durable log supplies history; it doesn't by itself make every remote action happen once.

وضعیت اولیه: فرض کن workflow اول رزرو داره بعد صدور رسید. رزرو با شناسه r7 موفق شده.

اجرای مرحله‌به‌مرحله: تصور کن engine پیشرفت رو پایدار کرده. بعد از crash از روی تاریخچه ادامه میده. ولی فعالیتی که نتیجه‌ش ثبت نشده ممکنه دوباره صدا زده بشه.

نتیجه و دلیل: یادت باشه اثر بیرونی رزرو باید با r7 امن تکرار بشه. نکته ماندگار: دوام workflow یعنی «ادامه از تاریخچه»، نه «فقط یه‌بار اجرا».

تصور کن شش شرکت‌کننده از چپ به راست‌ان: «Checkout» (زیرنویس: «workflow trigger»)، «Workflow Engine» (زیرنویس: «workflow runtime»)، «Durable Log» (زیرنویس: «write-ahead log»)، «Fraud Check» (زیرنویس: «internal service»)، «Card Network» و «Bank Service» (هر دو زیرنویس «third-party API»). دو نوار عنوان هم تو چپه: «First execution» و «Crash recovery and replay». یادت باشه اول اجرا، بعد نجات.

Example: Resuming a workflow after a crash

Setup: A workflow makes a reservation, then issues a receipt. The reservation with identifier r7 succeeds.

Walk through it: The engine retains progress and resumes from history after a crash. An activity whose outcome wasn't recorded may be called again.

What this tells you: The external reservation must be safe to retry with r7. Durable execution resumes from history; it doesn't guarantee each activity executes once.

Read the six participants from left to right: Checkout, labelled workflow trigger; Workflow Engine, labelled workflow runtime; Durable Log, labelled write-ahead log; Fraud Check, labelled internal service; then Card Network and Bank Service, both using a third-party API.

The bands First execution and Crash recovery and replay separate the initial calls from recovery. Track which successful results reached the durable log before the crash.

فرض کن تو اجرای اول «start payment workflow» از Checkout میاد به موتور. موتور قدم‌ها رو یکی‌یکی می‌فرسته: «activity: check fraud» به Fraud Check و جواب «not fraudulent». بعد «append step result» به Durable Log (فلش چین‌چین — یعنی هر قدم موفق اول ثبت میشه). بعد «activity: debit card» به Card Network و جواب «charged» و دوباره ثبت تو لاگ. قدم سوم «activity: deposit funds» به Bank Serviceئه که زیرش نوشته «worker crashes mid-step» — همین‌جا worker می‌میره.

The run begins with start payment workflow. The engine sends activity: check fraud, gets not fraudulent, then follows append step result into the log.

Next comes activity: debit card, returning charged; that result is logged too. The activity: deposit funds step reaches the point marked worker crashes mid-step. The earlier recorded results are known. The interrupted step needs careful retry handling.

تصور کن نوار دوم قصه نجاته: «re-execute workflow» (فلش چین‌چین از Checkout)، بعد «replay recorded steps» از موتور به Durable Log — موتور می‌بینه check fraud و debit card قبلاً انجام و ثبت شدن. پس فقط قدم گم‌شده رو می‌فرسته: «deposit funds (only missing step)» به Bank Service، جواب «deposited»، و پایان خوش «payment complete, exactly once» به Checkout.

In recovery, re-execute workflow begins replay recorded steps. The engine finds the recorded fraud-check and card-charge results, so it doesn't repeat those calls.

It sends deposit funds (only missing step), receives deposited, then returns payment complete, exactly once. That final label assumes the payment's external effects are protected against duplicate execution. If the original deposit happened before its response was recorded, retrying must recognize the same operation.

یادت باشه «دقیقاً یه‌بار» با تراکنش سنتی دیتابیسی به دست نمیاد. با لاگ پایدار + replay به دست میاد. نکته ماندگار: نجات مفت نیست — بهاش رو بخش بعد می‌بینی.

The durable log and replay let execution resume from recorded history. They don't replace every external service's transaction or idempotence rules. To explain an exactly-once outcome, include what happens when a remote effect succeeds but its result is lost.

مثال فنی: Replay با کد عوض‌شده

وضعیت اولیه: فرض کن workflow قدیمی تو تاریخچه‌ش اول «رزرو» داره بعد «رسید».

اجرای مرحله‌به‌مرحله: تصور کن کد تازه بدون نسخه‌بندی ترتیب تصمیم‌ها رو به‌هم می‌زنه. اون‌وقت replay ممکنه با تاریخچه ناسازگار بشه و بترکه.

نتیجه و دلیل: یادت باشه داده تصمیم و نسخه منطق باید خوانا بمونن. ساعت و تصادف و I/O رو بی‌قاعده ننداز وسط replay. نکته ماندگار: replay غیرقطعی یعنی کابوس.

  • فرض کن سرویس بیرونی (مثل درگاه third-party) هنوز باید idempotent باشه. تو باید با شناسه یکتا جلوی اجرای تکراری رو بگیری.
  • چارچوب صداها رو به ترتیب ثبت می‌کنه. انتظار داره اجرای بعدی دقیقاً همون صداها به همون ترتیب باشه. پس جابه‌جا کردن دو خط کد می‌تونه replay invocationهای در جریان رو مبهم کنه. راه امن: تغییر کد workflow رو به‌صورت نسخه جدا deploy کن تا قدیمی‌ها با منطق قدیم replay بشن.
  • یادت باشه replay باید قطعی (deterministic) باشه: همون ورودی ← همون خروجی. عدد تصادفی یا ساعت سیستم ممنوع. چارچوب‌ها نسخه قطعی این تابع‌ها رو میدن و ابزار مثل Workflow Check تخلف رو پیدا می‌کنه (برمی‌گردیم به فصل ۹). نکته ماندگار: تصادف تو replay یعنی تاریخچه خراب.
  • External side effects: use idempotent operations or unique IDs with deduplication for destinations such as payment gateways. An unfinished activity may be retried.
  • Versioning: replay must remain consistent with the recorded sequence of decisions and calls. Reordering steps can break in-flight workflows. Use the framework's versioning mechanisms so retained histories still replay with compatible logic.
  • Determinism: the same recorded inputs must produce the expected decisions. Uncontrolled random numbers, clock reads and I/O can change them. Frameworks provide supported ways to obtain those values; tools such as Workflow Check can detect violations. Chapter 9 returns to determinism.

۴.۵ معماری event-driven4.5 Event-driven architecture

فرض کن تو معماری رویدادمحور تولیدکننده خبر یه اتفاق رو منتشر می‌کنه. مصرف‌کننده‌ها مستقل واکنش نشون میدن. ولی شکل و نسخه رویداد هنوز قرارداد مشترکه. نکته ماندگار: جدایی در زمان، نه جدایی در قرارداد.

مثال فنی: رویداد مستقل از مصرف‌کننده

وضعیت اولیه: فرض کن سفارش 42 رویداد OrderPlaced رو منتشر کرده.

اجرای مرحله‌به‌مرحله: تصور کن هم گروه ارسال می‌گیرتش هم گروه تحلیل. تازه تو گروه ارسال چند worker کار رو بین خودشون تقسیم می‌کنن.

نتیجه و دلیل: یادت باشه pub/sub یعنی تکثیر بین گروه‌ها، queue یعنی تقسیم کار تو گروه. نکته ماندگار: باز هم تکرار و خطا رو باید کنترل کنی.

  • فرض کن تو این معماری درخواست یه event یا messageئه. فرستنده معمولاً منتظر پردازش گیرنده نمی‌مونه. پیام از یه message broker (event broker، message queue، MOM) رد میشه که موقتاً نگهش می‌داره.
  • تصور کن broker نسبت به RPC مستقیم این خوبی‌ها رو داره: بافر وقتی گیرنده نیست یا overloadئه، تحویل مجدد خودکار بعد از crash، بی‌نیازی از service discovery، فرستادن یه پیام به چند گیرنده، جدایی منطقی فرستنده و گیرنده (فرستنده فقط publish می‌کنه).
  • یادت باشه دو الگوی توزیع داری: queue (یه مصرف‌کننده از بین چندتا پیام رو می‌گیره) و topic / pub-sub (همه subscriberها نسخه خودشون رو می‌گیرن).
  • brokerها مدل داده تحمیل نمی‌کنن: پیام = بایت‌ها + metadata. رایج: Protobuf/Avro/JSON با schema registry، و AsyncAPI معادل OpenAPI برای پیام. مثال‌ها: RabbitMQ، ActiveMQ، NATS، Redpanda، Kafka (متن‌باز) و Kinesis، Azure Service Bus، Cloud Pub/Sub (ابری) — مقایسه تو فصل ۱۲.
  • دوام پیام: خیلی‌ها رو دیسک می‌نویسن تا با crash نپرن. ولی برخلاف دیتابیس، خیلی‌ها بعد از مصرف خودکار حذف می‌کنن. برای event sourcing به broker نیاز داری که پیام‌ها رو تا ابد نگه داره (فصل ۳).
  • فرض کن مصرف‌کننده‌ای پیام رو دوباره تو topic دیگه publish می‌کنه. باید فیلدهای ناشناخته رو حفظ کنه. وگرنه بلای شکل ۵-۱ این‌بار وسط pipeline میاد.
  • actor model: تصور کن به‌جای thread و قفل و deadlock، منطق تو actorها کپسوله میشه. هر actor state محلی خودش رو داره. با پیام ناهمزمان حرف می‌زنه. یه پیام در هر لحظه پردازش می‌کنه. تحویل پیام هم تضمینی نیست. تو چارچوب‌های توزیع‌شده مثل Akka، Orleans و Erlang/OTP همون مکانیزم محلی یا دور یکسانه (پیام شفاف encode میشه، اون‌طرف decode). location transparency این‌جا بهتر از RPC جواب میده چون مدل از اول «پیام ممکنه گم بشه» رو قبول کرده. یادت باشه برای rolling upgrade باز هم کدگذاری سازگار می‌خوای. نکته ماندگار: actor از اول با گم شدن کنار اومده، RPC نه.
  • In an event-driven system, a sender publishes an event or message and usually doesn't wait for the receiver's processing. A message broker, also called an event broker, message queue or MOM, holds and routes it.
  • Compared with direct RPC, a broker can buffer during receiver downtime or overload, redeliver after failure and distribute messages to several receivers. Senders address the broker rather than discovering each consumer endpoint.
  • A queue distributes work among consumers. A topic / pub-sub gives independent subscriber groups their own event stream; workers can share work within a group.
  • Payloads are bytes plus metadata. Common formats include Protobuf, Avro and JSON, often with a schema registry. AsyncAPI describes message interfaces. Examples include RabbitMQ, ActiveMQ, NATS, Redpanda and Kafka, plus Kinesis, Azure Service Bus and Cloud Pub/Sub. Chapter 12 compares them.
  • Durability and retention: many brokers persist messages, but some remove them after consumption. Event sourcing needs retained authoritative history for its replay requirements, whether in the broker or another durable history store.
  • A consumer that republishes data must preserve required unknown fields. Otherwise a transformation can repeat Figure 5-1's silent loss halfway through the pipeline.
  • In the actor model, an actor owns local state, receives asynchronous messages and processes them one at a time. Delivery guarantees depend on the framework and configuration. Distributed examples include Akka, Orleans and Erlang/OTP. Local and remote sends share an interface, with encoding at the remote boundary. The model already exposes asynchronous messaging; rolling upgrades still need compatible payloads.

۱. backward و forward compatibility یعنی چه و در APIها چطور معنا می‌شوند؟1. What do backward and forward compatibility mean — and in APIs?

backward یعنی کد جدید هنوز داده قدیمی رو بفهمه؛ forward یعنی کد قدیمی با داده جدید نترکه و نگهش داره. تو API جدا حساب کن کی request رو می‌نویسه و کی response رو می‌خونه.

مثال فنی: چهار ترکیب در rolling upgrade

وضعیت اولیه: تصور کن نصف سرورها هنوز نسخهٔ ۱‌ان، نصف دیگه رفتن روی نسخهٔ ۲.

اجرای مرحله‌به‌مرحله: اول نسخهٔ ۲ رکورد قدیمی رو می‌خونه و حالشو می‌بره؛ بعد نوبت نسخهٔ ۱ـه که یه رکورد دست‌نویس نسخهٔ ۲ دستش می‌رسه.

نتیجه و دلیل: تهش اینه: backward یعنی جدید قدیمی رو بخونه، forward یعنی قدیمی جدید رو نگه داره. rolling upgrade هر دو رو هم‌زمان می‌خواد، قاطی نکن.

Backward: new code reads old data. Forward: old code reads new data. If the old reader writes the record back, also test that it preserves required information.

For an old client and new server, requests need backward compatibility and responses need forward compatibility. Reverse the versions and reverse the directions. Identify the writer and reader for each payload.

What this tells you: Backward means the new reader handles old data. Forward means the old reader handles new data, retaining required information if it rewrites it. Mixed versions need both checks.

۲. چرا rolling upgrade هر دو نوع سازگاری را لازم دارد؟2. Why does a rolling upgrade need both compatibilities?

تو rolling upgrade همه nodeها با هم آپدیت نمی‌شن؛ یه مدت نسخه قدیم و جدید کنار هم کار می‌کنن و داده قدیم و جدید قاطی رد و بدل می‌شه. پس هر دو جهت خوندن رو لازم داری، نه فقط یکیش.

What this tells you: Backward means the new reader handles old data. Forward means the old reader handles new data, retaining required information if it rewrites it. Mixed versions need both checks.

۳. خطرِ شکل ۵-۱ کتاب چیست و چطور رفع می‌شود؟3. What is the book’s Figure 5-1 danger, and the fix?

کد قدیمی فیلد ناشناخته رو نمی‌فهمه و می‌ندازتش دور؛ بعد که همون رکورد رو پس می‌نویسه، اون فیلد برای همیشه از داده اصلی می‌پره. راه حل: یا فیلد ناشناخته رو نگه دار، یا به‌جای بازنویسی کل رکورد فقط همون تیکه لازم رو update کن.

مثال فنی: ویرایش نام، حذف email

وضعیت اولیه: فرض کن نسخه ۲ رکورد {name:Sara,email:a@b} رو نوشته. ولی نسخه ۱ فقط name رو می‌شناسه.

اجرای مرحله‌به‌مرحله: تصور کن نسخه ۱ کل شیء رو می‌خونه. name رو عوض می‌کنه. بعد بدون email پس می‌نویسه. مگه اینکه update رو فقط به name محدود کنی یا فیلد ناشناخته رو نگه داری.

نتیجه و دلیل: یادت باشه یه read-modify-write قدیمی می‌تونه داده جدید رو بی‌صدا ببلعه. حتی وقتی decode هیچ خطایی نداده. نکته ماندگار: decode موفق یعنی داده سالم؟ نه!

Old code can decode a record successfully, keep only the fields it knows and then overwrite the original record. The new field disappears without a parse error.

Preserve unknown fields through the whole round trip, or update only the intended field. Protobuf binary messages support preservation, but JSON conversion or rebuilding a message from known fields can lose it. Test the update path the application really uses.

Example: Changing a name and losing an email

Setup: Version 2 writes {name:Sara,email:a@b}. Version 1 knows only name.

Walk through it: Version 1 reads the whole object, changes name and writes it back without email. It can avoid that loss by preserving unknown fields or updating only name.

What this tells you: An old read-modify-write path can silently delete new information. Successful decoding alone doesn't prove a safe update.

۴. چهار مشکلِ اصلیِ کدگذاریِ ویژهٔ زبان (مثل Serializable و pickle) چیست؟4. What are the four core problems of language-native encoding (Serializable, pickle)?

Walk through it: A new version removes the class, or another language needs the file. The native decoder may no longer be able to rebuild the object.

What this tells you: Data can outlive its original code. Use an independent exchange schema for that lifetime, and don't pass untrusted input to unsafe object decoders.

JSON به هیچ خواننده‌ای قول دقت عدد نمی‌ده. مثلاً عدد معمولی JavaScript عدد صحیح بزرگ رو دقیق نگه نمی‌داره و گرد می‌کنه. پس id بزرگ رو number نفرست.

۶. چرا برای داده‌های باینری در JSON از Base64 استفاده می‌کنند و هزینه‌اش چیست؟6. Why is Base64 used for binary data in JSON — at what cost?

مثال فنی: Base64 برای بایت در JSON

اجرای مرحله‌به‌مرحله: تصور کن Base64 هر سه بایت رو می‌کنه چهار تا نویسه؛ برای ورودی بزرگ حدود یه‌سوم حجم می‌ره بالا، جدا از سربار خود JSON.

نتیجه و دلیل: این فقط راه حمل بایته تو رشته، فشرده‌سازی نیست؛ برای فایل بزرگ یه مسیر جدا بذار — سبک‌تر درمیای.

JSON/XML text doesn't directly store arbitrary binary bytes. Base64 represents them as text, adding roughly one-third to the size plus conversion work. It provides neither compression nor confidentiality. A binary format can offer a byte-string type directly; large files may fit a separate transfer path better.

What this tells you: This is a text representation of bytes, rather than compression. A large file may be better served through a separate transfer path.

۱۰. قواعد تکاملِ schema در protobuf برای افزودن/حذف/تغییر نوع چیست؟10. What are protobuf’s schema-evolution rules for add/remove/retype?

مثال فنی: تکامل protobuf با شمارهٔ ثابت

وضعیت اولیه: فرض کن فیلد string name = 1 منتشر شده و پیام‌های قدیمی هنوز این‌ور اون‌ور هستن.

نتیجه و دلیل: همون شماره رو از رشته بچرخونی به یه معنای عددی نامربوط، مهاجرت امن نیست؛ حفظ شماره به‌تنهایی حفظ معنا نیست — یادت باشه.

Add fields with unused numbers. Reserve retired numbers, and names where needed. Check type changes against the wire-compatibility rules and the permitted values. A 64-bit value read into an older 32-bit field can truncate even when the bytes parse.

Stable numbers protect identity. They don't prove that every reader interprets the value correctly.

Example: Evolving protobuf with stable numbers

Setup: The field string name = 1 has been published, and old messages remain in storage or transit.

Walk through it: Add a new field only with an unused number. Reserve retired numbers and the names needed by the contract. Check type changes against wire and value semantics.

What this tells you: Reusing a string field's number for an unrelated numeric meaning isn't a safe migration. A stable number alone doesn't preserve meaning either.

۱۱. Avro هنگام decode از چه چیزی استفاده می‌کند و writer's schema از کجا می‌آید؟11. What does Avro decode with — and where does the writer’s schema come from?

۱۲. قواعدِ Avro دربارهٔ مقدارِ پیش‌فرض (default) چیست؟12. What are Avro’s default-value rules?

اگه خواننده فیلدی بخواد که نویسنده نداره، باید تو اسکیمای خواننده default باشه وگرنه decode می‌ترکه. حذف فیلد هم همینه و به قرارداد خواننده قدیمی برمی‌گرده. default یعنی «جای خالی رو پر کن»، نه «نوشتن اختیاریه».

مثال فنی: Resolution در Avro

وضعیت اولیه: فرض کن writer فقط name داره، reader جدید اومده یه فیلد country با default مساوی IR اضافه کرده.

منبعِ توضیحِ فنی: قواعدِ رسمیِ تطبیقِ اسکیمای Avro

Setup: The writer has only name. A new reader adds country, with default IR.

Walk through it: When it reads the old record, the reader fills the missing country from its default.

What this tells you: A default fills a gap between writer and reader schemas. It doesn't make fields optional when encoding against the writer's schema.

۱۳. چرا در Avro برای nullable بودن باید union نوشت؟13. Why must Avro nullability use a union?

What this tells you: The alias supports the backward direction here. Test forward compatibility separately.

۱۵. مزایای قالب‌های باینریِ مبتنی بر schema نسبت به JSON چیست؟15. What advantages do schema-driven binary formats have over JSON?

با schema اسم و نوع فیلد از تک‌تک رکوردها حذف می‌شه — هم حجم کم می‌شه، هم قرارداد شفافه، هم validation و codegen داری. ولی schema به‌خودی‌خود سازگاری نمیاره؛ قاعده تغییر و پیاده‌سازی درست می‌خواد.

مثال فنی: مقایسهٔ قالب روی همان رکورد

وضعیت اولیه: فرض کن همون رکورد user_id=17, active=true رو می‌خوای با چند تا قالب بنویسی.

اجرای مرحله‌به‌مرحله: تصور کن JSON اسم فیلدها رو دونه‌دونه با خودش حمل می‌کنه؛ ولی قالب schemaدار می‌تونه به‌جاش شناسه یا جای فیلد رو بذاره.

نتیجه و دلیل: یادت باشه سیب با سیب مقایسه کن — همون داده، همون کتابخونه؛ باینری بودن به‌تنهایی نه یعنی کم‌حجم‌تر، نه یعنی تکامل بهتر.

A schema can remove repeated field metadata, document structure and support generated code and compatibility checks. A registry lets you check proposed changes before deployment.

The costs include schema management and tools for inspecting binary data. A schema defines the structure; the change rules and the implementation determine whether evolution is safe.

Example: Compare the same record

Setup: The record to encode is user_id=17, active=true.

Walk through it: JSON carries the field names. A schema-driven format can identify fields through numbers or their schema-defined positions.

What this tells you: Compare the same data with stated encoders and settings. A binary representation alone doesn't establish a smaller record or safer evolution.

۱۶. «data outlives code» یعنی چه و چه نتیجه‌ای دارد؟16. What does “data outlives code” mean — what follows?

داده خیلی بیشتر از کد عمر می‌کنه. deploy جدید فایل و رکورد قدیمی رو خودش نو نمی‌کنه؛ باید از اول طراحی کنی کدِ ننوشته فردا داده امروز رو بخونه، یا مهاجرت جدا بذاری. تموم شدن deploy یعنی تموم شدن داده قدیمی؟ نه!

مثال فنی: سه مسیر همان داده

وضعیت اولیه: فرض کن عوض شدن اسم کاربر رو میشه از سه‌جا خوند: رکورد دیتابیس، جواب API، یا پیام رویداد.

اجرای مرحله‌به‌مرحله: تصور کن دیتابیس نسخه‌های قدیمی رو نگه داشته. API هنوز با کلاینت قدیمی حرف می‌زنه. صف هم ممکنه پیام قدیمی رو دوباره بده.

نتیجه و دلیل: یادت باشه هر مسیر پنجره سازگاری خودش رو داره. تموم شدن deploy سرور یعنی تموم شدن داده قدیمی؟ نه! نکته ماندگار: داده از کد دیرتر می‌میره.

A deployment taking minutes doesn't rewrite data stored in 2019. An engine may convert records later, for example during LSM compaction, or represent a nullable SQL column without rewriting every row. Other changes need a separate migration.

Design for future readers of today's records, and retained old records under tomorrow's code. Deployment and data migration have different lifetimes.

Example: The same data on three paths

Setup: A changed user name appears in a database record, an API response and an event message.

Walk through it: The database retains older records. The API still serves old clients. A queue can redeliver an older message.

What this tells you: Each path has its own compatibility window. Completing the server rollout doesn't retire all old data or readers.

۱۷. سه تفاوتِ محوریِ فراخوانیِ شبکه‌ای با فراخوانیِ محلی چیست؟17. What are three core network-call vs local-call differences?

فراخوانی شبکه سه‌تا فرق بزرگ با تابع محلی داره: ممکنه اصلاً نرسه، بعد از timeout نمی‌دونی اجرا شد یا نه، و تأخیرش خیلی نوسان داره. تازه قالب تبادل بین برنامه‌ها رو هم باید حل کنی. شبیه بودن ظاهر RPC به تابع محلی این‌ها رو پاک نمی‌کنه.

مثال فنی: RPC ناموفق یا پاسخ نامعلوم؟

وضعیت اولیه: فرض کن کلاینت CreateOrder(request_id=r7) رو فرستاده. سرور سفارش رو ثبت کرده ولی جواب وسط راه گم شده.

اجرای مرحله‌به‌مرحله: تصور کن با همون شناسه retry می‌کنی، می‌رسی به همون نتیجه. ولی با شناسه تازه retry کنی ممکنه یه سفارش دوم بسازی.

نتیجه و دلیل: یادت باشه timeout یعنی «نمی‌دونم شد یا نه». نکته ماندگار: برخلاف تابع محلی، API باید خودش این ابهام رو مدیریت کنه.

A remote request may never arrive. A timeout can leave its outcome unknown. Latency can vary widely. Retrying an uncertain result can repeat an action, so the API needs an idempotence policy.

Values also cross a format and sometimes a language boundary; pointers don't. An RPC wrapper can simplify the call syntax without removing any of those responsibilities.

Example: A timeout with an unknown outcome

Setup: A client sends CreateOrder(request_id=r7). The server creates the order, but its response is lost.

Walk through it: With a matching idempotence contract, retrying the same identifier returns the same operation's result. Retrying with a new identifier can create a second order.

What this tells you: A timeout means the client doesn't know whether the action happened. The API must define how to resolve that uncertainty.

۱۸. چرا در RPC فقط backward برای request و forward برای response کافی است؟18. Why is backward-on-request + forward-on-response enough in RPC?

این دو جهت فقط وقتی کافیه که اول سرور آپدیت بشه بعد کلاینت: سرور جدید request قدیمی رو می‌خونه (backward)، کلاینت قدیمی response جدید رو تحمل می‌کنه (forward). اگه کلاینت جدید به سرور قدیمی بخوره، جهت‌های برعکس هم لازم داری — حکم کلی نده.

مثال فنی: API با سرور تازه

وضعیت اولیه: فرض کن کلاینت قدیمی درخواست نسخهٔ ۱ می‌فرسته و جواب تازه می‌گیره.

اجرای مرحله‌به‌مرحله: حالا سرور باید request قدیمی رو بخوره، کلاینت هم باید response جدید رو تحمل کنه؛ اگه سرور قدیمی هنوز زنده‌ست request تازه هم باید براش قابل‌قبول بمونه.

نتیجه و دلیل: جهت سازگاری بستگی داره کی نوشته کی خونده؛ یه حکم کلی برای همه rolloutها نداریم — حواست باشه.

Only under a server-first rollout can you limit that transition to backward-compatible requests and forward-compatible responses. A new client reaching an old server needs the reverse checks too.

Across organizations, you don't control the client's upgrade date. Agree on a support period or parallel API versions. Check the actual deployment paths before choosing compatibility directions.

Example: An API with a newer server

Setup: An old client sends a version 1 request and receives a response from a new server.

Walk through it: The server must read the old request; the client must handle the new response. If old servers remain, new requests may need to work with them too.

What this tells you: Compatibility direction follows the writer-reader pair. One rollout assumption doesn't establish safety for every deployment order.

۱۹. تفاوتِ queue و topic (pub/sub) چیست؟19. What’s the queue vs topic (pub/sub) difference?

تو queue هر پیام فقط به یه consumer می‌رسه — تقسیم کار. تو pub/sub هر گروه subscriber یه کپی از همون رویداد می‌گیره — تکثیر بین گروه‌ها؛ تازه داخل هر گروه می‌شه بار رو تقسیم کرد.

مثال فنی: رویداد مستقل از مصرف‌کننده

وضعیت اولیه: فرض کن سفارش 42 رویداد OrderPlaced رو منتشر کرده.

اجرای مرحله‌به‌مرحله: تصور کن هم گروه ارسال می‌گیرتش هم گروه تحلیل. تازه تو گروه ارسال چند worker کار رو بین خودشون تقسیم می‌کنن.

نتیجه و دلیل: یادت باشه pub/sub یعنی تکثیر بین گروه‌ها، queue یعنی تقسیم کار تو گروه. نکته ماندگار: باز هم تکرار و خطا رو باید کنترل کنی.

A queue shares work among consumers: one worker handles a delivery. Pub/sub gives independent subscriber groups access to the same event; workers can share work within each group. Redelivery can still occur, so neither pattern removes duplicate-handling requirements.

Choose a payload contract and, where useful, a schema registry. A forwarding consumer must retain unknown information that downstream readers still need.

Example: An event with independent consumers

Setup: Order 42 publishes OrderPlaced.

Walk through it: Shipping and analytics each consume it. Several shipping workers can share the work within their group.

What this tells you: Pub/sub distributes the event across groups; queue-style consumption shares work within a group. Both still need failure and duplicate handling.

۲۰. durable execution چطور «دقیقاً یک‌بار» می‌دهد و چه محدودیت‌هایی دارد؟20. How does durable execution deliver “exactly once” — and its limits?

موتور durable پیشرفت رو ذخیره می‌کنه و بعد از crash از روی تاریخچه ادامه می‌ده. ولی «دقیقاً یه‌بار» برای دنیای بیرون مفت نیست — مقصد باید idempotent باشه یا با id تکراری مهار بشه. دوام یعنی ادامه از تاریخچه، نه یه‌بار اجرا شدن.

مثال فنی: ادامهٔ workflow بعد از crash

وضعیت اولیه: فرض کن workflow اول رزرو داره بعد صدور رسید. رزرو با شناسه r7 موفق شده.

اجرای مرحله‌به‌مرحله: تصور کن engine پیشرفت رو پایدار کرده. بعد از crash از روی تاریخچه ادامه میده. ولی فعالیتی که نتیجه‌ش ثبت نشده ممکنه دوباره صدا زده بشه.

نتیجه و دلیل: یادت باشه اثر بیرونی رزرو باید با r7 امن تکرار بشه. نکته ماندگار: دوام workflow یعنی «ادامه از تاریخچه»، نه «فقط یه‌بار اجرا».

Durable execution stores history and uses recorded results when execution resumes. It can skip calls whose success was recorded, while an activity with no recorded outcome may be retried.

Protect external effects with idempotence or stable IDs and deduplication. Keep workflow changes compatible with existing histories, preserve the expected decision order and use deterministic replay. Avoid uncontrolled clock reads, randomness or I/O in that replay path. Durable means resumable; it doesn't mean every activity runs only once.

Example: Resuming a workflow after a crash

Setup: A workflow makes a reservation, then issues a receipt. The reservation with identifier r7 succeeds.

Walk through it: The engine retains progress and resumes from history after a crash. An activity whose outcome wasn't recorded may be called again.

What this tells you: The external reservation must be safe to retry with r7. Durable execution resumes from history; it doesn't guarantee each activity executes once.

5.3اشتباهات رایج در جواب‌های مصاحبه5.3 Common interview mistakes

  • قاطی کردن backward و forward؛ همیشه از خودت بپرس «کی داره چی رو می‌خونه؟» — جوابش جهت رو معلوم می‌کنه.
  • فکر کنی «JSON که schema نداره پس تکامل نمی‌خواد» — داده JSON هم سال‌ها می‌مونه و کد قدیمی می‌تونه فیلد جدید رو بی‌صدا پاک کنه.
  • دست بردن به tag تو protobuf یا دادن شماره فیلد حذف‌شده به یه فیلد جدید — یعنی داده قدیمی رو با معنای غلط می‌خونی، عملاً نابودش می‌کنی.
  • تو Avro فیلد بدون default اضافه کنی بعد تعجب کنی چرا backward ترکید — بدون default خواننده جدید داده قدیمی رو نمی‌فهمه.
  • فرض کنی همه کتابخونه‌ها فیلد ناشناخته رو نگه می‌دارن؛ این رفتار رو باید صریح چک و تست کنی، حدس نزن.
  • فکر کنی «باینری یعنی فشرده»؛ MessagePack فقط ۶۶ در برابر ۸۱ بایته — فشردگی واقعی وقتی میاد که schema اسم فیلدها رو از wire حذف کنه.
  • با RPC مثل تابع محلی رفتار کنی و timeout و retry و idempotence رو یادت بره — تهش تو پروداکشن می‌فهمی فرقشون چیه.
  • تو workflow ـی durable ترتیب activityها رو به‌هم بزنی و انتظار replay سالم داشته باشی، یا determinism رو یادت بره.
  • یادت بره تو معماری event-driven و workflow، صدا زدن API غریبه بدون idempotent بودن یعنی تکرار = دردسر.
  • Mixing up backward and forward. Identify who wrote the data and who's reading it.
  • Assuming JSON needs no evolution policy. Old code can still discard new fields during a rewrite.
  • Changing a protobuf tag or reusing a retired number for a different meaning.
  • Adding an Avro reader field without the default needed for older writer schemas.
  • Assuming every library or transformation preserves unknown fields. Test the actual round trip.
  • Generalizing “binary is smaller” from one record. The 66-versus-81-byte example isn't a universal compression ratio.
  • Treating RPC as a local call and leaving timeouts, uncertain results and idempotence unexplained.
  • Reordering durable-workflow decisions without planning how old histories replay.
  • Retrying an external action in a workflow or event handler without an idempotence or deduplication contract.

  • تعریف backward/forward رو بگو + بگو تو API به request/response چی می‌شه.
  • قصه شکل ۵-۱ رو تو ۳ جمله بگو: فیلد ناشناخته چرا می‌پره و چطور جلوش رو می‌گیری.
  • سه خانواده قالب و حکم نهایی: ویژه زبان (ممنوع)، متنی (تبادل انسان‌خوان)، باینری schema-driven (فشرده و تکامل‌پذیر).
  • قاعده تکامل protobuf (تگ ثابته، اسم آزاده، حذف‌شده reserve) و Avro (default اجباری، null فقط با union، alias فقط backward).
  • سه‌جایی که writer's schema تو Avro ازش میاد + ایده resolution (ignore / default) رو بگو.
  • «data outlives code» یعنی چی و تو چهار حالت جریان داده (پایگاه داده، RPC، workflow، broker) تکلیف سازگاری چیه — جدول بخش ۴ رو از حفظ بگو.
  • پنج‌تا فرق RPC با تابع محلی + سه محدودیت durable execution (idempotence، ترتیب، determinism) رو بگو.

  2. Explain Figure 5-1 in three sentences: how the unknown field is lost and how to preserve it.
  3. Compare language-native, textual and schema-driven binary formats, including their lifetime and reader assumptions.
  4. Explain protobuf's stable tags and reserved numbers, plus Avro defaults, nullable unions and reader-side aliases.
  5. Name three ways to retrieve an Avro writer schema and explain ignore/default resolution.
  6. Explain “data outlives code” for databases, APIs, workflow histories and broker messages.
  7. Give five differences between RPC and local calls, then explain durable execution's idempotence, ordering and determinism requirements.

برای پروفایل کاربر schemaهای Avro و Protobuf بنویس با نسخهٔ runtime مشخص. افزودن فیلد و rename و singular→repeated رو در هر دو جهت old writer→new reader و new writer→old reader آزمایش کن. توی Avro مقدار default سمت reader و جهت alias رو صریح بنویس؛ nullable بودن به‌تنهایی default نمی‌سازه. توی Protobuf tag رو ثابت نگه دار و فرق binary با JSON رو بسنج: حفظ unknown field در binary round-trip در برابر حذفش در JSON یا کپی field-by-field. برای cardinality نوع scalar و message و packed بودن رو مشخص کن و فقط به parse موفق بسنده نکن — باید همهٔ مقدارها چک بشن. مسیر امن رو با فیلد و tag تازه و دورهٔ dual-read و dual-write و آزمون rollback طراحی کن؛ معیار قبولی «حفظ معنا»ست.

Write Avro and Protobuf user-profile schemas with named runtime versions. Test field addition, rename, and singular→repeated in both old-writer→new-reader and new-writer→old-reader directions. In Avro, state the reader default and the alias direction explicitly — nullable alone gives you no default. In Protobuf, keep tags fixed and compare binary with JSON: unknown-field preservation in a binary round-trip versus dropping it in JSON or field-by-field copies. For cardinality, pin down the scalar/message type and packed encoding, and don't stop at successful parsing — verify every value. Design the safe path with a new field and new tag, a dual-read/dual-write window, and rollback tests. Semantic preservation is the acceptance bar.
