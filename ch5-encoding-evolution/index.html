ایدهٔ کلیدی فصلChapter thesis

تصور کن داده می‌خواد از حافظهٔ برنامه بزنه بیرون — بره روی دیسک یا توی شبکه. باید بشه بایت. نگران نشو، دعوای این فصل سر «چطور بایت کنیم» نیست؛ سر اینه: وقتی قالب عوض شد، نسخهٔ قدیمی و جدید چطور هنوز همدیگه رو بفهمن؟ یادت باشه قالب عوض می‌شه، داده می‌مونه.

مثال فنی: رکورد قدیمی زیر کد جدید

وضعیت اولیه: فرض کن نسخهٔ ۱ فقط رکورد {name: "Sara"} رو نوشته، بعد نسخهٔ ۲ اومده یه فیلد email هم اضافه کرده.

اجرای مرحله‌به‌مرحله: حالا خوانندهٔ جدید باید بلد باشه رکورد قدیمیِ بدون email رو بخوره؛ خوانندهٔ قدیمی هم نباید با دیدن فیلد جدید قاطی کنه، فقط تحملش کنه.

نتیجه و دلیل: یادت باشه تست واقعی هر دو جهت رو می‌خواد؛ اینکه کد جدید با خودش حرف بزنه که هنر نیست.

یادت باشه مثال‌های این فصل همشون تمرینی‌ان، از دل کار روزمره. عددها رو جدی نگیر، فقط برای فهم‌اند؛ مال هیچ شرکت خاصی نیستن. نکتهٔ ماندگار: مثال را بخوان، قرارداد را یاد بگیر.

Whenever data crosses a process boundary — written to disk, sent over the network, or handed to the next version of the program itself — it must be encoded from “in-memory structures” into a sequence of bytes. This chapter isn’t about the details of that conversion; it’s about its architectural consequences: if you change the byte layout, who can no longer read the data?

یادت باشه deploy تو سیستم بزرگ یهویی نیست؛ تدریجی است (rolling upgrade)، تیکه‌تیکه میاد بالا. کلاینت‌ها رو هم نمی‌تونی مجبور کنی آپدیت کنن. پس تصور کن نسخهٔ قدیمی و جدیدِ کد هم‌زمان دارن کار می‌کنن، دادهٔ قدیمی و جدید هم قاطیِ همن. پس هر قالب باید هم backward باشه (کد جدید، دادهٔ قدیمی رو ببلعه) و هم forward (کد قدیمی با دیدن دادهٔ جدید نترکه). نکتهٔ ماندگار: وسط آپدیت همه‌چیز قاطیه، قالب باید هر دو طرف را نگه دارد.

Because deploys in large systems are gradual (rolling upgrades) and clients can’t be forced to update, old and new versions of the code run side by side while old and new data sit next to each other. So every data format must be both backward compatible (new code reads old data) and forward compatible (old code doesn’t destroy new data).

یادت باشه این فصل دو تیکهٔ مشخص داره:

This chapter has two distinct halves:

  • نیمهٔ اول — قالب‌های کدگذاری: تصور کن از قالب مخصوص خود زبون شروع می‌کنی (مثل java.io.Serializable)، می‌رسی به JSON/XML/CSV، بعد می‌رسی به باینری‌های schemaدار مثل Protocol Buffers و Avro. یادت باشه هر کدوم قلق تکامل (schema evolution) خودشون رو دارن. نکتهٔ ماندگار: اسم قالب عوض بشه، قواعد بازی هم عوض می‌شه.
  • نیمهٔ دوم — حالت‌های جریان داده (modes of dataflow): داده بین processها چطور می‌چرخه؟ با پایگاه داده (نوشتن یعنی پیام دادن به خود آینده‌ات)، با سرویس‌ها (REST/RPC)، با workflow engine‌ها (اجرای پایدار)، یا با message broker و actorها (معماری event-driven). نگران نشو، هر مسیر ترکیب خودش از backward/forward رو می‌خواد. نکتهٔ ماندگار: مسیر عوض بشه، مدل سازگاری هم عوض می‌شه.
  • First half — encoding formats: from language-native formats (like java.io.Serializable) through JSON/XML/CSV to schema-driven binary formats like Protocol Buffers and Avro. Each has different schema-evolution rules.
  • Second half — dataflow modes: how does data move between processes? Via a database (writing = messaging your future self), via services (REST/RPC), via workflow engines (durable execution), or via a message broker and actors (event-driven architecture). Each mode needs a different mix of backward/forward compatibility.
نکتهٔ مصاحبهInterview tip
یادت باشه جملهٔ طلایی این فصل اینه: «data outlives code» — کد تو چند دقیقه deploy می‌شه و میره، ولی دادهٔ پنج‌ساله هنوز با همون فرمت روز اول رو دیسکه. پس هر انتخاب قالب یه تعهد بلندمدته، خیلی بلندتر از عمر هر نسخهٔ کد. نکتهٔ ماندگار: کد میره، داده می‌مونه.

This chapter’s golden line: “data outlives code” — code deploys in minutes, but five-year-old data still sits on disk in its day-one format. Every data-format decision is a longer-term commitment than any code version’s lifetime.

۱1encode و decodeEncoding and decoding

تصور کن encoding یعنی دادهٔ توی برنامه رو بکنی بایت که بشه ذخیره یا ارسالش کرد. decode هم همون بایت‌ها رو برمی‌گردونه به دادهٔ به‌دردبخور. یادت باشه این ربطی به رمزنگاری امنیتی نداره؛ قاطیشون نکن. نکتهٔ ماندگار: encode می‌بره، decode برمی‌گردونه.

مثال فنی: شیء با بایت فرق دارد

وضعیت اولیه: تصور کن برنامه‌ات یه شیء تو حافظه داره با user_id=17 و name=Sara.

اجرای مرحله‌به‌مرحله: حالا encoder می‌بردش سمت بایت‌ها، decoder هم با همون قواعد قالب برش می‌گردونه سر جاش.

نتیجه و دلیل: نگران نشو، pointer و کلاسِ زبون خودش قرارداد نیست؛ یادت باشه قالب باید بگه هر فیلد یعنی چی.

Programs hold data in two shapes:

  • درون حافظه: تصور کن object، struct، لیست، آرایه، hash table، درخت — چیزایی که برای سرعت CPU (معمولاً با pointer) ردیفن.
  • روی دیسک / شبکه: باید دنباله‌ای خوداتکا از بایت‌ها باشه (مثل یه سند JSON)؛ چون pointer برای process دیگه هیچ معنایی نداره. نکتهٔ ماندگار: pointer از درِ process بیرون نمی‌ره.
  • In memory: objects, structs, lists, arrays, hash tables, trees — structures optimized for fast CPU access (usually with pointers).
  • On disk / network: must be a self-contained byte sequence (like one JSON document); a pointer means nothing to another process.
تصور کن از حافظه به بایت رفتن می‌شه encoding (اسم‌های دیگه‌ش: serialization یا marshaling). برگشتنش می‌شه decoding (parsing، deserialization یا unmarshaling). یادت باشه فقط اسم‌ها قلمبه‌ان، کار یکیه. نکتهٔ ماندگار: رفت می‌شه encode، برگشت می‌شه decode.

Translating from the in-memory representation to bytes is encoding (common synonyms: serialization, marshaling); the reverse is decoding (parsing, deserialization, unmarshaling).

دامِ اصطلاحTerminology trap
یادت باشه واژهٔ serialization تو بحث تراکنش‌ها (فصل ۸) یه معنای کاملاً متفاوت داره (ترتیب‌پذیری اجرا). کتاب برای اینکه قاطی نکنی، همه‌جا می‌گه encoding. نکتهٔ ماندگار: یه کلمه، دو دنیا؛ تو این فصل فقط encoding بگو.

The word serialization means something completely different in transaction discussions (Chapter 8: execution orderability). To avoid ambiguity, the book says encoding everywhere.

  • تصور کن گاهی encode/decode اصلاً لازم نیست: مثلاً موتوری که مستقیم روی دادهٔ فشردهٔ خونده‌شده از دیسک کار می‌کنه (بخش Query Execution در فصل ۴)، یا قالب‌های zero-copy مثل Cap'n Proto و FlatBuffers که همون بایت‌ها هم نمای اجراان هم نمای ذخیره، دیگه تبدیلی تو کار نیست.
  • ولی نگران نشو، اکثر سیستم‌ها این تبدیل بین آبجکت توی حافظه و رشتهٔ بایت رو می‌خوان — و انتخاب قالب فقط بحث اندازه و سرعت نیست؛ بحثِ تکامل‌پذیری است. نکتهٔ ماندگار: قالب خوب قالبیه که با تغییر نمی‌ترکه.
  • Sometimes no encode/decode is needed: e.g. an engine working directly on compressed data read from disk (the Query Execution part of Chapter 4), or zero-copy formats like Cap’n Proto and FlatBuffers where the same bytes are both the execution and the storage view, with no separate conversion.
  • But most systems must convert between in-memory objects and byte sequences — and the format choice isn’t just about size and speed; it’s about evolvability.

۲2سازگاری و ارتقای تدریجیCompatibility and gradual upgrades

تصور کن وسط rolling upgrade هستی: کد قدیم و جدید هم‌زمان دارن کار می‌کنن. یادت باشه backward یعنی کد جدید بتونه دادهٔ قدیم رو بخونه. forward یعنی کد قدیم بتونه با دادهٔ جدید طبق قرارداد کنار بیاد.

مثال فنی: چهار ترکیب در rolling upgrade

وضعیت اولیه: تصور کن نصف سرورها هنوز نسخهٔ ۱‌ان، نصف دیگه رفتن روی نسخهٔ ۲.

اجرای مرحله‌به‌مرحله: اول نسخهٔ ۲ رکورد قدیمی رو می‌خونه و حالشو می‌بره؛ بعد نوبت نسخهٔ ۱ـه که یه رکورد دست‌نویس نسخهٔ ۲ دستش می‌رسه.

نتیجه و دلیل: تهش اینه: backward یعنی جدید قدیمی رو بخونه، forward یعنی قدیمی جدید رو نگه داره. rolling upgrade هر دو رو هم‌زمان می‌خواد، قاطی نکن.

Changes in program features usually mean changes in the data it stores: a fresh field, a fresh record type, or a fresh rendering of old data. But code never changes in one instant:

  • در سمت سرور: با rolling upgrade (یا staged rollout) میری جلو. نسخهٔ جدید رو nodeبه‌node deploy می‌کنی، پایش می‌کنی، بعد میری سراغ بعدی. downtime نداری؛ با ریلیزهای کوچیک و پشت‌سرهم.
  • در سمت کلاینت: کاربر حال نداره اپ رو آپدیت کنه؛ ماه‌ها با نسخهٔ قدیمی می‌مونه. این تیکه دیگه دست تو نیست.
  • Server side: rolling upgrades (or staged rollouts) — the new version deploys node by node, gets monitored, and moves on. No downtime, with small frequent releases.
  • Client side: users may not update the app for a long time; that timing is out of your hands.
پس چاره‌ای نیست: کد قدیم و جدید و دادهٔ قدیم و جدید باید یه مدت کنار هم زندگی کنن:

So old and new versions of the code and old and new versions of the data formats must live side by side:

در APIها دقیقاً چه چیزی سازگار می‌خواهد؟What exactly needs compatibility in APIs?
تصور کن کلاینت قدیمی داره سرویس جدید رو صدا می‌زنه: روی request سازگاری backward می‌خوای، روی response سازگاری forward. اگه کلاینت جدید با سرویس قدیمی حرف بزنه، برعکس. یادت باشه backward معمولاً راحته چون فرمت قدیم رو می‌شناسی؛ forward سخت‌تره چون کد قدیم باید چیز ناشناخته رو بی‌صدا رد کنه ولی نگهش داره.

If an old client must call a new service: requests need backward compatibility, responses need forward compatibility. A new client talking to an old service is the mirror image. Backward is usually easy (you know the old format); forward is harder since old code must silently set aside unknown things.

تصور کن سه نفر از چپ به راست نشستن: «Service v2.2» (زیرنویس: «new code, new field» — همون کد جدید)، وسط «Record Store» (زیرنویس: «shared database»)، و سمت راست «Service v2.1» (زیرنویس: «old code still live» — همون قدیمی که هنوز زنده‌ست). زمان از بالا به پایین میره و سه نوار عنوان سمت چپ، سه پردهٔ داستان رو از هم جدا می‌کنن.

Three participants, left to right: Service v2.2 (new code, new field), Record Store (shared database), and Service v2.1 (old code still live). Time flows downward through three titled bands.

پردهٔ اول، «Rolling upgrade»: فلش پررنگ «write record with new field» از v2.2 میره سمت Record Store. بعد فلش معمولی «read record» از v2.1 میاد (یادت باشه وسط rolling upgrade نود قدیمی هنوز داره سرویس میده) و جواب برمی‌گرده: «record incl. unknown field» — یعنی رکورد با فیلد ناشناخته افتاده دست کد قدیمی.

Act one, Rolling upgrade: bold write record with new field from v2.2 to the store; then plain read record from v2.1 (during gradual rollout the old node still serves) with the reply record incl. unknown field — the unknown-field record in old code’s hands.

پردهٔ دوم، «Unknown-field hazard»: فلش پررنگ «update known fields, write back» از v2.1 میره سمت Store — و یادداشت زیر همون فلش میگه «decoded into a plain model object» (رکورد توی یه آبجکت ساده decode شده که فیلد ناشناخته رو نگه نمی‌داره). بعد v2.2 دوباره می‌خونه («read record again») و جواب تلخه: «new field gone — data lost» با یادداشت «unknown field was not preserved». این همون گم‌شدن بی‌صدای شکل ۵-۱ـه.

Act two, Unknown-field hazard: bold update known fields, write back from v2.1 to the store — annotated decoded into a plain model object (the record decoded into a plain object that keeps no unknown field). v2.2 reads again (read record again) and the reply is bitter: new field gone — data lost (unknown field was not preserved). That is Figure 5-1’s silent loss.

پردهٔ سوم، «Preserving unknown fields»: فلش چین‌چین «write record with field tag 4» — یعنی رکورد با شمارهٔ تگ فیلد کد شده، نه با اسم. این‌بار کد قدیم رکورد رو round-trip می‌کنه («old code round-trips the record») و جواب خبر خوبه: «field tag 4 still intact». فیلد سر جاشه.

Act three, Preserving unknown fields: the dashed write record with field tag 4 — the record encoded with a field tag number, not a name. Old code round-trips the record (old code round-trips the record) and this time the reply is good news: field tag 4 still intact.

درس شکل چیه؟ مشکل از «قدیمی بودن کد» نیست؛ مشکل از قرارداد decoderـه. قالب‌های schemaدار (مثل Protocol Buffers و Avro) به کد قدیم میگن: چیز ناشناخته رو نادیده بگیر ولی بایت‌هاش رو دست‌نخورده نگه دار. همین یه جمله نجاتت میده.

The lesson: the problem isn’t “old code”; it’s the decoder contract. Schema-driven formats (like Protocol Buffers and Avro) tell old code to ignore unknown things but keep their bytes untouched.

قالب تبادل یعنی: داده رو چطور بنویسی که خواننده هم بفهمه ساختارش چیه. انتخابت مستقیم می‌زنه به حجم، خوانایی، حرف زدن زبان‌های مختلف با هم، و اینکه بعداً بتونی عوضش کنی یا نه.

مثال فنی: مقایسهٔ قالب روی همان رکورد

وضعیت اولیه: فرض کن همون رکورد user_id=17, active=true رو می‌خوای با چند تا قالب بنویسی.

اجرای مرحله‌به‌مرحله: تصور کن JSON اسم فیلدها رو دونه‌دونه با خودش حمل می‌کنه؛ ولی قالب schemaدار می‌تونه به‌جاش شناسه یا جای فیلد رو بذاره.

نتیجه و دلیل: یادت باشه سیب با سیب مقایسه کن — همون داده، همون کتابخونه؛ باینری بودن به‌تنهایی نه یعنی کم‌حجم‌تر، نه یعنی تکامل بهتر.

Now that we know which compatibilities are needed, what are the options? This part surveys three families: language-native formats, textual formats (JSON/XML/CSV), and schema-driven binary formats (Protocol Buffers and Avro).

۳.۲ قالب‌های ویژهٔ زبان3.2 Language-native formats

قالب‌های مخصوص زبان کارت رو راحت می‌کنن: شیء همون زبان رو تند ذخیره می‌کنی. ولی وقتی پای زبون دیگه یا نسخهٔ جدید وسط باشه، قاطی می‌کنی. تازه بعضی‌هاشون برای ورودی مشکوک خطرناکن.

مثال فنی: نام کلاس، قرارداد پایدار نیست

وضعیت اولیه: فرض کن فایل ذخیره‌شده‌ات به کلاس OldUser نسخهٔ قبلی چسبیده.

اجرای مرحله‌به‌مرحله: حالا نسخهٔ جدید اون کلاس رو پاک کرده یا زبون عوض شده؛ decoder مخصوص اون زبون ممکنه اصلاً نتونه شیء رو بسازه و بترکه.

نتیجه و دلیل: یادت باشه داده از کد بیشتر عمر می‌کنه؛ برای تبادل schema مستقل می‌خوای و ورودی مطمئن.

  • تقریباً همهٔ زبان‌ها کدگذاری داخلی دارن: java.io.Serializable تو Java، pickle تو Python، Marshal تو Ruby و چیزایی مثل Kryo. خوبیشون؟ با دو خط کد object رو ذخیره و برمی‌گردونی.
  • ولی چهار تا مشکل اساسی دارن:
  • قفل زبانی: به یه زبان چسبیدی؛ خوندن داده با زبون دیگه سخته و وصل شدن به سازمان دیگه عملاً نمی‌شه.
  • امنیت: decoder برای ساختن object باید هر classای رو instantiate کنه — مهاجم بایت دلخواه بفرسته، کارت ساخته‌ست: می‌رسه به اجرای کد دلخواه (RCE).
  • نسخه‌بندی فرعی: اینا برای «سریع و راحت» ساخته شدن؛ سازگاری forward/backward براشون مهم نیست.
  • کارایی فرعی: serialization داخلی Java معروفه به کندی و بادکردگی.
  • حرف آخر: جز برای کار خیلی موقتی، سراغ کدگذاری داخلی زبان نرو.
  • Most languages ship a built-in encoding library: java.io.Serializable in Java, pickle in Python, Marshal in Ruby, plus libraries like Kryo. They’re comfortable: store and restore objects with minimal code.
  • But they carry four fundamental problems:
  • Language lock-in: encoding is tied to one language; reading the data in another language is hard, and integrating with other organizations becomes impossible.
  • Security: to rebuild objects the decoder must instantiate arbitrary classes — if an attacker sends arbitrary bytes, arbitrary code execution (RCE) usually follows.
  • Versioning as an afterthought: these libraries are built for “fast and easy” and mostly ignore forward/backward compatibility.
  • Performance as an afterthought: Java’s built-in serialization is famously slow and bloated.
  • Verdict: never use language-internal encoding except for very transient purposes.

۳.۳ JSON، XML، CSV و JSON Schema3.3 JSON, XML, CSV and JSON Schema

JSON و XML اسم فیلد رو با خودشون دارن؛ CSV فقط به درد جدول ساده می‌خوره و ریزه‌کاری‌هاش رو باید با هم توافق کنی. JSON Schema هم می‌تونه بگه type فیلد چیه و اجباریه یا نه.

مثال فنی: شناسهٔ بزرگ در JSON

وضعیت اولیه: فرض کن شناسهٔ 9007199254740993 به‌صورت JSON number می‌رسه دست JavaScript.

اجرای مرحله‌به‌مرحله: نگران نشو اگه دیدی تبدیلش به Number گرد شد به 9007199254740992؛ اگه شناسه رو رشته‌ای قرارداد کنی رقم‌هاش سر جاش می‌مونه.

نتیجه و دلیل: یادت باشه JSON قول دقت به همه نمی‌ده؛ نوع فیلد رو دو طرف شفاف قرارداد کن.

Standard multi-language formats: JSON and XML (plus CSV, which holds only tabular data and doesn’t nest). They’re textual and fairly human-readable, but their problems are real:

  • XML معمولاً حرفش اینه: طولانی و زیادی پیچیده‌ست.
  • ابهام عددها: تو XML و CSV اصلاً نمی‌فهمی این «123» عدده یا رشته (مگر با schema بیرونی). JSON رشته و عدد رو جدا می‌کنه ولی integer و floating-point رو نه، دقت هم معلوم نیست. عدد بزرگ‌تر از 2^53 تو IEEE 754 دقیق نمی‌مونه؛ مثلاً X شناسهٔ ۶۴بیتی هر post رو هم عدد JSON میده هم رشتهٔ متنی، که JavaScript قاطی نکنه.
  • رشتهٔ باینری ندارن: JSON/XML فقط Unicode (متن انسان‌خوان) می‌فهمن، نه بایت خام. راه رایج Base64 ـه که کار رو راه می‌ندازه ولی حجم رو حدود یک‌سوم باد می‌کنه.
  • XML Schema و JSON Schema قوی‌ان و برای همین پیچیده‌ان؛ اگه ازشون استفاده نکنی باید منطق encode/decode رو hardcode کنی.
  • CSV اصلاً schema نداره؛ معنی هر سطر و ستون با خودته و escape کردن ویرگول و خط جدید هم گنگه.
  • با همهٔ این‌ها، برای تبادل بین سازمان‌ها همینا «به‌اندازهٔ کافی خوب»‌ن: تا وقتی دو طرف روی قالب توافق دارن، خوشگلی و سرعت حرف دومه.
  • XML is usually criticized as verbose and over-complex.
  • Number ambiguity: in XML and CSV you can’t tell a number from a numeric string at all (without an external schema). JSON separates strings from numbers but not integers from floats, and pins no precision. Numbers above 2^53 don’t survive IEEE 754 exactly; e.g. X returns each post’s 64-bit id both as a JSON number and as a text string so JavaScript won’t corrupt it.
  • No binary strings: JSON/XML support Unicode (human-readable text), not raw byte sequences. The common workaround is Base64, which roughly works and inflates size by about a third.
  • XML Schema and JSON Schema are powerful and hence complex; programs that skip them must hardcode the encode/decode logic.
  • CSV has no schema at all; the program must define each row and column’s meaning, and escaping commas and newlines is murky.
  • Still, for cross-organization exchange these are “good enough”: as long as both sides agree on the format, beauty and efficiency matter less.
JSON Schema در عملJSON Schema in practice
JSON Schema امروز همه‌جا هست: تو OpenAPI (سرویس‌های وب)، registryهایی مثل Confluent Schema Registry و Apicurio، و دیتابیس‌ها (افزونهٔ pg_jsonschema تو PostgreSQL و $jsonSchema تو MongoDB). به‌جز typeهای پایه (string، number، integer، object، array، boolean، null) قانون اعتبارسنجی هم داره (مثلاً port بین ۱ تا ۶۵۵۳۵).

JSON Schema is common today in OpenAPI (web services), registries like Confluent Schema Registry and Apicurio, and databases (the pg_jsonschema extension in PostgreSQL, $jsonSchema in MongoDB). Beyond base types (string, number, integer, object, array, boolean, null) it has validation rules (e.g. a port between 1 and 65535).

The subtle point: an open vs closed content model. Open (whose default is additionalProperties: true) accepts any undefined field; so JSON Schema usually says what is not allowed rather than what is. The book’s example for a “numeric-key → string-value” map:

JSON Schema شرط if/else، type نام‌دار و ارجاع به schemaهای راه دور هم بلده — قویه، ولی تکامل سازگار باهاش کار سختیه. XML Schema هم همین درد رو داره.

JSON Schema also handles if/else conditions, named types and remote-schema references — powerful, but evolving it compatibly is hard work. XML Schema shares similar concerns.

باینری‌های «JSON» فقط نصفِ راه‌اند“JSON” binaries are only half the road
چیزایی مثل MessagePack، CBOR و BSON همون مدل JSON رو باینری می‌کنن (گاهی با چند type اضافه مثل رشتهٔ باینری). ولی چون schema ندارن، هنوز اسم همهٔ فیلدها تو بایت‌هاست. مثال کتاب: رکورد سه‌فیلدی {"userName": "Martin", "favoriteNumber": 1337, "interests": [...]} با MessagePack میشه ۶۶ بایت در برابر ۸۱ بایت JSON متنی بدون فاصله — یه ذره صرفه‌جویی به قیمت از دست دادن انسان‌خوانی. همین رکورد رو جلوتر با Protocol Buffers (۳۳ بایت) و Avro (۳۲ بایت) می‌بینی.

Formats like MessagePack, CBOR and BSON binarize the same JSON model (sometimes with a few extra types like binary strings). But schema-less, every field name still sits inside the bytes. The book’s example: the three-field record {"userName": "Martin", "favoriteNumber": 1337, "interests": [...]} becomes 66 bytes in MessagePack vs 81 bytes of spaceless textual JSON — a small saving for the loss of human-readability. Ahead we’ll see the same record at 33 bytes (Protocol Buffers) and 32 (Avro).

۳.۴ Protocol Buffers3.4 Protocol Buffers

تو Protocol Buffers هر فیلد یه شماره داره و همین شماره بخشی از هویتشه رو سیم. اسم عوض کردن کجا، شمارهٔ یه فیلد حذف‌شده رو دوباره دادن کجا — قاطیشون نکن.

مثال فنی: Tag هویت فیلد است

وضعیت اولیه: فرض کن تو schema پیامت داری string name = 1، بعد اومدی string email = 2 رو اضافه کردی.

اجرای مرحله‌به‌مرحله: یادت باشه شمارهٔ ۱ همیشه مال name می‌مونه؛ اگه email رو حذف کردی، شمارهٔ ۲ رو نده به یه معنای دیگه.

نتیجه و دلیل: اسم عوض کردن با هویت wire فرق داره؛ reuse شماره یعنی دادهٔ قدیمی رو با معنای اشتباه می‌خونی — تهش می‌ترکه.

Protocol Buffers (protobuf) is Google’s binary encoding library; Apache Thrift (from Facebook) is very similar. Every datum needs a schema — in the IDL language:

syntax = "proto3";

message Person {
  string user_name = 1;
  int64 favorite_number = 2;
  repeated string interests = 3;
}
  • ابزار codegen از این schema تو زبان‌های مختلف class می‌سازه؛ کدت هم همون کد تولیدشده رو صدا می‌زنه. زبون schema خیلی ساده‌تر از JSON Schema ـه: فقط فیلد و type، بدون قانون اعتبارسنجی عجیب.
  • همون رکورد مثال فقط ۳۳ بایت میشه. برخلاف MessagePack، اسم فیلدها تو داده نیست؛ به‌جاش شمارهٔ تگ (tag) میاد: همون ۱ و ۲ و ۳ که تو schema دیدی — یه اسم مستعار جمع‌وجور برای فیلد.
  • نوع فیلد و تگ تو یه بایت جا میشن؛ عددها طول‌متغیر (varint) ـن: ۱۳۷۱ تو دو بایت (بیت بالایی هر بایت یعنی «باز ادامه داره»). عددهای −64..63 تو یه بایت و −8192..8191 تو دو بایت جا میشن.
  • لیست صریح نداره؛ repeated میگه فیلد چندمقداریه و تو بایت‌ها تکرار همون تگ یعنی آیتم‌ها.
  • The codegen tool builds classes in many languages from this schema; application code calls into that generated code. The schema language is far simpler than JSON Schema: just fields and types, no complex validation rules.
  • Encoding the same example record takes only 33 bytes. Unlike MessagePack, field names aren’t in the data; instead come tag numbers: the 1, 2, 3 you saw in the schema — a compact alias for each field.
  • A field’s type and tag fit in one byte; numbers are variable-length (varint): 1337 fits in two bytes (each byte’s top bit means “more follows”). Numbers −64..63 fit in one byte, −8192..8191 in two.
  • There is no explicit list; repeated marks a multi-valued field, and in the bytes, repeating the same tag represents the items.

  • رکورد کدشده فقط چسبوندن فیلدهای کدشده‌ست؛ فیلدی که set نشده اصلاً نوشته نمیشه. پس تگ‌ها معنی داده رو می‌سازن.
  • اسم فیلد رو راحت عوض کن (اسم تو داده نیست)؛ ولی تگ رو دست نزن — همهٔ داده‌های موجود می‌ترکه.
  • فیلد جدید با تگ تازه = forward compatible: کد قدیمی تگ ناشناس رو نادیده می‌گیره و (اگه درست پیاده شده باشه) بایت‌هاش رو نگه می‌داره. backward هم اوکیه چون دادهٔ قدیمی برای فیلد تازه مقدار پیش‌فرض می‌گیره.
  • حذف فیلد آینهٔ اضافه کردنه: تگ قدیمی رو هیچ‌وقت دوباره استفاده نکن (هنوز داده با اون تگ نوشته شده)؛ می‌تونی تگ‌های بازنشسته رو تو schema reserve کنی.
  • عوض کردن type فیلد برای بعضی typeها میشه ولی خطر truncation داره: ۳۲بیتی ← ۶۴بیتی برای کد جدید راحته، ولی کد قدیمی مقدار ۶۴بیتی رو می‌ریزه تو متغیر ۳۲بیتی و می‌بُره.
  • An encoded record is just concatenated encoded fields; an unset field is never written. So tags make the data’s meaning.
  • Renaming a field is free (names aren’t in the data); changing a tag is forbidden — all existing data becomes invalid.
  • Adding a field with a fresh tag = forward compatible: old code skips unknown tags and (if implemented right) preserves their bytes. Backward holds too, since old data takes the default for the fresh field.
  • Removing a field mirrors adding: the old tag must never be reused (data is still written with it); retired tags can be reserved in the schema.
  • Changing a field’s type is possible for some types but risks truncation: 32-bit → 64-bit is easy for new code, but old code pours a 64-bit value into a 32-bit variable and clips it.

۳.۵ Avro + نمودار ۳3.5 Avro + Diagram 3

تو Avro موقع خوندن، schema نویسنده و خواننده میان کنار هم تا داده معنی بشه. اسم فیلدها، قواعد سازگاری و مقدار پیش‌فرض، موقع تغییر ساختار حرف اول رو می‌زنن.

مثال فنی: Resolution در Avro

وضعیت اولیه: فرض کن writer فقط name داره، reader جدید اومده یه فیلد country با default مساوی IR اضافه کرده.

اجرای مرحله‌به‌مرحله: حالا وقتی رکورد قدیمی رو می‌خونی، reader مقدار گمشدهٔ country رو از default برمی‌داره.

نتیجه و دلیل: یادت باشه default فقط جای خالی writer رو پر می‌کنه؛ به‌جای نوشتن اجباری تو schema نویسنده نمی‌شینه.

Apache Avro (since 2009, a Hadoop subproject) differs from protobuf in interesting ways. It has two schema languages: Avro IDL for humans and a JSON rendering for machines. Example:

record Person {
  string userName;
  union { null, long } favoriteNumber = null;
  array<string> interests;
}
  • اینجا هیچ tagای در کار نیست. همون رکورد فقط ۳۲ بایت میشه — جمع‌وجورترین همه. تو بایت‌ها نه اسم فیلد هست نه type؛ فقط مقدارهای چسبیده به هم (رشته = طول + بایت‌های UTF-8). درست decode کردن فقط با دقیقاً همون schemaای که باهاش نوشتی ممکنه.
  • پس موقع خوندن با دو تا schema کار داری: writer's schema (همونی که موقع نوشتن بوده) و reader's schema (همونی که کد فعلی می‌خواد). Avro با مقایسهٔ این دو تا، داده رو از دید writer به دید reader ترجمه می‌کنه.
  • No tag numbers at all. Encoding the same record takes only 32 bytes — the most compact of all. The bytes hold neither field names nor data types; just concatenated values (a string = length + UTF-8 bytes). Correct decoding is possible only with exactly the schema used at write time.
  • So at read time the program works with two schemas: the writer’s schema (the one at write time) and the reader’s schema (what current code expects). Avro translates the data from the writer’s view to the reader’s view by comparing the two.

قواعد resolution (فرمولِ شکل ۵-۶ کتاب)Resolution rules (the book’s Figure 5-6 formula)

خواننده باید داده‌ای که با schema قبلی نوشته شده رو با قواعد سازگاری به schema خودش نگاشت کنه؛ مقدار پیش‌فرض برای فیلد غایب به کار میاد.

مثال فنی: فیلد اضافی و فیلد غایب

وضعیت اولیه: فرض کن writer فیلدهای name, age رو داره ولی reader فقط name, country می‌خواد.

اجرای مرحله‌به‌مرحله: تصور کن age به کار reader نمیاد پس می‌ره کنار؛ ولی country باید default معتبر داشته باشه وگرنه resolution می‌ترکه.

نتیجه و دلیل: «نسخه‌ها فرق دارن» همیشه حل‌شدنی نیست؛ این قواعد schemaست که می‌گه خوندن آزاده یا نه.

  • فیلدها با اسم جفت میشن؛ ترتیبشون مهم نیست.
  • فیلد تو writer هست ولی تو reader نه ← می‌ره کنار.
  • فیلدی که reader می‌خواد ولی writer ننوشته ← با مقدار پیش‌فرض reader پر میشه.
  • برای سازگاری فقط فیلد defaultدار رو می‌تونی اضافه یا حذف کنی. اضافه کردن فیلد بدون default ← backward می‌ترکه؛ حذف فیلد بدون default ← forward.
  • تو Avro، null پیش‌فرض همه‌چیز نیست: برای nullable باید union { null, ... } بنویسی و فقط وقتی می‌تونی default رو null بذاری که null شاخهٔ اول union باشه.
  • عوض کردن اسم فیلد با alias تو reader's schema میشه → backward هست ولی forward نیست. اضافه کردن شاخه به union هم فقط backward ـه.
  • Fields pair by name; field order doesn’t matter.
  • A field present in the writer but not the reader is ignored.
  • A field the reader expects but the writer never wrote is filled with the reader’s default.
  • For compatibility you may only add or remove a field with a default. Adding a default-less field breaks backward; removing one breaks forward.
  • In Avro, null isn’t everything’s default: for nullability you must write union { null, ... }, and you may default to null only when null is the union’s first branch.
  • Renaming a field is possible with an alias in the reader’s schema → backward yes, but not forward. Adding a union branch is backward-only too.

اما writer's schema را از کجا بیاوریم؟But where do we get the writer’s schema?

برای درست فهمیدن داده باید schema نویسنده دم دست باشه؛ یا تو خود فایله یا با یه شناسه تو schema registry معرفیش می‌کنی.

مثال فنی: پیدا کردن schema نویسنده

وضعیت اولیه: فرض کن پیام Avro یه شناسهٔ schema مساوی 23 داره به‌علاوه بایت‌های رکورد.

اجرای مرحله‌به‌مرحله: حالا مصرف‌کننده می‌ره schema شماره ۲۳ رو از registry برمی‌داره و می‌ذاره کنار reader schema جلوی decoder.

نتیجه و دلیل: یادت باشه فقط reader schema کافی نیست؛ شناسه رو نگه دار و schemaهای قدیمی رو دور ننداز.

The lesson: reading data in Avro means translating between two schemas, not just decoding bytes. And the two golden resolution rules sit in the last tag: extras ignored and defaults filled in.

۳.۶ مزایای schema و اسکیماهای پویا3.6 Schema benefits and dynamic schemas

schema میگه شکل و معنی داده چیه. فقط داشتن فایل schema کافی نیست؛ باید نسخه‌ها، قواعد تغییر و اینکه خواننده به ساختار درست برسه رو هم مدیریت کنی.

مثال فنی: قرارداد پیش از ورود داده

وضعیت اولیه: فرض کن پیام ورودی فیلد age رو با متن old فرستاده، ولی قراردادت عدد می‌خواد.

اجرای مرحله‌به‌مرحله: تصور کن validation همون‌جا پیام رو رد یا قرنطینه می‌کنه و خطا رو ثبت می‌کنه؛ فقط کلاس ساختن از schema کافی نیست.

نتیجه و دلیل: schema اختلاف نوع رو زود لو می‌ده؛ ولی سن منفی و این حرف‌ها کنترل جدا می‌خواد — قاطیشون نکن.

  • schema پویا با Avro راحت‌تره: چون tag تو schema نیست، می‌تونی مستقیم از schema رابطه‌ای Avro schema بسازی (هر جدول ← یه record، هر ستون ← یه فیلد) و dump کامل دیتابیس رو بنویسی. اگه schema دیتابیس عوض شد، همون مبدل رو دوباره اجرا می‌کنی؛ چون فیلدها با اسم شناخته میشن، reader's schema قدیمی هنوز جفت میشه. تو protobuf باید tagها رو دستی بدی و حواست باشه tag تکراری نره.
  • قالب‌های باینری schemaدار چند تا برد بزرگ دارن: از «JSONهای باینری» جمع‌وجورترن (اسم فیلدها حذف میشه)؛ خود schema سند زنده‌ست (برخلاف داک دستی، همیشه به‌روزه چون برای decode لازمه)؛ با نگه داشتن registry می‌تونی سازگاری تغییر رو قبل از deploy چک کنی؛ و برای زبان‌های statically typed کد می‌سازه (چک type تو compile-time).
  • این ایده‌ها جدید نیستن: ASN.1 از ۱۹۸۴ با tag تکامل schema داشت (هنوز تو گواهی‌های SSL/X.509 با کدگذاری DER استفاده میشه) ولی پیچیده و بدمستنده. بیشتر دیتابیس‌های رابطه‌ای هم پروتکل باینری خودشون رو دارن که driver (JDBC/ODBC) بازش می‌کنه.
  • قانون عملی: تعداد قالب‌های هم‌زمان تو سیستم رو کم نگه دار؛ هر قالب اضافه یعنی دردسر بیشتر برای نگه داشتن سازگاری.
  • Dynamic schemas are easier with Avro: with no tags in the schema you can generate an Avro schema straight from a relational schema (each table → one record, each column → one field) and write a full database dump. If the database schema changes, re-run the same converter; since fields are known by name, the old reader’s schema still pairs up. In protobuf you must allocate tags by hand and watch none get reused.
  • Schema-driven binary formats carry big wins: denser than “JSON binaries” (field names drop out); the schema itself is living documentation (unlike hand docs, always current since decoding needs it); with a registry you can test a change’s compatibility before deploy; and they generate code for statically typed languages (compile-time type checks).
  • These ideas aren’t new: ASN.1 has had tag-based schema evolution since 1984 (still used in SSL/X.509 certificates with DER encoding) but is complex and badly documented. Most relational databases also have their own proprietary binary protocol that the driver (JDBC/ODBC) decodes.
  • Practical rule: keep the number of simultaneous formats in the system small; each extra format means more work keeping compatibility.

وضعیت اولیه: فرض کن می‌خوای از full_name بری به given_name, family_name.

اجرای مرحله‌به‌مرحله: اول خواننده‌ها رو کاری کن هر دو شکل رو بخورن؛ بعد writerها رو یکی‌یکی عوض کن؛ حذف نهایی فقط وقتیه که مصرف‌کننده و دادهٔ قدیمی پوشش داده شدن.

نتیجه و دلیل: یادت باشه حذف فیلد فقط دست بردن تو یه فایل schema نیست؛ عمر داده و همه readerها جزئی از مهاجرتن.

So far we’ve seen how writer’s and reader’s schemas get along via resolution rules: the writer’s extra field is ignored, the writer’s missing field is filled with the reader’s default. But these rules only save us if schema change arrives step by step: in a live system, during a rolling upgrade old and new code versions run side by side for hours or days, and every message must stay readable to both. So “adding one field” isn’t one deploy; it’s a multi-stage cycle, each step guaranteeing one compatibility.

قانون طلایی این چرخه readers first ـه: اول کدی رو deploy کن که فیلد تازه رو می‌خونه و اگه نبود تحملش می‌کنه، بعد کدی که می‌نویستش. مفت‌ترین تغییر، اضافه کردن فیلد اختیاری با مقدار پیش‌فرض ـه — تو Avro یعنی union { null, ... } با default مناسب — چون خوانندهٔ قدیمی نادیده‌ش می‌گیره و خوانندهٔ جدید با پیش‌فرض خودش پرش می‌کنه. ولی عوض کردن اسم یا type یه فیلد یعنی «حذف + اضافه»: اگه یه‌ضرب انجامش بدی، یکی از دو سازگاری backward/forward می‌ترکه.

This cycle’s golden rule is readers first: first deploy code that reads the fresh field and tolerates its absence, then code that writes it. The cheapest changes add an optional field with a default — in Avro a union { null, ... } with a proper default — since old readers ignore it and new readers fill it with their own default. But renaming or retyping a field equals “delete + add”: done in one step, one of the two backward/forward compatibilities breaks.

چرا حذف همیشه آخره؟ چون داده از کد بیشتر عمر می‌کنه: پیام‌های قدیمی مونده تو صف‌ها، backupها و فایل‌های آرشیوی برای همیشه با همون schema قدیمی می‌مونن. پس اول نوشتن فیلد رو متوقف می‌کنی (deprecated) ولی خواننده‌ها هنوز باید رکوردهای دارای اون رو بخونن، و فقط وقتی هیچ خواننده‌ای بهش نیاز نداشت از schema حذفش می‌کنی. نمودار ۶ همین چرخه رو مثل یه state machine کشیده: پنج حالت اصلی فیلد، دو «دروازهٔ سازگاری» برای تصمیم‌های سخت، و یه بن‌بست برای وقتی که ترتیب رو اشتباه رفتی.

And why is deletion always the last step? Because data outlives code: old messages stuck in queues, backups and archive files keep their old schema forever. So first stop writing the field (deprecated) while readers must still read records containing it, and only drop it from the schema once no reader needs it. اجرای مرحله‌به‌مرحله: اول خواننده‌ها رو کاری کن هر دو شکل رو بخورن؛ بعد writerها رو یکی‌یکی عوض کن؛ حذف نهایی فقط وقتیه که مصرف‌کننده و دادهٔ قدیمی پوشش داده شدن.

The diagram has three horizontal lanes, top to bottom: Field states (a field’s life), Compatibility gates (compatibility decision gates), Terminal (dead end). The top lane’s five states are numbered 01–05 and form a field’s normal life; the middle lane’s two diamonds are gates, the bottom lane’s red state the failure destination.

از چپ نوار بالا شروع کن: «Proposed» (قدم «01») با زیرنویس «schema change drafted» و برچسب «not deployed» — یعنی تغییر هنوز فقط رو کاغذه و به هیچ سروری نرسیده. فلش پررنگ «deploy readers first» می‌بردت به «Added Optional» (قدم «02») — زیرنویس «new field, default or null» و برچسب «writers may omit it»: فیلد تو schema هست و خواننده‌ها تحملش می‌کنن، ولی هنوز هیچ writerای پرش نمی‌کنه. فلش بعدی، «writers fill it»، می‌رسه به «In Use» (قدم «03») — زیرنویس «new writers fill it» و برچسب «old readers ignore it» — تنها حالت از این پنج‌تا که فیلد واقعاً داده حمل می‌کنه.

Start left on the top lane: Proposed (step 01; schema change drafted; not deployed) — the change is still only on paper. The bold deploy readers first leads to Added Optional (step 02; new field, default or null; writers may omit it): the field is in the schema and readers tolerate it, but no writer fills it yet. Next, writers fill it reaches In Use (step 03; new writers fill it; old readers ignore it) — the only one of the five where the field really carries data.

از اینجا داستان جمع کردنه. فلش «stop writing it» میره به «Deprecated» (قدم «04») — زیرنویس «no new writes» و برچسب «readers still tolerate it»: نوشتن تازه وایساده، ولی رکوردهای قدیمی هنوز فیلد رو دارن و خواننده‌ها باید همونا رو بخونن. آخرش فلش «drop the field» می‌رسه به «Removed» (قدم «05») — زیرنویس «gone from the schema» و برچسب خیال‌راحت‌کن «safe to drop». حواست باشه این پنج قدم فقط به همین ترتیب امن‌ان؛ اگه ترتیب رو جابه‌جا کنی، یکی از دو دروازهٔ نوار میانی باید «بله» بده.

From here it’s the winding-down story. stop writing it goes to Deprecated (step 04; no new writes; readers still tolerate it): fresh writes stop, but old records still carry the field and readers must keep reading them. Finally drop the field reaches Removed (step 05; gone from the schema; reassuringly safe to drop). These five steps are only safe in this order; any reordering must pass one of the middle lane’s two gates.

حالا دروازه‌ها. از «Added Optional» فلش چین‌چین «need it now?» میاد پایین به نوار «Compatibility gates»: لوزی «All Writers Upgraded?» با زیرنویس «old code still running» و برچسب «gate». اگه همهٔ writerها بالا رفته باشن، فلش «yes, all upgraded» مستقیم برمی‌گرده به «In Use» — یعنی نوشتن فیلد فقط بعد از رد شدن از این دروازه شروع میشه. ولی اگه نسخهٔ قدیمی هنوز داره کار می‌کنه، فلش قرمز «no, mixed fleet» میره به نوار «Terminal»: «Breaking Change» با زیرنویس «old code crashes or drops data» و برچسب «roll back» — یعنی یا کد قدیمی می‌ترکه یا داده رو قورت میده، و تنها راه برگردوندن deploy ـه.

Now the gates. From Added Optional the dashed need it now? descends to the Compatibility gates lane: the diamond All Writers Upgraded? (old code still running; gate). If all writers are up, yes, all upgraded returns straight to In Use — writing the field starts only past this gate. But if an old version still runs, the red no, mixed fleet drops to the Terminal lane: Breaking Change (old code crashes or drops data; roll back) — either old code breaks or it swallows data, and the only way out is rolling the deploy back.

دروازهٔ دوم سمت راست همون نواره: از «Deprecated» فلش چین‌چین «can we drop it?» میاد پایین به «All Readers Upgraded?» با زیرنویس «ignore unknown fields» و برچسب «gate». جواب مثبت — فلش «yes, all upgraded» — فیلد رو می‌رسونه به «Removed»؛ ولی جواب منفی — فلش «not yet» — برمی‌گرده به خود «Deprecated»: حلقه‌ای که ممکنه هفته‌ها و ماه‌ها بچرخه تا آخرین خواننده‌ای که هنوز به فیلد نیاز داره بازنشسته بشه. حذف فیلد فقط وقتی «safe to drop» ـه که این دروازه برای همیشه بسته شده باشه.

The second gate sits right on the same lane: from Deprecated the dashed can we drop it? descends to All Readers Upgraded? (ignore unknown fields; gate). A yes — yes, all upgraded — carries the field to Removed; a no — not yet — loops right back to Deprecated: a loop that may repeat for weeks and months until the last reader still needing the field retires. Dropping is safe to drop only once this gate closes for good.

درس اول شکل رو تو یه ترتیب جمع کن: readers first، writers second، drop last. اول کد خواننده رو ببر بالا که فیلد ناشناس رو تحمل کنه، بعد کد نویسنده رو که فیلد رو پر کنه، و حذف رو فقط آخر کار و بعد از هر دو دروازه انجام بده. تو یه rolling upgrade واقعی یعنی deployها رو باید با همین ترتیب بچینی: نسخه‌ای که فقط «می‌خونه» همیشه امنه، نسخه‌ای که «می‌نویسه» فقط بعد از اون.

Sum the figure’s first lesson into one order: readers first, writers second, drop last. First raise reader code to tolerate the unknown field, then writer code to fill it, and delete only at the very end, past both gates. In a real rolling upgrade that means scheduling deploys in exactly this order: a version that only “reads” is always safe; one that “writes” only after it.

و درس دوم: داده از کد بیشتر عمر می‌کنه، و هر تغییر «به‌ظاهر کوچیک» ممکنه لباس «حذف + اضافه» تنش باشه — عوض کردن اسم فیلد، عوض کردن type، یا حتی عوض کردن مقدار پیش‌فرض. قیمت به‌هم ریختن ترتیب همون یه فلش قرمز «no, mixed fleet» ـه: «Breaking Change» و بعد «roll back». اگه هر تغییر schema رو با همین پنج قدم و دو دروازه بسنجی، deploy بدون downtime دیگه شانس نیست؛ نتیجهٔ منطقی ترتیب درسته.

And the second lesson: data outlives code, and every “seemingly small” change may wear a “delete + add” costume — renaming a field, retyping it, even changing its default. The price of scrambling the order is that one red arrow no, mixed fleet: Breaking Change, then roll back. Weigh every schema change against these five steps and two gates, and downtime-free deploy stops being luck — it becomes the logical result of the right order.

۴.۲ جریان داده از طریق پایگاه داده4.2 Dataflow via databases

فرض کن نوشتن تو دیتابیس یعنی نامه فرستادن به خودِ آینده‌ت. ممکنه نسخه بعدی برنامه رکوردی رو بخونه که سال‌ها پیش ساخته شده. نکته ماندگار: ذخیره کردن یعنی پیام به آینده.

مثال فنی: ویرایش نام، حذف email

وضعیت اولیه: فرض کن نسخه ۲ رکورد {name:Sara,email:a@b} رو نوشته. ولی نسخه ۱ فقط name رو می‌شناسه.

اجرای مرحله‌به‌مرحله: تصور کن نسخه ۱ کل شیء رو می‌خونه. name رو عوض می‌کنه. بعد بدون email پس می‌نویسه. مگه اینکه update رو فقط به name محدود کنی یا فیلد ناشناخته رو نگه داری.

نتیجه و دلیل: یادت باشه یه read-modify-write قدیمی می‌تونه داده جدید رو بی‌صدا ببلعه. حتی وقتی decode هیچ خطایی نداده. نکته ماندگار: decode موفق یعنی داده سالم؟ نه!

  • فرض کن تو دیتابیس نویسنده encode می‌کنه، خواننده decode. اگه فقط یه process داری، خواننده همون خودتی در آینده. ذخیره کردن یعنی پیام به خودِ آینده‌ت. پس backward compatibility حتماً لازمه.
  • ولی معمولاً چند process هم‌زمان به دیتابیس وصل‌ان. وسط rolling upgrade بعضی جدیدن، بعضی قدیمی. پس forward compatibility هم لازمه. یادت باشه نسخه‌ها کنار هم زندگی می‌کنن.
  • data outlives code: تصور کن یه مقدار ۵ میلی‌ثانیه پیش نوشته شده، یکیش ۵ سال پیش. کد تو چند دقیقه عوض میشه. ولی داده تا بازنویسی صریح با همون فرمت قدیمی می‌مونه.
  • فرض کن می‌خوای همه داده رو به schema جدید migrate کنی. روی داده بزرگ گرونه. پس موتورها deferred و best-effort انجامش میدن. موتور LSM موقع compaction با فرمت جدید بازنویسی می‌کنه. دیتابیس رابطه‌ای ستون nullable اضافه می‌کنه بدون rewrite (ردیف قدیمی رو با null می‌خونه). نتیجه: دیتابیس «انگار» یه schema داره، ولی زیرش مخلوطی از نسخه‌هاست.
  • تغییر سخت‌تر (تک‌مقداری ← چندمقداری، جابه‌جایی به جدول جدا) هنوز بازنویسی سطح برنامه می‌خواد. نگه داشتن سازگاری تو این migrationها هنوز کار پژوهشیه.
  • بایگانی (archival): تصور کن snapshot یا dump معمولاً با جدیدترین schema و یکدست نوشته میشه. چون dump یه‌جا نوشته و فریز میشه، Avro object container files عالی‌ان. تازه فرصت خوبیه برای کدگذاری ستونی مثل Parquet (فصل ۱۱). نکته ماندگار: dump جای تسویه‌حساب با نسخه‌های قدیمیه.
  • In a database the writer process encodes and the reader process decodes. With a single process the reader is the same program in the future: storing means messaging your future self — so backward compatibility is definitely needed.
  • But usually several processes touch the database at once (different services, or several instances of one service), and mid-rolling-upgrade some are new and some old; so forward compatibility is needed too.
  • Data outlives code: one value may be 5 milliseconds old, another 5 years. Code changes in minutes; data keeps its old format until explicitly rewritten.
  • Rewriting (migrating) data to a new schema is possible but expensive on big data; so engines do it deferred and best-effort: LSM engines rewrite in the newest format during compaction; relational databases add nullable columns without rewrites (reading an old row fills null). Result: the whole database looks “as if” encoded with one schema, though the underlying storage mixes versions.
  • Trickier changes (single- → multi-valued, moving to a separate table) still need application-level rewrites, and keeping compatibility through such migrations is still research territory.
  • Archival: a snapshot or dump is usually written uniformly with the newest schema (since the actual data is being copied). Since a dump is written at once and frozen, Avro object container files are ideal — and a good moment for columnar encodings like Parquet (Chapter 11).

  • فرض کن الگوی رایج همون کلاینت و سرورئه. سرور API رو می‌ذاره رو شبکه. کلاینت درخواست می‌فرسته. وب هم همینه (GET برای HTML/CSS/JS، POST برای فرستادن داده) با پروتکل‌های استاندارد (HTTP، URL، TLS، HTML).
  • یادت باشه کلاینت فقط مرورگر نیست. اپ موبایل و دسکتاپ و اپ JavaScript مرورگر هم با HTTP وصل میشن. معمولاً JSON می‌گیرن.
  • تصور کن سرویس‌ها شبیه دیتابیس‌ان (داده می‌گیرن و میدن). ولی به‌جای query language عمومی، API ویژه برنامه دارن با ورودی/خروجی ازپیش‌تعیین‌شده. همین میشه کپسوله‌سازی.
  • هدف microservices اینه هر سرویس مستقل deploy و تکامل پیدا کنه (معمولاً یه تیم، یه سرویس، release مکرر). پس نسخه قدیم و جدید سرور و کلاینت هم‌زمان‌ان. تا وقتی API سازگاره، تیم آزاده زیرش رو عوض کنه.
  • web service یعنی سرویس روی HTTP. سه‌جا به کار میره: کلاینت روی دستگاه کاربر (اینترنت عمومی)، سرویس‌به‌سرویس تو یه سازمان (شبکه خصوصی)، و سازمان‌به‌سازمان (API عمومی مثل پرداخت یا OAuth).
  • REST محبوب‌ترین فلسفه طراحیه: فرمت ساده، URL برای شناسایی منابع، امکانات HTTP برای cache و احراز هویت و content negotiation. ولی کلاینت هنوز باید بدونه کدوم endpoint و چه فرمتی. برای همین IDL می‌نویسن: OpenAPI (Swagger) برای JSON و Protocol Buffers برای gRPC. ابزار IDL داک می‌سازه، سازگاری schema رو چک می‌کنه، GUI تست میده. نکته ماندگار: قرارداد نانوشته، قرارداد نیست.
  • The common pattern: client and server. The server puts an API on the network and the client sends it requests. The web works this way (GET for HTML/CSS/JS, POST for sending data) with a standard protocol set (HTTP, URL, TLS, HTML).
  • Clients aren’t just browsers: mobile and desktop apps and browser JavaScript apps also reach servers over HTTP, usually taking JSON.
  • Services resemble databases (they take and give data) but instead of a general query language they expose a program-specific API with predefined inputs/outputs — which brings encapsulation.
  • The microservices goal is for each service to deploy and evolve independently (usually one team, one service, frequent releases). So old and new server and client versions coexist, and teams are free to change internals only while APIs stay compatible.
  • A web service is a service over HTTP; used in three settings: user-device clients (the public internet), service-to-service inside one organization (private network), and org-to-org (public APIs like payment processing or OAuth).
  • REST is the most popular design philosophy: simple formats, URLs for resource identity, and HTTP facilities for caching, auth and content negotiation. But the client must still know which endpoint and format; hence IDLs: OpenAPI (Swagger) for JSON services, Protocol Buffers for gRPC. IDL tools build docs, check schema-change compatibility, and give testing GUIs.
چرا «فراخوانی از راه دور» مثل فراخوانیِ محلی نیست؟Why isn’t a “remote call” like a local call?

فرض کن تو REST یا RPC از یه سرویس دیگه کار می‌خوای. این صدا روی شبکه‌ست. ممکنه دیر برسه. جوابش گم بشه. یا نتیجه‌اش نامشخص بمونه. نکته ماندگار: شبکه مثل تابع محلی قول نمی‌ده.

مثال فنی: RPC ناموفق یا پاسخ نامعلوم؟

وضعیت اولیه: فرض کن کلاینت CreateOrder(request_id=r7) رو فرستاده. سرور سفارش رو ثبت کرده ولی جواب وسط راه گم شده.

اجرای مرحله‌به‌مرحله: تصور کن با همون شناسه retry می‌کنی، می‌رسی به همون نتیجه. ولی با شناسه تازه retry کنی ممکنه یه سفارش دوم بسازی.

نتیجه و دلیل: یادت باشه timeout یعنی «نمی‌دونم شد یا نه». نکته ماندگار: برخلاف تابع محلی، API باید خودش این ابهام رو مدیریت کنه.

The RPC model wants a network request to look like calling a function (location transparency) — but the differences are fundamental:

  • فرض کن صدای محلی قابل‌پیش‌بینیه. ولی درخواست شبکه‌ای غیرقابل‌پیش‌بینیئه (گم شدن، کندی ماشین دور).
  • تابع محلی یا مقدار میده یا exception. ولی درخواست شبکه‌ای پایان سوم هم داره: timeout بدون نتیجه. نمی‌دونی اصلاً اجرا شد یا نه.
  • یادت باشه retry ممکنه عمل رو دوبار اجرا کنه (اگه فقط جواب گم شده باشه). مگه قرارداد idempotence و شناسه یکتا داشته باشی (فصل ۱۲).
  • latency شبکه متغیره: از کمتر از یه میلی‌ثانیه تا چند ثانیه. تابع محلی این‌طوری نیست.
  • نمی‌تونی pointer بدی. همه‌چیز باید encode بشه. برای داده بزرگ و object mutable دردسر میشه.
  • کلاینت و سرور ممکنه زبون متفاوت داشته باشن. ترجمه نوع‌ها زشت میشه (مثل اعداد بزرگ‌تر از 2^53 در JavaScript). نکته ماندگار: مرز زبان یعنی مرز سوءتفاهم.
  • A local call is predictable; a network request is unpredictable (lost packets, a slow far machine).
  • A local call’s outcome is a value or an exception; a network request has a third ending: timeout with no result — you don’t know if it ran at all.
  • Retrying may run the action twice (if only the response was lost); unless you hold an idempotence contract and unique IDs (Chapter 12).
  • Network latency varies: from under a millisecond to seconds, unlike a local function.
  • You can’t pass pointers; everything must be encoded — painful for big data and mutable objects.
  • Client and server may speak different languages, and type translation gets ugly (like the bigger-than-2^53 numbers problem in JavaScript).
تصور کن جذابیت REST اینه انتقال state روی شبکه رو فراتر از صدا زدن تابع می‌فهمه. یادت باشه تاریخچه پر از شکست پرطمطراقه: EJB و RMI فقط Java، DCOM فقط مایکروسافت، CORBA پیچیده و ناسازگار، SOAP/WS-* پیچیده. نکته ماندگار: شفافیت لوکیشنِ دروغین گرون تموم میشه.

Part of REST’s appeal is understanding state transfer over the network as beyond function calls. History is full of grandiose failures too: EJB and RMI for Java only, DCOM for Microsoft only, CORBA complex and incompatible, SOAP/WS-* complex.

سازگاریِ RPC دقیقاً چه می‌خواهد؟What exactly does RPC compatibility need?
فرض کن قراره اول همه سرورها، بعد کلاینت‌ها به‌روز بشن. پس روی request فقط backward لازمه. روی response فقط forward. gRPC و Avro RPC قواعد همون قالب کدگذاری‌شون رو ارث می‌برن. تو REST/JSON معمولاً «افزودن پارامتر اختیاری request» و «افزودن فیلد response» سازگار حساب میشه. ولی یادت باشه RPC اغلب از مرز سازمان رد میشه. کنترلی روی کلاینت‌ها نیست. پس سازگاری شاید باید تا ابد بمونه (یا چند نسخه API کنار هم). نسخه‌بندی هم توافق جهانی نداره: شماره تو URL، هدر Accept، یا نسخه هر کلاینت تو سرور. نکته ماندگار: API عمومی قول بلندمدت می‌خواد.

Since we may assume servers upgrade first, clients after: requests need only backward, responses only forward. gRPC and Avro RPC inherit their encoding format’s rules; in REST/JSON “adding an optional request parameter” and “adding a response field” usually count as compatible. But since RPC often crosses org boundaries there is no control over clients, and compatibility may need keeping forever (or several API versions side by side). Versioning has no global agreement either: a number in the URL, the Accept header, or each client’s version on the server.

۴.۴ workflow و اجرای پایدار (Durable Execution) + نمودار ۵4.4 Workflows and durable execution + Diagram 5

فرض کن گردش‌کار پایدار وضعیت قدم‌ها رو نگه می‌داره. تا بعد از توقف برنامه بشه ادامه داد. ولی اثر بیرونی هر قدم هنوز باید ضد اجرای دوباره باشه. نکته ماندگار: ادامه از تاریخچه، نه اجرای تکراری بی‌حساب.

مثال فنی: ادامهٔ workflow بعد از crash

وضعیت اولیه: فرض کن workflow اول رزرو داره بعد صدور رسید. رزرو با شناسه r7 موفق شده.

اجرای مرحله‌به‌مرحله: تصور کن engine پیشرفت رو پایدار کرده. بعد از crash از روی تاریخچه ادامه میده. ولی فعالیتی که نتیجه‌ش ثبت نشده ممکنه دوباره صدا زده بشه.

نتیجه و دلیل: یادت باشه اثر بیرونی رزرو باید با r7 امن تکرار بشه. نکته ماندگار: دوام workflow یعنی «ادامه از تاریخچه»، نه «فقط یه‌بار اجرا».

The book’s example: a payment that must charge the card and deposit money to the bank account — separate services for fraud detection, card connectivity and bank connectivity. Running one payment = several service calls; this sequence is a workflow, each step a task (Temporal calls them activities; some say durable functions). Workflows are usually graphs of tasks, defined in a general language, a DSL, or BPEL.

  • فرض کن workflow engine تصمیم می‌گیره هر task کِی و رو کدوم ماشین بدوه. با خرابی چی کار کنه. چقدر موازی کنه. از یه orchestrator (زمان‌بندی) و یه یا چند executor (اجرا) ساخته شده. شروع با triggerئه: زمان‌بندی، وب‌سرویس، یا انسان.
  • خانواده‌ها رو تصور کن: ابزار داده‌ای مثل Airflow / Dagster / Prefect (هماهنگی ETL)، ابزار گرافیکی مثل Camunda / Orkes با BPMN برای غیرمهندس‌ها، و چارچوب durable execution مثل Temporal / Restate. نکته ماندگار: اسم‌ها عوض میشن، نقش orchestrator و executor همون‌ان.
  • A workflow engine decides when and on which machine each task runs, what to do on failure, and how much to parallelize; it is an orchestrator (scheduling) plus one or more executors (running). Runs start with a trigger: a schedule, a web service, or a human.
  • Families: data tools like Airflow / Dagster / Prefect (ETL orchestration), graphical tools like Camunda / Orkes with BPMN for non-engineers, and durable execution frameworks like Temporal / Restate.
durable execution چه دردی رو دوا می‌کنه؟What problem does durable execution solve?
فرض کن تو معماری سرویسی نمی‌تونی دو صدای کارت و بانک رو تو یه تراکنش دیتابیسی بپیچی. تازه با درگاه third-party هم طرفی. ولی می‌خوای هر پرداخت دقیقاً یه‌بار پردازش بشه. راه‌حل: چارچوب همه صداها و تغییرهای state رو تو ذخیره‌سازی پایدار (مثل write-ahead log) ثبت می‌کنه. اگه task بشکنه دوباره اجرا میشه. ولی قدم‌های موفق قبلی رد میشن و نتیجه قبلی‌شون برمی‌گرده. انگار صدا تکرار نشده. نکته ماندگار: exactly-once با لاگ و replayئه، نه با تراکنش کلاسیک.

In a service architecture you can’t wrap the card and bank calls in one database transaction; you also work with third-party payment gateways. But you want each payment processed exactly once. The fix: the framework records every call and state change in durable storage (like a write-ahead log). If a task fails it re-runs, but previously successful steps are skipped with their old results returned — as if the call never repeated.

مثال فنی برای خواندنِ نمودار: ادامهٔ workflow بعد از crash

وضعیت اولیه: فرض کن workflow اول رزرو داره بعد صدور رسید. رزرو با شناسه r7 موفق شده.

اجرای مرحله‌به‌مرحله: تصور کن engine پیشرفت رو پایدار کرده. بعد از crash از روی تاریخچه ادامه میده. ولی فعالیتی که نتیجه‌ش ثبت نشده ممکنه دوباره صدا زده بشه.

نتیجه و دلیل: یادت باشه اثر بیرونی رزرو باید با r7 امن تکرار بشه. نکته ماندگار: دوام workflow یعنی «ادامه از تاریخچه»، نه «فقط یه‌بار اجرا».

تصور کن شش شرکت‌کننده از چپ به راست‌ان: «Checkout» (زیرنویس: «workflow trigger»)، «Workflow Engine» (زیرنویس: «workflow runtime»)، «Durable Log» (زیرنویس: «write-ahead log»)، «Fraud Check» (زیرنویس: «internal service»)، «Card Network» و «Bank Service» (هر دو زیرنویس «third-party API»). دو نوار عنوان هم تو چپه: «First execution» و «Crash recovery and replay». یادت باشه اول اجرا، بعد نجات.

Six participants, left to right: Checkout (workflow trigger), Workflow Engine (workflow runtime), Durable Log (write-ahead log), Fraud Check (internal service), Card Network and Bank Service (both third-party API). Two title bands at left: First execution and Crash recovery and replay.

فرض کن تو اجرای اول «start payment workflow» از Checkout میاد به موتور. موتور قدم‌ها رو یکی‌یکی می‌فرسته: «activity: check fraud» به Fraud Check و جواب «not fraudulent». بعد «append step result» به Durable Log (فلش چین‌چین — یعنی هر قدم موفق اول ثبت میشه). بعد «activity: debit card» به Card Network و جواب «charged» و دوباره ثبت تو لاگ. قدم سوم «activity: deposit funds» به Bank Serviceئه که زیرش نوشته «worker crashes mid-step» — همین‌جا worker می‌میره.

First run: start payment workflow arrives from Checkout. The engine sends steps one by one: activity: check fraud to Fraud Check, reply not fraudulent; then dashed append step result to the Durable Log (every successful step is recorded first); then activity: debit card to Card Network, reply charged, recorded in the log again. The third step, activity: deposit funds to Bank Service, is annotated worker crashes mid-step — the worker dies right there.

تصور کن نوار دوم قصه نجاته: «re-execute workflow» (فلش چین‌چین از Checkout)، بعد «replay recorded steps» از موتور به Durable Log — موتور می‌بینه check fraud و debit card قبلاً انجام و ثبت شدن. پس فقط قدم گم‌شده رو می‌فرسته: «deposit funds (only missing step)» به Bank Service، جواب «deposited»، و پایان خوش «payment complete, exactly once» به Checkout.

Band two is the rescue story: re-execute workflow (dashed arrow from Checkout), then replay recorded steps from the engine to the Durable Log — the engine sees fraud-check and debit-card already done and recorded. So it sends only the missing step: deposit funds (only missing step) to Bank Service, reply deposited, and the happy end payment complete, exactly once to Checkout.

یادت باشه «دقیقاً یه‌بار» با تراکنش سنتی دیتابیسی به دست نمیاد. با لاگ پایدار + replay به دست میاد. نکته ماندگار: نجات مفت نیست — بهاش رو بخش بعد می‌بینی.

The lesson: “exactly once” doesn’t come from a traditional database transaction; it comes from a durable log + replay. And of course it has a price — which the next part covers.

چالش‌های durable executionDurable-execution challenges

فرض کن اجرای پایدار باید با سه‌چیز کنار بیاد: تکرار قدم، عوض شدن نسخه کد، نتیجه نامشخص سرویس بیرونی. نکته ماندگار: دوام یعنی کنار اومدن با تکرار.

مثال فنی: Replay با کد عوض‌شده

وضعیت اولیه: فرض کن workflow قدیمی تو تاریخچه‌ش اول «رزرو» داره بعد «رسید».

اجرای مرحله‌به‌مرحله: تصور کن کد تازه بدون نسخه‌بندی ترتیب تصمیم‌ها رو به‌هم می‌زنه. اون‌وقت replay ممکنه با تاریخچه ناسازگار بشه و بترکه.

نتیجه و دلیل: یادت باشه داده تصمیم و نسخه منطق باید خوانا بمونن. ساعت و تصادف و I/O رو بی‌قاعده ننداز وسط replay. نکته ماندگار: replay غیرقطعی یعنی کابوس.

  • فرض کن سرویس بیرونی (مثل درگاه third-party) هنوز باید idempotent باشه. تو باید با شناسه یکتا جلوی اجرای تکراری رو بگیری.
  • چارچوب صداها رو به ترتیب ثبت می‌کنه. انتظار داره اجرای بعدی دقیقاً همون صداها به همون ترتیب باشه. پس جابه‌جا کردن دو خط کد می‌تونه replay invocationهای در جریان رو مبهم کنه. راه امن: تغییر کد workflow رو به‌صورت نسخه جدا deploy کن تا قدیمی‌ها با منطق قدیم replay بشن.
  • یادت باشه replay باید قطعی (deterministic) باشه: همون ورودی ← همون خروجی. عدد تصادفی یا ساعت سیستم ممنوع. چارچوب‌ها نسخه قطعی این تابع‌ها رو میدن و ابزار مثل Workflow Check تخلف رو پیدا می‌کنه (برمی‌گردیم به فصل ۹). نکته ماندگار: تصادف تو replay یعنی تاریخچه خراب.
  • Outside services (like third-party payment gateways) must still be idempotent; you must block repeat runs with unique IDs.
  • The framework records calls in order and expects the next run to make exactly the same calls in the same order; so swapping two code lines can blur the replay behavior of in-flight invocations. The safe fix: deploy workflow-code changes as a separate version so old invocations replay with old logic.
  • Replay must be deterministic: same input → same output. Random numbers and system-clock reads are banned; frameworks give deterministic versions of these functions, and tools like Workflow Check catch violations. (Back to the determinism debate in Chapter 9.)

۴.۵ معماری event-driven4.5 Event-driven architecture

فرض کن تو معماری رویدادمحور تولیدکننده خبر یه اتفاق رو منتشر می‌کنه. مصرف‌کننده‌ها مستقل واکنش نشون میدن. ولی شکل و نسخه رویداد هنوز قرارداد مشترکه. نکته ماندگار: جدایی در زمان، نه جدایی در قرارداد.

مثال فنی: رویداد مستقل از مصرف‌کننده

وضعیت اولیه: فرض کن سفارش 42 رویداد OrderPlaced رو منتشر کرده.

اجرای مرحله‌به‌مرحله: تصور کن هم گروه ارسال می‌گیرتش هم گروه تحلیل. تازه تو گروه ارسال چند worker کار رو بین خودشون تقسیم می‌کنن.

نتیجه و دلیل: یادت باشه pub/sub یعنی تکثیر بین گروه‌ها، queue یعنی تقسیم کار تو گروه. نکته ماندگار: باز هم تکرار و خطا رو باید کنترل کنی.

  • فرض کن تو این معماری درخواست یه event یا messageئه. فرستنده معمولاً منتظر پردازش گیرنده نمی‌مونه. پیام از یه message broker (event broker، message queue، MOM) رد میشه که موقتاً نگهش می‌داره.
  • تصور کن broker نسبت به RPC مستقیم این خوبی‌ها رو داره: بافر وقتی گیرنده نیست یا overloadئه، تحویل مجدد خودکار بعد از crash، بی‌نیازی از service discovery، فرستادن یه پیام به چند گیرنده، جدایی منطقی فرستنده و گیرنده (فرستنده فقط publish می‌کنه).
  • یادت باشه دو الگوی توزیع داری: queue (یه مصرف‌کننده از بین چندتا پیام رو می‌گیره) و topic / pub-sub (همه subscriberها نسخه خودشون رو می‌گیرن).
  • brokerها مدل داده تحمیل نمی‌کنن: پیام = بایت‌ها + metadata. رایج: Protobuf/Avro/JSON با schema registry، و AsyncAPI معادل OpenAPI برای پیام. مثال‌ها: RabbitMQ، ActiveMQ، NATS، Redpanda، Kafka (متن‌باز) و Kinesis، Azure Service Bus، Cloud Pub/Sub (ابری) — مقایسه تو فصل ۱۲.
  • دوام پیام: خیلی‌ها رو دیسک می‌نویسن تا با crash نپرن. ولی برخلاف دیتابیس، خیلی‌ها بعد از مصرف خودکار حذف می‌کنن. برای event sourcing به broker نیاز داری که پیام‌ها رو تا ابد نگه داره (فصل ۳).
  • فرض کن مصرف‌کننده‌ای پیام رو دوباره تو topic دیگه publish می‌کنه. باید فیلدهای ناشناخته رو حفظ کنه. وگرنه بلای شکل ۵-۱ این‌بار وسط pipeline میاد.
  • actor model: تصور کن به‌جای thread و قفل و deadlock، منطق تو actorها کپسوله میشه. هر actor state محلی خودش رو داره. با پیام ناهمزمان حرف می‌زنه. یه پیام در هر لحظه پردازش می‌کنه. تحویل پیام هم تضمینی نیست. تو چارچوب‌های توزیع‌شده مثل Akka، Orleans و Erlang/OTP همون مکانیزم محلی یا دور یکسانه (پیام شفاف encode میشه، اون‌طرف decode). location transparency این‌جا بهتر از RPC جواب میده چون مدل از اول «پیام ممکنه گم بشه» رو قبول کرده. یادت باشه برای rolling upgrade باز هم کدگذاری سازگار می‌خوای. نکته ماندگار: actor از اول با گم شدن کنار اومده، RPC نه.
  • In this architecture a request is an event or message and the sender usually doesn’t wait for the receiver’s processing; the message passes through a message broker (event broker, message queue, MOM) holding it temporarily.
  • Broker advantages over direct RPC: buffering when the receiver is down or overloaded; automatic redelivery after a crash; no service discovery needed; sending one message to several receivers; and logical sender/receiver decoupling (the sender only publishes).
  • Two distribution patterns: queue (one of several consumers takes the message) and topic / pub-sub (every subscriber gets its own copy).
  • Brokers impose no data model: a message = bytes + metadata. Common: Protobuf/Avro/JSON with a schema registry; AsyncAPI as the message-world OpenAPI. Examples: RabbitMQ, ActiveMQ, NATS, Redpanda, Kafka (open source) and Kinesis, Azure Service Bus, Cloud Pub/Sub (cloud) — compared in Chapter 12.
  • Message durability: many write to disk to survive crashes; unlike databases, many auto-delete after consumption. For event sourcing you need a broker keeping messages forever (Chapter 3).
  • If a consumer republishes a message to another topic it must preserve unknown fields — otherwise Figure 5-1’s curse strikes mid-pipeline.
  • Actor model: instead of threads, locks and deadlocks, logic is encapsulated in actors; each actor owns its local state, talks over async messages, processes one message at a time, and delivery isn’t guaranteed. In distributed frameworks like Akka, Orleans and Erlang/OTP the same mechanism works locally or remotely (messages transparently encode here, decode there). Location transparency works better here than in RPC because the model accepts “messages may be lost” from the start. Rolling upgrades still need compatible encoding.

۱. backward و forward compatibility یعنی چه و در APIها چطور معنا می‌شوند؟1. What do backward and forward compatibility mean — and in APIs?

backward یعنی کد جدید هنوز داده قدیمی رو بفهمه؛ forward یعنی کد قدیمی با داده جدید نترکه و نگهش داره. تو API جدا حساب کن کی request رو می‌نویسه و کی response رو می‌خونه.

مثال فنی: چهار ترکیب در rolling upgrade

وضعیت اولیه: تصور کن نصف سرورها هنوز نسخهٔ ۱‌ان، نصف دیگه رفتن روی نسخهٔ ۲.

اجرای مرحله‌به‌مرحله: اول نسخهٔ ۲ رکورد قدیمی رو می‌خونه و حالشو می‌بره؛ بعد نوبت نسخهٔ ۱ـه که یه رکورد دست‌نویس نسخهٔ ۲ دستش می‌رسه.

نتیجه و دلیل: تهش اینه: backward یعنی جدید قدیمی رو بخونه، forward یعنی قدیمی جدید رو نگه داره. rolling upgrade هر دو رو هم‌زمان می‌خواد، قاطی نکن.

Backward = new code still gets old data. Forward = old code survives new data without mangling it. APIs: old client, new server? Requests go backward, responses forward. New client, old server? Mirror it. Directions matter, friend.

۲. چرا rolling upgrade هر دو نوع سازگاری را لازم دارد؟2. Why does a rolling upgrade need both compatibilities?

تو rolling upgrade همه nodeها با هم آپدیت نمی‌شن؛ یه مدت نسخه قدیم و جدید کنار هم کار می‌کنن و داده قدیم و جدید قاطی رد و بدل می‌شه. پس هر دو جهت خوندن رو لازم داری، نه فقط یکیش.

مثال فنی: چهار ترکیب در rolling upgrade

وضعیت اولیه: تصور کن نصف سرورها هنوز نسخهٔ ۱‌ان، نصف دیگه رفتن روی نسخهٔ ۲.

اجرای مرحله‌به‌مرحله: اول نسخهٔ ۲ رکورد قدیمی رو می‌خونه و حالشو می‌بره؛ بعد نوبت نسخهٔ ۱ـه که یه رکورد دست‌نویس نسخهٔ ۲ دستش می‌رسه.

نتیجه و دلیل: تهش اینه: backward یعنی جدید قدیمی رو بخونه، forward یعنی قدیمی جدید رو نگه داره. rolling upgrade هر دو رو هم‌زمان می‌خواد، قاطی نکن.

Mid-deploy, new and old nodes share the floor; fresh data may land in old hands (forward!) and ancient data in new ones (backward!). You need both directions — and clients update whenever they feel like it, so good luck herding them.

۳. خطرِ شکل ۵-۱ کتاب چیست و چطور رفع می‌شود؟3. What is the book’s Figure 5-1 danger, and the fix?

کد قدیمی فیلد ناشناخته رو نمی‌فهمه و می‌ندازتش دور؛ بعد که همون رکورد رو پس می‌نویسه، اون فیلد برای همیشه از داده اصلی می‌پره. راه حل: یا فیلد ناشناخته رو نگه دار، یا به‌جای بازنویسی کل رکورد فقط همون تیکه لازم رو update کن.

مثال فنی: ویرایش نام، حذف email

وضعیت اولیه: فرض کن نسخه ۲ رکورد {name:Sara,email:a@b} رو نوشته. ولی نسخه ۱ فقط name رو می‌شناسه.

اجرای مرحله‌به‌مرحله: تصور کن نسخه ۱ کل شیء رو می‌خونه. name رو عوض می‌کنه. بعد بدون email پس می‌نویسه. مگه اینکه update رو فقط به name محدود کنی یا فیلد ناشناخته رو نگه داری.

نتیجه و دلیل: یادت باشه یه read-modify-write قدیمی می‌تونه داده جدید رو بی‌صدا ببلعه. حتی وقتی decode هیچ خطایی نداده. نکته ماندگار: decode موفق یعنی داده سالم؟ نه!

Old code meets an unknown field, shrugs, rewrites — poof, field gone forever. The fix: keep the stranger’s bytes on round-trip (protobuf does), or decode into something that explicitly hoards unknowns. Don’t drop what you don’t understand.

۴. چهار مشکلِ اصلیِ کدگذاریِ ویژهٔ زبان (مثل Serializable و pickle) چیست؟4. What are the four core problems of language-native encoding (Serializable, pickle)?

چهار تا دردسر بزرگ داره: به یه زبان و کلاس قفل می‌شی، بازسازی object از ورودی غریبه امنیت رو می‌ترکونه (RCE)، عوض کردن نسخه باهاش سخته، و برای تبادل داده تمیز نیست. برای ورودی نامطمئن؟ اصلاً سراغش نرو.

مثال فنی: نام کلاس، قرارداد پایدار نیست

وضعیت اولیه: فرض کن فایل ذخیره‌شده‌ات به کلاس OldUser نسخهٔ قبلی چسبیده.

اجرای مرحله‌به‌مرحله: حالا نسخهٔ جدید اون کلاس رو پاک کرده یا زبون عوض شده؛ decoder مخصوص اون زبون ممکنه اصلاً نتونه شیء رو بسازه و بترکه.

نتیجه و دلیل: یادت باشه داده از کد بیشتر عمر می‌کنه؛ برای تبادل schema مستقل می‌خوای و ورودی مطمئن.

Four headaches: language jail (good luck reading it elsewhere), the instantiate-anything RCE nightmare, versioning? never heard of her, and Java-serialization-grade slowness. Ephemeral use only — never for data that outlives the process.

۵. مشکلِ اعداد در JSON چیست؟5. What’s the numbers problem in JSON?

JSON به هیچ خواننده‌ای قول دقت عدد نمی‌ده. مثلاً عدد معمولی JavaScript عدد صحیح بزرگ رو دقیق نگه نمی‌داره و گرد می‌کنه. پس id بزرگ رو number نفرست.

مثال فنی: شناسهٔ بزرگ در JSON

وضعیت اولیه: فرض کن شناسهٔ 9007199254740993 به‌صورت JSON number می‌رسه دست JavaScript.

اجرای مرحله‌به‌مرحله: نگران نشو اگه دیدی تبدیلش به Number گرد شد به 9007199254740992؛ اگه شناسه رو رشته‌ای قرارداد کنی رقم‌هاش سر جاش می‌مونه.

نتیجه و دلیل: یادت باشه JSON قول دقت به همه نمی‌ده؛ نوع فیلد رو دو طرف شفاف قرارداد کن.

JSON can’t tell ints from floats and promises zero precision; past 2^53, doubles start lying. That’s why X ships a post’s 64-bit id as number AND string. XML and CSV? Even worse — numbers and numeric strings wear the same clothes.

۶. چرا برای داده‌های باینری در JSON از Base64 استفاده می‌کنند و هزینه‌اش چیست؟6. Why is Base64 used for binary data in JSON — at what cost?

Base64 فقط بایت رو می‌کنه متن که بشه تو JSON حملش کرد. هزینش حدود یه‌سوم حجم اضافه‌ست؛ این encoding ـه، نه رمز — هیچ محرمانگی نمی‌ده.

مثال فنی: Base64 برای بایت در JSON

وضعیت اولیه: فرض کن یه فایل باینری سه‌بایتی رو باید بچپونی تو یه فیلد متنی JSON.

اجرای مرحله‌به‌مرحله: تصور کن Base64 هر سه بایت رو می‌کنه چهار تا نویسه؛ برای ورودی بزرگ حدود یه‌سوم حجم می‌ره بالا، جدا از سربار خود JSON.

نتیجه و دلیل: این فقط راه حمل بایته تو رشته، فشرده‌سازی نیست؛ برای فایل بزرگ یه مسیر جدا بذار — سبک‌تر درمیای.

JSON/XML can’t hold raw bytes, period — Base64 disguises bytes as text, schema winks “totally Base64”. Price: ~a third extra bulk plus encode/decode sweat. Real binary formats just HAVE a binary type. No costume needed.

۷. content model باز و بسته در JSON Schema یعنی چه؟7. What are open and closed content models in JSON Schema?

مدل باز فیلد اضافه رو قبول می‌کنه؛ مدل بسته ردش می‌کنه. باز باشی نسخه جدید راحت رد می‌شه ولی غلط ورودی رو نمی‌گیری؛ بسته باشی برعکس.

مثال فنی: Schema باز یا بسته

وضعیت اولیه: فرض کن قراردادت فقط name رو تعریف کرده ولی پیام تازه email هم آورده.

اجرای مرحله‌به‌مرحله: تصور کن با additionalProperties:false همون‌جا validator فیلد اضافه رو رد می‌کنه؛ مدل باز می‌تونه قبولش کنه.

نتیجه و دلیل: اضافه کردن فیلد همیشه سازگار نیست؛ این سیاست خواننده‌ست که معلوم می‌کنه فیلد ناشناخته بمونه یا بپره.

Open door: surprise fields welcome (additionalProperties: true by default). Closed door: listed guests only. So JSON Schema mostly polices what’s not allowed — bouncer logic. Fancy combos (patternProperties + additionalProperties) even write house rules like “keys digits-only, values strings-only”.

۸. MessagePack چقدر فضا جبران می‌کند و چرا کتاب چندان تحویلش نمی‌گیرد؟8. How much space does MessagePack save — and why doesn’t the book rate it?

تو مثال همین فصل MessagePack فقط از ۸۱ رسیده به ۶۶ بایت؛ همین عدد رو همه‌جا تعمیم نده. چون schema نداره، اسم فیلدها هنوز تو داده سفر می‌کنه — صرف باینری بودن معجزه نمی‌کنه.

مثال فنی: MessagePack چه چیزی را حذف می‌کند؟

وضعیت اولیه: فرض کن شیء JSON اسم فیلد customer_id رو تو هر رکورد هی تکرار می‌کنه.

اجرای مرحله‌به‌مرحله: حالا MessagePack نوع و مقدار رو باینری‌تر می‌کنه، ولی تو استفادهٔ map معمولی اسم فیلد هنوز با هر رکورد سفر می‌کنه.

نتیجه و دلیل: سود حجم بستگی به داده داره؛ قالب schemaدار می‌تونه اسم‌ها رو از wire حذف کنه و قرارداد تکامل جدا بده — اون فرق اصلیه.

Our demo record: 66 vs 81 JSON bytes — ~18% off. Schemaless means field names still ride along; only the JSON shape got binarized. Meh savings for murdered readability — and don’t extrapolate one record to the universe. Real schemas hit 32–33 bytes.

۹. field tag در Protocol Buffers چیست و چه قوانینی دارد؟9. What is a field tag in Protocol Buffers — what are its rules?

تگ همون شماره شناسنامه فیلد رو wire ـه. اسم فیلد رو هر وقت خواستی عوض کن، ولی شماره رو نه؛ شماره فیلد حذف‌شده رو هم به چیز جدید نده، reserve ـش کن.

مثال فنی: Tag هویت فیلد است

وضعیت اولیه: فرض کن تو schema پیامت داری string name = 1، بعد اومدی string email = 2 رو اضافه کردی.

اجرای مرحله‌به‌مرحله: یادت باشه شمارهٔ ۱ همیشه مال name می‌مونه؛ اگه email رو حذف کردی، شمارهٔ ۲ رو نده به یه معنای دیگه.

نتیجه و دلیل: اسم عوض کردن با هویت wire فرق داره؛ reuse شماره یعنی دادهٔ قدیمی رو با معنای اشتباه می‌خونی — تهش می‌ترکه.

The tag is the field’s ID badge on the wire — names never travel. Rename freely, but tags are FOREVER: change one and every old record rots. Retired tags? Reserve them like hallowed ground. Never hand a dead badge to a rookie.

۱۰. قواعد تکاملِ schema در protobuf برای افزودن/حذف/تغییر نوع چیست؟10. What are protobuf’s schema-evolution rules for add/remove/retype?

فیلد جدید فقط با شماره جدید؛ شماره حذف‌شده reserve می‌شه. تغییر نوع رو باید با جدول سازگاری wire چک کنی — حتی تغییر مجاز هم ممکنه بعضی مقدارها رو ببره (truncation). شماره ثابت به‌تنهایی یعنی معنا حفظ شده؟ نه.

مثال فنی: تکامل protobuf با شمارهٔ ثابت

وضعیت اولیه: فرض کن فیلد string name = 1 منتشر شده و پیام‌های قدیمی هنوز این‌ور اون‌ور هستن.

اجرای مرحله‌به‌مرحله: حالا فیلد تازه رو فقط با شمارهٔ آزاد اضافه کن؛ حذف یعنی شماره و اسم لازم رو reserved کن؛ تغییر نوع هم باید قواعد wire و معنی مقدار رو رعایت کنه.

نتیجه و دلیل: همون شماره رو از رشته بچرخونی به یه معنای عددی نامربوط، مهاجرت امن نیست؛ حفظ شماره به‌تنهایی حفظ معنا نیست — یادت باشه.

Add with a virgin tag: safe both ways (old code skips-and-keeps, new code defaults the gap). Remove = add in reverse, tags stay buried. Retype? Sometimes, but watch the truncation trap (64-bit dreams into a 32-bit bed). And a steady tag alone never proves meaning survived — check the values, not just the parse.

۱۱. Avro هنگام decode از چه چیزی استفاده می‌کند و writer's schema از کجا می‌آید؟11. What does Avro decode with — and where does the writer’s schema come from?

Avro موقع decode اسکیمای نویسنده و خواننده رو جفت می‌کنه (resolution). بایت خالی به‌تنهایی هیچی نیست؛ اسکیمای نویسنده یا تو سرآغاز فایله یا با id از registry میاد.

مثال فنی: پیدا کردن schema نویسنده

وضعیت اولیه: فرض کن پیام Avro یه شناسهٔ schema مساوی 23 داره به‌علاوه بایت‌های رکورد.

اجرای مرحله‌به‌مرحله: حالا مصرف‌کننده می‌ره schema شماره ۲۳ رو از registry برمی‌داره و می‌ذاره کنار reader schema جلوی decoder.

نتیجه و دلیل: یادت باشه فقط reader schema کافی نیست؛ شناسه رو نگه دار و schemaهای قدیمی رو دور ننداز.

Avro always dances with TWO schemas: the writer’s (frozen at write time) and the reader’s (today’s expectations); resolution matchmakes by name. Where’s the writer’s schema? Once up front in big files, per-record id + registry on streams (Confluent-style), or handshake at connect (Avro RPC). Three doors, pick yours.

۱۲. قواعدِ Avro دربارهٔ مقدارِ پیش‌فرض (default) چیست؟12. What are Avro’s default-value rules?

اگه خواننده فیلدی بخواد که نویسنده نداره، باید تو اسکیمای خواننده default باشه وگرنه decode می‌ترکه. حذف فیلد هم همینه و به قرارداد خواننده قدیمی برمی‌گرده. default یعنی «جای خالی رو پر کن»، نه «نوشتن اختیاریه».

مثال فنی: Resolution در Avro

وضعیت اولیه: فرض کن writer فقط name داره، reader جدید اومده یه فیلد country با default مساوی IR اضافه کرده.

اجرای مرحله‌به‌مرحله: حالا وقتی رکورد قدیمی رو می‌خونی، reader مقدار گمشدهٔ country رو از default برمی‌داره.

نتیجه و دلیل: یادت باشه default فقط جای خالی writer رو پر می‌کنه؛ به‌جای نوشتن اجباری تو schema نویسنده نمی‌شینه.

منبعِ توضیحِ فنی: قواعدِ رسمیِ تطبیقِ اسکیمای Avro

No default, no add-or-remove — house rule. Add without a default and the new reader stares blankly (backward 💥). Remove one and the old reader finds an empty chair (forward 💥). Default means “fill the gap”, NOT “writing is optional”.

۱۳. چرا در Avro برای nullable بودن باید union نوشت؟13. Why must Avro nullability use a union?

تو Avro هیچ فیلدی خودش null‌پذیر نیست؛ باید تو union صریح بگی null هم مجازه. نبودن فیلد، null بودن مقدار، و default داشتن سه‌تای جدان — قاطیشون نکن.

مثال فنی: Nullable در Avro

وضعیت اولیه: فرض کن email ممکنه رشته باشه یا null.

اجرای مرحله‌به‌مرحله: تصور کن schema باید union مثل ["null","string"] رو مجاز کنه؛ برای رکوردهای قدیمی هم می‌تونی تو reader یه default معتبر null بذاری.

نتیجه و دلیل: نبودن فیلد با null بودن مقدار با default داشتن سه‌تای جداان؛ قاطیشون نکن، جدا طراحیشون کن.

Avro hands nobody a free null: spell out every type a field may wear — union { null, long } or bust. Null-default only when null leads the union parade. Missing field, null value, has-a-default: three strangers, stop introducing them as family.

۱۴. تغییر نامِ فیلد در Avro چرا فقط backward است؟14. Why is an Avro field rename backward-only?

با alias خواننده جدید اسم قدیمی نویسنده رو می‌فهمه — پس rename فقط backward می‌شه. خواننده قدیمی اسم جدید رو نمی‌شناسه، پس forward نداری. هر جهت رو جدا تست کن.

مثال فنی: تغییر نام با alias

وضعیت اولیه: فرض کن writer قدیمی surname نوشته و reader جدید family_name با alias مساوی surname داره.

اجرای مرحله‌به‌مرحله: حالا reader جدید اسم قدیمی رو می‌فهمه و جفت می‌کنه؛ ولی reader قدیمی alias تازه رو نمی‌شناسه پس جهت برعکس خودش حل نمی‌شه.

نتیجه و دلیل: می‌بینی؟ backward می‌شه ولی forward نه؛ هر دو جهت رو جدا تست کن.

Reader-side alias = the new kid understands grandpa’s name for the field (backward ✓). But grandpa never learned the new name, so new-writer data baffles him (forward ✗). Rename = one-way street. New union branch? Same verdict. Test each direction like they owe you money.

۱۵. مزایای قالب‌های باینریِ مبتنی بر schema نسبت به JSON چیست؟15. What advantages do schema-driven binary formats have over JSON?

با schema اسم و نوع فیلد از تک‌تک رکوردها حذف می‌شه — هم حجم کم می‌شه، هم قرارداد شفافه، هم validation و codegen داری. ولی schema به‌خودی‌خود سازگاری نمیاره؛ قاعده تغییر و پیاده‌سازی درست می‌خواد.

مثال فنی: مقایسهٔ قالب روی همان رکورد

وضعیت اولیه: فرض کن همون رکورد user_id=17, active=true رو می‌خوای با چند تا قالب بنویسی.

اجرای مرحله‌به‌مرحله: تصور کن JSON اسم فیلدها رو دونه‌دونه با خودش حمل می‌کنه؛ ولی قالب schemaدار می‌تونه به‌جاش شناسه یا جای فیلد رو بذاره.

نتیجه و دلیل: یادت باشه سیب با سیب مقایسه کن — همون داده، همون کتابخونه؛ باینری بودن به‌تنهایی نه یعنی کم‌حجم‌تر، نه یعنی تکامل بهتر.

Why bother: denser (names vanish), the schema doubles as living docs (decoders NEED it), registries let you rehearse compatibility pre-deploy, plus free codegen for typed languages. The bill: kiss human-readability goodbye without tooling.

۱۶. «data outlives code» یعنی چه و چه نتیجه‌ای دارد؟16. What does “data outlives code” mean — what follows?

داده خیلی بیشتر از کد عمر می‌کنه. deploy جدید فایل و رکورد قدیمی رو خودش نو نمی‌کنه؛ باید از اول طراحی کنی کدِ ننوشته فردا داده امروز رو بخونه، یا مهاجرت جدا بذاری. تموم شدن deploy یعنی تموم شدن داده قدیمی؟ نه!

مثال فنی: سه مسیر همان داده

وضعیت اولیه: فرض کن عوض شدن اسم کاربر رو میشه از سه‌جا خوند: رکورد دیتابیس، جواب API، یا پیام رویداد.

اجرای مرحله‌به‌مرحله: تصور کن دیتابیس نسخه‌های قدیمی رو نگه داشته. API هنوز با کلاینت قدیمی حرف می‌زنه. صف هم ممکنه پیام قدیمی رو دوباره بده.

نتیجه و دلیل: یادت باشه هر مسیر پنجره سازگاری خودش رو داره. تموم شدن deploy سرور یعنی تموم شدن داده قدیمی؟ نه! نکته ماندگار: داده از کد دیرتر می‌میره.

Code ships in minutes; data from 2019 still wears 2019 clothes. Migrating everything costs a fortune, so engines procrastinate (LSM compaction, nullable SQL columns). Design every format for readers that DON’T EXIST YET — deploy-day isn’t data-day. Ever.

۱۷. سه تفاوتِ محوریِ فراخوانیِ شبکه‌ای با فراخوانیِ محلی چیست؟17. What are three core network-call vs local-call differences?

فراخوانی شبکه سه‌تا فرق بزرگ با تابع محلی داره: ممکنه اصلاً نرسه، بعد از timeout نمی‌دونی اجرا شد یا نه، و تأخیرش خیلی نوسان داره. تازه قالب تبادل بین برنامه‌ها رو هم باید حل کنی. شبیه بودن ظاهر RPC به تابع محلی این‌ها رو پاک نمی‌کنه.

مثال فنی: RPC ناموفق یا پاسخ نامعلوم؟

وضعیت اولیه: فرض کن کلاینت CreateOrder(request_id=r7) رو فرستاده. سرور سفارش رو ثبت کرده ولی جواب وسط راه گم شده.

اجرای مرحله‌به‌مرحله: تصور کن با همون شناسه retry می‌کنی، می‌رسی به همون نتیجه. ولی با شناسه تازه retry کنی ممکنه یه سفارش دوم بسازی.

نتیجه و دلیل: یادت باشه timeout یعنی «نمی‌دونم شد یا نه». نکته ماندگار: برخلاف تابع محلی، API باید خودش این ابهام رو مدیریت کنه.

Three rude awakenings: it might never arrive, timeout leaves you clueless (did it run?! — hence idempotence), and latency mood-swings wildly. Plus: no pointers, and types get lost in translation. So an RPC in a function costume? Don’t let the outfit fool you.

۱۸. چرا در RPC فقط backward برای request و forward برای response کافی است؟18. Why is backward-on-request + forward-on-response enough in RPC?

این دو جهت فقط وقتی کافیه که اول سرور آپدیت بشه بعد کلاینت: سرور جدید request قدیمی رو می‌خونه (backward)، کلاینت قدیمی response جدید رو تحمل می‌کنه (forward). اگه کلاینت جدید به سرور قدیمی بخوره، جهت‌های برعکس هم لازم داری — حکم کلی نده.

مثال فنی: API با سرور تازه

وضعیت اولیه: فرض کن کلاینت قدیمی درخواست نسخهٔ ۱ می‌فرسته و جواب تازه می‌گیره.

اجرای مرحله‌به‌مرحله: حالا سرور باید request قدیمی رو بخوره، کلاینت هم باید response جدید رو تحمل کنه؛ اگه سرور قدیمی هنوز زنده‌ست request تازه هم باید براش قابل‌قبول بمونه.

نتیجه و دلیل: جهت سازگاری بستگی داره کی نوشته کی خونده؛ یه حکم کلی برای همه rolloutها نداریم — حواست باشه.

Works ONLY if servers upgrade first, clients second: new server reads old requests (backward ✓), old client stomachs new responses (forward ✓). New client yelling at an old server? You’ll want the mirror directions too. Cross-org? You don’t own their upgrade day — keep compat forever or ship parallel API versions. No universal law here.

۱۹. تفاوتِ queue و topic (pub/sub) چیست؟19. What’s the queue vs topic (pub/sub) difference?

تو queue هر پیام فقط به یه consumer می‌رسه — تقسیم کار. تو pub/sub هر گروه subscriber یه کپی از همون رویداد می‌گیره — تکثیر بین گروه‌ها؛ تازه داخل هر گروه می‌شه بار رو تقسیم کرد.

مثال فنی: رویداد مستقل از مصرف‌کننده

وضعیت اولیه: فرض کن سفارش 42 رویداد OrderPlaced رو منتشر کرده.

اجرای مرحله‌به‌مرحله: تصور کن هم گروه ارسال می‌گیرتش هم گروه تحلیل. تازه تو گروه ارسال چند worker کار رو بین خودشون تقسیم می‌کنن.

نتیجه و دلیل: یادت باشه pub/sub یعنی تکثیر بین گروه‌ها، queue یعنی تقسیم کار تو گروه. نکته ماندگار: باز هم تکرار و خطا رو باید کنترل کنی.

Queue = one message, ONE lucky consumer (chore wheel). Topic = the broker photocopies to EVERY subscriber (fan-out party). Brokers rarely dictate data shape but keep a schema registry for peace; and if you republish, carry the unknown fields along — don’t drop strangers’ luggage.

۲۰. durable execution چطور «دقیقاً یک‌بار» می‌دهد و چه محدودیت‌هایی دارد؟20. How does durable execution deliver “exactly once” — and its limits?

موتور durable پیشرفت رو ذخیره می‌کنه و بعد از crash از روی تاریخچه ادامه می‌ده. ولی «دقیقاً یه‌بار» برای دنیای بیرون مفت نیست — مقصد باید idempotent باشه یا با id تکراری مهار بشه. دوام یعنی ادامه از تاریخچه، نه یه‌بار اجرا شدن.

مثال فنی: ادامهٔ workflow بعد از crash

وضعیت اولیه: فرض کن workflow اول رزرو داره بعد صدور رسید. رزرو با شناسه r7 موفق شده.

اجرای مرحله‌به‌مرحله: تصور کن engine پیشرفت رو پایدار کرده. بعد از crash از روی تاریخچه ادامه میده. ولی فعالیتی که نتیجه‌ش ثبت نشده ممکنه دوباره صدا زده بشه.

نتیجه و دلیل: یادت باشه اثر بیرونی رزرو باید با r7 امن تکرار بشه. نکته ماندگار: دوام workflow یعنی «ادامه از تاریخچه»، نه «فقط یه‌بار اجرا».

Write down every call and state flip in durable ink; after a crash, replay and skip the done steps with their old answers. The fine print: outsiders must be idempotent (unique IDs, please), step order is sacred (new code = new version), and code must be deterministic — no dice rolls, no peeking at the clock. Durable means resumable, NOT run-once.

  • فکر کنی «JSON که schema نداره پس تکامل نمی‌خواد» — داده JSON هم سال‌ها می‌مونه و کد قدیمی می‌تونه فیلد جدید رو بی‌صدا پاک کنه.
  • دست بردن به tag تو protobuf یا دادن شماره فیلد حذف‌شده به یه فیلد جدید — یعنی داده قدیمی رو با معنای غلط می‌خونی، عملاً نابودش می‌کنی.
  • تو Avro فیلد بدون default اضافه کنی بعد تعجب کنی چرا backward ترکید — بدون default خواننده جدید داده قدیمی رو نمی‌فهمه.
  • فرض کنی همه کتابخونه‌ها فیلد ناشناخته رو نگه می‌دارن؛ این رفتار رو باید صریح چک و تست کنی، حدس نزن.
  • فکر کنی «باینری یعنی فشرده»؛ MessagePack فقط ۶۶ در برابر ۸۱ بایته — فشردگی واقعی وقتی میاد که schema اسم فیلدها رو از wire حذف کنه.
  • با RPC مثل تابع محلی رفتار کنی و timeout و retry و idempotence رو یادت بره — تهش تو پروداکشن می‌فهمی فرقشون چیه.
  • تو workflow ـی durable ترتیب activityها رو به‌هم بزنی و انتظار replay سالم داشته باشی، یا determinism رو یادت بره.
  • یادت بره تو معماری event-driven و workflow، صدا زدن API غریبه بدون idempotent بودن یعنی تکرار = دردسر.
  • Mixing backward with forward; the lifeline: always ask “WHO is reading WHAT?”
  • Thinking “JSON has no schema so who cares” — JSON data outlives code too, and old code happily wipes new fields.
  • Touching a protobuf tag or recycling a dead field’s number — congratulations, you just corrupted grandpa’s data.
  • Adding a default-less Avro field, then acting shocked when backward breaks. The default IS the deal.
  • Assuming every library preserves unknowns; check it, test it, don’t vibe it.
  • “Binary = compact”? MessagePack says 66 vs 81 — yawn. Real density is schemas deleting field names off the wire.
  • Cuddling RPC like a local function, forgetting timeouts, retries, idempotence — production will teach the difference. Painfully.
  • Shuffling durable-workflow steps and expecting a healthy replay, determinism be damned.
  • Calling a stranger’s API without idempotence in event-driven land — repeats will bite.

۵.۴ چک‌لیست مرور ۵ دقیقه‌ای قبل از مصاحبه5.4 Five-minute pre-interview checklist

  • تعریف backward/forward رو بگو + بگو تو API به request/response چی می‌شه.
  • قصه شکل ۵-۱ رو تو ۳ جمله بگو: فیلد ناشناخته چرا می‌پره و چطور جلوش رو می‌گیری.
  • سه خانواده قالب و حکم نهایی: ویژه زبان (ممنوع)، متنی (تبادل انسان‌خوان)، باینری schema-driven (فشرده و تکامل‌پذیر).
  • قاعده تکامل protobuf (تگ ثابته، اسم آزاده، حذف‌شده reserve) و Avro (default اجباری، null فقط با union، alias فقط backward).
  • سه‌جایی که writer's schema تو Avro ازش میاد + ایده resolution (ignore / default) رو بگو.
  • «data outlives code» یعنی چی و تو چهار حالت جریان داده (پایگاه داده، RPC، workflow، broker) تکلیف سازگاری چیه — جدول بخش ۴ رو از حفظ بگو.
  • پنج‌تا فرق RPC با تابع محلی + سه محدودیت durable execution (idempotence، ترتیب، determinism) رو بگو.
  1. Backward/forward cold + what they mean for requests and responses.
  2. Figure 5-1 in 3 sentences: why the unknown field dies and how you save it.
  3. Three format families and the verdict: native (banned!), textual (readable trade), schema binary (compact + evolvable).
  4. Protobuf rules (frozen tags, free renames, reserve the dead) and Avro’s (defaults or death, unions for null, backward-only aliases).
  5. Avro’s three writer-schema hideouts + resolution (ignore / default).
  6. “Data outlives code” + who owes compatibility in all four dataflows (DB, RPC, workflow, broker) — chant section 4’s table.
  7. Five RPC-vs-local diffs + three durable-execution chains (idempotence, order, determinism).
