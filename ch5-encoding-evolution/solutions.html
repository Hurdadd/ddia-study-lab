سؤال مصاحبهInterview question
داستان از این قراره که یه رکورد کوچیک داری و می‌خوای خرج JSON و MessagePack و Protobuf رو بفهمی. فرقشون توی schema و حجم و debugging رو بگو. یه tag رو دستی decode کن. بعد فیلد email رو اضافه کن و دو مسیر رو مقایسه کن: binary round-trip در برابر تبدیل به JSON، از نظر حفظ unknown field.
Honestly, friend, you've got one small record and you want to feel the cost of JSON versus MessagePack versus Protobuf. Explain how they differ in schema, size, and debugging. Decode one tag by hand. Then add an email field and compare two paths — a binary round-trip against a JSON conversion — in terms of keeping unknown fields.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

‏JSON نام همه فیلدها را حمل می‌کند (۸۱ بایت آموزشی، انسان‌خوان، بدون قاعده تکامل)؛ MessagePack همان مدل را باینری می‌کند (۶۶ بایت آموزشی) ولی نام‌ها همچنان در داده‌اند؛ Protobuf نام‌ها را با tag جایگزین می‌کند (۳۳ بایت آموزشی) به‌علاوه قواعد تکامل مشخص. نکته مصاحبه عدد بایت‌ها نیست بلکه آزمون email است: ‏round-trip باینری با runtime درست، تگ ناشناخته ۴ را حفظ می‌کند، ولی تبدیل از مسیر JSON یا کپی فیلدبه‌فیلد بی‌صدا حذفش می‌کند. سازگاری سیمی با حفظ معنا یکی نیست و هیچ‌کدام با سازگاری کد برابر نیستند.
JSON carries every field name (81 teaching bytes, human-readable, no evolution rules); MessagePack binarizes the same model (66 teaching bytes) but still ships the names; Protobuf replaces names with tags (33 teaching bytes) plus declared evolution rules. The interview point is not the byte totals but the email test: a binary round-trip through a proper runtime preserves unknown tag 4, while converting through JSON or copying field-by-field silently drops it. Wire compatibility is not meaning preservation, and neither equals code compatibility.

صورت مسئله و فرض‌هاProblem and assumptions

  • فقط رکورد آموزشی: userName=Martin, favoriteNumber=1337, interests=[daydreaming, hacking]. مجموع بایت‌های ۸۱/۶۶/۳۳ اعداد آموزشی فصل‌اند، نه بنچمارک.
  • مسیر باینری با کد تولیدشده Protobuf است که runtime آن فیلدهای ناشناخته را نگه می‌دارد؛ مسیر JSON به آبجکت JSON (یا پیام تازه ساخته‌شده فیلدبه‌فیلد) decode می‌شود که جایی برای بایت‌های ناشناخته ندارد.
  • فیلد تازه email با تگ تازه ۴ است؛ تگ بازنشسته دوباره استفاده نمی‌شود.
  • Teaching record only: userName=Martin, favoriteNumber=1337, interests=[daydreaming, hacking]. Byte totals 81/66/33 are teaching numbers from the chapter, not benchmarks.
  • Binary path uses generated Protobuf code whose runtime retains unknown fields; the JSON path decodes into a JSON object (or a fresh message built field-by-field), which has nowhere to store unknown bytes.
  • The new field is email with fresh tag 4, never reusing a retired tag.

چرا این روش و این عددها؟Why this method and these numbers?

اندازهٔ wire را با جمع tag، length و payload می‌سنجیم چون هر سه واقعاً ارسال می‌شوند. varint در هر بایت هفت بیت داده دارد، پس برای عدد مثبت ۱۳۳۷ دو بایت لازم است چون از ۱۲۷ بزرگ‌تر و از ۱۶۳۸۳ کوچک‌تر است. تفاوت ۸۱/۶۶/۳۳ به متن، فاصله‌ها، encoding و schema همین نمونه وابسته است. حفظ unknown field به runtime و مسیر round-trip وابسته است؛ JSON جای بایت ناشناخته را تضمین نمی‌کند.

Sum tag, length and payload because all travel on the wire. A varint carries seven data bits per byte: positive 1337 needs two bytes because it exceeds 127 but is below 16384. The 81/66/33 totals depend on this sample’s text, whitespace, encoding and schema. Unknown-field preservation depends on runtime and round-trip path; JSON does not guarantee retention of unknown bytes.

مدل ذهنیMental model

بایت‌ها را نامه و schema را لغت‌نامه خواننده فرض کن. JSON هر بار واژه‌های کامل را پست می‌کند؛ Protobuf کدهای شماره‌دار کوتاه می‌فرستد و دو طرف از قبل روی دفترچه کد توافق کرده‌اند. وقتی واژه تازه (تگ ۴) می‌رسد که خواننده قدیمی نیاموخته، فقط یک سؤال مهم است: خواننده قدیمی پاکت دربسته را دست‌نخورده نگه می‌دارد، یا بازش می‌کند، واژه‌هایی که می‌شناسد را رونویسی می‌کند و بقیه را دور می‌ریزد؟
Think of the bytes as a letter and the schema as the reader's dictionary. JSON posts the full words every time; Protobuf posts short numbered codes and both sides agree on the codebook in advance. When a new word (tag 4) arrives that the old reader never learned, the only question that matters is: does the old reader pocket the sealed envelope untouched, or open it, copy out the words it knows, and throw the rest away?

حل گام‌به‌گامStep by step

  1. نام‌ها روی سیم JSON نام‌ها را می‌نویسد: userName و favoriteNumber و interests داخل همان ۸۱ بایت آموزشی سفر می‌کنند، پس هر خواننده‌ای — و هر انسانی با ویرایشگر متن — ساختار را می‌بیند. هزینه: حجم، ابهام اعداد، و صفر قاعده تکامل مگر خودت registry و قرارداد اضافه کنی.
  2. همان مدل، باینری MessagePack همان مدل بدون schema را باینری می‌کند: بایت‌های نوع و طول جای گیومه و دونقطه می‌نشینند و به حدود ۶۶ بایت آموزشی می‌رسیم. نام‌ها همچنان سفر می‌کنند، اشکال‌زدایی decoder می‌خواهد، و تکامل دقیقاً به‌اندازه قراردادهای JSON خودت منضبط است — یا بی‌انضباط.
  3. یک تگ را دستی decode کن Protobuf نام‌ها را حذف می‌کند و به‌جایش تگ + نوع سیمی می‌نویسد: بایت 0x0a یعنی فیلد ۱ (0x0a >> 3) با نوع سیمی ۲ (0x0a & 7 یعنی طول‌دار)، و ۱۳۳۷ با varint دوبایتی b9 0a می‌رود. جمع: ۳۳ بایت آموزشی. تغییر نام فیلد آزاد است؛ تغییر تگ ممنوع.
  4. دو مسیر، دو سرنوشت email را با تگ ۴ اضافه کن و دو مسیر را اجرا کن. round-trip باینری (کد قدیمی تولیدشده می‌خواند و بازمی‌نویسد): runtime بایت‌های تگ ۴ را دست‌نخورده عبور می‌دهد و خواننده جدید نشانی را سالم می‌یابد. تبدیل JSON یا کپی فیلدبه‌فیلد: گام میانی فقط فیلدهای ۱ تا ۳ را می‌شناسد، پس تگ ۴ جایی برای زندگی ندارد و خواننده جدید email گمشده می‌بیند. سیم یکسان، نتیجه برعکس — تفاوت در قرارداد decoder است نه بایت‌ها.
  1. Names on the wire JSON writes the names: userName, favoriteNumber, interests travel inside the 81 teaching bytes, so any reader — and any human with a text editor — sees the structure. Cost: size, number ambiguity, and zero evolution rules unless you add a registry and conventions yourself.
  2. Same model, binary MessagePack binarizes the same schemaless model: type and length bytes replace quotes and colons, landing near 66 teaching bytes. Names still travel, debugging needs a decoder, and evolution is exactly as disciplined — or undisciplined — as your JSON conventions.
  3. Decode one tag by hand Protobuf drops the names and writes tag + wire type instead: byte 0x0a is field 1 (0x0a >> 3) with wire type 2 (0x0a & 7, length-prefixed), and 1337 rides as the two-byte varint b9 0a. Total: 33 teaching bytes. Renaming a field is free; changing a tag is forbidden.
  4. Two paths, two fates Add email as tag 4 and run the two paths. Binary round-trip (old generated code reads, rewrites): the runtime carries tag 4's bytes through untouched, and the new reader finds the address intact. JSON conversion or field-by-field copy: the middle step only knows fields 1–3, so tag 4 has nowhere to live and the new reader sees a missing email. Same wire, opposite outcomes — the difference is the decoder contract, not the bytes.

مثال محاسبه‌شدهWorked example

رکورد آموزشی {"userName":"Martin","favoriteNumber":1337,"interests":["daydreaming","hacking"]}: ‏JSON بدون فاصله = ۸۱ بایت، ‏MessagePack حدود ۶۶ بایت، ‏Protobuf برابر ۳۳ بایت (۸ بایت فیلد ۱ + ۳ بایت فیلد ۲ + ۲۲ بایت دو آیتم تکراری). افزودن email (تگ ۴، ۱۳ بایت متن + ۲ بایت قاب) رکورد باینری را به ۴۸ بایت می‌رساند؛ خواننده باینری قدیمی همچنان فیلدهای ۱ تا ۳ را می‌فهمد و تگ ۴ را ندیده عبور می‌دهد.

Teaching record {"userName":"Martin","favoriteNumber":1337,"interests":["daydreaming","hacking"]}: spaceless JSON = 81 bytes, MessagePack ≈ 66 bytes, Protobuf = 33 bytes (8 for field 1 + 3 for field 2 + 22 for the two repeated items). Adding email (tag 4, 13 text bytes + 2 framing bytes) grows the binary record to 48 bytes; the old binary reader still parses fields 1–3 and forwards tag 4 unseen.

چرا کد قدیمی بایت‌هایی را عبور می‌دهد که نمی‌فهمد؟

پاسخ: چون سازگاری forward یعنی حمل، نه فهم: ناشناخته را نادیده بگیر ولی بایت‌هایش را نگه دار.

Answer: Because forward compatibility means carrying, not comprehending: ignore the unknown but keep its bytes.

  • ماندن روی JSON با registry و بازبینی سخت‌گیرانه: اشکال‌زدایی انسان‌خوان و تبادل بین‌سازمانی می‌ماند، به قیمت payload بزرگ‌تر و قواعد تکامل دستی.
  • Stay on JSON with a registry and strict review: keeps human-readable debugging and cross-org exchange, at the cost of bigger payloads and hand-enforced evolution rules.

سناریوهای خرابیFailure scenarios

  • پراکسی قدیمی رکورد را فیلدبه‌فیلد بازنویسی می‌کند: تگ ۴ در همان گام کپی حذف می‌شود و هر خواننده جدید پایین‌دستی برای همیشه email گمشده می‌بیند — گم‌شدن داده، نه خطای parse.
  • استفاده دوباره از شماره تگ ۴ برای فیلد دیگر: ایمیل‌های رکوردهای قدیمی بی‌صدا مقدار فیلد تازه می‌شوند — خرابی‌ای که هیچ تست سازگاری بعداً نمی‌گیرد.
  • Old proxy rewrites the record field-by-field: tag 4 is dropped at the copy step and every downstream new reader permanently sees a missing email — data loss, not a parse error.
  • Reusing tag 4's number for a different field later: old records' emails silently become the new field's values — corruption no compatibility test can catch after the fact.

import java.nio.charset.StandardCharsets;

public class TagDemo {
    static byte[] varint(long n) {
        byte[] tmp = new byte[10];
        int i = 0;
        while (true) {
            int b = (int) (n & 0x7F);
            n >>>= 7;
            if (n != 0) {
                tmp[i++] = (byte) (b | 0x80);
            } else {
                tmp[i++] = (byte) b;
                break;
            }
        }
        byte[] out = new byte[i];
        System.arraycopy(tmp, 0, out, 0, i);
        return out;
    }

    static String hex(byte[] a) {
        StringBuilder sb = new StringBuilder();
        for (byte b : a) {
            sb.append(String.format("%02x", b));
        }
        return sb.toString();
    }

    static byte[] join(byte[]... parts) {
        int n = 0;
        for (byte[] p : parts) {
            n += p.length;
        }
        byte[] out = new byte[n];
        int o = 0;
        for (byte[] p : parts) {
            System.arraycopy(p, 0, out, o, p.length);
            o += p.length;
        }
        return out;
    }

    public static void main(String[] args) {
        byte[] v = varint(1337);
        System.out.println("1337 as varint: " + hex(v));
        byte[] rec = join(
                new byte[]{0x0a, 0x06}, "Martin".getBytes(StandardCharsets.UTF_8),
                new byte[]{0x10}, v,
                new byte[]{0x1a, 0x0b}, "daydreaming".getBytes(StandardCharsets.UTF_8),
                new byte[]{0x1a, 0x07}, "hacking".getBytes(StandardCharsets.UTF_8));
        System.out.println("record bytes: " + rec.length);
        int first = rec[0] & 0xFF;
        System.out.printf("first tag byte 0x%02x: field %d, wire type %d (2 = length-prefixed)%n",
                first, first >> 3, first & 7);
    }
}

پاسخ ۶۰ثانیه‌ایThe 60-second answer

افزودن فیلد اختیاری در هر دو سمت امن است: تگ تازه Protobuf (کد قدیمی رد می‌کند و نگه می‌دارد، کد جدید به داده قدیمی مقدار پیش‌فرض می‌دهد) و فیلد Avro با default خواننده (اضافه نادیده گرفته می‌شود، غایب پر می‌شود). تغییر نام در Protobuf آزاد است (نام روی سیم نیست) ولی در Avro فقط backward است (alias خواننده جدید داده قدیمی را می‌خواند؛ خواننده‌های قدیمی نام تازه را هیچ‌وقت نمی‌آموزند). تبدیل یک مقدار به چند مقدار درجا ناامن است — به نوع فیلد، packed بودن و جهت وابسته است — پس با فیلد تازه، دوره سازگاری دوگانه، تست سازگاری registry و نقشه rollback مهاجرت کن. حذف فقط وقتی آخرین مصرف‌کننده قدیمی رفت.
Adding an optional field is safe on both sides: a fresh Protobuf tag (old code skips and preserves, new code defaults old data) and an Avro field with a reader default (extras ignored, missing filled). Renaming is free in Protobuf (names are not on the wire) but backward-only in Avro (the new reader's alias reads old data; old readers never learn the new name). Changing one value into many in place is unsafe — it depends on field type, packed-ness and direction — so migrate via a NEW field with a dual-compat period, a registry compatibility test, and a rollback plan. Removal only after the last old consumer is gone.

چرا این روش و این عددها؟Why this method and these numbers?

سازگاری را جهت‌دار می‌سنجیم چون reader تازه و reader قدیم اطلاعات یکسانی ندارند؛ alias تازه نمی‌تواند reader قدیم را تغییر دهد. در Protobuf tag هویت wire است، برای همین rename باینری با تغییر tag یکسان نیست. تبدیل چند مقدار به یک مقدار ممکن است parse شود ولی بقیه را دور بریزد؛ پس معیار اصلی حفظ معناست. فیلد تازه مسیر rollback می‌دهد چون مصرف‌کنندهٔ قدیم هنوز فیلد قبلی را می‌خواند؛ حذف آن فقط بعد از خروج آخرین reader قدیمی مجاز است.

Compatibility is directional because new and old readers know different schemas; a new alias cannot teach an old reader. Protobuf wire identity is the tag, so binary renaming differs from changing tags. Reading many values as one may parse yet discard values, making semantics the criterion. A new field preserves rollback while old readers use the old field; remove it only after the last old reader retires.

مدل ذهنیMental model

قبل از «سازگار است؟» همیشه بپرس «کی نوشت، کی می‌خواند؟». ‏backward یعنی خواننده جدید نویسنده قدیمی را می‌فهمد؛ ‏forward یعنی خواننده قدیمی از نویسنده جدید جان سالم به در می‌برد. و parse شدن بدون خطا با حفظ معنا یکی نیست: خواننده رشته تکراری می‌تواند بایت‌های packed قدیمی را هم به‌اندازه مقدارها، خوشحال به آشغال تبدیل کند.
Always ask 'who wrote this, who reads it?' before 'is it compatible?'. Backward means the NEW reader understands the OLD writer; forward means the OLD reader survives the NEW writer. And parsing without an error is not the same as keeping the meaning: a repeated string reader can 'read' old packed bytes into garbage just as happily as into values.

حل گام‌به‌گامStep by step

  1. افزودن: امن در هر دو سمت افزودن اختیاری در هر دو قالب: ‏Protobuf تگ تازه می‌دهد — خواننده‌های قدیمی بایت‌هایش را رد می‌کنند و نگه می‌دارند (forward)، خواننده‌های جدید روی داده قدیمی پیش‌فرض می‌گذارند (backward). ‏Avro فیلدی با default خواننده اضافه می‌کند — خواننده‌های جدید رکوردهای قدیمی را پر می‌کنند، قدیمی‌ها اضافه را نادیده می‌گیرند. تگ‌های بازنشسته را در فهرست reserved بگذار و هرگز دوباره استفاده نکن.
  2. تغییرنام: آزاد در برابر فقط-backward تغییرنام، نامتقارن: تغییرنام در Protobuf هیچ هزینه‌ای ندارد چون نام‌ها هرگز به سیم نمی‌رسند — همان تگ، هر دو جهت سالم. ‏Avro با نام جفت می‌کند، پس خواننده جدید به alias نام قدیمی نیاز دارد: جدید-قدیمی‌خوان کار می‌کند (backward)، ولی خواننده‌های قدیمی روبه‌روی داده تازه‌نوشته نام تازه را جفت نمی‌کنند (forward می‌شکند). هرگز فرض نکن alias هر دو جهت کار می‌کند.
  3. تعداد: هرگز بازنوع نکن تغییر تعداد درجا، ناامن: تبدیل تکی به repeated در Protobuf به نوع فیلد، packed بودن فرم سیمی و جهتی که از مرز نسخه‌ها می‌گذرد وابسته است — ارتقای عددی unpackشده ممکن است لنگ‌لنگان کار کند ولی رشته‌ها و فرم‌های packed گم می‌کنند یا به‌هم می‌ریزند؛ Avro هیچ قاعده resolutionای ندارد که یک مقدار را به چند مقدار تبدیل کند. parse شدن بی‌خطا این‌جا هیچ‌چیز را درباره مقدارها ثابت نمی‌کند.
  4. مهاجرت امن با فیلد تازه مهاجرت کن: emails را کنار email اضافه کن، در پنجره سازگاری هر دو را بنویس، خواننده‌ها را گروه‌به‌گروه به فیلد تازه ببر، بعد قدیمی را deprecated کن و — فقط وقتی آخرین مصرف‌کننده قدیمی رفت — حذفش کن. اول خواننده‌ها، بعد نویسنده‌ها، حذف آخر.
  5. تست و rollback هر گام را پیش از deploy با بررسی سازگاری registry دروازه‌بانی کن و rollbackای داشته باش که نسخه قبلی schema به‌علاوه باینری قبلی را برمی‌گرداند؛ در طول پنجره خطاهای خواندن هر نسخه و شمارنده‌های حذف فیلد ناشناخته را بپا.
  1. Add: safe on both sides Add optional, both formats: Protobuf assigns a fresh tag — old readers skip and preserve its bytes (forward), new readers default it on old data (backward). Avro adds a field with a reader default — new readers fill old records, old readers ignore the extra. Remove retired tags to a reserved list and never reuse them.
  2. Rename: free vs backward-only Rename, asymmetric: Protobuf renames cost nothing because names never reach the wire — same tag, both directions fine. Avro matches by name, so the new reader needs an alias of the old name: new-reads-old works (backward), but old readers facing new-written data never pair the fresh name (forward fails). Never assume the alias works both ways.
  3. Cardinality: never retype Cardinality in place, unsafe: Protobuf singular-to-repeated depends on the field type, whether the wire form is packed, and which direction crosses versions — numeric unpacked upgrades can limp along while strings and packed forms lose or garble; Avro has no resolution rule that turns one value into many. Parsing without error here proves nothing about the values.
  4. The safe migration Migrate with a NEW field: add emails alongside email, dual-write both during the compat window, move readers to the new field one cohort at a time, then deprecate and — only after the last old consumer is gone — remove the old field. Readers-first, writers-second, drop-last.
  5. Test and rollback Gate every step with a registry compatibility check before deploy and a rollback that restores the previous schema version plus the previous binary; monitor per-version read errors and unknown-field-drop counters during the window.

Why does rollback restore both the schema and the binary?

Answer: Because reader and writer are a pair: a new schema with an old binary (or vice versa) brings the same incompatibility back.

گزینه‌های جایگزینAlternatives

  • بازنویسی یک‌جای داده ذخیره‌شده به schema تازه: بعدش برای همیشه یک نسخه، به قیمت downtime مهاجرت و کپی‌های آرشیوی که هنوز شکل قدیمی را دارند.
  • Stop-the-world rewrite of stored data to the new schema: one version forever after, at the cost of migration downtime and archived copies that still carry the old shape.

سناریوهای خرابیFailure scenarios

  • تغییر تکی‌به‌چندتایی درجا روی رشته‌ها از مسیر رندر JSON: رشته‌های تکی قدیمی و آرایه‌های تازه هر دو جهت parse می‌شوند ولی مقدارها خراب‌اند — بدترین خرابی چون مانیتورها سبز می‌مانند.
  • حذف فیلد قدیمی وقتی مصرف‌کننده‌های عقب‌مانده هنوز می‌خوانندش: decodeهایشان پیش‌فرض می‌گذارد یا داده موردنیاز را می‌اندازد — حذف را با شاهد عقب‌ماندگی مصرف‌کننده زمان‌بندی کن، نه با تقویم.
  • In-place singular-to-repeated on strings via JSON rendering: old single strings and new arrays parse in both directions yet values corrupt — the worst failure because monitors stay green.
  • Removing the old field while lagging consumers still read it: their decodes default or drop data they still need — schedule removal by consumer-lag evidence, not by calendar.

public class CompatDemo {
    // Teaching model of the chapter's evolution rules (not the real
    // libraries): prints the verdict matrix and measures packed vs
    // unpacked repeated-int32 bytes to show why packing matters.

    static int varintLen(int n) {
        int l = 1;
        while ((n >>>= 7) != 0) {
            l++;
        }
        return l;
    }

    public static void main(String[] args) {
        int[] vals = {25, 31, 44};
        int unpacked = 0;
        int packedBody = 0;
        for (int v : vals) {
            unpacked += 1 + varintLen(v);
            packedBody += varintLen(v);
        }
        int packed = 1 + varintLen(packedBody) + packedBody;
        System.out.println("repeated int32 x3 unpacked bytes: " + unpacked);
        System.out.println("repeated int32 x3 packed bytes: " + packed);
        String[][] rows = {
            {"add optional", "B ok F ok", "B ok F ok (default)"},
            {"rename", "B ok F ok", "B ok (alias) F no"},
            {"one-to-many in place", "depends: do not", "no rule: do not"},
        };
        for (String[] r : rows) {
            System.out.println(r[0] + " | protobuf " + r[1] + " | avro " + r[2]);
        }
        if (unpacked != 6 || packed != 5) {
            throw new AssertionError("packing math moved");
        }
        System.out.println("packing check: unpacked=6 packed=5, verdicts as taught");
    }
}

اشتباهات رایجCommon mistakes

  • فرض این‌که alias در Avro هر دو جهت کار می‌کند. فقط به خواننده جدید نام قدیمی را می‌آموزد؛ خواننده‌های قدیمی از نام تازه بی‌خبر می‌مانند.
  • گفتن تکی‌به‌چندتایی «سازگار است چون parse می‌شود». قابل‌تجزیه بودن بدون نگاشت بی‌اتلاف مقدار، مانیتور سبز روی داده خراب است.
  • افزودن فیلد Avro بدون default و مقصر دانستن registry. قاعده صریح است: بدون default، سازگاری backward نیست.
  • Assuming an Avro alias works both ways. It only teaches the NEW reader the old name; old readers stay ignorant of the new one.
  • Calling singular-to-repeated 'compatible because it parses'. Parseability without a lossless value mapping is a green monitor over corrupt data.
  • Adding an Avro field without a default and blaming the registry. The rule is explicit: no default, no backward compatibility.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

به هر گام شناسه پایدار بده (order id + step name + code version)، نتیجه هر گام را پیش از اعلام موفقیت در لاگ پایدار بنویس، و بازپخش را با همان شناسه‌ها دوباره قدم بزن: گام‌های ثبت‌شده رد می‌شوند و نتیجه قبلی‌شان برمی‌گردد. گام‌های برگشت‌ناپذیر جبران روبه‌جلو (saga) می‌گیرند، نه بازگشت در زمان. تغییر ترتیب، شاخه یا payload را با نسخه تازه کد منتشر کن — invocationهای در جریان با همان قدیمی تمام می‌شوند. هزینه recovery خواندن‌های محدود بازپخش است به‌علاوه، برای ارسال‌کننده بدون کلید، یک جاروی مغایرت‌گیری.
Give every step a stable id (order id + step name + code version), append each result to the durable log BEFORE reporting success, and replay by re-walking with the same ids: logged steps are skipped with old results returned. Irreversible steps get forward compensations (saga), never rollbacks in time. Ship step-order, branch or payload changes as a NEW code version — in-flight invocations finish on the old one. Recovery cost is bounded replay reads plus, for the keyless shipper, a reconciliation sweep.

صورت مسئله و فرض‌هاProblem and assumptions

  • گردش‌کار آموزشی سه‌گامی سفارش: رزرو موجودی، شارژ کارت، ارسال مرسوله. کرش هرجا ممکن است، از جمله میان اثر و نوشتن لاگ — بدترین حالت.
  • درگاه پرداخت کلید idempotency می‌پذیرد؛ ارسال‌کننده طرح پایه روی شناسه گام ما تکراری‌زدایی می‌کند. ارسال‌کننده بدون کلید سناریوی پیگیری است.
  • اعداد هزینه recovery پایین کران‌های آموزشی همین گردش‌کارند، نه ردپای اندازه‌گیری‌شده.
  • Teaching three-step order workflow: reserve stock, charge card, ship parcel. Crash may strike anywhere, including between the effect and the log append — the worst case.
  • Payment gateway accepts an idempotency key; the base-design shipper dedups on our step id. The keyless shipper is the follow-up scenario.
  • Recovery-cost numbers below are teaching bounds for this workflow, not measured traces.

چرا این روش و این عددها؟Why this method and these numbers?

نتیجهٔ step باید ثبت شود تا replay همان تصمیم را ادامه دهد؛ اما crash پس از charge و پیش از ثبت نتیجه هنوز مبهم است. کلید ثابتِ همان step به gateway اجازه می‌دهد retry را همان عملیات بداند؛ شناسهٔ تازه در هر retry این خاصیت را از بین می‌برد. نسخهٔ workflow در invocation ثبت می‌شود تا replay بعد از deploy کد جدید مسیر دیگری نرود. تعداد step و هزینهٔ recovery، ویژگی سناریو هستند و باید با تعداد invocation و مدت retention مقیاس داده شوند.

Persist each step result so replay follows the original decision. A crash after charging but before logging is still ambiguous; a stable step key lets the gateway recognize the retry, while a new key per retry defeats it. Bind workflow version to invocation so deployments do not change replay paths. Recovery cost scales with invocation count, step count and retention, not a universal constant.

مدل ذهنیMental model

موتور پس از کرش فراموشی کامل دارد جز یک چیز: لاگ پایدار. بازپخش یعنی قدم‌زدن دوباره همان مسیر کد با همان شناسه‌ها و پرسیدن از لاگ در هر گام: قبلاً انجام شده؟ پس استفاده مجدد. جبران سفر در زمان نیست — گام تازه روبه‌جلوست که اثر قدیمی را خنثی می‌کند (بازپرداخت پس از شارژ).
The engine has total amnesia after a crash except for one thing: the durable log. Replay is re-walking the same code path with the same step ids and asking the log at every step: done already? Then reuse. Compensation is not time travel — it is a new forward step that undoes an old effect (refund after charge).

حل گام‌به‌گامStep by step

  1. شناسه پایدار شناسه هر گام از سه تکه ساخته می‌شود: شناسه سفارش + نام گام + نسخه کد (order:1001:ship:v1). در retry همان شناسه تکرار می‌شود، پس اثر دوباره با همان کلید به مقصد می‌رسد و تکراری‌زدایی ممکن می‌شود.
  2. اول لاگ، بعد اعلام نتیجه هر گام موفق پیش از اعلام موفقیت در لاگ پایدار نوشته می‌شود. اگر کرش میان اثر و لاگ بیفتد، گام «باز» می‌ماند و دوباره اجرا می‌شود — برای همین اثرها باید idempotent باشند.
  3. بازپخش و تحویل تکراری restart تاریخچه را می‌خواند و با همان شناسه‌ها قدم می‌زند: reserve و charge رد می‌شوند (نتیجه قدیمی برمی‌گردد) و فقط ship باز اجرا می‌شود. تحویل تکراری نتیجه ship هم فقط reuse است، نه مرسوله دوم.
  4. جبران روبه‌جلو اگر ship پس از charge ناممکن شود، تاریخ به عقب برنمی‌گردد: گام تازه refund شارژ را برمی‌گرداند و release موجودی را آزاد می‌کند. هر جبران خودش شناسه پایدار و نتیجه ثبت‌شده دارد.
  5. نسخه‌بندی و هزینه تغییر ترتیب گام‌ها، شاخه‌بندی یا payload با نسخه تازه (v2) منتشر می‌شود؛ invocationهای در جریان با v1 تمام می‌شوند چون تاریخچه v1 فقط با کد v1 قدم زده می‌شود. هزینه recovery: بازخوانی تاریخچه (کران آموزشی: تعداد گام‌ها) به‌علاوه جاروی مغایرت‌گیری برای ارسال‌کننده بدون کلید.
  1. Stable ids Each step id has three parts: order id + step name + code version (order:1001:ship:v1). Retries repeat the same id, so a repeated effect reaches the destination under the same key and dedups.
  2. Log first, then report Each successful step's result lands in the durable log before success is reported. A crash between effect and log leaves the step 'open' to run again — which is why effects must be idempotent.
  3. Replay and duplicates The restart loads history and re-walks with the same ids: reserve and charge are skipped (old results returned) and only ship re-runs. Duplicate delivery of the ship result is also just reuse, never a second parcel.
  4. Forward compensation If shipping becomes impossible after charging, history does not rewind: a fresh refund step returns the charge and a release step frees the stock. Each compensation carries its own stable id and logged result.
  5. Versioning and cost Step-order, branch or payload changes ship as a new version (v2); in-flight invocations finish on v1 because v1 history is only ever walked by v1 code. Recovery cost: re-reading history (teaching bound: number of steps) plus a reconciliation sweep for the keyless shipper.

طراحی مشخصConcrete design

اجزا: orchestrator (زمان‌بندی، مالک دروازه نسخه)، لاگ پایدار (write-ahead، تاریخچه هر invocation)، اجراکننده‌های گام (رزرو/شارژ/ارسال، هرکدام کلیددار)، جبران‌کننده‌ها (بازپرداخت، آزادسازی، لغو مرسوله). مسیر نوشتن: اجرای گام ← نوشتن نتیجه ← اعلام. مسیر خواندن (بازپخش): بارگذاری تاریخچه ← قدم‌زدن دوباره کد با همان شناسه‌ها ← ثبت‌شده رد، باز اجرا. کلیدها: order:{id}:reserve:{v} و charge و ship.

Components: orchestrator (schedules, owns the version gate), durable log (write-ahead, per-invocation history), step executors (reserve/charge/ship, each keyed), compensation handlers (refund, release, cancel-parcel). Write path: execute step → append result → report. Read path (replay): load history → re-walk code with same ids → skip logged, run open. Keys: order:{id}:reserve:{v}, order:{id}:charge:{v}, order:{id}:ship:{v}.

گزینه‌های جایگزینAlternatives

  • کوروگرافی رویدادی بدون orchestrator: هر سرویس به رویداد قبلی واکنش نشان می‌دهد. هزینه: تاریخچه پراکنده، بازپخش و نسخه‌بندی سخت‌تر، جبران بدون مالک واحد.
  • Event choreography with no orchestrator: each service reacts to the previous event. Cost: scattered history, harder replay and versioning, compensation with no single owner.

سناریوهای خرابیFailure scenarios

  • کرش میان اثر ship و نوشتن لاگ: ship دوباره اجرا می‌شود. با تکراری‌زدایی روی شناسه، مرسوله دوم ساخته نمی‌شود؛ بدون کلید، جاروی مغایرت‌گیری مرسوله‌های بی‌صاحب را به سفارش وصل می‌کند.
  • بازپخش تاریخچه v1 با کد v2 جابه‌جاشده: دروازه نسخه جلوی قدم‌زدن اشتباه را می‌گیرد و invocation را به کد v1 میخ می‌کند.
  • شکست خود جبران (مثلاً refund ناموفق): جبران retry می‌شود با همان شناسه؛ پس از پایان بودجه، هشدار انسانی با حالت دقیق لاگ — invocation نه «نیمه‌تمام رها» بلکه «منتظر اقدام» است.
  • Crash between the ship effect and the log write: ship re-runs. With dedup on the step id no second parcel is made; without a key, the reconciliation sweep attaches orphan parcels to the order.
  • Replaying v1 history against reordered v2 code: the version gate blocks the wrong walk and pins the invocation to v1 code.
  • The compensation itself fails (e.g. refund rejected): it retries under the same id; after the budget, a human alert with the exact log state — the invocation is 'awaiting action', never 'abandoned halfway'.

import java.util.LinkedHashMap;
import java.util.Map;
import java.util.TreeSet;
import java.util.function.Supplier;

public class WorkflowDemo {
    // Durable log: step id -> result. Teaching stand-in for a write-ahead log.
    static Map<String, String> log = new LinkedHashMap<>();

    static String runStep(String id, Supplier<String> fn) {
        if (log.containsKey(id)) {
            System.out.println("replay " + id + ": skip, reuse " + log.get(id));
            return log.get(id);
        }
        String r = fn.get();
        log.put(id, r); // append BEFORE reporting success
        System.out.println("exec   " + id + ": " + r + " (logged)");
        return r;
    }

    public static void main(String[] args) {
        String wid = "order-1001";
        runStep(wid + ":reserve:v1", () -> "stock-42 reserved");
        runStep(wid + ":charge:v1", () -> "pay-7 charged");
        System.out.println("-- crash before ship; restart replays --");
        runStep(wid + ":reserve:v1", () -> "stock-42 reserved");
        runStep(wid + ":charge:v1", () -> "pay-7 charged");
        runStep(wid + ":ship:v1", () -> "parcel-9 created");
        System.out.println("-- duplicate delivery of ship result --");
        runStep(wid + ":ship:v1", () -> "parcel-9 created");
        System.out.println("durable log keys: " + new TreeSet<>(log.keySet()));
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): provider ارسال idempotency key نداره. تضمینت چطور عوض می‌شه؟Follow-up (Staff): The shipping provider has no idempotency key. How does your guarantee change?

تضمین از «اثر دقیقاً یک‌بار» به «حداکثر یک مرسوله بی‌صاحب + مغایرت‌گیری» می‌لغزد: retry کور ممنوع، چون هر تلاش ممکن است مرسوله تازه بسازد. به‌جایش: ship را یک بار صدا بزن، نتیجه نامشخص را «نامعلوم» ثبت کن، و جاروی مغایرت‌گیری (تطبیق مرسوله‌ها با شناسه سفارش در سمت خودت) اثر را قطعی کند. هزینه recovery همان جاروست.

The guarantee slides from 'exactly-once effects' to 'at most one orphan parcel + reconciliation': blind retries are banned, since each attempt may mint a fresh parcel. Instead: call ship once, record an unclear outcome as 'unknown', and let a reconciliation sweep (matching parcels to your order id on your side) settle the effect. Recovery cost is that sweep.

اشتباهات رایجCommon mistakes

  • قول «exactly-once» برای اثر بیرونی. لاگ پایدار اجرای دقیقاً یک‌بار می‌دهد، نه اثر دقیقاً یک‌بار — اثر به کلید مقصد وابسته است.
  • استفاده از عدد تصادفی یا ساعت سیستم در کد workflow. بازپخش باید قطعی باشد؛ همان ورودی، همان قدم‌ها.
  • جابه‌جایی آزاد ترتیب گام‌ها روی invocationهای در جریان. تاریخچه قدیمی فقط با منطق قدیمی قدم زده می‌شود — تغییر، نسخه تازه می‌خواهد.
  • Promising 'exactly-once' for outside effects. The durable log delivers exactly-once execution, not exactly-once effects — effects depend on the destination's key.
  • Using random numbers or the system clock in workflow code. Replay must be deterministic; same input, same walk.
  • Freely reordering steps over in-flight invocations. Old history is only ever walked by old logic — change needs a new version.
