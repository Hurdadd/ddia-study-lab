سؤال مصاحبهInterview question
داستان از این قراره که یه رکورد کوچیک داری و می‌خوای خرج JSON و MessagePack و Protobuf رو بفهمی. فرقشون توی schema و حجم و debugging رو بگو. یه tag رو دستی decode کن. بعد فیلد email رو اضافه کن و دو مسیر رو مقایسه کن: binary round-trip در برابر تبدیل به JSON، از نظر حفظ unknown field.
Honestly, friend, you've got one small record and you want to feel the cost of JSON versus MessagePack versus Protobuf. Explain how they differ in schema, size, and debugging. Decode one tag by hand. Then add an email field and compare two paths — a binary round-trip against a JSON conversion — in terms of keeping unknown fields.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که اسم فیلدها روی سیم می‌مونن یا نه. JSON اسم همهٔ فیلدها رو حمل می‌کنه (۸۱ بایت آموزشی، آدم‌خوان، بدون قاعدهٔ تکامل)؛ MessagePack همون مدل رو باینری می‌کنه (۶۶ بایت آموزشی) ولی اسم‌ها همچنان توی داده‌ان؛ Protobuf اسم‌ها رو با tag جایگزین می‌کنه (۳۳ بایت آموزشی) به‌علاوهٔ قواعد تکامل مشخص. ولی نکتهٔ مصاحبه اصلاً عدد بایت‌ها نیست؛ آزمون email است: ‏round-trip باینری با runtime درست تگ ناشناخته ۴ رو نگه می‌داره، ولی تبدیل از مسیر JSON یا کپی فیلدبه‌فیلد بی‌صدا حذفش می‌کنه. سازگاری سیمی با حفظ معنا یکی نیست و هیچ‌کدومشون با سازگاری کد برابر نیستن — این رو قاب کن.
Here's the thing — the whole difference is whether field names ride along on the wire. JSON carries every name (81 teaching bytes, human-readable, no evolution rules); MessagePack binarizes the same model (66 teaching bytes) but still ships the names; Protobuf swaps the names for tags (33 teaching bytes) plus declared evolution rules. But the interview point isn't the byte totals, it's the email test: a binary round-trip through a proper runtime preserves unknown tag 4, while converting through JSON or copying field-by-field silently drops it. Wire compatibility is not meaning preservation, and neither one equals code compatibility. Remember that.

صورت مسئله و فرض‌هاProblem and assumptions

  • فقط رکورد آموزشی: userName=Martin, favoriteNumber=1337, interests=[daydreaming, hacking]. مجموع بایت‌های ۸۱/۶۶/۳۳ هم اعداد آموزشی فصل‌ان، نه بنچمارک.
  • مسیر باینری با کد تولیدشدهٔ Protobuf کار می‌کنه و runtime اون فیلدهای ناشناخته رو نگه می‌داره. مسیر JSON اما به آبجکت JSON (یا پیام تازه ساخته‌شده فیلدبه‌فیلد) decode می‌شه، و اون‌جا جایی برای بایت‌های ناشناخته نیست.
  • ایده‌ش ساده‌ست: فیلد تازهٔ email با تگ تازهٔ ۴ میاد؛ تگ بازنشسته رو دوباره استفاده نمی‌کنی.
  • Teaching record only: userName=Martin, favoriteNumber=1337, interests=[daydreaming, hacking]. The byte totals 81/66/33 are teaching numbers from the chapter, not benchmarks.
  • The binary path uses generated Protobuf code, and its runtime keeps unknown fields around. The JSON path instead decodes into a JSON object (or a fresh message built field-by-field) — and there's nowhere there to put unknown bytes.
  • The idea is simple: the new field email comes in with a fresh tag 4, and you never reuse a retired tag.

چرا این روش و این عددها؟Why this method and these numbers?

اندازهٔ wire را با جمع tag، length و payload می‌سنجیم، چون هر سه واقعاً روی سیم می‌رن. varint در هر بایت هفت بیت داده جا می‌ده، پس عدد مثبت ۱۳۳۷ دو بایت می‌خواد: از ۱۲۷ بزرگ‌تره و از ۱۶۳۸۳ کوچک‌تر. تفاوت ۸۱/۶۶/۳۳ به متن، فاصله‌ها، encoding و schema همین نمونه وابسته‌ست — با دادهٔ خودت عوض می‌شه. و حفظ unknown field کارِ runtime و مسیر round-tripه؛ JSON هیچ تضمینی برای جای بایت ناشناخته نداره.

We sum tag, length and payload because all three really do travel on the wire. A varint packs seven data bits into every byte, so positive 1337 needs two bytes — it exceeds 127 but stays below 16384. The 81/66/33 totals belong to this sample's text, whitespace, encoding and schema; swap in your own data and they move. Unknown-field preservation is the runtime's and the round-trip path's job; JSON gives you no guarantee that unknown bytes are kept.

مدل ذهنیMental model

تصور کن بایت‌ها نامه‌ان و schema لغت‌نامهٔ خواننده. JSON هر بار واژه‌های کامل رو پست می‌کنه؛ Protobuf کدهای شماره‌دار کوتاه می‌فرسته و دو طرف از قبل روی دفترچهٔ کد توافق کردن. حالا واژهٔ تازه‌ای (تگ ۴) می‌رسه که خوانندهٔ قدیمی نیاموخته؛ فقط یک سؤال مهم مونده: خوانندهٔ قدیمی پاکت دربسته رو دست‌نخورده نگه می‌داره، یا بازش می‌کنه، واژه‌هایی که می‌شناسه رو رونویسی می‌کنه و بقیه رو دور می‌ریزه?
Picture the bytes as a letter and the schema as the reader's dictionary. JSON posts the full words every time; Protobuf posts short numbered codes, and both sides agreed on the codebook in advance. Then a new word (tag 4) shows up that the old reader never learned — and there's really only one question that matters: does that old reader pocket the sealed envelope untouched, or open it, copy out the words it knows and toss the rest?

حل گام‌به‌گامStep by step

  1. اسم‌ها روی سیم JSON اسم‌ها رو می‌نویسه: userName و favoriteNumber و interests داخل همون ۸۱ بایت آموزشی سفر می‌کنن؛ هر خواننده‌ای — و هر آدمی با ویرایشگر متن — ساختار رو می‌بینه. هزینه‌اش هم سه‌تاست: حجم، ابهام اعداد، و صفر قاعدهٔ تکامل، مگر خودت registry و قرارداد اضافه کنی.
  2. همون مدل، باینری MessagePack همون مدلِ بدون schema رو باینری می‌کنه: بایت‌های نوع و طول جای گیومه و دونقطه می‌نشینن و می‌رسیم به حدود ۶۶ بایت آموزشی. اسم‌ها همچنان سفر می‌کنن، اشکال‌زدایی decoder می‌خواد، و تکامل دقیقاً به‌اندازهٔ قراردادهای JSON خودت منضبطه — یا بی‌انضباط.
  3. یک تگ را دستی decode کن Protobuf اسم‌ها رو حذف می‌کنه و به‌جایش تگ + نوع سیمی می‌نویسه: بایت 0x0a یعنی فیلد ۱ (0x0a >> 3) با نوع سیمی ۲ (0x0a & 7 یعنی طول‌دار)، و ۱۳۳۷ با varint دوبایتی b9 0a می‌ره. جمع: ۳۳ بایت آموزشی. تغییر اسم فیلد آزاده؛ تغییر تگ ممنوع.
  4. دو مسیر، دو سرنوشت email رو با تگ ۴ اضافه کن و دو مسیر رو اجرا کن. round-trip باینری (کد قدیمیِ تولیدشده می‌خونه و بازمی‌نویسه): runtime بایت‌های تگ ۴ رو دست‌نخورده عبور می‌ده و خوانندهٔ جدید نشانی رو سالم می‌یابه. تبدیل JSON یا کپی فیلدبه‌فیلد: گام میانی فقط فیلدهای ۱ تا ۳ رو می‌شناسه؛ تگ ۴ جایی برای زندگی نداره و خوانندهٔ جدید email گمشده می‌بینه. سیم یکسان، نتیجه برعکس — فرق در قرارداد decoder است، نه در بایت‌ها.
  1. Names on the wire JSON writes the names out: userName, favoriteNumber, interests all travel inside the 81 teaching bytes, so any reader — and any human with a text editor — sees the structure straight away. The bill comes due in three places: size, number ambiguity, and zero evolution rules unless you add a registry and conventions yourself.
  2. Same model, binary MessagePack takes that same schemaless model and packs it into bytes: type and length bytes take the place of quotes and colons, and you land near 66 teaching bytes. The names still travel, debugging now wants a decoder, and evolution is exactly as disciplined — or as undisciplined — as your JSON conventions happen to be.
  3. Decode one tag by hand Protobuf drops the names and writes tag + wire type instead. Byte 0x0a is field 1 (0x0a >> 3) with wire type 2 (0x0a & 7, length-prefixed), and 1337 rides along as the two-byte varint b9 0a. Total: 33 teaching bytes. Renaming a field is free; changing a tag is forbidden.
  4. Two paths, two fates Add email as tag 4 and run both paths. Binary round-trip (old generated code reads, then rewrites): the runtime carries tag 4's bytes through untouched, and the new reader finds the address intact. JSON conversion or field-by-field copy: the middle step only knows fields 1–3, so tag 4 has nowhere to live and the new reader sees a missing email. Same wire, opposite outcomes — the difference is the decoder contract, not the bytes.

مثال محاسبه‌شدهWorked example

رکورد آموزشی {"userName":"Martin","favoriteNumber":1337,"interests":["daydreaming","hacking"]}: ‏JSON بدون فاصله = ۸۱ بایت، ‏MessagePack حدود ۶۶ بایت، ‏Protobuf برابر ۳۳ بایت (۸ بایت فیلد ۱ + ۳ بایت فیلد ۲ + ۲۲ بایت دو آیتم تکراری). حالا email (تگ ۴، ۱۳ بایت متن + ۲ بایت قاب) رو اضافه کن: رکورد باینری می‌ره روی ۴۸ بایت؛ خوانندهٔ باینریِ قدیمی همچنان فیلدهای ۱ تا ۳ رو می‌فهمه و تگ ۴ رو ندیده عبور می‌ده. همین‌جاست که می‌بینی حجم یه داستانه و سرنوشت فیلد یه داستان دیگه.

Teaching record {"userName":"Martin","favoriteNumber":1337,"interests":["daydreaming","hacking"]}: spaceless JSON = 81 bytes, MessagePack ≈ 66 bytes, Protobuf = 33 bytes (8 for field 1 + 3 for field 2 + 22 for the two repeated items). Now add email (tag 4, 13 text bytes + 2 framing bytes) and the binary record grows to 48 bytes; the old binary reader still parses fields 1–3 and forwards tag 4 unseen. Size is one story, the field's fate is another — that's the whole point.

Which paths in the diagram preserve tag 4 — and why can't the JSON path?

Answer: Only the binary round-trip through a preserving runtime. JSON text has no slot for tag 4's bytes, so anything that passes through a JSON-shaped model loses it on the way.

گزینه‌های جایگزینAlternatives

  • اگه بخوای روی JSON بمونی، باید یه registry و یه بازبینی سخت‌گیرانه هم کنارش بذاری: اشکال‌زدایی آدم‌خوان و تبادل بین‌سازمانی می‌مونه، به قیمت payload بزرگ‌تر و قواعد تکاملی که با دست نگه داشته می‌شن.
  • Stay on JSON, but then you owe it a registry and a strict review process: you keep human-readable debugging and easy cross-org exchange, and you pay for it with bigger payloads plus evolution rules that somebody has to enforce by hand.

سناریوهای خرابیFailure scenarios

  • پراکسی قدیمی رکورد رو فیلدبه‌فیلد بازنویسی می‌کنه: تگ ۴ توی همون گام کپی حذف می‌شه و هر خوانندهٔ جدید پایین‌دستی برای همیشه email گمشده می‌بینه — این خطای parse نیست، گم‌شدن داده‌ست.
  • شمارهٔ تگ ۴ رو برای فیلد دیگه‌ای دوباره استفاده کنی: ایمیل‌های رکوردهای قدیمی بی‌صدا می‌شن مقدارِ فیلد تازه — خرابی‌ای که هیچ تست سازگاری بعداً نمی‌گیره.
  • An old proxy rewrites the record field by field: tag 4 gets dropped at the copy step, and every downstream new reader permanently sees a missing email. That's data loss, not a parse error.
  • Reusing tag 4's number for a different field later on: old records' emails quietly turn into the new field's values. That's corruption no compatibility test can catch after the fact.

import java.nio.charset.StandardCharsets;

public class TagDemo {
    static byte[] varint(long n) {
        byte[] tmp = new byte[10];
        int i = 0;
        while (true) {
            int b = (int) (n & 0x7F);
            n >>>= 7;
            if (n != 0) {
                tmp[i++] = (byte) (b | 0x80);
            } else {
                tmp[i++] = (byte) b;
                break;
            }
        }
        byte[] out = new byte[i];
        System.arraycopy(tmp, 0, out, 0, i);
        return out;
    }

    static String hex(byte[] a) {
        StringBuilder sb = new StringBuilder();
        for (byte b : a) {
            sb.append(String.format("%02x", b));
        }
        return sb.toString();
    }

    static byte[] join(byte[]... parts) {
        int n = 0;
        for (byte[] p : parts) {
            n += p.length;
        }
        byte[] out = new byte[n];
        int o = 0;
        for (byte[] p : parts) {
            System.arraycopy(p, 0, out, o, p.length);
            o += p.length;
        }
        return out;
    }

    public static void main(String[] args) {
        byte[] v = varint(1337);
        System.out.println("1337 as varint: " + hex(v));
        byte[] rec = join(
                new byte[]{0x0a, 0x06}, "Martin".getBytes(StandardCharsets.UTF_8),
                new byte[]{0x10}, v,
                new byte[]{0x1a, 0x0b}, "daydreaming".getBytes(StandardCharsets.UTF_8),
                new byte[]{0x1a, 0x07}, "hacking".getBytes(StandardCharsets.UTF_8));
        System.out.println("record bytes: " + rec.length);
        int first = rec[0] & 0xFF;
        System.out.printf("first tag byte 0x%02x: field %d, wire type %d (2 = length-prefixed)%n",
                first, first >> 3, first & 7);
    }
}

بایت‌های تگ ۴ اصلاً به پیام تازه نمی‌رسن: پراکسی به مدلی decode می‌کنه که فقط فیلدهای ۱ تا ۳ رو داره، بعد از همون مدل دوباره encode می‌کنه. email برای هر خوانندهٔ پایین‌دستی رفته، با این‌که هیچ خطایی رخ نداده. راه‌حل: به‌جای کپی کردن فیلدهای شناخته‌شده، بایت‌های ناشناخته رو دست‌نخورده عبور بده (یا schema پراکسی رو به‌روز کن).

The bytes for tag 4 never make it into the fresh message: the proxy decodes into a model that only holds fields 1–3, then re-encodes straight from that model. The email is gone for every downstream reader, and nothing errored on the way. So the fix is to forward the opaque bytes (or upgrade the proxy's schema) instead of copying the fields it happens to recognize.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که اول باید جهت رو نام ببری، بعد حکم بدی. افزودن فیلد اختیاری در هر دو سمت امنه: تگ تازهٔ Protobuf (کد قدیمی ردش می‌کنه و نگهش می‌داره، کد جدید به دادهٔ قدیمی مقدار پیش‌فرض می‌ده) و فیلد Avro با default سمت خواننده (اضافه نادیده گرفته می‌شه، غایب پر می‌شه). تغییر اسم توی Protobuf آزاده (اسم اصلاً روی سیم نمی‌ره)، ولی توی Avro فقط backward جواب می‌ده (alias خوانندهٔ جدید دادهٔ قدیمی رو می‌خونه؛ خواننده‌های قدیمی اسم تازه رو هیچ‌وقت یاد نمی‌گیرن). تبدیل یه مقدار به چند مقدار درجا ناامنه — به نوع فیلد، packed بودن و جهت بستگی داره — پس با فیلد تازه، دورهٔ سازگاری دوگانه، تست سازگاری registry و نقشهٔ rollback مهاجرت کن. حذف هم فقط وقتی آخرین مصرف‌کنندهٔ قدیمی رفت. یادت باشه: همیشه اول جهت، بعد حکم.
Here's the thing: name the direction first, then hand out the verdict. Adding an optional field is safe on both sides: a fresh Protobuf tag (old code skips and preserves, new code defaults old data) and an Avro field with a reader default (extras ignored, missing filled). Renaming is free in Protobuf (names never hit the wire) but backward-only in Avro (the new reader's alias reads old data; old readers never learn the new name). Turning one value into many in place is unsafe — it depends on the field type, packed-ness and the direction — so migrate through a NEW field with a dual-compat window, a registry compatibility test and a rollback plan. And removal only after the last old consumer is gone. Direction first, verdict second — that's the whole answer.

  • حفظ کن: بررسی‌های سازگاری registry و پنجره‌های انتشار پایین، اعداد سیاستی آموزشی‌ان — نه ردپای اندازه‌گیری‌شده.

چرا این روش و این عددها؟Why this method and these numbers?

سازگاری رو جهت‌دار می‌سنجیم، چون خوانندهٔ تازه و خوانندهٔ قدیم اطلاعات یکسانی ندارن؛ یه alias تازه نمی‌تونه خوانندهٔ قدیم رو عوض کنه. توی Protobuf هویت روی سیم همون tag است، برای همین rename باینری با تغییر tag فرق داره. تبدیل چند مقدار به یک مقدار ممکنه parse بشه ولی بقیه رو دور بریزه؛ پس معیار اصلی حفظ معناست. فیلد تازه مسیر rollback می‌ده، چون مصرف‌کنندهٔ قدیم هنوز فیلد قبلی رو می‌خونه؛ حذفش هم فقط بعد از رفتن آخرین خوانندهٔ قدیمی مجازه.

Compatibility is directional because the new and old readers know different schemas; a fresh alias can't teach an old reader anything. On the Protobuf wire the identity is the tag, so renaming in binary is a different thing from changing a tag. Reading many values as one may parse and still throw values away, which is why semantics is the real criterion. A new field keeps the rollback path open, since the old consumer still reads the old field; you only remove it after the last old reader retires.

مدل ذهنیMental model

قبل از این‌که بپرسی «سازگار هست؟»، همیشه بپرس «کی نوشت، کی می‌خونه؟». ‏backward یعنی خوانندهٔ جدید نویسندهٔ قدیمی رو می‌فهمه؛ ‏forward یعنی خوانندهٔ قدیمی از نویسندهٔ جدید سالم رد می‌شه. یه چیز دیگه هم یادت نره: parse شدن بدون خطا با حفظ معنا یکی نیست — خوانندهٔ رشتهٔ تکراری می‌تونه بایت‌های packed قدیمی رو هم به‌اندازهٔ مقدارها، خوشحالانه تبدیل به آشغال کنه.
Before you ask 'is it compatible?', always ask 'who wrote this, who reads it?'. Backward means the NEW reader understands the OLD writer; forward means the OLD reader survives the NEW writer. And one more thing: parsing without an error is not the same as keeping the meaning — a repeated-string reader will happily 'read' old packed bytes into garbage, exactly as happily as into values.

حل گام‌به‌گامStep by step

  1. افزودن: امن در هر دو سمت افزودن اختیاری، هر دو قالب: ‏Protobuf یه تگ تازه می‌ده — خواننده‌های قدیمی بایت‌هاش رو رد می‌کنن و نگه می‌دارن (forward)، خواننده‌های جدید روی دادهٔ قدیمی پیش‌فرض می‌ذارن (backward). ‏Avro یه فیلد با default خواننده اضافه می‌کنه — خواننده‌های جدید رکوردهای قدیمی رو پر می‌کنن، قدیمی‌ها اضافه رو نادیده می‌گیرن. تگ‌های بازنشسته رو هم بذار توی فهرست reserved و هرگز دوباره استفاده نکن.
  2. تغییر اسم: آزاد در برابر فقط-backward تغییر اسم، نامتقارن: توی Protobuf تغییر اسم هیچ هزینه‌ای نداره، چون اسم‌ها هرگز به سیم نمی‌رسن — همون تگ، هر دو جهت سالم. ‏Avro با اسم جفت می‌کنه، پس خوانندهٔ جدید به alias اسم قدیمی نیاز داره: جدید-قدیمی‌خوان کار می‌کنه (backward)، ولی خواننده‌های قدیمی روبه‌روی دادهٔ تازه‌نوشته اسم تازه رو جفت نمی‌کنن (forward می‌شکنه). هرگز فرض نکن alias هر دو جهت کار می‌کنه.
  3. تعداد: هرگز بازنوع نکن تغییر تعداد درجا، ناامن: تبدیل تکی به repeated توی Protobuf به نوع فیلد، packed بودن فرم سیمی و جهتی که از مرز نسخه‌ها رد می‌شه بستگی داره — ارتقای عددیِ unpackشده شاید لنگ‌لنگان کار کنه، ولی رشته‌ها و فرم‌های packed یا گم می‌کنن یا به‌هم می‌ریزن؛ Avro هم اصلاً قاعدهٔ resolutionای نداره که یه مقدار رو به چند مقدار تبدیل کنه. parse شدن بی‌خطا این‌جا دربارهٔ مقدارها هیچی ثابت نمی‌کنه.
  4. مهاجرت امن با فیلد تازه مهاجرت کن: emails رو کنار email اضافه کن، توی پنجرهٔ سازگاری هر دو رو بنویس، خواننده‌ها رو گروه‌به‌گروه ببر سمت فیلد تازه، بعد قدیمی رو deprecated کن و — فقط وقتی آخرین مصرف‌کنندهٔ قدیمی رفت — حذفش کن. اول خواننده‌ها، بعد نویسنده‌ها، حذف آخر. این ترتیب رو حفظ کن.
  5. تست و rollback هر گام رو پیش از deploy پشت دروازهٔ بررسی سازگاری registry نگه دار و یه rollback هم آماده کن که نسخهٔ قبلی schema به‌علاوهٔ باینری قبلی رو برگردونه؛ توی طول پنجره هم خطای خواندن هر نسخه و شمارندهٔ حذف فیلد ناشناخته رو بپا.
  1. Add: safe on both sides Add an optional field in both formats: Protobuf hands out a fresh tag — old readers skip those bytes and preserve them (forward), new readers fill in a default on old data (backward). Avro adds a field with a reader default — new readers fill old records, old readers shrug at the extra. Retire the old tags into a reserved list and never reuse them.
  2. Rename: free vs backward-only Rename, and it's asymmetric: in Protobuf a rename costs nothing because names never reach the wire — same tag, both directions fine. Avro matches by name, so the new reader needs an alias for the old name: new-reads-old works (backward), but old readers meeting new-written data never pair the fresh name (forward fails). Never assume the alias works both ways.
  3. Cardinality: never retype Cardinality in place, unsafe: turning a singular into a repeated in Protobuf depends on the field type, whether the wire form is packed, and which direction crosses the version boundary — numeric unpacked upgrades can limp along, while strings and packed forms lose values or garble them; Avro has no resolution rule that turns one value into many. Parsing without an error here proves nothing at all about the values.
  4. The safe migration Migrate with a NEW field: add emails alongside email, dual-write both during the compat window, move the readers over one cohort at a time, then deprecate the old field and — only after the last old consumer is gone — remove it. Readers first, writers second, drop last. That's the order to remember.
  5. Test and rollback Gate every step behind a registry compatibility check before deploy, and keep a rollback that restores the previous schema version plus the previous binary; during the window, watch the per-version read errors and the unknown-field-drop counters.

طراحی مشخصConcrete design

پروتو: message Profile { string name = 1; int32 age = 2; string email = 3; } — تغییر اسم name آزاده، افزودن repeated string emails = 4 با تگ تازه، تگ‌های بازنشسته هم reserve می‌شن. Avro: رکورد با name و age که default دارن، به‌علاوهٔ فیلد union تازهٔ emails با پیش‌فرض خالی؛ تغییر اسم فقط با aliases: ["oldName"] روی خوانندهٔ جدید. انتشار: بررسی registry ← deploy خواننده‌های متحمل ← نوشتن دوگانهٔ قدیم+جدید ← کوچ گروه‌های خواننده ← deprecated ← حذف بعد از مهلت مصرف‌کننده‌های عقب‌مانده.

Proto: message Profile { string name = 1; int32 age = 2; string email = 3; } — rename name freely, add repeated string emails = 4 with a fresh tag, and reserve the retired tags. Avro: a record with name and age carrying defaults, plus the new union field emails defaulting to empty; rename via aliases: ["oldName"] on the new reader only. Rollout: registry check → deploy tolerant readers → dual-write old+new → migrate the reader cohorts → deprecate → remove after the lagging-consumer deadline.

گزینه‌های جایگزینAlternatives

سناریوهای خرابیFailure scenarios

  • تغییر تکی‌به‌چندتایی درجا روی رشته‌ها، از مسیر رندر JSON: رشته‌های تکیِ قدیمی و آرایه‌های تازه هر دو جهت parse می‌شن، ولی مقدارها خرابن — بدترین نوع خرابی، چون مانیتورها سبز می‌مونن.
  • حذف فیلد قدیمی وقتی مصرف‌کننده‌های عقب‌مانده هنوز می‌خوننش: decodeهاشون پیش‌فرض می‌ذاره یا دادهٔ موردنیاز رو می‌ندازه — حذف رو با شاهد عقب‌ماندگی مصرف‌کننده زمان‌بندی کن، نه با تقویم.
  • An in-place singular-to-repeated change on strings, via the JSON rendering: old single strings and new arrays parse in both directions, yet the values are corrupted — the worst kind of failure, because the monitors stay green.
  • Removing the old field while lagging consumers still read it: their decodes default or drop data they still need. Schedule the removal on consumer-lag evidence, not on the calendar.

    // Teaching model of the chapter's evolution rules (not the real
    // libraries): prints the verdict matrix and measures packed vs
    // unpacked repeated-int32 bytes to show why packing matters.

    static int varintLen(int n) {
        int l = 1;
        while ((n >>>= 7) != 0) {
            l++;
        }
        return l;
    }

    public static void main(String[] args) {
        int[] vals = {25, 31, 44};
        int unpacked = 0;
        int packedBody = 0;
        for (int v : vals) {
            unpacked += 1 + varintLen(v);
            packedBody += varintLen(v);
        }
        int packed = 1 + varintLen(packedBody) + packedBody;
        System.out.println("repeated int32 x3 unpacked bytes: " + unpacked);
        System.out.println("repeated int32 x3 packed bytes: " + packed);
        String[][] rows = {
            {"add optional", "B ok F ok", "B ok F ok (default)"},
            {"rename", "B ok F ok", "B ok (alias) F no"},
            {"one-to-many in place", "depends: do not", "no rule: do not"},

            System.out.println(r[0] + " | protobuf " + r[1] + " | avro " + r[2]);

اشتباهات رایجCommon mistakes

  • فرض این‌که alias توی Avro هر دو جهت کار می‌کنه. فقط به خوانندهٔ جدید اسم قدیمی رو یاد می‌ده؛ خواننده‌های قدیمی از اسم تازه بی‌خبر می‌مونن.
  • گفتن تکی‌به‌چندتایی «سازگار هست چون parse می‌شه». قابل‌تجزیه بودن بدون نگاشت بی‌اتلافِ مقدار، یعنی مانیتور سبز روی دادهٔ خراب.
  • افزودن فیلد Avro بدون default و مقصر دانستن registry. قاعده صریحه: بدون default، سازگاری backward نیست.
  • Assuming an Avro alias works both ways. It only teaches the NEW reader the old name; the old readers stay ignorant of the new one.
  • Calling singular-to-repeated 'compatible because it parses'. Parseability without a lossless value mapping is just a green monitor sitting on top of corrupt data.
  • Adding an Avro field without a default and then blaming the registry. The rule is explicit: no default, no backward compatibility.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که موتور بعد از کرش هیچی یادش نمی‌مونه، پس کارِ تو اینه که همه‌چیز رو از لاگ بازسازی کنی. به هر گام شناسهٔ پایدار بده (order id + step name + code version)، نتیجهٔ هر گام رو پیش از اعلام موفقیت توی لاگ پایدار بنویس، و بازپخش رو با همون شناسه‌ها دوباره قدم بزن: گام‌های ثبت‌شده رد می‌شن و نتیجهٔ قبلی‌شون برمی‌گرده. گام‌های برگشت‌ناپذیر جبران روبه‌جلو (saga) می‌گیرن، نه بازگشت در زمان. تغییر ترتیب، شاخه یا payload رو با نسخهٔ تازه کد منتشر کن — invocationهای در جریان با همون قدیمی تموم می‌شن. هزینهٔ recovery هم بازپخشِ محدودِ تاریخچه‌ست، به‌علاوه یه جاروی مغایرت‌گیری برای ارسال‌کنندهٔ بدون کلید. یادت باشه: لاگ، تنها حافظهٔ موتوره.
Here's the thing: after a crash the engine remembers nothing, so your whole job is to rebuild everything from the log. Give every step a stable id (order id + step name + code version), append each result to the durable log BEFORE reporting success, and replay by re-walking with the same ids: logged steps get skipped and their old results come back. Irreversible steps get forward compensations (saga), never a rollback in time. Ship step-order, branch or payload changes as a NEW code version — in-flight invocations finish on the old one. Recovery cost is the bounded replay reads plus, for the keyless shipper, one reconciliation sweep. The log is the engine's only memory — treat it that way.

  • اعداد هزینهٔ recovery پایین، کران‌های آموزشی همین گردش‌کارن — نه ردپای اندازه‌گیری‌شده.
  • Picture this: a teaching three-step order workflow — reserve stock, charge card, ship parcel. A crash can strike anywhere, including between the effect and the log append. That's the worst case.
  • The payment gateway accepts an idempotency key, and the base-design shipper dedups on our step id. The keyless shipper is the follow-up scenario.

چرا این روش و این عددها؟Why this method and these numbers?

نتیجهٔ step باید ثبت بشه تا replay همون تصمیم رو ادامه بده؛ اما crash پس از charge و پیش از ثبت نتیجه هنوز مبهمه. کلیدِ ثابتِ همون step به gateway اجازه می‌ده retry رو همون عملیات بشناسه؛ شناسهٔ تازه در هر retry این خاصیت رو از بین می‌بره. نسخهٔ workflow توی invocation ثبت می‌شه تا replay بعد از deploy کد جدید مسیر دیگه‌ای نره. تعداد step و هزینهٔ recovery هم ویژگیِ سناریوئن و باید با تعداد invocation و مدت retention مقیاس داده بشن.

Persist each step result so the replay follows the original decision. A crash after charging but before logging is still ambiguous; a stable step key lets the gateway recognize the retry, while a fresh key on every retry throws that away. Bind the workflow version to the invocation so a deployment can't change the replay path. And the recovery cost scales with the invocation count, the step count and the retention window — it isn't a universal constant.

مدل ذهنیMental model

تصور کن موتور پس از کرش جز یه چیز هیچ یادش نمی‌مونه: لاگ پایدار. بازپخش یعنی دوباره قدم زدن روی همون مسیر کد با همون شناسه‌ها و پرسیدن از لاگ در هر گام: قبلاً انجام شده؟ پس همون نتیجه رو دوباره استفاده کن. جبران هم سفر در زمان نیست — یه گام تازهٔ روبه‌جلوئه که اثر قدیمی رو خنثی می‌کنه (بازپرداخت بعد از شارژ). ساده‌ست؟ آره، ولی همین سادگی کل کار رو می‌سازه.
Picture the engine after a crash: total amnesia, with exactly one exception — the durable log. Replay means walking the same code path again with the same step ids and asking the log at every step: already done? Then reuse the old result. And compensation isn't time travel — it's a fresh forward step that undoes an old effect (a refund after the charge). Simple? Sure — and that simplicity is the whole design.

  1. شناسه پایدار شناسهٔ هر گام از سه تکه ساخته می‌شه: شناسهٔ سفارش + اسم گام + نسخهٔ کد (order:1001:ship:v1). توی retry همون شناسه تکرار می‌شه، پس اثر دوباره با همون کلید به مقصد می‌رسه و تکراری‌زدایی ممکن می‌شه.
  2. اول لاگ، بعد اعلام نتیجهٔ هر گام موفق، پیش از اعلام موفقیت، توی لاگ پایدار نوشته می‌شه. اگه کرش بین اثر و لاگ بیفته، گام «باز» می‌مونه و دوباره اجرا می‌شه — برای همین اثرها باید idempotent باشن.
  3. بازپخش و تحویل تکراری restart تاریخچه رو می‌خونه و با همون شناسه‌ها قدم می‌زنه: reserve و charge رد می‌شن (نتیجهٔ قدیمی برمی‌گرده) و فقط ship باز اجرا می‌شه. تحویل تکراریِ نتیجهٔ ship هم فقط reuse هست، نه مرسولهٔ دوم.
  4. جبران روبه‌جلو اگه ship بعد از charge ناممکن بشه، تاریخ به عقب برنمی‌گرده: یه گام تازهٔ refund شارژ رو برمی‌گردونه و یه گام release موجودی رو آزاد می‌کنه. هر جبران خودش شناسهٔ پایدار و نتیجهٔ ثبت‌شده داره.
  5. نسخه‌بندی و هزینه تغییر ترتیب گام‌ها، شاخه‌بندی یا payload با نسخهٔ تازه (v2) منتشر می‌شه؛ invocationهای در جریان با v1 تموم می‌شن، چون تاریخچهٔ v1 فقط با کد v1 قدم زده می‌شه. هزینهٔ recovery هم بازخوانی تاریخچه (کران آموزشی: تعداد گام‌ها) به‌علاوهٔ جاروی مغایرت‌گیری برای ارسال‌کنندهٔ بدون کلید.
  1. Stable ids Each step id is built from three parts: order id + step name + code version (order:1001:ship:v1). A retry repeats the same id, so a repeated effect reaches the destination under the same key and can be deduped.
  2. Log first, then report Each successful step's result lands in the durable log before the success is reported. A crash between the effect and the log leaves the step 'open' to run again — which is exactly why the effects have to be idempotent.
  3. Replay and duplicates The restart loads the history and re-walks with the same ids: reserve and charge get skipped (the old results come back) and only ship runs again. A duplicate delivery of the ship result is just reuse as well — never a second parcel.
  4. Forward compensation If shipping becomes impossible after the charge, history doesn't rewind: a fresh refund step gives the charge back and a release step frees the stock. Every compensation carries its own stable id and its own logged result.
  5. Versioning and cost Step-order, branch or payload changes ship as a new version (v2); in-flight invocations finish on v1, because v1 history is only ever walked by v1 code. Recovery cost: re-reading the history (teaching bound: the number of steps) plus a reconciliation sweep for the keyless shipper.

طراحی مشخصConcrete design

اجزا: orchestrator (زمان‌بندی، مالک دروازهٔ نسخه)، لاگ پایدار (write-ahead، تاریخچهٔ هر invocation)، اجراکننده‌های گام (رزرو/شارژ/ارسال، هرکدام کلیددار)، جبران‌کننده‌ها (بازپرداخت، آزادسازی، لغو مرسوله). مسیر نوشتن: اجرای گام ← نوشتن نتیجه ← اعلام. مسیر خواندن (بازپخش): بارگذاری تاریخچه ← قدم‌زدن دوبارهٔ کد با همون شناسه‌ها ← ثبت‌شده رد، باز اجرا. کلیدها: order:{id}:reserve:{v} و charge و ship.

Components: an orchestrator (schedules, owns the version gate), the durable log (write-ahead, per-invocation history), the step executors (reserve/charge/ship, each keyed), and the compensation handlers (refund, release, cancel-parcel). Write path: execute step → append result → report. Read path (replay): load history → re-walk the code with the same ids → skip what's logged, run what's open. Keys: order:{id}:reserve:{v}, order:{id}:charge:{v}, order:{id}:ship:{v}.

گزینه‌های جایگزینAlternatives

  • کوروگرافی رویدادی بدون orchestrator: هر سرویس به رویداد قبلی واکنش نشون می‌ده. هزینه‌اش هم اینه: تاریخچه پراکنده، بازپخش و نسخه‌بندی سخت‌تر، جبران بدون مالک واحد.
  • Event choreography with no orchestrator: each service reacts to the previous event. The bill: scattered history, harder replay and versioning, and compensation with nobody clearly owning it.

سناریوهای خرابیFailure scenarios

  • کرش بین اثر ship و نوشتن لاگ: ship دوباره اجرا می‌شه. با تکراری‌زدایی روی شناسه، مرسولهٔ دوم ساخته نمی‌شه؛ بدون کلید، جاروی مغایرت‌گیری مرسوله‌های بی‌صاحب رو به سفارش وصل می‌کنه.
  • بازپخش تاریخچهٔ v1 با کد v2 جابه‌جاشده: دروازهٔ نسخه جلوی قدم‌زدن اشتباه رو می‌گیره و invocation رو به کد v1 میخ می‌کنه.
  • شکستِ خودِ جبران (مثلاً refund ناموفق): جبران با همون شناسه retry می‌شه؛ پس از تموم شدن بودجه، هشدار انسانی با حالت دقیق لاگ — invocation نه «نیمه‌تمام رها»، بلکه «منتظر اقدام».
  • A crash between the ship effect and the log write: ship re-runs. With dedup on the step id, no second parcel is made; without a key, the reconciliation sweep attaches the orphan parcels back to the order.
  • Replaying v1 history against reordered v2 code: the version gate blocks the wrong walk and pins the invocation to v1 code.
  • The compensation itself fails (say, the refund is rejected): it retries under the same id; once the budget is spent, a human alert goes out with the exact log state — the invocation is 'awaiting action', never 'abandoned halfway'.

import java.util.LinkedHashMap;
import java.util.Map;
import java.util.TreeSet;
import java.util.function.Supplier;

public class WorkflowDemo {
    // Durable log: step id -> result. Teaching stand-in for a write-ahead log.
    static Map<String, String> log = new LinkedHashMap<>();

    static String runStep(String id, Supplier<String> fn) {
        if (log.containsKey(id)) {
            System.out.println("replay " + id + ": skip, reuse " + log.get(id));
            return log.get(id);
        }
        String r = fn.get();
        log.put(id, r); // append BEFORE reporting success
        System.out.println("exec   " + id + ": " + r + " (logged)");
        return r;
    }

    public static void main(String[] args) {
        String wid = "order-1001";
        runStep(wid + ":reserve:v1", () -> "stock-42 reserved");
        runStep(wid + ":charge:v1", () -> "pay-7 charged");
        System.out.println("-- crash before ship; restart replays --");
        runStep(wid + ":reserve:v1", () -> "stock-42 reserved");
        runStep(wid + ":charge:v1", () -> "pay-7 charged");
        runStep(wid + ":ship:v1", () -> "parcel-9 created");
        System.out.println("-- duplicate delivery of ship result --");
        runStep(wid + ":ship:v1", () -> "parcel-9 created");
        System.out.println("durable log keys: " + new TreeSet<>(log.keySet()));
    }
}

پیگیری (استف): provider ارسال idempotency key نداره. تضمینت چطور عوض می‌شه؟Follow-up (Staff): The shipping provider has no idempotency key. How does your guarantee change?

تضمین از «اثر دقیقاً یک‌بار» می‌لغزه به «حداکثر یه مرسولهٔ بی‌صاحب + مغایرت‌گیری»: retry کور ممنوعه، چون هر تلاش ممکنه مرسولهٔ تازه بسازه. به‌جایش: ship رو یه بار صدا بزن، نتیجهٔ نامشخص رو «نامعلوم» ثبت کن، و بذار جاروی مغایرت‌گیری (تطبیق مرسوله‌ها با شناسهٔ سفارش، توی سمت خودت) اثر رو قطعی کنه. هزینهٔ recovery همون جاروئه.

The guarantee slides from 'exactly-once effects' down to 'at most one orphan parcel + reconciliation': blind retries are banned, because each attempt may mint a fresh parcel. Instead: call ship once, record the unclear outcome as 'unknown', and let a reconciliation sweep (matching parcels to your order id on your side) settle the effect. That sweep is the recovery cost — and it's the price of no key.

اشتباهات رایجCommon mistakes

  • قول «exactly-once» برای اثر بیرونی. لاگ پایدار اجرای دقیقاً یک‌بار می‌ده، نه اثر دقیقاً یک‌بار — اثر به کلیدِ مقصد وابسته‌ست.
  • استفاده از عدد تصادفی یا ساعت سیستم توی کد workflow. بازپخش باید قطعی باشه؛ همون ورودی، همون قدم‌ها.
  • جابه‌جایی آزادِ ترتیب گام‌ها روی invocationهای در جریان. تاریخچهٔ قدیمی فقط با منطق قدیمی قدم زده می‌شه — تغییر، نسخهٔ تازه می‌خواد.
  • Promising 'exactly-once' for outside effects. The durable log gives you exactly-once execution, not exactly-once effects — the effect depends on the destination's key.
  • Using random numbers or the system clock in workflow code. Replay has to be deterministic — same input, same walk.
  • Freely reordering steps over in-flight invocations. Old history is only ever walked by old logic — a change needs a new version.
