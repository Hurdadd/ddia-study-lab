انتخاب‌ها و هزینه‌های معماری سیستم‌های دادهTrade-offs in data systems architecture

In this chapter, you'll work out what to speed up, what that costs, where the source of truth lives, how copies get made, and when to move beyond one machine.

ایده کلیدی فصلChapter thesis

حرف اصلی فصل همینه رفیق، معماری داده یعنی همین یه جمله: چی رو تندتر کنیم و بابتش چی بدیم؟ تو این فصل با هم می‌بینیم ثبت سفارش با گزارش فروش چه فرقی داره، حرف اصلی کجاست و کپی‌ها از کجا میان، و کی یه ماشین بسه و کی باید پخشش کنیم.

مثال فنی: مسیر یک سفارش در سه مخزن

وضعیت اولیه: فرض کن سفارش id=42 با مبلغ 500 تازه توی PostgreSQL نشسته. همین مرجع اصلیه.

اجرای مرحله‌به‌مرحله: حالا خبرش پخش می‌شه: یه کپی می‌ره توی Redis تا نمایش سریع بشه، یه کپی هم می‌ره توی ایندکس جست‌وجو. آخر شب هم گزارش فروش همین مبلغ رو جمع می‌زنه.

نتیجه و دلیل: حالا اگه Redis بترکه چی؟ هیچی — سفارش سر جاشه و کش رو از نو می‌سازیم. فقط یادت باشه تا خبر برسه، ممکنه چند ثانیه عدد قدیمی ببینی؛ طبیعیه.

یه چیز رو هم روشن کنم: مثال‌های این فصل قصه‌های کلاسین از کارهای روزمره، نه افشای معماری یه شرکت خاص. عددها رو برای فهم انتخاب کردیم.

Start with one question: what does this part of the system need to do, and what are you willing to pay for it? Checkout needs to record an order. A sales report needs to add up lots of orders. Choosing a tool means choosing those trade-offs, so ask the right question before picking one.

The examples here are teaching scenarios based on everyday engineering work. They don't describe a particular company's architecture, and the numbers are chosen to make the ideas easier to follow.

Example: One order, three stores

Setup: Say order id=42, amount 500, has just been recorded in PostgreSQL. That's the source of truth.

Walk through it: A change goes to Redis for faster display and to the search index for lookup. The nightly sales report includes the same amount.

What this tells you: If Redis fails, the order is still recorded and the cache can be rebuilt. While changes are catching up, a copy may show an older value for a few seconds. The order and its copies have different jobs.

سیستم data-intensive چیست؟What is a data-intensive system?

داستان از این قراره: سیستم داده‌محور یعنی برنامه‌ای که درد اصلیش نگه‌داشتن، پیدا کردن و به‌روز نگه‌داشتن داده‌ست. ولی تو سیستم محاسبه‌محور، درد اصلی خود محاسبه‌ست — اینکه یه حساب سنگین رو چطور موازی کنی.

مثال فنی: دادهٔ بیشتر یا محاسبهٔ بیشتر؟

وضعیت اولیه: یه سرویس سفارش رو تصور کن که روزی یه میلیون رکورد با customer_id و status قورت می‌ده.

اجرای مرحله‌به‌مرحله: حالا صحنه رو بچین: پرس‌وجوی وضعیت فقط دنبال یه رکورد درست با ایندکس می‌گرده؛ اون‌ور یه سرویس تبدیل ویدیو داره با CPU روی یه فایل عرق می‌ریزه.

نتیجه و دلیل: پس دغدغه اولی داده‌ست، دغدغه دومی محاسبه. یادت باشه یه محصول می‌تونه هر دو دغدغه رو هم‌زمان داشته باشه.

An order service spends much of its effort storing, finding and keeping data up to date. That's a data-intensive system. A video converter spends its effort on the calculation itself. That's Compute-intensive. Large volumes, frequent changes, failures and concurrent requests make the first job hard. Splitting up a heavy computation makes the second job hard. A product can have both.

Example: More data, or more computation?

Setup: Picture an order service taking in a million records a day, each with customer_id and status.

Walk through it: A status query uses an index to find the right record. Compare that with a video converter spending CPU time processing a file.

What this tells you: The first service's main challenge is the data; the second's is computation. A single product can need both kinds of work.

بلوک‌های ساختمانی (که بارها در کتاب تکرار می‌شوند)Building blocks (recurring throughout the book)

قضیه اینه که هیچ ابزاری همه‌کاره نیست، هر کدوم یه تیکه کار رو برمی‌داره: پایگاه داده جنس رو انبار می‌کنه، کش خوندن رو تند می‌کنه، پردازشگرها هم دادهٔ خام رو تبدیل می‌کنن به چیزی که به درد بخوره.

مثال فنی: پایگاه داده، کش و ایندکس چه می‌کنند؟

وضعیت اولیه: فرض کن قیمت کالای P7 توی مرجع شده 120، ولی توی کش هنوز 100 مونده. آشناست، نه؟

اجرای مرحله‌به‌مرحله: حالا بریم سراغ مسیر خرید: API قیمت معتبر رو فقط از مرجع برمی‌داره. بعد مصرف‌کنندهٔ تغییر میاد کش و ایندکس جست‌وجو رو به نسخهٔ 120 می‌رسونه.

نتیجه و دلیل: پس کش فقط برای سرعته، ایندکس فقط برای جست‌وجو. هیچ‌کدوم بدون قرارداد مشخص مرجع تأیید قیمت نیستن — اینو قاطی نکن.

  • پایگاه داده‌ها: انبار کردن داده برای بعداً
  • کش: نگه‌داشتن جواب کارهای گرون که خوندن تند بشه
  • ایندکس جست‌وجو: دنبال کلمه گشتن و فیلترهای پیچیده
  • پردازش جریانی (Stream Processing): همین لحظه به اتفاق‌ها واکنش نشون دادن
  • پردازش دسته‌ای (Batch Processing): یه عالمه دادهٔ جمع‌شده رو یه‌جا جویدن

A database stores the facts. A cache speeds up reads. A search index helps you find things. Stream and batch processors turn the stored data into something useful. Each has a job; no single tool does all of them equally well.

  • Databases: store data for later use
  • Caches: keep expensive results around for faster reads
  • Search indexes: find words and apply complex filters
  • Stream processing: react to events as they arrive
  • Batch processing: process a large collection of saved data together

Example: What do the database, cache and index each do?

Setup: Product P7 now costs 120 in the record, but the cache still shows 100.

Walk through it: For checkout, the API takes the authoritative price from the record. A change consumer then brings the cache and search index up to 120.

What this tells you: The cache speeds up reads; the index supports search. Neither becomes the authority for confirming a price without an explicit contract. A fast answer can still be an old answer.

اصطلاحات ضروریEssential terminology

بذار ساده بگم: فرانت‌اند همون چیزیه که کاربر می‌بینه؛ بک‌اند درخواست رو تحویل می‌گیره و اجراش می‌کنه. هر اطلاعاتی هم که باید بعد تموم شدن درخواست بمونه، می‌ره تو یه جای مطمئن برای نگه‌داشتن.

مثال فنی: از مرورگر تا دیسک

وضعیت اولیه: تصور کن دکمهٔ خرید رو زدی؛ مرورگرت یه POST /orders با request_id=r7 می‌فرسته.

اجرای مرحله‌به‌مرحله: بک‌اند اول چک می‌کنه درخواست درسته یا نه، بعد پایگاه داده سفارش رو ثبت می‌کنه. آخرش هم جواب با order_id=42 برمی‌گرده.

نتیجه و دلیل: پس مرورگر فقط کلاینته، بک‌اند مجریه، پایگاه داده هم صندوق اماناته. نگران نشو، این سه‌تا لازم نیست سه تا ماشین جدا باشن.

  • Frontend: کد سمت کلاینت (مرورگر/موبایل) — فقط با دادهٔ همون یه کاربر سر و کار داره.
  • Backend: کد سمت سرور — با دادهٔ همهٔ کاربرها سر و کار داره؛ دردسر زیرساخت داده دقیقاً همین‌جاست.
  • Data infrastructure: همون دیتابیس‌ها، کش‌ها و صف‌های پیام که کد برنامه باهاشون کار می‌کنه.
  • کد برنامه معمولاً stateless ـه؛ هر چی باید بین دو تا درخواست بمونه، یا می‌ره سمت کلاینت یا تو زیرساخت داده می‌خوابه.
  • Transaction تو این فصل فعلاً شل باهاش برخورد می‌کنیم یعنی «خوندن‌ها و نوشتن‌های تند که یه واحد منطقین» (تعریف سفت‌وسختش فصل ۸).

The frontend is what the user interacts with. The backend receives the request and does the work. Anything that needs to outlive that request needs somewhere to stay.

  • Frontend: client-side code in the browser or mobile app, working with that user's data.
  • Backend: server-side code handling data across users. This is where most data-infrastructure work happens.
  • Data infrastructure: the databases, caches and message queues the application uses.
  • App code is usually stateless. State that needs to survive between requests stays on the client or in data infrastructure.
  • For now, read transaction as fast reads and writes that belong to one logical unit. Chapter 8 gives you the stricter definition.

Example: From the browser to disk

Setup: Press the buy button. The browser sends POST /orders with request_id=r7.

Walk through it: The backend checks the request, the database records the order, and the response comes back with order_id=42.

What this tells you: The browser is the client, the backend does the work, and the database keeps the record. Those roles don't have to live on three separate machines.

۱1 سیستم‌های عملیاتی در برابر تحلیلیOperational vs analytical systems

ایده کلیدیKey idea

داستان اینه: دادهٔ عملیاتی مال همین حالای کاربره — اینکه سفارشش ثبت بشه. دادهٔ تحلیلی مال فهمیدن الگوی هزاران تا از همین کارهاست. دو تا دنیای جدا با نیازهای جدا.

مثال فنی: ثبت خرید در برابر گزارش فروش

وضعیت اولیه: فرض کن ثبت سفارش فقط ردیف سفارش 42 و موجودی کالای P7 رو دست می‌زنه. یه کار کوچیک و تمیز.

اجرای مرحله‌به‌مرحله: حالا گزارش ماهانه با SUM(amount) GROUP BY city رو نگاه کن: باید میلیون‌ها ردیف رو بخونه. اگه هر دو رو بندازی روی یه منبع ضعیف، صف درست می‌شه.

نتیجه و دلیل: پس نسخهٔ تحلیلی دعوا سر منابع رو کم می‌کنه. فقط یادت باشه گزارش به اندازهٔ تأخیر انتقال از مرجع عقبه؛ تازه نیست، طبیعیه.

Recording a purchase and reporting monthly sales use the same orders in different ways. The operational side serves the person placing an order. The analytical side studies a read-only copy. Separating them lets each do its work without competing for the same resources.

Example: Recording a purchase vs reporting sales

Setup: Recording order 42 touches the order row and the stock for product P7. That's a small amount of work.

Walk through it: The monthly report uses SUM(amount) GROUP BY city and reads millions of rows. Put both workloads on an underpowered shared resource and requests start queuing.

What this tells you: An analytical copy reduces that competition. Its report is still behind the record by however long data transfer takes. Separation buys room to work, with freshness to account for.

چه کسانی با داده کار می‌کنند؟Who works with data?

راستش همه با همون یه داده سر و کار دارن، ولی سؤالشون یکیه؟ نه! توسعه‌دهنده عملیات رو می‌سازه، تحلیلگر گزارش می‌خواد، مهندس داده هم جادهٔ بین این دوتا رو می‌کشه.

مثال فنی: مسئولیت‌ها روی یک خطای مبلغ

وضعیت اولیه: فرض کن سرویس سفارش مبلغ رو به ریال ثبت می‌کنه، ولی یه منبع دیگه با تومان می‌فرسته. بوی دردسر میاد، نه؟

اجرای مرحله‌به‌مرحله: حالا نوبت نقش‌هاست: توسعه‌دهنده واحد API رو مشخص می‌کنه، مهندس داده توی تبدیل واحدها رو یکی می‌کنه، تحلیلگر هم جمع فروش رو با چند نمونه سفارش چک می‌کنه.

نتیجه و دلیل: پس عدد نهایی با اضافه کردن سرور درست نمی‌شه. قرارداد واحد و کنترل کیفیت توی زنجیره رو جدی بگیر؛ وگرنه آشغال منظم تحویل می‌گیری.

  • Backend Engineer: سرویس خوندن/نوشتن برای کاربرها می‌سازه (عملیاتی)
  • Business Analyst: برای مدیریت گزارش می‌سازه — Business Intelligence (BI)
  • Data Scientist: دنبال بینش می‌گرده، مدل ML و قابلیت داده‌محور محصول (پیشنهاددهنده، امتیاز ریسک، فیلتر اسپم)
  • Data Engineer: پل بین این دو دنیاست و صاحب زیرساخت داده
  • Analytics Engineer: داده رو برای تحلیلگرها مدل و تبدیل می‌کنه

Follow a wrong sales total back through the pipeline. The backend defines the amount's unit, the data pipeline keeps that unit consistent, and the analyst checks the result against sample orders. Different roles own different parts of that chain.

  • Backend engineer: builds the services that read and write data for users
  • Business analyst: builds reports for management, often through Business Intelligence (BI)
  • Data scientist: looks for insights and builds ML models and features such as recommendations, risk scores and spam filters
  • Data engineer: builds and runs the pipelines connecting the operational and analytical sides
  • Analytics engineer: shapes data into something analysts can use

Example: Who fixes a wrong sales total?

Setup: The order service records amounts in rials, but another source sends tomans. Adding the raw values together won't give a meaningful total.

Walk through it: The developer defines the API's unit, the data engineer converts the sources to a common unit, and the analyst checks the total against sample orders.

What this tells you: Another server won't fix the number. The unit contract and quality checks have to hold all the way through the pipeline.

OLTP در برابر OLAPOLTP vs OLAP

فرقشون رو این‌جوری بفهم: تو OLTP معمولاً چند تا رکورد مشخص رو می‌خونی یا عوض می‌کنی. تو OLAP خروار رکورد رو کنار هم می‌ذاری تا به آمار و الگو برسی — مقیاسشون زمین تا آسمونه.

مثال فنی: دو پرس‌وجو، دو الگوی دسترسی

وضعیت اولیه: فرض کن جدول orders صد میلیون ردیف داره — یه غول واقعی. روی id هم ایندکس شده.

اجرای مرحله‌به‌مرحله: WHERE id=42 با ایندکس مثل برق فقط چند صفحه رو می‌خونه؛ ولی SUM(amount) کل سال مجبوره ستون مبلغ رو شخم بزنه.

نتیجه و دلیل: اولی OLTP ـه، دومی OLAP. یادت باشه ایندکسی که اولی رو پرواز می‌ده، لزوماً دومی رو نجات نمی‌ده.

Ask for one order by ID: that's the usual OLTP pattern, a point query. A user action might read, insert, update or delete a few records. Now ask for a year's sales total: that's the usual OLAP pattern. You scan many records and calculate count / sum / avg. The result summarizes the records instead of returning each one. Same data, very different work.

Setup: Take an orders table with a hundred million rows and an index on id.

Walk through it: With the index, WHERE id=42 reads just a few pages. A full year's SUM(amount) has to scan the relevant amounts.

What this tells you: The first query is OLTP; the second is OLAP. An index that helps the first doesn't necessarily help the second. Match the layout to the work.

مثال فنی برای خواندنِ نمودار: دو پرس‌وجو، دو الگوی دسترسی

وضعیت اولیه: فرض کن جدول orders صد میلیون ردیف داره — یه غول واقعی. روی id هم ایندکس شده.

اجرای مرحله‌به‌مرحله: WHERE id=42 با ایندکس مثل برق فقط چند صفحه رو می‌خونه؛ ولی SUM(amount) کل سال مجبوره ستون مبلغ رو شخم بزنه.

نتیجه و دلیل: اولی OLTP ـه، دومی OLAP. یادت باشه ایندکسی که اولی رو پرواز می‌ده، لزوماً دومی رو نجات نمی‌ده.

خوب، دو تا ستون سبز و آبی رو از روی برچسب‌های زرد وسط بخون: هفت سطر از READ تا SIZE. ستون چپ (OLTP) دنیای عملیاته — پیدا کردن چند رکورد با کلید، نوشتن تک‌تک، کاربر وب و موبایل، کوئری‌های ثابت تو دل کد، تعداد زیاد ولی کوچیک، معنای «وضعیت فعلی» و حجم گیگ تا ترا. ستون راست (OLAP) دنیای تحلیله — شخم زدن میلیون‌ها رکورد و جمع بستن، ورود دسته‌ای یا جریانی، تحلیلگر داخل شرکت، کوئری دلبخواهی، تعداد کم ولی سنگین، معنای «تاریخچه» و حجم ترا تا پتا.

نوار پایینی همون جواب سؤال مصاحبه‌ست: چرا تحلیل رو روی OLTP اجرا نکنیم؟ چهار تا جعبه: SILOS (داده تو ده‌ها سیستم جدا پخش‌وپلاست)، SCHEMA (اسکیمای خوب عملیاتی = اسکیمای بد تحلیلی)، COST (اسکن سنگین نفس کاربرها رو می‌گیره) و ACCESS (دست مستقیم معمولاً از نظر امنیتی ممنوعه). جمع‌بندیش یه خطه: OLTP جواب امروز رو می‌ده، OLAP گذشته رو توضیح می‌ده.

انبارداده، دریاچه داده، ETL و Reverse ETLWarehouse, lake, ETL and reverse ETL

انبارداده (Data Warehouse)Data warehouse

انبار داده رو این‌جوری به خاطر بسپر: آشپزخونهٔ گزارش‌گیریه: اطلاعات رو تمیز و آماده می‌چینه. دریاچهٔ داده انباره که هر قالبی رو همون خام می‌قاپه. ETL یعنی استخراج، تبدیل، بارگذاری؛ ELT یعنی اول بار بزن بعد تبدیل کن — جاشون عوض می‌شه.

مثال فنی: ساخت جدول قابل‌تحلیل

وضعیت اولیه: فرض کن سفارش‌ها amount_rial دارن و زمانشون هم با منطقهٔ زمانی قاطی شده.

اجرای مرحله‌به‌مرحله: حالا بریم سر ETL: زمان رو تبدیل می‌کنه به روز گزارش، واحد مبلغ رو یکی می‌کنه، بعد می‌نویسه توی fact_sales(day, product_id, amount).

نتیجه و دلیل: حالا تحلیلگر راحت فروش روزانه رو جمع می‌زنه. ولی اگه واحد یا timezone مبهم بمونه، انبار داده فقط خطا رو شیک و منظم ذخیره کرده — گول نظمش رو نخور.

Picture a clean set of sales tables that analysts can query without slowing checkout. That's the warehouse's job: a separate database with a read-only copy of data collected from operational systems.

With ETL, you extract the data through dumps or a change stream, transform and clean it, then load the analysis-ready result. With ELT, you load first and transform at the destination. Follow where the transformation runs; that's the difference.

Walk through it: ETL maps the timestamps to reporting days, standardizes the amount unit, and writes fact_sales(day, product_id, amount).

What this tells you: Now the analyst can add up daily sales. If the unit or timezone stays ambiguous, the warehouse has only organized the mistake. A tidy table still needs a clear meaning.

دریاچه داده (Data Lake)Data lake

دریاچهٔ داده هم داستانش اینه: انبار قالب‌های جورواجوره؛ ولی برای استفاده هنوز فهرست و کیفیت و قرارداد لازم داری — انبار شلخته هم دفتر می‌خواد.

مثال فنی: فایل خام در دریاچهٔ داده

وضعیت اولیه: تصور کن رویدادهای وب به شکل JSON و عکس‌های کالا به شکل JPEG ریختن توی object storage.

اجرای مرحله‌به‌مرحله: حالا کار job اینه: فیلد event_time رو از JSON می‌خونه و خروجی ستونی می‌سازه؛ عکس‌ها هم از یه مسیر دیگه پردازش می‌شن.

نتیجه و دلیل: پس دریاچه هر قالبی رو قورت می‌ده. ولی برای تحلیل هنوز باید schema و نسخه و کیفیت هر مجموعه مشخص باشه؛ خام بودن یعنی بی‌قانون بودن نیست.

یه انبار مرکزی از فایل‌های خام بدون زور فرمت/اسکیما: رکوردهای دیتابیسی با فرمت Avro یا Parquet، ولی متن و عکس و ویدیو هم هست. معمولاً ارزون‌تر از ذخیرهٔ رابطه‌ای چون روی object storage خوابیده. قانون معروف: «sushi principle: raw data is better» — دادهٔ خام رو نگه دار تا هرکی خودش تبدیلش کنه.

A data lake keeps raw files in different formats: database records in Avro or Parquet, alongside text, images and video. It usually uses object storage, which is often cheaper than relational storage.

The “sushi principle: raw data is better” means keeping the input so each consumer can transform it for its own needs. You still need a catalog, schema and version information, and quality checks. Raw doesn't mean nobody knows what's in there.

Setup: Web events arrive as JSON and product photos as JPEG files in object storage.

Walk through it: A job reads event_time from the JSON and builds columnar output. A separate path processes the photos.

What this tells you: The lake can hold both formats. Analysis still needs a schema, version and quality contract for each dataset. Keeping the input raw doesn't remove those decisions.

HTAP و Reverse ETLand reverse ETL

HTAP دلش می‌خواد بار عملیاتی و تحلیلی رو به هم بچسبونه. Reverse ETL برعکسه: نتیجهٔ آمادهٔ تحلیل رو برمی‌گردونه تو ابزار عملیاتی. دو تا کار جدا — قاطی‌شون نکن.

مثال فنی: برگرداندن نتیجهٔ تحلیل به عملیات

وضعیت اولیه: فرض کن انبار داده برای مشتری 17 حساب کرده مجموع خرید ۹۰ روزه شده 8000.

اجرای مرحله‌به‌مرحله: حالا job میاد وسط: هرکی بالای 5000 خریده رو با کلید customer_id می‌فرسته توی CRM، زمان محاسبه رو هم همراهش می‌فرسته.

نتیجه و دلیل: حالا CRM از برچسب آماده استفاده می‌کنه — اسمش Reverse ETL ـه. فقط یادت باشه این برچسب تا اجرای بعدی تازه نمی‌شه؛ تاریخ انقضا داره.

  • HTAP (Hybrid Transactional/Analytical Processing): هدفش اجرای هر دو بار تو یه سیستمه، ولی تو عمل تو دلش یه موتور OLTP و یه موتور تحلیلی پشت یه رابط مشترکن؛ پس جای انبارداده رو نمی‌گیره.
  • Reverse ETL: خروجی سیستم تحلیلی برمی‌گرده تو سیستم عملیاتی؛ مثلاً مدل ML آموزش‌دیده می‌ره تو پروداکشن تا پیشنهاد «کی X خریده Y هم بخره» رو بسازه.

Keep these two ideas separate. HTAP brings transactional and analytical work closer together. Reverse ETL sends a finished analytical result back into an operational tool.

  • HTAP (Hybrid Transactional/Analytical Processing): combines the workloads behind one interface, often with an OLTP engine and an analytical engine inside. You may still need a warehouse to combine sources and history.
  • Reverse ETL: sends analytical output into daily operations. A trained ML model serving “people who bought X also buy Y” recommendations is one example.

Example: Bringing analysis back into operations

Setup: The warehouse calculates that customer 17 spent 8000 over 90 days.

Walk through it: A job sends customers who spent more than 5000 into the CRM, keyed by customer_id, with the calculation time attached.

What this tells you: The CRM uses that prepared label. That's Reverse ETL. The label won't update until the job runs again, so its age matters.

۲2 سیستم مرجع در برابر داده مشتق‌شدهSystem of record vs derived data

ایده کلیدیKey idea

نوبتی هم باشه نوبت مرجعه: سیستم مرجع همون‌جاست که نسخهٔ درست داده نگه داشته می‌شه. کش و ایندکس جست‌وجو و گزارش‌ها معمولاً از روش ساخته می‌شن؛ اگه بترکن، باید بشه از نو ساختشون — مرجع نه.

مثال فنی: بازسازی دادهٔ مشتق‌شده

وضعیت اولیه: فرض کن مرجع کالا P7 رو با version=12 نگه داشته، ولی ایندکس جست‌وجو ترَکیده.

اجرای مرحله‌به‌مرحله: حالا بریم سراغ بازسازی: اول snapshot مرجع تا موقعیت لاگ 500 می‌ره توی ایندکس تازه، بعد تغییرهای بعد از 500 یکی‌یکی اعمال می‌شن.

نتیجه و دلیل: با مرز مشخص snapshot و لاگ هماهنگ، ایندکس برمی‌گرده. نگران نشو، ولی فقط با یه کپی قدیمی جلو نرو — تغییرهای وسط کپی جا می‌مونن.

System of record (source of truth): the authoritative home for a fact. In this design, writes land here first. When a cache or report disagrees with it, this is the version you use to resolve the disagreement.

Derived data: data built from those recorded facts, such as a cache, search index, materialized view, denormalized copy or trained ML model. You need a known way to build and update it. If it breaks, rebuilding depends on still having the source data and the inputs the build needs.

Example: Rebuilding derived data

Setup: The record has product P7 at version=12, but the search index has failed.

Walk through it: Load a snapshot of the record through log position 500 into a new index. Then apply the changes after 500 in order.

What this tells you: A defined snapshot boundary and the matching log let the index catch up. An old copy alone can miss changes made during the copy. You need both sides of that boundary.

  • سیستم‌های تحلیلی معمولاً مشتق‌شده‌ان چون مهمون سفره‌ای‌ان که یه جای دیگه پخته شده.
  • خود ابزار تعیین نمی‌کنه: این تویی که با نوع استفادت تو معماری به چیزی می‌گی «مرجع» یا «مشتق».
  • درد اصلی: وقتی مرجع عوض می‌شه، همهٔ مشتق‌ها باید دنبالش بیان → راه‌حل: pipeline داده (فصل ۱۱).
  • Derived data duplicates information, but makes particular reads much faster: one source can support several views.
  • Analytical systems are usually derived because they analyze facts recorded somewhere else.
  • The role comes from the design: how you use a tool decides whether it holds the record or a derived copy.
  • The work to plan for: when the record changes, its copies need to catch up. That's the job of a data pipeline (Chapter 11).

فلش‌های چین‌چین مسیر تغییرن: CDC events از مرجع می‌رن به Change Capture، بعد refresh/evict به کش، index update به ایندکس و recompute به Materialized Views. تحلیلگرها رو همین نماها کوئری می‌زنن، نه رو دیتابیس زنده.

حرف اصلی: مرجع که عوض شد همه باید دنبالش بیان. ناسازگاری موقتی اشکالی نداره، ولی گم شدن همیشگی دادهٔ مرجع هرگز — خط قرمزه.

Example: What do the database, cache and index each do?

Setup: Product P7 now costs 120 in the record, but the cache still shows 100.

Walk through it: For checkout, the API takes the authoritative price from the record. A change consumer then brings the cache and search index up to 120.

What this tells you: The cache speeds up reads; the index supports search. Neither becomes the authority for confirming a price without an explicit contract. A fast answer can still be an old answer.

Take the middle horizontal line first. That's the write path: Users → API Service → System of Record. The primary is labelled source of truth because this is where the design records authoritative changes.

Now follow the read path along the top. The API Service sends a cache lookup to the Cache or a search query to the Search Index. Both are labelled derived: they're copies prepared for particular reads.

The dashed arrows show how those copies catch up. CDC events go from the record to Change Capture. Then refresh/evict updates the cache, index update updates the index, and recompute updates the Materialized Views. In this design, analysts query those views rather than the live database.

If a copy falls behind, you can briefly see an older value. Losing the authoritative fact is a different failure. Keep that distinction clear: a stale copy can catch up only if the source and the required changes survive.

۳3 کلاود در برابر خودمیزبانیCloud vs self-hosting

ایده کلیدیKey idea

دیگه وقتشه بریم سراغ دعوای کلاود و خودمیزبانی: کدوم کار رو خودت بکنی و کدوم رو بدی دست ارائه‌دهنده. هزینه و بلدی تیم و میزان کنترل، هر سه تو این تصمیم بازی می‌کنن.

مثال فنی: مرز مسئولیت در میزبانی

وضعیت اولیه: فرض کن یه پایگاه داده داری که patch و backup و آزمون restore می‌خواد. مثل بچه‌ست، رسیدگی می‌خواد.

اجرای مرحله‌به‌مرحله: توی خودمیزبانی خودت آستین بالا می‌زنی و همه رو انجام می‌دی؛ توی سرویس مدیریت‌شده بخشی رو می‌سپری به ارائه‌دهنده. ولی schema و مجوزهای برنامه هنوز با توئه، فرار نداره.

نتیجه و دلیل: پس مدیریت‌شده بودن مسئولیت رو جابه‌جا می‌کنه، حذف نمی‌کنه. یادت باشه backup که تست restore نشده مثل چتر نجاتی که بازش نکردی — موقع پرش معلوم می‌شه.

A database needs patches, backups and restore checks whoever hosts it. The cloud decision is about which work the team keeps and which work a provider takes on. Weigh the total cost, the team's operational experience and the control the product needs. Build what sets the product apart; consider buying the standard parts.

Example: Who owns the hosting work?

Walk through it: With self-hosting, the team does that work. With a managed service, the provider takes on part of it. The application schema and permissions still belong to the team.

What this tells you: Managed hosting moves responsibility; it doesn't remove it. A backup you haven't tested restoring is still an untested recovery plan.

طیف برون‌سپاریThe outsourcing spectrum

قضیهٔ برون‌سپاری اینه: صفر و یک نیست: از اینکه تیمت همه‌چی رو بنویسه و اجرا کنه تا اینکه یه نرم‌افزار آماده رو فقط مصرف کنی، چند تا پله وسطه.

مثال فنی: سه راه ساخت جست‌وجو

وضعیت اولیه: فرض کن محصولت جست‌وجوی متن می‌خواد که غلط املایی رو بفهمه و رتبه‌بندی هم بده.

اجرای مرحله‌به‌مرحله: حالا سه راه داری: خودت موتور بنویسی، موتور آماده رو روی سرور خودت بالا بیاری، یا API مدیریت‌شده بخری. هر سه رو باید با یه مجموعه آزمون ثابت بسنجی.

نتیجه و دلیل: هزینهٔ ساخت و عملیات و وابستگی‌شون فرق داره. پول دادن برای API یعنی کیفیت جست‌وجو تضمین شده؟ نه عزیز، خودت باید تست کنی.

There's a spectrum here. At one end, bespoke software means the team writes and runs it. In the middle, self-hosted means running a packaged tool such as MySQL, either on-prem or on IaaS. At the other end, a cloud service or SaaS exposes an API. Moving along that spectrum changes who does the work and how much control the team keeps.

کی کلاود به‌صرفه است؟When does cloud win?

کی ابر می‌صرفه؟ وقتی انعطاف منابع یا کم شدن کار عملیاتی، کرایه‌ش رو جبران کنه. باید ته حساب رو دید: زیرساخت، آدم‌ها، انتقال داده و خرابی‌ها — همه با هم.

مثال فنی: حساب هزینهٔ ظرفیت فصلی

وضعیت اولیه: فرض کن بار عادی با ۲ تا worker راه می‌افته، ولی حراج دو روزه ۲۰ تا worker می‌خواد.

اجرای مرحله‌به‌مرحله: توی مدل ساعتی، اون ۱۸ تا worker اضافه فقط همون دو روز روشنن. هزینهٔ ذخیره و شبکه و سرویس‌های ثابت رو هم جدا حساب کن.

نتیجه و دلیل: پس کشسانی هزینهٔ ظرفیت بیکار رو کم می‌کنه. ولی از این مثال نپر به اینکه ابر همیشه ارزون‌تره — بار دائمی حساب دیگه‌ای داره.

  • به نفع کلاود: راه انداختن سیستمی که بلد نیستی؛ بار خیلی پرنوسان؛ سرعت و اینکه تیم بچسبه به مسئله‌های مهم‌تر.
  • به نفع خودمیزبانی: تجربهٔ عملیات داری و بار قابل پیش‌بینیه؛ کنترل کامل می‌خوای (مثل high-frequency trading)؛ می‌خوای برای بار خودت تیون کنی.

Cloud makes sense when flexible capacity or less operational work offsets the rental bill. Add up infrastructure, people, data transfer and failures before deciding.

  • Cloud wins when: the team lacks operational experience, load varies sharply, or getting started quickly frees the team to work on the product.
  • Self-hosting wins when: the team has operational experience and predictable load, needs full control, or benefits from tuning for a specific workload such as high-frequency trading.

Cloud Native و جدایی ذخیره‌سازی از محاسبهCloud native and storage/compute disaggregation

  • Cloud Native: معماری که از اول برای ابر طراحی شده؛ نه اینکه «نرم‌افزار قدیمی رو بندازی رو VM».
  • لایه‌بندی: سرویس‌های کف مثل Object Storage فایل‌های گنده رو نگه می‌دارن؛ سرویس‌های بالایی (مثل Snowflake) رو همونا سوار می‌شن.
  • جدایی (disaggregation): ذخیره تو S3، حساب‌وکتاب یه جای دیگه؛ پس دیسک محلی ماشین ابری دیگه «ماندگار» نیست — یه کش موقتیه، دل نبند.
  • تله دیسک مجازی: EBS ادای دیسک رو رو شبکه درمیاره؛ هر I/O یه سفر شبکه‌ست.
  • Multitenancy: سخت‌افزار مشترک بین مشتری‌ها — بازده بالاتر، ولی جداسازی تمیز کارایی و امنیت رو می‌خواد.
  • Cloud native: designed to use cloud capabilities, rather than simply moving an existing app onto a VM.
  • Layering: services such as object storage hold large files; services such as Snowflake build on that storage.
  • Disaggregation: storage stays in S3 while compute runs separately. In this design, the compute node's ephemeral local disk is a temp cache.
  • Virtual-disk trap: EBS provides block storage over the network, so I/O includes a network trip.
  • Multitenancy: customers share hardware to use it more efficiently; performance and security still need isolation.

ایده کلیدیKey idea

قانون اول: رو یه ماشین همه‌چی ساده‌ست؛ رو چند تا ماشین می‌تونی ظرفیت و تحمل خرابی بیشتری بسازی، ولی شبکه و هماهنگی هم می‌پرن وسط معرکه.

وضعیت اولیه: فرض کن دادهٔ فعالت 80 GB ـه و راحت توی سرور 128 GB جا می‌شه؛ تست بار هم می‌گه جواب می‌ده.

اجرای مرحله‌به‌مرحله: حالا اگه شارد اضافه کنی، مسیریابی و هماهنگی میاد توی مسیر — بدون اینکه هنوز ثابت شده باشه ظرفیت کم داری.

نتیجه و دلیل: پس فعلاً همون یه ماشین ساده‌تر و ارزون‌تره. replica برای تحمل خرابی یه نیاز جداست؛ با sharding قاطیش نکن.

Start by checking whether one machine can do the job. A single node is usually simpler and cheaper to operate. Tools such as DuckDB, SQLite and KùzuDB can handle many workloads on one machine. Distribution can add capacity and fault tolerance, but it also adds network and coordination work. Know which limit you're fixing.

Setup: The active dataset is 80 GB, it fits on a 128 GB server, and a load test says the machine can handle the requests.

Walk through it: Adding shards now adds routing and coordination before there's evidence of a capacity problem.

What this tells you: For this workload, one machine is simpler and cheaper for now. A replica for fault tolerance is a separate decision. Don't mix it up with sharding for capacity.

چرا اصلاً توزیع کنیم؟ (دلایل واقعی)Why distribute at all? (real reasons)

توزیع کردن باید یه درد مشخص رو دوا کنه: جا کم آوردی، می‌خوای موقع خرابی سرپا بمونی، یا می‌خوای داده رو ببری نزدیک کاربر. هر درد، نسخهٔ خودش رو می‌خواد.

مثال فنی: توزیع برای حل یک محدودیت مشخص

وضعیت اولیه: فرض کن آرشیوت 40 TB ـه، ولی هر سرور فقط 10 TB جا داره. جا نمی‌شه، خب؟

اجرای مرحله‌به‌مرحله: حالا کلیدها رو پخش می‌کنی بین چند shard، بعد برای هر shard یه نسخهٔ پشتیبان زنده هم می‌ذاری.

نتیجه و دلیل: پس sharding ظرفیت رو زیاد می‌کنه، replication تحمل خرابی رو. دو تا کار جدا — قاطی‌شون نکن که تو مصاحبه لو می‌ری.

  • توزیع ذاتی: دو تا کاربر با دو تا گوشی بخوان حرف بزنن، راهی جز شبکه نیست.
  • تحمل خرابی / دسترس‌پذیری: یه ماشین افتاد، سرویس نباید بخوابه.
  • مقیاس‌پذیری: حجم یا حساب از زور یه ماشین بیشتر بشه.
  • تأخیر: کاربر جهانی داری ← سرور ببر نزدیک هر کاربر.
  • ارتجاع: فقط پول همون چیزی رو بده که مصرف کردی، تو اوج و فرود بار.
  • سخت‌افزار خاص، قانون محل داده (data residency) و انرژی — اینا هم هستن.

Distribute to solve a specific problem: more data than one machine can hold, a service that must survive a machine failure, or users who need a nearby server. Each reason points to a different design.

  • Inherent distribution: users on separate phones need a network to communicate.
  • Fault tolerance / availability: keep serving requests when a machine fails.
  • Scalability: handle more data or computation than one machine can manage.
  • Latency: place servers closer to users in different regions.
  • Elasticity: adjust resources to changing load and pay for the capacity used.
  • Specialized hardware, data-residency laws and energy constraints can also require distribution.

Walk through it: Spread keys across shards, then give each shard a live replica for fault tolerance.

What this tells you: Sharding adds capacity; replication adds fault tolerance. Name which of those jobs the design needs before adding machines.

هزینه‌های توزیع + میکروسرویس و ServerlessCosts of distribution + microservices and serverless

حالا که سرویس‌ها رو جدا کردی، هر درخواست ممکنه از چند تا سیم شبکه رد بشه. تأخیر و خطا و تکرار و خرج اجرای هر تیکه رو هم باید حساب کنی — مفت نیست.

مثال فنی: ثبت موفق، پاسخ گم‌شده

وضعیت اولیه: فرض کن سرویس سفارش درخواست r7 رو ثبت کرده، ولی جواب توی شبکه گم شده. استرس نگیر.

اجرای مرحله‌به‌مرحله: کلاینت همون r7 رو دوباره می‌فرسته؛ قید یکتایی روی شناسهٔ درخواست نمی‌ذاره سفارش دوم ساخته بشه و نتیجهٔ قبلی برمی‌گرده.

نتیجه و دلیل: پس timeout یعنی «نمی‌دونم چی شد»، نه «انجام نشد». اگه هر retry یه شناسهٔ تازه بسازه، یهو دو تا سفارش واقعی داری — این دام معروفه.

  • هر درخواست شبکه ممکنه timeout بخوره؛ نمی‌دونی سرویس گرفته یا نه، و «تکرار کورکورانه» ممکنه خطرناک باشه (فصل ۹).
  • صدا زدن شبکه خیلی کندتر از صدا زدن تابع تو همون فرآینده؛ گاهی بردن «محاسبه» سمت داده تندتره. گرهٔ بیشتر ≠ سرعت بیشتر — حفظ کن.
  • دیباگ سخت می‌شه ← Observability: متریک و لاگ و ردیابی با OpenTelemetry و Zipkin و Jaeger — چراغ‌قوه‌ته.
  • وقتی هر سرویس دیتابیس خودش رو داره، جور کردن داده بین سرویس‌ها می‌افته گردن خود برنامه — کسی دیگه نیست.

Once a request crosses service boundaries, the network becomes part of the work. Account for its latency, failures, retries and operating costs.

  • A network call can time out without telling you whether the service completed the operation. A blind retry can repeat the effect (Chapter 9).
  • A network call is much slower than an in-process call. Sometimes moving computation closer to the data is faster. More nodes don't automatically mean more speed.
  • Debugging needs observability: metrics, logs and tracing with tools such as OpenTelemetry, Zipkin and Jaeger.
  • When each service owns its database, the application has to coordinate data across services.

Example: The order succeeded; the response disappeared

Setup: The order service records request r7, but the response gets lost on the network.

Walk through it: The client sends the same r7 again. A unique constraint on the request identifier prevents a second order, and the service returns the existing result.

What this tells you: A timeout means the outcome is unknown. If every retry gets a fresh identifier, the system can create two real orders. Keep the identifier stable.

میکروسرویس و Serverless در یک نگاهMicroservices and serverless at a glance
  • میکروسرویس: هر سرویس یه هدف، یه API و یه تیم؛ معمولاً هر سرویس دیتابیس خودش رو داره. سود: آپدیت مستقل. خرج: تست و استقرار و مانیتورینگ و عوض شدن API.
  • حرف طلایی: «میکروسرویس جواب فنی به یه مسئلهٔ انسانیه» — تو شرکت کوچیک فقط خرج اضافه‌ست.
  • Serverless / FaaS: فقط پول اجرایی که کردی؛ ولی سقف زمان تابع و محیط تنگ و cold start هم هست.
  • Microservices: each service has a purpose, an API and an owning team, and usually its database. Independent releases are the benefit; testing, deployment, monitoring and API changes are the cost.
  • Think of microservices as a technical way to support team independence. For a small team, the extra work may cost more than that independence saves.
  • Serverless / FaaS: pay for execution, with function time limits, a restricted environment and cold starts to account for.

مثال فنی: حذف در چند نسخه

وضعیت اولیه: فرض کن دادهٔ مشتری 17 هم توی مرجع هست، هم توی ایندکس، هم توی فایل گزارش. سه‌جا پخشه.

اجرای مرحله‌به‌مرحله: حالا جریان حذف با همون شناسه می‌ره سراغ همهٔ مقصدها. وضعیت حذف و زمان نگهداری و محدودیت backup هم ثبت می‌شه.

نتیجه و دلیل: پس پاک کردن یه ردیف یعنی همهٔ کپی‌ها پاک شدن؟ نه! دامنهٔ حذف و قانون نگهداری رو برای همون کاربرد چک کن؛ restore هم می‌تونه مرده رو زنده کنه.

An architecture also decides what gets collected, who can see it, and how it can be corrected or deleted. People's rights belong in those decisions alongside speed and capacity.

  • انطباق گنگه: قانون حرف‌های کلی می‌زنه که هرکی یه جور می‌فهمه، تکنولوژی خاص نمی‌گه.

  • GDPR (since 2018), CCPA and the EU AI Act are part of the regulatory context. Rights such as the right to be forgotten affect data design.
  • Deletion work: account for immutable append-only files and derived copies such as ML training datasets.
  • Compliance: translate general legal principles into concrete engineering choices for the particular use case.
  • Data minimization (Datensparsamkeit): collect and keep less, rather than saving everything. Storage costs also include exposure to leaks, reputational damage, fines and legal work.
  • In payments and software services, account for PCI and SOC 2, respectively, and periodic independent audits.

۱. سیستم data-intensive یعنی چه؟ فرقش با compute-intensive؟1. What is a data-intensive system? How does it differ from compute-intensive?

تو سیستم داده‌محور درد اصلی نگه‌داشتن و پیدا کردن و هماهنگ نگه‌داشتن اطلاعاته. تو سیستم محاسبه‌محور درد اصلی خود حساب سنگینه‌ست — این دو تا رو قاطی نکن.

مثال فنی: دادهٔ بیشتر یا محاسبهٔ بیشتر؟

وضعیت اولیه: یه سرویس سفارش رو تصور کن که روزی یه میلیون رکورد با customer_id و status قورت می‌ده.

اجرای مرحله‌به‌مرحله: حالا صحنه رو بچین: پرس‌وجوی وضعیت فقط دنبال یه رکورد درست با ایندکس می‌گرده؛ اون‌ور یه سرویس تبدیل ویدیو داره با CPU روی یه فایل عرق می‌ریزه.

نتیجه و دلیل: پس دغدغه اولی داده‌ست، دغدغه دومی محاسبه. یادت باشه یه محصول می‌تونه هر دو دغدغه رو هم‌زمان داشته باشه.

Data-intensive means the hard part is storing, finding and keeping information consistent as data changes and requests overlap. Compute-intensive means the calculation itself is the hard part. Ask where the work goes: looking after the data, or performing the computation?

Example: More data, or more computation?

Setup: Picture an order service taking in a million records a day, each with customer_id and status.

Walk through it: A status query uses an index to find the right record. Compare that with a video converter spending CPU time processing a file.

What this tells you: The first service's main challenge is the data; the second's is computation. A single product can need both kinds of work.

۲. پنج تفاوت OLTP و OLAP را بگو.2. Name five OLTP vs OLAP differences.

حفظ کن: پنج تا فرق اصلی: خوندن چند رکورد در برابر شخم زدن خروار رکورد؛ تغییر کوچیک در برابر ورود دسته‌ای؛ کاربر محصول در برابر تحلیلگر؛ کوئری مشخص در برابر دلبخواهی؛ وضعیت فعلی در برابر تاریخچه — همین پنج تا رو بگو، تمومه.

مثال فنی: دو پرس‌وجو، دو الگوی دسترسی

وضعیت اولیه: فرض کن جدول orders صد میلیون ردیف داره — یه غول واقعی. روی id هم ایندکس شده.

اجرای مرحله‌به‌مرحله: WHERE id=42 با ایندکس مثل برق فقط چند صفحه رو می‌خونه؛ ولی SUM(amount) کل سال مجبوره ستون مبلغ رو شخم بزنه.

نتیجه و دلیل: اولی OLTP ـه، دومی OLAP. یادت باشه ایندکسی که اولی رو پرواز می‌ده، لزوماً دومی رو نجات نمی‌ده.

Walk through five differences: reads touch a few records vs scan many; writes are small changes vs bulk or streaming input; users are product users vs analysts; queries are fixed vs free-form; and data describes current state vs history. Those five give you a clear comparison. The scale also differs: gigabytes through terabytes for OLTP, terabytes through petabytes for OLAP.

Example: Two queries, two access patterns

Setup: Take an orders table with a hundred million rows and an index on id.

Walk through it: With the index, WHERE id=42 reads just a few pages. A full year's SUM(amount) has to scan the relevant amounts.

What this tells you: The first query is OLTP; the second is OLAP. An index that helps the first doesn't necessarily help the second. Match the layout to the work.

۳. Data Warehouse و Data Lake چه فرقی دارند؟3. Warehouse vs lake?

فرقشون ساده‌ست: انبار داده معمولاً اطلاعات تمیز و آمادهٔ تحلیل داره. دریاچهٔ داده قالب‌های جورواجور، از جمله فایل خام، نگه می‌داره؛ هر دو هم مدیریت کیفیت و معنا می‌خوان — هیچ‌کدوم بی‌صاحب نیستن.

مثال فنی: یک ورودی، فایل خام و جدول آماده

وضعیت اولیه: فرض کن فایل JSON فروش مبلغ رو با دو واحد قاطی داره، عکس کالا هم بغلش خوابیده.

اجرای مرحله‌به‌مرحله: حالا دریاچه همهٔ فایل‌های خام با هر قالبی رو نگه می‌داره؛ pipeline واحد مبلغ رو یکی می‌کنه و جدول fact فروش رو برای انبار آماده می‌کنه.

نتیجه و دلیل: پس کوئری انبار روی قرارداد آمادهٔ fact اجرا می‌شه. ولی خوندن خام توی lake هنوز تشخیص schema و کیفیت می‌خواد — خام یعنی آماده نیست، یادت باشه.

A warehouse usually holds cleaned, analysis-ready tables for reporting. A lake holds data in varied formats, including raw files that consumers prepare later. Both need clear meaning and quality checks. Putting files in a lake doesn't remove that work.

Example: One input, raw files and prepared tables

Setup: A sales JSON file mixes amount units, with product photos stored alongside it.

Walk through it: The lake keeps the raw files in their different formats. A pipeline standardizes the amounts and prepares a sales fact table for the warehouse.

What this tells you: Warehouse queries use that prepared contract. Reading the lake's raw files still needs schema and quality checks. Stored doesn't mean analysis-ready.

۴. ETL در برابر ELT؟4. ETL vs ELT?

تو ETL داده قبل ورود به مقصد تبدیل می‌شه. تو ELT اول وارد مقصد می‌شه، بعد همون‌جا تبدیل می‌شه — فرقشون فقط جای تبدیله.

مثال فنی: ETL و ELT روی واحد مبلغ

وضعیت اولیه: فرض کن منبع اول مبلغ 100 تومان می‌فرسته، منبع دوم 1000 ریال. همون پول، دو زبون.

اجرای مرحله‌به‌مرحله: توی ETL هر دو قبل از بارگذاری می‌شن 1000 ریال؛ توی ELT اول دادهٔ خام بارگذاری می‌شه، بعد تبدیل توی مقصد اجرا می‌شه.

نتیجه و دلیل: پس خروجی نهایی می‌تونه یکی باشه. فرق سر محل و زمان تبدیله و اینکه CPU کی رو بسوزونی — همین.

With ETL, transform the data before loading it into the destination. With ELT, load it first and transform it there. Follow the transformation: its location is the difference.

Example: ETL and ELT with amount units

Setup: One source sends 100 tomans; another sends 1000 rials. Same amount, different units.

Walk through it: ETL converts both to 1000 rials before loading. ELT loads the raw input first, then converts it at the destination.

What this tells you: The final result can match. What changes is where and when the transformation runs, and which system supplies the compute.

۵. چرا تحلیل را روی پایگاه داده عملیاتی اجرا نمی‌کنیم؟5. Why not run analytics on the operational DB?

چون تحلیل ممکنه دادهٔ چند تا سیستم رو بخواد، با ساختار عملیاتی حال نکنه، منابع زیادی بخوره یا دسترسی جدا بخواد. جداسازی برای همینه، نه اینکه تحلیل رو مرجع همیشه ممنوعه — دلیل داره.

مثال فنی: ثبت خرید در برابر گزارش فروش

وضعیت اولیه: فرض کن ثبت سفارش فقط ردیف سفارش 42 و موجودی کالای P7 رو دست می‌زنه. یه کار کوچیک و تمیز.

اجرای مرحله‌به‌مرحله: حالا گزارش ماهانه با SUM(amount) GROUP BY city رو نگاه کن: باید میلیون‌ها ردیف رو بخونه. اگه هر دو رو بندازی روی یه منبع ضعیف، صف درست می‌شه.

نتیجه و دلیل: پس نسخهٔ تحلیلی دعوا سر منابع رو کم می‌کنه. فقط یادت باشه گزارش به اندازهٔ تأخیر انتقال از مرجع عقبه؛ تازه نیست، طبیعیه.

Give the reason that fits: the report needs several source systems, the OLTP schema doesn't suit the analysis, the query competes with live traffic, or access needs to be separated. These explain why a separate analytical copy helps. They don't mean every analytical query on the record is forbidden.

Example: Recording a purchase vs reporting sales

Setup: Recording order 42 touches the order row and the stock for product P7. That's a small amount of work.

Walk through it: The monthly report uses SUM(amount) GROUP BY city and reads millions of rows. Put both workloads on an underpowered shared resource and requests start queuing.

What this tells you: An analytical copy reduces that competition. Its report is still behind the record by however long data transfer takes. Separation buys room to work, with freshness to account for.

۶. System of Record و Derived Data را تعریف و مثال بزن.6. Define system of record and derived data, with examples.

تعریفش اینه: سیستم مرجع نسخهٔ درست هر داده رو نگه می‌داره. دادهٔ مشتق‌شده با تبدیل مرجع ساخته می‌شه و باید راه ساخت و به‌روزشدنش مشخص باشه — بی‌لوله قبول نیست.

مثال فنی: بازسازی دادهٔ مشتق‌شده

اجرای مرحله‌به‌مرحله: حالا بریم سراغ بازسازی: اول snapshot مرجع تا موقعیت لاگ 500 می‌ره توی ایندکس تازه، بعد تغییرهای بعد از 500 یکی‌یکی اعمال می‌شن.

The system of record holds the authoritative version of a fact. Derived data is built from it, such as a cache, index, materialized view or ML model. Explain how each copy gets built and updated, and what inputs you'd need to rebuild it.

Example: Rebuilding derived data

What this tells you: A defined snapshot boundary and the matching log let the index catch up. An old copy alone can miss changes made during the copy. You need both sides of that boundary.

کش و ایندکس داده رو برای یه خوندن خاص آماده می‌کنن. اگه فقط از مرجع ساخته شده باشن و مواد لازم موجود باشه، خرابیشون با از نو ساختن جبران می‌شه — نگران نباش.

۸. HTAP چیست و چرا جایگزین انبارداده نشد؟8. What is HTAP, and why didn’t it replace the warehouse?

HTAP بار تراکنشی و تحلیلی رو به هم نزدیک می‌کنه، ولی نیاز جمع کردن دادهٔ چند منبع و تاریخچه و ساختار مناسب تحلیل رو خودش حذف نمی‌کنه — جادو نیست.

مثال فنی: HTAP و نیاز چندمنبعی

وضعیت اولیه: فرض کن یه موتور هم ثبت سفارش رو انجام می‌ده، هم گزارش سریع روی همون سفارش‌ها می‌ده. همه‌کاره به نظر میاد، نه؟

اجرای مرحله‌به‌مرحله: ولی گزارش نرخ تبدیل کلیک وب و تماس پشتیبانی رو هم می‌خواد. اینا هنوز باید با customer_id و بازهٔ زمانی قاطی و یکدست بشن.

نتیجه و دلیل: پس چسبوندن OLTP و OLAP دردسر جمع کردن دادهٔ چند سامانه رو حذف نمی‌کنه. HTAP جادو نیست، یادت باشه.

HTAP brings transactional and analytical workloads into one system, often using separate engines behind a shared interface. You still need to combine data from different sources, keep history and shape it for analysis. HTAP doesn't make those warehouse jobs disappear.

Example: HTAP still needs other sources

What this tells you: Combining OLTP and OLAP doesn't remove the job of combining several systems' data. HTAP doesn't do that work for you.

۹. Reverse ETL چیست؟9. What is reverse ETL?

Reverse ETL یعنی نتیجهٔ آمادهٔ تحلیل رو برگردونی تو ابزار عملیاتی تا تو کار روزمره استفاده بشه — رفت و برگشت.

مثال فنی: برگرداندن نتیجهٔ تحلیل به عملیات

وضعیت اولیه: فرض کن انبار داده برای مشتری 17 حساب کرده مجموع خرید ۹۰ روزه شده 8000.

اجرای مرحله‌به‌مرحله: حالا job میاد وسط: هرکی بالای 5000 خریده رو با کلید customer_id می‌فرسته توی CRM، زمان محاسبه رو هم همراهش می‌فرسته.

نتیجه و دلیل: حالا CRM از برچسب آماده استفاده می‌کنه — اسمش Reverse ETL ـه. فقط یادت باشه این برچسب تا اجرای بعدی تازه نمی‌شه؛ تاریخ انقضا داره.

Reverse ETL takes a finished analytical result back into an operational tool. Think of a customer segment sent to the CRM or a trained recommender used by a production service. The analysis becomes something the product can act on.

Example: Bringing analysis back into operations

Setup: The warehouse calculates that customer 17 spent 8000 over 90 days.

Walk through it: A job sends customers who spent more than 5000 into the CRM, keyed by customer_id, with the calculation time attached.

What this tells you: The CRM uses that prepared label. That's Reverse ETL. The label won't update until the job runs again, so its age matters.

۱۰. Cloud Native یعنی چه؟ جدایی storage و compute چه فایده‌ای دارد؟10. What is cloud native? What does storage/compute separation buy you?

طراحی ابری یعنی از قابلیت‌های محیط ابر استفاده کنی. با جدایی ذخیره و محاسبه می‌تونی ظرفیت پردازش رو جدا از داده کم‌وزیاد کنی؛ فقط اجرا شدن رو ماشین ابری کافی نیست — ابر فقط یه اسم نیست.

مثال فنی: پردازش جدا از فایل‌ها

وضعیت اولیه: فرض کن گزارشت روی 10 TB فایل فروش خوابیده توی یه مخزن مشترک.

اجرای مرحله‌به‌مرحله: سر آخر ماه ۲۰ تا worker میان فایل‌ها رو تقسیم می‌کنن، کار رو می‌کنن، بعد خاموش می‌شن. فایل‌ها سر جاشون می‌مونن.

نتیجه و دلیل: پس compute رو مستقل از حجم داده کم و زیاد می‌کنی. فقط یادت باشه سرعت خوندن مخزن و شبکه هنوز می‌تونه گلوت رو بگیره.

Cloud native means designing around cloud capabilities. Separating storage and compute lets you add or remove processing capacity while the stored data stays in place. Running an existing app on a cloud VM alone doesn't give you that design.

Example: Compute separate from the files

Setup: A report reads 10 TB of sales files in shared storage.

Walk through it: At month-end, 20 workers split up the files, process them and shut down. The files stay where they are.

What this tells you: Compute capacity changes independently of data volume. Storage read speed and network bandwidth can still be the bottleneck. More workers don't remove those limits.

۱۱. دیسکِ محلیِ موقت و EBS چه تفاوتی دارند؟11. Why is the cloud local disk ephemeral, and what is the EBS trap?

دیسک محلی موقت با دیسک پایدار ابری فرق داره. تو EC2، instance store مال دادهٔ موقته؛ EBS ذخیرهٔ بلوکی وصل از شبکه‌ست و رفتار و خرجش رو باید جدا سنجید — دو تا چیز جدا.

مثال فنی: دیسک موقت در برابر EBS

وضعیت اولیه: فرض کن worker ابری دو چیز تولید می‌کنه: یه فایل میانی که اگه پاک بشه قابل ساخت مجدده، و یه نسخهٔ سفارش تأییدشده که تکیه.

اجرای مرحله‌به‌مرحله: فایل میانی رو بنداز روی instance store، اشکالی نداره. ولی برای دادهٔ معتبر ذخیرهٔ پایدار و سیاست backup می‌خوای. EBS هم از دیسک محلی جداست؛ پاک شدنش موقع پایان نمونه بستگی به تنظیمات داره، خودکار فرضش نکن.

نتیجه و دلیل: پس نوع دیسک و عمرش بخشی از طراحی ماندگاریه. «روی ابره پس امنه» جواب نیست — این جمله رو تو مصاحبه نگی.

منبعِ توضیحِ فنی: ذخیرهٔ موقتِ EC2 · ذخیرهٔ بلوکیِ EBS

An ephemeral local disk is temporary storage tied to the machine. EBS is block storage reached over the network, with a different lifecycle, performance profile and cost. Don't treat the two as interchangeable. Check what survives each operation before relying on it.

Example: Temporary disk vs EBS

Setup: A cloud worker produces a rebuildable intermediate file and the only copy of a confirmed order.

Walk through it: The intermediate file can use instance store. Authoritative data needs durable storage and a backup policy. EBS has a separate lifecycle; whether it gets deleted on instance termination depends on configuration.

What this tells you: Disk type and lifecycle are part of the durability design. Being in the cloud doesn't tell you what survives.

۱۲. Multitenancy چه سود و چه ریسکی دارد؟12. Multitenancy: benefit and risk?

چندمستاجری منابع و عملیات رو مشترک می‌کنه و می‌تونه خرج رو کم کنه. ولی جداسازی دسترسی و جلوگیری از اینکه بار یه مشتری بقیه رو خفه کنه واجبه — همسایهٔ پرمصرف رو یادته؟

مثال فنی: همسایهٔ پرمصرف

وضعیت اولیه: فرض کن دو تا tenant روی یه پایگاه داده سوارن؛ tenant A یه گزارش اسکن کامل می‌فرسته که همه‌چی رو شخم می‌زنه.

اجرای مرحله‌به‌مرحله: حالا برای A سهم منابع و سقف هم‌زمانی می‌ذاری، بعد همهٔ کوئری‌ها رو با tenant_id قفل می‌کنی به همون مستأجر.

نتیجه و دلیل: پس سهم‌بندی نمی‌ذاره B خفه بشه. ولی یادت باشه کنترل دسترسی یه درد جداست — نشت داده بین tenantها با سهمیه حل نمی‌شه.

Sharing hardware and operational work can reduce cost. But you need to keep each tenant's data private and stop one heavy workload from slowing everyone else down. Resource sharing helps only when access and performance are properly isolated.

Example: The noisy neighbor

Setup: Two tenants share a database. Tenant A starts a report that scans the whole table.

Walk through it: Give A a resource share and concurrency limit. Scope every query to its tenant with tenant_id.

What this tells you: Resource limits protect B from A's workload. Access control is a separate requirement: a quota doesn't prevent a cross-tenant data leak.

۱۳. کی باید سراغ سیستم توزیع‌شده برویم؟13. When should we go distributed?

وقتی یه درد واقعی داری — جا کم آوردی، خرابی، تأخیر جغرافیایی، کشسانی، سخت‌افزار خاص یا قانون محل داده — اون‌وقت توزیع رو بررسی کن. و کمترین توزیع لازم رو انتخاب کن — زیاده‌روی ممنوع.

مثال فنی: توزیع برای حل یک محدودیت مشخص

وضعیت اولیه: فرض کن آرشیوت 40 TB ـه، ولی هر سرور فقط 10 TB جا داره. جا نمی‌شه، خب؟

اجرای مرحله‌به‌مرحله: حالا کلیدها رو پخش می‌کنی بین چند shard، بعد برای هر shard یه نسخهٔ پشتیبان زنده هم می‌ذاری.

نتیجه و دلیل: پس sharding ظرفیت رو زیاد می‌کنه، replication تحمل خرابی رو. دو تا کار جدا — قاطی‌شون نکن که تو مصاحبه لو می‌ری.

Consider distribution when there's a real need: users already on separate devices, fault tolerance, capacity beyond one machine, geographic latency, elasticity, specialized hardware, data residency or energy constraints. State the need first, then choose the smallest distributed design that meets it.

Example: Distributing to fix a specific limit

Setup: The archive is 40 TB, but each server holds only 10 TB. It won't fit on one machine.

Walk through it: Spread keys across shards, then give each shard a live replica for fault tolerance.

What this tells you: Sharding adds capacity; replication adds fault tolerance. Name which of those jobs the design needs before adding machines.

وضعیت اولیه: فرض کن سرویس سفارش درخواست r7 رو ثبت کرده، ولی جواب توی شبکه گم شده. استرس نگیر.

اجرای مرحله‌به‌مرحله: کلاینت همون r7 رو دوباره می‌فرسته؛ قید یکتایی روی شناسهٔ درخواست نمی‌ذاره سفارش دوم ساخته بشه و نتیجهٔ قبلی برمی‌گرده.

نتیجه و دلیل: پس timeout یعنی «نمی‌دونم چی شد»، نه «انجام نشد». اگه هر retry یه شناسهٔ تازه بسازه، یهو دو تا سفارش واقعی داری — این دام معروفه.

A network adds latency and uncertain outcomes. Then come retries, harder debugging and the work of keeping data consistent across services. Include those costs when you explain what distribution buys.

Example: The order succeeded; the response disappeared

Setup: The order service records request r7, but the response gets lost on the network.

Walk through it: The client sends the same r7 again. A unique constraint on the request identifier prevents a second order, and the service returns the existing result.

What this tells you: A timeout means the outcome is unknown. If every retry gets a fresh identifier, the system can create two real orders. Keep the identifier stable.

۱۵. چرا retry کورکورانه خطرناک است؟15. Why is blind retry dangerous?

بعد timeout نمی‌دونی عملیات اجرا شده یا نه. شناسهٔ ثابت و عملیات مقاوم به تکرار یا استعلام نتیجه جلوی اثر دوباره رو می‌گیرن — همون ورد جادویی idempotency.

مثال فنی: ثبت موفق، پاسخ گم‌شده

وضعیت اولیه: فرض کن سرویس سفارش درخواست r7 رو ثبت کرده، ولی جواب توی شبکه گم شده. استرس نگیر.

اجرای مرحله‌به‌مرحله: کلاینت همون r7 رو دوباره می‌فرسته؛ قید یکتایی روی شناسهٔ درخواست نمی‌ذاره سفارش دوم ساخته بشه و نتیجهٔ قبلی برمی‌گرده.

نتیجه و دلیل: پس timeout یعنی «نمی‌دونم چی شد»، نه «انجام نشد». اگه هر retry یه شناسهٔ تازه بسازه، یهو دو تا سفارش واقعی داری — این دام معروفه.

A timeout doesn't tell you whether the operation ran. Retrying can repeat an effect that already happened. Use a stable request identifier with an idempotent operation, or check the recorded result before trying again. Explain how the system recognizes the same attempt.

۱۶. چرا میکروسرویس برای تیم کوچک overkill است؟16. Why are microservices overkill for a small team?

میکروسرویس می‌تونه استقلال تیم‌ها رو بیشتر کنه، ولی استقرار و آزمون و پایش و قرارداد شبکه خرج دارن. برای تیم کوچیک این خرج ممکنه از سود جداسازی بیشتر باشه — حساب کن.

مثال فنی: هزینهٔ خرد کردن برنامه

وضعیت اولیه: فرض کن سه نفرین روی یه برنامهٔ ماژولار با یه مسیر انتشار. جمع‌وجور و راحت.

اجرای مرحله‌به‌مرحله: حالا تیکه‌تیکه‌ش کن به ۱۰ تا سرویس: قرارداد شبکه می‌خواد، مانیتورینگ می‌خواد، timeout و انتشار جدا برای هر سرویس می‌خواد. می‌بینی چقدر خرج رو دستت می‌ذاره؟

نتیجه و دلیل: پس جداسازی وقتی می‌ارزه که استقلال یا مقیاس بده. سرویس بیشتر مساوی معماری بهتر نیست — اینو قاب کن بزن به دیوار.

Microservices can let teams release independently. They also add deployments, tests, monitoring and network contracts. For a small team, that work may outweigh the benefit. Compare the saved coordination with the extra operational work before splitting the application.

Example: The cost of splitting an application

Setup: Three people work on a modular application with one release path.

Walk through it: Split it into 10 services. Now each service needs network contracts, monitoring, timeout handling and its own deployment.

What this tells you: The split needs to earn its cost through independence or scale. A larger service count alone doesn't make the architecture better.

۱۷. «حق فراموش شدن» با لاگ‌های append-only چه تضادی دارد؟17. How does the right to be forgotten clash with append-only logs?

لاگ فقط‌افزودنی برای نگه‌داشتن تاریخچه ساخته شده، ولی حذف داده باید تو مرجع و نسخه‌های مشتق‌شده و سیاست نگه‌داری دیده بشه. جزئیات حقوقی‌ش هم موردبه‌مورد فرق داره.

مثال فنی: حذف در چند نسخه

وضعیت اولیه: فرض کن دادهٔ مشتری 17 هم توی مرجع هست، هم توی ایندکس، هم توی فایل گزارش. سه‌جا پخشه.

اجرای مرحله‌به‌مرحله: حالا جریان حذف با همون شناسه می‌ره سراغ همهٔ مقصدها. وضعیت حذف و زمان نگهداری و محدودیت backup هم ثبت می‌شه.

نتیجه و دلیل: پس پاک کردن یه ردیف یعنی همهٔ کپی‌ها پاک شدن؟ نه! دامنهٔ حذف و قانون نگهداری رو برای همون کاربرد چک کن؛ restore هم می‌تونه مرده رو زنده کنه.

An append-only log is built to preserve history; deleting an individual person's data asks for something different. You need to account for the record, derived copies and retention policy together. The exact legal requirements depend on the case, so don't treat deleting one row as proof that every copy is gone.

Walk through it: The deletion flow uses the same identifier to reach each destination. It also records deletion status, retention periods and backup limitations.

What this tells you: Deleting one row doesn't prove every copy is gone. Check the deletion scope and retention rules for the use case. A restore can bring old data back too.

۶.۳ اشتباهات رایج در جواب‌های مصاحبه6.3 Common interview mistakes

  • گفتن «میکروسرویس بهتره» بدون گفتن دلیل و خرجش — شعار نده.
  • کش/ایندکس رو گذاشتن جای حقیقت، یا نداشتن لولهٔ انتشار تغییر — هر دو غلطه.
  • نفهمیدن فرق «کپی فقط‌خوندنی تحلیلی» با «دیتابیس عملیاتی» — دو تا دنیای جدا.
  • یادت بره که تو سیستم پخش‌شده timeout یعنی «نمی‌دونم» نه «نشد» — فرقش زمین تا آسمونه.
  • تریدآف رو تحلیل نکردن: هر جواب باید بگه «به چه قیمتی» — اینو نگفتی یعنی هیچی نگفتی.
  • Choosing microservices without naming the problem they solve or the extra work they add.
  • Treating a derived cache or index as the source of truth, or leaving out the change-propagation path.
  • Confusing a read-only analytical copy with the operational database.
  • Reading a timeout as proof of failure when the outcome is still unknown.
  • Giving a design choice without explaining what it costs.

۶.۴ چک‌لیست مرور ۵ دقیقه‌ای6.4 Five-minute checklist

  1. جدول OLTP/OLAP رو از حفظ بگو (۵ سطر) — چشم‌بسته.
  2. تعریف record/derived با مثالش — با مثال، نه حفظی.
  3. مسیر داده رو بکش: operational ← ETL ← warehouse/lake ← consumer ← reverse ETL.
  4. سه تا سود و سه تا ریسک کلاود + یه جمله دربارهٔ جدایی storage/compute.
  5. سه تا دلیل توزیع + سه تا خرجش + کلمهٔ جادویی idempotency.
  6. یه جمله دربارهٔ GDPR و data minimization — کوتاه و دقیق.
  1. Explain the OLTP/OLAP comparison from memory (5 rows).
  2. Define record and derived data, then give a concrete example.
  3. Draw the path: operational → ETL → warehouse/lake → consumer → reverse ETL.
  4. Give three reasons to choose cloud and three risks, then explain storage/compute separation in one sentence.
  5. Name three reasons to distribute, three costs and how idempotency makes retries safe.
  6. Explain GDPR and data minimization in one sentence.
