پردازش جریانیStream Processing

ببین رفیق، تو پردازش جریانی داده یواش‌یواش میاد و هیچ‌وقت «تمام» نمی‌شه. جلوت چهار تا سؤال می‌مونه: ترتیب چیه، پیامِ تکراری چه بلایی میاره، دادهٔ دیررس رو کِی حساب می‌کنیم و بعد از خرابی از کِی ادامه بدیم.
Here's the thing: batch wants a bounded input with a known end — but real user data never finishes. It just keeps arriving, piece by piece, unbounded. You can fake it with a daily batch, or you can do the honest thing: process each event continuously — that's stream processing. Three questions carry the whole chapter: how events get transported (messaging and logs), how they relate to databases (sync, CDC, the state/stream duality), and how they get processed (windows, joins, time, exactly-once).

قضیه اینه که داده تو پردازش جریانی هیچ‌وقت «تمام» نمی‌شه. چهار تا سؤال رو باید جواب بدی: ترتیب چیه، پیامِ تکراری چه می‌کنه، دادهٔ دیررس رو کِی حساب می‌کنی و بعد از خرابی از کِی ادامه می‌دی.

مثال فنی: از پیام تا اثرِ پایدار

وضعیت اولیه: رویداد e7 می‌گه سفارش ۴۲ به مبلغ ۲۰۰ ثبت شده.

اجرای مرحله‌به‌مرحله: مصرف‌کننده‌اش رو می‌خونه، جمعِ فروش رو عوض می‌کنه و موقعیتِ پیشرفت رو ذخیره می‌کنه؛ اگه crash بینِ همین دو تا بیفته، تکرار می‌سازه.

نتیجه و دلیل: طراحیِ استریم باید دو چیز رو با هم روشن کنه: پیام کجا نگه داشته می‌شه، و اثر با پیشرفت چطور اتمی می‌شه. — یادت باشه.

مثال‌های این فصل سناریوهای آموزشیِ برگرفته از کارهای روزمره‌اند. عددهای انتخاب‌شده برای توضیح‌اند؛ معماریِ داخلیِ یک شرکت مشخص را توصیف نمی‌کنند.

In batch a job's input and output are files. The streaming equivalents: an event (a small, self-contained, immutable record of something that happened at a point in time, usually with a timestamp), a topic (a group of same-kind events — the filename equivalent), and a broker (the filesystem equivalent: where the producer writes and the consumer reads).

And just as immutable input made replay and testing possible back in Chapter 11, the append-only log does the same job here: consuming means reading, not deleting — so you can reprocess yesterday. That's the whole trick, friend.

۱1 انتقالِ رویدادهاTransporting events

۱.۱. رویداد، تاپیک، تولیدکننده و مصرف‌کننده1.1. Events, topics, producers and consumers

رویداد یعنی «این اتفاق افتاد». تولیدکننده می‌فرسته‌اش، تاپیک دستهٔ منطقیِ پیام‌هاست و مصرف‌کننده برای کارِ خودش می‌خونش.

مثال فنی: چهار نقش، یک سفارش

وضعیت اولیه: سرویسِ سفارش رویداد {id:e7, order_id:42, amount:200} رو می‌سازه.

اجرای مرحله‌به‌مرحله: پیام تو topic سفارش‌ها ثبت می‌شه؛ مصرف‌کنندهٔ گزارش می‌خونش و جمع رو عوض می‌کنه.

نتیجه و دلیل: نقش‌ها روشنن: تولیدکننده منشأِ پیام، topic جریانِ دسته‌بندی‌شده، مصرف‌کننده مجریِ پردازش. رویداد یه رخدادِ شناخته‌شده با هویت و زمانه. — چهار نقش، همین.

When the input is a file (a sequence of bytes), the first step is usually parsing it into records. In the streaming world a record is called an event — same thing, different hat: a small, self-contained, immutable entity describing something that happened at a point in time. A user click, a purchase, a sensor temperature, one line of the web-server log. An event usually carries a timestamp too (wall-clock time; how that differs from a monotonic clock was covered in Chapter 9).

رویداد رو می‌شه encode کرد (متن، JSON، باینری — فصل ۵)، ذخیره‌اش کرد (فایل، جدول، داکیومنت) و روی شبکه فرستاد. تو بچ، فایل یه‌بار نوشته می‌شه و شاید چند job بخوننش؛ تو استریم هم رویداد یه‌بار توسط تولیدکننده (producer / publisher / sender) ساخته می‌شه و شاید چند مصرف‌کننده (consumer / subscriber / recipient) پردازشش کنن. رویدادهای هم‌جنس تو تاپیک (topic / stream) جمع می‌شن — همون معادلِ نامِ فایل تو فایل‌سیستم.

You can encode an event (text, JSON, binary — Chapter 5), store it (file, table, document) and send it over the network. In batch a file is written once and maybe read by several jobs; in streaming an event is produced once by a producer (publisher / sender) and maybe handled by several consumers (subscribers / recipients). Same-kind events pile up in a topic (stream) — the filename equivalent, if you like.

نگاهِ اول اینجوریه: یه فایل یا یه پایگاه داده کافیه تا تولیدکننده و مصرف‌کننده رو وصل کنی. تولیدکننده بنویسه، مصرف‌کننده دوره‌ای poll کنه — دقیقاً همون کاری که بچِ روزانه می‌کنه. ولی هرچی delay کمتر می‌خوای، polling گرون‌تر می‌شه: هرچی بیشتر poll کنی، درصدِ بیشتری از درخواست‌ها دستِ خالی برمی‌گردن. بهتره مصرف‌کننده مطلع بشه که رویدادِ تازه اومده. پایگاه‌های دادهٔ رابطه‌ای تریگر دارن، ولی محدود و حاشیه‌ای‌ان؛ برای همین ابزارهای تخصصیِ اعلانِ رویداد ساخته شدن.

On the surface, a file or a database is enough to connect producer and consumer: the producer writes, the consumer polls every so often — exactly what a daily batch does. But the lower you want the latency, the more expensive polling gets: poll more often and more of your requests come back empty-handed. Better if the consumer just gets notified that a fresh event arrived. Relational databases do have triggers, but they're limited and marginal — hence the specialized event-notification tools.

۱.۲. پیام‌رسانیِ مستقیم در برابر بروکر + نمودار ۱1.2. Direct messaging vs brokers + Diagram 1

تو پیام‌رسانیِ مستقیم، فرستنده و گیرنده باید خودشون شرایطِ ارتباط رو با هم هماهنگ کنن. بروکر می‌شینه بینشون تا پذیرش، نگهداری و تحویلِ پیام رو طبق قرارداد مدیریت کنه.

مثال فنی: مستقیم یا بروکر؟

وضعیت اولیه: سرویسِ گزارش ۱۰ دقیقه خاموشه، ولی سفارش‌ها دارن میان.

اجرای مرحله‌به‌مرحله: ارسالِ مستقیم بدون ذخیرهٔ پایدار می‌تونه پیام‌ها رو گم کنه؛ brokerِ پایدار طبق سیاست retention نگهشون می‌داره تا گزارش برگرده.

نتیجه و دلیل: broker وابستگیِ زمانی رو کم می‌کنه؛ ظرفیتِ دیسک، دوام و مدتِ نگهداری هنوز باید کافی باشن. — حساب کن.

The simplest messenger is a direct channel — a Unix pipe, a TCP connection between producer and consumer. But those wire exactly one sender to one receiver, while a real messenger has to connect many producers to one topic, and one topic to many consumers.

  • پیام‌رسانیِ مستقیم (بدونِ واسطه): UDP multicast در بازارِ سهام (تأخیرِ کم، بازیابیِ بستهٔ گم‌شده در سطحِ اپ)، کتابخانه‌های بدونِ بروکر مثل ZeroMQ و nanomsg، عامل‌های متریک مثل StatsD روی UDP (شمارنده‌ها فقط وقتی درست‌ان که همهٔ پیام‌ها رسیده باشن)، و webhookها (تولیدکننده با HTTP/RPC به مصرف‌کننده push می‌کنه). فرضِ مشترکشون یکیه: طرفین دائم آنلاین‌ان؛ مصرف‌کنندهٔ آفلاین پیام رو از دست می‌ده، و اگه خودِ تولیدکننده crash کنه، بافرِ retry هم باهاش می‌میره.
  • بروکرِ پیام (message broker / queue): سروری شبیه پایگاه‌داده که برای استریمِ پیام بهینه شده. تولیدکننده به بروکر می‌نویسه، بروکر به مصرف‌کننده تحویل می‌ده. چون داده تو بروکر متمرکزه، آمدورفت و crash کلاینت‌ها راحت تحمل می‌شه و سؤالِ durability منتقل می‌شه به خودِ بروکر (بعضی فقط تو حافظه، بعضی با تنظیم روی دیسک). مصرف‌کننده‌ها ناهمگام‌ان: تولیدکننده فقط منتظرِ تأییدِ بافرشدن تو بروکر می‌مونه، نه پردازشِ نهایی.
  • Direct messaging (no middleman): UDP multicast in stock markets (low latency, app-level lost-packet recovery), brokerless libraries like ZeroMQ and nanomsg, metric agents like StatsD over UDP (your counters are only right if every message arrived), and webhooks (the producer pushes to the consumer over HTTP/RPC). Here's the catch they all share: both sides have to be permanently online. An offline consumer loses the message, and if the producer itself crashes, its retry buffer dies with it.
  • Message broker (queue): a server like a database, but optimized for message streams. The producer writes to the broker; the broker hands the message to the consumer. Because the data lives in the broker, client churn and crashes are easy to absorb — and the durability question moves into the broker (in-memory for some, on disk by configuration for others). Consumers are asynchronous: the producer only waits for the broker's buffering ack, not for the final processing.

بروکرها شبیه پایگاه داده‌ان (حتی بعضی‌شون تو پروتکلِ کامیتِ د two-phase با XA/JTA شرکت می‌کنن) ولی چند تفاوتِ عملی دارن: دیتا رو تا حذفِ صریح نگه می‌دارن درحالی‌که بعضی بروکرها پیامِ تحویل‌شده رو خودکار پاک می‌کنن (پس برای ذخیرهٔ بلندمدت مناسب نیستن)؛ فرضشون صف‌های کوتاهه (بافرِ زیاد → افتِ throughput)؛ به‌جای زبانِ کوئری، اشتراک روی الگوی تاپیک دارن؛ و به‌جای نتیجه بر اساسِ snapshotِ نقطه‌ای، اعلانِ تغییر می‌دن (پیامِ تازه رسید — چیزی که پایگاه داده نداره). این همون نگاهِ سنتیِ JMS/AMQPه (RabbitMQ، ActiveMQ و هم‌خانواده‌ها).

Brokers look like databases (some even join two-phase commit via XA/JTA) but they differ in practice: databases keep data until you explicitly delete it, while some brokers auto-delete delivered messages (so they don't fit long-term storage); they assume short queues (deep buffering kills throughput); instead of a query language they offer topic-pattern subscriptions; and instead of point-in-time snapshot results they emit change notifications (a fresh message arrived — something databases lack). This is the traditional JMS/AMQP view (RabbitMQ, ActiveMQ and kin).

نتیجه و دلیل: broker وابستگیِ زمانی رو کم می‌کنه؛ ظرفیتِ دیسک، دوام و مدتِ نگهداری هنوز باید کافی باشن. — حساب کن.

نمودار دو نیمِ جداست، هر کدوم تو یه قاب (region). از نیمهٔ بالا شروع کن: AMQP/JMS world. سمتِ چپ دو جعبهٔ Producer 1 و Producer 2 داری که هر دو با فلشِ send می‌زنن به جعبهٔ میانیِ JMS Broker — زیرنویسش می‌گه assigns each message و برچسبش ack + redeliver: کارِ بروکر دقیقاً همین تخصیصِ پیام‌هاست.

از سمتِ راستِ بروکر دو فلش بیرون می‌زنه: یکی با برچسبِ queue به جعبهٔ Queue: orders (زیرنویس: load balancing) و یکی با برچسبِ publish به جعبهٔ Topic: prices (زیرنویس: fan-out to all). حالا ستونِ آخر رو ببین: از Queue دو فلشِ 1 of 2 به Consumer 1 و Consumer 2 می‌رسه — یعنی هر پیام فقط به یکی از این دوتا می‌رسه و کار تقسیم می‌شه. ولی از Topic دو فلشِ to all به Subscriber 1 و Subscriber 2 می‌رسه — یعنی هر پیام به هر دو می‌رسه. همین تضادِ «یکی» در برابرِ «همه» قلبِ بخشِ بعدیه.

نیمهٔ پایینی، Log-based worldه. سمتِ چپ Producer A و Producer B با فلش‌های append به Partition 0 و Partition 1 می‌نویسن (برچسبِ هر دو پارتیشن: append-only با زیرنویسِ ordered offsets). از هر پارتیشن یه فلشِ read in order به مصرف‌کنندهٔ هم‌ردیفش تو Group A می‌رسه: Group A, C1 با زیرنویسِ owns partition 0 و Group A, C2 با owns partition 1 — یعنی هر پارتیشن دقیقاً یه مالک داره. و آخرش جعبهٔ پهنِ Group B, C1 با زیرنویسِ reads every partition و برچسبِ fan-out across groups: گروهِ دوم مستقل از گروهِ اول، همون پارتیشن‌ها رو دوباره می‌خونه. دو فلشِ بدونِ برچسبِ اون — یکی از بالای Partition 0 از کریدورِ بالا، یکی از پایینِ Partition 1 از کریدورِ پایین — هیچ فلشِ دیگه‌ای رو قطع نمی‌کنن.

درسِ این نمودار اینه: تو مدلِ سنتی، بروکر تصمیم می‌گیره هر پیام به چه کسی برسد؛ تو مدلِ لاگ‌محور، مصرف‌کننده با offset تصمیم می‌گیره تا کِی خونده — و همین تفاوت، بازپخش رو ممکن می‌کنه.

Read the top half (AMQP/JMS world) first: Producer 1 and Producer 2 both send into the middle JMS Broker (assigns each message, ack + redeliver). Two arrows leave the broker: a queue arrow to Queue: orders (load balancing) and a publish arrow to Topic: prices (fan-out to all).

From the Queue, two 1 of 2 arrows reach Consumer 1 and Consumer 2 — each message goes to one of them, splitting the work. From the Topic, two to all arrows reach Subscriber 1 and Subscriber 2 — each message goes to both. That “one vs all” contrast is the heart of the next section.

The bottom half (Log-based world) flips the responsibility: Producer A/B append to Partition 0/1 (append-only, ordered offsets); each partition is read in order by exactly one owner in Group A, while Group B independently re-reads every partition (fan-out across groups). Lesson: in the classic model the broker decides who gets each message; in the log model the consumer decides with its offset — and that difference makes replay possible.

۱.۳. متعادل‌سازیِ بار در برابر fan-out1.3. Load balancing vs fan-out

متعادل‌سازیِ بار یعنی یه کار بینِ چند مصرف‌کننده تقسیم بشه. Fan-out یعنی گروه‌های مستقل، هرکدوم همون رویداد رو برای هدفِ خودشون بگیرن.

مثال فنی: دو گروه، چند worker

وضعیت اولیه: topic سفارش‌ها ۴ پارتیشن داره؛ گروهِ ارسال دو worker داره و گروهِ تحلیل هم دو worker.

اجرای مرحله‌به‌مرحله: تو هر گروه پارتیشن‌ها تقسیم می‌شن؛ هر گروه مستقل، همهٔ جریان رو دنبال می‌کنه.

نتیجه و دلیل: load balancing تقسیمِ کارِ یه گروهه؛ fan-out رسوندنِ جریان به گروه‌های مستقل. — این دوتا رو قاطی نکن.

When several consumers read one topic, there are two patterns (Fig. 12-1) — and the difference between them is the whole ballgame:

  • متعادل‌سازیِ بار (load balancing): هر پیام به یکی از مصرف‌کننده‌ها می‌رسه؛ بروکر دلخواه تخصیص می‌ده. وقتی پردازشِ هر پیام گرونه و می‌خوای با اضافه‌کردنِ مصرف‌کننده موازیش کنی. (تو AMQP با چند کلاینت روی یه صف، تو JMS با shared subscription.)
  • پخش به همه (fan-out): هر پیام به همهٔ مصرف‌کننده‌ها می‌رسه؛ هر کدوم مستقل به همون پخش گوش می‌دن — معادلِ جریانیِ چند job بچ که یه فایلِ ورودی رو می‌خونن. (تو JMS با topic subscription، تو AMQP با exchange binding.)
  • Load balancing: each message reaches one of the consumers; the broker assigns as it pleases. Use it when processing a single message is expensive and you want to parallelize by adding consumers. (In AMQP with several clients on one queue; in JMS with a shared subscription.)
  • Fan-out: each message reaches all the consumers; each one listens to the same broadcast independently — the streaming twin of several batch jobs reading one input file. (In JMS with a topic subscription; in AMQP with an exchange binding.)

این دوتا با هم هم ترکیب می‌شن: مثلاً با consumer groupهای کافکا، هر پیام به یه مصرف‌کننده تو هر گروه می‌رسه (تعادلِ بار درونِ گروه) و به همهٔ گروه‌ها می‌رسه (fan-out میانِ گروه‌ها) — دقیقاً همون چیزی که تو نیمهٔ پایینیِ نمودار ۱ دیدی.

The two compose: with Kafka consumer groups, each message reaches one consumer within each group (load balancing inside the group) and all groups (fan-out across groups) — exactly what the bottom half of Diagram 1 shows.

۲.۱. سه راهِ مواجهه با مصرف‌کنندهٔ کند2.1. Three ways to handle a slow consumer

وقتی تولید سریع‌تر از مصرفه، سه راه داری: پیام رو بندازی، موقتاً نگهش داری، یا سرعتِ تولید رو میاری پایین. کدوم رو انتخاب کنی به ارزشِ پیام و ظرفیتِ بافر بستگی داره.

مثال فنی: حساب backlog

وضعیت اولیه: تولید 1000 msg/s داریم و مصرف 700 msg/s.

اجرای مرحله‌به‌مرحله: backlog هر ثانیه ۳۰۰ پیام و در ۱۰ دقیقه ۱۸۰ هزار پیام بزرگ می‌شه؛ بزرگ‌کردنِ بافر فقط زمان می‌خره.

نتیجه و دلیل: یا نرخِ تولید رو کم می‌کنی، یا ظرفیتِ مصرف رو زیاد، یا طبقِ نیازِ بخشی رو حذف می‌کنی؛ صفِ نامحدود راه‌حلِ پایدارِ اختلافِ نرخ نیست. — حساب کن.

If the producer sends faster than the consumer processes, you've got three options: dropping messages, buffering them in a queue, or backpressure / flow control — stall the producer until there's room. Unix pipes and TCP take the third path with a small fixed buffer: when it's full, the sender blocks until the receiver takes something. And if you do buffer, you have to work out what happens as the queue grows: it won't fit in memory? It spills to disk? What does disk do to performance? And when the disk fills, then what?

پرسشِ دوم: اگه نودی crash کنه یا موقتاً آفلاین بشه، پیامی گم می‌شه؟ مثل پایگاه داده، durability ترکیبِ نوشتن روی دیسک و replicationه — و این هزینه داره. اگه گاهی بتونی پیام گم کنی، روی همون سخت‌افزار throughput بیشتر و تأخیرِ کمتری می‌گیری. قابل‌قبول‌بودنِ گم‌شدن به کاربرد بستگی داره: برای readingهای دوره‌ایِ سنسور، یه نقطهٔ گم‌شده مهم نیست (مقدارِ تازه دقایقی بعد میاد — ولی حواست باشه اگه خیلی پیام بیفته، نادرستیِ متریک‌ها معلوم نمی‌شه)؛ ولی اگه داری رویداد می‌شماری، هر پیامِ گم‌شده یعنی شمارندهٔ غلط، پس تحویلِ مطمئن لازمه.

Second question: if a node crashes or goes briefly offline, is any message lost? Like a database, durability is disk writes plus replication — and it costs. If you can occasionally lose messages, the same hardware buys you higher throughput and lower latency. Whether loss is acceptable depends on the use case: for periodic sensor readings one lost dot hardly matters (a fresh value arrives minutes later — though beware that if many messages drop, metric inaccuracy goes unnoticed); but if you are counting events, every lost message means a wrong counter, so reliable delivery is required.

اگه مصرف‌کننده بعد از انجامِ کار تأیید نده، پیام ممکنه دوباره تحویل بشه. این تکرار می‌تونه با ترتیبِ پیام‌های دیگه قاطی بشه؛ پردازشِ موازی هم بی‌تاثیر نیست.

مثال فنی: Retry ترتیب تکمیل را عوض می‌کند

وضعیت اولیه: پیامِ اول set status=paid تو worker A گیر کرده؛ پیامِ دوم set status=shipped تو B زودتر تموم می‌شه.

اجرای مرحله‌به‌مرحله: تحویلِ دوبارهٔ پیامِ اول می‌تونه بعداً وضعیت رو برگردونه به paid، اگه نسخه یا ترتیبِ هر سفارش کنترل نشه.

نتیجه و دلیل: ترتیبِ تحویل با ترتیبِ پایانِ پردازش یکی نیست؛ برای همون موجودیت، کلیدگذاری، سریالی‌کردن یا کنترلِ نسخه لازمه. — این دام معروفه.

A consumer can crash at any moment: the broker delivered the message but it was never processed, or only half-processed. The fix is acknowledgment: the client must explicitly confirm that a message is done so the broker drops it from the queue. If the connection closes without an ack, or times out, the broker assumes the message was never processed and redelivers it to another consumer. (And here's the subtlety: the message may be fully processed with only the ack lost on the network — handling that needs an atomic-commit protocol, unless the operation is idempotent or exactly-once isn't required.)

نتیجه و دلیل: ترتیبِ تحویل با ترتیبِ پایانِ پردازش یکی نیست؛ برای همون موجودیت، کلیدگذاری، سریالی‌کردن یا کنترلِ نسخه لازمه. — این دام معروفه.

چهار ستون داری: Producer 1 (منبعِ مرتبِ رویداد)، Message Broker (صفِ متعادل‌شده)، Consumer 1 (پردازش و ack می‌کنه) و Consumer 2 (روی m3 می‌میره). اول Producer 1 با فلشِ درشتِ send m1, m2, m3, m4, m5 in order هر پنج پیام رو به‌ترتیب می‌فرسته — یادداشتِ زیرش تأکید می‌کنه ترتیبِ تولیدکننده m1 تا m5ه.

بعد تحویلِ متعادل‌شده شروع می‌شه: deliver m1 به مصرف‌کنندهٔ ۱ و برگشتِ ack m1؛ بعد deliver m2 به مصرف‌کنندهٔ ۲ و ack m2. بعد بروکر m3 رو به مصرف‌کنندهٔ ۲ می‌ده و هم‌زمان m4 رو به مصرف‌کنندهٔ ۱ — یادداشت می‌گه m4 وقتی تحویل شد که مصرف‌کنندهٔ ۲ هنوز مشغولِ m3 بود. این‌جا نقطهٔ شکسته: فلشِ خط‌چینِ crash while processing m3 — no ack؛ اتصال بسته/timeout شده و بروکر فرض می‌کنه m3 هیچ‌وقت پردازش نشد.

ولی مصرف‌کنندهٔ ۱ بی‌خبر ادامه می‌ده و ack m4 رو می‌فرسته — یادداشتش می‌گه تا این‌جا فقط m4 رو پردازش کرده، هم‌زمان با crash روی m3. حالا بروکر m3 رو redeliver می‌کنه — با تأکیدِ درشت و یادداشتِ «تلاشِ مجدد به مصرف‌کنندهٔ دیگر، در زمانی دیرتر» — و بعد deliver m5. آخرین فلشِ برگشتی ack m3, m5ه با یادداشتِ پایانی: ترتیبِ پردازشِ مصرف‌کنندهٔ ۱ شد m4, m3, m5 — یعنی m3 و m4 خلافِ ترتیبِ تولیدکننده اومدن.

سه کارتِ پایین رو هم بخون: پروتکلِ تأیید (حالتِ گم‌شدنِ ack و نیاز به idempotence یا کامیتِ اتمی)، دامِ به‌هم‌ریختن (حتی تضمینِ ترتیبِ JMS/AMQP هم وقتی تعادلِ بار با تحویلِ مجدد قاطی بشه نمی‌تونه جلوش رو بگیره؛ راه‌حل: صفِ جدا به‌ازای هر مصرف‌کننده یا پیام‌های مستقل)، و پیام‌های سمی با صفِ نامه‌های مرده. درس: ترکیبِ «تعادلِ بار + تحویلِ مجدد» ذاتاً ترتیب رو به‌هم می‌زنه — اگه پیام‌ها وابستگیِ علّی داشته باشن، این دام واقعیه.

Four columns: Producer 1 (the ordered event source), Message Broker (the balanced queue), Consumer 1 (processes and acks) and Consumer 2 (dies on m3). First the producer sends m1–m5 in order; delivery is load-balanced — m1/m2 go out and are acked — then the broker hands m3 to Consumer 2 while m4 goes to Consumer 1.

The breaking point is the dashed crash while processing m3 — no ack arrow. The connection closed, so the broker assumes m3 was never processed — while Consumer 1 innocently continues and acks m4. The broker then redelivers m3 to the other consumer (later in time), followed by m5; the final ack m3, m5 leaves Consumer 1's processing order as m4, m3, m5 — m3 and m4 against producer order.

The three cards generalize: the ack protocol (lost acks need idempotence or atomic commit), the reordering trap (even JMS/AMQP ordering guarantees can't survive load balancing mixed with redelivery — fix it with a separate queue per consumer or independent messages), and poison messages with dead-letter queues. Lesson: “load balancing + redelivery” inherently reorders — a real trap wherever messages have causal dependencies.

۲.۳. پیامِ سمی و صفِ نامه‌های مرده2.3. Poison messages and dead-letter queues

پیامِ سمی اون ورودی‌ایه که هر بار پردازش رو می‌شکنه. صفِ پیام‌های ناموفق کمک می‌کنه جدا کنیش تا بررسیش کنی؛ ولی صرفِ جدا کردن، خطا رو درست نمی‌کنه.

مثال فنی: پیامِ سمی

وضعیت اولیه: پیامِ e7 نسخهٔ schema نامعتبر داره و هر بار decoder رو می‌شکنه.

اجرای مرحله‌به‌مرحله: بعد از چند تلاشِ محدود، پیام با علتِ خطا و هویتِ اصلیش می‌ره تو DLQ؛ بعد از اصلاح هم یه بازپردازشِ کنترل‌شده انجام می‌شه.

نتیجه و دلیل: retryِ بی‌پایان همون خطا رو تکرار می‌کنه و ممکنه پارتیشن رو معطل کنه؛ DLQ هم بدونِ رسیدگی، محلِ گم‌شدنِ خاموشِ داده می‌شه. — این دام معروفه.

Redelivery doesn't just reorder; it can waste resources or wedge the flow forever. Here's the classic scenario: a producer that serializes badly — say it drops a required key from a JSON object. The keyless message crashes the consumer, which restarts; no ack arrives, the broker resends, the next consumer dies too — and the loop runs forever. With a hard ordering guarantee no progress is possible at all; with relaxed ordering you progress but burn resources on messages that never get acked.

راه‌حل، صفِ نامه‌های مرده (dead letter queue / DLQ)ه: به‌جای retry تا ابد، پیام به صفِ دیگه‌ای منتقل می‌شه تا مصرف‌کننده‌ها آزاد بشن. روی DLQ معمولاً مانیتورینگه — هر پیامِ توش یه خطاست و اپراتور تصمیم می‌گیره: برای همیشه بندازش، دستی اصلاح و بازتولید کنه، یا کدِ مصرف‌کننده رو درست کنه. DLQ تو بیشترِ سیستم‌های صف رایجه و سیستم‌های لاگ‌محور و پردازشِ استریم هم حالا ازش پشتیبانی می‌کنن.

The fix is a dead letter queue (DLQ): instead of retrying forever, the message moves to a separate queue so the consumers stay free. You normally monitor that DLQ — every message in it is an error, and the operator decides: drop it forever, fix it by hand and replay it, or fix the consumer code. DLQs are common in most queueing systems, and log-based and stream-processing systems support them now too.

۳.۱. لاگ، پارتیشن و offset3.1. Logs, partitions and offsets

بروکرِ لاگ‌محور پیام‌ها رو تو پارتیشن‌های مرتب نگه می‌داره. Offset جای پیام تو همون پارتیشنه و مشخص می‌کنه خواندن از کِی ادامه پیدا کنه؛ شمارهٔ سراسریِ همهٔ پیام‌ها نیست. شرح رسمیِ لاگ و تضمین‌های پردازش در Kafka.

مثال فنی: Offset جایگاهِ یک پارتیشن است

وضعیت اولیه: پیام e7 تو پارتیشن ۲ با offset=۱۰۱ ثبت شده.

اجرای مرحله‌به‌مرحله: گروه A تا offset ۱۰۰ و گروه B تا ۹۰ پیش رفته؛ پیشرفتشون مستقل از همه.

نتیجه و دلیل: offset شناسهٔ سراسریِ کلِ topic نیست؛ برای موقعیت، نامِ topic و partition هم لازمه. — یادت باشه.

Sending a packet over the network, or a request to a service, is a transient act that leaves no permanent trace — and the lightweight AMQP/JMS brokers inherited that transient mindset: even when they write a message to disk, they delete it soon after delivery. Databases and filesystems are the opposite: whatever is written is, as a rule, recorded forever until someone explicitly deletes it. That mindset difference wrecks “derived data”: in batch you can repeat the processing as often as you like without harming the input, but in traditional messaging, receiving a message with an ack is destructive (the message leaves the broker) — so you can’t rerun the same consumer and expect the same result. And a fresh consumer only gets messages after it registered; everything earlier is gone — unlike files and databases, where a late-arriving client still reads the past.

چرا ترکیبی نداشته باشیم: ذخیرهٔ بادوامِ پایگاه داده‌ها + اعلانِ کم‌تأخیرِ پیام‌رسان‌ها؟ این همون ایدهٔ بروکرِ لاگ‌محوره. لاگ فقط دنباله‌ای append-only از رکوردها روی دیسکه (همون که تو موتورهای ذخیره‌سازیِ فصل ۴، replication فصل ۶ و اجماعِ فصل ۱۰ دیدیم). تولیدکننده با append پیام رو به انتهای لاگ می‌فرسته، مصرف‌کننده با خواندنِ ترتیبی پیام رو می‌گیره، و وقتی به انتهای لاگ می‌رسه، منتظرِ اعلانِ پیامِ تازه می‌مونه — دقیقاً مثل tail -f تو Unix.

Why not have both: database-like durable storage plus messenger-like low-latency notification? That's the log-based broker idea. A log is just an append-only sequence of records on disk (the same one we saw in Chapter 4 storage engines, Chapter 6 replication and Chapter 10 consensus). The producer sends by appending to the log tail; the consumer receives by reading sequentially; and on reaching the tail it waits for fresh-message notification — exactly like tail -f in Unix.

برای throughput بیشتر از یه دیسک، لاگ shard می‌شه (فصل ۷): هر shard یه لاگِ مستقل روی ماشینِ خودشه و تاپیک گروهی از shardهاست که پیام‌های هم‌جنس حمل می‌کنن (شکل ۱۲-۳ کتاب — نیمهٔ پایینیِ نمودار ۱). تو هر shard که کافکا بهش پارتیشن می‌گه، بروکر به هر پیام شمارهٔ ترتیبیِ صعودی می‌ده: offset. چون پارتیشن append-onlyه، پیام‌های درونِ یه پارتیشن کاملاً مرتب‌ان؛ ولی هیچ تضمینِ ترتیبی میانِ پارتیشن‌ها نیست. Apache Kafka و Amazon Kinesis همین‌طور کار می‌کنن (و با sharding روی چند ماشین و replication به میلیون‌ها پیام در ثانیه و تحملِ خرابی می‌رسن).

For throughput beyond one disk, the log is sharded (Chapter 7): each shard is an independent log on its own machine, and a topic is a group of shards carrying same-kind messages (Fig. 12-3 — the bottom half of Diagram 1). Within each shard, which Kafka calls a partition, the broker assigns every message an ascending sequence number: the offset. Because a partition is append-only, messages inside one partition are fully ordered; but there is no ordering guarantee across partitions. Apache Kafka and Amazon Kinesis work this way (reaching millions of messages per second with fault tolerance through multi-machine sharding and replication).

۳.۲. لاگ در برابر پیام‌رسانیِ سنتی3.2. Logs vs traditional messaging

  • fan-outِ بدیهی: چند مصرف‌کنندهٔ مستقل لاگ رو می‌خونن بی‌آن‌که روی هم اثر بذارن؛ خواندن، پیام رو از لاگ پاک نمی‌کنه. برای تعادلِ بار، بروکر به‌جای تخصیصِ تک‌تکِ پیام‌ها، shardهای کامل رو به نودهای گروهِ مصرف‌کننده می‌ده و هر کلاینت پیام‌های shardِ خودش رو تک‌نخی و ترتیبی می‌خونه.
  • سقفِ موازی‌سازی = تعدادِ shardها: چون پیام‌های یه shard به یه نود می‌رسن، نودهای همکارِ یه تاپیک حداکثر به‌اندازهٔ shardهای اون تاپیک‌ان. (می‌شه کارِ یه shard رو هم تقسیم کرد ولی مدیریتِ offset رو پیچیده می‌کنه؛ تک‌نخ به‌ازای shard ترجیح داره و موازی‌سازی با shardِ بیشتر.)
  • انسدادِ سرِ صف (head-of-line blocking): اگه یه پیام کند پردازش بشه، پیام‌های بعدیِ همون shard پشتش می‌مونن.
  • Trivial fan-out: several independent consumers read the log without getting in each other's way; reading never deletes from the log. For load balancing, instead of assigning individual messages the broker hands whole shards to consumer-group nodes, and each client reads its own shard single-threaded and in order.
  • Parallelism ceiling = shard count: since one shard's messages reach one node, the cooperating nodes of a topic are at most its shard count. (One shard's work can be split, but that complicates offset management; one thread per shard is preferred, and you parallelize with more shards.)
  • Head-of-line blocking: if one message is slow to process, the later messages of the same shard wait behind it.

تو صفِ کاریِ معمول، محورِ کار «تحویل و تأییدِ هر پیام»ه؛ تو لاگ، محور «نگهداریِ تاریخچه و موقعیتِ خواندنِ هر گروه». جزئیاتِ دقیق به محصول و تنظیمات بستگی داره.

مثال فنی: مصرف پیام، حذف فوری نیست

وضعیت اولیه: گروهِ گزارش پیامِ ۱۰۱ رو خونده، ولی گروهِ حسابرسی هنوز روی ۸۰ئه.

اجرای مرحله‌به‌مرحله: تو brokerِ لاگ‌محور، مصرفِ گروهِ اول پیام رو از لاگ برای گروهِ دوم حذف نمی‌کنه؛ retention سیاستِ مستقلِ خودش رو داره.

نتیجه و دلیل: گروه‌ها می‌تونن با سرعتِ جدا پیش برن، تا وقتی دادهٔ لازم از retention خارج نشده باشه. — حساب کن.

So, the rule of thumb: if messages are expensive and you want to parallelize them one by one while order hardly matters, a lightweight JMS/AMQP broker is the better fit; if throughput is high, each message processes fast and order matters, the log-based approach shines — though the boundary between the two architectures is blurring (Kafka now supports lightweight JMS/AMQP-style consumer groups too). And since order survives only within a shard, every event that must stay ordered has to go to the same shard — e.g. by partitioning on the user ID key.

مصرفِ ترتیبیِ shard یه هدیه هم داره: لازم نیست بروکر برای تک‌تکِ پیام‌ها ack نگه داره؛ کافیه دوره‌ای offset مصرف‌کننده رو ثبت کنه. همهٔ پیام‌های با offsetِ کمتر پردازش شدن، بزرگ‌ترها هنوز دیده نشدن. همین دفترداریِ کمتر + batching و pipelining، throughput سیستم‌های لاگ‌محور رو بالا می‌بره. بهایش: اگه مصرف‌کننده بمیره، از آخرین offsetِ ثبت‌شده ادامه می‌ده نه آخرین offsetِ دیده‌شده — پس بعضی پیام‌ها رو دوباره می‌بینه. این offset دقیقاً همون شمارهٔ ترتیبیِ لاگ تو replication تک‌رهبریِ پایگاه داده‌ست (فصل ۶): بروکر مثل پایگاه دادهٔ رهبر، مصرف‌کننده مثل دنباله‌رو.

Sequential shard consumption brings a gift: the broker needn't track per-message acks; periodically recording the consumer offset is enough. Every message below the offset is processed; the larger ones are unseen. That lighter bookkeeping plus batching and pipelining is what lifts log-based throughput. The price: if the consumer dies it resumes from the last recorded offset, not the last seen one — so it sees some messages twice. And that offset is exactly the log sequence number of single-leader database replication (Chapter 6): the broker is like the leader database, the consumer like a follower.

حسابِ سرانگشتیِ بافرِ دیسکیDisk-buffer arithmetic

اگه فقط append کنی، بالاخره دیسک پر می‌شه: لاگ به segment تقسیم می‌شه و segmentهای قدیمی پاک یا آرشیو می‌شن. یعنی لاگ عملاً یه بافرِ حلقه‌ایِ (circular / ring buffer) محدود ولی بزرگه که پیام‌های قدیمی‌تر از گنجایشش رو می‌ندازه. حسابِ کتاب: دیسکِ ۲۰ ترابایتی با توانِ نوشتنِ ترتیبیِ 250MB/s حدود ۲۲ ساعت طول می‌کشه تا پر بشه — پس لاگِ دیسکی حتی تو بدترین حالت دست‌کم ۲۲ ساعت پیام بافر می‌کنه، و در عمل (که پهنای باند کامل مصرف نمی‌شه) چند روز تا چند هفته. خیلی از بروکرها حالا پیام‌ها رو تو object storage هم نگه می‌دارن (tiered storage) که هم ارزان‌تره و هم یکپارچگی با بچ و انبارِ داده رو ساده می‌کنه.

If you only append, the disk eventually fills: the log splits into segments and old segments are deleted or archived. So the log is effectively a bounded but large circular / ring buffer that drops messages older than its capacity. The math: a 20 TB disk with 250 MB/s sequential write takes about 22 hours to fill — so even in the worst case a disk log buffers at least 22 hours of messages, and in practice (bandwidth never fully consumed) days to weeks. Many brokers now also keep messages in object storage (tiered storage), which is cheaper and simplifies integration with batch and the warehouse.

۳.۳. بازپخش و بافرِ دیسکی3.3. Replay and disk buffering

بازپخش یعنی دوباره خوندنِ پیام‌های نگه‌داشته‌شده از یه نقطهٔ قبلی. لاگ بافرِ نامحدود نیست؛ اگه مصرف‌کننده بیش از دورهٔ نگهداری عقب بمونه، تاریخچهٔ لازم ممکنه حذف بشه.

مثال فنی: Replay بعد از اصلاح فرمول

وضعیت اولیه: خطای محاسبه از offset ۱۰۰۰ تا ۲۰۰۰ رخ داده و لاگ هنوز موجوده.

اجرای مرحله‌به‌مرحله: پردازشگرِ اصلاح‌شده از ۱۰۰۰ تو خروجیِ تازه بازپخش می‌کنه؛ اثرِ قبلی باید جایگزین بشه یا با هویتِ پیام از شمارشِ دوباره مصون بمونه.

نتیجه و دلیل: عقب‌بردنِ offset به‌تنهایی جدولِ قدیمی رو پاک یا اصلاح نمی‌کنه؛ مقصد هم بخشی از برنامهٔ replayه. — یادت باشه.

In the three-way classification (drop / buffer / backpressure), the log-based approach is buffering with a large fixed buffer (bounded by disk space). If a consumer lags so far that its offset points at a deleted segment, those messages are lost — i.e. the broker effectively drops messages older than the buffer. You can watch a consumer's lag behind the log tip and alert when it grows; since the buffer is big, a human operator gets time to fix the slow consumer and catch up before anything is dropped.

  • فقط همون مصرف‌کننده آسیب می‌بینه — سرویسِ بقیه مختل نمی‌شه. مزیتِ عملیاتیِ بزرگیه: می‌تونی لاگِ production رو برای توسعه و دیباگِ آزمایشی مصرف کنی بی‌آن‌که نگرانِ سرویسِ production باشی. وقتی مصرف‌کننده خاموش یا crash می‌کنه، مصرفِ منابعش قطع می‌شه — تنها چیزی که می‌مونه offsetِ اونه. (برخلافِ بروکرهای سنتی که باید صف‌های مصرف‌کنندهٔ خاموش رو پاک کنی تا حافظهٔ مصرف‌کننده‌های فعال رو نخورن.)
  • بازپخش (replay): تو بروکرِ سنتی مصرف مخربه، ولی تو لاگ‌محور مصرف مثل خوندنِ فایله — یه عملیاتِ read-only که لاگ رو عوض نمی‌کنه. تنها اثرِ جانبی، جلو رفتنِ offsetه که کارِ خودِ مصرف‌کننده‌ست؛ می‌تونی یه کپی از مصرف‌کننده رو با offsetِ دیروز بالا بیاری، خروجی رو جای دیگه‌ای بنویسی، و روزِ گذشته رو هر چند بار که خواستی با کدِ متفاوت بازپردازش کنی — دقیقاً مثل بچ که دادهٔ مشتق‌شده رو با تبدیلِ تکرارپذیر از ورودی جدا می‌کنه.
  • Only that consumer suffers — everyone else's service is undisturbed. That's a big operational win: you can consume the production log for experimental development and debugging without worrying about the live service. When the consumer is off or crashed, its resource consumption stops — all that remains is its offset. (Unlike traditional brokers, where you have to purge a dormant consumer's queues so they don't eat the active consumers' memory.)
  • Replay: in a traditional broker consumption is destructive, but in a log-based one it is like reading a file — a read-only operation that doesn't change the log. The only side effect is advancing the offset, and that's the consumer's own business; so you can raise a copy of the consumer at yesterday's offset, write the output somewhere else, and reprocess the past with different code as many times as you like — exactly like batch separating derived data from input with a repeatable transform.

Brokers and databases were always seen as two separate categories, but log-based brokers brought database ideas into messaging — and the reverse works too: streaming ideas can be brought into databases. You can even make the event stream the system of record: instead of a data model mutated by updates and deletes, model every state change as an immutable event in an append-only log and derive readable materialized views from it — the event sourcing of Chapter 3. A log-based broker (one that never deletes old events) is well-built for this. But you needn't go as far as event sourcing; even with a mutable model an event stream helps the database — because every database write is itself an event that can be captured, stored and processed. The replication log (Chapter 6) is the leader's write-event stream, and the state-machine replication principle (Chapter 10) is the same: if each event is a write and each replica processes the same events in the same order, all reach the same final state.

حالا interleaving بدشانس: اپلیکیشن اول write X = A رو به پایگاه داده می‌فرسته (یادداشت: write مشتریِ ۱ اول اعمال شد) و بعد write X = B (یادداشت: مقدارِ نهاییِ پایگاه داده B است). ولی تو ایندکسِ جستجو ترتیب برعکس می‌رسه: اول index X = B (یادداشت: write مشتریِ ۲ اول رسید) و بعد index X = A (یادداشت: مقدارِ نهاییِ ایندکس A است).

دو فلشِ خط‌چینِ پایانی حکم رو می‌گن: فلشِ DB = B, index = A از پایگاه داده به ایندکس با یادداشتِ «هیچ خطایی رخ نداد — واگراییِ بی‌صدا؛ تشخیصِ هم‌زمانی نیست»؛ و فلشِ if one write fails با یادداشتِ «اون یکی باز هم commit می‌شه — هردو-یا-هیچ‌کدام مسئلهٔ کامیتِ اتمی (2PC)ه، نه هم‌زمانی». سه کارت هم چارچوب رو می‌دن: چیدمان (دو رهبرِ مستقل یعنی هیچ ترتیبِ writeِ واحدی نیست)، خودِ مسابقه (A بعد B تو پایگاه داده در برابرِ B بعد A تو ایندکس، بدونِ خطا)، و چراییِ ماندگاربودنِ خرابی (رونویسیِ بی‌صدا؛ بردارِ نسخه متوجه می‌شد؛ و راهِ CDC فقط تو یه خط ارجاع شده — نمودارِ بعدی). درس: بدونِ رهبرِ واحد، ترتیبِ writeها تو دو سیستم می‌تونه برای همیشه واگرا بمونه.

Five columns: Client 1 (wants X = A), Client 2 (wants X = B), the Application (writes to both systems), the Database (with its own leader) and the Search Index (with its own leader too). The first two arrows are simultaneous: set X = A from Client 1 and set X = B from Client 2 into the application.

Then the unlucky interleaving: the application sends write X = A to the database first (Client 1's write applied first) and then write X = B (the database's final value is B). But the writes reach the search index in reverse: index X = B first (Client 2's write arrived first), then index X = A (the index's final value is A).

The two dashed arrows at the bottom give the verdict: DB = B, index = A — “no error occurred: silent divergence, undetectable concurrency”; and if one write fails — “the other still commits: both-or-neither is the atomic-commit (2PC) problem, not concurrency.” The three cards frame it: the setup (two independent leaders means no single write order), the race itself (A-then-B in the database vs B-then-A in the index, with no error), and why the damage persists (silent overwrite; a version vector would have noticed; the CDC way out is referenced in one line — the next diagram). Lesson: without a single leader, write orders in two systems can diverge forever.

مشکلِ دومِ نوشتنِ دوگانه تحملِ خرابیه، نه هم‌زمانی: یکی از writeها موفق و اون یکی ناموفق می‌شه و دو سیستم ناسازگار می‌مونن. اینکه «هر دو موفق بشن یا هر دو شکست بخورن» همون مسئلهٔ کامیتِ اتمیه که حلش گرونه (2PC فصل ۸). اگه فقط یه پایگاه دادهٔ تک‌رهبری داشتی، رهبر ترتیبِ writeها رو تعیین می‌کرد و replication ماشینِ وضعیت کار می‌کرد؛ ولی تو شکلِ بالا رهبرِ واحدی نیست — پایگاه داده رهبرِ خودش رو داره و ایندکس رهبرِ خودش رو (وضعیتی شبیه replication چندرهبریِ فصل ۶). ای‌کاش واقعاً فقط یه رهبر بود — مثلاً پایگاه داده — و ایندکس دنباله‌رویِ پایگاه داده می‌شد. آیا در عمل می‌شه؟

The second dual-write problem is fault tolerance, not concurrency: one write succeeds and the other fails, leaving the two systems inconsistent. Getting “both succeed or both fail” is the atomic-commit problem, and it's expensive to solve (Chapter 8's 2PC). With a single-leader database the leader would order the writes and state-machine replication would work; but in the figure above there is no single leader — the database has its own leader and the index its own (a situation like Chapter 6's multi-leader replication). How nice it would be if there really were one leader — the database, say — with the index following it. Is that practical?

۴.۲. CDC: یک رهبر، چند دنباله‌رو + نمودار ۴4.2. CDC: one leader, many followers + Diagram 4

CDC تغییرهای پایگاه داده رو به یه جریانِ قابل‌مصرف تبدیل می‌کنه. مصرف‌کننده می‌تونه نمایِ دیگه‌ای رو به‌روز کنه؛ مرزِ تصویرِ اولیه، ترتیب، حذف‌ها و بازتلاش باید مدیریت بشن.

مثال فنی: CDC با مرز سازگار

وضعیت اولیه: snapshotِ جدول تا موقعیتِ لاگ ۵۰۰ گرفته شده.

اجرای مرحله‌به‌مرحله: snapshot میاد تو جست‌وجو و بعد تغییرهای پس از ۵۰۰ به‌ترتیبِ مناسب اعمال می‌شن؛ lag و gap کنترل می‌شه.

نتیجه و دلیل: اگه مرز اشتباه باشه، تغییرِ حینِ snapshot جا می‌افته یا نادرست تکرار می‌شه؛ صرفِ خوندنِ دوره‌ایِ کلِ جدول، CDC دقیق نیست. — حساب کن.

The trouble with most databases' replication logs was that they were treated as an internal implementation detail, not public API — for decades there was no documented way to tap the change log. But recently change data capture (CDC) has been taken seriously: observing every change written to the database and pulling it out in a form replicable to other systems — and even nicer when those changes are available as a stream right away. Just capture the changes and continuously apply them to the search index; if the change log is applied in the same order, the index data matches the database. The index and every other derived system are just consumers of the change stream — and Diagram 3's race is solved: although requests A and B reach the database concurrently, the database itself orders their execution and writes them to the replication log in that order; the index picks up and applies the same order. If another system (say, the warehouse) is needed later, just add another consumer to the same stream.

مثال فنی برای خواندنِ نمودار: CDC با مرز سازگار

وضعیت اولیه: snapshotِ جدول تا موقعیتِ لاگ ۵۰۰ گرفته شده.

اجرای مرحله‌به‌مرحله: snapshot میاد تو جست‌وجو و بعد تغییرهای پس از ۵۰۰ به‌ترتیبِ مناسب اعمال می‌شن؛ lag و gap کنترل می‌شه.

نتیجه و دلیل: اگه مرز اشتباه باشه، تغییرِ حینِ snapshot جا می‌افته یا نادرست تکرار می‌شه؛ صرفِ خوندنِ دوره‌ایِ کلِ جدول، CDC دقیق نیست. — حساب کن.

این یه dataflow پنج‌ستونه‌ست: System of Record، Replication Log، CDC Capture، Change Stream و Derived Data. مسیرِ اصلی ردیفِ پایینه: OLTP Database (برچسب: decides write order) با فلشِ commit in one order به Replication Log (برچسب: in commit order)؛ بعد فلشِ read the log به CDC Connector (زیرنویس: Debezium-style)؛ بعد فلشِ change events (با طبقه‌بندیِ keyed by primary key) به Log-Based Broker (برچسب: log-compacted)؛ و از اون‌جا چهار فلشِ کوتاهِ index، cache، load و feed به ستونِ آخر: Search Index، Cache، Data Warehouse و Stream Processor (هر چهارتا با زیرنویسِ derived data system).

دو مسیرِ کمکی هم هست که معنایشون تو کارت‌هاست: از OLTP Database فلشِ خط‌چینِ consistent copy به جعبهٔ Initial Snapshot می‌ره و از اون‌جا فلشِ then apply changes from offset به ایندکس — یعنی اول snapshot تو offsetِ معلوم، بعد اعمالِ تغییرات از همون offset. و فلشِ same transaction از پایگاه داده به جعبهٔ Outbox Table (برچسب: written in one txn) و از اون‌جا reads outbox schema به کانکتور — یعنی CDC به‌جای اسکیمای داخلی، اسکیمای پایدارِ outbox رو می‌خونه. درس: مصرف‌کننده‌های مشتق‌شده فقط دنباله‌روهای رهبرِ واحدن، و ترتیبِ واحدِ اون واگرایی رو ناممکن می‌کنه.

A five-column dataflow: System of Record, Replication Log, CDC Capture, Change Stream and Derived Data. The main path is the bottom row: the OLTP Database (decides write order) via commit in one order to the Replication Log (in commit order); then read the log to the CDC Connector (Debezium-style); then change events (keyed by primary key) to the Log-Based Broker (log-compacted); and from there four short index / cache / load / feed arrows to the last column: Search Index, Cache, Data Warehouse and Stream Processor (all four derived data systems).

Two helper paths carry the meaning in the cards: from the OLTP Database a dashed consistent copy arrow goes to Initial Snapshot, then then apply changes from offset to the index — first a snapshot at a known offset, then changes from that offset. And a same transaction arrow from the database to the Outbox Table (written in one txn), then reads outbox schema to the connector — so CDC reads a stable outbox schema instead of the internal one. Lesson: derived consumers are just followers of a single leader, and its single order makes divergence impossible.

عملاً CDC پایگاه دادهٔ مبدأ رو رهبر می‌کنه و بقیه رو دنباله‌رو، و بروکرِ لاگ‌محور برای حملِ رویدادهای تغییر خوش‌ساخته چون ترتیب رو حفظ می‌کنه. لاگِ replication منطقی (row-based) با همهٔ چالش‌هاش (تغییرِ اسکیما، مدل‌کردنِ update) همین کار رو می‌کنه؛ پروژهٔ متن‌بازِ Debezium (با کانکتورِ MySQL و PostgreSQL و Oracle و …) و فریم‌ورکِ Kafka Connect همین مسیر رو هموار کردن؛ Maxwell برای MySQL با parse کردنِ binlog و GoldenGate برای Oracle مشابه‌ان. مثل بروکرها، CDC معمولاً ناهمگامه: پایگاه دادهٔ مبنا منتظرِ اعمالِ تغییر روی مصرف‌کننده نمی‌مونه — خوبیش اینه که مصرف‌کنندهٔ کند سیستمِ مبنا رو اذیت نمی‌کنه، و بدیش اینه که همهٔ مسائلِ lagِ replication (فصل ۶) این‌جا هم هست.

In effect CDC makes the source database the leader and everything else a follower, and the log-based broker is well-built for carrying change events because it preserves order. The logical (row-based) replication log does this job with all its challenges (schema change, modelling updates); the open-source Debezium project (with MySQL, PostgreSQL, Oracle connectors and more) and the Kafka Connect framework paved the way; Maxwell for MySQL by parsing the binlog and GoldenGate for Oracle are similar. Like brokers, CDC is usually asynchronous: the record database doesn't wait for the change to be applied downstream — the upside is a slow consumer never bothers the record system; the downside is that all the Chapter-6 replication-lag issues apply here too.

۴.۳. snapshot، compaction و outbox4.3. Snapshots, compaction and outbox

Snapshot تصویرِ یه نقطه‌ست؛ compaction می‌تونه آخرین مقدارِ هر کلید رو تو لاگ نگه داره؛ outbox هم تغییرِ داده و ثبتِ پیامِ قابل‌ارسال رو تو یه تراکنش کنار هم می‌ذاره.

مثال فنی: Outbox کنار سفارش

وضعیت اولیه: تو همون تراکنش، سفارش ۴۲ و ردیفِ outbox با event_id=e7 نوشته می‌شن.

اجرای مرحله‌به‌مرحله: relay پیام رو منتشر می‌کنه و ممکنه بعد از crash دوباره بفرستش؛ مصرف‌کننده e7 رو تکراری تشخیص می‌ده.

نتیجه و دلیل: outbox شکافِ «ثبتِ سفارش» و «ثبتِ قصدِ انتشار» رو می‌بنده؛ ولی تحویلِ فیزیکیِ دقیقاً یک‌باره رو خودکار تضمین نمی‌کنه. — حساب کن.

  • snapshot اولیه: اگه لاگِ همهٔ تغییراتِ تاریخ رو داشتی، با بازپخشش کلِ وضعیت رو می‌ساختی؛ ولی معمولاً نگه‌داشتنِ همهٔ تاریخ پرهزینه‌ست و لاگ باید کوتاه بشه. برای آوردنِ سیستمِ مشتق‌شدهٔ تازه (مثلاً ایندکسِ متنیِ نو) به snapshotِ سازگار نیاز داری (فصل ۶) — و اون snapshot باید متناظر با position/offset معلومی تو لاگِ تغییر باشه تا بدونی از کِی به بعد تغییرات رو اعمال کنی. بعضی ابزارهای CDC این رو توکار دارن، بعضی دستی‌اش گذاشتن؛ Debezium با الگوریتمِ watermarkingِ DBLog نتفلیکس snapshot تدریجی می‌ده.
  • فشرده‌سازیِ لاگ (log compaction): همون ایدهٔ موتورهای ذخیره‌سازیِ فصل ۴ — موتور دوره‌ای رکوردهای هم‌کلید رو پیدا می‌کنه، تکراری‌ها رو می‌ندازه و فقط تازه‌ترین updateِ هر کلید رو نگه می‌داره (شکل ۱۲-۶ کتاب با ویدیوهای گربه!). update با مقدارِ null ویژه (tombstone) یعنی حذفِ کلید. فضای دیسکِ لاگِ فشرده فقط به محتوای فعلی بستگی داره نه تعدادِ writeهای تاریخ. همین ایده تو CDC جواب می‌ده: اگه هر تغییر کلیدِ اصلی داشته باشه و هر update جایگزینِ قبلی بشه، نگه‌داشتنِ فقط تازه‌ترین writeِ هر کلید کافیه — و مصرف‌کنندهٔ تازه می‌تونه از offset صفر کلِ لاگ رو اسکن کنه و کپیِ کاملِ پایگاه داده رو بگیره بی‌آن‌که snapshot تازه‌ای از مبدأ لازم باشه. کافکا این ویژگی رو داره و به بروکر اجازه می‌ده نقشِ ذخیرهٔ بادوام رو هم بازی کنه، نه فقط پیام‌رسانیِ گذرا.
  • الگوی outbox: با CDC اسکیمای داخلیِ پایگاه داده عملاً API عمومی می‌شه (حذفِ یه ستون، مصرف‌کننده‌های پایین‌دست رو می‌شکنه — و چون CDC استریمه، مصرف‌کننده‌اش ممکنه سرویسِ production باشه و قطعیِ روبه‌مشتری بده؛ data contractها برای همین‌ان). راهِ جداکردنِ اسکیمای داخلی از خارجی، جدولِ outbox با اسکیمای خودشه که CDC اون رو می‌خونه نه مدلِ دامنه رو. این هم dual-writeه — ولی هر دو write تو یک سیستم (پایگاه داده) و تو یک تراکنش‌ان، ولی چالش‌های بخشِ قبل رو نداره. بهایش: نگه‌داشتنِ تبدیلِ میانِ دو اسکیما و حجمِ write بیشتر تو پایگاه داده.
  • CDC در برابر event sourcing: هر دو همهٔ تغییرات رو لاگ می‌کنن ولی تو سطحِ abstraction متفاوت: تو CDC اپ با پایگاه دادهٔ جهش‌پذیر کار می‌کنه و لاگ از سطحِ پایین (parse لاگِ replication) استخراج می‌شه — پس ترتیبِ استخراج دقیقاً همون ترتیبِ واقعیِ writeهاست و مسابقهٔ نمودار ۳ پیش نمیاد. تو event sourcing منطقِ اپ صریح روی رویدادهای immutableِ سطحِ اپلیکیشن ساخته شده؛ رویدادها نیتِ کنشِ کاربر رو می‌گن نه مکانیکِ update رو، پس رویدادِ بعدی معمولاً قبلی رو override نمی‌کنه و برای بازسازیِ وضعیتِ نهایی کلِ تاریخ لازمه (compaction مثل CDC ممکن نیست). انتخاب بستگی به وضعیت داره: event sourcing تغییرِ بزرگیه (فصل ۳) ولی CDC رو با کمترین تغییر به پایگاه دادهٔ موجود اضافه می‌کنی — حتی شاید اپِ نویسنده اصلاً نفهمه CDC در جریانه.
  • Initial snapshot: if you had the log of all historical changes, replaying it would build the whole state; but keeping all of history is usually too expensive and the log must be shortened. So bringing up a fresh derived system (say, a new text index) needs a consistent snapshot (Chapter 6) — and that snapshot must correspond to a known position/offset in the change log so you know where onward to apply changes from. Some CDC tools have this built in, some left it manual; Debezium offers gradual snapshots via Netflix's DBLog watermarking algorithm.
  • Log compaction: the same idea as Chapter 4 storage engines — the engine periodically finds same-key records, drops duplicates and keeps only each key's latest update (Fig. 12-6 with the cat videos!). An update with a special null value (tombstone) means key deletion. A compacted log's disk footprint depends only on current content, not on the number of historical writes. The same idea works in CDC: if every change has a primary key and each update supersedes the previous one, keeping only each key's latest write suffices — and a fresh consumer can scan the whole log from offset zero and take a full database copy without needing a fresh snapshot from the source. Kafka has this feature, letting the broker also play durable storage, not just transient messaging.
  • Outbox pattern: with CDC the database's internal schema effectively becomes public API (dropping a column breaks downstream consumers — and since CDC is a stream, its consumer may be a production service, causing customer-facing outages; data contracts exist for this). The way to separate internal from external schema is an outbox table with its own schema that CDC reads instead of the domain model. This is dual-write too — but both writes are in one system (the database) and in one transaction, so it lacks the previous section's challenges. Its price: maintaining the conversion between the two schemas and higher write volume in the database.
  • CDC vs event sourcing: both log all changes but at different abstraction levels: in CDC the app works with a mutable database and the log is extracted from a low level (parsing the replication log) — so the extracted order is exactly the real write order and Diagram 3's race never arises. In event sourcing the app logic is explicitly built on immutable application-level events; events state the user's intent, not update mechanics, so a later event usually doesn't override the earlier one and rebuilding the final state needs the whole history (CDC-style compaction is impossible). The choice is situational: event sourcing is a big change (Chapter 3), while CDC can be added to an existing database with minimal change — the writing app may never even know CDC is running.

۴.۴. دوگانِ state و stream + نمودار ۵4.4. The state/stream duality + Diagram 5

جریانِ رویدادها تاریخچهٔ تغییر رو بیان می‌کنه و وضعیت، نتیجهٔ اعمالِ همون تغییره. بازسازی یا تاریخچهٔ کافی می‌خواد یا تصویرِ شروعِ معتبر به‌همراه تابعِ پردازشِ مشخص.

مثال فنی: ساخت state از رخدادها

وضعیت اولیه: جریانِ کلید K به‌ترتیب K=1,K=3,K=DELETE هست.

اجرای مرحله‌به‌مرحله: اعمالِ این تغییرات state نهاییِ «K وجود نداره» رو می‌سازه؛ compaction می‌تونه برای بازسازیِ state آخرین تغییرِ لازمِ هر کلید رو نگه داره.

نتیجه و دلیل: stream تاریخچهٔ تغییره و state حاصلِ اعمالِ اون؛ حذف‌ها و retention باید تو bootstrap درست تفسیر بشن. — یادت باشه.

In Chapter 11 we saw batch profit from input immutability; the same immutability principle powers event sourcing and CDC. We usually think of the database as holding current state (optimized for reading), but any state that changes is the product of events that mutated it over time: the list of free seats is the product of processed reservations; an account balance the product of credits and debits. No matter how much is done and redone, the fact remains that those events happened. The key idea: mutable state and the append-only log of immutable events are not in conflict; they are two sides of one coin. The log of all changes is the evolution of state over time — mathematically inclined: application state is the integral of the event stream over time, and the change stream is the time-derivative of state (Fig. 12-7). As Gray and Reuter put it (1992): “Fundamentally, there is no need to keep a database; the log has all the information. The only reason for storing a database (i.e. the current end of the log) is retrieval efficiency.” And log compaction is the bridge between the two pictures: only each record's latest version remains.

چرا immutable؟ چند خاصیتِ عملیWhy immutable? Practical properties
  • حسابرسی: حسابدارها قرن‌هاست immutable کار می‌کنن — دفترِ کلِ append-only، و اشتباه با تراکنشِ جبرانی درست می‌شه نه با پاک‌کردن. اگه کدِ باگی دادهٔ بد بنویسه، با لاگِ append-only فهمیدنِ «چه شد» و برگشتن خیلی ساده‌تر از بازنویسیِ مخربه.
  • اطلاعاتِ بیشتر از وضعیت: مشتری یه قلم رو به سبد اضافه می‌کنه و بعد حذفش می‌کنه — از نظرِ انجامِ سفارش خنثی شد، ولی برای تحلیل دانستنِ «بهش فکر کرده» ارزشمنده. لاگِ رویداد اینو داره، پایگاه‌داده‌ای که با حذف پاک می‌کنه نداره.
  • چند view از یه لاگ: با جداکردنِ stateِ جهش‌پذیر از لاگِ immutable، چند نمایشِ خواندنی از همون لاگ می‌سازی (مثل چند مصرف‌کنندهٔ یه استریم)؛ اضافه‌کردنِ ویژگیِ تازه یعنی ساختنِ view تازه کنارِ سیستمِ قدیمی، نه migration پیچیدهٔ اسکیما.
  • هم‌زمانیِ ساده‌تر: تو event sourcing هر کنشِ کاربر یه رویدادِ خودکفاست — فقط یه append اتمی به لاگ. اگه لاگ و state هم‌شارد باشن، مصرف‌کنندهٔ تک‌نخیِ لاگ اصلاً به کنترلِ هم‌زمانی برای write نیاز نداره؛ لاگ با تعریفِ ترتیبِ سریال، نادترمینیسمِ هم‌زمانی رو حذف می‌کنه.
  • Auditing: accountants have worked immutably for centuries — an append-only ledger, with mistakes fixed by compensating transactions, not deletion. If buggy code writes bad data, an append-only log makes understanding “what happened” and rolling back far simpler than destructive overwrite.
  • More information than state: a customer adds an item to the basket then removes it — neutral for fulfilling the order, but knowing “they considered it” is valuable for analytics. The event log has it; a database that deletes on remove does not.
  • Several views of one log: by separating mutable state from the immutable log you build several readable views of the same log (like several consumers of one stream); adding a fresh feature means building a fresh view beside the old system, not a complex schema migration.
  • Simpler concurrency: in event sourcing each user action is a self-contained event — just one atomic log append. If log and state are co-sharded, the log's single-threaded consumer needs no write concurrency control at all; by defining the serial order, the log removes concurrency nondeterminism.

دو سایه هم هست. اول، مصرف‌کننده‌های لاگ معمولاً ناهمگام‌ان: کاربر write می‌کنه و از view مشتق‌شده می‌خونه و writeِ خودش رو هنوز نمی‌بینه (همون «خوندنِ writeهای خودت» فصل ۶). همگام‌کردنش تراکنشِ توزیع‌شده یا انتظار می‌خواد که معمولاً غیرعملیه — پس viewها ناهمگام به‌روز می‌شن. دوم، محدودیتِ immutability: بعضی workloadها update/delete سنگین روی dataset کوچیک دارن (تاریخِ immutable انفجار می‌کنه)، و گاهی قانون (مثل GDPR) یا لو رفتنِ دادهٔ حساس، حذفِ واقعی می‌خواد — یعنی بازنویسیِ تاریخ و وانمودکردنِ اینکه داده هیچ‌وقت نوشته نشده (تو Datomic بهش excision می‌گن). حذفِ واقعی شگفت‌انگیز سخته (کپی همه‌جاست، بکاپ‌ها عمداً immutable‌ان)؛ یه راه crypto-shreddingه: داده رو رمزنگاری‌شده نگه دار و برای حذف، کلید رو فراموش کن — ولی این فقط مسئله رو جابه‌جا می‌کنه (انبارِ کلید جهش‌پذیر می‌شه) و باید از قبل تصمیم بگیری چه داده‌ای با چه کلیدی رمز بشه.

There are two shadows. First, log consumers are usually asynchronous: the user writes and reads from a derived view, not yet seeing their own write (the Chapter-6 “read your own writes”). Synchronizing it needs distributed transactions or waiting, usually impractical — so views update asynchronously. Second, the limits of immutability: some workloads heavily update/delete a small dataset (immutable history explodes), and sometimes law (like GDPR) or leaked sensitive data demands real deletion — i.e. rewriting history and pretending the data was never written (in Datomic called excision). Real deletion is surprisingly hard (copies everywhere, backups deliberately immutable); one way is crypto-shredding: keep the data encrypted and forget the key to delete — but that only moves the problem (the key store becomes mutable) and you have to decide upfront which data is encrypted with which key.

۵5 پردازشِ استریم‌هاProcessing streams

پردازش جریانی روی داده‌ای کار می‌کنه که دائماً میاد و پایانِ کلی نداره. به‌جای صبر کردن برای تکمیلِ همهٔ داده، نتیجه‌ها مرحله‌به‌مرحله عوض می‌شن.

مثال فنی: یک رخداد، سه پردازش

وضعیت اولیه: یه سفارشِ تازه به مبلغ ۲۰۰ رسیده.

اجرای مرحله‌به‌مرحله: یه پردازشگر الگوی تقلب رو بررسی می‌کنه، یکی دیگه جمعِ دقیقه رو عوض می‌کنه و سومی نمای وضعیتِ سفارش رو می‌سازه.

نتیجه و دلیل: همه‌شون streaming‌ان، ولی state، شرطِ تکمیل و تحملِ تأخیرشون یکی نیست. — این دام معروفه.

So far we've seen where streams come from (user events, sensors, database writes) and how they get carried. What's left is what you can do with a stream. Three broad ways: 1) write the events into a database/cache/index for others to query (the streaming equivalent of batch uses — especially when the stream consumer is that database's sole writer); 2) deliver events to humans (alert emails, pushes, realtime dashboards); 3) process one or more input streams into one or more output streams — possibly as a multi-stage pipeline. The rest of the chapter lives in that third way: the snippet turning a stream into a derived stream (operator / job), kin to Unix processes and Chapter-11 MapReduce jobs — same dataflow pattern (read the input read-only, write the output append-only somewhere else) and the same sharding and parallelization. Simple operations like transform and filter work the same way.

یک تفاوتِ سرنوشت‌ساز با بچA fateful difference from batch

استریم هیچ‌وقت تموم نمی‌شه؛ مرتب‌سازی روی dataset نامحدود بی‌معناست و joinهای sort-merge (فصل ۱۱) به کار نمیان؛ و مکانیزمِ تحملِ خرابی هم باید عوض بشه — با job بچی که چند دقیقه کار کرده می‌شه task شکسته رو از اول restart کرد، ولی با job استریمی که چند سال کار کرده، restart از اولِ تاریخ بعد از crash گزینهٔ واقعی نیست.

A stream never ends. So sorting an unbounded dataset is meaningless and sort-merge joins (Chapter 11) don't apply; and the fault-tolerance mechanism has to change too — a batch job that ran minutes can restart its broken task from scratch, but a streaming job that ran years can't restart from the beginning of history after a crash as a realistic option.

۵.۱. سه کاربرد: CEP، تحلیل، نماهای مادی‌شده5.1. Three uses: CEP, analytics, materialized views

پردازشِ رویداد می‌تونه الگوی خاصی رو تشخیص بده، آمار بسازه یا نمای خواندنی رو به‌روز کنه. فرقش تو نوعِ خروجی و شرایطِ زمانیه.

مثال فنی: CEP با جمع‌زدن فرق داره

وضعیت اولیه: برای یه حساب، سه ورودِ ناموفق و بعد یه ورودِ موفق تو دو دقیقه رخ داده.

اجرای مرحله‌به‌مرحله: CEP ترتیب و فاصلهٔ رخدادها رو برای یه الگو می‌سنجه؛ تحلیلِ معمولی می‌تونه فقط تعدادِ ورودِ ناموفقِ دقیقه رو جمع کنه.

نتیجه و دلیل: یه مجموعِ ساده ترتیبِ «سه شکست سپس موفقیت» رو نگه نمی‌داره؛ نوعِ سؤال، stateِ لازم رو تعیین می‌کنه. — حساب کن.

  • پردازشِ رویدادِ پیچیده (complex event processing / CEP): رویکردِ دههٔ ۹۰ برای تحلیلِ استریم، مخصوصِ اپ‌هایی که دنبالِ الگوی خاصی از رویدادن — مثل regex که الگوی کاراکتر تو رشته پیدا می‌کنه، CEP با زبانِ declarative (شبیه SQL) یا GUI الگوی رویداد تو استریم تعریف می‌کنه و موتور با ماشینِ وضعیتِ داخلی match می‌کنه و رویدادِ پیچیده با جزئیاتِ الگوی پیداشده منتشر می‌کنه. نسبتِ کوئری و داده این‌جا برعکسِ پایگاه دادهٔ عادیه: معمولاً داده دائمه و کوئری گذرا و فراموش می‌شه؛ تو موتورِ CEP کوئری‌ها بلندمدت ذخیره می‌شن و با هر رویدادِ تازه بررسی می‌شن الگویی match شده یا نه. نمونه‌ها: Esper، Apama، StreamBase — و پردازشگرهای توزیع‌شده مثل Flink و Spark هم SQL روی استریم دارن.
  • تحلیلِ استریم (stream analytics): مرزِ باریکی با CEP داره ولی کمتر دنبالِ دنبالهٔ خاص و بیشتر دنبالِ تجمیع و متریکِ آماری روی حجمِ زیاد: نرخِ یه نوع رویداد، میانگینِ غلتان، مقایسه با بازهٔ قبلی (تشخیصِ روند یا هشدارِ غیرعادی). این آمارها معمولاً روی بازهٔ زمانیِ ثابت (پنجره — بخشِ ۵.۳) حساب می‌شن. گاهی از الگوریتم‌های احتمالاتی (Bloom، HyperLogLog برای کاردینالیتی، تخمینِ پرسنتیل) استفاده می‌شه که جوابِ تقریبی با حافظهٔ خیلی کمتر می‌دن — ولی این فقط بهینه‌سازیه؛ هیچ چیزِ ذاتاً تقریبی تو پردازشِ جریانی نیست. فریم‌ورک‌ها: Storm، Spark Streaming، Flink، Samza، Beam، Kafka Streams (و سرویس‌های میزبانی‌شده مثل Dataflow و Stream Analytics).
  • نگه‌داشتنِ نماهای مادی‌شده (materialized views): استریمِ تغییراتِ پایگاه داده، سیستم‌های مشتق‌شده (کش، ایندکس، انبارِ داده) رو به‌روز نگه می‌داره — و تو event sourcing هم وضعیتِ اپ همون view مادی‌شده‌ست. برخلافِ تحلیل، پنجرهٔ محدودِ زمانی کافی نیست: ساختنِ view شاید همهٔ رویدادها رو بخواد (پنجره‌ای که تا ابتدایِ زمان برمی‌گردد)؛ Kafka Streams و ksqlDB روی compaction کافکا همین کاربرد رو می‌سازن. پایگاه‌داده‌ها view مادی‌شده دارن ولی معمولاً با بچِ دوره‌ای یا REFRESH MATERIALIZED VIEW تازه می‌کنن — دو ایراد برای استریم: ناکارایی (هر بار همهٔ داده بازپردازش می‌شه) و کهنگی (تغییرِ مبدأ تا به‌روزرسانیِ بعدی دیده نمی‌شه). راهِ عمومی، نگه‌داریِ تدریجیِ view (incremental view maintenance / IVM)ه: کوئریِ SQL به عملگرهای محاسبهٔ تدریجی تبدیل می‌شه و فقط دادهٔ عوض‌شده بازحساب می‌شه — پس به‌روزرسانی خیلی پربسامدتر و تازه‌تر می‌شه (Materialize، RisingWave، ClickHouse، Feldera: رویدادهای تازه تو حافظه بافر و دوره‌ای روی view دیسکی اعمال می‌شن).
  • دو کاربردِ کوچک‌تر: جستجو روی استریم (مثل CEP ولی برای تک‌رویداد با معیارِ پیچیده — کوئری‌ها ذخیره‌ان و سندها با آن‌ها match می‌شن؛ ویژگیِ percolator الاستیک‌سرچ) و معماریِ رویدادمحور در برابر RPC (فصل ۵): فریم‌ورک‌های actor بیشتر مکانیزمِ هم‌زمانی‌ان تا تکنیکِ مدیریتِ داده — ارتباطشون گذرا و یک‌به‌یکه (نه بادوام و چندمشترکی)، و چرخهٔ دلخواه دارن (نه خطِ بدونِ چرخهٔ مشتق‌شدگیِ خوش‌تعریف)؛ و خیلی‌هاشون با crash تحویل رو تضمین نمی‌کنن مگر retry اضافه کنی.
  • Complex event processing (CEP): the 1990s approach to stream analysis, for apps hunting a specific event pattern — like a regex finding character patterns in a string, CEP defines event patterns in a stream with a declarative language (SQL-like) or GUI, and the engine matches with internal state machines, publishing a complex event detailing the found pattern. The query/data ratio here is the inverse of a normal database: usually data is permanent and queries transient and forgotten; in a CEP engine queries are long-lived and stored, and each fresh event is checked for a match. Examples: Esper, Apama, StreamBase — and distributed processors like Flink and Spark have SQL on streams too.
  • Stream analytics: a thin border with CEP, but less after specific sequences and more after aggregation and statistics over volumes: the rate of an event type, rolling averages, comparison with the previous window (trend detection or anomaly alerts). These stats are usually computed over a fixed time range (a window — §5.3). Probabilistic algorithms are sometimes used (Bloom, HyperLogLog for cardinality, percentile estimation) that give approximate answers with far less memory — but that is only optimization; there is nothing inherently approximate about stream processing. Frameworks: Storm, Spark Streaming, Flink, Samza, Beam, Kafka Streams (plus hosted services like Dataflow and Stream Analytics).
  • Maintaining materialized views: the database's change stream keeps derived systems (cache, index, warehouse) fresh — and in event sourcing the app's state is that same materialized view. Unlike analytics, a bounded time window isn't enough: building the view may need every event (a window reaching back to the beginning of time); Kafka Streams and ksqlDB do this on top of Kafka compaction. Databases have materialized views too, but they usually refresh them with a periodic batch or REFRESH MATERIALIZED VIEW — two problems for streams: inefficiency (every refresh reprocesses everything) and staleness (the source change stays invisible until the next refresh). The general answer is incremental view maintenance (IVM): the SQL query is turned into incremental operators and only the changed data is recomputed — so updates get far more frequent and fresher (Materialize, RisingWave, ClickHouse, Feldera: fresh events buffered in memory and applied to the on-disk view periodically).
  • Two smaller uses: search over a stream (like CEP but for a single event with a complex criterion — the queries are stored and documents are matched against them; the percolator feature of Elasticsearch) and event-driven architecture vs RPC (Chapter 5): actor frameworks are mostly concurrency mechanisms rather than data-management techniques — their communication is transient and one-to-one (not durable and multi-subscriber), and they have arbitrary lifecycles (not a line with a well-defined derived lifecycle); and many of them don't guarantee delivery across a crash unless you add retries.

تو اتصالِ جریانی، دادهٔ دو جریان یا یه جریان و یه جدول با هم ترکیب می‌شن. چون ورودی پایان نداره، باید زمان، مدتِ نگهداری و رفتارِ تغییرات مشخص باشه.

مثال فنی: سه join با سه state

وضعیت اولیه: کلیک و نمایشِ تبلیغ هر دو جریان‌ان؛ مشخصاتِ کاربر یه جدوله.

اجرای مرحله‌به‌مرحله: stream-stream کلیک رو تو بازهٔ زمانی به نمایش وصل می‌کنه؛ stream-table مشخصاتِ کاربر رو هنگامِ رخداد می‌خونه؛ table-table دو نمای به‌روز رو هماهنگ می‌کنه.

نتیجه و دلیل: هر join زمانِ نگهداری و معنای نسخهٔ طرفِ مقابل رو می‌خواد؛ join دو streamِ نامحدود بدون محدودیتِ state، stateِ نامحدود می‌سازه. — این دام معروفه.

Since stream processing generalizes the data pipeline to incremental processing of unbounded datasets, batch's join need shows up here too — but joining on a stream is harder, because a fresh event may arrive at any moment. Three kinds to tell apart:

  • join استریم–استریم (window join): مثلاً برای نرخِ کلیکِ هر URL تو نتایجِ جستجو، باید رویدادِ «جستجو» و رویدادِ «کلیک» با session id یکسان به هم برسن. کلیک شاید هیچ‌وقت نیاد (رهاکردنِ جستجو) و فاصله‌اش از ثانیه تا روزها متغیر باشه؛ حتی به‌خاطرِ تأخیرِ شبکه ممکنه کلیک قبل از جستجو برسه. برای همین پنجره انتخاب می‌کنی (مثلاً کلیکِ حداکثر یک‌ساعت‌بعد به جستجو می‌چسبه). دقت: جاسازیِ جزئیاتِ جستجو تو رویدادِ کلیک معادلِ join نیست — اون فقط کلیک‌شده‌ها رو می‌گه، ولی برای نرخِ دقیق به جستجوهای بی‌کلیک هم نیاز داری. پیاده‌سازی: پردازشگر state نگه می‌داره (مثلاً همهٔ رویدادهای یک ساعتِ گذشته به تفکیکِ session)؛ با هر رویداد، به ایندکس اضافه‌اش می‌کنه و ایندکسِ طرفِ دیگه رو برای همون session چک می‌کنه؛ match شد منتشر می‌کنه، و اگه جستجو بدونِ کلیک منقضی شد، «کلیک‌نشده» منتشر می‌کنه.
  • join استریم–جدول (stream enrichment): همون join شکل ۱۱-۲ (رویدادهای فعالیت + جدولِ پروفایل)، ولی پیوسته: ورودی استریمِ رویدادِ فعالیت با user id و خروجی همون رویدادِ غنی‌شده با اطلاعاتِ پروفایل. lookup از راهِ دور کنده و برای پایگاه داده خطرناکه (فصل ۱۱)؛ راهش کپیِ محلیِ پایگاه داده تو پردازشگره (hash join — اگه کوچیک باشه جدولِ hash تو حافظه، وگرنه ایندکسِ دیسکِ محلی). تفاوت با بچ: snapshotِ نقطه‌ایِ ثابت نیست، چون پایگاه داده تو طولِ عمرِ پردازشگر عوض می‌شه — پس کپیِ محلی رو باید با CDC به‌روز نگه داشت: پردازشگر هم مشترکِ changelog پروفایل‌هاست و هم استریمِ فعالیت؛ با هر ساخت/تغییرِ پروفایل، کپیِ محلی رو عوض می‌کنه. عملاً join دو استریمه (رویدادهای فعالیت + updateهای پروفایل) — با این تفاوت که سمتِ جدول پنجره‌ای تا «ابتدایِ زمان» داره (نامتناهیِ مفهومی) و نسخهٔ تازه جای قدیمی رو می‌گیره، و سمتِ استریم شاید اصلاً پنجره نگه نداره.
  • join جدول–جدول (materialized view maintenance): مثلاً کشِ تایم‌لاینِ شبکهٔ اجتماعی — به‌جای گران‌بودنِ خوندن (پیمودنِ همهٔ دنبال‌شونده‌ها و merge)، صندوقِ ورودیِ هر کاربر رو مادی می‌کنی: با هر پستِ تازه، به تایم‌لاینِ همهٔ دنبال‌کننده‌ها اضافه؛ با حذفِ پست/اکانت، از همه حذف؛ با follow تازه، پست‌های اخیر اضافه؛ با unfollow، حذف. پردازشگر استریمِ پست‌ها و استریمِ followها رو می‌گیره و پایگاه دادهٔ دنبال‌کننده‌ها رو نگه می‌داره تا بدونه با هر پست کدوم تایم‌لاین‌ها رو به‌روز کنه — یعنی view مادی‌شدهٔ join دو جدول (posts JOIN follows با group by دنبال‌کننده). نگاهِ قشنگ: اگه استریم رو مشتقِ جدول بگیری (شکل ۱۲-۷) و join رو ضربِ دو جدول، استریمِ تغییراتِ joinِ مادی‌شده از قاعدهٔ مشتقِ ضرب پیروی می‌کنه: (u·v)′ = u′v + uv′ — هر تغییرِ پست‌ها با آخرینِ دنباله‌کننده‌ها join می‌شه و برعکس.
  • Stream–stream join (window join): e.g. for each URL's click rate in search results, the “search” event and the “click” event with the same session id must meet. The click may never come (abandoned search) and its distance varies from seconds to days; network delay may even deliver the click before the search. So you pick a window (e.g. clicks up to one hour later attach to the search). One caveat: embedding search details in the click event is not a join — that only tells you about the clicked ones, while an exact rate also needs the clickless searches. Implementation: the processor keeps state (e.g. all last-hour events by session); with each event it adds to the index and checks the other side's index for the same session; on a match it emits, and if a search expires clickless it emits “unclicked”.
  • Stream–table join (stream enrichment): the same join as Fig. 11-2 (activity events + profile table), but continuous: input is the activity-event stream keyed by user id, output the same events enriched with profile info. A remote lookup is slow and dangerous for the database (Chapter 11); the fix is the database's local copy inside the processor (hash join — in-memory hash table if small, local disk index otherwise). Difference from batch: no fixed point-in-time snapshot, since the database changes over the processor's lifetime — so the local copy must be kept fresh with CDC: the processor subscribes to both the profile changelog and the activity stream; on each profile create/change it mutates the local copy. So it's effectively a two-stream join (activity events + profile updates) — except the table side has a window to “the beginning of time” (conceptually infinite) with fresh versions replacing old ones, while the stream side may keep no window at all.
  • Table–table join (materialized view maintenance): e.g. a social network's timeline cache — instead of expensive reads (walking every follower and merging), you materialize each user's inbox: every new post is appended to every follower's timeline; a deleted post/account is removed everywhere; a new follow adds the recent posts; an unfollow removes them. The processor takes the posts stream and the follows stream and keeps a database of followers so it knows which timelines to update for each post — i.e. a materialized view of the two-table join (posts JOIN follows grouped by follower). The pretty view: treat the stream as the derivative of a table (Fig. 12-7) and the join as the product of two tables, and the change stream of the materialized join follows the product-derivative rule: (u·v)′ = u′v + uv′ — each change of the posts joins the latest followers and vice versa.

هر سه join یه نقطهٔ مشترک دارن: پردازشگر از یه ورودی state می‌سازه و با رکوردهای ورودیِ دیگه کوئریش می‌کنه — و ترتیبِ رویدادهای نگه‌دارندهٔ state مهمه (اول follow بعد unfollow، یا برعکس؟). تو لاگِ shardشده مثل کافکا ترتیب فقط درونِ یه shard حفظ می‌شه، نه میانِ استریم‌ها و shardها — پس اگه رویدادهای دو استریم نزدیکِ هم رخ بدن، با چه ترتیبی پردازش می‌شن؟ مثلاً update پروفایل با کدوم رویدادهای فعالیت join می‌شه: اون‌هایی که قبلش پردازش شدن (پروفایلِ قدیمی) یا بعدش (جدید)؟ اگه ترتیبِ میانِ استریم‌ها نامعین باشه، join ناقطعی (nondeterministic) می‌شه: با اجرای دوباره روی همون ورودی لزوماً همون نتیجه رو نمی‌گیری. تو انبارِ داده به این می‌گن slowly changing dimension و راهش شناسهٔ یکتا برای هر نسخه‌ست (مثلاً هر تغییرِ نرخِ مالیات شناسهٔ تازه می‌گیره و فاکتور شناسهٔ نرخِ زمانِ فروش رو داره) — ولی بهایش نگه‌داشتنِ همهٔ نسخه‌ها و ناممکن‌شدنِ compactionه؛ راهِ دیگه denormalize کردنه (گذاشتنِ نرخ تو خودِ رویدادِ فروش).

All three joins share one point: the processor builds state from one input and queries it with the other's records — and the order of state-holding events matters (follow first then unfollow, or the reverse?). In a sharded log like Kafka, order survives only within a shard, not across streams and shards — so if two streams' events happen close together, in what order are they processed? Say, which activity events does a profile update join with: those processed before it (old profile) or after (new)? If the cross-stream order is undefined, the join becomes nondeterministic: rerunning on the same input needn't give the same result. Warehouses call this slowly changing dimension, fixed with a unique ID per version (e.g. each tax-rate change gets a fresh ID and the invoice carries the sale-time rate's ID) — but at the price of keeping all versions and making compaction impossible; the other way is denormalizing (putting the rate in the sale event itself).

  • لغزان (sliding): همهٔ رویدادهایی که تو فاصلهٔ معینی از هم‌ان (مثلاً دو رویداد با فاصلهٔ ۴.۵ دقیقه تو پنجرهٔ ۵دقیقه‌ای‌ان، هرچند هیچ مرزِ ثابتی اون‌ها رو یه‌جا نمی‌کنه).
  • نشست (session): بدونِ مدتِ ثابت — همهٔ رویدادهای نزدیکِ همِ یه کاربر، و پایان وقتی که کاربر مدتی (مثلاً ۳۰ دقیقه) غیرفعال بوده؛ رایج تو تحلیلِ وب‌سایت.
  • Tumbling: fixed length, each event in exactly one window (e.g. all 10:03-minute events in one window).
  • Hopping: fixed length but consecutive windows overlap (e.g. a 5-minute window with a one-minute hop: 10:03–10:07, then 10:04–10:08).
  • Sliding: all events within a given distance of each other (e.g. two events 4.5 minutes apart share a 5-minute window, though no fixed boundary would hold them together).
  • Session: no fixed duration — all nearby events of one user, ending when the user has been idle a while (e.g. 30 minutes); common in website analytics.

عملیاتِ پنجره معمولاً state موقت نگه می‌داره: گاهی با اندازهٔ ثابت (شمارنده فقط یه عدده، هرقدر هم پنجره بزرگ بشه)، گاهی بافرِ رویداد تا پایانِ پنجره (پنجرهٔ لغزان یا join استریمی) — پس باید مطمئن بشی ماشین‌ها گنجایشِ state رو دارن.

Window operations usually keep temporary state: sometimes fixed-size (a counter is just one number however big the window grows), sometimes an event buffer until the window ends (sliding windows or stream joins) — so you must make sure the machines have room for the state.

۵.۴. زمانِ رویداد در برابر زمانِ پردازش + نمودار ۸5.4. Event time vs processing time + Diagram 8

زمانِ رویداد می‌گه اتفاق کِی رخ داده؛ زمانِ پردازش می‌گه کِی به پردازشگر رسیده. قطعِ اینترنت و صف باعث می‌شن این دوتا فرق کنن.

مثال فنی: رخداد دیر رسیده

وضعیت اولیه: خرید تو 10:02 رخ داده، ولی به‌خاطرِ قطعِ دستگاه تو 10:12 به پردازشگر رسیده.

اجرای مرحله‌به‌مرحله: گزارشِ event-time اون رو تو بازهٔ 10:00–10:05 می‌ذاره؛ گزارشِ processing-time هم تو بازهٔ دریافت.

نتیجه و دلیل: برای گزارشِ رخدادِ واقعی به lateness و اصلاحِ نتیجه نیاز داری؛ دو ساعت، دو سؤالِ متفاوت رو جواب می‌دن. — حساب کن.

Stream processors deal with time a lot (e.g. “the average of the last five minutes”), and what “the last five minutes” means is surprisingly subtle. In batch, tasks chew through history fast, and when they need time separation they look at each event's embedded timestamp — looking at the executing machine's clock is meaningless, since run time has nothing to do with occurrence time (a minutes-long batch may read a year of history; the timeline that matters is that year, not those minutes). And that use of the event timestamp makes processing deterministic: rerunning on the same input gives the same result.

ولی خیلی از فریم‌ورک‌های جریانی برای پنجره‌بندی از ساعتِ محلیِ ماشینِ پردازشگر استفاده می‌کنن (زمانِ پردازش — processing time): ساده‌ست و اگه فاصلهٔ تولید تا پردازش ناچیز باشه معقوله؛ ولی با هر lag می‌شکنه. پردازش به هزار دلیل عقب می‌افته: صف، خرابیِ شبکه، contention، restart مصرف‌کننده، یا بازپردازشِ گذشته بعد از رفعِ باگ. تأخیر حتی ترتیب رو هم غیرقابل‌پیش‌بینی می‌کنه: کاربر اول به سرورِ A و بعد به سرورِ B درخواست می‌زنه، ولی رویدادِ B زودتر به بروکر می‌رسه — پردازشگر اول B رو می‌بینه بعد A رو، خلافِ ترتیبِ رخداد. تشبیهش فیلم‌های جنگِ ستارگانه: قسمتِ IV تو ۱۹۷۷ و قسمتِ I تو ۱۹۹۹ اومد؛ اگه به ترتیبِ اکران ببینی (processing time)، با ترتیبِ روایت (شمارهٔ قسمت = event timestamp) ناسازگاری — انسان کنار میاد ولی الگوریتمِ استریم باید صریح براش نوشته بشه.

But many streaming frameworks window by the processing machine's local clock (processing time): simple, and reasonable when the produce-to-process gap is negligible — but it breaks with any significant lag. Processing lags for a thousand reasons: queues, network failures, contention, consumer restarts, or reprocessing the past after a bugfix. Delay even makes order unpredictable: the user requests server A first then server B, but B's event reaches the broker sooner — the processor sees B first, then A, against occurrence order. The analogy is the Star Wars films: episode IV came out in 1977, episode I in 1999; watching in release order (processing time) clashes with story order (episode number = event timestamp) — humans cope, but a streaming algorithm must be explicitly written for it.

The “whose clock” problem runs deeper: an offline mobile app buffers events on-device and sends them hours later (extreme stragglers); the timestamp should be the device-clock interaction time, but the user-controlled device clock is untrustworthy (wrong deliberately or accidentally). The server's arrival time (your own clock) is more precise but less meaningful. One way out is recording three timestamps: occurrence time (device clock), send time (device clock), receive time (server clock — subtracting the second from the third estimates the device skew and corrects the timestamp). This problem isn't stream-only; batch has it too, only in streams you feel time passing more and notice it.

Here's the subtle part of defining windows with event time: you're never sure whether all of a window's events arrived or more are on the way. Say you count events in one-minute windows; minute-37's events are counted and now most inputs are minutes 38 and 39 — when do you declare minute 37's window done and emit its counter? You can time out (no fresh event for that window for a while, so declare it ready), but some events may be buffered on another machine (network partition). You have to cope with those late stragglers arriving after the announcement; two broad ways: ignore them (normally a small fraction — metric the dropped count and alert if it grows) or publish a correction (the window's updated value including the laggards, possibly retracting the previous output). Sometimes a special message says “from now on no message with timestamp before t will come” and the consumer triggers the window with it — but with producers on different machines each producer's threshold must be tracked separately, and adding/removing producers gets harder.

۶6 تحملِ خرابی و exactly-onceFault tolerance and exactly-once

بعد از خرابی، پردازشگر باید وضعیت و محلِ خوندن رو سازگار بازیابی کنه. ادعای exactly-once هم فقط تو محدودهٔ مشخصِ ورودی، وضعیت و خروجی معنا داره.

مثال فنی: شکافِ اثر و offset

وضعیت اولیه: جمعِ فعلی ۱۰۰۰ئه و پیامِ ۱۰۱ مبلغِ ۲۰۰ داره.

اجرای مرحله‌به‌مرحله: worker جمع رو ۱۲۰۰ می‌کنه، ولی قبل از ذخیرهٔ پیشرفت crash می‌کنه؛ replayِ بی‌حفاظ دوباره می‌زنه و می‌رسه به ۱۴۰۰.

نتیجه و دلیل: «دقیقاً یک اثر» به اتمی‌بودنِ state و پیشرفت، یا dedupِ معتبر نیاز داره؛ فقط ack کردنِ پیام کافی نیست. — این دام معروفه.

In Chapter 11 we saw batch tolerate failure simply: the broken task restarts from scratch on another machine and its partial output is discarded; since input is immutable and each task's output goes to a separate file that appears only on successful completion. The result looks as if no failure happened — as if each input record was processed exactly once, although restarts mean some records were processed several times with only one visible effect. This is called exactly-once semantics (effectively-once is the more precise description). Streams have the same problem but no simpler: waiting for a task's “end” to reveal output is impossible, since the stream is infinite and never ends.

۶.۱. microbatch و checkpoint6.1. Microbatching and checkpoints

Microbatch ورودی رو به دسته‌های کوچک تقسیم می‌کنه. Checkpoint یه نقطهٔ بازیابیِ وضعیت و پیشرفته؛ بعد از خرابی، پردازش از نقطهٔ سازگار ادامه پیدا می‌کنه.

مثال فنی: Checkpoint سازگار

وضعیت اولیه: تو checkpoint شمارهٔ ۷، جمعِ ۱۲۰۰ و موقعیتِ ورودی تا پیامِ ۱۰۱ با هم ثبت شدن.

اجرای مرحله‌به‌مرحله: بعد از crash، state و ورودی از همون مرز بازیابی می‌شن؛ خروجیِ بیرونی هم باید با قراردادِ checkpoint سازگار باشه.

نتیجه و دلیل: بازیابیِ state تا ۱۰۱ همراهِ offsetِ ۱۰۰ همون مرز نیست و می‌تونه دوباره‌شماری بسازه. — حساب کن.

One way is cutting the stream into small blocks and treating each block like a miniature batch: microbatching (in Spark Streaming; batch size usually about a second — an efficiency tradeoff: smaller batches mean more scheduling and coordination overhead, bigger batches mean more latency before results show). Microbatching also builds a tumbling window the size of the batch (in processing time, not event timestamps); jobs wanting bigger windows must explicitly carry state from one microbatch to the next. The different approach in Flink: periodically producing a rolling checkpoint of state and writing it to durable storage; if an operator crashes it restarts from the freshest checkpoint and discards output between the last checkpoint and the crash. Checkpoints are triggered by barriers in the message stream — like microbatch boundaries but without imposing a particular window size. Within a stream processor's boundaries, both approaches give batch's exactly-once.

درونِ مرزهای فریم‌ورکِ پردازشِ استریم، هر دو رویکرد همون exactly-once بچ رو می‌دن. ولی به‌محض اینکه خروجی از پردازشگر بیرون بره (write تو پایگاه داده، انتشار تو بروکرِ بیرونی، فرستادنِ ایمیل)، فریم‌ورک دیگه نمی‌تونه خروجیِ microbatch شکسته رو دور بریزه — restart باعث می‌شه اثرِ بیرونی دوباره رخ بده، و microbatch/checkpoint به‌تنهایی جلوش رو نمی‌گیره.

But the moment output leaves the processor (a database write, a publish to an external broker, sending an email), the framework can no longer discard the broken microbatch's output — a restart makes the external effect happen twice, and microbatch/checkpoint alone can't stop it.

۶.۲. کامیتِ اتمی و idempotence6.2. Atomic commit and idempotence

برای اثرِ یک‌باره، ثبتِ خروجی و پیشرفت باید هماهنگ باشه یا نوشتنِ تکراری اثرِ اضافه نذاره. تضمینِ داخلِ بروکر خودبه‌خود به هر سیستمِ بیرونی منتقل نمی‌شه.

مثال فنی: یک تراکنش برای اثر و شناسه

وضعیت اولیه: تو مقصدِ SQL، event_id=e7 uniqueه و جمعِ فروش باید ۲۰۰ زیاد بشه.

اجرای مرحله‌به‌مرحله: داخل یه تراکنش، شناسه ثبت و جمع زیاد می‌شه؛ اگه شناسه از قبل باشه، افزایشِ دوباره انجام نمی‌شه.

نتیجه و دلیل: commitِ offset جدا می‌تونه عقب بمونه و پیام تکرار بشه، ولی این مقصد اثر رو دوباره اعمال نمی‌کنه؛ حفظِ شناسه به افقِ replay وابسته‌ست. — یادت باشه.

For exactly-once appearance under failure, you must ensure all outputs and side effects of processing one event persist if and only if processing succeeded: messages to downstream operators or external systems (even emails and pushes), database writes, operator state changes, and input-message acknowledgment (including advancing the offset in a log-based broker) — all must happen atomically: all or none. Sound familiar? It is Chapter 8's “exactly-once message processing” with distributed transactions and 2PC. But in a narrower environment such an atomic commit can be implemented efficiently (Google's Dataflow, VoltDB, Kafka): unlike XA, which transacts across heterogeneous technologies, these keep the transaction internal — managing both state changes and messaging inside the framework — and the protocol overhead is amortized by processing several input messages in one transaction.

راهِ دیگرِ دورریختنِ خروجیِ ناقصِ task شکسته، تکیه بر idempotenceه (فصل ۵): عملیاتی که چند بار اجرایش همون اثرِ یک‌بار رو داره — مثل حذفِ کلید تو key-value store (حذفِ دوباره اثری نداره) در برابرِ افزایشِ شمارنده (اجرای دوباره یعنی دو بار افزایش). حتی عملیاتِ غیر-idempotent رو هم معمولاً با کمی metadata می‌شه idempotent کرد: موقعِ مصرف از کافکا هر پیام offset ماندگارِ صعودی داره؛ موقعِ نوشتن تو پایگاه دادهٔ بیرونی می‌تونی offset پیامی که آخرین write رو trigger کرد همراهِ مقدار بنویسی — پس می‌فهمی update قبلاً اعمال شده و دوباره انجامش نمی‌دی (مدیریتِ state تو Trident استورم هم همین ایده‌ست). تکیه بر idempotence چند فرض می‌خواد: restart باید همون پیام‌ها رو به همون ترتیب بازپخش کنه (بروکرِ لاگ‌محور همین کار رو می‌کنه)، پردازش قطعی باشه، و نودِ دیگری هم‌زمان همون مقدار رو update نکنه — موقعِ failover از نودی به نودِ دیگر شاید fencing لازم بشه (فصل ۹) تا نودی که مرده فرض شده ولی زنده‌ست دخالت نکنه. با همهٔ این قیدها، عملیاتِ idempotent با سربارِ کم به exactly-once می‌رسه.

The other way to discard a broken task's partial output is relying on idempotence (Chapter 5): an operation whose repeated execution has the same effect as running once — like deleting a key in a key-value store (deleting again has no effect) versus incrementing a counter (rerunning means incrementing twice). Even non-idempotent operations can usually be made idempotent with a little metadata: when consuming from Kafka each message has a durable ascending offset; when writing to an external database you can store, alongside the value, the offset of the message that triggered the last write — so you know the update was already applied and skip redoing it (Storm's Trident state management is the same idea). Relying on idempotence needs assumptions: restarts must replay the same messages in the same order (a log-based broker does exactly that), processing must be deterministic, and no other node may concurrently update the same value — on failover from one node to another, fencing may be needed (Chapter 9) so the presumed-dead-but-alive node doesn't interfere. With all these constraints, idempotent operations reach exactly-once at low overhead.

و state؟ هر پردازشِ stateدار (تجمیعِ پنجره‌ای، جدول‌ها و ایندکس‌های join) باید بعد از خرابی state رو بازیابی کنه: یا state رو تو datastore راهِ دور نگه داری و replicate کنی (ولی کوئریِ راهِ دور به‌ازای هر پیام کنده)، یا state رو محلی نگه داری و دوره‌ای replicate کنی تا task تازه بعد از خرابی بخونه و بی‌اتلاف ادامه بده (Flink دوره‌ای snapshot می‌گیره؛ Kafka Streams تغییرهای state رو تو تاپیکِ جداگانهٔ کافکا با compaction می‌فرسته، شبیه CDC؛ VoltDB با پردازشِ افزونهٔ هر ورودی روی چند نود). گاهی اصلاً replicate لازم نیست چون state از استریم‌های ورودی بازسازی می‌شه (تجمیعِ پنجرهٔ کوتاه رو سریع بازپخش می‌کنی؛ replica محلیِ پایگاه داده رو از change stream فشرده می‌سازی) — همه‌چیز به کاراییِ زیرساخت بستگی داره و هیچ راهی برای همهٔ وضعیت‌ها ایده‌آل نیست.

And state? Every stateful process (windowed aggregation, join tables and indexes) must recover state after failure: either keep state in a remote datastore and replicate it (but a remote query per message is slow), or keep state local and periodically replicate so a fresh task reads it after failure and continues loss-free (Flink snapshots periodically; Kafka Streams sends state changes to a separate compacted Kafka topic, CDC-like; VoltDB by redundantly processing each input on several nodes). Sometimes no replication is needed at all because state rebuilds from the input streams (replay a short-window aggregation fast; build a database's local replica from the compacted change stream) — everything depends on infrastructure efficiency, and no way is ideal for all situations.

Read the two rows separately. The top row is “inside the framework” — batch's own trick: MICROBATCH (Spark — cutting the stream into ~1-second blocks, each running like a mini-batch, with broken blocks restarted) and CHECKPOINT (Flink — rolling state snapshots via barriers, restarting from the latest). The bottom row is “outside effects” the framework cannot unsend: ATOMIC COMMIT (state + messages + offset together, all-or-nothing, inside one framework) and IDEMPOTENT SINK (storing the Kafka offset with the write so repeats go harmless — assuming same-order replay and fencing).

The bottom strip rules: exactly-once = effectively-once — the visible effect as if once, even when retried.

The tree has five rows: Broker Decision, AMQP / JMS Queue, Log-Based Broker, Delivery Semantics and Processing Guarantee — and since it is tall, the page gives it extra height. Second question, Order per Entity Matters? (each entity's event order): no → the AMQP / JMS Broker outcome (per-message ack, load balancing); yes → the Log Broker outcome (keyed partitioning, replay). Third question, Throughput High, Msgs Fast? (cheap work per message): yes → the same Log Broker; no → back to the second question (expensive messages must first pass the ordering filter). (redelivery after crash) — yes → the Idempotent Writes outcome (at-least-once + offset dedup); no → the fifth question: All Effects in Framework? (state and sinks committed together?) — yes → the Atomic Sink Commit outcome (checkpoint + transactional sink); no → Idempotent Writes again, since outside the framework “practically exactly once” is the ceiling.

Lesson: replay, ordering and throughput pick the broker, and the side effects' location picks the guarantee — and most of the real world stands on “at-least-once + idempotent”.

۱. رویداد، تاپیک، تولیدکننده و مصرف‌کننده را در یک خط تعریف کن.1. Define event, topic, producer and consumer in one line each.

رویداد یعنی «این اتفاق افتاد»؛ تولیدکننده می‌نویسش، تاپیک دستهٔ منطقیِ همون رویدادهاست و مصرف‌کننده برای کارِ خودش می‌خونش. قالب و معنای رویداد باید بینِ همه یکی باشه. — همین چهار نقش، تمامِ مدلِ رویداده.

مثال فنی: چهار نقش، یک سفارش

وضعیت اولیه: سرویسِ سفارش رویداد {id:e7, order_id:42, amount:200} رو می‌سازه.

اجرای مرحله‌به‌مرحله: پیام تو topic سفارش‌ها ثبت می‌شه؛ مصرف‌کنندهٔ گزارش می‌خونش و جمع رو عوض می‌کنه.

نتیجه و دلیل: نقش‌ها روشنن: تولیدکننده منشأِ پیام، topic جریانِ دسته‌بندی‌شده، مصرف‌کننده مجریِ پردازش. رویداد یه رخدادِ شناخته‌شده با هویت و زمانه. — چهار نقش، همین.

Event: a small self-contained immutable record of something that happened, plus a timestamp. Topic: a group of same-kind events — the filename equivalent. The producer writes it once; there may be several consumers, each doing its own thing. Four roles, one model.

۲. چرا polling پایگاه داده برای استریم جواب نمی‌دهد؟2. Why doesn't database polling work for streams?

Polling بارِ تکراری می‌سازه و هر تغییری که بینِ دو خوندن اتفاق بیفته از قلم می‌افته؛ حذف و ترتیب هم سخت‌تر دیده می‌شن. یه منبعِ تغییرِ پایدار، قراردادِ روشن‌تری می‌ده. — سنجش رو باید از خودِ لاگ گرفت، نه از وضعیتِ لحظه‌ای.

مثال فنی: Polling چه رخدادی رو جا می‌ندازه؟

وضعیت اولیه: رکورد از pending می‌ره به paid و پیش از pollingِ بعدی به shipped.

اجرای مرحله‌به‌مرحله: خوندنِ دوره‌ایِ وضعیت فقط shipped رو می‌بینه و رخدادِ paid رو بازسازی نمی‌کنه؛ لاگِ تغییر هر دو transition رو حمل می‌کنه.

نتیجه و دلیل: snapshotِ وضعیت با تاریخچهٔ همهٔ تغییرات یکی نیست؛ timestampِ آخرین تغییر هم رخدادهای حذف‌شده رو خودکار برنمی‌گردونه. — این دام معروفه.

Because as you move toward low latency, most polls come back empty-handed and the overhead climbs; the consumer should just be notified instead. Database triggers are limited and marginal too — hence the specialized messenger. Polling reads a snapshot; a change stream tells you what actually happened.

۳. وقتی تولید سریع‌تر از مصرف است، سه راه چیست؟ مثال بزن.3. When production outruns consumption, what are the three options? Give an example.

سه راه: پیام رو بندازی، بافر کنی، یا فشارِ برگشتی بذاری و تولید رو کم کنی. ارزشِ داده، ظرفیت و پیامدِ انتظار تعیین می‌کنن کدوم پذیرفتنیه. — انتخاب با جوابه.

مثال فنی: حساب backlog

وضعیت اولیه: تولید 1000 msg/s داریم و مصرف 700 msg/s.

اجرای مرحله‌به‌مرحله: backlog هر ثانیه ۳۰۰ پیام و در ۱۰ دقیقه ۱۸۰ هزار پیام بزرگ می‌شه؛ بزرگ‌کردنِ بافر فقط زمان می‌خره.

نتیجه و دلیل: یا نرخِ تولید رو کم می‌کنی، یا ظرفیتِ مصرف رو زیاد، یا طبقِ نیازِ بخشی رو حذف می‌کنی؛ صفِ نامحدود راه‌حلِ پایدارِ اختلافِ نرخ نیست. — حساب کن.

Drop it, buffer it, or push back (stalling the producer). Unix pipes and TCP take the third with a small fixed buffer; when it's full, the sender stays blocked until the receiver reads. The right one depends on what the message is worth.

۴. پیام‌رسانیِ مستقیم چه فرضی دارد و کی می‌شکند؟4. What does direct messaging assume, and when does it break?

ارتباطِ مستقیم بیشتر به حضور و توانِ هم‌زمانِ طرف‌ها وابسته‌ست. قطع شدنِ گیرنده و کند شدنِ مصرف‌کننده، بافر و تحویلِ صریح می‌خوانه. — فرض کن طرفین همیشه آنلاین‌ان.

مثال فنی: مستقیم یا بروکر؟

وضعیت اولیه: سرویسِ گزارش ۱۰ دقیقه خاموشه، ولی سفارش‌ها دارن میان.

اجرای مرحله‌به‌مرحله: ارسالِ مستقیم بدون ذخیرهٔ پایدار می‌تونه پیام‌ها رو گم کنه؛ brokerِ پایدار طبق سیاست retention نگهشون می‌داره تا گزارش برگرده.

نتیجه و دلیل: broker وابستگیِ زمانی رو کم می‌کنه؛ ظرفیتِ دیسک، دوام و مدتِ نگهداری هنوز باید کافی باشن. — حساب کن.

It assumes both sides are permanently online. An offline consumer loses the outage-time messages; and if the producer itself crashes, its retry buffer dies with it. So the fault tolerance is thin, and your app code has to accept that loss is possible (UDP multicast, ZeroMQ, StatsD, webhooks). The broker is the safety net you're paying for.

۵. بروکر چه مشکلی را حل می‌کند و مصرف‌کننده‌اش چرا ناهمگام است؟5. What problem does a broker solve, and why is its consumer asynchronous?

بروکر تولید و مصرف رو از نظرِ زمان و مکان جدا می‌کنه و طبقِ قرارداد پیام رو نگه می‌داره. مصرف‌کننده با سرعتِ خودش می‌خونه؛ ماندگاریِ واقعی به نوع و تنظیماتِ بروکر بستگی داره. — ناهمگام بودنِ مصرف‌کننده، بهای همین جداسازیه.

مثال فنی: مستقیم یا بروکر؟

وضعیت اولیه: سرویسِ گزارش ۱۰ دقیقه خاموشه، ولی سفارش‌ها دارن میان.

اجرای مرحله‌به‌مرحله: ارسالِ مستقیم بدون ذخیرهٔ پایدار می‌تونه پیام‌ها رو گم کنه؛ brokerِ پایدار طبق سیاست retention نگهشون می‌داره تا گزارش برگرده.

نتیجه و دلیل: broker وابستگیِ زمانی رو کم می‌کنه؛ ظرفیتِ دیسک، دوام و مدتِ نگهداری هنوز باید کافی باشن. — حساب کن.

By centralizing the data in the broker, client churn and crashes are easy to absorb, and durability moves into the broker (in-memory or on-disk, your call). The producer only waits for the buffering ack; delivery to the consumer happens at some unknown point in the future — hence asynchronous. That's the trade: you get the decoupling, and you inherit the broker's guarantees.

۶. متعادل‌سازیِ بار و fan-out چه فرقی دارند؟ ترکیبشان چیست؟6. How do load balancing and fan-out differ? What combines them?

تقسیمِ بار هر پیام رو بینِ اعضای یه گروه پخش می‌کنه؛ fan-out همون خبر رو به گروه‌های مستقل می‌رسونه. می‌شه تو هر گروه چند مصرف‌کننده داشت. — دوتا رو قاطی نکن.

مثال فنی: دو گروه، چند worker

وضعیت اولیه: topic سفارش‌ها ۴ پارتیشن داره؛ گروهِ ارسال دو worker داره و گروهِ تحلیل هم دو worker.

اجرای مرحله‌به‌مرحله: تو هر گروه پارتیشن‌ها تقسیم می‌شن؛ هر گروه مستقل، همهٔ جریان رو دنبال می‌کنه.

نتیجه و دلیل: load balancing تقسیمِ کارِ یه گروهه؛ fan-out رسوندنِ جریان به گروه‌های مستقل. — این دوتا رو قاطی نکن.

In the first one each message reaches a single consumer (that splits expensive work, and you scale by adding consumers); in the second each message reaches everyone (an independent broadcast, like several batch jobs reading one file). Combine them and you get the Kafka consumer group: load balancing inside the group, fan-out across groups.

۷. ack چیست و تحویلِ مجدد چطور ترتیب را به‌هم می‌زند؟7. What is an ack, and how does redelivery break ordering?

Ack یعنی «رسیدگی شد، طبقِ قرارداد». اگه بعد از اثرگذاری گم بشه، پیام دوباره می‌رسه؛ و ممکنه پیام‌های بعدی زودتر اجرا شده باشن و ترتیبِ اثرها قاطی بشه. — این دام معروفه.

مثال فنی: Retry ترتیب تکمیل را عوض می‌کند

وضعیت اولیه: پیامِ اول set status=paid تو worker A گیر کرده؛ پیامِ دوم set status=shipped تو B زودتر تموم می‌شه.

اجرای مرحله‌به‌مرحله: تحویلِ دوبارهٔ پیامِ اول می‌تونه بعداً وضعیت رو برگردونه به paid، اگه نسخه یا ترتیبِ هر سفارش کنترل نشه.

نتیجه و دلیل: ترتیبِ تحویل با ترتیبِ پایانِ پردازش یکی نیست؛ برای همون موجودیت، کلیدگذاری، سریالی‌کردن یا کنترلِ نسخه لازمه. — این دام معروفه.

The consumer has to explicitly say “done” so the message can leave the queue; no ack (closed connection or timeout) means redelivery to somebody else. Because the first consumer processed and acked the next message meanwhile, the redelivered one lands later — like m4 before m3. Even the JMS/AMQP ordering guarantees can't save you from “load balancing + redelivery”.

۸. پیامِ سمی چیست و DLQ چه می‌کند؟8. What is a poison message, and what does a DLQ do?

پیامِ سمی اون ورودی‌ایه که پردازشِ تکراری‌اش می‌شکنه. DLQ جدا کردنش می‌کنه تا بقیه راهشون رو باز کنن؛ ولی اصلاح، ترتیب و بازگرداندن رو باید خودت برنامه‌ریزی کنی. — DLQِ بی‌رسیدگی، انبارِ کثافتِ داده‌ست.

مثال فنی: پیامِ سمی

وضعیت اولیه: پیامِ e7 نسخهٔ schema نامعتبر داره و هر بار decoder رو می‌شکنه.

اجرای مرحله‌به‌مرحله: بعد از چند تلاشِ محدود، پیام با علتِ خطا و هویتِ اصلیش می‌ره تو DLQ؛ بعد از اصلاح هم یه بازپردازشِ کنترل‌شده انجام می‌شه.

نتیجه و دلیل: retryِ بی‌پایان همون خطا رو تکرار می‌کنه و ممکنه پارتیشن رو معطل کنه؛ DLQ هم بدونِ رسیدگی، محلِ گم‌شدنِ خاموشِ داده می‌شه. — این دام معروفه.

A message that kills every consumer (say, JSON missing a required key) and, since no ack comes, retries forever — burning resources or wedging everything (with hard ordering). The DLQ moves it to a separate queue so the flow stays free; DLQs are monitored, and the operator decides: drop it, fix it by hand, or fix the code. A DLQ nobody watches is just a graveyard.

۹. بروکرِ لاگ‌محور چطور کار می‌کند و مصرفش چرا تکرارپذیر است؟9. How does a log-based broker work, and why is its consumption repeatable?

پیام‌ها تو لاگِ پارتیشن نگه داشته می‌شن و گروهِ مصرف‌کننده موقعیتِ خوندنش رو ثبت می‌کنه. تا وقتی تاریخچه هست، می‌شه دوباره بخونی؛ ولی بازپخشِ اثرهای بیرونی باید کنترل بشه. — خوندن، لاگ رو پاک نمی‌کنه.

مثال فنی: Offset جایگاهِ یک پارتیشن است

وضعیت اولیه: پیام e7 تو پارتیشن ۲ با offset=۱۰۱ ثبت شده.

اجرای مرحله‌به‌مرحله: گروه A تا offset ۱۰۰ و گروه B تا ۹۰ پیش رفته؛ پیشرفتشون مستقل از همه.

نتیجه و دلیل: offset شناسهٔ سراسریِ کلِ topic نیست؛ برای موقعیت، نامِ topic و partition هم لازمه. — یادت باشه.

The producer appends, the consumer reads sequentially and waits at the log tail for a notification (like tail -f). Reading doesn't change the log — only the offset advances, and that's the consumer's own business — so you can raise a copy of the consumer at yesterday's offset and replay the past.

۱۰. offset چیست و چرا تکرارِ پیام پیش می‌آید؟10. What is an offset, and why do messages repeat?

Offset جای پیام تو یه پارتیشنه. اگه اثر اعمال بشه ولی موقعیت ذخیره نشه، بعد از بازیابی همون پیام دوباره خونده می‌شه. — تکرار، بهای همین فاصله‌ست.

مثال فنی: شکافِ اثر و offset

وضعیت اولیه: جمعِ فعلی ۱۰۰۰ئه و پیامِ ۱۰۱ مبلغِ ۲۰۰ داره.

اجرای مرحله‌به‌مرحله: worker جمع رو ۱۲۰۰ می‌کنه، ولی قبل از ذخیرهٔ پیشرفت crash می‌کنه؛ replayِ بی‌حفاظ دوباره می‌زنه و می‌رسه به ۱۴۰۰.

نتیجه و دلیل: «دقیقاً یک اثر» به اتمی‌بودنِ state و پیشرفت، یا dedupِ معتبر نیاز داره؛ فقط ack کردنِ پیام کافی نیست. — این دام معروفه.

Each message's ascending number inside its partition (total order within a partition, none across them). The broker only records the offset periodically — no per-message ack — so after a crash you resume from the last recorded one, not the last seen, and the messages in between repeat. Same deal as the LSN in replication.

۱۱. چرا تعدادِ مصرف‌کننده‌ها سقف دارد؟11. Why is the consumer count capped?

تو مدلِ معمولِ گروهِ مصرف‌کنندهٔ لاگ، هر پارتیشن هم‌زمان به یه عضو واگذار می‌شه؛ تعدادِ اعضای فعالِ اون تاپیک به تعدادِ پارتیشن‌ها محدوده. ولی این سقفِ همهٔ مدل‌های پردازش نیست. — حساب کن.

مثال فنی: سقفِ موازی‌سازیِ یه گروه

وضعیت اولیه: تو مدلِ معمولِ consumer group کافکا، topic چهار پارتیشن داره و گروه شش مصرف‌کننده.

اجرای مرحله‌به‌مرحله: حداکثر چهار مصرف‌کننده هم‌زمان مالکِ پارتیشنِ فعال‌ان و دو تای دیگه بی‌تخصیص می‌مونن.

نتیجه و دلیل: اضافه‌کردنِ worker بیشتر از تعدادِ پارتیشن، تو این مدل ظرفیت رو خودکار زیاد نمی‌کنه؛ پردازشِ درون‌پارتیشن و حفظِ ترتیب هم محدودیت دارن. — حساب کن.

Because a whole shard goes to one node, and a topic's cooperating nodes are at most its shard count. If one message is slow, the rest of its shard waits behind it (head-of-line blocking). For expensive per-message work where order doesn't matter, a traditional broker is the better deal.

۱۲. مسابقهٔ dual-write را با شکل توضیح بده.12. Explain the dual-write race with the figure.

نوشتن تو مرجع و مقصدِ دوم جداست؛ یکی می‌تونه شکست بخوره یا دو تغییر به ترتیبِ متفاوت برسن. باید یه مسیرِ مشترکِ معتبرِ تغییر داشته باشی یا تصمیمی که هماهنگه. — رهبرِ واحد، راهِ کم‌دردسر.

مثال فنی: Dual-write وسطِ کار می‌ترکه

وضعیت اولیه: برنامه قیمتِ P7 رو تو مرجع ۱۲۰ می‌کنه و پیش از نوشتنِ ایندکس crash می‌کنه.

اجرای مرحله‌به‌مرحله: مرجع ۱۲۰ و ایندکس ۱۰۰ می‌مونن؛ و تو دو ویرایشِ هم‌زمان، حتی ترتیبِ اعمالِ دو مقصد می‌تونه فرق کنه.

نتیجه و دلیل: retryِ ساده همیشه ترتیب رو درست نمی‌کنه؛ یه لاگِ معتبرِ تغییر یا outbox مسیرِ بازپخش‌پذیر می‌ده. — این دام معروفه.

Two clients concurrently want X as A and B; both write the database first, then the index. The database sees A then B (final: B) but the index sees B then A (final: A) — a permanent, silent divergence with no error at all. The cause is two independent leaders and no single order; without a version vector you don't even notice. The fix is one leader (the database) plus CDC.

۱۳. CDC چیست و چه چیزهایی لازم دارد؟13. What is CDC, and what does it need?

CDC تغییرها رو از مرجع به جریان تبدیل می‌کنه. تصویرِ شروع، نقطهٔ لاگ، حذف‌ها، ترتیبِ لازم، قراردادِ ساختار و تکرار باید مدیریت بشن تا نمای مقصد قابل‌بازیابی بمونه. — مرز رو درست انتخاب کن.

مثال فنی: CDC با مرز سازگار

وضعیت اولیه: snapshotِ جدول تا موقعیتِ لاگ ۵۰۰ گرفته شده.

اجرای مرحله‌به‌مرحله: snapshot میاد تو جست‌وجو و بعد تغییرهای پس از ۵۰۰ به‌ترتیبِ مناسب اعمال می‌شن؛ lag و gap کنترل می‌شه.

نتیجه و دلیل: اگه مرز اشتباه باشه، تغییرِ حینِ snapshot جا می‌افته یا نادرست تکرار می‌شه؛ صرفِ خوندنِ دوره‌ایِ کلِ جدول، CDC دقیق نیست. — حساب کن.

Extracting the database change log as an ordered stream (Debezium, Kafka Connect) that derived systems apply in the same order — the database leads, the rest follow. It's asynchronous, so it has lag. For a fresh system: a consistent snapshot at a known offset and then applying from there (or a compacted log from offset zero). Stabilize the schema with the outbox (single-transaction dual write).

۱۴. log compaction چطور جای snapshot را می‌گیرد؟14. How does log compaction replace the snapshot?

تو لاگِ فشرده‌شده، نسخهٔ لازمِ هر کلید می‌تونه برای بازسازیِ وضعیتِ فعلی بمونه — به شرطِ قراردادِ درست برای حذف و نگهداری. ولی این کار همهٔ تاریخچه یا هر نوعِ snapshot رو جایگزین نمی‌کنه. — حواست به tombstone باشه.

مثال فنی: Bootstrap با لاگِ compactشده

وضعیت اولیه: برای کلیدها تغییرهای A=1,A=2,B=5 ثبت شدن.

اجرای مرحله‌به‌مرحله: بعد از compaction، مصرف‌کننده می‌تونه با آخرینِ مقدارهای موجود stateِ A=2 و B=5 رو بسازه؛ tombstone و retention باید حذف‌ها رو پوشش بدن.

نتیجه و دلیل: لاگِ compactشده snapshotِ خودکارِ یه نقطهٔ زمانی نیست؛ bootstrap و شروعِ مصرفِ پیوسته باید مرز و سیاستِ روشن داشته باشن. — حساب کن.

Only each key's latest value remains (deletes via tombstone), and the footprint depends only on the current content. A fresh consumer scans the whole log from offset zero and takes a full copy — no fresh snapshot needed from the source. (For event sourcing, where events are intents rather than replacements, it doesn't work.)

۱۵. دوگانِ state و stream یعنی چه؟15. What does the state/stream duality mean?

جریانِ تغییرها وضعیت رو با اعمالِ مرحله‌ای می‌سازه؛ وضعیتِ فعلی همهٔ گذشته رو نگه نمی‌داره. برای بازسازی یا تاریخچهٔ کافی می‌خوای یا تصویرِ شروعِ معتبر. — لاگ مبناست، state مشتق‌شده.

مثال فنی: ساخت state از رخدادها

وضعیت اولیه: جریانِ کلید K به‌ترتیب K=1,K=3,K=DELETE هست.

اجرای مرحله‌به‌مرحله: اعمالِ این تغییرات state نهاییِ «K وجود نداره» رو می‌سازه؛ compaction می‌تونه برای بازسازیِ state آخرین تغییرِ لازمِ هر کلید رو نگه داره.

نتیجه و دلیل: stream تاریخچهٔ تغییره و state حاصلِ اعمالِ اون؛ حذف‌ها و retention باید تو bootstrap درست تفسیر بشن. — یادت باشه.

Mutable state and the immutable log are two sides of one coin: state = the event integral over time, the stream = the time-derivative of state. Treat the log as the record and state as derived — then replay, auditing and building several views from one log all come for free. (Gray and Reuter: the log has all the information.)

۱۶. CEP و تحلیلِ استریم چه فرقی دارند؟16. How do CEP and stream analytics differ?

CEP به الگوی رویدادهای مرتبط واکنش می‌ده؛ تحلیلِ جریانی معمولاً آمار و تجمیع می‌سازه. فرق تو خروجی و نیازِ ترتیب و زمانه. — CEP دنبالِ الگو می‌گرده، نه دنبالِ میانگین.

مثال فنی: CEP با جمع‌زدن فرق داره

وضعیت اولیه: برای یه حساب، سه ورودِ ناموفق و بعد یه ورودِ موفق تو دو دقیقه رخ داده.

اجرای مرحله‌به‌مرحله: CEP ترتیب و فاصلهٔ رخدادها رو برای یه الگو می‌سنجه؛ تحلیلِ معمولی می‌تونه فقط تعدادِ ورودِ ناموفقِ دقیقه رو جمع کنه.

نتیجه و دلیل: یه مجموعِ ساده ترتیبِ «سه شکست سپس موفقیت» رو نگه نمی‌داره؛ نوعِ سؤال، stateِ لازم رو تعیین می‌کنه. — حساب کن.

CEP hunts specific multi-event patterns (like regex; long-lived queries, transient data — the database's inverse). Analytics hunts aggregation and metrics over windows (rates, rolling averages); its probabilistic algorithms are only an optimization, not the nature of streams. One asks “did this happen?”, the other asks “how much?”.

۱۷. سه join استریمی را مقایسه کن.17. Compare the three stream joins.

جریان–جریان رویدادهای دو جریان رو با محدودهٔ زمان ترکیب می‌کنه؛ جریان–جدول رویداد رو با وضعیت کامل می‌کنه؛ جدول–جدول تغییرهای دو وضعیت رو تو نمای مشترک منعکس می‌کنه. — هر سه، state از یه ورودی می‌سازن.

مثال فنی: سه join با سه state

وضعیت اولیه: کلیک و نمایشِ تبلیغ هر دو جریان‌ان؛ مشخصاتِ کاربر یه جدوله.

اجرای مرحله‌به‌مرحله: stream-stream کلیک رو تو بازهٔ زمانی به نمایش وصل می‌کنه؛ stream-table مشخصاتِ کاربر رو هنگامِ رخداد می‌خونه؛ table-table دو نمای به‌روز رو هماهنگ می‌کنه.

نتیجه و دلیل: هر join زمانِ نگهداری و معنای نسخهٔ طرفِ مقابل رو می‌خواد؛ join دو streamِ نامحدود بدون محدودیتِ state، stateِ نامحدود می‌سازه. — این دام معروفه.

Stream–stream: two event streams inside a bounded window (search+click; expiry = unclicked). Stream–table: enrichment with a local copy plus CDC (an infinite window on the table side; fresh replaces old). Table–table: maintaining a materialized view from two changelogs with (u·v)′ = u′v + uv′. All three are “state from one input + lookup with the other” — and undefined cross-stream order makes a join nondeterministic.

۱۸. event time و processing time چرا قاطی می‌شوند؟ راه چیست؟18. Why do event time and processing time get mixed? What's the fix?

زمانِ وقوع با زمانِ رسیدن فرق داره. پنجرهٔ مبتنی بر زمانِ رویداد و سیاستِ پیامِ دیررس، نسبت‌دادنِ داده رو روشن می‌کنن؛ ولی watermark تضمینِ نبودِ دیررس نیست. — قاطی نکن.

مثال فنی: رخداد دیر رسیده

وضعیت اولیه: خرید تو 10:02 رخ داده، ولی به‌خاطرِ قطعِ دستگاه تو 10:12 به پردازشگر رسیده.

اجرای مرحله‌به‌مرحله: گزارشِ event-time اون رو تو بازهٔ 10:00–10:05 می‌ذاره؛ گزارشِ processing-time هم تو بازهٔ دریافت.

نتیجه و دلیل: برای گزارشِ رخدادِ واقعی به lateness و اصلاحِ نتیجه نیاز داری؛ دو ساعت، دو سؤالِ متفاوت رو جواب می‌دن. — حساب کن.

Many frameworks window by the machine clock; under lag (restarts, backlogs) a flat rate turns into an artificial spike (Fig. 12-8). The fix: window by the event timestamp (deterministic and replayable) plus watermarks for closing, and for laggards either ignore them (with a metric) or correct (with a retraction). Device clocks are untrustworthy — use three timestamps.

۱۹. چهار نوع پنجره را با مثال بگو.19. Describe the four window types with an example each.

پنجرهٔ ثابت مرزِ جدا داره؛ پنجرهٔ لغزان تو فاصله‌های منظم روی بازه‌های هم‌پوشان خروجی می‌ده؛ پنجرهٔ متحرک فاصلهٔ زمانیِ رویدادها رو دنبال می‌کنه؛ نشست هم با سکوتِ میانِ فعالیت‌ها جدا می‌شه. — مرزها رو دقیق تعریف کن.

مثال فنی: چهار پنجره با یک جریان

وضعیت اولیه: برای یه کلید، رخدادها تو 10:01,10:04,10:12 رسیدن و زمانِ خودِ رخداد ملاکه.

اجرای مرحله‌به‌مرحله: tumbling پنج‌دقیقه‌ای دو رخدادِ اول رو تو [10:00,10:05) می‌ذاره؛ hopping با اندازهٔ ۱۰ و گام ۵ اون‌ها رو تو دو پنجرهٔ هم‌پوشان می‌شمره؛ sliding ده‌دقیقه‌ای تو ۱۰:۱۲ فقط ۱۰:۰۴ و ۱۰:۱۲ رو داره.

نتیجه و دلیل: session با قانونِ «فاصلهٔ بیش از پنج دقیقه، نشستِ تازه» دو رخدادِ اول رو یه نشست و رخدادِ سوم رو نشستِ بعد می‌گیره؛ تعریفِ مرزِ هر پنجره باید مشخص باشه. — حساب کن.

Tumbling: the 10:03 minute is one window, no overlap. Hopping: 5-minute windows with a one-minute hop (that's the smoothing). Sliding: two events 4.5 minutes apart share a window (the window follows the events; needs a sorted buffer). Session: a user's activity cluster until 30 minutes idle (variable width, common in web analytics). Say the boundaries out loud — that's the part interviews test.

۲۰. در استریم به exactly-once چطور می‌رسی؟20. How do you reach exactly-once in streams?

وضعیت، محلِ خوندن و خروجی باید تو محدودهٔ تضمین هماهنگ بازیابی بشن، یا نوشتنِ تکراری اثرِ اضافه نذاره. مقصدِ بیرونی هم باید تو همین قرارداد باشه. — مرزِ تضمین رو تا مقصد دنبال کن.

مثال فنی: مرز تضمین را تا مقصد دنبال کن

وضعیت اولیه: پردازشگر از Kafka می‌خونه و روی topic دیگه‌ای می‌نویسه، یا به API پیامک زنگ می‌زنه.

اجرای مرحله‌به‌مرحله: تراکنشِ Kafka می‌تونه outputِ Kafka و offset رو تو دامنهٔ خودش هماهنگ کنه؛ API پیامک بیرون از اون به کلیدِ تکرارپذیری و قراردادِ خودش نیاز داره.

نتیجه و دلیل: exactly-once رو برای مسیرِ مشخص می‌گیم؛ تضمینِ داخلِ broker رو بی‌دلیل به هر اثرِ بیرونی تعمیم نمی‌دیم. — حساب کن.

Like batch (retry + discarding the partial) but with no “end”: inside the framework with microbatch (~1 second) or rolling checkpoints (barriers); for external effects either an internal atomic commit (state + messages + offset together) or idempotent writes (the Kafka offset alongside the value; assumes same-order replay, determinism and fencing). The precise name for it is effectively-once.

۷.۳. اشتباهات رایج در جواب‌های مصاحبه7.3. 7.3 Common interview mistakes

  • «کافکا ترتیبِ سراسری تضمین می‌کند» — نه؛ فقط درونِ هر پارتیشن. رویدادهای دو پارتیشن می‌تونن هر ترتیبی برسن؛ اگه ترتیبِ موجودیتی لازمه، کلیدِ پارتیشن‌بندیش کن.
  • «ack یعنی دقیقاً یک‌بار» — نه؛ ack یعنی دست‌کم یک‌بار (تحویلِ مجدد + گم‌شدنِ ack = تکرار). دقیقاً یک‌بار به کامیتِ اتمی یا idempotence هم نیاز داره.
  • «مصرف‌کننده اضافه کن تا سریع بشه» — فقط تا سقفِ تعدادِ پارتیشن‌ها؛ بعدش نودِ بیکار می‌مونه. اول پارتیشن رو زیاد کن.
  • «لاگ رو پاک کن مثلِ صف» — مصرفِ لاگ read-onlyه؛ پاک‌کردنِ دستی، بازپخشِ بقیه رو خراب می‌کنه. نگه‌داشت با retention/compaction مدیریت می‌شه نه با حذفِ دستی.
  • «dual-write با try/catch درست می‌شه» — نه؛ مسابقهٔ ترتیب (شکل ۱۲-۴) با هیچ خطایی رخ نمی‌ده و try/catch نمی‌فهمهش. فقط رهبرِ واحد + CDC.
  • «CDC همون event sourcingه» — نه؛ CDC لاگِ سطحِ پایینِ مدلِ جهش‌پذیر رو استخراج می‌کنه (ترتیبِ واقعیِ writeها)، sourcing رویدادِ سطحِ بالای immutable می‌نویسه (نیتِ کاربر). compaction برای دومی جواب نمی‌ده.
  • «پنجره رو با ساعتِ سرور ببند» — با lag، دادهٔ بد می‌سازی (شکل ۱۲-۸). پنجره با event time + watermark؛ ساعتِ پردازشگر فقط وقتی که lag ناچیزِ تضمینیه.
  • «دیررس‌ها رو همیشه بی‌خیال شو» — بستگی داره: برای متریکِ نرخ شاید، ولی برای صورت‌حساب باید اصلاحیه بدی (و قبلی رو پس بگیری). سیاست رو صریح انتخاب کن و متریکش کن.
  • «میکروبچ یعنی exactly-once سرتاسری» — فقط درونِ فریم‌ورک؛ اثرِ بیرونی (پایگاه داده، ایمیل) با retry تکرار می‌شه مگر کامیتِ اتمی یا idempotent باشه.
  • «join استریمی مثلِ join بچه» — نه؛ ورودی تموم نمی‌شه پس به پنجره و state نیاز داری، ترتیبِ میانِ استریم‌ها نامعینه (ناقطعی‌بودن)، و انقضا خودش یه خروجیه («کلیک‌نشده»).
  • “Kafka guarantees global order” — no; only inside each partition. Two partitions' events can arrive in any order, so partition-key it if you need per-entity order.
  • “Ack means exactly once” — no; ack means at-least-once (redelivery + lost acks = duplicates). Exactly-once also needs atomic commit or idempotence.
  • “Add consumers to go faster” — only up to the partition count; beyond that your nodes just sit there. Raise the partition count first.
  • “Delete from the log like a queue” — log consumption is read-only, and a manual delete breaks everyone else's replay. Retention is managed with retention/compaction, not manual deletes.
  • “Dual writes are fixed with try/catch” — no; the ordering race (Fig. 12-4) happens with zero errors, and try/catch can't see it. You need a single leader + CDC.
  • “CDC is the same as event sourcing” — no; CDC extracts the low-level log of a mutable model (the real write order), sourcing writes high-level immutable events (user intent). Compaction doesn't work for the latter.
  • “Close windows by the server clock” — under lag you manufacture bad data (Fig. 12-8). Window by event time + watermark; the processor clock only when lag is guaranteed negligible.
  • “Always ignore laggards” — it depends: fine for a rate metric, but billing needs corrections (retracting the old one). Pick the policy explicitly and metric it.
  • “Microbatch means end-to-end exactly-once” — only inside the framework; external effects (database, email) duplicate on retry unless they're atomic or idempotent.
  • “A stream join is like a batch join” — no; the input never ends so you need windows and state, the cross-stream order is undefined (nondeterminism), and expiry is itself an output (“unclicked”).
