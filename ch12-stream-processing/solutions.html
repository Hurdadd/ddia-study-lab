سؤال مصاحبهInterview question
فرض کن از Kafka با سه partition می‌خونی و click count رو تو DB نگه می‌داری. اثر و checkpoint هر (topic,partition) رو تو یه تراکنش ذخیره کن. یادت باشه last_offset هر کاربر فقط با key-to-partition ثابت معنا داره. crash، گم‌شدن ACK، rebalance و consumer کهنه رو با fencing و replay مرتب تحلیل کن.
Picture this, you're counting clicks from three Kafka partitions into a database. You commit each (topic,partition) effect and checkpoint together in one transaction. Remember, a per-user last_offset means something only with fixed key-to-partition routing. You walk through crashes, lost ACKs, rebalances, and stale consumers with fencing and ordered replay.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

ببین رفیق، کلیک‌ها را با کلید user id بفرست تا هر کاربر دقیقاً روی یک پارتیشن زندگی کند. تحویل at-least-once را بپذیر و sink را idempotent کن: totalها و checkpointِ per-(topic, partition) را تو یک تراکنش پایگاه داده commit کن، با یک نگهبان مقایسه offset. مالک‌های کهنه را با epoch گروه fence کن تا فقط مالک فعلی بنویسد. بده‌بستان هم اینجاست: شمارش effectively-once، به قیمت ترتیب per-partition، انسداد سر صف و یک checkpoint-write به‌ازای هر batch. — و این را نگه دار: exactly-once یعنی یه بار اثر، نه یه بار تحویل.
Key the clicks by user id so each user lives on exactly one partition. Expect at-least-once delivery and make the sink idempotent: commit the totals and the per-(topic, partition) checkpoint in ONE database transaction, guarded by an offset comparison. Fence stale owners with group epochs so only the current owner writes. The trade-off: effectively-once counting, paid for with per-partition ordering, head-of-line blocking and one checkpoint write per batch. — Remember that one: exactly-once means one effect, not one delivery.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن سه پارتیشن داریم، کلید = user id، و مسیریابی ثابت key-to-partition (نسخه‌دار، اگه روزی عوض شد). مقیاس آموزشی: حدود 10k کلیک بر ثانیه روی تاپیک، و checkpoint به‌ازای هر batch یا هر ثانیه — عدد آموزشیه، نه بنچمارک.
  • پایگاه دادهٔ مرجع تراکنشیه (آموزشی و شبه Postgres). گروه مصرف‌کننده به هر پارتیشن یه مالک می‌ده، و بازپخش لاگ درون هر پارتیشن مرتبه.
  • هیچ اثر بیرونی‌ای توی مسیر شمارش نیست. checkpoint فعال رو تا وقتی state متناظر معتبره نگه می‌داریم. بازپخش از قبلِ retention یعنی یا باید بازسازی کنی یا صریح ردش کنی.
  • Picture three partitions, key = user id, and fixed key-to-partition routing (versioned, in case it ever changes). Teaching scale: about 10k clicks/s across the topic, and a checkpoint once per batch or per second — a teaching number, not a benchmark.
  • The record database is transactional (teaching, Postgres-like). The consumer group assigns one owner per partition, and log replay stays ordered inside each partition.
  • No external effect is part of the count. You keep active checkpoints as long as their matching state stays valid. Replaying anything older than log retention means rebuilding it or rejecting it explicitly.

چرا این روش و این عددها؟Why this method and these numbers?

offset فقط شمارهٔ موقعیت توی یک partition است؛ offset=5 توی دو partition یعنی دو پیام مستقل. checkpoint و total باید توی یک commit باشن، چون جدا کردنشون انتخاب بدی بین «دوباره شمردن» و «جا انداختن» رو تحمیل می‌کنه. قفل checkpoint دو batch با همون epoch رو هم سریال می‌کنه؛ epoch فقط مالک کهنه رو رد می‌کنه و جای lock هم‌مالک رو نمی‌گیره. ۱۰هزار کلیک/ثانیه یه ورودیِ ظرفیته؛ اندازهٔ batch رو از سقف lag و هزینهٔ commit انتخاب می‌کنی. checkpoint فعال تاریخ انقضا نداره؛ عقب‌افتادن از retention لاگ به recovery نیاز داره.

An offset is just a position inside one partition; offset 5 in two partitions means two independent records. Checkpoint and total have to land in one commit, because splitting them forces a choice between double counting and dropping. Locking the checkpoint also serializes two batches with the same epoch; epoch fencing only turns stale owners away and is no substitute for that lock. Ten thousand clicks/s is a capacity input, and you pick the batch size from the lag ceiling and the commit cost. Active checkpoints don't expire, and falling behind log retention means you need recovery.

مدل ذهنیMental model

بروکر عامدانه دوباره تحویل می‌دهد، پس دو بار شمردن پیش‌فرض است نه حادثه. بذار ساده بگم: exactly-once را در sink می‌سازی — یه حافظه از این‌که چی را قبلاً شمردی، دقیقاً همون‌جایی که بروکر شماره می‌زند: جفت (topic, partition). — یعنی حافظه‌ات باید همون کلیدی را بگیرد که خودش صدا زده.
The broker redelivers on purpose, so counting twice is the default, not an accident. Honestly, the fix gets built at the sink: a memory of what you already counted, scoped to exactly the place where the broker does the numbering — the (topic, partition) pair. — In other words, remember it under the same key the broker called it by.

حل گام‌به‌گامStep by step

  1. با کلید مسیر بده، offset را پارتیشن‌محور ببین هر کلیک را با user id مسیر بده و offsetها را پارتیشن‌محور ببین. یه عدد روی دو پارتیشن هیچ ترتیبی نمی‌سازه، و کلید checkpoint همیشه (topic, partition) خودش رو حمل می‌کنه.
  2. برای هر اجرای دوباره یک نگهبان بگذار checkpoint هر پارتیشن را قفل کن و بخوان. هر offset کوچک‌تر یا مساوی آن، قبلاً اعمال شده. recordها را به‌ترتیب جلو ببر و تا وقتی اثرهای batch تمام نشده، checkpoint را جلو نبر.
  3. اثر و checkpoint را با هم ثبت کن نکته‌ش اینجاست: اثر و checkpoint آن را در یک تراکنش نگهبانی‌شده با epoch ثبت کن. این‌طوری crash میان apply و commit هیچ نیم‌حالتی نمی‌گذارد و ack گم‌شده جلوی حافظه‌ای صادق بازپخش می‌شود.
  4. نویسنده کهنه را فنس کن مالک تازه epoch خودش را با پروتکل انتقال مالکیت در sink ثبت می‌کند. تراکنش مالک قبلی یا باید پیش از انتقال تمام شود، یا بعد از آن با epoch کهنه رد شود؛ صرف callback گروه Kafka تضمینِ sink نیست.
  5. مرزها را نام ببر checkpoint فعال را با TTL پاک نکن. اگر نخستین offset موجود در لاگ از offset بعدیِ موردنیاز جلوتر بود، یه تیکه از ورودی گم است و باید rebuild یا بازیابیِ صریح بشه. از آن نقطه حدس نزن.
  1. Key it, and scope the offsets Route every click by user id and treat offsets as partition-scoped. The same number on two partitions orders nothing, so the checkpoint key always carries its (topic, partition).
  2. Guard every replay Lock the partition checkpoint and read it. Anything at or below that offset already went in. Walk the records in order, and don't move the checkpoint until the batch effects are committed.
  3. Commit the effect with the checkpoint Commit the effect and its checkpoint in one epoch-guarded transaction. Then a crash between apply and commit leaves no half-state behind, and a lost ack replays against an honest memory.
  4. Fence the stale writer Install the new ownership through a sink ownership-transfer protocol. An old transaction has to finish before the transfer, or fail its epoch check after it. Kafka group callbacks alone don't fence the sink.
  5. Name the boundaries Never expire active checkpoints by TTL. If the earliest record still in the log sits beyond the next offset you need, then input is missing: rebuild or recover explicitly instead of silently skipping ahead.

طراحی مشخصConcrete design

دو جدول داری: click_counts(user_id,total) و consumer_checkpoints(topic,partition,last_offset,owner_epoch) با کلید مرکب. توی هر تراکنش اول سطر checkpoint را قفل می‌کنی و می‌سنجی که epoch واقعاً مال sink است؛ بعد offsetهای تازه‌تر از checkpoint را به‌ترتیب اعمال می‌کنی و اثر و checkpoint را با هم commit می‌کنی. batchهایی که همان epoch را دارند هم از همین قفل رد می‌شوند. broker ACK بعد از commit می‌آید. نصب epoch تازه را باید در DB با مالکیت گروه هماهنگ کنی، چون Kafka خودش write پایگاه داده را fence نمی‌کند. دمو یک topic ثابت به اسم clicks دارد.

You get two tables: click_counts(user_id,total) and consumer_checkpoints(topic,partition,last_offset,owner_epoch) with a composite key. In one transaction you lock the checkpoint row first and check that the epoch really belongs to the sink; then you apply the ordered offsets newer than the checkpoint and commit effect plus checkpoint together. Same-epoch batches serialize on that same row too. The broker ACK comes after the commit. You coordinate the new-epoch installation at the database with group ownership, because Kafka does not automatically fence database writes. The demo has one fixed topic, clicks.

مثال محاسبه‌شدهWorked example

توی دمو u2 چهار کلیک در P1 دارد با offsetهای ۰ تا ۳ و u3 سه کلیک در همان پارتیشن با offsetهای ۴ تا ۶؛ و checkpoint مشترک P1 بعد از batch می‌شود ۶. بعد از rebalance، کلیک تازهٔ u2 با offset=7 می‌آید و totalش را به ۵ می‌رساند. offset=0 در P0 و P2 دو پیام مستقل‌اند؛ replay هر پارتیشن با checkpoint خودش سنجیده می‌شود. crash شبیه‌سازی‌شده قبل از commit هیچ اثری ندارد؛ ACK گمشده تحویل را تکرار می‌کند ولی total تکان نمی‌خورد.

In the demo u2 sits at P1 offsets 0..3 and u3 at 4..6, so the shared P1 checkpoint becomes 6. After the rebalance, u2's next click lands on offset 7 and takes its total to 5. Offset 0 in P0 and P2 is two independent records; replay is measured against each partition's own checkpoint. A simulated pre-commit crash changes nothing, while lost ACKs redeliver without moving the totals.

  2. هر پارتیشن دقیقاً یک مالک توی گروه داره؛ مالک offsetهای خودش را مرتب می‌خونه و هیچ‌وقت با offset پارتیشن دیگه مقایسه‌شون نمی‌کنه.

  1. Producers append with key = user id, so every user lands on exactly one partition. Per-user offsets are therefore totally ordered — but only inside that one partition, not across the topic.
  2. Every partition has exactly one owner in the group. That owner reads its offsets in order and never compares them with another partition's.
  3. The sink commits the totals and the (topic, partition) checkpoint in one epoch-guarded transaction. A redelivery then replays against a memory that only ever moved together with the effect.

نقطهٔ تصمیم: نقطهٔ تصمیم همون تراکنش sink است: اثر و checkpoint یا با هم commit می‌شوند یا هیچ‌کدام، و همه‌چیز مشروط به epoch.

رد خرابی: تو همین شکل crash را دنبال کن: کارِ ثبت‌نشدهٔ مصرف‌کننده محو می‌شود و poll بعدی همان offsetهای مرتب را می‌گذارد جلوی checkpointای که بدون اثر جلو نرفته. مالک کهنه را هم دنبال کن: پیکان‌هایش epoch قدیم را حمل می‌کنند و سر write شرطی می‌میرند.

تضمین نشان‌داده‌شده: این شکل سه‌تا رو روشن می‌کنه: ترتیب کجاست (درون پارتیشن‌ها)، اتمیک بودن کجاست (تراکنش sink) و fencing کجاست (شرط epoch). ولی ثابت نمی‌کنه که بروکر مرتب تحویل می‌ده — اون قرارداد خودِ لاگه.

تضمین نشان‌نداده‌شده: دربارهٔ اثرهای بیرونی، رکوردهای سمی و تغییر تعداد پارتیشن هیچی نمی‌گوید — این‌ها شاخهٔ خودشون را در شکل‌های بعد دارند.

Decision point: The decision point is the sink transaction: effect and checkpoint commit together or not at all — and the epoch gets a vote.

خودآزماییSelf-check

چرا checkpoint باید topic و partition خودش را نام ببرد، به‌جای این‌که یه عدد per-user باشه؟

پاسخ: چون offset فقط توی یک پارتیشن مرتب می‌شه. نگهبانِ «offset بزرگ‌تر از قبلی» فقط جلوی بازپخش همون یه پارتیشن رو می‌گیره، یعنی checkpoint باید (topic, partition) خودش رو نام ببره. — یه عدد per-user اینجا یه شمارهٔ خوش‌ظاهرِ بی‌معنیه.

Why does the checkpoint have to name its topic and partition instead of being one number per user?

Answer: Because an offset only sorts things inside one partition. The 'offset > last' guard is sound against that same partition's replay and nothing else, so the checkpoint has to name its (topic, partition). — A per-user number here is just a good-looking number that means nothing.

یه پارتیشن، دو مالک در طول زمان، سه بدبیاری. از بالا بخون: crash قبل از commit، ack گم‌شده روی سیم، بعد جابه‌جایی مالکیت درحالی‌که مالک قدیم هنوز زنده‌ست.
One partition, two owners over time, three mishaps. Read it top to bottom: a crash before the commit, an ack lost on the wire, then ownership moving while the old owner is still alive.
  1. شاخهٔ crash: بروکر offsetهای ۱۰۱ تا ۱۰۴ رو مرتب تحویل می‌ده؛ تراکنش فقط یه‌بار اعمالشون می‌کنه، چون checkpoint هیچ نیم‌commitای ثبت نکرده.
  2. شاخهٔ ack گم‌شده: commit شده ولی ack مرده، و offsetهای ۱۰۳ و ۱۰۴ برمی‌گردن و نگهبان، چون قبلاً شمرده شدن، skipشون می‌کنه.
  3. شاخهٔ rebalance: مالک تازه با epoch ۲ از checkpoint ۱۰۴ ادامه می‌ده، و write دیررسِ مالک قدیم با epoch ۱ همون‌جا که می‌رسه فنس می‌شه.
  1. Crash branch: the broker redelivers offsets 101–104 in order, and the transaction applies them exactly once — the checkpoint never recorded a half-commit.
  2. Lost-ack branch: the commit happened but the ack died, so offsets 103–104 come back — and the guard skips them as already counted.
  3. Rebalance branch: the new owner at epoch 2 resumes from checkpoint 104, and the old owner's epoch-1 write gets fenced the moment it arrives.

نقطهٔ تصمیم: نقطهٔ تصمیم، هر بازخوانیه: offset بزرگ‌تر از ذخیره‌شده یعنی بشمر، یعنی skip. و برابری epoch فراخوان با مالک یعنی بپذیر یا fence.

رد خرابی: شاخهٔ crash را بخون: apply بدون commit، بعد تحویل مجدد همون offsetهای مرتب — و totalها دو بار تکان نمی‌خورن. شاخهٔ rebalance رو هم بخون: write دیررسِ مالک قدیم با epoch ۱، بعد از این‌که مالکیت رفت به epoch ۲، می‌رسه و پایگاه داده ردش می‌کنه.

تضمین نشان‌داده‌شده: شکل نشان می‌ده هر مسیر تحویل مجدد به همون نگهبان می‌رسه. رکورد سمی و پرش offset رو نشان نمی‌ده — اون‌ها عامدانه از این مسیر خوش بیرون‌اند.

تضمین نشان‌نداده‌شده: اینجا فرض شده که بروکر همون پارتیشن رو با همون ترتیب بازپخش می‌کنه — برای لاگ درسته، برای صفی که تک‌پیام رو دوباره تخصیص می‌ده نادرسته.

Decision point: The decision point is every re-read: offset > stored means count it or skip it, and caller epoch = owner epoch means accept it or fence it.

Failure trace: Read the crash branch: an apply without commit, then a redelivery of the same ordered offsets — and the totals don't move twice. Now the rebalance branch: the old owner's late write shows up with epoch 1 after ownership moved to epoch 2, and the database turns it down.

Guarantee shown: The figure shows that every redelivery path ends at the same guard. It skips poison records and offset jumps — those deliberately step out of this happy path.

Not shown: It assumes the broker replays that same partition in the same order. True for a log; false for a queue that hands single messages out again.

خودآزماییSelf-check

مالک قدیمی که مرده فرض شده بیدار می‌شه و بعد از rebalance می‌نویسه. writeش چه می‌شه؟

پاسخ: شرط epoch ردش می‌کنه: مالکیت رفته به epoch ۲، و write با epoch ۱ از نگهبان رد نمی‌شه و هیچی رو عوض نمی‌کنه. — مرده‌ای که برگشته، با درِ قفل‌شده روبه‌رو می‌شه.

The old owner, presumed dead, wakes up and writes after the rebalance. What happens to that write?

Answer: The epoch condition turns it down: ownership moved to epoch 2, so the epoch-1 write fails the guard and changes nothing. — The zombie owner meets a locked door.

روایت مدرس / چطور این نمودار را بخوانیمTeacher narration / how to read this diagram
اسمبل نهایی: یه حلقه که هر batch اجراش می‌کنه و هر خرابی خروجی خودش رو داره. اول ستون فقرات، بعد هر لاین استثنا به‌عنوان جواب یه بدبیاری.
The assembly: one loop that runs every batch, and every failure gets its own exit. Read the spine first, then walk each exception lane as the answer to one mishap.
  1. ستون فقرات: poll یه پارتیشن، چک epoch، اعمال فقط offsetهای تازه‌تر، commit هم‌زمان total و checkpoint، تکرار به‌ازای هر batch.
  2. کهنه و مهاجرت: مالکِ فنس‌شده از نوشتن می‌ایسته و هویت dedupش زیر کلید مسیریابی نسخه‌دار جابه‌جا می‌شه، نه این‌که درجا ویرایش بشه.
  3. abort و هشدار: rebalanceها تراکنش باز رو rollback می‌کنن و پرش offset از روی retention به آدم page می‌زنه و re-seed می‌کنه.
  1. Spine: poll one partition, check the epoch, apply only the newer offsets, commit totals and checkpoint together, repeat per batch.
  2. Stale and migrate: a fenced owner stops writing, and its dedup identity moves under a versioned routing key rather than being edited in place.
  3. Abort and alert: a rebalance rolls back the open transaction, and an offset jump past retention pages a human and re-seeds.

نقطهٔ تصمیم: ناوردای این حلقه: checkpoint فقط توی همون تراکنشی جلو می‌ره که totalهای توصیف‌شده‌اش رو داره. — یا هر دو، یا هیچ‌کدوم.

رد خرابی: مالک کهنه، بعد از نصب epoch تازه در sink، رد می‌شه؛ batchهای هم‌epoch هم با قفل checkpoint سریال می‌شن. checkpoint فعال expire نمی‌شه و نبود بازهٔ لازم در لاگ به بازسازی صریح می‌رسه. و تغییر routing یعنی تعریف checkpoint تازه برای لاگ قبلی نیست.

تضمین نشان‌داده‌شده: شکل کلِ استدلال رو سوار می‌کنه: ترتیب پارتیشن‌محور + یه تراکنش اتمیک + fencing با epoch = شمارش effectively-once. اثرهای بیرونی و افق‌های بی‌کران همچنان بیرون می‌مونن — اون‌ها رو مرز بخون، نه حفره.

تضمین نشان‌نداده‌شده: رکوردهای سمی رو پوشش نمی‌ده (از شاخهٔ DLQِ متن بیرون می‌رن) و نه دسترس‌پذیری خود بروکر رو.

Decision point: The loop's invariant: the checkpoint advances only inside the very same transaction as the totals it describes. — Both or neither.

Failure trace: Once the new sink ownership is installed, stale owners get rejected, and the checkpoint lock serializes same-epoch batches. Active checkpoints never expire. Missing log input triggers explicit recovery. And a routing change does not redefine the checkpoints of the old log.

Guarantee shown: The figure assembles the whole argument: partition-scoped order, plus one atomic transaction, plus epoch fencing, equals effectively-once counting. External effects and unbounded horizons stay outside — read them as boundaries, not gaps.

Not shown: It doesn't cover poison records (they leave through the DLQ branch in the text) and it doesn't cover the broker's own availability.

خودآزماییSelf-check

سه مرزی رو نام ببر که این حلقه فقط توی همونا می‌تونه صادقانه ادعای exactly-once کنه.

پاسخ: دقیقاً همون سه مرز نام‌برده: ترتیب درون پارتیشن‌ها، اتمیک بودن توی یه تراکنش، و یه نویسنده per-partition با ضمانت epoch. بیرون از این‌ها این کلمه فقط آرزوئه. — ادعای exactly-once سه تا مرز داره، نه یه جملهٔ خوشگل.

Name the three boundaries inside which this loop can honestly claim exactly-once.

Answer: Exactly the three named boundaries: order inside the partitions, atomicity inside one transaction, and one writer per partition enforced by epochs. Outside those, the word is aspirational. — An exactly-once claim has three edges, not one nice sentence.

گزینه‌های جایگزینAlternatives

  • یه جدول dedup با event_id به‌جای نگهبان offset: هر event_id اعمال‌شده زیر قید UNIQUE می‌نشیند و همون قید بازپخش را رد می‌کند. وقتی بازپخش نامرتب برمی‌گردد یا اصلاً offset نداری (لاگ فشرده)، این برنده می‌شود. قیمتش هم روشن است: یه write اضافه، به‌علاوهٔ ایندکس یکتا برای هر event، و یه افق نگهداری برای خود جدول.
  • استریمینگ کاملاً تراکنشی (تراکنش کافکا، checkpoint فلینک) که همهٔ اثرها داخل خود فریم‌ورک‌اند. تا وقتی sink توی همان تراکنش شرکت می‌کند، می‌برد. ولی همین که پایگاه داده بیرونی می‌شود، می‌بازد — فریم‌ورک نمی‌تواند commitِ یه جای دیگه را rollback کند.
  • شمارش at-least-once با sketch تقریبی (HyperLogLog). وقتی محصول نرخ می‌خواهد و نه حسابرسی دقیق، جواب خوبی می‌دهد. ولی همهٔ استدلال صحتِ این تمرین را از دست می‌دهد.
  • An event-ID dedup table instead of offset guards: store each applied event_id under a UNIQUE constraint and let the constraint turn replays away. This one wins when the replay comes back unordered or offsets simply aren't there (compacted logs). What it costs: one extra write, plus a unique index per event, and the table needs a retention horizon of its own.
  • Fully transactional streaming (Kafka transactions, Flink checkpoints) with every effect inside the framework. It wins as long as the sink joins the same transaction. The moment your database lives outside, it loses: a framework cannot roll back a commit that happened somewhere else.
  • At-least-once counting with an approximate sketch (HyperLogLog). Fine when the product wants a rate and not an exact audit. What it gives up is every correctness argument this exercise stands on.

سناریوهای خرابیFailure scenarios

  • crash میان apply و commit: هیچی commit نشده، و بازپخشِ مرتب همان totalها را دوباره می‌سازد؛ +۹۹ اضافیِ دمو با همون تلاشِ ثبت‌نشده محو می‌شود.
  • ack گم‌شده بعد از commit: بروکر offsetهایی را پس می‌دهد که قبلاً checkpoint شده‌اند؛ نگهبان همه را skip می‌کند (۱۴ skip در دمو) و totalها تکان نمی‌خورند.
  • rebalance وسط batch: تراکنش باز rollback می‌شود، مالک تازهٔ epoch-2 از checkpoint ۱۰۴ ادامه می‌دهد و فقط offset ۴ — کلیک واقعاً تازه — اعمال می‌شود.
  • write مالک کهنه بعد از revoke: مرده فرض شده ولی زنده است. commit با epoch ۱ از شرط epoch رد نمی‌شود، و بدون دست زدن به totalها فنس می‌شود.
  • offset خارج از بازه بعد از retention: دیگه وجود ندارد، و مصرف‌کننده هشدار می‌دهد و از snapshot دوباره seed می‌کند به‌جای حدس زدن total.
  • رکورد سمی که هیچ‌وقت اعمال نمی‌شود: بعد از retryهای کران‌دار، با یه متریک می‌رود توی صف نامه‌های مرده و پارتیشن آگاهانه از رویش رد می‌شود.
  • Crash between apply and commit: nothing was committed, so the ordered replay rebuilds the same totals. The demo's garbage +99 vanishes with the attempt that never committed.
  • Lost ack after commit: the broker hands back offsets you already checkpointed. The guard skips every one of them (14 skips in the demo) and the totals don't move.
  • Rebalance mid-batch: the open transaction rolls back, the new epoch-2 owner resumes from checkpoint 104, and only offset 4 — the genuinely new click — goes in.
  • Stale owner writes after revoke: presumed dead but actually alive, its epoch-1 commit fails the epoch condition, so it gets fenced without ever touching the totals.
  • Offset out of range after retention: the offset you fetched isn't there anymore. So the consumer alerts and re-seeds from a snapshot instead of guessing a total.
  • A poison record that never applies: after bounded retries it heads for a dead-letter queue with a metric attached, and the partition moves past it on purpose.

این کد آموزشی و ساده‌سازی‌شده است؛ فقط برای آشنایی با ایده. کد واقعی پروداکشن ملاحظات بسیار بیشتری دارد و هیچ‌کس این‌شکلی کد پروداکشن نمی‌زند.Simplified teaching code for building intuition only — not production code; nobody ships production code like this.

import java.util.*;

// Teaching model: one fixed topic "clicks", three partitions, no real Kafka/DB.
// synchronized models a sink transaction + checkpoint-row lock, not network safety.
public class ExactlyOnceCounter {
    record Click(long offset, String user, int delta) {}
    static class Db {
        Map<String, Long> totals = new TreeMap<>();
        Map<Integer, Long> checkpoint = new TreeMap<>();
        Map<Integer, Long> epoch = new TreeMap<>();
        long skipped, fenced;
        synchronized void assign(int partition, long newEpoch) {
            if (newEpoch <= epoch.getOrDefault(partition, 0L))
                throw new IllegalArgumentException("epoch must increase");
            epoch.put(partition, newEpoch);
        }
        synchronized boolean consume(int partition, long callerEpoch,
                                     List<Click> batch, boolean crashBeforeCommit) {
            if (epoch.getOrDefault(partition, 0L) != callerEpoch) {
                fenced++;
                return false;
            }
            // Read under the same lock that guards commit, including same-owner batches.
            long upto = checkpoint.getOrDefault(partition, -1L);
            long previous = -1;
            Map<String, Long> staged = new HashMap<>();
            for (Click click : batch) {
                if (click.offset < previous)
                    throw new IllegalArgumentException("batch must preserve partition order");
                previous = click.offset;
                if (click.offset <= upto) { skipped++; continue; }
                staged.merge(click.user, (long) click.delta, Long::sum);
                upto = click.offset; // includes earlier records in THIS batch
            }
            if (crashBeforeCommit) return false; // no effects or checkpoint survive
            staged.forEach((user, delta) -> totals.merge(user, delta, Long::sum));
            checkpoint.put(partition, upto);
            return true; // only now may the broker be ACKed
        }
        synchronized void requireReplayAvailable(int p, long earliestAvailable) {
            if (earliestAvailable > checkpoint.getOrDefault(p, -1L) + 1)
                throw new IllegalStateException("required input missing: rebuild explicitly");
        }
    }
    static void check(boolean ok) { if (!ok) throw new AssertionError(); }
    public static void main(String[] args) {
        Db db = new Db();
        for (int p=0; p<3; p++) db.assign(p, 1);
        List<Click> p0 = new ArrayList<>(), p1 = new ArrayList<>(), p2 = new ArrayList<>();
        for (int i=0; i<5; i++) p0.add(new Click(i,"u1",1));
        for (int i=0; i<4; i++) p1.add(new Click(i,"u2",1));
        for (int i=4; i<7; i++) p1.add(new Click(i,"u3",1));
        for (int i=0; i<2; i++) p2.add(new Click(i,"u4",1));
        check(!db.consume(0,1,p0,true)); // simulated crash before atomic commit
        check(db.totals.isEmpty() && db.checkpoint.isEmpty());
        check(db.consume(0,1,p0,false));
        check(db.consume(1,1,p1,false));
        check(db.consume(2,1,p2,false)); // offset 0 on P2 is independent of P0
        Map<String,Long> beforeReplay = new TreeMap<>(db.totals);
        db.consume(0,1,p0,false); db.consume(1,1,p1,false); db.consume(2,1,p2,false);
        check(db.totals.equals(beforeReplay)); // lost ACK/redelivery has no new effect
        db.assign(1,2);
        p1.add(new Click(7,"u2",1));
        check(!db.consume(1,1,p1,false));
        check(db.totals.equals(beforeReplay));
        check(db.consume(1,2,p1,false));
        check(db.totals.equals(Map.of("u1",5L,"u2",5L,"u3",3L,"u4",2L)));
        // Duplicate record within one batch; later replay with the same epoch.
        List<Click> duplicate = List.of(new Click(8,"u2",1),new Click(8,"u2",1));
        db.consume(1,2,duplicate,false); db.consume(1,2,duplicate,false);
        check(db.totals.get("u2")==6 && db.checkpoint.get(1)==8);
        db.requireReplayAvailable(1,9);
        boolean refused=false;
        try { db.requireReplayAvailable(1,10); } catch (IllegalStateException e) { refused=true; }
        check(refused); // do not silently jump over missing log input
        check(db.checkpoint.equals(Map.of(0,4L,1,8L,2,1L)));
        System.out.println("OK totals="+db.totals+" checkpoints="+db.checkpoint);
        System.out.println("PASS: crash, replay, partition scope, stale epoch, same-batch duplicate, missing history");
    }
}

آزمون صحت و معیار عملیاتیCorrectness checks and operational criteria

ناورداها: total هر کاربر برابر جمع دلتاهای اعمال‌شدهٔ خودش است؛ checkpointها per-partition صعودی‌اند؛ kill -9 به‌علاوهٔ بازپخش مرتب هیچ totalی را تکان نمی‌دهد. اندازه بگیر: lag مصرف‌کننده per-partition، نرخ skipِ تحویل مجدد و شمارندهٔ write فنس‌شده. وقتی skipها رشد کردند، دردسر از سمت بروکر است؛ وقتی fenceها شلیک شدند، دردسر از سمت مالکیت. راهنمای اجرای محلی روی بروکر واقعی (فقط راهنماست، این‌جا اجرا نشده): کافکا را محلی بالا بیاور، تاپیک clicks با ۳ پارتیشن بساز، کلیک کلیددار produce کن، مصرف‌کننده را وسط batch بکش و ببین totalها سر جایشان می‌مانند.

Invariants: each user's total equals the sum of its applied deltas; checkpoints are monotonic per partition; a kill -9 plus ordered replay never moves a total. Measure three things: consumer lag per partition, the redelivery-skip rate and the fenced-write counter. When skips grow, the broker is in trouble; when fences fire, ownership is. Local-run guide on a real broker (guide only, not executed here): run Kafka locally, create topic clicks with 3 partitions, produce keyed clicks, kill the consumer mid-batch and watch the totals stay put.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): تعداد partitionها عوض بشه و کاربر جابه‌جا بشه، dedup key رو چطور مهاجرت می‌دی؟Follow-up (Staff): Partition count changes and a user moves. How do you migrate the dedup identity?

تغییر تعداد partition به‌تنهایی checkpoint موجودِ (topic,partition) رو بازنویسی نمی‌کنه. ولی اگر همان intent بره روی دو مسیر، offsetها فرق می‌کنن و dedup بین مسیرها به یه event_id پایدار نیاز داره. مرز مسیر قدیم رو ثبت کن، تا همون مرز drain کن و بعد cutover کن. برای هم‌زمانی چند پارتیشن هم، افزایش اتمیک total یا قفل روی سطر کاربر کافیه.

A partition-count change doesn't redefine an existing (topic,partition) checkpoint on its own. If the same intent now lives on two routes, the offsets differ and cross-route dedup needs a stable event ID. Record the old-route boundary, drain through it, then cut over. For concurrent partition updates, atomic total increments or a user-row lock keep the count honest.

پیگیری (سینیور): چرا خواندن-بعد-نوشتن total به‌تنهایی کافی نیست، و ستون last_offset دقیقاً چه شرطی رو چک می‌کنه؟Follow-up (Senior): Why isn't read-then-write of the total enough on its own, and what exactly does the last_offset column check?

خواندن-بعد-نوشتنِ بدون قفل یا CAS می‌تونه همون snapshot قدیمی رو دوبار اعمال کنه. checkpoint پارتیشن رو توی همون تراکنش اثر قفل کن یا compare-and-swap کن. epoch مالک کهنه رو رد می‌کنه، ولی دو batch از یه مالک باز هم سریال‌سازی می‌خوان.

An unprotected read-then-write can apply the same old snapshot twice. Lock the partition checkpoint, or compare-and-swap it, inside the effect transaction. Epoch checks turn stale owners away; same-owner batches still need serializing.

پیگیری (استف): پارتیشن شبکه دو مصرف‌کننده می‌ذاره که هرکدوم فکر می‌کنن مالک پارتیشن‌اند. شمارش چطور درست می‌مونه؟Follow-up (Staff): A network split leaves two consumers, each believing it owns the partition. How does the count stay correct?

مالک تازه epoch خودش رو با پروتکل انتقال مالکیت در sink ثبت می‌کنه. تراکنش مالک قبلی باید پیش از انتقال تموم بشه یا بعد از اون با epoch کهنه رد بشه؛ صرف callback گروه Kafka تضمینِ sink نیست.

You install the new ownership through a sink ownership-transfer protocol. An old transaction has to finish before the transfer, or fail its epoch check after it. Kafka group callbacks on their own don't fence the sink.

اشتباهات رایجCommon mistakes

  • مقایسهٔ offset دو پارتیشن با هم، انگار ۱۰۴ روی P0 کنار ۱۰۴ روی P1 معنایی دارد. offsetها دنبالهٔ per-partition‌اند؛ مقایسهٔ میان‌پارتیشنی گناه اولیهٔ این تمرینه.
  • ثبت offset قبل از اثر (شمارش at-most-once) یا در تراکنشی جدا از اثر — یعنی دقیقاً همون پنجرهٔ crashای که طراحی بسته بود، دوباره باز می‌شه.
  • فرض این‌که rebalanceها فوری‌اند. مالک قدیم هنوز یه batch زنده و یه قلم زنده داره، و بدون fencing با epoch نوشته‌هاش بعد از مالک تازه می‌نشینن.
  • ادعای exactly-once درحالی‌که یه اثر بیرونی (push، SMS، ایمیل) بدون کلید idempotency خودش سوار همون مسیره. تضمین بروکر هیچ‌وقت از اون مرز رد نمی‌شه.
  • Comparing offsets across partitions, as if 104 on P0 meant anything next to 104 on P1. Offsets are per-partition sequences — cross-partition comparison is the original sin of this exercise.
  • Committing the offset before the effect (that's at-most-once counting) or in a separate transaction from the effect — which reopens exactly the crash window the design closed.
  • Assuming rebalances are instant. The old owner still holds a live batch and a live pen, so without epoch fencing its writes land after the new owner's.
  • Claiming exactly-once while an external side effect (push, SMS, email) rides the same path without its own idempotency key. The broker's guarantee never crosses that boundary.

تصور کن search و click رو با session و event time تو پنجره یک‌ساعته join می‌کنی. هر دو arrival order، dedup و تعریف CTR رو پوشش بده. watermark، idle partition، allowed lateness و اصلاحیه رو بر اساس داده lateness خودت انتخاب کن؛ تو throughput ده‌برابری هم state و backpressure رو برآورد کن.
Think of it, you're joining search and click by session and event time in a one-hour window. You handle either arrival order, dedup, and your CTR definition. You pick your watermark, idle-partition policy, allowed lateness, and corrections from your own lateness data; then you estimate state and backpressure at tenfold throughput.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که هر دو سو را با کلید session id، در زمان رویداد و درون پنجرهٔ یک‌ساعته بافر کنی تا هر ترتیب رسیدنی join بشه. پنجره‌ها را با watermark ببند — کمینهٔ پارتیشن‌ها، با پارک کردن بیکارها — و هیچ‌وقت با ساعت دیواری. lateness مجاز را از توزیع اندازه‌گیری‌شدهٔ lateness بگیر؛ دیررس‌ها را یا با متریک بی‌خیال شو، یا با update پس‌گیرنده اصلاح کن. CTR را کلیک‌شده‌ها بر همهٔ جستجوها تعریف کن، با dedupِ اول‌کلیک-می‌برد. بده‌بستان هم اینجاست: lateness بیشتر، نرخ درست‌تر — به قیمت state بیشتر و ناتمامی طولانی‌تر.
Here's the thing: buffer both sides by session id, in event time, inside a one-hour window, so either arrival order joins. Close windows by watermark — the minimum across partitions, with the idle ones parked — never by the wall clock. Take your allowed lateness from the measured lateness distribution, then either drop latecomers with a meter or correct them with a retracting update. Define CTR as clicked searches over all searches, with first-click-wins dedup. The trade-off: more lateness buys a truer rate, paid for with more state and a longer stretch of incomplete numbers.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن استریم‌های جستجو و کلیک با session id هم‌پارتیشن‌ان (کلید یکسان، تعداد پارتیشن یکسان)، پس دو سوی هر session روی یه ماشین به هم می‌رسن. بار آموزشی: ۱M جستجو در ساعت با ۲۰۰k کلیک؛ میانگین lateness چهل ثانیه و p99 شش دقیقه — اعداد آموزشی‌ان، نه بنچمارک.
  • زمان رویداد از timestamp تعامل دستگاه می‌اد، با اصلاح انحراف ساعت دستگاه. تکراری‌ها با تحویل مجدد می‌ان و event id پایدار دارن.
  • اصلاحیه‌ها پایین‌دست پذیرفتنی‌ان: مصرف‌کنندهٔ CTR مقادیر نسخه‌دار رو می‌فهمه (اول v1، بعد v2 با پس‌گیری).
  • Picture the search and click streams co-partitioned by session id (same key, same partition count), so both sides of a session land on one machine. Teaching load: 1M searches/hour with 200k clicks; average lateness 40s, p99 6 minutes — teaching numbers, not benchmarks.
  • Event time comes from the device interaction timestamp, corrected for device skew. Duplicates arrive by redelivery, and they carry stable event ids.
  • Corrections are fine downstream: the CTR consumer understands versioned values (v1 first, then v2 with a retraction).

چرا این روش و این عددها؟Why this method and these numbers?

پنجره رو از توزیع lateness انتخاب می‌کنی، نه از یه عدد شانسی: با p99 شش دقیقه، پنجرهٔ کوتاه‌تر تقریباً بیشتر از یک درصد lateها رو بیرون می‌ندازه — ولی رفتار واقعی به تعریف همون توزیع بستگی داره. state تقریباً نرخ ورود × مدت نگهداری × بایتِ هر ورودیه؛ پنجرهٔ پهن‌تر یعنی RAM و recovery بیشتر. watermark یه ادعای پیشرفت در event-time با فرضِ منبعه، نه اثبات رسیدن همهٔ رویدادها. و retraction برای اصلاح نتیجه‌ای لازمه که قبلاً منتشر شده.

You pick the windows from the lateness distribution, not from a random number: with a p99 of six minutes, a shorter window leaves out a bit more than one percent of the late events — though what really happens depends on how that percentile is defined. State scales roughly as arrival rate × retention duration × bytes per entry, so a wider window means more RAM and slower recovery. A watermark is a claim about event-time progress that assumes its source; it is not proof that every event arrived. And a retraction is what you need to fix a result that was already published.

مدل ذهنیMental model

کلیک و جستجوش دو نامه‌ان که جدا پست شدن: هرکدوم ممکنه اول برسن. به‌ازای هر session یه کشو نگه دار تا پستچی — watermark — بگه دیگه نامه‌ای با تاریخ قدیم نمیاد. و از اول مشخص کن نامهٔ دیررس چه می‌ارزه: اصلاحیه، یا سطل با رسید.
A click and its search are two letters posted separately: either can turn up first. Keep a drawer per session until the postman — the watermark — says no more letters with old dates are coming. And decide upfront what a late letter is worth: a correction, or the bin with a receipt on it.

حل گام‌به‌گامStep by step

  1. بافر کن تا ترتیب رسیدن مهم نباشه به‌ازای هر session یه بافر دوسویه نگه دار: جستجوها و کلیک‌ها هرکدام منتظر اون یکی می‌مونن، تا کلیک-قبل-از-جستجو دقیقاً مثل جستجو-قبل-از-کلیک join بشه. مجموعهٔ دیده‌شدهٔ هر سو هم بازتحویل‌ها رو دور می‌ریزه.
  2. کمینهٔ watermark و پارک بیکار با زمان رویداد کار کن و کمینهٔ پارتیشن‌ها رو watermark کن: پارتیشنی که از timeout بیکاری گذشته، پارک می‌شه و با یه متریک از کمینه کنار گذاشته می‌شه — وگرنه یه استریم ساکت همهٔ پنجره‌ها رو گروگان می‌گیره.
  3. بودجه lateness از داده lateness مجاز رو از توزیع اندازه‌گیری‌شده بگذار (آموزشی: ۱۰ دقیقه روی p99 شش‌دقیقه‌ای): وقتی watermark از پایان به‌علاوهٔ lateness رد شد، ببند. timeout اندازه‌گیری‌نشده، حدسیه با نقابِ عدد.
  4. اصلاح یا drop، صریح به دیررس‌ها دو سرنوشت صریح بده: توی lateness یه اصلاحیهٔ پس‌گیرنده منتشر کن (v1 بیرون، v2 درون)؛ آن‌ورِ افق بیندازش، توی late_dropped_total بشمارش و با رشد سهم هشدار بده.
  5. برآورد صادقانه ۱۰ برابری قیمتِ رشد ده‌برابری رو قبل از این‌که سراغت بیاد حساب کن: state بافر با نرخ × پنجره × بایت مقیاس می‌گیره — sessionهای سرد رو به دیسک محلی سرریز کن و بذار بافرهای کران‌دار به‌جای drop بی‌صدا، با هشدار lag، backpressure بزنن.
  1. Buffer so arrival order stops mattering Keep a two-sided buffer per session: searches and clicks each wait for the other, so click-before-search joins exactly like search-before-click. A seen-set on each side throws the redeliveries away.
  2. Take the minimum, park the idle Run on event time and take the minimum across the partitions as your watermark. A partition quiet past the idle timeout gets parked and excluded, with a meter — otherwise one silent stream holds every window hostage.
  3. Budget lateness from data Take your allowed lateness from the measured lateness distribution (teaching: 10 minutes on top of a p99 of 6): close when the watermark passes end-plus-lateness. An unmeasured timeout is a guess wearing a number.
  4. Correct or drop, explicitly Give laggards two explicit fates: inside the lateness, publish a retracting correction (v1 out, v2 in); beyond the horizon, drop it, count it in late_dropped_total, and alert when the share grows.
  5. Estimate 10x honestly Price the tenfold growth before it arrives: buffer state scales with rate × window × bytes, so spill cold sessions to local disk and let the bounded buffers push backpressure with lag alerts instead of dropping silently.

طراحی مشخصConcrete design

هر دو استریم رو با session id و همون پارتیشنر کلید بزن، تا هر session روی یه ماشین پردازش بشه و هر دو سویش محلی باشن. state هر session: لیست جستجو و لیست کلیک درون پنجرهٔ یک‌ساعته، به‌علاوهٔ مجموعهٔ دیده‌شدهٔ event idها در هر سو. با هر رسیدن، بافرش کن و سوی دیگه رو probe کن؛ با match فقط یه‌بار clicked منتشر کن (اول‌کلیک می‌بره، و کلیک‌های بعدی همون session مدرک‌اند نه join تازه)؛ و وقتی watermark از پایان پنجره به‌علاوهٔ lateness مجاز گذشت، برای باقی‌ماندهٔ بی‌همتا unclicked منتشر کن.

CTR یعنی جستجوهای کلیک‌شده بر همهٔ جستجوهای پنجره‌های بسته، و نسخه‌دار: اصلاحیه v1 رو پس می‌گیره و v2 منتشر می‌کنه، و مخرج زیر اصلاحیه عوض نمی‌شه. watermark برابر کمینهٔ watermarkهای per-partition است؛ پارتیشنی که بیشتر از مهلت بیکاری ساکت مونده پارک می‌شه (با یه متریک کنار گذاشته می‌شه) تا داده برگرده.

Key both streams by session id with the same partitioner, so every session lands on one machine with both sides local. State per session: the search list and the click list inside the one-hour window, plus a seen-set of event ids on each side. Every arrival gets buffered and probes the other side; a match emits clicked exactly once (first click wins — later clicks in the same session are evidence, not new joins); and when the watermark passes the window end plus allowed lateness, you emit unclicked for whatever is still unmatched.

CTR is clicked searches over all searches in closed windows, and it's versioned: a correction retracts v1 and publishes v2, and the denominator never moves under a correction. The watermark is the minimum of the per-partition watermarks; a partition silent past the idle timeout is parked (excluded, with a meter) until data resumes.

مثال محاسبه‌شدهWorked example

اعداد آموزشی: ۱M جستجو در ساعت ≈ ۲۷۸ در ثانیه؛ هر session بافرشده حدود ۲۰۰ بایت × ۲ سو × ۱ ساعت ≈ چند گیگابایت به‌ازای هر ساعت پنجره نگه می‌داره — توی ۱۰ برابر، ده‌ها گیگابایت، پس sessionهای سرد به دیسک محلی سرریز می‌شن و داغ‌ها توی حافظه می‌مونن. p99 شش‌دقیقه‌ایِ lateness، مجاز رو ۱۰ می‌کنه؛ ۰.۳٪ دیرتر رسیده انداخته و شمرده می‌شن و CTR رو حداکثر به همان سهم به پایین بایاس می‌کنن — کنار نرخ روی داشبورد اعلام می‌شه، هیچ‌وقت پنهان نه. اصلاحیه‌ها کمتر از ۱ در ۳۰۰ پنجره رو بازبینی می‌کنن و هرکدام دقیقاً یه v1 رو پس می‌گیرن.

Teaching numbers: 1M searches/hour ≈ 278/s; each buffered session holds ~200 bytes × 2 sides × 1 hour ≈ a few GB per hour of window. At 10x that is tens of GB, so cold sessions spill to local disk while hot ones stay in memory. A lateness p99 of 6 minutes sets allowed lateness to 10; the 0.3% that arrive later get dropped and counted, biasing CTR down by at most that share — and that share goes on the dashboard next to the rate, never hidden. Corrections revise fewer than 1 in 300 windows, each retracting exactly one v1.

خودآزماییSelf-check

یه پارتیشن یه ساعت ساکت می‌مونه و بقیه جاری‌ان. پنجره‌ها اصلاً چطور بسته می‌شن؟

پاسخ: بعد از timeout بیکاری کران‌دار پارکش کن: با متریک از کمینهٔ watermark کنارش بگذار، به بستن پنجره‌ها ادامه بده و با داده برگردانش — هیچ‌وقت بی‌صدا صبر نکن.

One partition goes quiet for an hour while the rest keep streaming. So how do windows ever close?

Answer: Park it after a bounded idle timeout: pull it out of the watermark minimum with a meter, keep closing windows, and readmit it when data arrives — never wait silently.

گزینه‌های جایگزینAlternatives

  • پنجره‌های processing-time: با ساعت خود پردازشگر می‌بندی. این فقط وقتی جواب می‌ده که lag تولید-تا-پردازش تضمین‌شده ناچیز باشه؛ با هر lag واقعی، جهش مصنوعی شکل ۱۲-۸ رو می‌سازه — این تمرین با مدرک ردش می‌کنه.
  • جاسازی جزئیات جستجو توی رویداد کلیک، به‌جای join: دربارهٔ جستجوهای کلیک‌شده همه‌چیز رو می‌گیری و دربارهٔ کلیک‌نشده‌ها هیچی — مخرج نرخ از دست می‌ره. برای attribution می‌بره، برای CTR می‌بازه.
  • join استریم–جدول با جدول session و پنجرهٔ نامتناهی: وقتی sessionها state غنیِ کندتغییر دارن، می‌بره. قیمتش هم مشخصه — state نامتناهیِ جدول به‌علاوهٔ ناقطعی بودن ترتیب میان‌استریمی؛ جایی که بافر دوسویهٔ کران‌دارِ این تمرین صادق می‌مونه.
  • Processing-time windows: you close them with the processor's own clock. That only works when produce-to-process lag is guaranteed negligible. Under any real lag it manufactures the artificial spike of Figure 12-8, so this exercise throws it out with evidence.
  • Embedding the search details inside the click event instead of joining: now you know everything about clicked searches and nothing about the unclicked ones, so the rate loses its denominator. Great for attribution, bad for CTR.
  • A stream–table join against a session table with an infinite window: it wins when sessions carry rich, slowly-changing profile state. What it costs is unbounded table state plus the nondeterminism of cross-stream order — and this exercise's bounded two-sided buffer stays honest.

سناریوهای خرابیFailure scenarios

  • کلیک قبل از جستجو: کلیک توی بافر session می‌مونه و به‌محض رسیدن جستجو join می‌شه — ذاتاً بی‌نیاز از ترتیب، و توی دمو زنده می‌بینیش (c2 قبل از q2).
  • پارتیشن بیکار watermark رو گروگان می‌گیره: بعد از timeout بیکاری پارک می‌شه و با یه متریک از کمینه کنار گذاشته می‌شه تا پنجره‌ها بسته بشن. با داده برمی‌گرده و backlogش با زمان رویداد بازپخش می‌شه.
  • انحراف ساعت دستگاه: زمان وقوع رو با جفت ارسال/دریافت اصلاح می‌کنی، تا ساعت دروغگوی گوشی نتونه رویداد رو توی پنجرهٔ اشتباه بایگانی کنه.
  • تحویل تکراری در هر دو سو: event idهای پایدار رسیدن دوم رو skip می‌کنن، تا کلیکِ بازتحویل‌شده دوبار join نشه و CTR رو باد نکنه.
  • rebalance وسط پنجره یه session رو جابه‌جا می‌کنه: بافرش از changelog روی مالک تازه برمی‌گرده و بازپخش همگرا می‌شه، چون محتویات پنجره تابع خالصِ زمان رویداده.
  • throughput ده‌برابری: state بافر با پنجره حدود ۱۰ برابر می‌شه (نرخ × پنجره × بایت) — sessionهای سرد به دیسک محلی سرریز می‌شن و بافرهای کران‌دار به‌جای drop بی‌صدا، با هشدار lag، backpressure می‌زنن.
  • Click before search: the click waits in the session buffer and joins the moment the search lands — order-free by construction, and you can watch it live in the demo (c2 before q2).
  • An idle partition holds the watermark hostage: after the idle timeout it is parked and excluded from the minimum, with a meter, so windows keep closing. When data comes back it is readmitted and its backlog replays by event time.
  • Device clock skew: you correct the occurrence time with the send/receive pair, so a lying phone clock can't file an event into the wrong window.
  • Duplicate delivery on both sides: stable event ids turn the second arrival into a skip, so a redelivered click can't join twice or inflate the CTR.
  • Rebalance moves a session mid-window: its buffer is restored from the changelog on the new owner and the replay converges, because the window contents are a pure function of event time.
  • Tenfold throughput: buffer state grows about 10x with the window (rate × window × bytes), so cold sessions spill to local disk and the bounded buffers apply backpressure with lag alerts instead of dropping silently.

import java.util.*;

// Teaching demo: search-click windowed join on EVENT time with watermarks,
// idle-partition handling, allowed lateness and corrections. Both arrival
// orders work (two-sided per-session buffers + dedup sets). Stdlib only.
public class WindowedJoin {
    record Ev(String kind, String session, String id, long eventTime) {}
    static final long WINDOW = 60, ALLOWED = 10; // 1-hour window, 10-min allowed lateness (teaching)
    Map<String, List<Ev>> searches = new HashMap<>(), clicks = new HashMap<>();
    Set<String> seen = new HashSet<>(), matchedClick = new HashSet<>();
    long watermark = 0;
    int emitted = 0, unclicked = 0, droppedLate = 0, corrections = 0;

    void watermarkTo(long t, Set<Integer> idle) {
        watermark = t;
        if (!idle.isEmpty()) System.out.println("  watermark=" + t + " (idle partitions excluded: " + idle + ")");
    }

    void on(Ev e) {
        if (!seen.add(e.kind + ":" + e.id)) { System.out.println("  dedup: skip " + e.id); return; }
        long windowEnd = (e.eventTime / WINDOW + 1) * WINDOW;
        if (e.eventTime < watermark - ALLOWED && watermark > windowEnd) {
            droppedLate++;
            System.out.println("  late beyond horizon: DROP " + e.id + " (counted in late_dropped_total)");
            return;
        }
        (e.kind.equals("search") ? searches : clicks)
            .computeIfAbsent(e.session, k -> new ArrayList<>()).add(e);
        tryMatch(e.session, windowEnd);
    }

    void tryMatch(String s, long windowEnd) {
        List<Ev> ss = searches.getOrDefault(s, List.of());
        List<Ev> cs = clicks.getOrDefault(s, List.of());
        for (Ev c : cs) {
            if (matchedClick.contains(c.id)) continue;
            Optional<Ev> base = ss.stream()
                .filter(x -> c.eventTime >= x.eventTime && c.eventTime - x.eventTime <= WINDOW)
                .findFirst();
            if (base.isPresent()) {
                matchedClick.add(c.id);
                emitted++;
                System.out.println("  JOIN " + base.get().id + " x " + c.id + " (session " + s + ")");
            }
        }
    }

    // Watermark passes window end: searches with no click expire as "unclicked".
    void closeWindow(long windowEnd) {
        for (var en : searches.entrySet())
            for (Ev s : en.getValue())
                if (s.eventTime < windowEnd && clicks.getOrDefault(en.getKey(), List.of()).stream()
                        .noneMatch(c -> matchedClick.contains(c.id) && c.eventTime - s.eventTime <= WINDOW)) {
                    unclicked++;
                    System.out.println("  EXPIRE " + s.id + " -> unclicked");
                }
    }

    // Correction path: a laggard inside allowed lateness revises the metric.
    void correct(Ev lateClick, String searchId) {
        matchedClick.add(lateClick.id); corrections++; unclicked--; emitted++;
        System.out.println("  CORRECTION " + searchId + " x " + lateClick.id + " (retract unclicked, republish clicked)");
    }

    public static void main(String[] a) {
        WindowedJoin j = new WindowedJoin();
        System.out.println("== 1. both arrival orders ==");
        j.on(new Ev("search", "s1", "q1", 5));   // search first
        j.on(new Ev("click", "s1", "c1", 12));
        j.on(new Ev("click", "s2", "c2", 20));   // click BEFORE its search
        j.on(new Ev("search", "s2", "q2", 18));
        System.out.println("== 2. watermark with an idle partition ==");
        j.watermarkTo(60, Set.of(2));            // partition 2 idle -> excluded, windows still close
        j.closeWindow(60);
        System.out.println("== 3. laggard inside lateness -> correction; outside -> drop ==");
        j.on(new Ev("search", "s3", "q3", 61));
        j.watermarkTo(125, Set.of());
        j.closeWindow(120);
        j.correct(new Ev("click", "s3", "c3", 70), "q3"); // inside lateness: revises q3 from unclicked to clicked
        j.on(new Ev("click", "s4", "c9", 3));            // far too late -> drop
        long denom = j.emitted + j.unclicked;
        System.out.println("emitted=" + j.emitted + " unclicked=" + j.unclicked
            + " corrections=" + j.corrections + " droppedLate=" + j.droppedLate);
        System.out.println("CTR(clicked searches / all searches) = " + j.emitted + "/" + denom);
        System.out.println("OK");
    }
}

پیگیری (سینیور): یه partition بیکار watermark رو نگه داره، پنجره‌ها رو چطور می‌بندی؟Follow-up (Senior): An idle partition holds back your watermark. How do you close windows safely?

بعد از timeout بیکاری کران‌دار پارکش کن: از کمینهٔ watermark کنارش بگذار، کنارگذاری رو متریک کن، به بستن پنجره‌ها ادامه بده و با داده برگردانش. هیچ‌وقت بی‌صدا صبر نکن و backlog پارک‌شده رو بدون بازپخش با زمان رویداد دور نریز.

Park it after a bounded idle timeout: pull it out of the watermark minimum, meter the exclusion, keep closing windows, and readmit it when data shows up. Never wait silently, and never throw the parked backlog away without replaying it by event time.

پیگیری (سینیور): اگه کلیک قبل از جستجو برسه، کدوم سو کجا صبر می‌کنه؟Follow-up (Senior): If the click arrives before the search, which side waits, and where exactly?

هر دو: کلیک توی لیست کلیکِ session می‌مونه و جستجو با رسیدن، probeاش می‌کنه. بافر دقیقاً دوسویه‌ست تا هیچ ترتیبی خاص نباشه. دمو q2×c2 رو join می‌کنه، با این‌که c2 اول رسیده بود.

Both of them: the click waits in the session's click list, and the search probes that list on arrival. The buffer is two-sided precisely so no order is special. The demo joins q2×c2 even though c2 showed up first.

پیگیری (استف): یه اصلاحیه بعد از crash دوباره تحویل می‌شه. متریک چطور exactly-once می‌مونه؟Follow-up (Staff): A correction gets redelivered after a crash. How does the metric stay exactly-once?

اصلاحیه‌ها writeهای نسخه‌دار idempotent با کلید (session, window, version) هستن: اصلاحیهٔ بازپخش‌شده همون نسخه رو حمل می‌کنه و همگرا می‌شه، و مخرج سر بستن منجمده تا بازپخش‌ها بادش نکنن. exactly-once متریک به writeهای idempotent sink به‌علاوهٔ بازپخش قطعی فروکاسته می‌شه — همون دو نگهبان تمرین ۱.

Corrections are idempotent versioned writes keyed by (session, window, version): a replayed correction carries the same version and converges, and the denominator is frozen at close so replays can't inflate it. Exactly-once for the metric reduces to idempotent sink writes plus deterministic replay — the same two guards as Exercise 1.

اشتباهات رایجCommon mistakes

  • بستن با processing time، یا با چند دقیقهٔ ثابتی که بدون اندازه‌گیری انتخاب شده. timeout صورت آزمایشگاه فقط یه نگهدارنده‌ست تا وقتی توزیع lateness جایگزینش بشه.
  • join چندبه‌چند که هر جفت کلیک-جستجو رو می‌شماره: CTR می‌ترکه، چون یه جستجو با سه کلیک سه بار شمرده می‌شه. اول‌کلیک-می‌برد (یا یه قاعدهٔ صریح که اعلامش کنی) متریک رو صادق نگه می‌داره.
  • بی‌خیال شدن بی‌صدا از دیررس‌ها. سهم انداخته‌شده یه متریکه با هشدار: چون رشدش یعنی بودجهٔ lateness اشتباه بوده، نه داده.
  • پنداشتن watermark به‌عنوان تضمین این‌که هیچ دیررسی نمیاد. اون آستانهٔ بستنه، و کل ماشین drop-یا-اصلاح دقیقاً به این خاطره که آستانه می‌تونه اشتباه باشه.
  • Closing by processing time, or by a fixed few minutes picked without measuring anything. The timeout in the lab brief is only a stand-in until your lateness distribution replaces it.
  • A many-to-many join that counts every click-search pair: the CTR explodes, because one search with three clicks counts three times. First-click-wins (or some other rule you state out loud) keeps the metric honest.
  • Dropping laggards silently. The dropped share is a metric with an alert attached, because a growing late fraction means your lateness budget — not your data — was wrong.
  • Treating the watermark as a guarantee that nothing late will ever come. It's a threshold for closing, and the whole drop-or-correct machinery exists precisely because that threshold can be wrong.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

بذار ساده بگم: business و outbox رو تو یه تراکنش ثبت کن، و با پروتکل snapshot سازگارِ connector، state کامل رو همراه مرز logِ قابل‌بازپخش بساز. بعد از نصب snapshot، تغییرها رو به‌ترتیبِ هر entity اعمال کن: event_id برای dedup و entity_version برای جلوگیری از عقب‌رفتن. event topic تاریخ وقایع رو با retention نگه می‌داره؛ state topic اختیاری با کلید entity و tombstone، قرارداد دیگه‌ست. هزینهٔ snapshot و WAL رو بودجه‌بندی و اندازه‌گیری کن — فشار صفر و تازگی همیشگی تضمین نیستن.
Honestly, the shape is simple: commit the business rows together with their outbox records, and use a supported consistent snapshot/log-boundary protocol to get the complete state plus the replayable changes. Install the snapshot, then apply per-entity ordered changes with event-ID dedup and entity-version regression guards. The retained event history and an optional compacted entity-state topic have different contracts. Budget and measure the snapshot/WAL costs — zero load and perpetual freshness are not guarantees.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن یه پایگاه دادهٔ مرجع تراکنشی داریم با لاگ replication منطقی (آموزشی و شبه Postgres) و یه بروکر لاگ‌محور با compaction و retention. مقیاس آموزشی: ۵۰M سطر، snapshot مهار‌شده با ۲۰k سطر بر ثانیه و WAL با نگهداری ۳ روز — اعداد آموزشی‌ان، نه بنچمارک.
  • ایندکسر idempotent است و هیچ state‌ای نداره که مرجع نتونه بازسازی‌ش کنه. مصرف‌کننده‌های پایینِ ایندکس اصلاحیه‌های نسخه‌دار رو تاب می‌آورن، ولی خود ایندکس باید به مرجع همگرا بشه.
  • برای شروع، از snapshot پشتیبانی‌شدهٔ connector استفاده می‌کنیم. انتقال snapshot به replica فقط وقتی مجازه که نسخه پشتیبانی بشه و مرز‌های snapshot/LSN هماهنگ باشن؛ بار replica و WAL همچنان هزینه دارن.
  • Picture a transactional record database with a logical replication log (teaching, Postgres-like) and a log-based broker with compaction and retention. Teaching scale: 50M rows, a throttled snapshot at 20k rows/s and a WAL retained for 3 days — teaching numbers, not benchmarks.
  • The indexer is idempotent and owns no state the record can't rebuild. Consumers downstream of the index tolerate versioned corrections, but the index itself has to converge to the record.
  • To start, use the connector-supported snapshot protocol. Moving a snapshot to a replica is only allowed with version support and coordinated snapshot/LSN boundaries — and the replica load and the WAL still cost you.

چرا این روش و این عددها؟Why this method and these numbers?

۵۰میلیون سطر ÷۲۰هزار سطر/ثانیه =۲۵۰۰ ثانیه، حدود ۴۱٫۷ دقیقه؛ این حدِ پایینِ آموزشی، بدون overhead و بدون تغییرهای هم‌زمانه. سه روز WAL فقط وقتی کافیه که زمان snapshot+قطعی+catch-up+حاشیه ازش کمتر بشه و حجم دیسک هم جواب بده. snapshot هزینهٔ IO و نگهداری نسخه داره، حتی روی replica. مرز LSN از پروتکل snapshot سازگار میاد؛ event_id تکرارِ همون رویداد رو می‌گیره و entity_version جلوی عقب‌رفتن state رو. compaction برحسب key کار می‌کنه و جای snapshot کاملِ مرجع یا تاریخ وقایع رو نمی‌گیره.

50M rows / 20k rows/s = 2500 seconds, about 41.7 minutes — a teaching lower bound, before overhead and before concurrent changes. Three-day WAL retention is enough only if snapshot + outage + catch-up + margin fit inside it and the disk has room. A snapshot costs I/O and version retention even on a replica. LSN boundaries come from the consistent snapshot protocol; event IDs dedup the repeated event, and entity versions stop the state from regressing. Key-based compaction replaces neither the complete record snapshot nor the event history.

حل گام‌به‌گامStep by step

  1. یک تراکنش، یه قرارداد پایدار business و outbox رو یکجا ثبت کن؛ payload نسخه‌دار، event_id، entity_key و entity_version دارن. تغییرِ ستون داخلی فقط وقتی بیرون رو نمی‌شکنه که تبدیلِ payload سازگار هم توی همون rollout حفظ بشه.
  2. snapshot با مرز snapshot و مرز B رو با پروتکل رسمیِ connector هماهنگ کن؛ یه SELECT عادی با LSNی که زمانی دیگه خونده شده کافی نیست. نرخ snapshot رو زیر بودجهٔ IO و lag مهار کن.
  3. catch-up با dedup بعد از نصب snapshot، تغییرهای از مرز سازگار رو catch-up کن؛ event_id تکرارِ رویداد و entity_version بازپخشِ کهنه رو مهار می‌کنن. ولی توی یه state snapshot نمی‌دونیم کدوم event_idهای قبلی حضور دارن، و dedup شناسه به‌تنهایی snapshot overlap رو حل نمی‌کنه.
  4. سه قرارداد، جدا از هم سه قرارداد رو جدا نگه دار: snapshot یک‌بارمصرف، تاپیک append-only رویداد با کلید event id زیر retention، و تاپیک فشردهٔ state با کلید entity key که tombstoneها تا مشاهده می‌مونن. دفترچهٔ پاره هیچ‌وقت seed نمی‌کنه.
  5. پذیرش با kill ـه test با kill اثباتش کن: ایندکسر رو وسط catch-up نگه دار، ادامه بده و ایندکس رو در برابر مرجع، در مرز اعلام‌شده، checksum بگیر. نگهداری WAL رو پهن‌تر از کندترین bootstrap نگه دار و عکس رو مهار کن — وگرنه بلند re-snapshot بگیر.
  1. One transaction, one stable contract Commit the business row and the outbox row together, with a versioned payload, an event ID, an entity key and an entity version. An internal column change only leaves consumers alone when the compatible payload mapping is maintained through the rollout.
  2. Snapshot with a boundary Line up the snapshot and boundary B through the supported connector protocol; an ordinary SELECT with an independently sampled LSN isn't enough. Throttle the snapshot work against your I/O and lag budgets.
  3. Catch up with dedup Once the snapshot is installed, catch up from the consistent boundary. Event IDs dedup the repeated events; entity versions reject a stale replay. But a state snapshot doesn't list the historical event IDs, so event-ID dedup alone can't resolve the snapshot overlap.
  4. Three contracts, kept apart Keep the three contracts apart: the one-off snapshot, the append-only event topic keyed by event id under retention, and the compacted state topic keyed by entity key, where tombstones linger until someone observes them. A purged diary never seeds anybody.
  5. Acceptance by kill test Prove it with a kill: stop the indexer mid-catch-up, resume, and checksum the index against the record at a stated boundary. Keep WAL retention wider than the slowest bootstrap, and throttle the photo — or take a loud re-snapshot.

طراحی مشخصConcrete design

outbox(event_id UUID PK,entity_key,entity_version,type,payload) همراه سطر business commit می‌شه. توی این طرح، رویدادها با entity_key پارتیشن می‌شن تا ترتیبِ همون entity حفظ بشه، و event_id توی payload/header برای dedup می‌مونه؛ کلید event_id هم ممکنه، ولی ترتیب entity رو به یه پروتکل جدا نیاز داره. state topic اختیاری با entity key و null tombstone، آخرین state هر entity رو نگه می‌داره. compaction روی کلید یکتای هر event معمولاً فضا کم نمی‌کنه.

snapshot کاملِ مرجع و مرز B باید از یه پروتکل سازگار بیان؛ snapshot خودِ outboxِ purgeشده state کامل نیست. بعد از bulk-load، تغییرها به‌ترتیب و با version guard اعمال می‌شن. retention لاگ باید snapshot+قطعی+catch-up رو با حاشیه پوشش بده؛ اگه تاریخ لازم از دست رفت، بازسازی صریح لازمه. و checksum فقط بین stateهای یه مرز معتبر مقایسه می‌شه.

Commit outbox(event_id UUID PK,entity_key,entity_version,type,payload) together with the business rows. This design partitions the events by entity_key so the order of each entity survives, and it carries event_id in the payload/headers for dedup. Event-ID keys are also possible, but then the entity order needs a separate protocol. The optional compacted entity-keyed state topic uses null tombstones. Compaction over unique event keys usually saves no space.

Get the complete record snapshot and the boundary B from one consistent protocol; a snapshot of a purged outbox is incomplete state. Bulk-load first, then apply the ordered changes under version guards. Retention has to cover snapshot + outage + catch-up with some margin, and if the needed history is gone you need an explicit rebuild. Compare checksums only at a valid shared boundary.

پاسخ: تاپیک فشردهٔ entity-state، تا وقتی هنوز هر کلید رو نگه داشته، یا یه snapshot مهارشدهٔ تازه — هرگز outbox پاک‌شده، که صفر رویداد بازپخش می‌کنه.

Every outbox row older than a week is purged. So where does a brand-new consumer get its complete state?

Answer: The compacted entity-state topic, as long as it still holds every key — or a fresh throttled snapshot. Never the purged outbox: it replays zero events.

گزینه‌های جایگزینAlternatives

  • CDC مستقیمِ جدول، بدون outbox (Debezium روی جدول‌های دامنه): روز اول با صفر تغییر کد می‌بری. ولی همین که یه ستون داخلی حذف بشه، می‌بازی — چون اسکیمای داخلی حالا API عمومیه و یه مصرف‌کنندهٔ پروداکشن، سمت مشتری، می‌ترکه.
  • نوشتن دوگانه از کد اپ (اول پایگاه داده، بعد ایندکس): روی هر دو خطای §۴.۱ می‌بازه — مسابقهٔ ترتیب بدون هیچ خطایی، و جفتِ نیم‌commitشده. این‌جا فقط به‌عنوان آنتی‌پترنی که outbox جایگزینش می‌شه نگه داشته شده.
  • ETL دسته‌ای دوره‌ای به ایندکس: روی سادگی و کاتالوگ‌های کوچک می‌بره. تازگی رو می‌بازه (کهنه تا اجرای بعد) و هر اجرا تاریخ رو بیهوده بازپخش می‌کنه.
  • Direct table CDC with no outbox (Debezium on the domain tables): you win on day one with zero code changes. You lose the moment an internal column drops, because the internal schema is public API now — and a production consumer breaks, customer side.
  • Dual writes straight from application code (database, then index): it loses on both faults of §4.1 — the ordering race that throws no error at all, and the half-committed pair. It's kept here only as the anti-pattern the outbox replaces.
  • Periodic batch ETL into the index: it wins on simplicity and on tiny catalogs. It loses freshness (stale until the next run) and it replays history for nothing on every run.

سناریوهای خرابیFailure scenarios

  • شکاف snapshot/استریم: snapshot مرز LSN ـه B رو ثبت می‌کنه و جاری‌سازی از همون‌جا شروع می‌شه؛ چیزی جا نمی‌مونه. هم‌پوشانی بازپخش می‌شه و dedup ـه event-ID جذبش می‌کنه (دمو: e3 دوبار اعمال می‌شه، بی‌اثر).
  • تکراری snapshot/استریم: همون هم‌پوشانی، همون dedup — نگهبان همون event idـه، و بازپخش دوبارهٔ مرز همگرا می‌شه به‌جای دو برابر شدن.
  • kill وسط bootstrap: ایندکسر از checkpoint ادامه می‌ده، بازپخش و dedup می‌کنه و checksum مرز ثابت می‌کنه که دو طرف همگرا شدن (بخش ۲ دمو: یه skip و match درست).
  • حذف ستون داخلی: رله قرارداد outbox رو می‌خونه، نه جدول‌های دامنه رو — پس پایپ‌لاین سبز می‌مونه و هیچ‌کس page نمی‌شه.
  • گم شدن tombstone قبل از این‌که همهٔ دنباله‌روها ببیننش: حذف روی عقب‌مانده زنده می‌شه، پس نگهداری tombstone باید از lag کندترین دنباله‌رو به‌علاوهٔ حاشیه بیشتر باشه.
  • purge ـه outbox قبل از رسیدن تازه‌وارد: دفترچه هیچ‌کسی رو seed نمی‌کنه، و تازه‌وارد یا تاپیک فشردهٔ entity-state رو می‌خونه یا یه snapshot مهارشدهٔ تازه می‌گیره — بلند تصمیم می‌گیری، نه با حدس.
  • فشار بی‌کرانِ snapshot: خواندن‌ها از replica میان با نرخ سقفی و بودجهٔ اعلام‌شده میان (آموزشی ۲۰k سطر بر ثانیه) و بودجهٔ منفجرشده snapshot رو کند می‌کنه — هیچ‌وقت رهبر رو نه.
  • Snapshot/stream gap: the snapshot records LSN B and the stream starts right there, so nothing is missed. The overlap replays, and event-ID dedup swallows it (demo: e3 applies twice, harmlessly).
  • Snapshot/stream duplicate: the same overlap, the same dedup — the guard is the event id, so replaying the boundary twice converges instead of doubling the count.
  • Kill mid-bootstrap: the indexer picks up from its checkpoint, replays, dedups, and the boundary checksum proves the two sides converged (demo part 2: one skip, match true).
  • Internal column dropped: the relay reads the outbox contract and never the domain tables, so the pipeline stays green and nobody gets paged.
  • Tombstone lost before every follower observed it: the delete comes back to life on the laggard, so tombstone retention has to beat the slowest follower's lag plus a margin.
  • Outbox purged before a newcomer arrives: the diary can't seed anybody, so the newcomer reads the compacted entity-state topic or triggers a fresh throttled snapshot — decided loudly, never by guessing.
  • Unbounded snapshot pressure: the reads come from a replica at a capped rate with a stated budget (teaching 20k rows/s), and a blown budget slows the snapshot down — never the leader.

کد قابل اجراRunnable code

اجراشده و تأییدشده در همین محیطExecuted and verified in this environment

این کد آموزشی و ساده‌سازی‌شده است؛ فقط برای آشنایی با ایده. کد واقعی پروداکشن ملاحظات بسیار بیشتری دارد و هیچ‌کس این‌شکلی کد پروداکشن نمی‌زند.Simplified teaching code for building intuition only — not production code; nobody ships production code like this.

import java.util.*;

// Single-thread, in-memory teaching model. Snapshot+LSN is atomic by construction.
// A real connector must supply a consistent snapshot/log-boundary protocol.
// No real Kafka, database throttling or durable process crash is tested here.
public class CdcBootstrap {
    record Event(String eventId, String key, String value, long version) {}
    Map<String,String> record=new LinkedHashMap<>(), index=new LinkedHashMap<>();
    Map<String,Long> versions=new HashMap<>(); // includes tombstone versions
    List<Event> events=new ArrayList<>();
    Set<String> dedup=new HashSet<>();
    long lsn=0, snapshotBoundary=-1;
    void write(String key,String value) {
        lsn++;
        if(value==null) record.remove(key); else record.put(key,value);
        events.add(new Event("e"+lsn,key,value,lsn));
    }
    void snapshot() {
        // No concurrent writes in this model: source state and boundary agree.
        snapshotBoundary=lsn;
        index.clear(); index.putAll(record); versions.clear(); dedup.clear();
        for(String key:index.keySet()) versions.put(key,snapshotBoundary);
    }
    void apply(Event event) {
        // A snapshot has state, not old event IDs; guard old overlap by boundary.
        if(event.version<=snapshotBoundary || dedup.contains(event.eventId)) return;
        if(event.version>versions.getOrDefault(event.key,-1L)) {
            if(event.value==null) index.remove(event.key); else index.put(event.key,event.value);
            versions.put(event.key,event.version);
        }
        dedup.add(event.eventId); // apply+version+dedup are one modeled sink step
    }
    void catchUp(int stopAfter) {
        int applied=0;
        for(Event event:events) {
            if(event.version<=snapshotBoundary || dedup.contains(event.eventId)) continue;
            apply(event);
            if(++applied==stopAfter) return; // simulated consumer pause
        }
    }
    void check(boolean condition) { if(!condition) throw new AssertionError(); }
    public static void main(String[] args) {
        CdcBootstrap c=new CdcBootstrap();
        c.write("p1","red boots"); c.write("p2","blue coat"); c.write("p3","green hat");
        c.snapshot(); // B=3
        c.write("p2","navy coat"); c.write("p3",null);
        c.catchUp(1); // pause with only e4 applied, then resume from modeled sink state
        c.check(!c.index.equals(c.record));
        c.catchUp(Integer.MAX_VALUE); c.check(c.index.equals(c.record));
        c.apply(c.events.get(2)); // old pre-snapshot row must not resurrect deleted p3
        c.check(!c.index.containsKey("p3"));
        c.catchUp(Integer.MAX_VALUE); c.check(c.index.equals(c.record));
        c.write("p1","v6"); Event old=c.events.get(c.events.size()-1);
        c.write("p1","v7"); Event newer=c.events.get(c.events.size()-1);
        c.apply(newer); c.apply(old); c.apply(newer);
        c.check(c.index.get("p1").equals("v7"));
        c.check(c.index.equals(c.record));
        Map<String,String> stateTopic=new HashMap<>(c.record); // full current-state model
        List<Event> purgedHistory=List.of();
        c.check(purgedHistory.isEmpty() && !c.record.isEmpty());
        c.check(stateTopic.equals(c.record));
        System.out.println("PASS snapshot B=3, pause/resume, duplicate, stale overlap, version regression, tombstone");
        System.out.println("PASS purged events cannot seed full state; index="+c.index);
    }
}

آزمون صحت و معیار عملیاتیCorrectness checks and operational criteria

پذیرش: ایندکسر رو وسط catch-up بکش و lag-تا-صفر به‌علاوهٔ تطبیق checksum مرز رو بخواه؛ یه ستون داخلی حذف کن و سبز ماندن پایپ‌لاین رو بخواه؛ outbox رو purge کن و بخواه ران‌بوک تازه‌وارد آن رو به‌عنوان seed رد کنه. متریک‌ها: lag سرتاسری، نرخ خواندن snapshot در برابر بودجه، سن tombstone در برابر کندترین دنباله‌رو و نرخ skipـه dedup. گام‌های واقعی Debezium/Kafka این‌جا فقط راهنما هستن.

Acceptance: kill the indexer mid-catch-up and demand lag-to-zero plus a boundary checksum match; drop an internal column and demand that the pipeline stays green; purge the outbox and demand that the newcomer runbook refuses it as a seed. Metrics: end-to-end lag, snapshot read rate against budget, tombstone age against the slowest follower, and the dedup-skip rate. Real Debezium/Kafka steps are guide-only here.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): سطرهای قدیمی outbox که purge شدن، مصرف‌کننده جدید state کامل رو از کجا می‌سازه؟Follow-up (Staff): Old outbox rows have been purged. Where does your new consumer get complete state?

تاپیک فشردهٔ entity-state، تا وقتی هر کلید رو نگه داشته — یا یه snapshot مهارشدهٔ تازه. هرگز outbox پاک‌شده: retention اون صفحه‌ها رو انداخته، و بازپخشش تاریخی پنیرسوییسی می‌سازه. شکل نوار دقیقاً به‌خاطر همین گذاشته شده که این اشتباه ناشدنی بشه.

The compacted entity-state topic, as long as it still retains every key — or a fresh throttled snapshot. Never the purged outbox: retention already dropped those pages, so replaying it rebuilds a history full of holes. The strip figure exists to make exactly this mistake unmakeable.

پیگیری (سینیور): کدوم‌یک از دو تاپیک باید log-compact بشه و چرا فشرده کردن اون یکی غلطه؟Follow-up (Senior): Which of the two topics should be log-compacted, and why is compacting the other one the wrong call?

تو این طرح، state topic با entity key از compaction سود می‌بره، چون قراردادش آخرین state رو می‌خواد. ولی event topic باید همهٔ وقایع داخل retention رو نگه داره، و compaction با entity key می‌تونه اون history لازم رو پاک کنه. اگه کلید event_id یکتا باشه، compaction معمولاً چیزی حذف نمی‌کنه — و قطعاً history رو خودکار از بین نمی‌بره.

The entity-keyed state topic profits from compaction, because its contract asks for the latest state. Event history has to keep every event inside the supported window, and entity-key compaction can erase that history. With unique event-ID keys, compaction generally removes nothing — it certainly doesn't delete history for you.

پیگیری (استف): دو سازندهٔ ایندکس هنگام مهاجرت هم‌زمان می‌دونن. کی خواندن سرو می‌کنه و با kill چی می‌مونه؟Follow-up (Staff): Two index builders run at once during a migration. Who serves the reads, and what survives a kill?

دو ایندکسر می‌تونن هم‌زمان بسازن (ایندکس آبی-سبز)، ولی به‌ازای هر alias فقط یکی مالک سرو خواندنه و هر دو مستقل checkpoint می‌گیرن: kill یکی، اون یکی رو عقب نمی‌بره. cutover بعد از checksum مرز alias رو می‌چرخونه و rollback برمی‌گردونه — سوییچ اتمیک، aliasـه نه داده.

Two indexers may build side by side (a blue-green index), but only one of them owns the serving reads per alias, and both checkpoint independently: a kill on one never rewinds the other. Cutover flips the alias after the boundary checksum, and rollback flips it back — the alias, not the data, is the atomic switch.

اشتباهات رایجCommon mistakes

  • seed کردن تازه‌وارد از outbox پاک‌شده: retention اون صفحه‌ها رو انداخته، و بازپخش تاریخ ناقص می‌سازه و کلیدهای گمشده بی‌صدا می‌شکنن. outbox دفترچه‌ست، نه دفتر تلفن.
  • فشرده کردن تاپیک رویداد outbox با کلید entity برای «صرفه‌جویی جا»: تاریخی رو نابود می‌کنه که مصرف‌کننده‌های دیگه می‌خوان، و یه کپی per-entity نگه می‌داره — بدترینِ هر دو قرارداد با هم.
  • snapshot بدون ثبت مرز LSN: استریم بعد از یه حدس شروع می‌شه و سؤالِ شکاف-یا-تکراری دیگه جواب صادق نداره.
  • خوندن جدول‌های داخلی با CDC، انگار قرارداد پایداری هستن. اولین ستونِ حذف‌شده، نصف‌شب، به مصرف‌کنندهٔ پروداکشن page می‌زنه.
  • فرض این‌که فشار snapshot صفره: export انبوهِ مهارنشده با رهبر رقابت می‌کنه و قطعی‌ای که می‌سازه، خودزده‌ست.
  • Seeding a newcomer from the purged outbox: retention already dropped those pages, so the replay rebuilds a partial history and the missing keys fail silently. The outbox is a diary, not a phone book.
  • Compacting the outbox event topic by entity key to 'save space': it destroys the history other consumers need while keeping one copy per entity — the worst of both contracts at once.
  • Snapshotting without recording the LSN boundary: the stream then starts from a guess, and the gap-or-duplicate question has no honest answer left.
  • Reading internal tables through CDC as if they were a stable contract. The first dropped column pages a production consumer at night.
  • Assuming snapshot pressure is zero: an unthrottled bulk export contends with the leader, and the outage it causes is one you inflicted on yourself.
