سؤال مصاحبهInterview question
فرض کن API انتقال بین دو حساب داری. request ID رو از client تا DB ببر. payload و نتیجه رو به ID بچسبون؛ UNIQUE، debit و credit و log باید اتمیک باشن. پاسخ commit گم‌شده و retry رو تحلیل کن و projection موجودی رو مستقل از log بساز.
Picture this, you're designing a transfer API between two accounts. You carry a request ID end to end, from client to DB. You bind payload and result to that ID; your UNIQUE constraint, debit and credit, and log commit together. You handle the lost commit response plus retry, and you rebuild balance projections independently from the log.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که: سطر درخواست را با UNIQUE(request_id) اول می‌نویسی، در همان تراکنشی که بستانکاری و سطر لاگ ورودی را commit می‌کند؛ payload و نتیجه را هم به همان شناسه bind می‌کنی. از این به بعد، retry با همان شناسه فقط نتیجهٔ ذخیره‌شده را برمی‌گرداند و پول تکان نمی‌خورد؛ همان شناسه با payload تازه رد می‌شود؛ همان payload با شناسهٔ تازه یک انتقال عمدی تازه است. بالانس‌ها را فقط از لاگ بازسازی کن تا خودِ replay سندِ درستی‌اش را امضا کند. تریدآف هم روشن است: یک سطر نوشتن اضافه و رقابت UNIQUE به‌ازای هر شناسه، در برابر اثر دقیقاً-یک‌بار روی تحویلِ حداقل-یک‌بار. — کل بازی سرِ همین یک شناسه است، نه سرِ پول.
Here's the thing: write the request row FIRST under UNIQUE(request_id), inside the very transaction that commits the debit, the credit and the input-log row, and bind the payload and the result to that same ID. From then on, a retry with the same ID only returns the stored result and no money moves; the same ID with a new payload is rejected; the same payload with a new ID is a new intentional transfer. Rebuild the balances from the log alone so the replay signs its own correctness. The trade-off: one extra row write and UNIQUE contention per ID, in exchange for an exactly-once effect over at-least-once delivery. — the whole game is played on that one ID, not on the money.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن دامنه تک‌دفترکله: هر دو حساب توی یه پایگاه داده‌ان، پس یه تراکنش می‌تونه درخواست و حرکت‌ها و لاگ رو bind کنه. legهای بین‌سیستمی تمرین ۳ است.
  • اعداد آموزشی: A=1000 و B=500 و req-7 دویست واحد می‌بره. اعداد کوچک بررسی replay رو خوانا نگه می‌دارن؛ بنچمارک نیستند.
  • قضیه اینه که: تحویل حداقل-یک‌باره — پاسخ می‌تونه گم بشه، کلاینت‌ها با همون شناسه retry می‌کنن، و رسیدن هم‌زمانِ تکراری‌ها هم ممکنه.
  • و یه قانون ساده: به‌ازای هر نیت کاربر یه شناسه، ساختهٔ کلاینت (UUID). سرور برای retryهای کلاینت شناسه نمی‌سازه.
  • Picture the scope: single-ledger. Both accounts live in one database, so one transaction can bind the request, the moves and the log. The cross-system legs are exercise 3.
  • The teaching numbers: A=1000, B=500, and req-7 moves 200. Small integers keep the replay check readable — they are not benchmarks.
  • Here's the thing: delivery is at-least-once. A reply can get lost, clients retry with the same ID, and duplicates can arrive at the same time.
  • One ID per user intent, generated by the client (UUID). The server never invents an ID for client retries.

چرا این روش و این عددها؟Why this method and these numbers?

request_id هویت intent کاربر است و در retry ثابت می‌ماند؛ hash payload هم جلوی استفادهٔ همان ID برای intent متفاوت را می‌گیرد. دو حساب در یک DB هستند تا debit و credit و نتیجه در یک تراکنش commit شوند؛ جمع ۱۰۰۰+۵۰۰=۱۵۰۰ باید پس از انتقال ۲۰۰ ثابت بماند. این اعداد کوچک‌اند تا invariant را با چشم ببینی، نه با حدس. دو DB مستقل این مرز اتمیک را ندارند و طراحی چندshardی می‌خواهند — و آن، بحثِ یک طراحیِ دیگر است.

A request ID identifies user intent and stays fixed across retries; a payload hash catches you reusing it for a different intent. Both accounts share a database so the debit, the credit and the result commit together. The initial 1000+500=1500 stays conserved after moving 200; the small numbers let you eyeball the invariant instead of trusting it. Independent databases don't share that atomic boundary — and reaching past it is a different design problem.

مدل ذهنیMental model

فرض کن یه اداره پست با دفتر رسید داری: هر نامه پیش از آن‌که پولی تکان بخوره یک رسید شماره‌دار می‌گیرد، و روی همان رسید از قبل نوشته شده نتیجه چیست. کپی رسید گم بشه، پول دوباره راه نمی‌افته — کارمند شماره را پیدا می‌کند و همان رسید را دوباره می‌دهد. نامهٔ متفاوت شمارهٔ تازه می‌خواهد؛ همان شماره روی نامهٔ متفاوت جعل است و رد می‌شود. — رسید خودِ نامه نیست؛ رسید کاری می‌کند که نامه تکرارناپذیر شود.
Picture a post office with a receipt book: every letter gets a numbered receipt BEFORE any money moves, and the receipt already names the result. Lose the copy of a receipt and the money never goes out twice — the clerk looks up the number and hands over the same receipt again. A different letter needs a new number; the same number on a different letter is forgery and gets rejected. — the receipt isn't the letter; the receipt is what makes the letter un-repeatable.

حل گام‌به‌گامStep by step

  1. سطر اول، یک‌بار commit بذار ساده بگم: یک تراکنش باز می‌کنی، اول سطر درخواست را INSERT می‌کنی، بعد بدهی و بستانکاری و سطر لاگ را می‌افزایی و آخرش commit می‌کنی. یکتایی و حرکت پول و لاگ یک سرنوشت اتمی دارند: یا هر سه، یا هیچ‌کدام.
  2. پاسخ گمشده می‌شود یک lookup حالا بریم سراغ بدترین حالت: commit موفق شد ولی پاسخ روی سیم مرد. کلاینت نمی‌تواند commit را از شکست تشخیص دهد، پس تنها حرکت امن این است که با همان شناسه و همان payload دوباره retry می‌کند. این retry به conflict یکتایی می‌خورد و مستقیم می‌رود سراغ سطر ذخیره‌شده، و نتیجه عیناً برمی‌گردد. همان شناسه با payload عوض‌شده رد می‌شود؛ همان payload با شناسهٔ تازه پذیرفته می‌شود، چون نیت تازه است.
  3. replay دفترکل را راستی‌آزمایی می‌کند ببین، یک مصرف‌کنندهٔ جدا فقط ستون لاگ ورودی را می‌خواند و هر بالانس را از نو می‌سازد. اگر replay در یک آفست با حالت زنده فرق کند، آن باگ projection است نه lag — و خط OK پایانی دمو دقیقاً همین بررسی است. — اینجاست که حرف‌ها به عدد تبدیل می‌شوند.
  1. Insert the row, one commit One transaction, that's all: you INSERT the request row first, then debit, credit and append the log row, and you commit at the end. Uniqueness, money movement and the log share one atomic fate — all three or none.
  2. A lost reply becomes a lookup Now the nasty case: the commit succeeded but the reply died on the wire. The client cannot tell commit from failure, so the only safe move is to retry with the same ID and the same payload. That retry trips the UNIQUE conflict and lands on the stored row, whose result comes back verbatim. The same ID with a changed payload is rejected; the same payload under a new ID is honored, because that is a new intent.
  3. Replay audits the ledger And a separate consumer reads only the input-log column and rebuilds every balance from scratch. If the replay ever differs from live state at the same offset, that is a projection bug, not lag — the demo's final OK line is exactly this check. — this is where the talk turns into numbers.

طراحی مشخصConcrete design

جدول‌ها: requests(request_id PK, payload, status, result) و accounts(id, balance) — و ستون درخواست‌ها هم‌زمان نقش لاگ ورودی را هم بازی می‌کند. API: POST /transfers {request_id, from, to, amount} که 200 {result} می‌دهد، برای استفادهٔ دوبارهٔ شناسه با payload متفاوت 409 می‌دهد، و 202 pending می‌دهد وقتی دوقلوی هم‌زمان هنوز دارد کار می‌کند. مسیر نوشتن: BEGIN، درج سطر درخواست، چک موجودی، UPDATE هر دو حساب، ذخیرهٔ نتیجه، COMMIT — همه در یک تراکنش. مسیر خواندن: خواندن‌های صورت‌حساب از نمای بالانسِ بازسازی‌شده از لاگ می‌آیند، یعنی ممکن است با تأخیر کران‌دار و اندازه‌گیری‌شده از commit عقب باشند. — یک سطر بیشتر و یک تراکنش کمتر: همین، تمام طراحی است.

Tables: requests(request_id PK, payload, status, result), accounts(id, balance), and the requests column doubling as the input log. API: POST /transfers {request_id, from, to, amount} hands back 200 {result}, answers 409 when the same ID comes back with a different payload, and answers 202 pending while a concurrent twin is still working. Write path: BEGIN, INSERT request row, check funds, UPDATE both accounts, result stored, COMMIT — all of it one transaction. Read path: statement reads come from the balance view rebuilt from the log; they may lag the commit by a bounded, measured delay. — one extra row, one less transaction; that's the whole design.

مثال محاسبه‌شدهWorked example

اجرای آموزشی با A=1000 و B=500. req-7 دویست واحد می‌برد: commit پاسخ می‌دهد (بعد پاسخ را می‌اندازند) و retry با DEDUP برمی‌گردد و بالانس‌ها همان ۸۰۰/۷۰۰ می‌مانند. استفادهٔ دوبارهٔ req-7 برای ۹۹۹ رد می‌شود. req-8 تازه با همان payload دویست پذیرفته می‌شود: بالانس‌ها ۶۰۰/۹۰۰. replay مستقل از لاگ هم ۶۰۰/۹۰۰ می‌دهد — برابر، یعنی OK. — پول یک بار حرکت کرد؛ بقیه‌اش فقط اثبات است.

Teaching run with A=1000, B=500. req-7 moves 200: the commit replies (then the reply is dropped), the retry returns DEDUP with the balances still 800/700. Reusing req-7 for 999 is REJECTED. A fresh req-8 with the same 200 payload is honored: balances 600/900. The independent replay from the log gives 600/900 — equal, so OK. — the money moved once; everything after that is just proof.

نقطهٔ تصمیم: قید UNIQUE کار را راحت می‌کند: retry تبدیل به lookup کلید می‌شود — conflict یعنی سطر ذخیره‌شده را بخوان، هرگز به بالانس‌ها دست نزن.

رد خرابی: باگ کلاینت را روی همان شکل دنبال کن: اگر retry شناسهٔ تازه می‌آورد، INSERT دوم موفق می‌شد و پول دوبار می‌رفت — دفترکل وقتی کلاینت کلید را عوض کند، retry را از نیت تازه تشخیص نمی‌دهد. payload یکسان کلید تکراریابی نیست؛ شناسه است.

تضمین نشان‌داده‌شده: شکل نشان می‌دهد یک شناسه در ثبت و گم‌شدن و retry فقط یک بار اعمال می‌شود. جلوی پرداخت عمدی دوبار با دو شناسه را نمی‌گیرد.

تضمین نشان‌نداده‌شده: دربارهٔ legهای بین‌سیستمی (تمرین ۳) و این‌که نمای بالانس چقدر می‌تواند عقب باشد چیزی نمی‌گوید — تازگی، قرارداد جداست.

Decision point: The UNIQUE constraint turns a retry into a key lookup: a conflict means read the stored row, never touch the balances.

Failure trace: Trace the client bug on the same figure: if the retry carried a NEW id, the second INSERT would succeed and the money would move twice — the ledger can't tell a retry from a new intent once the client changes the key. The same payload is not the dedup key; the ID is.

Guarantee shown: The figure shows one ID applied exactly once across submit, loss and retry. It does not stop a user from paying twice on purpose with two IDs.

Not shown: It says nothing about cross-system legs (exercise 3) or how far the balance view may lag — freshness is a separate contract.

خودآزماییSelf-check

یک retry می‌رسد درحالی‌که تلاش اول شاید commit شده باشد شاید نه. API قبل از دست زدن به بالانس‌ها چه می‌کند؟

پاسخ: قبل از دست زدن به بالانس‌ها سطر درخواست را INSERT (یا conflict-check) می‌کند؛ روی conflict، برای payload یکسان نتیجهٔ ذخیره‌شده را برمی‌گرداند یا payload عوض‌شده را رد می‌کند.

A retry arrives while the first attempt may or may not have committed. What does the API do before it touches the balances?

Answer: INSERT (or conflict-check) the request row before touching the balances; on a conflict, return the stored result for the same payload, or reject a changed payload.

کل نخ را چپ‌به‌راست بخوان: نوشتن (کلاینت ثبت و retry می‌کند)، commit (API با INSERT-first)، ثبت (دفترکل)، replay (کار مستقلی که بالانس‌ها را بازمی‌سازد) و خواندن (خواندن‌های صورت‌حساب که ممکن است عقب باشند).
Read the whole thread left to right: Write (the client submits and retries), Commit (the INSERT-first API), Record (the ledger), Replay (the independent job rebuilding balances), Read (statement reads that may lag).
  1. کلاینت به API: ثبت با retryهای همان شناسه؛ API به دفترکل: یک تراکنش اتمی برای درخواست و حرکت‌ها و لاگ؛ دفترکل به API: commit موفق یا سطر ذخیره‌شده روی conflict.
  2. دفترکل به کار replay: سطرهای لاگ به‌ترتیب؛ کار به نمای بالانس: بالانس‌های بازمحاسبه‌شده فقط از لاگ — بدون یک ذره ورودی تازه.
  3. نمای بالانس به خواندن‌های صورت‌حساب: خواندن‌های سروشده که ممکن است با تأخیر کران‌دار از commit عقب باشند — تازگی اندازه‌گیری می‌شود، نه فرض.
  1. Client to API: the POST plus same-id retries; API to Ledger: one atomic txn of request plus moves plus log; Ledger back: commit ok, or the stored row on a conflict.
  2. Ledger to Replay job: the log rows in order; job to Balance view: recomputed balances from the log alone — not a drop of fresh input.
  3. Balance view to statement reads: the served reads, which may lag the commit by a bounded delay — freshness is measured, not assumed.

نقطهٔ تصمیم: یک commit اتمی و دو مصرف‌کننده: پاسخ کلاینت سطر ذخیره‌شده را می‌خواند، کار replay سطرهای لاگ را. هیچ‌کدام ورودی تازه نمی‌نویسند.

رد خرابی: ناسازگاری replay را روی همان شکل دنبال کن: اگر خروجی کار replay در یک آفست یکسانِ لاگ با دفترکل فرق کند، عیب باگ projection است نه lag — lag فقط نمای عقب‌مانده ولی سازگار را توضیح می‌دهد، و تابلوی lag در تمرین ۴ دقیقاً همان را می‌پاید.

تضمین نشان‌داده‌شده: شکل نشان می‌دهد یک commit دو مصرف‌کنندهٔ مستقل را راه می‌اندازد. تازه بودن نمای بالانس را قول نمی‌دهد — خواندن‌ها ممکن است عقب باشند.

تضمین نشان‌نداده‌شده: دربارهٔ مقیاس مصرف‌کنندهٔ replay یا توافق دفترکل‌های سیستم‌های مختلف چیزی نمی‌گوید — پارتیشن‌بندی و چندshardی، تمرین‌های بعدی‌اند.

Decision point: One atomic commit, two consumers: the client reply reads the stored row, the replay job reads the log rows. Neither path writes any fresh input.

Failure trace: Trace a replay mismatch on the same figure: if the Replay job's output ever differs from the Ledger at the same log offset, the fault is a projection bug, not lag — lag only explains a behind-but-consistent view, and the lag board in exercise 4 watches exactly that.

Guarantee shown: The figure shows one commit feeding two independent consumers. It doesn't promise the balance view is fresh — reads may lag.

Not shown: It says nothing about how the replay consumer scales, or how ledgers in different systems agree — partitioning and multishard are later exercises.

پاسخ: نتیجهٔ کلاینت (از سطر درخواست ذخیره‌شده) و کار replay (از سطرهای لاگ). ورودی تازه از هیچ‌کدام وارد نمی‌شود.

Answer: The client result (from the stored request row) and the replay job (from the log rows). Fresh input comes in through neither of them.

گزینه‌های جایگزینAlternatives

  • تکراریابی روی payload طبیعی (مبدأ، مقصد، مبلغ، پنجره): کلاینت را دست نمی‌زنی، ولی دو انتقال عمدیِ یکسان در یک پنجره به یکی فرومی‌روند — یعنی یک پرداخت واقعی بی‌صدا گم می‌شود. فقط نگهش دار وقتی تکرار هیچ‌وقت مشروع نیست؛ پول از آن‌ها نیست.
  • commit دوفازی بین سرویس موجودی و دفترکل: هزینهٔ هماهنگی برای مسئله‌ای که یک تراکنش پایگاه داده همین‌جا حلش می‌کند. فقط وقتی به 2PC ارتقا بده که legها واقعاً در سیستم‌های مختلف زندگی می‌کنند — آن تمرین ۳ است، نه این یکی.
  • Dedup on the natural payload (from, to, amount, window): the client doesn't change at all, but two intentional identical transfers inside one window collapse into one — a real payment silently disappears. Keep it only when a repeat is never legitimate; money is not one of those cases.
  • Two-phase commit across the balance service and the ledger: you pay a coordination cost for a problem one database transaction already solves right here. Promote to 2PC only when the legs genuinely live in different systems — that's exercise 3, not this one.

سناریوهای خرابیFailure scenarios

  • رسیدن هم‌زمان همان شناسه: هر دو INSERT مسابقه می‌دهند و قید یکتایی دقیقاً یکی را راه می‌دهد. بازنده باید سطر را بخواند — SUCCESS نتیجهٔ ذخیره‌شده را برمی‌گرداند، PENDING با ۲۰۲ و محل poll — و هرگز نباید انتقال دوم را محاسبه کند.
  • crash بین commit و پاسخ: از بیرونِ کلاینت، commit کند از شکست قابل‌تشخیص نیست. نگهبان همان retry با شناسهٔ یکسان به‌علاوهٔ نتیجهٔ ذخیره‌شده است؛ کلاینت تردیدش را با پرس‌وجوی شناسهٔ درخواست حل می‌کند، نه با ساختن شناسهٔ تازه.
  • lag یا توقف مصرف‌کنندهٔ replay: خواننده‌ها بالانس کهنه می‌بینند. نگهبانش یک متریک lag کران‌دار با هشدار است؛ lag فقط نمای عقب‌مانده ولی سازگار را توضیح می‌دهد — اختلاف در آفست یکسان یعنی corruption (تمرین ۴).
  • Concurrent same-ID arrivals: both INSERTs race and the UNIQUE constraint lets exactly one through. The loser must read the row — SUCCESS hands back the stored result, PENDING hands back 202 plus a poll location — and must never compute a second transfer.
  • Crash between commit and reply: from the client's seat, a slow commit looks exactly like a failure. The guard is the same-ID retry plus the stored result; the client settles its doubt by querying the request ID, never by minting a new one.
  • Replay consumer lag or stall: readers see stale balances. The guard is a bounded lag metric plus an alert; lag explains behind-but-consistent views only — a same-offset difference is corruption (exercise 4).

import java.util.*;

// Teaching demo: end-to-end request IDs (Example 13-2 pattern).
// One atomic commit binds UNIQUE(request_id) + debit/credit + input log.
// A lost commit reply + user retry must move money exactly once.
public class TransferDemo {
    static class Row { String payload; String status; String result; Row(String p){payload=p;status="PENDING";} }
    Map<String, Row> requests = new LinkedHashMap<>();
    Map<String, Long> balances = new LinkedHashMap<>(Map.of("A", 1000L, "B", 500L));
    List<String> inputLog = new ArrayList<>();

    // Returns the stored/fresh result string. Simulates one DB transaction.
    synchronized String submit(String id, String from, String to, long amount) {
        String payload = from + "->" + to + ":" + amount;
        Row old = requests.get(id);
        if (old != null) {
            if (!old.payload.equals(payload)) return "REJECTED: id reused with different payload";
            return "DEDUP: " + old.result; // same id + same payload -> stored result
        }
        Row row = new Row(payload);
        requests.put(id, row); // UNIQUE(request_id): a concurrent second insert fails here
        if (balances.get(from) < amount) { row.status = "FAILED"; row.result = "insufficient funds"; inputLog.add(id + "=FAIL"); return row.result; }
        balances.put(from, balances.get(from) - amount);
        balances.put(to, balances.get(to) + amount);
        row.status = "SUCCESS"; row.result = "moved " + amount + " " + from + "->" + to;
        inputLog.add(id + "=" + payload);
        return row.result;
    }

    // Independent consumer: rebuild balances ONLY from the input log.
    static Map<String, Long> replay(List<String> log) {
        Map<String, Long> b = new LinkedHashMap<>(Map.of("A", 1000L, "B", 500L));
        for (String e : log) {
            if (e.endsWith("=FAIL")) continue;
            String p = e.substring(e.indexOf('=') + 1); // from->to:amount
            String[] u = p.split("->|:");
            b.put(u[0], b.get(u[0]) - Long.parseLong(u[2]));
            b.put(u[1], b.get(u[1]) + Long.parseLong(u[2]));
        }
        return b;
    }

    public static void main(String[] a) {
        TransferDemo db = new TransferDemo();
        String r1 = db.submit("req-7", "A", "B", 200);
        System.out.println("first submit          = " + r1 + "   (reply LOST on the wire)");
        String r2 = db.submit("req-7", "A", "B", 200); // user retry, same id + same payload
        System.out.println("retry same id+payload = " + r2);
        System.out.println("reuse id, new payload = " + db.submit("req-7", "A", "B", 999));
        System.out.println("same payload, new id  = " + db.submit("req-8", "A", "B", 200) + " (independent transfer allowed)");
        System.out.println("balances              = " + db.balances + " (each id moved money exactly once)");
        Map<String, Long> rebuilt = replay(db.inputLog);
        System.out.println("replay from log       = " + rebuilt);
        System.out.println(rebuilt.equals(db.balances) ? "OK: replay matches live state" : "MISMATCH");
    }
}

آزمون صحت و معیار عملیاتیCorrectness checks and operational criteria

ناورداها: بقای جمع پول؛ هر شناسه درخواست حداکثر یک‌بار اعمال؛ replay در هر آفست برابر حالت زندهٔ همان آفست. تست‌های خرابی: پاسخ commit را بنداز و retry کن (با payload یکسان و عوض‌شده)؛ دو ثبت هم‌زمان با یک شناسه را مسابقه بده؛ مصرف‌کنندهٔ replay را متوقف کن و ببین خواننده‌ها lag می‌بینند نه واگرایی. متریک‌ها: نرخ dedup-hit، نرخ conflict یکتایی و lag replay به ثانیه با کران هشدار.
Invariants: the total money is conserved; each request ID is applied at most once; the replay at any offset equals the live state at that same offset. Failure tests: drop the commit reply and retry (same and changed payloads); race two same-ID submits concurrently; stall the replay consumer and confirm readers see lag, not divergence. Metrics: dedup-hit rate, UNIQUE-conflict rate, replay lag in seconds with an alert bound.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (سینیور): دو درخواست هم‌زمان با یه ID برسن؛ پاسخ موفق یا pending رو چطور تعیین می‌کنی؟Follow-up (Senior): Two requests with the same ID arrive concurrently. How do you return success or pending?

قید یکتایی کار را سریال می‌کند: یک INSERT می‌برد و انتقال را اجرا می‌کند؛ دیگری conflict کلید می‌گیرد و سطر را می‌خواند. اگر سطر از قبل SUCCESS می‌گوید، نتیجهٔ ذخیره‌شده را برگردان. اگر هنوز PENDING می‌گوید (یعنی برنده وسط تراکنش است)، ۲۰۲ در حال انجام با محل poll برگردان — و هرگز محاسبهٔ دوم را شروع نکن. حالت pending هم timeout می‌خواهد: برنده‌ای که crash کرده باید بالاخره سطرش را به FAILED بغلتاند تا منتظرها از poll دست بکشند.

The UNIQUE constraint serializes them: one INSERT wins and runs the transfer, the other gets a key conflict and reads the row. If the row already says SUCCESS, hand back the stored result. If it still says PENDING (the winner is mid-transaction), hand back 202 pending with a poll location — and never start a second computation. The pending state needs a timeout too: a winner that crashed must eventually roll its row to FAILED so the waiters stop polling.

پیگیری (سینیور): کلاینت بعد از گم شدن پاسخ، هیچ‌وقت retry نمی‌کند. یعنی پول گم شده؟Follow-up (Senior): The client never retries after the reply is lost. Is the money lost?

retry نمی‌کند؛ پول رفته و برگشتی در کار نیست. کلاینت با خواندن شناسهٔ درخواست (GET /transfers/{id}) یا صورت‌حسابش دوباره مطمئن می‌شود: نتیجهٔ ذخیره‌شده همان رسید است. قاعدهٔ طراحی: هر پاسخ جهش‌دهنده شناسهٔ درخواست را همراه دارد، تا پاسخ گمشده همیشه بدون نیت تازه دوباره قابل‌حل باشد.

It doesn't retry — the money already moved and nothing is coming back. The client gets its certainty back by reading the request ID (GET /transfers/{id}) or its statement: the stored result is the receipt. Design rule: every mutating response carries the request ID, so a lost reply is always re-resolvable without a new intent.

اشتباهات رایجCommon mistakes

  • دو UPDATE لخت بدون سطر درخواست: retry از انتقال تازه قابل‌تشخیص نیست و پول دوبار می‌رود. سطر درخواست کلید تکراریابی است نه تزئین.
  • تکراریابی روی payload به‌جای شناسه: انتقال‌های عمدیِ یکسان قورچاق می‌شوند. payload یکسان مجاز است؛ شناسهٔ یکسان یک‌بار.
  • برگرداندن خطا روی conflict یکتایی به‌جای نتیجهٔ ذخیره‌شده: کلاینت «قبلاً انجام شده» را از «شکست خورده» تشخیص نمی‌دهد و شناسهٔ تازه می‌سازد — و همان خرج دوباره‌ای را می‌سازد که قید آمده بود جلویش را بگیرد.
  • Two bare UPDATEs with no request row: you can't tell a retry from a new transfer, so the money moves twice. The request row is the dedup key, not decoration.
  • Deduping on the payload instead of the ID: identical intentional transfers get swallowed up. The same payload is allowed; the same ID means once.
  • Returning an error on the UNIQUE conflict instead of the stored result: the client can't tell 'already done' from 'failed', so it mints a new ID — and you get the very double-spend the constraint was built to stop.

سؤال مصاحبهInterview question

Think of it, you're migrating a catalog with one shared input log and independent old and new projections. You define backfill, catch-up, shadow reads, canary routing, rollback, and when you retire the old view. You inject a projection bug and lag; and you keep write ownership and compatibility explicit.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که: یک لاگ ورودی مشترک نگه دار و دو projection مستقل بساز. نمای تخت قدیم همین حالا سرو می‌دهد، درحالی‌که نمای تازه (جدول‌به‌علاوه‌جزئیات) backfill می‌کند، به نوک می‌رسد و مقایسهٔ سایه را با ترافیک زندهٔ صفر رد می‌کند. بعد خواندن‌ها را با یک flag برگشت‌پذیر شیفت بده — ۵٪ و ۵۰٪ و ۱۰۰٪ — آن‌هم فقط تا وقتی mismatch صفر و lag کران‌دار است. rollback یک چرخش flag است، چون نمای قدیم هیچ‌وقت از سرو نایستاد. نمای قدیم را هم فقط بعد از معیارهای cutover به‌علاوهٔ دورهٔ نگه‌داشت بازنشسته کن. تریدآف: دو برابر هزینهٔ projection و ذخیره‌سازی در مهاجرت، در برابر rollback بدون دان‌تایم. — تا وقتی ریل کهنه زیر پای قطار است، همیشه راه برگشت داری.
Here's the thing: keep one shared input log and build two independent projections. The old flat view keeps serving while the new table-plus-details view backfills, catches up, and clears the shadow comparison at 0% live traffic. Then shift the reads with one reversible flag — 5%, 50%, 100% — and only while mismatches stay zero and lag stays bounded. The rollback is one flag flip, because the old view never stopped serving. Retire the old view only after the cutover criteria plus a hold period. The trade-off: double the projection cost and storage during the migration, in exchange for a rollback that costs no downtime. — as long as the old rail is still under the train, there is always a way back.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن دامنه کاتالوگه: schema تختِ قدیم (یک سطر به‌ازای هر محصول) در برابر schema تازه (سطر به‌علاوهٔ سطر جزئیات). سه محصول آموزشی: چراغ ۳۰، صندلی ۱۲۰، میز ۲۵۰.
  • قضیه اینه که: مسیر نوشتن در مهاجرت هیچ‌وقت جابه‌جا نمی‌شه — همهٔ ورودی تازه هنوز توی لاگ مشترک می‌نشینه و هر دو projection مستقل مصرفش می‌کنن.
  • خواننده‌ها توی canary هر دو schema رو تحمل می‌کنن؛ flag درصد رو تعیین می‌کنه. rollback فقط تا وقتی ممکن می‌مونه که نوشتن‌های تازه old-readable بمونن.
  • Picture the scope: a catalog. The flat old schema (one row per product) versus the new schema (row plus details row). Three teaching products: Lamp 30, Chair 120, Desk 250.
  • The key point: the write path never moves during the migration. All fresh input still lands in the shared log, and both projections consume it independently.
  • Readers tolerate either schema during the canary, and the flag decides the percent. Rollback stays possible only while the new writes remain old-readable.

چرا این روش و این عددها؟Why this method and these numbers?

shared log همهٔ تغییرها را به دو projection می‌رساند تا dual write مستقل شکاف نسازد. مقایسه در checkpoint مشترک لازم است، چون نمای عقب‌مانده با نمای خراب فرق دارد و قاطی کردنشان یعنی page کردن الکی. درصد canary یک فرض مدیریت ریسک است: مرحله را وقتی بالا ببر که mismatch، lag و خطای هر cohort داخل معیار باشد؛ گذشتن چند دقیقه به‌تنهایی کافی نیست. rollback فقط تا وقتی معتبر است که مسیر قدیم دادهٔ تازه را بفهمد؛ حذف زودهنگام فیلدها آن در را می‌بندد.

A shared log feeds both projections without independent dual-write gaps. You compare at a common checkpoint to tell lag apart from corruption — mixing the two up means paging for nothing. The canary percentages are a risk-management assumption: move up only when mismatch, lag and per-cohort errors are inside the criteria, not merely because some minutes passed. Rollback holds only while the old path understands the new data; removing fields early closes that door.

مدل ذهنیMental model

ببین، دو ریل کنار هم درحالی‌که قطار همچنان می‌رود: ریل قدیم همهٔ مسافرها را می‌برد، درحالی‌که ریل تازه کنارش کشیده می‌شود، اول با واگن‌های خالی تست می‌شود (سایه)، بعد با چند واگن (canary) و بعد با کل ترافیک. ریل قدیم فقط بعد از این‌که ریل تازه کل بار را در یک جدول زمانی کامل برد جمع می‌شود — و تا آن لحظه، برگشتن فقط سوزن ریل است.
Two rails side by side while the train keeps running: the old rail carries every passenger while the new rail is laid beside it, tested with empty cars (shadow), then a few cars (canary), then all the traffic. The old rail is torn up only after the new one has carried the full load through a whole timetable — and until then, switching back is just a set of points on the track.

حل گام‌به‌گامStep by step

  1. اول backfill، بعد catch-up نکته‌ش اینه: هر دو projector همان لاگ را از اولین آفست مصرف می‌کنند — اول تاریخچهٔ انبوه، بعد catch-up جریانی تا نوک. نمای قدیم در تمام این مدت صددرصد خواندن‌ها را سرو می‌دهد و هیچ‌چیز در مسیر نوشتن تکان نمی‌خورد.
  2. سایه قبل از canary حالا بریم سراغ بخش ترسناک: هر خواندن روی هر دو نما اجرا می‌شود ولی فقط جواب قدیم سرو می‌شود، و اختلاف‌ها به‌عنوان mismatch سایه شمرده می‌شوند. درصد canary تا وقتی mismatch غیرصفر است یا lag یکی از نماها از کرانش بگذرد صفر می‌ماند — باگ افتادن جزئیات در دمو دقیقاً همین‌جا می‌میرد، بی‌آن‌که کسی ببیند.
  3. canary و cutover و بازنشستگی دیرهنگام راستش، اینجا همه‌چیز به انضباط برمی‌گردد: flag روی صفر mismatch و lag کران‌دار از ۵ به ۵۰ به ۱۰۰ می‌رود، و هر پسرفتی آن را در یک حرکت به صددرصد قدیم برمی‌گرداند. بعد از معیارها به‌علاوهٔ دورهٔ نگه‌داشت در ۱۰۰٪، projector قدیم را متوقف کن، یک snapshot را در نگهداری نگه دار و تازه آن‌وقت بازنشسته‌اش کن.
  1. Backfill first, catch up second Both projectors eat the same log from the very first offset: bulk history first, then streaming catch-up to the tip. The old view keeps serving 100% of the reads the whole way through, and nothing about the write path changes.
  2. Shadow first, canary second Now the scary part: every read runs against both views, but only the old answer is served, and the differences get counted as shadow mismatches. The canary percent stays at 0 while mismatches are nonzero or either view's lag exceeds its bound — the demo's dropped-details bug dies right here, where nobody can see it.
  3. Canary, cutover, then a late retirement Honestly, this part is pure discipline: the flag walks 5 to 50 to 100 on zero mismatches and bounded lag, and any regression flips it to 100% old in one move. After the criteria plus a hold period at 100%, stop the old projector, keep one snapshot through retention, and only then retire it.

طراحی مشخصConcrete design

اجزا: یک لاگ ورودی فقط‌افزودنی؛ دو projector مستقل (تخت قدیم و شکافتهٔ تازه)؛ دو نما؛ یک flag ترافیک (درصد هر نما، قابل‌چرخش در یک انتشار). API: خواندن‌های لیست محصول نسخه ندارند — مسیریاب خودش نما را انتخاب می‌کند؛ نوشتن‌ها همیشه به شکل لاگی می‌روند که هر دو projector می‌فهمند. معیارهای cutover: صفر mismatch سایه در یک چرخهٔ کاری کامل، lag نمای تازه زیر SLO خواندن، به‌علاوهٔ دورهٔ نگه‌داشت در ۱۰۰٪ پیش از انداختن نمای قدیم. مالکیت: لاگ مالک مسیر نوشتن است؛ هیچ نمایی حق نوشتن مستقیم ندارد. — یک مسیر نوشتن، دو نما، و یک اهرم که با یک حرکت برمی‌گردد.

Components: one append-only input log; two independent projectors (old-flat, new split); two views; one traffic flag (percent per view, flippable in one deploy). API: product-list reads carry no version — the router picks the view; writes always target the log shape both projectors understand. Cutover criteria: zero shadow mismatches over a full business cycle, new-view lag under the read SLO, plus a hold period at 100% before the old view is dropped. Ownership: the log owns the write path; neither view may accept direct writes. — one write path, two views, and a single lever you can pull back with one move.

گزینه‌های جایگزینAlternatives

  • cutover یک‌باره (توقف نوشتن، مهاجرت، شروع دوباره): ساده‌ترین حالت برای استدلال، ولی یک قطعی نوشتن می‌خواهد و rollbackای جز برگشت از بکاپ ندارد. فقط برای کاتالوگ‌های کوچک با پنجرهٔ نگهداری اعلام‌شده قابل‌قبول است؛ وگرنه هزینهٔ دو نما، قیمت صادقانهٔ دان‌تایم صفر است.
  • بازنویسی درجا (ALTER TABLE با backfill درجا): نصف ذخیره‌سازی، ولی خواننده‌ها یک schema نیمه‌مهاجرت‌شده می‌بینند و rollback یعنی یک بازنویسی دیگر. وقتی تغییر افزایشی و backward-readable است ترجیحش بده؛ وقتی شکل تازه old-readable نیست، نماهای دوگانه را نگه دار.
  • Big-bang cutover (stop writes, migrate, restart): the simplest thing to reason about, but it needs a write outage and it has no rollback except restoring from backup. Acceptable only for tiny catalogs with a declared maintenance window; otherwise the dual-view cost is the honest price of zero downtime.
  • In-place row rewrite (ALTER TABLE + backfill in place): half the storage, but the readers see a half-migrated schema and the rollback means another rewrite. Prefer it when the change is additive and backward-readable; keep the dual views when the new shape isn't old-readable.

سناریوهای خرابیFailure scenarios

  • باگ در projection تازه (افتادن جزئیات): مقایسهٔ سایه در ترافیک زندهٔ صفر می‌گیردش. نگهبانش دروازهٔ صفر-mismatch پیش از هر درصد canary است — دمو دقیقاً همین باگ را تزریق می‌کند.
  • lag نمای تازه فراتر از SLO خواندن: خواندن‌های canary سطرهای کهنه را مثل تازه سرو می‌کنند. نگهبانش یک متریک lag کران‌دار برای هر نما است؛ تا وقتی یکی از نماها عقب است، flag را بلوکه کن.
  • توقف بی‌صدای projector قدیم وسط مهاجرت: هدف rollback کهنه می‌شود و rollback دیگر فوری نیست. نگهبانش این است که هر دو نما از یک watermark نوکِ مشترک projection شوند، به‌علاوهٔ هشدار عقب‌ماندگی نمای قدیم — rollback فقط تا وقتی فوری است که به‌روز باشد.
  • Bug in the new projection (dropped details): the shadow compare catches it at 0% live traffic. The guard is the zero-mismatch gate in front of every canary percent — the demo injects exactly this bug.
  • New-view lag beyond the read SLO: canary reads would serve stale rows as if they were fresh. Guard it with a bounded lag metric per view; block the flag while either view is behind.
  • Old projector silently stalls mid-migration: the rollback target goes stale. Guard it by projecting both views from the same tip watermark, and alert when the old view falls behind — the rollback is only instant while it is current.

import java.util.*;

// Teaching demo: dual-schema migration from one shared input log.
// Old flat projection vs new (table + details) projection, % traffic,
// shadow compare, deliberate bug in the new projection, rollback.
public class MigrationDemo {
    record Upsert(String id, String name, long price, String detail) {}
    // old view: flat row per product. new view: row + details row.
    Map<String, String> oldView = new LinkedHashMap<>();
    Map<String, String> newView = new LinkedHashMap<>();
    Map<String, String> newDetails = new LinkedHashMap<>();
    List<Upsert> log = new ArrayList<>(List.of(
        new Upsert("p1", "Lamp", 30, "warm LED"),
        new Upsert("p2", "Chair", 120, "oak"),
        new Upsert("p3", "Desk", 250, "standing")));

    void projectOld(Upsert u) { oldView.put(u.id, u.name + "|" + u.price); }
    void projectNew(Upsert u, boolean buggy) {
        newView.put(u.id, u.name + "|" + u.price);
        // BUG (injected): details dropped when price > 100
        if (!(buggy && u.price > 100)) newDetails.put(u.id, u.detail);
    }

    public static void main(String[] a) {
        MigrationDemo m = new MigrationDemo();
        // backfill + catch-up: both projections consume the same log
        for (Upsert u : m.log) { m.projectOld(u); m.projectNew(u, true); }
        System.out.println("backfill done: old=" + m.oldView.size() + " new=" + m.newView.size());
        // shadow read: compare every read against the old view (0% live traffic yet)
        int mism = 0;
        for (String id : m.oldView.keySet())
            if (!m.newDetails.containsKey(id)) { mism++; System.out.println("shadow mismatch: " + id + " details missing in new view"); }
        System.out.println("shadow mismatches = " + mism + " -> canary BLOCKED, stays 0%");
        // fix projection, re-project from the same log (replay, not patch)
        m.newView.clear(); m.newDetails.clear();
        for (Upsert u : m.log) m.projectNew(u, false);
        mism = 0;
        for (String id : m.oldView.keySet()) if (!m.newDetails.containsKey(id)) mism++;
        System.out.println("after fix: mismatches = " + mism + " -> canary 5% -> 50% -> 100%");
        // rollback drill: flag back to 100% old; old view untouched throughout
        String flag = "new";
        flag = "old"; // one flag flip
        System.out.println("rollback: traffic flag = " + flag + " (old view served reads all along: " + m.oldView.size() + " rows)");
        System.out.println("OK: write path never moved; old view retired only after cutover criteria held");
    }
}

ناورداها: نمای قدیم و تازه روی هر کلید در آفست یکسانِ لاگ با هم توافق دارند (برابری سایه)؛ جمع درصدهای سروشده همیشه ۱۰۰ است؛ هیچ نوشتنی لاگ را دور نمی‌زند. تست‌های خرابی: باگ projection تزریق کن و ببین canary باز نمی‌شود؛ یک projector را متوقف کن و تأیید کن نمای آن از خواندن فنس شده؛ rollback را وسط canary بچرخان و تأیید کن خواندن‌ها در یک حرکتِ flag برمی‌گردند. متریک‌ها: نرخ mismatch سایه، lag هر نما نسبت به watermark نوک و درصد سروشدهٔ هر نما.
Invariants: the old and new views agree on every key at the same log offset (shadow equality); the percent served always sums to 100; no write bypasses the log. Failure tests: inject a projection bug and confirm the canary never opens; stall one projector and confirm its view is fenced off from reads; flip the rollback mid-canary and confirm the reads come back in one flag move. Metrics: shadow mismatch rate, per-view lag against the tip watermark, percent served per view.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): کاربر بعد از خوندن schema جدید داده‌ای بنویسه که نسخه قدیم نمی‌فهمه؛ rollback هنوز ممکنه؟Follow-up (Staff): A client writes data the old schema can't represent after reading the new schema. Is rollback still possible?

نه همیشه. اگر کلاینت فقط schema تازه را خوانده باشد، rollback هنوز یک چرخش flag است. ولی اگر داده‌ای نوشته باشد که schema قدیم نمی‌تواند نمایشش دهد (یک فیلد اجباری تازه، یا شکافی که سطر تخت نمی‌گیرد)، برگشتن یا آن داده را می‌اندازد یا غلط سرو می‌کند. نگهبان: در canary نوشتن‌ها باید old-readable بمانند (فیلدهای تازه اختیاری و نادیده‌گرفته‌شده توسط projector قدیم)، یا یک کار forward-fill داشته باشی که شکل تازه را پیش از rollback به نمای قدیم برگرداند. اگر هیچ‌کدام برقرار نیست، صریح بگو: rollback از آن نوشتن به بعد خراب است و تنها راه برگشت اصلاح روبه‌جلوست.

Not always. If the client only READ the new schema, the rollback is still one flag flip. But if it WROTE data the old schema cannot represent (a new required field, a split the flat row cannot hold), flipping back either drops that data or serves it wrongly. Guard: during the canary, writes must stay old-readable (new fields optional and ignored by the old projector), or you carry a forward-fill job that backfills the new shape into the old view before any rollback. If neither holds, say so out loud: the rollback is broken from that write on, and the only way back is a forward-fix.

پیگیری (استف): دقیقاً کِی نمای قدیم را حذف می‌کنی؟Follow-up (Staff): When exactly do you drop the old view for good?

بعد از این‌که معیارها پایدار ماندند: خواندن صددرصد تازه در یک چرخهٔ کاری کامل، با صفر mismatch، lag داخل SLO و بدون rollback در پنجرهٔ نگه‌داشت. بعد projector قدیم را متوقف کن، آخرین snapshotش را یک دورهٔ نگهداری دیگر نگه دار (بیمهٔ ارزان) و تازه آن‌وقت حذفش کن. بازنشستگی فقط با درصدهای canary — بدون دورهٔ نگه‌داشت — اگر باگ کندسوز یک هفته بعد سر بزند، تو را بی‌پناه می‌گذارد.

After the criteria hold: 100% new reads for a full business cycle with zero mismatches, lag inside the SLO, and no rollback inside the hold window. Then stop the old projector, keep its last snapshot for one more retention period (cheap insurance), and only then delete it. Retiring on canary percentages alone — without the hold — strands you if a slow-burn bug surfaces a week later.

اشتباهات رایجCommon mistakes

  • مهاجرت خواندن‌ها پیش از بازپخش تاریخچه توسط نمای تازه: درصدهای canary روی نمای ناقص، جواب‌های غلطِ مطمئن سرو می‌کنند. اول backfill با catch-up، بعد درصدها.
  • گذاشتن نوشتن مستقیم در نماها حین مهاجرت: projectionها از لاگ واگرا می‌شوند و replay دیگر هیچ نمایی را بازنمی‌سازد. همهٔ ورودی تازه از لاگ می‌رود، بدون استثنا.
  • بازنشستگی نمای قدیم در canary صددرصد بدون دورهٔ نگه‌داشت: rollback همان روزی می‌میرد که باگ کندسوز به آن نیاز دارد. اول معیارهای cutover با نگه‌داشت، بعد بازنشستگی.
  • Migrating the reads before the new view has replayed history: canary percentages over an incomplete view serve confident wrong answers. Backfill plus catch-up first, percentages second.
  • Letting the views accept direct writes during the migration: the projections drift away from the log and the replay can no longer rebuild either view. All fresh input goes through the log, no exceptions.
  • Retiring the old view at 100% canary without a hold period: the rollback dies the same day a slow-burn bug needs it. Cutover criteria plus the hold, then retire.

سؤال مصاحبهInterview question
داستان از این قراره که انتقال مبدأ، مقصد و کارمزد رو با سه log و پردازش قطعی طراحی می‌کنی. رکورد framed با checksum و fsync، رزرو موجودی، تصمیم پایدار، outbox و dedup رو مشخص کن. crash بعد از انتشار بخشی از خروجی رو بازیابی کن و فرق integrity نهایی، pending state و رؤیت اتمیک رو بگو.
Here's the thing, you're designing source, destination, and fee transfers with three logs and deterministic processing. You pin down framed checksummed records with fsync, reserved funds, a persistent decision, an outbox, and dedup. You recover after publishing only some outputs. And you spell out the difference between pending funds, final integrity, and atomic visibility.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که: تصمیم، رزرو و تعهد انتشار legها را در یک رکورد قاب‌بندی‌شده و checksumدار ثبت کن — و قبل از ACK با fsync. مقصد اثر و dedup همان leg را از یک لاگ پایدار بازسازی می‌کند. بعد از restart، تصمیم دوباره گرفته نمی‌شود؛ همان خروجی‌ها با dedup بازپخش می‌شوند. pending هر leg فقط تا پیش از اعمال آن حساب می‌شود. یعنی همگرایی نهایی داری، اما خواندن‌های مستقل shardها رؤیت اتمیک نمی‌دهند. — پول یک بار تصمیم می‌گیرد؛ بقیه‌اش فقط پخش است.
Here's the thing: keep the decision, the reservation and the publication obligations for the legs in one framed, checksummed record, fsynced before the ACK. Each destination rebuilds its leg effect and dedup from one durable log. Restart replays the stored decision and outputs without re-deciding. Count a leg as pending only until it has applied. So you get eventual convergence under the recovery and delivery assumptions — not atomic visibility across independent shard reads. — the money decides once; the rest is just delivery.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن: سه shard، هرکدام با یه پردازندهٔ تک‌نخ (مبدأ و مقصد و کارمزد). رهبرِ هر shard مالکِ leg خودشه؛ هیچ تراکنشی روی shardها کشیده نمی‌شه.
  • مبدأ ۱۰۰۰ داره و مقصد ۱۰۰؛ پرداخت ۲۰۰ با کارمزد ۵ است. invariant توی مرز منطقیِ مشترک: مجموع موجودی‌ها به‌علاوهٔ فقط legهای اعمال‌نشده برابر ۱۱۰۰ می‌شه.
  • قضیه اینه که: دیسک‌ها می‌تونن وسط نوشتن crash کنن و پردازنده‌ها وسط انتشار بمیرن؛ شبکه ممکنه تکراری بده ولی رکوردهای قاب‌بندی‌شده رو خراب نمی‌کنه (CRC خرابی رو رد می‌کنه).
  • Picture it: three shards with one single-threaded processor each (source, destination, fee). Each shard's leader owns its leg, and no transaction spans shards.
  • The source starts at 1000 and the destination at 100; the payment is 200 plus a fee of 5. At a common logical boundary, the balances plus only the unapplied legs sum to 1100.
  • The honest part: disks can crash mid-write and processors can die mid-publish. The network may duplicate records but it won't corrupt the framed ones (CRC rejects corruption).

چرا این روش و این عددها؟Why this method and these numbers?

framing مرز رکورد، checksum خرابی بایت و fsync درخواست دوام پیش از ACK را مشخص می‌کنند؛ هیچ‌کدام به‌تنهایی یک تراکنش چندshardی نمی‌سازند. تصمیم پایدار از تغییرِ نظر بعد از restart جلوگیری می‌کند و dedup پایدار مانعِ دوباره‌اعمال‌شدن leg می‌شود. ۱۰۰۰+۱۰۰=۱۱۰۰ کل اولیه است؛ بعد از credit مقصد ۲۰۰ فقط کارمزد ۵ هنوز در راه است، نه تمام ۲۰۵. جمعِ خواندن‌های مستقل در لحظه‌های مختلف شاهد conservation نیست؛ در دمو از logهای بازیابی‌شده در مرز منطقی مشترک استفاده می‌کنیم.

Framing identifies the record boundaries, a checksum detects byte corruption, and fsync requests durability before the ACK; none of them creates a cross-shard transaction. A durable decision prevents re-deciding after a restart, and durable dedup prevents duplicate legs. The initial total is 1000+100=1100. After crediting 200 to the destination, only fee 5 remains in transit, not all 205. Independent reads taken at different instants do not prove conservation; compare the recovered logs at a common logical boundary.

مدل ذهنیMental model

ببین، سه صندوقدار در سه باجه با یک بلیت شماره‌دار: صندوقدار اول کیفت را چک می‌کند و APPROVED را روی ته‌بلیت مهر می‌زند و پولت را در جعبهٔ شیشه‌ای قفل می‌کند که همه می‌بینند. پیک‌ها کپی همان بلیت را به باجه‌های دیگر می‌برند؛ هر کپی تکراری دم در پاره می‌شود. اگر پیکی زمین بخورد، پیک تازه ته‌بلیت را بازمی‌خواند — هرگز دوباره تصمیم نمی‌گیرد — و فقط کپی‌های نرسیده دوباره راه می‌افتند. جعبهٔ شیشه‌ای هم فقط وقتی باز می‌شود که هر باجه تأیید کند. — سه باجه، یک تصمیم.
Three cashiers in three booths, one numbered ticket: the first cashier checks your wallet, stamps APPROVED on the ticket stub, and locks your cash in a glass box everyone can see. Runners carry copies of that same ticket to the other booths, and any duplicate copy gets torn up at the door. If a runner trips, the next runner re-reads the stub — he never re-decides — and only the copies that never arrived go out again. The glass box opens only when every booth confirms. — three booths, one decision.

حل گام‌به‌گامStep by step

  1. اول قاب‌بندی، بعد fsync نکته‌ش اینه: length مرز رکورد را مشخص می‌کند، CRC خرابی payload را می‌یابد، و force پیش از ACK داده را از buffer فرایند بیرون می‌کشد. recovery فقط suffix ناقص را truncate می‌کند؛ checksum خراب یا طول نامعتبر باعث توقف و بررسی می‌شود. این دمو دوام در crash پردازنده با دیسک باقی‌مانده را می‌آزماید.
  2. یک‌بار تصمیم، رزروِ نمایان یک رکورد D تصمیم، مبلغ رزرو و خروجی‌های لازم را ثبت می‌کند. replay همان رکورد کسر موجودی و obligationها را بازسازی می‌کند، پس شکافی میان لاگ تصمیم و state جدا نمی‌ماند. — یک سطر، همهٔ حقیقت.
  3. انتشار، dedup، همگرایی legها با کلید (shard,payment_id) ارسال می‌شوند. مقصد از رکورد C هم اعتبار و هم dedup را بازسازی می‌کند، پس retry می‌تواند همهٔ legها را دوباره بفرستد و مقصد تکرارها را حذف می‌کند. هر leg اعمال‌شده از مبلغ in-transit کم می‌شود؛ این جمع در مرز مشترک harness حساب می‌شود، نه از خواندنِ تصادفیِ چند shard.
  1. Frame it, then fsync it Here's the shape: the length marks the record boundary, the CRC catches a corrupt payload, and force before the ACK pushes the data out of the process buffer. Recovery truncates an incomplete suffix and nothing else; a checksum mismatch or an invalid length stops recovery and asks for a human. This demo tests a processor restart with the files that survived.
  2. Decide once, then reserve visibly One D record holds the decision, the reservation amount and the outputs that are owed. Replaying it rebuilds the source debit and the obligations, so there is no gap between a decision log and state kept somewhere else. — one row, all the truth.
  3. Publish it, dedup it, converge The legs go out keyed by (shard,payment_id). Each C record rebuilds both the credit and the dedup, so a replay may resend every leg and the destination simply absorbs the repeats. Applied legs come out of the in-transit value at the harness's common logical boundary — not from some random read across shards.

طراحی مشخصConcrete design

لاگ src رکورد D(id,amount,fee,approved) دارد؛ همان رکورد مرجعِ تصمیم، کسر موجودی و تعهد ارسال است. لاگ‌های dst و fee هرکدام C(id,amount) دارند و replay همان رکورد هم effect و هم dedup را می‌سازد. src با S(id) پایان انتشار را ثبت می‌کند. framing شامل length/payload/CRC است و ACK بعد از force(true) می‌آید؛ دم ناقص پیش از append بعدی truncate می‌شود و checksum ناسازگار بازیابی را متوقف می‌کند. دمو crash پردازنده با فایل‌های باقی‌مانده را مدل می‌کند؛ دوام در قطع برق و directory fsync روی فایل‌های تازه نیاز به آزمون filesystem و runbook جدا دارد.

در harness می‌توانی لاگ‌ها را در مرز منطقی مشترک بخوانی و فقط legهای اعمال‌نشده را pending حساب کنی؛ این قابلیت، API اتمیک برای balanceهای توزیع‌شده نیست. در production باید وضعیت pending/settled، ACK هر leg و reconciliation را با شناسهٔ پایدار طراحی کنی. — فایل‌ها حرف می‌زنند، ولی به زبانِ خودشان.

The src log records D(id,amount,fee,approved), the authority for the decision, the reservation and the publication obligations. The dst and fee logs record C(id,amount); the replay reconstructs both the effects and the dedup. Src records S(id) after publication. Frames contain length/payload/CRC with force(true) before ACK. Recovery truncates incomplete suffixes before later appends and stops on checksum mismatch. The demo models processor crashes with surviving files; power-loss durability and directory fsync for new files require separate filesystem testing.

The harness inspects the logs at a common logical boundary and counts only unapplied legs as pending. That is not an atomic distributed balance API. In production you have to design the pending/settled states, the per-leg ACKs and the reconciliation with persistent identities and explicit protocols. — the files talk, but in their own language.

مثال محاسبه‌شدهWorked example

بعد از رزرو: src=795 و dst=100 و fee=0 و مبلغ در راه ۲۰۵؛ جمع ۱۱۰۰ می‌شود. بعد از credit مقصد: dst=300 و فقط ۵ کارمزد در راه است؛ نگه‌داشتن ۲۰۵ به‌عنوان پول در راه، دوباره‌شماریِ پول است. بعد از recovery و اعمال کارمزد: src=795,dst=300,fee=5 و pending=0. پردازندهٔ تازه فقط فایل می‌خواند؛ هیچ map از فرایند قبلی کپی نمی‌شود. — جمع، هر قدر هم بین shardها بگرده، تکان نمی‌خورد.

After the reservation: src=795, dst=100, fee=0, in-transit=205, total=1100. After the destination credit: dst=300 and only fee 5 remains in transit; counting all 205 again double-counts the money. The recovery applies the fee, yielding src=795,dst=300,fee=5,pending=0. A fresh processor reads files only; no prior process maps are copied. — the total never moves, no matter how the money hops between shards.

گزینه‌های جایگزینAlternatives

  • 2PC روی سه shard: رؤیت اتمیک واقعی، ولی هر پرداخت هزینهٔ هماهنگی بین‌شاردی می‌دهد و دسترس‌پذیری کندترین shard را به ارث می‌برد. فقط وقتی انتخابش کن که خواننده‌ها هیچ‌وقت نباید پرداخت جزئی ببینند (نادر است)؛ وگرنه پروتکل مرحله‌ای با جبران، ارزان‌تر و در‌دسترس‌تر است.
  • پول تک‌شارد (عبور هر حساب از یک shard دفترکل): با shard نکردن اتمیک بودن را نگه می‌دارد و توان را روی یک ماشین سقف می‌زند. تا وقتی نرخ می‌گنجد نگهش دار؛ روزی که نگنجید، بر اساس حساب shard کن و هزینهٔ پروتکل بالا را بپرداز.
  • 2PC across the three shards: real atomic visibility, but every payment pays for cross-shard coordination and inherits the slowest shard's availability. Pick it only when readers must never observe a partial payment (rare); otherwise the staged protocol plus compensation is cheaper and far more available.
  • Single-shard money (route every account through one ledger shard): it keeps atomicity by refusing to shard, and it caps the throughput at one machine. Keep it while the rate fits; the day it doesn't, shard by account and pay for the protocol above.

سناریوهای خرابیFailure scenarios

  • crash منطقی بعد از credit مقصد: پردازندهٔ تازه تصمیم و dedup را از فایل می‌خواند و replay می‌کند؛ credit مقصد دوباره اعمال نمی‌شود و کارمزدِ باقی‌مانده اعمال می‌شود. — بازیابی، تکرارِ اثر نیست؛ تکرارِ کارِ اثر است.
  • نوشتن نیمه‌کاره در suffix با truncate پیش از append بعدی ترمیم می‌شود. checksum خراب، حتی در آخرین رکورد، بی‌صدا حذف نمی‌شود: recovery متوقف می‌شود تا repair یا restore معتبر تصمیم بگیرد. — دور انداختنِ تاریخچهٔ شکسته راحت‌تر از حدس زدن است، ولی حدس زدن غلط است.
  • تلاش مقصد برای خرج کردن leg رسیده پیش از settle کارمزد: پرداخت جزئی مشاهده می‌شود. نگهبانش معنای صادقانهٔ رؤیت است — legها فقط با قاعدهٔ صریح محصول per-leg قابل‌خرج‌اند، و رزرو معلق، باقیماندهٔ تسویه‌نشده را تا settle یا جبران حساب‌شده نگه می‌دارد.
  • A logical crash after the destination credit is recovered by a fresh processor that reads the decisions and the dedup from the files. The replay does not credit the destination twice and it applies the outstanding fee. — recovery repeats the work, never the effect.
  • Truncate an incomplete suffix before the later appends. A checksum mismatch, even in the last frame, stops the recovery instead of silently discarding history that might have been committed; the repair or restore needs a verified decision. — throwing away a broken history is easier than guessing, but guessing is wrong.
  • The destination tries to spend an arriving leg before the fee settles: it observes a partial payment. The guard is honest visibility semantics — a leg is spendable per-leg only by an explicit product rule, and the pending reservation keeps the unsettled remainder accounted until settle or compensation.

import java.io.*;
import java.nio.*;
import java.nio.channels.*;
import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.util.*;
import java.util.zip.CRC32;

// Teaching crash model: fsynced files survive a processor restart.
// The harness can inspect all logs at one logical boundary; this is NOT an
// atomic remote balance API or proof against power loss/directory-entry loss.
public class ShardPayDemo {
    record Decision(String id, long amount, long fee, boolean approved) {}
    final Path dir;
    final Map<String, Decision> decisions = new LinkedHashMap<>();
    final Map<String, Long> balances = new LinkedHashMap<>();
    final Set<String> seen = new HashSet<>(), settled = new HashSet<>();
    ShardPayDemo(Path dir) throws IOException {
        this.dir=dir; Files.createDirectories(dir);
        balances.put("src",1000L); balances.put("dst",100L); balances.put("fee",0L);
        for (String row : read("src")) {
            String[] t=row.split(" ");
            if (t[0].equals("D")) {
                Decision d=new Decision(t[1],Long.parseLong(t[2]),Long.parseLong(t[3]),Boolean.parseBoolean(t[4]));
                if (decisions.putIfAbsent(d.id,d)==null && d.approved)
                    balances.merge("src",-(d.amount+d.fee),Long::sum);
            } else if (t[0].equals("S")) settled.add(t[1]);
        }
        for (String shard : List.of("dst","fee"))
            for (String row : read(shard)) {
                String[] t=row.split(" "); String key=shard+":"+t[1];
                if (seen.add(key)) balances.merge(shard,Long.parseLong(t[2]),Long::sum);
            }
    }
    void append(String shard,String payload) throws IOException {
        byte[] p=payload.getBytes(StandardCharsets.UTF_8); CRC32 crc=new CRC32(); crc.update(p);
        ByteBuffer b=ByteBuffer.allocate(p.length+12).putInt(p.length).put(p).putLong(crc.getValue()); b.flip();
        try (FileChannel ch=FileChannel.open(dir.resolve(shard+".log"),StandardOpenOption.CREATE,StandardOpenOption.WRITE,StandardOpenOption.APPEND)) {
            while(b.hasRemaining()) ch.write(b);
            ch.force(true);
        }
    }
    List<String> read(String shard) throws IOException {
        Path path=dir.resolve(shard+".log"); List<String> rows=new ArrayList<>();
        if (!Files.exists(path)) return rows;
        ByteBuffer b=ByteBuffer.wrap(Files.readAllBytes(path)); int validEnd=0;
        while(b.hasRemaining()) {
            if(b.remaining()<4) break; // incomplete final frame
            int length=b.getInt();
            if(length<0 || length>1_048_576) throw new IOException("invalid length: fail closed");
            if(b.remaining()<length+8) break;
            byte[] payload=new byte[length]; b.get(payload); long expected=b.getLong();
            CRC32 crc=new CRC32(); crc.update(payload);
            if(crc.getValue()!=expected) throw new IOException("checksum mismatch: stop recovery");
            rows.add(new String(payload,StandardCharsets.UTF_8)); validEnd=b.position();
        }
        // Repair an incomplete suffix before accepting any new append.
        if(validEnd!=b.limit()) try(FileChannel ch=FileChannel.open(path,StandardOpenOption.WRITE)) {
            ch.truncate(validEnd); ch.force(true);
        }
        return rows;
    }
    void credit(String shard,String id,long amount) throws IOException {
        String key=shard+":"+id;
        if(seen.contains(key)) return;
        // The log record is the authority for BOTH the effect and dedup on replay.
        append(shard,"C "+id+" "+amount);
        seen.add(key); balances.merge(shard,amount,Long::sum);
    }
    void process(String id,long amount,long fee,int crashAfterLegs) throws IOException {
        if(amount<0 || fee<0) throw new IllegalArgumentException();
        Decision d=decisions.get(id);
        if(d==null) {
            d=new Decision(id,amount,fee,balances.get("src")>=amount+fee);
            // ONE durable record describes decision, reservation AND pending outputs.
            append("src","D "+id+" "+amount+" "+fee+" "+d.approved);
            decisions.put(id,d);
            if(d.approved) balances.merge("src",-(amount+fee),Long::sum);
        }
        if(d.amount!=amount || d.fee!=fee) throw new IllegalArgumentException("ID reused with different payload");
        if(!d.approved || settled.contains(id)) return;
        if(crashAfterLegs==0) return;
        credit("dst",id,d.amount); if(crashAfterLegs==1) return;
        credit("fee",id,d.fee); if(crashAfterLegs==2) return;
        append("src","S "+id); settled.add(id);
    }
    long inTransitAtCommonBoundary() {
        long pending=0;
        for(Decision d:decisions.values()) if(d.approved) {
            if(!seen.contains("dst:"+d.id)) pending+=d.amount;
            if(!seen.contains("fee:"+d.id)) pending+=d.fee;
        }
        return pending;
    }
    void checkConservation() {
        long total=balances.values().stream().mapToLong(Long::longValue).sum()+inTransitAtCommonBoundary();
        if(total!=1100) throw new AssertionError("conservation: "+total);
    }
    public static void main(String[] args) throws IOException {
        for(int cut=0;cut<=3;cut++) {
            Path dir=Files.createTempDirectory("shardpay-");
            ShardPayDemo first=new ShardPayDemo(dir); first.process("pay-1",200,5,cut);
            first.checkConservation();
            // Fresh processor: NO copying maps or dedup from the previous instance.
            ShardPayDemo restarted=new ShardPayDemo(dir); restarted.checkConservation();
            restarted.process("pay-1",200,5,3); restarted.process("pay-1",200,5,3);
            restarted.checkConservation();
            if(!restarted.balances.equals(Map.of("src",795L,"dst",300L,"fee",5L)) || restarted.inTransitAtCommonBoundary()!=0)
                throw new AssertionError("replay changed effects");
            System.out.println("PASS cut="+cut+" recovered="+restarted.balances+" pending=0");
        }
        Path dir=Files.createTempDirectory("shardpay-tail-");
        ShardPayDemo p=new ShardPayDemo(dir); p.process("pay-1",200,5,1);
        Files.write(dir.resolve("src.log"),new byte[]{0,0},StandardOpenOption.APPEND);
        ShardPayDemo repaired=new ShardPayDemo(dir); repaired.process("pay-1",200,5,3); repaired.checkConservation();
        byte[] corrupt=Files.readAllBytes(dir.resolve("src.log")); corrupt[4]^=1;
        Files.write(dir.resolve("src.log"),corrupt);
        boolean rejected=false;
        try { new ShardPayDemo(dir); } catch(IOException e) { rejected=true; }
        if(!rejected) throw new AssertionError("corruption silently accepted");
        System.out.println("PASS truncated suffix repaired; checksum corruption rejected");
    }
}

پیگیری (استف): مقصد برای همیشه بسته شده باشه؛ پرداخت pending رو چطور حل می‌کنی؟Follow-up (Staff): The destination account closes permanently. How do you resolve your pending transfer?

اول سرنوشت legهای قبلی را با شناسه‌هایشان reconcile کن؛ timeout به معنی اعمال‌نشدن نیست. مبلغی که هنوز هرگز credit نشده می‌تواند آزاد شود؛ اما مبلغ creditشده باید با یک debit جبرانیِ مجاز و بادوام در مقصد برگردد و بعد در مبدأ credit شود. compensation شناسه، نوع عملیات و dedup مستقل خودش را دارد؛ استفاده از همان کلید credit قبلی می‌تواند اشتباهی تکرارش کند. اگر برگشت مجاز یا ممکن نیست، یک وضعیت unresolved و مسیر عملیاتی لازم داری؛ refund بی‌قیدِ ۲۰۵ می‌تواند پول خلق کند.

Reconcile the earlier legs by identity first; a timeout never proves that something wasn't applied. Release the reservations that were never credited, but pull the credited money back with an authorized, durable compensating debit before you refund the source. Compensation needs its own operation type, its own identity and its own dedup; reusing the original credit key can quietly suppress it. If the reversal isn't available, keep an unresolved state and an operational recovery path. An unconditional 205 refund can create money out of nothing.

پیگیری (استف): بعد از بازیابی، پرداخت integral است، atomic است، یا هیچ‌کدام؟Follow-up (Staff): After the recovery, is the payment integral, atomic, or neither?

بعد از بازیابی کامل، integrity یعنی تصمیمِ واحد، اثرِ حداکثر یک‌بارهٔ هر leg و بقای اقتصادی در یک مرز مقایسهٔ معتبر. این مدل رؤیت اتمیک نمی‌دهد. برای دیدن یک snapshot مشترک، خوانندگان و نویسندگان باید یک پروتکل تراکنش/commit و snapshot یکسان داشته باشند؛ صرفِ اضافه کردنِ کلمهٔ consensus یا 2PC بدون قراردادِ خواندن، کافی نیست.

After a complete recovery, integrity means one decision, at-most-once leg effects and economic conservation at a valid comparison boundary. The model does not give you atomic visibility. A shared snapshot needs the readers and the writers to follow a common transaction/commit and snapshot protocol; dropping the words consensus or 2PC into the design without a read contract is not enough.

اشتباهات رایجCommon mistakes

  • پایدار خواندنِ الصاق خام فایل: بدون قاب‌بندی و checksum و fsync و یک گذر بازیابی که دم‌های پاره را می‌اندازد، crash وسط نوشتن پول می‌سازد یا گمش می‌کند. پایداری همان پروتکل چهاربخشی است، نه فراخوانیِ الصاق.
  • اتمیک خواندنِ همگرایی نهایی: جمع‌های متوازن یعنی خواننده‌ها همهٔ legها را با هم دیده‌اند نیست. بقاشده با حساب‌شده را وعده بده و مشاهده‌پذیریِ جزئی را صریح نام ببر.
  • بیرون گذاشتن پول معلق از حسابداری: پول بین رزرو و settle به سطر رزروِ نمایان تعلق دارد. پول در حال انتقالِ حساب‌نشده، بررسیِ جمع را دقیقاً وقتی می‌شکند که crash بیشترین نیاز را به آن دارد.
  • Calling a raw file append durable: without framing, a checksum, fsync and a recovery pass that discards torn tails, a crash mid-write invents money or loses it. Durability is that four-part protocol, not the append call.
  • Reading the final convergence as atomic visibility: balanced totals do not mean the readers saw all the legs together. Promise conserved plus accounted, and name the partial observability out loud.
  • Leaving the pending money out of the accounting: the funds between reserve and settle belong to a visible reservation row. In-flight money that nobody accounts for breaks the sum check exactly when a crash needs it most.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که: یک checker مستقل اجرا کن که لاگ مرجع را با کد جدا تا checkpoint اعلام‌شده بازپخش می‌کند، state واقعی را در همان checkpoint می‌خواند و فیلدبه‌فیلد مقایسه می‌کند. عقب‌مانده ولی سازگار یعنی lag — روی تابلو رصدش کن و page نکن؛ اختلاف در checkpoint یکسان یعنی corruption — به انسان page کن. یک update گمشده تزریق کن تا کارکرد تشخیص اثبات شود. تشخیص فقط page می‌کند؛ تعمیر پشت دروازه می‌ماند. و checker صادقانه می‌گوید چه چیزی را نمی‌تواند اثبات کند: لاگ ناقص، یا باگ مشترکِ هر دو مسیر کد. تریدآف: محاسبهٔ replay و دفترداریِ checkpoint در برابر تشخیص corruption خاموش که assertهای داخلی نمی‌دهند. — حسابرسی همان چیزی است که pager را به‌جای شلوغ‌کردن، مفید می‌کند.
Run an independent checker that replays the authoritative log with separate code up to a stated checkpoint, reads the actual state at that same checkpoint, and compares field by field. Behind-but-consistent means lag (track it on a board, don't page); a same-checkpoint difference means corruption (page a human). Inject a missing update to prove the detection works. Detection only pages — the repair stays gated — and the checker honestly names what it cannot prove: an incomplete log, or a bug shared by both code paths. The trade-off: replay compute and checkpoint bookkeeping in exchange for catching the silent corruption that inline asserts cannot. — an audit is what makes the pager worth trusting.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن دامنه‌اش تاریخچهٔ انتقاله: چهار انتقال آموزشی t1 تا t4 روی حساب‌های A=500 و B=300 و C=200. و نکتهٔ تلخ: derivation تحت حسابرسی بی‌صدا t3 رو می‌ندازه.
  • قضیه اینه که: checker هیچ کدی با derivation نداره — یه بازمحاسبهٔ مستقل‌نوشته‌شده از همون لاگ، که توی یه checkpoint اعلام‌شده (آفست ۴) مقایسه می‌شه.
  • و یه نکتهٔ آخر: checkpointها آفست‌های لاگ‌ان که هر دو طرف می‌تونن نام ببرن. نمایی که هنوز به checkpoint نرسیده، عقب است، نه خراب.
  • Picture the scope: the transfer history. Four teaching transfers t1..t4 over accounts A=500, B=300, C=200. And the sting: the derivation under audit silently drops t3.
  • The rule here: the checker shares no code with the derivation. It's an independently written recomputation from the same log, compared at one stated checkpoint (offset 4).
  • And one last thing: checkpoints are log offsets both sides can name. A view that hasn't reached the checkpoint yet is behind, not corrupt.

چرا این روش و این عددها؟Why this method and these numbers?

اگر checker و projection یک کد داشته باشند، یک باگ مشترک می‌تواند هر دو را به یک جواب غلط برساند؛ محاسبهٔ مستقل شانس کشف را بالا می‌برد. مقایسه در offset=4 یک انتخاب آموزشی است، چون t3 گم‌شده باید در هر دو طرف تا آن مرز پردازش شده باشد. اختلافِ قبل از هم‌مرزشدن می‌تواند فقط lag باشد. checksum سریع است ولی محل خطا را نمی‌گوید؛ برای repair باید تا bucket و بعد تا رکوردهای متفاوت پایین بروی. — سختیِ واقعی، تفکیک کردنِ دیری از خرابی است.

Sharing the derivation's code with the checker can reproduce the same bug twice; an independent recomputation improves the odds of catching it. Offset 4 is chosen because both sides should have processed the missing transfer t3 by then. A difference before that boundary may be nothing but lag. A checksum detects a mismatch quickly but doesn't locate it; for the repair you have to descend through the buckets to the individual records. — the hard part is telling lateness apart from corruption.

مدل ذهنیMental model

فرض کن یه صندوقدار دوم داری که همان نوار را با ماشین‌حساب خودش بازمی‌شمارد: به جمع‌های صندوقدار اول اعتماد نمی‌کند و هر ورودی را خودش تا شمارهٔ خط دایره‌شده بازپخش می‌کند و خط‌به‌خط مقایسه می‌کند. کشویی که فقط از برنامه عقب است دیر است، نه کسری. کشویی که روی خط دایره‌شده اختلاف دارد کسری است — و فقط کشوی کسری مدیر را بیدار می‌کند. ولی اگر خود نوار صفحه کم داشته باشد، بازشماری‌اش هیچ‌چیز اثبات نمی‌کند، و همین را بلند می‌گوید. — صادق بودن با مدیر، خودش بخشی از حسابرسی است.
A second cashier recounting the same tape with her own calculator: she doesn't trust the first cashier's totals, she replays every entry herself up to a circled line number, and compares line by line. A drawer that is merely behind schedule is late, not short. A drawer that disagrees on the circled line is short — and only a short drawer wakes the manager. But if the tape itself is missing pages, her recount proves nothing, and she says that out loud. — being straight with the manager is part of the audit.

حل گام‌به‌گامStep by step

  1. بازپخش مستقل تا checkpoint نکته‌ش اینه: checker لاگ مرجع را با کدی که خودت نوشته‌ای بازپخش می‌کند و دقیقاً در checkpoint اعلام‌شده (آفست ۴) می‌ایستد. تابع‌های derivation را هرگز import نمی‌کند — کد مشترک، نقاط کور مشترک می‌آورد. — دو نگاه مستقل، نه دو کپی از یک نگاه.
  2. مقایسه در یک نقطه، فیلدبه‌فیلد حالا بریم سراغ قسمت ظریف کار: state زندهٔ سنجاق‌شده در همان checkpoint خوانده و فیلدبه‌فیلد diff گرفته می‌شود. نمای عقب‌مانده ولی سازگار، به‌مثابه lag کران‌دار ثبت می‌شود؛ فقط اختلاف در checkpoint یکسان mismatch است — t3 افتادهٔ دمو دقیقاً همین‌جا روی A و C شلیک می‌کند. — دیر بودن جرم نیست؛ اختلاف جرم است.
  3. مسیریابی، و تعمیرِ دروازه‌دار راستش، اینجا بحثِ سلیقه نیست و بحثِ ترتیب است: mismatch می‌رود به pager و تعمیرِ تأییدِ انسانی که از لاگ بازپخش می‌شود؛ lag با روندش می‌نشیند روی تابلو. هزینه از تابلوی پیوسته به replay ساعتی به جمع‌های روزانه به بازبینی هر incident رشد می‌کند — درحالی‌که لاگ ناقص یا باگ مشترک بیرون هر بررسی می‌ماند و صریح نام برده می‌شود. — اول تشخیص، بعد تعمیر؛ نه برعکس.
  1. Replay to the checkpoint, independently Here's the trick: the checker replays the authoritative log with code you wrote yourself, and stops exactly at the stated checkpoint (offset 4). It never imports the derivation's functions — shared code would share the blind spots. — two independent looks, not two copies of one look.
  2. Compare at one point, field by field Now the delicate part: the live state is read pinned at the same checkpoint and diffed field by field. A behind-but-consistent view gets recorded as lag with a bound; only a same-checkpoint difference counts as a mismatch — the demo's dropped t3 fires on A and C exactly here. — being late is not a crime; being different is.
  3. Route the verdict, gate the repair Honestly, this part is about order, not taste: a mismatch goes to the pager and to a human-approved repair that replays through the log, while lag lands on the board with its trend. The cost grows from a continuous board to an hourly replay to daily sums to a per-incident review — while an incomplete log or a shared bug stays outside every check, named out loud. — detection first, repair second; never the other way round.

طراحی مشخصConcrete design

اجزا: لاگ ورودی مرجع با آفست‌های نام‌دار؛ derivation تحت حسابرسی؛ checker (باینری جدا و کد جدا)؛ تابلوی lag و pager. پروتکل: checker تا checkpoint با شماره N بازپخش می‌کند و state زندهٔ سنجاق‌شده در N را می‌خواند و فیلدبه‌فیلد diff می‌گیرد. تطابق با lag صفر سبز است؛ تطابق با lag ورودی تابلوست؛ هر diff در checkpoint یکسان page می‌کند. دروازهٔ تعمیر: تشخیص هیچ‌وقت state را بازنویسی نمی‌کند — انسان تعمیر را از diffِ checker تأیید می‌کند و خودِ تعمیر از لاگ بازپخش می‌شود. زمان‌بندی: تابلوی lag پیوسته، replayِ checkpoint ساعتی، جمع‌بندیِ total روزانه. — سه لایهٔ ارزان، و هیچ‌کدام بی‌خبر از کار نمی‌افتد.

Components: the authoritative input log with named offsets; the derivation under audit; the checker (separate binary, separate code); a lag board and a pager. Protocol: the checker replays to checkpoint N, reads the live state pinned at N, and diffs field by field. A match plus lag zero is green; a match with lag is a board entry; any same-checkpoint diff pages. Repair gate: detection never rewrites state — a human approves the repair from the checker diff, and the repair itself replays through the log. Schedule: the lag board runs continuous, the checkpoint replay is hourly, the totals sum-check is daily. — three cheap layers, and none of them quietly drops out of the job.

تضمین نشان‌نداده‌شده: برای دو جعبهٔ هلویی هیچ تشخیصی وعده نمی‌دهد: لاگ‌های ناقص و باگ‌های مشترک بیرون هر میله‌اند.

Which check runs most often for the least cost, and what does it keep off the pager?

Answer: The lag board: it runs continuously at the lowest cost, and it separates every benign behind-ness from real corruption.

خودآزماییSelf-check

دو یال از لاگ ورودی بیرون می‌روند. چه چیزی یکی را حسابرسی می‌کند، به‌جای این‌که تکراری‌اش کند؟

پاسخ: یال replay در برابر یال derivation: هر دو همان لاگ را می‌خوانند، ولی فقط مسیر checker مستقل نوشته شده — همان نامتقارنی، خودِ حسابرسی است.

Two edges leave the input log. What makes one of them an audit instead of a plain duplicate?

Answer: Replay edge versus derivation edge: both read the same log, but only the checker's path is written independently — that asymmetry is the audit itself.

گزینه‌های جایگزینAlternatives

  • assertionهای داخل خط derivation: ارزان‌ترین اجرا، ولی همان کد و همان نقاط کورِ خط را دارند — باگ مشترک از هر assert رد می‌شود. assertها را برای fail-fast نگه دار، ولی حسابرسیِ مستقل نیستند.
  • اجرای دوگانهٔ کامل با رأی (دو derivation مستقل و page روی هر اختلاف): قوی‌ترین تشخیص، تقریباً دو برابر محاسبه، به‌علاوهٔ قاعدهٔ تساوی‌شکن برای وقتی دو checker با هم اختلاف کنند. برای دفترکل‌های پول‌بر نگهش دار؛ تک-checker با تابلوی lag این‌جا پیش‌فرضِ متناسب است.
  • Inline assertions inside the derivation pipeline: the cheapest thing to run, but they share the same code and the same blind spots as the pipeline — a shared bug slips past every assert. Keep the asserts for fail-fast, but they are not an independent audit.
  • Full dual-run with a vote (two independent derivations, page on any disagreement): the strongest detection, roughly double the compute, plus a tie-break rule for when the two checkers disagree with each other. Reserve it for money-moving ledgers; the single checker plus a lag board here is the proportionate default.

سناریوهای خرابیFailure scenarios

  • update افتادهٔ خاموش (t3): در replayِ checkpoint بعدی، به‌مثابه mismatch در checkpoint یکسان روی A و C گرفته می‌شود. نگهبانش replay مستقلِ زمان‌بندی‌شده است — دمو دقیقاً همین را تزریق می‌کند.
  • اجرای checker روی آفست لاگِ تازه‌تر از state زنده‌ای که رسیده: هر مقایسه به‌غلط page می‌کند. نگهبانش سنجاق کردن هر دو خواندن به checkpoint اعلام‌شده است، و این‌که هر عقب‌ماندگی lag کران‌دار شمرده شود، هرگز corruption.
  • قطعی checker (بدون verdict در یک چرخه): سکوت مثل سلامتی به نظر می‌رسد. نگهبانش هشدار تازگی روی خودِ جریان verdict است — حسابرسیِ گمشده incident است، نه قبولی.
  • Silent dropped update (t3): the next checkpoint replay catches it as a same-checkpoint mismatch on A and C. The guard is the scheduled independent replay — the demo injects exactly this.
  • The checker runs against a newer log offset than the live state has reached: every comparison pages for nothing. The guard is pinning both reads to the stated checkpoint, and treating anything behind as lag with a bound — never as corruption.
  • Checker outage (no verdicts for a cycle): the silence looks like health. The guard is a freshness alert on the verdict stream itself — a missing audit is an incident, not a pass.

این کد آموزشی و ساده‌سازی‌شده است؛ فقط برای آشنایی با ایده. کد واقعی پروداکشن ملاحظات بسیار بیشتری دارد و هیچ‌کس این‌شکلی کد پروداکشن نمی‌زند.Simplified teaching code for building intuition only — not production code; nobody ships production code like this.

import java.util.*;

// Teaching demo: end-to-end audit checker over transfer histories.
// Independent recomputation to a STATED checkpoint; same-checkpoint compare;
// lag vs corruption distinguished; missing update injected; incomplete log admitted.
public class AuditDemo {
    record Xfer(String id, String from, String to, long amount) {}
    List<Xfer> log = new ArrayList<>(List.of(
        new Xfer("t1", "A", "B", 100), new Xfer("t2", "B", "C", 40),
        new Xfer("t3", "A", "C", 50), new Xfer("t4", "C", "A", 10)));

    // The REAL derivation under audit (has an injected silent bug: t3 skipped).
    Map<String, Long> derivedWithBug(int checkpoint) {
        Map<String, Long> b = new LinkedHashMap<>(Map.of("A", 500L, "B", 300L, "C", 200L));
        for (int i = 0; i < checkpoint; i++) {
            Xfer x = log.get(i);
            if (x.id.equals("t3")) continue; // SILENT DROPPED UPDATE (injected)
            b.put(x.from, b.get(x.from) - x.amount);
            b.put(x.to, b.get(x.to) + x.amount);
        }
        return b;
    }

    // The CHECKER: written independently, straight from the log. No shared code.
    static Map<String, Long> recompute(List<Xfer> log, int checkpoint) {
        Map<String, Long> b = new LinkedHashMap<>(Map.of("A", 500L, "B", 300L, "C", 200L));
        for (int i = 0; i < checkpoint; i++) {
            Xfer x = log.get(i);
            b.put(x.from, b.get(x.from) - x.amount);
            b.put(x.to, b.get(x.to) + x.amount);
        }
        return b;
    }

    public static void main(String[] a) {
        AuditDemo d = new AuditDemo();
        int cp = 4; // stated checkpoint: log offset 4
        Map<String, Long> actual = d.derivedWithBug(cp);
        Map<String, Long> expect = recompute(d.log, cp);
        System.out.println("checkpoint=" + cp + " actual=" + actual + " expected=" + expect);
        for (String k : expect.keySet())
            if (!expect.get(k).equals(actual.get(k)))
                System.out.println("MISMATCH at " + k + ": live=" + actual.get(k) + " recomputed=" + expect.get(k));
        // lag, not corruption: derived state is just older (checkpoint 2 vs 4)
        Map<String, Long> older = d.derivedWithBug(2);
        System.out.println("stale read cp=2 vs checkpoint 4 -> " + (older.equals(expect) ? "match" : "LAG (behind, not corrupt): " + older));
        // honest limit: if the input log itself is incomplete, the checker is blind
        List<Xfer> partial = d.log.subList(0, 3);
        System.out.println("log truncated to 3 entries: checker recomputes " + recompute(partial, 3));
        System.out.println("OK: caught silent t3 at same checkpoint; lag separated; incomplete log admitted");
    }
}

آزمون صحت و معیار عملیاتیCorrectness checks and operational criteria

ناورداها: توافق checker و derivation در هر checkpoint کامل در اجراهای سالم؛ هر verdict شناسهٔ checkpointش را دارد؛ بدون بررسی کامل بودن پیشوند لاگ هیچ verdictای صادر نمی‌شود. تست‌های خرابی: update افتاده تزریق کن و page را تأیید کن؛ نمای کهنه سرو کن و ورود تابلو بدون page را تأیید کن؛ لاگ را ببر و به‌جای verdict، «نامعلوم، لاگ ناقص» را تأیید کن؛ checker را ساکت کن و شلیک هشدار تازگی را تأیید کن. متریک‌ها: نرخ mismatch، توزیع lag هر نما، زمان تا تشخیص در هر سطح بررسی و تازگی verdict.
Invariants: the checker and the derivation agree at every completed checkpoint on healthy runs; every verdict names its checkpoint; there is no verdict without a completeness check on the log prefix. Failure tests: inject a dropped update and confirm the page; serve a stale view and confirm a board entry with no page; truncate the log and confirm 'unknown, log incomplete' instead of a verdict; silence the checker and confirm the freshness alert fires. Metrics: mismatch rate, lag distribution per view, time-to-detect per check tier, verdict freshness.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): لاگ ورودی خودش ناقص باشه؛ auditor دیگه چی رو نمی‌تونه ثابت کنه؟Follow-up (Staff): The input log itself is incomplete. What can your auditor no longer prove?

آن‌وقت فراتر از همان پیشوند هیچ‌چیز اثبات نمی‌کند — و باید همین را بلند بگوید. بازمحاسبه از لاگِ بریده مقادیر «موردانتظار»ِ غلط می‌دهد، بی‌تقصیرِ derivation؛ مقایسه‌شان به‌غلط page می‌کند و به تیم یاد می‌دهد pager را نادیده بگیرد. طراحی صادقانه: checker اول کامل بودن لاگ تا checkpoint را راستی‌آزمایی می‌کند (پیوستگی آفست و بدون شکاف) و وقتی پیش‌فرض شکست خورد، از دادن verdict خودداری می‌کند و می‌گوید «نامعلوم، لاگ ناقص». حسابرسی که ورودی‌اش را راستی‌آزمایی نکند، هیچ‌چیز را حسابرسی نمی‌کند.

Then it can prove nothing beyond that prefix — and it has to say so out loud. Recomputation from a truncated log yields 'expected' values that are wrong through no fault of the derivation; comparing them pages falsely and teaches the team to ignore the pager. The honest design: the checker first verifies the log's completeness to the checkpoint (offset continuity, no gaps), and when that premise fails it refuses to verdict and reports 'unknown, log incomplete'. An auditor that cannot verify its input audits nothing.

پیگیری (استف): derivation و checker یک باگ مشترک داشته باشند؛ حسابرسی می‌گیردش؟Follow-up (Staff): The derivation and the checker share one bug. Does the audit catch it?

نمی‌تواند — از روی ساخت. اگر هر دو مسیر همان بدخوانی را داشته باشند (همان کتابخانه، همان بدفهمیِ spec، همان تابع کپی‌شده)، خروجی‌هایشان توافق می‌کنند و حسابرسی روی state غلط سبز می‌شود. دفاع‌ها جزئی‌اند: checker را از spec بنویس، نه از کد خط؛ نویسندگی را بچرخان؛ یک جمع‌بندی total متفاوت بگذار (محاسبهٔ دیگری که بعضی باگ‌های مشترک را می‌گیرد)؛ و ریسک باقی‌مانده را در ران‌بوک نام ببر به‌جای ادعای استقلال کامل. عمق تشخیص متناسب با ناهمسانی واقعی است.

It cannot — by construction. If both paths share the same misreading (same library, same spec misunderstanding, same copied function), their outputs agree and the audit goes green over a wrong state. The defenses are partial: write the checker from the spec, not from the pipeline code; rotate the authorship; add a differently-shaped Totals sum-check (another computation that catches some shared bugs); and name the residual risk in the runbook instead of claiming full independence. The depth of your detection is proportional to the real dissimilarity.

اشتباهات رایجCommon mistakes

  • مقایسهٔ تازه‌ترین با تازه‌ترین به‌جای checkpoint یکسان: lag عادیِ replication مثل corruption page می‌کند، تیم pager را بی‌صدا می‌کند و mismatch واقعی در نویز پنهان می‌شود. اول checkpoint را سنجاق کن، بعد مقایسه کن.
  • استفادهٔ دوباره از تابع‌های خودِ خط داخل checker: حسابرسی تکراری می‌شود و باگ‌های مشترک بی‌صدا رد می‌شوند. استقلال یعنی کد جداگانه‌نوشته‌شده از spec، نه فراخوانیِ کتابخانهٔ مشترک.
  • تعمیر خودکار روی تشخیص: آن‌وقت باگِ checker یا جهش lag، state خوب را بازنویسی می‌کند. تشخیص page می‌کند؛ انسان تأیید می‌کند؛ تعمیر از لاگ بازپخش می‌شود — همیشه به همین ترتیب.
  • Comparing latest-against-latest instead of at the same checkpoint: normal replication lag pages as corruption, the team mutes the pager, and the real mismatch hides in the noise. Pin the checkpoint first, compare second.
  • Reusing the pipeline's own functions inside the checker: the audit becomes a duplicate, and the shared bugs pass silently. Independence means separately written code from the spec, not a shared library call.
  • Auto-repairing on detection: a checker bug or a lag spike then rewrites good state. Detection pages, a human approves, and the repair replays through the log — in that order, always.
