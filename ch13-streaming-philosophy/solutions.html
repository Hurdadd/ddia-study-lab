سؤال مصاحبهInterview question
فرض کن API انتقال بین دو حساب داری. request ID رو از client تا DB ببر. payload و نتیجه رو به ID بچسبون؛ UNIQUE، debit و credit و log باید اتمیک باشن. پاسخ commit گم‌شده و retry رو تحلیل کن و projection موجودی رو مستقل از log بساز.
Picture this, you're designing a transfer API between two accounts. You carry a request ID end to end, from client to DB. You bind payload and result to that ID; your UNIQUE constraint, debit and credit, and log commit together. You handle the lost commit response plus retry, and you rebuild balance projections independently from the log.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

اول سطر درخواست را با UNIQUE(request_id) در همان تراکنش بدهی و بستانکاری و سطر لاگ ورودی commit کن؛ payload و نتیجه را به همان شناسه bind کن. retry با همان شناسه نتیجه ذخیره‌شده را برمی‌گرداند بدون حرکت پول؛ همان شناسه با payload تازه رد می‌شود؛ همان payload با شناسه تازه یک انتقال عمدی تازه است. بالانس‌ها را فقط از لاگ بازسازی کن تا replay اثبات شود. تریدآف: یک سطر نوشتن اضافه و رقابت UNIQUE به‌ازای هر شناسه در برابر اثر دقیقاً-یک‌بار روی تحویلِ حداقل-یک‌بار.
Commit the request row FIRST under UNIQUE(request_id) in the same transaction as debit, credit and the input-log row; bind payload and result to that ID. A retry with the same ID returns the stored result without moving money; the same ID with a new payload is rejected; the same payload with a new ID is a new intentional transfer. Rebuild balances from the log alone to prove replay. The trade-off: one extra row write and UNIQUE contention per ID for an exactly-once effect over at-least-once delivery.

صورت مسئله و فرض‌هاProblem and assumptions

  • دامنه تک‌دفترکل: هر دو حساب در یک پایگاه داده‌اند، پس یک تراکنش می‌تواند درخواست و حرکت‌ها و لاگ را bind کند. legهای بین‌سیستمی تمرین ۳ است.
  • اعداد آموزشی: A=1000 و B=500 و req-7 دویست واحد می‌برد. اعداد کوچک بررسی replay را خوانا نگه می‌دارند؛ بنچمارک نیستند.
  • تحویل حداقل-یک‌بار: پاسخ می‌تواند گم شود، کلاینت‌ها با همان شناسه retry می‌کنند و رسیدن هم‌زمان تکراری‌ها ممکن است.
  • یک شناسه به‌ازای هر نیت کاربر، ساخته کلاینت (UUID). سرور برای retryهای کلاینت شناسه نمی‌سازد.
  • Single-ledger scope: both accounts live in one database, so one transaction can bind request, moves and log. Cross-system legs are exercise 3.
  • Teaching numbers: A=1000, B=500, req-7 moves 200. Small integers keep the replay check readable; they are not benchmarks.
  • At-least-once delivery: replies can be lost, clients retry with the same ID, and concurrently arriving duplicates are possible.
  • One ID per user intent, generated by the client (UUID). The server never invents IDs for client retries.

چرا این روش و این عددها؟Why this method and these numbers?

request_id هویت intent کاربر است، پس در retry ثابت می‌ماند؛ hash payload جلوی استفادهٔ همان ID برای intent متفاوت را می‌گیرد. دو حساب در یک DB هستند تا debit و credit و نتیجه در یک تراکنش commit شوند؛ جمع ۱۰۰۰+۵۰۰=۱۵۰۰ باید پس از انتقال ۲۰۰ ثابت بماند. این اعداد کوچک مشاهدهٔ invariant را ساده می‌کنند. دو DB مستقل همین مرز اتمیک را ندارند و به طراحی تمرین چندshardی نیاز دارند.

A request ID identifies user intent and stays fixed across retries; a payload hash detects reusing it for a different intent. Both accounts share a database so debit, credit and result commit together. The initial 1000+500=1500 remains conserved after transferring 200; small numbers make the invariant inspectable. Independent databases do not share this atomic boundary.

مدل ذهنیMental model

اداره پست با دفتر رسید: هر نامه پیش از حرکت پول یک رسید شماره‌دار می‌گیرد و رسید از قبل نتیجه را نام می‌برد. گم‌شدن کپی رسید هرگز پول را دوباره نمی‌فرستد — کارمند شماره را پیدا می‌کند و همان رسید را دوباره می‌دهد. نامه متفاوت شماره تازه می‌خواهد؛ همان شماره روی نامه متفاوت جعل است و رد می‌شود.
A post office with a receipt book: every letter gets a numbered receipt BEFORE any money moves, and the receipt already names the result. A lost copy of the receipt never re-sends the money — the clerk looks up the number and hands over the same receipt again. A different letter needs a new number; the same number on a different letter is forgery and gets rejected.

حل گام‌به‌گامStep by step

  1. اول INSERT، یک‌بار commit API یک تراکنش باز می‌کند، اول سطر درخواست را INSERT می‌کند، بعد بدهی و بستانکاری و سطر لاگ را می‌افزاید و commit می‌کند. یکتایی و حرکت پول و لاگ یک سرنوشت اتمی دارند.
  2. پاسخ گمشده می‌شود lookup commit موفق شد ولی پاسخ روی سیم مرد. کلاینت با همان شناسه و payload retry می‌کند؛ conflict یکتایی به سطر ذخیره‌شده می‌رسد که نتیجه‌اش عیناً برمی‌گردد. همان شناسه با payload عوض‌شده رد می‌شود؛ همان payload با شناسه تازه به‌عنوان نیت تازه پذیرفته می‌شود.
  3. replay دفترکل را اثبات می‌کند یک مصرف‌کننده جدا فقط ستون لاگ ورودی را می‌خواند و هر بالانس را بازمحاسبه می‌کند. اگر replay در آفست یکسان با حالت زنده فرق کند، آن باگ projection است نه lag — خط OK پایانی دمو دقیقاً همین بررسی است.
  1. INSERT first, commit once The API opens one transaction, INSERTs the request row first, then debits, credits and appends the log row, then commits. Uniqueness, money movement and the log share one atomic fate.
  2. Lost reply becomes a lookup Commit succeeded but the reply died on the wire. The client retries with the same ID and payload; the UNIQUE conflict routes to the stored row, whose result is returned verbatim. Same ID with a changed payload is rejected; the same payload under a new ID is honored as a new intent.
  3. Replay proves the ledger A separate consumer reads only the input-log column and recomputes every balance. If replay at the same offset ever differs from live state, that is a projection bug, not lag — the demo's final OK line is exactly this check.

طراحی مشخصConcrete design

جدول‌ها: requests(request_id PK, payload, status, result) و accounts(id, balance) که ستون درخواست‌ها هم نقش لاگ ورودی را دارد. API: POST /transfers {request_id, from, to, amount} با 200 {result} و 409 برای استفاده دوباره شناسه با payload متفاوت و 202 pending وقتی دوقلوی هم‌زمان هنوز در حال کار است. مسیر نوشتن: BEGIN، درج سطر درخواست، چک موجودی، UPDATE هر دو حساب، ذخیره نتیجه، COMMIT — یک تراکنش. مسیر خواندن: خواندن‌های صورت‌حساب از نمای بالانسِ بازسازی‌شده از لاگ می‌آیند؛ ممکن است با تأخیر کران‌دار و اندازه‌گیری‌شده از commit عقب باشند.

Tables: requests(request_id PK, payload, status, result), accounts(id, balance), and the requests column doubling as the input log. API: POST /transfers {request_id, from, to, amount} returns 200 {result}, 409 on ID reuse with a different payload, 202 pending while a concurrent twin is still working. Write path: BEGIN, INSERT request row, check funds, UPDATE both accounts, result stored, COMMIT — one transaction. Read path: statement reads come from the balance view rebuilt from the log; they may lag the commit by a bounded, measured delay.

مثال محاسبه‌شدهWorked example

اجرای آموزشی با A=1000 و B=500. req-7 دویست واحد می‌برد: commit پاسخ می‌دهد (بعد پاسخ انداخته می‌شود) و retry با DEDUP برمی‌گردد و بالانس‌ها همان ۸۰۰/۷۰۰ می‌مانند. استفاده دوباره req-7 برای ۹۹۹ رد می‌شود. req-8 تازه با همان payload دویست پذیرفته می‌شود: بالانس‌ها ۶۰۰/۹۰۰. replay مستقل از لاگ هم ۶۰۰/۹۰۰ می‌دهد — برابر، پس OK.

Teaching run with A=1000, B=500. req-7 moves 200: commit replies (then the reply is dropped), retry returns DEDUP with balances still 800/700. Reusing req-7 for 999 is REJECTED. A fresh req-8 with the same 200 payload is honored: balances 600/900. Independent replay from the log gives 600/900 — equal, so OK.

رد خرابی: باگ کلاینت را روی همان شکل دنبال کن: اگر retry شناسه تازه می‌آورد، INSERT دوم موفق می‌شد و پول دوبار می‌رفت — دفترکل وقتی کلاینت کلید را عوض کند retry را از نیت تازه تشخیص نمی‌دهد. payload یکسان کلید تکراریابی نیست؛ شناسه است.

تضمین نشان‌داده‌شده: شکل نشان می‌دهد یک شناسه در ثبت و گم‌شدن و retry یک بار اعمال می‌شود. جلوی پرداخت عمدی دوبار با دو شناسه را نمی‌گیرد.

تضمین نشان‌نداده‌شده: درباره legهای بین‌سیستمی (تمرین ۳) و این‌که نمای بالانس چقدر می‌تواند عقب باشد چیزی نمی‌گوید — تازگی قرارداد جداست.

Decision point: The UNIQUE constraint turns a retry into a key lookup: conflict means read the stored row, never touch the balances.

Failure trace: Trace the client bug on the same figure: if the retry carried a NEW id, the second INSERT would succeed and money would move twice — the ledger cannot tell a retry from a new intent when the client changes the key. Same payload is not the dedup key; the ID is.

Guarantee shown: The figure shows one ID applied once across submit, loss and retry. It does not stop a user from paying twice on purpose with two IDs.

Not shown: It says nothing about cross-system legs (exercise 3) or how far behind the balance view may lag — freshness is a separate contract.

خودآزماییSelf-check

یک retry می‌رسد درحالی‌که تلاش اول ممکن است commit شده باشد یا نه. API قبل از دست زدن به بالانس‌ها چه می‌کند؟

پاسخ: قبل از دست زدن به بالانس‌ها سطر درخواست را INSERT (یا conflict-check) کن؛ روی conflict برای payload یکسان نتیجه ذخیره‌شده را برگردان یا payload عوض‌شده را رد کن.

A retry arrives while the first attempt may or may not have committed. What does the API do before touching balances?

Answer: INSERT (or conflict-check) the request row before touching balances; on conflict, return the stored result for the same payload or reject a changed payload.

رد خرابی: ناسازگاری replay را روی همان شکل دنبال کن: اگر خروجی کار replay در یک آفست یکسان لاگ با دفترکل فرق کند، عیب باگ projection است نه lag — lag فقط نمای عقب‌مانده ولی سازگار را توضیح می‌دهد و تابلوی lag در تمرین ۴ دقیقاً همان را می‌پاید.

تضمین نشان‌داده‌شده: شکل نشان می‌دهد یک commit دو مصرف‌کننده مستقل را تغذیه می‌کند. تازه بودن نمای بالانس را قول نمی‌دهد — خواندن‌ها ممکن است عقب باشند.

تضمین نشان‌نداده‌شده: درباره مقیاس مصرف‌کننده replay یا توافق دفترکل‌های سیستم‌های مختلف چیزی نمی‌گوید — پارتیشن‌بندی و چندshardی تمرین‌های بعدی‌اند.

Decision point: One atomic commit, two consumers: the client reply reads the stored row, the replay job reads the log rows. Neither path writes fresh input.

Failure trace: Trace replay mismatch on the same figure: if the Replay job's output ever differs from the Ledger at the same log offset, the fault is a projection bug, not lag — lag only explains a behind-but-consistent view, and the lag board in exercise 4 watches exactly that.

Answer: The client result (from the stored request row) and the replay job (from the log rows). Fresh input enters through neither.

گزینه‌های جایگزینAlternatives

  • تکراریابی روی payload طبیعی (مبدأ، مقصد، مبلغ، پنجره): بدون تغییر کلاینت، ولی دو انتقال عمدی یکسان در یک پنجره به یکی فرومی‌روند — یک پرداخت واقعی بی‌صدا گم می‌شود. فقط وقتی نگه دار که تکرار هیچ‌وقت مشروع نیست؛ پول از آن‌ها نیست.
  • commit دوفازی بین سرویس موجودی و دفترکل: هزینه هماهنگی برای مسئله‌ای که یک تراکنش پایگاه داده همین‌جا حلش می‌کند. فقط وقتی به 2PC ارتقا بده که legها واقعاً در سیستم‌های مختلف‌اند — آن تمرین ۳ است نه این.
  • Dedup on the natural payload (from, to, amount, window): no client change, but two intentional identical transfers inside one window collapse into one — silently dropping a real payment. Reserve for cases where repeats are never legitimate; money is not one of them.
  • Two-phase commit across balance service and ledger: pays coordination cost for a problem one database transaction already solves here. Promote to 2PC only when legs genuinely live in different systems — that is exercise 3, not this one.

سناریوهای خرابیFailure scenarios

  • رسیدن هم‌زمان همان شناسه: هر دو INSERT مسابقه می‌دهند؛ قید یکتایی دقیقاً یکی را می‌پذیرد. بازنده باید سطر را بخواند — SUCCESS نتیجه ذخیره‌شده را برمی‌گرداند و PENDING با ۲۰۲ و محل poll — و هرگز نباید انتقال دوم محاسبه کند.
  • crash بین commit و پاسخ: در کلاینت از commit کند قابل‌تشخیص نیست. نگهبان همان retry با شناسه یکسان با نتیجه ذخیره‌شده است؛ کلاینت تردید را با پرس‌وجوی شناسه درخواست حل می‌کند نه با ساختن شناسه تازه.
  • lag یا توقف مصرف‌کننده replay: خواننده‌ها بالانس کهنه می‌بینند. نگهبان متریک lag کران‌دار با هشدار است؛ lag فقط نمای عقب‌مانده ولی سازگار را توضیح می‌دهد — اختلاف در آفست یکسان corruption است (تمرین ۴).
  • Concurrent same-ID arrivals: both INSERTs race; the UNIQUE constraint admits exactly one. The loser must read the row — SUCCESS returns the stored result, PENDING returns 202 plus a poll location — and must never compute a second transfer.
  • Crash between commit and reply: indistinguishable from a slow commit at the client. Guard is the same-ID retry plus the stored result; the client resolves doubt by querying the request ID, never by minting a new one.
  • Replay consumer lag or stall: readers see stale balances. Guard with a bounded lag metric and alert; lag explains behind-but-consistent views only — same-offset differences are corruption (exercise 4).

import java.util.*;

// Teaching demo: end-to-end request IDs (Example 13-2 pattern).
// One atomic commit binds UNIQUE(request_id) + debit/credit + input log.
// A lost commit reply + user retry must move money exactly once.
public class TransferDemo {
    static class Row { String payload; String status; String result; Row(String p){payload=p;status="PENDING";} }
    Map<String, Row> requests = new LinkedHashMap<>();
    Map<String, Long> balances = new LinkedHashMap<>(Map.of("A", 1000L, "B", 500L));
    List<String> inputLog = new ArrayList<>();

    // Returns the stored/fresh result string. Simulates one DB transaction.
    synchronized String submit(String id, String from, String to, long amount) {
        String payload = from + "->" + to + ":" + amount;
        Row old = requests.get(id);
        if (old != null) {
            if (!old.payload.equals(payload)) return "REJECTED: id reused with different payload";
            return "DEDUP: " + old.result; // same id + same payload -> stored result
        }
        Row row = new Row(payload);
        requests.put(id, row); // UNIQUE(request_id): a concurrent second insert fails here
        if (balances.get(from) < amount) { row.status = "FAILED"; row.result = "insufficient funds"; inputLog.add(id + "=FAIL"); return row.result; }
        balances.put(from, balances.get(from) - amount);
        balances.put(to, balances.get(to) + amount);
        row.status = "SUCCESS"; row.result = "moved " + amount + " " + from + "->" + to;
        inputLog.add(id + "=" + payload);
        return row.result;
    }

    // Independent consumer: rebuild balances ONLY from the input log.
    static Map<String, Long> replay(List<String> log) {
        Map<String, Long> b = new LinkedHashMap<>(Map.of("A", 1000L, "B", 500L));
        for (String e : log) {
            if (e.endsWith("=FAIL")) continue;
            String p = e.substring(e.indexOf('=') + 1); // from->to:amount
            String[] u = p.split("->|:");
            b.put(u[0], b.get(u[0]) - Long.parseLong(u[2]));
            b.put(u[1], b.get(u[1]) + Long.parseLong(u[2]));
        }
        return b;
    }

    public static void main(String[] a) {
        TransferDemo db = new TransferDemo();
        String r1 = db.submit("req-7", "A", "B", 200);
        System.out.println("first submit          = " + r1 + "   (reply LOST on the wire)");
        String r2 = db.submit("req-7", "A", "B", 200); // user retry, same id + same payload
        System.out.println("retry same id+payload = " + r2);
        System.out.println("reuse id, new payload = " + db.submit("req-7", "A", "B", 999));
        System.out.println("same payload, new id  = " + db.submit("req-8", "A", "B", 200) + " (independent transfer allowed)");
        System.out.println("balances              = " + db.balances + " (each id moved money exactly once)");
        Map<String, Long> rebuilt = replay(db.inputLog);
        System.out.println("replay from log       = " + rebuilt);
        System.out.println(rebuilt.equals(db.balances) ? "OK: replay matches live state" : "MISMATCH");
    }
}

آزمون صحت و معیار عملیاتیCorrectness checks and operational criteria

ناورداها: بقای جمع پول؛ هر شناسه درخواست حداکثر یک‌بار اعمال؛ replay در هر آفست برابر حالت زنده همان آفست. تست‌های خرابی: انداختن پاسخ commit و retry (با payload یکسان و عوض‌شده)؛ مسابقه دو ثبت هم‌زمان همان شناسه؛ متوقف کردن مصرف‌کننده replay و تأیید lag نه واگرایی برای خواننده‌ها. متریک‌ها: نرخ dedup-hit، نرخ conflict یکتایی و lag replay به ثانیه با کران هشدار.
Invariants: conservation of total funds; each request ID applied at most once; replay at any offset equals live state at that offset. Failure tests: drop the commit reply and retry (same and changed payloads); race two same-ID submits concurrently; stall the replay consumer and confirm readers see lag, not divergence. Metrics: dedup-hit rate, UNIQUE-conflict rate, replay lag in seconds with an alert bound.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (سینیور): دو درخواست هم‌زمان با یه ID برسن؛ پاسخ موفق یا pending رو چطور تعیین می‌کنی؟Follow-up (Senior): Two requests with the same ID arrive concurrently. How do you return success or pending?

قید یکتایی آن‌ها را سریال می‌کند: یک INSERT می‌برد و انتقال را اجرا می‌کند؛ دیگری conflict کلید می‌گیرد و سطر را می‌خواند. اگر سطر از قبل SUCCESS می‌گوید نتیجه ذخیره‌شده را برگردان. اگر هنوز PENDING می‌گوید (برنده وسط تراکنش است) ۲۰۲ در حال انجام با محل poll برگردان — و هرگز محاسبه دوم شروع نکن. حالت pending به timeout نیاز دارد: برنده crashکرده باید بالاخره سطرش را به FAILED بغلتاند تا منتظرها از poll دست بکشند.

The UNIQUE constraint serializes them: one INSERT wins and runs the transfer; the other gets a key conflict and reads the row. If the row already says SUCCESS, return the stored result. If it still says PENDING (the winner is mid-transaction), return 202 pending with a poll location — and never start a second computation. The pending state needs a timeout: a crashed winner must eventually roll its row to FAILED so waiters stop polling.

پیگیری (سینیور): کلاینت بعد از پاسخ گمشده هیچ‌وقت retry نمی‌کند. پول گم شده؟Follow-up (Senior): The client never retries after a lost reply. Is money lost?

retry نمی‌کند؛ پول قبلاً رفته. کلاینت با خواندن شناسه درخواست (GET /transfers/{id}) یا صورت‌حسابش قطعیت را برمی‌گرداند: نتیجه ذخیره‌شده همان رسید است. قاعده طراحی: هر پاسخ جهش‌دهنده شناسه درخواست را دارد تا پاسخ گمشده همیشه بدون نیت تازه قابل‌حل دوباره باشد.

It does not retry; the money already moved. The client recovers certainty by reading the request ID (GET /transfers/{id}) or its statement: the stored result is the receipt. Design rule: every mutating response includes the request ID, so a lost reply is always re-resolvable without a new intent.

اشتباهات رایجCommon mistakes

  • دو UPDATE لخت بدون سطر درخواست: retry از انتقال تازه قابل‌تشخیص نیست، پس پول دوبار می‌رود. سطر درخواست کلید تکراریابی است نه تزئین.
  • تکراریابی روی payload به‌جای شناسه: انتقال‌های عمدی یکسان بلعیده می‌شوند. payload یکسان مجاز است؛ شناسه یکسان یک‌بار است.
  • برگرداندن خطا روی conflict یکتایی به‌جای نتیجه ذخیره‌شده: کلاینت «قبلاً انجام شده» را از «شکست خورده» تشخیص نمی‌دهد و شناسه تازه می‌سازد — و همان خرج دوباره‌ای را می‌سازد که قید برای جلوگیریش بود.
  • Two bare UPDATEs with no request row: the retry cannot be distinguished from a new transfer, so money moves twice. The request row is the dedup key, not decoration.
  • Deduping on the payload instead of the ID: identical intentional transfers get swallowed. Same payload is allowed; same ID is once.
  • Returning an error on the UNIQUE conflict instead of the stored result: the client cannot tell 'already done' from 'failed' and mints a new ID — causing the very double-spend the constraint was meant to stop.

سؤال مصاحبهInterview question

Think of it, you're migrating a catalog with one shared input log and independent old and new projections. You define backfill, catch-up, shadow reads, canary routing, rollback, and when you retire the old view. You inject a projection bug and lag; and you keep write ownership and compatibility explicit.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

یک لاگ ورودی مشترک با دو projection مستقل نگه دار: نمای تخت قدیم سرو می‌دهد درحالی‌که نمای تازه جدول‌به‌علاوه‌جزئیات backfill می‌کند و به نوک می‌رسد و مقایسه سایه را در ترافیک زنده صفر می‌گذراند. خواندن‌ها را با flag برگشت‌پذیر شیفت بده — ۵٪ و ۵۰٪ و ۱۰۰٪ — فقط تا وقتی mismatch صفر و lag کران‌دار است؛ rollback یک چرخش flag است چون نمای قدیم هیچ‌وقت از سرو نایستاد. نمای قدیم را فقط بعد از معیارهای cutover به‌علاوه دوره نگه‌داشت بازنشسته کن. تریدآف: دو برابر هزینه projection و ذخیره‌سازی در مهاجرت در برابر rollback بدون دان‌تایم.
Keep one shared input log and two independent projections: the old flat view keeps serving while the new table-plus-details view backfills, catches up, and passes shadow comparison at 0% live traffic. Shift reads by a reversible flag — 5%, 50%, 100% — only while mismatches stay zero and lag stays bounded; rollback is one flag flip because the old view never stopped serving. Retire the old view only after cutover criteria plus a hold period. The trade-off: double projection cost and storage during migration for zero-downtime rollback.

صورت مسئله و فرض‌هاProblem and assumptions

  • دامنه کاتالوگ: schema تخت قدیم (یک سطر به‌ازای هر محصول) در برابر schema تازه (سطر به‌علاوه سطر جزئیات). سه محصول آموزشی: چراغ ۳۰، صندلی ۱۲۰، میز ۲۵۰.
  • مسیر نوشتن در مهاجرت هیچ‌وقت جابه‌جا نمی‌شود: همه ورودی تازه هنوز در لاگ مشترک می‌نشیند و هر دو projection مستقل مصرفش می‌کنند.
  • خواننده‌ها در canary هر دو schema را تحمل می‌کنند؛ flag درصد را تعیین می‌کند. rollback فقط تا وقتی ممکن می‌ماند که نوشتن‌های تازه old-readable بمانند.
  • Catalog scope: flat old schema (one row per product) versus new schema (row plus details row). Three teaching products: Lamp 30, Chair 120, Desk 250.
  • The write path never moves during migration: all fresh input still lands in the shared log, and both projections consume it independently.
  • Readers tolerate either schema during canary; the flag decides the percent. Rollback stays possible only while new writes remain old-readable.

چرا این روش و این عددها؟Why this method and these numbers?

shared log همهٔ تغییرها را به دو projection می‌رساند تا dual write مستقل شکاف نسازد. مقایسه در checkpoint مشترک لازم است چون نمای عقب‌مانده با نمای خراب فرق دارد. درصد canary فرض مدیریت ریسک است: مرحله را وقتی افزایش بده که mismatch، lag و خطای هر cohort داخل معیار باشد؛ گذشتن چند دقیقه به‌تنهایی کافی نیست. rollback فقط تا وقتی معتبر است که مسیر قدیم دادهٔ تازه را بفهمد؛ حذف زودهنگام فیلدها آن را می‌بندد.

A shared log feeds both projections without independent dual-write gaps. Compare at a common checkpoint to distinguish lag from corruption. Canary percentages manage exposure: advance only when mismatch, lag and per-cohort errors meet criteria, not merely after elapsed time. Rollback requires the old path to understand new data; early field removal closes that option.

مدل ذهنیMental model

دو ریل درحالی‌که قطار همچنان می‌رود: ریل قدیم همه مسافرها را می‌برد درحالی‌که ریل تازه کنارش کشیده می‌شود، با واگن‌های خالی تست می‌شود (سایه)، بعد چند واگن (canary) و بعد کل ترافیک. ریل قدیم فقط بعد از این‌که تازه کل بار را در یک جدول زمانی کامل برد جمع می‌شود — و تا آن موقع برگشتن فقط سوزن ریل است.
Two rails while the train keeps running: the old rail carries every passenger while the new rail is laid beside it, tested with empty cars (shadow), then a few cars (canary), then all traffic. The old rail is torn up only after the new one has carried full load through a whole timetable — and until then, switching back is just points on the track.

حل گام‌به‌گامStep by step

  1. backfill و بعد catch-up هر دو projector همان لاگ را از اولین آفست مصرف می‌کنند: اول تاریخچه انبوه و بعد catch-up جریانی تا نوک. نمای قدیم همه‌حال صددرصد خواندن‌ها را سرو می‌دهد؛ هیچ‌چیز مسیر نوشتن عوض نمی‌شود.
  2. سایه پیش از canary هر خواندن روی هر دو نما اجرا می‌شود ولی فقط جواب قدیم سروشده می‌شود؛ اختلاف‌ها به‌عنوان mismatch سایه شمرده می‌شوند. درصد canary تا وقتی mismatch غیرصفر است یا lag هر نما از کرانش بگذرد صفر می‌ماند — باگ افتادن جزئیات دمو دقیقاً همین‌جا می‌میرد.
  3. canary و cutover و بازنشستگی دیر flag روی صفر mismatch و lag کران‌دار از ۵ به ۵۰ به ۱۰۰ می‌رود؛ هر پسرفتی آن را در یک حرکت به صددرصد قدیم برمی‌گرداند. بعد از معیارها به‌علاوه دوره نگه‌داشت در ۱۰۰٪، projector قدیم را متوقف کن و یک snapshot را در نگهداری نگه دار و بعد بازنشسته کن.
  1. Backfill, then catch up Both projectors consume the same log from the first offset: bulk history first, then streaming catch-up to the tip. The old view keeps serving 100% of reads the whole time; nothing about the write path changes.
  2. Shadow before canary Every read runs against both views but only the old answer is served; differences are counted as shadow mismatches. The canary percent stays 0 while mismatches are nonzero or either view's lag exceeds its bound — the demo's dropped-details bug dies exactly here.
  3. Canary, cutover, retire late The flag walks 5 to 50 to 100 on zero mismatches and bounded lag; any regression flips it to 100% old in one move. After criteria plus a hold period at 100%, stop the old projector, keep one snapshot through retention, then retire.

طراحی مشخصConcrete design

اجزا: یک لاگ ورودی فقط‌افزودنی؛ دو projector مستقل (تخت قدیم و شکافته تازه)؛ دو نما؛ یک flag ترافیک (درصد هر نما، قابل‌چرخش در یک انتشار). API: خواندن‌های لیست محصول نسخه ندارند — مسیریاب نما را انتخاب می‌کند؛ نوشتن‌ها همیشه به شکل لاگی می‌روند که هر دو projector می‌فهمند. معیارهای cutover: صفر mismatch سایه در یک چرخه کاری کامل، lag نمای تازه زیر SLO خواندن، به‌علاوه دوره نگه‌داشت در ۱۰۰٪ پیش از انداختن نمای قدیم. مالکیت: لاگ مالک مسیر نوشتن است؛ هیچ نمایی حق نوشتن مستقیم ندارد.

Components: one append-only input log; two independent projectors (old-flat, new split); two views; one traffic flag (percent per view, flippable in one deploy). API: product-list reads carry no version — the router picks the view; writes always target the log shape both projectors understand. Cutover criteria: zero shadow mismatches over a full business cycle, new-view lag under the read SLO, plus a hold period at 100% before the old view is dropped. Ownership: the log owns the write path; neither view may accept direct writes.

گزینه‌های جایگزینAlternatives

  • cutover یک‌باره (توقف نوشتن، مهاجرت، شروع دوباره): ساده‌ترین برای استدلال، ولی قطعی نوشتن می‌خواهد و rollbackای جز برگشت از بکاپ ندارد. فقط برای کاتالوگ‌های کوچک با پنجره نگهداری اعلام‌شده قابل‌قبول است؛ وگرنه هزینه دو نما قیمت صادقانه دان‌تایم صفر است.
  • بازنویسی درجا (ALTER TABLE با backfill درجا): نصف ذخیره‌سازی، ولی خواننده‌ها schema نیمه‌مهاجرت‌شده می‌بینند و rollback یعنی بازنویسی دیگر. وقتی تغییر افزایشی و backward-readable است ترجیح بده؛ وقتی شکل تازه old-readable نیست نماهای دوگانه را نگه دار.
  • Big-bang cutover (stop writes, migrate, restart): simplest to reason about, but needs a write outage and has no rollback except restoring from backup. Acceptable only for tiny catalogs with a declared maintenance window; otherwise the dual-view cost is the honest price of zero downtime.
  • In-place row rewrite (ALTER TABLE + backfill in place): half the storage, but readers see a half-migrated schema and rollback means another rewrite. Prefer when the change is additive and backward-readable; keep dual views when the new shape is not old-readable.

سناریوهای خرابیFailure scenarios

  • باگ در projection تازه (افتادن جزئیات): با مقایسه سایه در ترافیک زنده صفر گرفته می‌شود. نگهبان دروازه صفر-mismatch پیش از هر درصد canary است — دمو دقیقاً همین باگ را تزریق می‌کند.
  • lag نمای تازه فراتر از SLO خواندن: خواندن‌های canary سطرهای کهنه را مثل تازه سرو می‌کنند. نگهبان متریک lag کران‌دار هر نماست؛ تا هر نما عقب است flag را بلوکه کن.
  • توقف بی‌صدای projector قدیم وسط مهاجرت: هدف rollback کهنه می‌شود. نگهبان projection هر دو نما از watermark نوک یکسان با هشدار عقب‌ماندگی نمای قدیم است — rollback فقط تا وقتی فوری است که به‌روز باشد.
  • Bug in the new projection (dropped details): caught by shadow compare at 0% live. Guard is zero-mismatch gating before any canary percent — the demo injects exactly this bug.
  • New-view lag beyond the read SLO: canary reads would serve stale rows as if they were fresh. Guard with a bounded lag metric per view; block the flag while either view is behind.
  • Old projector silently stalls mid-migration: rollback target goes stale. Guard by projecting both views from the same tip watermark and alerting when the old view falls behind — rollback is only instant while it is current.

import java.util.*;

// Teaching demo: dual-schema migration from one shared input log.
// Old flat projection vs new (table + details) projection, % traffic,
// shadow compare, deliberate bug in the new projection, rollback.
public class MigrationDemo {
    record Upsert(String id, String name, long price, String detail) {}
    // old view: flat row per product. new view: row + details row.
    Map<String, String> oldView = new LinkedHashMap<>();
    Map<String, String> newView = new LinkedHashMap<>();
    Map<String, String> newDetails = new LinkedHashMap<>();
    List<Upsert> log = new ArrayList<>(List.of(
        new Upsert("p1", "Lamp", 30, "warm LED"),
        new Upsert("p2", "Chair", 120, "oak"),
        new Upsert("p3", "Desk", 250, "standing")));

    void projectOld(Upsert u) { oldView.put(u.id, u.name + "|" + u.price); }
    void projectNew(Upsert u, boolean buggy) {
        newView.put(u.id, u.name + "|" + u.price);
        // BUG (injected): details dropped when price > 100
        if (!(buggy && u.price > 100)) newDetails.put(u.id, u.detail);
    }

    public static void main(String[] a) {
        MigrationDemo m = new MigrationDemo();
        // backfill + catch-up: both projections consume the same log
        for (Upsert u : m.log) { m.projectOld(u); m.projectNew(u, true); }
        System.out.println("backfill done: old=" + m.oldView.size() + " new=" + m.newView.size());
        // shadow read: compare every read against the old view (0% live traffic yet)
        int mism = 0;
        for (String id : m.oldView.keySet())
            if (!m.newDetails.containsKey(id)) { mism++; System.out.println("shadow mismatch: " + id + " details missing in new view"); }
        System.out.println("shadow mismatches = " + mism + " -> canary BLOCKED, stays 0%");
        // fix projection, re-project from the same log (replay, not patch)
        m.newView.clear(); m.newDetails.clear();
        for (Upsert u : m.log) m.projectNew(u, false);
        mism = 0;
        for (String id : m.oldView.keySet()) if (!m.newDetails.containsKey(id)) mism++;
        System.out.println("after fix: mismatches = " + mism + " -> canary 5% -> 50% -> 100%");
        // rollback drill: flag back to 100% old; old view untouched throughout
        String flag = "new";
        flag = "old"; // one flag flip
        System.out.println("rollback: traffic flag = " + flag + " (old view served reads all along: " + m.oldView.size() + " rows)");
        System.out.println("OK: write path never moved; old view retired only after cutover criteria held");
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): کاربر بعد از خوندن schema جدید داده‌ای بنویسه که نسخه قدیم نمی‌فهمه؛ rollback هنوز ممکنه؟Follow-up (Staff): A client writes data the old schema can't represent after reading the new schema. Is rollback still possible?

نه همیشه. اگر کلاینت فقط schema تازه را خوانده باشد rollback هنوز یک چرخش flag است. ولی اگر داده‌ای نوشته که schema قدیم نمی‌تواند نمایش دهد (فیلد اجباری تازه یا شکافی که سطر تخت نمی‌گیرد)، برگشتن یا آن داده را می‌اندازد یا غلط سرو می‌کند. نگهبان: در canary نوشتن‌ها باید old-readable بمانند (فیلدهای تازه اختیاری و نادیده‌گرفته‌شده توسط projector قدیم) یا کار forward-fill باشد که شکل تازه را پیش از rollback به نمای قدیم برگرداند. اگر هیچ‌کدام نیست صریح بگو: rollback از آن نوشتن به بعد خراب است و تنها راه برگشت اصلاح روبه‌جلوست.

Not always. If the client only READ the new schema, rollback is still one flag flip. But if it WROTE data the old schema cannot represent (a new required field, a split the flat row cannot hold), flipping back either drops that data or serves it wrongly. Guard: during canary, writes must stay old-readable (new fields optional/ignored by the old projector), or carry a forward-fill job that backfills the new shape into the old view before any rollback. If neither holds, say so: rollback is broken from that write on, and the only way back is forward-fix.

پیگیری (استف): دقیقاً کی نمای قدیم را حذف می‌کنی؟Follow-up (Staff): When exactly do you delete the old view?

بعد از پایداری معیارها: خواندن صددرصد تازه در یک چرخه کاری کامل با صفر mismatch و lag داخل SLO و بدون rollback در پنجره نگه‌داشت. بعد projector قدیم را متوقف کن و آخرین snapshotش را یک دوره نگهداری دیگر نگه دار (بیمه ارزان) و فقط بعد حذف کن. بازنشستگی فقط با درصدهای canary — بدون نگه‌داشت — اگر باگ کندسوز یک هفته بعد سر بزند تو را بی‌پناه می‌گذارد.

After the criteria hold: 100% new reads for a full business cycle with zero mismatches, lag inside SLO, and no rollback in the hold window. Then stop the old projector, keep its last snapshot for one more retention period (cheap insurance), and only then delete. Retiring on canary percentages alone — without the hold — strands you if a slow-burn bug surfaces a week later.

اشتباهات رایجCommon mistakes

  • مهاجرت خواندن‌ها پیش از بازپخش تاریخچه توسط نمای تازه: درصدهای canary روی نمای ناقص جواب‌های غلط مطمئن سرو می‌کنند. اول backfill با catch-up، بعد درصدها.
  • گذاشتن نوشتن مستقیم در نماها حین مهاجرت: projectionها از لاگ واگرا می‌شوند و replay دیگر هیچ نمایی را بازنمی‌سازد. همه ورودی تازه از لاگ می‌رود، بدون استثنا.
  • بازنشستگی نمای قدیم در canary صددرصد بدون دوره نگه‌داشت: rollback همان روزی می‌میرد که باگ کندسوز به آن نیاز دارد. اول معیارهای cutover با نگه‌داشت، بعد بازنشستگی.
  • Migrating reads before the new view has replayed history: canary percentages over an incomplete view serve confident wrong answers. Backfill plus catch-up first, percentages second.
  • Letting views accept direct writes during migration: the projections diverge from the log and replay can no longer rebuild either view. All fresh input goes through the log, no exceptions.
  • Retiring the old view at 100% canary without a hold period: rollback dies the same day a slow-burn bug needs it. Cutover criteria plus hold, then retire.

Here's the thing, you're designing source, destination, and fee transfers with three logs and deterministic processing. You pin down framed checksummed records with fsync, reserved funds, a persistent decision, an outbox, and dedup. You recover after publishing only some outputs. And you spell out the difference between pending funds, final integrity, and atomic visibility.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

تصمیم، رزرو و تعهد انتشار legها را در یک رکورد قاب‌بندی‌شده و checksumدار، پیش از ACK با fsync ثبت کن. مقصد اثر و dedup همان leg را از یک لاگ پایدار بازسازی می‌کند. پس از restart، تصمیم دوباره گرفته نمی‌شود؛ همان خروجی‌ها با dedup بازپخش می‌شوند. pending هر leg فقط تا پیش از اعمال آن حساب می‌شود. این مدل همگرایی نهایی دارد؛ خواندن‌های مستقل shardها رؤیت اتمیک نمی‌دهند.
Persist the decision, reservation and output obligations in one framed, checksummed record, fsynced before ACK. Each destination rebuilds its leg effect and dedup from one durable log. Restart replays the stored decision and outputs without re-deciding. Count a leg as pending only until it has applied. This provides eventual convergence under recovery/delivery assumptions, not atomic visibility across independent shard reads.

صورت مسئله و فرض‌هاProblem and assumptions

  • سه shard هرکدام با یک پردازنده تک‌نخ (مبدأ و مقصد و کارمزد). رهبر هر shard مالک leg خودش است؛ هیچ تراکنشی روی shardها کشیده نمی‌شود.
  • مبدأ ۱۰۰۰ و مقصد ۱۰۰ دارد؛ پرداخت ۲۰۰ با کارمزد ۵ است. invariant در مرز منطقی مشترک، مجموع موجودی‌ها به‌علاوه فقط legهای اعمال‌نشده برابر ۱۱۰۰ است.
  • دیسک‌ها می‌توانند وسط نوشتن crash کنند و پردازنده‌ها وسط انتشار بمیرند؛ شبکه ممکن است تکراری بدهد ولی رکوردهای قاب‌بندی‌شده را خراب نمی‌کند (CRC خرابی را رد می‌کند).
  • Three shards with one single-threaded processor each (source, destination, fee). Each shard's leader owns its leg; no transaction spans shards.
  • Source starts at 1000, destination at 100; payment is 200 plus fee 5. At a common logical boundary, balances plus only unapplied legs sum to 1100.
  • Disks can crash mid-write and processors can die mid-publish; the network may duplicate but not corrupt framed records (CRC rejects corruption).

چرا این روش و این عددها؟Why this method and these numbers?

framing مرز رکورد، checksum خرابی بایت و fsync درخواست دوام پیش از ACK را مشخص می‌کنند؛ هیچ‌کدام به‌تنهایی تراکنش چندshardی نیست. تصمیم پایدار از تغییر نظر پس از restart جلوگیری می‌کند و dedup پایدار مانع دوباره‌اعمال‌شدن leg می‌شود. ۱۰۰۰+۱۰۰=۱۱۰۰ کل اولیه است؛ پس از اعتبار مقصد ۲۰۰، فقط کارمزد ۵ هنوز در راه است، نه تمام ۲۰۵. جمعِ خواندن‌های مستقل در لحظه‌های مختلف شاهد conservation نیست؛ در دمو از logهای بازیابی‌شده در مرز منطقی مشترک استفاده می‌کنیم.

Framing identifies record boundaries, checksums detect byte corruption and fsync requests durability before ACK; none creates a cross-shard transaction. Durable decisions prevent re-deciding after restart; durable dedup prevents duplicate legs. The initial total is 1000+100=1100. After crediting 200 to the destination, only fee 5 remains in transit, not all 205. Independent reads at different instants do not prove conservation; compare recovered logs at a common logical boundary.

مدل ذهنیMental model

سه صندوقدار در سه باجه با یک بلیت شماره‌دار: صندوقدار اول کیفت را چک می‌کند و APPROVED را روی ته‌بلیت مهر می‌زند و پولت را در جعبه شیشه‌ای که همه می‌بینند قفل می‌کند. پیک‌ها کپی همان بلیت را به باجه‌های دیگر می‌برند؛ هر کپی تکراری دم در پاره می‌شود. اگر پیکی زمین بخورد، پیک تازه ته‌بلیت را بازمی‌خواند — هرگز دوباره تصمیم نمی‌گیرد — و فقط کپی‌های نرسیده دوباره می‌روند. جعبه شیشه‌ای فقط وقتی باز می‌شود که هر باجه تأیید کند.
Three cashiers in three booths, one numbered ticket: the first cashier checks your wallet, stamps APPROVED on the ticket stub, and locks your cash in a glass box everyone can see. Runners carry copies of the same ticket to the other booths; any duplicate copy is torn up at the door. If a runner trips, a new runner re-reads the stub — he never re-decides — and only the undelivered copies go out again. The glass box opens only when every booth confirms.

حل گام‌به‌گامStep by step

  1. قاب‌بندی و checksum و fsync length مرز رکورد را مشخص می‌کند، CRC خرابی payload را می‌یابد و force پیش از ACK، داده را از buffer فرایند خارج می‌کند. recovery فقط suffix ناقص را truncate می‌کند؛ checksum خراب یا طول نامعتبر باعث توقف و بررسی می‌شود. این دمو دوام در crash پردازنده با دیسک باقی‌مانده را می‌آزماید.
  2. یک‌بار تصمیم و رزرو نمایان یک رکورد D تصمیم، مبلغ رزرو و خروجی‌های لازم را ثبت می‌کند. replay همان رکورد کسر موجودی و obligationها را بازسازی می‌کند؛ بنابراین شکاف میان لاگ تصمیم و state جدا نداریم.
  3. انتشار و dedup و همگرایی legها با کلید (shard,payment_id) ارسال می‌شوند. مقصد از رکورد C هم اعتبار و هم dedup را بازسازی می‌کند؛ retry می‌تواند همهٔ legها را دوباره بفرستد و مقصد تکرار را حذف می‌کند. هر leg اعمال‌شده از مبلغ in-transit کم می‌شود؛ این جمع در مرز مشترک harness حساب می‌شود، نه از خواندن تصادفی چند shard.
  1. Frame, checksum, fsync Length identifies record boundaries, CRC detects corrupt payloads and force precedes ACK. Recovery truncates an incomplete suffix only; checksum mismatches or invalid lengths stop recovery. This demo tests processor restart with surviving files.
  2. Decide once, reserve visibly One D record persists the decision, reservation amounts and required outputs. Replaying it reconstructs source debit and obligations, avoiding a gap between a decision log and separately stored state.
  3. Publish, dedup, converge Publish legs keyed by (shard,payment_id). Each C record reconstructs both credit and dedup; replay may resend all legs and destinations absorb repeats. Remove applied legs from in-transit value at the harness’s common logical boundary, not from arbitrary cross-shard reads.

طراحی مشخصConcrete design

لاگ src رکورد D(id,amount,fee,approved) دارد؛ همان رکورد مرجع تصمیم، کسر موجودی و تعهد ارسال است. لاگ‌های dst و fee هرکدام C(id,amount) دارند و replay همان رکورد هم effect و هم dedup را می‌سازد. src با S(id) پایان انتشار را ثبت می‌کند. framing شامل length/payload/CRC است و ACK بعد از force(true) می‌آید؛ دم ناقص پیش از append بعدی truncate می‌شود و checksum ناسازگار بازیابی را متوقف می‌کند. دمو crash پردازنده با فایل‌های باقی‌مانده را مدل می‌کند؛ دوام در قطع برق و directory fsync روی فایل‌های تازه نیاز به آزمون filesystem و runbook جدا دارد.

در harness می‌توان لاگ‌ها را در مرز منطقی مشترک خواند و فقط legهای اعمال‌نشده را pending دانست؛ این قابلیت، API اتمیک برای balanceهای توزیع‌شده نیست. در production باید وضعیت pending/settled، ACK هر leg و reconciliation را با شناسهٔ پایدار طراحی کرد.

The src log records D(id,amount,fee,approved), the authority for decision, reservation and publication obligations. The dst and fee logs record C(id,amount); replay reconstructs both effects and dedup. Src records S(id) after publication. Frames contain length/payload/CRC with force(true) before ACK. Recovery truncates incomplete suffixes before later appends and stops on checksum mismatch. The demo models processor crashes with surviving files; power-loss durability and directory fsync for new files require separate filesystem testing.

The harness inspects logs at a common logical boundary and counts only unapplied legs as pending. This is not an atomic distributed balance API. Production pending/settled states, per-leg ACKs and reconciliation need persistent identities and explicit protocols.

مثال محاسبه‌شدهWorked example

پس از رزرو، src=795 و dst=100 و fee=0 و مبلغ در راه ۲۰۵ است؛ جمع ۱۱۰۰ می‌شود. پس از credit مقصد، dst=300 و فقط ۵ کارمزد در راه است؛ نگه‌داشتن ۲۰۵ به‌عنوان پول در راه دوباره‌شماری است. پس از recovery و اعمال کارمزد، src=795,dst=300,fee=5 و pending=0 داریم. پردازندهٔ تازه فقط فایل می‌خواند؛ هیچ map از فرایند قبلی کپی نمی‌شود.

After reservation: src=795, dst=100, fee=0, in-transit=205, total=1100. After destination credit: dst=300 and only fee 5 remains in transit; counting all 205 again double-counts money. Recovery applies the fee, yielding src=795,dst=300,fee=5,pending=0. A fresh processor reads files only; no prior process maps are copied.

خودآزماییSelf-check

بعد از crash وسط انتشار، کدام دو سازوکار restart را بدون اعمال دوباره همگرا می‌کنند؟

پاسخ: تصمیم ذخیره‌شده (بازخوانی، هرگز بازمحاسبه) با dedup هر leg روی همان شناسه: تکرارها نادیده گرفته و legهای گمشده بازپخش می‌شوند.

After a mid-publish crash, what two mechanisms make the restart converge without double-applying?

Answer: The stored decision (re-read, never recomputed) plus per-leg dedup on the same ID: repeats are ignored, missing legs are replayed.

گزینه‌های جایگزینAlternatives

  • 2PC روی سه shard: رؤیت اتمیک واقعی، ولی هر پرداخت هزینه هماهنگی بین‌شاردی می‌دهد و دسترس‌پذیری کندترین shard را به ارث می‌برد. فقط وقتی انتخابش کن که خواننده‌ها هیچ‌وقت نباید پرداخت جزئی ببینند (نادر)؛ وگرنه پروتکل مرحله‌ای با جبران ارزان‌تر و دردسترس‌تر است.
  • پول تک‌شارد (عبور هر حساب از یک shard دفترکل): با shard نکردن اتمیک بودن را نگه می‌دارد و توان را به یک ماشین سقف می‌زند. تا وقتی نرخ می‌گنجد نگه دار؛ روزی که نگنجید بر اساس حساب shard کن و پروتکل بالا را بپرداز.
  • 2PC across the three shards: real atomic visibility, but every payment pays cross-shard coordination and inherits the slowest shard's availability. Choose it only when readers must never observe a partial payment (rare); otherwise the staged protocol plus compensation is cheaper and more available.
  • Single-shard money (route every account through one ledger shard): keeps atomicity by refusing to shard, and caps throughput at one machine. Keep while the rate fits; shard by account the day it does not, and pay the protocol above.

سناریوهای خرابیFailure scenarios

  • crash منطقی بعد از credit مقصد: پردازندهٔ تازه تصمیم و dedup را از فایل می‌خواند و replay می‌کند؛ credit مقصد تکرار نمی‌شود و کارمزد باقی‌مانده اعمال می‌شود.
  • نوشتن نیمه‌کاره در suffix با truncate پیش از append بعدی ترمیم می‌شود. checksum خراب، حتی در رکورد آخر، بی‌صدا حذف نمی‌شود: recovery متوقف می‌شود تا repair یا restore معتبر تصمیم بگیرد.
  • تلاش مقصد برای خرج leg رسیده پیش از settle کارمزد: پرداخت جزئی مشاهده می‌شود. نگهبان معنای صادقانه رؤیت است — legها فقط با قاعده صریح محصول per-leg قابل‌خرج‌اند و رزرو معلق باقیمانده تسویه‌نشده را تا settle یا جبران حساب‌شده نگه می‌دارد.
  • A logical crash after destination credit is recovered by a fresh processor reading decisions and dedup from files. Replay does not credit the destination twice and applies the outstanding fee.
  • Truncate an incomplete suffix before later appends. A checksum mismatch, even in the last frame, stops recovery rather than silently discarding possibly committed history; repair/restore needs a verified decision.
  • Destination tries to spend an arriving leg before fee settles: it observes a partial payment. Guard is honest visibility semantics — legs are spendable per-leg only by explicit product rule, and pending reservation keeps the unsettled remainder accounted until settle or compensation.

import java.io.*;
import java.nio.*;
import java.nio.channels.*;
import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.util.*;
import java.util.zip.CRC32;

// Teaching crash model: fsynced files survive a processor restart.
// The harness can inspect all logs at one logical boundary; this is NOT an
// atomic remote balance API or proof against power loss/directory-entry loss.
public class ShardPayDemo {
    record Decision(String id, long amount, long fee, boolean approved) {}
    final Path dir;
    final Map<String, Decision> decisions = new LinkedHashMap<>();
    final Map<String, Long> balances = new LinkedHashMap<>();
    final Set<String> seen = new HashSet<>(), settled = new HashSet<>();
    ShardPayDemo(Path dir) throws IOException {
        this.dir=dir; Files.createDirectories(dir);
        balances.put("src",1000L); balances.put("dst",100L); balances.put("fee",0L);
        for (String row : read("src")) {
            String[] t=row.split(" ");
            if (t[0].equals("D")) {
                Decision d=new Decision(t[1],Long.parseLong(t[2]),Long.parseLong(t[3]),Boolean.parseBoolean(t[4]));
                if (decisions.putIfAbsent(d.id,d)==null && d.approved)
                    balances.merge("src",-(d.amount+d.fee),Long::sum);
            } else if (t[0].equals("S")) settled.add(t[1]);
        }
        for (String shard : List.of("dst","fee"))
            for (String row : read(shard)) {
                String[] t=row.split(" "); String key=shard+":"+t[1];
                if (seen.add(key)) balances.merge(shard,Long.parseLong(t[2]),Long::sum);
            }
    }
    void append(String shard,String payload) throws IOException {
        byte[] p=payload.getBytes(StandardCharsets.UTF_8); CRC32 crc=new CRC32(); crc.update(p);
        ByteBuffer b=ByteBuffer.allocate(p.length+12).putInt(p.length).put(p).putLong(crc.getValue()); b.flip();
        try (FileChannel ch=FileChannel.open(dir.resolve(shard+".log"),StandardOpenOption.CREATE,StandardOpenOption.WRITE,StandardOpenOption.APPEND)) {
            while(b.hasRemaining()) ch.write(b);
            ch.force(true);
        }
    }
    List<String> read(String shard) throws IOException {
        Path path=dir.resolve(shard+".log"); List<String> rows=new ArrayList<>();
        if (!Files.exists(path)) return rows;
        ByteBuffer b=ByteBuffer.wrap(Files.readAllBytes(path)); int validEnd=0;
        while(b.hasRemaining()) {
            if(b.remaining()<4) break; // incomplete final frame
            int length=b.getInt();
            if(length<0 || length>1_048_576) throw new IOException("invalid length: fail closed");
            if(b.remaining()<length+8) break;
            byte[] payload=new byte[length]; b.get(payload); long expected=b.getLong();
            CRC32 crc=new CRC32(); crc.update(payload);
            if(crc.getValue()!=expected) throw new IOException("checksum mismatch: stop recovery");
            rows.add(new String(payload,StandardCharsets.UTF_8)); validEnd=b.position();
        }
        // Repair an incomplete suffix before accepting any new append.
        if(validEnd!=b.limit()) try(FileChannel ch=FileChannel.open(path,StandardOpenOption.WRITE)) {
            ch.truncate(validEnd); ch.force(true);
        }
        return rows;
    }
    void credit(String shard,String id,long amount) throws IOException {
        String key=shard+":"+id;
        if(seen.contains(key)) return;
        // The log record is the authority for BOTH the effect and dedup on replay.
        append(shard,"C "+id+" "+amount);
        seen.add(key); balances.merge(shard,amount,Long::sum);
    }
    void process(String id,long amount,long fee,int crashAfterLegs) throws IOException {
        if(amount<0 || fee<0) throw new IllegalArgumentException();
        Decision d=decisions.get(id);
        if(d==null) {
            d=new Decision(id,amount,fee,balances.get("src")>=amount+fee);
            // ONE durable record describes decision, reservation AND pending outputs.
            append("src","D "+id+" "+amount+" "+fee+" "+d.approved);
            decisions.put(id,d);
            if(d.approved) balances.merge("src",-(amount+fee),Long::sum);
        }
        if(d.amount!=amount || d.fee!=fee) throw new IllegalArgumentException("ID reused with different payload");
        if(!d.approved || settled.contains(id)) return;
        if(crashAfterLegs==0) return;
        credit("dst",id,d.amount); if(crashAfterLegs==1) return;
        credit("fee",id,d.fee); if(crashAfterLegs==2) return;
        append("src","S "+id); settled.add(id);
    }
    long inTransitAtCommonBoundary() {
        long pending=0;
        for(Decision d:decisions.values()) if(d.approved) {
            if(!seen.contains("dst:"+d.id)) pending+=d.amount;
            if(!seen.contains("fee:"+d.id)) pending+=d.fee;
        }
        return pending;
    }
    void checkConservation() {
        long total=balances.values().stream().mapToLong(Long::longValue).sum()+inTransitAtCommonBoundary();
        if(total!=1100) throw new AssertionError("conservation: "+total);
    }
    public static void main(String[] args) throws IOException {
        for(int cut=0;cut<=3;cut++) {
            Path dir=Files.createTempDirectory("shardpay-");
            ShardPayDemo first=new ShardPayDemo(dir); first.process("pay-1",200,5,cut);
            first.checkConservation();
            // Fresh processor: NO copying maps or dedup from the previous instance.
            ShardPayDemo restarted=new ShardPayDemo(dir); restarted.checkConservation();
            restarted.process("pay-1",200,5,3); restarted.process("pay-1",200,5,3);
            restarted.checkConservation();
            if(!restarted.balances.equals(Map.of("src",795L,"dst",300L,"fee",5L)) || restarted.inTransitAtCommonBoundary()!=0)
                throw new AssertionError("replay changed effects");
            System.out.println("PASS cut="+cut+" recovered="+restarted.balances+" pending=0");
        }
        Path dir=Files.createTempDirectory("shardpay-tail-");
        ShardPayDemo p=new ShardPayDemo(dir); p.process("pay-1",200,5,1);
        Files.write(dir.resolve("src.log"),new byte[]{0,0},StandardOpenOption.APPEND);
        ShardPayDemo repaired=new ShardPayDemo(dir); repaired.process("pay-1",200,5,3); repaired.checkConservation();
        byte[] corrupt=Files.readAllBytes(dir.resolve("src.log")); corrupt[4]^=1;
        Files.write(dir.resolve("src.log"),corrupt);
        boolean rejected=false;
        try { new ShardPayDemo(dir); } catch(IOException e) { rejected=true; }
        if(!rejected) throw new AssertionError("corruption silently accepted");
        System.out.println("PASS truncated suffix repaired; checksum corruption rejected");
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): مقصد برای همیشه بسته شده باشه؛ پرداخت pending رو چطور حل می‌کنی؟Follow-up (Staff): The destination account closes permanently. How do you resolve your pending transfer?

ابتدا سرنوشت legهای قبلی را با شناسه‌هایشان reconcile کن؛ timeout به معنی اعمال‌نشدن نیست. مبلغی که هنوز هرگز credit نشده می‌تواند آزاد شود؛ مبلغ creditشده باید با debit جبرانیِ مجاز و بادوام در مقصد برگردد و سپس در مبدأ credit شود. compensation شناسه و نوع عملیات مستقل و dedup خودش را دارد؛ استفاده از همان کلید credit قبلی می‌تواند آن را اشتباه تکراری کند. اگر برگشت مجاز یا ممکن نیست، وضعیت unresolved و مسیر عملیاتی لازم است؛ refund بی‌قید ۲۰۵ می‌تواند پول خلق کند.

Reconcile previous legs by identity first; timeout does not establish non-application. Release never-credited reservations, but recover credited funds through an authorized durable compensating debit before refunding source. Compensation needs its own operation type/identity and dedup; reusing the original credit key can suppress it. If reversal is unavailable, retain an unresolved state and operational recovery. An unconditional 205 refund can create money.

پیگیری (استف): بعد از بازیابی، پرداخت integral است یا atomic یا هیچ‌کدام؟Follow-up (Staff): After recovery, is the payment integral, atomic, or neither?

بعد از بازیابی کامل، integrity یعنی تصمیم واحد، اثر حداکثر یک‌بارهٔ هر leg و بقای اقتصادی در مرز مقایسهٔ معتبر. این مدل رؤیت اتمیک نمی‌دهد. برای دیدن یک snapshot مشترک باید خوانندگان و نویسندگان پروتکل تراکنش/commit و snapshot یکسانی داشته باشند؛ صرف افزودن نام consensus یا 2PC بدون قرارداد خواندن کافی نیست.

After complete recovery, integrity means one decision, at-most-once leg effects and economic conservation at a valid comparison boundary. The model does not provide atomic visibility. Shared snapshots require readers and writers to follow a common transaction/commit and snapshot protocol; naming consensus or 2PC alone is insufficient.

اشتباهات رایجCommon mistakes

  • پایدار خواندن الصاق خام فایل: بدون قاب‌بندی و checksum و fsync و گذر بازیابی که دم‌های پاره را می‌اندازد، crash وسط نوشتن پول می‌سازد یا گم می‌کند. پایداری همان پروتکل چهاربخشی است نه فراخوانی الصاق.
  • اتمیک خواندن همگرایی نهایی: جمع‌های متوازن یعنی خواننده‌ها همه legها را با هم دیده‌اند نیست. بقاشده با حساب‌شده را وعده بده و مشاهده‌پذیری جزئی را صریح نام ببر.
  • بیرون گذاشتن پول معلق از حسابداری: پول بین رزرو و settle به سطر رزرو نمایان تعلق دارد. پول در حال انتقال حساب‌نشده بررسی جمع را دقیقاً وقتی می‌شکند که crash بیشترین نیاز را به آن دارد.
  • Calling a raw file append durable: without framing, checksum, fsync and a recovery pass that discards torn tails, a crash mid-write invents money or loses it. Durability is the four-part protocol, not the append call.
  • Reading final convergence as atomic visibility: balanced totals do not mean readers saw all legs together. Promise conserved plus accounted, and name partial observability explicitly.
  • Leaving pending money out of the accounting: funds between reserve and settle belong to a visible reservation row. Unaccounted in-flight money breaks the sum check exactly when a crash needs it most.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

یک checker مستقل اجرا کن که لاگ مرجع را با کد جدا تا checkpoint اعلام‌شده بازپخش می‌کند و state واقعی را در همان checkpoint می‌خواند و فیلدبه‌فیلد مقایسه می‌کند. عقب‌مانده ولی سازگار یعنی lag (روی تابلو رصدش کن و page نکن)؛ اختلاف در checkpoint یکسان یعنی corruption (به انسان page کن). یک update گمشده تزریق کن تا کارکرد تشخیص اثبات شود. تشخیص فقط page می‌کند — تعمیر پشت دروازه می‌ماند — و checker صادقانه می‌گوید چه چیزی را نمی‌تواند اثبات کند: لاگ ناقص یا باگ مشترک هر دو مسیر کد. تریدآف: محاسبه replay و دفترداری checkpoint در برابر تشخیص corruption خاموش که assertهای داخلی نمی‌دهند.
Run an independent checker that replays the authoritative log with separate code up to a stated checkpoint, reads actual state at that same checkpoint, and compares field by field. Behind-but-consistent means lag (track it on a board, do not page); same-checkpoint difference means corruption (page a human). Inject a missing update to prove detection works. Detection only pages — repair stays gated — and the checker honestly names what it cannot prove: an incomplete log or a bug shared by both code paths. The trade-off: replay compute and checkpoint bookkeeping for silent-corruption detection that inline asserts cannot give.

صورت مسئله و فرض‌هاProblem and assumptions

  • دامنه تاریخچه انتقال: چهار انتقال آموزشی t1 تا t4 روی حساب‌های A=500 و B=300 و C=200. derivation تحت حسابرسی بی‌صدا t3 را می‌اندازد.
  • checker هیچ کدی با derivation ندارد: بازمحاسبه مستقل‌نوشته‌شده از همان لاگ که در یک checkpoint اعلام‌شده (آفست ۴) مقایسه می‌شود.
  • checkpointها آفست‌های لاگ‌اند که هر دو طرف می‌توانند نام ببرند. نمایی که هنوز به checkpoint نرسیده عقب است نه خراب.
  • Transfer history scope: four teaching transfers t1..t4 over accounts A=500, B=300, C=200. The derivation under audit silently drops t3.
  • The checker shares no code with the derivation: independently written recomputation from the same log, compared at one stated checkpoint (offset 4).
  • Checkpoints are log offsets both sides can name. A view that has not reached the checkpoint yet is behind, not corrupt.

چرا این روش و این عددها؟Why this method and these numbers?

اگر checker و projection یک کد داشته باشند، یک bug مشترک می‌تواند هر دو را به یک جواب غلط برساند؛ محاسبهٔ مستقل شانس کشف را بالا می‌برد. مقایسه در offset=4 انتخاب آموزشی است چون t3 گم‌شده باید در هر دو طرف تا آن مرز پردازش شده باشد. اختلاف قبل از هم‌مرزشدن می‌تواند فقط lag باشد. checksum سریع است ولی محل خطا را نمی‌گوید؛ برای repair باید به bucket و سپس رکوردهای متفاوت برسیم.

Sharing derivation code with the checker can reproduce the same bug twice; independent recomputation improves detection. Offset 4 is chosen because both sides should have processed missing transfer t3 by then. Earlier differences may be lag. A checksum detects mismatch quickly but does not locate it; descend through buckets to records for repair.

مدل ذهنیMental model

صندوقدار دومی که همان نوار را با ماشین‌حساب خودش بازمی‌شمارد: به جمع‌های صندوقدار اول اعتماد نمی‌کند و هر ورودی را خودش تا شماره خط دایره‌شده بازپخش می‌کند و خط‌به‌خط مقایسه می‌کند. کشویی که فقط از برنامه عقب است دیر است نه کسری. کشویی که روی خط دایره‌شده اختلاف دارد کسری است — و فقط کشوی کسری مدیر را بیدار می‌کند. ولی اگر خود نوار صفحه کم داشته باشد، بازشماری‌اش هیچ‌چیز اثبات نمی‌کند و همین را بلند می‌گوید.
A second cashier recounting the same tape with her own calculator: she does not trust the first cashier's totals, she replays every entry herself up to a circled line number, and compares line by line. A drawer that is merely behind schedule is late, not short. A drawer that disagrees on the circled line is short — and only a short drawer wakes the manager. But if the tape itself is missing pages, her recount proves nothing, and she says so out loud.

حل گام‌به‌گامStep by step

  1. بازپخش تا checkpoint checker لاگ مرجع را با کد مستقل‌نوشته‌شده بازپخش می‌کند و دقیقاً در checkpoint اعلام‌شده (آفست ۴) می‌ایستد. تابع‌های derivation را هرگز import نمی‌کند — کد مشترک نقاط کور مشترک می‌آورد.
  2. مقایسه در یک نقطه state زنده سنجاق‌شده در همان checkpoint خوانده و فیلدبه‌فیلد diff گرفته می‌شود. نمای عقب‌مانده ولی سازگار به‌مثابه lag کران‌دار ثبت می‌شود؛ فقط اختلاف در checkpoint یکسان mismatch است — t3 افتاده دمو دقیقاً همین‌جا روی A و C شلیک می‌کند.
  3. مسیریابی با تعمیر دروازه‌دار mismatch به pager و تعمیر تأییدانسانی می‌رود که از لاگ بازپخش می‌شود؛ lag با روندش به تابلو می‌رود. هزینه از تابلوی پیوسته به replay ساعتی به جمع‌های روزانه به بازبینی هر incident رشد می‌کند — درحالی‌که لاگ ناقص یا باگ مشترک بیرون هر بررسی می‌ماند و صریح نام برده می‌شود.
  1. Replay to the checkpoint The checker replays the authoritative log with independently written code, stopping exactly at the stated checkpoint (offset 4). It never imports the derivation's functions — shared code would share blind spots.
  2. Compare at one point Live state is read pinned at the same checkpoint and diffed field by field. A behind-but-consistent view is recorded as lag with a bound; only a same-checkpoint difference is a mismatch — the demo's dropped t3 fires on A and C exactly here.
  3. Route, repair gated Mismatch routes to the pager and a human-approved repair that replays through the log; lag routes to the board with its trend. Cost grows from continuous board to hourly replay to daily sums to per-incident review — while an incomplete log or a shared bug stays outside every check, named explicitly.

طراحی مشخصConcrete design

اجزا: لاگ ورودی مرجع با آفست‌های نام‌دار؛ derivation تحت حسابرسی؛ checker (باینری جدا و کد جدا)؛ تابلوی lag و pager. پروتکل: checker تا checkpoint با شماره N بازپخش می‌کند و state زنده سنجاق‌شده در N را می‌خواند و فیلدبه‌فیلد diff می‌گیرد. تطابق با lag صفر سبز است؛ تطابق با lag ورودی تابلوست؛ هر diff در checkpoint یکسان page می‌کند. دروازه تعمیر: تشخیص هیچ‌وقت state را بازنویسی نمی‌کند — انسان تعمیر را از diff checker تأیید می‌کند و خود تعمیر از لاگ بازپخش می‌شود. زمان‌بندی: تابلوی lag پیوسته و replay checkpoint ساعتی و جمع‌بندی total روزانه.

Components: the authoritative input log with named offsets; the derivation under audit; the checker (separate binary, separate code); a lag board and a pager. Protocol: checker replays to checkpoint N, reads live state pinned at N, diffs field by field. Match plus lag zero is green; match with lag is a board entry; any same-checkpoint diff pages. Repair gate: detection never rewrites state — a human approves repair from the checker diff, and the repair itself replays through the log. Schedule: lag board continuous, checkpoint replay hourly, totals sum-check daily.

گزینه‌های جایگزینAlternatives

  • assertionهای داخل خط derivation: ارزان‌ترین اجرا، ولی همان کد و همان نقاط کور خط را دارند — باگ مشترک از هر assert رد می‌شود. assertها را برای fail-fast نگه دار، ولی حسابرسی مستقل نیستند.
  • اجرای دوگانه کامل با رأی (دو derivation مستقل و page روی هر اختلاف): قوی‌ترین تشخیص، تقریباً دو برابر محاسبه با قاعده تساوی‌شکن وقتی دو checker با هم اختلاف کنند. برای دفترکل‌های پول‌بر نگه دار؛ تک-checker با تابلوی lag این‌جا پیش‌فرض متناسب است.
  • Inline assertions inside the derivation pipeline: cheapest to run, but they share the same code and the same blind spots as the pipeline — a shared bug passes every assert. Keep asserts for fail-fast, but they are not an independent audit.
  • Full dual-run with vote (two independent derivations, page on any disagreement): strongest detection, roughly double compute plus a tie-break rule for when the two checkers disagree with each other. Reserve for money-moving ledgers; the single-checker-plus-lag-board here is the proportionate default.

سناریوهای خرابیFailure scenarios

  • update افتاده خاموش (t3): در replay checkpoint بعدی به‌مثابه mismatch در checkpoint یکسان روی A و C گرفته می‌شود. نگهبان replay مستقل زمان‌بندی‌شده است — دمو دقیقاً همین را تزریق می‌کند.
  • اجرای checker روی آفست لاگ تازه‌تر از رسیده state زنده: هر مقایسه به‌غلط page می‌کند. نگهبان سنجاق هر دو خواندن به checkpoint اعلام‌شده و رفتار با هر عقب‌ماندگی به‌مثابه lag کران‌دار است، هرگز corruption.
  • قطعی checker (بدون verdict در یک چرخه): سکوت مثل سلامتی به نظر می‌رسد. نگهبان هشدار تازگی روی خود جریان verdict است — حسابرسی گمشده incident است نه قبولی.
  • Silent dropped update (t3): caught at the next checkpoint replay as a same-checkpoint mismatch on A and C. Guard is the scheduled independent replay — the demo injects exactly this.
  • Checker runs against a newer log offset than live state has reached: every comparison pages falsely. Guard is pinning both reads to the stated checkpoint and treating anything behind as lag with a bound, never as corruption.
  • Checker outage (no verdicts for a cycle): silence looks like health. Guard is a freshness alert on the verdict stream itself — a missing audit is an incident, not a pass.

import java.util.*;

// Teaching demo: end-to-end audit checker over transfer histories.
// Independent recomputation to a STATED checkpoint; same-checkpoint compare;
// lag vs corruption distinguished; missing update injected; incomplete log admitted.
public class AuditDemo {
    record Xfer(String id, String from, String to, long amount) {}
    List<Xfer> log = new ArrayList<>(List.of(
        new Xfer("t1", "A", "B", 100), new Xfer("t2", "B", "C", 40),
        new Xfer("t3", "A", "C", 50), new Xfer("t4", "C", "A", 10)));

    // The REAL derivation under audit (has an injected silent bug: t3 skipped).
    Map<String, Long> derivedWithBug(int checkpoint) {
        Map<String, Long> b = new LinkedHashMap<>(Map.of("A", 500L, "B", 300L, "C", 200L));
        for (int i = 0; i < checkpoint; i++) {
            Xfer x = log.get(i);
            if (x.id.equals("t3")) continue; // SILENT DROPPED UPDATE (injected)
            b.put(x.from, b.get(x.from) - x.amount);
            b.put(x.to, b.get(x.to) + x.amount);
        }
        return b;
    }

    // The CHECKER: written independently, straight from the log. No shared code.
    static Map<String, Long> recompute(List<Xfer> log, int checkpoint) {
        Map<String, Long> b = new LinkedHashMap<>(Map.of("A", 500L, "B", 300L, "C", 200L));
        for (int i = 0; i < checkpoint; i++) {
            Xfer x = log.get(i);
            b.put(x.from, b.get(x.from) - x.amount);
            b.put(x.to, b.get(x.to) + x.amount);
        }
        return b;
    }

    public static void main(String[] a) {
        AuditDemo d = new AuditDemo();
        int cp = 4; // stated checkpoint: log offset 4
        Map<String, Long> actual = d.derivedWithBug(cp);
        Map<String, Long> expect = recompute(d.log, cp);
        System.out.println("checkpoint=" + cp + " actual=" + actual + " expected=" + expect);
        for (String k : expect.keySet())
            if (!expect.get(k).equals(actual.get(k)))
                System.out.println("MISMATCH at " + k + ": live=" + actual.get(k) + " recomputed=" + expect.get(k));
        // lag, not corruption: derived state is just older (checkpoint 2 vs 4)
        Map<String, Long> older = d.derivedWithBug(2);
        System.out.println("stale read cp=2 vs checkpoint 4 -> " + (older.equals(expect) ? "match" : "LAG (behind, not corrupt): " + older));
        // honest limit: if the input log itself is incomplete, the checker is blind
        List<Xfer> partial = d.log.subList(0, 3);
        System.out.println("log truncated to 3 entries: checker recomputes " + recompute(partial, 3));
        System.out.println("OK: caught silent t3 at same checkpoint; lag separated; incomplete log admitted");
    }
}

خروجی مورد انتظار: در checkpoint ۴ checker روی A و C ناسازگاری flag می‌کند (t3 خاموش)؛ نمای checkpoint دو lag می‌خواند نه corruption؛ لاگ سه‌تایی صادقانه از همان که دارد بازمحاسبه می‌کند؛ OK. (خروجی واقعی همین محیط)

Run: javac AuditDemo.java && java AuditDemo — stdlib Java only, instant.

Expected output: At checkpoint 4 the checker flags MISMATCH on A and C (silent t3); a checkpoint-2 view reads LAG, not corruption; a 3-entry log recomputes honestly from what it has; OK. (actual output of this environment)

آزمون صحت و معیار عملیاتیCorrectness checks and operational criteria

ناورداها: توافق checker و derivation در هر checkpoint کامل در اجراهای سالم؛ هر verdict شناسه checkpointش را دارد؛ بدون بررسی کامل بودن پیشوند لاگ هیچ verdictای نیست. تست‌های خرابی: تزریق update افتاده و تأیید page؛ سرو نمای کهنه و تأیید ورودی تابلو بدون page؛ بریدن لاگ و تأیید «نامعلوم، لاگ ناقص» به‌جای verdict؛ ساکت کردن checker و تأیید شلیک هشدار تازگی. متریک‌ها: نرخ mismatch و توزیع lag هر نما و زمان تا تشخیص هر سطح بررسی و تازگی verdict.
Invariants: checker and derivation agree at every completed checkpoint on healthy runs; every verdict names its checkpoint; no verdict without a completeness check on the log prefix. Failure tests: inject a dropped update and confirm the page; serve a stale view and confirm a board entry with no page; truncate the log and confirm 'unknown, log incomplete' instead of a verdict; silence the checker and confirm the freshness alert fires. Metrics: mismatch rate, lag distribution per view, time-to-detect per check tier, verdict freshness.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): لاگ ورودی خودش ناقص باشه؛ auditor دیگه چی رو نمی‌تونه ثابت کنه؟Follow-up (Staff): The input log itself is incomplete. What can your auditor no longer prove?

آن‌وقت فراتر از همان پیشوند هیچ‌چیز اثبات نمی‌کند — و باید همین را بگوید. بازمحاسبه از لاگ بریده مقادیر «موردانتظار» غلط می‌دهد بی‌تقصیر derivation؛ مقایسه‌شان به‌غلط page می‌کند و به تیم یاد می‌دهد pager را نادیده بگیرد. طراحی صادقانه: checker اول کامل بودن لاگ تا checkpoint را راستی‌آزمایی می‌کند (پیوستگی آفست و بدون شکاف) و وقتی پیش‌فرض شکست خورد از verdict خودداری می‌کند — «نامعلوم، لاگ ناقص» گزارش می‌دهد. حسابرسی که ورودی‌اش را راستی‌آزمایی نکند هیچ‌چیز را حسابرسی نمی‌کند.

Then it can prove nothing beyond that prefix — and it must say so. Recomputation from a truncated log yields 'expected' values that are wrong through no fault of the derivation; comparing them pages falsely and teaches the team to ignore the pager. The honest design: the checker first verifies log completeness to the checkpoint (offset continuity, no gaps), and refuses to verdict — reporting 'unknown, log incomplete' — when the premise fails. An auditor that cannot verify its input audits nothing.

پیگیری (استف): derivation و checker یک باگ مشترک داشته باشند. حسابرسی می‌گیردش؟Follow-up (Staff): Derivation and checker share one Bug. Does the audit catch it?

نمی‌تواند — از روی ساخت. اگر هر دو مسیر همان بدخوانی را داشته باشند (همان کتابخانه و همان بدفهمی spec و همان تابع کپی‌شده)، خروجی‌هایشان توافق می‌کنند و حسابرسی روی state غلط سبز است. دفاع‌ها جزئی‌اند: checker را از spec بنویس نه از کد خط؛ نویسندگی را بچرخان؛ جمع‌بندی total متفاوت بگذار (محاسبه دیگری که بعضی باگ‌های مشترک را می‌گیرد)؛ و ریسک باقی‌مانده را در ران‌بوک نام ببر به‌جای ادعای استقلال کامل. عمق تشخیص متناسب با ناهمسانی واقعی است.

It cannot — by construction. If both paths share the misreading (same library, same spec misunderstanding, same copied function), their outputs agree and the audit is green over a wrong state. Defenses are partial: write the checker from the spec, not from the pipeline code; rotate authorship; vary a Totals sum-check (a different computation that catches some shared bugs); and name the residual risk in the runbook instead of claiming full independence. Detection depth is proportional to genuine dissimilarity.

اشتباهات رایجCommon mistakes

  • مقایسه تازه‌ترین با تازه‌ترین به‌جای checkpoint یکسان: lag عادی replication مثل corruption page می‌کند و تیم pager را بی‌صدا می‌کند و mismatch واقعی در نویز پنهان می‌شود. اول checkpoint را سنجاق کن و بعد مقایسه کن.
  • استفاده دوباره از تابع‌های خود خط داخل checker: حسابرسی تکراری می‌شود و باگ‌های مشترک بی‌صدا رد می‌شوند. استقلال یعنی کد جداگانه‌نوشته‌شده از spec نه فراخوانی کتابخانه مشترک.
  • تعمیر خودکار روی تشخیص: آن‌وقت باگ checker یا جهش lag state خوب را بازنویسی می‌کند. تشخیص page می‌کند؛ انسان تأیید می‌کند؛ تعمیر از لاگ بازپخش می‌شود — همیشه به همین ترتیب.
  • Comparing latest-against-latest instead of same-checkpoint: normal replication lag pages as corruption, the team mutes the pager, and the real mismatch hides in the noise. Pin the checkpoint first, compare second.
  • Reusing the pipeline's own functions inside the checker: the audit becomes a duplicate, and shared bugs pass silently. Independence means separately written code from the spec, not a shared library call.
  • Auto-repairing on detection: a checker bug or a lag spike then rewrites good state. Detection pages; a human approves; the repair replays through the log — in that order, always.
