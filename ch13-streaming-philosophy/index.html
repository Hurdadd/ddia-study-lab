فلسفهٔ سیستم‌های جریانیA Philosophy of Streaming Systems

ببین رفیق، این فصل دربارهٔ یک چیزِ ساده‌ست: چطور همه‌چیز رو از یک مسیرِ واحدِ تغییر بسازی. مرجع، جست‌وجو، کش و گزارش همه از یک منبع مشتق می‌شن — و اینجا یاد می‌گیری نماها رو چطور از نو بسازی، تدریجی عوض کنی، و فرقِ «درست بودنِ داده» با «زود دیده شدنش» رو از هم جدا کنی.
Twelve chapters of tools — storage, replication, partitioning, transactions, consensus, batch and stream. This chapter assembles them into a working philosophy: no single tool covers every need, so you stitch specialized systems together with derived data — fresh input enters through one system of record, and every other view is built from it with deterministic, idempotent processing. Then you stay correct without distributed transactions: end-to-end IDs, asynchronous constraints, and the occasional calculated apology — and you measure timeliness on its own.

No software — not even the so-called “general-purpose” ones — is built for every consumption pattern, so a real application always mixes several specialized tools. The way to mix them without chaos: declare one system the record (system of record) — the only path for fresh input — and keep the rest derived from it: an ordered log, a deterministic function, idempotent writes. Then, instead of expensive distributed transactions, you reach integrity with end-to-end IDs and asynchronous constraints; and you measure timeliness on its own.

داستان از این قراره: بخشِ ۱ («یکپارچه‌سازی») با نظمِ «یک مبنا» شروع می‌کنه و نشون می‌ده dual-write چرا واگرا می‌شه. بخشِ ۲ batch و stream رو دو رویِ یک سکه می‌کنه (بازپردازش + مهاجرتِ تدریجی). بخشِ ۳ پایگاه داده رو «unbundle» می‌کنه: federated برای خواندن، event log برای نوشتن. بخشِ ۴ اپلیکیشن رو حولِ dataflow بازطراحی می‌کنه (به‌جای RPC، replica محلی؛ مسیرِ نوشتن/خواندن). و بخشِ ۵ — قلبِ فصل — «درستی» است: آرگومانِ سرتاسری، قیدها، timeliness در برابر integrity، و نقطهٔ بهینه‌ای که در آن هماهنگی فقط همون‌قدر هست که لازمه.

Here's the plan. Section 1 starts “integration” with the “one record” discipline and shows why dual writes diverge. Section 2 makes batch and stream two sides of one coin (reprocessing + gradual migration). Section 3 “unbundles” the database: federated for reads, event log for writes. Section 4 redesigns the application around dataflow (local replicas instead of RPC; write/read paths). And Section 5 — the heart — is “correctness”: the end-to-end argument, constraints, timeliness vs integrity, and the sweet spot where coordination is exactly as much as needed.

۱.۱. یک مبنا، چند نمای مشتق‌شده1.1. One record, many derived views

وقتی چند تا ابزار از یک داده استفاده می‌کنن، باید روشن باشه مرجعش کجاست و بقیه چطور ازش ساخته می‌شن. یک مرجعِ واحد جلوی تغییرهای مستقل و متناقض رو می‌گیره.

مثال فنی: یک مرجع، سه خروجی

وضعیت اولیه: تو مثالِ زیر، مشخصات P7 توی مرجع ثبت شده و رویدادِ تغییر با version=12 تولید شده.

اجرای مرحله‌به‌مرحله: مصرف‌کنندهٔ جست‌وجو از همین تغییر سند می‌سازه، مصرف‌کنندهٔ کش مقدار، و مصرف‌کنندهٔ تحلیل هم ردیفِ گزارش.

نتیجه و دلیل: خروجی‌ها مدل‌های جدا دارن، ولی چون منشأشون مشترکه و ترتیبشون معتبره، می‌دونی چطور تطبیقشون بدی و از نو بسازیشون — اینو قاب کن.

This chapter opens with a simple observation that stitches the whole book together: for a problem like “store data and find it later” there's no single right answer — every tool is built for one consumption pattern. So a real application inevitably combines several pieces of software: an OLTP database for recording, a search index for words, a warehouse for analytics, a cache for display, an ML model for recommendations, and a notification service for news. The hard part isn't picking the tool; it's mapping tools to conditions — and then keeping all these views together.

راه‌حلِ پیشنهادی: بعضی سیستم‌ها رو مبنا اعلام کن و بقیه رو مشتق‌شده از آن‌ها. مثلاً تغییراتِ پایگاه دادهِ مبنا با CDC گرفته می‌شه و به‌همان‌ترتیب روی ایندکسِ جستجو اعمال می‌شه. اگه CDC تنها راهِ به‌روزرسانیِ ایندکس باشه، می‌تونی مطمئن باشی ایندکس تماماً از مبنا مشتق‌شده و (به‌جز باگِ نرم‌افزاری) باهاش سازگاره. نوشتن توی پایگاه داده، تنها راهِ تزریقِ ورودیِ تازه به سیستمه. این همون ایدهٔ replication ماشینِ حالت (فصلِ ۱۰) است که این‌بار در سطحِ معماریِ کلِ سازمان اعمال می‌شه.

The proposed fix: declare some systems the record and keep the rest derived from them. Say the record database's changes are captured with CDC and applied in the same order onto the search index. If CDC is the index's only update path, you can be sure the index is fully derived from the record and (barring software bugs) consistent with it. Writing to the database stays the only way to inject fresh input into the system. That's the state-machine replication idea (Chapter 10), applied this time at the scale of a whole organization's architecture.

The diagram runs left to right. First the Client app (writes new input) reaches the System-of-record DB (durable source of truth) via the “only input path” arrow — the golden discipline: fresh input enters through this one door only. From the database, the “CDC captures changes” arrow goes to the Change stream / event log (same-order change feed); changes are captured in commit order.

The log then fans out like a hub to the five-column derived views: Full-text search index, Analytics / warehouse, Cache / materialized view, ML model / recommendations and Notification service. All five sit in one shared frame labelled “same order, deterministic, idempotent'” — all read in the same order, process with a deterministic function, and write idempotently.

The three cards at the bottom complete the lesson: first the warning — “writing directly to two stores means each takes its own order and they stay inconsistent forever (Fig. 12-4)”; then the opposite principle — “funnel all input through one system that decides the total order”; and finally the operational note: “CDC or event sourcing doesn't matter; deciding the order matters — and since derivation is asynchronous and loosely coupled, an error in one corner doesn't spread to the rest.”

۱.۲. چرا نوشتنِ دوگانه واگرا می‌شود1.2. Why dual writes diverge

وقتی مستقیم توی دو مقصد می‌نویسی، ممکنه یکی جا بمونه یا تغییرها با ترتیبِ متفاوت برسند. مسیرِ واحدِ تغییر کمک می‌کنه نسخه‌های مشتق‌شده از ترتیبِ معتبر پیروی کنن.

مثال فنی: دو ترتیب که با هم نمی‌خوانن

وضعیت اولیه: یه سناریوی ساده‌ست: T1 قیمت ۱۰۰ و T2 قیمت ۱۲۰ رو می‌نویسن.

اجرای مرحله‌به‌مرحله: مرجع T1 رو بعد T2 اعمال می‌کنه؛ ولی وقتی جدا به ایندکس می‌فرستی، به‌ترتیب T2 بعد T1 بهش می‌رسه و ایندکس روی ۱۰۰ گیر می‌کنه.

نتیجه و دلیل: موفق بودنِ هر چهار نوشتن کافی نیست؛ یا لاگِ مرتبِ تغییر یا کنترلِ نسخه باید ترتیبِ معتبر رو به مقصد برسونه — این دام معروفه.

If the app writes directly to both the database and the search index, it walks straight into the Fig. 12-4 trap: two clients send two conflicting writes at once, and the two systems apply them in two different orders. Neither the database nor the index is “in charge of order”; each decides contradictorily, and they stay inconsistent forever. The fix is funnelling all input through one system that decides every write's order — the same state-machine-replication idea, one level up. Updating the derived system from the event log can usually be made deterministic and idempotent, which makes error recovery simple.

The diagram has two acts. Act one: “Two clients, two stores, no ordering authority”. Five participants: client A and client B (both “concurrent writers”), the database (“system of record”) and the search index (“derived data”). Follow the four tangled arrows: A writes x=1 and B writes x=2 — but the database applies A then B (note: “database order #1/#2”) while the index sees B then A (“index order #1/#2”). The closing dashed arrow summarizes: “DB x=2 ≠ index x=1” — the stores stay inconsistent forever because nobody owns the order.

Act two: “One ordering authority — a single total order”. This time both clients only write to the database (“all user input is funnelled through one system”, “the database decides one total order”). Then CDC: change log hands the changes in commit order (first x=1, then x=2) to the fifth participant, the event log, and the “apply in same total order” arrow updates the index — noting “derived updates are deterministic and idempotent, so recovery is simple”. The last arrow: “consistent: x=2” — CDC or event sourcing, what matters is deciding the total order.

۱.۳. دادهٔ مشتق در برابر تراکنشِ توزیع‌شده1.3. Derived data vs distributed transactions

تراکنشِ توزیع‌شده می‌خواد تصمیمِ تأییدِ چند بخش رو هماهنگ کنه. ساختنِ نمایِ مشتق‌شده از لاگ معمولاً اجازه می‌ده مقصد کمی عقب بمونه و بعد به مرجع برسه؛ این دو تا تضمین یکی نیستن.

مثال فنی: همین‌الان یا بعداً؟

وضعیت اولیه: نگاه کن: تغییرِ قیمت توی مرجع commit شده، ولی جست‌وجو هنوز نسخهٔ قدیمی رو نشون می‌ده.

اجرای مرحله‌به‌مرحله: توی dataflow، مصرف‌کننده بعداً تغییر رو می‌رسونه؛ توی atomic commit، منابعِ participant به یه تصمیمِ مشترکِ commit/abort متعهد می‌شن.

نتیجه و دلیل: روشِ اول lag رو می‌پذیره و بازپخش می‌خواد؛ روشِ دوم هماهنگی و مسیرِ انتظارِ خرابیِ خودش رو داره — حساب کن.

The classic way to keep systems in sync is the distributed transaction (2PC, Chapter 8). At an abstract level both chase one goal with two means: transactions guarantee atomic application via atomic commit; the log-based system reaches correctness via deterministic retry and idempotence. The biggest difference is that a transactional system usually guarantees “after writing, you immediately read the fresh value” (read-your-writes), while an asynchronous derived system offers no such promise.

تراکنش‌های توزیع‌شده توی محیط‌هایی که حاضرند هزینهٔ عملکرد و عملیاتشون رو بپردازن موفق بودن — ولی XA تحملِ خطا و عملکردِ ضعیفی داره که کاربردش رو شدیداً محدود می‌کنه. ساختنِ پروتکلِ بهتر ممکنه، ولی جاانداختنش توی ابزارهای موجود بعید است به‌زودی رخ بده. و توی نبودِ یه پروتکلِ خوبِ فراگیر، دادهٔ مشتقِ لاگ‌محور امیدبخش‌ترین راهِ یکپارچه‌سازیِ سیستم‌های متفاوت است. البته گفتنِ «eventual consistency اجتناب‌ناپذیره، بساز و بسوز» هم بدونِ راهنمایِ «چطور بسوزی» حرفِ مفیدی نیست — و ادامهٔ همین فصل دقیقاً همون راهنماست: چطور روی سیستم‌های مشتقِ ناهمگام تضمین‌های قوی‌تر بسازیم و به نقطهٔ میانیِ بینِ تراکنشِ توزیع‌شده و لاگِ ناهمگام برسیم.

Distributed transactions have succeeded in environments willing to pay their performance and operational cost; but XA has poor fault tolerance and performance that sharply limits its use. A better protocol is possible, but getting it adopted into existing tools is unlikely to happen soon. So in the absence of a good universal protocol, log-based derived data is the most promising way to integrate different systems. And sure, saying “eventual consistency is inevitable, build and burn” without a “how to burn” guide isn't useful either — but the rest of this chapter is exactly that guide: how to build stronger guarantees on asynchronous derived systems and reach the middle ground between distributed transactions and the asynchronous log.

۱.۴. وقتی ترتیبِ کامل می‌شکند1.4. When total order breaks

مرتب‌کردنِ همهٔ رویدادهای دنیا معمولاً لازم نیست و هماهنگیِ زیادی می‌خواد. باید تشخیص بدی کدوم تغییرها واقعاً به هم وابسته‌ان و همون ترتیب رو نگه‌داریم.

مثال فنی: علت، ولی روی دو پارتیشن

وضعیت اولیه: رویدادِ ایجادِ سفارش ۴۲ روی پارتیشنِ A و لغوِ همون روی B قرار گرفته.

اجرای مرحله‌به‌مرحله: مصرف‌کننده ممکنه لغو رو پیش از ایجاد ببینه؛ هم‌پارتیشن کردنِ رخدادهای همون سفارش یا نگهداریِ وابستگی این مسئله رو کنترل می‌کنه.

نتیجه و دلیل: رخدادهای مستقل الزاماً ترتیبِ جهانی نمی‌خوان؛ رخدادهای وابسته بدونِ قراردادِ ترتیب، stateِ نامعتبر می‌سازن — حساب کن.

While the system is small, a fully ordered event log is feasible (single-leader databases build exactly that log). But as the scale grows, the limits show up:

  • ساختنِ لاگِ کاملاً مرتب معمولاً یعنی همهٔ رویدادها از یک رهبرِ واحد رد بشن که ترتیب رو تعیین می‌کنه. اگه نرخِ رویداد از توانِ یک ماشین بیشتر بشه، باید لاگ رو shard کنی — و اون‌وقت ترتیبِ رویدادهای دو shard مبهم می‌شه.
  • اگه سرورها در چند region جغرافیایی باشن (تا وقتی کلِ یک دیتاسنتر رو از دست بدی)، معمولاً هر دیتاسنتر رهبرِ خودش رو داره، چون هماهنگیِ همگامِ بین‌قاره‌ای کنده — پس ترتیبِ رویدادهای دو دیتاسنتر تعریف‌نشده‌ست.
  • توی معماریِ میکروسرویس، هر سرویس stateِ پایدارِ خودش رو داره و stateای بینِ سرویس‌ها مشترک نیست — رویدادهای دو سرویسِ متفاوت هیچ ترتیبی ندارن.
  • اپ‌هایی که state سمتِ کلاینت رو بلافاصله روی ورودیِ کاربر به‌روز می‌کنن (حتی آفلاین)، باعث می‌شن کلاینت و سرور رویدادها رو با ترتیب‌های متفاوت ببینن.
  • Building a fully ordered log usually means all events pass through a single leader that decides the order. If the event rate exceeds one machine's power, you must shard the log — and then the order of two shards' events is ambiguous.
  • If servers sit in several geographic regions (to survive losing a whole datacenter), each datacenter usually has its own leader since synchronous cross-continent coordination is slow — so the order of two datacenters' events is undefined.
  • In a microservice architecture each service has its own durable state with no state shared between services — two different services' events have no order.
  • Apps that immediately update client-side state on user input (even offline) make client and server see events in different orders.

به زبانِ صوری، تصمیم‌گرفتن روی ترتیبِ کاملِ رویدادها همون total order broadcast است که (فصلِ ۱۰) معادلِ consensus است. و الگوریتم‌های consensus برای جایی طراحی شدن که توانِ یک نود برای کلِ جریانِ رویداد کافی باشه — مکانیزمی ندارن که چند نود کارِ «مرتب‌کردن» رو بین خودشون تقسیم کنن.

Formally, deciding the total order of events is total order broadcast, which (Chapter 10) equals consensus. And consensus algorithms are built for the case where one node's power suffices for the whole event flow — they have no mechanism for several nodes to share the “ordering” work.

حالا سؤالِ ظریف‌تر: اگه پیوندِ علّی بینِ رویدادها نباشه، نبودِ ترتیبِ کامل مشکلِ بزرگی نیست — رویدادهای هم‌زمان رو می‌شه دلخواه مرتب کرد. به‌روزرسانی‌های متعددِ یک آبجکت رو هم می‌شه با هدایتِ همهٔ به‌روزرسانی‌های همون ID به یک shard، کاملاً مرتب کرد. ولی وابستگی‌های علّی گاهی پنهان‌ان. مثالِ کتاب: توی یه شبکهٔ اجتماعی، کاربری دوستش رو حذف می‌کنه (unfriend) و بعد برای بقیهٔ دوستانش پیامی دربارهٔ همون دوستِ سابق می‌فرسته — با این نیت که دوستِ سابق پیامِ تند رو نبینه. ولی اگه وضعیتِ دوستی یه‌جا و پیام‌ها جای دیگه‌ای ذخیره بشن، وابستگیِ ترتیبیِ «اول unfriend، بعد پیام» ممکنه گم بشه و سرویسِ اعلان، پیام رو قبل از unfriend پردازش کنه و اشتباهی به دوستِ سابق هم اعلان بفرسته. در واقع این اعلان‌ها یه join بینِ پیام‌ها و لیستِ دوستانن — همون مسئلهٔ زمانِ joinها.

Now the subtler question: if there's no causal link between events, lacking total order isn't a big problem — concurrent events can be ordered arbitrarily. Multiple updates of one object can be totally ordered by routing all of that ID's updates to one shard. But causal dependencies are sometimes hidden. The book's example: in a social network, a user unfriends someone (unfriend) and then messages the remaining friends about that ex-friend — intending the ex-friend not to see the harsh message. But if friendship state lives in one place and messages in another, the “unfriend first, then message” order may be lost, and the notification service may process the message before the unfriend and wrongly notify the ex-friend too. These notifications are really a join between messages and the friend list — the same join-timing problem.

راه‌هایی که کتاب برای گرفتنِ علّیت پیشنهاد می‌ده، بدونِ گلوگاهِ broadcastِ ترتیبِ کامل:

The book's suggested starting points for capturing causality without the total-order-broadcast bottleneck:

  • timestamp منطقی بدونِ هماهنگی ترتیبِ کامل می‌ده (فصلِ ۱۰)، ولی گیرنده هنوز باید رویدادهای نامرتب رو تحمل کنه و متادیتای اضافه حمل بشه.
  • می‌شه رویدادی لاگ کرد که وضعیتِ دیده‌شده توسط کاربر رو ثبت کنه و بهش شناسهٔ یکتا بدی؛ بعد رویدادهای بعدی با ارجاع به همون شناسه، وابستگیِ علّی رو ثبت می‌کنن.
  • الگوریتم‌های حلِ تعارض (فصل ۶) برای رویدادهایی که با ترتیبِ غیرمنتظره می‌رسن کمک می‌کنن — برای نگه‌داشتنِ state خوبن، ولی اگه action اثرِ بیرونی داشته باشه (مثلِ فرستادنِ اعلان) کاری نمی‌کنن.
  • Logical timestamps give total order without coordination (Chapter 10), but the receiver must still tolerate out-of-order events and extra metadata is carried.
  • You can log an event recording the user-seen state and give it a unique ID; later events cite that ID to record the causal dependency.
  • Conflict-resolution algorithms (Chapter 6) help for unexpectedly ordered events — good for keeping state, but useless when the action has an external effect (like sending a notification).

این یه درختِ تصمیم است. ریشه Event Ordering Needed با زمینهٔ «total order = consensus» — یعنی همون اول یادآوری می‌کنه داریم دربارهٔ مسئله‌ای به‌سختیِ اجماع حرف می‌زنیم. سؤالِ اول: Single Node Ordering? («one node must order all»). اگه جواب بله‌ست، مستقیم می‌ری به برگِ Total Order Log («single leader; simplest capped throughput») — ساده‌ترین راه، با سقفِ توانِ یک ماشین.

اگه نه، سؤالِ دوم: Same-Object Updates? («ordering only per key»). بله یعنی فقط به‌روزرسانی‌های یک آبجکت باید مرتب باشن، و برگِ Shard by Object ID («one shard per key no cross-shard order») — هر کلید به shard خودش، بدونِ هیچ ترتیبی بینِ shardها.

اگه مسئله فراتر از یک کلید باشه، سؤالِ سوم: Causal Order Needed? («or are events unlinked?»). اگه واقعاً پیوندِ علّی نیست، برگِ Order Arbitrarily («no causal link concurrent is fine») — رویدادهای هم‌زمان رو دلخواه مرتب کن. و اگه علّیت لازمه، سؤالِ چهارم: Reference Seen State? («log seen state, cite ID»). بله می‌شه برگِ Causal References («record the dependency cite the seen event») — همون ایدهٔ «ثبتِ چیزی که کاربر دیده بود». نه هم می‌شه برگِ Logical Timestamps («handle out-of-order side effects unsafe») — با timestamp منطقی جلو می‌ری، ولی می‌دونی اثرِ بیرونی هنوز ناامنه.

نکتهٔ خواندنِ درخت اینه: هرچی به راست می‌ری، از «ترتیبِ قوی و گران» به «ترتیبِ ضعیف و ارزان» می‌رسی؛ و هر برگ دقیقاً می‌گه چی رو فدا کردی و چی رو نگه داشتی.

This is a decision tree. The root is Event Ordering Needed with the context “total order = consensus'” — reminding you upfront that we're discussing a consensus-hard problem. First question: Single Node Ordering? (“one node must order all”). Yes goes straight to the Total Order Log leaf (“single leader; simplest, capped throughput”) — the simplest path, capped at one machine's power.

If not, second question: Same-Object Updates? (“ordering only per key”). Yes means only one object's updates must be ordered, so the Shard by Object ID leaf (“one shard per key, no cross-shard order”) — each key to its own shard, with no order between shards.

If the problem spans keys, third question: Causal Order Needed? (“or are events unlinked?”). If truly no causal link, the Order Arbitrarily leaf (“no causal link, concurrent is fine”) — order concurrent events arbitrarily. And if causality is needed, fourth question: Reference Seen State? (“log seen state, cite ID”). Yes becomes the Causal References leaf (“record the dependency, cite the seen event”) — the “record what the user had seen” idea. No becomes the Logical Timestamps leaf (“handle out-of-order, side effects unsafe”) — proceed with logical timestamps knowing external effects are still unsafe.

The way to read the tree: moving right goes from “strong, expensive order” to “weak, cheap order”; and each leaf says exactly what you sacrificed and what you kept.

۲.۱. حفظِ state مشتق‌شده2.1. Maintaining derived state

نمایِ مشتق‌شده نتیجهٔ تبدیلِ دادهٔ مبناست. برای نگه‌داشتنش باید تغییرهای جدید رو اعمال کنی، و برای اصلاحِ منطق هم باید امکانِ بازسازی از تاریخچه یا تصویرِ معتبر داشته باشی.

مثال فنی: یه سفارش، یه اصلاح

وضعیت اولیه: گزارشِ روزانه جمعِ ۱۰۰۰ داره و مبلغِ سفارش ۴۲ از ۲۰۰ به ۲۵۰ اصلاح می‌شه.

اجرای مرحله‌به‌مرحله: پردازشگر سهمِ قبلی رو کم می‌کنه و سهمِ جدید رو اضافه می‌کنه، یا تفاوتِ ۵۰ رو طبقِ نسخهٔ معتبر اعمال می‌کنه.

نتیجه و دلیل: اضافه‌کردنِ کورکورانهٔ ۲۵۰، گزارش رو ۱۲۵۰ می‌کنه؛ نگه‌داشتنِ نمایِ مشتق یعنی update و deleteِ دقیق — غصه نخور.

Integration's goal is data sitting in the right shape in all the right places: taking input, transforming, joining, filtering, aggregating, training models, evaluating, and writing to the right output. The tools are Chapters 11–12's batch and stream processors, and their outputs are those derived datasets: search indexes, materialized views, recommendations, aggregate metrics. You already know their fundamental difference: stream input is unbounded, batch input bounded and known.

پردازشِ batch یه طعمِ قویِ functional داره: تابع‌های قطعیِ خالص که خروجی‌شون فقط به ورودی بستگی داره و جز خروجیِ صریح، side effect ندارن؛ ورودی immutable و خروجی append-only. پردازشِ stream هم همینه، فقط عملگرها رو گسترش می‌ده تا stateِ مدیریت‌شده و fault-tolerant هم داشته باشن. این اصلِ «تابعِ قطعی با ورودی/خروجیِ مشخص» فقط برای تحملِ خطا خوب نیست؛ استدلال دربارهٔ dataflowهای یک سازمان رو هم ساده می‌کنه: فرقی نمی‌کنه مشتقِ ایندکس باشه یا مدلِ آماری یا کش — همه خطِ لوله‌ای‌ان که چیزی رو از چیزِ دیگری مشتق می‌کنن.

Batch processing has a strong functional flavor: pure deterministic functions whose output depends only on input, with no side effects but the explicit output; immutable input and append-only output. Stream processing is the same, only the operators grow to have managed, fault-tolerant state too. This “deterministic function with clear input/output” principle isn't just good for fault tolerance; it makes reasoning about an organization's dataflows simple: a derived index, a statistical model or a cache — all of them are pipelines deriving something from something else.

در اصل می‌شد سیستمِ مشتق رو همگام نگه داشت — همون‌طور که پایگاه دادهِ رابطه‌ای ایندکسِ ثانویه رو توی همون تراکنشِ نوشتن به‌روز می‌کنه. ولی ناهمگامی همون چیزیه که سیستمِ لاگ‌محور رو قوی می‌کنه: خطا توی یه گوشه مهار می‌شه؛ درحالی‌که تراکنشِ توزیع‌شده اگه یکی از شرکت‌کننده‌هاش بمیره abort می‌شه و خطا رو به بقیه سرایت می‌ده. همین‌طور ایندکسِ ثانویه‌ای که مرزِ shard رو رد می‌کنه، قابل‌اعتمادترین و مقیاس‌پذیرترین نگه‌داریش همون نگه‌داریِ ناهمگامه.

In principle the derived system could be kept synchronous — as a relational database updates its secondary index in the same write transaction. But asynchrony is exactly what makes the log-based system strong: errors in one corner stay contained, while a distributed transaction aborts if one participant dies and spreads the error to the rest. And the most reliable, scalable way to maintain a shard-crossing secondary index is asynchronous maintenance.

۲.۲. مهاجرتِ تدریجیِ نماها2.2. Gradual view migration

برای عوض‌کردنِ نمای داده بدونِ قطعِ خدمت، نسخهٔ تازه رو کنارِ نسخهٔ فعلی می‌سازیم، تغییرهای زنده رو بهش می‌رسونیم و بعد از بررسی، خواندن رو منتقل می‌کنیم.

مثال فنی: مهاجرتِ ایندکس، بدونِ حفره

وضعیت اولیه: search-v1 فعاله و v2 باید فیلدِ برند داشته باشه.

اجرای مرحله‌به‌مرحله: snapshot تا موقعیت ۵۰۰ توی v2 بارگذاری می‌شه؛ تغییرهای بعدی catch up می‌شن؛ و بعد از تطبیق، خواندن به v2 منتقل می‌شه.

نتیجه و دلیل: تغییرهای حینِ backfill گم نمی‌شن؛ ولی cutover پیش از رسیدن به مرزِ لازم می‌تونه نمایِ کهنه رو فعال کنه — سرِ هم نذار.

Streams reflect input changes in derived views with low latency; batch lets you reprocess the accumulated historical volume and build a fresh view of the existing dataset. And reprocessing is a great mechanism for application evolution: without it, schema evolution stays limited to simple changes (a fresh optional field, a fresh record); with it, a dataset can be rebuilt into a wholly different model that serves the new need better.

قیاسِ ریلِ راه‌آهن — مهاجرتِ schema در دنیای غیرکامپیوتریThe railway-track analogy — schema migration in the non-computer world

توی انگلستانِ قرنِ ۱۹ چند استانداردِ رقیب برای gauge (فاصلهٔ دو ریل) وجود داشت؛ قطارِ یک gauge روی ریلِ gauge دیگر نمی‌رفت. بعد از تثبیتِ gauge استاندارد در ۱۸۴۶، باید ریل‌ها تبدیل می‌شدن — ولی چطور، بدونِ بستنِ خط برای ماه‌ها؟ راه‌حل: اول ریل رو با افزودنِ ریلِ سوم به dual gauge تبدیل کردن؛ این کار تدریجی انجام شد و وقتی تموم شد، قطارهای هر دو gauge می‌تونستن روی خط برن. سرانجام که همهٔ قطارها به gauge استاندارد تبدیل شدن، ریلِ اضافه برداشته شد. «بازپردازشِ» ریل‌ها و نگه‌داشتنِ نسخهٔ قدیم و جدید کنار هم، تغییر رو در طولِ سال‌ها ممکن کرد — و هر مرحله برگشت‌پذیر بود.

In 19th-century England several competing standards existed for gauge (rail distance); a train of one gauge couldn't run on another gauge's rails. After the standard gauge was fixed in 1846, the rails had to convert — but how, without closing lines for months? The fix: first convert rails to dual gauge by adding a third rail; that was done gradually, and when finished, trains of both gauges could run on the line. Once all trains converted to the standard gauge, the extra rail was removed. “Reprocessing” the rails and keeping old and new versions side by side made the change possible over years — and every step was reversible.

نماهای مشتق همین اجازه رو می‌دن: اگه می‌خوای dataset رو بازسازی کنی، لازم نیست مهاجرت یه سوییچِ ناگهانی باشه. schema قدیم و جدید رو به‌صورتِ دو نمایِ مستقلِ مشتق از همان دادهٔ زیرین کنار هم نگه دار؛ بعد تعدادِ کمی کاربر رو ببر روی نمای تازه تا عملکردش رو بسنجی و باگش رو پیدا کنی، درحالی‌که اکثرِ کاربران هنوز به نمای قدیم می‌رن. تدریجاً سهمِ نمای تازه رو زیاد کن و در پایان نمای قدیم رو حذف کن. زیباییش اینه که هر مرحله به‌راحتی برگشت‌پذیره؛ همیشه یه سیستمِ سالم داری که بهش برگردی. و کم‌کردنِ ریسکِ آسیبِ برگشت‌ناپذیر، جرئتِ جلو‌رفتن و سرعتِ بهبود رو بیشتر می‌کنه.

Derived views allow the same: to rebuild a dataset, migration needn't be a sudden switch. Keep old and new schemas as two independent views derived from the same underlying data side by side; then move a few users to the fresh view to gauge its performance and find its bugs while most users still go to the old view. Gradually raise the fresh view's share and drop the old view at the end. Its beauty is that every step easily reverses; you always have a healthy system to return to. And lowering the risk of irreversible damage gives you more courage to move forward and more speed to improve.

A state machine with two lanes: Migration stages (the main path) and Reversible exit (the final outlet). ۲.۳. از lambda تا kappa2.3. From lambda to kappa

معماریِ Lambda معمولاً دو مسیرِ جدا داره: یکی دسته‌ای، یکی زنده. Kappa می‌کوشه بازپخشِ تاریخچه و پردازشِ زنده رو با مسیرِ مشترک انجام بده. مناسب بودنِ هرکدوم به نیاز و محدودیت‌هات بستگی داره.

مثال فنی: یه منطق، هم برای تاریخچه هم برای زنده

وضعیت اولیه: جمعِ فروش هم از فایلِ تاریخی و هم از جریانِ تازه محاسبه می‌شه.

اجرای مرحله‌به‌مرحله: اگه دو کد قواعدِ refund متفاوت داشته باشن، خروجی‌ها واگرا می‌شن؛ منطقِ مشترک با replayِ ورودیِ نسخه‌دار این اختلاف رو کم می‌کنه.

نتیجه و دلیل: kappa فقط «stream همه‌چیز» نیست؛ تاریخچهٔ کافی، بازپردازش، کنترلِ state و اثرهای بیرونی هم لازمن — یادت باشه.

The original proposal for integrating batch and stream was the lambda architecture, which had its own problems and is now retired. Newer systems let batch computation (history reprocessing) and stream computation (fresh-event processing) run in the same one system — an approach sometimes called kappa. Unifying in one system needs three things:

  • بازپخشِ تاریخچه از همون موتورِ پردازشی که جریانِ رویدادهای تازه رو می‌خوره (بروکرِ لاگ‌محور که replay بلده؛ پردازنده‌ای که از DFS/object store هم می‌خونه).
  • semantics دقیقاً-یک‌بار برای پردازندهٔ stream — یعنی خروجی همونی باشه که انگار هیچ خطایی رخ نداده، حتی اگه رخ داده باشه؛ مثلِ batch، با دورریختنِ خروجیِ ناقصِ taskهای شکست‌خورده.
  • windowing بر اساسِ event time، نه processing time — چون هنگامِ بازپردازشِ تاریخچه، زمانِ پردازش بی‌معناست (مثلِ APIی Beam که روی Flink یا Dataflow اجرا می‌شه).
  • History replay from the same processing engine that eats the fresh-event flow (a log-based broker that knows replay; a processor that also reads from DFS/object stores).
  • Exactly-once semantics for the stream processor — output identical to as if no error ever occurred, even when some did; like batch, by discarding broken tasks' partial output.
  • Windowing on event time, not processing time — since when reprocessing history, processing time is meaningless (like the Beam API running on Flink or Dataflow).

۳3 unbundle کردنِ پایگاه دادهUnbundling the database

باز کردنِ اجزای پایگاه داده یعنی کارهایی مثلِ ذخیره، ایندکس و پردازش رو بینِ ابزارهای جدا پخش کنیم. در مقابل، مسئولیتِ هماهنگیِ این اجزا بیشتر می‌ره سراغِ معماریِ برنامه.

مثال فنی: قطعاتِ جدا، یه قراردادِ مشترک

وضعیت اولیه: پایگاه داده سفارش رو نگه می‌داره و یه موتورِ دیگه جست‌وجوی متن رو سرو می‌کنه.

اجرای مرحله‌به‌مرحله: بینِ دو قطعه، لاگِ تغییر، مرزِ snapshot، موقعیتِ مصرف و مسیرِ بازسازی تعریف می‌شه.

نتیجه و دلیل: جدا کردنِ قابلیت‌های پایگاه داده انعطاف می‌ده، ولی هماهنگی‌ای که موتورِ یکپارچه انجام می‌داد رو باید صریحاً طراحی کنی — همین رو نگه دار.

At an abstract level a database, a batch/stream processor and an operating system all do one job: hold data and let you process and query it. A database keeps data in the records of a data model, a filesystem in files — but at their core both are “information management systems”, and the batch processor (Chapter 11) is like the distributed version of Unix. Real practical differences exist, of course (a directory with 10 million tiny files is a disaster for many filesystems; a table with 10 million tiny records is ordinary for a database). But the similarities and the differences are worth exploring.

Unix و پایگاه دادهِ رابطه‌ای با دو فلسفهٔ متفاوت سراغِ مدیریتِ اطلاعات رفتن: Unix یه انتزاعِ سطح‌پایینِ سخت‌افزار به برنامه‌نویس داد؛ پایگاه دادهِ رابطه‌ای یه انتزاعِ سطح‌بالا که پیچیدگیِ ساختارِ دیسک، هم‌زمانی و بازیابی از crash رو پنهان می‌کنه. Unix لوله و فایل ساخت (دنبالهٔ بایت)؛ پایگاه داده SQL و تراکنش. کدوم بهتره؟ بستگی داره چی می‌خوای. Unix «ساده‌تره» به این معنا که پوششِ نازکی روی سخت‌افزاره؛ پایگاه دادهِ رابطه‌ای «ساده‌تره» به این معنا که یه کوئریِ اعلانیِ کوتاه می‌تونه از زیرساختِ قدرتمندی (بهینه‌ساز، ایندکس، کنترلِ هم‌زمانی، replication) استفاده کنه بی‌آنکه نویسندهٔ کوئری جزئیاتِ پیاده‌سازی رو بدونه. این کشمکشِ چنددهه‌ای هنوز حل نشده (جنبشِ NoSQL رو می‌شه تلاش برای بردنِ رویکردِ سطح‌پایینِ سبکِ Unix به قلمروِ ذخیره‌سازیِ توزیع‌شدهٔ OLTP دونست). این بخش می‌خواد اون دو رو آشتی بده تا بهترینِ هر دو رو با هم داشته باشیم.

Unix and the relational database took two different philosophies to information management: Unix gave the programmer a low-level hardware abstraction; the relational database a high-level one hiding disk layout, concurrency, crash-recovery complexity. Unix built pipes and files (byte sequences); the database SQL and transactions. Which is better? Depends what you want. Unix is “simpler” in being a thin cover over hardware; the relational database is “simpler” in that a short declarative query can use powerful machinery (optimizer, indexes, concurrency control, replication) without the query author knowing the implementation details. This decades-long tension is still unresolved (the NoSQL movement can be seen as trying to bring Unix-style lightweight low-level approaches into distributed OLTP storage). This section wants to reconcile the two and have the best of both.

۳.۱. ساختِ ایندکس یعنی بازپردازش3.1. Building an index is reprocessing

ساختنِ ایندکسِ تازه، یه نوع پردازشِ دوبارهٔ دادهٔ موجوده. بعد از ساختِ اولیه باید تغییرهای هم‌زمان هم برسن تا ایندکس موقعِ استفاده از دادهٔ مرجع عقب نمونه.

مثال فنی: فیلترِ تازه یعنی backfill

وضعیت اولیه: ایندکسِ فعال فقط عنوانِ کالا رو داره و فیلترِ برند لازم شده.

اجرای مرحله‌به‌مرحله: همهٔ کالاهای قدیمی با کدِ تازه تبدیل می‌شن؛ و تغییرهای زنده هم تا مرزِ مشخص واردِ ایندکسِ جدید می‌شن.

نتیجه و دلیل: اضافه‌کردنِ ستون به schema بدونِ پردازشِ دادهٔ قبلی، مقدارِ برند رو برای رکوردهای قدیمی نمی‌سازه — ملاحظه کن.

Think of database features: secondary indexes, materialized views (precomputed caches of query results), replication logs, full-text indexes. And in Chapters 11–12 we talked about building exactly these with batch and stream. There's a deep parallel between an “internal database feature” and an “external derived system”.

نگاه کن وقتی CREATE INDEX رو توی پایگاه دادهٔ رابطه‌ای اجرا می‌کنی چه می‌شه: پایگاه داده باید روی یه snapshotِ سازگار از جدول بچرخد، مقادیرِ فیلدِ ایندکس‌شده رو برداره، مرتب کنه و ایندکس رو بنویسه؛ بعد backlog نوشته‌هایی که از زمانِ snapshot اومدن رو پردازش کنه (با فرضِ این‌که جدول قفل نبوده و نوشتن ادامه داشته)؛ و از اون به بعد ایندکس رو با هر تراکنشِ نوشتن به‌روز نگه داره. این فرآیند به‌طرزِ شگفتی شبیه راه‌انداختنِ یه follower تازه (فصل ۶) است و خیلی شبیه bootstrap کردنِ CDC توی سیستمِ جریانی. هر بار که CREATE INDEX می‌زنی، پایگاه داده عملاً datasetِ موجود رو بازپردازش می‌کنه و ایندکس رو به‌عنوانِ نمای تازه‌ای از دادهٔ موجود مشتق می‌کنه.

Watch what happens when you run CREATE INDEX in a relational database: the database must scan a consistent snapshot of the table, take the indexed field's values, sort them and write the index; then process the backlog of writes that arrived since the snapshot (assuming the table wasn't locked and writes continued); and from then on keep the index fresh with every write transaction. This process is surprisingly similar to starting a fresh follower (Chapter 6) and very similar to bootstrapping CDC in a streaming system. Every time you run CREATE INDEX, the database effectively reprocesses the existing dataset and derives the index as a fresh view of existing data.

از این زاویه، جریانِ دادهٔ کلِ یک سازمان شبیه یک پایگاه دادهِ خیلی بزرگ می‌شه: هر فرآیندِ batch، stream یا ETL که داده رو از جایی و شکلی به جای و شکلِ دیگری می‌بره، داره مثلِ همون زیرسیستمِ پایگاه داده عمل می‌کنه که ایندکس یا viewی materialized رو به‌روز نگه می‌داره. پردازنده‌های batch و stream می‌شن پیاده‌سازی‌های مفصلی از trigger و stored procedure و الگوریتمِ نگه‌داریِ viewی materialized؛ و سیستم‌های مشتق‌شده‌ای که نگه می‌دارن می‌شن «تیپ‌های ایندکسِ» متفاوت. فرقش اینه که به‌جای این‌که همه داخلِ یه محصولِ یکپارچه باشن، تکه‌تکه‌ان: نرم‌افزارهای متفاوت، روی ماشین‌های متفاوت، دستِ تیم‌های متفاوت.

From this angle, a whole organization's dataflow looks like one very large database: every batch, stream or ETL process moving data from one place and shape to another acts like the database subsystem keeping an index or materialized view fresh. Batch and stream processors become elaborate implementations of triggers and stored procedures and the materialized-view maintenance algorithm; and the derived systems they maintain become different “index types”. The difference is that instead of all living inside one integrated product, they're fragmented: different software, on different machines, owned by different teams.

۳.۲. federated در برابر unbundled3.2. Federated vs unbundled

توی جست‌وجوی فدره، یه درخواست از چند منبعِ داده می‌خونه و نتیجه‌ها رو ترکیب می‌کنه. توی معماریِ اجزای جدا، تغییرها از قبل بینِ ابزارها جریان دارن و نماهای مناسب ساخته می‌شن.

مثال فنی: خواندن با هم یا نوشتن با هم

وضعیت اولیه: گزارشِ فروش به سفارش در A و موجودی در B نیاز داره.

اجرای مرحله‌به‌مرحله: federation موقعِ query از دو منبع می‌خونه؛ unbundling تغییرهای منابع رو از قبل به نمایِ خدمت‌دهی می‌رسونه.

نتیجه و دلیل: اولی هزینه و سازگاریِ خواندنِ هم‌زمان رو داره، دومی هزینهٔ نگه‌داری و تازگیِ نما رو — این رو از قلم نینداز.

If you accept that no single data model or storage format fits every access pattern, there are two ways to combine different tools into one coherent system:

Federated databases (unifying reads)

توی خواندنِ فدره، یه درخواست به چند منبع می‌ره و پاسخ‌ها کنار هم قرار می‌گیرن. معنای زمان و سازگاریِ پاسخ‌ها باید روشن باشه.

مثال فنی: Joinِ دوردست، روی دو لحظهٔ متفاوت

وضعیت اولیه: query اول موجودی رو از A و بعد سفارش‌ها رو از B می‌خونه؛ بینِ این دو یه خریدِ تازه ثبت می‌شه.

اجرای مرحله‌به‌مرحله: بدونِ snapshotِ مشترک، نتیجه می‌تونه موجودیِ قبل و سفارشِ بعد رو با هم ترکیب کنه.

نتیجه و دلیل: رابطِ queryِ یکپارچه خودبه‌خود دیدگاهِ زمانیِ یکپارچه نمی‌ده؛ تضمینِ snapshot بینِ منابع باید صریح باشه — این رو جدی بگیر.

یه رابطِ کوئریِ یکپارچه روی موتورهای ذخیره‌سازی و روش‌های پردازشِ متنوع — مثلِ foreign data wrapper در PostgreSQL و موتورهای federated مثلِ Trino. اپی که مدلِ تخصصی می‌خواد مستقیم به موتورِ زیرین وصل می‌شه؛ کسی هم که می‌خواد از جاهای متفاوت ترکیب کنه، از رابطِ federated استفاده می‌کنه. این راه، سنتِ رابطه‌ایه: یه سیستمِ یکپارچه با زبانِ سطح‌بالا و semantic تمیز، ولی پیاده‌سازیِ پیچیده.

A unified query interface over diverse storage engines and processing methods — like foreign data wrappers in PostgreSQL and federated engines like Trino. An app that wants a specialized model connects directly to the underlying engine; whoever wants to combine from different places uses the federated interface. This is the relational tradition: one integrated system with a high-level language and clean semantics, but a complex implementation.

Unbundled databases (unifying writes)

توی یکپارچه‌سازیِ مسیرِ تغییر، دادهٔ مرجع از قبل به ابزارهای تخصصی منتقل می‌شه تا هر‌کدام نمایشِ مناسبِ خواندن رو نگه دارن.

مثال فنی: همون جریان، دو مقصد

وضعیت اولیه: تغییرِ P7, version=12 باید هم به کش برسد هم به جست‌وجو.

اجرای مرحله‌به‌مرحله: هر مقصد پیشرفتِ خودش رو ثبت می‌کنه و می‌تونه از لاگِ باقی‌مانده catch up کنه؛ نسخهٔ قدیمی نباید نسخهٔ تازه رو بازنویسی کنه.

نتیجه و دلیل: مقصدها می‌تونن موقتاً متفاوت باشن، ولی قراردادِ ترتیب و replay امکانِ همگامی و ترمیم رو می‌ده — دقت کن.

federation جوابِ کوئریِ فقط‌خواندنی روی چند سیستم رو می‌ده، ولی برای همگام‌کردنِ نوشتن‌ها روی اون سیستم‌ها جوابِ خوبی نداره. همون‌طور که داخلِ یه پایگاه داده «ساختنِ ایندکسِ سازگار» یه ویژگیِ داخلیه، وقتی چند سیستمِ ذخیره‌سازی رو ترکیب می‌کنی هم باید مطمئن بشی همهٔ تغییرها با وجودِ خطا به همهٔ جاهای درست می‌رسن. آسان‌کردنِ اتصالِ قابل‌اعتمادِ سیستم‌ها (با CDC و لاگِ رویداد) مثلِ unbundle کردنِ ویژگیِ نگه‌داریِ ایندکسِ پایگاه داده است — به‌شکلی که نوشتن‌ها رو روی فناوری‌های متفاوت همگام کنه. این راه، سنتِ Unix است: ابزارهای کوچکِ تک‌کاره که با یه API یکنواختِ سطح‌پایین (لوله) حرف می‌زنن و با زبانی سطح‌بالاتر (شل) ترکیب می‌شن.

Federation answers read-only queries over several systems, but has no good answer for synchronizing writes across them. Just as “building a consistent index” inside one database is an internal feature, when you combine several storage systems you must make sure every change reaches all the right places despite errors. Easing reliable system-to-system connection (with CDC and event logs) is like unbundling the database's index-maintenance feature — so that writes stay in sync across different technologies. This is the Unix tradition: small single-purpose tools speaking one uniform low-level API (pipes) and composed with a higher-level language (the shell).

۳.۳. چرا unbundle جواب می‌دهد3.3. Why unbundling works

این تفکیک وقتی به درد می‌خوره که ابزارهای تخصصی با قراردادِ روشن به هم وصل بشن. لاگ، بازپخش و قواعدِ تکرار و ترتیب، امکانِ ترمیم و بازسازی رو فراهم می‌کنن.

مثال فنی: نمای خراب، ولی قابلِ بازسازی

وضعیت اولیه: shardِ جست‌وجو پاک شده، ولی مرجع و تاریخچهٔ لازم سالم‌ان.

اجرای مرحله‌به‌مرحله: نمای تازه از snapshot و تغییرهای بعد از مرزش ساخته می‌شه و پیش از فعال شدن بررسی می‌شه.

نتیجه و دلیل: انعطافِ unbundling به بازسازی وابسته‌ست؛ بدونِ نگه‌داریِ ورودی و نسخهٔ تبدیل، از دست دادنِ نما شاید جبران‌ناپذیر باشه — خیالِ راحت.

Federation and unbundling are two sides of one coin: building a reliable, scalable system from diverse parts. Mapping one data model to another (for federated read-only queries) takes thought but is ultimately a manageability problem. The hard engineering problem is keeping writes in sync across several storage systems — and that's our focus here. Its traditional approach is distributed transactions over heterogeneous systems, which is problematic; transactions inside one storage system or stream are feasible, but when data crosses the boundary of two different technologies, the asynchronous event log with idempotent writes is far stronger and more practical. E.g. distributed transactions inside some stream processors work well for exactly-once semantics; but when a transaction must involve systems written by different groups (writing from a stream processor to a distributed key-value store or a search index), the lack of a standard transaction protocol makes integration hard — and the ordered log with an idempotent consumer is a far simpler abstraction, implementable across heterogeneous systems.

مزیتِ بزرگِ یکپارچه‌سازیِ لاگ‌محور، پیوندِ سست بینِ قطعاته، در دو سطح:

The big advantage of log-based integration is loose coupling between parts, on two levels. At the system level: asynchronous flows make the whole system resilient to one part's outage or slowness — if a consumer slows or dies, the log buffers the messages; producer and other consumers continue unaffected; the broken consumer catches up when fixed, no data is lost, and the error stays contained. At the human level: unbundling lets different teams develop and maintain parts and services independently of each other.

  • سطحِ سیستم: جریان‌های ناهمگام کلِ سیستم رو در برابرِ outage یا کندیِ یک قطعه قوی می‌کنن. اگه مصرف‌کننده‌ای کند شد یا مرد، لاگ پیام‌ها رو بافر می‌کنه؛ تولیدکننده و بقیهٔ مصرف‌کننده‌ها بی‌تأثیر ادامه می‌دن. مصرف‌کنندهٔ خراب وقتی درست شد catch-up می‌کنه، داده‌ای از دست نمی‌ره و خطا مهار می‌مونه. در مقابل، تعاملِ همگامِ تراکنشِ توزیع‌شده خطای محلی رو به خرابیِ بزرگ تشدید می‌کنه.
  • سطحِ انسانی: unbundle اجازه می‌ده قطعات و سرویس‌ها رو تیم‌های متفاوت، مستقل از هم توسعه و نگه‌داری کنن. تخصصی‌شدن یعنی هر تیم روی «یه کارِ خوب» تمرکز کنه با رابطِ مشخص به سیستمِ تیم‌های دیگه. لاگِ رویداد رابطیه که هم‌زمان هم به‌قدرِ کافی قدرتمنده (دوام و ترتیبِ رویدادها → ویژگیِ سازگاریِ نسبتاً قوی) و هم به‌قدرِ کافی عمومی که تقریباً برای هر نوع داده‌ای کاربرد داره.
  • System level: asynchronous flows harden the whole system against one part's outage or slowness. If a consumer slows or dies, the log buffers messages; the producer and other consumers continue unaffected. The broken consumer catches up when fixed, no data is lost and the error stays contained. Synchronous distributed-transaction interaction, by contrast, amplifies a local error into a large failure.
  • Human level: unbundling lets different teams develop and maintain parts and services independently. Specialization means each team focuses on “one job well” with a clear interface to other teams' systems. The event log is an interface simultaneously powerful enough (event durability and order → fairly strong consistency properties) and general enough for almost any data type.
unbundle به چه معنا نیستWhat unbundling is not

اگه unbundle آینده باشه، جای پایگاه داده‌ها رو به شکلِ فعلیشون نمی‌گیره. پایگاه داده‌ها همچنان لازم‌ان — برای نگه‌داشتنِ state توی پردازنده‌های stream و برای سروِ خروجیِ پردازش‌های batch و stream. موتورهای کوئریِ تخصصی هم برای workload خودشون مهم می‌مونن (موتورِ warehouse برای کوئریِ تحلیلیِ اکتشافی عالیه). پیچیدگیِ گردوندنِ چند زیرساخت هم واقعیه: هر نرم‌افزار منحنیِ یادگیری و قلقِ عملیاتیِ خودش رو داره، و باید تا می‌شه قطعاتِ متحرکِ کمتری داشته باشی. محصولِ یکپارچهٔ واحد ممکنه روی workload هدفش عملکردِ بهتر و قابل‌پیش‌بینی‌تری بده. ساختن برای مقیاسی که لازم نداری، تلاشِ هدررفته و قفل‌شدن توی طراحیِ خشکه — نوعی بهینه‌سازیِ زودرس. هدفِ unbundle رقابت با تک‌تکِ پایگاه داده‌ها روی عملکرد نیست؛ هدف ترکیبِ چند پایگاه داده برای پوششِ طیفِ خیلی وسیع‌تری از workloadهاست. بحث پهناست، نه عمق. پس اگه یه فناوری همهٔ نیازت رو می‌ده، همون رو بگیر و خودت از نو نساز؛ مزیتِ unbundle فقط وقتی بیرون می‌زنه که هیچ تکه‌نرم‌افزاری به‌تنهایی همهٔ نیازها رو نداشته باشه. خبرِ خوب: ابزارهای ترکیب دارن بهتر می‌شن — Debezium از خیلی پایگاه داده‌ها جریانِ تغییر می‌گیره، پروتکلِ Kafka داره استانداردِ de facto جریانِ رویداد می‌شه، و موتورهای نگه‌داریِ نمایِ افزایشی کشِ کوئری‌های پیچیده رو ازپیش‌محاسبه و به‌روز می‌کنن.

If unbundling is the future, it doesn't replace databases as such. Databases are still needed — for holding state in stream processors and for serving batch/stream processing outputs. Specialized query engines stay important for their own workload (the warehouse engine is excellent for exploratory analytical queries). The complexity of running several infrastructures is real too: each software has its own learning curve and operational quirks, so keep the moving parts as few as possible. A single integrated product may give better, more predictable performance on its target workload. Building for scale you don't need is wasted effort locked into rigid design — a kind of premature optimization. Unbundling's goal isn't competing with each database on performance; it's combining several databases to cover a far wider workload range. The debate is breadth, not depth.

So if one technology covers all your needs, take it and don't rebuild it yourself; unbundling's advantage only shows when no single piece of software covers every need. Good news: composition tools keep improving — Debezium streams changes from many databases, the Kafka protocol is becoming the de facto event-streaming standard, and incremental-view engines precompute and refresh caches of complex queries.

The two cards state the two ways of combining tools. توی طراحیِ جریان‌محور، تغییرِ دادهٔ ورودی، نتیجه‌های وابسته رو به‌روز می‌کنه. شبیه صفحه‌گسترده‌ایه که تغییرِ یه سلول، فرمول‌های وابسته رو دوباره محاسبه می‌کنه.

مثال فنی: هر خروجی، به داده‌اش وصل

وضعیت اولیه: اصلاحِ سفارش ۴۲، جمعِ روز، جمعِ شعبه و ویژگیِ مدل رو عوض می‌کنه.

اجرای مرحله‌به‌مرحله: dataflow وابستگی‌ها رو مشخص می‌کنه تا همون اصلاح به همهٔ خروجی‌های وابسته برسه.

نتیجه و دلیل: اگه یه مسیر فقط insert رو بفهمه و اون یکی update، نامِ مشترکِ «رویداد» اون‌ها رو سازگار نمی‌کنه — یادت نره.

The idea of “updating derived data when underlying data changes” isn't new. Spreadsheets have strong dataflow power: you put a formula in a cell (e.g. a column sum) and whenever the formula's input changes, the result auto-recomputes — exactly what we want at data-system scale: a database record changes, its index auto-updates, dependent views and aggregations auto-refresh; without worrying about refresh technicalities and trusting it works. The difference from spreadsheets is that today's data system must be fault-tolerant, scalable and durable, and must integrate different technologies written by different groups over time. Expecting all software built with one language and framework is unrealistic.

کدِ تبدیل، ورودیِ مرجع رو به یه خروجیِ مشتق‌شده تبدیل می‌کنه. برای بازپخشِ قابل‌اعتماد، ورودی‌های جانبی و رفتارِ غیرقطعی هم باید کنترل بشن.

مثال فنی: تابعی که دوباره اجرا می‌شه

وضعیت اولیه: رویدادِ فروش مبلغِ دلاری داره و نرخِ همون زمانِ معامله هم rate=50000 است.

اجرای مرحله‌به‌مرحله: تبدیل، مبلغِ ریالی رو با نرخِ همون رویداد حساب می‌کنه؛ replay نباید API نرخِ امروز رو بخونه.

نتیجه و دلیل: با ورودی و نسخهٔ منطقِ ثابت، نتیجه قابل‌تکرار می‌مونه؛ وابستگیِ پنهان به زمانِ حال، خروجیِ تاریخی رو عوض می‌کنه — این دام معروفه.

When one dataset derives from another, a transform function sits in the middle. A few examples:

  • ایندکسِ ثانویه با تابعِ ساده‌ای ساخته می‌شه: به‌ازای هر سطر/سندِ جدولِ پایه، مقادیرِ ستونِ ایندکس‌شده برداشته و بر اساسِ اون‌ها مرتب می‌شن (اگه ایندکس SSTable یا B-tree باشه که بر اساسِ کلید مرتب‌ان).
  • ایندکسِ full-text با توابعِ پردازشِ زبان (تشخیصِ زبان، سگمنتیشنِ کلمه، stemming، اصلاحِ املا، مترادف‌یابی) و بعد ساختنِ ساختارِ جستجوی کارا (ایندکسِ معکوس) ساخته می‌شه.
  • توی سیستمِ ML می‌شه مدل رو مشتق از دادهٔ آموزشی دونست (با استخراجِ ویژگی و تحلیلِ آماری)؛ و خروجیِ مدل روی ورودیِ تازه هم مشتق از همون ورودی و پارامترهای یادگرفته‌شده است (یعنی غیرمستقیم، از دادهٔ آموزشی).
  • کش اغلب تجمیعی از داده به همون شکلیه که قراره در UI نمایش داده بشه؛ و پرکردنِ کش نیازمندِ دونستنِ اینه که UI به کدوم فیلدها ارجاع می‌ده، و تغییرِ UI ممکنه تعریفِ پرکردنِ کش رو عوض کنه و بازسازیش رو لازم کنه.
  • A secondary index is built with a simple function: for each row/document of the base table, take the indexed column's values and sort by them (if the index is an SSTable or B-tree, which are key-sorted).
  • A full-text index is built with language-processing functions (language detection, word segmentation, stemming, spell correction, synonym finding) and then an efficient search structure (inverted index).
  • In an ML system the model can be seen as derived from training data (via feature extraction and statistical analysis); and the model's output on fresh input is derived from that input and the learned parameters (i.e. indirectly, from training data).
  • A cache is often an aggregation of data in the shape the UI will display; so filling the cache needs knowing which fields the UI references, and a UI change may redefine cache filling and require rebuilding it.

تابعِ مشتقِ ایندکسِ ثانویه انقدر پرتکراره که داخلِ خیلی پایگاه داده‌ها به‌عنوانِ ویژگیِ اصلی تعبیه شده و با یه CREATE INDEX صداش می‌زنن. ولی برای full-textِ پیشرفته، تنظیمِ دامنه‌ خاص لازمه؛ و در ML، مهندسیِ ویژگی بدنامه به application-specific بودن و نیاز به دانشِ دقیقِ تعاملِ کاربر و استقرار. وقتی تابعِ ساختِ dataset مشتق، تابعِ استانداردِ قالبی نیست، کدِ سفارشی لازمه — و این دقیقاً همون جاییه که خیلی پایگاه داده‌ها به زحمت می‌افتن: trigger و stored procedure و UDF دارن، ولی این‌ها توی طراحیِ پایگاه داده یه کم «بعداً اضافه‌شده» بودن.

The secondary-index derivation function is so common it's embedded in many databases as a core feature, invoked with one CREATE INDEX. But advanced full-text needs domain-specific tuning; and in ML, feature engineering is notorious for being application-specific, needing precise knowledge of user interaction and deployment. When the derived-dataset-building function isn't a standard template, custom code is needed — and that is exactly where many databases struggle: they have triggers, stored procedures and UDFs, but these were somewhat “bolted on” in database design.

۴.۲. جداییِ کد و state4.2. Separating code and state

جدا کردنِ کد و وضعیت یعنی عمرِ پردازشگر رو از عمرِ داده مستقل کنی. پردازشگر قابل‌جایگزینیه، ولی وضعیت و محلِ ادامه باید یه جای معتبر حفظ بشن.

مثال فنی: کد عوض می‌شه، state می‌مونه

وضعیت اولیه: پردازشگرِ جمعِ فروش تا offset ۱۰۰۱ پیش رفته و stateش پایداره.

اجرای مرحله‌به‌مرحله: نسخهٔ تازه با schemaِ سازگارِ state از همون checkpoint ادامه می‌ده؛ توی تغییرِ ناسازگار، مهاجرت یا بازسازی لازمه.

نتیجه و دلیل: restart کد نباید جمع رو صفر کنه و ورودی رو از وسط شروع کنه؛ state و موقعیتِ ورودی باید با هم معنی داشته باشن — یادت نره.

In theory the database could be the deployment environment for arbitrary application code, just like the operating system. In practice it turned out badly: it pairs poorly with modern development needs (dependency and package management, version control, rolling upgrades, evolvability, monitoring, calling network services, integrating with external systems). Cluster deployment and management tools (Kubernetes, Docker, Mesos, YARN and the rest) are built exactly for this — and since they focus on “one job well”, they do it far better than a database for which running UDFs is just one of dozens of features.

اکثر وب‌اپ‌های امروز به‌صورتِ سرویسِ stateless مستقر می‌شن: هر درخواستی به هر سروری می‌تونه بره و سرور بعد از پاسخ، همه‌چیز رو فراموش می‌کنه. اضافه‌وکم‌کردنِ سرور راحته — ولی state باید یه جا بره (معمولاً پایگاه داده). روند این بوده که منطقِ stateless رو از مدیریتِ state جدا نگه دارن: نه منطقِ اپلیکیشن توی پایگاه داده، نه state پایدار توی اپلیکیشن. (به شوخیِ اهلِ functional programming: «ما به جداییِ Church و state اعتقاد داریم» — اشاره به Alonzo Church و lambda calculus که state mutable نداره.)

Most web apps today deploy as stateless services: any request can go to any server, and after responding the server forgets everything. Adding/removing servers is easy — but state has to go somewhere (usually a database). The trend has been keeping stateless logic separate from state management: no application logic in the database, no durable state in the application. (To borrow the functional programmers' joke: “we believe in the separation of Church and state” — a nod to Alonzo Church and the state-free lambda calculus.)

توی این مدلِ رایج، پایگاه داده مثلِ یه متغیرِ مشترکِ mutable است که از روی شبکه به‌صورتِ همگام خونده و به‌روز می‌شه؛ و پایگاه داده دوام و کمی کنترلِ هم‌زمانی و تحملِ خطا رو به عهده می‌گیره. ولی توی اکثر زبان‌ها نمی‌شه به تغییرِ متغیر subscribe کرد — فقط می‌شه دوره‌ای خوندش (patternِ observer رو باید خودت پیاده کنی؛ ویژگیِ داخلیِ زبان نیست). پایگاه داده‌ها همین رویکردِ منفعل رو به ارث بردن: اگه بخوای بفهمی محتوای پایگاه داده عوض شده، اغلب تنها راه poll است (تکرارِ دوره‌ایِ کوئری). subscribe به تغییرها تازه داره به‌عنوانِ ویژگی ظهور می‌کنه.

In this common model the database is like a shared mutable variable, read and updated synchronously over the network; and the database takes on durability plus some concurrency control and fault tolerance. But in most languages you can't subscribe to a variable's change — you can only poll it periodically (the observer pattern has to be hand-built; it isn't a built-in language feature). Databases inherited that passive approach: to learn the database's content changed, often the only way is polling (periodically repeating a query). Subscribing to changes is only now emerging as a feature.

dataflow: رابطهٔ کد و state را از نو مذاکره کنDataflow: renegotiating the code/state relationship

فکرکردن بر حسبِ dataflow یعنی به‌جای این‌که پایگاه داده رو متغیرِ منفعلی بدانی که اپلیکیشن دستکاری‌اش می‌کنه، خیلی بیشتر به تعامل و همکاریِ state، تغییرِ state و کدی که آن‌ها را پردازش می‌کند فکر کنی: کدِ اپلیکیشن به تغییرِ state در یک‌جا با راه‌انداختنِ تغییرِ state در جای دیگر واکنش نشان می‌ده. این ایده رو توی CDC، مدلِ actor، trigger و نگه‌داریِ نمایِ افزایشی دیدیم؛ unbundle کردنِ پایگاه داده یعنی اعمالِ همون روی ساختِ dataset مشتق بیرونِ پایگاه دادهٔ اصلی: کش، ایندکسِ جستجو، ML، سیستمِ تحلیلی — با پردازشِ stream و سیستمِ پیام‌رسانی. نگه‌داریِ دادهٔ مشتق سه چیز می‌خواد که بروکرِ لاگ‌محور می‌ده: ترتیبِ تغییرهای state (چون چند نما باید رویدادها رو به‌همان‌ترتیب بخورن تا با هم سازگار بمونن) و تحملِ خطا (گم‌شدنِ حتی یک پیام، مشتق رو برای همیشه از منبع عقب می‌ندازه؛ هم تحویلِ پیام و هم به‌روزرسانیِ state مشتق باید قابل‌اعتماد باشن). ترتیبِ پایدار و پردازشِ fault-tolerant خواسته‌های سختی‌ان، ولی خیلی ارزون‌تر و عملیاتی‌تر از تراکنشِ توزیع‌شده‌ان؛ پردازنده‌های stream مدرن این تضمین‌ها رو در مقیاس می‌دن و اجازه می‌دن کدِ اپلیکیشن به‌صورتِ عملگرِ stream اجرا بشه — کدِ دلخواهی که توابعِ مشتقِ داخلیِ پایگاه داده معمولاً نمی‌دن. و مثلِ ابزارهای Unix که با لوله زنجیر می‌شن، عملگرهای stream رو می‌شه ترکیب کرد و سیستم‌های بزرگ حولِ dataflow ساخت: هر عملگر جریانِ تغییرِ state رو ورودی می‌گیره و جریانِ تغییرِ state دیگری خروجی می‌ده.

Thinking in dataflow means renegotiating the code/state relationship: instead of seeing the database as a passive variable the application manipulates, think far more about the interaction of state, state change, and the code processing them — application code reacts to a state change in one place by triggering a state change elsewhere. We've seen this idea in CDC, the actor model, triggers and incremental view maintenance; unbundling the database means applying it to building derived datasets outside the main database: caches, search indexes, ML, analytical systems — with stream processing and messaging. Maintaining derived data needs three things a log-based broker provides: ordered state changes (several views must consume events in the same order to stay mutually consistent) and fault tolerance (losing even one message leaves the derivative permanently behind its source; both message delivery and derived-state updates must be reliable). Stable order and fault-tolerant processing are hard demands, but far cheaper and more operational than distributed transactions; modern stream processors give these guarantees at scale and let application code run as stream operators — arbitrary code that databases' built-in derivation functions usually don't offer. And like Unix tools chained with pipes, stream operators compose into large dataflow-built systems: each operator takes one state-change flow as input and emits another.

۴.۳. stream در برابر RPC4.3. Streams vs RPC

توی RPC، برای هر نیاز از سرویسِ دیگه پاسخ می‌خوای. با جریانِ تغییرها می‌تونی نسخهٔ محلی بسازی و ازش بخونی؛ این روش، وابستگیِ لحظه‌ای رو با مسئلهٔ تازگی عوض می‌کنه.

مثال فنی: نرخ ارز، از جریانِ محلی

وضعیت اولیه: پردازشگر برای هر سفارش به آخرین نرخِ معتبر نیاز داره؛ سرویسِ نرخ موقتاً قطع می‌شه.

اجرای مرحله‌به‌مرحله: با subscription، آخرین نرخِ دریافت‌شده همراهِ نسخه و زمان توی state محلی هست؛ با RPCِ هر سفارش، قطعِ سرویس مستقیماً مسیر رو معطل می‌کنه.

نتیجه و دلیل: جریان، وابستگیِ لحظه‌ای رو کم می‌کنه، ولی سیاستِ نرخِ کهنه و زمانِ اعتبار باید مشخص باشه — گوش کن.

Today's dominant style is breaking capability into services talking over synchronous network requests (REST); its advantage over monoliths is organizational scalability with loose coupling (different teams, independent deploys). Composing stream operators in a dataflow system has many of the same properties, but the communication mechanism differs: a one-way asynchronous message flow instead of synchronous request interaction. Beyond advantages like better fault tolerance, a dataflow system can also be faster than REST/RPC. The book's example: a customer buys an item priced in one currency but pays in another; the conversion needs the day's exchange rate. Two ways:

  • میکروسرویس: کدِ پردازشِ خرید، سرویس یا پایگاه دادهٔ نرخِ ارز رو برای نرخِ جاری کوئری می‌کنه.
  • dataflow: کدِ پردازشِ خرید از قبل مشترکِ جریانِ به‌روزرسانیِ نرخِ ارز شده و نرخِ جاری رو هر بار که عوض بشه توی یه پایگاه دادهٔ محلی ضبط می‌کنه؛ موقعِ پردازشِ خرید مستقیم همون پایگاه دادهٔ محلی رو می‌خونه (شاید روی همون ماشین، حتی همون پروسه).
  • Microservices: the purchase-processing code queries the exchange-rate service or database for the current rate.
  • Dataflow: the purchase-processing code already subscribes to the exchange-rate update flow and records the current rate in a local database every time it changes; when processing the purchase it reads that same local database directly (perhaps on the same machine, even the same process).

راهِ دوم درخواستِ شبکه‌ایِ همگام به سرویسِ دیگه رو با کوئریِ محلی جایگزین می‌کنه. توی راهِ اول هم می‌شد نرخ رو محلی کش کرد، ولی برای تازه‌نگه‌داشتنِ کش باید دوره‌ای poll می‌کردی یا مشترکِ جریانِ تغییر می‌شدی — که دقیقاً همون کارِ راهِ دومه. و راهِ dataflow نه‌فقط سریع‌تر، که در برابرِ خرابیِ سرویسِ دیگه هم قوی‌تره: سریع‌ترین و قابل‌اعتمادترین درخواستِ شبکه‌ای، هیچ درخواستی نیست! به‌جای RPC حالا یه joinِ جریانی بینِ رویدادهای خرید و رویدادهای به‌روزرسانیِ نرخ داری. این join وابسته‌به‌زمانه: اگه رویدادهای خرید رو بعداً بازپردازش کنی، نرخ عوض شده؛ برای بازسازیِ خروجیِ اصلی باید نرخِ تاریخیِ همون لحظهٔ خرید رو داشته باشی — چه با کوئریِ سرویس، چه با اشتراکِ جریان، این وابستگیِ زمانی رو باید مدیریت کنی. مشترک‌شدن در جریانِ تغییر (به‌جای کوئریِ state جاری در لحظهٔ نیاز) ما رو به مدلِ محاسباتیِ spreadsheet-گونه نزدیک می‌کنه: داده‌ای عوض بشه، هر مشتقِ وابسته‌اش سریع به‌روز می‌شه.

The second way replaces a synchronous network request to another service with a local query. The first way could cache the rate locally too, but keeping the cache fresh would need periodic polling or subscribing to the change flow — which is exactly the second way's work. So the dataflow way is not only faster but also more resilient to the other service's failure: the fastest, most reliable network request is no request at all! Instead of RPC you now have a streaming join between purchase events and rate-update events. And that join is time-dependent: if you later reprocess purchase events, the rates have changed; to reproduce the original output you need that purchase moment's historical rate — whether by querying the service or subscribing to the flow, this time dependency has to be managed. Subscribing to the change flow (instead of querying current state at need-time) brings us closer to a spreadsheet-like computation model: data changes, every dependent derivative updates fast.

On that purchase-entry arrow in act two sits another key note: “this is a streaming join between purchase events and rate updates — time-dependent: reprocessing wants historical rates.”

۴.۴. مسیرِ نوشتن و مسیرِ خواندن4.4. Write path and read path

مسیرِ نوشتن داده رو ثبت می‌کنه و نماهای مناسب رو آماده می‌کنه. مسیرِ خواندن از این نماها جواب می‌سازه؛ بخشی از هزینه می‌تونه از زمانِ خواندن به زمانِ تغییر منتقل بشه.

مثال فنی: هزینه رو کجا می‌دیم؟

وضعیت اولیه: برای هر خرید، جمعِ روزانه توی نمای sales_by_day به‌روز می‌شه.

اجرای مرحله‌به‌مرحله: مسیرِ نوشتن کارِ نگه‌داریِ نما رو انجام می‌ده؛ مسیرِ خواندن فقط مقدارِ آماده رو می‌گیره.

نتیجه و دلیل: خواندنِ سریع، در عوضِ نوشتن و ترمیمِ پرهزینه‌تره؛ و اگه query عوض بشه، نمایِ قدیمی ممکنه کافی نباشه — این رو نگه دار.

The previous section's dataflow systems give you a process for building derived datasets and keeping them fresh — call it the write path: whenever information is written, it may pass several batch and stream stages until all derived datasets update; Fig. 13-1 shows search-index updating as an example. But why build a derived dataset at all? Because you'll probably want to query it later — that is the read path: when serving a user request, you read from the derivative, perhaps process further and build the answer. Together, the whole data journey from collection moment to consumption moment (probably by another human). The write path is the journey's precomputed part — eager, as soon as data arrives, unasked; the read path is the part happening only when someone asks (lazy). If you know functional languages, the write path resembles eager evaluation and the read path lazy evaluation.

dataset مشتق جاییه که دو مسیر به هم می‌رسن. پس یه بده‌بستان بینِ «چقدر کار موقعِ نوشتن» و «چقدر کار موقعِ خواندن» داریم. ایندکسِ full-text نمونهٔ خوبیه: نوشتن باید ورودیِ ایندکسِ همهٔ termهای سند رو به‌روز کنه؛ خواندن باید هر کلمهٔ کوئری رو بجوید و منطقِ Boolean بزنه (AND برای «همهٔ کلمات»، OR برای مترادف‌ها). اگه ایندکس نداشتی، کوئری باید همهٔ سندها رو scan می‌کرد (مثلِ grep) — نوشتن ارزان، خواندن خیلی گران. سرِ دیگرِ طیف، می‌شد جوابِ همهٔ کوئری‌های ممکن رو ازپیش‌محاسبه کرد — خواندن فقط «پیدا کن و برگردان»، ولی نوشتن وحشتناک گران؛ و چون مجموعهٔ کوئری‌های ممکن نامتناهی است (نمایی در تعدادِ termها)، اصلاً شدنی نیست. گزینهٔ میانی: فقط جوابِ پرکاربردترین کوئری‌ها رو ازپیش‌محاسبه کن (کشِ کوئری‌های رایج — که می‌شه اسمش رو viewی materialized هم گذاشت، چون با آمدنِ سندِ تازه باید به‌روز بشه) و کوئری‌های نادر رو از ایندکس سرو کن. و نقشِ کش و ایندکس و viewی materialized ساده‌ست: جابه‌جاکردنِ مرزِ بینِ مسیرِ خواندن و مسیرِ نوشتن — با ازپیش‌محاسبه، کارِ بیشتری موقعِ نوشتن می‌کنی تا موقعِ خواندن کمتر کار کنی. (این‌جابه‌جاییِ مرز، موضوعِ همان مطالعهٔ موردیِ timeline شبکهٔ اجتماعی در فصلِ ۱ بود — با مرزِ متفاوت برای سلبریتی و کاربرِ عادی. بعد از ۵۰۰ صفحه به نقطهٔ شروع برگشتیم!)

The derived dataset is where the two paths meet. So it's a tradeoff between “how much work at write time” and “how much at read time”. The full-text index is a good example: writing must update the index entries of every document term; reading must look up each query word and apply Boolean logic (AND for “all words”, OR for synonyms). Without an index, queries would scan all documents (like grep) — cheap writes, very expensive reads. At the spectrum's other end, you could precompute every possible query's answer — reading just “find and return”, but horribly expensive writing; and since the possible-query set is infinite (exponential in term count), not feasible at all. The middle option: precompute only the most-used queries' answers (a cache of common queries — also nameable a materialized view, since fresh documents must update it) and serve rare queries from the index. So the role of caches, indexes and materialized views is simple: moving the boundary between read path and write path — precomputing means doing more work at write time to do less at read time. (This boundary-shifting was the subject of the Chapter-1 social-timeline case study — with different boundaries for celebrities and ordinary users. After 500 pages we're back where we started!)

۴.۵. کلاینتِ stateful و «خواندن‌ها هم رویدادند»4.5. Stateful clients; reads are events too

کلاینت می‌تونه وضعیتِ محلی و اشتراکِ فعال داشته باشه. توی این حالت، پاسخ فقط یه عکسِ لحظه‌ای نیست؛ تغییرهای مرتبط هم باید به کاربر برسن.

مثال فنی: خواندن به‌صورت subscription

وضعیت اولیه: کلاینت با درخواستِ q7 می‌خواد وضعیتِ سفارش ۴۲ رو دنبال کنه.

اجرای مرحله‌به‌مرحله: سیستم q7 رو با تغییرهای سفارش join می‌کنه و بعد از snapshotِ اولیه، updateها رو می‌رسونه؛ reconnect باید gap و تکرار رو کنترل کنه.

نتیجه و دلیل: خواندنِ یک‌باره با پاسخ تموم می‌شه؛ subscription یه وابستگیِ زنده و stateِ مدیریت‌پذیر می‌سازه — یه چیزِ دیگه یادت نره.

The write/read-path boundary idea shows up in another context too. Browsers used to be stateless clients (offline you could only scroll the previous page); but single-page web apps and mobile apps now keep lots of state on-device. With durable local state, a class of apps can work offline and sync in the background when the network returns — and since the UI needn't wait for synchronous requests, the experience is far better. On-device state can be seen as a cache of server state: the page's pixels are a materialized view of the client app's model objects, and the model objects are a local replica of the far datacenter's state.

ولی صفحهٔ وبِ معمولی تغییرِ بعدیِ سرور رو نمی‌فهمه تا reload کنی — کشِ کهنه‌ایه که pollش نمی‌کنی. پروتکل‌های تازه‌تر (server-sent events، WebSocket) کانالی می‌دن که سرور از همون راه تغییرِ state رو push کنه و کهنگیِ state سمتِ کلاینت کم بشه. توی مدلِ مسیرها، این یعنی کشیدنِ مسیرِ نوشتن تا خودِ کاربر: کلاینت برای state اولیه هنوز مسیرِ خواندن لازم داره، ولی بعدش به جریانِ تغییرهای سرور تکیه می‌کنه. دستگاه‌ها گاهی آفلاین‌ان و اعلان رو نمی‌گیرن — ولی همون تکنیکِ offset مصرف‌کنندهٔ بروکرِ لاگ‌محور این‌جا هم جواب می‌ده: هر دستگاه یه subscriber کوچیک به یه جریانِ کوچیکه که بعد از وصل‌شدنِ دوباره چیزی رو از دست نمی‌ده. تغییرهای state می‌تونن یه مسیرِ نوشتنِ سرتاسری رو طی کنن: از تعاملِ یه دستگاه، از لاگ و مشتق‌ها و پردازنده‌ها، تا UI دستگاهِ دیگه — با تأخیرِ زیرِ یک ثانیه. چرا همهٔ اپ‌ها این‌طوری نیستن؟ چون فرضِ «کلاینتِ stateless + request/response» توی پایگاه داده و کتابخانه و پروتکل ریشه دوانده؛ خیلی datastoreها عملیاتِ «یک درخواست، یک پاسخ» دارن و خیلی کم‌ترشان «یک درخواست، جریانی از پاسخ‌ها در طولِ زمان» (subscribe به تغییر) بلدن. کشیدنِ مسیرِ نوشتن تا کاربر یعنی بازاندیشیِ بنیادین به‌سمتِ publish/subscribe — پرهزینه، ولی UI پاسخ‌گوتر و آفلاینِ بهتر.

But the ordinary web page doesn't learn the server's next change until reload — a stale cache you don't poll. Newer protocols (server-sent events, WebSocket) give a channel for the server to push state changes down the same path, cutting client-side staleness. In the paths model, this means pulling the write path all the way to the user: the client still needs the read path for initial state, but then relies on the server's change flow. Devices are sometimes offline and miss notifications — but the log-based broker's consumer-offset technique works here too: each device is a tiny subscriber to a tiny flow that loses nothing after reconnecting. State changes can travel an end-to-end write path: from one device's interaction, through logs, derivatives and processors, to another device's UI — with sub-second latency. Why aren't all apps like this? Because the “stateless client + request/response” assumption is rooted in databases, libraries and protocols; many datastores have “one request, one response” operations and far fewer know “one request, a flow of responses over time” (subscribing to change). Pulling the write path to the user means fundamental rethinking toward publish/subscribe — costly, but a more responsive UI and better offline.

یه قدم جلوتر: تا این‌جا نوشتن‌ها از لاگ می‌رفتن و خواندن‌ها درخواستِ گذرای شبکه بودن که مستقیم به نودِ نگه‌دارنده می‌رفتن. ولی می‌شه درخواستِ خواندن رو هم به‌صورتِ جریانِ رویداد نشون داد و هم رویدادِ خواندن و هم رویدادِ نوشتن رو از یه عملگرِ stream رد کرد؛ عملگر با انتشارِ نتیجه به جریانِ خروجی به رویدادِ خواندن جواب می‌ده. وقتی خواندن و نوشتن هر دو رویداد باشن و به یه عملگر برسن، داری یه joinِ stream-table بینِ جریانِ کوئری‌های خواندن و پایگاه داده انجام می‌دی: هر رویدادِ خواندن باید به shardای بره که دادهٔ مربوط رو داره — درست مثلِ copartition کردنِ ورودی‌ها روی همون کلید در joinهای batch و stream. این تناظرِ «سروِ درخواست = join» بنیادیه: خواندنِ one-off از عملگرِ join رد می‌شه و عملگر بلافاصله فراموشش می‌کنه؛ درخواستِ subscribe یه joinِ پایداره با رویدادهای گذشته و آیندهٔ اون‌طرفِ join. لاگ‌کردنِ رویدادهای خواندن برای ردیابیِ وابستگیِ علّی و provenance هم فایده داره (می‌شه بازسازی کرد کاربر قبل از تصمیم چه دیده بود — مثلاً تاریخِ ارسال و موجودی‌ای که مشتری دیده روی خریدش اثر می‌ذاره)؛ ولی هزینهٔ ذخیره‌سازی و I/O اضافه داره و بهینه‌سازیش مسئلهٔ بازِ پژوهشیه.

When reads and writes are both events reaching one operator, you're doing a stream-table join. A one-off read passes through the join operator and the operator immediately forgets it; a subscribe is a durable join with the other side's past and future events. Logging reads also improves provenance and causal tracing, at storage and I/O cost.

برای کوئریِ تک-shard، فرستادن از دلِ stream و جمع‌کردنِ پاسخِ جریانی شاید overkill باشه؛ ولی این ایده درِ اجرایِ توزیع‌شدهٔ کوئری‌های پیچیدهٔ چندshardی رو باز می‌کنه با همون زیرساختِ مسیریابی و shard و joinِ پردازندهٔ stream. نمونه: distributed RPC در Storm برای «اجتماعِ مجموعهٔ فالوئرهای همهٔ کسانی که یک URL رو پست کرده‌اند» (ترکیبِ نتیجهٔ خیلی shardها)، یا ارزیابیِ ریسکِ تقلبِ یک خرید با join پی‌درپی با پایگاه‌های داده reputation که هر‌کدام جدا shard شده‌اند. اگه این جنس join چندshardی لازم داری، احتمالاً ساده‌تره از پایگاه‌داده‌ای استفاده کنی که همین ویژگی رو بده تا این‌که با پردازندهٔ stream پیاده‌اش کنی — ولی «کوئری به‌مثابهٔ جریان» گزینه‌ایه برای اپ‌های بزرگی که به سقفِ راه‌حل‌های آماده می‌خورن.

For single-shard queries, sending through the stream and gathering the streaming answer may be overkill; but this idea opens the door to distributed execution of complex multishard queries with the same routing, sharding and join machinery of the stream processor. Example: distributed RPC in Storm for “unioning the follower sets of everyone who posted a URL” (combining many shards' results), or fraud-risk scoring of a purchase by successive joins with reputation databases each sharded separately. If you need this kind of multishard join, it's probably simpler to use a database offering the feature than to implement it with a stream processor — but “queries as flows” is an option for big apps hitting ready-made solutions' ceilings.

۵5 هدف‌گرفتنِ درستی (Aiming for Correctness)Aiming for correctness

درستیِ کلِ برنامه به قراردادِ همهٔ مراحل وابسته‌ست. ذخیره‌سازِ قوی نمی‌تونه ورودیِ غلط، شناسهٔ اشتباه یا اثرِ بیرونیِ تکراری رو خودبه‌خود اصلاح کنه.

مثال فنی: تراکنش درست، ولی با هویتِ غلط

وضعیت اولیه: درخواستِ اول سفارش رو با id=r7 ثبت می‌کنه، ولی پاسخ گم می‌شه.

اجرای مرحله‌به‌مرحله: کلاینت برای retry شناسهٔ r8 می‌سازه؛ هر تراکنش جداگانه کاملاً serializable است، ولی دو سفارش ثبت می‌شن.

نتیجه و دلیل: درستیِ دامنه از لایهٔ کلاینت تا مقصد ادامه داره؛ isolationِ قوی، دو درخواستِ مستقل رو یه نیتِ واحد تشخیص نمی‌ده — مواظبِ این دام باش.

With a read-only stateless service, if something breaks it's no problem: you fix the bug, restart, and everything returns. A stateful system like a database isn't like that: it's supposed to remember (more or less) everything forever, so a failure's effect potentially lasts forever too — and needs more careful thought. We want to build apps that are reliable and correct (clear, understood semantics, despite various errors). Four decades of atomicity, isolation and durability were the tools for this; but these foundations are shakier than they look (witness the confusion of weak isolation levels). In some domains transactions are abandoned altogether, replaced with a model giving better performance and scalability but messier semantics. Everyone says “consistency” and few define it precisely. Kyle Kingsbury's Jepsen tests showed the naked gap between some products' “claimed guarantee” and “actual behavior” under network trouble and crashes — and even if the infrastructure were flawless, application code must still use features correctly, which is error-prone with hard-to-understand configuration (weak isolation, quorums and the rest).

اگه اپت گاهی خراب‌کردن یا گم‌کردنِ داده رو تحمل می‌کنه، زندگی ساده‌ست (چشم‌ها رو ببند و امیدوار باش). ولی اگه تضمینِ قوی‌تر لازم داری، serializability و atomic commit راه‌های جاافتاده‌ان — با هزینه: معمولاً فقط توی یک دیتاسنتر جواب می‌دن (معماریِ جغرافیایی رو خط می‌زنن) و مقیاس و تحملِ خطا رو محدود می‌کنن. رویکردِ تراکنشیِ سنتی نمی‌ره، ولی حرفِ آخر هم در درست و مقاوم‌کردنِ اپ نیست. این بخش راه‌های دیگرِ فکرکردن به درستی توی معماریِ dataflow رو می‌کاوه.

If your app tolerates occasionally breaking or losing data, life is simple (close your eyes and hope). But if you need stronger guarantees, serializability and atomic commit are the established paths — at a cost: they usually work only in one datacenter (ruling out geographic architectures) and limit scale and fault tolerance. The traditional transactional approach isn't leaving, but neither is it the last word on making apps correct and resilient. This section explores other ways of thinking about correctness in dataflow architectures.

۵.۱. سرکوبِ تکراری، سرتاسری5.1. End-to-end duplicate suppression

جلوگیری از تکرار باید از آغازِ درخواست تا محلِ ایجادِ اثر ادامه داشته باشه. ثبتِ شناسه و تغییرِ مربوط باید اتمیک باشن تا بینشون فاصلهٔ خطرناک پیش نیاد.

مثال فنی: یه هویت، تا آخرِ مسیر

وضعیت اولیه: مرورگر برای خرید r7 شناسه می‌سازه و همون شناسه به سرویس و جدولِ درخواست‌ها می‌رسه.

اجرای مرحله‌به‌مرحله: اثر و رکوردِ r7 توی یه تراکنش ثبت می‌شن؛ پاسخِ گم‌شده با استعلام یا تکرارِ همون r7 بازیابی می‌شه.

نتیجه و دلیل: dedup باید همان نیت کاربر را سرتاسری بشناسد؛ تولید شناسهٔ تازه در هر لایه این زنجیره را می‌شکند.

That an app uses a data system with a strong feature (like a serializable transaction) doesn't mean it's safe from lost or corrupted data: a bug writing or deleting wrong data isn't saved by a serializable transaction — itself an argument for immutable, append-only data, since recovering from mistakes is simpler if broken code can't destroy healthy data. But immutability alone doesn't cure everything; the subtler example is “exactly-once execution” of an operation.

ایده: اگه موقعِ پردازشِ پیام چیزی خراب بشه، یا بی‌خیال می‌شی (گم‌شدنِ پیام = ازدست‌رفتنِ داده) یا دوباره تلاش می‌کنی. ولی اگه تلاشِ دوباره کنی، ممکنه پردازشِ اول در واقع موفق شده بوده و فقط تأییدش رو نگرفته باشی — پس پیام دو بار پردازش می‌شه. دو بار پردازش نوعی خرابیِ داده‌ست: دوبار شارژکردنِ مشتری یا دوبار شمردنِ کانتر. دقیقاً-یک‌بار یعنی ترتیبی بدی که اثرِ نهایی همونی باشه که انگار هیچ خطایی رخ نداده، حتی اگه به‌خاطرِ خطا بازتلاش شده. یکی از مؤثرترین راه‌ها idempotent کردنِ عملیاته: اثرش یکی باشه، چه یک بار اجرا بشه چه چند بار. ولی idempotent کردنِ عملیاتی که ذاتاً idempotent نیست زحمت و دقت می‌خواد: شاید متادیتای اضافه لازم داشته باشی (مثلِ مجموعهٔ IDهای عملیاتی که مقداری رو به‌روز کردن) و موقعِ failover باید fencing کنی (فصل ۹).

The idea: if something breaks while processing a message, either give up (lost message = lost data) or retry. But if you retry, the first attempt may actually have succeeded with only its acknowledgment lost — so the message gets processed twice. Processing twice is itself a data failure: charging the customer twice or double-counting a counter. Exactly-once means arranging for the final effect to equal as if no error ever happened, even if errors caused retries. One of the most effective ways is making operations idempotent: same effect whether run once or several times. But idempotizing an inherently non-idempotent operation takes work and care: it may need extra metadata (like the set of operation IDs that updated a value), and on failover you must fence (Chapter 9).

همین الگوی «سرکوبِ تکراری» جاهای دیگه‌ای هم هست. TCP با sequence number روی پکت‌ها ترتیب رو درست می‌کنه و پکتِ گم‌شده رو بازمی‌فرسته و تکراری رو حذف می‌کنه — ولی فقط داخلِ یک اتصالِ TCP. فرض کن اتصالِ TCP، اتصالِ کلاینت به پایگاه داده است و داره تراکنشِ مثالِ ۱۳-۱ رو اجرا می‌کنه (تو خیلی پایگاه داده‌ها تراکنش به اتصالِ کلاینت گره خورده چون چند کوئری روی همون اتصال یعنی همون تراکنش). اگه کلاینت بعد از فرستادنِ COMMIT و قبل از شنیدنِ پاسخ، قطعیِ شبکه و timeout بخوره، نمی‌دونه تراکنش commit شده یا abort (همون وضعیتِ شکلِ ۹-۱).

The same “duplicate suppression” pattern appears elsewhere. TCP orders packets with sequence numbers, resends lost ones and drops duplicates — but only inside one TCP connection. Suppose the TCP connection is a client-to-database connection running Example 13-1's transaction (in many databases a transaction is tied to the client connection, since several queries on the same connection mean the same transaction). If the client, after sending COMMIT and before hearing the reply, hits a network break and timeout, it doesn't know whether the transaction committed or aborted (the same situation as Fig. 9-1).

BEGIN TRANSACTION;
UPDATE accounts SET balance = balance + 11.00 WHERE account_id = 1234;
UPDATE accounts SET balance = balance - 11.00 WHERE account_id = 4321;
COMMIT;

کلاینت می‌تونه وصل بشه و تراکنش رو بازتلاش کنه، ولی حالا بیرونِ قلمروِ سرکوبِ تکراریِ TCP است. و چون این تراکنش idempotent نیست، ممکنه به‌جای ۱۱ دلار، ۲۲ دلار جابه‌جا بشه. پس حتی این کد — که مثالِ استانداردِ atomicity تراکنشه — درست نیست، و بانک‌های واقعی این‌طوری کار نمی‌کنن. پروتکلِ 2PC نگاشتِ یک‌به‌یکِ «اتصالِ TCP = تراکنش» رو می‌شکنه (coordinator باید بعد از خطا بتونه به پایگاه داده وصل بشه و بگه تراکنشِ in-doubt رو commit کنه یا abort) — ولی این هم برای «فقط یک‌بار اجرا شدن» کافی نیست. حتی اگه تکراریِ بینِ کلاینت و سرورِ پایگاه داده رو سرکوب کنی، هنوز شبکهٔ بینِ دستگاهِ کاربر و سرورِ اپلیکیشن مونده: کاربر با اینترنتِ ضعیف POST رو می‌فرسته، ولی قبل از گرفتنِ پاسخ سیگنال رو از دست می‌ده؛ پیامِ خطا می‌بینه و دستی retry می‌کنه (مرورگر هم می‌پرسه «مطمئنی دوباره submit کنی؟» — و کاربر بله می‌گه چون می‌خواد عملیات انجام بشه). از دیدِ وب‌سرور، retry یه درخواستِ جداست؛ و از دیدِ پایگاه داده، یه تراکنشِ جدا. مکانیزم‌های عادیِ dedup کمکی نمی‌کنن.

The client can reconnect and retry the transaction, but now it's outside TCP's duplicate-suppression territory. And since this transaction isn't idempotent, $22 may move instead of $11. So even this code — the textbook atomicity example — is incorrect — and real banks don't work this way. The 2PC protocol breaks the one-to-one “TCP connection = transaction” mapping (the coordinator must reconnect after failure and tell the database to commit or abort the in-doubt transaction) — but even that isn't enough for “executing just once”. Even suppressing duplicates between client and database server leaves the network between the user's device and the app server: the user on weak internet sends the POST but loses signal before the reply; sees an error and manually retries (the browser even asks “are you sure you want to resubmit?” — and the user says yes, wanting the operation done). To the web server the retry is a separate request; to the database, a separate transaction. Ordinary dedup mechanisms don't help.

راه‌حل: شناسهٔ یکتا را سرتاسر حمل کن (مثالِ ۱۳-۲)Fix: carry a unique ID end to end (Example 13-2)

برای idempotent کردنِ درخواست از چند hop شبکه، تکیه به مکانیزمِ تراکنشِ پایگاه داده کافی نیست؛ باید جریانِ سرتاسریِ درخواست رو ببینی. مثلاً به‌ازای هر درخواست شناسهٔ یکتا بساز (UUID) و به‌عنوانِ فیلدِ مخفیِ فرم بگذار، یا hash فیلدهای فرم رو شناسه کن. اگه مرورگر POST رو دو بار بفرسته، هر دو همون شناسه رو دارن. بعد همون شناسه رو تا پایگاه داده حمل کن و چک کن که همیشه فقط یه درخواست با اون ID اجرا بشه:

To idempotize a request across several network hops, the database's transaction mechanism isn't enough; you must see the request's end-to-end flow. E.g. mint a unique ID per request (a UUID) as a hidden form field, or hash the form fields into an ID. If the browser POSTs twice, both carry the same ID. Then carry that ID down to the database and check that only one request with that ID ever executes.

ALTER TABLE requests ADD UNIQUE (request_id);
BEGIN TRANSACTION;
INSERT INTO requests
(request_id, from_account, to_account, amount)
VALUES('0286FDB8-D7E1-423F-B40B-792B3608036C', 4321, 1234, 11.00);
UPDATE accounts SET balance = balance + 11.00 WHERE account_id = 1234;
UPDATE accounts SET balance = balance - 11.00 WHERE account_id = 4321;
COMMIT;

این کد به قیدِ یکتاییِ ستونِ request_id تکیه می‌کنه: اگه تراکنشی بخواد ID تکراری insert کنه، INSERT می‌شکست و تراکنش abort می‌شه و دو بار اثر نمی‌کنه. پایگاه‌های دادهِ رابطه‌ای معمولاً قیدِ یکتایی رو درست نگه می‌دارن حتی در isolation ضعیف (درحالی‌که چک-بعد-insert توی سطحِ اپلیکیشن، زیرِ isolation غیرسریال‌شدنی می‌شکست — write skew فصل ۸). تازه جدولِ requests عملاً یه لاگِ رویداد هم هست که برای event sourcing یا CDC به کار میاد: به‌روزرسانیِ بالانس‌ها لازم نیست توی همون تراکنشِ درجِ رویداد باشه، چون افزونه‌ان و می‌شه از رویداد توی مصرف‌کنندهٔ پایین‌دستی مشتقشون کرد — به‌شرطی که رویداد دقیقاً یک‌بار پردازش بشه، که باز همون شناسه تضمینش می‌کنه.

This code relies on the request_id column's uniqueness constraint: if a transaction tries inserting a duplicate ID, the INSERT breaks and the transaction aborts, never applying twice. Relational databases usually uphold uniqueness correctly even under weak isolation (while check-then-insert at app level breaks under non-serializable isolation — Chapter 8's write skew). The requests table is also effectively an event log, useful for event sourcing or CDC: the balance updates needn't be in the same transaction as the event insert, since they're additive and can be derived from the event in a downstream consumer — provided the event is processed exactly once, which the same ID guarantees.

سناریوی سرکوبِ تراکنشِ تکراری فقط یه نمونه از یه اصلِ کلی‌تره: «تابعِ موردنظر فقط با دانش و کمکِ اپلیکیشنِ دو سرِ سیستمِ ارتباطی می‌شه کامل و درست پیاده کرد؛ پس ارائه‌اش به‌عنوانِ ویژگیِ خودِ سیستمِ ارتباطی ممکن نیست (گاهی نسخهٔ ناقصش به‌عنوانِ بهبودِ عملکرد به کار میاد).» توی مثالِ ما اون تابع، سرکوبِ تکراری بود: دیدیم TCP تکراری رو توی سطحِ اتصال سرکوب می‌کنه و بعضی پردازنده‌های stream یه چیزی به اسمِ semantics دقیقاً-یک‌بار توی سطحِ پردازشِ پیام می‌دن — ولی هیچ‌کدوم برای جلوگیری از submit تکراریِ کاربر بعد از timeout کافی نیستن. TCP و تراکنشِ پایگاه داده و پردازندهٔ stream به‌تنهایی نمی‌تونن این تکراری‌ها رو منتفی کنن؛ راه‌حل سرتاسری می‌خواد: شناسهٔ تراکنش که از کلاینتِ کاربر تا پایگاه داده حمل بشه. همین استدلال برای چک‌کردنِ integrity داده هم هست: checksumهای Ethernet و TCP و TLS خرابیِ پکت توی شبکه رو می‌گیرن، ولی خرابیِ ناشی از باگِ نرم‌افزار توی دو سرِ اتصال یا خرابیِ دیسک رو نه — برای گرفتنِ همهٔ منابعِ خرابی، checksum سرتاسری هم لازمه. و برای رمزنگاری هم همین‌طور (WiFi خانگی، TLS، و در نهایت رمزنگاریِ سرتاسری). ویژگی‌های سطح‌پایین بی‌فایده نیستن (بدونِ مرتب‌کردنِ پکتِ TCP، درخواست‌های HTTP مدام به‌هم می‌ریختند) — فقط به‌تنهایی برای درستیِ سرتاسری کافی نیستن. و این ما رو به تزِ اصلی برمی‌گردونه: صرفِ این‌که اپ از سیستمِ داده‌ای با ویژگیِ قوی استفاده می‌کنه، تضمینِ رهایی از گم‌شدن/خراب‌شدنِ داده نیست؛ خودِ اپلیکیشن هم باید اقدامِ سرتاسری بکنه (مثلِ سرکوبِ تکراری). حیف است، چون مکانیزمِ تحملِ خطا سخت می‌شه درست کرد؛ ولی به‌نظر می‌رسه هنوز انتزاعِ درستی پیدا نکرده‌ایم که ماشینِ تحملِ خطای سطح‌بالا رو جمع‌وجور کنه تا کدِ اپلیکیشن نگرانش نباشه. تراکنش مدت‌ها اون انتزاعِ مفید بود (طیفِ وسیعی از مسائل — نوشتنِ هم‌زمان، نقضِ قید، crash، قطعیِ شبکه، خرابیِ دیسک — رو به دو خروجیِ commit/abort فرومی‌کاهد؛ ساده‌سازیِ بزرگی توی مدلِ برنامه‌نویسی، ولی ناکافی). تراکنش گرونه، مخصوصاً روی فناوری‌های ناهمگن؛ و وقتی از تراکنشِ توزیع‌شده فرار می‌کنیم چون گرونه، ناچار می‌شیم مکانیزمِ تحملِ خطا رو توی کدِ اپلیکیشن بازپیاده کنیم — و همون‌طور که نمونه‌های کتاب نشون دادند، استدلال دربارهٔ همزمانی و خرابیِ جزئی سخت و خلافِ شهوده و بیشترِ مکانیزم‌های سطحِ اپلیکیشن درست کار نمی‌کنن؛ نتیجه گم‌شدن یا خراب‌شدنِ داده‌ست. پس ارزش دارد دنبالِ انتزاع‌های تحملِ خطایی بگردیم که دادنِ ویژگیِ درستیِ سرتاسریِ خاصِ اپلیکیشن رو آسان کنن ولی عملکرد و ویژگیِ عملیاتیِ خوب رو توی محیطِ توزیع‌شدهٔ بزرگ نگه دارن.

The duplicate-transaction suppression scenario is just one instance of a broader principle: “the desired function can be completely and correctly implemented only with the knowledge and help of the applications at the communication system's endpoints; so providing it as a feature of the communication system itself is impossible (an incomplete version sometimes serves as a performance improvement).” In our example the function was duplicate suppression: TCP suppresses duplicates at connection level and some stream processors offer so-called exactly-once semantics at message-processing level, but neither suffices against a user's resubmit after timeout. TCP, database transactions and stream processors alone can't rule out these duplicates; the fix must be end to end: a transaction ID carried from the user's client to the database. The same argument holds for data-integrity checking: Ethernet, TCP and TLS checksums catch packet corruption on the network, but not corruption from software bugs at either end or disk failures — catching every failure source needs an end-to-end checksum too. And likewise for encryption (home WiFi, TLS, and ultimately end-to-end encryption). Low-level features aren't useless (without TCP packet ordering, HTTP requests would constantly scramble) — just insufficient alone for end-to-end correctness.

And this brings us back to the main thesis: using a data system with a strong feature doesn't guarantee freedom from lost or corrupted data; the application itself has to act end to end (like duplicate suppression). A pity, since fault-tolerance machinery is hard to get right — but it seems we haven't found the right abstraction yet, one that compactly delivers high-level fault-tolerant machinery so application code needn't worry about it. Transactions were that useful abstraction for a long time (they folded a wide range of problems — concurrent writes, constraint violations, crashes, network breaks, disk failures — into two outcomes, commit/abort; a big simplification of the programming model, but an insufficient one). Transactions are expensive, especially on heterogeneous technologies; and the moment you flee distributed transactions because they're expensive, you end up reimplementing fault tolerance inside application code — and as the book's examples show, reasoning about concurrency and fine-grained failure is hard and counter-intuitive, and most application-level mechanisms don't work correctly; the result is lost or corrupted data. So it's worth hunting for fault-tolerance abstractions that make it easy to give an application its own end-to-end correctness, while keeping good performance and good operational properties in a large distributed environment.

نتیجه و دلیل: حذفِ هماهنگی بدونِ پذیرشِ صریحِ خطا و جبران، همون قیدِ قبلی رو نگه نمی‌داره — این رو از قلم نینداز.

We saw end-to-end duplicate suppression with an ID carried from the client to the recording database. What about other constraints? Focus on the uniqueness constraint (the one Example 13-2 relied on): usernames or emails must identify the user uniquely; a file store can't hold two same-named files; two people can't book one flight or theater seat. Other constraints are much alike: account balances must not go negative; don't sell beyond warehouse stock; meeting rooms must have no overlapping bookings. The uniqueness-enforcement technique often works for this kind of constraint too.

قیدِ یکتایی در محیطِ توزیع‌شده نیازمندِ اجماع است (فصلِ ۱۰): اگه چند درخواستِ هم‌زمان مقدارِ یکسان داشته باشن، سیستم باید تصمیم بگیره کدوم عملیاتِ متعارض پذیرفته بشه و بقیه به‌عنوانِ نقضِ قید رد بشن. رایج‌ترین راهِ رسیدن به این اجماع، رهبرکردنِ یه نود و سپردنِ همهٔ تصمیم‌ها به اونه — تا وقتی اشکالی نداره که funnel کردنِ همهٔ درخواست‌ها از یه نود (حتی اگه کلاینت اون‌طرفِ دنیا باشه) و خراب‌شدنِ اون نود رو تحمل کنی. الگوریتم‌های اجماع مثلِ Raft مسئلهٔ انتخابِ امنِ رهبرِ تازه بعد از خرابیِ رهبر و جلوگیری از split-brain رو حل می‌کنن. چکِ یکتایی رو می‌شه با shard بر اساسِ مقداری که باید یکتا بماند مقیاس داد: برای یکتاییِ request ID، همهٔ درخواست‌های با همون request ID به همون shard برن؛ برای یکتاییِ username، shard بر اساسِ hash نامِ کاربری. ولی replication ناهمگامِ multi-leader منتفیه، چون رهبرهای متفاوت می‌تونن هم‌زمان نوشتنِ متعارض رو بپذیرن و مقادیر دیگه یکتا نیستن. اگه بخوای هر نوشتنِ ناقضِ قید رو بلافاصله رد کنی، هماهنگیِ همگام گریزناپذیره.

A uniqueness constraint in a distributed environment needs consensus (Chapter 10): if several concurrent requests share a value, the system must decide which conflicting operation is accepted and reject the rest as constraint violations. The most common way to this consensus is making one node the leader and entrusting it with every decision — fine while you tolerate funnelling every request through one node (even if the client is across the world) and that node breaking. Consensus algorithms like Raft solve safely electing a fresh leader after the leader's failure and preventing split-brain. Uniqueness checks scale by sharding on the value that must stay unique: for request-ID uniqueness, route all requests with the same request ID to the same shard; for username uniqueness, shard by username hash. But asynchronous multi-leader replication is out, since different leaders can concurrently accept conflicting writes and values stop being unique. If you want every constraint-violating write rejected immediately, synchronous coordination is unavoidable.

یکتایی در پیام‌رسانیِ لاگ‌محور: لاگِ مشترک تضمین می‌کنه همهٔ مصرف‌کننده‌ها پیام‌ها رو به‌همان‌ترتیب ببینن (تضمینِ total order broadcast که معادلِ consensus است). توی رویکردِ پایگاه دادهِ unbundle با پیام‌رسانیِ لاگ‌محور، می‌شه با رویکردِ خیلی مشابهی قیدِ یکتایی رو enforce کرد: پردازندهٔ stream همهٔ پیام‌های یه shard لاگ رو ترتیبی روی یه thread مصرف می‌کنه؛ پس اگه لاگ بر اساسِ مقداری که باید یکتا بمونه shard شده باشه، پردازنده می‌تونه بدونِ ابهام و قطعی تصمیم بگیره کدوم‌یک از چند عملیاتِ متعارض در لاگ اول اومده. مثلاً چند کاربر می‌خوان یه username رو بگیرن: (۱) هر درخواست به‌صورتِ پیام در shardای که با hash username تعیین می‌شه append می‌شه؛ (۲) پردازندهٔ stream درخواست‌ها رو ترتیبی می‌خونه و با پایگاه دادهِ محلی ردیابی می‌کنه کدوم نام‌ها گرفته شدن — برای هر نامِ آزاد، گرفته ثبت می‌کنه و پیامِ success به جریانِ خروجی می‌ده، و برای نامِ گرفته‌شده پیامِ reject؛ (۳) کلاینتی که نام رو خواسته، جریانِ خروجی رو تماشا می‌کنه و منتظرِ success/reject خودش می‌مونه. این الگوریتم همون ساختارِ «رسیدن به اجماع با لاگِ مشترک» فصلِ ۱۰ است؛ و با زیادکردنِ shard به‌راحتی به توانِ بالا مقیاس می‌شه چون هر shard مستقل پردازش می‌شه. این رویکرد فقط برای یکتایی نیست، برای خیلی قیدهای دیگه هم جواب می‌ده؛ اصلِ بنیادینش اینه که هر نوشتن‌هایی که ممکنه باهم درگیر بشن به همان shard هدایت و ترتیبی پردازش می‌شوند. تعریفِ «درگیری» به اپلیکیشن بستگی داره، ولی پردازنده می‌تونه با منطقِ دلخواه درخواست رو validate کنه.

Uniqueness in log-based messaging: the shared log guarantees every consumer sees messages in the same order (the total-order-broadcast guarantee that equals consensus). In the unbundled-database approach with log-based messaging, the uniqueness constraint can be enforced with a very similar approach: the stream processor consumes one log shard's messages sequentially on one thread; so if the log is sharded by the value that must stay unique, the processor can unambiguously and deterministically decide which of several conflicting operations in the log came first. E.g. several users want one username: (1) each request appends as a message to the shard set by the username's hash; (2) the stream processor reads requests sequentially and tracks with a local database which names are taken — for each free name it records taken and emits a success message to the output flow, and for taken names a reject message; (3) the requesting client watches the output flow and waits for its own success/reject. This algorithm is the same “reaching consensus with a shared log” structure as Chapter 10; and it scales easily to high throughput with more shards since each shard processes independently. This approach isn't only for uniqueness — it works for many other constraints; its fundamental principle is routing every potentially conflicting write to the same shard for sequential processing. What counts as “conflict” depends on the application, but the processor can validate requests with arbitrary logic.

اجرای مرحله‌به‌مرحله: ثبتِ نام روی مسیرِ هماهنگ رقابت می‌کنه؛ در فروشِ دوم، سیاستِ مشخصِ تأمینِ جایگزین یا بازپرداخت می‌تونه جبران کنه.

این یه درختِ تصمیم است. ریشه Constraint Must Hold با زمینهٔ «reservation, seat, balance» — یعنی از اول معلومه داریم دربارهٔ قیدهای واقعی (رزرو، صندلی، بالانس) حرف می‌زنیم. سؤالِ اول: Needs Strict Guarantee? («reject conflicts now»). اگه بله — باید همین‌الان درگیری رو رد کنی — مستقیم به برگِ Single Leader per Shard می‌ری («shard by constrained value» + «هماهنگیِ همگام»); یعنی همون راهِ اجماع.

اگه تضمینِ سخت لازم نیست، سؤالِ دوم: Can You Compensate Later? («viable apology path?» — آیا مسیرِ عذرخواهیِ شدنی داری؟). بله یعنی برگِ Apologize and Compensate («write first, fix up later» — «refunds, overbooking») — خوش‌بینانه بنویس و بعد درستش کن.

و اگه جبران هم شدنی نیست، سؤالِ سوم: Must Decide Synchronously? («can the client wait?»). بله می‌شه برگِ Shard by Conflict Key («same shard, ordered check» — «success / reject events») — نوشتن‌های درگیر به همان shard و چکِ ترتیبی با رویدادِ success/reject. نه هم می‌شه برگِ Async Validate + Notify («validate later, notify») — توی لاگ بنویس و بعداً validate کن و خبر بده. کارتِ پایینِ نمودار هم جمع‌بندیِ کلِ بخشِ ۵ رو می‌ده: «سیستم‌های coordination-avoiding — integrity قوی بدونِ consensus؛ چون integrity با timeliness فرق داره».

This is a decision tree. The root is Constraint Must Hold with the context “reservation, seat, balance” — clear from the start that we're talking about real constraints (reservations, seats, balances). First question: Needs Strict Guarantee? (“reject conflicts now”). Yes — conflicts must be rejected right now — goes straight to the Single Leader per Shard leaf (“shard by constrained value” + “synchronous coordination”); the consensus path.

If no hard guarantee is needed, second question: Can You Compensate Later? (“viable apology path?” — is there a feasible apology path?). Yes means the Apologize and Compensate leaf (“write first, fix up later” — “refunds, overbooking”) — write optimistically, fix later. And if compensation isn't feasible either, third question: Must Decide Synchronously? (“can the client wait?”). Yes becomes the Shard by Conflict Key leaf (“same shard, ordered check” — “success / reject events”) — conflicting writes to the same shard with a sequential check and success/reject events. No becomes Async Validate + Notify (“validate later, notify”) — write to the log, validate later, notify. The card at the bottom summarizes all of Section 5: “coordination-avoiding systems — strong integrity without consensus; because integrity differs from timeliness.”

۵.۳. پرداختِ چندshardی بدونِ commit اتمیک5.3. Multishard payment without atomic commit

می‌شه یه دستورِ معتبر رو یک‌بار ثبت کرد و اثرهای اون رو مرحله‌ای به شاردها رسوند. این طراحی به تحویلِ پایدار، جلوگیری از تکرار، کنترلِ قواعد و راستی‌آزمایی نیاز داره؛ رؤیت‌پذیریِ هم‌زمانِ همهٔ اثرها رو خودبه‌خود نمی‌ده.

مثال فنی: دستورِ پایدار، اثرِ مرحله‌ای

وضعیت اولیه: دستورِ T7: A→B, amount=100 پایدار و پذیرفته‌شده.

اجرای مرحله‌به‌مرحله: shardِ A کسر رو با شناسهٔ T7 یک‌بار اعمال می‌کنه؛ shardِ B واریز رو با همون شناسه اعمال می‌کنه؛ مراحلِ ناتمام retry و تطبیق می‌شن.

نتیجه و دلیل: به شرطِ پروتکلِ درست، اعتبارسنجی و پیشرفت، اثرها کامل می‌شن؛ تا تکمیل ممکنه وضعیتِ میانی دیده بشه و atomic visibility نداریم — ملاحظه کن.

When several shards are involved, atomically enforcing operations with constraints gets more attractive. In Example 13-2 there are potentially three shards: one for the request ID, one for the recipient account, one for the payer account — with no reason for all three to share one shard since they're independent. In the traditional database approach, running this transaction wants atomic commit across all three shards, effectively funnelling it with every other transaction of all three shards into one total order; and with cross-shard coordination now present, shards no longer process independently and throughput drops. But equivalent correctness is reachable without cross-shard transactions, using sharded logs and stream processors. Fig. 13-2 shows an example: a payment transaction that must check the source account holds enough money and, if so, atomically move the amount to the destination account minus a fee. The steps:

  1. درخواستِ انتقال از حسابِ مبدأ به مقصد، یه request ID یکتا از کلاینتِ کاربر می‌گیره و در shardِ لاگی که بر اساسِ ID حسابِ مبدأ است append می‌شه.
  2. پردازندهٔ stream لاگِ درخواست‌ها رو می‌خونه و پایگاه‌داده‌ای نگه می‌داره که state حسابِ مبدأ و IDهای درخواست‌هایی که قبلاً پردازش کرده رو داره (محتوای این پایگاه داده تماماً از لاگ مشتق‌شده). وقتی به درخواستی با ID نادیده می‌رسه، توی پایگاه دادهٔ محلی چک می‌کنه حسابِ مبدأ پولِ کافی داره یا نه. اگه داشت، پایگاه دادهٔ محلی رو به‌روز می‌کنه تا مبلغ روی حسابِ مبدأ رزرو بشه و رویداد به چند لاگِ دیگه می‌فرسته: رویدادِ پرداختِ خروجی به shardِ لاگِ حسابِ مبدأ (لاگِ ورودیِ خودش)، رویدادِ پرداختِ ورودی به shardِ لاگِ حسابِ مقصد، و رویدادِ پرداختِ ورودی به shardِ لاگِ حسابِ کارمزد — و request ID اصلی توی اون رویدادهای منتشرشده هست.
  3. سرانجام رویدادِ پرداختِ خروجی به پردازندهٔ حسابِ مبدأ برمی‌گرده (که ممکنه بینش رویدادهای نامرتبط گرفته باشه). پردازنده از روی request ID می‌فهمه این پرداختیه که قبلاً رزروش کرده و پرداخت رو اجرا می‌کنه و دوباره state محلیِ حسابِ مبدأ رو به‌روز می‌کنه؛ و تکراری‌ها رو بر اساسِ request ID نادیده می‌گیره.
  4. shardهای لاگِ حسابِ مقصد و کارمزد رو taskهای مستقلِ پردازشِ stream مصرف می‌کنن؛ وقتی رویدادِ پرداختِ ورودی رو می‌گیرن، state محلی رو به‌روز می‌کنن و رویدادها رو بر اساسِ request ID dedup می‌کنن.
  1. The transfer request from source to destination account takes a unique request ID from the user's client and appends in the log shard keyed by the source account ID.
  2. The stream processor reads the request log and keeps a database holding the source account's state and the request IDs it already processed (this database's content is fully derived from the log). On reaching an unseen-ID request, it checks in the local database whether the source account holds enough money. If so, it updates the local database to reserve the amount on the source account and sends events to several other logs: the outgoing-payment event to the source account's log shard (its own input log), the incoming-payment event to the destination account's log shard, and the incoming-payment event to the fee account's log shard — with the original request ID present in those published events.
  3. Finally the outgoing-payment event returns to the source-account processor (which may have taken unrelated events in between). From the request ID the processor knows this is a payment it already reserved, executes the payment and updates the source account's local state again; and ignores duplicates by request ID.
  4. The destination- and fee-account log shards are consumed by independent stream-processing tasks; on taking the incoming-payment event they update local state and dedup events by request ID.

توی شکل هر سه حساب توی سه shard جدایند، ولی می‌تونستن توی یه shard هم باشن — فرقی نمی‌کنه. تنها شرط‌ها این‌ان: رویدادهای هر حساب دقیقاً به‌ترتیبِ لاگ با semantics حداقل-یک‌بار پردازش بشن و پردازنده‌ها deterministic باشن. مثلاً ببین اگه پردازندهٔ حسابِ مبدأ وسطِ پردازشِ درخواستِ پرداخت crash کنه چه می‌شه: پیام‌های خروجی ممکنه قبل از crash منتشر شده باشن یا نه. بعد از recovery، همون درخواست دوباره پردازش می‌شه (به‌خاطرِ حداقل-یک‌بار) و همون تصمیمِ «پرداخت مجازه یا نه» رو می‌گیره (چون قطعیه) — پس همون پیام‌های خروجی رو با همون request ID به shardهای خروجی/ورودی/کارمزد می‌فرسته؛ و اگه پیام‌ها تکراری باشن، مصرف‌کننده‌های پایین‌دستی بر اساسِ request ID نادیده‌شون می‌گیرن. atomicity در این سیستم از تراکنش نمیاد، از این واقعیت میاد که نوشتنِ رویدادِ درخواستِ اولیه در لاگِ حسابِ مبدأ یه action اتمیک است. وقتی اون یه رویداد توی لاگ هست، همهٔ رویدادهای پایین‌دستی سرانجام نوشته می‌شن — شاید بعد از recovery پردازنده‌ها از crash، و شاید با تکراری، ولی سرانجام میان. با semantics دقیقاً-یک‌بار پیاده‌سازی ساده‌تر می‌شه، چون state محلیِ پردازنده با مجموعهٔ پیام‌هایی که پردازش کرده سازگار می‌مونه؛ پس اگه crash کرد و بعضی پیام‌ها رو بازپردازش کرد، state محلی‌اش هم به همون قبلِ اون پیام‌ها برمی‌گرده.

In the figure all three accounts sit in three separate shards, but they could share one shard too — it makes no difference. The only conditions: each account's events process exactly in log order with at-least-once semantics, and processors are deterministic. E.g. see what happens if the source-account processor crashes mid-payment: the output messages may or may not have published before the crash. After recovery the same request reprocesses (thanks to at-least-once) and takes the same “payment allowed or not” decision (since deterministic) — so it sends the same output messages with the same request ID to the outgoing/incoming/fee shards; and if messages duplicate, downstream consumers ignore them by request ID. Atomicity in this system doesn't come from transactions but from the fact that writing the initial request event to the source account's log is one atomic action. Once that one event is in the log, all downstream events eventually get written — perhaps after processors recover from crashes, and perhaps duplicated, but eventually. Exactly-once semantics simplifies implementation, since the processor's local state stays consistent with the message set it processed; so if it crashes and reprocesses some messages, its local state returns to just before those messages too.

اگه کاربرِ شکلِ ۱۳-۲ بخواد بفهمه انتقالش تأیید شده یا نه، می‌تونه مشترکِ shardِ لاگِ حسابِ مبدأ بشه و منتظرِ رویدادِ پرداختِ خروجی بمونه. و برای این‌که اگه موجودی کافی نبود صریح به کاربر خبر بده، پردازنده می‌تونه رویدادِ «پرداختِ ردشده» به همون shard بفرسته. با شکستنِ تراکنشِ چندshardی به چند stage با shard متفاوت و استفاده از request ID سرتاسری، به همون ویژگیِ درستی می‌رسیم (هر درخواست دقیقاً یک‌بار روی هر دو حسابِ پرداخت‌کننده و گیرنده اعمال می‌شه)، حتی با وجودِ خطا — بدونِ پروتکلِ commit اتمیک.

If Fig. 13-2's user wants to know whether their transfer confirmed, they can subscribe to the source account's log shard and wait for the outgoing-payment event. And to explicitly tell the user when funds were insufficient, the processor can send a “payment declined” event to the same shard. By breaking the multishard transaction into stages with different shards and using an end-to-end request ID, we reach the same correctness property (each request applied exactly once on both payer and payee accounts), even under failure — with no atomic-commit protocol.

نتیجه و دلیل: به شرطِ پروتکلِ درست، اعتبارسنجی و پیشرفت، اثرها کامل می‌شن؛ تا تکمیل ممکنه وضعیتِ میانی دیده بشه و atomic visibility نداریم — ملاحظه کن.

نمودار پنج ستون داره. اول Client Request («unique request ID» — «append») با فلشِ «request + unique ID» به Source Processor («checks + reserves» — «derived DB») می‌رسه — این تنها action اتمیکِ کلِ سیستمه: یه append. بعد با فلشِ «reserve + emit 3 events» به هابِ میانیِ 3 Derived Events («same request ID») می‌ره — همون سه رویدادی که پردازندهٔ مبدأ منتشر می‌کنه.

از هاب سه فلش بیرون می‌زنه (بدونِ هیچ تقاطعی): «outgoing payment» به Source Log («outgoing+declined» — «subscribe» — همون لاگی که کاربر برای فهمیدنِ نتیجه مشترکِ اون می‌شه)، «incoming payment» به Destination Proc («apply + dedup» — «request ID»)، و «fee payment» به Fees Processor («apply + dedup» — «request ID»). فلشِ پایانی «completed / declined» به Completed («eventually written» — «no 2PC») می‌رسه. سه کارتِ نمودار هم درس‌ها رو نگه می‌دارن: atomicity از همون یه append میاد؛ crash یعنی بازپردازشِ قطعی با همون خروجی و همون شناسه پس تکراری‌ها نادیده گرفته می‌شن؛ و دقیقاً-یک‌بار کار رو ساده‌تر می‌کنه چون state با مجموعهٔ پردازش‌شده سازگار می‌مونه.

۵.۴. timeliness در برابر integrity5.4. Timeliness vs integrity

تازگی می‌گه نتیجه چقدر زود دیده می‌شه؛ یکپارچگی می‌گه داده گم، تکراری یا متناقض نشده. یه نتیجه می‌تونه درست باشه ولی دیر دیده بشه.

مثال فنی: تازگی با درستی فرق داره

وضعیت اولیه: مرجع دو سفارشِ ۱۰۰ و ۲۰۰ داره.

اجرای مرحله‌به‌مرحله: نمای اول فقط سفارشِ اول رو داره و جمعش ۱۰۰ه؛ نمای دوم هر دو رو فوراً دیده، ولی اولی رو دوبار شمرده و جمعش ۴۰۰ه.

نتیجه و دلیل: اولی مشکلِ timeliness داره و دومی مشکلِ integrity؛ جلوتر بودنِ موقعیتِ مصرف به‌تنهایی درست بودنِ محاسبه رو ثابت نمی‌کنه — این دام معروفه.

The comfortable property of many transactional systems is that once a transaction commits, its writes are immediately visible to other transactions — formalized as strict serializability (Chapter 10). When you break an operation across several stream-processor stages, that doesn't hold. Log consumers are inherently asynchronous, so the producer doesn't wait for consumers to process its message. But the client may wait for its message to appear in the output flow — like the user waiting for the outgoing- or declined-payment event in Fig. 13-2, depending on whether the source account held enough money. In this example, the correctness of the source-balance check doesn't depend on whether the user waits for the result; waiting only synchronously informs the user whether the payment succeeded — that notification is separate from processing the request's effect.

کلی‌تر، واژهٔ «consistency» دو نیاز رو قاطی می‌کنه که ارزش داره جدا بررسیشون کنی:

More generally, the word “consistency” mixes two needs worth examining separately:

Timeliness

تازگی، فاصلهٔ تغییرِ واقعی تا دیده شدنش توی خروجی رو توصیف می‌کنه.

مثال فنی: lag قابلِ اندازه‌گیری

وضعیت اولیه: مرجع تا offset ۱۲۰ و گزارش تا ۱۱۰ پیش رفته.

اجرای مرحله‌به‌مرحله: ۱۰ رخداد عقب‌مانده و زمانِ قدیمی‌ترین رخدادِ اعمال‌نشده ثبت می‌شه؛ و بعد از catch up نتیجه تازه می‌شه.

نتیجه و دلیل: timeliness دربارهٔ زمانِ دیده شدنِ دادهٔ درسته؛ باید با معیارِ مناسب بار سنجیده بشه، نه‌فقط روشن بودنِ worker — حساب کن.

یعنی مطمئن بشی کاربرای سیستم رو در حالتِ به‌روز می‌بینن. اگه کاربر از کپیِ کهنه بخونه، ممکنه اون رو در حالتِ ناسازگار ببینه (مشکل‌های replication lag، فصل ۶) — ولی اون ناسازگاری موقتیه و با صبرکردن و دوباره‌تلاش‌کردن حل می‌شه. قضیهٔ CAP «consistency» رو به معنای linearizability به کار می‌بره که راهِ قویِ رسیدن به timeliness است؛ ویژگی‌های ضعیف‌ترِ timeliness مثلِ read-after-write هم می‌تونن مفید باشن.

Being sure users see the system up to date. Reading from a stale copy may show it in an inconsistent state (replication-lag problems, Chapter 6) — but that inconsistency is temporary and resolves with waiting and retrying. The CAP theorem uses “consistency” to mean linearizability, the strong way to timeliness; weaker timeliness properties like read-after-write can be useful too.

Integrity

یکپارچگی یعنی داده طبقِ قواعدِ تعیین‌شده گم، تکراری یا ناسازگار نشه؛ سرعتِ رسیدنِ نتیجه موضوعِ جداگانه‌ایه.

مثال فنی: جمعِ سریع، ولی غلط

وضعیت اولیه: پیامِ فروش e7 مبلغِ ۲۰۰ رو دو بار به جمعِ اولیهٔ ۱۰۰۰ اضافه کرده.

اجرای مرحله‌به‌مرحله: مصرف‌کننده تا آخرِ لاگ رسیده، ولی جمع ۱۴۰۰ه؛ dedupِ اتمیک می‌تونست نتیجه رو ۱۲۰۰ نگه داره.

نتیجه و دلیل: backlogِ صفر درستی رو ثابت نمی‌کنه؛ خطای integrity می‌تونه پس از تموم شدنِ پردازش هم باقی بمونه — این رو جدی بگیر.

یعنی نبودِ خرابی — نه گم‌شدنِ داده، نه دادهٔ متناقض یا غلط. به‌ویژه اگه dataset مشتق به‌عنوانِ viewای روی دادهٔ زیرین نگه‌داری بشه، مشتق‌سازی باید درست باشه: ایندکسِ پایگاه داده باید محتوای پایگاه داده رو درست منعکس کنه — ایندکسی که رکورد کم داره به درد نمی‌خوره. اگه integrity نقض بشه، ناسازگاری دائمیه؛ صبرکردن و دوباره‌تلاش‌کردن توی بیشترِ موارد خرابیِ پایگاه داده رو درست نمی‌کنه و چک و تعمیرِ صریح لازمه. توی دنیای تراکنشِ ACID، «consistency» معمولاً همین مفهومِ integrity خاصِ اپلیکیشن فهمیده می‌شه؛ و atomicity و durability ابزارهای مهمِ حفظِ اون‌ان.

The absence of corruption — no lost data, no contradictory or wrong data. Especially when a derived dataset is maintained as a view over underlying data, derivation must be correct: the database's index must faithfully reflect the database's content — an index missing records is useless. Violated integrity means permanent inconsistency; waiting and retrying won't fix database corruption in most cases — explicit checking and repair is needed. In the ACID-transaction world, “consistency” is usually understood as this application-specific integrity notion; and atomicity and durability are key tools for preserving it.

به زبانِ شعاری: نقضِ timeliness زیرِ eventual consistency مجاز است؛ ولی نقضِ integrity یعنی ناسازگاریِ دائمی. توی بیشترِ اپ‌ها integrity خیلی مهم‌تر از timelinessه: نقضِ timeliness آزاردهنده و گیج‌کننده‌ست، ولی نقضِ integrity می‌تونه فاجعه باشه. مثلاً توی صورت‌حسابِ کارتِ اعتباری عجیب نیست اگه تراکنشی که در ۲۴ ساعتِ گذشته کردی هنوز نیومده — عادیه که این سیستم‌ها lag داشته باشن؛ می‌دونیم بانک‌ها تراکنش‌ها رو ناهمگام reconcile و settle می‌کنن و timeliness این‌جا خیلی مهم نیست. ولی خیلی بد می‌شد اگه بالانسِ صورت‌حساب با جمعِ تراکنش‌ها به‌علاوهٔ بالانسِ قبلی برابر نبود (خطا در جمع‌ها)، یا تراکنشی به تو شارژ بشه ولی به فروشنده پرداخت نشه (پولِ گم‌شده) — این‌ها نقضِ integrity سیستم بودن.

As a slogan: timeliness violations are permitted under eventual consistency; but an integrity violation means permanent inconsistency. In most apps integrity matters far more than timeliness: timeliness violations are annoying and confusing, but integrity violations can be catastrophic. E.g. in a credit-card statement it's unsurprising if a last-24-hours transaction hasn't arrived yet — these systems normally lag; we know banks reconcile and settle transactions asynchronously and timeliness matters little here. But it would be very bad if the statement balance didn't equal the transactions' sum plus the previous balance (summing errors), or a transaction charged you without paying the merchant (lost money) — those would violate the system's integrity.

تراکنش‌های ACID معمولاً هر دو تضمینِ timeliness (مثلِ linearizability) و integrity (مثلِ atomic commit) رو می‌دن؛ و اگه از زاویهٔ تراکنشِ ACID به درستیِ اپلیکیشن نگاه کنی، تمایزِ timeliness و integrity چندان مهم نیست. ولی ویژگیِ جالبِ سیستم‌های dataflow رویدادمحوری که توی این فصل دیدیم اینه که timeliness و integrity رو از هم جدا می‌کنن: موقعِ پردازشِ ناهمگامِ جریانِ رویداد، هیچ تضمینِ timelinessای نیست، مگر این‌که صریح مصرف‌کننده‌ای بسازی که قبل از برگشتن منتظرِ رسیدنِ پیام بمونه (مثلاً کاربر پرداخت رو درخواست می‌کنه و بعد state حسابش رو می‌خونه قبل از این‌که پردازنده درخواست رو اجرا کرده باشه — پرداختی رو که تازه خواسته نمی‌بینه). ولی integrity در واقع محورِ سیستم‌های جریانیه: semantics دقیقاً-یک‌بار یا عملاً-یک‌بار مکانیزمِ حفظِ integrity است — اگه رویدادی گم بشه یا دو بار اثر کنه، integrity سیستم می‌تونه نقض بشه؛ پس تحویلِ fault-tolerant پیام و سرکوبِ تکراری (عملیاتِ idempotent) برای حفظِ integrity در برابرِ خطا مهم‌ان. و همون‌طور که توی بخشِ قبل دیدیم، سیستم‌های پردازشِ stream قابل‌اعتماد می‌تونن integrity رو بدونِ تراکنشِ توزیع‌شده و پروتکلِ commit اتمیک حفظ کنن — یعنی به درستیِ قابل‌مقایسه با عملکرد و قوی‌بودنِ عملیاتیِ خیلی بهتر برسند. این integrity رو با ترکیبی از مکانیزم‌ها گرفتیم:

ACID transactions usually give both timeliness (like linearizability) and integrity (like atomic commit) guarantees; so viewed from the ACID-transaction angle, the timeliness/integrity distinction matters little. But the interesting property of this chapter's event-driven dataflow systems is that they separate timeliness from integrity: in asynchronous event-flow processing there is no timeliness guarantee, unless you explicitly build a consumer that waits for the message before returning (e.g. the user requests a payment then reads their account state before the processor executed the request — not seeing the just-requested payment). But integrity is actually the streaming systems' focus: exactly-once or effectively-once semantics is an integrity-preserving mechanism — if an event is lost or applied twice, system integrity can break; so fault-tolerant message delivery and duplicate suppression (idempotent operations) matter for preserving integrity against failure. And as the previous section showed, reliable stream processors can preserve integrity without distributed transactions and atomic-commit protocols — i.e. reach comparable correctness with far better performance and operational robustness. That integrity was taken with a combination of mechanisms:

  • نشون‌دادنِ محتوای عملیاتِ نوشتن به‌صورتِ یک پیامِ واحد که می‌شه اتمیک نوشت — رویکردی که خیلی خوب با event sourcing جفت می‌شه؛
  • مشتق‌کردنِ بقیهٔ به‌روزرسانی‌های state از همون یه پیام با تابعِ مشتقِ قطعی، شبیهِ stored procedure؛
  • ردکردنِ request ID تولیدشدهٔ کلاینت از همهٔ این لایه‌های پردازش، که سرکوبِ تکراری و idempotence سرتاسری رو ممکن می‌کنه؛
  • immutable کردنِ پیام‌ها و اجازهٔ بازپردازشِ گاه‌به‌گاهِ دادهٔ مشتق، که بازیابی از باگ رو ساده‌تر می‌کنه.
  • Showing a write operation's content as a single message that can be written atomically — an approach pairing very well with event sourcing;
  • Deriving the rest of the state updates from that one message with a deterministic derivation function, like a stored procedure;
  • Passing the client-generated request ID through all these processing layers, enabling end-to-end duplicate suppression and idempotence;
  • Making messages immutable and allowing occasional reprocessing of derived data, simplifying bug recovery.

۵.۵. نقطهٔ بهینه: هماهنگیِ کمتر، عذرِ بیشتر5.5. The sweet spot: less coordination, more apology

هماهنگی رو جایی مصرف کن که نقضِ قید هزینهٔ غیرقابل‌قبول داشته باشه. اگه جبران مجازه، باید روش، سقفِ خطا و تجربهٔ کاربر از قبل طراحی بشه.

مثال فنی: محلِ هماهنگی رو کجا بذاریم؟

وضعیت اولیه: برای آخرین صندلیِ شماره‌دار دو خریدار داریم، ولی برای شمارشِ بازدید محدودیتِ مشابهی نیست.

اجرای مرحله‌به‌مرحله: فروشِ صندلی روی منبعِ مالکیت رقابت می‌کنه؛ شمارندهٔ بازدید می‌تونه غیرهم‌زمان ادغام بشه.

نتیجه و دلیل: هزینهٔ هماهنگی رو به قیدِ لازم می‌دیم؛ جبران فقط وقتی معنی داره که محصول اون نتیجه رو واقعاً بپذیره — این رو نگه دار.

Enforcing a uniqueness constraint needs consensus, which usually means funnelling one shard's every event through one node — and if you want the traditional form of the uniqueness constraint, that limit is unavoidable and stream processing doesn't bypass it. But many real apps have a business need that permits violating what you think of as a “hard constraint”:

  • اگه مشتری بیشتر از موجودیِ انبار سفارش داد، می‌شه بیشتر سفارش داد، برای تأخیر عذر خواست و تخفیف داد — همون کاری که اگه لیفتراک روی کالاهای انبار می‌رفت و موجودی از تصور کمتر می‌شد هم باید می‌کردی. و workflow عذرخواهی به‌هرحال برای چنین حادثه‌هایی باید بخشی از فرآیندِ کسب‌وکار باشه و قیدِ سختِ روی تعدادِ موجودی انبار شاید لازم نباشه.
  • خیلی ایرلاین‌ها با فرضِ این‌که بعضی مسافرها به پرواز نمی‌رسن overbook می‌کنن، و خیلی هتل‌ها اتاق رو overbook می‌کنن با فرضِ کنسلیِ بعضی مهمان‌ها. این‌جا قیدِ «یک نفر برای هر صندلی» عمداً برای دلیلِ کسب‌وکاری نقض می‌شه و فرآیندِ جبران (refund، ارتقا، اتاقِ رایگان در هتلِ همسایه) برای تقاضای بیش از عرضه گذاشته می‌شه. حتی بدونِ overbook هم فرآیندِ عذر و جبران برای رویدادهایی مثلِ کنسلیِ پرواز به‌خاطرِ هوای بد یا اعتصاب لازم بود — بازیابی از این مسائل فقط بخشیِ عادیِ کسب‌وکار است.
  • اگه کسی بیشتر از موجودیِ حسابش برداشت کرد، بانک می‌تونه کارمزدِ overdraft بگیره و بخواد بدهی رو پس بده؛ و با محدودکردنِ کلِ برداشتِ روزانه، ریسکِ بانک محدود می‌مونه.
  • توی سیستم‌هایی که داده رو بینِ سازمان‌ها یکپارچه می‌کنن، ناسازگاری ناگزیر پیش میاد و مکانیزمِ اصلاح لازمه؛ تسویهٔ پرداخت بینِ بانک‌ها (فصلِ ۱۱) نمونه‌شه.
  • If a customer orders beyond warehouse stock, you can oversell, apologize for the delay and discount — the same thing you'd do if a forklift drove into the warehouse goods and stock fell short of imagination. So the apology workflow must be part of the business process for such incidents anyway, and a hard constraint on stock count may be unnecessary.
  • Many airlines overbook assuming some passengers miss the flight, and many hotels overbook rooms assuming some guests cancel. Here the “one person per seat” constraint is deliberately violated for business reasons, with a compensation process (refunds, upgrades, a free room at the neighboring hotel) laid on for over-demand. Even without overbooking, apology-and-compensation processes were needed for events like weather- or strike-cancelled flights — recovering from such issues is just an ordinary part of business.
  • If someone withdraws beyond their account balance, the bank can charge an overdraft fee and ask the debt repaid; and by capping total daily withdrawals the bank's risk stays bounded.
  • In systems integrating data across organizations, inconsistency inevitably arises and a correction mechanism is needed; inter-bank payment settlement (Chapter 11) is an example.

توی خیلی زمینه‌های کسب‌وکاری پس قابلِ قبوله که قید رو موقتاً نقض کنی و بعد با عذرخواهی درستش کنی. این جنس اصلاحِ اشتباه compensating transaction نامیده می‌شه. هزینهٔ عذرخواهی (پول یا اعتبار) فرق می‌کنه ولی اغلب کمه: ایمیلِ فرستاده‌شده رو نمی‌شه پس گرفت، ولی می‌شه ایمیلِ اصلاحیِ بعدی فرستاد؛ اگه کارت رو دوبار شارژ کردی، می‌شه یکیش رو refund کرد و هزینه‌فقط کارمزدِ پردازش و شاید شکایتِ مشتری است. (پولی که از ATM بیرون رفته رو مستقیم نمی‌شه پس گرفت — هرچند در اصل می‌شه برای حسابِ منفی مانده مأمورِ وصول فرستاد.) این‌که هزینهٔ عذرخواهی قابلِ قبوله یا نه، تصمیمِ کسب‌وکاری است. اگه قابلِ قبول باشه، مدلِ سنتیِ «چک‌کردنِ همهٔ قیدها قبل از حتی نوشتنِ داده» بی‌جهت محدودکننده‌ست؛ کاملاً ممکنه معقول باشه که خوش‌بینانه بنویسی و قید رو بعداً چک کنی. هنوز می‌شه validation رو قبل از actionهایی گذاشت که بازیابی‌شون گرانه — ولی این به این معنا نیست که باید قبل از حتی نوشتنِ داده validate کنی. این اپ‌ها integrity می‌خوان (نمی‌خوای رزرو گم بشه یا پول با بده-بستانِ نامتطابق ناپدید بشه) ولی timeliness در enforce قید نمی‌خوان: اگه بیشتر از موجودی فروختی، می‌شه بعداً درستش کرد — شبیه همون رویکردهای حلِ تعارضِ «برخورد با نوشتنِ متعارض» (فصل ۶).

In many business contexts it's thus acceptable to temporarily violate a constraint and fix it later with an apology. This kind of mistake-fixing is called a compensating transaction. The apology's cost (money or reputation) varies but is often small: a sent email can't be unsent, but a corrective follow-up email can be sent; if you double-charged a card, one charge can be refunded at only the processing fee plus perhaps a customer complaint. (Cash out of an ATM can't directly be taken back — though in principle a collector can be sent for a negative balance.) Whether the apology cost is acceptable is a business decision. If acceptable, the traditional “check every constraint before even writing data” model is needlessly restrictive; it may be perfectly reasonable to write optimistically and check the constraint later. Validation can still sit before actions whose recovery is expensive — but that doesn't mean validating before even writing data. These apps want integrity (you don't want a reservation lost or money vanished with mismatched debit-credit) but no timeliness in constraint enforcement: oversold stock can be fixed later — like Chapter 6's “handling conflicting writes” conflict-resolution approaches.

حالا دو مشاهدهٔ جالب کنار هم می‌نشینن: (۱) سیستم‌های dataflow می‌تونن تضمینِ integrity روی دادهٔ مشتق رو بدونِ commit اتمیک و linearizability و هماهنگیِ همگامِ بین-shardی نگه دارن؛ (۲) با این‌که قیدِ سختِ یکتایی timeliness و هماهنگی می‌خواد، خیلی اپ‌ها با قیدِ شلی که ممکنه موقتاً نقض و بعد درست بشه راحتن، تا وقتی integrity همیشه حفظ بشه. با هم یعنی سیستم‌های dataflow می‌تونن برای خیلی اپ‌ها سرویسِ مدیریتِ داده بدن بدونِ این‌که هماهنگی لازم داشته باشند، ولی همچنان تضمینِ integrity قوی بدن. چنین سیستم‌های coordination-avoiding جذابیتِ زیادی دارن: عملکرد و تحملِ خطای بهتری از سیستم‌هایی دارن که باید هماهنگیِ همگام کنن. مثلاً چنین سیستمی می‌تونه توزیع‌شده روی چند دیتاسنتر توی پیکربندیِ multi-leader کار کنه و بینِ regionها ناهمگام replicate کنه؛ هر دیتاسنتری می‌تونه مستقل از بقیه کار کنه چون هماهنگیِ همگامِ بین-regionای لازم نیست. چنین سیستمی تضمینِ timeliness ضعیفی داره (بدونِ هماهنگی linearizable نمی‌شه) ولی همچنان می‌تونه تضمینِ integrity قوی داشته باشه. توی این فضا، تراکنشِ serializable هنوز به‌عنوانِ بخشی از نگه‌داریِ state مشتق مفیده، ولی می‌شه توی scope کوچکی اجرایش کرد که خوب جواب می‌ده؛ تراکنشِ توزیع‌شدهٔ ناهمگنِ سبکِ XA لازم نیست. هماهنگیِ همگام رو هنوز می‌شه جاهایی که لازمه آورد (مثلاً enforce قیدِ سخت قبل از عملیاتی که بازیابی ازش ممکن نیست)، ولی لازم نیست همه‌چیز هزینهٔ هماهنگی رو بده اگه فقط بخشِ کوچکی از اپ به اون نیاز داشته باشه. نگاهِ دیگه به هماهنگی و قیدها اینه که تعدادِ عذرخواهی‌ها برای ناسازگاری رو کم می‌کنن ولی بالقوه عملکرد و دسترس‌پذیریِ سیستم رو کم می‌کنن و پس بالقوه تعدادِ عذرخواهی‌ها برای outage رو زیاد می‌کنن. نمی‌شه تعدادِ عذرها رو به صفر رسوند، ولی می‌شه بهترین بده‌بستان رو برای نیازت پیدا کنی — نقطهٔ بهینه‌ای که نه ناسازگاریِ زیاد داره نه مشکلِ دسترس‌پذیریِ زیاد.

Now two interesting observations sit side by side: (1) dataflow systems can hold integrity guarantees on derived data without atomic commit, linearizability or synchronous cross-shard coordination; (2) although hard uniqueness constraints want timeliness and coordination, many apps are comfortable with a loose constraint that may temporarily break and later heal, as long as integrity always holds. Together they mean dataflow systems can serve data management for many apps with no coordination required, yet still give strong integrity guarantees. Such coordination-avoiding systems are highly attractive: better performance and fault tolerance than systems needing synchronous coordination. E.g. such a system can run distributed across several datacenters in a multi-leader configuration, replicating asynchronously between regions; each datacenter can work independently of the rest since no synchronous cross-region coordination is needed. Such a system has weak timeliness guarantees (no linearizability without coordination) but can still have strong integrity guarantees. In this space, serializable transactions remain useful as part of derived-state maintenance, but can run in a small scope where they perform well; heterogeneous XA-style distributed transactions aren't needed. Synchronous coordination can still be brought where needed (e.g. enforcing a hard constraint before an irrecoverable action), but not everything must pay coordination's price if only a small app part needs it. Another view of coordination and constraints is that they reduce apology counts for inconsistency but potentially cut system performance and availability, thus potentially raising apology counts for outages. Apology counts can't reach zero, but you can find the best tradeoff for your needs — a sweet spot with neither much inconsistency nor many availability problems.

۵.۶. اعتماد کن، ولی راستی‌آزمایی کن5.6. Trust, but verify

علاوه بر جلوگیری از خطا، باید بتونیم داده رو بررسی کنیم و ناسازگاری رو کشف کنیم. تطبیقِ مستقل و امکانِ بازسازی، خطاهایی رو آشکار می‌کنن که از فرض‌های طراحی عبور کردن.

مثال فنی: تطبیق با شناسه، نه‌فقط با جمع

وضعیت اولیه: مرجع سفارش‌های 42:100 و 43:200 رو داره؛ گزارش مجموعِ ۳۰۰ رو نشون می‌ده.

اجرای مرحله‌به‌مرحله: ممکنه گزارش ۴۲ رو حذف کرده باشه و سفارشِ دیگه‌ای رو اشتباهاً اضافه کرده باشه؛ مقایسهٔ شناسه، نسخه و مبلغ، اختلافِ واقعی رو پیدا می‌کنه.

نتیجه و دلیل: یکسان بودنِ مجموع شاهدِ کافی برای یکسان بودنِ داده نیست؛ ممیزی و مسیرِ ترمیم باید از مرجعِ معتبر تغذیه بشن — اینو قاب کن.

All the correctness, integrity and fault-tolerance discussion assumed some things can break and some can't — called the system model (Chapter 9). E.g. we assume processes crash, machines lose power, networks delay or drop messages arbitrarily; and assume disk-written data after fsync isn't lost, memory data doesn't corrupt, and the CPU's multiply always answers right. These assumptions are often true, and if we constantly worried about computer mistakes nothing would get done. But the traditional system model has a binary view of faults (some happen, some never); in reality it's mostly probability: some likelier, some less likely; and the question is whether assumption violations happen enough to meet them in practice. We saw data can corrupt in memory (Chapter 1), on disk (Chapter 6) and on the network (Chapter 9) — should we attend to it more? If you work at large enough scale, even the very unlikely happen.

گذشته از سخت‌افزار، همیشه ریسکِ باگِ نرم‌افزاری هست که checksumهای سطح‌پایینِ شبکه و حافظه و فایل‌سیستم نمی‌گیرنش. حتی پایگاه‌های دادهٔ پراستفاده باگ دارن — نسخه‌های قدیمیِ MySQL قیدِ یکتایی رو درست نگه نمی‌داشتن و سطحِ serializable در PostgreSQL ناهنجاریِ write skew نشون داده، با این‌که هر دو پایگاه داده قوی و battle-tested‌ان؛ توی نرم‌افزارِ کم‌بلوغ‌تر وضع احتمالاً خیلی بدتره. با همهٔ تلاشِ طراحی و تست و بازبینی، باگ می‌خزه تو؛ نادره و سرانجام پیدا و درست می‌شه، ولی یه دوره‌ای هست که می‌تونه داده رو خراب کنه. و دربارهٔ کدِ اپلیکیشن باید باگِ خیلی بیشتری فرض کنی، چون بیشترِ اپ‌ها به‌اندازهٔ کدِ پایگاه داده بازبینی و تست نمی‌بینن؛ خیلی‌هاشان حتی ویژگی‌های حفظِ integrity پایگاه داده (کلیدِ خارجی، قیدِ یکتایی) رو درست به کار نمی‌برن. «سازگاری» به معنای ACID روی این ایده استواره که پایگاه داده از حالتِ سازگار شروع می‌کنه و تراکنش اون رو از یه حالتِ سازگار به حالتِ سازگارِ دیگری می‌بره — پس انتظار داری پایگاه داده همیشه سازگار باشه؛ ولی این حرف فقط وقتی معنا داره که فرض کنی تراکنش بی‌باگه. اگه اپ از پایگاه داده غلط استفاده کنه (مثلاً isolation ضعیف رو ناامن به کار ببره)، integrity پایگاه داده تضمین‌شدنی نیست.

Past hardware, there's always software-bug risk that low-level network, memory and filesystem checksums don't catch. Even heavily used databases have bugs — old MySQL versions didn't uphold uniqueness correctly and PostgreSQL's serializable level showed write-skew anomalies, though both are strong battle-tested databases; in less mature software it's probably far worse. Despite all design, test and review effort, bugs creep in; rare, eventually found and fixed, but there's a window where they can corrupt data. And about application code you must assume far more bugs, since most apps see less review and testing than database code; many don't even correctly use the database's integrity-preserving features (foreign keys, uniqueness constraints). “Consistency” in the ACID sense rests on the idea that the database starts from a consistent state and transactions move it from one consistent state to another — so you expect the database always consistent; but that only makes sense assuming bug-free transactions. If the app misuses the database (e.g. unsafely using weak isolation), database integrity can't be guaranteed.

کورکورانه به وعده‌ها اعتماد نکنDon't blindly trust promises

وقتی نه سخت‌افزار نه نرم‌افزار همیشه به ایده‌آل عمل نمی‌کنن، خرابیِ داده دیر یا زود ناگزیر به‌نظر می‌رسه؛ و دست‌کم باید راهی داشته باشیم بفهمیم داده خراب شده تا درستش کنیم و منشأ خطا رو پیدا کنیم. چک‌کردنِ integrity داده همون حسابرسی (auditing) است. حسابرسی فقط برای مالی نیست، ولی توی مالی خیلی مهمه دقیقاً چون همه می‌دونن اشتباه رخ می‌ده و باید بتونه مشکل رو ببینه و درست کنه. سیستم‌های بالغ هم همین‌طور احتمالِ رخ‌دادنِ نامحتمل‌ها رو در نظر می‌گیرن و ریسکش رو مدیریت می‌کنن: مثلاً سیستم‌های ذخیره‌سازیِ بزرگ مثلِ HDFS و S3 کورکورانه به دیسک اعتماد نمی‌کنن؛ پروسه‌های پس‌زمینه دارن که مدام فایل‌ها رو می‌خونن، با replicaهای دیگه مقایسه می‌کنن و فایل رو از دیسکی به دیسکِ دیگه می‌برن تا ریسکِ خرابیِ خاموش رو کم کنن. اگه می‌خوای مطمئن بشی داده‌ات هنوز هست، باید بخونیش و چک کنی؛ بیشترِ وقت‌ها هست، ولی اگه نبود می‌خوای زود بفهمی نه دیر. به همین استدلال، مهمه گاه‌به‌گاه restore از backup رو هم امتحان کنی — وگرنه ممکنه وقتی بفهمی backup خرابه که دیر شده و داده رو از دست دادی. کورکورانه اعتماد نکن که همه‌چیز دارد کار می‌کند. سیستم‌هایی مثلِ HDFS و S3 هنوز باید فرض کنن دیسک‌ها بیشترِ وقت‌ها درست کار می‌کنن — فرضِ معقولیه، ولی با فرضِ «همیشه درست کار می‌کنن» فرق داره. ولی خیلی سیستم‌های فعلی این رویکردِ «اعتماد، ولی راستی‌آزمایی» و حسابرسیِ مداومِ خودشون رو ندارن؛ خیلی‌ها فرض می‌کنن تضمین‌های درستی مطلق‌ان و برای احتمالِ خرابیِ نادرِ داده هیچ تمهیدی ندارن. در آینده ممکنه سیستم‌های خود‌اعتبارسنج بیشتری ببینیم که مدام integrity خودشون رو چک می‌کنن به‌جای اعتمادِ کور.

When neither hardware nor software always meets the ideal, data corruption sooner or later seems inevitable; so at minimum we need a way to learn data corrupted, to fix it and find the error's source. Checking data integrity is auditing. Auditing isn't only for finance, but it matters hugely in finance precisely because everyone knows mistakes happen and problems must be seen and fixed. Mature systems likewise account for unlikely-event probability and manage its risk: e.g. large storage systems like HDFS and S3 don't blindly trust disks; they run background processes constantly reading files, comparing with other replicas and moving files disk to disk to cut silent-corruption risk. To be sure your data still exists, you must read and check it; mostly it's there, but if not you want to learn early, not late. By the same argument, it's important to occasionally test restoring from backup — otherwise you may learn the backup is broken only when it's too late and data is lost.

Don't blindly trust that everything is working. Systems like HDFS and S3 must still assume disks work correctly most of the time — a reasonable assumption, but different from “always work correctly”. Yet many current systems lack this “trust, but verify” approach and continuous self-auditing; many assume correctness guarantees are absolute, with no provision for rare data-failure probability. In the future we may see more self-validating systems continuously checking their own integrity instead of blind trust.

طراحی برای حسابرسی‌پذیری: اگه تراکنشی چند آبجکت رو توی پایگاه داده mutate کنه، فهمیدنِ دلیلِ زیرین بعداً سخته؛ حتی اگه لاگِ تراکنش رو بگیری، insert و update و delete توی جدول‌های مختلف لزوماً تصویرِ روشنی از «چرا این mutationها انجام شدن» نمی‌دن — فراخوانیِ منطقِ اپلیکیشن که اون mutationها رو تصمیم گرفت گذرا است و قابلِ بازتولید نیست. در مقابل، سیستم‌های رویدادمحور حسابرسی‌پذیریِ بهتری می‌دن: توی رویکردِ event sourcing، ورودیِ کاربر به سیستم به‌صورتِ یه رویدادِ immutable واحد نشون داده می‌شه و هر به‌روزرسانیِ stateای از همون رویداد مشتق می‌شه. مشتق‌سازی رو می‌شه قطعی و تکرارپذیر کرد، طوری که اجرای همون لاگِ رویدادها با همون نسخهٔ کدِ مشتق، همون به‌روزرسانی‌های state رو بده. صریح‌بودن دربارهٔ dataflow، provenance داده رو خیلی روشن‌تر می‌کنه و چک‌کردنِ integrity رو شدنی‌تر: برای لاگِ رویداد می‌شه با hash چک کرد ذخیرهٔ رویداد خراب نشده؛ و برای هر state مشتق می‌شه پردازنده‌های batch و streamای که از لاگِ رویداد مشتقش کردن رو دوباره اجرا کرد و دید همون نتیجه میاد یا نه — یا حتی مشتقِ افزونه رو موازی اجرا کرد. dataflow قطعی و خوش‌تعریف، debug و trace اجرای سیستم رو هم ساده‌تر می‌کنه تا بفهمی چرا کاری کرد — اگه چیزِ غیرمنتظره‌ای رخ داد، ارزشمنده که بتونی دقیقاً همون شرایطی که به رویدادِ غیرمنتظره رسید رو بازتولید کنی — نوعی قابلیتِ debug سفر-در-زمان.

Designing for auditability: if a transaction mutates several objects in the database, understanding the underlying reason later is hard; even capturing the transaction log, inserts, updates and deletes across tables needn't paint a clear picture of “why these mutations happened” — the application-logic call deciding those mutations is transient and irreproducible. Event-driven systems, by contrast, give better auditability: in event sourcing, user input to the system shows as one immutable event, and every state update derives from that event. Derivation can be made deterministic and repeatable, so running the same event log with the same derivation-code version yields the same state updates. Being explicit about dataflow makes data provenance far clearer and integrity checking feasible: for an event log, hashing can check event storage isn't corrupted; and for each derived state, the batch and stream processors that derived it from the event log can be rerun to see if the same result comes — or even run a redundant derivative in parallel. Deterministic, well-defined dataflow also simplifies debugging and tracing system execution to learn why it did something — valuable when something unexpected happens: the ability to reproduce exactly the conditions that led to the unexpected event — a kind of time-travel debugging.

دوباره آرگومانِ سرتاسری: اگه نتونیم کاملاً اعتماد کنیم که هر جزءِ سیستم عاری از خرابیه — که هر سخت‌افزاری بی‌ایراد و هر نرم‌افزاری بی‌باگه — پس دست‌کم باید دوره‌ای integrity داده‌مون رو چک کنیم؛ اگه چک نکنیم، از خرابی خبردار نمی‌شیم تا وقتی که دیر شده و خسارتِ پایین‌دستی زده و ردیابی‌اش خیلی سخت‌تر و گرون‌تر شده. چک‌کردنِ integrity سیستم‌های داده بهتره سرتاسری انجام بشه: هرچه سیستم‌های بیشتری رو در چکِ integrity بگنجانیم، فرصتِ کمتری هست که خرابی توی مرحله‌ای از فرآیند دیده‌نشده بمونه. اگه بتونیم چک کنیم که کلِ خطِ لولهٔ دادهٔ مشتق سرتاسر درسته، اون‌وقت همهٔ دیسک‌ها و شبکه‌ها و سرویس‌ها و الگوریتم‌های سرِ راه ضمناً توی چک گنجانده شدن. چکِ مداومِ integrity سرتاسری اعتماد به درستیِ سیستم‌ها رو بیشتر می‌کنه و این به‌نوبهٔ خود اجازه می‌ده سریع‌تر حرکت کنی (مثلِ تستِ خودکار، حسابرسی شانسِ زود پیداشدنِ باگ رو بیشتر می‌کنه و ریسکِ این‌که تغییری توی سیستم یا فناوریِ ذخیره‌سازیِ تازه خسارت بزنه رو کم می‌کنه)؛ اگه از تغییر نترسی، خیلی بهتر می‌تونی اپ رو برای نیازِ در حالِ تغییر تکامل بدی.

And here's the end-to-end argument again: if we can't fully trust every system part to be failure-free — that all hardware is flawless and all software bug-free — then we must at least check our data's integrity periodically; unchecked, we won't learn of corruption until too late, when it has caused downstream damage and tracing is far harder and pricier. Checking data-system integrity is better done end to end: the more systems you include in the integrity check, the less room for a failure to slip past unseen at some stage of the pipeline. If you can check that the whole derived-data pipeline is correct end to end, then every disk, network, service and algorithm along the way is implicitly included in the check. Continuous end-to-end integrity checking raises your trust in system correctness, which in turn lets you move faster (like automated tests, auditing raises the chance of finding a bug early and cuts the risk that a change or a fresh storage technology causes damage); and if you don't fear change, you can evolve the app far better for changing needs.

ابزارهای سیستمِ دادهٔ حسابرسی‌پذیر: در حالِ حاضر خیلی سیستم‌های داده حسابرسی‌پذیری رو دغدغهٔ سطحِ اول نمی‌کنن. بعضی اپ‌ها مکانیزمِ حسابرسیِ خودشون رو پیاده می‌کنن (مثلاً لاگ‌کردنِ همهٔ تغییرها توی جدولِ audit جدا) ولی تضمینِ integrity لاگِ حسابرسی و state پایگاه داده هنوز سخته. لاگِ تراکنش رو می‌شه با امضای دوره‌ای با ماژولِ امنیتیِ سخت‌افزاری tamper-proof کرد، ولی این تضمین نمی‌کنه که اصلاً تراکنش‌های درست واردِ لاگ شدن. بلاکچین‌هایی مثلِ Bitcoin و Ethereum لاگ‌های append-only مشترک با چکِ سازگاریِ رمزنگاری‌ان؛ تراکنش‌هایی که ذخیره می‌کنن رویدادن و قراردادهای هوشمند اساساً پردازندهٔ stream‌ان؛ و پروتکلِ اجماع‌شون مطمئن می‌شه همهٔ نودها روی همون دنبالهٔ رویدادها توافق داشته باشن. فرق‌شون با پروتکل‌های اجماعِ فصلِ ۱۰ اینه که بلاکچین‌ها Byzantine fault-tolerant‌ان — یعنی حتی اگه بعضی نودهای شرکت‌کننده دادهٔ خراب داشته باشن کار می‌کنن چون replicaها مدام integrity همدیگر رو چک می‌کنن. برای بیشترِ اپ‌ها بلاکچین‌ها overhead زیادی دارن که مفید باشن؛ ولی بعضی ابزارهای رمزنگاری‌شون رو می‌شه توی زمینهٔ سبک‌تر هم به کار برد: مثلاً Merkle treeها درخت‌های hash‌ان که می‌شه باهاشون کارا ثابت کرد رکوردی توی dataset هست (و چند چیزِ دیگه). Certificate transparency از لاگ‌های append-only تأییدشدهٔ رمزنگاری و درخت‌های Merkle برای چک‌کردنِ اعتبارِ گواهی‌های TLS/SSL استفاده می‌کنه؛ و با داشتنِ یه رهبر برای هر لاگ، از نیاز به پروتکلِ اجماع پرهیز می‌کنه. الگوریتم‌های چکِ integrity و حسابرسی، مثلِ certificate transparency و ledgerهای توزیع‌شده، ممکنه در آینده توی سیستم‌های داده به‌طورِ کلی بیشتر استفاده بشن؛ کمی کار لازمه تا به‌مقیاسِ سیستم‌های بدونِ حسابرسیِ رمزنگاری برسند و جریمهٔ عملکرد رو پایین نگه دارن، ولی به‌هرحال جالن.

Auditable data-system tools: currently few data systems make auditability a first-class concern. Some apps implement their own audit machinery (e.g. logging every change in a separate audit table) but the audit log's and the database state's integrity guarantees remain hard. The transaction log can be made tamper-proof by periodic signing with a hardware security module, but that doesn't guarantee the right transactions entered the log at all. Blockchains like Bitcoin and Ethereum are shared append-only logs with cryptographic consistency checks; the transactions they store are events and smart contracts are basically stream processors; and their consensus protocol ensures all nodes agree on the same event sequence. Their difference from Chapter-10 consensus protocols is that blockchains are Byzantine fault-tolerant — they work even with some participants holding corrupt data, since replicas constantly check each other's integrity. For most apps blockchains carry too much overhead to be useful; but some of their cryptographic tools apply in lighter contexts too: e.g. Merkle trees are hash trees that can efficiently prove a record's presence in a dataset (and several other things). Certificate Transparency uses cryptographically verified append-only logs and Merkle trees for checking TLS/SSL certificate validity; and by having one leader per log it avoids needing a consensus protocol. Integrity-checking and auditing algorithms, like certificate transparency and distributed ledgers, may see wider data-system use in future; some work is needed to scale them to non-cryptographically-audited systems' scale while keeping the performance penalty low — but they're interesting regardless.

۱. چرا نوشتنِ مستقیمِ هم‌زمان در پایگاه داده و ایندکسِ جستجو ایدهٔ بدی است؟1. Why is simultaneously writing directly to the database and the search index a bad idea?

تعریفش اینه: دو نوشتنِ مستقل می‌تونن نیمه‌کاره بمونن یا ترتیبِ متفاوت بسازن. مسیرِ واحدِ معتبرِ تغییر و مصرفِ قابل‌بازیابی کمک می‌کنه ایندکس از مرجع ساخته بشه؛ تأخیرِ مقصد همچنان باید دیده بشه — این دام معروفه.

مثال فنی: دو ترتیب که با هم نمی‌خوانن

وضعیت اولیه: یه سناریوی ساده‌ست: T1 قیمت ۱۰۰ و T2 قیمت ۱۲۰ رو می‌نویسن.

اجرای مرحله‌به‌مرحله: مرجع T1 رو بعد T2 اعمال می‌کنه؛ ولی وقتی جدا به ایندکس می‌فرستی، به‌ترتیب T2 بعد T1 بهش می‌رسه و ایندکس روی ۱۰۰ گیر می‌کنه.

نتیجه و دلیل: موفق بودنِ هر چهار نوشتن کافی نیست؛ یا لاگِ مرتبِ تغییر یا کنترلِ نسخه باید ترتیبِ معتبر رو به مقصد برسونه — این دام معروفه.

Because neither one is “in charge of order”: two concurrent clients send two conflicting writes and each system applies its own order; the result is permanent divergence (Fig. 12-4, Diagram 2). The fix: funnel all input through one record and build the derivatives from that same ordered log.

۲. فرقِ دادهٔ مشتقِ لاگ‌محور با تراکنشِ توزیع‌شده چیست؟2. How does log-based derived data differ from a distributed transaction?

جوابش کوتاهه: تراکنشِ توزیع‌شده تصمیمِ تأییدِ مشترک می‌سازه؛ نمای لاگ‌محور تغییرِ مرجع رو بعداً اعمال می‌کنه و می‌تونه موقتاً عقب بمونه. این دو، تضمینِ رؤیت‌پذیری و هماهنگیِ یکسانی ندارن.

مثال فنی: همین‌الان یا بعداً؟

وضعیت اولیه: نگاه کن: تغییرِ قیمت توی مرجع commit شده، ولی جست‌وجو هنوز نسخهٔ قدیمی رو نشون می‌ده.

اجرای مرحله‌به‌مرحله: توی dataflow، مصرف‌کننده بعداً تغییر رو می‌رسونه؛ توی atomic commit، منابعِ participant به یه تصمیمِ مشترکِ commit/abort متعهد می‌شن.

نتیجه و دلیل: روشِ اول lag رو می‌پذیره و بازپخش می‌خواد؛ روشِ دوم هماهنگی و مسیرِ انتظارِ خرابیِ خودش رو داره — حساب کن.

Both chase one goal with two means: transactions with atomic commit, log-based with deterministic retry and idempotence. Transactions usually give read-your-writes but are expensive and failure-intolerant (XA); async derivatives are cheap and strong but give no instant-freshness guarantee. The rest of this chapter is the middle path: stronger guarantees on an async system.

۳. چرا ترتیبِ کامل در مقیاس نمی‌گنجد؟ چهار محدودیت را بگو.3. Why doesn't total order scale? Name the four limits.

چهار محدودیت رو نگه دار: ظرفیتِ مسیرِ مرتب‌کننده، تأخیرِ هماهنگیِ جغرافیایی، مرجع‌های مستقلِ سرویس‌ها و تغییرِ آفلاینِ کلاینت. ترتیبِ مشترکِ همهٔ اتفاق‌ها ممکنه خیلی گران یا نامتناسب بشه — حساب کن.

مثال فنی: علت، ولی روی دو پارتیشن

وضعیت اولیه: رویدادِ ایجادِ سفارش ۴۲ روی پارتیشنِ A و لغوِ همون روی B قرار گرفته.

اجرای مرحله‌به‌مرحله: مصرف‌کننده ممکنه لغو رو پیش از ایجاد ببینه؛ هم‌پارتیشن کردنِ رخدادهای همون سفارش یا نگهداریِ وابستگی این مسئله رو کنترل می‌کنه.

نتیجه و دلیل: رخدادهای مستقل الزاماً ترتیبِ جهانی نمی‌خوان؛ رخدادهای وابسته بدونِ قراردادِ ترتیب، stateِ نامعتبر می‌سازن — حساب کن.

Total order = total order broadcast = consensus, tied to an ordering node: (1) one leader's power doesn't cover the whole flow → sharding and cross-shard order ambiguity; (2) geographic regions have separate leaders (synchronous cross-continent coordination is slow); (3) microservices share no state; (4) offline client-side state changes the seen order.

۴. مثالِ unfriend و پیام چه چیزی را نشان می‌دهد؟4. What does the unfriend-and-message example show?

قضیه اینه که اگه تصمیمِ مجوز و ارسالِ پیام توی مسیرهای مستقل باشن، قطعِ رابطه می‌تونه دیرتر از پیام توی مسیرِ مجوز دیده بشه. وابستگیِ علت و معلول و نقطهٔ بررسیِ دسترسی باید روشن باشه.

مثال فنی: اول unfriend، بعد پیام

وضعیت اولیه: A رابطهٔ دوستی رو حذف می‌کنه و بعد پیامِ محدود به دوستان می‌فرسته.

اجرای مرحله‌به‌مرحله: اگه حذفِ رابطه و پیام توی جریان‌های جدا بی‌ترتیب برسن، سیستم ممکنه پیام رو با مجوزِ قدیمی نشون بده.

نتیجه و دلیل: این دو رخداد رابطهٔ علّی دارن؛ ترتیبِ جهانیِ همهٔ کاربران لازم نیست، ولی وابستگیِ همین عملیات باید حفظ بشه — حدس نزن، استعلام کن.

A hidden causal dependency: the user's intent is “unfriend first, then message”, but if friendship and messages live in two different places the order is lost and the ex-friend wrongly gets notified too. Notification is really a join between messages and the friend list — the same join-timing problem. The fixes: logical timestamps, recording “seen state” with IDs and later references, or conflict resolution (which doesn't fix external effects).

۵. چطور بدونِ قطعی schema را مهاجرت می‌دهی؟5. How do you migrate schema with no outage?

ایده‌ش ساده‌ست: نمایِ تازه رو از تاریخچه می‌سازیم، تغییرهای زنده رو می‌رسونیم، اختلاف رو می‌سنجیم و بعد خواندن رو تدریجی منتقل می‌کنیم. نسخهٔ قبلی تا اطمینان می‌تونه مسیرِ بازگشت باشه.

مثال فنی: مهاجرتِ ایندکس، بدونِ حفره

وضعیت اولیه: search-v1 فعاله و v2 باید فیلدِ برند داشته باشه.

اجرای مرحله‌به‌مرحله: snapshot تا موقعیت ۵۰۰ توی v2 بارگذاری می‌شه؛ تغییرهای بعدی catch up می‌شن؛ و بعد از تطبیق، خواندن به v2 منتقل می‌شه.

نتیجه و دلیل: تغییرهای حینِ backfill گم نمی‌شن؛ ولی cutover پیش از رسیدن به مرزِ لازم می‌تونه نمایِ کهنه رو فعال کنه — سرِ هم نذار.

With two independent views derived from the same data (old + reprocessing-built new), a gradual shift of a small user percent to the fresh view (canary), gradually raising its share, and dropping the old view at the end — like the railway's dual rails, every step reversible (Diagram 4).

۶. سه شرطِ یکپارچه‌سازیِ batch و stream در یک سیستم (kappa) چیست؟6. What are the three conditions for unifying batch and stream in one system (kappa)?

برای الگوی مشترکِ تاریخچه و جریان، امکانِ بازپخش، مدیریتِ سازگارِ خروجیِ تکراری یا ناقص و استفاده از زمانِ رویداد توی محاسباتِ زمانی مهم‌ان. این‌ها نیازهای طراحی‌ان، نه تضمینِ خودکارِ نامِ Kappa.

مثال فنی: یه منطق، هم برای تاریخچه هم برای زنده

وضعیت اولیه: جمعِ فروش هم از فایلِ تاریخی و هم از جریانِ تازه محاسبه می‌شه.

اجرای مرحله‌به‌مرحله: اگه دو کد قواعدِ refund متفاوت داشته باشن، خروجی‌ها واگرا می‌شن؛ منطقِ مشترک با replayِ ورودیِ نسخه‌دار این اختلاف رو کم می‌کنه.

نتیجه و دلیل: kappa فقط «stream همه‌چیز» نیست؛ تاریخچهٔ کافی، بازپردازش، کنترلِ state و اثرهای بیرونی هم لازمن — یادت باشه.

(1) History replay from the same stream engine; (2) exactly-once semantics (discarding broken tasks' partial output, like batch); (3) event-time windowing, not processing-time, since processing time is meaningless during reprocessing.

۷. federated و unbundled چه فرقی دارند و مسئلهٔ سخت کدام است؟7. How do federated and unbundled differ, and which problem is hard?

فرقشون ساده‌ست: فدره هنگامِ خواندن چند منبع رو ترکیب می‌کنه؛ اجزای جدا می‌تونن تغییرها رو از قبل به نماها برسونن. نگاشتِ معنا و نگه‌داشتنِ نسخه‌ها در هر دو، بخشِ سختِ کاره.

مثال فنی: خواندن با هم یا نوشتن با هم

وضعیت اولیه: گزارشِ فروش به سفارش در A و موجودی در B نیاز داره.

اجرای مرحله‌به‌مرحله: federation موقعِ query از دو منبع می‌خونه؛ unbundling تغییرهای منابع رو از قبل به نمایِ خدمت‌دهی می‌رسونه.

نتیجه و دلیل: اولی هزینه و سازگاریِ خواندنِ هم‌زمان رو داره، دومی هزینهٔ نگه‌داری و تازگیِ نما رو — این رو از قلم نینداز.

Federated unifies reads (one query interface over different engines, like Trino); unbundled syncs writes with the event log (unbundling the database's index maintenance). The hard problem is keeping writes in sync, not model-mapping for reads. And the selection metric is breadth (workload coverage), not depth (single-job performance).

۸. چرا به‌جای RPC به سرویسِ نرخِ ارز، مشترکِ جریانِ تغییر شوی؟8. Why subscribe to the change flow instead of RPC-ing the exchange-rate service?

جریانِ تغییر می‌تونه یه نسخهٔ محلیِ نرخ بسازه و وابستگیِ لحظه‌ای به شبکه رو کم کنه. در مقابل، میزانِ تازگی و نرخِ معتبرِ هر عملیات باید روشن باشن — این رو نگه دار.

مثال فنی: نرخ ارز، از جریانِ محلی

وضعیت اولیه: پردازشگر برای هر سفارش به آخرین نرخِ معتبر نیاز داره؛ سرویسِ نرخ موقتاً قطع می‌شه.

اجرای مرحله‌به‌مرحله: با subscription، آخرین نرخِ دریافت‌شده همراهِ نسخه و زمان توی state محلی هست؛ با RPCِ هر سفارش، قطعِ سرویس مستقیماً مسیر رو معطل می‌کنه.

نتیجه و دلیل: جریان، وابستگیِ لحظه‌ای رو کم می‌کنه، ولی سیاستِ نرخِ کهنه و زمانِ اعتبار باید مشخص باشه — گوش کن.

Because synchronous requests add both latency and a failure dependency; and a local cache needs poll or a change flow for freshness anyway. With upfront subscription and a local replica the query becomes local — “the fastest network request is none”. Its cost: you now own a time-dependent streaming join, and reprocessing wants historical rates (Diagram 5).

۹. مسیرِ نوشتن و مسیرِ خواندن یعنی چه و نقشِ ایندکس در آن چیست؟9. What are the write path and read path, and what is the index's role?

تعریفش اینه: مسیرِ نوشتن تغییر رو ثبت و نما رو آماده می‌کنه؛ مسیرِ خواندن از نمای مناسب جواب می‌ده. ایندکس بخشی از کار رو زودتر انجام می‌ده تا هر پرس‌وجو همهٔ داده رو نگردد.

مثال فنی: هزینه رو کجا می‌دیم؟

وضعیت اولیه: برای هر خرید، جمعِ روزانه توی نمای sales_by_day به‌روز می‌شه.

اجرای مرحله‌به‌مرحله: مسیرِ نوشتن کارِ نگه‌داریِ نما رو انجام می‌ده؛ مسیرِ خواندن فقط مقدارِ آماده رو می‌گیره.

نتیجه و دلیل: خواندنِ سریع، در عوضِ نوشتن و ترمیمِ پرهزینه‌تره؛ و اگه query عوض بشه، نمایِ قدیمی ممکنه کافی نباشه — این رو نگه دار.

The write path is eager precomputed work and the read path lazy at-request work; the derived dataset is where they meet. Indexes/caches/views only move the boundary between them: more work at write time for less at read time. The spectrum's ends: no index (cheap writes, expensive scans) and precomputing everything (impossible) — Diagram 6.

۱۰. چرا تراکنشِ serializable به‌تنهایی تضمینِ «درست‌بودنِ اپ» نیست؟10. Why isn't a serializable transaction alone a guarantee of “app correctness”?

چون سریال‌پذیری فقط دربارهٔ تراکنشِ داخلِ محدودهٔ موتوره. ورودیِ غلط، شناسهٔ تازه توی بازتلاش یا اثرِ بیرونیِ تکراری می‌تونه با همون تضمین، خروجیِ ناخواسته بسازه — این دام معروفه.

مثال فنی: تراکنش درست، ولی با هویتِ غلط

وضعیت اولیه: درخواستِ اول سفارش رو با id=r7 ثبت می‌کنه، ولی پاسخ گم می‌شه.

اجرای مرحله‌به‌مرحله: کلاینت برای retry شناسهٔ r8 می‌سازه؛ هر تراکنش جداگانه کاملاً serializable است، ولی دو سفارش ثبت می‌شن.

نتیجه و دلیل: درستیِ دامنه از لایهٔ کلاینت تا مقصد ادامه داره؛ isolationِ قوی، دو درخواستِ مستقل رو یه نیتِ واحد تشخیص نمی‌ده — مواظبِ این دام باش.

Because transactions don't save app bugs (wrong writes, deletes); and “always consistent” only makes sense assuming “bug-free transactions”. Misusing the database (like unsafe weak isolation) destroys integrity. So the app itself must act end to end.

۱۱. مثالِ ۱۳-۱ چرا غلط است و ۱۳-۲ چطور درستش می‌کند؟11. Why is Example 13-1 wrong, and how does 13-2 fix it?

دو UPDATE با COMMIT انتقال رو توی همون اجرا هماهنگ می‌کنن، ولی تکرارِ درخواست رو نمی‌شناسن. ثبتِ شناسهٔ یکتا و اثر توی یه تراکنش، اجرای دوبارهٔ همون درخواست رو کنترل می‌کنه.

مثال فنی: Retry با شناسهٔ تازه یا ثابت

وضعیت اولیه: موجودیِ A برابر ۱۰۰۰ و B برابر ۰ است و انتقالِ ۱۰۰ واحدی commit شده، ولی پاسخ نرسیده.

اجرای مرحله‌به‌مرحله: تکرارِ دو UPDATE بدونِ هویتِ نیت می‌تونه A=800 و B=200 بسازه؛ با request_id ثابت، درجِ unique و دو تغییر توی یه تراکنش، تلاشِ تکراری دوباره اثر نمی‌گذاره.

نتیجه و دلیل: نتیجهٔ یه انتقال باید A=900 و B=100 بمونه؛ کنترلِ درخواستِ تکراری، درست بودنِ محاسبه و کنترلِ موجودی، هر سه لازم‌ان — حساب کن.

13-1 (two UPDATEs + COMMIT) isn't idempotent: if the reply is lost after COMMIT and retried, $22 moves instead of $11 — and real banks don't work that way. 13-2 first inserts the request's unique ID under a UNIQUE constraint; the second attempt on the same ID breaks and the transaction aborts. Databases uphold uniqueness even under weak isolation, unlike app-level check-then-insert.

۱۲. آرگومانِ سرتاسری را با مثالِ سرکوبِ تکراری توضیح بده.12. Explain the end-to-end argument with duplicate suppression.

نکته‌ش اینه: حفاظتِ تکرار باید به محلِ اثرِ نهایی برسه. اگه فقط یه مرحله شناسه رو چک کنه و مرحلهٔ بعد هویتِ کار رو از دست بده، تکرار هنوز ممکنه — این رو جدی بگیر.

مثال فنی: یه هویت، تا آخرِ مسیر

وضعیت اولیه: مرورگر برای خرید r7 شناسه می‌سازه و همون شناسه به سرویس و جدولِ درخواست‌ها می‌رسه.

اجرای مرحله‌به‌مرحله: اثر و رکوردِ r7 توی یه تراکنش ثبت می‌شن؛ پاسخِ گم‌شده با استعلام یا تکرارِ همون r7 بازیابی می‌شه.

نتیجه و دلیل: dedup باید همان نیت کاربر را سرتاسری بشناسد؛ تولید شناسهٔ تازه در هر لایه این زنجیره را می‌شکند.

TCP suppresses duplicates only inside one connection; the database transaction only inside one hop; but the user's post-timeout retry is a separate request neither sees. So the “duplicate suppression” function is fully implementable only with both ends' knowledge (an ID from client to database). Lower layers (TCP, checksums, transactions) stay useful — they lower the problem's odds — but alone insufficient (Diagram 7).

۱۳. چرا قیدِ یکتایی در توزیع‌شده نیازمندِ اجماع است؟ چطور مقیاسش می‌دهی؟13. Why does a uniqueness constraint need consensus in a distributed system? How do you scale it?

قضیه اینه که قیدِ سختِ یکتایی نیاز به تصمیمِ هماهنگ برای کلیدهای درگیر داره. تقسیم بر کلیدِ قید می‌تونه هماهنگی رو محلی‌تر کنه؛ بررسیِ جدا و سپس درج، بدونِ قیدِ اتمیک کافی نیست.

مثال فنی: قیدِ سخت یا جبرانِ پذیرفته‌شده

وضعیت اولیه: نامِ کاربری sara باید فقط یه مالک داشته باشه؛ کالای قابل‌تأمین ممکنه موقتاً بیش‌فروش بشه.

اجرای مرحله‌به‌مرحله: ثبتِ نام روی مسیرِ هماهنگ رقابت می‌کنه؛ در فروشِ دوم، سیاستِ مشخصِ تأمینِ جایگزین یا بازپرداخت می‌تونه جبران کنه.

نتیجه و دلیل: حذفِ هماهنگی بدونِ پذیرشِ صریحِ خطا و جبران، همون قیدِ قبلی رو نگه نمی‌داره — این رو از قلم نینداز.

Because among several concurrent same-value requests one must be accepted and the rest rejected — a single decision is needed. The common path is a single decision leader (with Raft for safe leader change). Scale by sharding on the constrained value (request ID, username hash); but async multi-leader is out, and immediate rejection wants synchronous coordination. In log-based: conflicts to the same shard + single-thread sequential consumption → a deterministic first/rest-rejected decision (Diagram 8).

۱۴. ثبتِ دستور و اعمالِ مرحله‌ای در چند شارد، چه تضمینی می‌دهد؟14. How does Fig. 13-2's multishard payment stay atomic without 2PC?

ثبتِ یه دستورِ معتبر و اعمالِ مرحله‌ایِ اثرها می‌تونه یکپارچگیِ نهایی بسازه، به شرطِ تحویل، جلوگیری از تکرار، کنترلِ موجودی و تطبیق. این روش رؤیتِ اتمیکِ هم‌زمانِ همهٔ شاردها رو خودبه‌خود نمی‌ده — یادت باشه.

مثال فنی: دستورِ پایدار، اثرِ مرحله‌ای

وضعیت اولیه: دستورِ T7: A→B, amount=100 پایدار و پذیرفته‌شده.

اجرای مرحله‌به‌مرحله: shardِ A کسر رو با شناسهٔ T7 یک‌بار اعمال می‌کنه؛ shardِ B واریز رو با همون شناسه اعمال می‌کنه؛ مراحلِ ناتمام retry و تطبیق می‌شن.

نتیجه و دلیل: به شرطِ پروتکلِ درست، اعتبارسنجی و پیشرفت، اثرها کامل می‌شن؛ تا تکمیل ممکنه وضعیتِ میانی دیده بشه و atomic visibility نداریم — ملاحظه کن.

By breaking into sharded stages: the only atomic action is appending the request with a unique request ID to the source account's log; the source processor checks and reserves funds and publishes three events with the same ID; each destination shard applies with ID-based dedup. A crash means deterministic reprocessing of the same decision and outputs → duplicates ignored. Atomicity comes from that one initial event (Diagram 9).

۱۵. timeliness و integrity چه فرقی دارند و کدام مهم‌تر است؟15. How do timeliness and integrity differ, and which matters more?

تازگی زمانِ رسیدنِ نتیجه‌ست؛ یکپارچگی حفظِ قواعدِ معتبر و جلوگیری از گم‌شدن یا تکراره. اهمیتِ هرکدوم به کاربرد وابسته‌ست؛ جبرانِ نتیجهٔ غلط معمولاً سخت‌تره — حساب کن.

مثال فنی: تازگی با درستی فرق داره

وضعیت اولیه: مرجع دو سفارشِ ۱۰۰ و ۲۰۰ داره.

اجرای مرحله‌به‌مرحله: نمای اول فقط سفارشِ اول رو داره و جمعش ۱۰۰ه؛ نمای دوم هر دو رو فوراً دیده، ولی اولی رو دوبار شمرده و جمعش ۴۰۰ه.

نتیجه و دلیل: اولی مشکلِ timeliness داره و دومی مشکلِ integrity؛ جلوتر بودنِ موقعیتِ مصرف به‌تنهایی درست بودنِ محاسبه رو ثابت نمی‌کنه — این دام معروفه.

Timeliness means “the user sees up-to-date state” — its violation is temporary, fixed by waiting/retrying (like a 24h-missing card transaction). Integrity means “no loss, no contradiction” — its violation is permanent, wanting explicit check/repair (like balance ≠ transaction sums). Integrity matters more. Dataflow systems don't guarantee the former but give the latter with four mechanisms: an atomic single message, a deterministic derivation function, an end-to-end ID, immutability + reprocessing (Diagram 10).

۱۶. نقطهٔ بهینهٔ هماهنگی کجاست؟ مثالِ کسب‌وکاری بزن.16. Where is coordination's sweet spot? Give a business example.

هماهنگی رو برای نقض‌های غیرقابل‌قبول نگه دار. اگه کسب‌وکار جبرانِ خطا رو می‌پذیره، روشِ جبران، سقفِ خطا و وعدهٔ کاربر باید از قبل تعیین بشن.

مثال فنی: محلِ هماهنگی رو کجا بذاریم؟

وضعیت اولیه: برای آخرین صندلیِ شماره‌دار دو خریدار داریم، ولی برای شمارشِ بازدید محدودیتِ مشابهی نیست.

اجرای مرحله‌به‌مرحله: فروشِ صندلی روی منبعِ مالکیت رقابت می‌کنه؛ شمارندهٔ بازدید می‌تونه غیرهم‌زمان ادغام بشه.

نتیجه و دلیل: هزینهٔ هماهنگی رو به قیدِ لازم می‌دیم؛ جبران فقط وقتی معنی داره که محصول اون نتیجه رو واقعاً بپذیره — این رو نگه دار.

Coordination cuts inconsistency apologies and raises outage apologies; no absolute zero. When apology is cheap (oversold warehouse with discounts, overbooked flights with refunds) write optimistically and fix later with compensating transactions. When recovery is impossible (cash out of an ATM) coordinate hard. And put synchronous coordination only where needed (Diagram 11).

۱۷. «اعتماد، ولی راستی‌آزمایی» در عمل یعنی چه؟17. What does “trust, but verify” mean in practice?

صحت رو با سنجشِ مستقلِ شمارش، جمع، شناسه و ارتباطِ داده‌ها بررسی می‌کنیم و امکانِ بازسازیِ مقصد رو نگه می‌داریم. سالم بودنِ سرویس، اثباتِ درست بودنِ داده نیست — اینو قاب کن.

مثال فنی: تطبیق با شناسه، نه‌فقط با جمع

وضعیت اولیه: مرجع سفارش‌های 42:100 و 43:200 رو داره؛ گزارش مجموعِ ۳۰۰ رو نشون می‌ده.

اجرای مرحله‌به‌مرحله: ممکنه گزارش ۴۲ رو حذف کرده باشه و سفارشِ دیگه‌ای رو اشتباهاً اضافه کرده باشه؛ مقایسهٔ شناسه، نسخه و مبلغ، اختلافِ واقعی رو پیدا می‌کنه.

نتیجه و دلیل: یکسان بودنِ مجموع شاهدِ کافی برای یکسان بودنِ داده نیست؛ ممیزی و مسیرِ ترمیم باید از مرجعِ معتبر تغذیه بشن — اینو قاب کن.

Don't assume failure never comes: continuous and preferably end-to-end auditing (the more systems in the check, the less room for unseen failure) + provenance-by-design (event sourcing with immutable events and repeatable deterministic derivation, hashes on the log, re-running derivatives for checks, Merkle/certificate-transparency for lightweight proofs). Like HDFS/S3, which don't blindly trust disks.

۱۸. خواندنِ one-off و subscribe در مدلِ «سروِ درخواست = join» چه فرقی دارند؟18. How do one-off reads and subscribes differ in the “serving = join” model?

خواندنِ یک‌باره تصویرِ همون درخواست رو می‌ده؛ اشتراک، تغییرهای بعدیِ مرتبط رو هم تحویل می‌ده. قطع و وصل، مجوز و محلِ ادامهٔ اشتراک باید مدیریت بشن.

مثال فنی: خواندن به‌صورت subscription

وضعیت اولیه: کلاینت با درخواستِ q7 می‌خواد وضعیتِ سفارش ۴۲ رو دنبال کنه.

اجرای مرحله‌به‌مرحله: سیستم q7 رو با تغییرهای سفارش join می‌کنه و بعد از snapshotِ اولیه، updateها رو می‌رسونه؛ reconnect باید gap و تکرار رو کنترل کنه.

نتیجه و دلیل: خواندنِ یک‌باره با پاسخ تموم می‌شه؛ subscription یه وابستگیِ زنده و stateِ مدیریت‌پذیر می‌سازه — یه چیزِ دیگه یادت نره.

When reads and writes are both events reaching one operator, you're doing a stream-table join. A one-off read passes through the join operator and the operator immediately forgets it; a subscribe is a durable join with the other side's past and future events. Logging reads also improves provenance and causal tracing, at storage and I/O cost.

۶.۳. اشتباهات رایج در جواب‌های مصاحبه6.3. 6.3 Common interview mistakes

  1. «تراکنشِ serializable داریم پس اپ‌مان درسته» — باگِ اپ و استفادهٔ غلط از پایگاه داده رو تراکنش پوشش نمی‌ده.
  2. «دقیقاً-یک‌بارِ پردازندهٔ stream یعنی کاربر دوبار submit نمی‌کنه» — scope اش فقط پردازشِ پیامه؛ retryِ کاربر یه درخواستِ جداست و شناسهٔ سرتاسری می‌خواد.
  3. «TCP تکراری رو حذف می‌کنه پس retry امنه» — فقط داخلِ یه اتصال؛ اتصالِ تازه scope تازه‌ست.
  4. «eventual consistency یعنی بی‌خیالِ درستی شو» — نه: integrity (دائمی) رو باید نگه‌داری؛ فقط timeliness (موقتی) رو شل می‌گیری.
  5. «قیدِ یکتایی رو توی اپ با چک-بعد-insert می‌گیریم» — زیرِ isolation غیرسریال‌شدنی می‌شکست؛ قیدِ پایگاه داده یا shard + چکِ ترتیبی لازمه.
  6. «multi-leader ناهمگام + یکتاییِ سخت» — با هم نمی‌شه؛ رهبرهای متفاوت درگیری رو هم‌زمان می‌پذیرن.
  7. «برای یکپارچه‌سازی dual-write می‌زنیم» — بدونِ مرجعِ ترتیب، واگراییِ دائمی می‌گیری.
  8. «CDC باشه یا event sourcing، فرقی نداره» — از نظرِ اصلِ «تصمیم روی ترتیبِ کامل» درسته، ولی هر‌کدام trade-off عملیاتیِ خودش رو داره؛ جمله رو کامل بگو.
  9. «همه‌چیز رو با یه پایگاه دادهِ یکپارچه حل می‌کنیم» — اگه یه فناوری همهٔ نیاز رو بده عالیه؛ ولی بحثِ unbundle پهنا (طیفِ workload) است نه عمق — معیار رو اشتباه نگیر.
  10. «برای timeliness بیشتر، هماهنگی رو زیاد می‌کنیم» بدونِ حسابِ عذرِ outage — نقطهٔ بهینه دوطرفه‌ست.
  11. «timestamp منطقی مشکلِ ترتیبِ علّی رو کامل حل می‌کنه» — نه: تحویلِ نامرتب رو گیرنده هنوز باید تحمل کنه و اثرِ بیرونی (اعلان) رو درست نمی‌کنه.
  12. «backup داریم پس داده امنه» — تا restore رو امتحان نکرده‌ای، نمی‌دونی backup سالمه؛ اعتمادِ کور ممنوع.
  1. “We have serializable transactions so our app is correct” — transactions don't cover app bugs or database misuse.
  2. “The stream processor's exactly-once means users can't double-submit” — its scope is message processing only; a user's retry is a separate request, and it needs an end-to-end ID.
  3. “TCP drops duplicates so retry is safe” — only inside one connection; a fresh connection is a fresh scope.
  4. “Eventual consistency means giving up on correctness” — no: you must keep integrity (permanent); only timeliness (temporary) gets relaxed.
  5. “We enforce uniqueness in the app with check-then-insert” — breaks under non-serializable isolation; you need a database constraint, or a shard plus a sequential check.
  6. “Async multi-leader + hard uniqueness” — impossible together; different leaders concurrently accept conflicting writes.
  7. “We integrate with dual writes” — with no ordering authority you get permanent divergence.
  8. “CDC or event sourcing, no difference” — true for the “decide the total order” principle, but each carries its own operational tradeoffs; say the full sentence.
  9. “We solve everything with one integrated database” — great if one technology covers all your needs; but the unbundle debate is breadth (workload range), not depth — don't mistake the metric.
  10. “For more timeliness, add coordination” without accounting for the outage apologies — the sweet spot is two-sided.
  11. “Logical timestamps fully solve causal ordering” — no: the receiver must still tolerate unordered delivery, and external effects (notifications) stay unfixed.
  12. “We have backups so data is safe” — until you've tested a restore, you don't know the backup is healthy; blind trust is banned.

End-to-end IDs in practice: build a simple balance-transfer form (two accounts + amount) on a relational database that, instead of two direct UPDATEs, first inserts a unique request_id under a UNIQUE constraint (the Example 13-2 pattern). تمرین ۳ — پرداختِ چندshardیِ مینیاتوریExercise 3 — Miniature multishard payment

L3 · Staff / PrincipalL3 · Staff / Principalوابسته به نقشRole-specific50 دقیقه بحث50 min discussion

داستان از این قراره که رکورد فایل framing و checksum و fsync داره؛ تصمیم و تعهد انتشار هم پایدارن. مبلغ pending و اثر هر leg رو هم باید تو مرز مشاهده مشخص حساب کنی.Here's the thing, your file records carry framing and checksums plus fsync; your decisions and publication obligations are durable. And you account for pending funds and each leg's effect at a defined observation boundary.

نسخهٔ بازبینی‌شده برای مصاحبهReviewed interview brief

داستان از این قراره که انتقال مبدأ، مقصد و کارمزد رو با سه log و پردازش قطعی طراحی می‌کنی. رکورد framed با checksum و fsync، رزرو موجودی، تصمیم پایدار، outbox و dedup رو مشخص کن. crash بعد از انتشار بخشی از خروجی رو بازیابی کن و فرق integrity نهایی، pending state و رؤیت اتمیک رو بگو.Here's the thing, you're designing source, destination, and fee transfers with three logs and deterministic processing.   • جبران یا پیشبرد تصمیم رو با مدرک انتخاب می‌کنیYou spell out your visibility guarantees

سه shard مبدأ، مقصد و کارمزد با پردازنده تک‌نخ و لاگ فایلی بساز. قرارداد فایل [length,payload,checksum]، fsync پیش از ACK، و recovery دم ناقص رو تعریف کن؛ خرابی میانی رو بی‌صدا دور ننداز. تصمیم و رزرو وجه و تعهد انتشار outbox باید از یه رکورد پایدار قابل بازسازی باشن. هر leg کلید (payment_id,leg_type) داره؛ مقصد اثر و dedup رو با هم پایدار می‌کنه. بعد از هر انتشار crash بده و پس از restart همون تصمیم ذخیره‌شده رو replay کن. مبلغ pending رو به تفکیک leg حساب کن تا پرداختی که تو مقصد اعمال شده دوباره تو pending شمرده نشه؛ جمع اقتصادی فقط تو یه مرز منطقی مشترک قابل سنجشه. همگرایی نهایی، رؤیت اتمیک بین shardها نمی‌ده؛ تأخیر بی‌نهایت و leg ناموفق به وضعیت محصول و پروتکل reconciliation و compensation مشخص نیاز داره.

Build source, destination, and fee shards with single-thread processors and file logs. Define [length,payload,checksum], fsync-before-ACK, and truncated-tail recovery; never silently discard interior corruption. Reconstruct your decision, reservation, and outbox obligation from one durable record. Identify each leg by (payment_id,leg_type); persist destination dedup with its effect. Crash after each publication and replay the stored decision after restart. Track pending per leg so credited funds aren't counted again as pending; economic conservation needs a common logical observation boundary. Eventual convergence doesn't give you cross-shard atomic visibility. Indefinite delay or a permanently failed leg needs an explicit product state plus a reconciliation and compensation protocol.

جمع‌بندیِ فصل در یک پاراگرافThe chapter in one paragraph

ورودیِ تازه فقط از مبنا وارد می‌شود و بقیهٔ نماها با لاگِ مرتب و تابعِ قطعی و نوشتنِ idempotent مشتق می‌مانند؛ وقتی ترتیبِ کامل نمی‌گنجد فقط همان ترتیبی را نگه دار که علّیت واقعاً می‌خواهد؛ مهاجرت را با دو نمای کنار هم و شیفتِ تدریجی انجام بده؛ به‌جای RPC پرتکرار، مشترکِ جریان شو و محلی بخوان؛ تکراری را با شناسه‌ای سرکوب کن که از کلاینت تا پایگاه داده می‌رود؛ قیدِ سخت را با اجماع (رهبرِ هر shard) بگیر وگرنه خوش‌بینانه بنویس و با compensating transaction عذر بخواه؛ تراکنشِ چندshardی را به stageهای shardشده با همان شناسه بشکن؛ timeliness را از integrity جدا بسنج (اولی موقتی، دومی دائمی)؛ هماهنگی را فقط همان‌قدر بگذار که لازم است؛ و در پایان به هیچ‌چیز کورکورانه اعتماد نکن — حسابرسی کن.

Fresh input enters only through the record, and other views stay derived with an ordered log, a deterministic function and idempotent writes; when total order doesn't fit, keep only the order causality truly wants; migrate with two side-by-side views and gradual shifts; instead of repeated RPC, subscribe to the flow and read locally; suppress duplicates with an ID travelling client to database; take hard constraints with consensus (each shard's leader), otherwise write optimistically and apologize with compensating transactions; break multishard transactions into sharded stages with the same ID; judge timeliness apart from integrity (the former temporary, the latter permanent); coordinate only as much as needed; and finally trust nothing blindly — audit.
