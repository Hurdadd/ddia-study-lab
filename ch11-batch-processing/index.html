ایدهٔ کلیدی فصلChapter thesis

داستان این فصل: پردازش دسته‌ای روی یه ورودیِ محدود، یه نتیجهٔ قابل‌انتشار می‌سازه. از زنجیرهٔ ابزارهای ساده شروع می‌کنیم و می‌رسیم به تقسیمِ کار، انتقالِ داده و نجاتِ وظیفهٔ شکست‌خورده روی چند ماشین.

مثال فنی: بازمحاسبهٔ گزارش از ورودی ثابت

وضعیت اولیه: فرض کن فایل فروش ۱۴ مهر بسته شده و نسخهٔ ورودی معلومه.

اجرای مرحله‌به‌مرحله: حالا job مجموع فروش هر شعبه رو تو خروجی نسخهٔ v2 می‌نویسه؛ اگه فرمول غلط بود، با کد اصلاح‌شده از همون ورودی دوباره اجراش می‌کنیم.

نتیجه و دلیل: ورودی immutable و خروجی نسخه‌داره، پس خطای محاسبه قابل‌بازسازیه؛ بازنویسی مستقیمِ دادهٔ مرجع همچین آزادی‌ای نمی‌ده — همین.

مثال‌های این فصل قصه‌های آموزشی‌ان که از کار روزمره اومدن. عددها فقط برای فهم بهتر انتخاب شدن و معماری هیچ شرکت واقعی رو توصیف نمی‌کنن.

A batch job takes read-only, immutable input and produces derived output — output rebuilt from scratch every run, so you can delete it, fix the logic and rerun. That one simple contract changes everything: retries are safe, you can roll back (time travel), and you can even recover from your own bugs (human fault tolerance). And the price is just as clear: nobody sees output until the whole job ends, and even a tiny input change means reprocessing everything.

نکته‌ش اینجاست: معماری این فصل رو می‌شه تو سه لایه دید — و نمودار ۲ دقیقاً همون سه لایه رو کشیده: ذخیره‌سازی (فایل‌سیستمِ توزیع‌شده یا object store)، هماهنگ‌سازی (scheduler، resource manager و workflow scheduler) و محاسبه (taskهای منزوی که یه shard ورودی می‌خونن و یه shard خروجی می‌نویسن). مدل‌های پردازش روی همین سه لایه می‌شینن: MapReduce، موتورهای dataflow (مثل Spark و Flink)، زبان‌های کوئری مثل SQL و APIهای DataFrame. و کاربردها هم تو چهار دسته جمع می‌شن: ETL، تحلیل، یادگیری ماشین و سرویس‌دهیِ دادهٔ مشتق‌شده.

Think of this chapter's architecture as three layers — and Diagram 2 draws exactly them: storage (a distributed filesystem or object store), orchestration (scheduler, resource manager and workflow scheduler) and compute (isolated tasks each reading one input shard and writing one output shard). Processing models sit on these layers: MapReduce, dataflow engines (like Spark and Flink), query languages like SQL and DataFrame APIs. And the applications fall into four buckets: ETL, analytics, machine learning and serving derived data.

۱.۱. آنلاین در برابر دسته‌ای1.1. Online vs batch

قضیه اینه که: پردازش آنلاین برای جواب دادن به درخواستِ همون لحظه کار می‌کنه؛ پردازش دسته‌ای روی یه مجموعهٔ ته‌دار اجرا می‌شه و خروجی رو بعداً آماده می‌کنه. معیار موفقیتِ این دو تا الزاماً یکی نیست.

مثال فنی: پاسخ کاربر یا پایان job

وضعیت اولیه: فرض کن API وضعیت سفارش باید تو چندصد میلی‌ثانیه جواب بده؛ گزارش کل سال ممکنه نیم ساعت طول بکشه.

اجرای مرحله‌به‌مرحله: حالا API درخواست محدود رو همون لحظه انجام می‌ده؛ job دسته‌ای ورودیِ کران‌دار رو کامل می‌خونه و خروجی رو منتشر می‌کنه.

نتیجه و دلیل: معیار آنلاین بیشتر latency هر درخواسته و معیار batch بیشتر زمان پایان و هزینهٔ کل پردازش — همین.

Most things you've built so far were “ask, get an answer”: the browser wants a page, a remote service calls an API, and the database, cache and search answer. Those are online systems, and their core metric is response time. But sometimes you're holding a computation that fits no interactive request: training a model, transforming a huge data volume, or analyzing a large dataset. Those are batch jobs, and the systems running them are offline systems.

قانون اول — قراردادِ یه job دسته‌ای ساده‌ست: ورودیِ read-only بخون، خروجی رو از صفر بساز. مثلِ تراکنشِ read/write نیست که داده رو mutate کنه؛ خروجی از ورودی derivedـه. اگه از خروجی خوشت نیومد، پاکش کن، منطقِ job رو درست کن، دوباره اجراش کن. همین «immutable بودنِ ورودی + نداشتنِ side effect» چند تا مزیتِ بزرگ می‌ده:

A batch job's contract is simple: read read-only input, build output from scratch. Unlike a read/write transaction it never mutates data; output is derived from input. Dislike the output? Delete it, fix the job logic, rerun. This “immutable input + no side effects” buys several big wins:

  • بازگشت از باگِ کد: اگه باگ بزنی و خروجی خراب بشه، کافیه به نسخهٔ قبلیِ کد برگردی و job رو دوباره اجرا کنی — یا حتی ساده‌تر: خروجیِ قبلی رو تو یه مسیرِ دیگه نگه داشتی و بهش سوییچ می‌کنی. بیشترِ object storeها و open table formatها این رو پشتیبانی می‌کنن و بهش time travel می‌گن. پایگاه‌های داده تراکنشی معمولاً این خاصیت رو ندارن: اگه کدِ باگی دادهٔ بد بنویسه، برگردوندنِ کد هیچی رو درست نمی‌کنه. به این تواناییِ نجات از خطای کد می‌گن human fault tolerance.
  • توسعهٔ سریع‌تر: وقتی اشتباه یعنی «آسیبِ برگشت‌ناپذیر» نیست، تیم‌ها سریع‌تر feature می‌سازن. این همون اصلِ «کمینه‌سازیِ برگشت‌ناپذیری»ـه که برای توسعهٔ چابک هم خوبه.
  • استفادهٔ مجدد از یه مجموعه فایل: همون ورودی می‌تونه ورودیِ jobهای مختلف باشه، از جمله jobهای مانیتورینگی که خروجیِ job رو با اجرای قبلی مقایسه و اختلاف رو اندازه می‌گیرن.
  • بهره‌وری از منابع: frameworkهای دسته‌ای منابع رو کارآمد مصرف می‌کنن؛ پردازشِ دسته‌ای با سیستم‌های آنلاین (مثل پایگاه دادهٔ OLTP یا اپ‌سرور) ممکنه ولی از نظرِ منابع خیلی گرون‌تره.
  • Recovering from code bugs: if you ship a bug and corrupt the output, just revert to the previous code version and rerun the job — or simpler: you kept the previous output under another path and switch back to it. Most object stores and open table formats support this, calling it time travel. Transactional databases usually lack this property: if buggy code writes bad data, reverting the code fixes nothing. This recovery-from-code-errors ability is called human fault tolerance.
  • Faster development: when a mistake means no “irreversible damage”, teams ship features faster. This is the same “minimize irreversibility” principle that serves agile development well.
  • Reusing one file set: the same input can feed different jobs, including monitoring jobs that compare a job's output with the previous run and measure the drift.
  • Resource efficiency: batch frameworks consume resources efficiently; batch work on online systems (like an OLTP database or app server) is possible but far costlier in resources.
بهای این مدلThe price of this model
تو بیشترِ frameworkها، خروجیِ job فقط بعد از پایانِ کلِ job به دردِ jobهای دیگه می‌خوره. و کارایی هم ممکنه افت کنه: هر تغییر تو ورودی — حتی یه بایت — یعنی پردازشِ دوبارهٔ کلِ dataset ورودی. یه job ممکنه دقیقه‌ها و ساعت‌ها و حتی روزها طول بکشه و معمولاً دوره‌ای (مثلاً روزانه) زمان‌بندی می‌شه؛ پس معیارِ اصلی throughputـه، نه سرعتِ پاسخ.
In most frameworks, a job's output is useful to other jobs only after the whole job ends. And performance can suffer: any input change — even one byte — means reprocessing the entire input dataset. A job can take minutes, hours or even days, and usually runs on a schedule (say, daily); so the core metric is throughput, not response speed.

بعضی سیستم‌های دسته‌ای با خطای task با «کشتن و اجرای دوبارهٔ کلِ job» کنار میان؛ بعضی دیگه fault tolerance دارن: job با وجودِ مردنِ چند نود باز هم کامل می‌شه. راستش مرزِ بینِ آنلاین و دسته‌ای همیشه تیز نیست — یه کوئریِ بلندِ پایگاه داده خیلی شبیهِ پردازشِ دسته‌ایه — ولی همین مدلِ دسته‌ایه که اون رو به بلوکِ ساختِ سیستم‌های قابل‌اتکا و مقیاس‌پذیر و قابل‌نگه‌داری تبدیل می‌کنه؛ مثلاً تو data integration و ETL. (جایگزینِ دسته‌ای، پردازش جریانیـه: job بعد از تموم شدنِ ورودی تموم نمی‌شه و تغییرات رو همون لحظه پردازش می‌کنه — فصل ۱۲.)

Some batch systems handle a task failure by “killing and rerunning the whole job”; others have fault tolerance: the job still completes though several nodes died. The online/batch boundary isn't always sharp — a long database query looks a lot like batch processing — but this batch model is what turns it into a building block of dependable, scalable, maintainable systems; e.g. in data integration and ETL. (Batch's alternative is stream processing: the job never ends after the input runs out and processes changes as they happen — Chapter 12.)

۱.۲. از MapReduce تا امروز1.2. From MapReduce to today

ایده‌ش ساده‌ست: MapReduce پردازش بزرگ رو می‌شکنه به کارهای کوچیک و نتیجه‌ها رو جمع می‌کنه. موتورهای جدیدتر می‌تونن زنجیره‌های پیچیده‌تری از تبدیل‌ها رو با سربار کمتر اجرا کنن.

مثال فنی: از چند job تا یک DAG

وضعیت اولیه: تصور کن اول داده پاک‌سازی می‌شه، بعد join می‌خوره و آخرش دو تا گزارش ساخته می‌شه.

اجرای مرحله‌به‌مرحله: حالا MapReduce می‌تونه این مرحله‌ها رو چند تا job جدا کنه؛ موتور dataflow اون‌ها رو به گراف عملگرها تبدیل می‌کنه و بعضی مرحله‌ها رو ادغام می‌کنه.

نتیجه و دلیل: مدل اجرا هزینهٔ فایل میانی و زمان‌بندی رو عوض می‌کنه؛ هدف هنوز ساختنِ خروجیِ درست از ورودیِ معلومه — خلاص.

Modern batch processing is deeply shaped by MapReduce — the algorithm Google published in 2004, later implemented in Hadoop, CouchDB and MongoDB. MapReduce is a fairly low-level programming model; less capable than the parallel execution engines of analytical databases. Fresh out of the gate, it was a leap in processable scale on commodity hardware — but today it's largely obsolete, and even Google doesn't use it anymore.

پردازشِ دسته‌ایِ امروز معمولاً با Spark یا Flink یا موتورهای کوئریِ data warehouse انجام می‌شه. این‌ها مثلِ MapReduce به sharding (فصل ۷) و اجرای موازی تکیه دارن، ولی استراتژی‌های کشینگ و اجرای خیلی پیچیده‌تری دارن. با بالغ شدنِ این سیستم‌ها، دغدغه‌های عملیاتی تا حدِ زیادی حل شد و تمرکز رفت به قابلیتِ استفاده: مدل‌های پردازشِ جدید مثل dataflow APIها، زبون‌های کوئری و DataFrame APIها حالا همه‌جا پشتیبانی می‌شن. ابزارهای orchestration هم بالغ شدن: schedulerهای Hadoop-محور مثل Oozie و Azkaban جاشون رو به راه‌حل‌های عمومی‌تر مثل Airflow و Dagster و Prefect دادن که طیفِ وسیعی از frameworkها و warehouseهای ابری رو پشتیبانی می‌کنن.

Today's batch processing usually runs on Spark or Flink or data-warehouse query engines. Like MapReduce they rely on sharding (Chapter 7) and parallel execution, but with far more sophisticated caching and execution strategies. As these systems matured, operational concerns were largely solved and focus moved to usability: new processing models like dataflow APIs, query languages and DataFrame APIs are now supported everywhere. Orchestration tooling matured too: Hadoop-centric schedulers like Oozie and Azkaban gave way to general solutions like Airflow, Dagster and Prefect supporting a wide range of frameworks and cloud warehouses.

و البته ابر: لایهٔ ذخیره‌سازیِ دسته‌ای داره از فایل‌سیستم‌های توزیع‌شده مثل HDFS و GlusterFS و CephFS به object storeهایی مثل S3 منتقل می‌شه؛ و data warehouseهای ابریِ مقیاس‌پذیر مثل BigQuery و Snowflake مرزِ بینِ warehouse و پردازشِ دسته‌ای رو محو کردن. نتیجه: «همگرایی» — که تو §۴.۶ دقیق‌تر می‌بینیمش.

And of course the cloud: batch storage is moving from distributed filesystems like HDFS, GlusterFS and CephFS to object stores like S3; and scalable cloud data warehouses like BigQuery and Snowflake blurred the line between warehouse and batch processing. Result: “convergence” — seen precisely in §4.6.

۲.۱. تحلیل لاگ با pipeline2.1. Log analysis with a pipeline

لاگ دسترسی، ردِ درخواست‌های وب رو نگه می‌داره. برای گزارش اول باید فیلدِ موردنظر رو جدا کنیم و بعد به شکل مناسبِ شمارش یا گروه‌بندی درش بیاریم.

مثال فنی: چرا sort قبل از uniq؟

وضعیت اولیه: تصور کن مسیرهای ورودی /a,/b,/a هستن.

اجرای مرحله‌به‌مرحله: حالا uniq -c فقط تکرارهای مجاور رو می‌شماره و بدون sort سه تا گروه می‌بینه؛ sort دو تا /a رو کنار هم می‌آره.

نتیجه و دلیل: مرتب‌سازی تو این pipeline برای درستیِ شمارش لازمه، نه فقط برای قشنگی خروجی — اینو قاب کن.

Suppose a web server appending one line to a log file per request. A standard NGINX access line looks like this:

  $status $body_bytes_sent "$http_referer" "$http_user_agent"

یعنی این یه خط می‌گه: تو تاریخِ مشخص، سرور درخواستِ فایلِ /css/typography.css رو از IPِ 216.58.210.78 گرفته؛ کاربر احراز هویت نشده (پس $remote_user خط تیره‌ست)؛ پاسخِ 200 بوده و 3,377 بایت حجم داشته. بیا «پنج صفحهٔ پربازدید» رو با ابزارهای پایه پیدا کنیم:

So this line says: at the given date the server got a request for /css/typography.css from IP 216.58.210.78; the user wasn't authenticated (so $remote_user is a dash); the response was 200 with 3,377 bytes. Now let's find the “top five pages” with basic tools:

cat /var/log/nginx/access.log |
    awk '{print $7}' |
    sort             |
    uniq -c          |
    sort -r -n       |
    head -n 5
  • cat /var/log/nginx/access.log — فایلِ لاگ رو می‌خونه. (راستش cat این‌جا لازم نیست؛ می‌شد فایل رو مستقیم به awk داد. ولی خطِ لوله‌ای با این شکلِ نوشتن واضح‌تر می‌شه.)
  • awk '{print $7}' — هر خط رو بر اساسِ فاصلهٔ خالی به فیلدها تقسیم می‌کنه و فقط فیلدِ هفتم رو چاپ می‌کنه که همون URL درخواست‌شدهست؛ تو خطِ نمونه یعنی /css/typography.css.
  • sort — فهرستِ URLها رو الفبایی مرتب می‌کنه. دلیلش اینه: اگه URLای n بار درخواست شده باشه، تو خروجیِ مرتب‌شده، همون URL n بار پشتِ سرِ هم میاد.
  • uniq -c — خطوطِ تکراریِ مجاور رو حذف می‌کنه؛ گزینهٔ -c یه شمارنده هم اضافه می‌کنه: برای هر URLِ متمایز، تعدادِ دفعاتِ ظهورش رو می‌نویسه.
  • sort -r -n — بارِ دوم مرتب‌سازی، این‌بار بر اساسِ عددِ ابتدای خط (-n) که همون تعدادِ درخواست‌هاست، و به‌صورتِ معکوس (-r) تا بزرگ‌ترین اول بیاد.
  • head -n 5 — فقط پنج خطِ اول رو نگه می‌داره و بقیه رو دور می‌ریزه.
  • cat /var/log/nginx/access.log — reads the log file. (Honestly cat is unneeded here; the file could go to awk directly. But the linear-pipeline style reads clearer.)
  • awk '{print $7}' — splits each line on whitespace and prints only the seventh field, the requested URL; in the sample line, /css/typography.css.
  • sort — sorts the URL list alphabetically. Why: if a URL was requested n times, the sorted output holds that same URL n times in a row.
  • uniq -c — drops adjacent duplicate lines; the -c flag adds a counter: one line with its count per distinct URL.
  • sort -r -n — sorts a second time, now by the leading number (-n), the request count, in reverse (-r) so the biggest comes first.
  • head -n 5 — keeps only the first five lines and discards the rest.

۲.۲. sort در برابر تجمیع در حافظه2.2. Sort vs in-memory aggregation

قضیهٔ شمارش با جدول هش اینه: معمولاً به حافظهٔ متناسب با تعداد کلیدهای متفاوت نیاز داره. مرتب‌سازیِ بیرونی می‌تونه از دیسک کمک بگیره و وقتی داده تو حافظه جا نمی‌شه هم ادامه بده.

مثال فنی: تجمیع بیرون از RAM

وضعیت اولیه: فرض کن ورودی یه میلیارد کلید متفاوت داره و جدول hashِ شمارنده‌ها تو RAM جا نمی‌شه.

اجرای مرحله‌به‌مرحله: حالا external sort تکه‌هایی که تو حافظه جا می‌شن رو مرتب می‌کنه و رو دیسک می‌نویسه، بعد ادغامشون می‌کنه.

نتیجه و دلیل: مرتب‌سازی می‌تونه با دیسک و حافظهٔ محدود ادامه بده؛ hash aggregation هم ممکنه spill داشته باشه، پس برتریِ مطلق مطرح نیست — روشنه، نه؟

The same job could be done with a simple program instead of the Unix chain. E.g. in Python:

from collections import defaultdict
  counts = defaultdict(int)
  with open('/var/log/nginx/access.log', 'r') as file:
      for line in file:
          url = line.split()[6]
          counts[url] += 1
  top5 = sorted(((count, url) for url, count in counts.items()),
                reverse=True)[:5]
  for count, url in top5:
      print(f"{count} {url}")
  • counts = defaultdict(int) — یه جدولِ hash که برای هر URL یه شمارنده نگه می‌داره؛ مقدارِ اولیهٔ هر شمارنده صفره.
  • line.split()[6] — URL درخواست‌شده رو از هر خط برمی‌داره؛ فیلدِ هفتمِ جداشده با فاصله (شاخصِ ۶ چون آرایه‌های پایتون از صفر شماره‌گذاری می‌شن).
  • counts[url] += 1 — شمارندهٔ URLِ همون خط رو یکی زیاد می‌کنه.
  • sorted(... reverse=True)[:5] — محتوای جدولِ hash رو بر اساسِ شمارنده (نزولی) مرتب می‌کنه و پنج موردِ اول رو برمی‌داره.
  • print(...) — همون پنج مورد رو چاپ می‌کنه.
  • counts = defaultdict(int) — a hash table keeping one counter per URL; each counter starts at zero.
  • line.split()[6] — takes the requested URL from each line; the seventh whitespace-separated field (index 6, since Python arrays count from zero).
  • counts[url] += 1 — increments that line's URL counter.
  • sorted(... reverse=True)[:5] — sorts the hash table's contents by counter (descending) and takes the top five.
  • print(...) — prints those five.

این برنامه به فشردگیِ زنجیرهٔ Unix نیست ولی خواناست و انتخاب بینشون تا حدی سلیقه‌ایه. ولی یه تفاوتِ بزرگ تو جریانِ اجرا هست که رو فایلِ بزرگ خودش رو نشون می‌ده:

This program is less compact than the Unix chain but readable, and the choice between them is partly taste. But one big execution-flow difference shows on large files:

  • تجمیع در حافظه (اسکریپتِ پایتون): جدولِ hashِ URLها تو حافظه می‌مونه. کارِ حافظه‌ایِ job (یعنی مقدارِ حافظه‌ای که job به دسترسیِ تصادفی نیاز داره — بهش working set می‌گن) فقط به تعدادِ URLهای متمایز بستگی داره: اگه یه URL یه میلیون بار اومده باشه، باز هم فقط یه URL + یه شمارنده جا می‌گیره. اگه این working set کوچیک باشه (مثلاً برای اکثرِ وب‌سایت‌ها تو ۱ گیگابایت جا می‌شه)، همون روش حتی رو لپ‌تاپ عالیه.
  • مرتب‌سازی (pipeline): اگه working set از حافظه بزرگ‌تر بشه، رویکردِ مرتب‌سازی برنده‌ست چون دیسک رو کارآمد استفاده می‌کنه — دقیقاً همون اصلِ «ذخیره‌سازیِ log-structured» (فصل ۴): تکه‌های داده تو حافظه مرتب می‌شن و به‌صورتِ segment file رو دیسک نوشته می‌شن، بعد چند تا segmentِ مرتبِ کوچیک تو یه فایلِ مرتبِ بزرگ‌تر ادغام می‌شن. mergesort الگوی دسترسیِ ترتیبی داره که رو دیسک (و SSD) خیلی بهتر از دسترسیِ تصادفی عمل می‌کنه.
  • و نکتهٔ عملی: دستورِ sort تو GNU Coreutils خودش datasetهای بزرگ‌تر از حافظه رو با spill به دیسک مدیریت می‌کنه و مرتب‌سازی رو رو چند هستهٔ CPU موازی می‌کنه. یعنی همون خطِ فرمانِ ساده بدونِ تموم شدنِ حافظه به datasetهای بزرگ مقیاس می‌خوره؛ گلوگاه احتمالاً نرخِ خوندنِ فایلِ ورودی از دیسکه.
  • In-memory aggregation (the Python script): the URL hash table lives in memory. The job's memory footprint (the memory needing random access — called the working set) depends only on the distinct URL count: a URL seen a million times still takes one URL + one counter. When this working set is small (e.g. most websites fit in 1 GB), this method is excellent even on a laptop.
  • Sorting (the pipeline): when the working set outgrows memory, sorting wins because it uses disk efficiently — exactly the “log-structured storage” principle (Chapter 4): data chunks are sorted in memory and written as segment files, then several small sorted segments merge into a bigger sorted file. Mergesort's sequential access pattern performs far better on disk (and SSD) than random access.
  • And the practical point: GNU Coreutils sort itself handles bigger-than-memory datasets by spilling to disk and parallelizes sorting across CPU cores. So the same simple command line scales to large datasets without running out of memory; the bottleneck is likely the input file's read rate.

۲.۳. محدودیتِ تک‌ماشین و گذار به توزیع‌شده2.3. The single-machine limit and the move to distributed

داستان از این قراره: وقتی زمان اجرا و ظرفیت دیسک یا توانِ یه ماشین کافی نیست، می‌شه داده و کار رو تقسیم کرد. توزیع، هزینهٔ شبکه و هماهنگی رو هم اضافه می‌کنه و همیشه قدم اول نیست.

مثال فنی: ورودی بزرگ‌تر از یک ماشین

وضعیت اولیه: تصور کن 10 TB لاگ داریم و یه ماشین روزانه فقط 1 TB رو تو زمان مجاز پردازش می‌کنه.

اجرای مرحله‌به‌مرحله: حالا فایل‌ها به taskهای مستقل تقسیم می‌شن؛ چند تا worker بخش‌ها رو می‌خونن و خروجی تجمیعی تو مرحلهٔ بعد ادغام می‌شه.

نتیجه و دلیل: توزیع ظرفیت رو زیاد می‌کنه، ولی شبکه و skew و هماهنگیِ taskها بخشی از زمان پایان می‌شن — جادو نیست.

Unix tools' limit is running on one machine. Datasets that fit neither in memory nor on local disk are the problem — and that is where distributed batch frameworks enter. The same Unix example had three cooperating parts: storage devices reachable through the OS filesystem interface; a scheduler deciding when each process runs and how much CPU it gets; and a set of Unix programs whose stdin and stdout are piped together. The same three parts exist in distributed frameworks — the key analogy of the next section.

۳.۱. قیاس با سیستم‌عامل و سه لایه3.1. The OS analogy and the three layers

نوبتی هم باشه نوبت قیاسه: چارچوبِ دسته‌ای مثل یه سیستم‌عامل، محل داده و سهم منابع و اجرای کارها رو مدیریت می‌کنه؛ با این فرق که این مسئولیت‌ها بین چند تا ماشین پخش شدن.

مثال فنی: سه مسئولیتِ چارچوب

وضعیت اولیه: فرض کن job به خوندن فایل و اجرای ۱۰۰ تا task و انتقال دادهٔ بین مرحله‌ها نیاز داره.

اجرای مرحله‌به‌مرحله: حالا لایهٔ ذخیره فایل رو نگه می‌داره؛ scheduler منابع می‌ده؛ موتور اجرا task و retry و shuffle رو مدیریت می‌کنه.

نتیجه و دلیل: قیاس با سیستم‌عامل یعنی برنامه همهٔ جزئیات ماشین‌ها رو خودش اداره نکنه؛ مرز هر لایه هنوز باید روشن باشه — حکش کن تو ذهنت.

Like we saw at the end of the last section, you can view a distributed batch framework as a distributed operating system: it's got a filesystem, a job scheduler, and programs passing data through the filesystem or other channels. Three main layers:

  • ذخیره‌سازی (Storage): بلاک‌ها و متادیتا و یه پروتکلِ دسترسیِ قابلِ تعویض — نقشِ فایل‌سیستم.
  • هماهنگ‌سازی (Orchestration): این‌که چی کجا و با چقدر حافظه و CPU اجرا بشه — نقشِ kernel.
  • محاسبه (Compute): taskهای منزوی که یه shard ورودی می‌خونن و یه shard خروجی می‌نویسن — نقشِ پروسه‌ها.
  • Storage: blocks, metadata and a swappable access protocol — the filesystem role.
  • Orchestration: what runs where with how much memory and CPU — the kernel role.
  • Compute: isolated tasks each reading one input shard and writing one output shard — the processes role.

از workflow scheduler فلشِ «submit job (N tasks, resources, code)» به Scheduler می‌ره (زیرنویس: decides which task runs where) و از scheduler یه فلشِ خط‌چینِ «query cluster state» به Resource manager می‌ره (زیرنویس: global cluster state، تگِ ZooKeeper / etcd) — یعنی scheduler تصمیمش رو بر اساسِ نمایِ سراسریِ خوشه می‌گیره.

بعد فلشِ «assign task, prefer data locality» از scheduler به لایهٔ محاسبه می‌ره: Executor on each node (زیرنویس: runs tasks, cgroups isolation، تگِ on every node) و از اون فلشِ «runs each task» به Batch task با زیرنویسِ input shard → output shard. یه فلشِ خط‌چینِ برگشتی هم هست: «heartbeats + task status» از executor به resource manager — همون heartbeat که زنده‌بودن رو خبر می‌ده.

لایهٔ پایین: از Batch task سه تا فلش به لایهٔ ذخیره‌سازی می‌ره: «read input shard / write output shard» به Data nodes (زیرنویس: blocks 128MB / 4MB، تگِ replicated or erasure-coded)؛ خطِ خط‌چینِ «resolve block locations» به Metadata service (زیرنویس: file locations, permissions، تگِ NameNode)؛ و «read input / write output through pluggable protocol (S3 API)» به Object store (زیرنویس: bucket + key, immutable، تگِ S3-style API). همین سه مسیر می‌گه: هم فایل‌سیستمِ توزیع‌شده و هم object store پشتِ یه پروتکلِ قابلِ تعویض قرار می‌گیرن.

۳.۲. فایل‌سیستم‌های توزیع‌شده3.2. Distributed filesystems

ایده‌ش ساده‌ست: فایل‌سیستم توزیع‌شده فایل بزرگ رو به بخش‌هایی رو چند تا ماشین تقسیم می‌کنه و معمولاً نسخه‌های اضافی نگه می‌داره. برنامه باید بتونه فایل رو بخونه، بدون این‌که محلِ تک‌تک بخش‌ها رو مدیریت کنه.

مثال فنی: بلاک بزرگِ فایل توزیع‌شده

وضعیت اولیه: فرض کن فایل 1 GB با بلاک فرضی 128 MB به هشت بخش تقسیم شده.

اجرای مرحله‌به‌مرحله: حالا metadata محل کپی هر بلاک رو می‌ده و worker از یه کپی سالم می‌خونه؛ اندازهٔ بلاک رو تعداد metadata و موازی‌سازی اثر داره.

نتیجه و دلیل: بلاکِ درشت برای اسکن ترتیبی و کاهش سربار مناسبه؛ با page کوچیکِ موتور پایگاه داده هدف یکسانی نداره — همین.

Your own OS filesystem has layers: at the bottom the block device driver talks to the disk directly, enabling raw block reads/writes; above it the page cache keeps recently-touched blocks in memory; then the filesystem layer (like ext4 or XFS) breaks big files into blocks and tracks metadata like inodes and directories; and finally the OS exposes filesystems to programs through one shared API called VFS.

فایل‌سیستم‌های توزیع‌شده (DFS) هم همین‌طور کار می‌کنن: فایل‌ها به بلاک شکسته و بینِ ماشین‌ها پخش می‌شن؛ ولی بلاک‌های DFS معمولاً خیلی بزرگ‌ترن: HDFS پیش‌فرضِ 128MB داره، JuiceFS و خیلی از object storeها 4MB — در برابرِ 4,096 بایتِ ext4. بلاکِ بزرگ‌تر یعنی متادیتای کمتر (که رو datasetهای petabyteی فرقِ بزرگی می‌کنه) و هزینهٔ seek نسبت به خوندن کمتر. یه تفاوتِ ظریف: دستگاه‌های فیزیکی نمی‌تونن «بخشی از بلاک» بنویسن و سیستم‌عامل مجبور به نوشتنِ کلِ بلاکه، ولی چون DFS رو فایل‌سیستمِ سیستم‌عاملِ نودها پیاده‌سازی می‌شه این الزام رو نداره: فایلِ 900MB با بلاکِ 128MB یعنی هفت تا بلاکِ 128MB و یه بلاکِ 4MB.

Distributed filesystems (DFS) work the same way: files break into blocks spread across machines; but DFS blocks are usually far bigger: HDFS defaults to 128MB, JuiceFS and many object stores to 4MB — vs ext4's 4,096 bytes. Bigger blocks mean less metadata (a big deal on petabyte datasets) and cheaper seeks relative to reads. One subtle difference: physical devices cannot write “part of a block” so the OS must write whole blocks, but since a DFS is implemented on the nodes' OS filesystems it has no such requirement: a 900MB file with 128MB blocks means seven 128MB blocks and one 4MB block.

بلاک‌های DFS با درخواستِ شبکه‌ای به ماشینی که بلاک رو نگه داشته خونده می‌شن. رو هر ماشین یه daemon می‌شینه که API برای خوندن/نوشتنِ بلاک‌ها به‌صورتِ فایل رو فایل‌سیستمِ محلی‌ش می‌ده: Hadoop به اون‌ها DataNode می‌گه و GlusterFS فرآیندهای glusterfsd. معادلِ توزیع‌شدهٔ page cache هم هست: چون بلاک‌ها به‌صورتِ فایل رو data nodeها هستن، هر خوندن از page cache سیستم‌عاملِ همون نود می‌گذره؛ بعضی DFSها لایه‌های کشِ بیشتر هم دارن (مثل کشِ سمتِ کلاینت و دیسکِ محلی تو JuiceFS).

DFS blocks are read with network requests to the machine holding the block. Each machine runs a daemon offering a block read/write API as files on its local filesystem: Hadoop calls them DataNodes, GlusterFS calls them glusterfsd processes. The distributed equivalent of the page cache exists too: since blocks sit as files on data nodes, every read passes through that node's OS page cache; some DFSs add more cache layers (like client-side caches and local disk in JuiceFS).

متادیتا هم دردِ خودش رو داره: ext4/XFS فضای خالی و جای بلاک‌های فایل و ساختارِ دایرکتوری و مجوزها رو نگه می‌دارن؛ DFS هم به راهی برای پیگیریِ جای فایل‌ها تو ماشین‌های مختلف نیاز داره. Hadoop سرویسی به نام NameNode داره؛ 3FS (پروژهٔ DeepSeek) سرویسِ متادیتایی داره که داده‌ش رو تو یه KV store مثل FoundationDB پایدار می‌کنه. و رو فایل‌سیستم، نقشِ VFS رو پروتکلِ DFS بازی می‌کنه: هر DFSای که اون پروتکل رو پیاده کنه قابلِ استفاده‌ست. API S3 دقیقاً به همین شکل فراگیر شده: MinIO و Cloudflare R2 و Tigris و Backblaze B2 و خیلی‌های دیگه اون رو پیاده‌سازی می‌کنن. بعضی DFSها کاملاً POSIX-سازگارن و با FUSE یا NFS به VFS می‌چسبن — NFS معروف‌ترین پروتکلِ فایل‌سیستمِ توزیع‌شده‌ست.

Metadata has its own problem: ext4/XFS track free space, file-block placement, directory structure and permissions; a DFS likewise needs a way to track file placement across machines. Hadoop has a service called NameNode; 3FS (DeepSeek's project) has a metadata service persisting its data in a KV store like FoundationDB. And the VFS role is played by the DFS protocol: any DFS implementing that protocol is usable. The S3 API became ubiquitous exactly this way: MinIO, Cloudflare R2, Tigris, Backblaze B2 and many more implement it. Some DFSs are fully POSIX-compatible and attach to VFS via FUSE or NFS — NFS being the most famous distributed-filesystem protocol.

One final architectural dimension: DFSs are built on the shared-nothing principle — vs the shared-disk approach of NAS and SAN, centralized appliances (sometimes with special hardware and Fibre Channel). Shared-nothing wants only commodity computers + an ordinary datacenter network. Commodity hardware is cheaper but fails more often; so blocks are replicated across machines (like Chapter 6) or protected with erasure coding like Reed–Solomon, cheaper in storage than full copies — the RAID idea, but over the datacenter network and without special hardware.

۳.۳. object store3.3. Object stores

داستان اینه: مخزن شیء، داده رو معمولاً به‌شکل اشیای نام‌دار با API ذخیره می‌کنه. رفتارش الزاماً مثل فایل‌سیستم محلی نیست؛ مثلاً تغییر یه بخش از فایل ممکنه به شکل دیگه‌ای انجام بشه.

مثال فنی: Object یک فایل POSIX کامل نیست

وضعیت اولیه: فرض کن خروجی job با کلید reports/run-42/part-1 تو object store نوشته می‌شه.

اجرای مرحله‌به‌مرحله: حالا برای انتشارِ نسخهٔ کامل، manifest یا اشاره‌گر نسخهٔ معتبر عوض می‌شه؛ نباید rename اتمیکِ دایرکتوری رو بدون پشتیبانی فرض کرد.

نتیجه و دلیل: API و تضمین عملیات object store باید جدا بررسی بشه؛ شبیه بودن اسم «فایل» رفتار یکسان نمی‌سازه — این دام معروفه.

Object storage services like Amazon S3, Google Cloud Storage, Azure Blob Storage and OpenStack Swift became the popular DFS replacement for batch jobs. The boundary between the two is blurring: FUSE drivers let you see an object store as a filesystem, and some DFS implementations like JuiceFS and Ceph offer both APIs (object and filesystem). But their APIs, performance and consistency guarantees differ a lot — adopt carefully and verify they really behave as you expect.

  • ساختارِ URL: هر object آدرسی مثل s3://my-photo-bucket/2025/04/01/birthday.png داره. بخشِ host (my-photo-bucket) اسمِ bucketـه (تو سطحِ جهانی یکتا) و بقیه، key شیئه که تو bucket باید یکتا باشه.
  • get/put و immutability: خوندن با get و نوشتن با putـه. برخلافِ فایل‌ها، object بعد از نوشتن immutableـه: برای تغییر باید کلش رو دوباره بنویسی — مثلِ key-value store. (Azure Blob و S3 Express One Zone append دارن، بقیه معمولاً نه.) هیچ file handleای مثل fopen/fseek تو کار نیست.
  • پیشوند به‌جای دایرکتوری: مسیرها شبیهِ دایرکتوری به نظر می‌رسن ولی object store اصلاً مفهومِ دایرکتوری نداره؛ اسلش‌ها بخشی از key هستن. فهرست‌گیری با یه پیشوند انجام می‌شه و دو تا فرق با ls داره: مثلِ ls -R بازگشتیه (همهٔ objectهای زیرمجموعه رو می‌آره) و دایرکتوریِ خالی ممکن نیست — اگه همهٔ objectهای زیرِ یه مسیر رو حذف کنی، دیگه اون مسیر تو list ظاهر نمی‌شه؛ رسمِ رایج ساختنِ یه object صفر‌بایتی به‌عنوانِ نمایندهٔ دایرکتوریِ خالیه.
  • نبودِ link و قفل، rename غیراتمیک: DFSها اغلب hard link و symbolic link و قفلِ فایل و rename اتمی دارن؛ object storeها ندارن. rename یعنی کپی به key جدید و بعد حذفِ کلیدِ قدیمی؛ و برای تغییرِ اسمِ یه «دایرکتوری» باید تک‌تک objectها رو تغییر نام بدی چون اسمِ دایرکتوری بخشی از keyـه.
  • تفاوت با KV store (فصل ۴): KV storeها برای مقدارهای کوچیک (کیلوبایت) و خوندن/نوشتنِ مکررِ کم‌تأخیر بهینه‌ان؛ DFS و object store برای objectهای بزرگ (مگابایت تا گیگابایت) و خوندن‌های بزرگ‌تر و کم‌دفعه‌تر. البته object storeها دارن این مرز رو جابه‌جا می‌کنن (مثلاً S3 Express One Zone با تأخیرِ تک‌میلی‌ثانیه‌ای).
  • locality: DFS مثل HDFS اجازه می‌ده task رو ماشینی اجرا بشه که نسخه‌ای از فایل رو داره — پس فایل از شبکه نمی‌گذره و اگه کدِ task از داده‌ای که می‌خونه کوچیک‌تر باشه، پهنای باند صرفه‌جویی می‌شه. object storeها معمولاً ذخیره‌سازی و محاسبه رو جدا نگه می‌دارن: پهنای باندِ بیشتری مصرف می‌شه (که با شبکه‌های سریعِ امروزی قابلِ قبوله)، ولی CPU و حافظه مستقل از ذخیره‌سازی مقیاس می‌گیرن.
  • URL structure: each object has an address like s3://my-photo-bucket/2025/04/01/birthday.png. The host part (my-photo-bucket) is the bucket name (globally unique); the rest is the object's key, unique within the bucket.
  • Get/put and immutability: reading is get, writing is put. Unlike files, an object is immutable after writing: changing it means rewriting it whole — like a key-value store. (Azure Blob and S3 Express One Zone have appends; most others don't.) No file handles like fopen/fseek exist.
  • Prefixes instead of directories: paths look directory-like but object stores have no directory concept; slashes are part of the key. Listing happens by prefix and differs from ls in two ways: it is recursive like ls -R (returning all objects below), and empty directories are impossible — deleting every object under a path makes the path vanish from listings; the common convention is creating a zero-byte object as the empty-directory stand-in.
  • No links or locks; non-atomic rename: DFSs often have hard links, symbolic links, file locks and atomic rename; object stores don't. Rename means copy-to-new-key then delete-old-key; and renaming a “directory” means renaming every object one by one, since the directory name is part of the key.
  • Difference from KV stores (Chapter 4): KV stores optimize for small values (kilobytes) and frequent low-latency reads/writes; DFS and object stores for big objects (megabytes to gigabytes) with bigger, rarer reads. Object stores are shifting this boundary though (e.g. S3 Express One Zone with single-digit-ms latency).
  • Locality: a DFS like HDFS lets a task run on a machine holding a copy of the file — so the file never crosses the network, and if the task code is smaller than the data it reads, bandwidth is saved. Object stores usually keep storage and compute apart: more bandwidth is consumed (acceptable on today's fast networks), but CPU and memory scale independently of storage.

۳.۴. هماهنگ‌سازیِ job3.4. Job orchestration

قضیهٔ هماهنگ‌کنندهٔ کار اینه: مشخص می‌کنه هر وظیفه کجا و کی اجرا بشه، نتیجه‌ش کجاست و بعد از شکست چی لازمه. این با خودِ منطقِ جمع‌زدنِ فروش فرق داره.

مثال فنی: Task دوباره زمان‌بندی می‌شود

وضعیت اولیه: فرض کن از ۱۰۰ تا task، workerِ اجرای task ۳۷ خاموش می‌شه.

اجرای مرحله‌به‌مرحله: حالا scheduler task ۳۷ رو رو یه worker دیگه اجرا می‌کنه و خروجیِ attempt موفق رو می‌پذیره.

نتیجه و دلیل: کلِ job لازم نیست از صفر تکرار بشه، اگه ورودی و وابستگی‌های لازم برای همون task در دسترس باشن — غصه نخور.

The same OS analogy holds in orchestration: running a Unix job means someone must actually launch the awk, sort and uniq processes, carry data from one's output to the next one's input, allocate memory and guarantee fair execution. On one machine that is the kernel's job; in a distributed setting it is the job orchestrator's. A job-run request carries metadata: task count, each task's memory/CPU/disk, the job id, access credentials, parameters (like input and output), needed hardware (like GPUs) and the runnable code's location.

  • task executor: یه daemon مثل NodeManager تو YARN یا kubelet تو Kubernetes رو هر نود می‌شینه: taskها رو اجرا می‌کنه، heartbeat می‌فرسته تا زنده‌بودنش معلوم بشه، و وضعیتِ task و تخصیصِ منابعِ نود رو پیگیری می‌کنه. وقتی درخواستِ شروعِ task می‌رسه، کدِ job رو می‌گیره و فرمانِ اجرا رو می‌زنه. خیلی از executorها با سیستم‌عامل جداسازیِ امنیتی و عملکردی هم می‌دن (مثلاً cgroups تو YARN و Kubernetes) تا taskی نتونه بدونِ مجوز به داده برسه یا با مصرفِ بی‌رویه، taskهای دیگهٔ نود رو کند کنه.
  • resource manager: متادیتای هر نود رو نگه می‌داره: سخت‌افزارِ در دسترس (CPU و GPU و حافظه و دیسک)، وضعیتِ taskها، موقعیتِ شبکه‌ای و وضعیتِ نود — یعنی نمایِ سراسری از وضعیتِ فعلیِ خوشه. متمرکز بودنش هم می‌تونه گلوگاهِ مقیاس‌پذیری و در دسترس‌پذیری بشه؛ YARN وضعیت رو تو ZooKeeper و Kubernetes تو etcd می‌نویسه.
  • scheduler: معمولاً یه زیرسیستمِ متمرکز که درخواستِ شروع/توقف/وضعیتِ job رو می‌گیره — مثلاً «یه job با ۱۰ تا task و فلان imageِ Docker رو نودهایی با فلان نوعِ GPU». scheduler با ترکیبِ درخواست و وضعیتِ resource manager تصمیم می‌گیره هر task کجا اجرا بشه و executorها رو خبر می‌کنه. بعضی تصمیم‌ها به schedulerهای اختصاصیِ برنامه نیاز دارن (مثلاً scale کردنِ replicaهای خوندن وقتی تعدادِ کوئری از آستانه گذشت)؛ scheduler متمرکز و این‌ها با هم کار می‌کنن — YARN به اون‌ها ApplicationMaster و Kubernetes به اون‌ها operator می‌گه.
  • Task executor: a daemon like YARN's NodeManager or Kubernetes' kubelet sits on each node: it runs tasks, sends heartbeats to prove liveness, and tracks task state and the node's resource allocation. When a task-start request arrives it fetches the job code and fires the run command. Many executors also give OS-level security and performance isolation (e.g. cgroups in YARN and Kubernetes) so no task can reach data unauthorized or slow its node's other tasks by overconsuming.
  • Resource manager: keeps each node's metadata: available hardware (CPU, GPU, memory, disk), task states, network position and node health — a global view of the cluster's current state. Its centrality can become a scalability and availability bottleneck; YARN writes state to ZooKeeper and Kubernetes to etcd.
  • Scheduler: usually a centralized subsystem taking job start/stop/state requests — e.g. “a job with 10 tasks and such Docker image on nodes with such GPU type”. The scheduler combines the request with the resource manager's state to decide where each task runs and notifies the executors. Some decisions need application-specific schedulers (e.g. scaling read replicas when query counts pass a threshold); the centralized scheduler and these work together — YARN calls them ApplicationMasters, Kubernetes calls them operators.

۳.۵. تخصیص منابع: انصاف در برابر کارایی3.5. Resource allocation: fairness vs efficiency

زمان‌بند بینِ کارها منابع تقسیم می‌کنه. انصاف و زمانِ پایانِ یه کار و استفادهٔ کامل از خوشه ممکنه هم‌زمان به بهترین مقدار نرسن.

مثال فنی: دو job روی ۱۶۰ هسته

وضعیت اولیه: فرض کن دو تا job که هرکدوم ۱۰۰ تا task تک‌هسته‌ایِ هم‌زمان تو مرحلهٔ جاری می‌خوان.

اجرای مرحله‌به‌مرحله: حالا با تقسیم ۸۰/۸۰ هر دو مرحله منتظر دو موج‌ان؛ تخصیصِ متفاوت می‌تونه یه job رو زودتر تموم کنه و منابعش رو آزاد کنه.

نتیجه و دلیل: انصاف لحظه‌ای و کمینه کردن زمان پایان همیشه یکی نیستن؛ اندازهٔ مرحله و امکان preemption تو تصمیم اثر دارن — همینه.

The scheduler's job is genuinely hard: it must distribute the cluster's limited resources “optimally” among competing jobs, and these decisions inherently balance fairness against efficiency. See the book's puzzle: a 5-node cluster with 160 CPU cores total, and two job requests each wanting 100 cores. What to do?

  • می‌تونی ۸۰ تا task از هر job رو اجرا کنی و ۲۰ تای باقی‌موندهٔ هر کدوم رو با آزاد شدنِ taskهای قبلی شروع کنی.
  • می‌تونی همهٔ taskهای یکی رو اجرا کنی و job دوم فقط وقتی شروع بشه که ۱۰۰ تا هسته آزاد باشه — استراتژی‌ای که بهش gang scheduling می‌گن.
  • اگه درخواستِ دوم خیلی دیرتر برسه، scheduler اطلاعاتِ ناقص داره: باید حدس بزنه همهٔ ۱۰۰ تا هسته رو به job اول بده یا مقداری رو نگه داره برای jobی که شاید هرگز نیاد.
  • Run 80 tasks of each job and start each one's remaining 20 as earlier tasks free up.
  • Run all of one's tasks and start the second only when 100 cores are free — a strategy called gang scheduling.
  • If the second request arrives much later, the scheduler holds incomplete information: it must guess whether to give all 100 cores to the first job or hold some back for a job that may never come.

همین مثالِ ساده پر از معاوضهٔ دشواره. تو gang scheduling اگه تا آزاد شدنِ هم‌زمانِ ۱۰۰ تا هسته صبر کنی، نودها بیکار می‌شینن، استفاده از منابع پایین میاد، و اگه jobهای دیگه هم بخوان رزرو کنن ممکنه deadlock رخ بده. اگه هم بی‌تکلیف منتظرِ ۱۰۰ تا هسته بمونی، ممکنه jobهای دیگه هسته‌ها رو برباین و خوشه مدتِ خیلی طولانی ۱۰۰ تا هستهٔ آزاد نداشته باشه — یعنی starvation. راهِ سوم اینه که preemption کنی: بعضی taskهای job اول رو بکُشی تا جا برای job دوم باز بشه؛ ولی taskهای کشته‌شده بعداً باید دوباره اجرا بشن و باز هم کاراییِ خوشه می‌افته.

Even this simple example overflows with hard trade-offs. In gang scheduling, waiting for 100 simultaneously-free cores idles nodes, drops utilization, and if other jobs also want reservations a deadlock may strike. Waiting aimlessly for 100 free cores, other jobs may snatch cores and the cluster may lack 100 free cores for very long — starvation. The third way is preemption: kill some of the first job's tasks to make room for the second; but killed tasks must rerun later and cluster efficiency drops again.

This decision tree has four lanes: Decision (the questions), Gang Scheduling, Preemption and Heuristic Policies. Read from the middle start box of lane one: 5 Nodes, 160 Cores (“two jobs want 100 cores each”, “fairness vs efficiency”) — exactly the text's puzzle. The “schedule” arrow reaches question one: Must Tasks Run Together? (“gang requirement”). “Yes” drops you into Gang Scheduling (“hold cores until all free”, “idle cores, deadlock risk”); “no” moves to question two: New Job Higher Priority? (“priority of the request”).

“Yes” means the Preempt Low-Priority path (“killed work restarts later”, “spot VMs”) — killing low-priority work to make room; killed work reruns later, and in the real world these are the cheap spot instances. “No” reaches question three: Fair-Share or Quota Set? (“fair-share policy available”). “Yes” means DRF / Priority / Quota (“fairness over optimality”, “heuristic policy”); “no” lands the tree's main path at its destination: FIFO / Bin-Packing (“starvation risk if jobs queue”). A separate dashed branch, “the hard limit”, runs from the start box down to Optimal Is NP-Hard (“schedulers use heuristics instead”; “FIFO, DRF, quotas, bin packing”): at hundreds or millions of requests, finding the optimal allocation is NP-hard, so schedulers make “suboptimal but reasonable” heuristic calls. The cards tally the numbers (“The Dilemma in Numbers”: 80+80 with the rest later), each answer's price (“The Cost of Each Answer”: idleness, deadlock, starvation, resuming the killed), and why heuristics (“Why Schedulers Use Heuristics”: the centralized scheduler works with application-specific subschedulers — YARN's ApplicationMasters, Kubernetes' operators).

بذار ساده بگم: گردش‌کار، وابستگیِ کارها رو مشخص می‌کنه. DAG نموداری بدون چرخه‌ست که نشون می‌ده کدوم مرحله باید پیش از مرحلهٔ دیگه تموم بشه.

مثال فنی: وابستگی در DAG

وضعیت اولیه: فرض کن پاک‌سازی A ورودیِ مشترک گزارش‌های B و Cـه.

اجرای مرحله‌به‌مرحله: حالا بعد از موفقیت A، دو شاخهٔ B و C می‌تونن موازی اجرا بشن؛ اگه A شکست بخوره، خروجی نهاییِ وابسته منتشر نمی‌شه.

نتیجه و دلیل: DAG ترتیب وابستگی رو می‌گه، نه یه فهرستِ لزوماً سریالی از دستورها — حفظ کن.

In the Unix example, each command's output reached the next one — and friend, distributed processing follows the same pattern: one job's output becomes one or more other jobs' input. That's called a workflow, or a DAG (directed acyclic graph) of jobs.

«workflow» این‌جا یعنی چه؟What does “workflow” mean here?
تو فصل ۵ از موتورهای durable execution حرف زدیم: اجرای پایدارِ زنجیره‌ای از گام‌ها، معمولاً با فراخوانیِ RPC. تو پردازشِ دسته‌ای، «workflow» معنای دیگه‌ای داره: زنجیره‌ای از jobهای دسته‌ای که هر کدوم داده می‌خونن و داده می‌نویسن، ولی معمولاً به سرویسِ بیرونی RPC نمی‌زنن. موتورهای durable execution معمولاً دادهٔ کمتری به‌ازای هر درخواست پردازش می‌کنن — هرچند مرز تا حدی مبهمه.
In Chapter 5 we discussed durable execution engines: durable execution of a chain of steps, usually via RPC calls. In batch processing “workflow” means something else: a chain of batch jobs each reading and writing data, but usually never RPC-ing an outside service. Durable execution engines usually process less data per request — though the boundary is somewhat blurry.

سه تا دلیلِ رایج که jobها زنجیره می‌شن:

Three common reasons jobs chain:

  • اگه خروجیِ یه job ورودیِ چند تا job دیگه‌ست که تیم‌های مختلفی نگه‌داری‌شون می‌کنن، بهتره job اول خروجی‌ش رو جایی بنویسه که همه بتونن بخونن؛ jobهای مصرف‌کننده هر بار که داده به‌روز شد (یا با برنامهٔ خودشون) اجرا بشن.
  • گاهی می‌خوای داده رو بینِ ابزارهای پردازش جابه‌جا کنی: مثلاً یه jobِ Spark رو HDFS خروجی بده، یه اسکریپتِ پایتون یه کوئریِ Trino رو رو همون فایل‌ها تریگر کنه و نتیجه به S3 بره.
  • گاهی خودِ pipeline چند تا مرحله می‌خواد: اگه مرحله‌ای داده رو با یه کلید shard کنه و مرحلهٔ بعدی به shard با کلیدِ دیگه‌ای نیاز داشته باشه، مرحلهٔ اول خروجی رو به همون شکلی آماده می‌کنه که مرحلهٔ دوم می‌خواد.
  • If one job's output feeds several jobs maintained by different teams, the first job should write its output where all can read it; consuming jobs run whenever data refreshes (or on their own schedule).
  • Sometimes you want to move data between processing tools: e.g. a Spark job outputs on HDFS, a Python script triggers a Trino query over the same files, and the result lands on S3.
  • Sometimes the pipeline itself needs stages: if one stage shards data by one key and the next needs sharding by another, the first stage prepares output exactly as the second wants it.

نکتهٔ مهندسیِ جالب: تو مثالِ Unix، لوله فقط یه بافرِ کوچیکِ تو حافظه‌ست و چیزی فایل نمی‌شه؛ اگه بافر پر بشه، تولیدکننده صبر می‌کنه تا مصرف‌کننده بخونه — یه جور backpressure. Spark و Flink هم مدلِ مشابهی دارن: خروجیِ یه task مستقیم به task بعدی می‌ره (اگه رو ماشین‌های مختلف‌ان، از شبکه). ولی معمول‌تر اینه که jobها با نوشتنِ میانی تو DFS/object store از هم جدا بشن: این جداسازیِ زمانی می‌ده و اگه jobی چند تا ورودی داشته باشه، workflow scheduler صبر می‌کنه تا همهٔ jobهای تولیدکننده با موفقیت تموم بشن. و توجه کن: schedulerهای داخلیِ YARN یا Spark رو job به job کار می‌کنن و کلِ workflow رو نمی‌فهمن؛ برای وابستگی‌ها، workflow schedulerهایی مثل Airflow و Dagster و Prefect ساخته شدن. workflowهای ۵۰ تا ۱۰۰ jobی تو pipelineهای داده عادی‌ان و تو سازمانِ بزرگ، تیم‌های زیادی رو خروجیِ هم job می‌زنن — پس ابزارِ مدیریتی واقعاً لازمه.

The interesting engineering note: in the Unix example the pipe is just a small in-memory buffer with nothing filed; when the buffer fills, the producer waits for the consumer to read — a kind of backpressure. Spark and Flink have a similar model: one task's output goes straight to the next task (over the network if on different machines). But more common is separating jobs by writing intermediate output to DFS/object store: this gives time-decoupling, and when a job has several inputs the workflow scheduler waits for all producing jobs to succeed. And note: YARN's or Spark's internal schedulers work job-by-job and never grasp the whole workflow; for dependencies, workflow schedulers like Airflow, Dagster and Prefect were built. 50-to-100-job workflows are ordinary in data pipelines, and in a big organization many teams run jobs on each other's outputs — so real management tooling is needed.

۳.۷. تحملِ خرابی3.7. Fault tolerance

اگه ورودی تغییرناپذیر باشه و خروجیِ تلاشِ ناقص جدا بمونه، می‌شه وظیفهٔ شکست‌خورده رو دوباره اجرا کرد. مدیریتِ خروجیِ میانی تعیین می‌کنه چه مقدار کار تکرار بشه.

مثال فنی: خروجی attempt ناموفق را منتشر نکن

وضعیت اولیه: فرض کن task قسمتی از فایل رو نوشته و پیش از پایان crash کرده.

اجرای مرحله‌به‌مرحله: حالا خروجی تو مسیر موقتِ attempt می‌مونه؛ سازوکار commit فقط خروجی موفق رو تو نسخهٔ job وارد می‌کنه.

نتیجه و دلیل: retry نباید فایل ناقص و فایل کامل رو با هم به‌عنوان خروجی معتبر نشون بده؛ I/O مستقیم به مقصد بیرونی سخت‌تره — قول می‌دم به کارت میاد.

Batch jobs run long; a long job with many parallel tasks will almost surely meet at least one task failure on its way — hardware faults (especially on commodity hardware) or network cuts. But a more common cause exists: the scheduler deliberately preempts (kills) the task. This pays off with priority levels: cheap low-priority tasks run whenever spare capacity exists, at the risk of being killed the moment a higher-priority job arrives. These cheap VMs are called spot instances on EC2, spot VMs on Azure and preemptible instances on Google Cloud. Since batch jobs are rarely urgent, using this cheap capacity is economical (and raises cluster use); but it means preemption happens far more than hardware failure.

چون jobهای دسته‌ای خروجی رو هر بار از صفر بازسازی می‌کنن، مدیریتِ خرابیِ task ساده‌تر از سیستم‌های آنلاینه: خروجیِ ناقصِ اجرای شکست‌خورده رو حذف می‌کنی و task رو دوباره رو یه ماشینِ دیگه زمان‌بندی می‌کنی. ولی اجرای دوبارهٔ کلِ job به‌خاطرِ یه task شکسته، اسرافه؛ پس MapReduce و جانشینانش اجرای taskهای موازی رو از هم مستقل نگه می‌دارن تا بشه تو سطحِ تک‌task بازتلاش کرد.

Because batch jobs rebuild output from scratch every time, task-failure handling is simpler than in online systems: delete the failed run's partial output and reschedule the task on another machine. But rerunning the whole job for one broken task is wasteful; so MapReduce and its successors keep parallel tasks' execution independent, enabling single-task-level retries.

کار وقتی سخت می‌شه که خروجیِ یه task ورودیِ task دیگه بشه (تو workflow). سه تا استراتژیِ معروف برای دادهٔ intermediate:

Things get hard when one task's output feeds another's input (in a workflow). Three famous strategies for intermediate data:

  • MapReduce: همهٔ دادهٔ میانی رو تو DFS می‌نویسه و صبر می‌کنه تا نوشتنِ task کامل بشه؛ حتی تو محیطِ پر از preemption کار می‌کنه، ولی یعنی نوشتن‌های خیلی زیاد تو DFS و کاراییِ پایین.
  • Spark: دادهٔ میانی رو تو حافظه نگه می‌داره (و اگه لازم شد به دیسکِ محلی spill می‌کنه) و فقط نتیجهٔ نهایی رو به DFS می‌نویسه؛ چون می‌دونه داده چطور محاسبه شده (lineage)، اگه از دست رفت دوباره محاسبه‌ش می‌کنه.
  • Flink: رویکردِ checkpoint: دوره‌ای از وضعیتِ taskها اسنپ‌شات می‌گیره و به ذخیره‌سازیِ پایدار می‌نویسه، به‌جای مادی‌سازیِ هر رکوردِ میانی.
  • MapReduce: writes all intermediate data to DFS and waits for the task's write to complete; works even in preemption-heavy settings, but means enormous DFS writes and low performance.
  • Spark: keeps intermediate data in memory (spilling to local disk when needed) and writes only the final result to DFS; knowing how data was computed (lineage), it recomputes on loss.
  • Flink: the checkpoint approach: periodically snapshots task state to durable storage instead of materializing every intermediate record.

قانون اولِ این بخش: مدل پردازش مشخص می‌کنه منطق برنامه چطور به وظیفه‌های اجرایی شکسته بشه. MapReduce الگوی محدودتری داره و dataflow زنجیرهٔ متنوع‌تری از تبدیل‌ها رو بیان می‌کنه.

مثال فنی: یک محاسبه، چند مدل اجرا

وضعیت اولیه: فرض کن ورودی فروش باید فیلتر بشه، با کالا join بخوره و بر دسته تجمیع بشه.

اجرای مرحله‌به‌مرحله: حالا می‌شه اون رو به jobهای MapReduce یا DAG عملگرها یا SQL رو موتور توزیع‌شده بیان کرد.

نتیجه و دلیل: اختلاف تو کنترل و بهینه‌سازی اجراست؛ برای مقایسه باید همون semanticsِ join و null و نوع عدد حفظ بشن — نقطه.

So far you've seen how jobs get scheduled and run; now comes how frameworks actually process data. Two common models: MapReduce and dataflow engines. Dataflow has in practice replaced MapReduce — but you still need to understand MapReduce, since it shaped many modern frameworks. Both models opened over time to multiple programming models: low-level programming APIs, relational query languages and DataFrame APIs.

۴.۱. MapReduce4.1. MapReduce

تو MapReduce، نگاشت برای هر ورودی جفتِ کلید–مقدار می‌سازه، جابه‌جایی داده کلیدهای یکسان رو جمع می‌کنه و کاهش نتیجهٔ هر کلید رو حساب می‌کنه.

مثال فنی: Map، shuffle، reduce

وضعیت اولیه: فرض کن متن‌های red blue و red ورودی‌ان.

اجرای مرحله‌به‌مرحله: حالا map جفت‌های (red,1),(blue,1),(red,1) رو می‌ده؛ shuffle redها رو کنار هم می‌فرسته؛ reduce جمع red=2,blue=1 رو می‌سازه.

نتیجه و دلیل: shuffle تصادفی نیست؛ گروه‌بندیِ کلید تعیین می‌کنه همهٔ مقدارهای یه کلید به محاسبهٔ مشترک برسن — قابش کن.

MapReduce's processing pattern will look familiar — it's basically Section 2's log analysis in four steps:

  1. خوندنِ ورودی و شکستن به رکورد: تو مثالِ لاگ، هر رکورد یه خطه (جداکنندهٔ رکورد \n). تو Hadoop، ورودی تو HDFS یا object store مثل S3ـه و قالب‌های فایلِ مختلفی داریم: مثل Apache Parquet (قالبِ ستونی) یا Apache Avro (قالبِ سطری).
  2. فراخوانیِ تابعِ mapper برای استخراجِ key و value از هر رکوردِ ورودی. تو مثالِ ما mapper همون awk '{print $7}'ـه که URL رو به‌عنوان key برمی‌داره و value خالی می‌مونه.
  3. مرتب‌سازیِ همهٔ جفت‌های (key, value) بر اساسِ key. تو مثال، همون دستورِ اولِ sort.
  4. فراخوانیِ reducer رو جفت‌های مرتب‌شده. چون رکوردهای هم‌کلید با مرتب‌سازی مجاور شدن، ترکیبِ مقدارشون بدونِ نگه‌داشتنِ state زیاد تو حافظه ممکنه. تو مثال، reducer همون uniq -cـه که تعدادِ رکوردهای مجاورِ هم‌کلید رو می‌شماره.
  1. Read input and break into records: in the log example each record is one line (record separator \n). In Hadoop, input sits in HDFS or an object store like S3, with various file formats: e.g. Apache Parquet (columnar) or Apache Avro (row-based).
  2. Call the mapper to extract key and value from each input record. In our example the mapper is awk '{print $7}', taking the URL as key with an empty value.
  3. Sort all (key, value) pairs by key. In the example, the first sort command.
  4. Call the reducer on the sorted pairs. Since same-key records became adjacent through sorting, combining their values needs little in-memory state. In the example the reducer is uniq -c, counting adjacent same-key records.

این چهار تا گام رو می‌شه تو یه jobِ MapReduce انجام داد. گام‌های ۲ (map) و ۴ (reduce) جایی‌ان که کدِ سفارشیِ خودت رو می‌نویسی؛ گامِ ۱ با parser ورودی حله؛ و گامِ ۳ یعنی sort تو MapReduce ضمنیـه — لازم نیست بنویسی‌ش، چون خروجیِ mapper همیشه قبل از رسیدن به reducer مرتب می‌شه.

These four steps fit in one MapReduce job. Steps 2 (map) and 4 (reduce) are where you write custom code; step 1 is solved by the input parser; and step 3, sorting, is implicit in MapReduce — you never write it, because mapper output is always sorted before reaching the reducer.

  • Mapper: برای هر رکوردِ ورودی دقیقاً یه بار صدا زده می‌شه و کارش استخراجِ key و valueـه؛ می‌تونه به‌ازای هر ورودی هر تعداد جفت (حتی صفر) تولید کنه. هیچ stateای از رکوردِ قبلی نگه نمی‌داره — هر رکورد مستقل پردازش می‌شه — و mapperهای زیادی می‌تونن موازی رو بخش‌های مختلفِ ورودی اجرا بشن.
  • Reducer: framework جفت‌های mapperها رو جمع می‌کنه، همهٔ مقدارهای یه key رو کنارِ هم می‌آره و reducer رو با یه iterator رو اون مجموعه صدا می‌زنه. reducer می‌تونه رکوردِ خروجی بسازه (مثل تعدادِ ظهورِ هر URL). reducerهای کلیدهای مختلف هم موازی اجرا می‌شن.
  • Mapper: called exactly once per input record, extracting key and value; it may emit any number of pairs (even zero) per input. It keeps no state from the previous record — each record is processed independently — and many mappers can run in parallel over different input parts.
  • Reducer: the framework collects the mappers' pairs, brings all values of one key together and calls the reducer with an iterator over that set. The reducer may build output records (like each URL's occurrence count). Reducers of different keys run in parallel too.

تو مثالِ لاگ، دستورِ دومِ sort برای رتبه‌بندی بود. تو MapReduce اگه به مرحلهٔ مرتب‌سازیِ دوم نیاز داشته باشی، یه jobِ MapReduce دوم می‌نویسی و خروجیِ job اول ورودی‌ش می‌شه. از همین زاویه به نقش‌ها نگاه کن: mapper داده رو برای مرتب‌سازی آماده می‌کنه و reducer دادهٔ مرتب‌شده رو پردازش می‌کنه.

In the log example the second sort was for ranking. In MapReduce, needing a second sort stage means writing a second MapReduce job with the first job's output as its input. Roles from this angle: the mapper prepares data for sorting, and the reducer processes sorted data.

ریشه در برنامه‌نویسیِ تابعیRoots in functional programming
اگهچه MapReduce برای پردازشِ دسته‌ای به کار می‌ره، مدلِ برنامه‌نویسی‌ش از برنامه‌نویسیِ تابعی میاد: لیسپ map و reduce (یا fold) رو به‌عنوانِ توابعِ مرتبه‌بالا رو لیست‌ها معرفی کرد. اصلِ «پرهیز از state تغییرپذیر» دقیقاً همون چیزیه که اجرای موازی رو ممکن می‌کنه: چون هر فراخوانیِ mapper/reducer فقط به داده‌ای که framework صریحاً به تابع می‌ده وابسته‌ست، framework آزاده فراخوانی‌های مستقل رو رو نودهای مختلف موازی اجرا کنه — و اگه taskی شکست بخوره، همون mapper/reducer رو با همون ورودی دوباره رو یه نودِ دیگه صدا بزنه.
Though MapReduce serves batch processing, its programming model comes from functional programming: Lisp introduced map and reduce (or fold) as higher-order list functions. The “avoid mutable state” principle is exactly what enables parallel execution: since each mapper/reducer call depends only on data the framework explicitly passes in, the framework is free to run independent calls on different nodes — and if a task fails, to recall the same mapper/reducer with the same input on another node.
زحمت و کندیِ MapReduceMapReduce's toil and slowness
پیاده‌سازیِ job پیچیده با API خامِ MapReduce واقعاً طاقت‌فرساست — مثلاً هر الگوریتمِ join رو باید از صفر بنویسی. MapReduce در برابرِ پردازنده‌های مدرن کُند هم هست؛ یه دلیلش I/O فایلی‌شه که pipelining رو ناممکن می‌کنه: نمی‌شه خروجی رو تو job پایین‌دستی پردازش کرد قبل از این‌که job بالادستی تموم بشه.
Implementing a complex job with raw MapReduce API is truly grueling — e.g. every join algorithm must be written from scratch. MapReduce is also slow next to modern processors; one reason is its file I/O, which makes pipelining impossible: output cannot be processed in the downstream job before the upstream job finishes.

مثال فنی برای خواندنِ نمودار: Map، shuffle، reduce

وضعیت اولیه: فرض کن متن‌های red blue و red ورودی‌ان.

اجرای مرحله‌به‌مرحله: حالا map جفت‌های (red,1),(blue,1),(red,1) رو می‌ده؛ shuffle redها رو کنار هم می‌فرسته؛ reduce جمع red=2,blue=1 رو می‌سازه.

نتیجه و دلیل: shuffle تصادفی نیست؛ گروه‌بندیِ کلید تعیین می‌کنه همهٔ مقدارهای یه کلید به محاسبهٔ مشترک برسن — قابش کن.

این dataflow پنج تا ستون داره: Input Shards، Map Tasks، Map Output، Shuffle + Reduce و Output Dataset — همون شکلِ ۱۱-۱ کتاب با سه تا mapper و سه تا reducer. از راست شروع کن: سه تا جعبهٔ Shard m1 و Shard m2 و Shard m3 با زیرنویسِ HDFS file/object و تگِ input dataset — یعنی ورودی از قبل shard شده. فلش‌های «m1 records» و «m2 records» و «m3 records» با توضیحِ «record by record» به سه تا Map Task می‌رسن (زیرنویسِ هر کدوم: emits (key,value)، تگِ one per shard).

قلبِ ماجرا: فلش‌های «key-value» با توضیحِ «hash(key) routing» از هر mapper به یه جعبهٔ Sorted Runs می‌رن: m1 Sorted Runs با زیرنویسِ m1r1 m1r2 m1r3 و تگِ local disk (و به همین ترتیب m2 و m3). یعنی هر mapper به‌ازای هر reducer یه فایلِ مرتبِ جدا رو دیسکِ محلی می‌نویسه: فایلِ m1r2 همون فایلیه که mapper ۱ برای reducer ۲ ساخته. همین‌جاست که مرتب‌سازیِ تو هر فایل هم انجام می‌شه — با همون تکنیکِ log-structured: جفت‌ها تو یه ساختارِ مرتبِ تو حافظه جمع می‌شن، به‌صورتِ segment مرتب نوشته می‌شن، و segmentهای کوچیک به‌مرور ادغام می‌شن.

بعد فلش‌های shuffle copy رو دنبال کن: «m1r2» و «m2r2» و «m3r2» هر سه به Reduce Task 2 می‌رن؛ و «m1r1» و «m3r3» (با توضیحِ sorted run) به reducer ۱ و ۳. هر reducer وقتی سهمش رو از همهٔ mapperها گرفت، فایل‌ها رو با حفظِ ترتیبِ مرتب، سبکِ mergesort ادغام می‌کنه — به همین دلیل زیرنویسِ reducerها «mergesort shares» و تگشون «group by key»ـه: رکوردهای هم‌کلید حالا مجاورن، حتی اگه از mapperهای مختلف اومده باشن.

و خروجی: فلش‌های «sorted file» با توضیحِ «one file per task» به سه تا جعبهٔ Output r1 و r2 و r3 (زیرنویس: sorted records، تگِ output shard) — این سه تا فایل، shardهای dataset خروجی می‌شن و به DFS/object store برمی‌گردن.

کارت‌ها رو هم بخون: «Shuffle Is Not Random» می‌گه hash(key) هر رکورد رو دقیقاً به یه reducer می‌فرسته و هر mapper یه فایلِ مرتب به‌ازای هر reducer می‌نویسه (m1r1 ... m3r3)؛ «Sort Is the Foundation» می‌گه مرتب‌سازی پایهٔ grouping و joinـه و reducer یه بار به‌ازای هر key با یه iterator رو مقدارش اجرا می‌شه؛ «Job Sizing» می‌گه تعدادِ map taskها = تعدادِ shardهای ورودی، ولی تعدادِ reduce taskها رو نویسندهٔ job تعیین می‌کنه نه اندازهٔ ورودی؛ و «Modern Shuffle Engines» اشاره می‌کنه موتورهای جدید دادهٔ shuffle رو تو حافظه نگه می‌دارن یا مرتب‌سازی رو به یه سرویسِ external sort می‌سپرن و دادهٔ shuffleشده رو replicate می‌کنن تا گم شدنِ یه نود job رو متوقف نکنه.

This dataflow has five columns — Input Shards, Map Tasks, Map Output, Shuffle + Reduce and Output Dataset — the book's Figure 11-1 with three mappers and three reducers. Three boxes — Shard m1, m2, m3 (“HDFS file/object”, “input dataset”) — i.e. pre-sharded input. The “m1 records” / “m2 records” / “m3 records” arrows (“record by record”) reach three Map Tasks (each “emits (key,value)”, “one per shard”).

Now the heart: “key-value” arrows (“hash(key) routing”) run from each mapper to a Sorted Runs box: m1 Sorted Runs (“m1r1 m1r2 m1r3”, “local disk”), and likewise m2, m3. Each mapper writes one separate sorted file per reducer on local disk: file m1r2 is what mapper 1 built for reducer 2. In-file sorting happens here too — with the same log-structured technique: pairs gather in an in-memory sorted structure, spill as sorted segments, and small segments gradually merge.

Then the shuffle copy arrows: m1r2, m2r2 and m3r2 all reach Reduce Task 2; m1r1 and m3r3 (“sorted run”) reach reducers 1 and 3. Each reducer, having collected its share from every mapper, merges the files mergesort-style keeping sorted order — hence the reducers' “mergesort shares” caption and “group by key” tag: same-key records are now adjacent even from different mappers. Output: “sorted file” arrows (“one file per task”) to Output r1, r2, r3 (“sorted records”, “output shard”) — the output dataset's shards, returning to DFS/object store. The cards add: “Shuffle Is Not Random” (hash(key) sends each record to exactly one reducer; each mapper writes one sorted file per reducer); “Sort Is the Foundation” (sorting underpins grouping and joins; the reducer runs once per key with an iterator over its values); “Job Sizing” (map-task count = input-shard count, but reduce-task count is the job author's call, not the input's size); and “Modern Shuffle Engines” (new engines keep shuffle data in memory or hand sorting to a dedicated external-sort service, replicating shuffled data so one lost node never stops the job).

۴.۲. موتورهای dataflow4.2. Dataflow engines

نکته‌ش اینجاست: موتور dataflow کلِ زنجیرهٔ تبدیل رو می‌بینه و می‌تونه مرحله‌ها رو ترکیب کنه یا دادهٔ میانی رو مناسب‌تر نگه داره. همهٔ مرحله‌ها الزاماً نباید به چند تا job مستقل شکسته بشن.

مثال فنی: ادغام عملگرهای متوالی

وضعیت اولیه: فرض کن مرحله‌های filter → map → groupBy رو داریم.

اجرای مرحله‌به‌مرحله: حالا موتور می‌تونه filter و map رو تو همون task اجرا کنه و پیش از groupBy داده رو shuffle کنه.

نتیجه و دلیل: حذف مرزِ غیرضروریِ job، فایل میانی و راه‌اندازی رو کم می‌کنه؛ مرحلهٔ نیازمند توزیعِ دوباره هنوز شبکه می‌خواد — همینو می‌خواستیم.

To fix MapReduce's problems, several new execution engines were built, most famously Spark and Flink. Their designs differ but share one thing: they see the whole workflow as one job, not a set of independent subjobs. Since they explicitly model data flow across processing stages, they are called dataflow engines. Like MapReduce they have a low-level API calling user functions record by record, but also higher-level operators like join and group by; they parallelize by sharding input and carry each task's output over the network to the next task's input. Unlike MapReduce, operators needn't alternate in a rigid map/reduce pattern and compose more flexibly. The style's roots are the Dryad and Nephele research systems.

شش تا مزیتِ این مدل نسبت به MapReduce:

Six advantages of this model over MapReduce:

  • کارِ گرونی مثل مرتب‌سازی فقط جایی انجام می‌شه که واقعاً لازمه، نه همیشه بینِ هر map و reduce.
  • اگه چند تا operator پشتِ سرِ هم shardingِ dataset رو عوض نکنن (مثل map یا filter)، می‌تونن تو یه task ادغام (fuse) بشن و هزینهٔ کپیِ داده کم بشه.
  • چون همهٔ joinها و وابستگی‌های داده صریحاً اعلام می‌شن، scheduler تصویرِ کلی داره و می‌تونه locality رو بهینه کنه: مثلاً task مصرف‌کننده رو رو همون ماشینِ تولیدکننده بذاره تا داده از بافرِ حافظهٔ مشترک رد بشه، نه از شبکه.
  • معمولاً state میانیِ بینِ operatorها رو می‌شه تو حافظه یا دیسکِ محلی نگه داشت — I/O خیلی کمتر از نوشتن تو DFS/object store (که باید چند نسخه و رو چند تا دیسک نوشته بشه). MapReduce این بهینه‌سازی رو برای خروجیِ mapper داشت؛ dataflow اون رو به همهٔ stateهای میانی تعمیم می‌ده.
  • operatorها می‌تونن به‌محضِ آماده شدنِ ورودی‌شون شروع کنن؛ نیازی نیست کلِ مرحلهٔ قبل تموم بشه.
  • پروسه‌های موجود برای اجرای operatorهای جدید دوباره استفاده می‌شن و هزینهٔ راه‌اندازی کم می‌شه (MapReduce برای هر task یه JVM تازه بالا می‌آره).
  • Expensive work like sorting happens only where truly needed, not always between every map and reduce.
  • Consecutive operators that don't change the dataset's sharding (like map or filter) can fuse into one task, cutting data-copy costs.
  • Since all joins and data dependencies are declared explicitly, the scheduler sees the whole picture and can optimize locality: e.g. placing the consuming task on the producer's machine so data passes through shared memory buffers, not the network.
  • Intermediate state between operators can usually live in memory or local disk — far less I/O than writing to DFS/object store (which must be written several times over several disks). MapReduce had this optimization for mapper output; dataflow generalizes it to all intermediate state.
  • Operators can start as soon as their input is ready; no need for the whole previous stage to finish.
  • Existing processes are reused for running new operators, cutting startup costs (MapReduce boots a fresh JVM per task).

با dataflow می‌شه همون محاسبه‌های workflowهای MapReduce رو نوشت و معمولاً به‌خاطرِ همین بهینه‌سازی‌ها قابلِ ملاحظه‌ای سریع‌تر اجرا می‌شن.

Dataflow can express the same computations as MapReduce workflows, and usually runs them observably faster thanks to these optimizations.

بندِ اول با عنوانِ «① MapReduce — every stage finishes by writing files to the distributed filesystem» شروع می‌شه: سه تا نوارِ سبزِ map 1 و map 2 و map 3 (هر کدوم «read shard → map()») موازی می‌دَوَن، بعد یه stage barrier میاد، بعد نوارِ خاکستریِ DFS write با توضیحِ «write intermediate to DFS (replicated, durable)» — و بعد دوباره barrier، بعد نوارهای reduce 1/2/3، barrier دیگه، و نوارِ output با «write output». جمعِ بندِ اول زیرش نوشته: «file-based I/O between every stage · no pipelining · new JVM per task · sort happens between every map and reduce».

بندِ دوم «② Dataflow engine (Spark / Flink) — one job, one DAG: operators start as soon as their input is ready»ـه: نوارِ map + filter با توضیحِ «map+filter fused into one task» (یادته فیوژنِ operatorها)، map 2 («read shard → map()»)، و بعد نوارهای reduce 1 و reduce 2 که کنارِ reduce 1 نوشته «reduce 1 · starts as soon as input is ready» — یعنی barrier نیست؛ هر کدوم به‌محضِ آماده شدنِ ورودی شروع می‌شن. نوارِ intermediate با توضیحِ «intermediate state: memory / local disk» نشون می‌ده دادهٔ میانی به DFS نمی‌ره؛ و فقط نوارِ پایانیِ output با «final output → DFS / object store» نوشتنِ پایدار داره. جمعِ این بند: «sort only where needed · whole DAG visible to the scheduler → data locality · reuse worker processes · lineage recompute / checkpoints instead of DFS writes».

درسِ نمودار رو این‌جوری نگاه کن: تو بندِ اول، فاصلهٔ بینِ نوارهای سبز رو نوارهای خاکستری و barrierها پر کردن — یعنی وقتِ مصرف‌شده برای I/O فایلی و انتظار؛ تو بندِ دوم، نوارهای سبز رو هم سوارن و فقط یه نوشتنِ پایدارِ نهایی هست. همون تفاوتِ «pipelining نداریم» با «pipelining داریم» — همین.

This shared-timeline diagram — “Where the Time Goes — MapReduce vs a Dataflow Engine” (“one shared time axis · green bars are compute tasks · grey bars are durable writes to the filesystem”) — has its color key on top: compute task (green bar), durable write to DFS / object store (grey bar) and stage barrier (barrier line), with time running right (“time →”, “not to scale”). Lane one, “① MapReduce — every stage finishes by writing files to the distributed filesystem”: three green map 1/2/3 bars (“read shard → map()”) run in parallel, then a stage barrier, then the grey DFS write (“write intermediate to DFS (replicated, durable)”) — then another barrier, the reduce 1/2/3 bars, another barrier, and the output bar (“write output”). Lane one's total reads: “file-based I/O between every stage · no pipelining · new JVM per task · sort happens between every map and reduce”.

Lane two, “② Dataflow engine (Spark / Flink) — one job, one DAG: operators start as soon as their input is ready”: a map + filter bar (“map+filter fused into one task” — operator fusion), map 2 (“read shard → map()”), then reduce 1 and reduce 2 — reduce 1 tagged “starts as soon as input is ready”: no barriers, each starts the moment its input exists. The intermediate bar (“intermediate state: memory / local disk”) shows intermediate data skipping DFS; only the final output bar (“final output → DFS / object store”) writes durably. See the lesson with your eyes: in lane one the gaps between green bars are filled with grey bars and barriers — time spent on file I/O and waiting; in lane two green bars overlap with a single durable write at the end. That is “no pipelining” vs “pipelining”.

۴.۳. Shuffle4.3. Shuffle

کارِ Shuffle اینه: داده دوباره بینِ وظیفه‌ها توزیع می‌شه تا رکوردهای مرتبط کنار هم قرار بگیرن. این جابه‌جایی معمولاً شبکه و مرتب‌سازی و گاهی دیسک رو درگیر می‌کنه.

مثال فنی: Shuffle بر کلید مشتری

وضعیت اولیه: فرض کن سفارش‌های مشتری ۱۷ تو چند تا فایل و چند تا worker پراکنده‌ان.

اجرای مرحله‌به‌مرحله: حالا partitioner همهٔ جفت‌های کلید ۱۷ رو به reducer همون کلید می‌فرسته؛ داده ممکنه رو شبکه منتقل و sort بشه.

نتیجه و دلیل: تمرکزِ یه کلید برای تجمیع لازمه؛ مشتری خیلی بزرگ می‌تونه reducer داغ و زمان پایان طولانی بسازه — این دام معروفه.

Like you've seen, both the Unix example and MapReduce are built on sorting. Batch processors must sort petabyte datasets — data fitting no single machine — so they need a distributed sort whose input and output are both sharded. That algorithm is called shuffle.

shuffle تصادفی نیست!Shuffle is not random!
وقتی دسته‌کارت رو «shuffle» می‌کنی، ترتیبِ تصادفی درمیاد. ولی shuffle این‌جا دقیقاً برعکسه: خروجیِ مرتب می‌ده، بدونِ هیچ تصادفی. این الگوریتمِ بنیادیِ پردازنده‌های دسته‌ایه و برای join و تجمیع به کار می‌ره: MapReduce و Spark و Flink و Daft و Dataflow و BigQuery همگی shuffleهای مقیاس‌پذیر و کارآمد پیاده کردن تا datasetهای بزرگ رو اداره کنن.
When you shuffle playing cards, random order comes out. But shuffle here is exactly the opposite: it yields sorted output, with zero randomness. This fundamental batch-processor algorithm serves joins and aggregation: MapReduce, Spark, Flink, Daft, Dataflow and BigQuery all implement scalable, efficient shuffles to handle big datasets.

مکانیزمِ هادوپی (نمودار ۶ و شکلِ ۱۱-۱) رو دیدیم: هر mapper به‌ازای هر reducer یه فایلِ مرتب می‌نویسه، مسیریابی با hash(key) انجام می‌شه و reducer سهمش رو با mergesort ادغام می‌کنه. ولی موتورهای dataflow و warehouseهای ابری پیشرفته‌ترن: سیستم‌هایی مثل BigQuery الگوریتمِ shuffle رو بهینه کردن تا داده رو تو حافظه نگه دارن، یا مرتب‌سازی رو به سرویسِ external sort اختصاصی بسپرن؛ چنین سرویس‌هایی shuffle رو سریع‌تر می‌کنن و دادهٔ shuffleشده رو replicate می‌کنن تا از دست رفتنِ یه نود کلِ job رو متوقف نکنه.

We saw the Hadoop mechanism (Diagram 6, Figure 11-1): each mapper writes one sorted file per reducer, routing by hash(key), and the reducer merges its share mergesort-style. But dataflow engines and cloud warehouses are more advanced: systems like BigQuery optimized the shuffle algorithm to hold data in memory, or hand sorting to a dedicated external sort service; such services speed shuffle and replicate shuffled data so losing one node never stops the whole job.

۴.۴. Join و Grouping4.4. Joins and grouping

داستان از این قراره: Join رکوردهای مرتبطِ دو مجموعه رو ترکیب می‌کنه و grouping رکوردهای یه مجموعه رو بر اساس کلید کنار هم می‌ذاره. روش اجرا به اندازهٔ داده و نحوهٔ توزیع و ترتیب اون بستگی داره.

مثال فنی: دو راهِ join

وضعیت اولیه: تصور کن فروش یه میلیارد ردیف داره و جدول دسته‌بندی محصول فقط 5 MBـه.

اجرای مرحله‌به‌مرحله: حالا جدول کوچیک رو می‌شه به workerها broadcast کرد؛ اگه هر دو طرف بزرگ باشن، تقسیم و sort-merge رو کلید مطرح می‌شه.

نتیجه و دلیل: اندازه و توزیع کلید تعیین‌کننده‌ان؛ broadcast جدول بزرگ می‌تونه حافظهٔ همهٔ workerها رو پر کنه — عددها خودشون حرف می‌زنن.

Now see how sorted data simplifies distributed joins and aggregation. The classic example: on the left, the logged-in users' event log (called activity events or clickstream) and on the right, the user database. Think of this as part of a star schema: the event log is the fact table, the user database one dimension. To analyze with user info included (e.g. whether certain pages are more popular among younger or older users — via the birth-date field), you must join the two tables. Assuming both are big enough to shard, how?

جواب تو همون خاصیتِ shuffleـه: همهٔ جفت‌های هم‌کلید رو، از هر shardی که اومده باشن، به یه reducer می‌رسونه. پس شناسهٔ کاربر رو کلید می‌گیریم: یه mapper رو رویدادها می‌ره و URLهای بازدیدشده رو با کلیدِ user_id منتشر می‌کنه؛ mapper دیگه‌ای رو پایگاه دادهٔ کاربران سطر به سطر می‌ره، شناسهٔ کاربر رو به‌عنوانِ key و تاریخِ تولد رو به‌عنوانِ value استخراج می‌کنه. shuffle تضمین می‌کنه reducer هم تاریخِ تولدِ یه کاربرِ خاص و هم همهٔ رویدادهاش رو هم‌زمان داشته باشه. MapReduce حتی می‌تونه رکوردها رو طوری مرتب کنه که reducer همیشه اول رکوردِ پایگاه دادهٔ کاربر رو ببینه و بعد رویدادها رو به ترتیبِ timestamp — تکنیکی که بهش secondary sort می‌گن.

The answer is that same shuffle property: it delivers every same-key pair, from whichever shard, to one reducer. So take user id as key: one mapper scans the events and publishes visited URLs keyed by user_id; another mapper scans the user database row by row, extracting user id as key and birth date as value. Shuffle guarantees the reducer holds one user's birth date and all their events at once. MapReduce can even order records so the reducer always sees the user-database record first, then events in timestamp order — a technique called secondary sort.

حالا منطقِ join ساده‌ست: اولین مقدار باید تاریخِ تولد باشه که reducer تو یه متغیرِ محلی نگه می‌داره؛ بعد رو رویدادهای همون user_id پیمایش می‌کنه و هر URL بازدیدشده رو به‌همراهِ تاریخِ تولدِ بیننده خروجی می‌ده. چون reducer همهٔ رکوردهای یه user_id رو یه‌جا پردازش می‌کنه، تو هر لحظه فقط یه رکوردِ کاربر تو حافظه لازمه و هرگز نیازی به درخواستِ شبکه‌ای نیست. اسمِ این الگوریتم sort-merge joinـه: خروجیِ mapperها بر اساسِ key مرتبه و reducer لیست‌های مرتبِ دو طرفِ join رو با هم ادغام می‌کنه.

Now the join logic is simple: the first value must be the birth date, which the reducer keeps in a local variable; then it walks the same user_id's events, emitting each visited URL alongside the viewer's birth date. Since the reducer processes one user_id's records together, it needs only one user record in memory at a time and never a network request. This algorithm is the sort-merge join: mapper output is key-sorted and the reducer merges both join sides' sorted lists.

و job بعدیِ workflow می‌تونه توزیعِ سنِ بیننده‌ها رو به‌ازای هر URL حساب کنه: داده رو با کلیدِ URL shuffle می‌کنه، و reducerها رو همهٔ بازدیدهای یه URL می‌چرخن، به‌ازای هر گروهِ سنی یه شمارنده نگه می‌دارن و با هر بازدید شمارندهٔ مربوط رو یکی زیاد می‌کنن — یعنی همون group by و aggregation.

And the workflow's next job can compute viewer-age distribution per URL: shuffle data keyed by URL, and reducers walk all of one URL's visits, keeping one counter per age group and incrementing on each visit — i.e. group by and aggregation.

۴.۵. زبان‌های کوئری4.5. Query languages

راستش زبون‌هایی مثل SQL نتیجهٔ موردنیاز رو بیان می‌کنن و بهینه‌ساز روشِ اجرا رو انتخاب می‌کنه. انتخابِ طرح اجرا می‌تونه مقدارِ دادهٔ خونده‌شده یا جابه‌جاشده رو خیلی تغییر بده.

مثال فنی: Optimizer چه تصمیمی می‌گیرد؟

وضعیت اولیه: فرض کن SQL فروش رو به کالا join می‌کنه و فقط دستهٔ book رو نگه می‌داره.

اجرای مرحله‌به‌مرحله: حالا optimizer می‌تونه فیلترِ دسته رو زودتر اعمال کنه و با آمار اندازه، نوع join رو انتخاب کنه.

نتیجه و دلیل: اعلانی بودن مسیر بهینه رو قابل‌انتخاب می‌کنه؛ آمار قدیمی یا skew می‌تونه طرح نامناسب بسازه — حساب کن.

Distributed execution engines grew up: infrastructure is now strong enough to store and process tens of petabytes on 10,000+-machine clusters. With operations mostly solved, everyone's focus moved to the programming model. MapReduce, dataflow engines and cloud warehouses all adopted SQL as batch processing's lingua franca — a natural pick: old warehouses had SQL, analytics and ETL tools already supported it, and every developer and analyst knows it.

  • تعاملی‌بودن: به‌جای jobهای MapReduce دست‌نویسِ طولانی، کوئریِ کوتاه می‌نویسی و از terminal یا GUI اجراش می‌کنی. این سبکِ کوئریِ تعاملی برای تحلیلگرانِ کسب‌وکار و مدیرانِ محصول و تیم‌های فروش و مالی راهِ طبیعیِ کاوش تو داده‌ست؛ و SQL، سیستم‌های دسته‌ای رو برای کوئری‌های اکتشافی هم مناسب کرده.
  • بهینه‌سازیِ ماشینی: زبونِ سطح‌بالا فقط انسان‌ها رو بهره‌ورتر نمی‌کنه؛ کاراییِ اجرا رو هم بهتر می‌کنه. موتورِ کوئری، SQL رو به درختِ syntax و بعد operatorهای فیزیکی تبدیل می‌کنه و همین ترجمه جای optimizer مبتنی بر costـه: Hive و Trino و Spark و Flink می‌تونن خواصِ ورودی‌های join رو تحلیل کنن و مناسب‌ترین الگوریتم رو انتخاب کنن — حتی ترتیبِ joinها رو عوض کنن تا state میانی کمینه بشه.
  • Interactivity: instead of long hand-written MapReduce jobs, write a short query and run it from a terminal or GUI. This interactive query style is the natural way for business analysts, product managers, sales and finance teams to explore data; and SQL made batch systems fit exploratory queries too.
  • Machine optimization: a high-level language doesn't just make humans more productive; it executes more efficiently too. The query engine turns SQL into a syntax tree and then physical operators, and that translation is where the cost-based optimizer lives: Hive, Trino, Spark and Flink can analyze join inputs' properties and pick the fittest algorithm — even reorder joins to minimize intermediate state.

البته SQL تنها زبونِ عمومی نیست و زبون‌های دیگه جای نیچ دارن: Apache Pig زبونی مبتنی بر operatorهای رابطه‌ای بود که pipeline رو گام‌به‌گام تعریف می‌کرد، نه به‌شکلِ یه کوئریِ بزرگِ SQL — Morel زبونِ مدرن‌تریه که از Pig الهام گرفته؛ DataFrameها (بخشِ بعد) هم ویژگیِ مشابهی دارن. بعضی‌ها سراغِ زبون‌های کوئریِ JSON رفتن: jq، JMESPath، JSONPath. و برای داده‌های گرافی (فصلِ مدل‌های داده)، frameworkهای پردازشِ گراف از زبون‌هایی مثل Gremlin (Apache TinkerPop) برای محاسبهٔ دسته‌ای پشتیبانی می‌کنن.

But SQL isn't the only general language, and other languages hold niches: Apache Pig was a relational-operator language defining the pipeline step by step instead of one big SQL query — Morel is a more modern Pig-inspired language; DataFrames (next section) share a similar trait. Some turned to JSON query languages: jq, JMESPath, JSONPath. And for graph data (the data-models chapter), graph-processing frameworks support languages like Gremlin (Apache TinkerPop) for batch computation.

۴.۶. همگرایی با cloud data warehouse4.6. Convergence with the cloud data warehouse

ماجرا از این قراره: انبارهای داده و چارچوب‌های پردازش، قابلیت‌های مشترک بیشتری پیدا کردن: ذخیره‌سازی جدا و SQL و اجرای موازی. با این حال محدودیت‌ها و هزینهٔ عملیاتیِ ابزارها هنوز متفاوته.

مثال فنی: انبار ابری هم پردازش توزیع‌شده دارد

وضعیت اولیه: فرض کن query رو صدها فایل ستونی، فروش روزانه رو جمع می‌زنه.

اجرای مرحله‌به‌مرحله: حالا سرویس، اسکن فایل‌ها و shuffle و aggregation رو بین workerها تقسیم می‌کنه و منابع اجرا رو مدیریت می‌کنه.

نتیجه و دلیل: رابط SQL خیلی از جزئیات رو پنهان می‌کنه؛ هزینهٔ اسکن و جابه‌جایی داده حذف نشده — جادو نیست.

Picture this: historically two separate streams existed — data warehouses on dedicated hardware running analytical SQL over relational data; and batch frameworks like MapReduce arriving for bigger scale and flexibility — with logic in general-purpose languages and reads/writes of arbitrary formats. Over time the two grew very alike:

  • Frameworkهای دسته‌ایِ مدرن از SQL پشتیبانی می‌کنن و با قالب‌های ستونیِ مثل Parquet و موتورهای اجرایِ بهینه‌شده، رو کوئری‌های رابطه‌ای هم عملکردِ خوب می‌گیرن.
  • Warehouseها با ابری شدن مقیاس‌پذیر شدن و همون تکنیک‌های scheduling و تحملِ خرابی و shuffle رو پیاده کردن که frameworkهای دسته‌ای داشتن؛ خیلی‌هاشون از فایل‌سیستمِ توزیع‌شده هم استفاده می‌کنن.
  • و برعکس: warehouseهای ابری مدل‌های پردازشِ جایگزین رو هم گرفتن — BigQuery کتابخانهٔ DataFrames داره و Snowpark تو Snowflake با Pandas یکپارچه می‌شه. ابزارهای orchestration مثل Airflow و Prefect و Dagster هم به warehouseهای ابری وصل می‌شن.
  • Modern batch frameworks support SQL and, with columnar formats like Parquet and optimized execution engines, perform well on relational queries too.
  • Warehouses became scalable in the cloud, implementing the same scheduling, fault-tolerance and shuffle techniques batch frameworks had; many also use distributed filesystems.
  • And vice versa: cloud warehouses adopted alternative processing models — BigQuery has a DataFrames library and Snowpark in Snowflake integrates with Pandas. Orchestration tools like Airflow, Prefect and Dagster also plug into cloud warehouses.

ولی همهٔ jobهای دسته‌ای به‌سادگی تو SQL بیان نمی‌شن: الگوریتم‌های تکراریِ گراف مثل PageRank و کارهای پیچیدهٔ ML و پردازشِ داده‌های غیررابطه‌ای و multimodal AI (تصویر و ویدیو و صدا). Warehouseهای ابری تو بعضی بارها هم به‌درد نمی‌خورن: محاسبهٔ سطربه‌سطر رو فرمت‌های ستونی ناکارآمده (اون‌جا API دیگهٔ warehouse یا سیستمِ دسته‌ای بهتره)، و معمولاً گرون‌ترن — برای jobهای بزرگ اجرای Spark یا Flink می‌تونه به‌صرفه‌تر باشه. معیارِ نهاییِ انتخاب: هزینه و راحتی و سادگیِ پیاده‌سازی و در دسترس بودن. شرکت‌های بزرگ معمولاً چند تا سیستمِ پردازشی دارن (و انعطافِ انتخاب)، شرکت‌های کوچیک‌تر اغلب با یکی کارشون راه می‌افته.

But not every batch job expresses easily in SQL: iterative graph algorithms like PageRank, complex ML work, and non-relational, multimodal AI data processing (images, video, audio). Cloud warehouses also misfit some loads: row-by-row computation over columnar formats is inefficient (there another warehouse API or a batch system does better), and they are usually pricier — running Spark or Flink can be cheaper for big jobs. The final selection metric: cost, comfort, implementation simplicity and skill availability. Big companies usually run several processing systems (and the flexibility to choose); smaller ones often get by with one.

۴.۷. DataFrameها4.7. DataFrames

بذار ساده بگم: DataFrame نمایی جدولی برای تبدیل داده‌ست. تو اجرای توزیع‌شده، ترتیب ردیف‌ها و زمانِ واقعیِ اجرای عملیات ممکنه با جدولِ تو حافظهٔ یه برنامه فرق داشته باشه.

مثال فنی: DataFrame محلی یا توزیع‌شده

وضعیت اولیه: فرض کن دستور df.filter(...).groupBy(...).sum() نوشته شده.

اجرای مرحله‌به‌مرحله: حالا تو موتور توزیع‌شده ممکنه فقط plan ساخته بشه و action اجرا رو شروع کنه؛ collect() تموم خروجی رو به driver می‌آره.

نتیجه و دلیل: ظاهراً مشابه بودن API با جدول محلی به‌معنی یکسان بودن هزینه نیست؛ خروجی بزرگ می‌تونه حافظهٔ driver رو پر کنه — این دام معروفه.

If you're a data scientist or statistician, you probably live in the DataFrame data model of R and Pandas: something like a relational table — a set of rows with same-typed values per column — except instead of one big SQL query you call relational-operator functions: filter, join, sort, aggregation and the rest.

اولش دستکاریِ DataFrameها به‌صورتِ محلی و تو حافظه بود و محدود به datasetهایی که تو یه ماشین جا می‌شدن. دانشمندانِ داده می‌خواستن با همون API آشنا به datasetهای بزرگِ محیط‌های دسته‌ای دسترسی داشته باشن (چون SQL و MapReduce برای نیازهاشون مناسب نبود)؛ پس frameworkهای توزیع‌شده مثل Spark و Flink و Daft APIهای DataFrame رو پذیرفتن. ولی پیاده‌سازی یه کم متفاوت رفتار می‌کنه و چند تا تفاوتِ semantic مهم هست:

DataFrame manipulation started local and in-memory, limited to datasets fitting one machine. Data scientists wanted the same familiar API on batch environments' big datasets (SQL and MapReduce didn't fit their needs); so distributed frameworks like Spark, Flink and Daft adopted DataFrame APIs. But the implementation behaves a bit differently, with a few important semantic differences:

  • DataFrameهای محلی معمولاً ایندکس‌شده و مرتب‌ان؛ DataFrameهای توزیع‌شده معمولاً نه. مهاجرت به frameworkهای دسته‌ای می‌تونه به‌خاطرِ همین، «غافلگیریِ عملکرد» بیاره — کد اجرا می‌شه ولی نتیجه یا ترتیب، اون چیزی نیست که انتظار داشتی.
  • eager در برابر lazy: Pandas وقتی متدِ DataFrame صدا زده می‌شه، فوراً اجرا می‌کنه؛ Spark اول همهٔ فراخوانی‌های API رو به یه query plan ترجمه می‌کنه، بهینه‌سازی رو اجرا می‌کنه، و بعد workflow رو رو موتورِ dataflow توزیع‌شده‌ش می‌دَوونه.
  • client/server: frameworkهایی مثل Daft هر دو رو دارن: عملیاتِ کوچیکِ تو حافظه‌ای رو client اجرا می‌شن و datasetهای بزرگ رو server. قالب‌های ستونیِ مثل Apache Arrow یه مدلِ دادهٔ مشترک می‌دن که هم موتورِ اجرایِ سمتِ client و هم سمتِ server می‌تونن به اشتراک بذارن.
  • Local DataFrames are usually indexed and ordered; distributed DataFrames usually aren't. Migrating to batch frameworks can therefore bring “performance surprises” — code runs, but results or ordering aren't what you expected.
  • Eager vs lazy: Pandas executes the moment a DataFrame method is called; Spark first translates all API calls into a query plan, runs optimization, then executes the workflow on its distributed dataflow engine.
  • Client/server: frameworks like Daft have both: small in-memory ops run on the client, big datasets on the server. Columnar formats like Apache Arrow give a shared data model both the client-side and server-side engines can share.

۴.۸. نقشهٔ مفهومیِ مدل‌های پردازش4.8. The processing-models concept map

هفت تا زیربخشِ قبلی رو یکی‌یکی جلو رفتیم: از MapReduce و shuffle تا موتورهای dataflow و زبون‌های کوئری و DataFrame. بد نیست یه بار دیگه همه رو تو یه تصویر ببینیم — نه به‌شکلِ «مسیرِ یه درخواست»، بلکه به‌شکلِ نمودار کلاسی: چه مفهومی زیرمجموعهٔ چه مفهومیه، چی به چی وابسته‌ست، و کدوم ایده‌ها بینِ چند تا مدل مشترک‌ان.

You've walked the previous seven subsections one by one: from MapReduce and shuffle to dataflow engines, query languages and DataFrames. Worth seeing them all once more in one picture — not as “one request's path” but as a class diagram: which concept subclasses which, what depends on what, and which ideas are shared across models.

پیامِ اصلیِ نقشه اینه: اون چیزی که تو بازار «پردازندهٔ دسته‌ای» نامیده می‌شه، چند تا فناوریِ بی‌ربط نیست؛ یه پشتهست. بالای پشته، مدل‌های برنامه‌نویسی قرار دارن (لوله‌های Unix و MapReduce و dataflow و SQL و DataFrame) که فقط شیوهٔ بیانِ محاسبه رو تعیین می‌کنن. وسطِ پشته، موتورِ اجرا و Shuffleـه. و زیرِ اون، Storage و Orchestrator قرار دارن که از مدلِ برنامه‌نویسی جدان و با protocolهای قابلِ تعویض به هم وصل می‌شن — همون ایده‌ای که تو «سیستم‌عاملِ توزیع‌شده» دیدیم.

The map's core message: what the market calls “batch processors” isn't several unrelated technologies; it is a stack. Atop the stack sit the programming models (Unix pipes, MapReduce, dataflow, SQL, DataFrames) which only set how computation is expressed. Mid-stack sit the execution engine and Shuffle. And below, Storage and the Orchestrator, separate from the programming model and joined by swappable protocols — the same idea as the “distributed operating system”.

تو خوشهٔ ۱، جعبهٔ مادر ProcessingModelـه با توضیحِ «abstract · bounded input → derived output» و دو خصیصه: input : immutable dataset, read once و output : derived dataset · terminates — دقیقاً همون تعریفِ فصل. سه تا فرزند با پیکانِ inheritance بهش وصل‌ان: UnixToolPipeline («sort-based · single machine»، لوله‌های stdin/stdout)، MapReduce («map, implicit sort, reduce»، I/O فایلی بین stageها، بازتلاشِ per-task) و DataflowEngine («whole workflow = one job · operators fused»، pipelined، دادهٔ میانی تو حافظه).

کنارِ این‌ها دو تا جعبهٔ دیگه هست که فرزند نیستن؛ با پیکانِ خط‌چینِ «compile to» به DataflowEngine وصل‌ان: SqlQueryEngine («SQL → physical plan»، optimizer مبتنی بر هزینه، ترتیبِ join عوض می‌شه) و DataFrameApi («relational ops as methods»، API سبکِ Pandas رو موتورِ توزیع‌شده). یعنی این دو «زبان»‌ان که به لایهٔ اجرا کامپایل می‌شن، نه مدلِ اجرایِ جدا.

جعبهٔ چهارمِ خوشهٔ ۱، Shuffleـه («shared helper · repartition»، hash(key) → one sorted file per reducer · merge-sorted) که دو تا پیکان بهش برمی‌گرده: MapReduce «always uses» و DataflowEngine «uses only where needed». این همون درسِ بخشِ ۴.۲ـه: مرتب‌سازی فقط جایی که لازمه.

خوشهٔ ۲ از جعبهٔ مادرِ Storage شروع می‌شه («pluggable read/write protocol»، «S3 API is the de-facto standard») با دو تا فرزندِ DistributedFS (بلوک‌های بزرگِ ۱۲۸MB رو data nodeها، metadata service، replication یا erasure coding، اشارهٔ locality) و ObjectStore (bucket + key، آبجکت‌های immutable، بدونِ lock و بدونِ rename اتمیک، جداییِ storage و compute). یه پیکانِ association از ProcessingModel به Storage می‌ره با برچسبِ «reads input / writes output through pluggable S3 API».

و خوشهٔ ۳: جعبهٔ مادرِ Orchestrator («abstract · runs batch jobs»، تصمیمِ «کجا و کی» اجرا بشه) با دو تا فرزندِ JobScheduler («one job»، task executor + resource manager، FIFO/DRF/priority/quotas) و WorkflowScheduler («DAG of jobs»، منتظرِ خروجیِ upstream، سبکِ Airflow). دو تا association جعبه‌ها رو به هم می‌دوزن: «submits jobs to» از WorkflowScheduler به JobScheduler، و «runs under» از ProcessingModel به Orchestrator.

حالا یه قدم به عقب برگرد و شکلِ کلی رو نگاه کن: سه تا ستونِ عمودی — مدل و storage و orchestration — که فقط با چند تا پیکانِ کم‌تعداد به هم وصل‌ان. اگه هر مربع رو یه «تصمیمِ معماری» بگیری، می‌بینی که انتخابِ مدلِ برنامه‌نویسی و انتخابِ storage و انتخابِ orchestrator مستقل از هم‌ان؛ و این دقیقاً همون چیزیه که سیستم‌های دستهٔ مدرن رو قابلِ ترکیب می‌کنه.

Reading each square as one “architecture decision”, the programming-model, storage and orchestrator choices are independent — exactly what makes modern batch systems composable.

درسِ جمع‌بندیِ بخش ۴Section 4 takeaway
اگه تو مصاحبه پرسیدن «MapReduce و Spark و SQL چه ربطی به هم دارن؟»، جواب همین نقشه‌ست: SQL و DataFrame به موتورِ dataflow کامپایل می‌شن؛ خودِ موتورِ dataflow تعمیمِ MapReduceـه (با اپراتورهای قابلِ ترکیب و بدونِ I/O فایلیِ اجباری بینِ هر مرحله)؛ و همهٔ این‌ها رو storage و orchestrator قابلِ تعویض می‌شینن. یه ترفند مصاحبه‌ای: انتخابِ درست یعنی تطبیقِ مدل با بارِ کاری، نه دنبالِ «بهترین ابزارِ مطلق» رفتن.
If an interviewer asks “how do MapReduce, Spark and SQL relate?”, this map is the answer: SQL and DataFrames compile to the dataflow engine; the dataflow engine itself generalizes MapReduce (composable operators, no forced file I/O between stages); and all of it sits on swappable storage and orchestration. And the right choice means matching the model to the workload, not chasing the “absolute best tool”.

پردازش دسته‌ای برای کارِ انبوه و تکرارپذیر مناسبه: تبدیل داده و تحلیل و ساختنِ خروجی‌های مشتق‌شده. معمولاً باید بینِ زمانِ آماده شدنِ نتیجه و هزینهٔ پردازش تعادل بذاریم.

مثال فنی: سه خروجی از ورودی مشترک

وضعیت اولیه: فرض کن از فایل سفارش، گزارش مالی و ویژگی مدل و ایندکس جست‌وجو ساخته می‌شن.

اجرای مرحله‌به‌مرحله: حالا هر job نسخهٔ ورودی و کدِ خودش رو ثبت می‌کنه و خروجی جدا می‌سازه.

نتیجه و دلیل: شکستِ ساختنِ یه خروجی نباید مرجع رو خراب کنه؛ رابطهٔ نسخهٔ داده و محاسبه امکان تطبیق و تکرار رو می‌ده — یادت باشه.

Now that you know the mechanism, let's see where it's used in practice. Batch jobs crush massive datasets but aren't built for low latency — so you'll find them wherever data is plenty and data freshness doesn't matter. Sounds limited? Honestly, a huge share of data processing fits this model: accounting and warehouse reconciliation, demand forecasting in manufacturing, recommender-model training in e-commerce and media, and many financial systems (the US banking network is almost entirely batch).

۵.۱. ETL5.1. ETL

تو ETL، داده استخراج و تبدیل می‌شه و بعد تو مقصد قرار می‌گیره. تبدیل باید قواعد کیفیت و معنای فیلدها رو هم پوشش بده، نه فقط تغییر قالبِ فایل.

مثال فنی: پاک‌سازی پیش از بارگذاری

وضعیت اولیه: فرض کن فایل فروش ردیف تکراری با order_id=42 و مبلغ با دو تا واحد داره.

اجرای مرحله‌به‌مرحله: حالا job با کلید مناسب deduplicate می‌کنه و واحدها رو یکسان می‌کنه؛ رکورد نامعتبر به مسیر خطا می‌ره.

نتیجه و دلیل: ETL فقط جابه‌جایی فایل نیست؛ قواعد تکرار و واحد تو درستی گزارش نقش دارن — حفظ کن.

ETL (Extract–Transform–Load) and ELT mean a data-processing pipeline extracting data from the operational database, transforming it and loading the result into the downstream system (usually a warehouse). Batch jobs are perfect for this workload, especially with a warehouse downstream.

  • embarrassingly parallel: ماهیتِ موازیِ jobهای دسته‌ای برای تبدیلِ داده عالیه؛ بیشترِ تبدیل‌های رایجِ warehouse — فیلتر کردن و project کردنِ فیلدها — کارهایی‌ان که به‌راحتی موازی می‌شن.
  • workflow schedulerها: محیط‌های دسته‌ای schedulerهای workflow قوی دارن که زمان‌بندی و اشکال‌زداییِ pipelineها رو ساده می‌کنن. موقع خطا، schedulerها اغلب job رو بازتلاش می‌کنن تا مشکلاتِ گذرا جبران بشن؛ jobی که مدام شکست بخوره به‌عنوانِ failed علامت می‌خوره و توسعه‌دهنده راحت می‌بینه کدوم jobِ pipeline ایستاده. Airflow حتی operatorهای آماده برای MySQL و PostgreSQL و Snowflake و Spark و Flink و ده‌ها سیستمِ دیگه داره.
  • دیباگ‌پذیری: وقتی اوضاع خراب می‌شه، jobهای دسته‌ای راحت عیب‌یابی و ترمیم می‌شن: فایل‌های خراب رو می‌شه بازرسی کرد تا معلوم بشه چی شده؛ مثلاً اگه ورودی فیلدِ موردِ نیازِ تبدیل رو نداشته باشه، مهندسِ داده راحت می‌بینه فیلد غایبه و منطقِ تبدیل یا job تولیدکننده رو درست می‌کنه.
  • مالکیتِ توزیع‌شده: قبلاً pipelineهای داده رو یه تیمِ واحدِ مهندسیِ داده اداره می‌کرد؛ حالا بهبودِ مدل‌های پردازش و مدیریتِ متادیتا باعث شده مهندس‌های هر تیمی بتونن pipeline خودشون رو بنویسن. رویه‌هایی مثل data mesh و data contract و data fabric استانداردها و ابزارهایی می‌دن تا تیم‌ها بتونن داده‌شون رو با امنیت برای مصرفِ بقیهٔ سازمان منتشر کنن.
  • مشترک‌شدنِ موتورِ اجرا: pipelineهای داده و کوئری‌های تحلیلی حالا نه‌تنها مدلِ پردازش، بلکه موتورِ اجرا رو هم مشترک دارن — دیدنِ تبدیل‌های pipeline و کوئری‌های تحلیلی به‌شکلِ کوئری‌های SparkSQL یا Trino یا DuckDB عادیه؛ و این مرزِ بینِ مهندسیِ اپلیکیشن و مهندسیِ داده و مهندسیِ تحلیل و تحلیلِ کسب‌وکار رو بیشتر محو می‌کنه.
  • Embarrassingly parallel: batch jobs' parallel nature suits data transformation perfectly; most common warehouse transforms — filtering, projecting fields — parallelize easily.
  • Workflow schedulers: batch environments have strong workflow schedulers simplifying pipeline scheduling and debugging. On error, schedulers often retry the job to absorb transient faults; a persistently failing job is marked failed so developers easily see which pipeline job stalled. Airflow even ships ready operators for MySQL, PostgreSQL, Snowflake, Spark, Flink and dozens of other systems.
  • Debuggability: when things break, batch jobs are easy to diagnose and repair: broken files can be inspected to learn what happened; e.g. if input lacks a transform's needed field, the data engineer plainly sees the missing field and fixes the transform logic or the producing job.
  • Distributed ownership: data pipelines used to be run by one data-engineering team; improved processing models and metadata management now let each team's engineers write their own pipelines. Practices like data mesh, data contracts and data fabric give standards and tooling for teams to publish their data securely for the rest of the organization.
  • Shared execution engine: data pipelines and analytical queries now share not just the processing model but the execution engine too — seeing pipeline transforms and analytical queries as SparkSQL, Trino or DuckDB queries is ordinary; and this further blurs the line between application, data, analytics engineering and business analysis.

۵.۲. تحلیل5.2. Analytics

تحلیل دسته‌ای با اسکن و تجمیعِ دادهٔ تاریخی، جوابِ سؤال‌های مدیریتی یا پژوهشی رو می‌سازه. اهمیتِ تازگیِ نتیجه باید متناسب با همون سؤال تعیین بشه.

مثال فنی: تحلیل روی مجموعهٔ مشخص

وضعیت اولیه: فرض کن گزارشِ روزانه، سفارش‌های تأییدشده تا مرز زمانی مشخص رو لازم داره.

اجرای مرحله‌به‌مرحله: حالا job همون ورودی نسخه‌دار رو فیلتر می‌کنه و مجموع رو حساب می‌کنه؛ زمان cutoff تو خروجی ثبت می‌شه.

نتیجه و دلیل: بدون مرز ورودی، دو اجرای ظاهراً یکسان می‌تونن صرفاً به‌خاطر رسیدن دادهٔ تازه عدد متفاوت بدن — این دام معروفه.

Analytical (OLAP) queries often scan huge record counts and group and aggregate. Such a workload can run on the batch system alongside the other batch jobs: the analyst writes SQL, the query engine executes, reading and writing DFS/object store. Table metadata (mapping tables to files, names, types) is managed with a table format like Apache Iceberg and a catalog like Unity — this architecture is called data lakehouse.

کوئری‌های تحلیلی رو frameworkهای دسته‌ای معمولاً دو تا سبک دارن:

Analytical queries on batch frameworks usually come in two styles:

  • Pre-aggregation (پیش‌تجمیع): داده تو OLAP cube یا data mart جمع‌بندی می‌شه تا کوئری‌ها سریع بشن. دادهٔ پیش‌تجمیع‌شده یا تو warehouse کوئری می‌شه یا به سیستم‌های OLAP بلادرنگِ اختصاصی مثل Apache Druid یا Apache Pinot فشار داده می‌شه. پیش‌تجمیع معمولاً با فاصلهٔ زمانیِ مشخص انجام می‌شه و همون workflow schedulerها مدیریتش می‌کنن.
  • Ad hoc: کاربر برای جواب به یه سؤالِ مشخصِ کسب‌وکار و بررسیِ رفتارِ کاربر یا اشکال‌زداییِ عملیاتی اجرا می‌کنه. این‌جا زمانِ پاسخ مهمه: تحلیل‌گر تکراری کوئری می‌زنه و با هر جواب بیشتر یاد می‌گیره؛ frameworkهای دسته‌ای با اجرای سریعِ کوئری، زمانِ انتظار رو کم می‌کنن.
  • Pre-aggregation: data is summarized in an OLAP cube or data mart to speed queries. Pre-aggregated data is either queried in the warehouse or pushed to dedicated real-time OLAP systems like Apache Druid or Apache Pinot. Pre-aggregation usually runs on a fixed cadence, managed by those same workflow schedulers.
  • Ad hoc: run by a user answering a specific business question, studying user behavior or debugging operations. Here response time matters: the analyst queries iteratively, learning more with each answer; batch frameworks cut waiting time by executing queries fast.

و پشتیبانیِ SQL یعنی یکپارچگی با صفحه‌گسترده‌ها و ابزارهای مصورسازی: Tableau و Power BI و Looker و Apache Superset — مثلاً Superset از Trino و Hive و Spark SQL و Presto پشتیبانی می‌کنه که در نهایت jobهای دسته‌ای‌ان.

And SQL support means integration with spreadsheets and visualization tools: Tableau, Power BI, Looker and Apache Superset — e.g. Superset supports Trino, Hive, Spark SQL and Presto, which are batch jobs underneath.

۵.۳. یادگیری ماشین5.3. Machine learning

پردازش دسته‌ای تو آماده‌سازی داده و ساختنِ ویژگی و آموزش مدل استفاده می‌شه. بازتولیدِ نتیجه به نسخهٔ ورودی و کد و تنظیمات وابسته‌ست.

مثال فنی: ویژگی مدل بدون نشت آینده

وضعیت اولیه: تصور کن برای پیش‌بینیِ روز ۱۰، مجموع خریدِ هفت روز قبل لازمه.

اجرای مرحله‌به‌مرحله: حالا job فقط رخدادهای پیش از روز ۱۰ رو join و aggregate می‌کنه؛ خرید روز ۱۱ نباید وارد ویژگیِ اون نمونه بشه.

نتیجه و دلیل: pipeline درست باید مرز زمانی رو حفظ کنه؛ استفاده از snapshot امروز ممکنه اطلاعات آینده رو به آموزش نشت بده — حساب کن.

ML leans hard on batch processing: data scientists and ML/AI engineers discovering data patterns, transforming data and training models. Three common uses:

  • Feature engineering: دادهٔ خام فیلتر و تبدیل می‌شه تا داده‌ای بشه که مدل رو می‌شه روش آموزش داد؛ مدل‌های پیش‌بین معمولاً دادهٔ عددی می‌خوان، پس فرم‌های دیگه (متن یا مقدارهای گسسته) باید تبدیل بشن.
  • آموزشِ مدل: دادهٔ آموزشی ورودیِ پردازشِ دسته‌ایه و وزن‌های مدلِ آموزش‌دیده، خروجی.
  • Batch inference: اگه dataset بزرگ باشه و نتیجهٔ بلادرنگ لازم نباشه، مدلِ آموزش‌دیده پیش‌بینی‌ها رو به‌صورتِ انبوه انجام می‌ده — از جمله ارزیابیِ پیش‌بینی‌ها رو dataset تست.
  • Feature engineering: raw data is filtered and transformed into trainable data; predictive models usually want numeric data, so other forms (text or discrete values) must convert.
  • Model training: training data is the batch input; the trained model's weights are the output.
  • Batch inference: when the dataset is big and no real-time result is needed, the trained model predicts in bulk — including evaluating predictions on the test dataset.

frameworkها ابزارِ اختصاصیِ این‌ها رو دارن: MLlib تو Spark و FlinkML تو Flink با مجموعه‌ای از ابزارهای feature engineering و تابع‌های آماری و classifierها. کاربردهایی مثل موتورهای پیشنهاددهنده و رتبه‌بندی به پردازشِ گراف هم سنگین‌ان: خیلی از الگوریتم‌های گراف با پیمایشِ یه یال تو هر گام بیان می‌شن — یه رأس رو به رأسِ مجاور join می‌کنی تا اطلاعاتی رو منتشر کنی، و تکرار تا رسیدن به شرط (مثلاً تا وقتی یالی برای پیمایش نمونده یا متریک همگرا بشه). مدلِ bulk synchronous parallel (BSP) برای پردازشِ گراف محبوب شده — تو Apache Giraph و API GraphX تو Spark و Gelly تو Flink — و به مدلِ Pregel هم معروفه.

Frameworks ship dedicated tooling for these: MLlib in Spark and FlinkML in Flink with feature-engineering tools, statistics functions and classifiers. Uses like recommenders and ranking also lean hard on graph processing: many graph algorithms express as traversing one edge per step — joining a vertex to neighbors to propagate information, iterating to a condition (e.g. until no edges remain or a metric converges). The bulk synchronous parallel (BSP) model grew popular for graph processing — in Apache Giraph, Spark's GraphX API and Flink's Gelly — also known as the Pregel model.

پردازشِ دسته‌ای بخشِ جدانشدنیِ آماده‌سازی و آموزشِ مدل‌های زبونیِ بزرگ (LLM) هم هست. دادهٔ متنِ خام (مثل محتوای وب‌سایت‌ها) معمولاً تو DFS/object storeـه و باید پیش‌پردازش بشه: استخراجِ متنِ ساده از HTML و اصلاحِ متنِ خراب، تشخیص و حذفِ اسنادِ بی‌کیفیت/نامرتبط/تکراری، و tokenize (تقسیم به کلمات) و تبدیل به embedding. frameworkهایی مثل Kubeflow و Flyte و Ray برای همین بارها ساخته شدن و یکپارچگیِ آماده با PyTorch و TensorFlow و XGBoost دارن (و پشتیبانیِ داخلی از feature engineering و آموزش و batch inference و fine-tuning). و بالاخره، دانشمندانِ داده اغلب تو notebookهای تعاملی مثل Jupyter یا Hex تجربه می‌کنن: سلول‌های کوچیکِ Markdown/Python/SQL که به‌ترتیب اجرا می‌شن و خروجی‌شون جدول و نموداره — و خیلی از notebookها از DataFrame API یا SQL به‌عنوانِ پردازشِ دسته‌ای استفاده می‌کنن.

Batch processing is inseparable from preparing and training large language models (LLMs) too. Raw text data (like website contents) usually sits in DFS/object store and must be preprocessed: extracting plain text from HTML and fixing broken text, detecting and dropping low-quality/irrelevant/duplicate documents, and tokenizing (splitting into words) plus embedding. Frameworks like Kubeflow, Flyte and Ray were built for exactly these loads, with ready PyTorch, TensorFlow and XGBoost integration (plus built-in feature engineering, training, batch inference and fine-tuning). And finally, data scientists often experiment in interactive notebooks like Jupyter or Hex: small Markdown/Python/SQL cells executed in order with tables and charts as output — and many notebooks use the DataFrame API or SQL as their batch processing.

نتیجه و دلیل: کاربر مخلوطِ خروجی ناقص و قدیمی نمی‌بینه؛ نوشتن مستقیمِ هر task رو ایندکس فعال این مزیت رو سخت‌تر می‌کنه — یادت باشه.

Batch jobs often build precomputed or derived datasets: product recommendations, user-facing reports and ML-model features. These are usually served from a production database, key-value store or search engine; so data must travel from the batch processor's DFS/object store to the database answering live traffic.

چرا نوشتنِ مستقیم به پایگاه داده، ایدهٔ بدی استWhy writing directly to the database is a bad idea
وسوسه‌انگیزه: کلاینتِ پایگاه دادهٔ محبوبت رو تو job بردار و رکوردرکورد مستقیم بنویس. کار می‌کنه (اگه firewall اجازه بده!) ولی به چند تا دلیل بده:
  • هر رکورد یه درخواستِ شبکه‌ای — چند مرتبه کندتر از توانِ عادیِ یه task دسته‌ای؛ حتی با batching هم عملکرد ضعیف می‌مونه.
  • frameworkهای دسته‌ای taskهای زیادی موازی دارن؛ اگه همه با نرخِ موردِ انتظارِ دسته‌ای بنویسن، پایگاه دادهٔ خروجی به‌راحتی غرق می‌شه و عملکردِ کوئری‌هاش می‌افته — و مشکل به بقیهٔ سیستم هم سرایت می‌کنه.
  • jobهای دسته‌ای معمولاً تضمینِ تمیزِ all-or-nothing دارن: اگه job موفق بشه، نتیجه «اجرای هر task دقیقاً یه بار»ـه — حتی اگه وسط راه taskها شکست و بازتلاش شده باشن؛ و اگه کلِ job شکست بخوره، هیچ خروجی‌ای تولید نمی‌شه. نوشتنِ مستقیم به سیستمِ بیرونی یعنی side effect قابلِ دیدنِ بیرونی که دیگه نمی‌شه پنهانش کرد: باید نگرانِ دیده شدنِ نتایجِ job نیمه‌کاره باشی، و taskی که شکست و restart شد ممکنه خروجیِ اجرای شکسته رو تکراری تولید کنه.
Tempting, right? Grab your favorite database client inside the job and write record by record, directly. It works (if the firewall allows!) but it's a bad idea for several reasons:
  • Each record is one network request — several times slower than a normal batch task's pace; even with batching, performance stays poor.
  • Batch frameworks run many tasks in parallel; if all write at the expected batch rate, the output database easily drowns and its query performance drops — and the trouble spreads to the rest of the system.
  • Batch jobs usually carry a clean all-or-nothing guarantee: a successful job means “each task ran exactly once” — even with mid-way task failures and retries; and a fully failed job produces no output at all. Writing directly to an outside system means an externally-visible side effect that can no longer be hidden: you must worry about half-done jobs' results being seen, and a failed-then-restarted task may duplicate the broken run's output.

راهِ بهتر اینه: jobهای دسته‌ای datasetهای آماده رو به جریان‌ها مثل topicهای Kafka فشار بدن. موتورهای جستجو مثل Elasticsearch و سیستم‌های OLAP بلادرنگ مثل Pinot و Druid و data storeهای مشتق‌شده مثل Venice و warehouseهای ابری مثل ClickHouse همگی قابلیتِ ingest از Kafka رو دارن. فشار دادن از طریقِ سیستمِ جریانی چند تا مشکل رو حل می‌کنه:

The better way: batch jobs push ready datasets to streams like Kafka topics. Search engines like Elasticsearch, real-time OLAP systems like Pinot and Druid, derived data stores like Venice and cloud warehouses like ClickHouse can all ingest from Kafka. Pushing through a streaming system fixes several problems:

  • سیستم‌های جریانی برای نوشتنِ ترتیبی بهینه‌ان — مناسبِ بارِ نوشتنِ انبوهِ یه job دسته‌ای.
  • می‌تونن به‌عنوانِ بافر بینِ job دسته‌ای و پایگاه‌های دادهٔ تولیدی عمل کنن: سیستم‌های پایین‌دستی نرخِ خوندنشون رو throttle می‌کنن تا بتونن هم‌زمان ترافیکِ تولیدی رو هم راحت سرو کنن.
  • خروجیِ یه job دسته‌ای رو می‌تونه چند تا سیستمِ پایین‌دستی مصرف کنن.
  • سیستم‌های جریانی می‌تونن مرزِ امنیتی بینِ محیطِ پردازشِ دسته‌ای و شبکهٔ تولیدی باشن: تو شبکه‌ای موسوم به DMZ (demilitarized zone) بینِ این دو مستقر می‌شن.
  • Streaming systems optimize for sequential writes — fitting a batch job's bulk write load.
  • They can act as a buffer between the batch job and production databases: downstream systems throttle their read rate so they can comfortably serve production traffic at the same time.
  • One batch job's output can feed several downstream systems.
  • Streaming systems can be a security boundary between the batch environment and the production network: deployed in a network called a DMZ (demilitarized zone) between the two.

ولی یه چیز رو جریان ذاتاً حل نمی‌کنه: تضمینِ all-or-nothing. برای این کار، job تو پایانِ کارش باید به سیستم‌های پایین‌دستی اعلام کنه job تموم شده و داده حالا قابلِ سروه. مصرف‌کننده‌های جریان باید داده‌ای که می‌گیرن تا اطلاعِ ثانوی از کوئری‌ها پنهون نگه دارن — دقیقاً مثلِ یه تراکنشِ uncommitted با ایزوله‌سازیِ read committed (فصل ۷) — تا خبرِ تموم شدنِ job برسه.

But one thing streams don't inherently fix: the all-or-nothing guarantee. For that, the job must announce completion to downstream systems at its end, and the data is servable only then. Stream consumers must keep received data hidden from queries until further notice — exactly like an uncommitted transaction under read committed isolation (Chapter 7) — until the job-done news arrives.

الگوی دیگه، مخصوصاً موقعِ bootstrap کردنِ پایگاه داده‌ها: ساختنِ یه پایگاه دادهٔ کاملاً نو تو job دسته‌ای و bulk-load مستقیمِ فایل‌ها از DFS/object store/دیسکِ محلی به پایگاه داده. ابزارهای bulk import زیادن: TiDB Lightning و jobهای Hadoop import تو Pinot و APIی bulk-import فایل‌های SST تو RocksDB. ساختنِ پایگاه داده تو دسته و bulk-load خیلی سریعه و سوییچِ اتمیکِ بینِ نسخه‌های dataset رو ساده می‌کنه؛ ولی به‌روزرسانیِ incremental رو همین پایگاه‌های دادهٔ نوساخته چالش‌برانگیزه. وقتی هم bootstrap لازمه و هم load تدریجی، رویکردِ ترکیبی رایجه — مثلاً Venice با «hybrid store» هم به‌روزرسانیِ سطریِ دسته‌ای داره و هم تعویضِ کاملِ dataset.

Another pattern, especially when bootstrapping databases: building a brand-new database inside the batch job and bulk-loading files straight from DFS/object store/local disk into the database. Bulk-import tools abound: TiDB Lightning, Hadoop import jobs in Pinot, and the bulk-import API for SST files in RocksDB. Building the database in batch and bulk-loading is very fast and simplifies the atomic dataset-version switch; but incremental updates on these freshly-built databases are challenging. When both bootstrapping and gradual loading are needed, a hybrid approach is common — e.g. Venice with its “hybrid store” has both batched row updates and full dataset replacement.

با همهٔ این حرف‌ها، تصمیمِ نهایی ساده بیان می‌شه: خروجیِ job از کدوم مسیر به سیستمِ سروِ تولیدی برسه؟ درختِ تصمیمِ زیر همون پرسش‌هایی رو مرتب می‌کنه که تو عمل باید یکی‌یکی از خودت بپرسی — و اولین شاخه‌ش همون «وسوسهٔ نوشتنِ مستقیم» رو به‌عنوانِ بن‌بست نشون می‌ده.

This decision tree reads left to right, top to bottom. The root is 01 Batch Output Ready (“derived dataset on disk”, “serve it to prod”) — the derived dataset sits ready on disk and must now reach real users. The “assess” arrow leads to question one: Write Direct to Prod DB? (“per-record network calls”). Answering “yes” drops straight into the Direct DB Writes leaf (“overloads DB, leaks output”, “duplicates on retry”) — the tree's “red” leaf: exactly the three problems from the box above (drowning the database, leaking half-done output, duplicate records).

So the right branch is “no”, reaching question two: Rebuild or Bootstrap? (“full dataset from scratch”). If yes — rebuilding the whole dataset — the branch runs to question three: Bulk-Import Tool?. Without the tool, the Publish Full Snapshot leaf (“to a stream topic”, “ingest at own pace”) — publishing the full snapshot to a stream. سه تا کارت جمع‌بندی می‌کنن: «All-or-Nothing Output» (موفقیتِ job یعنی هر task دقیقاً یه بار اجرا شده، حتی با شکست و بازتلاش؛ اگه کلِ job شکست بخوره اصلاً خروجی تولید نمی‌شه؛ shardهای ناقص تا پایانِ نوشتن از کوئری پنهون‌ان)، «Read-Committed Reveal» (مصرف‌کننده‌ها داده رو تا اعلانِ پایانِ job نامرئی نگه می‌دارن؛ این آشکارسازی مثلِ commit یه تراکنش تو سطحِ read committedـه) و «Recovery and Time Travel» (خروجیِ ناقصِ task شکسته حذف می‌شه و task از ورودیِ immutable بازتلاش می‌شه؛ خروجی‌های superseded برای rollback و time travel نگه داشته می‌شن؛ خروجیِ اجرای لغوشده حذف می‌شه یا هرگز اعلام نمی‌شه).

درسِ کلیِ نمودار: مرزِ commit تو پردازشِ دسته‌ای همون «اعلامِ پایانِ job»ـه. تا قبل از اون، هر چیزی قابلِ حذف و بازسازیه؛ بعد از اون، کلِ dataset یه‌جا برای خواننده‌ها واقعی می‌شه — اینو قاب کن.

This state machine has three lanes: Job output (the main path), Failure handling and Terminal exits. The main path has four numbered steps: 01 Writing Shards (“tasks writing shards”, “output hidden”) — tasks are writing output shards but output stays hidden — then “last task succeeds” to 02 Ready, Unpublished (“all shards written”, “invisible”): all shards written, yet nobody sees them.

The key step is the “job-complete notification” arrow (“read-committed style reveal”) to 03 Published (“consumers notified”, “serving queries”): the job-done announcement reveals the whole dataset at once — exactly the text's “read-committed reveal”. Then “next scheduled run publishes” moves to 04 Superseded (“replaced by newer run”, “kept for rollback”) — the replaced version kept for rollback and time travel. The failure path: from Writing Shards the red “task fails / preempted” reaches Task Failed (“partial output deleted”, “retryable”), and “retry from input” loops back to Writing Shards — partial output deleted, rebuilt from immutable input. From Ready, Unpublished, “job aborted” goes to Discarded (“deleted or never announced”, “terminal”): an aborted run is deleted or never announced downstream — and since never announced, nobody saw a thing.

Three cards conclude: “All-or-Nothing Output” (job success means every task ran exactly once, even with failures and retries; a fully failed job produces no output at all; incomplete shards stay hidden from queries until writing ends), “Read-Committed Reveal” (consumers keep data invisible until the job-done announcement; this reveal is like committing a transaction at read-committed level) and “Recovery and Time Travel” (a broken task's partial output is deleted and the task retried from immutable input; superseded outputs are kept for rollback and time travel; an aborted run's output is deleted or never announced). The diagram's overall lesson: the commit boundary in batch processing is exactly the “job-done announcement”. Before it everything is deletable and rebuildable; after it the whole dataset becomes real for readers at once.

نتیجه و دلیل: ورودی immutable و خروجی نسخه‌داره، پس خطای محاسبه قابل‌بازسازیه؛ بازنویسی مستقیمِ دادهٔ مرجع همچین آزادی‌ای نمی‌ده — همین.

گره مرکزی قرارداد فصله: ورودی immutable و خروجی derived. سه تا مفهوم بالا ریشه‌ها و موتورهان: pipeline یونیکس (لوله رو یه ماشین) و سیستم‌عامل توزیع‌شده (ذخیره‌سازی و زمان‌بندها و taskها) و MapReduce (map و sort ضمنی و reduce). سه تا مفهوم پایین مقیاس و مصرف‌ان: shuffle (مرتب‌سازی توزیع‌شده) و dataflow و SQL (یه job با pipelining) و سرویس‌دهی خروجی (جریان‌ها و all-or-nothing).

درس یه‌خطی نقشه: همه‌چیز از همون قرارداد ساده میاد — خروجی رو از صفر بساز تا بازتلاش امن و بازیابی ممکن و انتشار اتمیک بشه؛ و برای مقیاس، کار رو با shuffle بین taskهای مستقل پخش کن.

The center node is the chapter's contract: immutable in, derived out. Up top sit the roots and engines: the Unix pipeline (pipes on one machine), the distributed OS (storage, schedulers, tasks) and MapReduce (map, implicit sort, reduce). Down below are scale and consumption: shuffle (the distributed sort), dataflow and SQL (one pipelined job) and serving the output (streams, all-or-nothing).

The map's one-line lesson: everything flows from the same simple contract — build output from scratch so retries stay safe, recovery stays possible and publication stays atomic; and for scale, spread the work with shuffle across independent tasks.

۶.۲. سوالات پرتکرار مصاحبه6.2. Frequent interview questions

۱. پردازشِ دسته‌ای و آنلاین در یک جمله چه تفاوتی دارند؟1. How do batch and online processing differ in one sentence?

جوابش کوتاهه: آنلاین برای درخواستِ همون لحظه جواب می‌سازه؛ دسته‌ای رو ورودیِ محدود کار می‌کنه و خروجی رو بعداً آماده می‌کنه. تأخیرِ هدف و روشِ انتشارِ نتیجه فرق دارن.

مثال فنی: پاسخ کاربر یا پایان job

وضعیت اولیه: فرض کن API وضعیت سفارش باید تو چندصد میلی‌ثانیه جواب بده؛ گزارش کل سال ممکنه نیم ساعت طول بکشه.

اجرای مرحله‌به‌مرحله: حالا API درخواست محدود رو همون لحظه انجام می‌ده؛ job دسته‌ای ورودیِ کران‌دار رو کامل می‌خونه و خروجی رو منتشر می‌کنه.

نتیجه و دلیل: معیار آنلاین بیشتر latency هر درخواسته و معیار batch بیشتر زمان پایان و هزینهٔ کل پردازش — همین.

Here's the short version. Online: ask, get a fast answer — response time is the metric. Batch: process a bounded immutable dataset from scratch into derived output — throughput is the metric. Batch input never changes and output is rebuilt every time.

۲. منظور از «human fault tolerance» چیست؟2. What does “human fault tolerance” mean?

تعریفش اینه: تحملِ خطای انسانی یعنی با حفظِ ورودی و جداسازیِ خروجی، منطقِ اشتباه رو اصلاح کنیم و محاسبه رو دوباره اجرا کنیم. این امکان به تغییرناپذیری و کنترلِ اثرهای جانبی وابسته‌ست.

مثال فنی: بازمحاسبهٔ گزارش از ورودی ثابت

وضعیت اولیه: فرض کن فایل فروش ۱۴ مهر بسته شده و نسخهٔ ورودی معلومه.

اجرای مرحله‌به‌مرحله: حالا job مجموع فروش هر شعبه رو تو خروجی نسخهٔ v2 می‌نویسه؛ اگه فرمول غلط بود، با کد اصلاح‌شده از همون ورودی دوباره اجراش می‌کنیم.

نتیجه و دلیل: ورودی immutable و خروجی نسخه‌داره، پس خطای محاسبه قابل‌بازسازیه؛ بازنویسی مستقیمِ دادهٔ مرجع همچین آزادی‌ای نمی‌ده — همین.

It's the ability to recover from your own code bugs: since input is immutable and output derived, you revert code to the previous version and rerun the job — or switch to the previous output (kept under another path). Transactional databases lack this: if buggy code writes bad data, reverting code never fixes the data.

۳. چرا در مثالِ pipeline، اول sort می‌کنیم و بعد uniq -c؟3. Why sort first and uniq -c after in the pipeline example?

چون uniq فقط تکرارهای کنارِ هم رو می‌شماره. مرتب‌سازی مقدارهای یکسان رو کنارِ هم می‌آره تا شمارشِ همهٔ رخدادها درست باشه.

مثال فنی: چرا sort قبل از uniq؟

وضعیت اولیه: تصور کن مسیرهای ورودی /a,/b,/a هستن.

اجرای مرحله‌به‌مرحله: حالا uniq -c فقط تکرارهای مجاور رو می‌شماره و بدون sort سه تا گروه می‌بینه؛ sort دو تا /a رو کنار هم می‌آره.

نتیجه و دلیل: مرتب‌سازی تو این pipeline برای درستیِ شمارش لازمه، نه فقط برای قشنگی خروجی — اینو قاب کن.

Because uniq only drops adjacent duplicate lines. Sorting makes every n-times-seen URL appear n times in a row; then uniq -c turns each run into one counted line. Exactly MapReduce's implicit-sort role, bringing same-key records together for the reducer.

۴. «مرتب‌سازی» چرا نسبت به «تجمیع در حافظه» مقیاس می‌خورد؟4. Why does “sorting” scale better than “in-memory aggregation”?

تجمیعِ هش‌محور به حافظهٔ متناسب با تعدادِ کلیدهای متفاوت نیاز داره. مرتب‌سازیِ بیرونی می‌تونه بخش‌ها رو رو دیسک مرتب و ادغام کنه؛ برای دادهٔ بزرگ‌تر از حافظه راهی قابل‌کنترل می‌ده.

مثال فنی: تجمیع بیرون از RAM

وضعیت اولیه: فرض کن ورودی یه میلیارد کلید متفاوت داره و جدول hashِ شمارنده‌ها تو RAM جا نمی‌شه.

اجرای مرحله‌به‌مرحله: حالا external sort تکه‌هایی که تو حافظه جا می‌شن رو مرتب می‌کنه و رو دیسک می‌نویسه، بعد ادغامشون می‌کنه.

نتیجه و دلیل: مرتب‌سازی می‌تونه با دیسک و حافظهٔ محدود ادامه بده؛ hash aggregation هم ممکنه spill داشته باشه، پس برتریِ مطلق مطرح نیست — روشنه، نه؟

Because it uses disk efficiently: chunks sort in memory, spill as segments, and merge via mergesort (sequential access). A hash table instead wants memory per distinct key (the working set); bigger than memory, it breaks. GNU sort spills and parallelizes by itself though; the bottleneck becomes the input read rate.

۵. قیاسِ «framework دسته‌ای = سیستم‌عاملِ توزیع‌شده» یعنی چه؟5. What does the “batch framework = distributed OS” analogy mean?

چارچوبِ دسته‌ای محلِ داده و منابع و اجرای وظیفه و بازیابی رو بین چند تا ماشین مدیریت می‌کنه. این نقش‌ها شبیه وظایفِ سیستم‌عامل‌ان، ولی هزینهٔ شبکه و خرابیِ جزئی هم هست.

مثال فنی: سه مسئولیتِ چارچوب

وضعیت اولیه: فرض کن job به خوندن فایل و اجرای ۱۰۰ تا task و انتقال دادهٔ بین مرحله‌ها نیاز داره.

اجرای مرحله‌به‌مرحله: حالا لایهٔ ذخیره فایل رو نگه می‌داره؛ scheduler منابع می‌ده؛ موتور اجرا task و retry و shuffle رو مدیریت می‌کنه.

نتیجه و دلیل: قیاس با سیستم‌عامل یعنی برنامه همهٔ جزئیات ماشین‌ها رو خودش اداره نکنه؛ مرز هر لایه هنوز باید روشن باشه — حکش کن تو ذهنت.

The same three Unix-machine parts exist distributed: storage (DFS/object store = filesystem), orchestration (scheduler and resource manager = the kernel deciding what runs where with what resources), and compute (isolated tasks = processes exchanging data via the filesystem).

۶. چرا بلاک‌های DFS این‌قدر بزرگ‌تر از بلاک‌های فایل‌سیستمِ محلی‌اند؟6. Why are DFS blocks so much bigger than local-filesystem blocks?

بلوکِ بزرگ‌تر نسبتِ سربارِ هماهنگی و جست‌وجو به انتقالِ انبوه رو کم می‌کنه و برای خوندنِ ترتیبی مناسبه. اندازهٔ مناسب به بار و پیاده‌سازی وابسته‌ست.

مثال فنی: بلاک بزرگِ فایل توزیع‌شده

وضعیت اولیه: فرض کن فایل 1 GB با بلاک فرضی 128 MB به هشت بخش تقسیم شده.

اجرای مرحله‌به‌مرحله: حالا metadata محل کپی هر بلاک رو می‌ده و worker از یه کپی سالم می‌خونه؛ اندازهٔ بلاک رو تعداد metadata و موازی‌سازی اثر داره.

نتیجه و دلیل: بلاکِ درشت برای اسکن ترتیبی و کاهش سربار مناسبه؛ با page کوچیکِ موتور پایگاه داده هدف یکسانی نداره — همین.

Two reasons: less metadata to track (a big deal on petabyte datasets), and cheaper seeks relative to block reads. And since a DFS is implemented on the nodes' OS filesystems, the “write whole blocks” requirement vanishes: a 900MB file with 128MB blocks means seven 128MB blocks and one 4MB block.

۷. object store چه تفاوت‌هایی با فایل‌سیستم دارد؟7. How does an object store differ from a filesystem?

مخزنِ شیء با کلید و API داده رو نگه می‌داره؛ فایل‌سیستم قراردادِ فایل و پوشه و عملیاتِ متفاوتی داره. تغییرِ جزئی و تغییرنام و تضمین‌های سازگاری رو باید برای محصولِ مشخص بررسی کرد.

مثال فنی: Object یک فایل POSIX کامل نیست

وضعیت اولیه: فرض کن خروجی job با کلید reports/run-42/part-1 تو object store نوشته می‌شه.

اجرای مرحله‌به‌مرحله: حالا برای انتشارِ نسخهٔ کامل، manifest یا اشاره‌گر نسخهٔ معتبر عوض می‌شه؛ نباید rename اتمیکِ دایرکتوری رو بدون پشتیبانی فرض کرد.

نتیجه و دلیل: API و تضمین عملیات object store باید جدا بررسی بشه؛ شبیه بودن اسم «فایل» رفتار یکسان نمی‌سازه — این دام معروفه.

Objects are immutable after writing (updates = full puts); no directories exist and paths are just key-naming conventions; prefix listing is recursive like ls -R and empty directories are impossible; no links or locks, and rename is non-atomic (copy+delete). And unlike HDFS, compute and storage usually stay apart — no locality, but CPU/memory scale independently.

۸. resource manager چه می‌کند و چه ریسکی دارد؟8. What does the resource manager do, and what is its risk?

مدیرِ منابع سهمِ حافظه و پردازنده و محلِ اجرای کارها رو تعیین می‌کنه. تصمیمِ نامناسب می‌تونه گرسنگیِ کار و مصرفِ اضافی یا توقفِ هماهنگی بسازه؛ بازیابیِ خودِ مدیر هم مهمه.

مثال فنی: CPU آزاد، RAM ناکافی

وضعیت اولیه: فرض کن job برای هر task یه هسته و ۴ گیگابایت RAM درخواست می‌کنه؛ ماشین ۸ هسته و ۱۶ گیگابایت RAM داره.

اجرای مرحله‌به‌مرحله: حالا resource manager با این درخواست‌ها حداکثر چهار تا task رو هم‌زمان جا می‌ده، هرچند چهار تا هسته بیکار بمونه؛ درخواستِ کمتر از مصرف واقعی می‌تونه OOM بسازه.

نتیجه و دلیل: تخصیص منبع فقط شمردن هسته نیست؛ سهم حافظه و محدودیت هم‌زمانی و بازپس‌گیری منابع تو زمان‌بندی اثر دارن — حساب کن.

It keeps each node's metadata (available hardware, task states, network position) and gives the cluster's global view; the scheduler decides from exactly this view. Risk: its centrality can bottleneck scalability and availability; hence state is written to a coordination service like ZooKeeper or etcd.

۹. معمای ۱۶۰ هسته و دو job صدتایی چه چیزی را نشان می‌دهد؟9. What does the 160-cores, two-100-core-jobs puzzle show?

وقتی دو تا کارِ صدهسته‌ای با ۱۶۰ تا هسته رقابت می‌کنن، منابع برای خواستهٔ کاملِ هر دو کافی نیست. تقسیمِ عادلانه و پایانِ سریعِ یه کار و استفادهٔ کامل از منابع هدف‌های متفاوت‌ان.

مثال فنی: دو job روی ۱۶۰ هسته

وضعیت اولیه: فرض کن دو تا job که هرکدوم ۱۰۰ تا task تک‌هسته‌ایِ هم‌زمان تو مرحلهٔ جاری می‌خوان.

اجرای مرحله‌به‌مرحله: حالا با تقسیم ۸۰/۸۰ هر دو مرحله منتظر دو موج‌ان؛ تخصیصِ متفاوت می‌تونه یه job رو زودتر تموم کنه و منابعش رو آزاد کنه.

نتیجه و دلیل: انصاف لحظه‌ای و کمینه کردن زمان پایان همیشه یکی نیستن؛ اندازهٔ مرحله و امکان preemption تو تصمیم اثر دارن — همینه.

The fairness/efficiency balance: an 80-80 split, gang scheduling (idleness and deadlock risk), waiting for 100 free cores (starvation), or preemption (killing tasks and resuming). And at large scale optimal allocation is NP-hard; so schedulers make reasonable-but-suboptimal calls with heuristics like FIFO, DRF, priority queues, quotas and bin-packing.

۱۰. preemption چه تفاوتی با خرابیِ task دارد؟10. How does preemption differ from task failure?

فرقشون ساده‌ست: Preemption گرفتنِ برنامه‌ریزی‌شدهٔ منابع از یه وظیفه برای اولویتِ دیگه‌ست؛ خرابی توقفِ ناخواسته‌ست. هر دو ممکنه به بازیابی یا تکرار نیاز داشته باشن، ولی علت و سیاست فرق دارن.

مثال فنی: Preemption یعنی پس‌گرفتن منابع

وضعیت اولیه: فرض کن scheduler برای job فوری، task کم‌اولویت رو متوقف می‌کنه.

اجرای مرحله‌به‌مرحله: حالا task متوقف‌شده بعداً از checkpoint یا ابتدا ادامه پیدا می‌کنه؛ مثل crash باید اثر خروجی نیمه‌کاره کنترل بشه.

نتیجه و دلیل: علت توقف سیاست زمان‌بندیه، نه خرابی ماشین؛ ولی قرارداد retry و پاک‌سازی هنوز لازمه — یادت باشه.

Both take a task out of Running, but preemption is no error: the preempted task requeues penalty-free and eats no retry budget; a Failed task (crash or lost heartbeat) has its partial output deleted, spends budget, and with attempts exhausted reaches Failed Permanently. And in practice preemption (via spot capacity and priorities) is far more common than hardware faults.

۱۱. چرا بازتلاش در سطحِ task کافی است و کلِ job را دوباره اجرا نمی‌کنیم؟11. Why is task-level retry enough instead of rerunning the whole job?

اگه ورودی و خروجیِ وظیفه‌ها جدا و قابل‌بازیابی باشن، قسمتِ شکست‌خورده دوباره اجرا می‌شه. وابستگی‌ها ممکنه بخشی از کارِ بالادستی رو هم تکرار کنن؛ همیشه فقط یه وظیفه نیست.

مثال فنی: Task دوباره زمان‌بندی می‌شود

وضعیت اولیه: فرض کن از ۱۰۰ تا task، workerِ اجرای task ۳۷ خاموش می‌شه.

اجرای مرحله‌به‌مرحله: حالا scheduler task ۳۷ رو رو یه worker دیگه اجرا می‌کنه و خروجیِ attempt موفق رو می‌پذیره.

نتیجه و دلیل: کلِ job لازم نیست از صفر تکرار بشه، اگه ورودی و وابستگی‌های لازم برای همون task در دسترس باشن — غصه نخور.

Because tasks read immutable input and carry no outside side effects; rerunning them is safe. Only the broken task is rescheduled on another machine, rebuilding its output from scratch — so results never duplicate and the previous attempt's partial output was deleted.

۱۲. سه استراتژیِ مدیریتِ داده‌ی intermediate کدام‌اند؟12. What are the three intermediate-data strategies?

سه تا راهِ کلی: پایدار کردنِ خروجیِ مرحله‌ها، نگه داشتنِ موقتِ داده همراه با امکانِ محاسبهٔ مجدد، یا ثبتِ نقطهٔ بازیابی. دادهٔ میانیِ mapper تو Hadoop لزوماً تو HDFS نیست؛ خروجیِ job و دادهٔ shuffle فرق دارن.

مثال فنی: نگهداری دادهٔ میانی

وضعیت اولیه: فرض کن مرحلهٔ B به خروجی A نیاز داره و workerِ A ممکنه خاموش بشه.

اجرای مرحله‌به‌مرحله: حالا راه اول خروجی پایدار رو storageـه؛ راه دوم کپی رو چند تا worker؛ راه سوم بازساخت A از lineage.

نتیجه و دلیل: اولی I/O بیشتر، دومی هزینهٔ کپی و سومی هزینهٔ محاسبهٔ دوباره داره؛ انتخاب به هزینه و نرخ خرابی بستگی داره — حساب کن.

منبعِ توضیحِ فنی: راهنمایِ اجرا و خروجیِ میانیِ Hadoop

MapReduce: write all intermediate data to DFS and wait for the write to complete — resilient but I/O-heavy. Spark: in memory (spilling to local disk) + only the final result in DFS; recovery from lineage. Flink: periodic task-state checkpoints instead of materializing every intermediate record.

۱۳. MapReduce چهار گامش چیست و نقشِ mapper و reducer چیست؟13. What are MapReduce's four steps, and what do mapper and reducer do?

چهار تا گامِ اصلی: خوندنِ ورودی، map به کلید–مقدار، توزیع و گروه‌بندی بر کلید، و reduce برای خروجیِ هر گروه. چارچوب زمان‌بندی و انتقال رو مدیریت می‌کنه.

مثال فنی: Map، shuffle، reduce

وضعیت اولیه: فرض کن متن‌های red blue و red ورودی‌ان.

اجرای مرحله‌به‌مرحله: حالا map جفت‌های (red,1),(blue,1),(red,1) رو می‌ده؛ shuffle redها رو کنار هم می‌فرسته؛ reduce جمع red=2,blue=1 رو می‌سازه.

نتیجه و دلیل: shuffle تصادفی نیست؛ گروه‌بندیِ کلید تعیین می‌کنه همهٔ مقدارهای یه کلید به محاسبهٔ مشترک برسن — قابش کن.

1) Read files and break into records; 2) mapper: extract (key, value) per record, stateless, parallel; 3) implicit sort by key; 4) reducer: one call per key with an iterator over its values. The mapper prepares data for sorting; the reducer processes sorted data. A second sort = a second job.

۱۴. «shuffle» چیست و چرا نامش گمراه‌کننده است؟14. What is “shuffle” and why is the name misleading?

Shuffle تصادفی‌کردنِ داده نیست؛ توزیعِ دوباره بر اساسِ کلیده تا رکوردهای مرتبط به پردازشگرِ مناسب برسن. معمولاً شبکه و گاهی دیسک رو مصرف می‌کنه.

مثال فنی: Shuffle بر کلید مشتری

وضعیت اولیه: فرض کن سفارش‌های مشتری ۱۷ تو چند تا فایل و چند تا worker پراکنده‌ان.

اجرای مرحله‌به‌مرحله: حالا partitioner همهٔ جفت‌های کلید ۱۷ رو به reducer همون کلید می‌فرسته؛ داده ممکنه رو شبکه منتقل و sort بشه.

نتیجه و دلیل: تمرکزِ یه کلید برای تجمیع لازمه؛ مشتری خیلی بزرگ می‌تونه reducer داغ و زمان پایان طولانی بسازه — این دام معروفه.

The distributed-sort algorithm with sharded input and output, for petabyte data. Misleading because shuffle output is sorted, not random (unlike shuffling cards). In MapReduce: each mapper writes one sorted file per reducer (m1r2), routing by hash(key), and reducers mergesort their share. Newer engines do it in memory or with an external-sort service (with replication).

۱۵. sort-merge join چگونه کار می‌کند و چه زمانی مناسب است؟15. How does sort-merge join work, and why prefer it to hash join?

تو sort-merge، دو تا ورودی بر کلید مرتب می‌شن و بعد هماهنگ پیمایش می‌شن. برای ورودیِ مرتب یا دادهٔ بزرگ مناسبه؛ hash join هم بسته به اندازه و حافظه و طرحِ اجرا می‌تونه بهتر باشه.

مثال فنی: Sort-merge join روی دو جدول بزرگ

وضعیت اولیه: تصور کن فروش و مشتری هر دو بر customer_id تقسیم و مرتب شدن.

اجرای مرحله‌به‌مرحله: حالا دو تا جریان مرتب هم‌قدم خونده می‌شن؛ همهٔ فروش‌های کلید ۱۷ کنار ردیف مشتری ۱۷ قرار می‌گیرن.

نتیجه و دلیل: جدول hash کامل لازم نیست، ولی هزینهٔ sort/shuffle و کلیدهای خیلی پرتکرار هنوز هست — خلاص.

Both mappers publish user_id keys; shuffle brings one user's every record to one reducer, with secondary sort putting the profile (DOB) record first and events timestamp-ordered after. The reducer holds just one user record in memory and makes one streaming pass — no network lookups. Hash join must hold one whole side in a hash table; but shuffle output arrives pre-sorted, so merging is free and sort-join is the on-disk default.

۱۶. شش مزیتِ موتورِ dataflow بر MapReduce چیست؟16. What are dataflow's six advantages over MapReduce?

شش تا امکانِ مهم: مرتب‌سازیِ فقطِ لازم و ترکیبِ عملگرها و برنامه‌ریزیِ نزدیکِ داده و نگه‌داریِ مناسبِ دادهٔ میانی و عبورِ جریانیِ خروجی به مرحلهٔ بعد و استفادهٔ مجدد از فرایندها. بهرهٔ واقعی به موتور و طرح بستگی داره.

مثال فنی: ادغام عملگرهای متوالی

وضعیت اولیه: فرض کن مرحله‌های filter → map → groupBy رو داریم.

اجرای مرحله‌به‌مرحله: حالا موتور می‌تونه filter و map رو تو همون task اجرا کنه و پیش از groupBy داده رو shuffle کنه.

نتیجه و دلیل: حذف مرزِ غیرضروریِ job، فایل میانی و راه‌اندازی رو کم می‌کنه؛ مرحلهٔ نیازمند توزیعِ دوباره هنوز شبکه می‌خواد — همینو می‌خواستیم.

Sort only where needed; fusing same-sharding operators; locality optimization since the whole DAG is known; keeping intermediate state in memory/local disk; starting each operator as soon as its input is ready (pipelining); and reusing processes (MapReduce booted a fresh JVM per task).

۱۷. چرا SQL به زبانِ مشترکِ پردازشِ دسته‌ای تبدیل شد و optimizer چه می‌کند؟17. Why did SQL become batch processing's common language, and what does the optimizer do?

SQL نتیجه رو به زبونِ مشترکِ خیلی از تحلیلگرها بیان می‌کنه. بهینه‌ساز ترتیب و روشِ اجرا رو با توجه به آمار و هزینه انتخاب می‌کنه، ولی کیفیتِ طرح به اطلاعاتِ موجود وابسته‌ست.

مثال فنی: Optimizer چه تصمیمی می‌گیرد؟

وضعیت اولیه: فرض کن SQL فروش رو به کالا join می‌کنه و فقط دستهٔ book رو نگه می‌داره.

اجرای مرحله‌به‌مرحله: حالا optimizer می‌تونه فیلترِ دسته رو زودتر اعمال کنه و با آمار اندازه، نوع join رو انتخاب کنه.

نتیجه و دلیل: اعلانی بودن مسیر بهینه رو قابل‌انتخاب می‌کنه؛ آمار قدیمی یا skew می‌تونه طرح نامناسب بسازه — همین.

Because old warehouses had SQL, analytics and ETL tools supported it and everybody knew it — plus it enabled interactive querying. The cost-based optimizer translates queries into physical operators, picks the best join algorithm and even reorders joins to minimize intermediate state (Hive/Trino/Spark/Flink).

۱۸. تفاوت‌های semantic بینِ DataFrame محلی و توزیع‌شده چیست؟18. What semantic differences separate local and distributed DataFrames?

تو DataFrame توزیع‌شده، ترتیبِ سراسری و محلِ داده و زمانِ اجرا ممکنه ضمنی نباشن. عملیاتِ ظاهراً مشابه می‌تونه تنبل و موازی یا نیازمندِ shuffle باشه.

مثال فنی: DataFrame محلی یا توزیع‌شده

وضعیت اولیه: فرض کن دستور df.filter(...).groupBy(...).sum() نوشته شده.

اجرای مرحله‌به‌مرحله: حالا تو موتور توزیع‌شده ممکنه فقط plan ساخته بشه و action اجرا رو شروع کنه؛ collect() تموم خروجی رو به driver می‌آره.

نتیجه و دلیل: ظاهراً مشابه بودن API با جدول محلی به‌معنی یکسان بودن هزینه نیست؛ خروجی بزرگ می‌تونه حافظهٔ driver رو پر کنه — این دام معروفه.

The local version (R/Pandas) is usually indexed and ordered; the distributed one usually isn't — so migration can surprise ordering and performance. Plus Pandas is eager (immediate execution) while Spark is lazy (query plan + optimizer), and Daft has both: small ops on the client, big datasets on the server, with Arrow as the shared data model.

۱۹. چرا نوشتنِ مستقیمِ خروجیِ job به پایگاه دادهِ تولیدی بد است و راهِ بهتر چیست؟19. Why is writing job output straight to the production database bad, and what is better?

نوشتنِ مستقیم می‌تونه خروجیِ نیمه‌کاره و اثرِ تکراری و بارِ زیاد بسازه. نتیجه رو جدا می‌سازیم و اعتبارسنجی می‌کنیم و بعد نسخهٔ کامل رو تو مسیرِ خوندن قرار می‌دیم.

مثال فنی: انتشار ایندکس کامل

وضعیت اولیه: فرض کن job نسخهٔ search-v2 رو تو مسیر تازه می‌سازه و تعداد و کیفیت رکوردها رو می‌سنجه.

اجرای مرحله‌به‌مرحله: حالا بعد از موفقیتِ همهٔ بخش‌ها، اشاره‌گر خوندن از v1 به v2 عوض می‌شه؛ v1 برای بازگشت موقتاً می‌مونه.

نتیجه و دلیل: کاربر مخلوطِ خروجی ناقص و قدیمی نمی‌بینه؛ نوشتن مستقیمِ هر task رو ایندکس فعال این مزیت رو سخت‌تر می‌کنه — همین.

One network request per record (slow), drowning the database with parallel tasks, and destroying the all-or-nothing guarantee (outside side effects + retried-output duplication). Better: push to Kafka — sequential writes, buffering/rate control, multi-system consumption, a DMZ security boundary — plus a job-done announcement so consumers hide data like a read-committed transaction until completion is announced. The other pattern: bulk-load a fresh database + an atomic dataset-version switch.

۲۰. اگر قرار باشد فقط یک جمله از این فصل بگویی، کدام است؟20. If you had one sentence from this chapter, which?

پردازشِ دسته‌ای ورودیِ مشخص رو به خروجیِ قابل‌بازسازی تبدیل می‌کنه. جداسازیِ تلاش‌های ناقص و انتشارِ نسخهٔ کامل، به تحملِ خرابی و اصلاحِ منطق کمک می‌کنه.

مثال فنی: بازمحاسبهٔ گزارش از ورودی ثابت

وضعیت اولیه: فرض کن فایل فروش ۱۴ مهر بسته شده و نسخهٔ ورودی معلومه.

اجرای مرحله‌به‌مرحله: حالا job مجموع فروش هر شعبه رو تو خروجی نسخهٔ v2 می‌نویسه؛ اگه فرمول غلط بود، با کد اصلاح‌شده از همون ورودی دوباره اجراش می‌کنیم.

نتیجه و دلیل: ورودی immutable و خروجی نسخه‌داره، پس خطای محاسبه قابل‌بازسازیه؛ بازنویسی مستقیمِ دادهٔ مرجع همچین آزادی‌ای نمی‌ده — همین.

“Batch processing means turning immutable input into derived output from scratch; that contract makes task retries safe, errors recoverable and publication all-or-nothing — and for scale, spread the work with shuffle (distributed sorting) across independent tasks.”

۶.۳. اشتباهات رایج در جواب‌های مصاحبه6.3. Common mistakes in interview answers

  • ❌ «batch یعنی داده رو دسته‌ای آپدیت می‌کنیم.» → ✅ نه؛ ورودیِ job immutableـه و خروجی از صفر ساخته می‌شه؛ job به دادهٔ موجود دست نمی‌زنه.
  • ❌ «shuffle یعنی داده رو تصادفی پخش می‌کنیم.» → ✅ shuffle خروجیِ مرتب می‌ده؛ پایهٔ join و groupingـه، نه تصادف.
  • ❌ «برای هر تغییرِ ورودی، فقط بخشِ تغییرکرده رو پردازش می‌کنیم.» → ✅ تو مدلِ کلاسیکِ دسته‌ای، حتی یه بایت تغییر یعنی پردازشِ دوبارهٔ کلِ ورودی.
  • ❌ «task که شکست خورد، job رو از اول اجرا می‌کنیم.» → ✅ بازتلاش تو سطحِ taskـه؛ کلِ job فقط وقتی شکست می‌خوره که taskها با budget تموم‌شده بمونن.
  • ❌ «preempted یعنی failed.» → ✅ preemption خطا نیست: task بدونِ جریمه دوباره صف می‌شه؛ فقط Failed از budget بازتلاش می‌خوره.
  • ❌ «خروجیِ job هم‌زمان با نوشتنِ shardها دیده می‌شه.» → ✅ خروجی تا اعلانِ پایانِ job پنهونه (all-or-nothing و read-committed reveal).
  • ❌ «برای انتشار، مستقیم رکوردرکورد به پایگاه دادهٔ تولیدی می‌نویسیم.» → ✅ کند و غرق‌کننده و ناقص‌کنندهٔ all-or-nothing؛ راهِ درست push به جریان یا bulk-load + سوییچِ اتمیکه.
  • ❌ «object store هم فایل‌سیستمه؛ rename و قفل هم داره.» → ✅ rename غیراتمیکه (کپی+حذف)، link و قفل نداره و دایرکتوریِ خالی ممکن نیست.
  • ❌ «scheduler می‌تونه تخصیصِ بهینهٔ منابع رو حساب کنه.» → ✅ مسئله NP-hardـه؛ فقط heuristics (FIFO و DRF و quota و bin-packing) داریم.
  • ❌ «workflow این‌جا همون durable execution فصل ۵ـه.» → ✅ این‌جا یعنی DAG از jobهای دسته‌ای با دادهٔ ورودی/خروجی، معمولاً بدونِ RPC.
  • ❌ «DataFrame توزیع‌شده دقیقاً مثل Pandas رفتار می‌کنه.» → ✅ ایندکس و ترتیبِ نسخهٔ محلی رو نداره و lazyـه (query plan) — مهاجرت غافلگیری داره.
  • ❌ «HDFS و S3 از نظرِ معماری یکی‌ان.» → ✅ HDFS اجرای نزدیکِ داده (locality) می‌ده؛ object storeها compute و storage رو جدا می‌کنن و تضمین‌های متفاوتی دارن.
  • ❌ “Batch means updating data in batches.” → ✅ Nope; job input is immutable and output is built from scratch — the job never touches existing data.
  • ❌ “Shuffle means scattering data randomly.” → ✅ Nope; shuffle yields sorted output — it underpins joins and grouping, not randomness.
  • ❌ “For each input change, we only process the changed part.” → ✅ In the classic batch model, even one changed byte means reprocessing the whole input.
  • ❌ “When a task fails, we rerun the job from the start.” → ✅ Retries are task-level; the whole job fails only when tasks remain with budgets spent.
  • ❌ “Preempted means failed.” → ✅ Nope; preemption is no error — the task requeues penalty-free, and only Failed eats retry budget.
  • ❌ “Job output is visible while shards are being written.” → ✅ Output stays hidden until the job-done announcement (all-or-nothing, read-committed reveal).
  • ❌ “For publication we write record by record straight to the production DB.” → ✅ Slow, drowning, and all-or-nothing-breaking; push to a stream or bulk-load + atomic switch instead.
  • ❌ “An object store is a filesystem too; it has rename and locks.” → ✅ Rename is non-atomic (copy+delete), no links or locks exist, and empty directories are impossible.
  • ❌ “The scheduler can compute the optimal resource allocation.” → ✅ The problem is NP-hard; only heuristics (FIFO, DRF, quotas, bin-packing) exist.
  • ❌ “Workflow here is Chapter 5's durable execution.” → ✅ Here it means a DAG of batch jobs with input/output data, usually no RPC.
  • ❌ “A distributed DataFrame behaves exactly like Pandas.” → ✅ It lacks the local version's indexing and ordering and is lazy (query plan) — migration surprises.
  • ❌ “HDFS and S3 are architecturally one thing.” → ✅ HDFS gives near-data execution (locality); object stores separate compute and storage with different guarantees.

تمرین ۲ — sort-merge join روی دو فایلِ بزرگ‌تر از حافظهExercise 2 — sort-merge join on two bigger-than-memory files

L2 · SeniorL2 · Seniorوابسته به نقشRole-specific40 دقیقه بحث40 min discussion

تصور کن دو جریان جدا داری که فقط با user_id مرتب می‌شن و به‌ازای هر کاربر یه پروفایل یکتا داری. mixed reducer هم بدون profile-first ordering یا buffering جمع نمی‌شه.Think of it, you've got two separate streams sorted only by user_id with one unique profile per user. And your mixed reducer won't work without profile-first ordering or buffering.

نسخهٔ بازبینی‌شده برای مصاحبهReviewed interview brief

تصور کن کلیک‌های بزرگ داری و به‌ازای هر user فقط یه پروفایل یکتا. هر دو جریان جدا رو با external sort برحسب user_id مرتب کن و با streaming merge join بچسبونشون. یادت باشه null و missing profile و skew رو تعریف کنی. بعد جریان mixed reducer رو بذار کنارش که توش profile-first secondary sort یا buffering لازمه، و بگو قرارداد این دو مدل چه فرقی داره.Think of it, you've got huge clicks and just one unique profile per user. You externally sort both separate streams by user_id and join them with a streaming merge join. You define null and missing profiles plus skew. Then you contrast that with a mixed reducer stream where you need profile-first secondary sort or buffering, and you explain why the two contracts differ.

معیار پاسخ خوبWhat a good answer demonstrates

  • sort بزرگ‌تر از حافظه رو با spill واقعی روی دیسک انجام می‌دیYou spill a bigger-than-memory sort to disk for real
  • uniqueness پروفایل و join type رو مشخص می‌کنیYou pin down profile uniqueness and the join type
  • دو sorted stream جدا رو با mixed reducer قاطی نمی‌کنیYou don't confuse two sorted streams with a mixed reducer

پیگیری مصاحبه:Interview follow-up: اگه به‌ازای هر user چند نسخه تاریخی از پروفایل داشته باشی، کلیک باید به کدوم نسخه بچسبه؟With multiple historical profiles per user, which version should a click join to?

Externally sort both by user_id with real disk spills, then left-join them with two cursors; emit NULL and a metric for missing profiles. Explain why the join needs only O(1) profile state while you still account for sort memory and merge fan-in separately. Then build a mixed reducer stream where clicks arrive before profiles, and compare buffering cost against profile-first secondary sort. Timestamp order matters only if your output contract demands it. Test skew and duplicate profiles with an explicit reject or aggregation policy.

تمرین ۳ — یک shuffle سادهExercise 3 — a mini shuffle

L3 · Staff / PrincipalL3 · Staff / Principalوابسته به نقشRole-specific40 دقیقه بحث40 min discussion

قضیه اینه که shuffle و skew برای کارت تو data infra مهمه. ولی لازم نیست همه فایل‌ها رو از صفر بسازی؛ اون بخش، لب اختیاری طولانیه.Here's the thing, shuffle and skew really matter for your data-infra work. But you don't have to build every file from scratch; that's an optional extended lab.

نسخهٔ بازبینی‌شده برای مصاحبهReviewed interview brief

قضیه اینه که می‌خوای shuffle برای group-by بسازی. partition یکسان، sort محلی و merge تو reducer رو طراحی کن. حساب کن hot key، حجم شبکه، combiner و checksum فایل میانی چی می‌شن. حالا خروجی یه mapper خراب می‌شه؛ بگو دقیقاً چی رو بر اساس کدوم lineage دوباره اجرا می‌کنی.Here's the thing, you're building the shuffle for a group-by. You design identical partitioning, mapper-local sorting, and the reducer merge. You work through hot keys, network volume, the combiner, and checksums on intermediate files. Then one mapper's output corrupts, so you say exactly what you rerun and which lineage makes it safe.

معیار پاسخ خوبWhat a good answer demonstrates

  • hash رو تو همه workerها ثابت و مشترک نگه می‌داریYou keep one stable shared hash across workers
  • retry هر mapper رو با attempt جدا و ایزوله اجرا می‌کنیYou isolate each mapper retry in its own attempt
  • side effect بیرونی رو وسط replay راه نمی‌دی چون قرارداد رو می‌شکنهYou keep external side effects out so your retries stay deterministic and safe

پیگیری مصاحبه:Interview follow-up: یه key نصف داده رو داشته باشه، چطور reducer رو از hotspot نجات می‌دی؟One key holds half your records. How do you save your reducer from the hotspot?

یه shuffle چند-worker بنویس: N کارگر که رکوردها رو با hash(key) % N partition می‌کنن، هر worker به‌ازای هر partition یه فایل مرتب می‌نویسه (مثل m1r2)، و مرحله reduce فایل‌های هر partition رو mergesort می‌کنه. روی داده نمونه تست کن که همه رکوردهای هم‌کلید کنار هم برسن. سوال: اگه یه فایل میانی یه worker خراب بشه، برای ادامه job دقیقاً چی رو دوباره اجرا می‌کنی — و چرا اجراش امنه؟

Write a multi-worker shuffle: N workers partitioning records by hash(key) % N, each worker writing one sorted file per partition (like m1r2), with the reduce stage mergesorting each partition's files. Test on sample data that same-key records all land together. Question: if one worker's intermediate file corrupts, what exactly do you rerun to continue the job — and why is rerunning it safe?

L3 · Staff / PrincipalL3 · Staff / Principalوابسته به نقشRole-specific40 دقیقه بحث40 min discussion

داستان از این قراره که publication اتمیک واقعاً به کارت میاد. ولی یادت باشه rename تو فایل‌سیستم محلی رو بی‌قید به object storage تعمیم ندی.Honestly, atomic publication is genuinely useful for you. But don't assume your local rename semantics carry over to object storage.

نسخهٔ بازبینی‌شده برای مصاحبهReviewed interview brief

داستان از این قراره که یه job چندtaskی روی ورودی immutable داری. attempt output جدا و manifest نسخه‌دار طراحی کن. crash وسط write و قبل از publish تزریق کن. یادت باشه خواننده باید همیشه یه نسخه کامل و ثابت ببینه؛ CAS و atomic pointer و cleanup و retry رو متناسب با همون storage خودت انتخاب کن.Honestly, you've got a multi-task job over immutable inputs. معیار پاسخ خوبWhat a good answer demonstrates

  • task commit رو با job publish قاطی نمی‌کنیYou separate task completion from job publication
  • خواننده manifest رو یه بار pin می‌کنه و باهاش کار می‌کنهYou let each reader pin one manifest version
  • partial attempt و نسخه قدیمی رو امن جمع می‌کنیYou clean up partial attempts and old versions safely

پیگیری مصاحبه:Interview follow-up: دو job هم‌زمان روی یه نام خروجی publish کنن، کدوم نسخه برنده می‌شه؟Two jobs publish to the same output name at once. Which version wins?

آزمایشگاه تکمیلی · زمان تقریبی ۳–۶ ساعتExtended hands-on laboratory · estimated 3–6 hours

یه job چندtaskی بساز که shardهای ورودی immutable رو به shardهای خروجی تبدیل می‌کنه. بعد یه «خراب‌کننده» اضافه کن: با یه احتمال مشخص، وسط نوشتن خروجی یه task بمیره. منطق retry رو پیاده کن: خروجی ناقص رو پاک کن، task رو دوباره اجرا کن، و فقط وقتی همه موفق شدن commit کن. آخرش تست کن: خواننده یا «کل نتیجه» رو می‌بینه یا هیچی، حتی با چند خرابی وسط راه. سوال: اگه به‌جای پاک‌کردن خروجی ناقص نگهش داری و task رو دوباره اجرا کنی، چه نتیجه‌ای ممکنه بگیری؟
