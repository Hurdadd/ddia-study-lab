سؤال مصاحبهInterview question
فرض کن لاگت از RAM بزرگ‌تره و قراره top URLها رو دربیاری. حساب کن hash aggregation کجا جواب می‌ده و کجا external sort. یادت باشه cardinality، سقف RAM، spill، هزینه I/O و approximate counting رو شفاف کنی. بنچمارکتت هم باید ورودی و خروجی برابر با memory cap مشخص داشته باشه، و آستانه شکست رو فقط برای همون محیط خودت گزارش کنی.
Picture this, your logs don't fit in RAM and you've got to find the top URLs. You compare hash aggregation against external sort, and you spell out cardinality, your RAM cap, spill behavior, I/O cost, and approximate counting. You run a fair benchmark with equal outputs under one stated memory cap, and you report the breaking point for your own setup only.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قضیه اینه که وقتی working set ممکنه از RAM بگذره، پیش‌فرضت external sort باشه: یه chunk کران‌دار توی حافظه، runهای مرتب که روی دیسک spill می‌شن، و ادغام k-way که شمارش رو جاری می‌کنه. این مسیر همیشه تموم می‌شه — به‌جای مردن، با I/O کُند می‌شه. تجمیع hash رو نگه دار تا وقتی کلیدهای متمایز راحت توی RAM جا می‌شن. دست فقط وقتی ببر که top-100 تقریبی صریح مجاز شده باشه. تریدآف اصلی زمان در برابر قطعیته: sort برای اینکه تضمین کنه تموم می‌شه، I/O اضافه می‌پردازه. — یادت باشه: hash تا وقتی جا می‌شه، sort از لحظه‌ای که جا نمی‌شه.
Here's the thing: when the working set may exceed RAM, make external sort your default. Keep one bounded chunk in memory, spill the sorted runs to disk, and let a k-way merge stream the counts — that path always finishes, and when RAM runs out it slows down with I/O instead of dying. Stick with hash aggregation while the distinct keys comfortably fit in RAM. Reach for a sketch only when an approximate top-100 is explicitly allowed. The top trade-off is time versus certainty: sort pays extra I/O to buy the guarantee of finishing. Remember the rule: hash while it fits, sort once it doesn't.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن یه لاگ آموزشی داریم: ۲۰۰٬۰۰۰ خط با ۱۹٬۷۸۲ URL متمایز (محبوبیت چوله). همه‌اش از دموی قابل‌اجرای پایین میاد — نه بنچمارک پروداکشن.
  • سقف حافظه از اول اعلام شده: یه chunk بیست‌هزارخطی توی RAM می‌نشینه؛ هرچی از این بیشتر بشه باید به فایل موقت spill بشه.
  • top-5 دقیق لازمه؛ حالت تقریبی یه رژیم جداست با بودجهٔ خطای خودش.
  • قضیه اینه که: تک‌ماشین با دیسک موقت محلی داریم؛ shuffle توزیع‌شده مال تمرین‌های بعدیه.
  • Picture a teaching log: 200,000 lines with 19,782 distinct URLs (skewed popularity). All of it comes from the runnable demo below — not a production benchmark.
  • The memory cap is stated up front: one 20,000-line chunk in RAM. Anything past that has to spill to temp files.
  • You need an exact top-5; the approximate variant is a separate regime with its own error budget.
  • Here's the thing: a single machine with local temp disk — distributed shuffle belongs to the next exercises.

چرا این روش و این عددها؟Why this method and these numbers?

چرا این مدل به این تمرین می‌خوره: hash aggregation برای U کلید متمایز، state متناسب U می‌خواهد؛ زیادشدن تعداد خطوط با U ثابت همان رشد حافظه را ندارد. external sort با chunk محدود، بقیه را روی دیسک می‌برد و IO را به جای RAM می‌پردازد. ۲۰۰هزار خط و chunk بیست‌هزار باعث spill قابل مشاهده می‌شود؛ این اعداد آستانهٔ عمومی نیستند. زمان را همراه peak memory و حجم temporary بنویس تا طرح سریع‌تر ولی خارج از بودجه، برنده معرفی نشود.

Why this model fits: hash aggregation holds state proportional to distinct keys U; more lines with fixed U do not have the same memory growth. External sorting bounds RAM by spilling chunks and paying disk I/O. Two hundred thousand lines and 20k-line chunks force visible spills, not a universal threshold. Compare time with peak memory and temporary bytes, so a design that blows the budget doesn't win on speed alone.

مدل ذهنیMental model

شمارش رو این‌جوری ببین: یه انبوه کلید داری و می‌خوای بفهمی کدوم‌ها برابرن. hash می‌گه هر کلید یه شمارنده توی RAM داره، پس هرچه کلید متمایز بیشتر بشه، حافظه هم بیشتر می‌شه. sort راه دیگه‌ست: برابرها رو روی دیسک کنار هم می‌چینه. حالا working set — یعنی کلیدهای متمایز ضربدر سربار هر ورودی — تعیین می‌کنه کدوم راه اصلاً جا می‌شه.
Picture a pile of keys and one job: finding the equals. Hashing does it in RAM, with a counter per distinct key, so more distinct keys means more memory. Sorting does it on disk, lining the equals up side by side. The working set — distinct keys times the per-entry overhead — is what tells you which of the two actually fits.

حل گام‌به‌گامStep by step

  1. اول working set رو حساب کن قبل از هر چیز: کلیدهای متمایز رو در سربار هر ورودی ضرب کن. این حاصل همون working set‌ه و همین — نه جمع خط‌ها — تصمیم می‌گیره hash جا می‌شه یا نه.
  2. hash، ولی با راه فرارِ spill بعدش پارتیشن‌های داغ رو بفرست سراغ شمارنده‌های RAM و سردها رو سراغ فایل‌های spill مرتب. آخرش هر دو با شمارش دقیق روی یک ranker همگرا می‌شن.
  3. sort که همیشه تموم می‌شه حالا نوبت مسیر sort: chunkهای کران‌دار رو مرتب کن، runها رو spill کن، با O(run) خط توی RAM ادغام k-way کن، برابرهای مجاور رو بشمار و top-K رو رتبه بده.
  4. بنچمارک با خروجی برابر اینجا نباید عجله کنی: ورودی، سقف و K رو فیکس کن، top-K یکسان هر دو مسیر رو assert کن و بعد تازه زمان و بایت spill رو مقایسه کن. دموی پایین دقیقاً همین رو می‌کنه.
  5. تقریب، دقت رو شل می‌کنه اگه فقط top-100 تقریبی خواسته شد، بهش بودجه خطا بده و sketch یا نمونه‌برداری-بعد-شمارش رو بردار: حافظه کوچک در برابر خطای کران‌دار.
  1. Start with the working set First things first: multiply the distinct keys by the per-entry overhead. That product is the working set, and it's the working set — not the total line count — that decides whether hash fits in RAM.
  2. Hash with a spill escape Then route the hot partitions into RAM counters and the cold ones into sorted spill files. Both paths end up on one ranker, with exact counts.
  3. Sort that always finishes Now the sort path: sort the bounded chunks, spill the runs, k-way merge with O(runs) lines in RAM, count the adjacent equals, and rank the top-K.
  4. Benchmark equal outputs Slow down here: fix the input, the cap and K, assert that both paths print the same top-K, and only then compare time and spill bytes. The demo below does exactly that.
  5. Approximation relaxes exactness If the ask is only an approximate top-100, hand it an error budget and pick a sketch or sample-then-count: tiny memory in exchange for a bounded error.

طراحی مشخصConcrete design

مرحله‌ها: extract (URL هر خط) ← partition-or-chunk (RAM کران‌دار) ← spill store (runهای مرتب روی دیسک موقت) ← merge (k-way با یک خط به‌ازای هر run در RAM) ← rank (heapِ top-K).

پیکربندی: یک chunk_cap صریح (خط یا بایت) — همین سقفی است که بقیهٔ طراحی را کوچک نگه می‌دارد؛ دایرکتوری spill با رزرو فضای آزاد؛ seed قطعی برای سازنده آموزشی.

قراردادها: runها مرتب و checksummedاند؛ ادغام O(run) خط نگه می‌دارد نه O(url)؛ ranker فقط K ورودی نگه می‌دارد؛ هر دو مسیر برای ورودی یکسان top-K یکسان می‌دهند — و همین آخری است که بنچمارک را منصفانه می‌کند.

Stages: extract (URL per line) → partition-or-chunk (bounded RAM) → spill store (sorted runs on temp disk) → merge (k-way, one line per run in RAM) → rank (top-K heap).

Config: one explicit chunk_cap (lines or bytes) — that single cap is what keeps the rest of the design small; spill directory with free-space reserve; deterministic seed for the teaching generator.

Contracts: runs are sorted and checksummed; the merge holds O(runs) lines, never O(urls); the ranker keeps K entries; both paths emit identical top-K for identical input — and that last one is what makes the benchmark fair.

همون لاگ، ولی این‌بار از مسیر sort. پنج مرحله رو دنبال کن: استخراج، مرتب‌سازی یه chunk، spill کردن runها، ادغام-شمارش و رتبه‌بندی.
Same log, now through the sort path. Follow the five stages: extract, sort one chunk, spill the runs, merge and count, rank.
  1. مرتب‌سازی chunk: هر chunk کران‌دار توی RAM مرتب می‌شه، نوشته می‌شه و فراموش می‌شه.
  2. فایل‌های run: دیسک همهٔ runهای مرتب رو نگه می‌داره؛ ترافیک کل خطی با ورودی می‌مونه.
  3. ادغام به‌علاوه شمارش: یه خط به‌ازای هر run توی RAM، همسایه‌های برابر همون‌جا شمرده می‌شن و بعد رتبه‌بندی.
  1. Chunk sort: each bounded chunk gets sorted in RAM, written out, then forgotten.
  2. Run files: the disk holds every sorted run, and the total traffic stays linear in the input.
  3. Merge plus count: one line per run in RAM, equal neighbours counted on the fly, then ranked.

نقطهٔ تصمیم: نقطهٔ تصمیم اندازهٔ chunkه: chunk بزرگ‌تر یعنی run کمتر و ادغام ارزان‌تر — با RAM تنظیم می‌شه، هرگز حدسی نیست.

رد خرابی: اگه دیسک وسط spill پر بشه، job می‌افته: رزرو فضا و شمارندهٔ run می‌گیرنش. run کوتاه‌شده بی‌صدا شمارش رو خراب می‌کنه — checksum اون سوراخ رو می‌بنده.

تضمین نشان‌داده‌شده: شکل نشون می‌ده RAM دقیقاً یه chunk به‌علاوه یه خط به‌ازای هر run نگه می‌داره — O(run)، هرگز O(url). سرعت رو قول نمی‌ده: گلوگاه آشکارا می‌ره سراغ نرخ ترتیبی دیسک.

تضمین نشان‌نداده‌شده: فقط یه ماشین رو پوشش می‌ده: ادغام توزیع‌شده، stragglerها و spill روی object store بیرون این قاب‌ان.

Decision point: The decision point is the chunk size: bigger chunks mean fewer runs and a cheaper merge, tuned against RAM and never guessed.

Failure trace: A disk-full spill fails the job mid-run: the reserve and the run counter catch it. A silently truncated run would corrupt counts — checksums close that hole.

Guarantee shown: The figure shows RAM holding exactly one chunk plus one line per run — O(runs), never O(urls). It doesn't promise speed: the bottleneck visibly moves to sequential disk rates.

Not shown: It covers one machine only: distributed merge, stragglers and object-store spills are outside this frame.

گزینه‌های جایگزینAlternatives

  • تجمیع hash کاملاً درون‌حافظه، بدون مسیر spill: تا وقتی working set جا بشه سریع‌ترین گزینه‌ست، ولی اولین ورودیِ بزرگ‌تر job رو با OOM می‌کشه نه کُندش. نگهش دار فقط پشت نگهبانِ cardinalityِ اندازه‌گیری‌شده و با fallback به spill.
  • sketch به‌علاوه heap (مثلاً count-min با heapِ top-K): حافظه کوچک کران‌دار و فقط یک pass، ولی جواب‌ها تقریبی‌ان با کران خطای اعلام‌شده. می‌بره فقط وقتی مصاحبه صریحاً top-100 تقریبی رو مجاز کرده باشه.
  • Pure in-memory hash with no spill path: the fastest thing you can run while the working set fits, but the first oversized input kills the job with OOM instead of slowing it down. Keep it only behind a measured cardinality guard, with a spill fallback.
  • Sketch plus heap (say count-min with a top-K heap): tiny bounded memory and a single pass, but the answers are approximate with a stated error bound. It only wins when the interview explicitly allows an approximate top-100.

سناریوهای خرابیFailure scenarios

  • خواندن OOM به‌جای کُندی: jobِ hash به‌جای افت می‌میرد. نگهبان‌ها: سقف صریح، مسیر spill و هشدار روی نسبت spill — و یادت باشه OOM یه جواب غلطه، نه یه جواب کُند.
  • پر شدن دیسک وسط spill: runها دیگه نمی‌نشینن و ادغام یه مجموعه ناقص می‌خونه. نگهبان: رزرو فضای spill، checksum per-run و fail-fast به‌جای کوتاه‌شدن بی‌صدا.
  • بنچمارک نابرابر: ورودی، سقف یا K متفاوت روی دو مسیر، مقایسه رو بی‌معنا می‌کنه. نگهبان: اول ورودی، سقف و K رو فیکس کن، top-K یکسان رو assert کن، بعد برو سراغ زمان‌گیری.
  • Misreading OOM as slowness: the hash job dies instead of degrading. Guard with an explicit cap, a spill path, and an alert on the spill ratio — and remember OOM is a wrong answer, not a slow one.
  • Disk-full mid-spill: the runs stop landing and the merge reads a truncated set. Guard with a spill-space reserve, per-run checksums, and fail-fast instead of silent truncation.
  • An unequal benchmark: different inputs, caps or K across the two paths make the comparison meaningless. Guard by fixing the input, the cap and K, asserting the identical top-K, and only then timing.

import java.util.*;

// Teaching demo: top-K URLs two ways under a stated memory cap.
// Hash aggregation keeps one counter per distinct URL (working set grows
// with cardinality); external sort keeps one bounded chunk in RAM and
// spills sorted runs to temp files, then k-way merges them.
// Both paths must print the SAME top-5: equal outputs, stated cap.
public class TopUrlsDemo {
    static final int LINES = 200_000, DISTINCT = 20_000, TOP = 5, CHUNK = 20_000;

    public static void main(String[] a) throws Exception {
        Random rnd = new Random(11);
        String[] urls = new String[DISTINCT];
        for (int i = 0; i < DISTINCT; i++) urls[i] = "/p/" + i;
        // Skewed popularity: low ids are hotter (like real logs).
        List<String> log = new ArrayList<>(LINES);
        for (int i = 0; i < LINES; i++)
            log.add(urls[(int) (DISTINCT * Math.pow(rnd.nextDouble(), 3.0))]);

        // Path A: hash aggregation (working set = DISTINCT counters).
        Map<String, Integer> counts = new HashMap<>();
        for (String u : log) counts.merge(u, 1, Integer::sum);
        List<Map.Entry<String, Integer>> ha = new ArrayList<>(counts.entrySet());
        ha.sort((x, y) -> y.getValue().compareTo(x.getValue()));

        // Path B: external sort with a bounded in-RAM chunk.
        List<java.nio.file.Path> runs = new ArrayList<>();
        List<String> chunk = new ArrayList<>(CHUNK);
        for (String u : log) {
            chunk.add(u);
            if (chunk.size() == CHUNK) runs.add(spill(chunk));
        }
        if (!chunk.isEmpty()) runs.add(spill(chunk));
        // K-way merge over run files, counting adjacent-equal runs.
        List<RunReader> rs = new ArrayList<>();
        for (java.nio.file.Path p : runs) rs.add(new RunReader(p));
        PriorityQueue<RunReader> pq = new PriorityQueue<>(Comparator.comparing(r -> r.head));
        for (RunReader r : rs) if (r.head != null) pq.add(r);
        List<String> topUrls = new ArrayList<>();
        List<Integer> topCounts = new ArrayList<>();
        String cur = null;
        int curN = 0;
        long spilledBytes = 0;
        for (java.nio.file.Path p : runs) spilledBytes += java.nio.file.Files.size(p);
        while (!pq.isEmpty()) {
            RunReader r = pq.poll();
            String u = r.head;
            r.advance();
            if (r.head != null) pq.add(r);
            if (u.equals(cur)) { curN++; continue; }
            if (cur != null) tally(topUrls, topCounts, cur, curN);
            cur = u; curN = 1;
        }
        if (cur != null) tally(topUrls, topCounts, cur, curN);
        for (RunReader r : rs) r.close();

        System.out.println("lines=" + LINES + " distinct=" + counts.size()
            + " chunk_cap=" + CHUNK + " runs=" + runs.size()
            + " spilled_bytes=" + spilledBytes);
        for (int i = 0; i < TOP; i++)
            System.out.println("hash[" + i + "]=" + ha.get(i).getKey() + ":" + ha.get(i).getValue()
                + " sort[" + i + "]=" + topUrls.get(i) + ":" + topCounts.get(i));
        boolean same = true;
        for (int i = 0; i < TOP; i++)
            same &= ha.get(i).getKey().equals(topUrls.get(i))
                && ha.get(i).getValue().equals(topCounts.get(i));
        System.out.println("equal_top" + TOP + "=" + same);
        System.out.println("OK");
    }

    static java.nio.file.Path spill(List<String> chunk) throws Exception {
        Collections.sort(chunk);
        java.nio.file.Path p = java.nio.file.Files.createTempFile("run", ".txt");
        java.nio.file.Files.write(p, chunk);
        chunk.clear();
        return p;
    }

    static void tally(List<String> urls, List<Integer> counts, String u, int n) {
        int i = 0;
        while (i < counts.size() && counts.get(i) > n) i++;
        if (i < TOP) { urls.add(i, u); counts.add(i, n); }
        if (urls.size() > TOP) { urls.remove(TOP); counts.remove(TOP); }
    }

    static class RunReader {
        java.io.BufferedReader br; String head;
        RunReader(java.nio.file.Path p) throws Exception {
            br = java.nio.file.Files.newBufferedReader(p);
            p.toFile().deleteOnExit();
            advance();
        }
        void advance() throws Exception { head = br.readLine(); if (head == null) br.close(); }
        void close() throws Exception { br.close(); }
    }
}

روی ورودی مشترک، top-K یکسانِ هر دو مسیر رو assert کن؛ با سقف chunk و شمارش readerهای باز assert کن RAM ادغام O(run) می‌مونه؛ بایت spill و زمان هر اجرا رو ثبت کن؛ وقتی نسبت spill از آستانه تنظیم‌شده گذشت هشدار بده؛ بعد از هر تغییر سقف یا فرمت، چک برابری رو دوباره اجرا کن.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (سینیور): حالا فقط top-100 تقریبی بخوای، کدوم قید رو شل می‌کنی؟Follow-up (Senior): If you only need an approximate top-100, which constraint do you relax?

دقت رو شل کن، نه انضباط حافظه رو: sketchِ count-min با heapِ top-K (یا اول نمونه‌برداری، بعد شمارش دقیق بازمانده‌ها) خطای کران‌دار رو با حافظه کوچک عوض می‌کنه. بودجه خطا رو با همون واحد گزارش نام ببر، سقف و چک برابری روی نمونه‌ها رو نگه دار و بگو تقریب حق سرو کدوم کوئری‌ها رو نداره (صورت‌حساب، آستانه‌های سوءاستفاده).

Relax the exactness, not the memory discipline: a count-min sketch with a top-K heap (or sampling first, then exact-counting the survivors) trades a bounded error for tiny memory. Name the error budget in the same units as the report, keep the cap and the equality check on samples, and say which queries the approximation must never serve (billing, abuse thresholds).

پیگیری (سینیور): ورودی ده برابر بشه ولی کلیدهای متمایز ثابت بمونن — چی عوض می‌شه؟Follow-up (Senior): Input grows tenfold but distinct keys stay flat — what changes?

هر بار فقط یک متغیر رو عوض کن و سطر رو دوباره گزارش بده: ۱۰ برابر خط با cardinality ثابت فقط مسیر sort رو خطی طولانی می‌کنه، ولی ۱۰ برابر کلید متمایز مسیر hash رو از سطر اول می‌بره به دوم. جواب صادق اینه که بنچمارک خروجی‌برابر رو دوباره اجرا کنی، نه اینکه برون‌یابی کنی.

Change one variable at a time and re-report the row: 10x lines with the same cardinality only lengthen the sort path linearly, while 10x distinct keys push the hash path from the first row into the second. The honest answer re-runs the equal-output benchmark instead of extrapolating.

اشتباهات رایجCommon mistakes

  • نقل آستانه عمومی برای URL متمایز («hash در N میلیون URL می‌شکند»): نقطهٔ spill به سربار ورودی، سقف heap و دیسک همون ماشین وابسته‌ست — per-environment اندازه بگیر و هرگز ثابت نقل نکن.
  • خواندن OOM به‌جای کُندی عادی: jobِ hash بعد از RAM دیر تموم نمی‌شه — می‌میره. مسیر spill و هشدار رو قبل از رسیدن ورودی بزرگ طراحی کن.
  • بنچمارک کار نابرابر: ورودی، سقف حافظه یا K متفاوت، بعد اعلام برنده. اول ورودی، سقف و K رو فیکس کن، خروجی یکسان رو assert کن، بعد زمان رو مقایسه کن.
  • Quoting a universal distinct-URL threshold ('hash breaks at N million URLs'). The spill point depends on the entry overhead, the heap cap and the disk on that machine — measure it per environment, never quote it as a constant.
  • Treating OOM as ordinary slowness. A hash job past RAM doesn't finish late — it dies. Design the spill path and the alert before the big input arrives.
  • Benchmarking unequal work: different inputs, memory caps or K, then declaring a winner. Fix the input, the cap and K first, assert the identical outputs, and only then compare time.

سؤال مصاحبهInterview question
تصور کن کلیک‌های بزرگ داری و به‌ازای هر user فقط یه پروفایل یکتا. هر دو جریان جدا رو با external sort برحسب user_id مرتب کن و با streaming merge join بچسبونشون. یادت باشه null و missing profile و skew رو تعریف کنی. بعد جریان mixed reducer رو بذار کنارش که توش profile-first secondary sort یا buffering لازمه، و بگو قرارداد این دو مدل چه فرقی داره.
Think of it, you've got huge clicks and just one unique profile per user. You externally sort both separate streams by user_id and join them with a streaming merge join. You define null and missing profiles plus skew. Then you contrast that with a mixed reducer stream where you need profile-first secondary sort or buffering, and you explain why the two contracts differ.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

فرض کن دو فایل داری که هرکدوم از حافظه بزرگ‌ترن. هر دو رو با spill واقعی بر اساس user_id مرتب بیرونی کن، بعد با نگه‌داشتن حداکثر یک پروفایل، دو cursor رو ادغام جاری کن: تساوی (url, dob) می‌ده و کلیک‌های بدون پروفایل NULL شمارش‌شده می‌شن. دو جریان مرتبِ جدا فقط ترتیب کلید join رو لازم دارن — secondary sortِ profile-first مال قرارداد mixed-reducer است، نه این‌جا. تریدآف اصلی I/O در برابر حافظه کران‌داره: دو sort کامل ترافیک دیسک می‌پردازن تا حالت join از نوع O(1) تضمین بشه. — اگه حافظه‌ات کمه، این راه خودش رو جمع می‌کنه.
Here's the plan: sort both files externally by user_id with real spills, then streaming-merge the two cursors while holding at most one profile. Equality emits (url, dob); clicks without a profile become counted NULLs. Two separately sorted streams need only the join-key order — the profile-first secondary sort belongs to the mixed-reducer contract, not here. The top trade-off is I/O for bounded memory: two full sorts cost disk traffic to buy O(1) join state. Rule of thumb: pay the sort, never the memory.

صورت مسئله و فرض‌هاProblem and assumptions

  • فایل‌ها آموزشی‌ان: ۳۰٬۰۰۰ کلیک روی ۳٬۵۰۰ شناسه و ۳٬۰۰۰ پروفایل یکتا (user_id,dob). هر دو از سقف chunk هزارسطری رد می‌شن، پس spill واقعیه — نه نمایشی.
  • قضیه اینه که: یه پروفایل یکتا به‌ازای هر کاربر، از اول اعلام‌شده. تاریخچه و تکراری‌ها هم حالت خرابی صریح‌ان — نه fan-out بی‌صدا.
  • معنای left-join: هر کلیک دقیقاً یک‌بار خروجی می‌ده، و وقتی پروفایلش نبود با NULL به‌علاوهٔ شمارنده.
  • Teaching files: 30,000 clicks over 3,500 ids and 3,000 unique profiles (user_id,dob). Both blow past the 1,000-row chunk cap, so the spills are real, not staged.
  • Here's the thing: one unique profile per user, declared up front. History and duplicates are explicit failure cases, not silent fan-out.
  • Left-join semantics: every click emits exactly once, and a missing profile shows up as NULL plus a counter.

چرا این روش و این عددها؟Why this method and these numbers?

چرا این مدل به این تمرین می‌خوره: در دو جریان جدا، cursor پروفایل را تا user_id کلیک جلو می‌بریم؛ یکتایی پروفایل یعنی فقط یک رکورد لازم است. این O(1) دربارهٔ state join است، نه همهٔ حافظهٔ external sort. در mixed stream، کلیک زودرس بدون پروفایل باید نگه داشته شود؛ profile-first همین buffering را حذف می‌کند. ۳۰هزار و سه‌هزار رکورد از chunk هزارسطری بزرگ‌ترند تا spill واقعی رخ دهد. duplicate profile فرض یکتایی را می‌شکند و باید با قرارداد جدا حل شود.

Why this model fits: with separate streams, advance the profile cursor to the click’s user_id; unique profiles require one retained record. O(1) describes the join state, not all external-sort memory. Early clicks in a mixed stream have to be held until their profile arrives, and profile-first removes that buffering. Thirty thousand and three thousand records exceed the 1k-row chunk so the spills are real. Duplicate profiles violate the uniqueness premise and need a separate policy.

مدل ذهنیMental model

join یعنی دو خط مرتب رو با کلید هم‌تراز کنی. دو cursor جلو می‌رن، سمت عقب‌مانده خودش رو می‌رسونه و وقتی مساوی شدن، خروجی می‌دی. نکته‌ش اینجاست: مرتب‌سازی این خط‌ها رو قدم‌زدنی می‌کنه؛ خود ادغام هیچ‌وقت به عقب نگاه نمی‌کنه.
A join lines up two ordered lists by key. Two cursors walk forward, the lagging one catches up, and when they match you emit. Here's the thing: sorting is what makes the lines walkable — the merge itself never looks back.

حل گام‌به‌گامStep by step

  1. اول: یکتایی و نوع join رو اعلام کن قبل از اینکه به داده دست بزنی، معنای left-join و یکتایی پروفایل رو اعلام کن: هر کلیک یک‌بار می‌ده، و گمشده یعنی NULL به‌علاوه شمارنده.
  2. هر دو رو مرتب کن، آن‌سوی حافظه بعد هر سمت رو بر اساس user_id با chunkهای کران‌دار و spill واقعی مرتب کن؛ هر سمت دقیقاً یک جریان مرتب می‌ده.
  3. ادغام با یک پروفایل نگه‌داشته حالا هر دو ترتیب رو با دو cursor قدم بزن: سمت عقب‌مانده رو جلو ببر، حداکثر یک پروفایل نگه دار، روی تساوی (url, dob) بده و گمشده‌ها رو بشمار.
  4. مقایسه قرارداد میکس جریان میکس رو هم مقایسه کن: یک ورودی درهم به‌ازای هر reducer ترتیب profile-first می‌خواد — یا بافرینگ صریح با کران. دو جریان جدا هیچ‌کدوم رو نمی‌خوان.
  5. چولگی و تاریخچه، قیمت‌گذاشته چولگی رو با salt-and-combine قیمت بگذار و تاریخچه رو با قاعده live-at-ts فیصله بده؛ هر دو قبل از اجرا اعلام و حین اجرا رصد می‌شن.
  1. Declare uniqueness and join type Before you touch the data, state the left-join semantics and the profile uniqueness: every click emits once, and missing means NULL plus a counter.
  2. Sort both past memory Next, sort each side by user_id with bounded chunks and real spills; each side yields exactly one ordered stream.
  3. Merge with one profile held Now walk both orders with two cursors: advance the lagging side, hold at most one profile, emit (url, dob) on equality, and count the missing.
  4. Contrast the mixed contract Contrast the mixed stream too: one interleaved input per reducer wants profile-first ordering — or explicit buffering with a bound. Two separate streams need neither.
  5. Skew and history, priced Price the skew with salt-and-combine and settle the history with the live-at-ts rule; both are declared before the run and monitored during it.

طراحی مشخصConcrete design

فرمت‌ها: کلیک‌ها user_id,url,ts و پروفایل‌ها user_id,dob؛ کلید sort هر دو سمت user_id؛ runهای spill فایل‌های موقت CSV مرتب‌اند.

ادغام: دو cursor فایلی؛ سمت عقب‌مانده جلو می‌ره؛ روی تساوی یه پروفایل نگه داشته می‌شه و به‌ازای هر کلیک می‌ده؛ کلیک‌های بی‌پروفایل به شمارنده NULL می‌رن و پروفایل‌های بدون کلیک رد می‌شن.

چولگی و تاریخچه: کاربران داغ با salt شکافته و با گام combine جمع می‌شن (با قیمت علنی)؛ پروفایل‌های نسخه‌دار با قاعده live-at-ts که قبل از اجرا اعلام شده join می‌شن.

Formats: clicks user_id,url,ts, profiles user_id,dob; sort key user_id on both sides; spill runs are sorted CSV temp files.

Merge: two file cursors; advance the lagging side; on equality hold one profile and emit per click; missing clicks go to the NULL counter, and profiles without clicks are skipped.

Skew and history: hot users split by salt with a combine step (priced openly); versioned profiles join by the live-at-ts rule declared before the run. Nothing here keeps more than one profile in memory — that is the whole point.

گزینه‌های جایگزینAlternatives

  • join پخشی (سمت-map): وقتی سمت پروفایل توی RAM جا می‌شه، یک‌بار می‌ذارش توی جدول hash و کلیک‌ها رو از کنارش جاری می‌کنی — سمت بزرگ اصلاً sort نمی‌شه. تا وقتی پروفایل‌ها جا می‌شن می‌بره؛ روزی که جا نشن می‌بازه و به همین حل برمی‌گردی.
  • join میکس-reducer با secondary sortِ profile-first: جواب درست وقتی یه shuffle کلیک‌ها و پروفایل‌ها رو درهم می‌رسونه. کلید sort قوی‌تری می‌پردازه تا جاری بودن رو پس بگیره؛ برای دو فایل ازقبل‌جدا این قیمت رو نپرداز.
  • Broadcast (map-side) join: when the profile side fits in RAM, load it into a hash table once and stream the clicks past it — the big side is never sorted at all. It wins while the profiles fit, and it loses the day they stop fitting, when you fall back to this solution.
  • Mixed-reducer join with profile-first secondary sort: the right answer when one shuffle delivers clicks and profiles interleaved. It pays for a stronger sort key to recover the streaming property — don't pay that for two files that are already separate.

سناریوهای خرابیFailure scenarios

  • پروفایل تکراری یکتایی اعلام‌شده رو می‌شکنه: تساوی به چند سطر به‌ازای هر کلیک fan-out می‌کنه. نگهبانش assertِ dedupe روی سمت پروفایل قبل از ادغام و انداختن job است — هرگز fan-out رو بی‌صدا نده.
  • چولگی کاربر داغ: یه کاربر سهم عظیم کلیک داره و worker joinش می‌خوابه ولی بقیه بیکارن. نگهبان: اندازه‌گیری توزیع کلید، salt زدن کلید سنگین، join تکه‌ها و بعد combine — قیمت‌گذاشته‌شده، نه پنهان.
  • تاریخچه نسخه‌دار بدون قاعده: چند پروفایل یه کاربر رو شریک‌ان و join تعریف‌نشده‌ست. نگهبانش قاعده live-at-ts اعلام‌شده قبل از اجراست؛ بدون اون به‌جای join بایست.
  • Duplicate profiles break the declared uniqueness: equality fans out into several rows per click. Guard with a dedupe assert on the profile side before the merge, and fail the job — never emit the fan-out silently.
  • Hot-user skew: one user owns a huge click share, its join worker stalls while the others idle. Guard by measuring the key distribution, salting the heavy key, joining the parts, then combining — priced, not hidden.
  • Versioned history without a rule: several profiles share one user and the join is undefined. Guard with the live-at-ts rule declared before the run; without it, stop instead of joining.

import java.util.*;

// Teaching demo: sort-merge join on two files bigger than the memory cap.
// clicks(user_id,url,ts) + profiles(user_id,dob), one unique profile per
// user. Each side is externally sorted by user_id (bounded chunk, spill to
// temp files), then a streaming merge holds AT MOST one profile record in
// memory and emits (url,dob) per visit. Missing profiles are counted, not
// silently dropped. Two separately sorted streams: NO secondary sort needed.
public class SortMergeJoinDemo {
    static final int CLICKS = 30_000, USERS = 3_000, CHUNK = 1_000;

    public static void main(String[] a) throws Exception {
        Random rnd = new Random(12);
        java.nio.file.Path clickFile = java.nio.file.Files.createTempFile("clicks", ".csv");
        java.nio.file.Path profFile = java.nio.file.Files.createTempFile("profiles", ".csv");
        List<String> buf = new ArrayList<>();
        for (int i = 0; i < CLICKS; i++)
            buf.add((rnd.nextInt(USERS + 500)) + ",/p/" + rnd.nextInt(400) + "," + (1_700_000_000L + i));
        java.nio.file.Files.write(clickFile, buf);
        buf.clear();
        for (int u = 0; u < USERS; u++) buf.add(u + ",1990-01-" + String.format("%02d", 1 + (u % 28)));
        java.nio.file.Files.write(profFile, buf);

        java.nio.file.Path sortedClicks = externalSort(clickFile);
        java.nio.file.Path sortedProfiles = externalSort(profFile);

        // Streaming merge: advance the lagging cursor; equality emits.
        var clicks = java.nio.file.Files.newBufferedReader(sortedClicks);
        var profs = java.nio.file.Files.newBufferedReader(sortedProfiles);
        String c = clicks.readLine(), p = profs.readLine();
        long emitted = 0, missing = 0, heldProfiles = 0, maxHeld = 0;
        String heldDob = null;
        int heldUser = -1;
        List<String> sample = new ArrayList<>();
        while (c != null && p != null) {
            int cu = Integer.parseInt(c.split(",")[0]);
            int pu = Integer.parseInt(p.split(",")[0]);
            if (cu == pu) {
                heldUser = pu; heldDob = p.split(",")[1]; heldProfiles = 1;
                maxHeld = Math.max(maxHeld, heldProfiles);
                emitted++;
                if (sample.size() < 3) sample.add(c.split(",")[1] + " -> " + heldDob);
                c = clicks.readLine();
            } else if (cu < pu) {
                missing++; // click whose profile id is absent on the profile side
                c = clicks.readLine();
            } else {
                p = profs.readLine(); // profile with no clicks: skip
            }
        }
        while (c != null) { missing++; c = clicks.readLine(); }
        clicks.close(); profs.close();

        System.out.println("clicks=" + CLICKS + " profiles=" + USERS
            + " chunk_cap=" + CHUNK + " (both files exceed it: real spill)");
        for (String s : sample) System.out.println("emit " + s);
        System.out.println("emitted=" + emitted + " missing_profile=" + missing
            + " max_profiles_held=" + maxHeld);
        System.out.println("OK");
    }

    static java.nio.file.Path externalSort(java.nio.file.Path in) throws Exception {
        List<java.nio.file.Path> runs = new ArrayList<>();
        List<String> chunk = new ArrayList<>(CHUNK);
        for (String line : java.nio.file.Files.readAllLines(in)) {
            chunk.add(line);
            if (chunk.size() == CHUNK) runs.add(spill(chunk));
        }
        if (!chunk.isEmpty()) runs.add(spill(chunk));
        Comparator<String> byUser = Comparator.comparingInt(s -> Integer.parseInt(s.split(",")[0]));
        if (runs.size() == 1) return runs.get(0);
        // K-way merge of runs into one sorted file.
        java.nio.file.Path out = java.nio.file.Files.createTempFile("sorted", ".csv");
        List<java.io.BufferedReader> brs = new ArrayList<>();
        PriorityQueue<String[]> pq = new PriorityQueue<>((x, y) -> byUser.compare(x[0], y[0]));
        for (java.nio.file.Path p : runs) {
            var br = java.nio.file.Files.newBufferedReader(p);
            brs.add(br);
            String h = br.readLine();
            if (h != null) pq.add(new String[]{h, String.valueOf(brs.size() - 1)});
        }
        var w = java.nio.file.Files.newBufferedWriter(out);
        while (!pq.isEmpty()) {
            String[] e = pq.poll();
            w.write(e[0]); w.newLine();
            var br = brs.get(Integer.parseInt(e[1]));
            String h = br.readLine();
            if (h != null) pq.add(new String[]{h, e[1]});
        }
        w.close();
        for (var br : brs) br.close();
        return out;
    }

    static java.nio.file.Path spill(List<String> chunk) throws Exception {
        chunk.sort(Comparator.comparingInt(s -> Integer.parseInt(s.split(",")[0])));
        java.nio.file.Path p = java.nio.file.Files.createTempFile("run", ".csv");
        java.nio.file.Files.write(p, chunk);
        chunk.clear();
        p.toFile().deleteOnExit();
        return p;
    }
}

Assert that emitted plus missing equals the total clicks; assert that each run file is sorted; assert that max profiles held equals one; run twice for determinism; alert when the missing ratio crosses its threshold; fail on duplicate profile keys.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (سینیور): اگه به‌ازای هر user چند نسخه تاریخی از پروفایل داشته باشی، کلیک باید به کدوم نسخه بچسبه؟Follow-up (Senior): With multiple historical profiles per user, which version should a click join to?

هر کلیک رو به نسخهٔ پروفایل زنده در ts خودش وصل کن: پروفایل‌های هر کاربر رو با بازهٔ اعتبار مرتب کن و اونی که ts کلیک رو داره بردار. کلیک‌های بیرون همهٔ بازه‌ها به bin گمشده با شمارنده version-miss می‌رن (جدا از هرگز-پروفایل-نداشته) و بازه‌های هم‌پوشان job رو می‌اندازن — یعنی خود تاریخچه خرابه.

Join each click to the profile version that was live at its ts: order each user's profiles by validity interval and pick the one that contains the click ts. Clicks outside every interval go to the missing bin with a version-miss counter (separate from never-had-profile), and overlapping intervals fail the job — they mean the history itself is corrupt.

پیگیری (استف): توی جریان mixed-reducer بدون ترتیب profile-first، دقیقاً کجا می‌شکنی؟Follow-up (Staff): In a mixed reducer stream without profile-first ordering, where exactly does it break?

توی جریان میکس بدون profile-first، reducer باید کلیک‌ها رو تا رسیدن پروفایل بافر کنه — پس بافر رو کران بده (بعد از N گروه spill کن و بعد از M بایت بینداز) و high-water mark رو رصد کن. شکستِ رد کردن ترتیب دقیقاً همینه: گروه‌های بی‌کران، حافظهٔ بی‌کران و بعد OOM توی بدترین لحظه.

In a mixed stream without profile-first, the reducer must buffer clicks until the profile arrives — so bound the buffer (spill it past N groups, fail past M bytes) and watch its high-water mark. The breakage of skipping the ordering is exact: unbounded groups, unbounded memory, then OOM at the worst possible moment.

اشتباهات رایجCommon mistakes

  • الزام secondary sortِ profile-first برای دو جریان مرتبِ جدا: کار sort اضافه می‌کنه با صفر سود درستی، چون ادغام فقط کلیدهای join رو مقایسه می‌کنه. profile-first مال قرارداد تک‌جریان میکسه — به‌جای اعمال یه قاعده همه‌جا، بگو هرکدوم دقیقاً کجا می‌شکنن.
  • انداختن بی‌صدای کلیک‌های بدون پروفایل: نبودن یه واقعیت کسب‌وکاریه (کاربر حذف‌شده، بعدِ دیررس) — NULL بده، بشمار و روی نسبتش هشدار بده.
  • نگه‌داشتن همهٔ پروفایل‌ها توی حافظه چون «بعداً کوچک‌اند»: کوچکِ امروز، بزرگِ فصل بعده. ادغام ذاتاً یه پروفایل نگه می‌داره، پس رشد هرگز این تصمیم رو برنمی‌گردونه.
  • Demanding a profile-first secondary sort for two separately sorted streams. It adds sort work for zero correctness gain: the merge only compares join keys. Profile-first belongs to the mixed single-stream contract — say exactly where each one breaks instead of applying one rule everywhere.
  • Silently dropping clicks without profiles. Absence is a business fact (deleted user, late dimension) — emit NULL, count it, and alert on its ratio.
  • Holding every profile in memory because 'dimensions are small'. Small today is big next quarter: the merge holds one profile by construction, so growth never revisits this decision.

سؤال مصاحبهInterview question
قضیه اینه که می‌خوای shuffle برای group-by بسازی. partition یکسان، sort محلی و merge تو reducer رو طراحی کن. حساب کن hot key، حجم شبکه، combiner و checksum فایل میانی چی می‌شن. حالا خروجی یه mapper خراب می‌شه؛ بگو دقیقاً چی رو بر اساس کدوم lineage دوباره اجرا می‌کنی.
Here's the thing, you're building the shuffle for a group-by. You design identical partitioning, mapper-local sorting, and the reducer merge. You work through hot keys, network volume, the combiner, and checksums on intermediate files. Then one mapper's output corrupts, so you say exactly what you rerun and which lineage makes it safe.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

نکته‌ش اینجاست: با یه تابع پایدار همه‌جا پارتیشن کن (floorMod(hash, R))، توی هر mapper محلی مرتب کن، به‌ازای هر پارتیشن یه فایل مرتب mPrR بنویس و به‌ازای هر پارتیشن توی reducer ادغام k-way کن — رکوردهای هم‌کلید با حافظه کران‌دار کنار هم می‌نشینن. هرجا تابع اجازه داد با combiner پیش‌تجمیع کن، هر فایل میانی رو checksum بزن و فقط mapperهای گمشده رو از splitهای immutable با attempt id تازه دوباره اجرا کن. تریدآف اصلی شبکه و چولگیه: shuffle هر رکورد رو یک‌بار جابه‌جا می‌کنه و کلید داغ می‌تونه یه reducer رو غرق کنه. — یه تابع مشترک، کل shuffle رو می‌سازه.
Here's the shape of it: partition with one stable function everywhere (floorMod(hash, R)), sort locally in each mapper, write one sorted mPrR file per partition, and k-way merge per partition in the reducer — same-key records land together in bounded memory. Pre-aggregate with a combiner where the function allows, checksum every intermediate file, and recompute only the lost mappers from immutable splits under fresh attempt ids. The top trade-off is network and skew: the shuffle moves every record once, and a hot key can swamp one reducer. One shared function is what makes the whole thing work.

صورت مسئله و فرض‌هاProblem and assumptions

  • shuffle آموزشی: ۲ mapper و ۳ پارتیشن با ۱۲ کلید و ۲۵ مقدار (۳۰۰ رکورد) — هم‌مکانی و محاسبهٔ دوباره قابل‌مشاهده‌ان، نه بنچمارک.
  • تابع پارتیشن floorMod(hash, R) روی همهٔ worker‌ها یکسانه و با job نسخه‌بندی شده؛ عوض کردنش یعنی دوباره shuffle کردنِ همه‌چیز.
  • mapper‌ها قطعی و بدون side effect هستن، پس اجرای دوباره همون رکورد‌ها رو بازپخش می‌کنه — به‌عنوان پیش‌شرط اعلام‌شده و با دمو راستی‌آزمایی‌شده.
  • A teaching shuffle: 2 mappers, 3 partitions, 12 keys × 25 values (300 records) — colocation and recompute are observable, not benchmarks.
  • The partition function floorMod(hash, R) is identical on every worker and versioned with the job — change it and you reshuffle everything.
  • The mappers are deterministic and side-effect free, so a rerun replays the same records — stated as a precondition and verified by the demo.

چرا این روش و این عددها؟Why this method and these numbers?

چرا این مدل به این تمرین می‌خوره: hash(key) mod R همهٔ مقدارهای یه key رو به reducer یکسان می‌فرسته؛ برای همین تابع و نسخهٔ اون باید روی همهٔ mapperها یکسان باشه. سه partition و دو mapper فقط مسیرها رو واضح می‌کنن. sort ترتیب داخل partition رو می‌ده و با partitioning یه کار نمی‌کنه. deterministic و بدون side effect بودن mapper باعث می‌شه retry همون داده رو تولید کنه؛ ولی اگه خروجی تکراریِ attemptها هم‌زمان پذیرفته بشه، این کافی نیست و یه commit manifest که یک attempt رو انتخاب کنه لازم می‌شه.

Why this model fits: hash(key) mod R colocates a key's values, which means the partition function and its version have to be identical on all mappers. Three partitions and two mappers simply expose the paths. Sorting orders records within a partition and serves a different purpose. Deterministic, side-effect-free mappers reproduce the output on retry, but if duplicate attempt outputs are accepted at the same time, that is not enough — a commit manifest has to select one attempt.

مدل ذهنیMental model

shuffle یعنی یه sort توزیع‌شده. تصور کن هر worker یه زبانِ پارتیشن حرف می‌زنه، هرکدوم تکهٔ خودش رو مرتب می‌کنه و reducer تکه‌ها رو ادغام می‌کنه — دقیقاً مثل mergesort که runها رو ادغام می‌کنه. ترتیبش اینه: اول توافق، بعد جابه‌جایی.
A shuffle is a distributed sort. Picture every worker speaking the same partition language, sorting its own slice, while the reducer merges the slices the way a merge sort merges runs. Agreement first, movement second.

حل گام‌به‌گامStep by step

  1. یه تابع، همه‌جا یه تابع پارتیشن رو روی همهٔ workerها فیکس کن و با job نسخه‌بندی کن: کلید یکسان، پارتیشن یکسان، هر mapper و هر اجرا.
  2. مرتب‌سازی محلی و نوشتن فایل هر تکهٔ پارتیشن رو داخل mapper مرتب کن و یه فایل checksummedِ mPrR به‌ازای هر پارتیشن بنویس — همون قرارداد قابل fetch.
  3. fetch و ادغام به‌ازای هر پارتیشن بعد فایل‌های یه پارتیشن رو از همهٔ mapperها fetch کن و با یه خط به‌ازای هر فایل توی RAM ادغام k-way کن: کلیدهای یکسان کنار هم و مرتب می‌رسن.
  4. combiner و checksumها هرجا انجمنی بودن برقراره با combiner پیش‌تجمیع کن و هر فایل رو checksum بزن تا خرابی شناسایی بشه، نه بی‌صدا.
  5. اجرای محدود از lineage روی گم شدن، فقط mapper مالک رو از split immutable خودش با attempt id تازه دوباره اجرا کن؛ بازپخش قطعی، بازنویسی رو برابر فایل گمشده می‌کنه.
  1. One function everywhere Fix one partition function on every worker and version it with the job: same key, same partition, every mapper, every run.
  2. Sort locally, write files Sort each partition slice inside the mapper and write one checksummed mPrR file per partition — the fetchable contract.
  3. Fetch and merge per partition Fetch one partition's files from all mappers and k-way merge them with one line per file in RAM: same keys arrive together, sorted.
  4. Combiner and checksums Pre-aggregate with a combiner where associativity holds, and checksum every file so corruption gets detected, never silent.
  5. Scoped lineage rerun On a loss, rerun only the owning mapper from its immutable split under a fresh attempt id; deterministic replay makes the rewrite equal the lost file.

طراحی مشخصConcrete design

فایل‌ها: یک فایل مرتب checksummed به‌ازای هر (mapper, partition) با نام mPrR؛ مجموعهٔ فایل همون قرارداد shuffle است که reducer fetch می‌کنه.

attemptها: هر اجرای mapper یه attempt id داره؛ retry کل فایل‌ها رو با id تازه بازنویسی می‌کنه و هرگز به فایل شکست‌خورده الصاق نمی‌کنه.

reducer: فایل‌های یه پارتیشن رو از همهٔ mapperها fetch می‌کنه، با یه خط به‌ازای هر فایل توی RAM ادغام k-way می‌کنه و کلیدهای برابر رو گروه می‌کنه؛ combiner کار انجمنی (شمارش، جمع — هرگز میانگین تنها) رو قبل از عبور هر بایت از شبکه پیش‌تجمیع می‌کنه.

Files: one sorted checksummed file per (mapper, partition) named mPrR; the file set is the shuffle contract the reducer fetches.

Attempts: every mapper run carries an attempt id; a retry rewrites whole files under a fresh id and never appends to the failed one's.

Reducer: fetches one partition's files from all mappers, k-way merges with one line per file in RAM, groups equal keys; the combiner pre-aggregates associative work (counts, sums — never a bare average) before any byte crosses the network.

  2. بعد fetch فایل‌های یه پارتیشن رو با یه خط به‌ازای هر فایل توی RAM ادغام می‌کنه: کلیدهای یکسان کنار هم.

  1. The mappers partition, sort and combine; the sorted mPrR files flow to fetch.
  2. Fetch merges one partition's files with one line per file in RAM: same keys together.
  3. On a checksum failure only the lost mapper reruns; its files rejoin the same fetch.

After a file corrupts, what reruns and what stays?

Answer: Fetch, the k-way merge and the grouped output — plus exactly one mapper rerun on the file loss.

گزینه‌های جایگزینAlternatives

  • پارتیشن‌بندی بازه‌ای: هر reducer مالک یه بازهٔ کلیده، پس خروجی سراسری مرتب میاد. وقتی پایین‌دست ترتیب کلی می‌خواد می‌بره؛ ولی روی چولگی می‌بازه، چون یه بازه می‌تونه نصف داده رو بگیره بدون hash که پخشش کنه.
  • پخش سمت کوچک و حذف کامل shuffle، وقتی یه ورودی توی RAM هر worker جا می‌شه. با حذف شبکه، combiner و ادغام می‌بره؛ روزی که سمت «کوچک» جا نشه، دیگه نمی‌بره.
  • Range partitioning: each reducer owns a key range, so the output comes out globally sorted. It wins when downstream needs a total order, and it loses on skew, because one range can hold half the data with no hash to spread it.
  • Broadcast the small side and skip the shuffle entirely when one input fits in every worker's RAM. It wins by deleting the network, the combiner and the merge; it stops winning the day the 'small' side stops fitting.

سناریوهای خرابیFailure scenarios

  • فایل میانی خراب: بایت‌های دیسک دیگه با checksum نمی‌خونن. نگهبان: انداختن fetch اون پارتیشن و اجرای دوبارهٔ فقط mapper مالک از split خودش — هرگز کل job، نه.
  • کرش mapper وسط نوشتن: فایل mPrR ناقص، در نگاه اول کامل به نظر می‌رسه. نگهبان: attempt id به‌علاوهٔ checksum. retry کل فایل‌ها رو با id تازه بازنویسی می‌کنه و fetch فایل چک‌نشده رو رد می‌کنه.
  • mapper غیرقطعی یا side effect بیرونی: اجرای دوباره رکوردهای متفاوت بازپخش می‌کنه یا نوشتن‌های بیرونی رو تکرار می‌کنه. نگهبانش ساخت خودشه — نگاشت قطعی و بدون نوشتن بیرونی — چون هیچ پروتکل retry، mapper دروغ‌گو رو درست نمی‌کنه.
  • عوض شدن تابع پارتیشن وسط job: فایل‌های قدیم و جدید روی جای کلید اختلاف دارن و گروه‌بندی بی‌صدا می‌شکنه. نگهبان: نسخه‌بندی تابع با job و رد fetchهای چندنسخه‌ای.
  • A corrupt intermediate file: the bytes on disk no longer match the checksum. Guard by failing that partition's fetch and rerunning only the owning mapper from its split — never the whole job.
  • A mapper crash mid-write: a partial mPrR file looks complete at a glance. Guard with attempt ids plus checksums: the retry rewrites whole files under a fresh id, and fetch refuses unchecked files.
  • A nondeterministic mapper or outside side effects: the rerun replays different records or repeats external writes. Guard by construction — deterministic mapping, no outside writes — because no retry protocol fixes a mapper that lies.
  • The partition function changed mid-job: the old and new files disagree on key placement and grouping silently breaks. Guard by versioning the function with the job and refusing mixed-version fetches.

import java.util.*;

// Teaching demo: a mini shuffle. M mappers partition records by
// floorMod(hash(key), R); each mapper writes ONE sorted file per partition
// (m{i}r{p}), like real map-output files. Each reducer k-way merges its
// partition's files, so same-key records land together, sorted.
// Then one intermediate file is corrupted: only that mapper reruns, from
// its immutable input split with a fresh attempt id — safe because the
// mapper is deterministic and side-effect free.
public class ShuffleDemo {
    static final int MAPPERS = 2, PARTITIONS = 3, KEYS = 12, PER_KEY = 25;

    public static void main(String[] a) throws Exception {
        java.nio.file.Path dir = java.nio.file.Files.createTempDirectory("shuffle");
        // Immutable input splits: each mapper owns its lines.
        List<List<String>> splits = new ArrayList<>();
        Random rnd = new Random(13);
        for (int m = 0; m < MAPPERS; m++) {
            List<String> split = new ArrayList<>();
            for (int k = 0; k < KEYS; k++)
                for (int v = 0; v < PER_KEY; v++)
                    if ((k + v + m) % MAPPERS == 0)
                        split.add("key" + k + "=" + (m * 1000 + rnd.nextInt(999)));
            splits.add(split);
        }
        for (int m = 0; m < MAPPERS; m++) runMapper(dir, m, splits.get(m), 0);

        System.out.println("partitions=" + PARTITIONS + " mappers=" + MAPPERS
            + " partition_fn=floorMod(hash, " + PARTITIONS + ")");
        verify(dir, "before corruption");

        // Corrupt one intermediate file, then rerun ONLY that mapper.
        java.nio.file.Path victim = dir.resolve("m1r2.txt");
        java.nio.file.Files.writeString(victim, "GARBAGE\n");
        System.out.println("corrupted " + victim.getFileName());
        runMapper(dir, 1, splits.get(1), 1); // fresh attempt id, same input
        System.out.println("reran mapper=1 attempt=1 from immutable split");
        verify(dir, "after recompute");
        System.out.println("OK");
    }

    static void runMapper(java.nio.file.Path dir, int m, List<String> split, int attempt) throws Exception {
        List<List<String>> parts = new ArrayList<>();
        for (int p = 0; p < PARTITIONS; p++) parts.add(new ArrayList<>());
        for (String rec : split) {
            String key = rec.split("=")[0];
            parts.get(Math.floorMod(key.hashCode(), PARTITIONS)).add(rec);
        }
        for (int p = 0; p < PARTITIONS; p++) {
            Collections.sort(parts.get(p));
            java.nio.file.Path f = dir.resolve("m" + m + "r" + p + ".txt");
            java.nio.file.Files.write(f, parts.get(p)); // attempt rewrites whole file
        }
    }

    static void verify(java.nio.file.Path dir, String phase) throws Exception {
        boolean colocated = true, sorted = true;
        for (int p = 0; p < PARTITIONS; p++) {
            // Reducer: k-way merge of this partition's sorted map files.
            List<List<String>> files = new ArrayList<>();
            for (int m = 0; m < MAPPERS; m++)
                files.add(java.nio.file.Files.readAllLines(dir.resolve("m" + m + "r" + p + ".txt")));
            int[] pos = new int[MAPPERS];
            PriorityQueue<int[]> pq = new PriorityQueue<>(
                (x, y) -> files.get(x[0]).get(x[1]).compareTo(files.get(y[0]).get(y[1])));
            for (int m = 0; m < MAPPERS; m++)
                if (!files.get(m).isEmpty()) pq.add(new int[]{m, 0});
            List<String> merged = new ArrayList<>();
            String prev = null;
            while (!pq.isEmpty()) {
                int[] e = pq.poll();
                String rec = files.get(e[0]).get(e[1]);
                if (prev != null && prev.compareTo(rec) > 0) sorted = false;
                prev = rec;
                merged.add(rec);
                if (e[1] + 1 < files.get(e[0]).size()) pq.add(new int[]{e[0], e[1] + 1});
            }
            Set<String> keys = new HashSet<>();
            for (String r : merged) keys.add(r.split("=")[0]);
            for (String k : keys)
                colocated &= Math.floorMod(k.hashCode(), PARTITIONS) == p;
            System.out.println(phase + " reduce[" + p + "] records=" + merged.size()
                + " distinct_keys=" + keys.size());
        }
        System.out.println(phase + " colocated=" + colocated + " sorted=" + sorted);
        if (!colocated || !sorted) throw new IllegalStateException("shuffle broken: " + phase);
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): یه key نصف داده رو داشته باشه، چطور reducer رو از hotspot نجات می‌دی؟Follow-up (Staff): One key holds half your records. How do you save your reducer from the hotspot?

کلید داغ رو با salt بشکن: موقع map پسوند shard تصادفی بچسبون تا رکوردهایش روی reducerهای زیادی پخش بشن، به‌ازای (key, salt) تجمیع کن و بعد shardها رو توی یه pass سبک دوم combine کن. قیمتش رو علنی بگو — pass shuffle اضافه به‌علاوهٔ combine نهایی — و سهم کلید اول رو رصد کن تا فاکتور salt از اندازه‌گیری بیاد، نه از خرافه.

Split the hot key with salt: append a random shard suffix at map time so its records spread over many reducers, aggregate per (key, salt), then combine the shards in a second lightweight pass. Price it openly — one extra shuffle pass plus the final combine — and watch the top-key share so the salt factor follows the measurement, not superstition.

پیگیری (سینیور): combiner کی غلطه و به‌جایش چی رو combine می‌کنی؟Follow-up (Senior): When is a combiner wrong, and what do you combine instead?

فقط با جمع-به‌علاوه-شمارش، و هرگز میانگین تنها: combiner می‌تونه جمع و شمارش جزئی بده (انجمنی) و reducer آخر تقسیم می‌کنه. combiner که میانگینِ میانگین‌ها بگیره ذاتاً غلطه — به‌ازای هر تابع، انجمنی بودن رو قبل از اجازهٔ combine اثبات کن.

Only with sum-plus-count, never a bare average: the combiner may emit partial sums and counts (associative), and the reducer does the dividing at the end. A combiner that averages averages is wrong by construction — prove associativity for each function before you let it combine.

اشتباهات رایجCommon mistakes

  • اجرای دوبارهٔ کل job برای یه فایل گمشده: lineage دقیقاً mapper رو نام می‌بره؛ اجرای محدود کل نکتهٔ splitهای immutable به‌علاوهٔ انزوای attempt است.
  • استفادهٔ دوباره از نام فایل بین attemptها، طوری که دو اجرای یه mapper هر دو جاری به نظر برسن. id تازه به‌ازای هر retry؛ fetch دقیقاً یه نسل committed رو می‌پذیره.
  • side effect داخل mapper (نوشتن بیرونی، فراخوانی غیر-idempotent): بازپخش اون‌وقت دنیای بیرون رو تکرار می‌کنه — mapperها رو خالص نگه دار، وگرنه rerun تعریفاً ناامنه.
  • Rerunning the whole job for one lost file. The lineage names the exact mapper; scoped rerun is the whole point of immutable splits plus attempt isolation.
  • Reusing file names across attempts so two runs of one mapper both look current. Fresh attempt ids per retry; fetch accepts exactly one committed generation.
  • Side effects inside the mapper (external writes, non-idempotent calls). Replay then repeats the outside world — keep the mappers pure or the rerun is unsafe by definition.

سؤال مصاحبهInterview question
داستان از این قراره که یه job چندtaskی روی ورودی immutable داری. attempt output جدا و manifest نسخه‌دار طراحی کن. crash وسط write و قبل از publish تزریق کن. یادت باشه خواننده باید همیشه یه نسخه کامل و ثابت ببینه؛ CAS و atomic pointer و cleanup و retry رو متناسب با همون storage خودت انتخاب کن.
Honestly, you've got a multi-task job over immutable inputs. You design versioned attempt outputs plus a manifest. You inject a crash mid-write and another one just before publish. Remember, your readers must always see one complete pinned version, so you pick your CAS or atomic pointer, cleanup, and retry to match your storage.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

داستان از این قراره: هر task رو توی فایل attemptِ checksummed خودش بنویس، با حذف ناقص‌ها و اجرای دوباره با id تازه retry کن، پشت barrier منتظر همه taskها بمون و بعد با یه تعویض اتمی pointer منتشر کن — یه manifest نسخه‌دار که خواننده‌ها pin می‌کنن. اتم رو با storage جور کن: محلی rename محلی، و روی object store نوشتن شرطی یا pointer نسخه‌دار. تریدآف اصلی فضا در برابر ایمنیه: نسخه‌های قدیم تا garbage collection بایت می‌خورن و اون اجاره، خواننده‌هایی رو می‌خره که هرگز نصف job رو نمی‌بینن. — این همون چیزیه که مشتری می‌خره: هیچ‌وقت نصف job رو نبینه.
Here's the move: write each task to its own checksummed attempt file, retry by deleting the partials and rerunning under fresh ids, wait at a barrier for every task, then publish with one atomic pointer swap — a versioned manifest that readers pin. Match the atom to the storage: a local rename locally, a conditional write or a versioned pointer on object stores. The top trade-off is storage versus safety: the old versions cost bytes until garbage collection, and that rent buys readers that never see half a job. The punchline: the reader never sees half a job, and that is exactly what the rent buys.

صورت مسئله و فرض‌هاProblem and assumptions

  • job آموزشی: ۴ task و ۵۰۰ سطر از shard‌های immutable. یه killer با seed، با احتمال ۰٫۵ به‌ازای هر attempt، وسط نوشتن می‌میره — خرابی‌ها تزریق می‌شن، نه آرزو.
  • فایل‌سیستم موقت محلی، که تعویض pointer جانشین گام اتمی می‌شه. اتم object store (نوشتن شرطی) توی متن طراحی شده، با هزینهٔ متفاوت خودش.
  • خواننده‌ها pointer رو یک‌بار به‌ازای هر نشست خواندن حل می‌کنن و همون manifest رو pin می‌کنن. انتشار تک‌نویسنده‌ست، مگر قاعدهٔ CAS پیگیری بیاد.
  • A teaching job: 4 tasks × 500 rows from immutable shards. A seeded killer dies mid-write with probability 0.5 per task attempt — failures are injected, not hoped for.
  • A local temp filesystem, where the pointer swap stands in for the atomic step. The object-store atom (conditional write) is designed in the text, with its own different cost.
  • Readers resolve the pointer once per read session and pin that manifest. Publishing is single-writer, unless the CAS follow-up comes into play.

چرا این روش و این عددها؟Why this method and these numbers?

چرا این مدل به این تمرین می‌خوره: فایل نیمه‌نوشته رو منتشر نمی‌کنیم چون خواننده ممکنه خروجی ناقص رو کامل تصور کنه. هر attempt خروجی immutable داره و manifest فقط attempt برندهٔ همهٔ taskها رو معرفی می‌کنه؛ تعویض pointer لحظهٔ رؤیت است. احتمال crash برابر ۰٫۵ برای تزریق پرتکرار خرابیه، نه نرخ خرابی واقعی. rename اتمیک فرض همون filesystem است؛ روی object store باید شرط نسخه/CAS همون سرویس بررسی بشه و نمی‌شه از نام مشابه نتیجه گرفت.

Why this model fits: never expose partial files as complete output. Each attempt writes immutable output; a manifest selects one winning attempt per task, and switching the pointer is what changes visibility. A 0.5 crash probability injects frequent failures, not a real failure rate. An atomic rename assumes one supporting filesystem, and object storage needs its own documented conditional-write/CAS semantics.

مدل ذهنیMental model

قضیه اینه که commit با publish فرق داره. taskها نامرئی تموم می‌شن، مثل رأی‌هایی که توی صندوق مهرشده می‌ریزن، و یه چرخش pointer صندوق رو باز می‌کنه. هرچی قبل از چرخش باشه قابل retry و تمیزکاریه؛ هرچی بعدش باشه باید از قبل کامل باشه.
Think of commit as something different from publish. The tasks finish invisibly, like votes dropped into a sealed box, and one pointer flip opens the box. Everything before the flip can be retried and cleaned up; everything after it has to be whole already.

حل گام‌به‌گامStep by step

  1. خروجی attempt، نامرئی shardهای ورودی immutable رو منجمد کن و بذار هر task دقیقاً یه فایل attempt checksummed به‌ازای هر attempt id بنویسه — attemptها ذاتاً نامرئی‌ان.
  2. حذف ناقص و id تازه روی کرش اول فایل ناقص رو حذف کن، بعد همون ورودی رو با id تازه دوباره اجرا کن؛ فقط با checksum commit کن.
  3. barrier قبل از انتشار هر انتشار رو پشت barrier نگه دار که taskهای committed رو می‌شماره: all-or-nothing توی کد اعمال می‌شه، نه توی نثر وعده داده شده.
  4. یک تعویض اتمی pointer یه pointer رو اتمی عوض کن — rename محلی روی فایل‌سیستم و نوشتن شرطی روی object store — تا خواننده‌ها فقط بین نسخه‌های کامل جابه‌جا بشن.
  5. pin و سرو و بازنشستگی خواننده‌ها به‌ازای هر نشست یه manifest رو pin می‌کنن؛ نسخه‌های قدیم grace خودشون رو سرو می‌دن و بعد با شمارش pin جمع می‌شن.
  1. Invisible attempt outputs Freeze the immutable input shards and let each task write exactly one checksummed attempt file per attempt id — attempts are invisible by construction.
  2. Delete partial, fresh id On a crash, delete the partial file first, then rerun the same input under a fresh id; commit only on the checksum.
  3. Barrier before publish Hold every publish behind a barrier that counts the committed tasks: all-or-nothing is enforced in code, not promised in prose.
  4. One atomic pointer swap Swap one pointer atomically — a local rename on filesystems, a conditional write on object stores — so readers move between complete versions only.
  5. Pin, serve, retire Readers pin one manifest per session; the old versions serve out their grace, then get garbage-collected with pin counts.

طراحی مشخصConcrete design

attemptها: task-{t}-attempt-{n}.txt با checksum؛ retry اول ناقص رو حذف و n+1 رو اجرا می‌کنه؛ fetch و خواننده‌ها هرگز نام attempt رو نمی‌بینن، فقط manifest.

اتم انتشار به‌ازای هر storage: فایل‌سیستم محلی — rename اتمیِ CURRENT؛ object store — نوشتن شرطی (CAS) روی کلید pointer و بازنده کل انتشار رو retry می‌کنه؛ ناشرهای هم‌زمان با دقیقاً یه برندهٔ CAS فیصله پیدا می‌کنن.

پاک‌سازی: attemptهای ناقص موقع retry حذف می‌شن؛ نسخه‌های پشت‌سرگذاشته‌شده دورهٔ grace برای خواننده‌های pinشده می‌مونن و بعد garbage-collect می‌شن.

Attempts: task-{t}-attempt-{n}.txt with checksums; a retry deletes the partial first and runs n+1; fetch and readers never see attempt names, only manifests.

Manifest: manifest-v3.txt lists exactly the committed attempt files plus a version; CURRENT holds one manifest name and moves atomically.

Publish atom per storage: local filesystem — atomic rename of CURRENT; object store — conditional write (CAS) on the pointer key, and the loser retries the whole publish; concurrent publishers are resolved by exactly one CAS winner.

Cleanup: partial attempts are deleted on retry; superseded versions are kept through a grace period for the pinned readers, then garbage-collected.

گزینه‌های جایگزینAlternatives

  • بازنویسی درجا روی خروجی زنده: بدون نسخهٔ قدیم، بدون سفر در زمان، و خواننده‌های وسط job مخلوطی از سطرهای قدیم و جدید رو می‌بینن. فضا ارزون‌تره و همه‌چیز دیگه ضعیف‌تر — فقط وقتی قابل‌قبوله که حین job کسی نخونه و تاریخچه هرگز مهم نباشه.
  • دایرکتوری staging به‌علاوهٔ rename روی فایل‌سیستم محلی: taskها توی staging نسخه‌دار می‌نشینن و یه rename اتمی منتشرش می‌کنه. محلی ساده و درسته — ولی rename همون اتم است و اون اتم به object storage منتقل نمی‌شه.
  • In-place overwrite of the live output: no old version, no time travel, and the readers mid-job see a mix of old and new rows. Cheaper storage, weaker everything else — acceptable only when nobody reads during the job and history never matters.
  • Staging directory plus rename on a local filesystem: the tasks land in a versioned staging dir, and one atomic rename publishes it. Simple and correct locally — but the rename is the atom, and that atom does not travel to object storage.

سناریوهای خرابیFailure scenarios

  • نگه‌داشتن ناقص و الصاق موقع retry: دو نسل درهم می‌شن و checksum ممکنه روی زباله پاس بشه. نگهبانش حذف قبل از نوشتنه — خط‌های کامنت دمو جنازه و حذفش رو نشون می‌دن.
  • انتشار قبل از barrier: خواننده‌ها نصف job رو می‌بینن و پایین‌دست کش می‌کنن. نگهبانش barrier به‌عنوان کد (taskهای committed رو بشمار و انتشار زود رو رد کن)، نه عرف.
  • خوانندهٔ پاره: حل دو بارهٔ CURRENT توی یه نشست می‌تونه روی تعویض سوار بشه. نگهبانش pin کردن یک‌بار به‌ازای هر نشست و خواندن فقط manifest pinشده‌ست.
  • فرض rename محلی روی object storage: rename ممکنه copy-plus-delete باشه — مرئی، کُند و غیراتمی. نگهبانش انتخاب اتم خود store (نوشتن شرطی، pointer نسخه‌دار) و تست صریح خواندن پاره‌ست.
  • Keeping the partial and appending on retry: two generations interleave and the checksums may pass on garbage. Guard by deleting before writing — the demo's commented lines show the corpse and its deletion.
  • Publishing before the barrier: the readers see half the job and cache it downstream. Guard with the barrier as code (count the committed tasks, refuse an early publish), not as convention.
  • A torn reader: resolving CURRENT twice in one session can straddle a swap. Guard by pinning once per session and reading only the pinned manifest.
  • Assuming a local rename on object storage: a rename may be copy-plus-delete — visible, slow, non-atomic. Guard by choosing the store's own atom (conditional write, versioned pointer) and testing torn reads explicitly.

import java.util.*;

// Teaching demo: retry + all-or-nothing publication. A job of T tasks turns
// immutable input shards into output shards. A killer dies mid-write with
// probability P (seeded); retry DELETES the partial attempt output and reruns
// with a fresh attempt id. The manifest (versioned output pointer) is written
// only after EVERY task succeeds, so a reader pinning one manifest sees the
// whole result or nothing — never a mix of versions.
public class RetryPublishDemo {
    static final int TASKS = 4, ROWS = 500;
    static final double KILL_P = 0.5;

    public static void main(String[] a) throws Exception {
        Random killer = new Random(14);
        java.nio.file.Path dir = java.nio.file.Files.createTempDirectory("job");
        int[] attempts = new int[TASKS];
        boolean done = false;
        while (!done) {
            done = true;
            for (int t = 0; t < TASKS; t++) {
                java.nio.file.Path out = dir.resolve("task-" + t + "-attempt-" + attempts[t] + ".txt");
                List<String> rows = new ArrayList<>(ROWS);
                boolean died = false;
                for (int r = 0; r < ROWS; r++) {
                    rows.add("shard" + t + ":row" + r);
                    if (killer.nextDouble() < KILL_P / ROWS) { died = true; break; }
                }
                if (died) {
                    java.nio.file.Files.write(out, rows); // partial file left behind
                    java.nio.file.Files.delete(out);      // retry deletes it first
                    attempts[t]++;
                    done = false;                         // whole job waits: no publish yet
                } else if (java.nio.file.Files.notExists(out)) {
                    java.nio.file.Files.write(out, rows); // committed attempt output
                }
            }
        }
        // All-or-nothing publish: one manifest naming the committed attempts.
        var manifest = new ArrayList<String>();
        manifest.add("version=v1 tasks=" + TASKS);
        for (int t = 0; t < TASKS; t++)
            manifest.add("task-" + t + "-attempt-" + attempts[t] + ".txt");
        java.nio.file.Path ptr = dir.resolve("CURRENT");
        java.nio.file.Files.write(dir.resolve("manifest-v1.txt"), manifest);
        java.nio.file.Files.writeString(ptr, "manifest-v1.txt"); // atomic pointer swap
        // Reader pins ONE manifest and counts only its files.
        String pinned = java.nio.file.Files.readString(ptr).trim();
        long visible = 0;
        for (String line : java.nio.file.Files.readAllLines(dir.resolve(pinned)))
            if (line.endsWith(".txt"))
                visible += java.nio.file.Files.readAllLines(dir.resolve(line)).size();
        System.out.println("attempts_per_task=" + Arrays.toString(attempts));
        System.out.println("published " + pinned + " via atomic pointer " + ptr.getFileName());
        System.out.println("reader sees rows=" + visible + " expected=" + (TASKS * ROWS)
            + " all_or_nothing=" + (visible == TASKS * ROWS));
        System.out.println("OK");
    }
}

پیگیری (استف): دو job هم‌زمان روی یه نام خروجی publish کنن، کدوم نسخه برنده می‌شه؟Follow-up (Staff): Two jobs publish to the same output name at once. Which version wins?

دقیقاً یه برندهٔ CAS: هر دو job نوشتن‌های شرطی روی کلید pointer با نسخهٔ manifest خودشون مسابقه می‌دن؛ store مرتبشون می‌کنه، یکی موفق می‌شه و بازنده نسخهٔ برنده رو می‌بینه، در برابرش دوباره اعتبارسنجی (یا دوباره اجرا) می‌کنه و انتشار رو retry می‌کنه — هرگز کورکورانه بازنویسی نه. خواننده‌ها تمام مدت دست‌نخورده‌ان چون هر manifest قدیم و جدید کامل می‌مونه و خواندن‌های pinشده هرگز سوار نمی‌شن.

Exactly one CAS winner: both jobs race conditional writes on the pointer key with their own manifest version; the store orders them, one succeeds, and the loser sees the winner's version, re-validates (or re-runs) against it, then retries the publish — it never overwrites blindly. The readers stay undisturbed throughout, because every manifest, old and new, stays complete and a pinned read never straddles.

پیگیری (سینیور): object store هیچ rename اتمی نداره. اتم انتشار چیه؟Follow-up (Senior): The object store has no atomic rename. What is the publish atom?

از pointer نسخه‌دار به‌علاوهٔ CAS استفاده کن: manifest تازه رو زیر کلید نسخه‌دار تازه بنویس و بعد pointer رو شرطی از نسخهٔ قدیمِ موردانتظار به تازه بچرخون. اگه store اصلاً CAS نداره، نویسنده رو به یه ناشر تکی محدود کن (lease یا صف) و بگو — اتم ادعایی که نداری بدتر از گلوگاه مستنده.

Use a versioned pointer plus CAS: write the new manifest under a fresh versioned key, then conditionally flip the pointer from the expected old version to the new one. If the store offers no CAS at all, narrow the writer to a single publisher (a lease or a queue) and say so — an atom you claim but do not have is worse than a documented bottleneck.

اشتباهات رایجCommon mistakes

  • تعمیم اتمی بودن rename محلی به object storage: rename روی POSIX اتمیه، ولی «rename» روی object store اغلب copy به‌علاوهٔ delete است. به‌جای فرض سفرِ اتم آشنا، اتم خود store رو انتخاب و تست کن.
  • خلط commitِ task با انتشار job: attemptِ committed تموم‌شده ولی پنهانه؛ فقط barrier به‌علاوهٔ تعویض pointer چیزی رو مرئی می‌کنه. دیباگ attemptها رو می‌خونه و سرو manifestها رو.
  • جمع کردن نسخه‌هایی که خواننده‌های pinشده هنوز نگه داشتن: نسخهٔ قدیم تا پایان grace یه قرارداد زنده‌ست — بعد از grace با شمارش pin جمع کن، هرگز فقط با سن نه.
  • Generalizing local rename atomicity to object storage. A POSIX rename is atomic; an object-store 'rename' is often copy plus delete. Choose and test the store's own atom instead of assuming the familiar one travels.
  • Confusing task commit with job publication. A committed attempt is finished but hidden; only the barrier plus the pointer swap makes anything visible. Debugging reads the attempts, serving reads the manifests.
  • Garbage-collecting versions that the pinned readers still hold. The old version is a live contract until its grace expires — GC after the grace, with pin counts, never by age alone.
