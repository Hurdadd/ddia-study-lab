# ADR-014 — چرا از روز اول Kubernetes و microservice نه؟

Why defer Kubernetes and microservices?

Status: proposed · Date: 2026-10-15

## مسئله / Context

مرزِ منطقیِ ماژول با مرزِ deployment یکی نیست؛ نسخهٔ اول هنوز workload و HA مصوب نداره.

A logical module boundary isn't a deployment boundary, and the first version still has no approved workload or HA.

## گزینه‌ها / Alternatives

یک codebase با API/worker جدا؛ چند microservice؛ Kubernetes از ابتدا.

One codebase with API/workers, multiple microservices, or Kubernetes immediately.

## انتخاب فعلی / Choice

پیشنهاد: اجرای محلیِ تکرارپذیر با API و worker و DB؛ orchestration پیچیده بعد از نیازِ اثبات‌شده.

Our proposal: a reproducible local run with an API, a worker, and a DB; complex orchestration only after a proven need.

## چرایی و trade-off / Rationale and trade-off

عملیات کمتر برای یادگیری؛ در مقابل، isolation و scaling مستقل محدودتر است و در ADR مقیاس دوباره بررسی می‌شود.

Less operations for learning; the trade-off is limited isolation and independent scaling, revisited in the scale ADR.

## فرض‌ها / Assumptions

E01 پایلوت و E10 stress؛ تیمِ عملیات و cloud budget هنوز تعریف نشدن.

Pilot E01 and stress E10; the operations team and the cloud budget still aren't defined.

## روش آزمون / Validation

اجرای تازه از README، crash یک worker، load و drain؛ bottleneck هر پردازش جدا دیده بشه.

A fresh run from the README, a worker crash, load and drain; each process's bottleneck shows up separately.

## بازنگری / Revisit

HA واقعی، noisy neighbor، scaling مستقل یا نیاز استقرار تیم‌ها می‌تواند deployment جدا را توجیه کند. مرز منطقی، مرز استقرار نیست.

Real HA, a noisy neighbor, independent scaling, or a need to deploy per team can justify separate deployments. A logical boundary isn't a deployment boundary.
