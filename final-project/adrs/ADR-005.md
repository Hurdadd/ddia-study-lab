# ADR-005 — چرا Runtime ابتدا محدود باشد؟

Why start with a bounded runtime?

Status: proposed · Date: 2026-10-15

## مسئله / Context

agent عمومی با انتظار، retry، cancellation و اثر بیرونی، از یک حلقهٔ while خیلی پیچیده‌تر است.

A general agent with waits, retries, cancellation, and external effects is a lot more complex than a loop.

## گزینه‌ها / Alternatives

state machine دامنه‌ای کوچک؛ workflow engine آماده؛ موتور عمومی سفارشی.

A small domain state machine, an existing workflow engine, or a custom general engine.

## انتخاب فعلی / Choice

اول یک state machine محدود، برای یادگیریِ قرارداد؛ پیش از workflowهای بلند و پیچیده، engine آماده را benchmark می‌کنیم.

Start with a bounded state machine to learn the contract; benchmark an existing engine before long complex workflows.

## چرایی و trade-off / Rationale and trade-off

قرار نیست موتور workflow عمومی را بازنویسی کنیم. نقطهٔ یادگیری، مرز commit، epoch و outcome نامعلومه.

We don't rewrite a general workflow engine. What you learn here: commit boundaries, epochs, and unknown outcomes.

## فرض‌ها / Assumptions

E02 میانگین ۸ call فرضی است؛ سقف step و deadline جدا تعیین می‌شوند.

E02 takes eight calls on average as an assumption; the step cap and the deadline need their own decisions.

## روش آزمون / Validation

kill/resume؛ stale-owner rejection؛ pause بعد از tool effect؛ ابزار write باید خودش idempotency را enforce کند.

Kill/resume, stale-owner rejection, a pause after a tool effect; write tools enforce their own idempotency.

## بازنگری / Revisit

با انتظار انسانی، DAG پیچیده یا تغییرات ناسازگار workflow، ادامهٔ موتور دستی دوباره توجیه می‌شود. جادو نیست.

Hand-rolling the runtime earns its justification again when human waits, complex DAGs, or incompatible workflow evolution show up. It isn't magic.
