# ADR-008 — چرا اول provider و بعد GPU؟

Why provider first, GPU later?

Status: proposed · Date: 2026-10-15

## مسئله / Context

هدف اولیه اثبات قرارداد پلتفرم است؛ خرید ظرفیتِ بلااستفاده یادگیری را متوقف می‌کند.

The first goal is platform contracts; idle purchased capacity can stall learning.

## گزینه‌ها / Alternatives

provider API؛ model server محلی؛ هر دو از روز اول.

Provider API, local serving, or both on day one.

## انتخاب فعلی / Choice

adapter قابل‌تعویض با budget/trace؛ سپس آزمایش GPU محدود در فاز serving.

Swappable provider adapter with budgets/traces, followed by a bounded GPU experiment.

## چرایی و trade-off / Rationale and trade-off

زود به مسیر قابل‌آزمایش می‌رسیم و بعد کنترل ظرفیت را می‌آموزیم؛ API wrapper را مهندسی inference معرفی نمی‌کنیم.

Reach a testable path sooner, then learn capacity control; an API wrapper is not inference engineering.

## فرض‌ها / Assumptions

E09 قیمت‌های فرضی؛ E01 پایلوت کم‌حجم؛ هزینهٔ واقعی provider هنوز استعلام نشده است.

E09 hypothetical prices, low pilot volume E01; actual provider prices have not been quoted.

## روش آزمون / Validation

cost/task موفق و latency؛ در فاز GPU همان workload، model/config/hardware ثابت.

Cost per successful task and latency; GPU comparisons use pinned workloads/models/configuration/hardware.

## بازنگری / Revisit

نقطهٔ سربه‌سر هزینه، نیاز دادهٔ خصوصی یا bottleneck مستند می‌تواند اولویت GPU را تغییر دهد.

Cost break-even, private-data requirements, or measured bottlenecks can change GPU priority.
