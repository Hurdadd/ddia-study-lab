# ADR-008 — چرا اول provider و بعد GPU؟

Why provider first, GPU later?

Status: proposed · Date: 2026-10-15

## مسئله / Context

هدف اولیه اثبات قرارداد پلتفرم است؛ خریدِ ظرفیتِ بلااستفاده یادگیری را متوقف می‌کند.

The first goal is proving the platform contract; buying idle capacity stops the learning.

## گزینه‌ها / Alternatives

provider API؛ model server محلی؛ هر دو از روز اول.

Provider API, local serving, or both on day one.

## انتخاب فعلی / Choice

adapter قابل‌تعویض با budget/trace؛ بعد آزمایش GPU محدود در فاز serving.

A swappable adapter with budget/trace; then bounded GPU experiments in the serving phase.

## چرایی و trade-off / Rationale and trade-off

زودتر به مسیر قابل‌آزمایش می‌رسیم و بعد کنترل ظرفیت را یاد می‌گیریم؛ API wrapper را مهندسی inference معرفی نمی‌کند.

You reach a testable path sooner and learn capacity control afterwards; an API wrapper is not inference engineering.

## فرض‌ها / Assumptions

E09 قیمت‌ها فرضی است؛ E01 پایلوت کم‌حجم است؛ هزینهٔ واقعی provider هنوز استعلام نشده.

E09 prices are hypothetical; the E01 pilot is small; the real provider cost is still unquoted.

## روش آزمون / Validation

cost/task موفق و latency؛ در فاز GPU همان workload، با model/config/hardware ثابت.

Cost per successful task and latency; in the GPU phase the same workload, with fixed model/config/hardware.

## بازنگری / Revisit

نقطهٔ سربه‌سر هزینه، نیاز دادهٔ خصوصی یا bottleneck مستند می‌تواند اولویت GPU را عوض کند. اول عدد، بعد خرید.

Cost break-even, a private-data need, or a documented bottleneck can change the GPU priority. Number first, purchase second.
