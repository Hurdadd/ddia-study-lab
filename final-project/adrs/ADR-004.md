# ADR-004 — چرا PostgreSQL مرجع وضعیت باشد؟

Why PostgreSQL for authoritative state?

Status: proposed · Date: 2026-10-15

## مسئله / Context

run، بودجه و release به قید یکتا، تغییرِ شرطی و commit پایدار نیاز دارند.

Runs, budgets, and releases each need a unique constraint, a conditional update, and a durable commit.

## گزینه‌ها / Alternatives

PostgreSQL؛ document store؛ event log به‌عنوان تنها مرجع.

PostgreSQL, document storage, or an event log as the sole authority.

## انتخاب فعلی / Choice

پیشنهاد: PostgreSQL برای metadata و state؛ artifact بزرگ بیرون DB، با pointer/hash.

Propose PostgreSQL for metadata/state; large artifacts live outside, with pointers/hashes.

## چرایی و trade-off / Rationale and trade-off

transaction محلی، UNIQUE و CAS ریسکِ run تکراری و overspend را محدود می‌کنند؛ JSON هم برای payload جای خودش را دارد.

Local transactions, uniqueness, and CAS reduce duplicate-run/overspend risks; JSON still earns its place for payloads.

## فرض‌ها / Assumptions

E01 پایلوت و E10 burst؛ اندازهٔ واقعیِ state را هنوز نداریم.

Pilot E01 and burst E10; we still don't have real state sizes.

## روش آزمون / Validation

race روی idempotency/budget؛ EXPLAIN برای claim؛ crash بعد از commit؛ تست restore.

Idempotency/budget races, EXPLAIN plans for claims, crashes after commit, and restore tests.

## بازنگری / Revisit

وقتی قفل، I/O یا حجم index در workload واقعی bottleneck شد، partition/sharding را با یک ADR مستقل بررسی می‌کنیم. اول عدد، بعد معماری.

When measured locks, I/O, or index size become a bottleneck, we look at partitioning/sharding in a separate ADR. Number first, architecture second.
