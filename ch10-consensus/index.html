linearizability means a multi-node system acts as if there were only one copy of the data with atomic ops on it: once a write lands, every reader must see the new value. ۱1 خطی‌پذیری (Linearizability)Linearizability

۱.۱. یک نسخه از داده، یک تضمین تازگی1.1. One copy of the data, one freshness guarantee

خطی‌پذیری یعنی رفتارِ چند نسخه داده واسه یه عملیات، شبیه یه نسخه واحد باشه: خوندنی که بعد از تموم شدنِ نوشتن شروع می‌شه باید اون نوشتن یا تغییرِ بعدی رو ببینه.

مثال فنی: پس از پاسخ موفق

وضعیت اولیه: فرض کن SET x=1 کامل شده؛ بعدش یه کلاینتِ دیگه GET x رو شروع می‌کنه و نوشتنِ تازه‌ای هم تو کار نیست.

اجرای مرحله‌به‌مرحله: حالا خوندنِ خطی‌پذیر باید ۱ ببینه؛ replica عقب‌مونده‌ای که ۰ بده این قول رو شکسته.

نتیجه و دلیل: پس خطی‌پذیری ترتیبِ واقعیِ عملیاتِ جدا از هم رو نگه می‌داره، نه فقط همگراییِ آخرش رو — زمان مهمه.

When data spreads across replicas (Chapter 6), trouble brews: a read may land on a lagging replica and serve stale results. Two schools of thought: eventual consistency (the app cleans up conflicts itself) and strong consistency (the system acts like a single node). Linearizability — a.k.a. atomic consistency or external consistency — is that second school, defined precisely.

تعریف تو یه جمله: به‌محض اینکه یه نوشته با موفقیت تموم شد، همه خوندن‌های بعدی (از هر کلاینتی) باید مقدارِ جدید یا جدیدتر رو ببینن. به این می‌گن قولِ تازگی (recency guarantee). مثالِ کتاب: دو نفر که نتیجه یه بازی رو نگاه می‌کنن؛ نفرِ اول صفحه رو رفرش می‌کنه و نتیجه رو می‌بینه و به نفرِ دوم می‌گه؛ نفرِ دوم رفرش می‌کنه ولی می‌رسه به replica عقب‌افتاده و هنوز «بازی ادامه داره» می‌بینه. اگه هر دو هم‌زمان رفرش کرده بودن، جوابِ متفاوت عجیب نبود؛ ولی نفرِ دوم بعد از شنیدنِ خبر رفرش کرده — و این دقیقاً نقضِ خطی‌پذیریه.

The one-sentence version: as soon as a write lands successfully, every later read (from any client) must see the new value or a newer one. That's the recency promise. The book's example: two friends watching a match score; the first refreshes, sees the result, and tells the second; the second refreshes but lands on a lagging replica still showing “match in progress”. Had both refreshed at the same moment, different answers would be no surprise — but the second refreshed after hearing the news, and that's exactly a linearizability violation.

۱.۲. چه چیزی یک سیستم را خطی‌پذیر می‌کند؟1.2. What makes a system linearizable?

تو خطی‌پذیری، می‌شه هر عملیات رو به یه لحظه بینِ شروع و پایانش سنجاق کرد و ترتیبِ سازگار ساخت. عملیات‌های هم‌پوشان ممکنه ترتیب‌های مجازِ متفاوتی داشته باشن.

مثال فنی: عملیات هم‌پوشان

وضعیت اولیه: تصور کن خوندن x وقتی شروع می‌شه که نوشتن x=1 هنوز جواب نداده؛ مقدارِ قبلی هم ۰ـه.

اجرای مرحله‌به‌مرحله: حالا بسته به نقطه خطی‌شدن، خوندن می‌تونه ۰ یا ۱ برگردونه؛ ولی بعد از دیدنِ نوشتنِ تموم‌شده، خوندنِ بعدی — بدونِ نوشتنِ جدید — به ۰ برنمی‌گرده.

نتیجه و دلیل: باید کلِ تاریخچه با یه ترتیبِ لحظه‌ایِ درست جور دربیاد؛ ساعتِ روی دستِ کلاینت‌ها ملاک نیست — یادت باشه.

To get precise, picture operations as timeline bars: bar start = request sent, bar end = response received. The client never learns exactly when the work happened — only that it landed somewhere in between. If two bars overlap, those operations are concurrent in the system's eyes, and any order goes.

ولی «خوندنِ هم‌زمان هر جوابی بده» کافی نیست: وگرنه مقدار می‌تونست چند بار بینِ ۰ و ۱ بالا و پایین بپره! قانونِ دوم اینه: تصور کن نقطه‌ای بینِ شروع و پایانِ نوشته هست که مقدار تو اون لحظه atomically از ۰ به ۱ می‌پره (بهش می‌گن linearization point). خطی که این نقطه‌ها رو به هم وصل می‌کنه باید همیشه به جلو بره، هیچ‌وقت به عقب. یعنی به‌محض اینکه خوندنی مقدارِ جدید رو دید، همه خوندن‌های بعدی هم باید همون یا جدیدتر رو ببینن.

But “concurrent reads may return anything” doesn't cut it — otherwise the value could ping-pong between 0 and 1 forever! Rule two: imagine a point between the write's start and end where the value flips atomically from 0 to 1 (that's the linearization point). The line joining these points must always march forward, never back. Once a read spots the new value, every later read must see it or something newer.

اجرای مرحله‌به‌مرحله: حالا بسته به نقطه خطی‌شدن، خوندن می‌تونه ۰ یا ۱ برگردونه؛ ولی بعد از دیدنِ نوشتنِ تموم‌شده، خوندنِ بعدی — بدونِ نوشتنِ جدید — به ۰ برنمی‌گرده.

نتیجه و دلیل: باید کلِ تاریخچه با یه ترتیبِ لحظه‌ایِ درست جور دربیاد؛ ساعتِ روی دستِ کلاینت‌ها ملاک نیست — یادت باشه.

تو این نمودار دو تا بند داری. بندِ بالا با عنوانِ «یه اجرای خطی‌پذیر» شروع می‌شه: سه تا ردیفِ رنگی داری به اسم‌های client A و client B و client C. رو ردیفِ C یه نوارِ بنفشه به اسمِ write(x, 1) ⇒ OK — یعنی C داره مقدارِ x رو از ۰ به ۱ عوض می‌کنه. رو ردیفِ A دو تا نوارِ خوندن می‌بینی: اولی read(x) ⇒ 0 که کاملاً قبل از شروعِ نوشته وایساده، پس حتماً باید مقدارِ کهنه یعنی ۰ رو برگردونه. دومی read(x) ⇒ 1 که با نوشته هم‌پوشانی داره.

خطِ عمودیِ خط‌چینِ زرد رو دنبال کن: از بالای بند تا پایینِ نوارِ C کشیده شده و زیرش نوشته «نقطه خطی‌سازی — x دقیقاً همین‌جا به‌طور اتمی ۱ می‌شه». این نقطه داخلِ نوارِ نوشته‌ست — یه جایی بینِ شروع و پایانش. نوارِ اولِ A سمتِ چپِ این خطه (پس ۰)، نوارِ دومِ A از روش رد می‌شه (و ۱ برمی‌گردونه)، و نوارِ سبزِ read(x) ⇒ 1 رو ردیفِ B کاملاً سمتِ راستشه.

نکته مهم همون فلشِ سبزِ کوچیک بینِ تهِ نوارِ دومِ A و سرِ نوارِ Bـه که کنارش نوشته «ترتیبِ زمانیِ واقعی»: خوندنِ B بعد از تموم شدنِ خوندنِ A شروع شده، پس حتی اگه نوشته هنوز تموم نشده باشه، B هم باید ۱ ببینه.

بندِ پایین همون قانون رو به شکلِ یه نقض نشون می‌ده: خواننده ۱ نوارِ read(x) ⇒ 1 داره؛ بعد فلشِ صورتی می‌ره به سمتِ نوارِ قرمزِ خواننده ۲ که روش نوشته read(x) ⇒ 0 — STALE و کنارِ فلش این جمله‌ست: «۲ بعد از شنیدنِ نتیجه از ۱ دوباره خوند». این همون اشتباهِ معروفه: خوندن برگشته عقب. جعبه سمتِ راست قاعده رو جمع می‌کنه: «تا وقتی مقدارِ جدیدی بازنویسی نشده، هیچ خوندنِ بعدی نباید از چیزی که قبلاً دیدیم کهنه‌تر باشه.»

Read the top half as one linearizable execution across three rows — client A, client B, and client C. C's purple bar write(x, 1) ⇒ OK flips x from 0 to 1. A's first read read(x) ⇒ 0 sits fully before the write, so it must return the old value 0; the second read read(x) ⇒ 1 overlaps the write.

Now trace the dashed yellow vertical line: it runs from the top of the band to the bottom of C's bar, labeled “the linearization point — x atomically becomes 1 right here”. That point sits inside the write bar — somewhere between its start and end. A's first bar stands left of it (hence 0), the second crosses it (hence 1), and B's green read(x) ⇒ 1 stands fully right of it.

The key link is the small green arrow between the end of A's second bar and the start of B's, labeled “real-time order”: B's read started after A's read finished, so B must see 1 too, even if the write is still in flight. The bottom half stages the violation: reader 1 holds read(x) ⇒ 1, then a pink arrow points to reader 2's red read(x) ⇒ 0 — STALE bar — reader 2 re-read after hearing reader 1's result. Time walked backward. And the rule box on the right sums it up: once a new value is visible, no later read may return anything older.

۱.۳. خطی‌پذیری در برابر سریال‌پذیری1.3. Linearizability vs serializability

نکته‌ش اینجاست: خطی‌پذیری دعواش سرِ سازگاریِ عملیات با زمانِ واقعیه؛ سریال‌پذیری دعواش سرِ نتیجه تراکنش‌های چندعملیاتیه. داشتنِ یکیش، اون یکی رو خودش ثابت نمی‌کنه.

مثال فنی: تراکنش serial با خواندن کهنه

وضعیت اولیه: فرض کن دو تا تراکنشِ انتقال رو می‌شه با یه ترتیبِ serial توضیح داد.

اجرای مرحله‌به‌مرحله: حالا یه خوندنِ جدا که بعد از جوابِ commit شروع شده، ممکنه از replica قدیمی بیاد — اگه سیستم فقط serializability قول داده باشه.

نتیجه و دلیل: serializability دعواش سرِ قاطی شدنِ تراکنش‌هاست؛ linearizability ترتیبِ واقعیِ عملیات رو می‌خواد. ترکیبِ درستشون می‌رسه به strict serializability — هر دو با هم.

The two words sound alike but live on different axes, friend — and mixing them up is a classic interview faceplant.

۱.۵. کدام روشِ replication خطی‌پذیر است؟1.5. Which replication method is linearizable?

راستش، اسمِ روشِ تکثیر به‌تنهایی خطی‌پذیری رو تعیین نمی‌کنه. مسیرِ خوندن و تأییدِ نوشتن و انتخابِ رهبر و جلوی فعالیتِ رهبرِ قدیمی رو گرفتن باید با هم قول رو بسازن.

مثال فنی: رهبرِ هنوز معتبر؟

وضعیت اولیه: فرض کن A قبلاً رهبر بوده ولی از اکثریت جدا شده و B رهبرِ تازه شده.

اجرای مرحله‌به‌مرحله: حالا خوندنِ محلیِ A می‌تونه قدیمی باشه؛ پروتکل باید قبل از جوابِ خطی‌پذیر هم اعتبارِ رهبری رو چک کنه هم رسیدنِ state به نقطه لازم رو.

نتیجه و دلیل: single-leader بودن فقط اسمِ معماریه؛ خوندن از هر رهبرِ سابقی بدونِ چکِ اعتبار خطی‌پذیر نمی‌شه — رهبرِ سابق، بازنشسته‌ست.

مثال فنی: بهای قطع ارتباط

وضعیت اولیه: تصور کن دو تا مرکز داده سیمشون قطع شده و هر دو می‌خوان یه اسمِ یکتا رو تغییر بدن.

نتیجه و دلیل: CAP همین انتخابِ موقعِ partition رو توصیف می‌کنه؛ تو حالتِ سالم هم هماهنگیِ راه‌دور خرجِ تأخیر داره — قبضش رو حساب کن.

Picture two regions with the link between them cut (each region healthy inside), friend. With multi-leader, each region works solo and writes sync up later. And don't file this under “multi-region only”: any network fault at any scale forces the same call.

«سه‌تایی، دوتاش رو بردار» گول‌زنکه: partition یه خطاست، نه یه انتخاب؛ نمی‌تونی انتخابش نکنی. تنها راهِ «بدونِ partition» اینه که شبکه نداشته باشی (یه نود) — که اون‌وقت دردسترس‌بودنِ بالا هم نداری. فرمولِ بهتر: موقعِ partition یا سازگار باش یا در دسترس (CP یا AP). وقتی شبکه سالمه، هر دو رو می‌تونی داشته باشی. تعریفِ رسمیِ CAP هم خیلی محدوده: فقط linearizability و فقط partition — اون هم کمتر از ۸٪ حادثه‌های گوگل. تعمیمش یعنی PACELC: موقعِ partition بینِ A و C، وگرنه (else) بینِ تأخیرِ کم (L) و C انتخاب کن. امروزه CAP بیشتر ارزشِ تاریخی داره و با نتیجه‌های دقیق‌تر جایگزین شده.
“Pick two of three” is a trap: a partition is a fault, not a choice — you can't opt out of it. The only “partition-free” setup is having no network at all (one node) — which also waves goodbye to high availability. The better formula: during a partition, be consistent or available (CP or AP). With a healthy network you can have both. The formal CAP definition is also tiny: only linearizability and only partitions — under 8% of Google's incidents. Its generalization is PACELC: during a partition pick A or C, else pick low latency (L) or C. These days CAP is mostly history, replaced by sharper results.

نکته غافلگیرکننده آخر: خطی‌پذیری حتی تو یه کامپیوتر هم کمیابه! حافظه RAM رو CPU چندهسته‌ای خطی‌پذیر نیست — به‌خاطرِ cache و store buffer هر هسته — مگر با memory barrier. اون‌جا دلیل، سرعته نه تحملِ خرابی؛ و تو پایگاه‌داده‌های توزیع‌شده هم بیشترِ دلیل‌های کنار گذاشتنِ خطی‌پذیری، سرعتـه. و تهش یه اثباتِ مهم (Attiya & Welch): جواب‌زمانیِ خوندن/نوشتنِ خطی‌پذیر دست‌کم به اندازه عدمِ قطعیتِ تأخیرِ شبکه‌ست. تو شبکه با تأخیرِ متغیر (یعنی همه شبکه‌ها)، خطی‌پذیری ناگزیر کُنده؛ الگوریتمِ سریع‌ترِ خطی‌پذیر وجود نداره — فقط مدل‌های شل‌تر می‌تونن سریع باشن.

One surprise footnote to take home: linearizability is rare even inside one computer! RAM on a multi-core CPU is not linearizable — each core's cache and store buffer see to that — except behind a memory barrier. There the motive is speed, not fault tolerance; and in distributed databases most reasons for dropping linearizability are likewise speed. Finally, one landmark proof (Attiya & Welch): linearizable read/write latency runs at least proportional to network-delay uncertainty. On a variable-latency network (read: every network), linearizability is unavoidably slow; a faster linearizable algorithm doesn't exist — only weaker models can be fast.

۲.۱. شمارنده‌ی single-node و محدودیت‌هایش2.1. The single-node counter and its limits

قانون اول: شمارنده یه نود شناسه‌های پشتِ سرِ هم می‌ده، ولی ظرفیت و سرپا بودنش به همون یه مسیر وابسته‌ست. ترتیبِ گرفتنِ شناسه هم لزوماً ترتیبِ تأییدِ تراکنش‌ها نیست.

مثال فنی: شمارندهٔ یکتا روی یک نود

وضعیت اولیه: فرض کن سرور عددهای 100,101,102 رو به‌ترتیب پخش می‌کنه.

اجرای مرحله‌به‌مرحله: حالا اگه نود بپره — بدونِ ذخیره پایدار و بازیابیِ درست — یا تکرار پیش میاد یا توقف؛ صفِ درخواست‌ها هم سقفِ همون مسیر رو تنگ می‌کنه.

نتیجه و دلیل: شمارنده ساده‌ست ولی دوام و failover و throughputـش طراحی می‌خواد؛ یکتا بودن با بی‌وقفه بودن یکی نیست — دو تا چیزِ جدا.

In a single-node database, the auto-increment ID is both compact (64 bits) and keeps record-creation order: sort chat messages by ID and the conversation comes out right. Underneath, the generator is really a linearizable gadget: each ID request is one atomic fetch-and-add. But it's got three Achilles' heels: it's a single point of failure, fetching an ID from another region means a round trip across the planet, and it chokes under heavy write throughput. (Plus you've got to persist the counter, or a restart may hand out the same ID twice.)

۲.۲. طرح‌های توزیع‌شده‌ی شناسه2.2. Distributed ID schemes

نوبتی هم باشه نوبت شناسه‌های توزیع‌شده‌ست: شناسه توزیع‌شده می‌تونه با شانس، با ترکیبِ زمان و اسمِ نود، یا با گرفتنِ بازه ساخته شه. احتمالِ یکتایی و ترتیب و وابستگی به ساعت تو این روش‌ها یکسان نیست.

مثال فنی: یکتا لزوماً مرتب نیست

وضعیت اولیه: تصور کن دو تا نود بازه‌های 1…1000 و 1001…2000 رو گرفتن.

اجرای مرحله‌به‌مرحله: حالا نودِ دوم ممکنه زودتر ۱۰۰۱ بده و نودِ اول بعداً ۱ بده؛ شناسه‌ها هنوز یکتان.

نتیجه و دلیل: بلوک گرفتن خرجِ هماهنگیِ هر تخصیص رو کم می‌کنه، ولی ترتیبِ عددیِ شناسه دیگه ترتیبِ واقعیِ درخواست‌ها نیست — یکتا آره، مرتب نه.

Five alternative families are on the table, friend. Every one of them promises uniqueness; where they part ways is ordering and linearizability.

ستونِ دوم «② Distributed generators»ـه: Sharded counters (یکتا، ولی ترتیب بینِ شاردها گم می‌شه؛ «شناسه ۱۶ و ۱۷، کدوم زودتر؟»)، Preallocated blocks (نود A بازه ۱ تا ۱۰۰۰ و نود B بازه ۱۰۰۱ تا ۲۰۰۰؛ یه نوشته دیرتر می‌تونه شناسه کوچیک‌تر بگیره)، Random UUID v4 (۱۲۸ بیت، محلی، بدونِ تماس؛ ولی ترتیبش تصادفیه)، و Wall-clock + sequence که مثال‌هاش UUIDv7 / ULID / Snowflakeـه: تقریباً ترتیبِ زمانِ واقعی، ولی skew و پرشِ ساعت می‌تونه ترتیب رو وارونه کنه — پس «تقریباً قطعاً غیرخطی‌پذیر».

ستونِ سوم «③ Logical clocks»ـه با سه‌تا کارت: Lamport clock که جفتِ (counter, nodeID) می‌ده، قانونش counter := max(local, seen) + 1ـه و ترتیبِ کاملِ سازگار با علّیت می‌سازه (ولی نه مفهومِ زمانِ دیواری داره نه خطی‌پذیره)؛ Hybrid logical clock که زمانِ دیواری رو با همون قانون قاطی می‌کنه و حتی با پرشِ NTP هم فقط جلو می‌ره؛ و Vector clocks که واسه هر نود یه شمارنده نگه می‌داره و «هم‌زمان» رو از «بعدی» جدا می‌کنه، به قیمتِ اندازه بزرگ. چیپِ زرد: «ترتیبِ علّی ✓ · تازگیِ خطی‌پذیر ✗».

و نوارِ پایینِ نمودار، پلِ بخشِ بعد رو می‌زنه: «ترتیب دادن، تصمیم گرفتن نیست» — واسه اجرای یه قید، برنده باید بدونه کوچیک‌ترین timestamp رو داره، که یعنی شنیدن از همه نودها؛ یه نودِ خراب کلِ تصمیم رو فلج می‌کنه. تصمیمِ مقاوم در برابرِ خرابی یعنی consensus.

The diagram runs three columns, friend. Column one, “① Single node”, holds two cards: Autoincrement counter (unique + total order + linearizable — but SPOF and bottleneck) and Timestamp oracle, with its fine print: one counter with replication that persists a batch of IDs and hands them out in order — if the node dies, IDs get skipped but never doubled; it can't be sharded and every region must ask one node. The yellow chip at the column's foot sums it up: “linearizable ✓”.

Column two, “② Distributed generators”: Sharded counters (unique, but cross-shard order is lost — “ID 16 vs 17, which came first?”), Preallocated blocks (node A owns 1–1000, node B 1001–2000; a later write can take home a smaller ID), Random UUID v4 (128 bits, local, contact-free — but randomly ordered), and Wall-clock + sequence — UUIDv7 / ULID / Snowflake: roughly real-time ordered, but skew and clock jumps can flip the order — hence “almost certainly not linearizable”.

Column three, “③ Logical clocks”, holds three cards: the Lamport clock handing out (counter, nodeID) pairs under the rule counter := max(local, seen) + 1, building a causal total order (but with no physical-time meaning and no linearizability); the Hybrid logical clock mixing wall-clock time into the same rule so it only marches forward even across NTP jumps; and Vector clocks keeping one counter per node to split “concurrent” from “after” — at the price of size. Yellow chip: “causal order ✓ · linearizable freshness ✗”. And the bottom strip bridges to the next section: “ordering is not deciding” — to enforce a constraint the winner must know it holds the smallest timestamp, which means hearing from every node; one broken node freezes the whole decision. Fault-tolerant deciding means consensus.

۲.۳. ساعتِ منطقی: Lamport و HLC2.3. Logical clocks: Lamport and HLC

بذار ساده بگم: ساعتِ Lamport وابستگیِ رویدادها رو با شمارنده دنبال می‌کنه: علت، عددِ کوچیک‌تر از معلول می‌گیره. عکسِ این حرف درست نیست. HLC اطلاعاتِ منطقی رو با زمانِ دیواری قاطی می‌کنه.

مثال فنی: Lamport روی ارسال پیام

وضعیت اولیه: فرض کن شمارنده A عددِ ۵ـه و پیام رو با برچسبِ ۶ می‌فرسته؛ B هم رو عددِ ۳ـه.

اجرای مرحله‌به‌مرحله: حالا B موقعِ گرفتن مقدار رو می‌رسونه به max(3,6)+1=7. HLC هم همین منطقِ ترتیب رو با تیکه زمانِ دیواری قاطی می‌کنه.

نتیجه و دلیل: اگه a علتِ b باشه برچسبِ a کوچیک‌تره؛ ولی کوچیک‌تر بودنِ برچسب به‌تنهایی ثابت نمی‌کنه a علتِ b بوده — این دام معروفه.

Forget wall clocks for a minute, friend: a logical clock is an event-counting gadget — its number never tells you “what time is it”, but comparing two numbers tells you which came first. You want three things from one: compact unique timestamps; comparability (total order); and an order that respects causality (if A happened before B, A's timestamp sorts smaller).

ساعتِ Lamport (۱۹۷۸) ساده‌ست: هر نود یه شمارنده داره؛ موقعِ تولیدِ رویداد یکیش زیاد می‌کنه؛ هر وقت timestamp بزرگ‌تری از نودِ دیگه دید، شمارنده‌ش رو به اون می‌رسونه. timestamp جفتِ (counter, nodeID)ـه تا حتی با مساوی شدنِ شمارنده هم یکتا بمونه. مقایسه: اول شمارنده، بعد اسمِ نود. تهش یه ترتیبِ کاملِ سازگار با علّیت داری — ولی خطی‌پذیر نیست: فقط قول می‌ده هر رویدادی از هر چی که دیده بزرگ‌تر باشه، نه اینکه «تازه» باشه.

The Lamport clock (1978) is beautifully simple, friend: each node keeps a counter; it ticks up on every local event; whenever it spots a bigger timestamp from another node, it catches up. The timestamp is the pair (counter, nodeID), so it stays unique even on counter ties. Compare: counter first, node ID second. What you get is a causal total order — but not linearizable: it only promises each event beats everything it's seen, not that it's “fresh”.

سه شرکت‌کننده داریم: User A و User B و User C

سه‌تا شرکت‌کننده داری: User A و User B و User C و زیرِ هر سه نوشته «chat node, counter starts at 0» — هر کدوم یه نودِ ساعتِ Lamport با شمارنده صفر. نمودار دو تا فاز داره: «پست‌های هم‌زمان (A و C همدیگه رو ندیدن)» و «B شمارنده‌ها رو قاطی می‌کنه و جواب می‌ده».

تو فازِ اول دو تا فلشِ مستقل می‌بینی: از A به B با برچسبِ msg ts=(1,A) و از C به B با msg ts=(1,C). یادداشتِ کنارِ هر فلش حسابِ شمارنده رو نشون می‌ده: «A: counter 0→1 = ts (1,A)؛ B می‌پذیره max(0,1)=1» و واسه C هم همین‌طور — هر دو بدونِ خبر از هم، شمارنده‌شون رو به ۱ رسوندن. پس دو تا timestamp با شمارنده برابر داری که با اسمِ نود از هم جدا می‌شن.

تو فازِ دوم، B که حالا هر دو تا پیام رو دیده شمارنده‌ش ۱ـه؛ فلشِ reply ts=(2,B) از B به A می‌ره و یادداشتش می‌گه «B: counter 1→2 = ts (2,B)؛ A می‌پذیره max(1,2)=2». ترتیبِ نهایی اینه: (1,A) < (1,C) < (2,B) — اول شمارنده، بعد اسمِ نود. هر رویدادی که علّتاً قبل از اون یکیه، timestamp کوچیک‌تری هم داره. محدودیت هم همون‌جاست: رویدادهای «واقعاً هم‌زمان» با رویدادهای «مرتب ولی بی‌ربط» قابل تشخیص نیستن؛ واسه اون باید بری سراغِ vector clock.

Three chatters — User A, User B, and User C — each a Lamport node starting at counter 0 (“chat node, counter starts at 0”), across two phases: concurrent posts (A and C haven't seen each other) and B merging counters and replying. Phase one shows two independent arrows: A→B tagged msg ts=(1,A) and C→B tagged msg ts=(1,C), each with its counter math (“A: counter 0→1 = ts (1,A); B adopts max(0,1)=1”, same for C) — two equal-counter timestamps told apart by node ID.

In phase two B has seen both messages at counter 1 and fires reply ts=(2,B) back to A (“B: counter 1→2 = ts (2,B); A adopts max(1,2)=2”). Final order: (1,A) < (1,C) < (2,B) — counter first, node ID second. Every causally-earlier event sorts smaller. And the limit sits right there: “truly concurrent” events look just like “ordered but unrelated” ones; telling those apart takes a vector clock.

ساعتِ Lamport دو تا محدودیت داره: هیچ ربطی به زمانِ دیواری نداره (پس «پیام‌های امروز» رو نمی‌تونی باهاش جدا کنی)، و اگه دو تا نود هیچ‌وقت با هم حرف نزنن، شمارنده‌هاشون می‌تونه وحشتناک از هم فاصله بگیره. ساعتِ منطقیِ هیبریدی (HLC) ترکیبِ هر دوتاست: مثلِ ساعتِ دیواری ثانیه می‌شمره، ولی مثلِ Lamport وقتی timestamp بزرگ‌تری دید جلو می‌پره؛ و تو هر تولیدِ timestamp یکیم اضافه می‌کنه تا حتی با پرشِ روبه‌عقبِ NTP فقط جلو بره (یعنی ممکنه کمی از ساعتِ دیواری جلوتر باشه). تهش: timestampی که تقریباً مثلِ ساعتِ دیواری باهاش کار می‌کنی، با ترتیبِ سازگار با علّیت — بدونِ سخت‌افزارِ خاص و فقط با ساعتِ تقریباً همگام. CockroachDB از HLC استفاده می‌کنه.

Two weak spots haunt the Lamport clock, friend: zero link to wall-clock time (so “today's messages” can't be filtered with it), and counters that can drift worlds apart if two nodes never chat. The hybrid logical clock (HLC) blends both: it ticks like wall-clock time but leaps forward Lamport-style on seeing a bigger timestamp; and it adds one to every timestamp it mints, so even a backward NTP jump only moves it forward (possibly a hair ahead of physical time). Net effect: a timestamp you can use almost like wall-clock time, with causal order — no fancy hardware, just roughly-synced clocks. CockroachDB runs on HLC.

Lamport/HLC در برابر vector clockLamport/HLC vs vector clocks
Lamport و HLC واسه ساختنِ transaction ID تو MVCC عالین (اسنپ‌شات با علّیت سازگار می‌مونه). ولی وقتی دو تا timestamp متفاوت می‌بینی، نمی‌تونی بفهمی «هم‌زمان بودن» یا «یکیش قبل از اون یکیه». Vector clock همین رو می‌گه: واسه هر نود یه شمارنده؛ اگه A تو یه نود بزرگ‌تر و B تو نودِ دیگه بزرگ‌تر باشه، یعنی هم‌زمان بودن. قبضش اندازه timestampـه: یه عدد واسه هر نودِ سیستم.
Lamport and HLC are great for minting transaction IDs in MVCC (snapshots stay causally consistent). But staring at two different timestamps, you can't tell “concurrent” from “one before the other”. The vector clock answers exactly that: one counter per node — if A runs bigger on one node and B on another, they were concurrent. Its bill is timestamp size: one number per node in the system.

۲.۴. مولدِ شناسه‌ی خطی‌پذیر و چراییِ consensus2.4. The linearizable ID oracle and why consensus

یه ترفند مصاحبه‌ای: مولدِ شناسه خطی‌پذیر باید ترتیبِ تموم و شروعِ درخواست‌ها رو تو زمانِ واقعی نگه داره. واسه نگه داشتنِ این قول موقعِ خرابی، فقط یه شمارنده محلی تو هر نود کافی نیست.

مثال فنی: مولدِ مرتبِ سراسری

وضعیت اولیه: تصور کن درخواستِ اول شناسه ۱۰۷ گرفته و جوابش کامل شده؛ درخواستِ دوم بعداً شروع می‌شه.

اجرای مرحله‌به‌مرحله: حالا قولِ خطی‌پذیر به دومی شناسه بزرگ‌تر می‌ده؛ چند تا نودِ مستقل با بازه‌های آزاد این شرط رو خودکار نگه نمی‌دارن.

نتیجه و دلیل: واسه این قول باید ترتیبِ تخصیص رو هماهنگ کنی؛ UUID فقط دعواش سرِ یکتاییه — ترتیب پیشکش.

So why isn't Lamport enough, friend? Because linearizability plays by a real-time rule: if A's work finished and B's started after, B must take home the bigger ID — even if those two nodes never spoke. The book's example: a user first flips their account private, then posts a photo from a laptop; but photos and settings live on different shards and the photo shard's counter lags. Net effect: the photo takes the smaller timestamp, and in MVCC a viewer whose timestamp lands between the two still sees the account as “public” next to the private photo! The simple fix: a linearizable ID oracle.

ساده‌ترین پیاده‌سازی همون «تک‌نودِ مطمئن»ـه: شمارنده اتمی + پایدارسازی + replication تک‌رهبری. تو عمل بهش timestamp oracle می‌گن (الگوی Percolator تو TiKV). بهینه‌سازی: به‌جای هر درخواست، یه دسته از شناسه‌ها رو پایدار و replicate کن و یکی‌یکی تحویل بده — بعد از crash شناسه‌ها جا می‌مونن ولی تکراری یا وارونه صادر نمی‌شن. نمی‌تونی این مولد رو shard کنی (ترتیبِ خطی‌پذیرش می‌میره) و نمی‌تونی بینِ مناطق پخشش کنی — ولی کارش اون‌قدر ساده‌ست که یه نود بارِ زیادی برمی‌داره. جایگزینِ بدونِ تماس: روشِ Spanner — ساعتِ دیواری که به‌جای عدد بازه عدمِ قطعیت می‌ده و سیستم به اندازه عرضِ بازه صبر می‌کنه. سخت‌افزار/نرم‌افزارِ ساعتِ دقیق می‌خواد.

The simplest build is the same “reliable single node”: atomic counter + persistence + single-leader replication. Out in the wild it's called a timestamp oracle (the Percolator pattern in TiKV). The trick: persist and replicate a batch of IDs per request and hand them out one by one — after a crash IDs go missing but never double up or flip. You can't shard this oracle (linearizable order would die) nor spread it across regions — but its job is so simple one node shoulders heavy load. The contact-free alternative is Spanner's way — a physical clock handing out an uncertainty interval instead of a number, with the system sitting out the interval's width. It demands precise-clock hardware and software.

آخرین پل: ساعتِ منطقی برای قیدها کافی نیستFinal bridge: logical clocks are not enough for constraints
واسه قفل یا اسمِ کاربری، با ساعتِ منطقی می‌تونی به درخواست‌ها timestamp بدی و «کوچیک‌ترین» رو برنده اعلام کنی. ولی نودِ برنده از کجا می‌فهمه کوچیک‌ترین رو داره؟ باید از هر نودِ دیگه‌ای که ممکنه timestamp داده باشه بشنوه. اگه یکیشون خراب باشه یا از دسترس خارج شه، کلِ سیستم می‌خوابه — یعنی تحملِ خرابی نداری. واسه قفل‌ها و leaseهای مقاوم در برابرِ خرابی به چیزی قوی‌تر از ساعت نیاز داری: consensus.
For a lock or a username, logical clocks can stamp requests and crown the “smallest” the winner. But how does the winning node know it holds the smallest? It must hear from every other node that might have stamped anything. If one of them is broken or unreachable, the whole system naps — zero fault tolerance. For crash-proof locks and leases you need something stronger than clocks: consensus.

۳.۱. یک مسئله، چند شکل3.1. One problem, many faces

دیگه وقتشه بریم سراغ اجماع: توافقِ چند تا نود — با وجودِ بعضی خرابی‌ها — رو یه تصمیمِ معتبر. انتخابِ رهبر و ثبتِ ترتیبِ مشترک و بعضی عملیاتِ شرطی، شکل‌های مرتبطِ همین نیاز به توافق‌ان.

مثال فنی: یک تصمیم با چند اسم

وضعیت اولیه: فرض کن سه تا نود باید معلوم کنن کی مالکِ job J7ـه.

اجرای مرحله‌به‌مرحله: حالا انتخابِ رهبر و نوشتنِ مالک تو لاگِ توافق‌شده و اعمالِ همون تصمیم به state هر نود، شکل‌های مرتبطِ همین مسئله‌ان.

نتیجه و دلیل: هر نود یه مالکِ جدا قبول کنه و اسمش «اجماع» باشه؟ نه! پروتکل باید یه تصمیمِ معتبرِ مشترک بده.

Those three stories — split-brain-free leader election, a crash-proof ID mint, and failure-proof CAS — are secretly one problem: consensus, getting several nodes to agree on one value. It's one of the deepest, hardest problems in distributed computing, friend, and plenty of systems got it wrong through history. The famous names: Viewstamped Replication, Paxos, Raft and Zab. They all play in the non-Byzantine league (messages may arrive late or vanish, nodes may die, but nobody lies). Byzantine algorithms (where up to a third of nodes may turn hostile) live in blockchain-and-friends territory.

نتیجه‌ی FLP: پس چطور ممکن است؟The FLP result: so how is it possible?
نتیجه معروفِ FLP (Fischer–Lynch–Paterson) می‌گه: اگه خطرِ crash یه نود باشه، هیچ الگوریتمی نمی‌تونه همیشه به consensus برسه. ولی دو تا نکته قضیه رو عملی می‌کنه: اول اینکه FLP فقط می‌گه نمی‌شه پایان (termination) رو قول داد، نه اینکه consensus نشدنیه؛ دوم اینکه اثبات مالِ الگوریتمِ قطعی تو مدلِ ناهمگامـه — یعنی بدونِ هیچ timeout یا شانسی. اگه بذاری الگوریتم با timeout حدس بزنه نودی مرده (حتی گاهی اشتباه)، یا فقط از شانس استفاده کنه، consensus حل می‌شه.
The famous FLP result (Fischer–Lynch–Paterson) says: if any node may crash, no algorithm can always reach consensus. But two caveats keep it practical: FLP only says you can't promise termination, not that consensus is undoable; and the proof covers deterministic algorithms in the asynchronous model — no timeouts, no luck. Let the algorithm guess death via timeout (sometimes wrongly), or lean on randomness, and consensus works.

۳.۲. چهره‌های مختلف consensus و خواص چهارگانه3.2. The many faces of consensus and the four properties

اگه تو مصاحبه پرسیدن consensus یعنی چی، این چهارتا رو ردیف کن: توافقِ سرِ نتیجه، معتبر بودنِ پیشنهاد، عوض نشدنِ تصمیمِ نهایی و رسیدن به تصمیم تو شرایطِ لازم. شرایطِ پیشرفتش به مدلِ خرابی و شبکه گره خورده.

مثال فنی: تصمیم مشترکِ معتبر

وضعیت اولیه: تصور کن سه تا رأی‌دهنده پیشنهادهای A و B رو واسه رهبر دارن.

اجرای مرحله‌به‌مرحله: حالا تصمیمِ نهایی باید از پیشنهادِ معتبر باشه، نودها نباید تصمیمِ ناجور بدن و با فرض‌های پیشرفت بالاخره باید تصمیم گرفته شه.

نتیجه و دلیل: خاصیت‌های agreement و validity و integrity و termination با هم قول رو می‌سازن؛ فقط پیامِ رأی داشتن کافی نیست — یادت باشه.

Consensus has many faces, friend: agreeing on one value (like atomic CAS), building an append-only log (a.k.a. total order broadcast), the fetch-and-add op, and atomic commitment of a distributed transaction. And the deep bit: they're all equivalent — crack one and you've cracked them all.

این نمودارِ ساختاری یه قلب و چند تا بازو داره. قلب، جعبه بزرگِ وسطه با عنوانِ CONSENSUS و دو تا زیرنویس: «یه مقدارِ توافق‌شده، یه ترتیبِ توافق‌شده» و «safety همیشه، liveness با اکثریت».

ردیفِ بالا سه‌تا جعبه داره که هر کدوم با فلشِ سبز و برچسبِ «≡ equivalent» به قلب وصل‌ان: Single-value consensus (نودها مقدار پیشنهاد می‌کنن، یکیش انتخاب می‌شه — انتخابِ رهبر، ادعای lease، ثبتِ اسمِ کاربری)، Shared log / total order broadcast (اضافه کردنِ entry به یه ترتیبِ واحد، با «consensus number ∞» — شکلی که بیشترِ سیستم‌ها واقعاً می‌دن بیرون) و Linearizable CAS (مقایسه-و-تنظیم رو یه register، واسه قفل و قیدِ uniqueness).

ردیفِ وسط دو تا جعبه دیگه رو کنارِ قلب می‌ذاره: Atomic commitment (همه commit یا همه abort — consensus با حقِ وتو: یه رأیِ abort یعنی abort؛ پایه 2PC) و Fetch-and-add که با برچسبِ «consensus number 2» استثنای جمعه: فقط بینِ دو تا پیشنهاددهنده تصمیم می‌گیره.

ردیفِ پایین با فلش‌های «yields» از قلب می‌زنه بیرون: State machine replication (همون لاگ + اجرای قطعی = replicaهای یکسان)، Fencing tokens (index هر entry یه عددِ فزاینده‌ست — zxid و revision — که نوشته‌های زامبی رو می‌کُشه) و Leader election & leases (تو هر epoch یه تصمیم؛ بدونِ split brain).

و دو تا جعبه پایینِ صفحه رو آخر بخون: «چی رو باید قول بدی» — چهار تا خاصیتِ Uniform agreement (هیچ دو تا نودی متفاوت تصمیم نمی‌گیرن)، Integrity (تصمیم عوض نمی‌شه)، Validity (فقط مقدارِ پیشنهادشده می‌تونه ببره) و Termination (هر نودِ زنده‌ای بالاخره تصمیم می‌گیره — تنها خاصیتِ liveness که اکثریتِ زنده می‌خواد). سه‌تای اول safety‌ان و حتی با خرابیِ اکثریت هم نباید بشکنن؛ فقط پیشرفت می‌خوابه. جعبه کناری هم «دامِ FLP» رو یادآوری می‌کنه و اینکه Raft و Paxos و VR و Zab تو عمل، لاگِ مشترکِ با failover خودکارن.

Picture this structural diagram as one heart with several limbs. The heart is the big center box CONSENSUS — “one agreed value, one agreed order” — promising “safety always, liveness with a majority”. The top row holds three boxes joined to the heart by green “≡ equivalent” arrows: Single-value consensus (nodes propose, one wins — leader election, lease claims, username registration), Shared log / total order broadcast (appending entries to one order, “consensus number ∞” — the shape most systems actually ship), and Linearizable CAS (compare-and-set on one register, for locks and uniqueness).

The middle row parks two more boxes beside the heart: Atomic commitment (all commit or all abort — consensus with veto rights, where one abort vote means abort; the basis of 2PC) and Fetch-and-add, the odd one out tagged “consensus number 2”: it only settles things between two proposers. The bottom row flows out of the heart via “yields” arrows: State machine replication (the log + deterministic execution = identical replicas), Fencing tokens (each entry's index is a rising number — zxid, revision — that kills zombie writes), and Leader election & leases (one decision per epoch; no split brain).

Save the two bottom boxes for last: “what you must guarantee” — the four properties Uniform agreement (no two nodes decide differently), Integrity (the decision never changes), Validity (only a proposed value may win), and Termination (every live node eventually decides — the only liveness property, and it needs a live majority). The first three are safety and must hold even in catastrophe; only progress stalls. And the side box recalls the “FLP trap”, noting that Raft, Paxos, VR, and Zab are — in practice — shared logs with automatic failover.

۳.۳. از تک‌رهبری به consensus: epoch و دو دور رأی3.3. From single-leader to consensus: epochs and two rounds of voting

بذار ساده بگم: شماره دوره رهبری، تلاش‌های قدیمی و جدید رو از هم جدا می‌کنه. انتخابِ رهبر و تأییدِ ورودی‌های لاگ دو تا تصمیمِ جدان؛ ریزه‌کاریِ رأی‌گیری و نگه داشتنِ داده قبلی تعیین‌کننده‌ست.

مثال فنی: term بالاتر و رأی اکثریت

وضعیت اولیه: فرض کن تو گروهِ پنج‌نودی، A تو term ۷ بوده و B با سه تا رأی تو term ۸ انتخاب می‌شه.

اجرای مرحله‌به‌مرحله: حالا رأی‌دهنده تو هر term طبقِ پروتکل رأی می‌ده و پیامِ term قدیمی رد می‌شه؛ نامزدِ انتخاب هم باید شرطِ تازگیِ لاگ رو رعایت کنه.

نتیجه و دلیل: term قدیمی حقِ ادامه رهبری نمی‌ده؛ شرطِ رأی و لاگ جلوی دو تا تاریخچه پذیرفته‌شده ناجور رو می‌گیره — بزرگ‌تر می‌بره.

In old-school single-leader setups a human did the failover — hello downtime, goodbye termination. Consensus wants automatic leader election, but there's a chicken-and-egg puzzle: electing a leader needs consensus, and consensus needs a leader! The escape hatch: algorithms don't promise “one leader at every moment”; they hand out an epoch number (a ballot in Paxos, a view in VR, a term in Raft) and promise only one leader per epoch.

وقتی نودی مدتی از رهبر خبر نشنوه، انتخاباتِ جدیدی با شماره epoch بزرگ‌تر شروع می‌کنه. اگه دو تا رهبرِ مالِ دو تا epoch با هم دعوا کنن، رهبرِ با epoch بزرگ‌تر می‌بره. و قبل از اینکه رهبرِ جدید اجازه append به لاگ رو داشته باشه، باید از یه quorum (معمولاً اکثریت) رأی بگیره تا مطمئن شه رهبرِ با epoch بالاتری تو کار نیست. تهش: دو دور رأی‌گیری — یکیش واسه انتخابِ رهبر، یکیش واسه تصویبِ هر entry — و quorum این دو تا باید هم‌پوشانی داشته باشن.

When a node stops hearing from the leader, it kicks off a new election with a bigger epoch number. If two leaders from two epochs clash, the higher-epoch one wins. And before the new leader may append to the log, it must collect votes from a quorum (usually a majority) to be sure no higher-epoch leader is around. Net result: two rounds of voting — one to elect the leader, one to approve each entry — and the two quorums must overlap.

این شبیهِ 2PC است؟ نه!Like 2PC? No!
هر دو «دو مرحله رأی» دارن، ولی فرق‌هاشون اساسیه: تو consensus هر نودی می‌تونه انتخابات رو شروع کنه و فقط جوابِ quorum لازمه؛ تو 2PC فقط هماهنگ‌کننده رأی می‌گیره و به تک‌تک شرکت‌کننده‌ها نیاز داره (یکیشون ساکت بمونه، همه می‌خوابن). واسه همینِ ساده، هماهنگ‌کننده 2PC نقطه تکیِ خرابی می‌مونه مگر اینکه خودش با consensus سفت شه.
Both run “two voting rounds”, but don't be fooled: in consensus any node may start an election and only a quorum must answer; in 2PC only the coordinator collects votes and it needs every single participant — one silent node and the whole transaction naps. That's exactly why the 2PC coordinator stays a single point of failure unless consensus hardens it.

۳.۴. لاگِ مشترک و replication ماشینِ وضعیت3.4. The shared log and state machine replication

قضیه اینه که تو تکثیرِ ماشینِ حالت، نودها دستورهای یه لاگِ مشترک رو با همون ترتیب اجرا می‌کنن. اگه اجرای دستورها قطعی باشه و از وضعیتِ یکسان شروع کنن، به وضعیتِ یکسان می‌رسن.

مثال فنی: همان لاگ، همان state

وضعیت اولیه: تصور کن لاگِ commitشده set(x,1) و بعدش increment(x) رو داره.

اجرای مرحله‌به‌مرحله: حالا هر replica سالم هر دو رو با همون ترتیب اعمال می‌کنه و می‌رسه به x=2.

نتیجه و دلیل: state machine باید واسه همون ورودی‌ها همون خروجی رو بده؛ NOW() یا شانسِ جدا تو apply می‌تونه replicaها رو ناجور کنه — قطعی بمون.

Most consensus systems you'll meet ship a shared log (the total-order-broadcast face): Raft, VR, and Zab do it out of the box, and Paxos in practice means Multi-Paxos. The log is a beautiful replication tool: make each entry one database write, have every replica apply the same entries in the same order with deterministic logic, and they all land on one final state — that's state machine replication (and event sourcing's foundation too).

و از همین لاگ می‌شه بقیه شکل‌های consensus رو هم ساخت: مقدارِ اولِ لاگ = جوابِ consensus تک‌ارزشی؛ شماره صندلی تو entryها = consensus جدا واسه هر صندلی؛ جمعِ entryها = شمارنده fetch-and-add؛ و index هر entry = fencing token (تو ZooKeeper بهش zxid می‌گن).

And that one log builds every other consensus face: the log's first value = the single-value consensus answer; seat numbers across entries = one consensus per seat; summing entries = a fetch-and-add counter; and each entry's index = a fencing token (a zxid in ZooKeeper).

اجرای مرحله‌به‌مرحله: حالا هر replica سالم هر دو رو با همون ترتیب اعمال می‌کنه و می‌رسه به x=2.

نتیجه و دلیل: state machine باید واسه همون ورودی‌ها همون خروجی رو بده؛ NOW() یا شانسِ جدا تو apply می‌تونه replicaها رو ناجور کنه — قطعی بمون.

این یه dataflowـه: جریانِ داده از چپ به راست تو پنج‌تا مرحله می‌ره که بالای نمودار شماره خوردن: 01 / Propose، 02 / Append، 03 / Total order، 04 / Replicate و 05 / Apply. تو مرحله اول سه‌تا جعبه می‌بینی: Client 1 writes و Client 2 writes و Client 3 writes — هر سه با توضیحِ «concurrent / propose value»، یعنی چند تا کلاینت هم‌زمان پیشنهاد می‌نویسن. فلشِ «propose write» اون‌ها رو می‌رسونه به جعبه Leader با توضیحِ «single writer / append entry».

فلشِ «append / log entry» از رهبر می‌ره به Shared log (توضیحِ «entries #1 #2 #3 / total order»): یه ترتیبِ واحد از entryها — همون total order broadcast. بعد فلشِ «replicate / synchronous» می‌رسه به مرحله Quorum copy («replica copies / majority ack»): هر entry قبل از تأیید به کلاینت، به‌صورتِ هم‌زمان رو یه اکثریت کپی می‌شه و «majority ack» همون رأیِ quorum واسه هر entryـه. بعدش «deliver in order» می‌ره به Apply in order («in log order / deterministic») و فلشِ «apply» به State machine با توضیحِ «deterministic logic / same final state» می‌رسه: با منطقِ قطعی و ترتیبِ یکسان، همه replicaها به یه وضعیتِ نهایی می‌رسن.

دو تا شاخه فرعی هم از لاگ می‌زنه بیرون که زورِ لاگ رو نشون می‌دن: Fencing token («monotonic counter / log index = token» — فلشِ «index = token»؛ index هر entry یه توکنِ فزاینده‌ست) و Serial txns («stored procedure / one per entry» — فلشِ «stored procedure»؛ هر entry یه تراکنشِ قطعی باشه → تراکنش‌های سریال‌پذیر). حرفِ آخر: شارد کردنِ لاگ (یه لاگ واسه هر shard) مقیاس‌پذیری میاره ولی قول‌های بینِشاردی مثل اسنپ‌شاتِ سازگار و foreign key رو محدود می‌کنه.

Walk it left to right with me: a dataflow in five numbered stages — 01 / Propose, 02 / Append, 03 / Total order, 04 / Replicate, and 05 / Apply. Stage one shows three boxes — Client 1 writes, Client 2 writes, Client 3 writes — all “concurrent / propose value”: several clients pitching in at once. The “propose write” arrow carries them to the Leader (“single writer / append entry”).

The “append / log entry” arrow runs from the leader to the Shared log (“entries #1 #2 #3 / total order”): a single order of entries — total order broadcast in the flesh. Then “replicate / synchronous” reaches Quorum copy (“replica copies / majority ack”): each entry lands on a majority before the client hears back, and “majority ack” is the per-entry quorum vote. “Deliver in order” leads to Apply in order (“in log order / deterministic”), and “apply” to the State machine (“deterministic logic / same final state”): with deterministic logic and identical order, every replica lands on one final state. Two side branches show off the log's muscle: Fencing token (“monotonic counter / log index = token” — each entry's index is a rising token) and Serial txns (“stored procedure / one per entry” — one deterministic transaction per entry buys you serializable transactions). One closing note: sharding the log (one log per shard) buys scalability but clips cross-shard promises like consistent snapshots and foreign keys.

۳.۵. ظرایف: سرنوشتِ یک log entry3.5. Subtleties: the fate of one log entry

نکته‌ش اینجاست: بودنِ یه ورودی رو رهبر به‌معنیِ تأییدِ نهایی‌ش نیست. پروتکل معلوم می‌کنه کی ورودی موندگار و قابل‌اعماله و بعد از عوض شدنِ رهبر چی به سرش میاد.

مثال فنی: وجود روی یک نود، commit نیست

وضعیت اولیه: فرض کن رهبر entry رو رو خودش نوشته ولی قبل از تأییدِ quorum قطع می‌شه.

اجرای مرحله‌به‌مرحله: حالا entry ممکنه تو لاگِ رهبرِ جدید نباشه و بعداً جایگزین شه؛ جوابِ موفق رو فقط باید طبقِ قانونِ commit پروتکل داد.

نتیجه و دلیل: هر entry محلی ماندگارِ نهایی نیست؛ شرطِ commit و شرطِ انتخابِ رهبر با هم از تاریخچه پذیرفته‌شده محافظت می‌کنن — زود قول نده.

Raft, Multi-Paxos, VR, and Zab share one skeleton: a quorum vote elects the leader, and each entry wants another vote. The devil hides in the details: when the old leader dies and a new one shows up, entries the old leader acknowledged must survive. Raft bars lagging nodes from leading (their log must be at least as fresh as a followers' majority); Paxos lets anyone lead but makes the new leader catch its log up before appending.

مثال فنی برای خواندنِ نمودار: وجود روی یک نود، commit نیست

وضعیت اولیه: فرض کن رهبر entry رو رو خودش نوشته ولی قبل از تأییدِ quorum قطع می‌شه.

اجرای مرحله‌به‌مرحله: حالا entry ممکنه تو لاگِ رهبرِ جدید نباشه و بعداً جایگزین شه؛ جوابِ موفق رو فقط باید طبقِ قانونِ commit پروتکل داد.

نتیجه و دلیل: هر entry محلی ماندگارِ نهایی نیست؛ شرطِ commit و شرطِ انتخابِ رهبر با هم از تاریخچه پذیرفته‌شده محافظت می‌کنن — زود قول نده.

این نمودار یه ماشینِ وضعیتـه با سه‌تا گروه که بالاشون اسم نوشته شده: Entry lifecycle (مسیرِ اصلی)، Slow quorum and term change (مسیرِ خطاها) و Terminal outcomes (پایان‌ها). مسیرِ اصلی از 01 Proposed شروع می‌شه («client write arrives / next log slot» — درخواستِ نوشته رسید و رهبر مقدار رو واسه اسلاتِ بعدی پیشنهاد داد)، با فلشِ «append to own log» می‌ره به 02 Appended («leader log, current term»)، بعد با «send to followers» به 03 Replicating («quorum vote on the entry / second vote round» — دورِ دومِ رأی؛ دورِ اول فقط رهبر رو انتخاب کرده بود)، بعد با «acked by quorum» به 04 Committed («durable, client gets OK / never lost»)، و با «apply in log order» به 05 Applied («state machine updated»).

بریم سر مسیرِ خطاها: فلشِ «quorum not reached yet» از Replicating می‌ره به وضعیتِ Stalled («slow or failed nodes / retryable»): نودها کُندن یا خرابن و رهبر منتظر می‌مونه — و فلشِ برگشتیِ «retry and resend» از بالای صف‌ها دوباره برمی‌گردونه به Replicating. مسیرِ جدی‌تر فلشِ «higher term seen»ـه به Superseded («higher term discovered / leader steps down»): رهبرِ قبلی باید کنار بره.

سرنوشتِ entry از اینجا قطعی می‌شه: فلشِ «replaced by new leader» می‌ره به Dropped («uncommitted, overwritten» — entryهای تأییدنشده بازنویسی می‌شن) و فلشِ «client retries» درخت رو دوباره می‌بره به Proposed (کلاینت با رهبرِ جدید دوباره تلاش می‌کنه). و سمتِ سالمِ ماجرا: فلشِ «committed entry survives» از Applied به Durable می‌رسه («survives every failover»). خطِ بینِ این دو تا دقیقاً همون «commit»ـه: قبلش هیچی قطعی نیست، بعدش همه‌چی ابدیه — و دلیلش قانونِ Raftـه: فقط نودی رهبر می‌شه که لاگش دست‌کم به‌روزیِ اکثریت باشه.

Read it as a state machine with three groups: Entry lifecycle (the main path), Slow quorum and term change (the fault paths), and Terminal outcomes. The main path runs 01 Proposed (“client write arrives / next log slot”) → “append to own log” → 02 Appended (“leader log, current term”) → “send to followers” → 03 Replicating (“quorum vote on the entry / second vote round” — the second round; the first only elected the leader) → “acked by quorum” → 04 Committed (“durable, client gets OK / never lost”) → “apply in log order” → 05 Applied (“state machine updated”).

Now the fault paths: “quorum not reached yet” leads from Replicating to Stalled (“slow or failed nodes / retryable”) — the leader waits it out, and “retry and resend” loops back to Replicating. The graver path is “higher term seen” to Superseded (“higher term discovered / leader steps down”): the old leader must step aside. Then the entry's fate is sealed: “replaced by new leader” drops to Dropped (“uncommitted, overwritten” — uncommitted entries get rewritten) with “client retries” looping back to Proposed, while “committed entry survives” runs from Applied to Durable (“survives every failover”). The line between the two is exactly “commit”: before it nothing is final, after it everything is forever — thanks to Raft's rule that only a node at least as fresh as a majority may lead.

سازگاری در برابر دردسترس‌بودنِ انتخابِ رهبرConsistency vs leader-election availability
اگه نودی با داده کهنه رهبر شه، ممکنه رو entryهایی بنویسه که رهبرِ قبلی نوشته — و خاصیتِ append-only می‌شکنه. گاهی با چشمِ باز این قول رو شل می‌کنن تا سریع‌تر برگردن: مثلاً Kafka گزینه unclean leader election رو داره که هر replica‌ای می‌تونه رهبر شه، حتی عقب‌افتاده. تهش: دردسترسیِ بیشتر، ولی دیگه نظریه consensus حاکم نیست — تا وقتی خرابی نداشته باشی خوبه؛ با اولین ترکیبِ بدِ خرابی‌ها، داده گم یا خراب می‌شه. نکته دیگه: واسه خوندنِ خطی‌پذیر هم باید رأیِ quorum گرفت (مثلاً تو etcd) تا «رهبرِ هنوزمعتبر» تأیید شه؛ و الگوریتم‌ها واسه اضافه/کم کردنِ نود به reconfiguration نیاز دارن.
If a stale node takes the lead, it may scribble over entries the previous leader wrote — and append-only snaps. Sometimes teams knowingly loosen this promise to recover faster: Kafka's unclean leader election lets any replica lead, even a lagging one. Net effect: more availability, but consensus theory no longer rules — fine until the first nasty failure combo loses or corrupts data. Sibling point: linearizable reads need a quorum vote too (etcd does this) to confirm “still the valid leader”; and algorithms need reconfiguration to add or drop nodes.

۳.۶. مزایا و بهای consensus3.6. The benefits and price of consensus

راستش، اجماع تحملِ خرابی و تصمیمِ مشترک می‌ده، ولی پیام‌رسانی و نسخه اضافه و اکثریتِ در دسترس می‌خواد. واسه داده و عملیاتی که این هماهنگی رو لازم ندارن، خرجش ممکنه زیاد باشه.

مثال فنی: سه نود، تحمل یک خرابی

وضعیت اولیه: تصور کن گروهِ سه‌عضوی واسه عملیاتِ اکثریتی به دو تا عضوِ در دسترس نیاز داره.

اجرای مرحله‌به‌مرحله: حالا خرابیِ یه عضو قابل‌تحمله؛ با خرابیِ دو عضو پیشرفت می‌خوابه تا اکثریت برگرده.

نتیجه و دلیل: اضافه کردنِ اعضا خرجِ replication و هماهنگی داره؛ اجماع معمولاً مالِ تصمیم‌های لازمه، نه هر حسابِ مستقل — حساب کن.

Consensus is really “single-leader done right”, friend: automatic failover, no lost committed data, no split brain — surviving all of Chapter 9's troubles. The street rule: any automatic-failover system not built on a proven consensus algorithm is probably unsafe. A proven algorithm won't bless the whole system — bugs live elsewhere too — but it's a solid start.

  • اکثریتِ سخت‌گیرانه: سه تا نود واسه تحملِ یه خرابی، پنج تا نود واسه دو تا خرابی. هر عملیات = حرف زدن با quorum؛ اضافه کردنِ نود سیستم رو کُندتر می‌کنه، نه سریع‌تر. تو partition فقط طرفِ اکثریت جلو می‌ره.
  • وابستگی به timeout: فهمیدنِ خرابی با timeoutـه. timeout زیاد = برگشتنِ کُند؛ timeout کم = انتخاباتِ پشتِ سرِ هم و وقت تلف کردنِ سیستم سرِ انتخابِ رهبر به‌جای کارِ مفید. تو چندمنطقه‌ای تنظیمش سخته.
  • حساسیت به شبکه بد: اگه فقط یه لینکِ لرزون باشه، Raft می‌تونه تو حالتی گیر کنه که رهبری مدام بینِ دو تا نود بپره یا رهبر مجبور به استعفا شه و سیستم عملاً جلو نره. جوابِ بعدیِ Raft فازِ pre-vote بود؛ و EPaxos با حذفِ رهبر، جلوی نود/لینکِ بد بهتر وامیسته.
  • Strict majority: three nodes to survive one failure, five for two. Every operation means talking to a quorum; adding nodes makes the system slower, not faster. During a partition only the majority side moves on.
  • Timeout dependence: failure detection runs on timeouts. Long timeout, slow recovery; short timeout, endless elections with the system politicking instead of working. Tuning it across regions is rough.
  • Bad-network sensitivity: one flaky link can trap Raft in leadership ping-pong between two nodes, or force the leader to resign so the system stalls. Raft's later pre-vote phase answered that; EPaxos drops the leader and stands up to bad nodes and links better.

Meet ZooKeeper, etcd and Consul, friend: they look like key-value stores, but don't let that fool you — they're not built for heavy writes. They exist to coordinate the nodes of some other system. Kubernetes leans on etcd; Spark and Flink in HA mode lean on ZooKeeper. Their data is small, fits in memory (persisted to disk too), and rides on consensus across a small fixed crew (3 or 5 nodes) — Google's Chubby lock-service pattern. Four tricks in the bag:

  • قفل و lease: با CAS خطی‌پذیرِ consensus؛ اگه چند تا نود هم‌زمان واسه یه lease مسابقه بدن، فقط یکیشون می‌بره.
  • پشتیبانی از fencing: هر entry لاگ یه عددِ فزاینده می‌گیره (zxid تو ZooKeeper، revision تو etcd) و همین fencing token مجانیه.
  • تشخیصِ خرابی: کلاینت‌ها session بلندمدت دارن و heartbeat می‌فرستن؛ تا timeout برقراره lease زنده‌ست، وگرنه سرویس فرض می‌کنه کلاینت مرده و lease رو آزاد می‌کنه (تو ZooKeeper: ephemeral node).
  • اعلانِ تغییرات: کلاینت می‌تونه بخواد به‌محضِ عوض شدنِ یه کلید خبردار شه (به‌جای polling همیشگی) — مثلاً بفهمه نودِ جدید اومده یا اون یکی مرده.
  • Locks and leases: with consensus-backed linearizable CAS; when several nodes race for one lease, exactly one takes it home.
  • Fencing support: each log entry grabs a rising number (zxid in ZooKeeper, revision in etcd) — a free fencing token.
  • Failure detection: clients hold long-lived sessions and keep heartbeating; while the timeout holds the lease lives, otherwise the service calls the client dead and frees the lease (in ZooKeeper: an ephemeral node).
  • Change notifications: a client can ask for a ping the moment a key changes (instead of polling forever) — e.g. hearing a new node joined or another one died.

مرکز، جعبه بزرگِ Coordination serviceـه (ZooKeeper / etcd / Consul، به سبکِ Chubby) که تو مرزِ «small fixed cluster: 3 or 5 nodes» نشسته — نکته مهمِ نمودار همینه: اندازه این خوشه ثابته، هر چند هزار تا نود خوشه اپ داشته باشه. زیرش جعبه Consensus coreـه (Raft / Zab / Paxos با «in-memory + durable log») که با فلشِ «replicated log» به سرویس وصله.

از مرکز چهار تا فلش می‌ره به ستونِ قابلیت‌ها: «atomic ops» به Locks & leases (فقط یه برنده)، «log index» به Fencing tokens (zxid / revision)، «sessions» به Failure detection (session + heartbeat و نودهای موقتی)، و «key changes» به Change notifications (watch به‌جای polling).

و ستونِ راست مصرف‌کننده‌هان: Leader election با فلشِ «elect leader»، Shard assignment با «token» و «assign» (بازتخصیص موقعِ اومدن یا خرابی)، Config management با «watch» (پیکربندی رو بارگذاری و subscribe کن)، و Service discovery که خطِ خط‌چین و برچسبِ «optional / cache-first» داره: ثبتِ endpointها راحته، ولی این کار اغلب به consensus نیاز نداره و با کشِ DNS هم راه می‌افته.

۴.۲. کاربردها: پیکربندی، تخصیص کار، service discovery4.2. Uses: config, work assignment, service discovery

پیکربندی، کشفِ سرویس و واگذاریِ کار، همشون به اطلاعاتِ مشترک و قابل‌پیگیری نیاز دارن. تغییرِ ثبت‌شده باید به مصرف‌کننده برسه و با وضعیتِ واقعیِ سرویس سنجیده شه.

مثال فنی: اختصاص worker به job

وضعیت اولیه: فرض کن کنترل‌گر واسه job J7 مالکِ worker-B و نسلِ 8 رو ثبت می‌کنه.

اجرای مرحله‌به‌مرحله: حالا workerها تغییر رو می‌بینن و مقصدِ اثر، درخواستِ نسلِ ۷ رو رد می‌کنه.

نتیجه و دلیل: consensus تصمیمِ مالکیت رو هماهنگ می‌کنه؛ اجرای این تصمیم تو برنامه و مقصد هم تیکه‌ای از درستیه — تصمیم به‌تنهایی کافی نیست.

  • مدیریتِ پیکربندی: timeoutها و اندازه thread pool و از این چیزها رو key-value نگه دار و موقعِ تغییر خبردار شو. نکته‌ش اینجاست: این کار به consensus نیاز نداره؛ اگه سرویس رو از قبل داری راحته، وگرنه polling از فایل یا URL هم کارت رو راه می‌ندازه.
  • تخصیصِ کار به نودها: انتخابِ رهبر واسه سرویس‌های stateful و job scheduler؛ و معلوم کردنِ اینکه کدوم shard رو کدوم نوده — با اومدنِ نودِ جدید جابه‌جاییِ شاردها و با خرابیِ نود، تحویلِ کار به بقیه. ترکیبِ عملیاتِ اتمی + نودِ موقتی + خبرها این برگشتنِ خودکار رو ممکن می‌کنه (با کتابخونه‌هایی مثل Apache Curator). و سودِ بزرگ: consensus رو به ۳–۵ نودِ ثابت «برون‌سپاری» می‌کنی، نه هزاران نودِ سیستمِ اصلی.
  • Service discovery: تو ابر، IPها مدام عوض می‌شن؛ سرویس‌ها endpointشون رو ثبت می‌کنن و بقیه پیداشون می‌کنن. ولی اغلب overkillـه: این کار به خطی‌پذیری نیاز نداره و دردسترس بودن و سرعت مهم‌تره — پس معمولاً کش کردن بهتره (مثلِ چندلایه DNS). ZooKeeper واسه همین observer داره: replicaهایی که لاگ رو می‌گیرن ولی رأی نمی‌دن؛ خوندنشون خطی‌پذیر نیست ولی در دسترسه و توانِ خوندن رو بالا می‌بره.
  • Config management: keep timeouts, thread-pool sizes, and that crowd as key-value pairs, and get a ping on change. Heads up: this needs no consensus — handy if you already run the service, otherwise polling a file or URL does the job.
  • Assigning work to nodes: electing a leader for stateful services and job schedulers, and pinning each shard to its node — reshuffling on joins, handing work over on failures. Atomic ops + ephemeral nodes + notifications make this self-healing possible (libraries like Apache Curator help). And here's the big win: you “outsource” consensus to a fixed 3–5 nodes, not the main system's thousands.
  • Service discovery: in the cloud, IPs churn nonstop; services register endpoints and others find them. But honestly it's usually overkill: no linearizability needed here, and availability plus speed matter more — so caching usually wins (think multi-layer DNS). ZooKeeper ships observers for this: replicas that take the log but never vote; their reads aren't linearizable but stay available and lift read throughput.

۶.۲. سوالات پرتکرار مصاحبه6.2. Frequent interview questions

۱. linearizability دقیقاً چه چیزی را تضمین می‌کند؟1. What exactly does linearizability guarantee?

تعریفش اینه: هر عملیات انگار دقیقاً تو یه لحظه — بینِ شروع و پایانش — رو یه نسخه واحد انجام می‌شه. عملیاتی که بعد از پاسخِ نوشتن شروع شه، یا همون نوشتن رو می‌بینه یا تغییرِ بعدی رو — کهنه‌بینی ممنوع.

مثال فنی: پس از پاسخ موفق

وضعیت اولیه: فرض کن SET x=1 کامل شده؛ بعدش یه کلاینتِ دیگه GET x رو شروع می‌کنه و نوشتنِ تازه‌ای هم تو کار نیست.

اجرای مرحله‌به‌مرحله: حالا خوندنِ خطی‌پذیر باید ۱ ببینه؛ replica عقب‌مونده‌ای که ۰ بده این قول رو شکسته.

نتیجه و دلیل: پس خطی‌پذیری ترتیبِ واقعیِ عملیاتِ جدا از هم رو نگه می‌داره، نه فقط همگراییِ آخرش رو — زمان مهمه.

Think of it like this, friend: every operation lands at one instant between its start and finish, on a single copy. Anything starting after a write's response sees that write or something newer — stale views banned.

۲. تفاوتِ linearizability و serializability چیست؟2. What is the difference between linearizability and serializability?

فرقشون ساده‌ست: خطی‌پذیری ساعتِ عملیات رو با زمانِ واقعی جفت می‌کنه؛ سریال‌پذیری فقط می‌گه نتیجه تراکنش‌ها انگار پشتِ سرِ هم اجرا شدن — ولی اون پشتِ سرِ هم بودن لزوماً همون ترتیبِ واقعی نیست.

مثال فنی: تراکنش serial با خواندن کهنه

وضعیت اولیه: فرض کن دو تا تراکنشِ انتقال رو می‌شه با یه ترتیبِ serial توضیح داد.

اجرای مرحله‌به‌مرحله: حالا یه خوندنِ جدا که بعد از جوابِ commit شروع شده، ممکنه از replica قدیمی بیاد — اگه سیستم فقط serializability قول داده باشه.

نتیجه و دلیل: serializability دعواش سرِ قاطی شدنِ تراکنش‌هاست؛ linearizability ترتیبِ واقعیِ عملیات رو می‌خواد. ترکیبِ درستشون می‌رسه به strict serializability — هر دو با هم.

Here's the split: linearizability syncs operation order with real time; serializability only says transactions look sequential — but that sequence doesn't have to match real time.

۳. چرا شرطِ w + r > n به‌تنهایی خطی‌پذیری را تضمین نمی‌کند؟3. Why isn't a quorum with w + r > n linearizable?

داستان اینه: هم‌پوشانیِ جواب‌ها فقط یه شرطشه. نوشتنِ نصفه، تغییرِ هم‌زمان، تشخیصِ نسخه و ترتیبِ خوندن‌ها هم باید سرِ جاشون باشن؛ پروتکلِ خطی‌پذیر چند تا قانونِ دیگه هم رو میز می‌ذاره.

مثال فنی: Quorumِ ناقص در تاریخچه

وضعیت اولیه: فرض کن n=3,w=2,r=2ـه؛ نوشتنِ تازه فقط به A رسیده و هنوز کامل نشده.

اجرای مرحله‌به‌مرحله: حالا خوندنِ اول از A و B نسخه تازه می‌بینه؛ خوندنِ دوم از B و C می‌تونه قدیمی ببینه — اگه پروتکل فقط بزرگ‌ترین جواب رو برگردونه و ترمیمِ لازم رو نخواد.

نتیجه و دلیل: شرطِ هم‌پوشانیِ نوشتنِ کامل واسه کلِ تاریخچه کافی نیست؛ رفتارِ نوشتنِ نصفه و خوندن‌ها هم باید تعریف شه — quorum به‌تنهایی قول نیست.

Because overlapping replies are just one ingredient. Half-done writes, concurrent changes, version detection, and read ordering all need rules too — a linearizable protocol puts several more rules on the table.

۴. خطی‌پذیری چه قیمتی دارد؟4. What does linearizability cost?

قضیه‌ش اینه: خطی‌پذیری خرج داره — هماهنگی و نسخه معتبر می‌خواد، و هماهنگی هم تأخیر داره. موقعِ قطعی هم ممکنه بعضی درخواست‌ها نتونن طبقِ قول جوابِ موفق بگیرن — قبضش رو باید حساب کنی.

مثال فنی: بهای قطع ارتباط

وضعیت اولیه: تصور کن دو تا مرکز داده سیمشون قطع شده و هر دو می‌خوان یه اسمِ یکتا رو تغییر بدن.

اجرای مرحله‌به‌مرحله: حالا اگه هر دو جداگونه جوابِ موفق بدن، یکتایی می‌شکنه؛ مسیری که تصمیمِ واحد می‌خواد تو بخشی از شبکه باید صبر کنه یا خطا بده.

نتیجه و دلیل: CAP همین انتخابِ موقعِ partition رو توصیف می‌کنه؛ تو حالتِ سالم هم هماهنگیِ راه‌دور خرجِ تأخیر داره — قبضش رو حساب کن.

Because freshness has a bill attached: coordination plus a trusted copy, and coordination costs latency. During a cut, some requests just can't succeed under the guarantee — you've got to pay that bill.

۵. CAP را در یک جمله توضیح بده و ایرادش چیست؟5. Explain CAP in one sentence, and what's wrong with it?

جوابش کوتاهه: موقعِ جداییِ شبکه نمی‌شه هم خطی‌پذیر موند هم به همه نودهای سالم جوابِ موفق داد. ایراد CAP هم اینه که خرجِ حالتِ عادی و تنوعِ قول‌ها رو نشون نمی‌ده.

مثال فنی: بهای قطع ارتباط

وضعیت اولیه: تصور کن دو تا مرکز داده سیمشون قطع شده و هر دو می‌خوان یه اسمِ یکتا رو تغییر بدن.

اجرای مرحله‌به‌مرحله: حالا اگه هر دو جداگونه جوابِ موفق بدن، یکتایی می‌شکنه؛ مسیری که تصمیمِ واحد می‌خواد تو بخشی از شبکه باید صبر کنه یا خطا بده.

نتیجه و دلیل: CAP همین انتخابِ موقعِ partition رو توصیف می‌کنه؛ تو حالتِ سالم هم هماهنگیِ راه‌دور خرجِ تأخیر داره — قبضش رو حساب کن.

Short version: during a network split you can't stay linearizable and keep every healthy node answering successfully. And CAP's blind spot? It hides normal-case costs and the variety of guarantees.

۶. چرا نمی‌توانیم برای همه‌چیز از یک مولدِ شمارنده‌ی تک‌نودی استفاده کنیم؟6. Why can't we use one single-node counter for everything?

راستش، مولدِ مرکزی هم گلوگاهه هم نقطه وابستگی. واسه اینکه موقعِ خرابی جاش پر شه، وضعیتِ شمارنده باید سالم بمونه؛ ضمناً ترتیبِ صدورِ شناسه با ترتیبِ commit یکی نیست — قاطی‌شون نکن.

مثال فنی: شمارندهٔ یکتا روی یک نود

وضعیت اولیه: فرض کن سرور عددهای 100,101,102 رو به‌ترتیب پخش می‌کنه.

اجرای مرحله‌به‌مرحله: حالا اگه نود بپره — بدونِ ذخیره پایدار و بازیابیِ درست — یا تکرار پیش میاد یا توقف؛ صفِ درخواست‌ها هم سقفِ همون مسیر رو تنگ می‌کنه.

نتیجه و دلیل: شمارنده ساده‌ست ولی دوام و failover و throughputـش طراحی می‌خواد؛ یکتا بودن با بی‌وقفه بودن یکی نیست — دو تا چیزِ جدا.

Honestly, a central generator is both a bottleneck and a single leg to stand on. Filling its shoes after a crash means keeping counter state intact — and issue order isn't commit order. Don't mix those up.

۷. Lamport clock چگونه کار می‌کند و چه چیزی را تضمین نمی‌کند؟7. How does a Lamport clock work, and what doesn't it guarantee?

ایده‌ش ساده‌ست: هر نود شمارنده‌ش رو زیاد می‌کنه و موقعِ گرفتنِ پیام، خودش رو به شمارنده پیام می‌رسونه. علت عددِ کوچیک‌تر از معلول می‌گیره، ولی عددِ کوچیک‌تر دیدی دلیل نمی‌شه علتش باشه — این دام معروفه.

مثال فنی: Lamport روی ارسال پیام

وضعیت اولیه: فرض کن شمارنده A عددِ ۵ـه و پیام رو با برچسبِ ۶ می‌فرسته؛ B هم رو عددِ ۳ـه.

اجرای مرحله‌به‌مرحله: حالا B موقعِ گرفتن مقدار رو می‌رسونه به max(3,6)+1=7. HLC هم همین منطقِ ترتیب رو با تیکه زمانِ دیواری قاطی می‌کنه.

نتیجه و دلیل: اگه a علتِ b باشه برچسبِ a کوچیک‌تره؛ ولی کوچیک‌تر بودنِ برچسب به‌تنهایی ثابت نمی‌کنه a علتِ b بوده — این دام معروفه.

The idea's simple: each node bumps its counter and jumps to the message's counter on receive. Causes sort smaller than effects — but a smaller number doesn't prove causation. Classic trap.

۸. HLC چه چیزی را به Lamport اضافه می‌کند؟8. What does HLC add to Lamport?

HLC زمانِ دیواری رو با منطقِ Lamport قاطی می‌کنه تا عددِ ساعت هم به زمانِ واقعی نزدیک بمونه هم وابستگی‌ها حفظ شن. ولی حواست باشه: این هنوز قولِ ترتیبِ کاملِ واقعی نیست.

مثال فنی: Lamport روی ارسال پیام

وضعیت اولیه: فرض کن شمارنده A عددِ ۵ـه و پیام رو با برچسبِ ۶ می‌فرسته؛ B هم رو عددِ ۳ـه.

اجرای مرحله‌به‌مرحله: حالا B موقعِ گرفتن مقدار رو می‌رسونه به max(3,6)+1=7. HLC هم همین منطقِ ترتیب رو با تیکه زمانِ دیواری قاطی می‌کنه.

نتیجه و دلیل: اگه a علتِ b باشه برچسبِ a کوچیک‌تره؛ ولی کوچیک‌تر بودنِ برچسب به‌تنهایی ثابت نمی‌کنه a علتِ b بوده — این دام معروفه.

HLC blends wall-clock time with Lamport logic, so the number stays near real time and keeps causality. But heads up: that's still no promise of true total order.

۹. کی به vector clock نیاز داریم؟9. When do we need a vector clock?

وقتی لازمه بفهمی دو تا تغییر به هم وصلن یا مستقل و متعارضن، بردار به کارت میاد. یه عددِ مرتبِ ساده هم‌زمانیِ منطقی رو لو نمی‌ده — اینو قاب کن.

مثال فنی: دو تصمیمِ concurrent

وضعیت اولیه: تصور کن بردارِ رخدادِ اول {A:2,B:1}ـه و دومی {A:1,B:2}.

اجرای مرحله‌به‌مرحله: حالا بردارها incomparableـن و concurrent بودن لو می‌ره؛ یه Lamport scalar فقط می‌تونه بینشون ترتیبِ عددی بسازه.

نتیجه و دلیل: وقتی تشخیصِ نبودِ رابطه علّی لازمه، ترتیبِ کلیِ عددی اطلاعاتِ کافی نمی‌ده — اینجا بردار حرف می‌زنه.

You'll want vectors when you must tell linked changes from independent, conflicting ones. A single sorted number can't expose logical concurrency — frame that one.

۱۰. چهار خاصیتِ consensus کدام‌اند؟10. What are the four consensus properties?

حفظ کن: توافقِ تصمیم‌ها، یه‌بار تعیین شدنِ تصمیم، معتبر بودنِ مقدارِ پیشنهادی، و تموم شدنِ تصمیم‌گیری تو شرایطِ لازم. سه‌تای اول ایمنی‌ان، آخری پیشرفت.

مثال فنی: تصمیم مشترکِ معتبر

وضعیت اولیه: تصور کن سه تا رأی‌دهنده پیشنهادهای A و B رو واسه رهبر دارن.

اجرای مرحله‌به‌مرحله: حالا تصمیمِ نهایی باید از پیشنهادِ معتبر باشه، نودها نباید تصمیمِ ناجور بدن و با فرض‌های پیشرفت بالاخره باید تصمیم گرفته شه.

نتیجه و دلیل: خاصیت‌های agreement و validity و integrity و termination با هم قول رو می‌سازن؛ فقط پیامِ رأی داشتن کافی نیست — یادت باشه.

Memorize these four: agreeing decisions, deciding only once, deciding only proposed values, and actually finishing under the right conditions. The first three are safety; the last one is liveness.

۱۱. نتیجه‌ی FLP یعنی consensus ناممکن است؟11. Does the FLP result mean consensus is impossible?

نه! FLP فقط سقفِ قولِ همیشگیِ پیشرفتِ اجماعِ قطعی رو تو مدلِ کاملاً ناهمگام با ریسکِ crash نشون می‌ده. سیستم‌های واقعی با فرض‌هایی مثل همگامیِ نهایی یا شانس کار می‌کنن؛ timeout به‌تنهایی سندِ حل نیست.

مثال فنی: FLP و پیامِ نامعلومِ دیررس

وضعیت اولیه: فرض کن تو مدلِ کاملاً asynchronous زمانِ رسیدنِ پیام سقفِ مشخصی نداره و یه فرایند هم ممکنه crash کنه.

اجرای مرحله‌به‌مرحله: حالا الگوریتمِ قطعی نمی‌تونه تو همه زمان‌بندی‌ها هم توافق رو نگه داره هم پایانِ تصمیم رو قول بده؛ نرسیدنِ پیام معلوم نمی‌کنه فرایند مرده یا فقط دیره.

نتیجه و دلیل: این نتیجه اجرای عملیِ اجماع رو رد نمی‌کنه؛ پروتکل‌های واقعی safety رو نگه می‌دارن و پیشرفت رو به فرض‌هایی مثل بهتر شدنِ ارتباط و رهبریِ پایدار وصل می‌کنن — تئوری یه چی می‌گه، عمل یه چی.

Nope — FLP only caps the always-finish promise of deterministic consensus in fully async models with crash risk. Real systems lean on eventual synchrony or luck; a timeout alone proves nothing.

۱۲. اجماع، لاگِ مشترک و عملیاتِ اتمیک چه ارتباط و چه تفاوتی دارند؟12. What does “consensus has many equivalent faces” mean?

قضیه اینه که توافق رو مقدار، ترتیبِ معتبرِ لاگ و بعضی عملیاتِ شرطیِ قوی — با فرض‌های درست — به هم وصلن. ولی هر ابزارِ اتمیکی هم‌قدرت نیست و commit اتمیک همون مسئله اجماع نیست.

مثال فنی: یک تصمیم با چند اسم

وضعیت اولیه: فرض کن سه تا نود باید معلوم کنن کی مالکِ job J7ـه.

اجرای مرحله‌به‌مرحله: حالا انتخابِ رهبر و نوشتنِ مالک تو لاگِ توافق‌شده و اعمالِ همون تصمیم به state هر نود، شکل‌های مرتبطِ همین مسئله‌ان.

نتیجه و دلیل: هر نود یه مالکِ جدا قبول کنه و اسمش «اجماع» باشه؟ نه! پروتکل باید یه تصمیمِ معتبرِ مشترک بده.

The thing is, value agreement, a valid log order, and some strong conditional ops all connect under the right assumptions. But not every atomic tool is equally strong — and atomic commit isn't the same problem as consensus.

۱۳. epoch یا term چه نقشی در جلوگیری از split brain دارد؟13. How do epochs/terms prevent split brain?

دوره رهبری پیامِ قدیمی رو از تصمیمِ تازه جدا می‌کنه. نودها دوره و قانون‌های رأی رو رعایت می‌کنن تا رهبرِ قدیمی نتونه نوشته معتبرِ جدید بسازه — رهبرِ سابق، بازنشسته‌ست.

مثال فنی: term بالاتر و رأی اکثریت

وضعیت اولیه: فرض کن تو گروهِ پنج‌نودی، A تو term ۷ بوده و B با سه تا رأی تو term ۸ انتخاب می‌شه.

اجرای مرحله‌به‌مرحله: حالا رأی‌دهنده تو هر term طبقِ پروتکل رأی می‌ده و پیامِ term قدیمی رد می‌شه؛ نامزدِ انتخاب هم باید شرطِ تازگیِ لاگ رو رعایت کنه.

نتیجه و دلیل: term قدیمی حقِ ادامه رهبری نمی‌ده؛ شرطِ رأی و لاگ جلوی دو تا تاریخچه پذیرفته‌شده ناجور رو می‌گیره — بزرگ‌تر می‌بره.

A leadership era separates old messages from fresh decisions. Nodes honor eras and voting rules so an old leader can't mint valid new writes — yesterday's leader stays retired.

۱۴. تفاوتِ دو دورِ رأیِ consensus با 2PC چیست؟14. How do consensus's two votes differ from 2PC?

تو اجماع رأی مالِ انتخابِ رهبر و سفت کردنِ ورودیِ معتبره؛ تو 2PC شرکت‌کننده‌ها اول آمادگی‌شون رو اعلام می‌کنن بعد تصمیمِ مشترکِ commit یا abort رو اجرا می‌کنن. دو تا بازیِ جدا.

مثال فنی: اجماع با 2PC فرق دارد

وضعیت اولیه: فرض کن تو consensus سه تا replica از پنج‌تا می‌تونن با خرابیِ دو عضو جلو برن.

اجرای مرحله‌به‌مرحله: حالا تو 2PC، participant آماده‌ای که تصمیمِ coordinator رو نداره ممکنه معطل بمونه؛ رأیِ yes همه واسه مسیرِ commit لازمه.

نتیجه و دلیل: هر دو پیام‌های چندمرحله‌ای دارن، ولی یکیش تصمیمِ تکراریِ مقاوم به خرابیه اون یکی commit مشترکِ منابع رو می‌خواد — دو تا بازیِ جدا.

In consensus, votes elect leaders and nail down valid entries; in 2PC, participants first declare readiness, then carry out the joint commit-or-abort call. Two different games.

۱۵. state machine replication چیست و چرا مهم است؟15. What is state machine replication and why does it matter?

نسخه‌ها دستورهای لاگِ معتبر رو با همون ترتیب رو وضعیتِ یکسان اجرا می‌کنن. اجرای قطعی خروجی رو یکسان نگه می‌داره؛ ورودیِ غیرقطعی رو باید تو قرارداد کنترل کنی — قرارداد رو جدی بگیر.

مثال فنی: همان لاگ، همان state

وضعیت اولیه: تصور کن لاگِ commitشده set(x,1) و بعدش increment(x) رو داره.

اجرای مرحله‌به‌مرحله: حالا هر replica سالم هر دو رو با همون ترتیب اعمال می‌کنه و می‌رسه به x=2.

نتیجه و دلیل: state machine باید واسه همون ورودی‌ها همون خروجی رو بده؛ NOW() یا شانسِ جدا تو apply می‌تونه replicaها رو ناجور کنه — قطعی بمون.

Replicas run the valid log's commands in the same order on the same state. Deterministic execution keeps outputs identical — but you've got to fence non-deterministic inputs in the contract. Remember that.

۱۶. چرا رهبرِ جدید نباید داده‌ی کهنه داشته باشد؟16. Why mustn't the new leader hold stale data?

چون رهبرِ تازه باید چیزایی که واسه نگه داشتنِ ورودی‌های تأییدشده لازمه رو داشته باشه. انتخابِ نسخه عقب‌افتاده بدونِ قانون‌های لاگ ممکنه داده پذیرفته‌شده رو نابود کنه.

مثال فنی: وجود روی یک نود، commit نیست

وضعیت اولیه: فرض کن رهبر entry رو رو خودش نوشته ولی قبل از تأییدِ quorum قطع می‌شه.

اجرای مرحله‌به‌مرحله: حالا entry ممکنه تو لاگِ رهبرِ جدید نباشه و بعداً جایگزین شه؛ جوابِ موفق رو فقط باید طبقِ قانونِ commit پروتکل داد.

نتیجه و دلیل: هر entry محلی ماندگارِ نهایی نیست؛ شرطِ commit و شرطِ انتخابِ رهبر با هم از تاریخچه پذیرفته‌شده محافظت می‌کنن — زود قول نده.

A fresh leader must carry what it takes to preserve acknowledged entries. Electing a lagging copy without log rules can wipe out accepted data.

۱۷. در خواندنِ خطی‌پذیر چگونه مطمئن می‌شویم رهبر هنوز معتبر است؟17. Why vote even for a linearizable read?

قبل از خوندنِ قوی باید مطمئن شی رهبر هنوز مجوز داره و وضعیتِ لازم اعمال شده. تماس با اکثریت یا lease با فرض‌های معتبر از راه‌هاشه؛ ولی رأیِ جدا واسه هر خوندن قانونِ عمومی نیست.

مثال فنی: رهبرِ هنوز معتبر؟

وضعیت اولیه: فرض کن A قبلاً رهبر بوده ولی از اکثریت جدا شده و B رهبرِ تازه شده.

اجرای مرحله‌به‌مرحله: حالا خوندنِ محلیِ A می‌تونه قدیمی باشه؛ پروتکل باید قبل از جوابِ خطی‌پذیر هم اعتبارِ رهبری رو چک کنه هم رسیدنِ state به نقطه لازم رو.

نتیجه و دلیل: single-leader بودن فقط اسمِ معماریه؛ خوندن از هر رهبرِ سابقی بدونِ چکِ اعتبار خطی‌پذیر نمی‌شه — رهبرِ سابق، بازنشسته‌ست.

Before a strong read, make sure the leader's mandate is still good and the needed state is applied. Asking the majority or holding a valid lease both work — but a separate vote per read isn't the general rule.

۱۸. چرا consensus را همه‌جا به کار نمی‌بریم؟18. Why not use consensus everywhere?

آخه اجماع پیام و ذخیره و هماهنگی می‌خواد و پیشرفتش به تعدادِ کافیِ اعضا گره خورده. بهتره خرجش کنی واسه تصمیم‌هایی که اختلافشون قابل‌قبول نیست — حساب کن.

مثال فنی: سه نود، تحمل یک خرابی

وضعیت اولیه: تصور کن گروهِ سه‌عضوی واسه عملیاتِ اکثریتی به دو تا عضوِ در دسترس نیاز داره.

اجرای مرحله‌به‌مرحله: حالا خرابیِ یه عضو قابل‌تحمله؛ با خرابیِ دو عضو پیشرفت می‌خوابه تا اکثریت برگرده.

نتیجه و دلیل: اضافه کردنِ اعضا خرجِ replication و هماهنگی داره؛ اجماع معمولاً مالِ تصمیم‌های لازمه، نه هر حسابِ مستقل — حساب کن.

Since consensus eats messages, storage, and coordination, and progress hangs on having enough members around. Spend it on decisions where disagreement isn't an option. Do the math.

۱۹. سرویسِ هماهنگی دقیقاً چه چیزی روی consensus می‌سازد؟19. What exactly does a coordination service build on consensus?

سرویسِ هماهنگی رو توافقِ معتبر، چیزایی مثل نگاشت و پیکربندی و خبرِ تغییر و مالکیتِ زمان‌دار می‌سازه. ولی مصرف‌کننده هنوز باید قطعِ ارتباط و مالکیتِ قدیمی رو خودش جمع کنه.

مثال فنی: قفل و تنظیمات روی etcd

وضعیت اولیه: تصور کن کلید /jobs/J7/owner و نسخه پیکربندی تو سرویسِ هماهنگی نگه داشته می‌شن.

اجرای مرحله‌به‌مرحله: حالا عملیاتِ شرطی مالک رو معلوم می‌کنه و watch تغییر رو خبر می‌ده؛ مصرف‌کننده بعد از قطعِ اتصال باید وضعیت رو دوباره همگام کنه.

نتیجه و دلیل: watch فقط خبرِ تغییره، خودش مجوزِ اثر نیست؛ کارگر هنوز به lease و fencingِ مناسبِ منبعِ کار نیاز داره — خبر با مجوز فرق داره.

A coordination service builds mappings, config, change news, and timed ownership on top of valid agreement. But you, the consumer, still clean up disconnects and stale ownership yourself.

۲۰. اگر مجبور باشی یک جمله از این فصل را در مصاحبه بگویی، کدام است؟20. If you had one sentence from this chapter in an interview, which?

تضمین رو از رو عاقبتِ خطا انتخاب کن: تازگیِ خوندن و وابستگیِ رویداد و تصمیمِ مشترک سه‌تا نیازِ جدان. اسمِ ابزار هیچ‌وقت جای مشخص کردنِ قانونِ لازم رو نمی‌گیره — اینو قاب کن.

مثال فنی: تضمین را برای هر مسیر انتخاب کن

وضعیت اولیه: تصور کن ثبتِ اسمِ کاربری یکتاییِ فوری می‌خواد، ولی شمارنده بازدید می‌تونه چند ثانیه عقب باشه.

اجرای مرحله‌به‌مرحله: حالا مسیرِ اول هماهنگی و قیدِ سفت می‌گیره؛ مسیرِ دوم جمعِ غیرهم‌زمان با کنترلِ تکرار داره.

نتیجه و دلیل: قولِ قوی رو بر اساسِ قانونِ همون عملیات انتخاب می‌کنی؛ یه برچسبِ consistency واسه همه تیکه‌های محصول کافی نیست — یه برچسب واسه همه کافی نیست.

Pick the guarantee from the failure's fallout: read freshness, event dependence, and joint decisions are three separate needs. A tool's name never replaces naming the rule you need — frame that one.

۶.۳. اشتباهات رایج در جواب‌های مصاحبه6.3. Common mistakes in interview answers

  • ❌ «linearizability همون serializabilityـه.» → ✅ نه رفیق! یکیش قولِ تازگیِ یه تیکه داده‌ست، اون یکی ایزوله‌سازیِ تراکنشِ چندتیکه‌ای — قاطی‌شون نکن.
  • ❌ «quorum داریم (w + r > n) پس قویاً سازگاریم.» → ✅ نه! حتی با quorum هم خوندنِ کهنه ممکنه — نمودار ۳ همین دام رو نشونت می‌ده.
  • ❌ «CAP یعنی از سه‌تا دوتا بردار.» → ✅ partition چیزی نیست که تو انتخابش کنی؛ فقط موقعِ partition باید بینِ C و A یکی رو بگیری.
  • ❌ «UUID می‌ذاریم، پس ترتیب هم داریم.» → ✅ ترتیبِ UUID نسخه ۴ تصادفیه؛ ترتیب می‌خوای برو سراغ ULID/UUIDv7 یا ساعتِ منطقی.
  • ❌ «timestamp سرور کافیه؛ NTP هم داریم دیگه.» → ✅ skew و پرشِ ساعت ترتیب رو به هم می‌ریزه؛ ساعتِ دیواری خطی‌پذیر نیست — حساب کن.
  • ❌ «الگوریتم consensus داریم، پس همه عملیات‌هامون خطی‌پذیرن.» → ✅ خوندنی که نپرسه «هنوز رهبرم؟» راحت کهنه می‌شه — یادت باشه.
  • ❌ «FLP ثابت کرد consensus ممکن نیست.» → ✅ FLP فقط می‌گه termination تو مدلِ ناهمگامِ قطعی قول داده نمی‌شه؛ با timeout و شانس قضیه حل می‌شه.
  • ❌ «واسه سرعت، بذار replica عقب‌افتاده هم رهبر شه.» → ✅ یعنی قیدِ ایمنی رو ول کردی؛ نوشته commitشده ممکنه گم شه — این دام معروفه.
  • ❌ “Linearizability is serializability.” → ✅ Nope, friend — one is a freshness promise for a single object, the other is isolation for multi-object transactions. Don't mix them up.
  • ❌ “We've got a quorum (w + r > n), so we're strongly consistent.” → ✅ Not so fast — stale reads can still sneak through. Diagram 3 catches this red-handed.
  • ❌ “CAP means pick two of three.” → ✅ Partitions aren't on the menu — you don't pick them. You only pick C or A once a partition hits.
  • ❌ “We use UUIDs, so we've got order.” → ✅ UUID v4 order is random noise; if you want order, grab ULID/UUIDv7 or a logical clock.
  • ❌ “Server timestamps do the job; we've got NTP.” → ✅ Skew and clock jumps scramble order — wall-clock time is never linearizable. Do the math.
  • ❌ “We run consensus, so all our operations are linearizable.” → ✅ A read that never asks “am I still leader?” can quietly go stale. Remember that.
  • ❌ “FLP proved consensus is impossible.” → ✅ It only says termination isn't guaranteed in deterministic async models — timeouts and a little luck fix that.
  • ❌ “For speed, let a lagging replica lead.” → ✅ That's you dropping the safety belt — committed writes can vanish. Classic trap.

۶.۴. چک‌لیستِ ۵ دقیقه‌ای قبل از مصاحبه6.4. Five-minute checklist before the interview

  1. تعریف linearizability رو حفظ کن + قاعده «خوندنِ بعدی هیچ‌وقت کهنه‌تر نمی‌شه».
  2. فرق linearizability و serializability رو بگو + ترکیبشون (strict serializability).
  3. سه جایی که خطی‌پذیری واجبه: قفل و انتخابِ رهبر، قیدِ uniqueness سفت‌وسخت، کانال‌های موازی.
  4. چرا quorum به‌تنهایی کافی نیست + دو تا راهِ تعمیرش (read repair هم‌زمان + خوندنِ timestamp قبل از نوشتن).
  5. CAP رو درست بگو: «موقعِ partition، سازگار یا در دسترس» + یه اشاره به PACELC.
  6. سه‌تا ساعت رو ردیف کن: Lamport، HLC، vector — هر کدوم چی قول می‌دن.
  7. چهارتا خاصیت consensus رو بشمر + بگو کدوم safetyـه کدوم liveness.
  8. یه جمله درباره epoch/term، یه جمله درباره state machine replication — اینو قاب کن.
  1. Say linearizability's definition cold + the “later reads never go older” rule.
  2. Contrast linearizability vs serializability, then combine them (strict serializability).
  3. Name the three must-have spots: locks and leader election, hard uniqueness, parallel channels.
  4. Explain why quorums fall short + the two fixes (synchronous read repair + pre-write timestamp reads).
  5. State CAP right: “during a partition, consistent or available” + a nod at PACELC.
  6. Line up the three clocks — Lamport, HLC, vector — and what each one promises.
  7. Count off consensus's four properties + which are safety and which is liveness.
  8. One sentence on epoch/term, one on state machine replication — frame that one.

سه replica ابتدا v1 دارن. write تک‌نویسنده با هدف w=3 فقط n1 رو به v2 رسونده و هنوز کامل نشده. read اول با r=2 از {n1,n2} مقدار v2 و read دوم که بعد از پایان اول شروع می‌شه از {n2,n3} مقدار v1 می‌گیره؛ history رو رسم کن و نقض new-then-old رو ثابت کن. نسخه اصلاح‌شده، max نسخه رو پیش از پاسخ read به quorum دوگرهی write-back می‌کنه و replica هرگز به نسخه کمتر عقب نمی‌گرده. قبل و بعد از write-back crash تزریق کن و completed رو از دید caller تعریف کن. read repair پس‌زمینه این شرط رو نمی‌ده. مدل SWMR با عضویت ثابت رو صریح بنویس؛ برای MWMR query timestamp قبل از write، tag یکتای مرتب و quorum مناسب لازمه.

Start three replicas at v1. Your incomplete single-writer write targeting w=3 has updated only n1 to v2. Read1 from {n1,n2} with r=2 returns v2; Read2 starts after Read1 completes and returns v1 from {n2,n3}. Draw the history and prove new-then-old violates linearizability. Fix it with maximum-version write-back to a two-node quorum before returning, with replicas rejecting version regression. Inject crashes before and after write-back; completion is observed by the caller. Background repair doesn't satisfy the condition. State fixed-membership SWMR assumptions; MWMR additionally needs pre-write timestamp queries, uniquely ordered tags and suitable quorums.

تمرین ۳ — مولدِ شناسه‌ی oracle با failoverExercise 3 — an oracle ID generator with failover

رزرو بادوام بازه پیش از صدور، یکتایی رو با پذیرش gap حفظ می‌کنه؛ شاردها می‌تونن بازه یا namespace جدا داشته باشن.You durably reserve ranges before issuing IDs, so you keep uniqueness with gaps; your shards may allocate disjoint ranges or namespaces.

نسخهٔ بازبینی‌شده برای مصاحبهReviewed interview brief

حالا مولد ID رو با رزرو پایدار بازه طراحی کن و crash وسط دسته رو تحلیل کن. uniqueness، gap-free، ترتیب تخصیص و ترتیب مشاهده real-time رو جدا تعریف کن. طرح مرکزی، UUID و shard-prefixed ID رو مقایسه کن؛ برای failover، allocator رو fence کن.Think of it — you're building an ID generator.   • high-water mark رو قبل از صدور ID پایدار می‌کنیYou persist your high-water mark before issuing IDs
  • gap رو از duplicate جدا می‌کنیYou separate gaps from duplicate IDs
  • نیاز به هماهنگی رو به ضمانت ordering وصل می‌کنیYou tie coordination to your ordering guarantee

پیگیری مصاحبه:Interview follow-up: حالا دو تا node بازه جدا دارن؛ آیا IDهای صادرشده به ترتیب زمان جهانی زیاد می‌شن؟Two nodes issue IDs from disjoint ranges. Do your IDs increase in global real-time order?

آزمایشگاه تکمیلی · زمان تقریبی ۲–۴ ساعتExtended hands-on laboratory · estimated 2–4 hours

مولد شناسه، high-water mark دسته رو قبل از تحویل اولین ID پایدار می‌کنه. دسته ۱ تا ۵ رو رزرو کن، ۱ تا ۳ رو بده، crash کن و از ۶ شروع کن؛ نبود تکرار و مجازبودن gap رو assert کن. بعد دو allocator با بازه بادوام جدا یا namespace جدا بساز و یکتایی رو بیازما. uniqueness، gap-free، ترتیب تخصیص و ترتیب real-time پاسخ‌های غیرهم‌پوشان رو جدا تعریف کن؛ batching و چند allocator ممکنه ترتیب جهانی رو از بین ببره. تو failover هیچ بازه رزروشده رو دوباره واگذار نکن و reserve بعدی رو با epoch تو storage محافظت کن. fence روی reserve به‌تنهایی پاسخ‌های باقی‌مونده تو RAM رهبر قدیم رو متوقف نمی‌کنه؛ برای ترتیب جهانی، مسیر پاسخ هم باید مالک معتبر رو کنترل کنه.

Persist each batch high-water mark before issuing its first ID. Reserve 1..5, issue 1..3, crash and restart at 6; assert no duplicates with allowed gaps. Then implement two allocators with durably disjoint ranges or namespaces and test uniqueness. Define uniqueness, gap-free allocation, allocation order and real-time ordering of non-overlapping responses separately; batching across allocators can break global order. Never reassign reserved ranges after failover, and epoch-fence future reservations at storage. A reserve fence alone can't stop an old leader serving its remaining RAM IDs; global ordering also needs a valid-owner check on the response path.
