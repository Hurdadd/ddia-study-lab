سؤال مصاحبهInterview question
فرض کن سه تا process داری. send/receive و رخداد محلی رو با Lamport clock شماره‌گذاری کن. با tie-breaker از process ID ترتیب کامل بساز. یه مثال بزن که نشون بده L(a)
Picture this — you've got three processes passing messages. Label local events and messages using Lamport clocks and process-ID tie breaking. Show why increasing timestamps like L(a)

پاسخ ۶۰ثانیه‌ایThe 60-second answer

به هر پروسه یک شمارنده بده: هر رخداد محلی و هر ارسال ‎+1‎ بزن، روی دریافت max بگیر و هیچ‌وقت عقب نرو، بعد مهر (counter, processID) بزن. مرتب‌سازی با tie-break شناسه درمی‌آید: (1,A) < (1,C) < (2,B) — یک ترتیب کلی که به زنجیرهٔ پیام‌ها احترام می‌گذارد. ولی حواس باشه: این ترتیب علّیت نیست و هم‌زمانی درش اصلاً پیدا نمی‌شود؛ برای دیدنش باید سراغ ساعت برداری بری. شماره می‌دهد، ولی داستان علت‌ومعلول را برایت تعریف نمی‌کند.
Give every process a counter: tick +1 on local/send events, adopt max(local, seen) on receive, stamp (counter, processID). Sort by that stamp with the process-ID tie-break and you get a total order — (1,A) < (1,C) < (2,B) — that respects every message chain. Here's the catch: that order is not causality, and concurrency is invisible in it; seeing concurrency costs you vector clocks. It numbers events beautifully — it just doesn't tell you the story of cause and effect.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن سه پروسه A و B و C با شناسهٔ یکتا داریم. tie-break فقط یکتایی می‌خواد، نه هیچ‌چیز دیگه.
  • این سناریوی آموزشی از نمودار ۵ فصله: A و C هرکدام یک‌بار می‌فرستن و B هر دو رو می‌گیره، بعد جواب می‌ده.
  • پیام‌ها می‌تونن تأخیر داشته باشن، ولی قاعدهٔ دریافت per-delivery اعمال می‌شه؛ هیچ ساعت دیواری‌ای هم در کار نیست.
  • Picture three processes A, B and C with unique IDs. The tie-break only needs uniqueness — nothing else.
  • This teaching scenario comes straight from chapter diagram 5: A and C post once each, B merges both and then replies.
  • Messages can be delayed, but the receive rule is applied per delivery. No wall clock is used anywhere.

چرا این روش و این عددها؟Why this method and these numbers?

قاعدهٔ receive=max(local,received)+1 باعث می‌شود پیامِ دریافت‌شده بعد از ارسالش timestamp بزرگ‌تری داشته باشد؛ جمع یک برای جدا شدن رویداد دریافت از رویداد قبلی است. دو رویداد بی‌ربط می‌توانند timestamp برابر یا مرتب داشته باشند، پس عکس رابطهٔ happened-before برقرار نیست. process_id فقط tie-break قطعی می‌دهد؛ از آن علت‌ومعلول نمی‌سازیم. سه process کمترین سناریوی روشن برای ارسال مستقل و دریافت مشترک را فراهم می‌کنند.

Receive=max(local,received)+1 gives reception a timestamp greater than its send; that extra one separates the receive event from the one before it. Unrelated events may end up with equal or ordered timestamps, so the converse of happened-before fails. Process IDs only give you a deterministic tie-break — you cannot build causality out of them. Three processes make independent sends and a shared receiver easy to inspect.

مدل ذهنیMental model

ساعت Lamport ماشین شماره‌گذاریه، نه ماشین حقیقت. به هر رخداد یک مهر می‌زند که قشنگ مرتب شود و هیچ‌وقت با زنجیرهٔ پیام در تضاد نیفتد. پیام‌ها تنها واقعیت‌اند؛ مهرها فقط برچسب‌هایی‌اند که به پیام‌ها احترام می‌گذارند. عدد می‌زند، ولی دلیل را نمی‌گوید.
Think of a Lamport clock as a numbering machine, not a truth machine. It stamps every event so the stamps sort nicely and never contradict a message chain. The messages are the only facts; the stamps are just labels that respect them. It numbers events beautifully — it just doesn't explain them.

حل گام‌به‌گامStep by step

  1. شمارش از صفر برای هر پروسه یک شمارنده از صفر. هر رخداد محلی و هر ارسال ‎+1‎ می‌زند — ساعت فقط جلو می‌رود، یک قدم per-event.
  2. روی دریافت، max بگیر روی دریافت max بگیر. سناریوی کتاب را با هم برو: B از A می‌گیرد max(0,1)=1 و از C می‌گیرد max(1,1)=1، بعد ارسالِ جواب ‎۱+۱=۲‎ می‌زند. هیچ دریافتی ساعت را عقب نمی‌برد.
  3. مرتب کن، با tie-break مهرها را به‌صورت (counter, processID) مرتب کن، با tie-break شناسه: (1,A) < (1,C) < (2,B). یک ترتیب کلی که به هر زنجیرهٔ پیام احترام می‌گذارد — پست‌های هم‌زمان A و C فقط ترتیب شناسه را می‌گیرند.
  4. نام بردن چیزی که نمی‌تواند حالا محدودیتش را با همان تله نام ببر: x=(5,A) و y=(3,C) بدون پیام — مهرهای مرتب و صفر علّیت. برای تشخیص هم‌زمانی باید بری سراغ ساعت برداری: یک ورودی per-process و حالت و بایت مهر O(n).
  1. Start counting One counter per process, starting at 0. Every local event and every send ticks it +1 — the clock only ever moves forward, one step per event.
  2. Adopt the max on receive On receive, adopt max(local, seen). Walk the book's scenario with me: B takes max(0,1)=1 from A, max(1,1)=1 from C, then its reply-send ticks 1+1=2. No receive ever moves a clock backwards.
  3. Sort it, with a tie-break Sort the stamps as (counter, processID) with the process ID breaking ties: (1,A) < (1,C) < (2,B). A total order that respects every message chain — the concurrent posts A and C simply take ID order.
  4. Say what it cannot do Now name its limit with the trap: x=(5,A) and y=(3,C) with no messages — ordered stamps, zero causality. Detecting concurrency needs vector clocks: one entry per process, O(n) state and stamp bytes.

طراحی مشخصConcrete design

برای هر پروسه یک counter (عدد ‎۶۴بیتی) به‌علاوهٔ یک processID تغییرناپذیر. پاکت پیام (counter, processID) را حمل می‌کند؛ harness هر ارسال/دریافت را با مهر خودش ثبت می‌کند. مسیر خواندن: مرتب‌سازی مهرهای ثبت‌شده با (counter, processID). مسیر نوشتن: دو قاعده را در هر رخداد اعمال کن؛ بدون هماهنگی و بدون RPC اضافه.

One counter (u64) and one immutable processID per process. The message envelope carries (counter, processID), and the harness logs every send/receive with its stamp. Read path: sort the logged stamps by (counter, processID). Write path: apply the two rules at each event — no coordination, no extra RPC.

مثال محاسبه‌شدهWorked example

گام آموزشی (نمودار ۵ فصل): A می‌فرستد (1,A)؛ C می‌فرستد (1,C)؛ B نگه می‌دارد max(0,1)=1 و بعد max(1,1)=1؛ ارسالِ جوابِ B می‌شود (2,B)؛ A می‌گیرد max(1,2)=2. شمارنده‌های پایانی: A=2 و B=2 و C=1. مهرهای مرتب: (1,A) < (1,C) < (2,B).

Teaching walk (chapter diagram 5): A sends (1,A); C sends (1,C); B holds max(0,1)=1, then max(1,1)=1; B's reply-send ticks to (2,B); A adopts max(1,2)=2. Final counters: A=2, B=2, C=1. Sorted stamps: (1,A) < (1,C) < (2,B). Notice what this walk does not say: who caused whom.

سه پروسهٔ چت، هرکدام یک ساعت Lamport دارند. خط‌های زندگی را از بالا به پایین بخوان: اول باند Exchange، بعد باند Trap با دو گزارشِ بدون پیام.
Three chat processes, each with its own Lamport clock. Walk the lifelines from top to bottom: first the Exchange band, then the Trap band with its two message-free reports.
  1. A می‌فرستد: شمارنده از صفر می‌رود روی یک و پیام (1,A) را می‌برد. C هم می‌فرستد: شمارنده از صفر روی یک و پیام (1,C).
  2. B هر دو را می‌گیرد: max(0,1)=1 و بعد max(1,1)=1. جوابِ B یک رخداد ارسال است: ‎۱+۱=۲‎ با مهر (2,B)؛ و A می‌گیرد: max(1,2)=2.
  3. باند تله: x روی A با مهر (5,A) و y روی C با مهر (3,C)، بدون هیچ پیامی — (3,C) < (5,A) هیچ‌چیز را ثابت نمی‌کند چون x و y هرگز همو ندیدند.
  1. A posts: the counter goes 0 to 1 and the message carries (1,A). C posts: 0 to 1 as well, carrying (1,C).
  2. B receives both: max(0,1) = 1, then max(1,1) = 1. B's reply is itself a send event: 1 + 1 = 2, carrying (2,B); A adopts max(1,2) = 2.
  3. Trap band: x on A stamped (5,A) and y on C stamped (3,C), with no messages at all — (3,C) < (5,A) proves nothing, because x and y never met.

نقطهٔ تصمیم: نقطهٔ تصمیم شمارندهٔ B بعد از هر دریافت است: max را بگیر و هرگز عقب نرو. بقیه فقط مرتب‌سازی است.

رد خرابی: نپذیرفتن مهرِ دیده‌شده را دنبال کن: اگر B مهر دیده‌شده را نادیده بگیرد و روی صفر بماند، جوابش (1,B) می‌شود — کوچک‌تر از (1,C) که دیده بود و ساعت عقب می‌رود. قاعدهٔ دریافت دقیقاً برای ممنوع کردن همین است.

تضمین نشان‌داده‌شده: شکل نشان می‌دهد دو قاعده چطور مهرهای کتاب را می‌سازند و بند تله ترتیبِ بدون علّیت را نشان می‌دهد. زمان دیواری نشان نمی‌دهد — چون اصلاً وجود ندارد.

تضمین نشان‌نداده‌شده: تشخیص هم‌زمانی و رفتار با گم شدن پیام بیرون از این شکل‌اند — اسمبلی قیمت ساعت برداری را برای اولی نام می‌برد.

Decision point: The decision point is B's counter after every receive: take the max, never go backwards. Everything else is just sorting.

Failure trace: Follow the lost adoption: if B ignored the stamp it had seen and stayed at 0, its reply would carry (1,B) — smaller than the (1,C) it already saw, and the clock would move backwards. The receive rule exists exactly to forbid that.

Guarantee shown: The figure shows the two rules producing the book's stamps, plus the trap segment that shows order without causality. It shows no wall-clock time — there isn't any.

Not shown: Concurrency detection and message-loss handling sit outside this figure — the assembly names the vector-clock price for the first.

خودآزماییSelf-check

بعد از گرفتن (1,A) و بعد (1,C)، مقدار B چه می‌شود و چرا جواب (2,B) است؟

پاسخ: B بعد از دریافت اول ۱ است (max(0,1)) و بعد از دومی هنوز ۱ (max(1,1))؛ ارسالِ جواب به ۲ می‌رسد پس (2,B). آن ‎+1‎ که بعضی ارائه‌ها روی دریافت می‌گذارند همان افزایشی است که روی ارسالِ بعد حساب می‌شود — نتیجه هر دو جور یکی است.

After receiving (1,A) and then (1,C), what does B hold — and why does the reply come out as (2,B)?

Answer: B holds 1 after the first receive (max(0,1)) and still 1 after the second (max(1,1)); the reply-send ticks to 2, hence (2,B). The +1 some presentations put on receive is the same increment charged on the next send — the order comes out identical either way.

خودآزماییSelf-check

آیا (3,C) < (5,A) یعنی y قبل از x اتفاق افتاده؟

پاسخ: نه. مهرها نمایش را مرتب می‌کنند؛ فقط زنجیرهٔ پیام علّت‌ها را مرتب می‌کند. x و y تا پیامی وصلشان کند هم‌زمان می‌مانند و مهر Lamport این را نمی‌گوید.

Does (3,C) < (5,A) really mean y happened before x?

Answer: No. The stamps order the display; only a message chain orders causes. x and y stay concurrent until a message connects them, and Lamport stamps cannot tell you that.

گزینه‌های جایگزینAlternatives

  • ساعت برداری (یک شمارنده per-process): هم علّیت را می‌فهمد هم هم‌زمانی را — به قیمت حالت O(n) در هر گره و O(n) بایت در هر پیام. فقط وقتی سراغش برو که محصول باید «هم‌زمان» را بفهمد — ویرایش مشترک، تحویل علّی، فراداده CRDT. برای مرتب‌سازی ساده این فقط خرج اضافه است.
  • Vector clocks (one counter per process): they detect causality AND concurrency, at the price of O(n) state per node and O(n) bytes per message. Pay for that only when the product must know 'concurrent' — collaborative editing, causal delivery, CRDT metadata. For plain ordering it's just extra spend.

سناریوهای خرابیFailure scenarios

  • پیام گم یا تکراری: پذیرش idempotent است (max دو بار همان یک‌بار) ولی پیام گمشده گیرنده را جلو نمی‌برد — ترتیب معتبر می‌ماند، فقط درشت‌تر. هرگز مهری را که نگرفتی حدس نزن.
  • برخورد شناسهٔ پروسه: دو پروسه با یک شناسه tie-break را می‌شکنند و دو رخداد مهر یکسان می‌گیرند. نگهبان: شناسه‌ها را از یک رجیستری بگیر (یا همان oracle تمرین ۳) و روی ثبت تکراری crash کن.
  • سرریز شمارنده: شمارندهٔ ‎۶۴بیتی با نرخ آموزشی عملاً تمام‌نشدنی است؛ شمارندهٔ کوچک می‌چرخد و ترتیب را می‌شکند. نگهبان: ‎۶۴بیت ثابت و assert — هرگز بی‌صدا نچرخ.
  • A lost or duplicated message: adoption is idempotent (max twice is max once), but a message that never arrives simply doesn't advance the receiver — the order stays valid, only coarser. And never 'fill in' a stamp you did not receive.
  • Process-ID collision: two processes sharing one ID break the tie-break, and two events can end up stamped identically. Guard: hand out IDs from one registry (or reuse the oracle of exercise 3) and crash on a duplicate registration.
  • Counter overflow: a u64 counter ticking per event lasts effectively forever at teaching rates; a small counter wraps around and breaks the order. Guard: fix u64 and assert it — never wrap silently.

import java.util.*;
// Teaching demo: Lamport clocks on 3 processes (chapter diagram 5).
// send/local -> c+=1, stamp (c,pid); receive(m) -> adopt max(c,m.ts).
public class LamportDemo {
    record Ts(long c, String pid) implements Comparable<Ts> {
        public int compareTo(Ts o) {
            int r = Long.compare(c, o.c);
            return r != 0 ? r : pid.compareTo(o.pid);
        }
    }
    static class Proc {
        final String id; long c = 0;
        Proc(String id) { this.id = id; }
        Ts send() { c++; return new Ts(c, id); }
        void receive(Ts m) { c = Math.max(c, m.c()); }
    }
    public static void main(String[] a) {
        Proc A = new Proc("A"), B = new Proc("B"), C = new Proc("C");
        Ts mA = A.send(), mC = C.send();
        B.receive(mA); B.receive(mC);
        Ts mB = B.send(); A.receive(mB);
        System.out.println("stamps: A=" + mA + " C=" + mC + " B-reply=" + mB);
        List<Ts> order = new ArrayList<>(List.of(mB, mC, mA));
        Collections.sort(order);
        System.out.println("total order = " + order);
        Ts x = new Ts(1, "A"), y = new Ts(1, "C");
        System.out.println("L(x)=" + x + " < L(y)=" + y + " but no causal path");
        if (!order.equals(List.of(new Ts(1, "A"), new Ts(1, "C"), new Ts(2, "B"))))
            throw new AssertionError();
        System.out.println("OK: receive adopts max; total order <> causal order");
    }
}

قاعدهٔ دریافت را assert کن (بعد از هر تحویل هرگز عقب‌گرد)، ترتیب مرتب کتاب را هم assert کن ((1,A) < (1,C) < (2,B)) و تله را property-test کن: رخدادهای بدون پیام باید هر جفت مهری را بپذیرند. هزینه را هم بگو: O(1) در برابر O(n) بردارها — و بدون harness هیچ ادعای latency نکن.
Assert the receive rule (never backwards after any delivery), assert the book's sorted order (1,A) < (1,C) < (2,B), and property-test the trap: random message-free events must accept ANY stamp pair. Then say the cost out loud — O(1) per process versus O(n) for vectors — and make no latency claim without a harness.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (سینیور): حالا دو رخداد داری بدون هیچ پیام. چه timestampهایی می‌تونن داشته باشن؟Follow-up (Senior): What timestamps can your two independent events with no messages have?

هر جفتی که دلخواهت باشد — مثلاً (5,A) و (3,C) یا (1,A) و (100,C). بدون پیام هیچ قیدی نیست: هر شمارنده فقط خودش را دیده. همین آزادیِ بی‌حدّ و مرز دلیل ناتوانی مهر Lamport در تشخیص هم‌زمانی است: مهرهای مرتب بدون زنجیرهٔ پیام هیچ‌چیز را ثابت نمی‌کنند.

Any pair you like — for example (5,A) and (3,C), or (1,A) and (100,C). With no messages there is no constraint: each counter only ever saw itself. That freedom is exactly why Lamport stamps cannot detect concurrency: equal-or-ordered stamps without a message chain prove nothing.

پیگیری (سینیور): ساعت برداری با این هزینهٔ <span class="ltr">O(n)</span> کِی ارزشش را دارد که به‌جای <span class="ltr">Lamport</span> سراغش بروی؟Follow-up (Senior): When is a vector clock worth its O(n) cost instead of plain Lamport?

وقتی محصول باید هم‌زمانی را «بداند»، نه فقط مرتبش کند: ویرایش مشترک (ویرایش‌های هم‌زمان ادغام و بعدی‌های علّی اعمال)، انتشار علّی، فراداده CRDT. هزینه‌اش هم این است: O(n) شمارنده در هر گره و O(n) بایت مهر در هر پیام، به‌علاوهٔ منطق ادغام در هر دریافت. پیش‌فرض همان Lamport؛ ارتقا فقط با یک سؤال هم‌زمانی نام‌دار.

When the product must KNOW concurrency, not just order events: collaborative editing (concurrent edits merge, causally-after edits apply), causal broadcast, CRDT metadata. The price: O(n) counters per node and O(n) stamp bytes per message, plus join logic on every receive. Default to Lamport, and upgrade only when a named concurrency question shows up.

اشتباهات رایجCommon mistakes

  • خواندن L(a) < L(b) به‌معنای «a علّت b است». ترتیبِ مهر فقط ترتیبِ نمایش است؛ علّیت زنجیرهٔ پیام از a به b می‌خواهد.
  • ادعای تشخیص هم‌زمانی با Lamport («مهر برابر یعنی هم‌زمان»). دو رخدادِ بدون پیام هر مهری می‌توانند داشته باشند — برابری هم چیزی را ثابت نمی‌کند.
  • دست بردن به هم‌گام‌سازی ساعت دیواری. Lamport اصلاً ساعت هم‌گام نمی‌خواهد — نکتهٔ همین است؛ اضافه کردن NTP این‌جا هیچ‌چیزی را حل نمی‌کند، فقط یک حالت خرابی تازه یعنی skew می‌افزاید.
  • Reading L(a) < L(b) as 'a caused b'. Stamps only order the display; causality needs a message chain running from a to b.
  • Claiming Lamport detects concurrency ('equal stamps mean concurrent'). Two message-free events can hold any stamps at all — equality doesn't prove a thing either.
  • Reaching for wall-clock synchronization. Lamport needs no synchronized clocks at all — that's the whole point; adding NTP solves nothing here and only adds skew failure modes.

سؤال مصاحبهInterview question
تصور کن سه تا replica داری و write در جریانه که هنوز فقط به یکیش رسیده. دو تا quorum read بساز که اولی جدید و دومی قدیمی می‌خونه. بعد الگوریتم register رو با version مرتب و write-back به اکثریت پیش از برگشتن read مشخص کن. برای multi-writer مرحله query پیش از write و فرض membership ثابت رو تحلیل کن.
Here's the thing — you've got three replicas and an in-flight write that's reached only one. Construct new-then-old quorum reads, then specify ordered versions and majority write-back before returning a read. Discuss a query phase for multiple writers, fixed membership and crash assumptions.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

یه نوشتنِ در پرواز بساز که فقط به یکی از سه replica رسیده، بعد دو بار با r=2 بخون: quorum اول نسخهٔ تازه را می‌بیند و دومی که دیرتر شروع شده کهنه‌تر می‌خواند — تازه-بعد-کهنه، نقض خطی‌پذیری، درحالی‌که w + r > n سالم است. درستش را به روش ABD کن: نسخه‌ها مرتب‌اند و هر خواننده نسخهٔ بیشینه را قبل از برگشتن به quorum برمی‌گرداند. read-repair پس‌زمینه ناهمگام است و هیچ‌چیز را تضمین نمی‌کند؛ write-back قبل از بازگشت انجام می‌شود. قانون ساده است: تعمیر باید قبل از جواب برسد، نه بعدش.
Stage an in-flight write that reached only one of three replicas, then read with r=2 twice: the first quorum meets the new version, the second starts later yet reads older — new-then-old, a linearizability violation, with w + r > n still intact. Fix it the ABD way: versions are ordered, and every reader writes the max version back to a quorum BEFORE it returns. Background read-repair is async and guarantees nothing; write-back before return does. The rule is simple: the repair has to land before the answer, not after it.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن سه replica به نام n1 و n2 و n3 با membership ثابت داریم؛ حین سناریو rebalancing در کار نیست.
  • تک‌نویسنده با نسخه‌های مرتب v1 (کهنه) و v2 (تازه). نوشتن هدف w=3 داره، ولی فقط n1 نسخهٔ v2 رو ذخیره کرده — جزئی، و هرگز تأییدشده نیست.
  • خواندن‌ها با r=2 بیشینهٔ نسخهٔ دیده‌شده رو برمی‌گردونن. خواندنِ خوانندهٔ B بعد از برگشتن خواندن A شروع می‌شه.
  • Picture three replicas named n1/n2/n3 with fixed membership — no rebalancing during the scenario.
  • A single writer with ordered versions v1(old) and v2(new). The write targets w=3, but only n1 has stored v2 — partial, and never acknowledged.
  • Reads take r=2 and hand back the max version they meet. Reader B's read starts after reader A's read has returned.

چرا این روش و این عددها؟Why this method and these numbers?

read1 می‌تواند مقدارِ write ناتمام را ببیند، ولی همین که آن مقدار را برگرداند، read2 بعدی دیگر نمی‌تواند به قبلش برگردد. write-back پیش از پاسخ، مقدار دیده‌شده را روی اکثریت می‌گذارد؛ هر اکثریتِ بعدی با آن اشتراک دارد. پس برای n=3 دو عضو کافی است؛ درخواستِ ACK هر سه در این مثال فقط پنجرهٔ write ناتمام را واضح‌تر می‌کند. اثبات هم به monotonic نسخه گره خورده، هم به membership ثابت، هم به قواعدِ writer — نه به صرفِ جمعِ r+w.

Read1 may observe an incomplete write, but the moment it returns that value, a later Read2 cannot go backwards. The before-return write-back places the observed version on a majority; every later majority intersects it. With n=3, two replicas suffice — targeting all three merely makes the incomplete-write window obvious. The proof also needs monotonic versions, fixed membership and a defined writer protocol.

مدل ذهنیMental model

قضیه اینه که quorum یک پل میان نوشتن و خواندن است — ولی پل فقط چیزی را می‌برد که واقعاً رویش بار شده. نوشتنِ جزئی یک سر پل را بار می‌کند؛ خواندنی که از سرِ دیگر رد می‌شود چیز تازه‌ای نمی‌بیند. write-back یعنی خواننده خودش خبر را قبل از این‌که جواب بدهد، آن‌ور پل می‌برد.
Here's the thing: a quorum is a bridge between the write and the read — but a bridge only carries what was actually loaded onto it. A partial write loads one end; the read crossing from the other end finds nothing new. Write-back is the reader hauling the news across before it reports back.

حل گام‌به‌گامStep by step

  1. جزئی یعنی تأیید نشده اول هدف را از تأییدشده جدا کن: نوشتنِ w=3 نشانه گرفته بود ولی فقط n1 نسخهٔ v2 را ذخیره کرد. اسمش جزئی است — هیچ quorumای مدیونِ دیده‌شدنش نیست.
  2. بازپخش نقض، قدم به قدم حالا جفتِ ناقض را اجرا کن: خواندن اول از n1 و n2 برمی‌گرداند max(v2,v1)=v2 (هم‌زمان، مجاز)؛ خواندن دوم از n2 و n3 که بعد از برگشتن اول شروع شده، می‌گیرد max(v1,v1)=v1. تازه-بعد-کهنه، با نامساوی سالم.
  3. اول برگردان، بعد جواب درستِ ABD را اعمال کن: خواننده v2 را به n1 و n2 — یک quorum — قبل از برگشتن برمی‌گرداند. خواندن دوباره از n2 و n3 حالا v2 را می‌بیند. تعمیرِ قبل از بازگشت تضمین است؛ تعمیرِ بعدش آرایش.
  4. فرض‌های باقی‌مانده را نام ببر حالا فرض‌های باقی‌مانده را صادقانه بگو: این‌جا تک‌نویسنده‌ایم (چندنویسنده query timestamp قبل از نوشتن می‌خواهد)، membership ثابت (rebalancing quorum مشترک می‌خواهد) و نسخه‌های مرتب با ساخت — هرگز با ساعت دیواری.
  1. Partial isn't acked Separate targeted from acknowledged: the write aimed at w=3 but only n1 stored v2. Call it partial — no quorum owes it visibility.
  2. Replay the violation, step by step Now run the violating pair: read1 from {n1,n2} returns max(v2,v1)=v2 (concurrent, allowed); read2 from {n2,n3} starts after read1 has returned and gets max(v1,v1)=v1. New-then-old, with the inequality still intact.
  3. Write back before you answer Apply the ABD fix: the reader writes v2 back to {n1,n2} — a quorum — BEFORE it returns. The re-read from {n2,n3} now meets v2. Repair before the return is the guarantee; repair after it is cosmetics.
  4. Name what you still assume State the remaining assumptions honestly: a single writer here (multi-writer needs a pre-write timestamp query), fixed membership (rebalancing needs joint quorums), and versions ordered by construction, never by wall clock.

طراحی مشخصConcrete design

هر replica جفت (version, value) را با نسخه‌های کاملاً مرتب نگه می‌دارد. مسیر نوشتن (تک‌نویسنده): مهر v+1 بزن، به هر سه بفرست و منتظر w تأیید بمان — این‌جا فقط یکی می‌رسد، پس نوشتن در پرواز می‌ماند. مسیر خواندن: از r=2 بپرس، بیشینه را بردار، به r=2 برگردان، بعد برگرد. چندنویسنده یک فاز query اضافه می‌کند: قبل از مهر زدن، بالاترین timestamp را از quorum بخوان.

Each replica stores (version, value) with totally ordered versions. Write path (single writer): stamp v+1, send to all three, wait for w ACKs — here only one lands, so the write stays in flight. Read path: query r=2, pick the max version, write it back to r=2, then return. Multi-writer adds a query phase: read the highest timestamp from a quorum before you stamp the write.

مثال محاسبه‌شدهWorked example

اعداد آموزشی: replicaها نگه می‌دارند (v2=new) روی n1 و (v1=old) روی n2 و n3. خواندن اول از n1 و n2 می‌شود max(2,1)=v2. خواندن دوم از n2 و n3 می‌شود max(1,1)=v1 — نقض. write-back نسخهٔ v2 را روی n2 می‌گذارد؛ خواندن دوباره می‌شود max(2,1)=v2 — درست شد. هزینهٔ این درست (آموزشی): یک round-trip اضافهٔ quorum روی هر خواندن.

Teaching numbers: replicas hold (v2=new) on n1, (v1=old) on n2/n3. Read1 {n1,n2} = max(2,1) = v2. Read2 {n2,n3} = max(1,1) = v1 — violation. Write-back puts v2 on n2; re-read {n2,n3} = max(2,1) = v2 — fixed. The price of the fix (teaching): one extra quorum round-trip on every read. That is the whole trade — a round-trip per read buys freshness you can defend in the interview.

خودآزماییSelf-check

با این‌که w + r > n همه‌جا برقرار است، چرا خواندنِ کهنه هنوز ممکن است؟

w + r > n holds the whole way. So why is a stale read still possible?

Answer: Because the write never completed: only one replica stored v2, so no quorum was obliged to carry it. w + r > n promises that quorums overlap, not that a partial write is visible — overlapping with a replica that never saw v2 hands back v1: perfectly legal for sets, plainly wrong for freshness.

خودآزماییSelf-check

آیا read-repair پس‌زمینه می‌تونه جای write-back رو بگیره؟

پاسخ: نه. تعمیر باید قبل از برگشتنِ خواندن به صداکننده تمام شود. کارِ پس‌زمینه‌ای که بعداً می‌دود نمی‌تواند مقداری را که قبلاً برگشته عطف‌بماسبق خطی‌پذیر کند — صداکننده نقض را قبلاً دیده.

Can background read-repair take the write-back's place?

Answer: No. The repair has to finish before the read returns to its caller. A background task that runs later can't retroactively linearize a value that already went out — the caller already saw the violation.

گزینه‌های جایگزینAlternatives

  • خواندن خطی‌پذیر رهبرمحور (از رهبر بخوان یا با تأیید رهبر): استدلالش ساده‌تر است ولی هر خواندن هزینهٔ latency رهبر را می‌دهد و رهبر گلوگاه می‌شود. وقتی رقابت کم است و سادگی از توان خواندن مهم‌تر است انتخابش کن؛ وقتی خواندن باید مقیاس بخورد، سراغ خواندن رجیستری quorum برو.
  • Leader-based linearizable reads (read from the leader, or leader-confirmed reads): easier to reason about, but every read pays the leader's latency and the leader becomes the bottleneck. Choose it when contention is low and simplicity beats read throughput; choose quorum register reads when reads have to scale out.

سناریوهای خرابیFailure scenarios

  • خواننده بعد از دیدن v2 ولی قبل از write-back می‌میرد: اگر صداکننده پاسخی نگرفته، خواندن هرگز کامل نشده — یالِ تقدم نیست و write-back خوانندهٔ بعد هنوز v2 را پخش می‌کند. اگر v2 را برگرداند و بعد وسط write-back مرد، خواندنِ کامل‌شده تقدم را گذاشته و وظیفه می‌رسد سراغ خوانندهٔ بعد که هر بیشینه‌ای ببیند برمی‌گرداند. کامل یعنی پاسخ به صداکننده رسید، نه این‌که خواننده مقدار را درون خودش دید.
  • نویسنده‌های هم‌زمان بدون فاز query: دو نویسنده که مستقل مهر v2 می‌زنند، مقدار را دوشاخه می‌کنند — یک نسخه با دو دادهٔ متفاوت. نگهبان: اول بالاترین timestamp را از quorum بپرس (چندنویسندهٔ ABD) تا نسخه‌ها per-writer یکتا بمانند.
  • تغییر membership وسط سناریو: w + r > n روی دو مجموعهٔ عضوِ متفاوت هیچ هم‌پوشانی ندارد. نگهبان: quorumهای مشترک — مجموعه‌های قدیم و جدید تا پایانِ تغییر باید همو هم‌پوشانی کنند.
  • The reader crashes after seeing v2 but before the write-back: if the caller never got an answer, the read never completed — no precedence edge, and the next reader's write-back still propagates v2. If it returned v2 and then died mid-write-back, the completed read DID set precedence, and the duty passes to the next reader, which writes back whatever max it meets. Completed means the response reached the caller, not that the reader saw the value inside itself.
  • Concurrent writers without a query phase: two writers stamping v2 independently fork the value — same version, different data. Guard: query the highest timestamp from a quorum first (ABD multi-writer), so the versions stay unique per writer.
  • Membership change mid-scenario: w + r > n computed over two different member sets overlaps nothing. Guard: joint quorums — the old and new member sets must overlap each other until the change completes.

import java.util.*;
// Teaching demo: versions on 3 replicas, an in-flight write on n1 only,
// new-then-old r=2 reads, then the ABD fix: write-back before return.
public class QuorumDemo {
    record Ver(long v, String val) {}
    public static void main(String[] a) {
        Map<String, Ver> store = new LinkedHashMap<>(Map.of(
            "n1", new Ver(2, "new"), "n2", new Ver(1, "old"), "n3", new Ver(1, "old")));
        Ver r1 = maxOf(store, List.of("n1", "n2"));
        Ver r2 = maxOf(store, List.of("n2", "n3"));
        System.out.println("read1 {n1,n2} -> v" + r1.v() + "=" + r1.val());
        System.out.println("read2 {n2,n3} -> v" + r2.v() + "=" + r2.val());
        System.out.println("violation (new-then-old) = " + (r1.v() > r2.v()));
        store.put("n2", r1); // write-back of v2 to a quorum BEFORE return
        Ver r2b = maxOf(store, List.of("n2", "n3"));
        System.out.println("after write-back, read2 -> v" + r2b.v() + "=" + r2b.val());
        if (!(r1.v() == 2 && r2.v() == 1 && r2b.v() == 2)) throw new AssertionError();
        System.out.println("OK: versions ordered, write-back-before-return fixes it");
    }
    static Ver maxOf(Map<String, Ver> s, List<String> q) {
        return q.stream().map(s::get).max(Comparator.comparingLong(Ver::v)).orElseThrow();
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): حالا اگه یه reader بعد از خوندن مقدار جدید و قبل از write-back بمیره، کدوم read باید completed حساب بشه؟Follow-up (Staff): Your reader crashes after seeing the new value but before write-back. Should that read count as completed?

اگر reader پیش از write-back و پیش از پاسخ بمیرد، read کامل نشده است و می‌توان آن را از history کامل‌شده حذف کرد؛ read بعدی که مقدار قدیم می‌دهد لزوماً نقض نیست. اگر پاسخ v2 قبلاً به caller رسیده باشد، read کامل شده و برگشتن v1 در read بعدی نقض است. فقط سپردن وظیفه به خوانندهٔ بعد تضمین نمی‌دهد، چون ممکن است اصلاً v2 را نبیند؛ پروتکل درست پاسخ را تا پایانِ write-back quorum نگه می‌دارد.

If the reader dies before the write-back and before replying, the read is pending and may be omitted from a completed history; a later old read isn't necessarily a violation. If v2 already reached the caller, the completed read constrains later reads, and returning v1 violates linearizability. Handing the repair duty to the next reader isn't enough: it may never see v2. A correct protocol holds the reply back until the quorum write-back completes.

پیگیری (سینیور): چرا <span class="ltr">w + r &gt; n</span> به‌تنهایی خواندنِ تازه را تضمین نمی‌کند؟Follow-up (Senior): Why doesn't w + r > n on its own guarantee fresh reads?

چون حساب روی مجموعه‌هاست و تازگی سه پیش‌فرضِ دیگر می‌خواهد: نوشتن کامل شده باشد (هر w ذخیره، نه یکی)، نسخه‌ها مرتب باشند تا خواننده مقایسه کند، و بیشینه قبل از برگشتنِ خواندن برگردد. هم‌پوشانی quorum بدون این پیش‌فرض‌ها پلی است که شاید بارِ کهنه ببرد — همان مجموعه‌ها و همان جمع، با بارِ کهنه.

Because it's arithmetic over sets, and freshness needs three more premises: the write completed (all w stored, not one), versions are ordered so readers can compare, and the max is written back before the read returns. Quorum overlap without those premises is a bridge that may carry the old value — same sets, same sum, stale cargo.

اشتباهات رایجCommon mistakes

  • صد زدنِ w=3 هدف به‌عنوان w=3 تأییدشده. فرستادن به سه یعنی ذخیره روی سه؟ نه — فقط ACKها حساب‌اند و این‌جا یکی است.
  • ادعای خطی‌پذیر شدنِ خواندن با read-repair پس‌زمینه. تعمیر بعد از بازگشت آرایشِ تاریخ است — صداکننده نقض را قبلاً دیده. بگو «تعمیر eventual» و هرگز «خطی‌پذیر».
  • راستش، مقایسهٔ نسخه‌ها با timestamp ساعت دیواری (LWW). ساعت‌های دیواری skew دارند؛ مهرهای کج مقدارها را غلط و بی‌صدا مرتب می‌کنند. نسخه‌های این‌جا منطقی‌اند و با ساخت مرتب شده‌اند.
  • Calling the targeted w=3 an acknowledged w=3. Sent-to-three isn't stored-on-three; only ACKs count, and here there's exactly one.
  • Claiming that background read-repair makes reads linearizable. Repair after the return is history cosmetics — the caller already saw the violation. Say 'eventual repair', never 'linearizable'.
  • Comparing versions by wall-clock timestamps (LWW). Wall clocks skew; skewed stamps order the values wrongly and silently. The versions here are logical, ordered by construction.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

قبل از تحویل هر شناسه، انتهای بازه را بادوام رزرو کن؛ پس از crash هم از بعدِ mark ادامه بده. صدور ۱،۲،۳ از دستهٔ ۱ تا ۵ و سپس بازیابی از ۶ تکرار ندارد ولی gap دارد. یکتایی با بازه‌های جدا یا namespace جدا قابل شارد است. ترتیب عددیِ جهانیِ پاسخ‌های غیرهم‌پوشان قرارداد قوی‌تری است: fence روی reserve جلوی پاسخ‌دادنِ رهبر قدیم از RAM را نمی‌گیرد، پس مسیر صدور هم باید مالکِ معتبر را بررسی کند. خلاصه این‌که: اول رزرو، بعد تحویل — وگرنه یک بار دیگر همان شناسه را صادر می‌کنی.
Reserve the range high-water mark durably before you issue any ID; after a crash, restart above it. Issuing 1,2,3 out of 1..5 and then restarting at 6 keeps uniqueness, with gaps as the price. Disjoint ranges or separate namespaces give you sharded uniqueness. Global numeric ordering of non-overlapping responses is the stronger contract: fencing the reservation alone doesn't stop an old allocator serving IDs from RAM, so the issuance path needs a valid-owner check too. Short version: reserve first, serve second — otherwise you hand out the same ID twice.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن یه allocator oracle داریم که دسته‌های ‎۵تایی (اندازه آموزشی) تحویل می‌ده. high-water mark بادوامه، ولی اشاره‌گرِ تحویل ناپایداره.
  • قضیه اینه که: crash همهٔ حالت ناپایدار رو می‌بره و هیچ بادوامی رو نه. standby (اگه باشه) از همون mark بادوام شروع می‌کنه.
  • یکتایی، بدون‌gap، ترتیب تخصیص و ترتیب مشاهدهٔ real-time — چهار تضمین جدا هستن. قبل از انتخاب بگو محصول کدوم رو می‌خواد.
  • Picture one oracle allocator handing out batches of 5 (teaching size). The high-water mark is durable; the handout pointer is volatile.
  • Here's the thing: a crash loses all the volatile state and none of the durable state. The standby (if there is one) starts from that same durable mark.
  • Uniqueness, gap-free, allocation order and real-time observation order are four separate guarantees — say which one the product needs before you pick.

چرا این روش و این عددها؟Why this method and these numbers?

پایدار کردنِ high-water mark یعنی همهٔ شناسه‌های زیر آن رزروشده‌اند، حتی اگر هنوز تحویل نشده باشند؛ restart بعد از آن، تکرار را به gap تبدیل می‌کند. هزینهٔ write بادوام با دستهٔ b تقریباً بر b شناسه پخش می‌شود، ولی تا b−1 شناسه در crash می‌تواند جا بیفتد. b=5 برای دیدن دستیِ این بده‌بستان است. یکتایی با بازهٔ جدا قابل شارد است؛ ترتیب پاسخ جهانی کنترلِ مسیر صدور می‌خواهد و از fence روی ذخیرهٔ mark به‌تنهایی در نمی‌آید.

A persisted high-water mark reserves every ID below it, including the unissued ones; restarting above the mark exchanges duplication for gaps. A batch of b amortizes a durable write across b IDs, but a crash can still lose up to b−1 unissued IDs. Five makes the trade-off easy to inspect by hand. Disjoint ranges support sharded uniqueness; global response order needs control of the issuance path beyond fencing the mark storage.

مدل ذهنیMental model

allocator شناسه یک چیز می‌فروشد: اطمینان دربارهٔ گذشته (هرگز دو بار). اطمینان دربارهٔ ترتیب را اضافه‌تر می‌فروشد. یکتایی ارزان و shardشدنی است؛ هر قید ترتیبیِ بعدش — بدون-gap و مرتب و real-time — قیمت را بالا می‌برد تا فقط oracle fenced بتواند بپردازد. گذشته ارزان است؛ ترتیب گران.
An ID allocator sells certainty about the past (never twice) and charges extra for certainty about order. Uniqueness is cheap and shardable; every ordering word after it — gap-free, sorted, real-time — raises the price until only a fenced oracle can pay it. The past is cheap; order is the expensive part.

حل گام‌به‌گامStep by step

  1. اول mark، بعد تحویل اول رزرو را پایدار کن، بعد تحویل: دستهٔ ‎۱ تا ۵‎ را بادوام رزرو کن، بعد ‎۱و۲و۳‎ را از RAM تحویل بده. همین ترتیبِ mark-first کل ترفند است.
  2. کشتنِ وسطِ دسته وسطِ دسته crash کن و از mark بالا بیا: ‎۴و۵‎ هرگز صادر نشدند، پس صدورهای بعد ‎۶و۷‎ هستند. gap می‌آید و تکراری هرگز — issued=[1,2,3,6,7].
  3. جدا کردنِ چهار تضمین چهار قرارداد را جدا کن: یکتایی، gap-free، ترتیب تخصیص و ترتیب real-time پاسخ‌ها. طرحِ دسته‌ایِ ما عمداً gap دارد؛ بازه‌های جدا فقط یکتایی می‌دهند. برای ترتیب جهانی، همهٔ مسیرهای تحویل باید یک پروتکل ترتیبِ واحد را رعایت کنند.
  4. fence کردنِ failover standby همهٔ بازه‌های رزروشده را از mark بادوام رد می‌کند و فقط بازهٔ تازه می‌گیرد؛ epoch قدیمی در reserve رد می‌شود. بازهٔ قبلی را دوباره واگذار نکن. رهبر قدیمی ممکن است از RAM شناسهٔ یکتا ولی کوچک‌تر بدهد؛ اگر ترتیب جهانی لازم است، مسیر پاسخ هم باید مالکِ فعلی را بررسی کند.
  1. Mark first, then serve Persist the reservation before you serve: reserve batch 1..5 durably, then hand out 1,2,3 from RAM. The mark-first order is the whole trick.
  2. Crash the batch on purpose Crash mid-batch and recover from the mark: 4,5 were never issued, so the next issues are 6,7. Gaps show up, duplicates never do — issued=[1,2,3,6,7].
  3. Split the four guarantees Separate uniqueness, gap-free allocation, allocation order and real-time response order. This batched design deliberately allows gaps; disjoint ranges provide uniqueness. Global ordering needs every issuance path to follow one single ordering protocol.
  4. Fence the failover, always The standby skips every durably reserved range and reserves new ones under an epoch fence. Never reassign an old range. An old leader may still hand out unique but smaller RAM IDs; if you need global order, validate ownership on the response path too.

طراحی مشخصConcrete design

اجزا: یک allocator (اشاره‌گرِ تحویلِ ناپایدار + کشِ دسته)، یک فروشگاهِ بادوام برای high-water mark و یک standby که لاگ mark را بازپخش می‌کند. API: reserve(batch) اول mark را پایدار می‌کند و هنوز هیچ‌چیزِ قابل‌تحویل برنمی‌گرداند؛ nextID() از RAM تحویل می‌دهد. مسیر خواندن: تحویل از حافظه، بدون I/O. مسیر نوشتن: اول mark، بعد تحویل — crash میانشان فقط شناسه جا می‌اندازد. کلید پارتیشن: هیچی — oracle یک تصمیم‌گیرِ منطقی است؛ با دسته‌بندی مقیاس بده، نه با تکه کردنِ mark.

Components: one allocator (volatile handout pointer + batch cache), one durable store for the high-water mark, one standby replaying the mark log. API: reserve(batch) persists the mark and returns nothing servable yet; nextID() serves from RAM. Read path: serve from memory, no I/O. Write path: mark first, then serve — a crash between them only skips IDs. Partition key: none — the oracle is one logical decider; scale it by batching, not by splitting up the mark.

Why does the mark have to persist before the first ID leaves, and not after?

Answer: Persisting after issuing lets a crash lose track of the IDs already handed out, so recovery re-issues them: duplicates. Mark-first inverts the risk — a crash can only skip IDs that never left, which is a gap, never a duplicate.

گزینه‌های جایگزینAlternatives

  • UUID تصادفی (بدون هماهنگی): یکتایی بدون هیچ allocator و بدون داستان failover — به قیمتِ هیچ ترتیبی و کلیدهای پهن‌تر. وقتی ترتیب هرگز خوانده نمی‌شود انتخابش کن: شناسهٔ درخواست و span ردیابی. ولی هرگز وقتی چیزی با شناسه مرتب می‌شود.
  • شناسهٔ پیشوند-شاردی (A-* و B-* از بازه‌های جدا): یکتا و بدون هماهنگی، با ترتیب per-shard — ولی بدون ترتیب real-time سراسری. وقتی شاردها مالک سطرهای خودشان‌اند و مرتب‌سازیِ میان‌شاردی فقط نمایشی است، انتخابش کن.
  • UUIDs (random, no coordination): uniqueness without any allocator and without a failover story, at the cost of no order at all and wider keys. Pick it when order is never read — request IDs, tracing spans — and never when something sorts by ID.
  • Shard-prefixed IDs (A-*, B-* from disjoint ranges): unique and coordination-free, with per-shard order — but no global real-time order. Choose it when shards own their rows and cross-shard sorting is display-only.

سناریوهای خرابیFailure scenarios

  • failover بدون fencing: allocator قدیم زنده می‌شود و ‎۱و۲و۳‎ را کنار ‎۱و۲و۳‎ standby دوباره صادر می‌کند — تکراری، همان یک نتیجهٔ ممنوع. نگهبان: standby یک token epoch تازه می‌گیرد و storage epoch کوچک‌تر را بادوام رد می‌کند — قاعدهٔ fencing فصل ۹، اعمال‌شده روی epochهای allocator نه tokenهای per-write.
  • پایدار کردنِ mark بعد از تحویل: crash میان تحویل و پایداری ردِ شناسه‌های صادرشده را گم می‌کند — بازیابی دوباره صادرشان می‌کند. نگهبان: ترتیبِ mark-first در کد، که با تستِ کشتنِ وسطِ دسته assert می‌شود (همان دمو).
  • دو allocator روی بازه‌های هم‌پوشان (shardبندیِ غلط): جدایی فرض شده ولی هرگز اعمال نشده، میان شاردها تکراری می‌دهد. نگهبان: بازه‌ها از یک نسخهٔ کانفیگ تخصیص بگیرند و هر صادرکننده پیشوندِ شاردش را مهر بزند تا هم‌پوشانی قابل تشخیص باشد، نه بی‌صدا.
  • Failover without fencing: the old allocator revives and re-issues 1,2,3 right next to the standby's 1,2,3 — duplicates, the one forbidden outcome. Guard: the standby takes a fresh epoch token and storage durably rejects the smaller epoch — the fencing rule from chapter 9, applied to allocator epochs rather than per-write tokens.
  • Mark persisted after serving: a crash between the serving and the persisting loses track of the issued IDs, and recovery hands them out again. Guard: mark-first ordering in the code, asserted by a test that kills mid-batch (the demo).
  • Two allocators on overlapping ranges (mis-sharding): the disjointness is assumed but never enforced, and you get duplicates across shards. Guard: assign the ranges from one config version, and have each issuer stamp its shard prefix so an overlap is detectable rather than silent.

import java.util.*;
// Teaching demo: oracle allocator. Persist the batch high-water mark
// BEFORE issuing; crash mid-batch loses only the unissued tail.
public class OracleDemo {
    static class Allocator {
        long persistedHwm = 0, next = 1;
        final long batch = 5;
        final List<Long> issued = new ArrayList<>();
        void reserve() { persistedHwm += batch; }
        long issue() {
            if (next > persistedHwm) reserve();
            issued.add(next);
            return next++;
        }
        void crash() { next = persistedHwm + 1; } // volatile lost, mark survives
    }
    public static void main(String[] a) {
        Allocator al = new Allocator();
        System.out.println("issue " + al.issue() + ", " + al.issue() + ", " + al.issue());
        al.crash();
        System.out.println("CRASH -> recover from hwm=" + al.persistedHwm);
        System.out.println("next: " + al.issue() + ", " + al.issue());
        Set<Long> uniq = new HashSet<>(al.issued);
        System.out.println("issued=" + al.issued + " dups=" + (uniq.size() != al.issued.size()));
        if (uniq.size() != al.issued.size()) throw new AssertionError("duplicate ID!");
        System.out.println("OK: no duplicates, gaps allowed");
    }
}

پیگیری (سینیور): حالا دو تا node بازه جدا دارن؛ آیا IDهای صادرشده به ترتیب زمان جهانی زیاد می‌شن؟Follow-up (Senior): Two nodes issue IDs from disjoint ranges. Do your IDs increase in global real-time order?

نه. بازه‌های جدا فقط یکتایی و ترتیب per-shard را تضمین می‌کنند. A-2 می‌تواند ظهر صادر شود و B-100 ساعت ‎۱۱:۵۹‎ ولی بعدش مرتب شود — ترتیب صدورِ دیواری و ترتیب عددی میان شاردها ربطی به هم ندارند. اگر محصول سراسری با شناسه در real-time مرتب می‌کند، oracle fenced می‌خواهد، نه بازه.

No. Disjoint ranges guarantee uniqueness and per-shard order, nothing more. A-2 can be issued at noon and B-100 at 11:59 yet sort after it — wall-clock issue order and numeric order are unrelated across shards. پیگیری (استف): رهبرِ oracle وسطِ دسته failover می‌کند؛ صدور دوباره را چطور ممنوع می‌کنی؟Follow-up (Staff): The oracle leader fails over mid-batch. How do you stop the double-issue?

standby همهٔ بازه‌های رزروشده را از mark بادوام رد می‌کند و فقط بازهٔ تازه می‌گیرد؛ epoch قدیمی در reserve رد می‌شود. بازهٔ قبلی را دوباره واگذار نکن. رهبر قدیمی ممکن است از RAM شناسهٔ یکتا ولی کوچک‌تر بدهد؛ اگر ترتیب جهانی لازم است، مسیر پاسخ هم باید مالکِ فعلی را بررسی کند.

The standby skips all durably reserved ranges and reserves new ones under an epoch fence — never reassign an old range. An old leader may still issue unique but smaller RAM IDs; if global order is required, validate ownership on the response path too.

اشتباهات رایجCommon mistakes

  • «این oracle هرگز shard نمی‌شه.» غلطِ per-guarantee: یکتایی با بازه‌های جدا آزادانه shard می‌شه؛ فقط بدون-gap و ترتیب real-time سراسری مقاومت می‌کنن. بگو کدام تضمین، یا هیچی نگو.
  • پایدار کردنِ mark بعد از تحویل («برای سرعت نوشتن‌ها را بچ کن»). crash میانشان شناسه‌ها را دوباره صادر می‌کند — همان یک نتیجهٔ ممنوع، خریده‌شده به قیمتِ یک fsync کمتر. اول mark، همیشه.
  • fencing به‌صورت per-ID به‌جای per-epoch allocator. token باید epochِ leaseِ allocator را مشخص کند (یک بررسی fencing در هر failover) نه هر شناسهٔ صادرشده را — token به‌ازای هر ID به هر صدور یک بررسی بدون امنیت اضافه تحمیل می‌کند.
  • 'This oracle can never be sharded.' Wrong per guarantee: uniqueness shards freely with disjoint ranges; only gap-free and global real-time order resist sharding. Name the guarantee you mean, or say nothing.
  • Persisting the mark after serving ('batch the writes for speed'). A crash in between re-issues the IDs — the one forbidden outcome, bought for one fewer fsync. Mark first, always.
  • Fencing per ID instead of per allocator epoch. The token has to identify the allocator's lease epoch (one fencing check per failover), not every issued ID — a per-ID token adds a check to every issue and buys you no extra safety.

هر خواندن/نوشتن را با مهر invoke و return ثبت کن، تقدم real-time را بکش (تمام‌شده-قبل باید اول بیاید)، بعد همهٔ ترتیب‌های ترتیبیِ نگه‌دارندهٔ آن را با جست‌وجوی کران‌دار بگرد: هر خواندن باید تازه‌ترین نوشتنِ پیشینش را ببیند. نوشتنِ کامل‌شده بعد خواندنِ کهنه رد می‌شود؛ عملیات‌های هم‌پوشان هر دو طرف خطی می‌شوند؛ نوشتنِ timeoutخورده نامعلوم است — هر دو شاخه را امتحان کن. و یادت باشد: یک نمونهٔ قبول‌شده هرگز اجرای بعد را اثبات نمی‌کند.
Record every read/write with invoke and return stamps, draw the real-time precedence (done-before has to come first), then bounded-search every sequential order that keeps it: each read must see the latest write before it. A completed write followed by a stale read gets rejected; overlapping operations linearize either way; a timed-out write is indeterminate, so try both branches. And remember: a passing sample never proves the next execution.

صورت مسئله و فرض‌هاProblem and assumptions

  • فرض کن یه رجیستر داریم با history‌های کوچک (‎۲-۳‎ عملیات). جست‌وجوی کران‌دار جایگشت‌ها رو می‌شمرد — فقط اندازه‌های آموزشی.
  • مهر‌های invoke/return از ساعت harness می‌ان. تقدم فقط از «تمام‌شده-قبل-شروع» میاد، هرگز از مقایسهٔ مهر.
  • عملیات‌های معلق (بدون مهر بازگشت، مثل timeout‌ها) تا وقتی هر دو شاخه امتحان نشدن، نامعلوم‌ان.
  • A single register with small histories (2-3 ops). Bounded search enumerates the permutations — teaching sizes only.
  • The invoke/return stamps come from the harness clock. Precedence uses done-before-starts only — never a stamp comparison.
  • Pending operations (no return stamp, e.g. timeouts) stay indeterminate until you've branched both ways.

برای history کوچک، پیمایشِ ترتیب‌ها روشی قابل‌فهم است برای یافتن یک اجرای ترتیبیِ سازگار؛ n عملیات در بدترین حالت n! ترتیب دارند، پس این روش برای history بلند مناسب نیست. یال real-time فقط وقتی ساخته می‌شود که A کامل شود و بعد B شروع شود. pending operation را نمی‌توان خودکار failed گرفت چون ممکن است اثرش ثبت شده باشد. ساعت harness برای نسبتِ شروع/پایان است؛ timestamp خودِ داده نقطهٔ linearization را تعیین نمی‌کند.

Enumerating the orders makes a compatible sequential execution understandable for small histories. Worst-case n! permutations explain why it does not scale. Add a real-time edge only when A returns before B starts. A pending operation may have committed, so never discard it automatically as failed. Harness time orders invocation/return; the stored timestamps do not establish linearization points.

مدل ذهنیMental model

خطی‌سنج دادگاه است نه گوی بلورین: history شهادت می‌دهد، تقدم قانون است و رأی فقط پروندهٔ پیشِ رو را مقید می‌کند. عملیات‌های هم‌پوشان شهروندان آزادند — قانون فقط چیزی را قید می‌کند که قبل از شروع دیگری تمام شده. رأی تو را قانع می‌کند، نه دنیا را.
A checker is a courtroom, not a crystal ball: the history is the testimony, precedence is the law, and the verdict binds only the case in front of it. Overlapping operations are free citizens — the law constrains only what finished before another began. It convinces you about this window; it says nothing about the next one.

حل گام‌به‌گامStep by step

  1. اول مهر، بعد قید به هر عملیات از harness مهر invoke/return بزن. قاعدهٔ تقدم: اگر عملیات X قبل از شروع Y برگشت، X باید در هر ترتیب نامزد قبل از Y باشد — تنها قیدِ سخت.
  2. شمردنِ ترتیب‌های نگه‌دارنده ترتیب‌های نامزدی که تقدم را نگه می‌دارند بشمار؛ عملیات‌های هم‌پوشان آزاد جابه‌جا می‌شوند. h1 یک ترتیب می‌پذیرد (نوشتن و خواندن) و h3 هر دو را — آزادی نه شکست.
  3. قضاوت کردنِ هر ترتیب قاعدهٔ رجیستر را per-order اعمال کن: برو جلو، تازه‌ترین نوشتن را نگه دار و هر خواندن باید بخورد. تنها ترتیبِ h2 عدد ۱ می‌خواهد ولی صفر دارد — رد. یک ترتیبِ بازمانده history را قبول می‌کند.
  4. دوشاخه کردنِ نامعلوم عملیات‌های معلق را هر دو طرف دوشاخه کن: نوشتنِ timeoutخورده نامعلوم است — اگر هر شاخه (اثرکرد یا هرگز-نکرد) معتبر شود، قبول کن. بعد محدودیت را هم بگو: رأی فقط همین پنجره را مقید می‌کند.
  1. Stamp first, then constrain Stamp every op with invoke/return from the harness. The precedence rule: if op X returned before op Y started, X has to come before Y in every candidate order — that's the only hard constraint.
  2. Enumerate the keepers Enumerate the candidate orders that keep precedence; overlapping operations permute freely. h1 admits one order (write, read); h3 admits both — freedom, not failure.
  3. Judge every order Apply the register rule per order: walk it, keep hold of the latest write, and each read has to match it. h2's only order demands 1 but holds 0 — reject. One surviving order accepts the history.
  4. Fork the unknown, both ways Fork pending operations both ways: a timed-out write is indeterminate, so accept if either the took-effect or the never-did branch validates. Then state the limit out loud: the verdict binds this window only.

طراحی مشخصConcrete design

harness: یک پوشش دور مشتری key-value که per-op مهر invoke/return می‌زند (ساعت monotonic برای مدت‌ها و ساعت دیواری برای لاگ). خطی‌سنج: گرافِ تقدم از یال‌های تمام‌شده-قبل-شروع، بعد جست‌وجوی جایگشت کران‌دار با قاعدهٔ رجیستر per-order و عملیات‌های معلق دوشاخه. مسیر خواندن: جمع کردنِ یک پنجرهٔ history. مسیر نوشتن: هیچی — خطی‌سنج هرگز نمی‌نویسد، قضاوت می‌کند.

Harness: a wrapper around the key-value client stamping invoke/return per op (monotonic clock for durations, wall clock for the log). Checker: a precedence graph from the done-before-starts edges, then a bounded permutation search with the register rule per order, pending ops forked both ways. Read path: collect a history window. Write path: none — the checker never writes, it only judges.

گزینه‌های جایگزینAlternatives

  • بررسی مدلِ پیاده‌سازی (جست‌وجوی فراگیرِ پروتکل به سبک TLA+): به‌جای نمونه‌برداری از اجراها، طرح را برای اندازه‌های کران‌دار اثبات می‌کند. از خطی‌سنجِ history قوی‌تر است ولی نوشتنش سنگین‌تر — برای خودِ پروتکل replication ازش استفاده کن و خطی‌سنج history را برای سیستمِ در حال اجرا نگه دار.
  • Model checking the implementation (TLA+-style exhaustive search of the protocol): it proves the design for bounded sizes instead of sampling executions. Stronger than a history checker, heavier to write — use it for the replication protocol itself, and keep the history checker for the running system.

سناریوهای خرابیFailure scenarios

  • ساعتِ دروغ‌گوی harness (invoke بعد از return مهر خورده): تقدم وارونه می‌شود و رأی‌ها زباله‌اند. نگهبان: ساعت monotonic برای مدت‌ها و assert سلامتِ invoke <= return روی هر عملیات، و انداختنِ پرسروصدای پنجره‌های مردود.
  • نوشتنِ معلقِ شکست‌خورده فرض‌شده: نوشتنِ timeoutخورده شاید بعداً اثر کند — شکست نامیدنش باعث می‌شود خواندنِ بعدی مقدارش شبح به‌نظر برسد. نگهبان: مدل‌سازیِ نامعلوم با هر دو شاخه، همیشه.
  • پنجرهٔ history کوچک‌تر از شکارِ مسابقه (نمونه‌برداری فقط ساعت‌های خلوت): خطی‌سنج قبول می‌دهد و اطمینان دروغین است. نگهبان: نمونه‌برداری روی اوج و استقرارها، و گفتن این‌که رأی پنجره را پوشش می‌دهد — هرگز سیستم را نه.
  • A lying harness clock (invoke stamped after return): precedence inverts and the verdicts turn to garbage. Guard: a monotonic clock for durations, sanity-assert invoke <= return on every op, and drop the windows that fail it loudly.
  • Treating a pending write as failed: a timed-out write may still take effect later, and calling it failed makes a later read of its value look like a phantom. Guard: model it as indeterminate, try both branches, always.
  • A history window too small to catch the race (sampling only the quiet hours): the checker passes and the confidence is false. Guard: sample across peaks and deploys, and say plainly that the verdict covers the window — never the system.

import java.util.*;
// Teaching demo: mini linearizability checker for one register.
// Try every order that keeps real-time precedence; each read must see
// the latest preceding write. Pending/timeout ops branch both ways.
public class CheckerDemo {
    record Op(String name, char kind, String val, int start, int end) {}
    public static void main(String[] a) {
        List<Op> h1 = List.of(new Op("w", 'w', "1", 0, 2), new Op("r", 'r', "1", 3, 4));
        List<Op> h2 = List.of(new Op("w", 'w', "1", 0, 2), new Op("r", 'r', "0", 3, 4));
        List<Op> h3 = List.of(new Op("w", 'w', "1", 0, 5), new Op("r", 'r', "0", 2, 4));
        System.out.println("h1 completed-write, new read  -> " + check(h1));
        System.out.println("h2 completed-write, stale read -> " + check(h2));
        System.out.println("h3 overlapping read             -> " + check(h3));
        if (!check(h1).equals("LINEARIZABLE") || !check(h2).equals("NOT LINEARIZABLE")
                || !check(h3).equals("LINEARIZABLE")) throw new AssertionError();
        System.out.println("OK: precedence enforced, stale-after-complete rejected");
    }
    static String check(List<Op> ops) {
        for (List<Op> order : permutations(new ArrayList<>(ops))) {
            if (!respectsRealtime(order)) continue;
            if (validRegister(order)) return "LINEARIZABLE";
        }
        return "NOT LINEARIZABLE";
    }
    static boolean respectsRealtime(List<Op> order) {
        Map<String, Integer> pos = new HashMap<>();
        for (int i = 0; i < order.size(); i++) pos.put(order.get(i).name(), i);
        for (Op x : order) for (Op y : order)
            if (x.end() != -1 && x.end() < y.start() && pos.get(x.name()) > pos.get(y.name())) return false;
        return true;
    }
    static boolean validRegister(List<Op> order) {
        String cur = "0";
        for (Op o : order) {
            if (o.kind() == 'w') cur = o.val();
            else if (!o.val().equals(cur)) return false;
        }
        return true;
    }
    static List<List<Op>> permutations(List<Op> in) {
        List<List<Op>> out = new ArrayList<>();
        perm(in, 0, out);
        return out;
    }
    static void perm(List<Op> l, int k, List<List<Op>> out) {
        if (k == l.size()) { out.add(new ArrayList<>(l)); return; }
        for (int i = k; i < l.size(); i++) { Collections.swap(l, i, k); perm(l, k + 1, out); Collections.swap(l, i, k); }
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): حالا timeout یه write رو failed حساب می‌کنی یا indeterminate؟ چرا؟Follow-up (Staff): Do you model your timed-out write as failed or indeterminate, and why?

نامعلوم، همیشه. timeout یعنی نتیجه نامشخص است: درخواست یا نوشتن یا پاسخ، هرکدام ممکن است گم شده باشند — همان ابهام کلاسیک. خطی‌سنج باید هر دو شاخه را امتحان کند (اثرکرد / هرگز-نکرد) و با معتبر شدنِ هرکدام قبول دهد. مدل کردنش به‌عنوان شکست، نوشتنِ دیراثر را نقضِ دروغین می‌کند؛ مدل کردنش به‌عنوان انجام‌شده، نقض‌های واقعی را پنهان می‌کند.

Indeterminate, always. A timeout means the outcome is unknown: the request, the write or the response may each have been lost — the classic ambiguity. The checker has to try both branches (took effect / never did) and accept if either validates. Modelling it as failed turns a late-taking-effect write into a false violation; modelling it as done hides the real ones.

پیگیری (استف): خطی‌سنج روی ده‌هزار history نمونه قبول می‌ده؛ آیا سیستم خطی‌پذیره؟Follow-up (Staff): The checker passes on 10k sampled histories. So is the system linearizable?

نه. ده‌هزار پنجرهٔ قبول‌شده ده‌هزار پنجره را اثبات می‌کند، نه سیستم را: اجرای بعد و استقرارِ بعد و درهم‌تنیدگیِ اوج بارِ بعد قضاوت‌نشده مانده‌اند. تست متناهی اطمینان را بالا می‌برد؛ فقط اثباتِ پروتکل (بررسی مدل) به‌علاوهٔ کاوش پیوستهٔ پروداکشن (پروب نسخه و مانیتور واگرایی) تضمین را جلو می‌برد. بگو خطی‌سنج چه را پوشش می‌دهد: پنجره‌های نمونه‌برداری‌شده را.

No. Ten thousand passing windows prove ten thousand windows, not the system: the next execution, the next deploy, the next peak-load interleaving is unjudged. Finite testing raises confidence; only a protocol proof (model checking) plus continuous production probing (version probes, divergence monitors) carries the guarantee forward. Say what the checker covers: the sampled windows.

اشتباهات رایجCommon mistakes

  • گرفتن مقایسهٔ مهر به‌جای تقدم («نوشتنِ مهرزودتر باید اول مرتب شود»). تقدم یعنی تمام‌شده-قبل-شروع روی بازه‌های invoke/return — مقدارِ مهر، چه Lamport چه دیواری، هرگز تعیینش نمی‌کند.
  • قبول با اولین ترتیبِ قابل‌قبول، به‌جای گشتن همهٔ ترتیب‌های نگه‌دارندهٔ تقدم برای رد. یک ترتیبِ معتبر قبول می‌کند؛ ولی این‌که هیچ ترتیب معتبری نیست را فقط بعد از امتحانِ همه می‌دانی.
  • اجرا روی خواندن‌های replica و «درست» کردن شکست‌ها با ضعیف کردن historyها (انداختن خواندن‌های کهنه). خطی‌سنج نقضِ واقعی یافته — فروشگاه را درست کن (write-back و خواندن رهبر)، هرگز مدرک را نه.
  • Treating stamp comparison as precedence ('the earlier-stamped write must come first'). Precedence is done-before-starts on the invoke/return intervals — the stamp values, Lamport or wall-clock, never decide it.
  • Accepting on the first plausible order instead of searching every precedence-keeping order when you have to reject. One valid order is enough to accept; but you only know that none exists after trying them all.
  • Running the checker on replica reads and then 'fixing' the failures by weakening the histories (dropping the stale reads). The checker found a real violation — fix the store (write-back, leader reads), never the evidence.
