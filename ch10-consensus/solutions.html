سؤال مصاحبهInterview question
برای سه process، send/receive و رخداد محلی را با Lamport clock شماره‌گذاری کن. با tie-breaker process ID ترتیب کامل بساز. یک مثال نشان بده که L(a)<L(b) علت‌ومعلولی بودن را اثبات نمی‌کند؛ vector clock و هزینه‌اش را مقایسه کن.
Label local events and messages using Lamport clocks and process-ID tie breaking. Show why increasing timestamps do not imply causality or detect concurrency; compare vector-clock costs.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

به هر پروسه یک شمارنده بده: روی رخداد محلی/ارسال ‎+1‎ بزن، روی دریافت max بگیر و عقب‌گرد ممنوع، و مهر (counter, processID) بزن. مرتب‌سازی با tie-break شناسه می‌دهد: (1,A) < (1,C) < (2,B) — ترتیبی کلی که به علّیت احترام می‌گذارد. تریدآف: این ترتیب علّیت نیست و هم‌زمانی نامرئی است؛ دیدنش ساعت برداری می‌خواهد.
Give every process a counter: tick +1 on local/send events, adopt max(local, seen) on receive, stamp (counter, processID). Sorting by stamp with the process-ID tie-break gives a total order — (1,A) < (1,C) < (2,B) — that respects causality. The trade-off: the order is NOT causality, and concurrency is invisible; detecting it costs vector clocks.

صورت مسئله و فرض‌هاProblem and assumptions

  • سه پروسه A و B و C با شناسه یکتا؛ tie-break فقط یکتایی می‌خواهد نه هیچ‌چیز دیگر.
  • سناریوی آموزشی از نمودار ۵ فصل: A و C هرکدام یک‌بار می‌فرستند و B هر دو را می‌گیرد بعد جواب می‌دهد.
  • پیام‌ها می‌توانند تأخیر داشته باشند ولی قاعده دریافت per-delivery اعمال می‌شود؛ هیچ ساعت دیواری هیچ‌جا نیست.
  • Three processes A, B, C with unique IDs; the tie-break needs uniqueness, nothing else.
  • Teaching scenario from chapter diagram 5: A and C post once each, B merges both then replies.
  • Messages can be delayed but the receive rule is applied per delivery; no wall clock is used anywhere.

چرا این روش و این عددها؟Why this method and these numbers?

قاعدهٔ receive=max(local,received)+1 باعث می‌شود پیامِ دریافت‌شده بعد از ارسالش timestamp بزرگ‌تری داشته باشد؛ جمع یک برای جداشدن رویداد دریافت از قبلی است. دو رویداد بی‌رابطه ممکن است timestamp برابر یا مرتب داشته باشند، پس عکس رابطهٔ happened-before برقرار نیست. process_id فقط tie-break قطعی می‌دهد؛ از آن علت‌ومعلول نمی‌سازیم. سه process کمترین سناریوی روشن برای ارسال مستقل و دریافت مشترک را فراهم می‌کنند.

Receive=max(local,received)+1 gives reception a timestamp greater than its send; adding one distinguishes the receive event. Unrelated events may have equal or ordered timestamps, so the converse of happened-before fails. Process IDs provide deterministic tie-breaking, not causality. Three processes make independent sends and a shared receiver easy to inspect.

مدل ذهنیMental model

ساعت Lamport ماشین شماره‌گذاری است نه ماشین حقیقت: به هر رخداد مهری می‌زند که خوب مرتب شود و هرگز با زنجیره پیام تناقض نکند. پیام‌ها تنها واقعیت‌اند؛ مهرها فقط برچسب‌هایی‌اند که به آن‌ها احترام می‌گذارند.
A Lamport clock is a numbering machine, not a truth machine: it stamps every event so the stamps sort nicely and never contradict a message chain. Messages are the only facts; stamps are just labels that respect them.

حل گام‌به‌گامStep by step

  1. اول شمارش یک شمارنده برای هر پروسه از صفر. هر رخداد محلی و هر ارسال ‎+1‎ می‌زند — ساعت فقط جلو می‌رود، یک قدم per-event.
  2. پذیرش روی دریافت روی دریافت max بگیر. سناریوی کتاب را برو: B از A می‌گیرد max(0,1)=1 و از C می‌گیرد max(1,1)=1، بعد ارسالِ جواب ‎۱+۱=۲‎ می‌زند. هیچ دریافتی ساعت را عقب نمی‌برد.
  3. مرتب‌سازی با tie-break مهرها را به‌صورت (counter, processID) مرتب کن با tie-break شناسه: (1,A) < (1,C) < (2,B). ترتیب کلی که به هر زنجیره پیام احترام می‌گذارد — پست‌های هم‌زمان A و C فقط ترتیب شناسه می‌گیرند.
  4. نام بردن ناتوانی محدودیت را با تله نام ببر: x=(5,A) و y=(3,C) بدون پیام — مهرهای مرتب و صفر علّیت. تشخیص هم‌زمانی ساعت برداری می‌خواهد: یک ورودی per-process و حالت و بایت مهر O(n).
  1. Count first One counter per process, starting at 0. Every local event and every send ticks it +1 — the clock only moves forward, one step per event.
  2. Adopt on receive On receive, adopt max(local, seen). Walk the book's scenario: B takes max(0,1)=1 from A, max(1,1)=1 from C, then its reply-send ticks 1+1=2. No receive ever moves a clock backwards.
  3. Sort with tie-break Sort stamps as (counter, processID) with the process ID breaking ties: (1,A) < (1,C) < (2,B). A total order that respects every message chain — concurrent posts A and C simply take ID order.
  4. Name what it cannot do Name the limit with the trap: x=(5,A) and y=(3,C) with no messages — ordered stamps, zero causality. Concurrency detection needs vector clocks: one entry per process, O(n) state and stamp bytes.

طراحی مشخصConcrete design

یک counter (عدد ‎۶۴بیتی) به‌علاوه یک processID تغییرناپذیر برای هر پروسه. پاکت پیام (counter, processID) را حمل می‌کند؛ harness هر ارسال/دریافت را با مهرش ثبت می‌کند. مسیر خواندن: مرتب‌سازی مهرهای ثبت‌شده با (counter, processID). مسیر نوشتن: اعمال دو قاعده در هر رخداد؛ بدون هماهنگی و بدون RPC اضافه.

One counter (u64) plus one immutable processID per process. Message envelope carries (counter, processID); the harness logs every send/receive with its stamp. Read path: sort logged stamps by (counter, processID). Write path: apply the two rules at each event; no coordination, no extra RPC.

مثال محاسبه‌شدهWorked example

گام آموزشی (نمودار ۵ فصل): A می‌فرستد (1,A)؛ C می‌فرستد (1,C)؛ B نگه می‌دارد max(0,1)=1 بعد max(1,1)=1؛ ارسالِ جواب B می‌شود (2,B)؛ A می‌گیرد max(1,2)=2. شمارنده‌های پایانی: A=2 و B=2 و C=1. مهرهای مرتب: (1,A) < (1,C) < (2,B).

Teaching walk (chapter diagram 5): A sends (1,A); C sends (1,C); B holds max(0,1)=1, then max(1,1)=1; B's reply-send ticks to (2,B); A adopts max(1,2)=2. Final counters: A=2, B=2, C=1. Sorted stamps: (1,A) < (1,C) < (2,B).

سه پروسه چت هرکدام یک ساعت Lamport دارند. خط‌های زندگی را از بالا به پایین بخوان: اول باند Exchange، بعد باند Trap با دو گزارش بدون پیامش.
Three chat processes each keep a Lamport clock. Read the lifelines top to bottom through the Exchange band, then the Trap band with its two message-free reports.
  1. A می‌فرستد: شمارنده صفر به یک و پیام (1,A) را می‌برد. C می‌فرستد: شمارنده صفر به یک و پیام (1,C) را می‌برد.
  2. B هر دو را می‌گیرد: max(0,1)=1 بعد max(1,1)=1. جواب B یک رخداد ارسال است: ‎۱+۱=۲‎ با مهر (2,B)؛ و A می‌گیرد: max(1,2)=2.
  3. باند تله: x روی A با مهر (5,A) و y روی C با مهر (3,C) و هیچ پیامی — (3,C) < (5,A) هیچ‌چیز را ثابت نمی‌کند چون x و y هرگز هم را ندیدند.
  1. A posts: counter 0 to 1, message carries (1,A). C posts: counter 0 to 1, message carries (1,C).
  2. B receives both: max(0,1) = 1, then max(1,1) = 1. B's reply is a send event: 1 + 1 = 2, carrying (2,B); A adopts max(1,2) = 2.
  3. Trap band: x on A stamped (5,A) and y on C stamped (3,C) with no messages at all — (3,C) < (5,A) proves nothing, because x and y never met.

نقطهٔ تصمیم: نقطه تصمیم شمارنده B بعد از هر دریافت است: max را بگیر و هرگز عقب نرو. بقیه فقط مرتب‌سازی است.

رد خرابی: نپذیرفتن مهر دیده‌شده را دنبال کن: اگر B مهر دیده‌شده را نادیده بگیرد و روی صفر بماند، جوابش (1,B) می‌شود — کوچک‌تر از (1,C) که دیده بود و ساعت به عقب برمی‌گردد. قاعده دریافت دقیقاً برای ممنوع کردن همین است.

تضمین نشان‌داده‌شده: شکل نشان می‌دهد دو قاعده مهرهای کتاب را می‌سازند و بند تله ترتیب بدون علّیت را نشان می‌دهد. زمان دیواری نشان نمی‌دهد — چون هیچ‌جا نیست.

تضمین نشان‌نداده‌شده: تشخیص هم‌زمانی و رفتار با گم شدن پیام بیرون این شکل‌اند — اسمبلی قیمت ساعت برداری را برای اولی نام می‌برد.

Decision point: The decision point is B's counter after each receive: adopt the max, never go backwards. Everything else is sorting.

Failure trace: Trace a lost adoption: if B ignored the seen stamp and kept 0, its reply would carry (1,B) — smaller than the (1,C) it already saw, and the clock would move backwards. The receive rule exists exactly to forbid that.

Guarantee shown: The figure shows the two rules producing the book's stamps and the trap segment showing order without causality. It does not show wall-clock time — there is none.

Not shown: Concurrency detection and message-loss handling are outside this figure — the assembly names the vector-clock price for the first.

خودآزماییSelf-check

بعد از گرفتن (1,A) و بعد (1,C)، مقدار B چیست و چرا جواب (2,B) است؟

پاسخ: B بعد از دریافت اول ۱ است (max(0,1)) و بعد از دومی هنوز ۱ (max(1,1))؛ ارسالِ جواب به ۲ می‌رسد پس (2,B). آن ‎+1‎ که بعضی ارائه‌ها روی دریافت می‌گذارند همان افزایشی است که روی ارسال بعد حساب می‌شود — ترتیب هر دو جور یکی است.

After receiving (1,A) then (1,C), what does B hold, and why is the reply (2,B)?

Answer: B holds 1 after the first receive (max(0,1)) and still 1 after the second (max(1,1)); the reply-send ticks to 2, hence (2,B). The +1 some presentations put on receive is the same increment charged on the next send — the order is identical either way.

خودآزماییSelf-check

آیا (3,C) < (5,A) یعنی y قبل از x رخ داده؟

پاسخ: نه. مهرها نمایش را مرتب می‌کنند؛ فقط زنجیره پیام علّت‌ها را مرتب می‌کند. x و y تا پیامی وصلشان کند هم‌زمان‌اند و مهر Lamport این را نمی‌گوید.

Does (3,C) < (5,A) mean y happened before x?

Answer: No. The stamps order the display; only a message chain orders causes. x and y are concurrent until a message connects them, and Lamport stamps cannot tell you that.

گزینه‌های جایگزینAlternatives

  • ساعت برداری (یک شمارنده per-process): هم علیّت و هم هم‌زمانی را تشخیص می‌دهد، به قیمت حالت O(n) در هر گره و O(n) بایت در هر پیام. فقط وقتی بپرداز که محصول باید «هم‌زمان» را بفهمد — ویرایش مشترک، تحویل علّی، فراداده CRDT — نه برای مرتب‌سازی ساده.
  • Vector clocks (one counter per process): detect causality AND concurrency, at O(n) state per node and O(n) bytes per message. Pay for it only when the product must know 'concurrent' — collaborative editing, causal delivery, CRDT metadata — not for plain ordering.

سناریوهای خرابیFailure scenarios

  • گم شدن یا تکراری پیام: پذیرش idempotent است (max دو بار همان یک‌بار است) ولی پیام گمشده گیرنده را جلو نمی‌برد — ترتیب معتبر می‌ماند فقط درشت‌تر. هرگز مهری که نگرفتی حدس نزن.
  • برخورد شناسه پروسه: دو پروسه با یک شناسه tie-break را می‌شکنند و دو رخداد مهر یکسان می‌گیرند. نگهبان: شناسه از یک رجیستری (یا همان oracle تمرین ۳) و crash روی ثبت تکراری.
  • سرریز شمارنده: شمارنده ‎۶۴بیتی با نرخ آموزشی عملاً تمام‌نشدنی است؛ شمارنده کوچک می‌چرخد و ترتیب را می‌شکند. نگهبان: ‎۶۴بیت ثابت و assert — هرگز بی‌صدا نچرخ.
  • Lost or duplicated message: adoption is idempotent (max twice is max once), but a lost message simply never advances the receiver — the order stays valid, only coarser. Never 'fill in' a stamp you did not receive.
  • Process-ID collision: two processes sharing one ID break the tie-break and can stamp two events identically. Guard: assign IDs from one registry (or reuse the oracle of exercise 3) and crash on duplicate registration.
  • Counter overflow: a u64 counter ticking per event lasts effectively forever at teaching rates; a tiny counter wraps and breaks the order. Guard: fix u64 and assert — never silently wrap.

اجراشده و تأییدشده در همین محیطExecuted and verified in this environment

این کد آموزشی و ساده‌سازی‌شده است؛ فقط برای آشنایی با ایده. کد واقعی پروداکشن ملاحظات بسیار بیشتری دارد و هیچ‌کس این‌شکلی کد پروداکشن نمی‌زند.Simplified teaching code for building intuition only — not production code; nobody ships production code like this.

import java.util.*;
// Teaching demo: Lamport clocks on 3 processes (chapter diagram 5).
// send/local -> c+=1, stamp (c,pid); receive(m) -> adopt max(c,m.ts).
public class LamportDemo {
    record Ts(long c, String pid) implements Comparable<Ts> {
        public int compareTo(Ts o) {
            int r = Long.compare(c, o.c);
            return r != 0 ? r : pid.compareTo(o.pid);
        }
    }
    static class Proc {
        final String id; long c = 0;
        Proc(String id) { this.id = id; }
        Ts send() { c++; return new Ts(c, id); }
        void receive(Ts m) { c = Math.max(c, m.c()); }
    }
    public static void main(String[] a) {
        Proc A = new Proc("A"), B = new Proc("B"), C = new Proc("C");
        Ts mA = A.send(), mC = C.send();
        B.receive(mA); B.receive(mC);
        Ts mB = B.send(); A.receive(mB);
        System.out.println("stamps: A=" + mA + " C=" + mC + " B-reply=" + mB);
        List<Ts> order = new ArrayList<>(List.of(mB, mC, mA));
        Collections.sort(order);
        System.out.println("total order = " + order);
        Ts x = new Ts(1, "A"), y = new Ts(1, "C");
        System.out.println("L(x)=" + x + " < L(y)=" + y + " but no causal path");
        if (!order.equals(List.of(new Ts(1, "A"), new Ts(1, "C"), new Ts(2, "B"))))
            throw new AssertionError();
        System.out.println("OK: receive adopts max; total order <> causal order");
    }
}

آزمون صحت و معیار عملیاتیCorrectness checks and operational criteria

Assert the receive rule (never backwards after any delivery), assert the book's sorted order (1,A) < (1,C) < (2,B), and property-test the trap: random message-free events must accept ANY stamp pair. State cost as O(1) per process versus O(n) for vectors — no latency claim without a harness.

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (سینیور): دو رخداد بدون هیچ پیام چه timestampهایی می‌توانند داشته باشند؟Follow-up (Senior): What timestamps can two independent events with no messages have?

هر جفتی — مثلاً (5,A) و (3,C) یا (1,A) و (100,C). بدون پیام هیچ قیدی نیست: هر شمارنده فقط خودش را دیده. همین آزادی دقیقاً چرایی ناتوانی مهر Lamport در تشخیص هم‌زمانی است: مهرهای مرتب بدون زنجیره پیام هیچ‌چیز را ثابت نمی‌کنند.

Any pair at all — for example (5,A) and (3,C), or (1,A) and (100,C). With no messages there is no constraint: each counter only ever saw itself. That freedom is exactly why Lamport stamps cannot detect concurrency: equal-or-ordered stamps without a message chain prove nothing.

پیگیری (سینیور): ساعت برداری با هزینه <span class="ltr">O(n)</span> کی به <span class="ltr">Lamport</span> می‌ارزد؟Follow-up (Senior): When is a vector clock worth its O(n) cost over Lamport?

وقتی محصول باید هم‌زمانی را «بداند» نه فقط مرتبش کند: ویرایش مشترک (ویرایش‌های هم‌زمان ادغام و بعدی‌های علّی اعمال)، انتشار علّی، فراداده CRDT. هزینه: O(n) شمارنده در هر گره و O(n) بایت مهر در هر پیام، به‌علاوه منطق ادغام در هر دریافت. پیش‌فرض Lamport؛ ارتقا فقط با سؤال هم‌زمانی نام‌دار.

When the product must KNOW concurrency, not just order it: collaborative editing (concurrent edits merge, causally-after edits apply), causal broadcast, CRDT metadata. Cost: O(n) counters per node and O(n) stamp bytes per message, plus join logic on every receive. Default to Lamport; upgrade only on a named concurrency question.

اشتباهات رایجCommon mistakes

  • خواندن L(a) < L(b) به‌معنای «a علّت b است». ترتیب مهر ترتیب نمایش است؛ علّیت زنجیره پیام از a به b می‌خواهد.
  • ادعای تشخیص هم‌زمانی با Lamport («مهر برابر یعنی هم‌زمان»). دو رخداد بدون پیام هر مهری می‌توانند داشته باشند — برابری هم چیزی را ثابت نمی‌کند.
  • دست بردن به هم‌گام‌سازی ساعت دیواری. Lamport اصلاً ساعت هم‌گام نمی‌خواهد — نکته همین است؛ افزودن NTP این‌جا هیچ‌چیز را حل نمی‌کند و فقط حالت خرابی skew می‌افزاید.
  • Reading L(a) < L(b) as 'a caused b'. The stamp order is display order; causality needs a message chain from a to b.
  • Claiming Lamport detects concurrency ('equal stamps mean concurrent'). Two message-free events may hold any stamps — equality proves nothing either.
  • Reaching for wall-clock synchronization. Lamport needs no synchronized clocks at all — that is the point; adding NTP solves nothing here and adds skew failure modes.

سؤال مصاحبهInterview question
با سه replica و write در جریان که هنوز فقط به یکی رسیده، دو quorum read بساز که اولی جدید و دومی قدیمی می‌خواند. سپس الگوریتم register با version مرتب و write-back به اکثریت پیش از بازگشت read را مشخص کن. برای multi-writer مرحلهٔ query پیش از write و فرض membership ثابت را تحلیل کن.
Construct new-then-old quorum reads during an incomplete three-replica write. Specify ordered versions and majority write-back before returning a read. Discuss a query phase for multiple writers, fixed membership and crash assumptions.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

نوشتنی در پرواز بساز که فقط به یکی از سه replica رسیده، بعد دو بار با r=2 بخوان: quorum اول نسخه تازه را می‌بیند و دومی که دیرتر شروع شده کهنه‌تر می‌خواند — تازه-بعد-کهنه، نقض خطی‌پذیری با w + r > n سالم. درستش کن به روش ABD: نسخه‌ها مرتب‌اند و هر خواننده نسخه بیشینه را قبل از برگشتن به quorum برمی‌گرداند. read-repair پس‌زمینه ناهمگام است و هیچ‌چیز را تضمین نمی‌کند؛ write-back قبل از بازگشت می‌کند.
Stage an in-flight write that reached only one of three replicas, then read r=2 twice: the first quorum meets the new version, the second starts later yet reads older — new-then-old, a linearizability violation with w + r > n intact. Fix it the ABD way: versions are ordered, and every reader writes the max version back to a quorum BEFORE returning. Background read-repair is async and guarantees nothing; write-back-before-return does.

صورت مسئله و فرض‌هاProblem and assumptions

  • سه replica به نام n1 و n2 و n3 با membership ثابت؛ حین سناریو rebalancing نیست.
  • تک‌نویسنده با نسخه‌های مرتب v1 (کهنه) v2 (تازه)؛ نوشتن هدف w=3 دارد ولی فقط n1 نسخه v2 را ذخیره کرده — جزئی و هرگز تأییدشده نیست.
  • خواندن‌ها با r=2 بیشینه نسخه دیده‌شده را برمی‌گردانند؛ خواندن خواننده B بعد از برگشتن خواندن A شروع می‌شود.
  • Three replicas n1/n2/n3, fixed membership; no rebalancing during the scenario.
  • Single writer, ordered versions v1(old) < v2(new); the write targets w=3 but only n1 has stored v2 — partial, never acknowledged.
  • Reads take r=2 and return the max version they meet; reader B's read starts after reader A's read returned.

چرا این روش و این عددها؟Why this method and these numbers?

read1 مقدار write ناتمام را می‌تواند ببیند، ولی اگر آن مقدار را برگرداند، read2 بعدی دیگر نمی‌تواند به قبلش برگردد. write-back پیش از پاسخ، مقدار دیده‌شده را روی اکثریت می‌گذارد؛ هر اکثریت بعدی با آن اشتراک دارد. پس برای n=3 دو عضو کافی است؛ درخواست ACK هر سه در مثال فقط پنجرهٔ write ناتمام را واضح می‌کند. اثبات به monotonic نسخه، membership ثابت و قواعد writer وابسته است، نه صرف جمع r+w.

Read1 may observe an incomplete write, but once it returns that value a later Read2 cannot go backwards. Before-return write-back places the observed version on a majority; every later majority intersects it. With n=3, two replicas suffice; targeting all three writes merely exposes the incomplete-write window. The proof also needs monotonic versions, fixed membership and a defined writer protocol.

مدل ذهنیMental model

quorum پلی است میان نوشتن و خواندن — ولی پل فقط چیزی را می‌برد که واقعاً رویش بار شده. نوشتن جزئی یک سر را بار می‌کند؛ خواندنی که از سر دیگر می‌گذرد چیز تازه‌ای نمی‌یابد. write-back یعنی خواننده خبر را قبل از گزارش برگشتن آن‌طرف می‌برد.
A quorum is a bridge between the write and the read — but a bridge only carries what was actually loaded onto it. A partial write loads one end; the read crossing from the other end finds nothing new. Write-back is the reader carrying the news across before reporting back.

حل گام‌به‌گامStep by step

  1. جزئی یعنی تأییدنشده هدف را از تأییدشده جدا کن: نوشتن w=3 را نشانه گرفت ولی فقط n1 نسخه v2 را ذخیره کرد. نامش جزئی — هیچ quorumای مدیون رؤیت‌پذیری‌اش نیست.
  2. بازپخش نقض جفت ناقض را اجرا کن: خواندن اول از n1 و n2 برمی‌گرداند max(v2,v1)=v2 (هم‌زمان، مجاز)؛ خواندن دوم از n2 و n3 بعد از برگشتن اول شروع می‌شود و می‌گیرد max(v1,v1)=v1. تازه-بعد-کهنه با نامساوی سالم.
  3. برگرداندن قبل از بازگشت درست ABD را اعمال کن: خواننده v2 را به n1 و n2 — یک quorum — قبل از برگشتن برمی‌گرداند. خواندن دوباره از n2 و n3 حالا v2 را می‌بیند. تعمیر قبل از بازگشت تضمین است؛ تعمیر بعدش آرایش.
  4. نام بردن فرض‌ها فرض‌های مانده را صادقانه بگو: این‌جا تک‌نویسنده (چندنویسنده query timestamp قبل از نوشتن می‌خواهد)، membership ثابت (rebalancing quorum مشترک می‌خواهد) و نسخه‌های مرتب با ساخت، هرگز با ساعت دیواری.
  1. Partial is not acked Separate targeted from acknowledged: the write aimed at w=3 but only n1 stored v2. Name it partial — no quorum owes it visibility.
  2. Replay the violation Run the violating pair: read1 from {n1,n2} returns max(v2,v1)=v2 (concurrent, allowed); read2 from {n2,n3} starts after read1 returned and gets max(v1,v1)=v1. New-then-old with the inequality intact.
  3. Write back before return Apply the ABD fix: the reader writes v2 back to {n1,n2} — a quorum — BEFORE returning. The re-read from {n2,n3} now meets v2. Repair before the return is the guarantee; repair after it is cosmetics.
  4. Name the assumptions State the remaining assumptions honestly: single writer here (multi-writer needs a pre-write timestamp query), fixed membership (rebalancing needs joint quorums), and versions ordered by construction, never by wall clock.

طراحی مشخصConcrete design

هر replica جفت (version, value) را با نسخه‌های کاملاً مرتب نگه می‌دارد. مسیر نوشتن (تک‌نویسنده): مهر v+1 بزن، به هر سه بفرست و منتظر w تأیید بمان — این‌جا فقط یکی می‌رسد پس نوشتن در پرواز می‌ماند. مسیر خواندن: از r=2 بپرس، بیشینه را بردار، به r=2 برگردان، بعد برگرد. چندنویسنده فاز query می‌افزاید: قبل از مهر زدن بالاترین timestamp را از quorum بخوان.

Each replica stores (version, value) with totally ordered versions. Write path (single writer): stamp v+1, send to all three, wait for w ACKs — here only one lands, so the write stays in flight. Read path: query r=2, pick max version, write it back to r=2, then return. Multi-writer adds a query phase: read the highest timestamp from a quorum before stamping the write.

مثال محاسبه‌شدهWorked example

اعداد آموزشی: replicaها نگه می‌دارند (v2=new) روی n1 و (v1=old) روی n2 و n3. خواندن اول از n1 و n2 می‌شود max(2,1)=v2. خواندن دوم از n2 و n3 می‌شود max(1,1)=v1 — نقض. write-back نسخه v2 را روی n2 می‌گذارد؛ خواندن دوباره می‌شود max(2,1)=v2 — درست شد. هزینه درست (آموزشی): یک round-trip اضافه quorum روی هر خواندن.

Teaching numbers: replicas hold (v2=new) on n1, (v1=old) on n2/n3. Read1 {n1,n2} = max(2,1) = v2. Read2 {n2,n3} = max(1,1) = v1 — violation. Write-back puts v2 on n2; re-read {n2,n3} = max(2,1) = v2 — fixed. Cost of the fix (teaching): one extra quorum round-trip on every read.

آیا read-repair پس‌زمینه می‌تواند جای write-back را بگیرد؟

پاسخ: نه. تعمیر باید قبل از برگشتن خواندن به صداکننده تمام شود. کار پس‌زمینه‌ای که بعداً می‌دود نمی‌تواند مقداری که قبلاً برگشته را عطف‌بماسبق خطی‌پذیر کند — صداکننده نقض را قبلاً دیده.

Can background read-repair replace the write-back?

Answer: No. The repair must complete before the read returns to its caller. A background task that runs later cannot retroactively linearize a value already returned — the caller already observed the violation.

گزینه‌های جایگزینAlternatives

  • خواندن خطی‌پذیر رهبرمحور (خواندن از رهبر یا خواندن با تأیید رهبر): استدلالش ساده‌تر ولی هر خواندن هزینه latency رهبر را می‌دهد و رهبر گلوگاه است. وقتی رقابت کم است و سادگی به توان خواندن می‌ارزد انتخابش کن؛ وقتی خواندن باید مقیاس بخورد خواندن رجیستری quorum را.
  • Leader-based linearizable reads (read from the leader, or leader-confirmed reads): simpler to reason about, but every read pays leader latency and the leader is a bottleneck. Choose it when contention is low and simplicity beats read throughput; choose quorum register reads when reads must scale out.

سناریوهای خرابیFailure scenarios

  • مرگ خواننده بعد از دیدن v2 ولی قبل از write-back: اگر صداکننده پاسخی نگرفت خواندن هرگز کامل نشد — یال تقدم نیست و write-back خواننده بعد هنوز v2 را پخش می‌کند. اگر v2 را برگرداند بعد وسط write-back مرد، خواندن کامل‌شده تقدم را گذاشت و وظیفه به خواننده بعد می‌رسد که هر بیشینه‌ای ببیند برمی‌گرداند. کامل یعنی پاسخ به صداکننده رسید، نه این‌که خواننده مقدار را درون خود دید.
  • نویسنده‌های هم‌زمان بدون فاز query: دو نویسنده که مستقل مهر v2 می‌زنند مقدار را دوشاخه می‌کنند — یک نسخه با دو داده. نگهبان: اول بالاترین timestamp را از quorum بپرس (چندنویسنده ABD) تا نسخه‌ها per-writer یکتا بمانند.
  • تغییر membership وسط سناریو: w + r > n روی دو مجموعه عضو متفاوت هیچ هم‌پوشانی ندارد. نگهبان: quorumهای مشترک — مجموعه‌های قدیم و جدید تا پایان تغییر باید هم را هم‌پوشانی کنند.
  • Reader crashes after observing v2 but before write-back: if the caller never got a response, the read never completed — no precedence edge, and the next reader's write-back still propagates v2. If it returned v2 then died mid-write-back, the completed read DID set precedence, and the duty passes to the next reader, which writes back whatever max it meets. Completed means the response reached the caller, not that the reader saw the value internally.
  • Concurrent writers without a query phase: two writers stamping v2 independently fork the value — same version, different data. Guard: query the highest timestamp from a quorum first (ABD multi-writer), so versions stay unique per writer.
  • Membership change mid-scenario: w + r > n computed over two different member sets overlaps nothing. Guard: joint quorums — old and new member sets must overlap each other until the change completes.

import java.util.*;
// Teaching demo: versions on 3 replicas, an in-flight write on n1 only,
// new-then-old r=2 reads, then the ABD fix: write-back before return.
public class QuorumDemo {
    record Ver(long v, String val) {}
    public static void main(String[] a) {
        Map<String, Ver> store = new LinkedHashMap<>(Map.of(
            "n1", new Ver(2, "new"), "n2", new Ver(1, "old"), "n3", new Ver(1, "old")));
        Ver r1 = maxOf(store, List.of("n1", "n2"));
        Ver r2 = maxOf(store, List.of("n2", "n3"));
        System.out.println("read1 {n1,n2} -> v" + r1.v() + "=" + r1.val());
        System.out.println("read2 {n2,n3} -> v" + r2.v() + "=" + r2.val());
        System.out.println("violation (new-then-old) = " + (r1.v() > r2.v()));
        store.put("n2", r1); // write-back of v2 to a quorum BEFORE return
        Ver r2b = maxOf(store, List.of("n2", "n3"));
        System.out.println("after write-back, read2 -> v" + r2b.v() + "=" + r2b.val());
        if (!(r1.v() == 2 && r2.v() == 1 && r2b.v() == 2)) throw new AssertionError();
        System.out.println("OK: versions ordered, write-back-before-return fixes it");
    }
    static Ver maxOf(Map<String, Ver> s, List<String> q) {
        return q.stream().map(s::get).max(Comparator.comparingLong(Ver::v)).orElseThrow();
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): اگر یک reader بعد از خواندن جدید و قبل از write-back بمیرد، کدام read باید completed حساب شود؟Follow-up (Staff): A reader crashes after observing the new value but before write-back. Should that read count as completed?

اگر reader پیش از write-back و پیش از پاسخ بمیرد، read کامل نشده است و می‌توان آن را در history کامل‌شده حذف کرد؛ read بعدی که مقدار قدیم می‌دهد لزوماً نقض نیست. اگر پاسخ v2 قبلاً به caller رسیده باشد، read کامل است و بازگشت v1 در read بعدی نقض است. انتقال وظیفه به خوانندهٔ بعد تضمین نمی‌دهد، چون ممکن است اصلاً v2 را نبیند؛ پروتکل درست پاسخ را تا پایان write-back quorum نگه می‌دارد.

If the reader crashes before write-back and before replying, the read is pending and may be omitted from a completed history; a later old read is not necessarily a violation. If v2 already reached the caller, the completed read constrains later reads and returning v1 violates linearizability. Passing repair duty to the next reader is insufficient: it may never see v2. A correct protocol withholds the reply until quorum write-back completes.

پیگیری (سینیور): چرا <span class="ltr">w + r &gt; n</span> به‌تنهایی خواندن تازه را تضمین نمی‌کند؟Follow-up (Senior): Why doesn't w + r > n alone guarantee fresh reads?

چون حساب روی مجموعه‌هاست و تازگی سه پیش‌فرض دیگر می‌خواهد: نوشتن کامل شده باشد (هر w ذخیره، نه یکی)، نسخه‌ها مرتب باشند تا خواننده مقایسه کند، و بیشینه قبل از برگشتن خواندن برگردد. هم‌پوشانی quorum بدون این پیش‌فرض‌ها پلی است که شاید بار کهنه ببرد — همان مجموعه‌ها و همان جمع با بار کهنه.

Because it is arithmetic over sets, and freshness needs three more premises: the write completed (all w stored, not one), versions are ordered so readers can compare, and the max is written back before the read returns. Quorum overlap without those premises is a bridge that may carry the old value — same sets, same sum, stale cargo.

اشتباهات رایجCommon mistakes

  • نامیدن w=3 هدف با w=3 تأییدشده. ارسال به سه مساوی ذخیره روی سه نیست؛ فقط ACKها حساب‌اند و این‌جا یکی است.
  • ادعای خطی‌پذیر شدن خواندن با read-repair پس‌زمینه. تعمیر بعد از بازگشت آرایش تاریخ است — صداکننده نقض را قبلاً دیده. بگو «تعمیر eventual» و هرگز «خطی‌پذیر».
  • مقایسه نسخه‌ها با timestamp ساعت دیواری (LWW). ساعت‌های دیواری skew دارند؛ مهرهای کج مقدارها را غلط و بی‌صدا مرتب می‌کنند. نسخه‌های این‌جا منطقی‌اند و با ساخت مرتب‌اند.
  • Calling the targeted w=3 an acknowledged w=3. Sent-to-three is not stored-on-three; only ACKs count, and here there is one.
  • Claiming background read-repair makes reads linearizable. Repair after the return is history cosmetics — the caller already saw the violation. Say 'eventual repair', never 'linearizable'.
  • Comparing versions by wall-clock timestamps (LWW). Wall clocks skew; skewed stamps order values wrongly and silently. Versions here are logical and ordered by construction.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

پیش از تحویل هر شناسه، انتهای بازه را بادوام رزرو کن؛ پس از crash از بعدِ mark ادامه بده. صدور ۱،۲،۳ از دستهٔ ۱ تا ۵ و سپس بازیابی از ۶ تکرار ندارد ولی gap دارد. یکتایی با بازه‌های جدا یا namespace جدا قابل شارد است. ترتیب عددیِ جهانیِ پاسخ‌های غیرهم‌پوشان قرارداد قوی‌تری است؛ fence روی reserve، پاسخ‌دادن رهبر قدیم از RAM را متوقف نمی‌کند و مسیر صدور هم باید مالک معتبر را بررسی کند.
Reserve the range high-water mark durably before issuing IDs; restart above it after a crash. Issuing 1,2,3 from 1..5 then restarting at 6 preserves uniqueness with gaps. Disjoint ranges or namespaces support sharded uniqueness. Global numeric ordering of non-overlapping responses is stronger: fencing reservations alone does not stop an old allocator serving RAM IDs, so the issuance path also needs a valid-owner check.

صورت مسئله و فرض‌هاProblem and assumptions

  • یک allocator oracle دسته‌های ‎۵تایی (اندازه آموزشی) تحویل می‌دهد؛ high-water mark بادوام و اشاره‌گر تحویل ناپایدار است.
  • crash همه حالت ناپایدار را می‌برد و هیچ بادوامی را نه؛ standby (اگر باشد) از همان mark بادوام شروع می‌کند.
  • یکتایی و بدون-gap و ترتیب تخصیص و ترتیب مشاهده real-time چهار تضمین جدا هستند — قبل از انتخاب بگو محصول کدام را می‌خواهد.
  • One oracle allocator serves batches of 5 (teaching size); the high-water mark is durable, the handout pointer is volatile.
  • Crash loses all volatile state and nothing durable; the standby (if any) starts from the same durable mark.
  • Uniqueness, gap-free, allocation order and real-time observation order are four separate guarantees — define which the product needs before choosing.

چرا این روش و این عددها؟Why this method and these numbers?

پایدارکردن high-water mark یعنی همهٔ شناسه‌های زیر آن رزروشده‌اند، حتی اگر هنوز تحویل نشده باشند؛ restart بعد از آن، تکرار را به gap تبدیل می‌کند. هزینهٔ write بادوام با دستهٔ b تقریباً بر b شناسه تقسیم می‌شود ولی تا b−1 شناسه در crash می‌تواند جا بیفتد. b=5 برای دیدن دستی این بده‌بستان است. یکتایی با بازهٔ جدا قابل شارد است؛ ترتیب پاسخ جهانی نیازمند کنترل مسیر صدور است و از fence روی ذخیرهٔ mark به‌تنهایی نتیجه نمی‌شود.

Persisted high-water marks reserve every ID below them, including unissued ones; restarting above the mark exchanges duplication for gaps. A batch of b amortizes a durable write across b IDs but can lose up to b−1 unissued IDs on crash. Five makes the trade-off inspectable. Disjoint ranges support sharded uniqueness; global response order needs issuance-path control beyond fencing mark storage.

مدل ذهنیMental model

allocator شناسه اطمینان درباره گذشته می‌فروشد (هرگز دو بار) و برای اطمینان درباره ترتیب اضافه می‌گیرد. یکتایی ارزان و shardشدنی است؛ هر قید ترتیبی بعدش — بدون-gap و مرتب و real-time — قیمت را بالا می‌برد تا فقط oracle fenced بتواند بپردازد.
An ID allocator sells certainty about the past (never twice) and charges extra for certainty about order. Uniqueness is cheap and shardable; every ordering word after it — gap-free, sorted, real-time — raises the price until only a fenced oracle can pay.

حل گام‌به‌گامStep by step

  1. اول mark بعد تحویل رزرو را قبل از تحویل پایدار کن: دسته ‎۱ تا ۵‎ را بادوام رزرو کن بعد ‎۱و۲و۳‎ را از RAM تحویل بده. ترتیب mark-first کل ترفند است.
  2. کشتن وسط دسته وسط دسته crash کن و از mark بالا بیا: ‎۴و۵‎ هرگز صادر نشدند پس صدورهای بعد ‎۶و۷‎ هستند. gap می‌آید و تکراری هرگز — issued=[1,2,3,6,7].
  3. جدا کردن تضمین‌ها چهار قرارداد را جدا کن: یکتایی، gap-free، ترتیب تخصیص و ترتیب real-time پاسخ‌ها. طرح دسته‌ای همین پاسخ عمداً gap دارد؛ بازه‌های جدا فقط یکتایی را می‌دهند. برای ترتیب جهانی، همهٔ مسیرهای تحویل باید پروتکل ترتیب واحد را رعایت کنند.
  4. fence کردن failover standby همهٔ بازه‌های رزروشده را از mark بادوام رد می‌کند و فقط بازهٔ تازه می‌گیرد؛ epoch قدیمی در reserve رد می‌شود. بازهٔ قبلی را دوباره واگذار نکن. رهبر قدیمی ممکن است از RAM شناسهٔ یکتا ولی کوچک‌تر بدهد؛ اگر ترتیب جهانی لازم است، مسیر پاسخ هم باید مالک فعلی را بررسی کند.
  1. Mark first, serve second Persist the reservation before serving: reserve batch 1..5 durably, then hand out 1,2,3 from RAM. The mark-first order is the whole trick.
  2. Crash the batch Crash mid-batch and recover from the mark: 4,5 were never issued, so next issues are 6,7. Gaps appear, duplicates never do — issued=[1,2,3,6,7].
  3. Split the guarantees Separate uniqueness, gap-free allocation, allocation order and real-time response order. This batched design deliberately allows gaps; disjoint ranges provide uniqueness. Global ordering requires every issuance path to follow one ordering protocol.
  4. Fence the failover The standby skips all durably reserved ranges and reserves new ones under an epoch fence. Never reassign an old range. An old leader may still issue unique but smaller RAM IDs; if global order is required, validate ownership on the response path too.

طراحی مشخصConcrete design

اجزا: یک allocator (اشاره‌گر تحویل ناپایدار + کش دسته)، یک فروشگاه بادوام برای high-water mark و یک standby که لاگ mark را بازپخش می‌کند. API: reserve(batch) اول mark را پایدار می‌کند و هنوز هیچ‌چیز قابل تحویل برنمی‌گرداند؛ nextID() از RAM تحویل می‌دهد. مسیر خواندن: تحویل از حافظه بدون I/O. مسیر نوشتن: اول mark بعد تحویل — crash میانشان فقط شناسه جا می‌اندازد. کلید پارتیشن: هیچی — oracle یک تصمیم‌گیر منطقی است؛ با دسته‌بندی مقیاس بده نه با تکه کردن mark.

Components: one allocator (volatile handout pointer + batch cache), one durable store for the high-water mark, one standby replaying the mark log. API: reserve(batch) persists the mark and returns nothing servable yet; nextID() serves from RAM. Read path: serve from memory, no I/O. Write path: mark-first, then serve — a crash between them only skips IDs. Partition key: none — the oracle is one logical decider; scale it by batching, not by splitting the mark.

چرا mark باید قبل از بیرون رفتن اولین شناسه پایدار شود نه بعدش؟

پاسخ: پایدار کردن بعد از صدور می‌گذارد crash رد شناسه‌های تحویل‌شده را گم کند پس بازیابی دوباره صادرشان می‌کند: تکراری. mark-first ریسک را برعکس می‌کند: crash فقط می‌تواند شناسه‌های هرگزبیرون‌نرفته را جا بیندازد که gap است، هرگز تکراری.

Why must the mark persist before the first ID leaves, not after?

Answer: Persisting after issuing lets a crash lose track of handed-out IDs, so recovery re-issues them: duplicates. Mark-first inverts the risk: a crash can only skip IDs that never left, which is a gap, never a duplicate.

Do disjoint shard ranges give global real-time order?

گزینه‌های جایگزینAlternatives

  • UUID تصادفی (بدون هماهنگی): یکتایی بدون هیچ allocator یا داستان failover، به قیمت هیچ ترتیبی و کلیدهای پهن‌تر. وقتی ترتیب هرگز خوانده نمی‌شود انتخابش کن — شناسه درخواست و span ردیابی — هرگز وقتی چیزی با شناسه مرتب می‌شود.
  • شناسه پیشوند-شاردی (A-* و B-* از بازه‌های جدا): یکتا و بدون هماهنگی با ترتیب per-shard، ولی بدون ترتیب real-time سراسری. وقتی شاردها مالک سطرهایشان‌اند و مرتب‌سازی میان‌شاردی فقط نمایشی است انتخابش کن.
  • UUIDs (random, no coordination): uniqueness without any allocator or failover story, at the cost of no order at all and wider keys. Choose when order is never read — request IDs, tracing spans — never when something sorts by ID.
  • Shard-prefixed IDs (A-*, B-* from disjoint ranges): unique and coordination-free with per-shard order, but no global real-time order. Choose when shards own their rows and cross-shard sorting is display-only.

سناریوهای خرابیFailure scenarios

  • failover بدون fencing: allocator قدیم زنده می‌شود و ‎۱و۲و۳‎ را کنار ‎۱و۲و۳‎ standby دوباره صادر می‌کند — تکراری، همان یک نتیجه ممنوع. نگهبان: standby یک token epoch تازه می‌گیرد و storage epoch کوچک‌تر را بادوام رد می‌کند — قاعده fencing فصل ۹، اعمال‌شده روی epochهای allocator نه tokenهای per-write.
  • پایدار کردن mark بعد از تحویل: crash میان تحویل و پایداری رد شناسه‌های صادرشده را گم می‌کند — بازیابی دوباره صادرشان می‌کند. نگهبان: ترتیب mark-first در کد که با تست کشتن وسط دسته assert می‌شود (همان دمو).
  • دو allocator روی بازه‌های هم‌پوشان (shardبندی غلط): جدایی فرض شده ولی هرگز اعمال‌نشده میان شاردها تکراری می‌دهد. نگهبان: بازه‌ها از یک نسخه کانفیگ تخصیص یابند و هر صادرکننده پیشوند شاردش را مهر بزند تا هم‌پوشانی قابل تشخیص باشد نه بی‌صدا.
  • Failover without fencing: the old allocator revives and re-issues 1,2,3 beside the standby's 1,2,3 — duplicates, the one forbidden outcome. Guard: the standby takes a fresh epoch token and storage durably rejects the smaller epoch — the fencing rule from chapter 9, applied to allocator epochs, not per-write tokens.
  • Mark persisted after serving: a crash between serving and persisting loses track of issued IDs — recovery re-issues them. Guard: mark-first ordering in code, asserted by a test that kills mid-batch (the demo).
  • Two allocators on overlapping ranges (mis-sharding): disjointness assumed but never enforced gives duplicates across shards. Guard: ranges assigned from one config version, and each issuer stamps its shard prefix so overlap is detectable, not silent.

import java.util.*;
// Teaching demo: oracle allocator. Persist the batch high-water mark
// BEFORE issuing; crash mid-batch loses only the unissued tail.
public class OracleDemo {
    static class Allocator {
        long persistedHwm = 0, next = 1;
        final long batch = 5;
        final List<Long> issued = new ArrayList<>();
        void reserve() { persistedHwm += batch; }
        long issue() {
            if (next > persistedHwm) reserve();
            issued.add(next);
            return next++;
        }
        void crash() { next = persistedHwm + 1; } // volatile lost, mark survives
    }
    public static void main(String[] a) {
        Allocator al = new Allocator();
        System.out.println("issue " + al.issue() + ", " + al.issue() + ", " + al.issue());
        al.crash();
        System.out.println("CRASH -> recover from hwm=" + al.persistedHwm);
        System.out.println("next: " + al.issue() + ", " + al.issue());
        Set<Long> uniq = new HashSet<>(al.issued);
        System.out.println("issued=" + al.issued + " dups=" + (uniq.size() != al.issued.size()));
        if (uniq.size() != al.issued.size()) throw new AssertionError("duplicate ID!");
        System.out.println("OK: no duplicates, gaps allowed");
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (سینیور): دو node بازه‌های جدا دارند؛ آیا IDهای صادرشده به ترتیب زمان جهانی افزایش می‌یابند؟Follow-up (Senior): Two nodes issue IDs from disjoint ranges. Do the IDs increase in global real-time order?

نه. بازه‌های جدا فقط یکتایی و ترتیب per-shard را تضمین می‌کنند. A-2 می‌تواند ظهر صادر شود و B-100 ساعت ‎۱۱:۵۹‎ ولی بعدش مرتب شود — ترتیب صدور دیواری و ترتیب عددی میان شاردها ربطی ندارند. اگر محصول سراسری با شناسه در real-time مرتب می‌کند، oracle fenced می‌خواهد نه بازه.

No. Disjoint ranges guarantee uniqueness and per-shard order only. A-2 can be issued at noon and B-100 at 11:59 yet sort after it — wall-clock issue order and numeric order are unrelated across shards. If the product sorts globally by ID in real time, it needs the fenced oracle, not ranges.

پیگیری (استف): رهبر oracle وسط دسته failover می‌کند؛ صدور دوباره را چطور ممنوع می‌کنی؟Follow-up (Staff): The oracle leader fails over mid-batch. How do you avoid double-issue?

standby همهٔ بازه‌های رزروشده را از mark بادوام رد می‌کند و فقط بازهٔ تازه می‌گیرد؛ epoch قدیمی در reserve رد می‌شود. بازهٔ قبلی را دوباره واگذار نکن. رهبر قدیمی ممکن است از RAM شناسهٔ یکتا ولی کوچک‌تر بدهد؛ اگر ترتیب جهانی لازم است، مسیر پاسخ هم باید مالک فعلی را بررسی کند.

The standby skips all durably reserved ranges and reserves new ones under an epoch fence. Never reassign an old range. An old leader may still issue unique but smaller RAM IDs; if global order is required, validate ownership on the response path too.

اشتباهات رایجCommon mistakes

  • «این oracle هرگز shard نمی‌شود.» غلطِ per-guarantee: یکتایی با بازه‌های جدا آزادانه shard می‌شود؛ فقط بدون-gap و ترتیب real-time سراسری مقاومت می‌کنند. بگو کدام تضمین، یا هیچی نگو.
  • پایدار کردن mark بعد از تحویل («برای سرعت نوشتن‌ها را بچ کن»). crash میانشان شناسه‌ها را دوباره صادر می‌کند — همان یک نتیجه ممنوع خریده‌شده به قیمت یک fsync کمتر. اول mark، همیشه.
  • fencing per-ID به‌جای per-epoch allocator. token باید epoch lease allocator را مشخص کند (یک بررسی fencing per-failover) نه هر شناسه صادرشده را — token per-ID به هر صدور یک بررسی بدون امنیت اضافه تحمیل می‌کند.
  • 'This oracle can never be sharded.' Wrong per guarantee: uniqueness shards freely with disjoint ranges; only gap-free and global real-time order resist sharding. Say which guarantee, or say nothing.
  • Persisting the mark after serving ('batch the writes for speed'). A crash in between re-issues IDs — the one forbidden outcome bought for one fewer fsync. Mark first, always.
  • Fencing per ID instead of per allocator epoch. Tokens must identify the allocator's lease epoch (one fencing check per failover), not each issued ID — per-ID tokens add a check to every issue for no extra safety.

سؤال مصاحبهInterview question
یک history کوچک شامل invoke/return read و write را روی register خطی‌سنجی کن. ترتیب real-time را حفظ و عملیات هم‌پوشان را جابه‌جا کن. برای test harness bounded search طراحی کن؛ pending operation و timeout نامعلوم را درست مدل کن.
Check a small register history while preserving real-time precedence and reordering overlapping operations. Design bounded search, model pending/indeterminate operations and explain the limits of sampled histories.

پاسخ ۶۰ثانیه‌ایThe 60-second answer

هر خواندن/نوشتن را با مهر invoke و return ثبت کن، تقدم real-time را بکش (تمام‌شده-قبل باید اول مرتب شود) بعد همه ترتیب‌های ترتیبی نگه‌دارنده‌اش را با جست‌وجوی کران‌دار بگرد: هر خواندن باید تازه‌ترین نوشتن پیشینش را ببیند. نوشتن کامل‌شده بعد خواندن کهنه رد می‌شود؛ عملیات‌های هم‌پوشان هر دو طرف خطی می‌شوند؛ نوشتن timeoutخورده نامعلوم است — هر دو شاخه را امتحان کن. نمونه قبول‌شده هرگز اجرای بعد را اثبات نمی‌کند.
Record every read/write with invoke and return stamps, draw real-time precedence (done-before must order first), then bounded-search all sequential orders that keep it: each read must see the latest preceding write. Completed-write then stale-read rejects; overlapping operations linearize either way; timed-out writes are indeterminate — try both branches. A passing sample never proves the next execution.

صورت مسئله و فرض‌هاProblem and assumptions

  • تک رجیستر با historyهای کوچک (‎۲-۳‎ عملیات)؛ جست‌وجوی کران‌دار جایگشت‌ها را می‌شمرد — فقط اندازه‌های آموزشی.
  • مهرهای invoke/return از ساعت harness می‌آیند؛ تقدم فقط از تمام‌شده-قبل-شروع استفاده می‌کند، هرگز مقایسه مهر.
  • عملیات‌های معلق (بدون مهر بازگشت، مثل timeoutها) تا هر دو شاخه امتحان نشوند نامعلوم‌اند.
  • Single register, small histories (2-3 ops); bounded search enumerates permutations — teaching sizes only.
  • Invoke/return stamps come from the harness clock; precedence uses done-before-starts only, never stamp comparison.
  • Pending operations (no return stamp, e.g. timeouts) are indeterminate until branched both ways.

چرا این روش و این عددها؟Why this method and these numbers?

برای history کوچک، پیمایش ترتیب‌ها روشی قابل‌فهم برای یافتن یک اجرای ترتیبی سازگار است؛ n عملیات در بدترین حالت n! ترتیب دارند، پس روش برای history بلند مناسب نیست. یال real-time فقط وقتی A کامل شود و بعد B شروع شود ایجاد می‌شود. pending operation را نمی‌توان خودکار failed گرفت چون ممکن است اثرش ثبت شده باشد. ساعت harness برای نسبت شروع/پایان است؛ timestamp خود داده، نقطهٔ linearization را تعیین نمی‌کند.

Enumerating orders makes a compatible sequential execution understandable for small histories. Worst-case n! permutations explain why it does not scale. Add a real-time edge only when A returns before B starts. A pending operation may have committed, so do not automatically discard it as failed. Harness time orders invocation/return; stored timestamps do not establish linearization points.

مدل ذهنیMental model

خطی‌سنج دادگاه است نه گوی بلورین: history شهادت است و تقدم قانون و رأی فقط پرونده پیش رو را مقید می‌کند. عملیات‌های هم‌پوشان شهروندان آزادند — قانون فقط چیزی را قید می‌کند که قبل از شروع دیگری تمام شده.
A checker is a courtroom, not a crystal ball: the history is the testimony, precedence is the law, and the verdict binds only the case before it. Overlapping operations are free citizens — the law constrains only what finished before another began.

حل گام‌به‌گامStep by step

  1. اول مهر بعد قید به هر عملیات از harness مهر invoke/return بزن. قاعده تقدم: اگر عملیات X قبل از شروع Y برگشت، X باید در هر ترتیب نامزد قبل Y باشد — تنها قید سخت.
  2. شمردن نگه‌دارنده‌ها ترتیب‌های نامزد نگه‌دارنده تقدم را بشمر؛ عملیات‌های هم‌پوشان آزاد جابه‌جا می‌شوند. h1 یک ترتیب می‌پذیرد (نوشتن و خواندن) و h3 هر دو را — آزادی نه شکست.
  3. قضاوت هر ترتیب قاعده رجیستر را per-order اعمال کن: برو و تازه‌ترین نوشتن را نگه دار و هر خواندن باید بخورد. تنها ترتیب h2 عدد ۱ می‌خواهد ولی صفر دارد — رد. یک ترتیب بازمانده history را قبول می‌کند.
  4. دوشاخه کردن نامعلوم عملیات‌های معلق را هر دو طرف دوشاخه کن: نوشتن timeoutخورده نامعلوم است — با معتبر شدن هر شاخه اثرکرد یا هرگز-نکرد قبول کن. بعد محدودیت را بگو: رأی فقط همین پنجره را مقید می‌کند.
  1. Stamp, then constrain Stamp every op with invoke/return from the harness. Precedence rule: if op X returned before op Y started, X must precede Y in every candidate order — the only hard constraint.
  2. Enumerate keepers Enumerate candidate orders that keep precedence; overlapping operations permute freely. h1 admits one order (write, read); h3 admits both — freedom, not failure.
  3. Judge each order Apply the register rule per order: walk it, track the latest write, each read must match. h2's only order demands 1 but holds 0 — reject. One surviving order accepts the history.
  4. Fork the unknown Fork pending operations both ways: a timed-out write is indeterminate — accept if either the took-effect or the never-did branch validates. Then state the limit: the verdict binds this window only.

طراحی مشخصConcrete design

harness: پوششی دور مشتری key-value که per-op مهر invoke/return می‌زند (ساعت monotonic برای مدت‌ها و ساعت دیواری برای لاگ). خطی‌سنج: گراف تقدم از یال‌های تمام‌شده-قبل-شروع، بعد جست‌وجوی جایگشت کران‌دار با قاعده رجیستر per-order و عملیات‌های معلق دوشاخه. مسیر خواندن: جمع یک پنجره history. مسیر نوشتن: هیچی — خطی‌سنج هرگز نمی‌نویسد، قضاوت می‌کند.

Harness: a wrapper around the key-value client stamping invoke/return per op (monotonic clock for durations, wall clock for the log). Checker: precedence graph from done-before-starts edges, then bounded permutation search with the register rule per order, pending ops forked both ways. Read path: collect a history window. Write path: none — the checker never writes, it judges.

گزینه‌های جایگزینAlternatives

  • بررسی مدل پیاده‌سازی (جست‌وجوی فراگیر پروتکل به سبک TLA+): به‌جای نمونه‌برداری از اجراها، طرح را برای اندازه‌های کران‌دار اثبات می‌کند. قوی‌تر از خطی‌سنج history ولی سنگین‌تر برای نوشتن — برای خود پروتکل replication استفاده‌اش کن و خطی‌سنج history را برای سیستم در حال اجرا نگه دار.
  • Model checking the implementation (TLA+-style exhaustive search of the protocol): proves the design for bounded sizes instead of sampling executions. Stronger than a history checker, heavier to write — use it for the replication protocol itself, and keep the history checker for the running system.

سناریوهای خرابیFailure scenarios

  • ساعت دروغ‌گوی harness (invoke بعد از return مهر خورده): تقدم وارونه می‌شود و رأی‌ها زباله‌اند. نگهبان: ساعت monotonic برای مدت‌ها و assert سلامت invoke <= return روی هر عملیات و انداختن پرسروصدای پنجره‌های مردود.
  • نوشتن معلقِ شکست‌خورده فرض‌شده: نوشتن timeoutخورده شاید بعداً اثر کند — شکست نامیدنش باعث می‌شود خواندن بعدی مقدارش شبح به‌نظر برسد. نگهبان: مدل‌سازی نامعلوم با هر دو شاخه، همیشه.
  • پنجره history کوچک‌تر از شکار مسابقه (نمونه‌برداری فقط ساعت‌های خلوت): خطی‌سنج قبول می‌دهد و اطمینان دروغین است. نگهبان: نمونه‌برداری روی اوج و استقرارها و گفتن این‌که رأی پنجره را پوشش می‌دهد — هرگز سیستم را نه.
  • Lying harness clock (invoke stamped after return): precedence inverts and verdicts are garbage. Guard: monotonic clock for durations, sanity-assert invoke <= return on every op, drop windows that fail it loudly.
  • Pending write treated as failed: a timed-out write may still take effect later — calling it failed lets a later read of its value look like a phantom. Guard: indeterminate modeling, both branches, always.
  • History window too small to catch the race (sampling only quiet hours): the checker passes and confidence is false. Guard: sample across peaks and deploys, and say the verdict covers the window — never the system.

import java.util.*;
// Teaching demo: mini linearizability checker for one register.
// Try every order that keeps real-time precedence; each read must see
// the latest preceding write. Pending/timeout ops branch both ways.
public class CheckerDemo {
    record Op(String name, char kind, String val, int start, int end) {}
    public static void main(String[] a) {
        List<Op> h1 = List.of(new Op("w", 'w', "1", 0, 2), new Op("r", 'r', "1", 3, 4));
        List<Op> h2 = List.of(new Op("w", 'w', "1", 0, 2), new Op("r", 'r', "0", 3, 4));
        List<Op> h3 = List.of(new Op("w", 'w', "1", 0, 5), new Op("r", 'r', "0", 2, 4));
        System.out.println("h1 completed-write, new read  -> " + check(h1));
        System.out.println("h2 completed-write, stale read -> " + check(h2));
        System.out.println("h3 overlapping read             -> " + check(h3));
        if (!check(h1).equals("LINEARIZABLE") || !check(h2).equals("NOT LINEARIZABLE")
                || !check(h3).equals("LINEARIZABLE")) throw new AssertionError();
        System.out.println("OK: precedence enforced, stale-after-complete rejected");
    }
    static String check(List<Op> ops) {
        for (List<Op> order : permutations(new ArrayList<>(ops))) {
            if (!respectsRealtime(order)) continue;
            if (validRegister(order)) return "LINEARIZABLE";
        }
        return "NOT LINEARIZABLE";
    }
    static boolean respectsRealtime(List<Op> order) {
        Map<String, Integer> pos = new HashMap<>();
        for (int i = 0; i < order.size(); i++) pos.put(order.get(i).name(), i);
        for (Op x : order) for (Op y : order)
            if (x.end() != -1 && x.end() < y.start() && pos.get(x.name()) > pos.get(y.name())) return false;
        return true;
    }
    static boolean validRegister(List<Op> order) {
        String cur = "0";
        for (Op o : order) {
            if (o.kind() == 'w') cur = o.val();
            else if (!o.val().equals(cur)) return false;
        }
        return true;
    }
    static List<List<Op>> permutations(List<Op> in) {
        List<List<Op>> out = new ArrayList<>();
        perm(in, 0, out);
        return out;
    }
    static void perm(List<Op> l, int k, List<List<Op>> out) {
        if (k == l.size()) { out.add(new ArrayList<>(l)); return; }
        for (int i = k; i < l.size(); i++) { Collections.swap(l, i, k); perm(l, k + 1, out); Collections.swap(l, i, k); }
    }
}

پاسخ سؤال‌های پیگیریFollow-up answers

پیگیری (استف): timeout یک write را failed حساب می‌کنی یا indeterminate؟ چرا؟Follow-up (Staff): Do you model a timed-out write as failed or indeterminate, and why?

نامعلوم، همیشه. timeout یعنی نتیجه نامشخص است: درخواست یا نوشتن یا پاسخ هرکدام ممکن است گم شده باشند — همان ابهام کلاسیک. خطی‌سنج باید هر دو شاخه را امتحان کند (اثرکرد / هرگز-نکرد) و با معتبر شدن هرکدام قبول دهد. شکست مدل کردنش، نوشتنِ دیراثر را نقض دروغین می‌کند؛ شدنی مدل کردنش نقض‌های واقعی را پنهان می‌کند.

Indeterminate, always. A timeout means the outcome is unknown: the request, the write, or the response may each have been lost — the classic ambiguity. The checker must try both branches (took effect / never did) and accept if either validates. Modeling it as failed turns a late-taking-effect write into a false violation; modeling it as done hides real ones.

پیگیری (استف): خطی‌سنج روی ده‌هزار history نمونه قبول می‌دهد؛ آیا سیستم خطی‌پذیر است؟Follow-up (Staff): The checker passes on 10k sampled histories. Is the system linearizable?

نه. ده‌هزار پنجره قبول‌شده ده‌هزار پنجره را اثبات می‌کند نه سیستم را: اجرای بعد و استقرار بعد و درهم‌تنیدگی اوج بار بعد قضاوت‌نشده‌اند. تست متناهی اطمینان را بالا می‌برد؛ فقط اثبات پروتکل (بررسی مدل) به‌علاوه کاوش پیوسته پروداکشن (پروب نسخه و مانیتور واگرایی) تضمین را جلو می‌برد. بگو خطی‌سنج چه را پوشش می‌دهد: پنجره‌های نمونه‌برداری‌شده را.

No. Ten thousand passing windows prove ten thousand windows, not the system: the next execution, the next deploy, the next peak-load interleaving is unjudged. Finite testing raises confidence; only protocol proof (model checking) plus continuous production probing (version probes, divergence monitors) carry the guarantee forward. Say what the checker covers: the sampled windows.

اشتباهات رایجCommon mistakes

  • گرفتن مقایسه مهر به‌جای تقدم («نوشتنِ مهرزودتر باید اول مرتب شود»). تقدم تمام‌شده-قبل-شروع روی بازه‌های invoke/return است — مقدار مهر، Lamport یا دیواری، هرگز تعیینش نمی‌کند.
  • قبول با اولین ترتیب قابل‌قبول به‌جای گشتن همه ترتیب‌های نگه‌دارنده تقدم برای رد. یک ترتیب معتبر قبول می‌کند؛ ولی این‌که هیچی نیست را فقط بعد از امتحان همه می‌دانی.
  • اجرا روی خواندن‌های replica و «درست» کردن شکست‌ها با ضعیف کردن historyها (انداختن خواندن‌های کهنه). خطی‌سنج نقض واقعی یافته — فروشگاه را درست کن (write-back و خواندن رهبر)، هرگز مدرک را نه.
  • Treating stamp comparison as precedence ('write stamped earlier must order first'). Precedence is done-before-starts on invoke/return intervals — stamp values, Lamport or wall, never decide it.
  • Accepting on the first plausible order instead of searching all precedence-keeping orders for rejection. One valid order accepts; but you only know none exists after trying all.
  • Running the checker on replica reads and 'fixing' failures by weakening the histories (dropping the stale reads). The checker found a real violation — fix the store (write-back, leader reads), never the evidence.
