ایدهٔ کلیدی فصلChapter thesis

این فصل می‌ره تو دلِ موتورِ ذخیره‌سازی: داده کجا نوشته می‌شه و موقع خوندن چطور پیدا می‌شه؟ لاگ و ایندکس و B-tree و LSM و ذخیره‌سازی ستونی، هزینهٔ خوندن و نوشتن رو به شکل‌های مختلف تقسیم می‌کنن.

مثال فنی: یک داده، دو مسیر خواندن

وضعیت اولیه: فرض کن جدول سفارش با id خونده می‌شه و گزارش فروش فقط ستون amount رو جمع می‌زنه. دو تا کار جدا.

اجرای مرحله‌به‌مرحله: حالا lookup نقطه‌ای از ایندکس استفاده می‌کنه؛ اسکن تحلیلی از چیدمان ستونی سود می‌بره. هر کدوم ساز خودش رو می‌زنه.

نتیجه و دلیل: پس موتور ذخیره‌سازی رو باید با نوع خوندن و نوشتن سنجید. سریع بودن یه lookup دربارهٔ سرعت اسکن میلیاردی چیزی نمی‌گه — یادت باشه.

مثال‌های این فصل قصه‌های آموزشی‌ان که از کار روزمره اومدن. عددها فقط برای فهم بهتر انتخاب شدن و معماری هیچ شرکت واقعی رو توصیف نمی‌کنن.

At the lowest level every database must do just two things: keep the data you give it and hand it back when you ask later. Chapter 3 was about the “shape” of data and query languages; this chapter looks through the engine’s eyes: how data is laid out on disk and how it is found at query time.

چرا توسعه‌دهنده باید این رو بدونه؟ چون باید از میون موتورهای فراوون، موتورِ مناسب الگوی بارکاریِ خودت رو انتخاب کنی و پارامترهاش رو درست بچینی. برای هر دو کار، داشتن نقشهٔ ذهنی از زیر کاپوت لازمه.

Why should a developer know this? Because you must pick the right engine for your workload pattern out of dozens of options and set its parameters correctly. Both jobs need a mental map of what happens under the hood.

مهم‌ترین خطِ تقسیم این فصل، همان تفکیک OLTP در برابر OLAP از فصل ۱ است:

This chapter’s most important dividing line is the same OLTP vs OLAP split from Chapter 1:

  • موتورهای تراکنشی (OLTP): تعداد زیاد درخواست، هرکدوم چند تا رکورد کوچیک، پاسخ سریع. دسترسی معمولاً با کلید اصلی یا ایندکس ثانویه؛ ساختارهای اصلی: ایندکس‌های مرتب از کلید به رکورد که range query هم بدهن.
  • موتورهای تحلیلی (OLAP/انبارداده): چند تا پرس‌وجوی پیچیده که میلیون‌ها رکورد رو می‌پیماین. ساختار اصلی: ذخیره‌سازی ستونی با فشرده‌سازی (برای کم کردن دادهٔ خونده‌شده از دیسک) و اجرای JIT یا برداری (برای کم کردن زمان CPU).
  • Transactional (OLTP) engines: many requests, each touching a few small records, with fast responses. Access is usually by primary key or secondary index; the core structures are sorted key-to-record indexes that also serve range queries.
  • Analytical (OLAP/warehouse) engines: a few complex queries scanning millions of records. The core structure is columnar storage with compression (to minimize bytes read from disk) plus JIT or vectorized execution (to minimize CPU time).
تو سمت OLTP هم دو تا مکتب موتور داریم که بقیهٔ فصل حول اونا می‌چرخه:

On the OLTP side there are two engine schools that the rest of the chapter revolves around:

  • ساخت‌یافته / Log-Structured: فقط افزودن به فایل و حذف فایل‌های کهنه؛ هرگز بازنویسی درجا. SSTable، LSM-tree، RocksDB، Cassandra، HBase، ScyllaDB و حتی Lucene تو این خانواده‌ان. معمولاً بازده نوشتن بالا.
  • بازنویسی درجا / Update-in-place: دیسک مجموعه‌ای از صفحات با اندازهٔ ثابته که درجا بازنویسی می‌شن. B-treeها نمونهٔ برجسته‌ن و تقریباً تو همهٔ پایگاه‌های داده رابطه‌ای هستن. معمولاً خوندن سریع‌تر و قابل‌پیش‌بینی‌تر.
  • Log-structured: only append to files and delete stale files; never rewrite in place. SSTable, LSM-tree, RocksDB, Cassandra, HBase, ScyllaDB and even Lucene belong to this family. Usually high write throughput.
  • Update-in-place: the disk is a set of fixed-size pages rewritten in place. B-trees are the flagship example and live in almost every relational database. Usually faster, more predictable reads.
نکتهٔ مصاحبهInterview tip
کلِ مفهوم «ایندکس» یه تریدآفه: ساختاری مشتق‌شده از دادهٔ اصلی که خوندن رو سریع می‌کنه، ولی هر نوشتن باید اون رو هم به‌روز کنه؛ یعنی نوشتن کندتر و فضای بیشتر. به‌همین‌دلیل پایگاه داده‌ها همه‌جا ایندکس نمی‌سازن و انتخاب ایندکس با دونستن الگوی کوئری‌های تو انجام می‌شه.

The whole idea of an “index” is a trade-off: a structure derived from the primary data that speeds up reads, but every write must update it too — meaning slower writes and more space. That is why databases don’t index everything, and why index choice is made by someone who knows your query patterns: you.

۱1ساده‌ترین پایگاه داده جهانThe world’s simplest database

ساده‌ترین ذخیره‌ساز می‌تونه هر مقدار تازه رو به انتهای یه فایل اضافه کنه. نوشتن ساده‌ست، ولی برای پیدا کردن آخرین مقدارِ یه کلید باید فایل رو جست‌وجو کنیم.

مثال فنی: آخرین مقدار در لاگ

وضعیت اولیه: فرض کن فایل به‌ترتیب P7=100 و P7=120 داره. تهش آخریه.

اجرای مرحله‌به‌مرحله: حالا نوشتن فقط به انتهای فایل اضافه می‌کنه؛ خوندن بدون ایندکس باید آخرین رکورد P7 رو تو فایل پیدا کنه. بگرد تا پیدا کنی!

نتیجه و دلیل: پس append ساده‌ست، ولی خوندن با رشد فایل گرون می‌شه. ایندکس نشونی آخرین مقدار رو نگه می‌داره — آدرس رو یادداشت کن.

The book opens with two bash functions that form a complete key-value store — and every lesson of this chapter grows out of that simplicity:

#!/bin/bash
db_set () {
  echo "$1,$2" >> database
}
db_get () {
  grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}

$ db_set 12 '{"name":"London","attractions":["Big Ben"]}'
$ db_set 42 '{"name":"San Francisco","attractions":["Golden Gate"]}'
$ db_get 42
هر فراخوانیِ db_set یه خط به انتهای فایل افزوده می‌شه؛ مقدارهای قدیمیِ هر کلید بازنویسی نمی‌شن و آخرین مقدار، آخرین رخدادِ همون کلید تو فایله (به‌همین‌دلیل tail -n 1). این دقیقاً همون کاریه که پایگاه‌های داده واقعی با لاگ می‌کنن.

Each db_set call appends one line to the end of the file; old values of a key are never rewritten, and the latest value is the key’s last occurrence in the file (hence tail -n 1). That is exactly what real databases do with a log.

۱.۱ لاگ، ایندکس و تریدآف1.1 Log, index and trade-off

  • لاگ (log) تو این کتاب یعنی: دنباله‌ای فقط‌افزودنی از رکوردها رو دیسک. لازم نیست انسان‌خوان باشه؛ می‌تونه باینری و فقط داخلی باشه. افزودن به فایل، ساده‌ترین و معمولاً سریع‌ترین نوع نوشتنه.
  • مسئله تو خوندنه: db_get باید کل فایل رو بگرده؛ هزینهٔ هر جست‌وجو O(n)ـه — با دو برابر شدن رکوردها، دو برابر کندتر.
  • پاسخ: ایندکس — ساختاری اضافی و مشتق‌شده از دادهٔ اصلی (مثلاً مرتب‌شده بر اساس کلید) که یافتن داده رو سریع می‌کنه. افزودن و حذف ایندکس محتوای پایگاه داده رو عوض نمی‌کنه؛ فقط کارایی رو.
  • هر ایندکس نوشتن رو کند می‌کنه (چون با هر نوشتن باید اون هم به‌روز بشه) و فضا می‌گیره. چون هیچ ایندکسی رایگان نیست، پایگاه داده‌ها به‌طور پیش‌فرض رو همه‌چی ایندکس نمی‌زنن؛ تو با دونستن الگوی کوئری‌ها انتخاب می‌کنی.
  • Log in this book means: an append-only sequence of records on disk. It need not be human-readable; it can be binary and purely internal. Appending to a file is the simplest and usually the fastest kind of write.
  • The problem is reading: db_get must scan the whole file; every lookup costs O(n) — twice the records, twice as slow.
  • The answer: an index — an extra structure derived from the primary data (e.g. sorted by key) that finds data fast. Adding or dropping an index never changes the database’s content; only its performance.
  • Every index slows writes (each write must update it too) and takes space. Since no index is free, databases don’t index everything by default; you choose, knowing your query patterns.

مثال فنی: بهای ایندکسِ اضافه

A real database has three more problems: concurrent writes, reclaiming space so the log doesn’t grow forever, and half-written records during crash recovery (all covered in Chapter 8). But the “append to the end of the file” principle is the same.

شکل رو از چپ بخون: جعبهٔ «لاگ فقط‌افزودنی» (هر db_set به انتها اضافه می‌شه؛ نوشتن O(1) و ترتیبی) با فلش «نوشتن ارزون» می‌رسه به جعبهٔ «مشکل خوندن» (db_get همهٔ خط‌ها رو می‌گرده؛ خوندن O(n)). از اونجا فلش «خوندن کند» می‌ره به جعبهٔ «افزودن ایندکس مشتق‌شده» (ساختار مرتب بر اساس کلید؛ خوندن O(log n)). پنل پایین حکم رو می‌گه: هر ایندکس خوندن رو سریع می‌کنه، ولی هر نوشتن باید اون رو هم به‌روز کنه و فضا می‌گیره — «ایندکس رایگان نداریم؛ با دونستن الگوی کوئری انتخاب کن».

Read left to right: “Append-only log” (every db_set appends; O(1) sequential writes) leads via “cheap writes” to “The read problem” (db_get scans every line; O(n) reads), then via “slow reads” to “Add a derived index” (a key-sorted structure; O(log n) reads). The bottom panel states the verdict: every index speeds reads but must be updated on each write and takes space — “no free index; choose by query pattern.”

۲2ذخیره‌سازی Log-StructuredLog-structured storage

تو ذخیره‌سازی لاگ‌محور، تغییرات تازه به ساختارهای جدید افزوده می‌شن. تو پس‌زمینه، بخش‌های قدیمی ادغام می‌شن تا دادهٔ تکراری و فضای بلااستفاده کمتر بشه.

مثال فنی: نسخه‌های تازه در LSM

وضعیت اولیه: فرض کن P7=100 تو SSTable قدیمیه و P7=120 تو memtable نوشته می‌شه. دو جا، دو نسخه.

اجرای مرحله‌به‌مرحله: حالا نوشتن WAL و حافظه رو به‌روز می‌کنه؛ flush فایل مرتب تازه می‌سازه و compaction نسخه‌های لازم رو ادغام می‌کنه.

نتیجه و دلیل: پس خواننده باید نسخهٔ قابل‌مشاهدهٔ تازه رو انتخاب کنه. پیدا شدن کلید تو یه فایل قدیمی برای توقف کافی نیست — تا تهش برو.

Suppose you want to keep the same append-only file and only make reads fast. First idea: an in-memory hash map from each key to the byte offset of its latest value in the file. Writes = append to the file + update the hash; reads = jump to the offset and read (no I/O at all if it sits in the OS cache).

ولی این طرح سه تا مشکل جدی داره:

But this design has three serious problems:

  • فضای رکوردهای بازنویسی‌شده هرگز آزاد نمی‌شه؛ با نوشتن مداوم، دیسک پر می‌شه.
  • hash map پایدار نیست و بعد از restart باید با اسکن کل لاگ بازسازی بشه (restart کند).
  • hash map باید تو حافظه جا بشه؛ hash رو دیسک هم بدقلقه (دسترسی تصادفی زیاد، بزرگ‌سازی گرون، برخورد کلیدها).
  • range query نداره: نمی‌تونی ساده بگی «همهٔ کلیدهای ۱۰۰۰۰ تا ۱۹۹۹۹»؛ باید تک‌تک رو جداگانه بیابی.
  • Space of overwritten records is never reclaimed; with constant writes the disk fills up.
  • The hash map is not durable and must be rebuilt by scanning the whole log after a restart (slow restarts).
  • The hash map must fit in memory; a hash on disk is awkward (lots of random access, expensive growth, key collisions).
  • No range queries: you can’t simply ask for “keys 10000 to 19999”; each must be looked up separately.

از لاگ تا SSTableFrom log to SSTable

تو LSM، تغییرات اول تو حافظه جمع می‌شن و بعد به فایل‌های مرتب‌شدهٔ SSTable می‌رن. لاگِ بازیابی کمک می‌کنه خرابی، تغییراتِ هنوز منتقل‌نشده رو از بین نبره.

مثال فنی: بلوکِ مناسب به‌جای کل فایل

وضعیت اولیه: فرض کن SSTable کلیدهای مرتب 100…999 داره و ایندکس پراکنده شروع هر بلوک رو می‌شناسه. مثل فهرست کتاب.

اجرای مرحله‌به‌مرحله: حالا برای کلید 740 بلوکی که از 700 شروع می‌شه پیدا و همون بخش خونده می‌شه. فقط همون قفسه!

نتیجه و دلیل: پس مرتب بودن هم جست‌وجوی بلوک و هم اسکن بازهٔ 740…760 رو ممکن می‌کنه. هش به‌تنهایی ترتیب بازه رو نمی‌ده — نظم قیمتیه.

  • تو عمل، به‌جای hash، داده رو مرتب بر اساس کلید نگه می‌دارن. نمونه: SSTable (Sorted Strings Table) — جفت‌کلیدمقدارهای مرتب که هر کلید فقط یه‌بار میاد.
  • ایندکس پراکنده (sparse index): به‌جای همهٔ کلیدها، فقط اولین کلیدِ هر بلوکِ چند کیلوبایتی رو نگه می‌دارن. مثال کتاب: برای یافتن handiwork، چون مرتبه می‌دونی بین handbag و handsomeـه؛ به offset بلوک اول می‌پری و همون چند کیلوبایت رو می‌گردی.
  • هر بلوک قابل فشرده‌سازیـه: فضای کمتر + پهنای باند I/O کمتر، به بهای اندکی CPU.
  • ولی نوشتن سخت می‌شه: نمی‌شه ساده اضافه کرد (چون ترتیب می‌شکنه) و بازنویسی کل فایل هم خیلی گرونه. راه‌حل، رویکرد log-structuredـه:
  • memtable: هر نوشته اول به یه نقشهٔ مرتب تو حافظه می‌ره (red–black tree، skip list یا trie) — درج با هر ترتیبی، جست‌وجوی کارآمد، بازخونی مرتب.
  • flush: وقتی memtable از چند مگابایت بزرگ‌تر شد، مرتب رو دیسک به‌صورت یه SSTableِ جدا (جدیدترین سگمنت) نوشته می‌شه؛ هم‌زمان memtable تازه کار رو تحویل می‌گیره.
  • خوندن: اول memtable، بعد سگمنت‌ها از جدید به قدیم؛ اگه کلید هیچ‌جا نبود، وجود نداره.
  • merge و compaction: مثل mergesort — چند تا سگمنت کنار هم خونده می‌شن، کوچک‌ترین کلید به خروجی می‌ره و اگه کلیدی تکراری بود فقط تازه‌ترین مقدار می‌مونه. خروجی، سگمنتِ مرتبِ جدیده.
  • WAL جدا برای memtable: چون memtable تو حافظه‌ست، هر نوشته بلافاصله تو یه لاگ رو دیسک هم ثبت می‌شه تا بعد از crash بازسازی بشه. بعد از flush، همون بخش از لاگ قابل دور انداختنه.
  • حذف = tombstone: رکورد حذفِ ویژه‌ای اضافه می‌شه که موقع merge به فرآیند می‌گه مقادیر قبلیِ همون کلید رو دور بریزه.
  • این الگوریتم همون چیزیه که تو RocksDB و Cassandra و ScyllaDB و HBase هست (از مقالهٔ Bigtable با اصطلاحات SSTable و memtable) و اصل اون ۱۹۹۶ با نام LSM-tree (Log-Structured Merge-tree) منتشر شد. به همین دلیل به این موتورها LSM storage engines می‌گن.
  • سگمنت‌ها تغییرناپذیر‌ن: یه‌بار نوشته می‌شن و بعد فقط خونده/ادغام/حذف می‌شن. compaction تو thread پس‌زمینه انجام می‌شه و خوندن‌ها هم‌زمان با ورودی‌های merge سرویس می‌گیرن. crash وسط نوشتن هم ساده‌ست: فایل ناتمام دور انداخته می‌شه و لاگ با checksum رکوردهای خراب رو کنار می‌ذاره (جزئیات تو فصل ۸). این فایل‌ها حتی رو object storage هم عالی‌ان (مثل SlateDB و Delta Lake).
  • In practice, instead of a hash, data is kept sorted by key. Example: the SSTable (Sorted Strings Table) — sorted key-value pairs where each key appears once.
  • Sparse index: instead of all keys, keep only the first key of each multi-kilobyte block. The book’s example: to find handiwork, sorted order tells you it sits between handbag and handsome; jump to the first block’s offset and search just those kilobytes.
  • Each block can be compressed: less space + less I/O bandwidth, for a little CPU.
  • But writes get hard: you can’t simply append (order would break) and rewriting the whole file is far too expensive. The answer is the log-structured approach:
  • Memtable: every write first lands in an in-memory sorted map (red–black tree, skip list or trie) — inserts in any order, efficient lookup, sorted iteration.
  • Flush: when the memtable grows past a few megabytes it is written to disk, sorted, as a separate SSTable (the newest segment); a fresh memtable takes over.
  • Reads: memtable first, then segments newest to oldest; if the key is nowhere, it doesn’t exist.
  • Merge and compaction: like mergesort — several segments are read side by side, the smallest key goes to the output, and for duplicate keys only the newest value survives. The output is a new sorted segment.
  • A separate WAL for the memtable: since the memtable lives in memory, every write is also recorded immediately in an on-disk log so it can be rebuilt after a crash. After a flush, that part of the log can be discarded.
  • Deletes = tombstones: a special delete record is added that tells a merge to throw away that key’s older values.
  • This algorithm is what runs inside RocksDB, Cassandra, ScyllaDB and HBase (SSTable and memtable terms come from the Bigtable paper) and its essence was published in 1996 as the LSM-tree (Log-Structured Merge-tree). Hence these engines are called LSM storage engines.
  • Segments are immutable: written once, then only read, merged or deleted. Compaction runs in a background thread while reads keep being served from the merge inputs. A crash mid-write is simple too: the unfinished file is thrown away and the log’s checksums drop corrupt records (details in Chapter 8). These files are even great on object storage (e.g. SlateDB and Delta Lake).

The Write box (put(key, value)) sends update ordered map to the Memtable and append + fsync down to the Write-Ahead Log; the log’s only job is replay after crash back into the memtable.

از جعبهٔ «Write» با زیرنویسِ put(key, value) شروع کن — بالا سمت چپ. دو تا فلش ازش بیرون میاد: فلش پررنگِ «update ordered map» مستقیم به جعبهٔ «Memtable» (نقشهٔ مرتب تو حافظه) می‌ره، و فلش چین‌چینِ «append + fsync» به پایین، به جعبهٔ «Write-Ahead Log» با زیرنویسِ «append-only, checksummed». از همون لاگ، فلش چین‌چینِ دیگه‌ای با برچسب «replay after crash» به memtable برمی‌گرده — یعنی تنها دلیلِ وجودِ لاگ، بازسازیِ حافظه بعد از قطعیه.

The write path continues with flush sorted SSTable into SSTable Segments (sorted, immutable files, newest to oldest), then merge segments, keep newest value into Compaction, where tombstones dropped reminds you that deletes are collected here.

The write path continues with flush sorted SSTable into SSTable Segments, then merge segments, keep newest value into Compaction (tombstones dropped).

حالا نوار پایین: جعبهٔ «Point Read» با زیرنویسِ «get(key), newest first». سه تا فلش شماره‌گذاری‌شده داره: «1. check memtable» به بالا به memtable؛ «2. key in this segment?» به راست به جعبهٔ «Bloom Filter» (زیرنویس: «one bitmap per segment»)؛ و از Bloom filter فلشِ «3. seek sparse index + block» به بالا، به سگمنت‌ها. همین سه شماره، تموم قصهٔ جست‌وجوی نقطه‌ای تو LSMـه: اول حافظه، بعد سگمنت‌های جدید به قدیم، و هر سگمنت رو فقط اگه Bloom filter اجازه داد باز می‌کنیم.

Below, Point Read (get(key), newest first) follows three numbered arrows: 1. check memtable, then 2. key in this segment? to the Bloom Filter (one bitmap per segment), then 3. seek sparse index + block up into the segments. That is the whole LSM point-lookup story.

و درسِ ترکیبیِ شکل: مسیر نوشتن همیشه «افزودن»ـه (به لاگ، به memtable، به سگمنت تازه) و هیچ‌جا بازنویسی درجا نمی‌بینی؛ سنگینیِ کارِ مرتب‌سازی و پاک‌سازی به یه جعبهٔ پس‌زمینه یعنی Compaction منتقل شده.

The combined lesson: the write path is always “append” (to the log, the memtable, a fresh segment) with no in-place rewrite anywhere; all sorting and cleanup weight moves to one background box, Compaction.

۲.۲ Bloom filter و استراتژی compaction2.2 Bloom filters and compaction strategies

Bloom filter

پاسخِ «نیست» تو Bloom filter قطعیه و پاسخِ «شاید هست» بررسیِ واقعی می‌خواد. این فیلتر مقدارِ رکورد رو نگه نمی‌داره.

مثال فنی: شاید هست، قطعاً نیست

وضعیت اولیه: فرض کن برای یه SSTable، ـی Bloom filter می‌گه بیت لازم برای کلید P99 صفره. یعنی نیست.

اجرای مرحله‌به‌مرحله: حالا فایل برای P99 خونده نمی‌شه؛ ولی اگه همهٔ بیت‌ها یک باشن، فایل هنوز باید بررسی بشه. شاید هست، شاید نه.

نتیجه و دلیل: پس پاسخ مثبت می‌تونه کاذب باشه. فیلتر سالم برای مجموعهٔ ساخته‌شده پاسخ منفی کاذب نمی‌ده و جای بررسی داده رو نمی‌گیره — «نه» قطعیه، «شاید» مشکوکه.

  • برای هر سگمنت یه بیت‌آرایه؛ برای هر کلید چند تا هش حساب می‌شه و بیت‌های متناظر ۱ می‌شن.
  • موقع جست‌وجو: اگه حتی یه بیت ۰ بود، کلید قطعاً تو اون سگمنت نیست ← سگمنت رد می‌شه (بدون I/O).
  • اگه همه ۱ بودن، کلید احتمالاً هست — ولی ممکنه تصادفی باشه (false positive). اون‌وقت باید ایندکس پراکنده رو ببینی؛ اگه کلید نبود، فقط کمی کار بیهوده شده.
  • قاعدهٔ تجربی: حدود ۱۰ بیت به‌ازای هر کلید ← احتمال false positive حدود ۱٪؛ هر ۵ بیت اضافه، احتمال رو ده‌برابر کم می‌کنه.
  • One bit-array per segment; a few hashes per key set the corresponding bits to 1.
  • At lookup: if even one bit is 0, the key is definitely not in that segment → the segment is skipped (no I/O).
  • If all are 1, the key is probably there — but possibly by accident (false positive). Then you must check the sparse index; if the key is absent, only a little work was wasted.
  • Rule of thumb: ~10 bits per key → ~1% false-positive rate; every 5 extra bits cuts the rate tenfold.

دو استراتژی compactionThe two compaction strategies

  • Size-tiered: سگمنت‌های کوچیک و تازه با هم و بعد با سگمنت‌های بزرگ‌تر ادغام می‌شن (مثلاً چهار تا ۲۵۶MB ← یه ~۸۹۸MB؛ کمتر از ۱۰۲۴ چون حذف و overwrite و TTL جمع می‌شن). بازده نوشتن بالا، ولی فضای موقت زیاد و خوندن ممکنه چند تا سگمنت بزرگ رو بگرده.
  • Leveled: سگمنت‌ها اندازهٔ ثابت دارن و تو «سطح‌های» L0، L1، ... با محدودیت اندازهٔ فزاینده گروه‌بندی می‌شن؛ وقتی سطحی پر شد، به سطح بعدی ادغام می‌شه. فضای کمتر، ادغام تدریجی‌تر، و خوندن سریع‌تر (سگمنت‌های کمتری برای چک کردن).
  • قاعده: نوشتنِ غالب ← size-tiered؛ خوندنِ غالب ← leveled. خوشبختانه اکثر پیاده‌سازی‌ها هر دو رو دارن.
  • Size-tiered: small fresh segments merge together, then with bigger ones (e.g. four 256MB → one ~898MB; less than 1024 because deletes, overwrites and TTLs collapse). High write throughput, but lots of temporary space, and reads may scan several large segments.
  • Leveled: fixed-size segments grouped into “levels” L0, L1, … with growing size caps; when a level fills it merges into the next. Less space, more gradual merges, faster reads (fewer segments to check).
  • Rule: write-heavy → size-tiered; read-heavy → leveled. Luckily most implementations offer both.
دامنهٔ تصور غلطCommon misconception

Bloom filter می‌تونه با قطعیت بگه یه کلید تو فایل نیست، ولی جواب مثبتش نیاز به بررسی داره. Compaction فایل‌ها رو ادغام می‌کنه؛ نوع ادغام روی هزینهٔ خوندن و نوشتن و فضا اثر داره.

مثال فنی: دو سیاست ادغام

وضعیت اولیه: فرض کن چهار تا فایل 100 MB داری که بعضی کلیدهاشون هم‌پوشانی داره.

اجرای مرحله‌به‌مرحله: حالا size-tiered می‌تونه فایل‌های هم‌اندازه رو ادغام کنه؛ leveled فایل‌ها رو تو سطح‌ها و بازه‌های منظم‌تر نگه می‌داره. دو تا سلیقه.

نتیجه و دلیل: پس اولی معمولاً فایل و فضای موقت بیشتری می‌خواد؛ دومی ممکنه بازنویسی بیشتری بسازه. نتیجه به بار و تنظیمات وابسته‌ست — برندهٔ ثابت نداریم.

“LSM always means less space” — no! In size-tiered, until the next big merge both the old and the new version exist; definitive deletion (e.g. for data-protection law) can also take a while because the tombstone must propagate through every level. That same immutability does make cheap snapshots easy, though.

موتورهای جاسازی‌شده (Embedded)Embedded engines

موتور جاسازی‌شده داخل فرایندِ خودِ برنامه اجرا می‌شه. برخلاف یه سرور پایگاه دادهٔ جدا، برنامه مستقیماً از کتابخانهٔ موتور برای ذخیره و خوندن استفاده می‌کنه.

مثال فنی: RocksDB داخل فرایند

وضعیت اولیه: فرض کن یه worker شمارندهٔ هر customer_id رو تو RocksDB رو دیسک محلی نگه می‌داره. تو جیب خودشه.

اجرای مرحله‌به‌مرحله: حالا فراخوانی کتابخونه بدون RPC شبکه انجام می‌شه؛ ولی برای بازیابی ماشین ازدست‌رفته، checkpoint یا changelog بیرونی لازمه.

نتیجه و دلیل: پس embedded بودن سربار شبکه رو کم می‌کنه؛ ولی به‌خودی‌خود replication یا backup سراسری نمی‌ده — سرعت داره، نجات نه.

  • همهٔ پایگاه داده‌ها سرویس شبکه‌ای نیستن: موتورهای embedded کتابخانه‌ان و تو همون process برنامه اجرا می‌شن (RocksDB، SQLite، LMDB، DuckDB، KùzuDB). رایج تو اپ‌های موبایل؛ تو بک‌اند وقتی داده رو یه ماشین جا بشه و تراکنش‌های هم‌زمان زیاد نباشن (مثلاً یه نمونه به‌ازای هر tenant کوچیک و مستقل).
  • Not every database is a network service: embedded engines are libraries running in the application’s own process (RocksDB, SQLite, LMDB, DuckDB, KüzuDB). Common in mobile apps; on the backend when the data fits on one machine and concurrent transactions are few (e.g. one instance per small independent tenant).

۳3B-TreeB-trees

B-tree کلیدها رو تو ساختاری مرتب و چندسطحی نگه می‌داره. هر سطح بازهٔ جست‌وجو رو کوچیک‌تر می‌کنه تا بدون پیمایش همهٔ رکوردها به کلید برسیم.

مثال فنی: پیمایشِ B-tree

وضعیت اولیه: فرض کن ریشه کلید جداکنندهٔ 500 داره و برگ راست شامل 700,740,780ـه. درخت رو تصور کن.

اجرای مرحله‌به‌مرحله: حالا جست‌وجوی 740 با مقایسه تو ریشه می‌ره به فرزند راست و بعد برگ مربوط. پله‌پله پایین.

نتیجه و دلیل: پس هر سطح بازه رو محدود می‌کنه. لازم نیست برای یه کلید همهٔ صفحه‌ها خونده بشن — درخت یعنی نصف کردن راه.

The log-structured approach is popular, but not the only way. The most common structure for reading/writing records by key is the B-tree: introduced in 1970 and called “ubiquitous” less than a decade later. It is still the standard index implementation in almost every relational database.

ساختار: صفحه‌ها، نه سگمنت‌هاAnatomy: pages, not segments

صفحه واحدی از داده‌ست که موتور از دیسک می‌خونه یا می‌نویسه. تو B-tree، هر صفحه چند تا کلید و اشاره‌گر داره؛ پس یه خوندن می‌تونه اطلاعات زیادی برای انتخاب مسیر بده.

مثال فنی: صفحهٔ ثابت، تغییر کوچک

وضعیت اولیه: فرض کن موتور فرضی صفحه‌های 8 KB داره و رکورد هدف تو یه صفحه‌ست.

اجرای مرحله‌به‌مرحله: حالا تغییر چند بایت ممکنه ثبت WAL و dirty شدن همون صفحه رو لازم کنه؛ flush با واحدهای صفحه انجام می‌شه. واحد کار صفحه‌ست، نه بایت.

نتیجه و دلیل: پس اندازهٔ تغییر برنامه لزوماً برابر بایت نوشته‌شده رو دیسک نیست. cache و WAL تو مسیر دخالت دارن — چیزی که می‌بینی با چیزی که نوشته می‌شه یکیه؟ نه!

  • برخلاف سگمنت‌های با اندازهٔ متغیر و تغییرناپذیرِ LSM، B-tree پایگاه داده رو به صفحات با اندازهٔ ثابت (page) می‌شکنه که می‌تونن درجا بازنویسی بشن. اندازهٔ سنتی ۴ کیلوبایته؛ PostgreSQL حالا ۸ کیلوبایته و MySQL به‌طور پیش‌فرض ۱۶ کیلوبایت.
  • هر صفحه شماره داره و صفحه‌ها با شماره به هم ارجاع می‌دن (مثل pointer، ولی رو دیسک). اگه همه تو یه فایل باشن، شماره × اندازهٔ صفحه = offset بایتی.
  • یه صفحه rootـه و هر جست‌وجو از همون شروع می‌شه. هر صفحهٔ داخلی چند تا کلید و ارجاع به فرزند داره و هر فرزند مسئول یه بازهٔ پیوسته از کلیدهاست؛ کلیدهای بین ارجاع‌ها مرز بازه‌ها رو مشخص می‌کنن. (گاهی B+ tree می‌نامنش.)
  • تعداد ارجاع‌های هر صفحه = branching factor؛ تو عمل چند صدتاییه. به‌همین‌دلیل عمق درخت همیشه ۳ تا ۴ سطح می‌مونه (درخت ۴ سطحی با صفحات ۴KB و عامل انشعاب ۵۰۰ تا ۲۵۰ ترابایت رو نگه می‌داره).
  • برگ‌ها (leaf page) کلیدهای تکی رو دارن: یا مقدار رو inline نگه می‌دارن یا ارجاع به جایی که مقدار هست.
  • Unlike LSM’s variable-size immutable segments, a B-tree breaks the database into fixed-size pages that can be rewritten in place. The traditional size is 4 KB; PostgreSQL now uses 8 KB and MySQL 16 KB by default.
  • Each page has a number and pages reference each other by number (like pointers, but on disk). If all live in one file, number × page size = byte offset.
  • One page is the root and every lookup starts there. Each internal page holds several keys and child references, each child owning one contiguous key range; the keys between references mark the range boundaries. (Sometimes called a B+ tree.)
  • Each page’s child-reference count is the branching factor; in practice it is in the hundreds. That is why tree depth stays at 3–4 levels (a 4-level tree with 4KB pages and branching factor 500 holds up to 250 TB).
  • Leaf pages hold individual keys: either the value inline or a reference to where the value lives.

رشد: تقسیم صفحه (page split)Growth: page splits

وقتی صفحهٔ B-tree دیگه برای کلید تازه جا نداشته باشه، تقسیم می‌شه. کلیدهای اون میون دو تا صفحه پخش می‌شن و راهنمای سطح بالاتر هم به‌روز می‌شه.

مثال فنی: تقسیم برگِ پُر

وضعیت اولیه: فرض کن برگ ظرفیت سه تا کلید داره و شامل 10,20,30ـه؛ حالا کلید 25 می‌رسه. جا نیست!

اجرای مرحله‌به‌مرحله: حالا موتور برگ رو به دو بخش تقسیم می‌کنه و جداکنندهٔ مناسب رو تو والد ثبت می‌کنه. خونه رو دو نصف کن.

نتیجه و دلیل: پس اگه والد هم پر باشه تقسیم بالا می‌ره. خواننده باید پس از پایان، همهٔ کلیدها رو از مسیر درست پیدا کنه — تقسیم آبشاریه.

  • به‌روزرسانیِ کلید موجود = یافتن برگ و بازنویسی همون صفحه. درج کلید تازه = افزودن به صفحهٔ بازه‌ش؛ اگه جا نبود، صفحه به دو تا صفحهٔ نیمه‌پر split می‌شه و والد با کلید مرزیِ تازه به‌روز می‌شه.
  • مثال کتاب: درجِ 334 تو صفحهٔ ۳۳۳–۳۴۵ (پر) ← دو تا صفحهٔ ۳۳۳–۳۳۷ و ۳۳۷–۳۴۵ با مرزِ 337؛ اگه والد هم پر بود، split بالا می‌ره تا ریشه، و split ریشه یعنی ریشهٔ تازه بالای اون. حذف پیچیده‌تره (ممکنه صفحه‌ها merge بشن).
  • نتیجه: درخت همیشه متوازن می‌مونه و عمق O(log n)ـه.
  • Updating an existing key = find the leaf and rewrite that page. Inserting a fresh key = add it to its range’s page; if there is no room, the page splits into two half-full pages and the parent is updated with the fresh boundary key.
  • The book’s example: inserting 334 into full page 333–345 → two pages 333–337 and 337–345 with boundary 337; if the parent is full too, the split climbs toward the root, and a root split means a fresh root above it. Deletion is trickier (pages may merge).
  • Result: the tree stays balanced forever with O(log n) depth.

از ریشه دو تا فلش بیرون میاد: «between 200 and 300» به «Internal Page» بالایی (بازهٔ ۲۰۰–۳۰۰) و «between 300 and 400» به «Internal Page» پایینی (بازهٔ ۳۰۰–۴۰۰). چون کلید ما ۲۵۱ـه، مسیرِ بالایی درسته. از صفحهٔ داخلیِ بالایی هم دو تا فلش دیگه: «between 250 and 270» به «Leaf Page»‌ای با زیرنویسِ «keys 250–270» و برچسبِ «holds key 251» — مقصد نهاییِ جست‌وجو — و «between 271 and 300» به برگِ همسایه. یه فلش چین‌چینِ افقی با برچسبِ «sibling pointer» این دو تا برگ رو به هم دوخته تا اسکنِ مرتب بدون بازگشت به والد ممکن باشه. از برگ اول هم فلش چین‌چینِ «row pointer» به جعبهٔ «Heap File» (زیرنویس: «rows in no order») می‌ره — یعنی خودِ رکورد این‌جا نیست، فقط ارجاعش.

A dashed sibling pointer stitches the two leaves together for ordered scans without climbing back to the parent, and a row pointer leads from the leaf to the Heap File (rows in no order) — the record itself lives there, not in the index.

The lower half tells growth and safety: a third leaf (keys 333–345, split on overflow) shows how inserting 334 grows the tree, while the Write-Ahead Log (append-only, fsync before apply) takes log page change first and offers replay after crash back to the root.

درسِ شکل: مسیر خوندن «یه صفحه تو هر سطح»ـه و کوتاه؛ ولی هر نوشتن ممکنه چند تا صفحه رو بازنویسی کنه (split!) و چون بازنویسی درجا خطرناکه (crash وسط کار = درخت خراب)، اول هر تغییر باید تو WAL ثبت و fsync بشه.

The lesson: the read path is “one page per level” and short; but each write may rewrite several pages (splits!), and since in-place rewrites are dangerous (mid-work crash = broken tree), every change must hit the WAL with fsync first.

قابلیت اطمینان و واریانت‌هاReliability and variants

برای بازیابی بعد از خرابی، موتور باید بتونه تغییراتِ صفحات رو درست بازسازی کنه. WAL تغییر رو پیش از اعمالِ پایدارِ اون رو صفحات ثبت می‌کنه؛ قفل‌های داخلی هم تغییر هم‌زمانِ ساختار رو کنترل می‌کنن.

مثال فنی: لاگ پیش از صفحهٔ داده

وضعیت اولیه: فرض کن تغییر P7=120 اول تو WAL ثبت و طبق تنظیم ماندگاری پایدار می‌شه؛ صفحه هنوز رو دیسک قدیمیه.

اجرای مرحله‌به‌مرحله: حالا برق قطع می‌شه! موقع restart موتور با لاگ، تغییرهای لازم رو redo می‌کنه. از دفتر لاگ بخون.

نتیجه و دلیل: پس WAL امکان بازیابی تغییر تأییدشده رو می‌ده. تنظیمی که تأیید رو پیش از پایداری می‌ده تضمین ضعیف‌تری داره — اول بنویس، بعد قول بده.

  • عملیات پایهٔ B-tree بازنویسی یه صفحه درجاـه (برخلاف LSM که فقط append می‌کنه). بازنویسی چند تا صفحه (مثل split) خطرناکه: crash میونهٔ کار می‌تونه صفحهٔ یتیم یا صفحهٔ نیمه‌نوشته (torn page) بسازه.
  • راه‌حل استاندارد: write-ahead log (WAL) — فایلی فقط‌افزودنی که هر تغییر B-tree باید قبل از اعمال رو صفحات، توش نوشته بشه؛ بعد از crash، لاگ برای برگردوندن درخت به حالت سازگار بازپخش می‌شه. معادلش تو فایل‌سیستم‌ها journaling نام داره.
  • برای کارایی، صفحات تو حافظه بافر می‌شن؛ WAL تضمین می‌کنه تا وقتی داده با fsync رو دیسک رفته، بعد از crash قابل بازیابیه.
  • واریانت‌ها: copy-on-write (مثل LMDB — صفحهٔ تغییرکرده تو جای تازه نوشته می‌شه و والد جدید ساخته می‌شه؛ برای concurrency control هم مفیده)، کلیدهای مختصر تو صفحات داخلی (عامل انشعاب بیشتر، عمق کمتر)، چیدمان ترتیبی برگ‌ها رو دیسک برای اسکن سریع، و pointer خواهر/برادر بین برگ‌ها.
  • A B-tree’s basic operation is rewriting one page in place (unlike LSM, which only appends). Multi-page rewrites (like splits) are dangerous: a mid-work crash can create orphaned or half-written (torn) pages.
  • The standard fix: a write-ahead log (WAL) — an append-only file where every B-tree change must be recorded before touching the pages; after a crash the log is replayed to restore a consistent tree. The filesystem equivalent is called journaling.
  • For performance, pages are buffered in memory; the WAL guarantees that once data reached disk with fsync, it is recoverable after a crash.
  • Variants: copy-on-write (e.g. LMDB — a changed page is written to a fresh location with new parents; also handy for concurrency control), abbreviated keys in internal pages (higher branching factor, shallower depth), sequential leaf layout on disk for fast scans, and sibling pointers between leaves.

ثبتِ تغییر و پایدار کردن لاگ و نوشتن صفحه‌ها لزوماً هم‌زمان نیستن. مهمه تأییدِ موفقیت با تضمین ماندگاریِ انتخاب‌شده جور باشه.

مثال فنی: Crash وسطِ split

وضعیت اولیه: فرض کن دو تا صفحهٔ تازه ساخته شدن، ولی به‌روزرسانی والد هنوز رو دیسک نرفته. نصفه کاره!

اجرای مرحله‌به‌مرحله: حالا رکوردهای بازیابی موتور مشخص می‌کنن split چطور تکمیل یا اصلاح بشه. صرف نوشتن جداگانهٔ چند صفحه کافی نیست.

نتیجه و دلیل: پس ساختار درخت هم باید پس از crash معتبر بمونه. ماندگاری فقط حفظ مقدار یه رکورد نیست — اسکلت هم باید سرپا بمونه.

In-place page rewrites are the B-tree’s strength and its biggest danger at once: if power dies mid-write of a page, the disk holds neither a healthy old version nor a complete new one — a torn page. The fix is the same strict rule as before: before touching the page itself, write the change record to the write-ahead log. The log is append-only and log writes are sequential; so we fill the log first, then calmly rewrite the page with random writes.

ولی «تو لاگ نوشتن» به‌تنهایی کافی نیست: تا وقتی fsync برنگشته، رکورد فقط تو کشِ سیستم‌عامله و یه crash ساده اون رو می‌بلعه. مرزِ واقعیِ ماندگاری (durability) لحظه‌ایه که fsync با موفقیت برمی‌گرده؛ بعدش حتی اگه صفحه هرگز رو دیسک نوشته نشه، ریکاوری می‌تونه با redo — بازپخشِ رو به جلوِ لاگ — همه‌چی رو برگردونه، البته به شرطی که این بازپخش idempotent باشه، چون ممکنه دوبار اجرا بشه.

But “writing to the log” alone is not enough: until fsync returns, the record sits only in the OS cache and a plain crash swallows it. The real durability boundary is the moment fsync returns successfully; after that, even if the page never reaches disk, recovery can bring everything back with redo — forward replay of the log — provided the replay is idempotent, since it may run twice.

این نمودار چهار تا خط (lane) افقی داره که از بالا به پایین عنوان‌شون اینه: «Write path»، «Buffers and caches»، «Crash recovery» و «Terminal». پنج تا حالتِ خطِ اول شمارهٔ گام دارن — «01» تا «05» — و مسیرِ عادیِ نوشتن رو می‌سازن؛ سه تا حالتِ دیگه مسیرهای شکست و بازیابی‌ان.

This state machine has four lanes — Write path, Buffers and caches, Crash recovery, Terminal — with five numbered states (01–05) forming the normal write path, plus three failure/recovery states.

مسیرِ اصلی رو قدم‌به‌قدم برو. از «Dirty Page» شروع کن: زیرنویسش «modified in memory» و برچسبِ کنارش «not on disk yet» — یعنی صفحه تو حافظه تغییر کرده ولی هنوز چیزی رو دیسک نیست. فلشِ «append to log» اون رو به «WAL Appended» می‌رسونه (زیرنویس: «log entry written first»، برچسب: «sequential write»). فلشِ بعدی «fsync»ـه و به «WAL Synced» می‌رسه — حالتِ لوزی‌شکلِ مسیر با زیرنویسِ «fsync returns» و برچسبِ «now durable» — و این همون مرزِ ماندگاریه. از اونجا فلشِ «later, in background» به «Page Written» می‌ره (زیرنویس: «update in place on disk»، برچسب: «random write») و سرانجام فلشِ «periodically» به «Checkpoint» می‌رسه (زیرنویس: «old log discarded»، برچسب: «restart is fast»).

Walk the main path: Dirty Page (modified in memory, not on disk yet) → append to log → WAL Appended (sequential write) → fsync → the diamond WAL Synced (now durable) — the durability boundary — then later, in background to Page Written (random write) and periodically to Checkpoint (old log discarded, restart is fast).

حالا فلش‌های چین‌چینِ شکست. از «WAL Appended» فلشِ چین‌چینِ «crash before fsync» پایین میاد، به خطِ «Buffers and caches» و حالتِ «Unsynced Write» با زیرنویسِ «still in the OS cache» و برچسبِ «power loss loses it». از اونجا فلشِ «nothing to recover» به خطِ «Terminal» و حالتِ «Write Lost» می‌ره (زیرنویس: «never reached the disk»، برچسب: «rolled back»). این تنها مسیرِ بدونِ بازگشتِ شکله: تا قبل از fsync، یعنی تو دنیای کش‌ها، crash به معنی ازدست‌دادنِ همون نوشتنه.

Failure arrows: crash before fsync drops from WAL Appended to Unsynced Write (still in the OS cache, power loss loses it), then nothing to recover to the terminal Write Lost (rolled back) — the figure’s only one-way path: before fsync, a crash means losing that write.

سمتِ دیگهٔ مرز، بازیابیـه: از «WAL Synced» فلشِ چین‌چینِ «crash after fsync» پایین میاد به خطِ «Crash recovery» و حالتِ «Redo from WAL» با زیرنویسِ «roll forward on startup» و برچسبِ «idempotent replay»؛ بعد فلشِ پررنگِ «recovery completes» اون رو به همون «Checkpoint» برمی‌گردونه. دقت کن: مسیرِ بازیابی دقیقاً تو همون حالتی تموم می‌شه که مسیرِ عادی — یعنی هرچی با fsync ماندگار شده باشه، بعد از crash هم به مقصد می‌رسه.

Past the boundary lies recovery: crash after fsync falls to Redo from WAL (roll forward on startup, idempotent replay), and recovery completes returns to the same Checkpoint the normal path reaches — whatever fsync made durable gets home after a crash.

آخرین مسیرِ شکست از «Page Written» شروع می‌شه: فلشِ «crash mid-write» به حالتِ «Torn Write» تو خطِ «Terminal» می‌ره — زیرنویسِ «checksum mismatch» و برچسبِ «partial page on disk» — یعنی صفحه‌ای نیمه‌قدیمی و نیمه‌جدید که فقط checksum رو صفحه و بلاگِ لاگ می‌تونه آشکارش کنه. ولی این حالتِ پایانی نیست: فلشِ پررنگِ «rewrite from log» اون رو به «Redo from WAL» برمی‌گردونه و صفحه از روِ لاگِ ماندگار دوباره نوشته می‌شه.

The last failure starts at Page Written: crash mid-write leads to Torn Write (checksum mismatch, partial page on disk) — a half-old, half-new page only page and log checksums can expose. But it is not terminal: rewrite from log returns to Redo from WAL and the page is rewritten from the durable log.

درسِ این ماشینِ وضعیت رو تو یه قانون جمع کن: «اول لاگ، بعد صفحه»؛ و مرزِ ماندگاری فقط لحظه‌ایه که fsync با موفقیت برمی‌گرده. نوشتنِ لاگ sequential و ارزونه، بازنویسیِ صفحه random و خطرناک؛ پس هرگز دومی رو بدونِ اولی شروع نکن.

Sum the state machine into one rule: “log first, page second”; durability begins only when fsync returns. Log writes are sequential and cheap, page rewrites random and dangerous — never start the second without the first.

و چند تا نکته که باید بمونه: fsync همیشه راست نمی‌گه — بعضی سیستم‌عامل‌ها پیش از ماندگاریِ واقعی موفقیت گزارش کردن و بعضی SSDها تو تست‌های قطعِ برق دروغ گفتن — پس checksum رو هر صفحه و هر بلاگِ لاگ، فسادِ خاموش رو به خطایِ قابل‌تشخیص تبدیل می‌کنه. بازپخشِ لاگ باید idempotent باشه چون ممکنه دوبار اجرا بشه، و checkpoint هم حجمِ بازپخشِ ری‌استارت رو محدود می‌کنه و هم اجازه می‌ده سگمنت‌های قدیمیِ لاگ دور ریخته بشن. و یادت باشه WAL مخصوصِ B-tree نیست: موتورهای LSM برای بازیابیِ crash معمولاً بهش نیاز ندارن (چون memtable به‌صورت فایلِ مرتب flush می‌شه) و جایگزینِ کلاسیکِ اون، shadow paging با تعویضِ اتمیِ ریشه‌ست.

And a few things to keep: fsync doesn’t always tell the truth — some OSes reported success before real durability and some SSDs lied in power-cut tests — so checksums on every page and log block turn silent corruption into detectable errors. Log replay must be idempotent (it may run twice), checkpoints bound restart replay and let old log segments go, and the WAL isn’t B-tree-only: LSM engines usually don’t need it for crash recovery (the memtable flushes as a sorted file), and its classic alternative is shadow paging with an atomic root swap.

قاعدهٔ تجربیRule of thumb

B-tree و LSM هر دو برای خوندن و نوشتن طراحی شدن، ولی هزینه‌ها رو متفاوت توزیع می‌کنن. انتخاب به الگوی واقعیِ بار و رفتار موقع ادغام و افزایش داده وابسته‌ست.

اجرای مرحله‌به‌مرحله: حالا LSM نوشتن‌ها رو جمع می‌کنه و هزینهٔ compaction می‌ده؛ B-tree صفحه‌ها رو به‌روز می‌کنه و ساختار خوندن مرتب داره.

نتیجه و دلیل: پس انتخاب با اندازه‌گیری write/read/space amplification و tail latency رو همون بار انجام می‌شه. برندهٔ ثابت نداریم — اندازه بگیر، حدس نزن.

LSM fits write-heavy workloads better, B-trees read faster. But benchmarks are extremely sensitive to workload details; for a serious claim you must test with your own workload. And it isn’t either/or — some engines are hybrids (e.g. several B-trees merged LSM-style).

On HDD the reason is mechanical (head movement takes milliseconds). On SSD: flash can be read/written page by page (usually 4KB) but only erased block by block (usually 512KB). Before erasing, valid pages must be relocated (garbage collection). Sequential writes keep blocks uniform (later the whole block is erased at once); random writes pollute blocks, GC grows, and it costs both bandwidth and extra flash wear.

نکتهٔ بنچ‌مارکBenchmarking note
نوشتن رو یه LSMِ خالی گول‌زننده‌ست: هنوز compactionی در کار نیست و همهٔ پهنای باندِ دیسک مالِ نوشتنه. آزمایش رو اون‌قدر طولانی کن که compaction واقعاً وارد بازی بشه و write amplification خودش رو نشون بده.

Writing to an empty LSM is deceptive: no compaction is running yet and all disk bandwidth belongs to writes. Run the test long enough for compaction to really join the game and for write amplification to show itself.

۴.۱ ایندکس‌های ثانویه4.1 Secondary indexes

  • تا این‌جا فقط ایندکسِ کلید-مقدار (مثل کلید اصلی) داشتیم. ایندکس ثانویه (با CREATE INDEX) اجازه می‌ده رو ستون‌های دیگه هم جست‌وجو کنی — مثلاً همهٔ ردیف‌های یه user_id.
  • تفاوت: مقدارهای ایندکس‌شده لزوماً یکتا نیستن. دو تا راه‌حل: هر مقدار = فهرستی از شناسه‌های رکورد (مثل postings list) یا یکتا کردنِ هر ورودی با چسبوندن شناسهٔ ردیف. هم B-tree و هم LSM می‌تونن ایندکس ثانویه بسازن.
  • داده کجا باشد؟ سه الگو:
  • So far we only had key-value indexes (like the primary key). A secondary index (via CREATE INDEX) lets you search other columns too — e.g. all rows of one user_id.
  • The difference: indexed values aren’t necessarily unique. Two fixes: each value = a list of record IDs (like a postings list), or make each entry unique by appending the row ID. Both B-trees and LSM can build secondary indexes.

مثال فنی: حافظه و ماندگاری مستقل‌اند

وضعیت اولیه: فرض کن کل مجموعهٔ فعال 4 GBـه و تو RAM جا می‌شه. همه تو حافظه!

اجرای مرحله‌به‌مرحله: حالا خوندن از حافظه سریعه، ولی خاموشی RAM رو پاک می‌کنه. WAL پایدار یا replica طبق تضمین موردنیاز باید تغییرها رو حفظ کنه.

نتیجه و دلیل: پس in-memory بودن فقط محل اصلی خدمت‌دهی رو می‌گه. دربارهٔ دوام داده به‌تنهایی چیزی ثابت نمی‌کنه — سرعت داری، ولی دوام رو باید جدا بخری.

  • همهٔ ساختارهای این فصل پاسخی به نارسایی‌های دیسک بودن: دیسک با دو تا مزیتِ بزرگ تحمل می‌شه — پایداری (با قطع برق از بین نمی‌ره) و هزینهٔ هر گیگابایتِ کمتر از RAM.
  • با ارزون شدن RAM، خیلی از داده‌ها کوچیکن و کامل تو حافظه جا می‌شن ← پایگاه‌های داده درون‌حافظه‌ای. بعضی فقط cache‌ان (مثل Memcached — از دست رفتن داده با restart قبوله)؛ بعضی دوام می‌خوان: سخت‌افزار ویژه (RAM با باتری) یا متداول‌تر، نوشتن لاگ تغییرات/اسنپ‌شات دوره‌ای رو دیسک یا تکثیر وضعیت به ماشین‌های دیگه.
  • با وجود نوشتن رو دیسک، باز هم «درون‌حافظه‌ای» حساب می‌شن چون دیسک فقط لاگِ دوامه و خوندن کلاً از حافظه سرویس می‌شه. مزیت عملیاتی هم داره: فایل رو دیسک قابل backup و تحلیل با ابزار بیرونیه.
  • نمونه‌ها: VoltDB و SingleStore و Oracle TimesTen (رابطه‌ای، ادعای بهبود بزرگ با حذفِ سربارِ ساختارهای دیسکی)، RAMCloud (key-value با دوام و رویکرد log-structured)، Redis و Couchbase (دوام ضعیف، نوشتن ناهمزمان).
  • نکتهٔ ضدشهود: سرعتِ این پایگاه داده‌ها از «نخوندن از دیسک» نمیاد — موتور دیسکی هم با حافظهٔ کافی شاید هرگز به دیسک نزنه (cache سیستم‌عامل). علت واقعی، حذفِ سربارِ کدگذاریِ ساختارهای حافظه به قالبِ قابل‌نوشتن رو دیسکـه.
  • علاوه بر سرعت، مدل‌های دادهٔ غیرمتعارف رو هم راحت می‌کنن: مثلاً Redis رابطِ پایگاه داده‌مانند رو صفِ اولویت‌دار و مجموعه و ... می‌ده؛ چون همه‌چی تو حافظه‌ست، پیاده‌سازی این ساختارها ساده می‌مونه.
  • Every structure in this chapter answers the shortcomings of disk: disks are tolerated for two big virtues — durability (no power-cut loss) and lower cost per gigabyte than RAM.
  • As RAM got cheaper, much data is small enough to fit entirely in memory → in-memory databases. Some are just caches (e.g. Memcached — losing data on restart is acceptable); some want durability: special hardware (battery-backed RAM) or, more commonly, writing a change log / periodic snapshots to disk or replicating state to other machines.
  • Despite writing to disk they still count as “in-memory” because the disk is only a durability log and reads are served entirely from memory. There is an operational bonus too: the on-disk file can be backed up and analyzed with outside tools.
  • Examples: VoltDB, SingleStore and Oracle TimesTen (relational, claiming big wins by dropping on-disk-structure overhead), RAMCloud (durable key-value with a log-structured approach), Redis and Couchbase (weak durability, async writes).
  • Counter-intuitive point: these databases aren’t fast because they “don’t read from disk” — an on-disk engine with enough memory might never touch disk either (OS cache). The real cause is dropping the overhead of encoding in-memory structures into a disk-writable format.
  • Beyond speed, they also ease unconventional data models: e.g. Redis offers a database-like interface over priority queues, sets and more; with everything in memory these structures stay simple to implement.

اجرای مرحله‌به‌مرحله: حالا چیدمان ردیفی می‌تونه دادهٔ ستون‌های بی‌نیاز رو هم وارد I/O کنه؛ چیدمان ستونی فقط ستون‌های لازم رو جدا می‌خونه.

نتیجه و دلیل: پس برای اسکن تحلیلی حجم خوندن کم می‌شه. ولی بازسازی یه ردیف کامل ممکنه به چند تا ستون نیاز داشته باشه — هر چیدمان یه بده‌بستون داره.

A data warehouse’s data model is usually relational, because SQL answers analytical queries well: graphical analysis tools generate SQL, visualize results, and let analysts drill down and slice.

  • ظاهر انبارداده و پایگاه داده تراکنشی شبیهه (هر دو SQL دارن) ولی درون‌شون خیلی متفاوته: برای الگوهای کوئریِ کاملاً متفاوت بهینه شدن. بیشتر فروشنده‌ها حالا یا تراکنش رو پشتیبانی می‌کنن یا تحلیل رو، نه هر دو رو.
  • HTAP (hybrid transactional/analytical processing) مثل SQL Server و SAP HANA و SingleStore هر دو رو تو یه محصول داره، ولی عملاً به دو تا موتورِ ذخیره‌سازی و کوئریِ جدا با یه رابط SQLِ مشترک تبدیل می‌شن.
  • A warehouse and a transactional database look alike (both speak SQL) but are very different inside: each is optimized for a completely different query pattern. Most vendors now support either transactions or analytics — not both.
  • HTAP (hybrid transactional/analytical processing) like SQL Server, SAP HANA and SingleStore ships both in one product, but in practice becomes two separate storage and query engines behind one shared SQL interface.

The lesson: each box keeps a separate role — the query engine “how”, the storage format “how bytes”, the table format “which files = which table”, the catalog “which tables exist”. That very separation is what made independent scaling, time travel and data governance possible.

۷7ذخیره‌سازی ستونیColumnar storage

ذخیره‌سازی ستونی، مقدارهای هر ستون رو کنار هم نگه می‌داره. این کار برای اسکنِ چند تا ستون از جدول بزرگ و فشرده‌سازیِ مقدارهای مشابه مناسبه.

مثال فنی: فشرده‌سازیِ ستون مشابه

وضعیت اولیه: فرض کن ستون country تو یه بلوک هزار تا مقدار تکراری IR داره. همه یکی!

اجرای مرحله‌به‌مرحله: حالا encoding فرهنگ‌نامه‌ای می‌تونه IR رو با یه کد نشون بده و run-length طول تکرار رو ثبت کنه.

نتیجه و دلیل: پس دادهٔ هم‌نوع و مشابه بهتر فشرده می‌شه. این سود با مخلوط شدن همهٔ فیلدهای یه ردیف کمتر قابل‌استفاده‌ست — همسایهٔ خوب، فشردهٔ خوب.

Real fact tables in a warehouse are often 100+ columns wide, yet a typical analytical query wants only 4–5 columns (SELECT * is rarely needed in analytics). The book’s example:

SELECT dim_date.weekday, dim_product.category,
       SUM(fact_sales.quantity) AS quantity_sold
FROM fact_sales
JOIN dim_date    ON fact_sales.date_key   = dim_date.date_key
JOIN dim_product ON fact_sales.product_sk = dim_product.product_sk
WHERE dim_date.year = 2024
  AND dim_product.category IN ('Fresh fruit', 'Candy')
GROUP BY dim_date.weekday, dim_product.category;
تو ذخیره‌سازی ردیف‌محور (رایج تو OLTP و پایگاه‌های داده سندی) همهٔ مقادیرِ یه ردیف کنار هم‌ان؛ حتی با ایندکس، موتور باید کل ردیف‌های (۱۰۰+ صفتیِ) منطبق رو بارگذاری و تجزیه و فیلتر کنه — کند.

In row-oriented storage (common in OLTP and document databases) all values of a row sit together; even with indexes the engine must load, parse and filter whole (100+-attribute) matching rows — slow.

ایده: ستون‌ها را کنار هم بچینThe idea: lay columns side by side

  • ذخیره‌سازی ستونی (columnar): به‌جای یه ردیف، همهٔ مقادیر هر ستون کنار هم ذخیره می‌شن؛ پس کوئری فقط ستون‌های استفاده‌شده رو می‌خونه و تجزیه می‌کنه.
  • بازسازی ردیف: چون همهٔ ستون‌ها ردیف‌ها رو به یه ترتیب نگه می‌دارن، مؤلفهٔ k امِ هر ستون = ردیفِ k ام.
  • در عمل کلِ ستونِ تریلیون‌ردیفی یه‌جا نیست: جدول به بلوک‌هایی از هزاران/میلیون‌ها ردیف شکسته می‌شه و چون کوئری‌ها معمولاً بازهٔ تاریخی دارن، هر بلوک معمولاً یه بازهٔ زمانیه. کوئری فقط بلوک‌های هم‌پوشانِ بازه و فقط ستون‌های لازم رو می‌خونه.
  • این چیدمان تقریباً تو همهٔ پایگاه‌های داده تحلیلیِ امروز هست: از Snowflake گرفته تا DuckDB و Pinot و Druid؛ فرمت‌های Parquet و ORC و Lance و Nimble و قالب‌های درون‌حافظه‌ای مثل Arrow و Pandas/NumPy؛ و بعضی پایگاه‌های داده سری زمانی (InfluxDB IOx، TimescaleDB). Parquet حتی مدل سندی رو هم پشتیبانی می‌کنه (تکنیک shredding از Dremel).
  • ستون‌ها رو می‌شه فشرده کرد؛ چون ستون‌ها معمولاً تکرارِ زیادی دارن (میلیاردها تراکنش، ۱۰۰ هزار محصولِ متمایز). روش شاخص: bitmap encoding — برای هر مقدارِ متمایز یه bitmap با یه بیت به‌ازای هر ردیف. bitmapهای تنک رو run-length encoding می‌کنن و روش‌هایی مثل roaring bitmaps بین دو نمایش، فشرده‌تر رو برمی‌گزینن.
  • Columnar storage: instead of one row, all values of each column are stored together; so a query reads and parses only the columns it uses.
  • Row reconstruction: since every column keeps rows in the same order, the k-th element of each column = the k-th row.
  • In practice a trillion-row column never sits in one place: the table is split into blocks of thousands/millions of rows, and since queries usually span a date range, each block is typically one time slice. A query reads only overlapping blocks and only needed columns.
  • This layout is in almost every analytical database today: from Snowflake to DuckDB, Pinot and Druid; formats like Parquet, ORC, Lance and Nimble plus in-memory layouts like Arrow and Pandas/NumPy; and some time-series databases (InfluxDB IOx, TimescaleDB). Parquet even supports the document model (the shredding technique from Dremel).
  • Columns can be compressed; columns usually repeat a lot (billions of transactions, 100k distinct products). The flagship method: bitmap encoding — one bitmap per distinct value with one bit per row. Sparse bitmaps get run-length encoding, and methods like roaring bitmaps pick the denser of the two representations.

مثال فنی: فقط مبلغ‌ها را بخوان

وضعیت اولیه: فرض کن ردیف‌ها شامل id, address, description, amount هستن.

اجرای مرحله‌به‌مرحله: حالا برای SUM(amount) موتور ستونی فقط بلوک مبلغ رو می‌خونه و نشونی و توضیح رو کنار می‌ذاره. فقط همون که لازمه!

نتیجه و دلیل: پس سود از کمتر خوندن میاد. اگه query همهٔ ستون‌های یه ردیف رو بخواد، همین مزیت الزاماً برقرار نیست — معجزهٔ همیشگی نداریم.

Don’t confuse column-oriented with wide-column (column-family)! The wide-column model (e.g. Bigtable, Accumulo, HBase) lets each row hold thousands of different columns, but its storage is row-oriented (each row’s values sit together). Only the names are alike.

ترتیب مرتب‌سازی و نوشتنSort order and writes

ترتیب فیزیکی داده کمک می‌کنه بخش‌های نامربوط خونده نشن. ولی درج و به‌روزرسانیِ پراکنده تو فایل‌های مرتب هزینه داره و اغلب با بافر و ادغام مدیریت می‌شه.

مثال فنی: مرتب‌سازی و بلوک تازه

وضعیت اولیه: فرض کن بلوک‌های فروش بر اساس day مرتب‌ان و هر بلوک حداقل و حداکثر روز رو داره. قفسه‌بندی منظمه.

اجرای مرحله‌به‌مرحله: حالا فیلتر یه روز، بلوک‌های خارج از بازه رو رد می‌کنه؛ دادهٔ تازه اول جدا نوشته و بعد مرتب و ادغام می‌شه.

نتیجه و دلیل: پس sort order به data skipping کمک می‌کنه. ولی حفظ این نظم موقع نوشتن هزینه داره — نظم مجانی نیست.

  • ترتیبِ ردیف‌ها مهم نیست (ساده: همون ترتیب درج)، ولی می‌شه مرتب‌سازی انتخابی کرد و ازش به‌عنوان ایندکس بهره برد. نکته: ستون‌ها رو نمی‌شه مستقل مرتب کرد (ارتباط k ام‌ها می‌شکنه)؛ باید کلِ ردیف مرتب بشه هرچند ستونی ذخیره می‌شه.
  • کلیدِ مرتب‌سازی اول (مثلاً date_key) برای بازه‌های تاریخی؛ کلید دوم (مثلاً product_sk) برای گروه‌بندیِ درون همون روز. امتیاز جانبی: مرتب‌سازی، تکرارهای طولانی می‌سازه و فشرده‌سازیِ run-length رو حتی برای جدولِ میلیاردی چند کیلوبایتی می‌کنه (بیشترین اثر رو کلید اول).
  • نوشتن تو انبارداده معمولاً ورود دسته‌ای (ETL)ـه؛ درجِ تک‌ردیفی وسطِ جدولِ مرتب و فشرده خیلی ناکارآمده (باید از محل درج به بعد بازنویسی بشه). راه‌حل، باز هم رویکرد log-structured: نوشتن‌ها اول به یه فروشگاهِ ردیف‌محورِ مرتبِ درون‌حافظه‌ای می‌رن و بعد دسته‌ای با فایل‌های ستونیِ رو دیسک ادغام و تو فایل‌های تازه نوشته می‌شن؛ چون فایل‌ها تغییرناپذیرن، object storage جای خوبیه.
  • کوئری باید دادهٔ رو دیسک و نوشتن‌های اخیرِ درون حافظه رو با هم ببینه؛ موتور اجرا این تفکیک رو از کاربر پنهون می‌کنه. (Snowflake و Vertica و Pinot و Druid و ...)
  • Row order doesn’t matter (simplest: insertion order), but you may sort selectively and use it as an index. Catch: columns can’t be sorted independently (the k-th-element links would break); the whole row must be sorted even though it is stored column by column.
  • The first sort key (e.g. date_key) serves date ranges; the second (e.g. product_sk) groups within the same day. Side bonus: sorting builds long repetition runs and makes run-length compression shrink even billion-row tables to kilobytes (strongest effect on the first key).
  • Warehouse writes are usually batch ingest (ETL); single-row inserts into the middle of a sorted, compressed table are very inefficient (everything from the insert point on must be rewritten). The fix is the familiar log-structured approach: writes first land in a sorted in-memory row store, then batch-merge with on-disk columnar files into fresh files; since files are immutable, object storage is a good home.
  • A query must see on-disk data and recent in-memory writes together; the execution engine hides that split from the user. (Snowflake, Vertica, Pinot, Druid and more.)

مثال فنی: برداری در برابر کامپایل

وضعیت اولیه: فرض کن query باید یه میلیون مبلغ رو جمع کنه. یه میلیون!

اجرای مرحله‌به‌مرحله: حالا اجرای برداری دسته‌های مثلاً ۱۰۲۴تایی رو به عملگر می‌ده؛ کامپایل منطق query رو به کد اجرایی تخصصی تبدیل می‌کنه. دو تا ترفند جدا.

نتیجه و دلیل: پس یکی شکل پردازش دسته‌ای مقدارهاست و دیگری روش اجرای منطق. می‌شه هر دو رو هم‌زمان داشت — چرا یکیشون؟ هر دو!

  • کوئریِ تحلیلی به طرحی از operatorها شکسته می‌شه که ممکنه رو چند تا ماشین موازی بشن. ساده‌ترین اجرا «مفسر»ـه: تو حلقهٔ رو هر ردیف، ساختارِ کوئری چک می‌شه — برای تحلیلِ میلیون‌ردیفی کنده. دو تا رویکرد کارآمد:
  • Query compilation: موتور از SQL کد تولید می‌کنه (حلقهٔ ردیف‌ها، مقایسه‌ها، کپیِ مقادیر منطبق) و اون رو با کامپایلری مثل LLVM به کد ماشین تبدیل و اجرا می‌کنه — مشابه JIT تو JVM.
  • Vectorized processing: تفسیری می‌مونه، ولی به‌جای ردیف‌به‌ردیف، رو دسته‌ای از مقادیرِ یه ستون کار می‌کنه. مثال: اپراتور تساوی رو ستونِ product_sk و شناسهٔ «موز» یه bitmap برمی‌گردونه؛ همون اپراتور برای فروشگاه bitmap دوم؛ و اپراتور AND بیتی دو تا bitmap رو ترکیب می‌کنه (چون مؤلفهٔ k ام هر دو = همون ردیف).
  • هر دو از خصوصیات CPU امروزی بهره می‌برن: دسترسیِ ترتیبی به حافظه (cache miss کمتر)، حلقه‌های داخلیِ تنگ (pipeline شلوغ، پیش‌بینیِ شاخه کمتر)، موازی‌سازی با چند تا thread و دستورهای SIMD، و کار مستقیم رو دادهٔ فشرده بدون رمزگشایی.
  • An analytical query breaks into a plan of operators that may parallelize across machines. The simplest execution is an “interpreter”: loop over each row, check the query structure — slow for million-row analytics. Two efficient approaches:
  • Query compilation: the engine generates code from the SQL (row loops, comparisons, copying matches) and compiles it with something like LLVM into machine code — similar to JIT in the JVM.
  • Vectorized processing: stays interpreted, but works on batches of one column’s values instead of row by row. Example: an equality operator on product_sk for the “banana” id returns one bitmap; the same operator for the store returns a second; and a bitwise AND operator combines them (since the k-th element of both = the same row).
  • Both exploit modern CPUs: sequential memory access (fewer cache misses), tight inner loops (busy pipelines, fewer branch mispredicts), multi-thread parallelism and SIMD instructions, and working directly on compressed data without decoding.

وضعیت اولیه: فرض کن ردیف‌ها شامل id, address, description, amount هستن.

اجرای مرحله‌به‌مرحله: حالا برای SUM(amount) موتور ستونی فقط بلوک مبلغ رو می‌خونه و نشونی و توضیح رو کنار می‌ذاره. فقط همون که لازمه!

نتیجه و دلیل: پس سود از کمتر خوندن میاد. اگه query همهٔ ستون‌های یه ردیف رو بخواد، همین مزیت الزاماً برقرار نیست — معجزهٔ همیشگی نداریم.

چهار تا ستون داریم: «Source Table»، «Column Layout»، «Compression» و «Execution». تو نوار بالا، جعبهٔ «Fact Table» با زیرنویسِ «billions of rows, wide table» نشسته؛ فلش پررنگِ «split into blocks by date range» اون رو به «Column Blocks» می‌رسونه — جعبه‌ای با زیرنویسِ «one column per block» و برچسبِ «sorted by date_key».

Four columns: Source Table, Column Layout, Compression, Execution. Top lane: Fact Table (billions of rows, wide table); the bold split into blocks by date range leads to Column Blocks (one column per block, sorted by date_key).

نوار پایین، قصدِ کوئریـه: جعبهٔ «SQL Query» با زیرنویسِ «3 of 100 columns». فلش پررنگِ «column pruning: load 3 of 100» از اون به بالا، به Column Blocks می‌ره — همون لحظه‌ای که ۹۷ تا ستونِ دیگه اصلاً خونده نمی‌شن. فلشِ «encode low-cardinality columns» از Column Blocks به جعبهٔ «Bitmap + RLE» (زیرنویس: «one bitmap per value»، برچسب: «sparse bits counted») می‌ره.

Bottom lane is the query’s intent: SQL Query (3 of 100 columns). The bold column pruning: load 3 of 100 rises to Column Blocks — the moment 97 other columns are never read. Then encode low-cardinality columns goes to Bitmap + RLE (one bitmap per value).

بعد فلشِ «bitwise AND of filter bitmaps» به «Vectorized Filter» با زیرنویسِ «equality + bitwise AND» و برچسبِ «SIMD batches»؛ از اون فلشِ «matching row indexes» به پایین، به «Aggregation» (زیرنویس: «SUM by weekday, category») می‌ره و در نهایت فلش چین‌چینِ «GROUP BY + SUM» از همون SQL Query به Aggregation، مشخصاتِ تجمیع رو می‌رسونه.

Next bitwise AND of filter bitmaps reaches Vectorized Filter (equality + bitwise AND, SIMD batches); matching row indexes drops to Aggregation (SUM by weekday, category), and the dashed GROUP BY + SUM from the SQL Query supplies the aggregation spec.

درسِ شکل: دو تا جریان موازی می‌بینی — جریانِ بالا دادهـه که لایه‌به‌لایه فشرده و آماده می‌شه، و جریانِ پایین نیتِ کوئری که تعیین می‌کنه کدوم بلوک‌ها و کدوم بیت‌ها وارد بازی بشن. نقطهٔ اوج، Vectorized Filterـه: به‌جای گشتنِ ردیف‌به‌ردیف، یه AND بیتی رو دسته‌های بزرگ.

The lesson: two parallel flows — the upper flow is data, compressed and staged layer by layer, and the lower flow is the query’s intent, deciding which blocks and bits join the game. The climax is the Vectorized Filter: one bitwise AND over big batches instead of row-by-row hunting.

نماهای materialized و مکعب داده (data cube)Materialized views and the data cube

نمای ازپیش‌حساب‌شده نتیجهٔ یه پرس‌وجو رو ذخیره می‌کنه. مکعب داده، خلاصه‌ها رو تو چند تا بُعد و سطح آماده می‌کنه؛ خوندن سریع‌تر می‌شه ولی نگه‌داریِ خلاصه‌ها هزینه داره.

مثال فنی: نمای آمادهٔ فروش روزانه

وضعیت اولیه: فرض کن sales_by_day برای امروز جمع 1000 داره و سفارش تازه مبلغ 200 داره.

اجرای مرحله‌به‌مرحله: حالا نگهدارندهٔ نما مقدار رو به 1200 می‌رسونه؛ اصلاح یا حذف همون سفارش هم باید تغییر معکوس مناسب اعمال کنه.

نتیجه و دلیل: پس خوندن گزارش سریع‌تر می‌شه. ولی هزینهٔ نگه‌داری نما و کنترل شمارش دوباره به مسیر تغییر منتقل می‌شه — خرج از جیب خوندن، از جیب نوشتن.

  • View مجازی فقط میان‌برِ نوشتن کوئریـه و موقع خوندن به کوئریِ زیرین باز می‌شه؛ view materialized یه کپیِ واقعی از نتیجهٔ کوئریه که رو دیسک نوشته می‌شه. وقتی دادهٔ زیرین عوض بشه باید به‌روز بشه (بعضی پایگاه داده‌ها خودکار؛ سیستم‌هایی مثل Materialize تو همین تخصصی‌ان). هزینه رو نوشتن، بهبود رو خوندنِ تکراری.
  • Materialized aggregate نوعی از اونه: اگه همون COUNT/SUM/AVG ها تکرار می‌شن، چرا هر بار دادهٔ خام رو نسابیم؟ مکعب داده (OLAP cube) شبکه‌ای از تجمیعهاست که بر اساس بُعدها گروه‌بندی شده: مثلاً تاریخ تو یه محور و محصول تو محور دیگه، و هر خونه = SUM برای اون ترکیب. جمع رو هر سطر/ستون = خلاصه‌ای با یه بُعد کمتر (فروش به‌تفکیک محصول، صرف‌نظر از تاریخ).
  • با ۵ تا بُعد (تاریخ و محصول و فروشگاه و تبلیغ و مشتری) تصور hypercube سخته ولی اصل همونه. مزیت: بعضی کوئری‌ها («فروش دیروز هر فروشگاه») عملاً از پیش حساب شدن. محدودیت: انعطافِ دادهٔ خام رو نداره — مثلاً نمی‌تونی بپرسی «سهمِ فروشِ اقلام بالای ۱۰۰ دلار چقدره» اگه قیمت بُعد نباشه. به‌همین‌دلیل انبارداده‌ها دادهٔ خام رو نگه می‌دارن و مکعب رو فقط تقویت‌کنندهٔ کارایی می‌دونن.
  • A virtual view is just a query-writing shortcut, expanded into the underlying query at read time; a materialized view is a real copy of a query’s result written to disk. When underlying data changes it must be refreshed (some databases do it automatically; systems like Materialize specialize in exactly this). Cost on writes, wins on repeated reads.
  • A materialized aggregate is one flavor: if the same COUNT/SUM/AVG repeats, why grind raw data every time? A data cube (OLAP cube) is a lattice of aggregates grouped by dimensions: e.g. date on one axis, product on the other, each cell = SUM for that combo. Summing a row/column = a summary with one fewer dimension (sales per product regardless of date).
  • With 5 dimensions (date, product, store, campaign, customer) picturing the hypercube gets hard, but the principle holds. Upside: some queries (“yesterday’s sales per store”) are effectively precomputed. Limit: no raw-data flexibility — e.g. you can’t ask “what share of sales came from items over $100” if price isn’t a dimension. So warehouses keep raw data and treat the cube as a pure performance booster.

۸8ایندکس‌های چندبُعدی، متنی و برداریMultidimensional, text and vector indexes

جست‌وجوی عددی و مکانی و متنی و معنایی سؤال‌های متفاوتی‌ان. هرکدوم به ساختاری نیاز دارن که همون نوع شباهت یا محدوده رو سریع پیدا کنه.

مثال فنی: سه سؤال، سه ایندکس

وضعیت اولیه: فرض کن باید سفارش مشتری رو بیابی، سند دارای واژه رو پیدا کنی و محصول مشابه تصویر رو پیشنهاد بدی. سه تا کار، سه تا ساز.

اجرای مرحله‌به‌مرحله: حالا B-tree برای کلید مرتب، ـی inverted index برای واژه و ANN برای بردار مسیرهای متفاوت دارن. هر کدوم یه کاره.

نتیجه و دلیل: پس «ایندکس داریم» کافی نیست. نوع پرسش تعیین می‌کنه چه رابطه‌ای بین ورودی و محل داده لازمه — اول سؤال، بعد ابزار.

B-trees and LSM answer range queries over one attribute well (e.g. all names starting with L). But sometimes one attribute isn’t enough.

ایندکس چندستونی و چندبُعدیMulti-column and multidimensional indexes

ایندکس چندستونی به ترتیبِ ستون‌ها حساسه. ایندکس مکانی برای داده‌هایی مثل مختصات ساخته می‌شه تا جست‌وجوی محدوده و همسایگی رو راحت کنه.

مثال فنی: ترتیبِ ستون‌های ایندکس

وضعیت اولیه: فرض کن ایندکس (city, created_at) اول شهر و تو هر شهر زمان رو مرتب می‌کنه. ترتیب آبشاری.

اجرای مرحله‌به‌مرحله: حالا شرط شهر تهران همراه بازهٔ زمان پیوسته‌ست؛ ولی بازهٔ زمان برای همهٔ شهرها ممکنه به چند بخش یا روش دیگه‌ای نیاز داشته باشه.

نتیجه و دلیل: پس یه B-tree چندستونی جای ایندکس هندسی برای همهٔ شرط‌های دوبعدی رو نمی‌گیره — آچار فرانسه برای همهٔ پیچ‌ها نیست.

  • Concatenated index: چند تا فیلد رو به هم می‌چسبونه و کلیدِ ترکیبی می‌سازه (مثل دفتر تلفن: (lastname, firstname)). با ترتیبِ مرتب‌سازی، برای «همه با فامیلیِ X» یا «X + نامِ Y» عالیه، ولی برای «همه با نامِ Y» بی‌فایده‌ست.
  • کوئری چندبُعدی: مثال رستوران‌ها رو نقشه — جست‌وجوی مستطیلِ دیدِ کاربر با طول و عرض جغرافیایی. ایندکسِ چسبونده‌شده نمی‌تونه هر دو بازه رو هم‌زمان بده (یا بازهٔ عرض تو همهٔ طول‌ها، یا بالعکس).
  • راه‌ها: تبدیل مکان به یه عدد با space-filling curve + B-tree معمولی؛ یا ایندکس‌های تخصصی مثل R-tree و Bkd-tree که فضا رو طوری تقسیم می‌کنن که نقاطِ نزدیک تو یه زیردرخت بیفتن (PostGIS از R-tree با امکانات GiST پست‌گرس استفاده می‌کنه)؛ یا شبکه‌های منظم مثلثی/مربعی/شش‌ضلعی.
  • کاربرد فقط جغرافیایی نیست: ایندکس سه‌بُعدی رو (قرمز، سبز، آبی) برای جست‌وجوی بازهٔ رنگ تو فروشگاه، یا دو‌بُعدی رو (تاریخ، دما) برای «مشاهداتِ یه سال با دمای ۲۵ تا ۳۰ درجه».
  • Concatenated index: glues several fields into a composite key (like a phone book: (lastname, firstname)). With sort order it is great for “all with family name X” or “X + first name Y”, but useless for “all with first name Y”.
  • Multidimensional query: e.g. restaurants on a map — searching the user’s viewport rectangle with latitude and longitude. A glued index can’t serve both ranges at once (either the latitude range across all longitudes, or vice versa).
  • Options: turn location into one number with a space-filling curve + an ordinary B-tree; or specialized indexes like R-trees and Bkd-trees that split space so nearby points land in one subtree (PostGIS uses R-trees via Postgres GiST); or regular triangular/square/hexagonal grids.
  • Not only geography: a 3-D index over (red, green, blue) for color-range search in a shop, or 2-D over (date, temperature) for “observations of one year at 25–30 degrees”.

جست‌وجوی متن (Full-Text Search)Full-text search

ایندکس معکوس برای هر واژه مشخص می‌کنه تو کدوم سندها اومده. جست‌وجوی متن می‌تونه علاوه بر حضور واژه، شکل واژه و رتبهٔ نتیجه رو هم در نظر بگیره.

مثال فنی: تقاطع فهرست اسناد

وضعیت اولیه: فرض کن فهرست سیب برابر [1,3,7] و قرمز برابر [3,5,7]ـه. دو تا لیست.

اجرای مرحله‌به‌مرحله: حالا اشتراک فهرست‌ها سندهای 3,7 رو می‌ده؛ ولی برای عبارت دقیق باید موقعیت واژه‌ها هم پشت‌سرهم باشه. همسایگی مهمه!

نتیجه و دلیل: پس داشتن هر دو واژه با داشتن عبارت «سیب قرمز» یکی نیست. ایندکس باید اطلاعات لازم همون سؤال رو نگه داره — سؤال رو بفهم، بعد ایندکس بساز.

  • جست‌وجوی متن یعنی یافتن اسنادی که کلیدواژه‌ای هرجای متن‌شون هست. تو هسته، هر واژه (term) یه بُعدـه: سندِ دارایِ term مقدار ۱ و بقیه ۰ — یه کوئریِ چندبُعدی با تعدادِ ابعادِ خیلی زیاد.
  • ساختار رایج: inverted index — نگاشت از term به فهرستِ شناسهٔ اسنادِ حاویِ اون (postings list). اگه شناسه‌ها ترتیبی باشن، postings رو می‌شه با bitmap پراکنده هم نمایش داد (بیتِ n ام = سندِ n).
  • «سیب‌های قرمز» = بارگذاریِ bitmap دو تا واژه و AND بیتی‌شون — حتی با run-length هم خیلی سریعه. Lucene (مغز Elasticsearch و Solr) همین‌طور کار می‌کنه: نگاشتِ term به postings تو فایل‌هایِ مرتبِ SSTable-مانند که با همون رویکرد log-structured تو پس‌زمینه ادغام می‌شن. نوعِ GIN تو PostgreSQL هم برای متن و JSON از postings استفاده می‌کنه.
  • به‌جای شکستن به واژه‌ها، می‌شه همهٔ زیررشته‌های طول n (n-gram؛ مثلاً trigram های hello = hel, ell, lld) رو ایندکس کرد: جست‌وجوی هر زیررشتهٔ حداقل سه‌حرفی و حتی regex — به بهای حجمِ زیاد ایندکس.
  • برای غلط تایپی: Lucene می‌تونه کلماتِ با فاصلهٔ ویرایشیِ مشخص (افزودن/حذف/جایگزینیِ یه حرف) رو بیابه؛ مجموعهٔ واژه‌ها رو به‌صورت ماشینِ حالتِ متناهی رو کاراکترها (مثل trie) نگه می‌داره و به Levenshtein automaton تبدیل می‌کنه.
  • پردازشِ زبانی (زبان‌های بدون فاصله و مترادف‌ها و صرف‌ها) تخصصِ جداگانه‌ایه و خارج از دامنهٔ کتابه.
  • Text search means finding documents containing a keyword anywhere in their text. At heart, each word (term) is one dimension: a document with the term scores 1, the rest 0 — a multidimensional query with a huge number of dimensions.
  • The common structure: an inverted index — a map from term to the IDs of documents containing it (postings list). With sequential IDs, postings can also be sparse bitmaps (n-th bit = n-th document).
  • “Red apples” = load the two words’ bitmaps and bitwise AND them — very fast even with run-length. Lucene (the heart of Elasticsearch and Solr) works this way: term→postings maps in sorted SSTable-like files merged log-structured in the background. PostgreSQL’s GIN type uses postings for text and JSON too.
  • Instead of splitting into words, you can index every length-n substring (n-grams; e.g. trigrams of hello = hel, ell, lld): search any 3+-letter substring, even regex — at the cost of a huge index.
  • For typos: Lucene can find words at a given edit distance (adding/removing/replacing one letter); it keeps the word set as a finite-state machine over characters (like a trie) and converts it to a Levenshtein automaton.
  • Linguistic processing (spaceless languages, synonyms, inflections) is its own specialty and out of the book’s scope.

جست‌وجوی معنایی و بردارهاSemantic search and vectors

  • جست‌وجوی معنایی (semantic search) فراتر از مترادف و غلط تایپیه، مفهومِ سند و نیتِ کاربر رو می‌فهمه؛ بخش مهمی از کاربردهای AI مثل RAG (افزودن نتیجهٔ جست‌وجو به خروجی مدل زبانی). مثال: صفحهٔ «لغو اشتراک» باید با جست‌وجوی «چطور حسابم رو ببندم» هم پیدا بشه.
  • مدلِ embedding، سند رو به برداری از اعداد اعشاری (vector embedding) تبدیل می‌کنه: نقطه‌ای تو فضای چندبُعدی. اسنادِ از نظر معنایی شبیه، بردارهای نزدیک می‌گیرن. مثال سه‌بُعدی کتاب: صفحهٔ کشاورزی [0.38, 0.83, 0.41]، صفحهٔ سبزیجات [0.36, 0.64, 0.67] (نزدیک)، صفحهٔ اسکیمای ستاره‌ای [0.85, 0.10, -0.52] (دور). مدل‌های واقعی بیش از ۱۰۰۰ تا عدد دارن و معنای تک‌تک اعداد مهم نیست؛ فقط مختصات تو فضای انتزاعی‌ان.
  • اندازه‌گیریِ فاصله: cosine similarity (کسینوسِ زاویهٔ دو تا بردار) یا Euclidean distance (فاصلهٔ خط مستقیم). مدل‌های اولیه (Word2Vec و BERT و GPT) متنی بودن؛ بعد ویدیو/صدا/تصویر اومد و حالا مدل‌های چندحالته (multimodal) یه مدل برای چند تا نوع داده‌ان.
  • موتور جست‌وجو، کوئری رو هم به بردار تبدیل می‌کنه و با vector index دنبال نزدیک‌ترین بردارها می‌گرده. R-tree برای ابعادِ زیاد خوب کار نمی‌کنه؛ ساختارهای تخصصی:
  • Flat: همه‌چی ابتدایی؛ هر بار مقایسه با همهٔ بردارها — دقیق ولی کند.
  • IVF (inverted file): فضا به خوشه‌ها (centroid) شکسته می‌شه و کوئری فقط چند تا خوشه (تعدادِ probes) رو می‌گرده؛ سریع‌تر ولی تقریبی (ممکنه سندِ نزدیک تو خوشهٔ دیگه‌ای افتاده باشه). probes بیشتر = دقت بیشتر، سرعت کمتر.
  • HNSW (Hierarchical Navigable Small World): چند تا لایه گرافِ مجاورت؛ کوئری از لایهٔ بالایی (گره‌های کم) شروع می‌کنه، نزدیک‌ترین رو می‌یابه، به همون گره تو لایهٔ پایین‌تر می‌ره و تو گرافِ متراکم‌تر ادامه می‌ده تا لایهٔ آخر. مثل IVF تقریبیه.
  • کتابخانه‌های Faiss (چند تا واریانت از هر دو) و pgvector تو PostgreSQL (هر دو) رایج‌ان؛ جزئیات الگوریتم‌ها تو مقاله‌هاشونه.
  • Semantic search goes beyond synonyms and typos to grasp a document’s concept and the user’s intent; a big part of AI uses like RAG (feeding search results into a language model’s output). Example: the “cancel subscription” page should surface for “how do I close my account” too.
  • An embedding model turns a document into a vector of floats (vector embedding): a point in multi-dimensional space. Semantically close documents get nearby vectors. The book’s 3-D example: the farming page [0.38, 0.83, 0.41], the vegetables page [0.36, 0.64, 0.67] (nearby), the star-schema page [0.85, 0.10, -0.52] (far). Real models have 1000+ numbers and individual values don’t matter; they are just coordinates in an abstract space.
  • Distance measures: cosine similarity (cosine of the two vectors’ angle) or Euclidean distance (straight-line distance). Early models (Word2Vec, BERT, GPT) were textual; then came video/audio/image, and now multimodal models cover several data types in one.
  • The engine embeds the query too and hunts nearest vectors with a vector index. R-trees don’t work well for many dimensions; specialized structures:
  • Flat: the naive everything; compare against all vectors every time — exact but slow.
  • IVF (inverted file): space is split into clusters (centroids) and a query scans only a few clusters (probe count); faster but approximate (a nearby document may have fallen in another cluster). More probes = more accuracy, less speed.
  • HNSW (Hierarchical Navigable Small World): layered proximity graphs; the query starts at the top layer (few nodes), finds the nearest, descends to the same node in the lower layer and continues in the denser graph to the bottom. Approximate like IVF.
  • Faiss (several variants of both) and pgvector in PostgreSQL (both) are common; algorithm details live in their papers.

مثال فنی برای خواندنِ نمودار: ساختِ ایندکس جدا از سرو کردنِ کوئری

وضعیت اولیه: فرض کن یه میلیارد بردار داری و می‌خوای هم ایندکسِ ANN بسازی، هم کوئری بزنی — بدون اینکه این دوتا همدیگه رو کند کنن.

اجرای مرحله‌به‌مرحله: نوار بالا مسیرِ ساخته: K-Means توزیع‌شده مرکزها رو می‌ده، PQ Encoder اون‌ها رو به ۴۸ زیر‌بردار فشرده تبدیل می‌کنه، Fragment Writer خروجیِ immutable می‌نویسه و codebook‌ها می‌رن توی ایندکسِ فشردهٔ داخل حافظه. نوار پایین مسیرِ کوئریه: کوئری می‌ره به اسکنِ فاصلهٔ PQ روی همون ایندکس فشرده و بعد بررسیِ دقیق روی fragmentهای کامل‌دقت توی object storage.

نتیجه و دلیل: پس ساخت و سرو دو سازِ جدا دارن: کلاسترِ موقتیِ Spark نسخه‌های immutable می‌سازه و سرویسِ آنلاین فقط نسخهٔ پین‌شده رو لود می‌کنه — همین جداسازیه که اجازه می‌ده هر کدوم با سازِ خودش scale بشه. عددِ ۴۵ گیگ به‌ازای هر میلیارد بردار هم گزارشِ همون منبعه.

تو این نمودار پنج تا ایستگاه داری: «01 / Build (Spark)»، «02 / Object Store»، «03 / Parse»، «04 / Search» و «05 / Serve». نوار بالا مسیر آفلاینِ ساخته و نوار پایین مسیر آنلاینِ کوئریه؛ وسطشون دو تا ذخیره‌ست: «Compressed Index» و «Vector Fragments». ایدهٔ کل شکل یه جمله‌ست: ساخت ایندکس رو از سرو دادن جدا کن تا هر کدوم با ساز خودش scale بشه.

Picture this diagram as five stations — 01 / Build (Spark), 02 / Object Store, 03 / Parse, 04 / Search, 05 / Serve. The top lane builds the index offline, the bottom lane serves queries online, and two stores sit in the middle: the Compressed Index and the Vector Fragments. You'll get the whole figure from one sentence: decouple index-building from serving so each side scales on its own.

داستان ساخت از این قراره: جعبهٔ «Distributed K-Means» (زیرنویس: «Spark K-means + JAX»، برچسب: «~32K partitions, sampled») با فلشِ «centroids» می‌رسه به «PQ Encoder» (زیرنویس: «48 sub-vectors, residual»، برچسب: «64x compression»). از اون‌جا دو تا فلش بیرون می‌زنه: «partition IDs» به «Fragment Writer» (زیرنویس: «partition-aligned write»، برچسب: «immutable output»)، و «PQ codebooks» (چین‌چین) به «Compressed Index» (زیرنویس: «~45 GiB per 1B vectors»، برچسب: «in-memory ANN»). بعد «Fragment Writer» با فلشِ پررنگِ «immutable fragments» می‌رسه به «Vector Fragments» (زیرنویس: «full-precision columnar»، برچسب: «object storage»). این تکهٔ آفلاین روی کلاستر موقتی Spark اجرا می‌شه و خروجی‌ش یه نسخهٔ immutable همراه manifestـه — سرویس آنلاین فقط نسخهٔ مشخصی رو load می‌کنه.

Here's the thing on the build lane: Distributed K-Means (Spark K-means + JAX; ~32K partitions, sampled) feeds centroids into the PQ Encoder (48 sub-vectors, residual; 64x compression). Two arrows leave the encoder: partition IDs to the Fragment Writer (partition-aligned write; immutable output), and the dashed PQ codebooks to the Compressed Index (~45 GiB per 1B vectors; in-memory ANN). The writer then ships the bold immutable fragments into Vector Fragments (full-precision columnar; object storage). This offline leg runs on an ephemeral Spark cluster and publishes one immutable version with a manifest — the online service just loads a pinned version.

حالا مسیر کوئری رو قدم‌به‌قدم بگیر — پنج مرحله‌ست: اول «Parse & Route» (زیرنویس: «gRPC, async I/O»، برچسب: «Tokio runtime») که با فلشِ «query vector» می‌ره به «PQ Distance Scan» (زیرنویس: «probe nearest partitions»، برچسب: «CPU runtime»)؛ این جعبه روی «Compressed Index» که با «compressed codes» و «loaded at startup» بالا اومده کار می‌کنه. دوم، فلشِ «400 candidates for top-10» می‌رسه به «Fragment Fetch» (زیرنویس: «coalesced 256 KiB reads»، برچسب: «partition-pruned») که با «byte-range reads» و «coalesced range reads» فقط تکه‌های لازم رو از «Vector Fragments» می‌خونه. سوم، فلشِ «full-precision vectors» می‌ره به «Re-rank Shortlist» (زیرنویس: «exact-distance re-rank»، برچسب: «CPU runtime»)، و آخرش فلشِ «ranked top-N» می‌رسه به «Serialize & Return» (زیرنویس: «top-N + metadata»، برچسب: «~500 ms at 1B»). ترفندش اینه: جست‌وجوی تقریبیِ ارزون اول لیست رو کوچیک می‌کنه، بعد فقط همون چندصدتا با فاصلهٔ دقیق دوباره مرتب می‌شن — یادت باشه.

Now walk the query path step by step — five stages: first, Parse & Route (gRPC, async I/O; Tokio runtime) sends the query vector to PQ Distance Scan (probe nearest partitions; CPU runtime), which works against the Compressed Index brought up via compressed codes and loaded at startup. Second, the 400 candidates for top-10 arrow reaches Fragment Fetch (coalesced 256 KiB reads; partition-pruned), which pulls only the needed slices from Vector Fragments with byte-range reads and coalesced range reads. Third, full-precision vectors flow into Re-rank Shortlist (exact-distance re-rank; CPU runtime), and finally ranked top-N lands in Serialize & Return (top-N + metadata; ~500 ms at 1B). The trick: a cheap approximate scan shrinks the list first, then only those few hundred get an exact-distance re-rank — that's the punchline.

قضیهٔ عددها اینه — همه به‌نقل از گزارش نویسنده‌ست، نه اندازه‌گیری ما: حدود 1B بردار 768-dim تو هر ایندکس، ساخت زیر 8h، recall حدود ~90% با overfetch (همون 400 کاندید برای top-10)، و هزینهٔ سرو تا 7x کمتر از HNSW تمام‌حافظه‌ای. فشرده‌سازی PQ با 48 زیربردار (3072 بایت به 48 بایت، 64x) حدود 3 TiB بردار خام رو به ~45 GiB حافظه می‌رسونه — جدا کردن compute موقتیِ ساخت از سرویس آنلاین، قبض رو پایین نگه می‌داره.

Rule of thumb on the numbers — all as reported by the authors, not our own measurements: about 1B 768-dim vectors per index, builds finishing in under 8h, roughly ~90% recall with overfetch (those 400 candidates for the top-10), and up to 7x lower serving cost than memory-resident HNSW. PQ compression with 48 sub-vectors (3072 bytes down to 48 bytes, 64x) shrinks about 3 TiB of raw vectors to ~45 GiB in memory — keeping ephemeral build compute apart from online serving is what holds the bill down.

۱. پایگاه داده در پایین‌ترین سطح چه وظیفه‌ای دارد؟1. What is a database’s job at the lowest level?

موتور باید دادهٔ پذیرفته‌شده رو طبقِ تضمینِ ماندگاری نگه داره و بعداً بتونه اون رو پیدا کنه. ساختارهای این فصل راه‌های مختلفِ انجامِ همون دو تا کارن.

مثال فنی: آخرین مقدار در لاگ

وضعیت اولیه: فرض کن فایل به‌ترتیب P7=100 و P7=120 داره. تهش آخریه.

اجرای مرحله‌به‌مرحله: حالا نوشتن فقط به انتهای فایل اضافه می‌کنه؛ خوندن بدون ایندکس باید آخرین رکورد P7 رو تو فایل پیدا کنه. بگرد تا پیدا کنی!

نتیجه و دلیل: پس append ساده‌ست، ولی خوندن با رشد فایل گرون می‌شه. ایندکس نشونی آخرین مقدار رو نگه می‌داره — آدرس رو یادداشت کن.

Two jobs: keep the data you give it and return it when you ask. Everything in this chapter (indexes, LSM, B-trees, columnar) answers those two questions with different trade-offs.

۲. ایندکس چیست و تریدآف اصلی‌اش کدام است؟2. What is an index, and its core trade-off?

ایندکس ساختاری اضافی برای پیدا کردنِ داده‌ست. خوندن رو سریع‌تر می‌کنه، ولی فضا می‌گیره و تغییرِ داده باید اون رو هم به‌روز کنه.

مثال فنی: بهای ایندکسِ اضافه

وضعیت اولیه: فرض کن رو جدول سفارش، ایندکس customer_id ساختی.

اجرای مرحله‌به‌مرحله: حالا خوندن سفارش‌های مشتری ۱۷ دیگه کل جدول رو اسکن نمی‌کنه؛ ولی هر درج یا تغییر مشتری باید ایندکس رو هم اصلاح کنه. یه بام و دو هوا نیست.

نتیجه و دلیل: پس کم شدن هزینهٔ خوندن با فضای بیشتر و کار اضافهٔ نوشتن همراهه. ایندکس بلااستفاده مجانی نیست — یادت باشه.

An extra structure derived from the primary data (e.g. sorted by key) that speeds up search. The trade-off: every write must update the index too, and it consumes space. That is why we pick indexes manually, based on query patterns.

۳. چرا hash index به‌تنهایی کافی نیست؟3. Why isn’t a hash index enough on its own?

تو مدلِ سادهٔ فصل، ایندکسِ هشِ درونِ حافظه جست‌وجوی کلید رو سریع می‌کنه، ولی خوندنِ بازه و ظرفیتِ حافظه و بازیابی و جمع‌آوریِ نسخه‌های قدیمی مسائلِ جداگانه‌ان.

مثال فنی: بلوکِ مناسب به‌جای کل فایل

وضعیت اولیه: فرض کن SSTable کلیدهای مرتب 100…999 داره و ایندکس پراکنده شروع هر بلوک رو می‌شناسه. مثل فهرست کتاب.

اجرای مرحله‌به‌مرحله: حالا برای کلید 740 بلوکی که از 700 شروع می‌شه پیدا و همون بخش خونده می‌شه. فقط همون قفسه!

نتیجه و دلیل: پس مرتب بودن هم جست‌وجوی بلوک و هم اسکن بازهٔ 740…760 رو ممکن می‌کنه. هش به‌تنهایی ترتیب بازه رو نمی‌ده — نظم قیمتیه.

Four problems: overwritten values’ space is never freed; the hash map must be rebuilt by scanning the whole log on restart; it must fit in memory (hash on disk is slow and complex); and there are no range queries.

۴. SSTable چه مزیتی بر لاگ ساده دارد؟4. What advantage does an SSTable have over a plain log?

SSTable کلیدها رو مرتب نگه می‌داره. این نظم امکانِ ایندکسِ پراکنده و ادغامِ فایل‌ها و خوندنِ بازه‌ای رو فراهم می‌کنه؛ لازم نیست نشونیِ هر کلید تو حافظه باشه.

مثال فنی: بلوکِ مناسب به‌جای کل فایل

وضعیت اولیه: فرض کن SSTable کلیدهای مرتب 100…999 داره و ایندکس پراکنده شروع هر بلوک رو می‌شناسه. مثل فهرست کتاب.

اجرای مرحله‌به‌مرحله: حالا برای کلید 740 بلوکی که از 700 شروع می‌شه پیدا و همون بخش خونده می‌شه. فقط همون قفسه!

نتیجه و دلیل: پس مرتب بودن هم جست‌وجوی بلوک و هم اسکن بازهٔ 740…760 رو ممکن می‌کنه. هش به‌تنهایی ترتیب بازه رو نمی‌ده — نظم قیمتیه.

Sortedness by key: you can keep a sparse index (only each multi-KB block’s first key), compress blocks, and merge several SSTables mergesort-style with little memory. Lookup: jump to the right block, scan a few kilobytes.

۵. نقش memtable و WAL در موتور LSM چیست؟5. What do the memtable and WAL do in an LSM engine?

Memtable تغییرهای تازه رو تو حافظهٔ مرتب جمع می‌کنه؛ WAL اطلاعاتِ لازم برای بازیابیِ اون‌ها رو نگه می‌داره. پس از پر شدن، داده به SSTable منتقل می‌شه.

مثال فنی: نسخه‌های تازه در LSM

وضعیت اولیه: فرض کن P7=100 تو SSTable قدیمیه و P7=120 تو memtable نوشته می‌شه. دو جا، دو نسخه.

اجرای مرحله‌به‌مرحله: حالا نوشتن WAL و حافظه رو به‌روز می‌کنه؛ flush فایل مرتب تازه می‌سازه و compaction نسخه‌های لازم رو ادغام می‌کنه.

نتیجه و دلیل: پس خواننده باید نسخهٔ قابل‌مشاهدهٔ تازه رو انتخاب کنه. پیدا شدن کلید تو یه فایل قدیمی برای توقف کافی نیست — تا تهش برو.

The memtable is the in-memory sorted map accepting writes; when full it flushes, sorted, as an SSTable. Since the memtable is volatile, every write is simultaneously recorded in an on-disk log (WAL) for post-crash rebuild; after a flush the matching log section is discarded.

۶. جست‌وجوی نقطه‌ای در LSM چطور انجام می‌شود؟6. How does LSM point lookup work?

خوندن وضعیتِ تازه رو تو حافظه و فایل‌های مرتبط جست‌وجو می‌کنه. فیلترها و ایندکس‌ها فایل و بلوکِ لازم رو محدود می‌کنن؛ نسخه‌ها و علامتِ حذف تعیین می‌کنن چه نتیجه‌ای معتبره.

مثال فنی: نسخه‌های تازه در LSM

وضعیت اولیه: فرض کن P7=100 تو SSTable قدیمیه و P7=120 تو memtable نوشته می‌شه. دو جا، دو نسخه.

اجرای مرحله‌به‌مرحله: حالا نوشتن WAL و حافظه رو به‌روز می‌کنه؛ flush فایل مرتب تازه می‌سازه و compaction نسخه‌های لازم رو ادغام می‌کنه.

نتیجه و دلیل: پس خواننده باید نسخهٔ قابل‌مشاهدهٔ تازه رو انتخاب کنه. پیدا شدن کلید تو یه فایل قدیمی برای توقف کافی نیست — تا تهش برو.

In order: memtable, then segments newest to oldest. For each segment the Bloom filter is checked first; a “no” skips the segment, a “yes” sends you via the sparse index to the block. Costliest case: a key updated very long ago, or one that doesn’t exist at all.

۷. Bloom filter چطور کار می‌کند و false positive یعنی چه؟7. How does a Bloom filter work — what is a false positive?

برای کلید، چند تا موقعیتِ بیت علامت می‌خوره. اگه بیتِ لازم صفر باشه، کلید نیست؛ اگه همه یک باشن، شاید هست، چون کلیدهای دیگه هم همون بیت‌ها رو علامت زدن.

مثال فنی: شاید هست، قطعاً نیست

وضعیت اولیه: فرض کن برای یه SSTable، ـی Bloom filter می‌گه بیت لازم برای کلید P99 صفره. یعنی نیست.

اجرای مرحله‌به‌مرحله: حالا فایل برای P99 خونده نمی‌شه؛ ولی اگه همهٔ بیت‌ها یک باشن، فایل هنوز باید بررسی بشه. شاید هست، شاید نه.

نتیجه و دلیل: پس پاسخ مثبت می‌تونه کاذب باشه. فیلتر سالم برای مجموعهٔ ساخته‌شده پاسخ منفی کاذب نمی‌ده و جای بررسی داده رو نمی‌گیره — «نه» قطعیه، «شاید» مشکوکه.

Several hashes per key set bits in a bit-array. At lookup, one 0 bit means the key is definitely absent; all 1s means probably present (a false positive = an absent key that looks present). ~10 bits per key → ~1% error; in an LSM engine the error is harmless since it only causes a little wasted work.

۸. دو استراتژی compaction را مقایسه کن.8. Compare the two compaction strategies.

ادغامِ اندازه‌محور فایل‌های مشابه رو جمع می‌کنه و معمولاً فضای موقت و فایل‌های بیشتری داره. ادغامِ سطحی بازه‌ها رو منظم‌تر نگه می‌داره، ولی می‌تونه داده رو بیشتر بازنویسی کنه.

مثال فنی: دو سیاست ادغام

وضعیت اولیه: فرض کن چهار تا فایل 100 MB داری که بعضی کلیدهاشون هم‌پوشانی داره.

اجرای مرحله‌به‌مرحله: حالا size-tiered می‌تونه فایل‌های هم‌اندازه رو ادغام کنه؛ leveled فایل‌ها رو تو سطح‌ها و بازه‌های منظم‌تر نگه می‌داره. دو تا سلیقه.

نتیجه و دلیل: پس اولی معمولاً فایل و فضای موقت بیشتری می‌خواد؛ دومی ممکنه بازنویسی بیشتری بسازه. نتیجه به بار و تنظیمات وابسته‌ست — برندهٔ ثابت نداریم.

Size-tiered: small segments merge together, then with bigger ones; high write throughput, lots of temporary space, reads may scan several large segments. Leveled: fixed-size segments in levels L0, L1, … with size caps; gradual merges, less space, faster reads. Rule: write-heavy → size-tiered; read-heavy → leveled.

۹. tombstone چیست و چه چالشی دارد؟9. What is a tombstone, and its challenge?

Tombstone علامتِ حذفه تا خوندن و ادغام، نسخهٔ قدیمیِ رکورد رو دوباره زنده نکنن. حذفِ خودِ علامت فقط وقتی امنه که نسخه‌های پوشش‌داده‌شده دیگه برنگردن.

مثال فنی: علامت حذفِ هنوز لازم

وضعیت اولیه: فرض کن فایل قدیمی P7=100 داره و فایل تازه P7=DELETE. مرده، ولی دفنش نکن هنوز!

اجرای مرحله‌به‌مرحله: حالا خوندن علامت حذف رو می‌بینه و رکورد رو نشون نمی‌ده. compaction فقط وقتی حذف علامت امنه که نسخهٔ قدیمی مربوط دیگه برنگرده.

نتیجه و دلیل: پس پاک کردن زودهنگام tombstone می‌تونه مقدار قدیمی رو دوباره زنده کنه — مرده برمی‌گرده! عجله نکن.

A special delete record telling merges to throw away that key’s older values. Challenge: until the tombstone reaches the oldest segment, old versions still sit on disk — “definitive deletion” (e.g. privacy law) can take a while.

۱۰. ساختار B-tree را در چند جمله توضیح بده.10. Explain the B-tree structure in a few sentences.

B-tree درختی از صفحه‌های دارای کلید و اشاره‌گره. هر سطح بازه رو محدود می‌کنه؛ برگ‌ها کلیدهای مرتب رو نگه می‌دارن و محلِ رکورد به طراحیِ موتور بستگی داره.

مثال فنی: پیمایشِ B-tree

وضعیت اولیه: فرض کن ریشه کلید جداکنندهٔ 500 داره و برگ راست شامل 700,740,780ـه. درخت رو تصور کن.

اجرای مرحله‌به‌مرحله: حالا جست‌وجوی 740 با مقایسه تو ریشه می‌ره به فرزند راست و بعد برگ مربوط. پله‌پله پایین.

نتیجه و دلیل: پس هر سطح بازه رو محدود می‌کنه. لازم نیست برای یه کلید همهٔ صفحه‌ها خونده بشن — درخت یعنی نصف کردن راه.

Fixed-size pages (8–16 KB in common databases) referencing each other by page number. A root, internal pages with boundary keys, leaves with individual keys. A branching factor in the hundreds → 3–4 levels for large data; depth always O(log n).

۱۱. page split و WAL چه می‌کنند؟11. What do page splits and the WAL do?

Page split موقعِ پر شدنِ صفحه، اون رو تقسیم و راهنمای والد رو اصلاح می‌کنه. WAL تغییرهای لازم رو برای بازیابیِ امنِ ساختار و داده ثبت می‌کنه.

مثال فنی: Crash وسطِ split

وضعیت اولیه: فرض کن دو تا صفحهٔ تازه ساخته شدن، ولی به‌روزرسانی والد هنوز رو دیسک نرفته. نصفه کاره!

اجرای مرحله‌به‌مرحله: حالا رکوردهای بازیابی موتور مشخص می‌کنن split چطور تکمیل یا اصلاح بشه. صرف نوشتن جداگانهٔ چند صفحه کافی نیست.

نتیجه و دلیل: پس ساختار درخت هم باید پس از crash معتبر بمونه. ماندگاری فقط حفظ مقدار یه رکورد نیست — اسکلت هم باید سرپا بمونه.

When a page fills, it splits into two half-full pages and the parent is updated with the fresh boundary key (splits can climb to the root). Since these multi-page rewrites are crash-dangerous (orphaned or torn pages), every change is first written to the WAL with fsync, then applied to the page.

۱۲. مهم‌ترین تفاوت‌های B-tree و LSM چیست؟12. What are the key B-tree vs LSM differences?

B-tree معمولاً با مسیرِ صفحه‌ایِ مرتب می‌خونه؛ LSM تغییرها رو تو حافظه و فایل‌ها جمع و بعد ادغام می‌کنه. هزینهٔ نوشتن و خوندن و فضا و تأخیرِ پس‌زمینه به بار و پیاده‌سازی وابسته‌ست.

مثال فنی: بارِ نوشتن و خواندن

وضعیت اولیه: فرض کن بار A عمدتاً ورود رویداده؛ بار B عمدتاً lookup و تغییر رکوردهای کوچیکه. دو تا دنیای جدا.

اجرای مرحله‌به‌مرحله: حالا LSM نوشتن‌ها رو جمع می‌کنه و هزینهٔ compaction می‌ده؛ B-tree صفحه‌ها رو به‌روز می‌کنه و ساختار خوندن مرتب داره.

نتیجه و دلیل: پس انتخاب با اندازه‌گیری write/read/space amplification و tail latency رو همون بار انجام می‌شه. برندهٔ ثابت نداریم — اندازه بگیر، حدس نزن.

Reads: B-trees are fast and predictable (one page per level) with excellent range queries; LSM may scan several segments and ranges cost more. Writes: LSM is sequential with usually lower write amplification. Space: B-trees fragment, LSM compresses better but stale versions linger until compaction. Deletion and snapshots behave differently too.

۱۳. write amplification چیست و چرا مهم است؟13. What is write amplification, and why does it matter?

افزایشِ نوشتن یعنی مقدارِ واقعیِ نوشته‌شده بر رسانه، از دادهٔ تازهٔ برنامه بیشتر باشه. لاگ و صفحه‌ها و ایندکس و ادغام تو این هزینه نقش دارن.

مثال فنی: حسابِ write amplification

وضعیت اولیه: فرض کن برنامه تو یه بازه 1 GB دادهٔ تازه می‌نویسه، ولی لاگ و compaction مجموعاً 6 GB رو رسانه می‌نویسن. شش برابر!

اجرای مرحله‌به‌مرحله: حالا نسبت نوشتن واقعی به ورودی تو این اندازه‌گیری 6×ـه. دامنهٔ اندازه‌گیری، از جمله WAL، باید مشخص باشه — چی رو شمردی؟

نتیجه و دلیل: پس توان و عمر رسانه از بایت واقعی اثر می‌گیره. تنها نرخ دادهٔ ورودی کافی نیست — قبض رو بایت واقعی می‌ده.

The ratio of bytes actually written to disk vs data bytes (excluding indexes). In B-trees at least 2× (WAL + page, sometimes a whole page for a few bytes); in LSM per flush and compaction. In write-heavy workloads it caps write throughput and wears SSDs faster. Benchmarks must run long enough for compaction to join in.

۱۴. چرا SSD هم برای نوشتن ترتیبی سریع‌تر است؟14. Why are sequential writes faster even on SSDs?

فلش واحدهای خوندن و نوشتن و پاک‌کردنِ متفاوت داره و کنترل‌کننده داده رو جابه‌جا می‌کنه. نوشتنِ ترتیبی می‌تونه کارِ مدیریتِ رسانه رو کمتر کنه، ولی اثرش به دستگاه و بار وابسته‌ست.

مثال فنی: چرا نوشتن SSD رایگان نیست؟

وضعیت اولیه: فرض کن برنامه بلوک‌های کوچیک و پراکنده رو مرتب بازنویسی می‌کنه. ریزریز و همه جا!

اجرای مرحله‌به‌مرحله: حالا کنترل‌کننده برای پاک‌سازی بلوک‌های بزرگ‌تر ممکنه دادهٔ زنده رو جابه‌جا کنه. نوشتن منظم می‌تونه این فشار رو کم کنه.

نتیجه و دلیل: پس اثر به دستگاه و فضای آزاد و بار بستگی داره. SSD داشتن هزینهٔ garbage collection و write amplification رو حذف نمی‌کنه — SSD جادو نیست، یادت باشه.

Because flash erases only “block by block” (e.g. 512KB) and valid pages must first be relocated (garbage collection). Sequential writes keep blocks uniform and GC low; random writes pollute blocks, GC eats bandwidth and increases flash wear.

۱۵. clustered index، heap file و covering index چه تفاوتی دارند؟15. How do clustered, heap and covering indexes differ?

تو ایندکسِ خوشه‌ای، داده با نظمِ ایندکس نگه‌داری می‌شه؛ تو heap، ایندکس محلِ رکورد رو معرفی می‌کنه. ایندکسِ پوشاننده فیلدهای لازمِ پرس‌وجو رو هم داره.

مثال فنی: رکورد پشت ایندکس کجاست؟

وضعیت اولیه: فرض کن query شمارهٔ سفارش ۴۲ رو پیدا می‌کنه و مبلغش رو می‌خواد. ساده به نظر میاد، نه؟

اجرای مرحله‌به‌مرحله: حالا تو heap، ایندکس می‌تونه محل ردیف رو بده؛ تو الگوی clustered، داده با ترتیب کلید خوشه‌ای نگه داشته می‌شه؛ covering index خود مبلغ لازم رو هم داره. سه تا راه جدا.

نتیجه و دلیل: پس تعداد مراجعه‌ها و هزینهٔ تغییر رکورد فرق داره. معنای دقیق clustered و سازمان صفحه‌ها رو باید تو همون موتور بررسی کرد — اسم مشترک، رفتار مشترک نیست.

Clustered: the record itself lives inside the index structure (e.g. InnoDB primary keys). Heap file: the index only references, records sit in an unordered file (e.g. PostgreSQL). Covering: some record columns also live inside the index so queries answer without touching the heap — faster, but more space and writes.

۱۶. چرا ذخیره‌سازی ستونی برای تحلیل بهتر است؟16. Why is columnar storage better for analytics?

تحلیل اغلب تعدادِ زیادی ردیف ولی چند تا ستون رو می‌خواد. چیدمانِ ستونی خوندنِ بخشِ لازم و فشرده‌سازیِ مقدارهای مشابه رو راحت می‌کنه.

مثال فنی: فقط مبلغ‌ها را بخوان

وضعیت اولیه: فرض کن ردیف‌ها شامل id, address, description, amount هستن.

اجرای مرحله‌به‌مرحله: حالا برای SUM(amount) موتور ستونی فقط بلوک مبلغ رو می‌خونه و نشونی و توضیح رو کنار می‌ذاره. فقط همون که لازمه!

نتیجه و دلیل: پس سود از کمتر خوندن میاد. اگه query همهٔ ستون‌های یه ردیف رو بخواد، همین مزیت الزاماً برقرار نیست — معجزهٔ همیشگی نداریم.

Because an analytical query wants only 3–5 of 100+ columns; columnar layout reads just those. Columns repeat heavily and compress with bitmap + RLE; sorting whole rows builds long runs; predicates resolve with cheap bitwise AND/OR and vectorized execution.

۱۷. column-oriented با wide-column چه فرقی دارد؟17. How does column-oriented differ from wide-column?

Column-oriented روشِ چیدنِ فیزیکیِ داده برای خوندنِ ستون‌هاست. Wide-column یه مدلِ داده برای ردیف‌ها و خانواده‌های ستونه؛ شباهتِ اسم به‌معنی رفتارِ یکسان نیست.

مثال فنی: ستونی با wide-column فرق دارد

وضعیت اولیه: فرض کن یه انبار تحلیلی مبلغ همهٔ سفارش‌ها رو ستونی نگه می‌داره؛ سامانه‌ای دیگه کلید customer_id و ردیف‌های دارای ستون‌های متغیر داره. اسم هر دو column داره!

اجرای مرحله‌به‌مرحله: حالا اولی چیدمان فیزیکی برای اسکن ستونه؛ دومی مدل wide-column برای دسترسی به ردیف‌ها و خانواده‌های ستونه. دو تا دنیای جدا.

نتیجه و دلیل: پس اشتراک واژهٔ column به‌معنی یکسان بودن الگوی query یا موتور ذخیره‌سازی نیست — هم‌اسم بودن یعنی هم‌خانواده بودن؟ نه!

Wide-column (e.g. Bigtable, HBase) is a data model: each row may hold thousands of different columns, but its storage layout is row-oriented. Column-oriented is a storage layout: each column’s values side by side. Only the names are alike.

۱۸. تفاوت query compilation و vectorized processing؟18. Query compilation vs vectorized processing?

کامپایلِ پرس‌وجو بخشی از منطق رو به کدِ اجرایی تبدیل می‌کنه. پردازشِ برداری عملیات رو رو دسته‌ای از مقدارها انجام می‌ده؛ این دو تا روش می‌تونن کنارِ هم استفاده بشن.

مثال فنی: برداری در برابر کامپایل

وضعیت اولیه: فرض کن query باید یه میلیون مبلغ رو جمع کنه. یه میلیون!

اجرای مرحله‌به‌مرحله: حالا اجرای برداری دسته‌های مثلاً ۱۰۲۴تایی رو به عملگر می‌ده؛ کامپایل منطق query رو به کد اجرایی تخصصی تبدیل می‌کنه. دو تا ترفند جدا.

نتیجه و دلیل: پس یکی شکل پردازش دسته‌ای مقدارهاست و دیگری روش اجرای منطق. می‌شه هر دو رو هم‌زمان داشت — چرا یکیشون؟ هر دو!

Compilation: generate executable code from SQL and compile it (e.g. with LLVM) — like JIT. Vectorized: stays interpreted, but operators work over large batches of values (e.g. one column’s equality → one bitmap, combined with bitwise AND). Both exploit sequential access, tight loops, SIMD and work over compressed data.

۱۹. inverted index چیست و چطور «سیب قرمز» را جواب می‌دهد؟19. What is an inverted index — how does it answer “red apples”?

ایندکسِ معکوس هر واژه رو به سندهای دارای اون وصل می‌کنه. برای وجودِ هر دو تا واژه، فهرست‌ها مشترک‌گیری می‌شن؛ برای عبارتِ دقیق، موقعیتِ واژه‌ها هم لازمه.

مثال فنی: تقاطع فهرست اسناد

وضعیت اولیه: فرض کن فهرست سیب برابر [1,3,7] و قرمز برابر [3,5,7]ـه. دو تا لیست.

اجرای مرحله‌به‌مرحله: حالا اشتراک فهرست‌ها سندهای 3,7 رو می‌ده؛ ولی برای عبارت دقیق باید موقعیت واژه‌ها هم پشت‌سرهم باشه. همسایگی مهمه!

نتیجه و دلیل: پس داشتن هر دو واژه با داشتن عبارت «سیب قرمز» یکی نیست. ایندکس باید اطلاعات لازم همون سؤال رو نگه داره — سؤال رو بفهم، بعد ایندکس بساز.

A map from each word to the IDs of documents containing it (postings list). “Red apples” means fetching both words’ postings and intersecting (AND-ing) them bitwise — since the n-th bit of both points at the same document. Lucene (the heart of Elasticsearch/Solr) and PostgreSQL’s GIN type work this way.

۲۰. IVF و HNSW چه تفاوتی با هم دارند و «تقریبی» یعنی چه؟20. How do IVF and HNSW differ — what does “approximate” mean?

IVF جست‌وجو رو به چند تا خوشه محدود می‌کنه؛ HNSW رو گرافِ همسایگی مسیرِ جست‌وجو می‌سازه. تقریبی بودن یعنی ممکنه نزدیک‌ترین نتیجهٔ واقعی پیدا نشه؛ سرعت و دقت تنظیم می‌شن.

مثال فنی: جست‌وجوی تقریبی بردار

وضعیت اولیه: فرض کن query برداری نزدیک به محصول P7ـه، ولی فقط چند تا خوشه یا بخشی از گراف بررسی می‌شه. نه همه جا!

اجرای مرحله‌به‌مرحله: حالا IVF خوشه‌های منتخب رو می‌کاوه؛ HNSW مسیر همسایه‌ها رو رو گراف طی می‌کنه. گسترش جست‌وجو معمولاً کار بیشتری می‌خواد.

نتیجه و دلیل: پس ممکنه نزدیک‌ترین همسایهٔ واقعی جا بمونه. recall باید با جست‌وجوی دقیق رو نمونهٔ مرجع سنجیده بشه — تقریب یعنی گاهی اشتباه، یادت باشه.

Flat scans everything (exact, slow). IVF splits space into clusters and scans only a few (probes). HNSW is a layered proximity graph guiding from the sparse top layer to the dense bottom. Both are approximate: they may miss the nearest document; more probes/layers = more accuracy, less speed.

۹.۳ اشتباهات رایج در جواب‌های مصاحبه9.3 Common interview mistakes

  • قاطی کردنِ «NoSQL با LSM» و «SQL با B-tree» — موتور ذخیره‌سازی از مدل داده جداست؛ موتورهای رابطه‌ای با ساختارهای گوناگون هم میان.
  • فکر کردن به Bloom filter به‌عنوان جوابِ قطعی؛ ماهیتش تقریبیه (false positive) و فقط «نیست» گفتنش قطعیه.
  • نادیده گرفتن هزینهٔ ایندکس رو نوشتن؛ تعریفِ چند تا ایندکس بدون فکر به الگوی نوشتن، بازده نوشتن رو خفه می‌کنه.
  • قضاوت مطلق دربارهٔ «B-tree بهتره یا LSM»؛ بدون بارکاریِ مشخص و بنچ‌مارکِ طولانی (با compaction واقعی) ادعایی نمی‌شه کرد.
  • قاطی کردنِ column-oriented با wide-column، یا vectorized processing با vector embedding.
  • دونستنِ IVF و HNSW به‌عنوان جست‌وجوی دقیق؛ هر دو تقریبی‌ان و recall رو با latency مبادله می‌کنن.
  • یاد رفتن این‌که range query از Bloom filter بهره‌ای نمی‌بره و تو LSM گرون‌تر از نقطه‌ایه.
  • توضیح ندادنِ مسئلهٔ write amplification وقتی از بازده نوشتنِ LSM حرف می‌زنی.
  • Equating “NoSQL with LSM” and “SQL with B-trees” — storage engines are separate from data models; relational engines ship with varied structures too.
  • Treating the Bloom filter as a definitive answer; it is approximate by nature (false positives), and only its “absent” verdict is certain.
  • Ignoring index cost on writes; defining several indexes without thinking about the write pattern chokes write throughput.
  • Absolute verdicts on “B-tree vs LSM”; without a concrete workload and a long benchmark (with real compaction) no claim can be made.
  • Mixing up column-oriented with wide-column, or vectorized processing with vector embeddings.
  • Treating IVF and HNSW as exact search; both are approximate and trade recall against latency.
  • Forgetting that range queries gain nothing from Bloom filters and cost more than point reads in LSM.
  • Not explaining write amplification when discussing LSM write throughput.

۹.۴ چک‌لیست مرور ۵ دقیقه‌ای قبل از مصاحبه9.4 Five-minute pre-interview checklist

  • تریدآفِ اصلیِ ایندکس: خوندن سریع‌تر / نوشتن کندتر / فضای بیشتر.
  • مسیر نوشتن و خوندن تو LSM رو از حفظ بگو: WAL → memtable → flush → سگمنت‌ها → compaction؛ و جست‌وجو: memtable → جدید به قدیم + Bloom filter.
  • ساختار B-tree و دلیل WAL و page split رو تو ۳ جمله.
  • سه تا تفاوتِ محوریِ B-tree و LSM (خوندن/نوشتن/فضا) + مفهوم write amplification.
  • سه تا الگوی جا دادن رکورد (clustered و heap و covering) و یه جمله دربارهٔ ستونی: column pruning و bitmap.
  • ایندکس‌های پیشرفته تو یه جمله هرکدوم: R-tree و inverted index و IVF/HNSW — و یادآوریِ «تقریبی» بودنِ برداری‌ها.
  1. The core index trade-off: faster reads / slower writes / more space.
  2. Recite the LSM write and read paths: WAL → memtable → flush → segments → compaction; lookups: memtable → newest-to-oldest + Bloom filter.
  3. The B-tree structure and why WAL and page splits exist, in 3 sentences.
  4. Three core B-tree vs LSM differences (reads/writes/space) + write amplification.
  5. The three record-placement patterns (clustered, heap, covering) and one sentence on columnar: column pruning and bitmaps.
  6. Advanced indexes in one sentence each: R-tree, inverted index, IVF/HNSW — and the “approximate” reminder for vectors.
