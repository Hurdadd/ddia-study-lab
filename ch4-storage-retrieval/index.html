ایدهٔ کلیدی فصلChapter thesis

این فصل می‌ره تو دلِ موتورِ ذخیره‌سازی: داده کجا نوشته می‌شه و موقع خوندن چطور پیدا می‌شه؟ لاگ و ایندکس و B-tree و LSM و ذخیره‌سازی ستونی، هزینهٔ خوندن و نوشتن رو به شکل‌های مختلف تقسیم می‌کنن.

مثال فنی: یک داده، دو مسیر خواندن

وضعیت اولیه: فرض کن جدول سفارش با id خونده می‌شه و گزارش فروش فقط ستون amount رو جمع می‌زنه. دو تا کار جدا.

اجرای مرحله‌به‌مرحله: حالا lookup نقطه‌ای از ایندکس استفاده می‌کنه؛ اسکن تحلیلی از چیدمان ستونی سود می‌بره. هر کدوم ساز خودش رو می‌زنه.

نتیجه و دلیل: پس موتور ذخیره‌سازی رو باید با نوع خوندن و نوشتن سنجید. سریع بودن یه lookup دربارهٔ سرعت اسکن میلیاردی چیزی نمی‌گه — یادت باشه.

مثال‌های این فصل قصه‌های آموزشی‌ان که از کار روزمره اومدن. عددها فقط برای فهم بهتر انتخاب شدن و معماری هیچ شرکت واقعی رو توصیف نمی‌کنن.

A database needs to keep the data it accepts under its durability guarantees and find it when you ask later. Chapter 3 looked at data models and query languages. Here, you'll follow the storage engine: where the bytes go and how a query finds them.

A quick order lookup and a report over a billion rows ask different things of that engine. Logs, indexes, B-trees, LSM and columnar storage divide the work differently.

The examples are teaching scenarios based on everyday engineering work. Their numbers help explain the ideas; they don't describe a particular company's architecture.

Example: One dataset, two read paths

Setup: An order lookup uses id; a sales report sums only amount.

Walk through it: The point lookup benefits from an index. A broad analytical scan benefits from a columnar layout that reads just the needed fields.

What this tells you: Judge an engine against its reads and writes. A fast lookup doesn't tell you how quickly it can scan a billion rows.

چرا توسعه‌دهنده باید این رو بدونه؟ چون باید از میون موتورهای فراوون، موتورِ مناسب الگوی بارکاریِ خودت رو انتخاب کنی و پارامترهاش رو درست بچینی. برای هر دو کار، داشتن نقشهٔ ذهنی از زیر کاپوت لازمه.

Knowing this helps you choose an engine for a workload pattern and configure it sensibly. Ask which reads and writes matter, then connect them to the work happening underneath.

مهم‌ترین خطِ تقسیم این فصل، همان تفکیک OLTP در برابر OLAP از فصل ۱ است:

Start with the OLTP versus OLAP distinction from Chapter 1. Fetching one order and calculating total sales need different access paths:

  • موتورهای تراکنشی (OLTP): تعداد زیاد درخواست، هرکدوم چند تا رکورد کوچیک، پاسخ سریع. دسترسی معمولاً با کلید اصلی یا ایندکس ثانویه؛ ساختارهای اصلی: ایندکس‌های مرتب از کلید به رکورد که range query هم بدهن.
  • موتورهای تحلیلی (OLAP/انبارداده): چند تا پرس‌وجوی پیچیده که میلیون‌ها رکورد رو می‌پیماین. ساختار اصلی: ذخیره‌سازی ستونی با فشرده‌سازی (برای کم کردن دادهٔ خونده‌شده از دیسک) و اجرای JIT یا برداری (برای کم کردن زمان CPU).
  • Transactional (OLTP) engines: handle many requests, each touching a few small records and needing a quick response. Primary keys and secondary indexes locate those records. Sorted key-to-record indexes also support range queries.
  • Analytical (OLAP/warehouse) engines: handle complex queries over millions of records. Columnar storage and compression reduce the bytes read; JIT or vectorized execution reduces CPU work.
تو سمت OLTP هم دو تا مکتب موتور داریم که بقیهٔ فصل حول اونا می‌چرخه:

For OLTP, compare two ways of organizing updates. You'll follow both throughout the chapter:

  • ساخت‌یافته / Log-Structured: فقط افزودن به فایل و حذف فایل‌های کهنه؛ هرگز بازنویسی درجا. SSTable، LSM-tree، RocksDB، Cassandra، HBase، ScyllaDB و حتی Lucene تو این خانواده‌ان. معمولاً بازده نوشتن بالا.
  • بازنویسی درجا / Update-in-place: دیسک مجموعه‌ای از صفحات با اندازهٔ ثابته که درجا بازنویسی می‌شن. B-treeها نمونهٔ برجسته‌ن و تقریباً تو همهٔ پایگاه‌های داده رابطه‌ای هستن. معمولاً خوندن سریع‌تر و قابل‌پیش‌بینی‌تر.
  • Log-structured: append new data and later remove old files, rather than rewriting existing file contents in place. SSTable and LSM-tree belong here, along with RocksDB, Cassandra, HBase, ScyllaDB and Lucene. This approach often favors high write throughput.
  • Update-in-place: divide storage into fixed-size pages and rewrite those pages. B-trees are the common example in relational databases. They often offer quick, predictable reads.
نکتهٔ مصاحبهInterview tip
کلِ مفهوم «ایندکس» یه تریدآفه: ساختاری مشتق‌شده از دادهٔ اصلی که خوندن رو سریع می‌کنه، ولی هر نوشتن باید اون رو هم به‌روز کنه؛ یعنی نوشتن کندتر و فضای بیشتر. به‌همین‌دلیل پایگاه داده‌ها همه‌جا ایندکس نمی‌سازن و انتخاب ایندکس با دونستن الگوی کوئری‌های تو انجام می‌شه.

An index is extra structure derived from the primary data. It helps a read reach the right record without searching everything. But a relevant write has to update the index too, and the index takes space.

That's the trade-off: less work on reads, more work on writes and more storage. Choose indexes around the queries the application runs.

۱1ساده‌ترین پایگاه داده جهانThe world’s simplest database

ساده‌ترین ذخیره‌ساز می‌تونه هر مقدار تازه رو به انتهای یه فایل اضافه کنه. نوشتن ساده‌ست، ولی برای پیدا کردن آخرین مقدارِ یه کلید باید فایل رو جست‌وجو کنیم.

مثال فنی: آخرین مقدار در لاگ

وضعیت اولیه: فرض کن فایل به‌ترتیب P7=100 و P7=120 داره. تهش آخریه.

اجرای مرحله‌به‌مرحله: حالا نوشتن فقط به انتهای فایل اضافه می‌کنه؛ خوندن بدون ایندکس باید آخرین رکورد P7 رو تو فایل پیدا کنه. بگرد تا پیدا کنی!

نتیجه و دلیل: پس append ساده‌ست، ولی خوندن با رشد فایل گرون می‌شه. ایندکس نشونی آخرین مقدار رو نگه می‌داره — آدرس رو یادداشت کن.

Begin with two bash functions: one stores a key-value pair, the other reads it back. New values go at the end of a file. Writing is simple; finding the latest value gets harder as that file grows.

Example: Finding the latest log value

Setup: A file contains P7=100, followed by P7=120.

Walk through it: A write adds another line at the end. Without an index, reading P7 means finding its last occurrence in the file.

What this tells you: Appending is simple, but the read work grows with the file. An index can remember where the latest value lives.

#!/bin/bash
db_set () {
  echo "$1,$2" >> database
}
db_get () {
  grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}

$ db_set 12 '{"name":"London","attractions":["Big Ben"]}'
$ db_set 42 '{"name":"San Francisco","attractions":["Golden Gate"]}'
$ db_get 42
هر فراخوانیِ db_set یه خط به انتهای فایل افزوده می‌شه؛ مقدارهای قدیمیِ هر کلید بازنویسی نمی‌شن و آخرین مقدار، آخرین رخدادِ همون کلید تو فایله (به‌همین‌دلیل tail -n 1). این دقیقاً همون کاریه که پایگاه‌های داده واقعی با لاگ می‌کنن.

Each db_set call appends a line. It leaves the key's old values where they were. To read the latest value, find the key's last occurrence; that's why the read function uses tail -n 1. This append-only history is a log.

۱.۱ لاگ، ایندکس و تریدآف1.1 Log, index and trade-off

  • لاگ (log) تو این کتاب یعنی: دنباله‌ای فقط‌افزودنی از رکوردها رو دیسک. لازم نیست انسان‌خوان باشه؛ می‌تونه باینری و فقط داخلی باشه. افزودن به فایل، ساده‌ترین و معمولاً سریع‌ترین نوع نوشتنه.
  • مسئله تو خوندنه: db_get باید کل فایل رو بگرده؛ هزینهٔ هر جست‌وجو O(n)ـه — با دو برابر شدن رکوردها، دو برابر کندتر.
  • پاسخ: ایندکس — ساختاری اضافی و مشتق‌شده از دادهٔ اصلی (مثلاً مرتب‌شده بر اساس کلید) که یافتن داده رو سریع می‌کنه. افزودن و حذف ایندکس محتوای پایگاه داده رو عوض نمی‌کنه؛ فقط کارایی رو.
  • هر ایندکس نوشتن رو کند می‌کنه (چون با هر نوشتن باید اون هم به‌روز بشه) و فضا می‌گیره. چون هیچ ایندکسی رایگان نیست، پایگاه داده‌ها به‌طور پیش‌فرض رو همه‌چی ایندکس نمی‌زنن؛ تو با دونستن الگوی کوئری‌ها انتخاب می‌کنی.
  • A log here means an append-only sequence of records on disk. It can be binary and internal to the engine. Appending is simple and often an efficient way to write.
  • The problem is reading: db_get scans the file. A lookup costs O(n), so doubling the number of records roughly doubles the scan work.
  • An index adds a derived access path, such as a structure sorted by key. Adding or removing this access structure changes how records are found, rather than the primary records themselves.
  • The index consumes space and adds work to writes that affect it. Before adding one, name the query it will help.

۲2ذخیره‌سازی Log-StructuredLog-structured storage

تو ذخیره‌سازی لاگ‌محور، تغییرات تازه به ساختارهای جدید افزوده می‌شن. تو پس‌زمینه، بخش‌های قدیمی ادغام می‌شن تا دادهٔ تکراری و فضای بلااستفاده کمتر بشه.

مثال فنی: نسخه‌های تازه در LSM

وضعیت اولیه: فرض کن P7=100 تو SSTable قدیمیه و P7=120 تو memtable نوشته می‌شه. دو جا، دو نسخه.

اجرای مرحله‌به‌مرحله: حالا نوشتن WAL و حافظه رو به‌روز می‌کنه؛ flush فایل مرتب تازه می‌سازه و compaction نسخه‌های لازم رو ادغام می‌کنه.

نتیجه و دلیل: پس خواننده باید نسخهٔ قابل‌مشاهدهٔ تازه رو انتخاب کنه. پیدا شدن کلید تو یه فایل قدیمی برای توقف کافی نیست — تا تهش برو.

Keep the append-only file, then add an in-memory hash map. Each key points to the byte offset of its latest value. A write appends a record and updates that pointer. A read jumps to the recorded position.

If the relevant bytes are already in the OS cache, the read may need no disk I/O. The hash map fixes point lookups, but several other problems remain.

ولی این طرح سه تا مشکل جدی داره:

Check four limits of this simple hash-index design:

  • فضای رکوردهای بازنویسی‌شده هرگز آزاد نمی‌شه؛ با نوشتن مداوم، دیسک پر می‌شه.
  • hash map پایدار نیست و بعد از restart باید با اسکن کل لاگ بازسازی بشه (restart کند).
  • hash map باید تو حافظه جا بشه؛ hash رو دیسک هم بدقلقه (دسترسی تصادفی زیاد، بزرگ‌سازی گرون، برخورد کلیدها).
  • range query نداره: نمی‌تونی ساده بگی «همهٔ کلیدهای ۱۰۰۰۰ تا ۱۹۹۹۹»؛ باید تک‌تک رو جداگانه بیابی.
  • Old values keep taking space. Without reclamation, continued writes eventually fill the disk.
  • The in-memory map must be rebuilt after restart by scanning the log, so recovery gets slower as the log grows.
  • The map must fit in memory. Moving a hash structure to disk introduces random access, growth and collision-handling costs.
  • No sorted range access: the hash map alone can't walk “keys 10000 to 19999” in order. Individual lookups don't give it a range index.

از لاگ تا SSTableFrom log to SSTable

تو LSM، تغییرات اول تو حافظه جمع می‌شن و بعد به فایل‌های مرتب‌شدهٔ SSTable می‌رن. لاگِ بازیابی کمک می‌کنه خرابی، تغییراتِ هنوز منتقل‌نشده رو از بین نبره.

مثال فنی: بلوکِ مناسب به‌جای کل فایل

وضعیت اولیه: فرض کن SSTable کلیدهای مرتب 100…999 داره و ایندکس پراکنده شروع هر بلوک رو می‌شناسه. مثل فهرست کتاب.

اجرای مرحله‌به‌مرحله: حالا برای کلید 740 بلوکی که از 700 شروع می‌شه پیدا و همون بخش خونده می‌شه. فقط همون قفسه!

نتیجه و دلیل: پس مرتب بودن هم جست‌وجوی بلوک و هم اسکن بازهٔ 740…760 رو ممکن می‌کنه. هش به‌تنهایی ترتیب بازه رو نمی‌ده — نظم قیمتیه.

  • تو عمل، به‌جای hash، داده رو مرتب بر اساس کلید نگه می‌دارن. نمونه: SSTable (Sorted Strings Table) — جفت‌کلیدمقدارهای مرتب که هر کلید فقط یه‌بار میاد.
  • ایندکس پراکنده (sparse index): به‌جای همهٔ کلیدها، فقط اولین کلیدِ هر بلوکِ چند کیلوبایتی رو نگه می‌دارن. مثال کتاب: برای یافتن handiwork، چون مرتبه می‌دونی بین handbag و handsomeـه؛ به offset بلوک اول می‌پری و همون چند کیلوبایت رو می‌گردی.
  • هر بلوک قابل فشرده‌سازیـه: فضای کمتر + پهنای باند I/O کمتر، به بهای اندکی CPU.
  • ولی نوشتن سخت می‌شه: نمی‌شه ساده اضافه کرد (چون ترتیب می‌شکنه) و بازنویسی کل فایل هم خیلی گرونه. راه‌حل، رویکرد log-structuredـه:
  • memtable: هر نوشته اول به یه نقشهٔ مرتب تو حافظه می‌ره (red–black tree، skip list یا trie) — درج با هر ترتیبی، جست‌وجوی کارآمد، بازخونی مرتب.
  • flush: وقتی memtable از چند مگابایت بزرگ‌تر شد، مرتب رو دیسک به‌صورت یه SSTableِ جدا (جدیدترین سگمنت) نوشته می‌شه؛ هم‌زمان memtable تازه کار رو تحویل می‌گیره.
  • خوندن: اول memtable، بعد سگمنت‌ها از جدید به قدیم؛ اگه کلید هیچ‌جا نبود، وجود نداره.
  • merge و compaction: مثل mergesort — چند تا سگمنت کنار هم خونده می‌شن، کوچک‌ترین کلید به خروجی می‌ره و اگه کلیدی تکراری بود فقط تازه‌ترین مقدار می‌مونه. خروجی، سگمنتِ مرتبِ جدیده.
  • WAL جدا برای memtable: چون memtable تو حافظه‌ست، هر نوشته بلافاصله تو یه لاگ رو دیسک هم ثبت می‌شه تا بعد از crash بازسازی بشه. بعد از flush، همون بخش از لاگ قابل دور انداختنه.
  • حذف = tombstone: رکورد حذفِ ویژه‌ای اضافه می‌شه که موقع merge به فرآیند می‌گه مقادیر قبلیِ همون کلید رو دور بریزه.
  • این الگوریتم همون چیزیه که تو RocksDB و Cassandra و ScyllaDB و HBase هست (از مقالهٔ Bigtable با اصطلاحات SSTable و memtable) و اصل اون ۱۹۹۶ با نام LSM-tree (Log-Structured Merge-tree) منتشر شد. به همین دلیل به این موتورها LSM storage engines می‌گن.
  • سگمنت‌ها تغییرناپذیر‌ن: یه‌بار نوشته می‌شن و بعد فقط خونده/ادغام/حذف می‌شن. compaction تو thread پس‌زمینه انجام می‌شه و خوندن‌ها هم‌زمان با ورودی‌های merge سرویس می‌گیرن. crash وسط نوشتن هم ساده‌ست: فایل ناتمام دور انداخته می‌شه و لاگ با checksum رکوردهای خراب رو کنار می‌ذاره (جزئیات تو فصل ۸). این فایل‌ها حتی رو object storage هم عالی‌ان (مثل SlateDB و Delta Lake).
  • Keep a file sorted by key. An SSTable, or Sorted Strings Table, contains sorted key-value pairs, with each key appearing once within that table.
  • A sparse index stores the first key and offset of each multi-kilobyte block. To find handiwork, the book uses the bounds handbag and handsome: jump to the relevant block, then search those kilobytes.
  • Compress blocks to save space and I/O bandwidth, at the cost of some CPU work.
  • But inserting into the middle of a sorted file would break simple appends. Rewriting the whole file for every write is too expensive. The log-structured approach stages the work instead.
  • A memtable accepts writes into a sorted in-memory map, such as a red–black tree, skip list or trie. It supports insertion, lookup and sorted iteration.
  • Flush: once it reaches a threshold, such as a few megabytes, write its sorted contents as a new SSTable. A fresh memtable accepts subsequent writes.
  • Reads: check memory, then the relevant segments from newest to oldest. Choose the newest visible value, including any deletion marker.
  • Merge and compaction: read sorted inputs together, as in mergesort. Write keys in order to a new segment and discard superseded values when they're no longer needed.
  • WAL: also record writes in a separate on-disk log so a crash doesn't lose changes held only in memory. After a durable flush, the matching part of the log can be retired.
  • Tombstones record deletes. They suppress older values until compaction can safely remove the covered data and its deletion marker.
  • RocksDB, Cassandra, ScyllaDB and HBase use this family of algorithms. The SSTable and memtable terms come from Bigtable; the LSM-tree, or Log-Structured Merge-tree, was published in 1996. These are LSM storage engines.
  • Segments are immutable: create them, then read, merge or delete them. Background compaction can write a new file while reads continue against the input files. Recovery discards incomplete output and checks the log for valid records; Chapter 8 covers the details. Immutable files also suit object-storage designs, such as SlateDB and Delta Lake.

۲.۲ Bloom filter و استراتژی compaction2.2 Bloom filters and compaction strategies

Bloom filter

پاسخِ «نیست» تو Bloom filter قطعیه و پاسخِ «شاید هست» بررسیِ واقعی می‌خواد. این فیلتر مقدارِ رکورد رو نگه نمی‌داره.

مثال فنی: شاید هست، قطعاً نیست

وضعیت اولیه: فرض کن برای یه SSTable، ـی Bloom filter می‌گه بیت لازم برای کلید P99 صفره. یعنی نیست.

اجرای مرحله‌به‌مرحله: حالا فایل برای P99 خونده نمی‌شه؛ ولی اگه همهٔ بیت‌ها یک باشن، فایل هنوز باید بررسی بشه. شاید هست، شاید نه.

نتیجه و دلیل: پس پاسخ مثبت می‌تونه کاذب باشه. فیلتر سالم برای مجموعهٔ ساخته‌شده پاسخ منفی کاذب نمی‌ده و جای بررسی داده رو نمی‌گیره — «نه» قطعیه، «شاید» مشکوکه.

  • برای هر سگمنت یه بیت‌آرایه؛ برای هر کلید چند تا هش حساب می‌شه و بیت‌های متناظر ۱ می‌شن.
  • موقع جست‌وجو: اگه حتی یه بیت ۰ بود، کلید قطعاً تو اون سگمنت نیست ← سگمنت رد می‌شه (بدون I/O).
  • اگه همه ۱ بودن، کلید احتمالاً هست — ولی ممکنه تصادفی باشه (false positive). اون‌وقت باید ایندکس پراکنده رو ببینی؛ اگه کلید نبود، فقط کمی کار بیهوده شده.
  • قاعدهٔ تجربی: حدود ۱۰ بیت به‌ازای هر کلید ← احتمال false positive حدود ۱٪؛ هر ۵ بیت اضافه، احتمال رو ده‌برابر کم می‌کنه.
  • Build a bit array for each segment. Hash each key several ways and set the corresponding bits to 1.
  • During lookup, one required bit at 0 means the key is definitely absent from that segment. Skip its data read.
  • If all required bits are 1, the key may be present. Other keys might have set the same bits, giving a false positive. Check the index and data to find out.
  • The chapter's rule of thumb is about 10 bits per key for a roughly 1% false-positive rate; another 5 bits per key reduces that rate by about a factor of 10. A positive filter result still isn't a record lookup.

دو استراتژی compactionThe two compaction strategies

  • Size-tiered: سگمنت‌های کوچیک و تازه با هم و بعد با سگمنت‌های بزرگ‌تر ادغام می‌شن (مثلاً چهار تا ۲۵۶MB ← یه ~۸۹۸MB؛ کمتر از ۱۰۲۴ چون حذف و overwrite و TTL جمع می‌شن). بازده نوشتن بالا، ولی فضای موقت زیاد و خوندن ممکنه چند تا سگمنت بزرگ رو بگرده.
  • Leveled: سگمنت‌ها اندازهٔ ثابت دارن و تو «سطح‌های» L0، L1، ... با محدودیت اندازهٔ فزاینده گروه‌بندی می‌شن؛ وقتی سطحی پر شد، به سطح بعدی ادغام می‌شه. فضای کمتر، ادغام تدریجی‌تر، و خوندن سریع‌تر (سگمنت‌های کمتری برای چک کردن).
  • قاعده: نوشتنِ غالب ← size-tiered؛ خوندنِ غالب ← leveled. خوشبختانه اکثر پیاده‌سازی‌ها هر دو رو دارن.
  • Size-tiered: merge similarly sized segments into larger ones. The chapter's example merges four 256MB files into about 898MB, rather than 1024MB, after removing overwritten, deleted or expired data. This favors write throughput but needs temporary space, and reads may check several large segments.
  • Leveled: organize fixed-size segments into levels L0, L1, … with growing capacity limits. Move and merge data as levels fill. More organized key ranges can reduce read and space costs, at the expense of additional rewriting.
  • Start the comparison with write-heavy versus read-heavy workloads: size-tiered often favors the former, leveled the latter. Many implementations offer both. Measure with the intended settings.

دامنهٔ تصور غلطCommon misconception

Bloom filter می‌تونه با قطعیت بگه یه کلید تو فایل نیست، ولی جواب مثبتش نیاز به بررسی داره. Compaction فایل‌ها رو ادغام می‌کنه؛ نوع ادغام روی هزینهٔ خوندن و نوشتن و فضا اثر داره.

مثال فنی: دو سیاست ادغام

وضعیت اولیه: فرض کن چهار تا فایل 100 MB داری که بعضی کلیدهاشون هم‌پوشانی داره.

اجرای مرحله‌به‌مرحله: حالا size-tiered می‌تونه فایل‌های هم‌اندازه رو ادغام کنه؛ leveled فایل‌ها رو تو سطح‌ها و بازه‌های منظم‌تر نگه می‌داره. دو تا سلیقه.

نتیجه و دلیل: پس اولی معمولاً فایل و فضای موقت بیشتری می‌خواد؛ دومی ممکنه بازنویسی بیشتری بسازه. نتیجه به بار و تنظیمات وابسته‌ست — برندهٔ ثابت نداریم.

An LSM doesn't always use less space. During size-tiered compaction, old inputs and new output coexist. Deleted values can remain physically present until compaction carries their tombstones through the relevant levels, so immediate logical deletion differs from final removal.

The same immutable files make snapshots inexpensive: retain the files for the required version rather than copying every byte.

موتورهای جاسازی‌شده (Embedded)Embedded engines

موتور جاسازی‌شده داخل فرایندِ خودِ برنامه اجرا می‌شه. برخلاف یه سرور پایگاه دادهٔ جدا، برنامه مستقیماً از کتابخانهٔ موتور برای ذخیره و خوندن استفاده می‌کنه.

مثال فنی: RocksDB داخل فرایند

وضعیت اولیه: فرض کن یه worker شمارندهٔ هر customer_id رو تو RocksDB رو دیسک محلی نگه می‌داره. تو جیب خودشه.

اجرای مرحله‌به‌مرحله: حالا فراخوانی کتابخونه بدون RPC شبکه انجام می‌شه؛ ولی برای بازیابی ماشین ازدست‌رفته، checkpoint یا changelog بیرونی لازمه.

نتیجه و دلیل: پس embedded بودن سربار شبکه رو کم می‌کنه؛ ولی به‌خودی‌خود replication یا backup سراسری نمی‌ده — سرعت داره، نجات نه.

  • همهٔ پایگاه داده‌ها سرویس شبکه‌ای نیستن: موتورهای embedded کتابخانه‌ان و تو همون process برنامه اجرا می‌شن (RocksDB، SQLite، LMDB، DuckDB، KùzuDB). رایج تو اپ‌های موبایل؛ تو بک‌اند وقتی داده رو یه ماشین جا بشه و تراکنش‌های هم‌زمان زیاد نباشن (مثلاً یه نمونه به‌ازای هر tenant کوچیک و مستقل).
  • An embedded engine is a library inside the application's process, rather than a separate network service. Examples include RocksDB, SQLite, LMDB, DuckDB and KüzuDB. This is common on mobile and can fit backend workloads whose data and concurrency requirements suit one machine, such as independent small tenants.

Calling the library avoids a database RPC. Protecting against losing the whole machine still needs an appropriate checkpoint, backup or replication design.

ساختار: صفحه‌ها، نه سگمنت‌هاAnatomy: pages, not segments

صفحه واحدی از داده‌ست که موتور از دیسک می‌خونه یا می‌نویسه. تو B-tree، هر صفحه چند تا کلید و اشاره‌گر داره؛ پس یه خوندن می‌تونه اطلاعات زیادی برای انتخاب مسیر بده.

مثال فنی: صفحهٔ ثابت، تغییر کوچک

وضعیت اولیه: فرض کن موتور فرضی صفحه‌های 8 KB داره و رکورد هدف تو یه صفحه‌ست.

اجرای مرحله‌به‌مرحله: حالا تغییر چند بایت ممکنه ثبت WAL و dirty شدن همون صفحه رو لازم کنه؛ flush با واحدهای صفحه انجام می‌شه. واحد کار صفحه‌ست، نه بایت.

نتیجه و دلیل: پس اندازهٔ تغییر برنامه لزوماً برابر بایت نوشته‌شده رو دیسک نیست. cache و WAL تو مسیر دخالت دارن — چیزی که می‌بینی با چیزی که نوشته می‌شه یکیه؟ نه!

  • برخلاف سگمنت‌های با اندازهٔ متغیر و تغییرناپذیرِ LSM، B-tree پایگاه داده رو به صفحات با اندازهٔ ثابت (page) می‌شکنه که می‌تونن درجا بازنویسی بشن. اندازهٔ سنتی ۴ کیلوبایته؛ PostgreSQL حالا ۸ کیلوبایته و MySQL به‌طور پیش‌فرض ۱۶ کیلوبایت.
  • هر صفحه شماره داره و صفحه‌ها با شماره به هم ارجاع می‌دن (مثل pointer، ولی رو دیسک). اگه همه تو یه فایل باشن، شماره × اندازهٔ صفحه = offset بایتی.
  • یه صفحه rootـه و هر جست‌وجو از همون شروع می‌شه. هر صفحهٔ داخلی چند تا کلید و ارجاع به فرزند داره و هر فرزند مسئول یه بازهٔ پیوسته از کلیدهاست؛ کلیدهای بین ارجاع‌ها مرز بازه‌ها رو مشخص می‌کنن. (گاهی B+ tree می‌نامنش.)
  • تعداد ارجاع‌های هر صفحه = branching factor؛ تو عمل چند صدتاییه. به‌همین‌دلیل عمق درخت همیشه ۳ تا ۴ سطح می‌مونه (درخت ۴ سطحی با صفحات ۴KB و عامل انشعاب ۵۰۰ تا ۲۵۰ ترابایت رو نگه می‌داره).
  • برگ‌ها (leaf page) کلیدهای تکی رو دارن: یا مقدار رو inline نگه می‌دارن یا ارجاع به جایی که مقدار هست.
  • A B-tree uses fixed-size pages that can be rewritten in place. Compare that with LSM's immutable, variable-size segments. The chapter gives traditional 4 KB pages, PostgreSQL's 8 KB pages and MySQL's 16 KB default.
  • Pages reference other pages by number. In a single-file layout, page number × page size gives the byte offset.
  • Lookups begin at the root. Each internal page holds boundary keys and child references. Each child covers a contiguous key range. The leaf-based arrangement is often called a B+ tree.
  • The number of child references is the branching factor, often in the hundreds. That's why large trees can be only 3–4 levels deep. The chapter illustrates a four-level tree with 4KB pages and branching factor 500 holding up to 250 TB.
  • Leaf pages contain individual keys, with either the value itself or a reference to its record.

  • To update an existing key, find its leaf and change the page. To insert a new key, find its range. If the page is full, split it into two roughly half-full pages and add their boundary to the parent.

نتیجه و دلیل: پس WAL امکان بازیابی تغییر تأییدشده رو می‌ده. تنظیمی که تأیید رو پیش از پایداری می‌ده تضمین ضعیف‌تری داره — اول بنویس، بعد قول بده.

  • عملیات پایهٔ B-tree بازنویسی یه صفحه درجاـه (برخلاف LSM که فقط append می‌کنه). بازنویسی چند تا صفحه (مثل split) خطرناکه: crash میونهٔ کار می‌تونه صفحهٔ یتیم یا صفحهٔ نیمه‌نوشته (torn page) بسازه.
  • راه‌حل استاندارد: write-ahead log (WAL) — فایلی فقط‌افزودنی که هر تغییر B-tree باید قبل از اعمال رو صفحات، توش نوشته بشه؛ بعد از crash، لاگ برای برگردوندن درخت به حالت سازگار بازپخش می‌شه. معادلش تو فایل‌سیستم‌ها journaling نام داره.
  • برای کارایی، صفحات تو حافظه بافر می‌شن؛ WAL تضمین می‌کنه تا وقتی داده با fsync رو دیسک رفته، بعد از crash قابل بازیابیه.
  • واریانت‌ها: copy-on-write (مثل LMDB — صفحهٔ تغییرکرده تو جای تازه نوشته می‌شه و والد جدید ساخته می‌شه؛ برای concurrency control هم مفیده)، کلیدهای مختصر تو صفحات داخلی (عامل انشعاب بیشتر، عمق کمتر)، چیدمان ترتیبی برگ‌ها رو دیسک برای اسکن سریع، و pointer خواهر/برادر بین برگ‌ها.
  • A B-tree normally updates existing pages in place. A crash during a multi-page split can leave broken links, orphaned pages or torn pages that were only partly written.
  • A write-ahead log (WAL) records the recovery information before the corresponding dirty pages are written durably. On restart, recovery uses it to restore a consistent tree. Filesystem journaling uses a related idea.
  • Buffering pages in memory avoids writing each small change immediately. For synchronous durability, the required log records must reach stable storage through fsync before success is promised.
  • Variants include copy-on-write, as in LMDB, which writes changed pages and their parents to new locations; abbreviated keys for a higher branching factor; sequential leaf layout for scans; and sibling pointers between leaves. The exact recovery design depends on the engine.

ولی «تو لاگ نوشتن» به‌تنهایی کافی نیست: تا وقتی fsync برنگشته، رکورد فقط تو کشِ سیستم‌عامله و یه crash ساده اون رو می‌بلعه. مرزِ واقعیِ ماندگاری (durability) لحظه‌ایه که fsync با موفقیت برمی‌گرده؛ بعدش حتی اگه صفحه هرگز رو دیسک نوشته نشه، ریکاوری می‌تونه با redo — بازپخشِ رو به جلوِ لاگ — همه‌چی رو برگردونه، البته به شرطی که این بازپخش idempotent باشه، چون ممکنه دوبار اجرا بشه.

Appending a record to the OS cache doesn't establish power-loss durability. In the synchronous path shown here, wait for fsync to complete successfully before promising the write is durable. Unsynced data may be lost.

After that successful fsync, the data page can still be waiting for its disk write. Recovery uses redo to replay the durable change. Make that replay idempotent, so repeating recovery doesn't apply the change twice.

مسیرِ اصلی رو قدم‌به‌قدم برو. از «Dirty Page» شروع کن: زیرنویسش «modified in memory» و برچسبِ کنارش «not on disk yet» — یعنی صفحه تو حافظه تغییر کرده ولی هنوز چیزی رو دیسک نیست. فلشِ «append to log» اون رو به «WAL Appended» می‌رسونه (زیرنویس: «log entry written first»، برچسب: «sequential write»). فلشِ بعدی «fsync»ـه و به «WAL Synced» می‌رسه — حالتِ لوزی‌شکلِ مسیر با زیرنویسِ «fsync returns» و برچسبِ «now durable» — و این همون مرزِ ماندگاریه. از اونجا فلشِ «later, in background» به «Page Written» می‌ره (زیرنویس: «update in place on disk»، برچسب: «random write») و سرانجام فلشِ «periodically» به «Checkpoint» می‌رسه (زیرنویس: «old log discarded»، برچسب: «restart is fast»).

Begin at Dirty Page, with modified in memory and not on disk yet. The page has changed in memory. Follow append to log to WAL Appended, tagged sequential write. Appending the record comes before writing the changed page to disk.

The fsync arrow reaches WAL Synced, tagged now durable. That's the synchronous durability boundary in this diagram. The later, in background route then reaches Page Written, with random write. Finally, periodically reaches Checkpoint, with old log discarded and restart is fast. A completed checkpoint limits what the next restart must replay.

حالا فلش‌های چین‌چینِ شکست. از «WAL Appended» فلشِ چین‌چینِ «crash before fsync» پایین میاد، به خطِ «Buffers and caches» و حالتِ «Unsynced Write» با زیرنویسِ «still in the OS cache» و برچسبِ «power loss loses it». از اونجا فلشِ «nothing to recover» به خطِ «Terminal» و حالتِ «Write Lost» می‌ره (زیرنویس: «never reached the disk»، برچسب: «rolled back»). این تنها مسیرِ بدونِ بازگشتِ شکله: تا قبل از fsync، یعنی تو دنیای کش‌ها، crash به معنی ازدست‌دادنِ همون نوشتنه.

The crash before fsync branch leaves WAL Appended for Unsynced Write. Its labels still in the OS cache and power loss loses it mark the risk: data held only in volatile caches can disappear when power is lost.

Follow nothing to recover to Write Lost, labelled rolled back. This is the diagram's lost-write path. Before fsync completes, that write hasn't received the synchronous durability guarantee.

سمتِ دیگهٔ مرز، بازیابیـه: از «WAL Synced» فلشِ چین‌چینِ «crash after fsync» پایین میاد به خطِ «Crash recovery» و حالتِ «Redo from WAL» با زیرنویسِ «roll forward on startup» و برچسبِ «idempotent replay»؛ بعد فلشِ پررنگِ «recovery completes» اون رو به همون «Checkpoint» برمی‌گردونه. دقت کن: مسیرِ بازیابی دقیقاً تو همون حالتی تموم می‌شه که مسیرِ عادی — یعنی هرچی با fsync ماندگار شده باشه، بعد از crash هم به مقصد می‌رسه.

On the other side of the boundary, crash after fsync reaches Redo from WAL. The labels roll forward on startup and idempotent replay describe replay on startup that remains safe if repeated.

The recovery completes arrow returns to Checkpoint. After a successful fsync, the durable log can carry the change through a later crash even if its data page never reached disk.

آخرین مسیرِ شکست از «Page Written» شروع می‌شه: فلشِ «crash mid-write» به حالتِ «Torn Write» تو خطِ «Terminal» می‌ره — زیرنویسِ «checksum mismatch» و برچسبِ «partial page on disk» — یعنی صفحه‌ای نیمه‌قدیمی و نیمه‌جدید که فقط checksum رو صفحه و بلاگِ لاگ می‌تونه آشکارش کنه. ولی این حالتِ پایانی نیست: فلشِ پررنگِ «rewrite from log» اون رو به «Redo from WAL» برمی‌گردونه و صفحه از روِ لاگِ ماندگار دوباره نوشته می‌شه.

From Page Written, follow crash mid-write to Torn Write. The labels checksum mismatch and partial page on disk describe an incomplete page. A checksum can detect corruption; detecting it and repairing it are separate jobs.

The rewrite from log route reaches Redo from WAL. It assumes the engine has retained the recovery information needed to rebuild the page from the durable log.

درسِ این ماشینِ وضعیت رو تو یه قانون جمع کن: «اول لاگ، بعد صفحه»؛ و مرزِ ماندگاری فقط لحظه‌ایه که fsync با موفقیت برمی‌گرده. نوشتنِ لاگ sequential و ارزونه، بازنویسیِ صفحه random و خطرناک؛ پس هرگز دومی رو بدونِ اولی شروع نکن.

Remember the durable ordering: log first, data page second. In this synchronous path, fsync establishes the log's durability. The log writes are sequential; the page writes can be random. Don't flush a changed page before its required log records are safe.

و چند تا نکته که باید بمونه: fsync همیشه راست نمی‌گه — بعضی سیستم‌عامل‌ها پیش از ماندگاریِ واقعی موفقیت گزارش کردن و بعضی SSDها تو تست‌های قطعِ برق دروغ گفتن — پس checksum رو هر صفحه و هر بلاگِ لاگ، فسادِ خاموش رو به خطایِ قابل‌تشخیص تبدیل می‌کنه. بازپخشِ لاگ باید idempotent باشه چون ممکنه دوبار اجرا بشه، و checkpoint هم حجمِ بازپخشِ ری‌استارت رو محدود می‌کنه و هم اجازه می‌ده سگمنت‌های قدیمیِ لاگ دور ریخته بشن. و یادت باشه WAL مخصوصِ B-tree نیست: موتورهای LSM برای بازیابیِ crash معمولاً بهش نیاز ندارن (چون memtable به‌صورت فایلِ مرتب flush می‌شه) و جایگزینِ کلاسیکِ اون، shadow paging با تعویضِ اتمیِ ریشه‌ست.

The guarantee also depends on the storage stack honoring fsync. The chapter describes operating-system and SSD power-cut tests where reported success didn't mean the expected data was safe. Use checksums to detect damaged pages and log blocks; checksums don't repair the data themselves.

Recovery must be idempotent, and checkpoints limit replay and let old log segments be removed safely. WAL isn't specific to B-trees: an LSM can use it to recover an unflushed memtable. Immutable SSTables protect completed files, while the log protects recent changes still in memory. Another design is shadow paging, using new pages and an atomic root switch.

On an HDD, scattered access requires mechanical head movement that takes milliseconds. Flash has a different constraint: reads and writes use pages, illustrated here as 4KB, while erases use larger blocks, illustrated as 512KB. Live pages must be moved before their block is erased.

That's garbage collection inside the device. Sequential writes can make reclamation simpler; scattered rewrites can increase copying, bandwidth use and wear. The effect depends on the device, free space and workload. An SSD removes the moving head, but not the cost of managing writes.

Don't stop an LSM benchmark while the database is still empty. Early writes may have little compaction to compete with. Run long enough for background merges and write amplification to reach the behavior you need to assess.

۵5نگه‌داشتن همه‌چیز در حافظهKeeping everything in memory

نگه‌داریِ داده تو حافظه خوندن رو سریع می‌کنه، ولی ماندگاری و بازیابی و ظرفیت همچنان مسئله‌ان. حافظهٔ اصلی با ذخیره‌سازیِ پایدار یکی نیست.

مثال فنی: حافظه و ماندگاری مستقل‌اند

وضعیت اولیه: فرض کن کل مجموعهٔ فعال 4 GBـه و تو RAM جا می‌شه. همه تو حافظه!

اجرای مرحله‌به‌مرحله: حالا خوندن از حافظه سریعه، ولی خاموشی RAM رو پاک می‌کنه. WAL پایدار یا replica طبق تضمین موردنیاز باید تغییرها رو حفظ کنه.

نتیجه و دلیل: پس in-memory بودن فقط محل اصلی خدمت‌دهی رو می‌گه. دربارهٔ دوام داده به‌تنهایی چیزی ثابت نمی‌کنه — سرعت داری، ولی دوام رو باید جدا بخری.

  • همهٔ ساختارهای این فصل پاسخی به نارسایی‌های دیسک بودن: دیسک با دو تا مزیتِ بزرگ تحمل می‌شه — پایداری (با قطع برق از بین نمی‌ره) و هزینهٔ هر گیگابایتِ کمتر از RAM.
  • با ارزون شدن RAM، خیلی از داده‌ها کوچیکن و کامل تو حافظه جا می‌شن ← پایگاه‌های داده درون‌حافظه‌ای. بعضی فقط cache‌ان (مثل Memcached — از دست رفتن داده با restart قبوله)؛ بعضی دوام می‌خوان: سخت‌افزار ویژه (RAM با باتری) یا متداول‌تر، نوشتن لاگ تغییرات/اسنپ‌شات دوره‌ای رو دیسک یا تکثیر وضعیت به ماشین‌های دیگه.
  • با وجود نوشتن رو دیسک، باز هم «درون‌حافظه‌ای» حساب می‌شن چون دیسک فقط لاگِ دوامه و خوندن کلاً از حافظه سرویس می‌شه. مزیت عملیاتی هم داره: فایل رو دیسک قابل backup و تحلیل با ابزار بیرونیه.
  • نمونه‌ها: VoltDB و SingleStore و Oracle TimesTen (رابطه‌ای، ادعای بهبود بزرگ با حذفِ سربارِ ساختارهای دیسکی)، RAMCloud (key-value با دوام و رویکرد log-structured)، Redis و Couchbase (دوام ضعیف، نوشتن ناهمزمان).
  • نکتهٔ ضدشهود: سرعتِ این پایگاه داده‌ها از «نخوندن از دیسک» نمیاد — موتور دیسکی هم با حافظهٔ کافی شاید هرگز به دیسک نزنه (cache سیستم‌عامل). علت واقعی، حذفِ سربارِ کدگذاریِ ساختارهای حافظه به قالبِ قابل‌نوشتن رو دیسکـه.
  • علاوه بر سرعت، مدل‌های دادهٔ غیرمتعارف رو هم راحت می‌کنن: مثلاً Redis رابطِ پایگاه داده‌مانند رو صفِ اولویت‌دار و مجموعه و ... می‌ده؛ چون همه‌چی تو حافظه‌ست، پیاده‌سازی این ساختارها ساده می‌مونه.

If the active data fits in RAM, memory can serve the reads. Durability is still a separate choice:

  • Disk offers persistent storage and a lower cost per gigabyte than RAM. Many structures here organize access around its costs.
  • An in-memory database keeps its working structures in RAM. A cache such as Memcached may accept losing its contents. A durable design can use battery-backed memory, a disk change log, periodic snapshots or replication to other machines, according to the required failure guarantee.
  • Writing a recovery log to disk doesn't change where reads are served. The engine can still be in-memory. Those files can also support backups and analysis outside the running process.
  • The chapter's examples include VoltDB, SingleStore and Oracle TimesTen for relational processing; RAMCloud for durable log-structured key-value storage; and Redis and Couchbase with asynchronous persistence examples. Check the selected mode before drawing a durability conclusion.
  • Speed isn't explained by “no disk reads” alone. A disk-based engine may serve cached data from RAM too. Avoiding conversion between in-memory structures and a disk-oriented format can remove additional work.
  • Keeping structures in memory also simplifies other models. Redis, for example, exposes sets and priority queues through a database interface.

ایده: ستون‌ها را کنار هم بچینThe idea: lay columns side by side

  • ذخیره‌سازی ستونی (columnar): به‌جای یه ردیف، همهٔ مقادیر هر ستون کنار هم ذخیره می‌شن؛ پس کوئری فقط ستون‌های استفاده‌شده رو می‌خونه و تجزیه می‌کنه.
  • بازسازی ردیف: چون همهٔ ستون‌ها ردیف‌ها رو به یه ترتیب نگه می‌دارن، مؤلفهٔ k امِ هر ستون = ردیفِ k ام.
  • در عمل کلِ ستونِ تریلیون‌ردیفی یه‌جا نیست: جدول به بلوک‌هایی از هزاران/میلیون‌ها ردیف شکسته می‌شه و چون کوئری‌ها معمولاً بازهٔ تاریخی دارن، هر بلوک معمولاً یه بازهٔ زمانیه. کوئری فقط بلوک‌های هم‌پوشانِ بازه و فقط ستون‌های لازم رو می‌خونه.
  • این چیدمان تقریباً تو همهٔ پایگاه‌های داده تحلیلیِ امروز هست: از Snowflake گرفته تا DuckDB و Pinot و Druid؛ فرمت‌های Parquet و ORC و Lance و Nimble و قالب‌های درون‌حافظه‌ای مثل Arrow و Pandas/NumPy؛ و بعضی پایگاه‌های داده سری زمانی (InfluxDB IOx، TimescaleDB). Parquet حتی مدل سندی رو هم پشتیبانی می‌کنه (تکنیک shredding از Dremel).
  • ستون‌ها رو می‌شه فشرده کرد؛ چون ستون‌ها معمولاً تکرارِ زیادی دارن (میلیاردها تراکنش، ۱۰۰ هزار محصولِ متمایز). روش شاخص: bitmap encoding — برای هر مقدارِ متمایز یه bitmap با یه بیت به‌ازای هر ردیف. bitmapهای تنک رو run-length encoding می‌کنن و روش‌هایی مثل roaring bitmaps بین دو نمایش، فشرده‌تر رو برمی‌گزینن.
  • Columnar storage groups values by column. A query can read and parse the columns it uses instead of every field in each row.
  • Columns share the same row order: element k in each column belongs to row k. That alignment lets the engine reconstruct rows.
  • A trillion-row column isn't stored as one indivisible unit. Tables are split into blocks covering thousands or millions of rows. A time-range query can skip non-overlapping blocks and read only the needed columns.
  • The chapter's examples include Snowflake, DuckDB, Pinot and Druid; Parquet, ORC, Lance and Nimble; memory layouts such as Arrow and Pandas/NumPy; and time-series systems such as InfluxDB IOx and TimescaleDB. Parquet also represents nested documents using Dremel-style shredding.
  • Similar values often compress well. Think of billions of sales with only 100k products. Bitmap encoding uses a bitmap per distinct value, with a bit per row. Run-length encoding compresses runs, while roaring bitmaps choose suitable representations for their data density.

Those systems use row-oriented access in the comparison here. The shared word “column” doesn't give them the same analytical scan behavior.

ترتیب مرتب‌سازی و نوشتنSort order and writes

ترتیب فیزیکی داده کمک می‌کنه بخش‌های نامربوط خونده نشن. ولی درج و به‌روزرسانیِ پراکنده تو فایل‌های مرتب هزینه داره و اغلب با بافر و ادغام مدیریت می‌شه.

مثال فنی: مرتب‌سازی و بلوک تازه

وضعیت اولیه: فرض کن بلوک‌های فروش بر اساس day مرتب‌ان و هر بلوک حداقل و حداکثر روز رو داره. قفسه‌بندی منظمه.

اجرای مرحله‌به‌مرحله: حالا فیلتر یه روز، بلوک‌های خارج از بازه رو رد می‌کنه؛ دادهٔ تازه اول جدا نوشته و بعد مرتب و ادغام می‌شه.

نتیجه و دلیل: پس sort order به data skipping کمک می‌کنه. ولی حفظ این نظم موقع نوشتن هزینه داره — نظم مجانی نیست.

  • ترتیبِ ردیف‌ها مهم نیست (ساده: همون ترتیب درج)، ولی می‌شه مرتب‌سازی انتخابی کرد و ازش به‌عنوان ایندکس بهره برد. نکته: ستون‌ها رو نمی‌شه مستقل مرتب کرد (ارتباط k ام‌ها می‌شکنه)؛ باید کلِ ردیف مرتب بشه هرچند ستونی ذخیره می‌شه.
  • کلیدِ مرتب‌سازی اول (مثلاً date_key) برای بازه‌های تاریخی؛ کلید دوم (مثلاً product_sk) برای گروه‌بندیِ درون همون روز. امتیاز جانبی: مرتب‌سازی، تکرارهای طولانی می‌سازه و فشرده‌سازیِ run-length رو حتی برای جدولِ میلیاردی چند کیلوبایتی می‌کنه (بیشترین اثر رو کلید اول).
  • نوشتن تو انبارداده معمولاً ورود دسته‌ای (ETL)ـه؛ درجِ تک‌ردیفی وسطِ جدولِ مرتب و فشرده خیلی ناکارآمده (باید از محل درج به بعد بازنویسی بشه). راه‌حل، باز هم رویکرد log-structured: نوشتن‌ها اول به یه فروشگاهِ ردیف‌محورِ مرتبِ درون‌حافظه‌ای می‌رن و بعد دسته‌ای با فایل‌های ستونیِ رو دیسک ادغام و تو فایل‌های تازه نوشته می‌شن؛ چون فایل‌ها تغییرناپذیرن، object storage جای خوبیه.
  • کوئری باید دادهٔ رو دیسک و نوشتن‌های اخیرِ درون حافظه رو با هم ببینه؛ موتور اجرا این تفکیک رو از کاربر پنهون می‌کنه. (Snowflake و Vertica و Pinot و Druid و ...)
  • You can keep insertion order, or sort rows to support likely filters. Don't sort each column independently: that would disconnect values belonging to the same row.
  • A first key such as date_key groups date ranges; a second such as product_sk groups products within a date. Sorting also creates long runs of equal values. For a suitable first-key column, run-length encoding can reduce even a billion repeated values to a few kilobytes; this isn't a promise for every column or whole table.
  • Warehouses commonly use batch ingestion (ETL). Inserting one row into the middle of a sorted, compressed file is expensive. A log-structured approach buffers fresh rows in memory and merges them into new columnar files in batches. Immutable output also fits object storage.
  • Queries still need a coherent view of both persisted files and recent buffered writes. The engine handles that split in designs such as Snowflake, Vertica, Pinot and Druid.

Setup: Sales blocks are ordered by day, and each block records its minimum and maximum day.

Walk through it: A one-day filter skips blocks outside that range. New data is written separately, then sorted and merged.

What this tells you: Sort order enables data skipping, but maintaining that order adds work to writes.

اجرای کوئری: تفسیر، کامپایل و برداریQuery execution: interpretation, compilation, vectorization

بعد از خوندن داده، روش اجرای محاسبه هم مهمه: اجرای برداری رو دسته‌ای از مقدارها کار می‌کنه و کامپایل، بخشی از منطق پرس‌وجو رو به کدِ اجرایی تبدیل می‌کنه.

مثال فنی: برداری در برابر کامپایل

وضعیت اولیه: فرض کن query باید یه میلیون مبلغ رو جمع کنه. یه میلیون!

اجرای مرحله‌به‌مرحله: حالا اجرای برداری دسته‌های مثلاً ۱۰۲۴تایی رو به عملگر می‌ده؛ کامپایل منطق query رو به کد اجرایی تخصصی تبدیل می‌کنه. دو تا ترفند جدا.

نتیجه و دلیل: پس یکی شکل پردازش دسته‌ای مقدارهاست و دیگری روش اجرای منطق. می‌شه هر دو رو هم‌زمان داشت — چرا یکیشون؟ هر دو!

  • کوئریِ تحلیلی به طرحی از operatorها شکسته می‌شه که ممکنه رو چند تا ماشین موازی بشن. ساده‌ترین اجرا «مفسر»ـه: تو حلقهٔ رو هر ردیف، ساختارِ کوئری چک می‌شه — برای تحلیلِ میلیون‌ردیفی کنده. دو تا رویکرد کارآمد:
  • Query compilation: موتور از SQL کد تولید می‌کنه (حلقهٔ ردیف‌ها، مقایسه‌ها، کپیِ مقادیر منطبق) و اون رو با کامپایلری مثل LLVM به کد ماشین تبدیل و اجرا می‌کنه — مشابه JIT تو JVM.
  • Vectorized processing: تفسیری می‌مونه، ولی به‌جای ردیف‌به‌ردیف، رو دسته‌ای از مقادیرِ یه ستون کار می‌کنه. مثال: اپراتور تساوی رو ستونِ product_sk و شناسهٔ «موز» یه bitmap برمی‌گردونه؛ همون اپراتور برای فروشگاه bitmap دوم؛ و اپراتور AND بیتی دو تا bitmap رو ترکیب می‌کنه (چون مؤلفهٔ k ام هر دو = همون ردیف).
  • هر دو از خصوصیات CPU امروزی بهره می‌برن: دسترسیِ ترتیبی به حافظه (cache miss کمتر)، حلقه‌های داخلیِ تنگ (pipeline شلوغ، پیش‌بینیِ شاخه کمتر)، موازی‌سازی با چند تا thread و دستورهای SIMD، و کار مستقیم رو دادهٔ فشرده بدون رمزگشایی.
  • An analytical plan consists of operators, which may run in parallel across machines. A simple interpreter can repeatedly inspect the query structure for every row. For a million-row scan, that adds up.
  • Query compilation: generate code for the query's loops, comparisons and result copying, then compile it with a tool such as LLVM. The idea resembles JIT in the JVM.
  • Vectorized processing: give an operator a batch of values. Comparing product_sk with the banana ID produces a bitmap. A store comparison produces another. A bitwise AND keeps rows matching both, since bit k refers to the same row in each bitmap.
  • Both approaches can use sequential memory access, tight loops, fewer branch mispredictions, threads and SIMD. Some operators can work directly on compressed values. Compilation and batching are separate choices and can be combined.

Example: Batching and compilation

Setup: A query sums a million amounts.

Walk through it: Vectorized execution can pass batches of, say, 1,024 values to an operator. Compilation turns query logic into specialized executable code.

What this tells you: One changes the unit of processing; the other changes how the logic executes. An engine can combine both.

نماهای materialized و مکعب داده (data cube)Materialized views and the data cube

نمای ازپیش‌حساب‌شده نتیجهٔ یه پرس‌وجو رو ذخیره می‌کنه. مکعب داده، خلاصه‌ها رو تو چند تا بُعد و سطح آماده می‌کنه؛ خوندن سریع‌تر می‌شه ولی نگه‌داریِ خلاصه‌ها هزینه داره.

مثال فنی: نمای آمادهٔ فروش روزانه

وضعیت اولیه: فرض کن sales_by_day برای امروز جمع 1000 داره و سفارش تازه مبلغ 200 داره.

اجرای مرحله‌به‌مرحله: حالا نگهدارندهٔ نما مقدار رو به 1200 می‌رسونه؛ اصلاح یا حذف همون سفارش هم باید تغییر معکوس مناسب اعمال کنه.

نتیجه و دلیل: پس خوندن گزارش سریع‌تر می‌شه. ولی هزینهٔ نگه‌داری نما و کنترل شمارش دوباره به مسیر تغییر منتقل می‌شه — خرج از جیب خوندن، از جیب نوشتن.

  • View مجازی فقط میان‌برِ نوشتن کوئریـه و موقع خوندن به کوئریِ زیرین باز می‌شه؛ view materialized یه کپیِ واقعی از نتیجهٔ کوئریه که رو دیسک نوشته می‌شه. وقتی دادهٔ زیرین عوض بشه باید به‌روز بشه (بعضی پایگاه داده‌ها خودکار؛ سیستم‌هایی مثل Materialize تو همین تخصصی‌ان). هزینه رو نوشتن، بهبود رو خوندنِ تکراری.
  • Materialized aggregate نوعی از اونه: اگه همون COUNT/SUM/AVG ها تکرار می‌شن، چرا هر بار دادهٔ خام رو نسابیم؟ مکعب داده (OLAP cube) شبکه‌ای از تجمیعهاست که بر اساس بُعدها گروه‌بندی شده: مثلاً تاریخ تو یه محور و محصول تو محور دیگه، و هر خونه = SUM برای اون ترکیب. جمع رو هر سطر/ستون = خلاصه‌ای با یه بُعد کمتر (فروش به‌تفکیک محصول، صرف‌نظر از تاریخ).
  • با ۵ تا بُعد (تاریخ و محصول و فروشگاه و تبلیغ و مشتری) تصور hypercube سخته ولی اصل همونه. مزیت: بعضی کوئری‌ها («فروش دیروز هر فروشگاه») عملاً از پیش حساب شدن. محدودیت: انعطافِ دادهٔ خام رو نداره — مثلاً نمی‌تونی بپرسی «سهمِ فروشِ اقلام بالای ۱۰۰ دلار چقدره» اگه قیمت بُعد نباشه. به‌همین‌دلیل انبارداده‌ها دادهٔ خام رو نگه می‌دارن و مکعب رو فقط تقویت‌کنندهٔ کارایی می‌دونن.
  • A virtual view is a saved query definition expanded when read. A materialized view stores the query's result. When source data changes, that result needs refreshing. Some databases maintain it automatically; Materialize specializes in this work. Repeated reads become cheaper because maintenance does work earlier.
  • A materialized aggregate prepares repeated COUNT, SUM or AVG calculations. A data cube (OLAP cube) organizes aggregates across dimensions. With date and product as axes, each cell can hold their sales SUM. Summing across an axis gives a less detailed total.
  • With 5 dimensions, such as date, product, store, campaign and customer, the idea remains the same. A query like yesterday's sales by store may already be prepared. But you can't derive the share from items over $100 if the aggregate discarded the price detail needed to answer it. Keep raw data for questions the cube can't answer.

What this tells you: Reports read a prepared total. Maintaining it and preventing duplicate counting become part of the change path.

جست‌وجوی عددی و مکانی و متنی و معنایی سؤال‌های متفاوتی‌ان. هرکدوم به ساختاری نیاز دارن که همون نوع شباهت یا محدوده رو سریع پیدا کنه.

B-trees and LSM support sorted ranges over one key order, such as names starting with L. A question involving several independent ranges needs a closer look at what that order can and can't narrow down.

ایندکس چندستونی و چندبُعدیMulti-column and multidimensional indexes

ایندکس چندستونی به ترتیبِ ستون‌ها حساسه. ایندکس مکانی برای داده‌هایی مثل مختصات ساخته می‌شه تا جست‌وجوی محدوده و همسایگی رو راحت کنه.

مثال فنی: ترتیبِ ستون‌های ایندکس

وضعیت اولیه: فرض کن ایندکس (city, created_at) اول شهر و تو هر شهر زمان رو مرتب می‌کنه. ترتیب آبشاری.

اجرای مرحله‌به‌مرحله: حالا شرط شهر تهران همراه بازهٔ زمان پیوسته‌ست؛ ولی بازهٔ زمان برای همهٔ شهرها ممکنه به چند بخش یا روش دیگه‌ای نیاز داشته باشه.

نتیجه و دلیل: پس یه B-tree چندستونی جای ایندکس هندسی برای همهٔ شرط‌های دوبعدی رو نمی‌گیره — آچار فرانسه برای همهٔ پیچ‌ها نیست.

  • Concatenated index: چند تا فیلد رو به هم می‌چسبونه و کلیدِ ترکیبی می‌سازه (مثل دفتر تلفن: (lastname, firstname)). با ترتیبِ مرتب‌سازی، برای «همه با فامیلیِ X» یا «X + نامِ Y» عالیه، ولی برای «همه با نامِ Y» بی‌فایده‌ست.
  • کوئری چندبُعدی: مثال رستوران‌ها رو نقشه — جست‌وجوی مستطیلِ دیدِ کاربر با طول و عرض جغرافیایی. ایندکسِ چسبونده‌شده نمی‌تونه هر دو بازه رو هم‌زمان بده (یا بازهٔ عرض تو همهٔ طول‌ها، یا بالعکس).
  • راه‌ها: تبدیل مکان به یه عدد با space-filling curve + B-tree معمولی؛ یا ایندکس‌های تخصصی مثل R-tree و Bkd-tree که فضا رو طوری تقسیم می‌کنن که نقاطِ نزدیک تو یه زیردرخت بیفتن (PostGIS از R-tree با امکانات GiST پست‌گرس استفاده می‌کنه)؛ یا شبکه‌های منظم مثلثی/مربعی/شش‌ضلعی.
  • کاربرد فقط جغرافیایی نیست: ایندکس سه‌بُعدی رو (قرمز، سبز، آبی) برای جست‌وجوی بازهٔ رنگ تو فروشگاه، یا دو‌بُعدی رو (تاریخ، دما) برای «مشاهداتِ یه سال با دمای ۲۵ تا ۳۰ درجه».
  • A concatenated index builds a composite key. Think of (lastname, firstname) in a phone book. It groups family name X, then first name Y within X. First name Y alone isn't one contiguous leading-key range.
  • A multidimensional query might ask for restaurants in a map rectangle, using latitude and longitude ranges. A composite key orders one coordinate before the other; it doesn't make every rectangle a single contiguous range.
  • Options include a space-filling curve plus an ordinary B-tree; R-trees and Bkd-trees, which partition space; or triangular, square and hexagonal grids. PostGIS uses spatial indexing through PostgreSQL's GiST.
  • The same problem appears outside maps: a 3-D (red, green, blue) color search, or a 2-D (date, temperature) query for one year's observations at 25–30 degrees.

Walk through it: A Tehran filter plus a time range forms a contiguous portion. A time range across all cities may need several ranges or another access method.

What this tells you: A composite B-tree doesn't replace a spatial index for every two-dimensional query.

جست‌وجوی متن (Full-Text Search)Full-text search

ایندکس معکوس برای هر واژه مشخص می‌کنه تو کدوم سندها اومده. جست‌وجوی متن می‌تونه علاوه بر حضور واژه، شکل واژه و رتبهٔ نتیجه رو هم در نظر بگیره.

مثال فنی: تقاطع فهرست اسناد

وضعیت اولیه: فرض کن فهرست سیب برابر [1,3,7] و قرمز برابر [3,5,7]ـه. دو تا لیست.

اجرای مرحله‌به‌مرحله: حالا اشتراک فهرست‌ها سندهای 3,7 رو می‌ده؛ ولی برای عبارت دقیق باید موقعیت واژه‌ها هم پشت‌سرهم باشه. همسایگی مهمه!

نتیجه و دلیل: پس داشتن هر دو واژه با داشتن عبارت «سیب قرمز» یکی نیست. ایندکس باید اطلاعات لازم همون سؤال رو نگه داره — سؤال رو بفهم، بعد ایندکس بساز.

  • جست‌وجوی متن یعنی یافتن اسنادی که کلیدواژه‌ای هرجای متن‌شون هست. تو هسته، هر واژه (term) یه بُعدـه: سندِ دارایِ term مقدار ۱ و بقیه ۰ — یه کوئریِ چندبُعدی با تعدادِ ابعادِ خیلی زیاد.
  • ساختار رایج: inverted index — نگاشت از term به فهرستِ شناسهٔ اسنادِ حاویِ اون (postings list). اگه شناسه‌ها ترتیبی باشن، postings رو می‌شه با bitmap پراکنده هم نمایش داد (بیتِ n ام = سندِ n).
  • «سیب‌های قرمز» = بارگذاریِ bitmap دو تا واژه و AND بیتی‌شون — حتی با run-length هم خیلی سریعه. Lucene (مغز Elasticsearch و Solr) همین‌طور کار می‌کنه: نگاشتِ term به postings تو فایل‌هایِ مرتبِ SSTable-مانند که با همون رویکرد log-structured تو پس‌زمینه ادغام می‌شن. نوعِ GIN تو PostgreSQL هم برای متن و JSON از postings استفاده می‌کنه.
  • به‌جای شکستن به واژه‌ها، می‌شه همهٔ زیررشته‌های طول n (n-gram؛ مثلاً trigram های hello = hel, ell, lld) رو ایندکس کرد: جست‌وجوی هر زیررشتهٔ حداقل سه‌حرفی و حتی regex — به بهای حجمِ زیاد ایندکس.
  • برای غلط تایپی: Lucene می‌تونه کلماتِ با فاصلهٔ ویرایشیِ مشخص (افزودن/حذف/جایگزینیِ یه حرف) رو بیابه؛ مجموعهٔ واژه‌ها رو به‌صورت ماشینِ حالتِ متناهی رو کاراکترها (مثل trie) نگه می‌داره و به Levenshtein automaton تبدیل می‌کنه.
  • پردازشِ زبانی (زبان‌های بدون فاصله و مترادف‌ها و صرف‌ها) تخصصِ جداگانه‌ایه و خارج از دامنهٔ کتابه.
  • A keyword query asks which documents contain a term. Think of each term as a dimension: 1 when it's present, 0 when absent. There can be a huge number of these dimensions.
  • An inverted index maps a term to document IDs, its postings list. With suitable IDs, a bitmap can represent the set: bit n refers to document n.
  • To find documents containing both “red” and “apples”, intersect the postings, or use bitwise AND on bitmaps. Exact phrase search also needs word positions. Lucene, used by Elasticsearch and Solr, stores term and postings structures with background log-structured merging. PostgreSQL's GIN also supports postings for text and JSON.
  • N-grams index length-n substrings instead of only words. For hello, overlapping trigrams include hel and ell. A query for lld wouldn't match that word: its final trigram is “llo”. Such indexes can narrow searches for 3+-character substrings and regex patterns, at the cost of a large index.
  • For spelling errors, Lucene supports edit distance: adding, removing or replacing letters. Its term representation uses finite-state structures, related to tries, and Levenshtein automata support the matching.
  • Language-specific work such as word boundaries, synonyms and inflections is a separate subject outside the book's scope.

Setup: The postings for سیب, meaning “apple”, are [1,3,7]. For قرمز, meaning “red”, they're [3,5,7].

Walk through it: Intersect them to get documents 3,7. An exact phrase match also requires the words to occur in adjacent positions.

What this tells you: Having both words isn't the same as containing “red apple” as a phrase. Keep the information the particular query needs.

جست‌وجوی معنایی و بردارهاSemantic search and vectors

  • جست‌وجوی معنایی (semantic search) فراتر از مترادف و غلط تایپیه، مفهومِ سند و نیتِ کاربر رو می‌فهمه؛ بخش مهمی از کاربردهای AI مثل RAG (افزودن نتیجهٔ جست‌وجو به خروجی مدل زبانی). مثال: صفحهٔ «لغو اشتراک» باید با جست‌وجوی «چطور حسابم رو ببندم» هم پیدا بشه.
  • مدلِ embedding، سند رو به برداری از اعداد اعشاری (vector embedding) تبدیل می‌کنه: نقطه‌ای تو فضای چندبُعدی. اسنادِ از نظر معنایی شبیه، بردارهای نزدیک می‌گیرن. مثال سه‌بُعدی کتاب: صفحهٔ کشاورزی [0.38, 0.83, 0.41]، صفحهٔ سبزیجات [0.36, 0.64, 0.67] (نزدیک)، صفحهٔ اسکیمای ستاره‌ای [0.85, 0.10, -0.52] (دور). مدل‌های واقعی بیش از ۱۰۰۰ تا عدد دارن و معنای تک‌تک اعداد مهم نیست؛ فقط مختصات تو فضای انتزاعی‌ان.
  • اندازه‌گیریِ فاصله: cosine similarity (کسینوسِ زاویهٔ دو تا بردار) یا Euclidean distance (فاصلهٔ خط مستقیم). مدل‌های اولیه (Word2Vec و BERT و GPT) متنی بودن؛ بعد ویدیو/صدا/تصویر اومد و حالا مدل‌های چندحالته (multimodal) یه مدل برای چند تا نوع داده‌ان.
  • موتور جست‌وجو، کوئری رو هم به بردار تبدیل می‌کنه و با vector index دنبال نزدیک‌ترین بردارها می‌گرده. R-tree برای ابعادِ زیاد خوب کار نمی‌کنه؛ ساختارهای تخصصی:
  • Flat: همه‌چی ابتدایی؛ هر بار مقایسه با همهٔ بردارها — دقیق ولی کند.
  • IVF (inverted file): فضا به خوشه‌ها (centroid) شکسته می‌شه و کوئری فقط چند تا خوشه (تعدادِ probes) رو می‌گرده؛ سریع‌تر ولی تقریبی (ممکنه سندِ نزدیک تو خوشهٔ دیگه‌ای افتاده باشه). probes بیشتر = دقت بیشتر، سرعت کمتر.
  • HNSW (Hierarchical Navigable Small World): چند تا لایه گرافِ مجاورت؛ کوئری از لایهٔ بالایی (گره‌های کم) شروع می‌کنه، نزدیک‌ترین رو می‌یابه، به همون گره تو لایهٔ پایین‌تر می‌ره و تو گرافِ متراکم‌تر ادامه می‌ده تا لایهٔ آخر. مثل IVF تقریبیه.
  • کتابخانه‌های Faiss (چند تا واریانت از هر دو) و pgvector تو PostgreSQL (هر دو) رایج‌ان؛ جزئیات الگوریتم‌ها تو مقاله‌هاشونه.
  • Semantic search looks for related meaning. A “cancel subscription” page may be relevant to “how do I close my account”. This is useful in RAG, where retrieved information is supplied to a language model.
  • An embedding model maps content to a vector of floats. In the book's 3-D illustration, farming is [0.38, 0.83, 0.41], vegetables is [0.36, 0.64, 0.67], and star schema is [0.85, 0.10, -0.52]. The first two are closer. Real examples can have 1000+ coordinates; those individual numbers don't have standalone human meanings.
  • Use a measure such as cosine similarity, based on the vectors' angle, or Euclidean distance, their straight-line distance. Word2Vec, BERT and GPT illustrate text representations; image, audio, video and multimodal models extend the idea. Vector closeness estimates similarity; it doesn't guarantee semantic correctness.
  • Embed the query too, then use a vector index to find nearby vectors. R-trees don't handle this many-dimensional setting well. Compare three approaches:
  • Flat: compare the query with every vector. It gives exact nearest neighbors under the chosen measure, but the work grows with the collection.
  • IVF (inverted file): group vectors around cluster centroids and probe selected clusters. Fewer probes reduce work but can miss a nearby vector in another cluster.
  • HNSW (Hierarchical Navigable Small World): search a layered proximity graph, beginning with a sparse upper layer and descending into denser layers. It also trades search work for recall.
  • Faiss and PostgreSQL's pgvector provide variants of these methods. Their algorithm papers cover the details.

Example: Approximate vector search

Setup: A query vector is near product P7, but the search explores only selected clusters or part of a graph.

Walk through it: IVF probes chosen clusters. HNSW follows graph neighbors. Exploring more generally takes more work.

What this tells you: The true nearest neighbor can be missed. Measure recall against exact search on a reference sample, together with the latency.

دو معنای «vector»Two meanings of “vector”

جست‌وجوی برداری، متن یا تصویر رو به یه بردار عددی تبدیل می‌کنه و همسایه‌های نزدیکش رو می‌یابه. نزدیکیِ بردار تخمینی از شباهته و لزوماً درستیِ معنایی رو تضمین نمی‌کنه.

مثال فنی: جست‌وجوی تقریبی بردار

وضعیت اولیه: فرض کن query برداری نزدیک به محصول P7ـه، ولی فقط چند تا خوشه یا بخشی از گراف بررسی می‌شه. نه همه جا!

اجرای مرحله‌به‌مرحله: حالا IVF خوشه‌های منتخب رو می‌کاوه؛ HNSW مسیر همسایه‌ها رو رو گراف طی می‌کنه. گسترش جست‌وجو معمولاً کار بیشتری می‌خواد.

نتیجه و دلیل: پس ممکنه نزدیک‌ترین همسایهٔ واقعی جا بمونه. recall باید با جست‌وجوی دقیق رو نمونهٔ مرجع سنجیده بشه — تقریب یعنی گاهی اشتباه، یادت باشه.

Keep the two meanings of “vector” separate. Vectorized processing in section 7 means operating on batches of values. A vector embedding is a numerical point representing content in a multidimensional space. Batching calculations and searching for similar content solve different problems.

Start the query at Parse & Route, with gRPC, async I/O and Tokio runtime. Its query vector reaches PQ Distance Scan, labelled probe nearest partitions and CPU runtime. That scan uses Compressed Index, connected through compressed codes and loaded at startup.

Next, 400 candidates for top-10 reaches Fragment Fetch, with coalesced 256 KiB reads and partition-pruned. It fetches the needed slices from Vector Fragments through byte-range reads and coalesced range reads, rather than reading every full-precision vector.

The full-precision vectors reach Re-rank Shortlist, labelled exact-distance re-rank and CPU runtime. Finally, ranked top-N reaches Serialize & Return, with top-N + metadata and ~500 ms at 1B. The approximate scan first narrows the candidates; exact-distance re-ranking then works only on that shortlist. It can't recover a neighbor the shortlist missed.

What this tells you: The saved read work comes with extra space and write maintenance. Even an unused index has a cost.

۳. چرا hash index به‌تنهایی کافی نیست؟3. Why isn’t a hash index enough on its own?

۵. نقش memtable و WAL در موتور LSM چیست؟5. What do the memtable and WAL do in an LSM engine?

Memtable تغییرهای تازه رو تو حافظهٔ مرتب جمع می‌کنه؛ WAL اطلاعاتِ لازم برای بازیابیِ اون‌ها رو نگه می‌داره. پس از پر شدن، داده به SSTable منتقل می‌شه.

وضعیت اولیه: فرض کن P7=100 تو SSTable قدیمیه و P7=120 تو memtable نوشته می‌شه. دو جا، دو نسخه.

اجرای مرحله‌به‌مرحله: حالا نوشتن WAL و حافظه رو به‌روز می‌کنه؛ flush فایل مرتب تازه می‌سازه و compaction نسخه‌های لازم رو ادغام می‌کنه.

نتیجه و دلیل: پس خواننده باید نسخهٔ قابل‌مشاهدهٔ تازه رو انتخاب کنه. پیدا شدن کلید تو یه فایل قدیمی برای توقف کافی نیست — تا تهش برو.

The memtable accepts fresh changes in a sorted in-memory map. A WAL retains the information needed to recover changes not yet flushed. When the memtable fills, it becomes an SSTable. Once that file is durable and recovery no longer needs the corresponding log section, the section can be retired.

Example: Newer values in an LSM

Setup: An old SSTable contains P7=100. A new write puts P7=120 into the memtable.

Walk through it: The write updates the WAL and memory. A flush creates a new sorted file; compaction merges versions and retains the ones still needed.

What this tells you: The reader must return the newest visible version. Finding the key in an old file isn't enough if newer state exists elsewhere.

۷. Bloom filter چطور کار می‌کند و false positive یعنی چه؟7. How does a Bloom filter work — what is a false positive?

برای کلید، چند تا موقعیتِ بیت علامت می‌خوره. اگه بیتِ لازم صفر باشه، کلید نیست؛ اگه همه یک باشن، شاید هست، چون کلیدهای دیگه هم همون بیت‌ها رو علامت زدن.

مثال فنی: شاید هست، قطعاً نیست

وضعیت اولیه: فرض کن برای یه SSTable، ـی Bloom filter می‌گه بیت لازم برای کلید P99 صفره. یعنی نیست.

اجرای مرحله‌به‌مرحله: حالا فایل برای P99 خونده نمی‌شه؛ ولی اگه همهٔ بیت‌ها یک باشن، فایل هنوز باید بررسی بشه. شاید هست، شاید نه.

نتیجه و دلیل: پس پاسخ مثبت می‌تونه کاذب باشه. فیلتر سالم برای مجموعهٔ ساخته‌شده پاسخ منفی کاذب نمی‌ده و جای بررسی داده رو نمی‌گیره — «نه» قطعیه، «شاید» مشکوکه.

Several hashes set positions in a bit array. One required 0 bit proves the key isn't in the set represented by a correctly built filter. All 1s mean “maybe”: another key may have set the same bits.

The chapter's approximation is 10 bits per key for about 1% false positives. In an LSM lookup, that false positive causes an extra check rather than an incorrect returned record. The filter doesn't store the value.

Example: Definitely absent, possibly present

Setup: A Bloom filter has a required bit at zero for key P99 in an SSTable.

Walk through it: Skip reading that file for P99. If all required bits were one, you'd still need to check the actual data.

What this tells you: A correctly built filter has no false negatives for its represented set, but positive answers can be false. It rules files out; it doesn't return records.

اجرای مرحله‌به‌مرحله: حالا size-tiered می‌تونه فایل‌های هم‌اندازه رو ادغام کنه؛ leveled فایل‌ها رو تو سطح‌ها و بازه‌های منظم‌تر نگه می‌داره. دو تا سلیقه.

نتیجه و دلیل: پس اولی معمولاً فایل و فضای موقت بیشتری می‌خواد؛ دومی ممکنه بازنویسی بیشتری بسازه. نتیجه به بار و تنظیمات وابسته‌ست — برندهٔ ثابت نداریم.

Size-tiered compaction merges similarly sized files, often favoring write throughput while keeping more runs and requiring temporary space. Leveled compaction organizes files into levels L0, L1, … with size limits and more controlled ranges. That can improve read and space costs but add rewriting.

Compare size-tiered for write-heavy traffic and leveled for read-heavy traffic as starting points. Workload and settings decide the actual result.

Example: Two merge policies

Walk through it: Size-tiered compaction can merge similarly sized files. Leveled compaction keeps files in more controlled levels and ranges.

What this tells you: The first often needs more temporary space and more files to check. The second may rewrite more data. Compare the workload and settings.

۹. tombstone چیست و چه چالشی دارد؟9. What is a tombstone, and its challenge?

Tombstone علامتِ حذفه تا خوندن و ادغام، نسخهٔ قدیمیِ رکورد رو دوباره زنده نکنن. حذفِ خودِ علامت فقط وقتی امنه که نسخه‌های پوشش‌داده‌شده دیگه برنگردن.

نتیجه و دلیل: پس پاک کردن زودهنگام tombstone می‌تونه مقدار قدیمی رو دوباره زنده کنه — مرده برمی‌گرده! عجله نکن.

A tombstone records deletion so reads and compaction don't expose an older value. Remove the marker only when the versions it suppresses can no longer reappear. Logical deletion can happen before those bytes are physically removed; a tombstone isn't proof of immediate final erasure.

۱۰. ساختار B-tree را در چند جمله توضیح بده.10. Explain the B-tree structure in a few sentences.

B-tree درختی از صفحه‌های دارای کلید و اشاره‌گره. هر سطح بازه رو محدود می‌کنه؛ برگ‌ها کلیدهای مرتب رو نگه می‌دارن و محلِ رکورد به طراحیِ موتور بستگی داره.

A B-tree consists of fixed-size pages, commonly illustrated here as 8–16 KB, linked by page references. The root and internal boundary keys narrow the range until you reach a leaf. A branching factor in the hundreds keeps large examples around 3–4 levels deep, with O(log n) depth. The engine decides whether leaves contain records or references to them.

۱۱. page split و WAL چه می‌کنند؟11. What do page splits and the WAL do?

Page split موقعِ پر شدنِ صفحه، اون رو تقسیم و راهنمای والد رو اصلاح می‌کنه. WAL تغییرهای لازم رو برای بازیابیِ امنِ ساختار و داده ثبت می‌کنه.

مثال فنی: Crash وسطِ split

وضعیت اولیه: فرض کن دو تا صفحهٔ تازه ساخته شدن، ولی به‌روزرسانی والد هنوز رو دیسک نرفته. نصفه کاره!

اجرای مرحله‌به‌مرحله: حالا رکوردهای بازیابی موتور مشخص می‌کنن split چطور تکمیل یا اصلاح بشه. صرف نوشتن جداگانهٔ چند صفحه کافی نیست.

نتیجه و دلیل: پس ساختار درخت هم باید پس از crash معتبر بمونه. ماندگاری فقط حفظ مقدار یه رکورد نیست — اسکلت هم باید سرپا بمونه.

A full page splits, and its parent gets the new routing boundary. A full parent can split too, reaching the root. Recovery must preserve a valid tree even if a crash interrupts those page changes. WAL records the required recovery information; with synchronous durability, fsync makes the needed log records safe before the corresponding dirty pages reach disk.

Example: A crash during a split

Walk through it: The engine uses its recovery records to complete or repair the split. Writing the pages separately isn't sufficient.

What this tells you: Recovery must restore a valid tree structure as well as record values. Keeping bytes is useful only if the keys remain reachable.

۱۲. مهم‌ترین تفاوت‌های B-tree و LSM چیست؟12. What are the key B-tree vs LSM differences?

B-tree معمولاً با مسیرِ صفحه‌ایِ مرتب می‌خونه؛ LSM تغییرها رو تو حافظه و فایل‌ها جمع و بعد ادغام می‌کنه. هزینهٔ نوشتن و خوندن و فضا و تأخیرِ پس‌زمینه به بار و پیاده‌سازی وابسته‌ست.

مثال فنی: بارِ نوشتن و خواندن

وضعیت اولیه: فرض کن بار A عمدتاً ورود رویداده؛ بار B عمدتاً lookup و تغییر رکوردهای کوچیکه. دو تا دنیای جدا.

اجرای مرحله‌به‌مرحله: حالا LSM نوشتن‌ها رو جمع می‌کنه و هزینهٔ compaction می‌ده؛ B-tree صفحه‌ها رو به‌روز می‌کنه و ساختار خوندن مرتب داره.

نتیجه و دلیل: پس انتخاب با اندازه‌گیری write/read/space amplification و tail latency رو همون بار انجام می‌شه. برندهٔ ثابت نداریم — اندازه بگیر، حدس نزن.

B-trees follow a short page path for point reads and sorted leaves for ranges. LSM gathers changes in memory and immutable files, then merges them. Reads may check several runs; range reads merge their ordered results.

Compare writes, space and latency too. LSM compression can save space, but old versions and compaction need room. B-tree pages can fragment. Snapshots and final deletion follow different paths. Measure the real workload instead of declaring a universal winner.

Example: Compare two workloads

Setup: Workload A mostly ingests events. Workload B mostly looks up and changes small records.

Walk through it: LSM buffers writes and later pays for compaction. A B-tree updates pages and keeps an ordered read path.

What this tells you: Measure read, write and space amplification, plus tail latency, on those workloads. Neither structure wins every comparison.

۱۳. write amplification چیست و چرا مهم است؟13. What is write amplification, and why does it matter?

افزایشِ نوشتن یعنی مقدارِ واقعیِ نوشته‌شده بر رسانه، از دادهٔ تازهٔ برنامه بیشتر باشه. لاگ و صفحه‌ها و ایندکس و ادغام تو این هزینه نقش دارن.

مثال فنی: حسابِ write amplification

اجرای مرحله‌به‌مرحله: حالا نسبت نوشتن واقعی به ورودی تو این اندازه‌گیری 6×ـه. دامنهٔ اندازه‌گیری، از جمله WAL، باید مشخص باشه — چی رو شمردی؟

نتیجه و دلیل: پس توان و عمر رسانه از بایت واقعی اثر می‌گیره. تنها نرخ دادهٔ ورودی کافی نیست — قبض رو بایت واقعی می‌ده.

In the simple B-tree illustration, a change is written at least 2× through WAL and page writes, sometimes rewriting a whole page for a few bytes. LSM writes through WAL, flush and repeated compaction. Those physical bytes affect bandwidth and SSD wear. Run benchmarks long enough to include background work.

Walk through it: The measured ratio is 6×. State the measurement scope, including whether WAL is counted.

What this tells you: Bandwidth and media wear depend on physical bytes written. The input rate alone doesn't capture that cost.

۱۴. چرا SSD هم برای نوشتن ترتیبی سریع‌تر است؟14. Why are sequential writes faster even on SSDs?

فلش واحدهای خوندن و نوشتن و پاک‌کردنِ متفاوت داره و کنترل‌کننده داده رو جابه‌جا می‌کنه. نوشتنِ ترتیبی می‌تونه کارِ مدیریتِ رسانه رو کمتر کنه، ولی اثرش به دستگاه و بار وابسته‌ست.

مثال فنی: چرا نوشتن SSD رایگان نیست؟

وضعیت اولیه: فرض کن برنامه بلوک‌های کوچیک و پراکنده رو مرتب بازنویسی می‌کنه. ریزریز و همه جا!

اجرای مرحله‌به‌مرحله: حالا کنترل‌کننده برای پاک‌سازی بلوک‌های بزرگ‌تر ممکنه دادهٔ زنده رو جابه‌جا کنه. نوشتن منظم می‌تونه این فشار رو کم کنه.

نتیجه و دلیل: پس اثر به دستگاه و فضای آزاد و بار بستگی داره. SSD داشتن هزینهٔ garbage collection و write amplification رو حذف نمی‌کنه — SSD جادو نیست، یادت باشه.

Flash can erase a larger block, such as the chapter's 512KB example, only after its live pages are preserved elsewhere. That relocation is garbage collection. Sequential writes can reduce the device's management work; scattered rewrites can increase copying and wear. The result depends on the device, available space and workload. SSD doesn't mean writes have no cost.

Example: SSDs still have write costs

Setup: An application repeatedly rewrites small, scattered blocks.

Walk through it: To erase larger blocks, the controller may need to move live data. A more sequential pattern can reduce that pressure.

What this tells you: The effect depends on the device, free space and load. An SSD still performs garbage collection and can amplify writes.

۱۵. clustered index، heap file و covering index چه تفاوتی دارند؟15. How do clustered, heap and covering indexes differ?

تو ایندکسِ خوشه‌ای، داده با نظمِ ایندکس نگه‌داری می‌شه؛ تو heap، ایندکس محلِ رکورد رو معرفی می‌کنه. ایندکسِ پوشاننده فیلدهای لازمِ پرس‌وجو رو هم داره.

مثال فنی: رکورد پشت ایندکس کجاست؟

اجرای مرحله‌به‌مرحله: حالا تو heap، ایندکس می‌تونه محل ردیف رو بده؛ تو الگوی clustered، داده با ترتیب کلید خوشه‌ای نگه داشته می‌شه؛ covering index خود مبلغ لازم رو هم داره. سه تا راه جدا.

نتیجه و دلیل: پس تعداد مراجعه‌ها و هزینهٔ تغییر رکورد فرق داره. معنای دقیق clustered و سازمان صفحه‌ها رو باید تو همون موتور بررسی کرد — اسم مشترک، رفتار مشترک نیست.

A clustered layout keeps rows in the index's key order, as with an InnoDB primary key. A heap layout stores records separately and uses the index to locate them, as in PostgreSQL. Extra fields cost space and maintenance; check the engine's exact layout and access rules.

What this tells you: The number of accesses and update costs differ. Check the engine's exact clustered layout and page organization.

۱۶. چرا ذخیره‌سازی ستونی برای تحلیل بهتر است؟16. Why is columnar storage better for analytics?

تحلیل اغلب تعدادِ زیادی ردیف ولی چند تا ستون رو می‌خواد. چیدمانِ ستونی خوندنِ بخشِ لازم و فشرده‌سازیِ مقدارهای مشابه رو راحت می‌کنه.

مثال فنی: فقط مبلغ‌ها را بخوان

نتیجه و دلیل: پس سود از کمتر خوندن میاد. اگه query همهٔ ستون‌های یه ردیف رو بخواد، همین مزیت الزاماً برقرار نیست — معجزهٔ همیشگی نداریم.

An analytical query may need only 3–5 of a table's 100+ columns. Columnar storage can read just those columns. Similar values compress well with methods such as bitmap and RLE encoding; sorting complete rows builds longer runs. Filter bitmaps can combine with AND/OR, and operators can process batches. Retrieving one complete row has a different access pattern.

Column-oriented روشِ چیدنِ فیزیکیِ داده برای خوندنِ ستون‌هاست. Wide-column یه مدلِ داده برای ردیف‌ها و خانواده‌های ستونه؛ شباهتِ اسم به‌معنی رفتارِ یکسان نیست.

۱۸. تفاوت query compilation و vectorized processing؟18. Query compilation vs vectorized processing?

کامپایلِ پرس‌وجو بخشی از منطق رو به کدِ اجرایی تبدیل می‌کنه. پردازشِ برداری عملیات رو رو دسته‌ای از مقدارها انجام می‌ده؛ این دو تا روش می‌تونن کنارِ هم استفاده بشن.

مثال فنی: برداری در برابر کامپایل

وضعیت اولیه: فرض کن query باید یه میلیون مبلغ رو جمع کنه. یه میلیون!

نتیجه و دلیل: پس یکی شکل پردازش دسته‌ای مقدارهاست و دیگری روش اجرای منطق. می‌شه هر دو رو هم‌زمان داشت — چرا یکیشون؟ هر دو!

Compilation turns query logic into executable code, using tools such as LLVM, similar to JIT. Vectorized execution gives operators batches of values. An equality test can produce a bitmap, then bitwise AND combines filters.

The two choices can work together. Both can benefit from sequential memory access, tight loops, SIMD and operations on compressed data.

What this tells you: One changes the unit of processing; the other changes how the logic executes. An engine can combine both.

۱۹. inverted index چیست و چطور «سیب قرمز» را جواب می‌دهد؟19. What is an inverted index — how does it answer “red apples”?

ایندکسِ معکوس هر واژه رو به سندهای دارای اون وصل می‌کنه. برای وجودِ هر دو تا واژه، فهرست‌ها مشترک‌گیری می‌شن؛ برای عبارتِ دقیق، موقعیتِ واژه‌ها هم لازمه.

مثال فنی: تقاطع فهرست اسناد

وضعیت اولیه: فرض کن فهرست سیب برابر [1,3,7] و قرمز برابر [3,5,7]ـه. دو تا لیست.

اجرای مرحله‌به‌مرحله: حالا اشتراک فهرست‌ها سندهای 3,7 رو می‌ده؛ ولی برای عبارت دقیق باید موقعیت واژه‌ها هم پشت‌سرهم باشه. همسایگی مهمه!

نتیجه و دلیل: پس داشتن هر دو واژه با داشتن عبارت «سیب قرمز» یکی نیست. ایندکس باید اطلاعات لازم همون سؤال رو نگه داره — سؤال رو بفهم، بعد ایندکس بساز.

اجرای مرحله‌به‌مرحله: حالا IVF خوشه‌های منتخب رو می‌کاوه؛ HNSW مسیر همسایه‌ها رو رو گراف طی می‌کنه. گسترش جست‌وجو معمولاً کار بیشتری می‌خواد.

نتیجه و دلیل: پس ممکنه نزدیک‌ترین همسایهٔ واقعی جا بمونه. recall باید با جست‌وجوی دقیق رو نمونهٔ مرجع سنجیده بشه — تقریب یعنی گاهی اشتباه، یادت باشه.

Flat search compares every vector and finds exact neighbors under the chosen measure. IVF probes selected clusters; HNSW follows a layered proximity graph from sparse upper layers toward the denser base.

IVF and HNSW are approximate: either may miss the true nearest result. Increasing probes or graph search effort usually improves recall while increasing work. Measure recall against an exact reference alongside latency.

Example: Approximate vector search

Setup: A query vector is near product P7, but the search explores only selected clusters or part of a graph.

Walk through it: IVF probes chosen clusters. HNSW follows graph neighbors. Exploring more generally takes more work.

What this tells you: The true nearest neighbor can be missed. Measure recall against exact search on a reference sample, together with the latency.

۹.۳ اشتباهات رایج در جواب‌های مصاحبه9.3 Common interview mistakes

  • قاطی کردنِ «NoSQL با LSM» و «SQL با B-tree» — موتور ذخیره‌سازی از مدل داده جداست؛ موتورهای رابطه‌ای با ساختارهای گوناگون هم میان.
  • فکر کردن به Bloom filter به‌عنوان جوابِ قطعی؛ ماهیتش تقریبیه (false positive) و فقط «نیست» گفتنش قطعیه.
  • نادیده گرفتن هزینهٔ ایندکس رو نوشتن؛ تعریفِ چند تا ایندکس بدون فکر به الگوی نوشتن، بازده نوشتن رو خفه می‌کنه.
  • قضاوت مطلق دربارهٔ «B-tree بهتره یا LSM»؛ بدون بارکاریِ مشخص و بنچ‌مارکِ طولانی (با compaction واقعی) ادعایی نمی‌شه کرد.
  • قاطی کردنِ column-oriented با wide-column، یا vectorized processing با vector embedding.
  • دونستنِ IVF و HNSW به‌عنوان جست‌وجوی دقیق؛ هر دو تقریبی‌ان و recall رو با latency مبادله می‌کنن.
  • یاد رفتن این‌که range query از Bloom filter بهره‌ای نمی‌بره و تو LSM گرون‌تر از نقطه‌ایه.
  • توضیح ندادنِ مسئلهٔ write amplification وقتی از بازده نوشتنِ LSM حرف می‌زنی.
  • Equating NoSQL with LSM and SQL with B-trees. The data model and storage engine are separate choices.
  • Accepting a Bloom filter's positive answer as proof. Only its negative answer rules out the key; “maybe” requires a lookup.
  • Adding indexes without counting their write and space costs.
  • Declaring B-trees or LSM universally better without a concrete workload and a benchmark that includes compaction.
  • Confusing column-oriented with wide-column, or batch-based vectorized processing with vector embeddings.
  • Calling IVF or HNSW exact. Explain recall as well as latency.
  • Applying the point-key Bloom filter shortcut to an arbitrary range scan. LSM ranges still need sorted-run merging.
  • Discussing LSM write throughput without write amplification, background work or tail latency.

۹.۴ چک‌لیست مرور ۵ دقیقه‌ای قبل از مصاحبه9.4 Five-minute pre-interview checklist

  • تریدآفِ اصلیِ ایندکس: خوندن سریع‌تر / نوشتن کندتر / فضای بیشتر.
  • مسیر نوشتن و خوندن تو LSM رو از حفظ بگو: WAL → memtable → flush → سگمنت‌ها → compaction؛ و جست‌وجو: memtable → جدید به قدیم + Bloom filter.
  • ساختار B-tree و دلیل WAL و page split رو تو ۳ جمله.
  • سه تا تفاوتِ محوریِ B-tree و LSM (خوندن/نوشتن/فضا) + مفهوم write amplification.
  • سه تا الگوی جا دادن رکورد (clustered و heap و covering) و یه جمله دربارهٔ ستونی: column pruning و bitmap.
  • ایندکس‌های پیشرفته تو یه جمله هرکدوم: R-tree و inverted index و IVF/HNSW — و یادآوریِ «تقریبی» بودنِ برداری‌ها.
  1. Explain the index trade-off: faster reads, extra writes and more space.
  2. Trace LSM writes through WAL, memtable, flush, segments and compaction. Trace reads through memory, relevant files, Bloom filters and data blocks.
  3. Describe B-tree pages, splits and WAL recovery in three sentences.
  4. Compare B-tree and LSM read, write and space costs, including write amplification.
  5. Explain clustered, heap and covering layouts. Describe column pruning and bitmaps for analytical scans.
  6. Explain R-trees, inverted indexes and IVF/HNSW in one sentence each. Keep the approximate-search caveat attached to the vector methods.

الگوی /appl./ دو trigram ثابت app و ppl داره. اشتراک postingها فقط نامزد می‌سازه و regex نتیجه رو تأیید می‌کنه. recall@k هم با exact top-k مقایسه می‌شه.Here's the thing — the pattern /appl./ carries two fixed trigrams, app and ppl. قضیه اینه که قراره جست‌وجوی محصول بسازی: inverted index، فیلتر و vector index. برای red AND apples بگو اشتراک postings چطور کار می‌کنه. برای regex مثل /appl./ اول با trigram ثابت app و ppl فقط نامزد جمع کن، بعد خود regex رو روی نامزدها چک کن. توی IVF با nprobe=1، عدد recall@k رو نسبت به exact top-k و p95 latency بسنج. آخرش hybrid ranking و جداسازی tenant رو هم حساب کن.Here's the thing, friend — you're building product search with an inverted index, filters, and a vector index.
